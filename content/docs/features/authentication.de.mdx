LibreChat verfügt über ein Benutzerauthentifizierungssystem, das es Benutzern ermöglicht, sich sicher und einfach zu registrieren und anzumelden. Das System ist skalierbar und kann eine große Anzahl gleichzeitiger Benutzer verarbeiten, ohne die Leistung oder Sicherheit zu beeinträchtigen.

Standardmäßig sind die E-Mail-Registrierung und -Anmeldung aktiviert, was bedeutet, dass Benutzer ein Konto mit ihrer E-Mail-Adresse und einem Passwort erstellen können. Sie können ihr Passwort auch zurücksetzen, falls sie es vergessen haben.

Zusätzlich kann unser System Social Logins von verschiedenen Plattformen wie Google, GitHub, Discord, OpenID und weiteren integrieren. Dies bedeutet, dass Benutzer sich mit ihren bestehenden Konten auf diesen Plattformen anmelden können, ohne ein neues Konto erstellen oder sich ein weiteres Passwort merken zu müssen.

**Weitere Details finden Sie in den hier bereitgestellten Konfigurationsanleitungen: [Authentifizierung](/docs/configuration/authentication)**

<Callout type="warning" title="Wichtig">
- Wenn Sie zum ersten Mal eine nicht bereichsbezogene Single-Tenant-Bereitstellung ausführen, erstellen Sie ein Konto, indem Sie auf der Anmeldeseite auf **Sign up** klicken. Dieses erste Konto wird zum Administrator und verfügt über alle administrativen Funktionen auf der Instanz. Tenant-bezogene Bereitstellungen stufen ihren ersten registrierten Benutzer nicht automatisch hoch; stellen Sie Tenant-Administratoren über einen vertrauenswürdigen administrativen Prozess bereit. Siehe [Access Control](/docs/features/access_control) für das vollständige Autorisierungsmodell, das Benutzer, Gruppen, Rollen, Ressourcen-ACLs und Administratorrechte auf Systemebene abdeckt.
- Für eine nicht-bereichsgebundene Single-Tenant-Bereitstellung sollte das erste Konto idealerweise ein lokales Konto (E-Mail und Passwort) sein.
</Callout>

**Siehe auch:** [Access Control](/docs/features/access_control), das granulare Berechtigungssystem von LibreChat für Benutzer, Gruppen und Rollen, das die ressourcenbezogene Freigabe von Agents, Prompts, MCP Servern und Berechtigungen auf Funktionsebene abdeckt.

## Zwei-Faktor-Authentifizierung [#two-factor-authentication]

Lokale und LDAP-Konten können unter **Settings > Account > Two-factor authentication** einen zweiten Faktor (einen Einmalcode von einer Authenticator-App sowie Backup-Codes) hinzufügen. Konten, die sich über einen Identitätsanbieter (OAuth, OpenID Connect, SAML) anmelden, verwenden stattdessen die MFA dieses Anbieters.

Administratoren können 2FA mit `ENFORCE_TWO_FACTOR_AUTHENTICATION=true` verpflichtend machen. Benutzer ohne 2FA sehen nach der Anmeldung dann einen Bildschirm mit der Meldung **Two-Factor Authentication Required** und müssen die Einrichtung abschließen, bevor sie LibreChat nutzen können. Sobald dies erzwungen wird, zeigt das Deaktivierungs-Steuerelement **Required by administrator** an und 2FA kann nicht ausgeschaltet werden. Siehe [Required Two-Factor Authentication](/docs/configuration/authentication#required-two-factor-authentication).

## Passkeys [#passkeys]

Wenn ein Administrator sie aktiviert, können sich Benutzer mit lokalem Konto anstelle eines Passworts mit **Mit Passkey anmelden** anmelden, indem sie die Bildschirmsperre ihres Geräts, einen Passwort-Manager oder einen Sicherheitsschlüssel verwenden. Passkeys werden unter **Einstellungen > Konto > Passkeys** hinzugefügt und entfernt; beide Aktionen erfordern zuerst die Eingabe des Kontopassworts. Wenn für das Konto zusätzlich 2FA aktiviert ist, wird der Code auch nach einer Anmeldung mit Passkey abgefragt. Siehe [Passkeys](/docs/configuration/authentication/passkeys) für die Einrichtung.

## Ändern Ihrer E-Mail-Adresse [#changing-your-email-address]

Benutzer mit lokalem Konto können ihre registrierte E-Mail-Adresse unter **Settings > Account > Email address** ändern, indem sie **Change** auswählen. Geben Sie im Dialog **Change email address** die neue E-Mail-Adresse sowie das aktuelle Passwort ein und wählen Sie anschließend **Send verification link**.

- Die Änderung tritt erst in Kraft, nachdem der an die **neue** Adresse gesendete Link geöffnet wurde. Der Link ist nur einmal verwendbar und läuft standardmäßig nach 15 Minuten ab.
- Die **aktuelle** Adresse erhält eine Sicherheitsbenachrichtigung, sobald eine Änderung angefordert wird. Nachdem die Änderung bestätigt wurde, erhalten beide Adressen eine Benachrichtigung über die „E-Mail-Änderung“.
- Die neue Adresse darf nicht zu einem anderen Konto gehören und muss, falls festgelegt, in den für die Bereitstellung zulässigen Registrierungsdomänen liegen.
- Das Ändern Ihres Passworts vor dem Öffnen des Links macht den Link ungültig; fordern Sie einen neuen an.

Die Option erscheint nur, wenn der Server E-Mails senden kann und die Funktion aktiviert ist. Siehe [E-Mail-Adressänderung](/docs/configuration/authentication/email#email-address-change).

## Limits für 2FA-Verwaltungsversuche [#2fa-management-attempt-limits]

Die Einstellungen für die Zwei-Faktor-Authentifizierung teilen sich ein kontoweites Limit für Versuche: standardmäßig **7 Anfragen pro 5 Minuten**, was das Aktivieren, Verifizieren, Bestätigen, Deaktivieren und das Neuerstellen von Backup-Codes umfasst. Erfolgreiche Anfragen verbrauchen ebenfalls Versuche. Das Öffnen einer neuen Sitzung schafft kein weiteres Limit für denselben Mandanten (Tenant) und dasselbe Konto.

Wenn das Budget erschöpft ist, gibt LibreChat einen HTTP `429` zurück, bevor der Faktor überprüft oder Kontoeinstellungen geändert werden. Die Einstellungs-UI erklärt, wann Sie es erneut versuchen können, indem sie den `Retry-After`-Wert des Servers verwendet, oder zeigt eine allgemeine Nachricht zum Warten und erneuten Versuchen an, wenn dieser Header nicht verfügbar ist. Warten Sie, bevor Sie erneut senden; eine gedrosselte Anfrage bedeutet nicht, dass Ihr Code überprüft und als ungültig befunden wurde. Die separate 2FA-Abfrage während der Anmeldung behält ihr bestehendes Anmelde-Limit bei.

Administratoren können [`rateLimits.twoFactorManagement.requestsPerFiveMinutes`](/docs/configuration/librechat_yaml/object_structure/config#ratelimits) in der deployment YAML anpassen. Es akzeptiert eine Ganzzahl von mindestens `3`, was die Einrichtungssequenz mit drei Aufrufen ermöglicht. Das Limit kann nicht mit `0` deaktiviert werden. Multi-Prozess-Deployments benötigen ein gemeinsam genutztes Redis für ein deployment-weites Budget; ohne Redis zählt jeder API-Prozess seine eigenen Anfragen.

## Angemeldet bleiben [#staying-signed-in]

Die Nutzung von LibreChat erfordert ein Konto. Es gibt keinen anonymen oder Gast-Modus für Chats, daher können Sie keine Unterhaltung ohne Anmeldung beginnen. Die einzige Ausnahme ist das Betrachten: Wenn ein Administrator `ALLOW_SHARED_LINKS_PUBLIC=true` festlegt, kann jeder, der einen [shared link](/docs/features/shareable_links) besitzt, diese Unterhaltung ohne Konto lesen. Sie können sie jedoch nur lesen.

Zwei Einstellungen bestimmen, wie lange eine Sitzung dauert, und beide sind konfigurierbar:

- `SESSION_EXPIRY`: wie lange ein Zugriffstoken gültig bleibt. Standardwert sind **15 Minuten**.
- `REFRESH_TOKEN_EXPIRY`: wie lange Sie insgesamt angemeldet bleiben. Standardwert ist **7 Tage**.

Das kurze Zugriffstoken wird im Hintergrund automatisch erneuert, während Sie LibreChat verwenden. Die 15-Minuten-Angabe bezieht sich also nicht darauf, wie oft Sie aufgefordert werden, sich erneut anzumelden. Wenn Sie abgemeldet werden, bedeutet dies normalerweise, dass das Aktualisierungstoken (Refresh Token) das Ende seines Zeitfensters erreicht hat oder der Browser das Aktualisierungs-Cookie verworfen hat.

Jede Erneuerung gibt zwar einen neuen Refresh-Token zurück, dieser ist jedoch für dieselbe Sitzung signiert und übernimmt das ursprüngliche Ablaufdatum dieser Sitzung. `REFRESH_TOKEN_EXPIRY` wird daher ab dem Zeitpunkt der Anmeldung gemessen, nicht ab der letzten Aktivität: Aktiv zu bleiben verlängert die Dauer nicht, und Sie werden abgemeldet, sobald das Zeitfenster abgelaufen ist.

Wenn Sie früher als erwartet abgemeldet werden, erhöhen Sie `REFRESH_TOKEN_EXPIRY`. Beide Variablen sind in der [.env Referenz](/docs/configuration/dotenv) dokumentiert.

<Callout type="info" title="Die Wiederverwendung von OpenID-Tokens ändert die Inhaberschaft der Sitzung">

Alles oben Genannte beschreibt Refresh-Tokens, die LibreChat selbst ausstellt. Mit [`OPENID_REUSE_TOKENS=true`](/docs/configuration/authentication/OAuth2-OIDC/token-reuse) enthält das Cookie stattdessen das Refresh-Token Ihres OpenID-Anbieters, sodass die Lebensdauer-, Rotations- und Widerrufsrichtlinien dieses Anbieters bestimmen, wann die Sitzung endet. `REFRESH_TOKEN_EXPIRY` verlängert keine IdP-Anmeldeinformationen, die abgelaufen oder widerrufen wurden; ändern Sie die Sitzungsrichtlinie beim Anbieter.

</Callout>
