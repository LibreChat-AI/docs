# Agents: 맞춤형 AI 어시스턴트 구축 [#agents-build-custom-ai-assistants]

LibreChat의 AI Agents 기능은 다양한 모델 제공업체를 기반으로 하는 맞춤형 AI 어시스턴트를 생성하기 위한 유연한 프레임워크를 제공합니다.

이 기능은 OpenAI의 Assistants API 및 ChatGPT의 GPT와 유사하지만, 더 폭넓은 모델 지원과 노코드(no-code) 구현을 통해 전문적인 기능을 갖춘 정교한 어시스턴트를 구축할 수 있게 해줍니다.

## 시작하기 [#getting-started]

새로운 에이전트를 생성하려면, endpoint 메뉴에서 "Agents"를 선택하고 사이드 패널(Side Panel)에 있는 Agent Builder 패널을 여세요.

![Agents - Endpoints Menu](/images/agents/endpoints_menu.png)

생성 양식에는 다음이 포함됩니다:

- **Avatar**: 사용자 지정 아바타를 업로드하여 에이전트를 개인화하세요
- **Name**: 에이전트의 고유한 이름을 선택하세요
- **Description**: 에이전트의 목적에 대한 선택적 세부 정보
- **Instructions**: 에이전트의 동작을 정의하는 시스템 지침
- **Model**: 사용 가능한 공급자 및 모델 중에서 선택하세요
- **Conversation Starters**: 사용자가 에이전트와 새로운 채팅을 시작할 때 표시되는 최대 4개의 제안된 프롬프트

**Tools** 및 **Skills** 컨트롤은 내장 기능, 도구, MCP 서버, Actions 및 Skills를 위한 검색 가능한 라이브러리를 엽니다. 항목을 선택하여 구성한 다음 에이전트를 저장하세요.

**기존 에이전트는 사이드 패널 상단의 드롭다운에서 선택할 수 있습니다.**

- **채팅 입력창에서 "@"를 사용하여 언급할 수도 있습니다.**

![Agents - Mention](/images/agents/mention.png)

### Tool Library [#tool-library]

Agent Builder는 활성화된 항목을 **Tools** 및 **Skills** 섹션으로 분리하여 유지합니다. **Add tools**를 열어 전체 카탈로그를 검색하거나 **Official**, **Tools**, **MCP**, 또는 **Actions**별로 필터링할 수 있습니다. **Made by you**는 사용자가 생성한 MCP 서버와 Actions를 모아두며, **Favorites**는 즐겨찾기로 표시한 항목을 여러 에이전트에서 사용할 수 있도록 보관합니다. 각 사용자는 최대 100개의 도구 라이브러리 즐겨찾기를 저장할 수 있습니다.

빌더를 떠나지 않고 항목을 구성하려면 항목을 선택하세요. **Create new** 메뉴는 사용자에게 MCP 서버 또는 Action을 생성할 권한이 있을 때만 나타납니다. File Search, File Context 또는 Code Interpreter와 같은 파일 기반 기능을 제거하면 첨부된 파일을 검토해야 할 때 파일 관리자가 열립니다. 파일 기반 기능은 파일을 소유하고 있는 동안에는 선택된 상태로 유지되며 저장 시 보존됩니다. 기능을 제거하기 전에 해당 파일을 제거하거나 다시 할당하세요.

Skills는 자체적인 선택 도구를 사용하며, 개별적으로 선택하거나 전체 접근 가능한 카탈로그로 활성화할 수 있습니다. [Skills](/docs/features/skills#agent-scope)를 참조하세요.

운영자는 실험적인 [Agent Plugins](/docs/features/agent_plugins)을 사용하여 배포 Skills와 MCP 서버를 시작 시 로드되는 패키지로 묶을 수도 있습니다.

### 모델 구성 [#model-configuration]

모델 매개변수 인터페이스를 통해 에이전트의 응답을 미세 조정할 수 있습니다:

- Temperature (응답 창의성을 위한 0-1 범위의 척도)
- 최대 컨텍스트 토큰
- 최대 출력 토큰
- 네이티브 비전 이미지 입력을 위한 이미지 세부 정보(`low`, `auto` 또는 `high`)
- 추가적인 공급자별 설정

에이전트 지침은 `{{current_date}}`, `{{current_datetime}}`, 그리고 `{{iso_datetime}}`을 사용할 수 있습니다. LibreChat은 서버가 캡처한 논리적 턴의 시작 시점을 기준으로 이를 해석하며, 공급자 루프, Subagent 초기화, 그리고 human-in-the-loop 재개 과정 전반에 걸쳐 해당 타임스탬프를 일정하게 유지합니다. 앞의 두 가지는 요청 시간대를 사용하며, `{{iso_datetime}}`은 UTC로 유지됩니다.

인식된 model-not-found 및 provider rate-limit 오류는 현지화된 안내를 제공합니다. 다른 provider 오류는 유용한 provider 텍스트를 유지하지만, 메시지가 저장되기 전에 LangChain 문제 해결 URL은 생략합니다. [model-bound content protection](/docs/configuration/librechat_yaml/object_structure/message_filter#source-aware-filters)이 활성화된 경우, 일반적인 보호 오류가 여전히 우선합니다.

### 버전 기록 [#version-history]

편집 권한이 있는 사용자는 Agent Builder에서 **Version History**를 열어 타임라인에 저장된 구성을 검토할 수 있습니다. 각 항목은 저장된 시점을 보여주며 도구 및 기능에 대한 요약 정보를 제공합니다. 이전 항목을 복원하려면 확인이 필요하며, 현재 에이전트 구성이 해당 저장된 상태로 대체됩니다. 저장은 항상 에이전트의 현재 변경 사항을 적용하며, 결과 구성이 최신 기록 항목과 일치하는 경우 LibreChat은 중복 항목을 추가하지 않습니다.

### 대화 시작하기 (Conversation Starters) [#conversation-starters]

대화 시작 문구(Conversation starters)는 사용자가 에이전트와 대화를 빠르게 시작할 수 있는 방법을 제공합니다. 각 에이전트는 최대 4개까지 저장할 수 있습니다.

1. Agent Builder에서 **Conversation Starters** 필드를 찾으세요.
2. 프롬프트를 입력하고 **Enter**를 누르거나 **+** 버튼을 선택하세요. 4개의 스타터가 추가되면 입력 기능이 비활성화됩니다.
3. 저장된 스타터를 그 자리에서 수정하거나, **X** 버튼을 선택하여 삭제하세요.
4. 에이전트를 저장하세요.

사용자가 에이전트와 새로운 채팅을 시작하면, 빈 채팅 화면에 시작 문구(starters)가 버튼으로 나타납니다. 하나를 선택하면 즉시 첫 번째 메시지로 전송됩니다. 에이전트에 시작 문구가 설정되어 있으면, 사용 중인 Model Specs에 정의된 [`conversation_starters`](/docs/configuration/librechat_yaml/object_structure/model_specs#conversation_starters)보다 우선순위를 갖습니다. 시작 문구는 에이전트의 [Marketplace](#agent-marketplace) 상세 대화 상자에도 표시됩니다.

## 에이전트 기능 (Agent Capabilities) [#agent-capabilities]

> **참고:** 모든 기능은 `librechat.yaml` 구성 파일을 통해 전환할 수 있습니다. 자세한 내용은 [docs/configuration/librechat_yaml/object_structure/agents#capabilities](/docs/configuration/librechat_yaml/object_structure/agents#capabilities)를 참조하세요.

### Code Interpreter [#code-interpreter]

활성화되면, Code Interpreter 기능은 에이전트가 다음을 수행할 수 있도록 합니다:

- 다음과 같은 여러 언어로 코드를 실행하세요:
  - Python, JavaScript, TypeScript, Go, C, C++, Java, PHP, Rust 및 Fortran
- LibreChat Code Interpreter API를 통해 안전하게 파일 처리하기
- 로컬 설정, 구성 또는 샌드박스 배포 없이 코드 실행
- 파일 업로드 및 다운로드를 원활하게 처리하세요
- [Code Interpreter API에 대한 추가 정보](/docs/features/code_interpreter)
  - 오픈 소스 [code-interpreter](https://github.com/ClickHouse/code-interpreter) 서비스(자체 호스팅) 기반

대화에서 필요한 모든 Code Interpreter 파일이 현재 샌드박스로 복원되지 못할 경우, LibreChat은 모델을 호출하기 전에 에이전트를 중지하고 사용자에게 파일을 다시 첨부하도록 요청합니다. 이는 오래되었거나 액세스할 수 없는 파일 참조로 실행이 계속되는 것을 방지합니다.

대화 파일들이 동일한 Code Interpreter 파일 이름을 공유할 때, LibreChat은 각 파일에 고유한 샌드박스 대상을 할당하고 에이전트에게 확인된 경로를 알립니다. 충돌 동작 및 남아 있는 다중 에이전트 비공개 파일 제한 사항에 대해서는 [Seamless File Handling](/docs/features/code_interpreter#seamless-file-handling)을 참조하세요.

#### 상태 유지 코드 세션 (Stateful Code Sessions) [#stateful-code-sessions]

Stateful code sessions을 사용하면 에이전트가 코드 실행 간에 샌드박스 작업 공간을 재사용할 수 있습니다. 파일, 설치된 패키지 및 작업 상태가 일반적으로 유지되므로 반복적인 분석이나 다단계 파일 작업에 유용합니다. Agent Builder의 **Stateful environment** 선택기에서 해당 작업 공간을 공유할 대상을 제어할 수 있습니다:

- **사용자 작업 공간(권장):** 로그인한 사용자의 상태 저장 에이전트가 하나의 작업 공간을 공유합니다.
- **에이전트 + 사용자 작업 공간:** 각 사용자는 각 에이전트에 대해 별도의 작업 공간을 갖습니다.
- **대화 작업 공간(Conversation workspace):** 각 사용자는 대화마다 별도의 작업 공간을 갖습니다.

관리자는 [`statefulCodeSessions.environments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions) 아래에 명명된 백엔드를 구성할 수도 있습니다. 이 설정이 존재할 경우, 별도의 **Execution environment** 선택기를 통해 작업 공간을 소유하는 관리형 Code API, 운영자 연결 VM 또는 개인 워커를 선택할 수 있습니다. **Deployment default**는 구성된 기본 실행 환경을 사용합니다. 위의 공유 범위는 해당 백엔드 선택과 독립적으로 유지됩니다.

배포 환경에서 셀프 서비스 워커(self-service workers)가 활성화되면, 코드 환경 관리 권한이 있는 사용자는 **Settings > Code environments**를 열어 자신의 VM에서 아웃바운드 `@librechat/code` 워커를 페어링하고, Agent Builder에서 이를 선택한 뒤 나중에 취소할 수 있습니다. 개인 환경은 소유자에게 귀속되며 코드, 셸, 프로그래밍 방식 도구 호출(Programmatic Tool Calling)에 동일한 경로를 사용합니다. 실험적 설정 및 보안 모델에 대해서는 [Attached environments and pairing](/docs/features/code_interpreter#attached-environments-and-pairing)을 참조하세요.

연결된 작업 공간 내에서, 에이전트는 선택된 워커를 통해 디렉터리 목록을 나열하고, 파일을 읽고, 텍스트를 검색하고, 파일을 작성하며, Bash를 실행할 수 있습니다. 에이전트별 Git 이름과 이메일을 사용하면 저장소 자격 증명을 제공하지 않고도 해당 환경에서 수행된 커밋을 식별할 수 있습니다. 배포 시 [`statefulCodeSessions.principalWorkers`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions)를 사용하여 새로운 개인 워커를 제한할 수 있습니다.

연결된 워커가 여러 작업 공간 루트를 알릴 경우, 채팅 작성기는 에이전트나 그 하위 에이전트가 사용하는 각 연결된 환경에 대해 하나의 선택을 요구합니다. 대화는 턴이 바뀌거나 승인이 재개되어도 해당 선택 사항을 유지하며, LibreChat은 이를 실시간 워커와 대조하여 검증하고 필수 작업 공간이 누락되었거나 사용할 수 없는 경우 전송을 차단합니다. 정확히 하나의 작업 공간을 알리는 워커는 새 대화에 대해 자동으로 선택됩니다. 자세한 내용과 현재 제한 사항은 [Attached environments and pairing](/docs/features/code_interpreter#attached-environments-and-pairing)을 참조하세요.

새로운 에이전트는 처음에 **설정 > 데이터 제어 > 코드 실행**에 있는 로그인한 사용자의 **기본 상태 저장 작업 공간(Default stateful workspace)**을 사용합니다. 개인 기본값은 변경하기 전까지 **사용자 작업 공간(User workspace)**으로 설정되어 있습니다. 이 설정을 업데이트한다고 해서 기존 에이전트가 변경되거나 상태 저장 코드 세션(Stateful Code Sessions)이 자동으로 활성화되지는 않습니다. 관리자는 [`statefulCodeSessions.allowedEnvironments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions)를 통해 사용 가능한 범위를 제한할 수 있습니다. 저장된 개인 기본값이 더 이상 허용되지 않는 경우, 새로운 에이전트는 허용된 첫 번째 범위를 사용합니다.

<Callout type="warning" title="매우 실험적인 기능">
  Stateful Code Sessions는 초기 실험 단계에 있습니다. 해당 기능의 동작, 구성, 지속성 특성 및 기반 통합 방식은 크게 변경될 수 있습니다. 현재 구현을 안정적인 프로덕션 계약으로 간주하지 마십시오.
</Callout>

이 기능은 선택 사항입니다. 관리자는 [agent capabilities](/docs/configuration/librechat_yaml/object_structure/agents#capabilities)에 `stateful_code_sessions`를 추가하고, [`LIBRECHAT_CODE_BASEURL_STATEFUL`](/docs/configuration/dotenv#stateful-code-interpreter-endpoint) 또는 [`statefulCodeSessions.environments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions)를 통해 전용 stateful Code Interpreter 경로를 구성해야 합니다. 에이전트에서 Code Interpreter가 활성화되어 있어야 하며, 고급 설정에서 **Stateful code sessions**가 켜져 있어야 합니다.

Stateful 요청은 전용 URL이 누락되었거나 호환되지 않을 때 일반적인 stateless Code Interpreter endpoint로 대체되지 않습니다. Stateful 세션과 stateless 세션은 라이브 파일이나 설치된 패키지를 공유하지 않습니다. Stateful 작업 공간은 범위와 관계없이 언제든지 초기화될 수 있습니다. 관리형 Code Interpreter 환경에서는 중요한 출력물을 `/mnt/data` 아래에 저장하십시오. 연결된 작업 공간은 별도의 워커 소유 디렉토리입니다. 채팅 업로드는 기본적으로 해당 연결된 디렉토리에 복사되지 않습니다. 그 외의 경우 세션 상태를 영구 저장소로 의존하지 마십시오.

상태 유지형 `create_file` 또는 `edit_file` 도구가 응답 중에 파일을 생성하면, 어시스턴트 메시지에 간략한 **Workspace changes** 행이 표시됩니다. 이를 확장하여 변경된 고유 경로를 검토하고 LibreChat의 인증된 파일 흐름을 통해 각 파일을 다운로드할 수 있습니다. 이는 해당 도구에 의해 생성된 파일에 대한 메시지별 기록이며, 전체 작업 공간의 영구적인 스냅샷이 아닙니다. 상태 비저장 Code Interpreter 출력은 기존의 일반 인라인 첨부 파일 인터페이스를 계속 사용합니다.

연결된 환경의 경우, 컴포저는 대화 수준의 코드 승인 모드로 **Ask before changes**(변경 전 확인), **Accept edits**(편집 수락), **Full access**(전체 액세스)를 노출할 수 있습니다. 사용 가능 여부는 환경의 관리자가 정의한 권한 스키마에 따라 제한됩니다. 더 허용적인 모드를 선택하더라도 역할 권한, 명시적 도구 규칙, 훅(hook) 또는 샌드박스 경계가 무시되지는 않습니다. [Attached-environment tool permissions](/docs/features/code_interpreter#attached-environment-tool-permissions)를 참조하세요.

### File Search [#file-search]

File Search 기능은 다음을 가능하게 합니다:

- RAG (Retrieval-Augmented Generation) 기능
- 업로드된 문서에 대한 의미론적(Semantic) 검색
- 파일 내용을 기반으로 한 문맥 인식 응답
- 에이전트 및 채팅 스레드 수준 모두에서 파일 첨부 지원

### 파일 컨텍스트 [#file-context]

File Context 기능은 에이전트가 파일에서 추출한 텍스트를 시스템 지침의 일부로 저장할 수 있도록 합니다:

- 문서 구조와 서식을 유지하면서 텍스트 추출
- 다중 열 텍스트 및 혼합 콘텐츠를 포함한 복잡한 레이아웃 처리
- 표, 수식 및 기타 특수 콘텐츠 처리
- 다국어 콘텐츠 작업하기
- 텍스트는 데이터베이스 내 에이전트의 instructions에 저장됩니다.
- **OCR 서비스 불필요** - 기본적으로 텍스트 파싱을 사용하며 대체 방법을 지원합니다
- **OCR로 향상됨** - OCR이 구성된 경우, 이미지 및 스캔된 문서에 대한 추출 품질이 향상됩니다.
- "Upload as Text"와 동일한 처리 로직을 사용합니다: **OCR > STT > 텍스트 파싱**
- [OCR 구성에 대한 자세한 정보](/docs/features/ocr)

**참고:** 파일 컨텍스트는 에이전트의 시스템 지침에 추출된 텍스트를 포함합니다. 개별 대화에서 임시 문서 질문을 하려면 채팅에서 [Upload as Text](/docs/features/upload_as_text) 기능을 사용하세요.

### Model Context Protocol (MCP) [#model-context-protocol-mcp]

MCP는 애플리케이션이 거대 언어 모델(LLM)에 컨텍스트를 제공하는 방식을 표준화하는 개방형 프로토콜로, AI 도구와 데이터 소스를 위한 범용 어댑터 역할을 합니다.

더 자세한 정보는 [MCP](/docs/features/mcp) 문서를 참조하세요.

#### MCP 도구를 사용하는 Agents [#agents-with-mcp-tools]

1. `librechat.yaml` 파일에서 MCP 서버를 구성하세요
2. LibreChat을 재시작하여 연결을 초기화하세요
3. 에이전트 생성 또는 편집
4. Agent Builder에서 **Add tools**를 열고 **MCP**를 선택하세요.
5. 추가하려는 MCP 서버를 선택하세요. 각 서버는 단일 항목으로 표시됩니다.
6. 에이전트에 변경 사항을 저장하세요

이 예시에서는 **[Spotify MCP server](https://github.com/LibreChat-AI/spotify-mcp)**를 에이전트에 추가했습니다.

#### MCP 도구 관리 [#managing-mcp-tools]

MCP 서버가 에이전트에 추가되면, 사용 가능한 특정 도구를 세부적으로 조정할 수 있습니다:

- MCP 서버를 추가한 후, 해당 서버를 확장하여 사용 가능한 모든 도구를 확인하세요.
- 필요에 따라 개별 도구를 선택/선택 해제하세요
- 예를 들어, Spotify MCP 서버는 약 20개의 도구(검색, 재생 제어, 재생 목록 관리 등)를 제공합니다.
- 이 세밀한 제어를 통해 에이전트가 필요한 도구만 사용하도록 제한할 수 있습니다.

`{{LIBRECHAT_BODY_*}}`를 사용하는 요청 범위(request-scoped) 서버는 채팅 실행 시 해당 값들이 제공되기 전까지 도구를 열거할 수 없습니다. 따라서 Agent Builder는 도구별 토글 대신 전체 서버에 대한 하나의 런타임 도구 선택 항목을 표시하며, 해당 선택을 해제하면 서버 연결이 끊어집니다. OAuth 이후, LibreChat은 권한 부여 상태를 유지하며 연결을 위해 첫 번째 적격 실행이 발생할 때까지 대기합니다.

에이전트가 MCP 도구를 명시적으로 선택했으나 실행 시작 시 해결할 수 있는 도구가 없는 경우, LibreChat은 도구 없이 조용히 계속 진행하는 대신 연결 및 액세스 안내와 함께 실행을 중단합니다. 서버를 다시 연결하거나 인증하고, 도구 액세스 권한을 확인한 후 실행을 다시 시도하세요.

### Deferred Tools [#deferred-tools]

Deferred tools를 사용하면 에이전트가 많은 MCP 도구에 액세스할 때 이를 모두 LLM 컨텍스트에 미리 로드할 필요가 없습니다. 대신, deferred tools는 **Tool Search** 메커니즘을 통해 런타임에 검색할 수 있습니다.

이는 에이전트가 수십 개의 도구가 포함된 다수의 MCP 서버에 액세스할 때 특히 유용합니다. 모든 도구를 로드하면 컨텍스트 윈도우의 상당 부분을 차지하여 응답 품질이 저하될 수 있기 때문입니다.

**작동 방식:**

- "deferred"로 표시된 도구는 초기 LLM 컨텍스트에서 제외됩니다.
- `ToolSearch` 도구가 자동으로 추가되어, LLM이 필요에 따라 지연 로드된(deferred) 도구를 검색하고 불러올 수 있게 합니다.
- 일단 발견되면, 해당 도구는 남은 대화 동안 계속 사용할 수 있습니다.

**지연된 도구(deferred tools) 구성:**

1. Agent Builder를 열고 MCP 도구를 추가하세요
2. 모든 MCP 도구의 드롭다운을 클릭하세요
3. "Defer Loading" 토글 — 지연된 도구는 시계 아이콘으로 표시됩니다

**참고:** `deferred_tools` 기능은 기본적으로 활성화되어 있습니다. 이 기능은 [`librechat.yaml` 에이전트 구성](/docs/configuration/librechat_yaml/object_structure/agents#capabilities)을 통해 전환할 수 있습니다.

### 활동 그룹 [#activity-groups]

Activity groups는 연속된 에이전트 추론 및 도구 호출 블록을 생성된 한 줄 헤더 아래로 축소하여 긴 실행 과정을 더 쉽게 훑어볼 수 있게 합니다. 관리자는 `activityLabel`을 통해 이를 활성화할 수 있으며, 더 빠른 모델, 다른 구성된 endpoint, 사용자 지정 프롬프트 및 실행당 제한을 사용할 수 있습니다. 헤더 생성은 별도의 모델 호출이며, 해당 토큰과 비용이 기록됩니다. [Agent Activity Groups](/docs/configuration/librechat_yaml/object_structure/shared_endpoint_settings#agent-activity-groups)를 참조하세요.

관리자는 `activityPhaseLabel`을 독립적으로 활성화하여 최종 답변이 나오기 전에 두 개 이상의 논리적 활동을 접을 수 있는 상위 요약으로 묶을 수 있습니다. 이를 통해 긴 실행 과정에서 각 하위 활동을 유지하면서도 더 높은 수준의 개요를 제공할 수 있습니다. 단계 요약(Phase summaries)은 자체 모델, endpoint, 프롬프트 및 실행당 제한을 사용하며, 설정되지 않은 경우 활동 레이블 및 실행 설정으로 대체됩니다.

연속된 실행에 최소 두 개의 완료된 레이블이 지정된 도구 그룹이 포함되는 즉시, LibreChat은 선택적인 단계 요약이 도착하기 전이라도 해당 그룹들을 동일한 단계 카드 표면으로 접습니다. 가장 최근에 완료된 하위 레이블이 임시 헤더 역할을 하며, 실시간 추론 및 진행 중인 도구 호출은 접기 영역 외부에 유지됩니다. 로드된 기록도 동일한 그룹화를 사용하며, 나중에 서버에서 생성된 단계 요약이 사용자가 이미 열어둔 카드를 닫지 않고도 임시 헤더를 대체합니다.

[Smooth Streaming](/docs/features/smooth_streaming)이 활성화되면, 새로 생성된 상위 요약이 표시된 활동들을 접힌 그룹으로 부드럽게 전환합니다. 불러온 기록은 이 전환을 다시 재생하지 않으며, LibreChat은 기기의 동작 줄이기(reduced-motion) 설정을 존중합니다.

짧은 진행 상황 텍스트는 상위 단계(parent phase) 내부에 유지됩니다. 에이전트가 본격적인 답변을 시작하면, LibreChat은 해당 텍스트 이전에 단계를 닫아 사용자에게 보이는 결과가 접힌 요약 외부로 유지되도록 합니다. 한 번의 실행으로 이후 추론이나 도구가 또 다른 논리적 활동 블록을 시작할 때 여러 개의 상위 단계를 생성할 수 있습니다. 지속되는 단계 경계는 형식이 잘못되었거나 생략된 콘텐츠 부분이 압축될 때 재기준(rebased)되므로, 다시 로드한 후에도 그룹화가 정렬된 상태로 유지됩니다.

단계 내에서 생성된 파일은 접힌 카드 내부에 숨겨지는 대신 카드 아래의 미디어 행에 계속 표시됩니다. 파일 이름만 사용하거나 `/mnt/data/...` 또는 `sandbox:` 경로를 사용하는 Markdown 이미지 참조는 일치하는 턴 첨부 파일로 확인됩니다. 접힌 단계 외부의 인라인 이미지가 성공적으로 확인될 때만 해당 파일이 미디어 행에서 생략되며, 이는 잘못된 참조를 신뢰하지 않으면서 중복을 방지합니다.

일반 에이전트 및 MCP 도구 카드는 **준비 중(Preparing)**(SDK 핸드오프 이전, 승인 또는 기타 대기 시간이 포함될 수 있음)과 **호출 중(Calling)**(SDK 핸드오프부터 결과까지)을 구분합니다. 완료된 카드는 두 간격을 모두 보여주며, 호출 간격이 반드시 업스트림 MCP 또는 ClickHouse 실행 시간과 일치하는 것은 아닙니다. 이전에 저장된 메시지와 특수 코드, Bash, 파일 및 메모리 카드는 명확하게 라벨이 지정된 **총 경과(Total elapsed)** 실행 단계 시간을 유지합니다. 중지, 취소, 실패 및 완료된 단계는 대화 재로드 후에도 고유한 상태를 유지합니다.

도구가 실행되는 동안, 확장된 Bash, 코드 실행(Execute Code) 및 파일 작성(File Authoring) 상세 창은 스트리밍되는 명령, 코드 또는 미리보기 콘텐츠를 따라 아래로 이동합니다. 위로 스크롤하면 해당 따라가기 동작이 일시 중지되어 현재 읽고 있는 위치가 유지됩니다.

Bash 출력은 터미널 스타일의 텍스트로 렌더링됩니다. 긴 출력은 오류가 주로 발생하는 마지막 15줄로 축소되며, **Show more** 및 **Show less**를 사용하여 확장하거나 축소할 수 있고, **Copy** 버튼을 사용하여 출력을 복사할 수 있습니다. 아무것도 출력하지 않은 명령은 **No output**으로 표시됩니다. [연결된 작업 공간](/docs/features/code_interpreter#attached-environments-and-pairing)에서 실행된 명령의 경우, 실패한 명령은 그 이유(**exit code N**, `SIGKILL`과 같은 신호에 의한 **terminated by**, 또는 **timed out**)와 함께 표시되며, stderr은 stdout과 별도로 스타일이 지정됩니다. 완료된 명령은 **Ran command**로 레이블이 지정되며, 단일 호출을 포함하는 도구 그룹은 해당 호출의 세부 정보로 바로 열립니다.

### 실시간 추론 레이블 [#live-reasoning-labels]

실시간 추론(Live reasoning) 레이블은 일반적인 **Thinking** 또는 **Thoughts** 헤딩을 충분히 긴 최상위 추론 스트림에 따라 변화하는 짧은 방향성 문구로 대체합니다. 이 레이블은 기존 추론 헤딩을 제자리에서 업데이트하며, 메시지 파트를 추가하거나 재정렬하지 않습니다.

최신 실시간 추론 라벨과 응답 타이머는 생성 중에 반짝입니다. 완료된 추론, 이전 형제 응답, 그리고 더 이상 실시간 끝부분에 있지 않은 라벨은 정적 상태로 유지됩니다.

관리자는 `reasoningLabel`을 통해 이 기능을 활성화할 수 있으며, 별도의 모델, endpoint, 프롬프트, 업데이트 임계값 및 실행당 호출 제한을 선택할 수 있습니다. 각 수정본은 토큰과 비용이 기록되는 추가적인 모델 호출입니다. 기본값, 라우팅 우선순위 및 개인정보 보호 고려 사항은 [Live Reasoning Labels](/docs/configuration/librechat_yaml/object_structure/shared_endpoint_settings#live-reasoning-labels)를 참조하세요.

### 도구 의도 레이블 (Tool Intent Labels) [#tool-intent-labels]

도구 인텐트(Tool intent) 레이블은 일반적인 실시간 도구 상태를 해당 호출에 대해 모델이 작성한 짧은 설명으로 대체합니다. 관리자는 `tool_intents` [에이전트 기능](/docs/configuration/librechat_yaml/object_structure/agents#capabilities)을 선택적으로 추가해야 합니다. 기본 도구는 레이블을 자동으로 사용하며, 에이전트 빌더(Agent Builder)에서는 MCP 서버를 확장하고 개별 도구 또는 전체 서버에 대해 **Intent label**을 켜면 됩니다.

Model Specs의 경우, [`describeIntent`](/docs/configuration/librechat_yaml/object_structure/model_specs#describeintent)를 사용하여 모든 적격 도구를 활성화하거나 선택된 도구 ID를 지정할 수 있습니다. Intent 필드는 모델로 전송되는 도구 스키마에 추가되므로, 선택적 활성화를 통해 스키마 토큰 오버헤드를 줄일 수 있습니다.

의도 레이블(Intent labels)은 프로그래밍 전용 MCP 도구에는 적용되지 않습니다. 샌드박스 코드 내부에서 이루어진 호출은 개별 도구 카드를 렌더링하지 않기 때문입니다. 대신 확장된 프로그래밍 실행은 내부 호출에 대한 간결한 실시간 추적(live trace)을 보여줍니다.

### Programmatic Tool Calling [#programmatic-tool-calling]

Programmatic Tool Calling (PTC)을 사용하면 에이전트가 모델에서 각 도구를 직접 호출하는 대신 [Code Interpreter](/docs/features/code_interpreter) 샌드박스 내부에서 선택된 MCP 도구를 실행할 수 있습니다. 모델은 Code Interpreter 기반의 오케스트레이션 도구를 수신하고, 생성된 도구 함수를 호출하는 샌드박스 코드를 작성하며, 답변을 반환하기 전에 루프, 조건문, 재시도 및 결과 처리를 사용할 수 있습니다.

이는 여러 리소스를 쿼리하거나, 결과 페이지를 넘기거나, 출력을 비교하거나, 에이전트가 설명하기 전에 도구 응답을 변환하는 등 다단계 도구 워크플로우에 유용합니다.

**프로그래밍 방식 도구 구성:**

1. [`librechat.yaml` 에이전트 기능](/docs/configuration/librechat_yaml/object_structure/agents#capabilities)에서 `programmatic_tools`와 `execute_code`를 모두 활성화하세요.
2. 에이전트에서 Code Interpreter를 활성화하세요.
3. MCP 도구를 추가하고, MCP 서버를 확장하며, 개별 도구 또는 전체 서버에 대해 **Programmatic**을 토글합니다. Programmatic 도구는 코드 아이콘으로 표시됩니다.

Agent Builder는 Code Interpreter가 선택될 때까지 프로그래밍 방식(Programmatic) 토글을 비활성화 상태로 유지합니다. Code Interpreter를 제거하면 즉시 해당 에이전트의 프로그래밍 방식 선택 항목이 삭제됩니다. 생성, 업데이트, 복제 및 버전 복원 시, 서버는 `execute_code` 기능이나 Code Interpreter 도구를 사용할 수 없을 때마다 프로그래밍 방식 호출자 옵션을 제거합니다. 이를 통해 이전의 일관되지 않은 Agent를 열어 사용할 수 없는 구성을 유지하지 않고 수정할 수 있습니다.

**참고:** `programmatic_tools`는 옵트인(opt-in) 방식이며 기본 에이전트 기능 목록에는 포함되어 있지 않습니다. PTC는 또한 Tool Call Server 구성 요소가 포함된 Code Interpreter 배포가 필요합니다. 런타임 시 LibreChat은 현재 호출자-기능 프로젝션과 신뢰할 수 있는 도구 레지스트리를 교차 검사하므로, 이벤트 데이터가 사용 가능한 맵을 좁힐 수는 있지만 도구에 대한 권한을 부여할 수는 없습니다. 활성화되어 등록된 programmatic tools만 샌드박스에서 호출할 수 있으며, 등록되지 않은 호출은 거부됩니다.

프로그래밍 방식의 실행 중에 Code Interpreter 카드를 확장하여 각 내부 도구 호출, 인수 미리보기, 상태, 지속 시간 및 오류 발생 여부에 대한 터미널 스타일의 추적을 확인하세요. 이 추적은 현재 브라우저 세션 동안 실시간으로 유지되며 페이지를 새로 고침하면 복원되지 않습니다.

### Background Tool Calls [#background-tool-calls]

Background tool calls를 사용하면 에이전트가 장시간 실행되는 적격한 Code Interpreter, MCP, Plugin 또는 Action 도구를 시작하고 계속해서 작업을 수행할 수 있습니다. 초기 호출은 즉시 작업 참조(task reference)를 반환합니다. 저장된 에이전트의 경우, 지원되는 완료(completion)는 기본적으로 후속 연속 작업(follow-up continuation)을 통해 자동으로 전달됩니다. `check_background_task`는 명시적인 상태 확인, 제어, 아티팩트 수집 및 복구를 위해 계속 사용할 수 있습니다.

`check_background_task`는 프로세스 로컬 작업이 실행되는 동안 `started_at`과 현재 `elapsed_ms`를 보고합니다. 작업이 완료되면 `settled_at`을 보고하고 `elapsed_ms`를 완료된 지속 시간으로 고정합니다. 영구 저장소에서 복구된 최종 결과에는 원래의 프로세스 로컬 디스패치 타임스탬프를 사용할 수 없는 경우 시작 시간이나 경과 시간 없이 `settled_at`만 포함될 수 있습니다.

이 기능을 사용하려면 관리자가 `run_in_background` [에이전트 기능](/docs/configuration/librechat_yaml/object_structure/agents#capabilities)을 선택적으로 추가해야 합니다. 그런 다음 에이전트 빌더(Agent Builder)에서 적합한 도구를 구성하십시오:

- **Code Interpreter:** 에이전트에서 Code Interpreter를 활성화합니다. 코드 실행 및 셸 명령은 기본적으로 백그라운드 실행이 가능합니다. 이를 원치 않으면 도구 설정에서 **Background execution**을 끄십시오.
- **MCP:** MCP 서버를 열고 개별 도구 또는 전체 서버를 **Background**로 표시하세요.
- **Plugin tools:** 적합한 도구를 열고 **Background execution**을 켭니다.
- **Actions:** Action에 대해 **Background execution**을 켜면 해당 Action 내의 모든 적격 작업(operation)을 선택할 수 있습니다. OAuth Action은 이 스위치를 노출하지 않습니다. 또한 작업의 스키마에 이미 `run_in_background` 매개변수가 정의되어 있는 경우, LibreChat의 디스패치 플래그와의 충돌을 방지하기 위해 해당 작업은 제외됩니다.

이 설정들은 백그라운드 실행을 허용하지만 강제하지는 않습니다. 모델은 호출 시마다 적격한 도구를 백그라운드에서 실행할지 여부를 결정합니다.

LibreChat 채팅에서 백그라운드 코드가 완료되면, 해당 stdout과 생성된 파일은 이후의 폴링(poll)이 아닌 원래의 코드 호출 위치에 나타납니다. 생성된 파일은 후속 턴을 위해 유지됩니다. 자동 연속 작업은 완료된 작업을 원래 작업에 연결된 접기 가능한 웨이크업(wake-up) 태스크 카드에 표시합니다.

서버가 이전 포그라운드 실행이 완료된 후 해당 연속 작업을 시작하면, 열려 있는 대화가 새로운 생성에 연결되며 페이지를 새로고침할 필요 없이 완료된 작업 출력을 새로 고칩니다.

관리자가 [`endpoints.agents.backgroundTasks.completionWakeups: false`](/docs/configuration/librechat_yaml/object_structure/agents#backgroundtasks)로 설정하여 폴링 전용 동작으로 복원하지 않는 한, 자동 완성 웨이크업(wakeups)은 기본적으로 활성화됩니다. 호스트는 여러 개의 적격한 콘텐츠 전용 완성을 하나의 연속 작업으로 일괄 처리할 수 있습니다. 실시간 아티팩트를 생성하는 작업은 여전히 해당 실행을 소유한 프로세스에서의 폴링이 필요합니다.

관리자는 [`endpoints.agents.backgroundTasks.ordinaryToolCancellation: true`](/docs/configuration/librechat_yaml/object_structure/agents#backgroundtasks)를 통해 소유자 범위의 취소 기능을 선택적으로 활성화할 수 있습니다. 해당 작업은 기본 호출이 완료될 때까지 취소가 요청되었음을 보고하며, 그 기간 동안 작업 용량은 계속 예약된 상태로 유지됩니다. 취소는 협력적으로 이루어집니다. 즉, 중단 신호를 무시하는 도구는 여전히 성공적으로 완료될 수 있습니다. 이 제어 기능은 연결된 Bash를 포함한 일반적인 프로세스 로컬 백그라운드 도구에는 적용되지만, 독립적으로 소유된 분리형 Subagents에는 적용되지 않습니다.

적격한 도구만이 해당 설정을 노출합니다. 일반적인 백그라운드 실행은 프로세스 로컬이며 워커 프로세스가 손실되면 유지되지 않습니다. 그러나 콘텐츠 전용 터미널 결과가 영구 저장되면 자동 전달은 내구성을 갖게 되며 다른 복제본에서 계속될 수 있습니다. 프로세스 로컬 레지스트리는 대화, 사용자 및 프로세스별로 실행 중인 작업과 보존된 결과 페이로드를 제한합니다. 안전할 때 완료된 작업을 제거하고, 보류 중인 처리로 인해 안전한 제거가 불가능할 경우 범위가 지정된 용량 결과를 반환합니다. 호출이 취소를 무시하는 경우, LibreChat은 1분의 중단 후 유예 기간이 지나면 생산자 임대 갱신을 중단하고, 불확실한 외부 작업을 잘못된 시간 초과로 표시하지 않으면서 자동 완료 전달을 종료합니다. 분리된 서브에이전트(Detached Subagents)는 Redis로 라우팅되는 실시간 제어 기능을 갖춘 별도의 내구성 있는 작업 및 기록 경로를 사용합니다. [Detached Subagent Threads](/docs/features/subagents#detached-subagent-threads)를 참조하세요.

### 사용자 및 도구 승인 요청 (Ask User and Tool Approval) [#ask-user-and-tool-approval]

**Ask User** 도구는 에이전트가 실행을 일시 중지하여 누락된 정보를 요청하거나, 선택지를 제시하거나, 진행 방법을 확인하도록 합니다. 한 번의 호출로 최대 4개의 관련 질문을 그룹화할 수 있습니다. LibreChat은 뒤로, 다음, 클릭 가능한 진행 단계와 함께 한 번에 하나의 질문을 표시합니다. 단계 간 이동 중에도 답변은 유지되며, 단일 선택 답변은 제출하지 않아도 자동으로 다음으로 넘어갑니다. 모든 질문에 답변이 완료되면 마지막 단계에 제출 버튼이 나타나며, 건너뛰기 버튼을 누르면 어느 단계에서든 전체 질문 세트를 거부할 수 있습니다. 각 질문은 자유 형식의 답변이나 에이전트가 설정한 단일 또는 다중 선택 옵션을 허용합니다. 모델이 호출을 준비하는 동안 LibreChat은 질문을 진행 카드에 스트리밍하며, 준비가 완료되면 대화형 양식으로 대체됩니다. 제출이 완료되면 동일한 실행이 전체 답변 맵과 함께 재개됩니다. 도구 마켓플레이스에서 **Ask User**를 추가할 수 있으며, 관리자는 기본 `ask_user_question` 기능을 제거하여 이를 숨길 수 있습니다.

다중 질문 카드를 접으면 작성기(composer)는 일반적인 steer-or-queue 모드로 돌아가며, 일시 중지된 카드는 스레드에 그대로 유지됩니다. 카드는 여전히 확장, 답변, 건너뛰기 또는 중지가 가능합니다. 단일 질문 일시 중지는 계속해서 집중된 작성기 답변 모드를 사용합니다.

제출된 답변은 재개(resume) 작업과 함께 유지되므로, 재개된 실행이 초기화되는 동안 중단하더라도 수락된 답변은 삭제되지 않습니다.

질문 기록이 완료되면, 긴 답변이 대화 기록을 차지하지 않도록 기본적으로 한 줄짜리 도구 항목으로 축소됩니다. 질문과 답변에 보존된 줄 바꿈을 검토하려면 해당 항목을 여십시오. 기존의 **Auto-expand tool details** 설정으로도 이 완료된 보기를 제어할 수 있으며, 입력이 계속 필요한 동안에는 라이브 폼이 열린 상태로 유지됩니다.

각 질문은 최대 80자까지의 선택적 제목, 최대 2,000자까지의 질문 텍스트, 최대 4,000자까지의 선택적 지원 컨텍스트, 그리고 최대 12개의 선택지를 포함할 수 있습니다. 선택지 레이블은 280자, 선택지 값은 500자, 그리고 제출된 각 답변은 16,000자까지로 제한됩니다.

관리자는 일치하는 도구 호출이 실행되기 전에 검토를 요구할 수도 있습니다. 도구에 따라 사용자는 승인, 거부, 인수 편집 또는 직접 응답을 수행할 수 있습니다. 일시 중지된 실행은 체크포인트가 생성되므로 결정 후 재개할 수 있으며, 기본 MongoDB 체크포인터를 사용하는 경우 다른 복제본에서도 재개할 수 있습니다. 배포 전체의 도구 승인은 기본적으로 비활성화되어 있지만, 연결된 코드 환경을 사용하는 에이전트는 관리자가 명시적으로 비활성화하지 않는 한 [ask-by-default 안전 정책](/docs/features/code_interpreter#attached-environment-tool-permissions)을 적용받습니다. [`toolApproval` 및 `checkpointer`](/docs/configuration/librechat_yaml/object_structure/agents#toolapproval)를 참조하세요.

승인 대기 중인 컴포저 검토 패널이 열려 있는 동안, 해당 스레드 카드는 결정 버튼을 중복 표시하는 대신 요청을 기록으로 보여줍니다. 메시지 상자 위의 패널에서 호출을 검토하고 **Continue**를 선택하세요. 컴포저 칩에서 패널을 접으면 결정 사항이 유지된 채 스레드 카드의 제어 기능이 복원되며, 다시 열면 검토 권한이 패널로 돌아갑니다. 다른 작업에 대한 카드는 자체 제어 기능을 유지합니다.

### Skills [#skills]

Skills를 사용하면 에이전트가 `SKILL.md` 정의에서 재사용 가능한 지침을 로드할 수 있습니다. 이는 채팅에서 `$`를 사용하여 수동으로 선택하거나, 모델이 스킬 카탈로그를 통해 자동으로 검색하거나, 모든 턴에 항상 적용되도록 설정할 수 있습니다. Agent Builder는 독립형 런타임 작성을 활성화할 수도 있습니다. 즉, 에이전트가 기존 카탈로그를 받지 않고도 Skill을 생성하거나, 사용자가 해당 권한을 가지고 있을 때 선택된 Skill을 편집할 수 있습니다.

작성, 호출 및 액세스 제어에 대한 자세한 내용은 [Skills](/docs/features/skills)를 참조하세요.

### Memory [#memory]

**Memory** 도구는 사용자가 명시적으로 무언가를 기억하거나 잊어달라고 요청할 때 에이전트가 구조화된 사용자 메모리를 저장, 업데이트 또는 삭제할 수 있도록 합니다. Memory는 배포를 위해 구성되어야 하며, 사용자 역할 및 개인화 설정에서 허용되어야 하고, 에이전트에서 활성화되어야 합니다.

기본적으로 에이전트는 사용자가 공유하는 개인 메모리 풀을 사용합니다. **Keep memories separate for this agent**를 켜면 해당 에이전트에게 사용자별, 에이전트별 전용 파티션을 제공할 수 있습니다. 격리된 에이전트는 기존의 공유 메모리나 다른 격리된 에이전트가 생성한 메모리를 볼 수 없습니다. 사용자는 메모리 패널에서 개인 메모리 또는 에이전트별 메모리로 필터링할 수 있습니다. 에이전트 파티션을 읽거나, 생성하거나, 업데이트하려면 해당 에이전트에 대한 현재 액세스 권한이 필요합니다. 삭제 작업은 에이전트가 제거된 후에도 파티션을 정리할 수 있습니다. [User Memory](/docs/features/memory#agent-memory)를 참조하세요.

### Artifacts [#artifacts]

Artifacts 기능은 에이전트가 대화형 콘텐츠를 생성하고 표시할 수 있도록 지원합니다:

- React 컴포넌트, HTML 코드 및 Mermaid 다이어그램 생성
- 채팅 옆 전용 패널에 콘텐츠를 표시하며, 전체 화면으로 확장하거나 별도의 브라우저 창에서 열 수 있습니다.
- 에이전트 수준에서 아티팩트별 지침을 구성하세요
- [Artifacts에 대한 추가 정보](/docs/features/artifacts)

활성화되면 다음 세 가지 지침 모드 중 하나를 선택하세요:

- **Normal**: React, HTML, SVG, Markdown 및 Mermaid에 대한 표준 아티팩트(artifact) 지침을 추가합니다.
- **shadcn/ui**: 표준 지침과 더불어 shadcn/ui 컴포넌트 라이브러리를 사용하여 인터페이스를 구축하기 위한 가이드를 추가합니다.
- **Custom**: 아티팩트 렌더링은 활성화된 상태로 유지하지만 내장된 아티팩트 지침을 주입하지 않으므로, 에이전트 고유의 지침이 모든 제어권을 갖게 됩니다.

에이전트 수준에서 아티팩트를 구성하는 것이 권장되는 방식입니다. 이는 기존의 앱 전체 구성보다 더 세밀한 제어가 가능하기 때문입니다.

**Custom**을 선택하는 경우, 지침에 최소한 기본 아티팩트 형식을 포함하세요.

다음은 필요한 최소한의 지침에 대한 간단한 예시입니다:

````md
When creating content that should be displayed as an artifact, use the following format:

:::artifact{identifier="unique-identifier" type="mime-type" title="Artifact Title"}

```
Your artifact content here
```

:::

For the type attribute, use one of:

- "text/html" for HTML content
- "application/vnd.mermaid" for Mermaid diagrams
- "application/vnd.react" for React components
- "image/svg+xml" for SVG images
````

### Handoffs [#handoffs]

Handoff는 기본 에이전트가 관련 컨텍스트와 함께 대화를 전문가 에이전트로 전달할 수 있도록 합니다. **Advanced settings**에서 orchestration 섹션을 열고 최대 10개의 handoff 에이전트를 추가하세요. 구성된 각 handoff는 전문가의 전문 지식이 필요할 때 모델이 동적으로 선택할 수 있는 transfer 도구를 생성합니다.

각 핸드오프(handoff)에 대해 모델이 올바른 전문가를 선택하도록 돕는 설명을 추가할 수 있습니다. 또한 기본 에이전트가 전문가를 위해 생성해야 할 콘텐츠를 설명하는 패스스루(passthrough) 지침을 제공하고, 선택적으로 콘텐츠 매개변수의 이름을 기본값인 `instructions`에서 변경할 수도 있습니다. 핸드오프는 Agent Builder에서 항상 사용할 수 있으며, Agent Chain이나 Subagents와 달리 엔드포인트 기능을 활성화할 필요가 없습니다. 도달 가능한 핸드오프 에이전트의 도구 호출은 이후 턴에서도 구조화된 상태로 유지되므로, 제공자는 평면화된 텍스트 대신 유효한 도구 호출 기록을 받게 됩니다.

### Agent Chain [#agent-chain]

Agent Chain 기능은 Mixture-of-Agents (MoA) 접근 방식을 지원하여, 함께 작동하는 에이전트 시퀀스를 생성할 수 있게 합니다:

- 복잡한 작업을 위한 전문 에이전트 체인 생성
- 체인의 각 에이전트는 이전 에이전트의 출력에 접근할 수 있습니다.
- 에이전트 체인의 최대 단계 수를 구성합니다
- **참고:** 이 기능은 Agent Builder의 고급 설정(Advanced Settings) 패널에서 액세스할 수 있습니다.
- **참고:** 이 기능은 현재 베타 버전이며 변경될 수 있습니다.
  - 현재 체이닝할 수 있는 에이전트의 최대 개수는 10개이지만, 향후 설정 가능하도록 변경될 수 있습니다.

이 기능은 LibreChat에 계층화된 Mixture-of-Agents 아키텍처를 도입합니다. [동명의 "Mixture-of-Agents" 논문](https://arxiv.org/abs/2406.04692)에 설명된 바와 같이, 각 에이전트는 이전 계층에 있는 에이전트들의 모든 출력을 응답 생성 시 보조 정보로 활용합니다.

### Subagents [#subagents]

Subagents를 사용하면 에이전트가 집중적인 작업을 격리된 하위 실행(child run)이나 저장된 에이전트 팀(Agent team)에 위임할 수 있습니다. 각 하위 에이전트는 격리된 컨텍스트와 도구 실행 권한을 가지며, 모든 중간 단계를 부모 컨텍스트에 채우는 대신 간결한 결과만을 부모에게 반환합니다. 분리된 하위 작업은 탐색 가능한 읽기 전용 스레드로도 보존됩니다.

Subagents는 Agent Chain과는 다릅니다. Chain 실행은 여러 에이전트를 그래프 참여자로 조정하는 반면, Subagents는 에이전트가 범위가 지정된 위임을 위한 도구 호출(tool call)로서 생성합니다. LibreChat은 도달 가능한 하위 에이전트와 저장된 팀 멤버가 이후 턴에서도 필요로 하는 구조화된 도구 호출 기록을 보존하는 동시에, 활성 실행에서 사용할 수 없는 도구는 제외합니다. 설정 및 제한 사항은 [Subagents](/docs/features/subagents)를 참조하세요.

### 고급 설정 [#advanced-settings]

"capabilities" 외에 에이전트에 대한 고급 설정(에이전트 양식의 고급 보기에서 찾을 수 있음)입니다.

#### 최대 에이전트 단계 (Max Agent Steps) [#max-agent-steps]

이 설정은 에이전트가 "run" 내에서 수행할 수 있는 단계 수를 제한할 수 있게 해주며, 이는 최종 응답이 제공되기 전의 에이전트 루프를 의미합니다.

설정하지 않을 경우 기본값은 25단계이지만, 필요에 따라 조정할 수 있습니다. 관리자의 경우 [`librechat.yaml`](/docs/configuration/librechat_yaml/object_structure/agents#recursionlimit) 파일에서 전역 기본값과 전역 최댓값을 설정할 수 있습니다.

턴이 전체 단계 예산을 모두 사용하면, LibreChat은 오류로 대체하는 대신 부분적인 응답과 도구 호출을 유지합니다. 메시지에는 새로운 도구 예산으로 새 턴을 시작하는 **Keep going**과, 추가 도구 없이 이미 완료된 작업으로 에이전트가 답변하도록 요청하는 **Answer now** 옵션이 제공됩니다. 알림을 닫아도 현재 브라우저 뷰에만 영향을 미칩니다.

관리자는 [Agent stream circuit breakers](/docs/configuration/librechat_yaml/object_structure/agents#stream-circuit-breakers)를 사용하여 스트리밍되는 도구 호출(tool-call) 인수 및 모델 델타 이벤트를 제한할 수도 있습니다.

"단계(step)"는 AI API 요청 또는 도구 사용 회차(LLM이 단일 요청에서 제공하는 도구 호출 수에 따라 1개 또는 다수의 도구)를 의미합니다.

단일 비도구 응답은 1단계입니다. 단일 도구 사용 라운드는 일반적으로 3단계로 구성됩니다:

1. API 요청 -> 2. 도구 사용 (1개 또는 다수의 도구) -> 3. 후속 API 요청

## 파일 관리 [#file-management]

Agents는 파일을 다루는 여러 가지 방법을 지원합니다:

### 채팅 인터페이스에서 [#in-chat-interface]

에이전트와 대화할 때, 네 가지 업로드 옵션을 사용할 수 있습니다:

1. **이미지 업로드**
   - 네이티브 비전 모델 지원을 위해 이미지를 업로드합니다
   - 이미지를 모델 제공업체로 직접 전송합니다

2. **텍스트로 업로드** (`context` 기능 필요)
   - 대화에 전체 문서 내용을 추출하고 포함합니다
   - 기본적으로 텍스트 파싱을 사용하며, 설정된 경우 OCR을 통해 향상됩니다.
   - 현재 대화에만 콘텐츠가 존재합니다
   - [Upload as Text](/docs/features/upload_as_text)를 참조하세요.

3. **파일 검색을 위한 업로드** (`file_search` 기능이 필요하며, ON으로 설정해야 함)
   - 벡터 저장소를 사용한 의미론적 검색(RAG)을 활용합니다
   - 도구 사용을 통해 관련 청크를 반환합니다
   - 대용량 문서/다중 파일에 최적화됨
   - 구조화된 데이터(CSV, Excel, JSON 등)에는 최적화되어 있지 않음

4. **코드 인터프리터용 업로드** (`execute_code` 기능이 필요하며, ON으로 설정해야 함)
   - 코드 인터프리터 환경에 파일을 추가합니다
   - 구조화된 데이터(CSV, Excel, JSON 등)에 최적화되어 있습니다.
   - [Code Interpreter](/docs/features/code_interpreter)에 대한 추가 정보

### Agent Builder에서 [#in-agent-builder]

에이전트를 구성할 때, 다양한 카테고리의 파일을 첨부할 수 있습니다:

1. **이미지 업로드**: 에이전트가 참조할 수 있는 시각적 콘텐츠용
2. **파일 검색 업로드(File Search Upload)**: RAG 기능을 위한 문서
3. **Code Interpreter 업로드**: 코드 처리를 위한 파일
4. **파일 컨텍스트**: 에이전트 지침을 보완하기 위해 텍스트가 추출된 문서

**File Context**는 `context` 기능을 사용하며 ["Upload as Text"](/docs/features/upload_as_text)와 동일하게 작동합니다. 기본적으로 텍스트 파싱을 사용하며, 설정 시 OCR을 통해 향상됩니다. 텍스트는 업로드 시점에 추출되어 에이전트의 지침(instructions)에 저장됩니다. 이는 문서, PDF, 코드 파일 또는 텍스트가 포함된 이미지로부터 에이전트에게 지속적인 지식을 제공하는 데 이상적입니다.

**처리 우선순위:** OCR > STT > 텍스트 파싱 (Upload as Text와 동일)

**참고:** 추출된 텍스트는 에이전트의 시스템 지침의 일부로 포함됩니다.

## 공유 및 권한 [#sharing-and-permissions]

에이전트는 LibreChat의 세분화된 [access control](/docs/features/access_control) 시스템을 사용합니다. 각 에이전트에는 고유한 액세스 제어 목록(ACL)이 있으며, 선택한 권한 수준에 따라 특정 **사용자**, **그룹**, **역할** 또는 **공개**로 공유할 수 있습니다.

신뢰할 수 있는 서비스는 베타 [Agent Management API](/docs/features/agents_api#agent-management-api)를 통해 에이전트, 첨부 파일 및 스킬을 관리할 수도 있습니다. 관리자는 각 OIDC 머신 클라이언트를 기존 LibreChat 사용자 및 테넌트 하나에 바인딩합니다. 모든 요청은 별도의 관리자 권한을 받는 대신 해당 사용자의 현재 역할 기능과 리소스 ACL을 상속받습니다.

### 액세스 역할 [#access-roles]

에이전트를 공유할 때, 피공유자에게는 다음 세 가지 역할 중 하나가 할당됩니다:

| 역할 | 권한 부여 대상이 할 수 있는 작업 |
| ---------- | ----------------------------------------------------------------------------------------------------- |
| **Viewer** | 대화에서 에이전트 사용; 빌더를 열거나 지침, 도구, 첨부 파일을 볼 수 없음 |
| **Editor** | 보기 + 에이전트의 지침, 모델, 도구 및 파일 수정 |
| **Owner** | 전체 제어: 에이전트 보기, 편집, 삭제 및 재공유 |

원작자와 관리자는 ACL과 관계없이 항상 모든 권한을 유지합니다.

### 에이전트 공유하기 [#sharing-an-agent]

1. Agent Builder에서 에이전트를 엽니다.
2. 바닥글에 있는 **Share** 버튼을 클릭하세요(작성자이거나, 관리자이거나, 해당 에이전트에 대한 `SHARE` 권한을 부여받은 경우에 표시됩니다).
3. 사용자 선택기에서 사용자, 그룹 또는 역할을 검색하고 각각에 역할을 할당하세요.
4. 선택적으로 **Public**을 토글하여 해당 인스턴스의 모든 사용자가 에이전트를 볼 수 있도록 설정할 수 있습니다(`SHARE_PUBLIC` 기능 권한이 필요합니다).

에이전트 카드와 랜딩 뷰에는 구성된 지원 연락처가 표시됩니다. 설정된 연락처가 없는 경우, LibreChat은 확인 가능한 첫 번째 소유자의 표시 이름으로 대체할 수 있지만, 지원 연락처로 명시적으로 구성되지 않은 한 소유자의 이메일 주소는 노출하지 않습니다.

대화 표면(Conversation surfaces)은 Agent를 가시적인 정체성으로 유지하며, 기반 모델이나 Model Specs 레이블로 대체되지 않습니다.

주체(principals), 권한 비트(permission bits), 그리고 ACL이 역할 기반 기능 권한과 어떻게 구성되는지에 대한 자세한 내용은 [Access Control](/docs/features/access_control)을 참조하세요.

### 에이전트 마켓플레이스 [#agent-marketplace]

**Agent Marketplace**를 통해 사용자는 자신에게 제공되는 에이전트를 탐색할 수 있습니다. 사이드바의 **Agent Marketplace**에서 열 수 있으며, 이 항목은 Marketplace 사용이 허용된 사용자에게만 표시됩니다.

- **탐색 및 검색**: 에이전트가 그리드 형태로 표시됩니다. 검색 필드를 사용하여 이름이나 설명으로 에이전트를 찾거나, 카테고리 필(예: **Top Picks**, **All** 또는 특정 카테고리)을 사용하여 목록을 좁힐 수 있습니다.
- **정렬**: **정렬 기준(Sort by)**을 사용하여 에이전트를 **최신순**(기본값), **오래된순**, **인기순**(가장 많이 고정됨) 또는 **작성자 이름순**으로 정렬할 수 있습니다.
- **My agents**: **My agents**를 켜면 본인이 생성한 에이전트만 표시됩니다. **Top Picks**에서 이 기능을 켜면 **All**로 전환됩니다.
- **공유 가능한 뷰**: 검색, 정렬 및 **My agents** 필터는 페이지 URL(`?q=`, `?sort=`, `?mine=1`)에 유지되므로, 필터링된 뷰를 즐겨찾기에 추가하거나 공유할 수 있습니다.

에이전트 카드를 선택하여 상세 대화 상자를 엽니다. 여기에는 전체 설명과 에이전트의 연락처 정보, 그리고 다음과 같은 작업이 표시됩니다:

- **고정(Pin)** 또는 **고정 해제(Unpin)**: 에이전트를 고정된 에이전트 목록에 추가하거나 제거합니다.
- **링크 복사**: 에이전트와의 새로운 대화를 시작하는 링크를 복사합니다.
- **Start Chat**: 에이전트와 새로운 대화를 시작합니다.
- **대화 시작하기 시도**: 에이전트에 [conversation starters](#conversation-starters)가 설정되어 있는 경우, 하나를 선택하여 해당 프롬프트가 메시지 입력창에 미리 채워진 상태로 새 채팅을 시작할 수 있습니다. 자동으로 전송되지 않으므로 먼저 수정할 수 있습니다.

관리자는 [`interface.marketplace`](/docs/configuration/librechat_yaml/object_structure/interface#marketplace) 설정과 [액세스 제어](/docs/features/access_control)에 설명된 역할 권한을 사용하여 액세스를 제어할 수 있습니다.

### 관리자 제어 [#administrator-controls]

관리자는 에이전트 빌더 UI 내에서 전역 권한 설정에 액세스할 수 있습니다:

- 모든 사용자 간의 에이전트 공유 활성화/비활성화
- 에이전트 사용 권한 제어
- 에이전트 생성 권한 관리
- 플랫폼 전체 설정 구성

범위가 지정되지 않은 단일 테넌트 배포에서는 인스턴스에 대해 생성된 첫 번째 계정이 관리자가 됩니다. 테넌트 범위가 지정된 배포는 첫 번째로 등록된 사용자를 자동으로 승격하지 않으므로, 신뢰할 수 있는 관리 흐름을 통해 테넌트 관리자를 프로비저닝하십시오. 수동으로 관리자를 추가해야 하는 경우, [MongoDB에 액세스](/docs/configuration/mongodb/mongodb_auth)하여 사용자 프로필을 업데이트할 수 있습니다:

```
db.users.updateOne(
  { email: 'USER_EMAIL_ADDRESS' },
  { $set: { role: 'ADMIN' } }
)
```

모든 사용자에 대한 에이전트 사용은 설정(config)을 통해 비활성화할 수도 있습니다. [자세한 정보](/docs/configuration/librechat_yaml/object_structure/interface).

기능 수준 권한(누가 에이전트를 _사용_, _생성_, _공유_ 또는 _공개 공유_할 수 있는지)은 각 역할(사용자 지정 역할 포함)에 대해 [**LibreChat 관리자 패널**](/docs/features/admin_panel)에서 관리됩니다. `librechat.yaml`의 [`interface.agents`](/docs/configuration/librechat_yaml/object_structure/interface#agents) 블록을 통해 시작 시 기본 제공 `USER` 역할에 대한 기본값을 설정할 수는 있지만, 향후 수정 사항은 관리자 패널을 사용하는 것이 권장됩니다.

### 사용자 수준 공유 [#user-level-sharing]

개별 사용자는 다음을 수행할 수 있습니다:

- 특정 사용자, 그룹 또는 역할과 에이전트를 공유합니다(해당 역할에 대해 `SHARE`가 활성화된 경우).
- 인스턴스의 모든 사용자에게 에이전트를 공개합니다 (`SHARE_PUBLIC`이 활성화된 경우)
- 각 수신자에게 서로 다른 액세스 수준(Viewer / Editor / Owner)을 부여하세요.
- 공유 대화 상자에서 언제든지 액세스 권한을 다시 공유하거나 취소할 수 있습니다.

## Steering 및 대기 중인 메시지 [#steering-and-queued-messages]

Agent가 응답하는 동안 [composer](/docs/features/composer)에서 다음 두 가지 방법 중 하나로 다른 메시지를 보낼 수 있습니다:

- **Steer**는 현재 실행 중인 작업의 다음 도구 또는 에이전트 단계에 메시지를 삽입하여, 에이전트가 작업을 완료하기 전에 스스로 조정할 수 있도록 합니다.
- **Queue**는 메시지를 보관했다가 현재 응답이 완료된 후 일반적인 후속 턴으로 전송합니다.

현재 서버에 저장된 Agent 대화의 경우, 일반적인 대기열 후속 작업은 MongoDB에 저장됩니다. LibreChat은 FIFO 순서를 유지하며 브라우저 연결 해제, 앱 재시작, 복제본 핸드오프 전반에 걸쳐 텍스트, 첨부 파일, 인용된 발췌문 및 수동으로 선택한 Skill을 유지합니다. 처리는 다음 차례를 허용하기 전에 이전 응답이 완료될 때까지 대기합니다. 이러한 내구성은 자동이며 YAML 또는 환경 설정 토글이 없습니다. 활성 생성 에포크가 없는 이전 서버 및 짧은 시작 창은 클라이언트 측 호환성 대기열을 유지합니다.

서버 승인은 각 대화 대기열 레인 내에서 직렬화됩니다. 이전 증거가 불분명하거나 혼합 버전 소유권이 모호한 경우, LibreChat은 **Awaiting reconciliation**(조정 대기 중)을 표시하고 추측하여 순서 없이 시작하는 대신 영향을 받는 대기열 턴을 차단하거나 실패 처리합니다.

**Steer sooner**는 에이전트가 다음 도구 단계까지 기다리는 대신 다음 안전 지점에서 메시지를 처리하도록 요청합니다. 아직 유지하기에 안전한 답변 텍스트나 도구 활동이 없는 경우, LibreChat은 짧은 유예 기간 동안 대기한 후, 침묵하거나 추론만 수행한 시도를 폐기하고 메시지를 삽입한 다음 해당 지시사항으로 모델을 다시 시작합니다. 답변 텍스트를 유지할 수 있게 되면, LibreChat은 공급자에게 안전한 경계에서 중단하고, 부분적인 응답을 보존하며, 메시지를 삽입한 후 동일한 어시스턴트 응답을 재개합니다. 실행 중인 도구 호출은 조향(steering)에 의해 폐기되거나 중단되지 않으며, 해당 작업이 안전한 경계에 도달했을 때 메시지가 적용됩니다.

**중지(Stop)**를 사용하여 활성 추론을 종료하고 포그라운드 도구 호출 취소를 요청하세요. 중지 기능은 신호 인식(signal-aware) 포그라운드 도구에 취소 신호를 전달하며, 분리된 백그라운드 작업은 독립적인 수명 주기를 유지합니다. 전용 컴포저 컨트롤을 사용하거나, 전송 버튼 메뉴에서 선택하거나, `Command/Ctrl + Shift + .`를 누르세요. 배포 환경에서 활성 공급자 스트림을 중단할 수 없는 경우, 이 작업은 일반적인 제어 방식으로 대체됩니다.

**설정 → 채팅**의 **생성 중 Enter 키 동작**에서 기본 동작을 선택할 수 있습니다. 전송 버튼 메뉴를 통해 개별 메시지에 대해 해당 선택을 재정의할 수 있으며, **Enter 키 입력 시 즉시 제어**를 활성화하면 제어가 기본값일 때 Enter 키를 눌러 더 이른 안전 지점을 요청하게 됩니다.

파일 및 [인용된 발췌문](/docs/features/message_actions#quote-excerpts)은 steer, queue 및 interrupt 메시지와 함께 전송됩니다. 수동으로 선택된 Skill은 실행 중간의 steer에 첨부되는 대신 다음 전체 턴을 위해 준비된 상태로 유지됩니다.

대기 중인 steer는 스트리밍 응답의 끝부분에 나타나며, 서버가 이를 실행에 삽입할 때까지 해당 위치에 머무릅니다. 수신 상태는 **Sending**(전송 중)에서 **Delivered**(전송 완료)로 진행되며, 더 빠른 안전 지점이 요청되면 **Steer sooner requested**(더 빠른 steer 요청됨) 상태가 되고, 마지막으로 인라인 메시지 오른쪽 하단에 이중 체크 표시와 함께 **Applied**(적용됨) 상태가 됩니다. 적용이 확인된 수신 내역은 새로고침 후에도 유지되며 공유 또는 검색 보기에서도 확인할 수 있습니다. 불확실하거나 전송에 실패한 경우에는 확인 체크 표시가 나타나지 않습니다. 승인된 후에는 메시지 메뉴를 통해 steer를 다시 가져와 편집하거나, 대기 중인 후속 작업으로 변환하거나, 취소하여 텍스트와 첨부 파일을 작성기로 복원할 수 있습니다. LibreChat은 더 최신인 초안을 덮어쓰지 않도록 방지합니다. 만약 작성기를 사용할 수 없는 경우, 가져온 메시지를 대기열에 보존합니다. 실패한 steer는 재시도, 편집, 대기열 추가 또는 제거가 가능합니다.

대기 중인 후속 메시지는 입력창 위의 목록에 나타납니다. 각 메시지는 편집(**Edit message**), 제거(**Remove message**), **Send now**를 통한 즉시 전송이 가능하며, 핸들을 드래그하거나 화살표 키를 눌러 순서를 변경할 수 있습니다. 대기 중인 후속 메시지는 실행이 활성화된 동안 스티어(steer)로 변환하거나 **Steer sooner**를 통해 에스컬레이션할 수 있습니다. 진행 중인 스티어는 도구 경계를 기다리는 동안 동일한 에스컬레이션 옵션을 제공합니다. 서버 기반의 대기 중인 메시지를 제거하면 먼저 해당 영구 소스가 취소된 다음, 가능한 경우 빈 입력창으로 복원됩니다. 이전 응답이 중단되거나 실패하면, LibreChat은 영향을 받은 대기 중인 턴을 자동으로 전송하는 대신 검토를 위해 실패한 것으로 표시합니다.

대화 하나당 최대 100개의 활성 대기 턴을 가질 수 있습니다. 각 대기 턴은 최대 16,000자 및 10개의 파일을 허용합니다. 별도로, 하나의 활성 실행은 최대 10개의 보류 중인 steer를 허용하며, 각 steer는 최대 10개의 파일을 포함할 수 있고 [`STEER_MAX_LENGTH`](/docs/configuration/dotenv#agent-conversation-controls)에 의해 제한됩니다. **Steer sooner**는 대기 중인 턴을 내구성 있는 FIFO 레인의 맨 앞으로 옮기는 대신 실시간 steering 경로를 계속 사용합니다.

Redis 기반의 다중 복제본 배포는 generation protocol v2를 자동으로 협상합니다. `v0.8.8-rc1` 이전 릴리스에서 업그레이드할 때는 [generation protocol compatibility guidance](/docs/configuration/redis#generation-protocol-compatibility)를 따르십시오.

### 참고 사항 [#notes]

- 지침, 모델 매개변수, 첨부 파일 및 도구는 편집 권한이 있는 사용자에게만 노출됩니다.
  - 에이전트는 대화 과정에서 지침이나 파일을 포함하여 첨부된 모든 데이터를 유출할 수 있으므로, 편집자(Editor)/소유자(Owner) 권한을 부여하거나 에이전트를 공개하기 전에 지침이 이러한 위험에 대해 충분히 견고한지 확인하십시오.
- 원작자, 관리자, 그리고 소유자 권한을 가진 피허가자만이 공유된 에이전트를 삭제할 수 있습니다.
- 에이전트는 공유되지 않는 한 작성자만 볼 수 있습니다.

## 에이전트 이벤트 전달 [#agent-event-delivery]

LibreChat은 비동기 Agent 이벤트를 위한 소스 중립적 전달 계층을 포함합니다. 배포 소유 어댑터는 검증된 웹훅, 큐 메시지, MCP 이벤트, 채널 이벤트 또는 내부 제품 이벤트를 새로운 Agent 실행(`fire`), 기존에 저장된 Agent 및 브랜치에서의 새로운 턴(`continue`), 또는 활성 실행의 변경(`steer`)으로 정규화할 수 있습니다. 어댑터는 큐에 추가하기 전에 네이티브 소스를 인증하고, 페이로드를 정리하며, 신뢰할 수 있는 대상을 선택할 책임을 집니다.

베타 [Agents API 이벤트 엔드포인트](/docs/features/agents_api#agent-events)는 인증된 `fire`, `continue`, `steer` 접근 권한을 Remote Agents API 키에 노출합니다. 외부 시스템은 소스 액터를 직접적인 하위 Agent에 바인딩하고 추가적인 기능 토글 없이 이벤트 전반에 걸쳐 해당 액터를 계속 유지할 수 있습니다. LibreChat은 API 키로부터 사용자, 테넌트 및 소스 ID를 도출하고, Agent 접근 및 콘텐츠 필터를 적용하며, 멱등성 키(idempotency key)를 요구합니다. 이는 인증되지 않은 범용 웹훅 수신기가 아니므로, 공급자별 어댑터는 이를 호출하기 전에 반드시 네이티브 웹훅 서명을 검증해야 합니다.

실험적인 [Scheduled Chats](/docs/features/scheduled_chats) 기능은 이 계층을 위한 LibreChat의 첫 번째 내장 프로듀서입니다. 이 기능은 저장된 Agent를 위해 반복적인 `fire` 전달을 생성하며, 관리자가 선택하기 전까지는 비활성화되어 있습니다. 분리된(Detached) Subagent는 자식 Agent가 완료된 후 저장된 부모 Agent를 깨우기 위해 자동으로 멱등성(idempotent) `continue` 전달을 사용합니다. 취소된 자식 Agent와 일시적인(ephemeral) 부모 Agent는 제외됩니다.

MongoDB는 제한된 버전의 봉투(bounded versioned envelopes), 멱등성 키(idempotency keys), 순서 레인(ordering lanes), 임대(leases), 재시도 기록, 영구 수신 확인(durable receipts) 및 데드 레터(dead letters)를 저장합니다. 워커는 펜싱된 클레임(fenced claims)과 제한된 지수 백오프(bounded exponential backoff)를 사용하여 최소 한 번 전달(at-least-once delivery)을 수행하며, 성공적인 수신 확인은 90일 후에 만료되고 데드 레터는 명시적인 신뢰할 수 있는 재대기열(trusted requeue)이 필요합니다. Fire 전달은 새로운 대화를 생성합니다. Continue 전달은 정확한 대화 분기에 새로운 턴을 생성하며, 해당 분기가 실행 중이거나, 일시 중지되었거나, 마무리되는 동안에는 지연됩니다. 바운드 액터(bound actors) 또한 자동 메일함을 가지고 있습니다. 하나의 액터는 다음 이벤트를 발송하기 전에 현재 턴의 처리 결과를 기다리며, 서로 다른 액터들은 병렬로 실행될 수 있습니다. Steer 전달은 기존 대화와 생성을 식별해야 하며, 모호한 재시도가 동일한 명령을 두 번 주입하지 못하도록 엄격한 승인(strict admission)을 사용해야 합니다.

바운드 연속(bound continuations)의 경우, 전송 성공은 별도의 지속 가능한 처리 수명 주기를 시작합니다. 전달은 `started`에서 `applied`, `completed_no_action`, `failed` 또는 `cancelled`로 진행됩니다. 소스는 `expectedAction`을 통해 정확한 도구와 선택적 인수 하위 집합을 요구할 수 있습니다. LibreChat은 모델이 작성한 산문이 아닌, 호스트가 관찰한 일치하는 도구 증거를 통해서만 `applied`를 보고합니다. 호환되는 관찰 이벤트는 소스 이벤트당 하나의 멱등성(idempotency) 레코드와 영수증을 유지하면서 제한된 `coalesce.key` 배치를 공유할 수 있습니다. 체크포인트 연속은 호환될 때 사용되며, 그렇지 않은 경우에는 지속 가능한 메시지 기록으로 대체됩니다.

Bound Event Actor는 Ask User 또는 도구 승인을 위해 일시 중지될 수 있으며, LibreChat의 일반적인 human-in-the-loop 인터페이스를 통해 정확히 서명된 actor 호출을 재개할 수 있습니다. 해당 actor의 메일박스는 일시 중지가 재개되거나 해결될 때까지 차단된 상태로 유지되어, 이후의 이벤트가 결정을 앞지르는 것을 방지합니다. 이러한 actor는 내구성이 있는 MongoDB checkpointer를 필요로 합니다. LibreChat은 actor 상태와 요청 기능으로부터 체크포인트 연속성 또는 내구성 있는 기록 재구성을 자동으로 선택하며, 기존 protocol-v1 작업은 소진될 때까지 기록 경로에 유지됩니다.

이벤트 액터(Event Actors)에 의해 시작된 분리된 작업(Detached Actions)은 내장 생성 저장소(generation store)가 지원을 알릴 때 자동으로 활성화됩니다. 액터는 최종 증거(terminal evidence)가 원래의 호출을 재개할 때까지 일시 중단된 상태로 유지되므로, 백그라운드 실행만으로는 `expectedAction`을 충족하지 못합니다. 인메모리 저장소는 프로세스가 살아 있는 동안 이 수명 주기를 일관되게 유지합니다. Redis는 지속 가능한 재시작 복구 및 복제본 핸드오프 기능을 추가합니다. 기능 소유 완료 작업은 혼합 버전 드레인(mixed-version drain) 중에 이전 작업자로부터 격리되며, 운영자가 기능 플래그(feature flag)를 통해 이 동작을 선택할 수는 없습니다.

실행 호스트는 일반적으로 현재 프로세스의 바인딩된 리스너를 호출합니다. [`endpoints.agents.eventDriven.selfUrl`](/docs/configuration/librechat_yaml/object_structure/agents#eventdriven)은 TLS 프론트 도어와 같이 신뢰할 수 있는 내부 허용 경로가 다른 HTTP 오리진을 통과해야 하는 경우에만 구성하십시오.

## 마이그레이션 필요 (v0.8.0-rc3+) [#migration-required-v080-rc3]

<Callout type="warning" title="중요: 에이전트 권한 마이그레이션 필요">
  v0.8.0-rc3 버전부터 LibreChat은 에이전트를 위한 새로운 ACL(Access Control List) 기반 권한 시스템을 사용합니다. 이전 버전에서 업그레이드하는 경우, 기존 에이전트에 계속 액세스할 수 있도록 에이전트 권한 마이그레이션을 실행해야 합니다.
</Callout>

### 마이그레이션의 역할 [#what-the-migration-does]

에이전트 권한 마이그레이션은 에이전트를 단순한 소유권 모델에서 다음과 같은 다중 권한 수준을 갖춘 정교한 ACL 기반 시스템으로 전환합니다:

- **OWNER**: 에이전트에 대한 전체 제어 권한
- **EDITOR**: 에이전트를 보거나 수정할 수 있습니다
- **VIEWER**: 에이전트에 대한 읽기 전용 액세스 권한

이 마이그레이션을 실행하지 않으면, 기존 에이전트는 새로운 권한 인식 API endpoint를 통해 액세스할 수 없게 됩니다.

### 마이그레이션 실행하기 [#running-the-migration]

배포 방식에 따라 적절한 명령어를 선택하세요:

#### 1. 기본 `docker-compose.yml`의 경우 (`docker compose up`을 사용하여 앱을 시작하는 경우): [#1-for-the-default-docker-composeyml-if-you-use-docker-compose-up-to-start-the-app]

**변경 사항 미리보기 (dry run):**

```bash
docker compose exec api npm run migrate:agent-permissions:dry-run
```

**마이그레이션 실행:**

```bash
docker compose exec api npm run migrate:agent-permissions
```

**사용자 지정 배치 크기 (대규모 데이터셋용):**

```bash
docker compose exec api npm run migrate:agent-permissions:batch
```

#### 2. `deploy-compose.yml`의 경우 [#2-for-the-deploy-composeyml]

[Ubuntu Docker 가이드](/docs/remote/docker_linux)를 따랐다면:

**변경 사항 미리보기 (dry run):**

```bash
docker exec -it LibreChat-API /bin/sh -c "cd .. && npm run migrate:agent-permissions:dry-run"
```

**마이그레이션 실행:**

```bash
docker exec -it LibreChat-API /bin/sh -c "cd .. && npm run migrate:agent-permissions"
```

**사용자 지정 배치 크기 (대규모 데이터셋용):**

```bash
docker exec -it LibreChat-API /bin/sh -c "cd .. && npm run migrate:agent-permissions:batch"
```

### 마이그레이션 중 발생하는 일 [#what-happens-during-migration]

- **Private Agents**: 생성자에게만 액세스 권한이 유지됩니다(OWNER 권한을 받음)
- **공유 에이전트(Shared Agents)**: 이전에 공유된 에이전트인 경우, 공개 에이전트(모든 사용자에게 공유됨)로서 적절한 ACL 항목이 부여됩니다.
- **시스템 감지**: LibreChat은 시작 시 마이그레이션되지 않은 에이전트를 자동으로 감지하여 경고를 표시합니다.

Agent Builder UI를 통해 결과로 생성된 에이전트 권한을 조정할 수 있습니다.

<Callout type="info" title="참고">
  동일한 마이그레이션 프로세스가 프롬프트에도 적용됩니다. 기존 프롬프트가 있는 경우, 동일한 명령어를 사용하되 명령어 이름에서 `agent`를 `prompt`로 변경하여 프롬프트 권한 마이그레이션을 실행하세요.
</Callout>

## Agents API (베타) [#agents-api-beta]

LibreChat 에이전트는 API를 통해 프로그래밍 방식으로 액세스할 수도 있으며, 이를 통해 외부 애플리케이션과 스크립트가 OpenAI 호환 SDK 또는 Open Responses 형식을 사용하여 에이전트와 상호 작용할 수 있습니다.

설정 및 사용에 대한 자세한 내용은 [Agents API 문서](/docs/features/agents_api)를 참조하세요.

## 다음 단계는 무엇인가요? [#whats-next]

LibreChat Agents는 LibreChat 내의 경험 전반에 걸쳐 특정 작업 및 워크플로우를 위한 에이전트를 통해 향후 파이프라인을 간소화할 수 있는 앱의 새로운 시대를 열어줍니다.

향후 업데이트에는 다음이 포함될 예정입니다:

- 현재 Agent 경험에 대한 일반적인 개선 사항
- 복잡한 워크플로우를 위한 멀티 에이전트 오케스트레이션
- 다양한 기능을 위한 에이전트 사용자 지정 기능: 제목 지정(채팅 스레드 이름 지정), 메모리 관리(사용자 컨텍스트/기록), 프롬프트 향상(입력 지원/예측)
- 더 많은 도구, 구성 가능한 도구 매개변수, 동적 도구 생성.

또한, 이번 업데이트는 LibreChat의 새로운 패러다임을 제시합니다. 기본 아키텍처가 앱에 꼭 필요한 쇄신을 제공하여 사용자 경험과 전반적인 앱 성능을 모두 최적화하기 때문입니다.

주목할 만한 최적화 중 하나를 강조하자면, 약 1000 토큰의 AI 생성은 기존 endpoint(작성 시점 기준으로 Agents 및 AWS Bedrock을 제외한 모든 endpoint 옵션)를 사용할 경우 약 1MB의 데이터를 전송하게 됩니다.

에이전트를 사용하면 동일한 생성 작업에서 약 52kb의 데이터만 전송되므로 데이터 전송량이 95% 감소하며, 이는 서버와 사용자 기기의 부하를 그만큼 줄여줍니다.

---

LibreChat의 AI Agents는 코딩 지식 없이도 전문화된 어시스턴트를 생성할 수 있는 강력한 방법을 제공하며, 동시에 선호하는 AI 모델 및 제공업체와 유연하게 작업할 수 있도록 지원합니다.
