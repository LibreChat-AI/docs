<Callout type="warning" title="베타 기능">
Agents API는 현재 베타 버전입니다. 안정적인 릴리스를 위해 반복적으로 개선하는 과정에서 endpoint, 요청/응답 형식 및 동작이 변경될 수 있습니다.
</Callout>

LibreChat은 추론 및 이벤트 전달 API를 통해 에이전트를 외부 애플리케이션, 스크립트 및 서비스에 노출합니다.

## 개요 [#overview]

Agents API는 두 가지 추론 인터페이스, 인증된 이벤트 전달, 그리고 베타 관리 경로를 제공합니다:

- **OpenAI 호환 Chat Completions** — `POST /api/agents/v1/chat/completions`
- **Open Responses API** — `POST /api/agents/v1/responses`
- **에이전트 이벤트(Agent Events)** — `POST /api/agents/v1/events`
- **에이전트 관리** — `/api/agents/v1/agents`
- **스킬 관리** — `/api/agents/v1/skills`

추론 인터페이스는 API-key 인증, 선택적 OIDC 인증 및 스트리밍 응답을 지원합니다. Agent Events는 Remote Agents API-key 인증을 사용하여 LibreChat이 각 전달을 안정적인 소스 ID에 바인딩할 수 있도록 합니다. 반면 관리 경로는 OIDC 머신 클라이언트를 기존 LibreChat 사용자 및 테넌트 하나에 바인딩하는 배포 허용 목록(allowlist)을 사용합니다.

LibreChat은 에이전트를 서비스하기 위한 기본 API 프레임워크로 [Open Responses](https://www.openresponses.org/)를 채택하고 있습니다. Chat Completions endpoint는 기존 OpenAI 호환 도구와의 하위 호환성을 제공하지만, Open Responses endpoint는 향후의 발전 방향을 나타냅니다.

## Agents API 활성화하기 [#enabling-the-agents-api]

Agents API는 `remoteAgents` 인터페이스 구성 뒤에 게이트되어 있습니다. 모든 권한은 기본적으로 `false`로 설정됩니다.

```yaml filename="librechat.yaml"
interface:
  remoteAgents:
    use: true
    create: true
```

사용 가능한 모든 옵션은 [Interface Configuration — remoteAgents](/docs/configuration/librechat_yaml/object_structure/interface#remoteagents)를 참조하세요.

**참고:** 관리자 사용자는 기본적으로 모든 원격 에이전트 권한이 활성화되어 있습니다.

### OpenAPI 사양 및 대화형 문서 [#openapi-specification-and-interactive-docs]

LibreChat은 `/api/openapi.json`에서 공개 Agents API 사양을, `/api/docs`에서 대화형 Swagger UI 문서를 제공할 수 있습니다. 두 경로 모두 기본적으로 비활성화되어 있습니다. 최상위 `openapi` 설정을 사용하여 활성화하십시오:

```yaml filename="librechat.yaml"
openapi:
  enabled: true
```

이 사양은 이 페이지에 설명된 공개 추론(inference), 이벤트, 에이전트(Agent) 관리 및 스킬(Skill) 관리 경로를 다룹니다. 배포 환경에서 API 문서를 노출할 의도가 없다면 해당 경로를 비활성화 상태로 유지하세요.

## API Key Management [#api-key-management]

`remoteAgents.use` 및 `remoteAgents.create`가 활성화되면, 사용자는 LibreChat UI에서 API 키를 생성할 수 있습니다. 이 키들은 Agents API에 대한 요청을 인증하는 데 사용됩니다.

## 인증 [#authentication]

Agents API는 독립적으로 또는 함께 사용할 수 있는 두 가지 인증 방법을 지원합니다.

### API Key [#api-key]

API 키 인증은 기본적으로 활성화되어 있습니다. `remoteAgents.use` 및 `remoteAgents.create`가 활성화되면 LibreChat UI에서 API 키를 생성하십시오.

```bash
Authorization: Bearer <YOUR_API_KEY>
```

### OIDC Bearer Token [#oidc-bearer-token]

인프라에 이미 OIDC 공급자가 있는 기계 간(machine-to-machine) 시나리오의 경우, LibreChat API 키 없이 OIDC Bearer 토큰으로 직접 인증할 수 있습니다.

`librechat.yaml`에서 OIDC 인증을 구성하세요:

```yaml filename="librechat.yaml"
endpoints:
  agents:
    remoteApi:
      auth:
        apiKey:
          enabled: false
        oidc:
          enabled: true
          issuer: https://auth.example.com/realms/myrealm
          # jwksUri is optional and auto-discovered from issuer if omitted
          audience: my-client-id
```

그런 다음 OIDC 액세스 토큰을 사용하여 API를 호출하세요:

```bash
curl -X POST https://your-librechat-instance/api/agents/v1/responses \
  -H "Authorization: Bearer YOUR_OIDC_ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"model": "agent_abc123", "input": "Hello!"}'
```

<Callout type="info">
  OIDC 토큰은 LibreChat에 이미 존재하는 사용자의 것이어야 합니다. 일치 여부는 `sub` 클레임을 우선적으로 사용하며, 그 다음으로 `email`, `preferred_username` 또는 `upn`을 순차적으로 확인합니다.
</Callout>

모든 구성 옵션은 [Agents Endpoint - remoteApi](/docs/configuration/librechat_yaml/object_structure/agents#remoteapi)를 참조하세요.

<Callout type="warning" title="Agent Events에는 API 키가 필요합니다">
  OIDC 전용 인증은 Agent Events 엔드포인트에서 지원되지 않습니다. 바인딩 생성, 이벤트 대기열 추가 및 전달 상태 폴링 시에는 Remote Agents API 키를 사용하세요.
</Callout>

## 에이전트 관리 API [#agent-management-api]

베타 Agent Management API를 사용하면 브라우저 세션 없이도 서비스가 Agent와 그에 연결된 리소스를 관리할 수 있습니다. 이는 추론 및 Agent 이벤트와는 독립적으로 인증되며, [`endpoints.agents.managementApi`](/docs/configuration/librechat_yaml/object_structure/agents#managementapi)에 구성된 OIDC 머신 토큰만 허용됩니다.

구성된 각 OAuth 클라이언트는 기존의 LibreChat `userId` 및 `tenantId` 하나에 바인딩됩니다. 토큰 검증 후, 모든 요청은 해당 사용자로 실행되며 사용자의 현재 역할 권한, 에이전트 및 스킬 ACL, 공급자 제한, 도구 권한, 파일 제한 및 테넌트 격리를 유지합니다. 클라이언트 바인딩은 사용자를 관리자로 만들거나 사용자가 달리 관리할 수 없는 리소스에 대한 액세스 권한을 부여하지 않습니다.

### Agent Routes [#agent-routes]

| 메서드 | 경로 | 목적 |
| -------- | ------------------------------------------ | -------------------------------------------- |
| `POST`   | `/api/agents/v1/agents`                    | 에이전트 생성 |
| `GET`    | `/api/agents/v1/agents`                    | 액세스 가능한 에이전트 목록 조회 |
| `GET`    | `/api/agents/v1/agents/{id}`               | 액세스 가능한 특정 에이전트 읽기 |
| `PATCH`  | `/api/agents/v1/agents/{id}`               | 에이전트 업데이트 |
| `DELETE` | `/api/agents/v1/agents/{id}`               | 에이전트 삭제 |
| `POST`   | `/api/agents/v1/agents/{id}/files`         | 에이전트 리소스 파일 업로드 및 첨부 |
| `GET`    | `/api/agents/v1/agents/{id}/files`         | 에이전트가 액세스할 수 있는 첨부 파일 목록 조회 |
| `DELETE` | `/api/agents/v1/agents/{id}/files/{fileId}` | 에이전트에서 첨부 파일 제거 |

Agent 생성 및 업데이트 페이로드는 Agent Builder와 동일한 외부 지원 필드를 사용하며, 알 수 없는 최상위 필드는 거부합니다. 생성 시에는 `model`이 필요하며, 업데이트 시에는 제공된 필드만 허용됩니다. 응답에는 지원되는 Agent 구성과 함께 `id`, `provider`, nullable `model`, `version`, `createdAt`, `updatedAt`이 포함되며, 지속성 소유권 필드는 제외됩니다.

목록은 1에서 100까지의 `limit`을 허용하며, 기본값은 20이고, 불투명한 `cursor`를 사용합니다. `has_more`가 true일 경우, 반환된 `after` 값을 다음 커서로 전달하십시오. 클라이언트에서 커서를 디코딩하거나 생성하지 마십시오.

```bash
curl https://your-librechat-instance/api/agents/v1/agents?limit=20 \
  -H "Authorization: Bearer YOUR_MACHINE_ACCESS_TOKEN"
```

```bash
curl -X POST https://your-librechat-instance/api/agents/v1/agents \
  -H "Authorization: Bearer YOUR_MACHINE_ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Release assistant",
    "provider": "openAI",
    "model": "gpt-5.6",
    "instructions": "Prepare concise release notes from verified changes."
  }'
```

파일 업로드는 `multipart/form-data`를 사용하며, 하나의 `file`과 `context`, `file_search` 또는 `execute_code`와 같은 `tool_resource` 값을 포함합니다. LibreChat은 리소스를 첨부하기 전에 배포 기능, 역할 부여, 업로드 속도 제한, 파일당 제한, 파일 개수 제한 및 총 크기 제한 검사를 적용합니다. 파일을 제거하려면 해당 Agent에 대한 편집 권한이 필요하며, 이는 기본 파일 승인 규칙을 약화시키지 않습니다.

### Skill Routes [#skill-routes]

| 메서드 | 경로 | 목적 |
| ------- | ---------------------------------------------------- | ------------------------------------- |
| `GET`   | `/api/agents/v1/skills`                              | 액세스 가능한 Skill 목록 조회 |
| `GET`   | `/api/agents/v1/skills/{id}`                         | 액세스 가능한 Skill 하나 읽기 |
| `PATCH` | `/api/agents/v1/skills/{id}`                         | 지원되는 Skill 메타데이터 업데이트 |
| `GET`   | `/api/agents/v1/skills/{id}/files`                   | Skill 내 파일 목록 조회 |
| `GET`   | `/api/agents/v1/skills/{id}/files/{relativePath}`    | Skill 파일 하나 읽기 |
| `PUT`   | `/api/agents/v1/skills/{id}/files/{relativePath}`    | 지원되는 파일 하나 생성 또는 교체 |

Skill 작업은 바인딩된 사용자에게 표시되는 Skill로 제한됩니다. 읽기 작업에는 Skill 액세스 권한이 필요하며, 메타데이터 또는 파일 쓰기 작업에는 해당 편집 및 Skill 작성 권한이 필요합니다. 경로는 Skill 루트 아래에서 정규화되며, 경로 탐색, 지원되지 않는 파일 및 용량을 초과하는 콘텐츠는 거부됩니다.

### 오류 및 인증 [#errors-and-authentication]

관리 응답은 `invalid_request`, `not_found`, `permission_denied`, `conflict` 또는 `internal_error` 코드가 포함된 구조화된 오류를 사용합니다. 리소스 권한 부여 실패는 호출자가 접근할 수 없는 ID를 탐색하지 못하도록 `not_found`로 반환될 수 있습니다.

머신 토큰은 만료되지 않아야 하며, 구성된 발급자와 일치해야 하고, `azp` 또는 `client_id`를 통해 허용 목록에 있는 클라이언트 중 하나를 식별해야 하며, 구성된 주체(subject) 규칙을 충족해야 합니다. 기본적으로 토큰은 구성된 대상(audience)과도 일치해야 합니다. `aud` 대신 `client_id`가 포함된 머신 액세스 토큰을 발급하는 Amazon Cognito와 같은 제공업체의 경우, `tokenUse: access`를 설정하고 `audience`를 생략하며 `requiredScopes`를 통해 필요한 OAuth 범위를 요구하십시오. 구성이 누락되었거나 자격 증명이 유효하지 않으면 `401`이 반환되며, 삭제 중인 바인딩된 계정은 `409`를 반환합니다. 전체 클레임 및 바인딩 규칙은 [`managementApi.auth.oidc`](/docs/configuration/librechat_yaml/object_structure/agents#managementapiauthoidc) 및 [`managementApi.auth.clients`](/docs/configuration/librechat_yaml/object_structure/agents#managementapiauthclients)를 참조하십시오.

## Endpoints [#endpoints]

### Chat Completions (OpenAI-compatible) [#chat-completions-openai-compatible]

```
POST /api/agents/v1/chat/completions
```

LibreChat 인스턴스를 가리키도록 설정하여 OpenAI 호환 SDK를 사용하세요. `model` 매개변수는 에이전트 ID에 해당합니다.

**curl을 사용한 예시:**
```bash
curl -X POST https://your-librechat-instance/api/agents/v1/chat/completions \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "agent_abc123",
    "messages": [
      {"role": "user", "content": "Hello, what can you help me with?"}
    ],
    "stream": true
  }'
```

**OpenAI SDK (Python) 사용 예시:**
```python
from openai import OpenAI

client = OpenAI(
    base_url="https://your-librechat-instance/api/agents/v1",
    api_key="YOUR_API_KEY"
)

response = client.chat.completions.create(
    model="agent_abc123",
    messages=[{"role": "user", "content": "Hello!"}],
    stream=True
)

for chunk in response:
    print(chunk.choices[0].delta.content, end="")
```

### 모델 목록 (List Models) [#list-models]

```
GET /api/agents/v1/models
```

사용 가능한 에이전트를 모델로 반환합니다. API 키로 어떤 에이전트에 액세스할 수 있는지 확인하는 데 유용합니다.

### Open Responses API [#open-responses-api]

```
POST /api/agents/v1/responses
```

Open Responses endpoint는 OpenAI가 시작하고 오픈 소스 AI 커뮤니티가 구축한 개방형 추론 표준인 [Open Responses specification](https://www.openresponses.org/)을 따릅니다. 이는 추론, 도구 사용, 구조화된 출력 및 스트리밍 의미론적 이벤트에 대한 기본 지원을 통해 에이전트 워크플로우를 위해 설계되었습니다.

```bash
curl -X POST https://your-librechat-instance/api/agents/v1/responses \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "agent_abc123",
    "input": "What is the weather today?"
  }'
```

#### Caller-Executed Function Tools [#caller-executed-function-tools]

Open Responses endpoint는 호출자가 제공하는 표준 `function` 도구를 허용합니다. LibreChat은 이러한 정의를 모델에 노출하지만 직접 실행하지는 않습니다. 모델이 도구를 선택하면, 응답에는 호출자가 실행할 수 있는 `function_call` 출력 항목이 포함됩니다.

계속하려면, 반환된 `function_call` 항목과 그에 대응하는 `function_call_output` 항목을 순서대로 `input`에 포함하여 새로운 요청을 보내야 합니다. 이 핸드오프는 상태를 저장하지 않습니다(stateless). 즉, 일시 중단된 실행(suspended run)을 생성하지 않으며, `previous_response_id`만으로는 재현된 도구 교환을 대체할 수 없습니다.

```json
{
  "model": "agent_abc123",
  "input": [
    {
      "type": "function_call",
      "call_id": "call_abc123",
      "name": "lookup_order",
      "arguments": "{\"order_id\":\"A-42\"}"
    },
    {
      "type": "function_call_output",
      "call_id": "call_abc123",
      "output": "{\"status\":\"shipped\"}"
    }
  ]
}
```

Caller 도구 이름은 문자, 숫자, 밑줄, 하이픈을 포함할 수 있습니다. 이름은 고유해야 하며 서버에서 제공하는 도구를 대체할 수 없습니다. Caller가 실행하는 도구는 해당 턴에서 선택된 유일한 도구여야 합니다. 만약 모델이 이를 서버에서 실행되는 도구와 혼용할 경우, LibreChat은 모델에게 Caller 도구만 단독으로 다시 시도하도록 요청합니다.

LibreChat에서 실행되는 에이전트 도구의 경우, 두 헤드리스 추론 엔드포인트 모두 `deny`, `ask` 및 프로그래밍 방식의 훅을 포함하는 활성화된 [`endpoints.agents.toolApproval`](/docs/configuration/librechat_yaml/object_structure/agents#toolapproval) 정책을 강제합니다. 이러한 호출에는 대화형 승인/재개 채널이 없으므로, `deny` 및 `ask`는 승인 프롬프트를 여는 대신 도구를 차단합니다. API 클라이언트가 무인으로 실행할 수 있어야 하는 도구에 대해서만 명시적 허용(allow)을 구성하십시오. 정책이 비활성화되면 해당 승인 훅은 실행되지 않습니다. 호출자가 실행하는 함수 도구는 호출자의 책임으로 남습니다.

## Agent Events [#agent-events]

Agent Events를 사용하면 인증된 컨트롤러나 소스 어댑터가 Agent에 지속 가능한 작업을 전달할 수 있습니다. 이벤트 전달은 베타 기능이며, 요청, 응답 및 런타임 동작이 변경될 수 있습니다.

endpoint는 인증된 사용자, 테넌트 및 API 키를 사용하며, 대상 Agent는 기존 Remote Agents 권한에 따라 해당 사용자에게 보여야 합니다. Agent Event 요청은 전용 [`rateLimits.agentEvents`](/docs/configuration/librechat_yaml/object_structure/config#ratelimits) 버킷을 사용합니다.

### 이벤트 전달 [#deliver-an-event]

```http
POST /api/agents/v1/events
Authorization: Bearer <REMOTE_AGENTS_API_KEY>
Idempotency-Key: webhook-42-resource-7
Content-Type: application/json

{
  "mode": "fire",
  "event": {
    "id": "resource-7-ready-3",
    "type": "resource.ready",
    "occurredAt": 1786967999000,
    "payload": { "resourceId": "resource-7" }
  },
  "target": { "agentId": "agent_abc123" },
  "input": "Resource resource-7 is ready. Inspect it and report the result.",
  "orderingKey": "resource-7"
}
```

정확히 하나의 `Idempotency-Key` 헤더를 전송하고, 동일한 소스 이벤트에서 타겟으로의 전달을 재시도할 때 이를 재사용하십시오. 키는 1-256자의 영문자, 숫자 또는 `._~:/+=-` 문자를 포함해야 합니다. 서로 다른 전달 콘텐츠로 키를 재사용하면 충돌이 발생합니다.

호출자는 이벤트 `id`, `type`, `occurredAt` 및 정리된(sanitized) `payload`를 제공합니다. LibreChat은 호출자가 제공한 `event.source`를 인증된 API 키 ID로 대체하고 사용자, 테넌트, 요청 ID 및 수신 시간을 파생합니다. 허용된 전달 항목은 지속적으로 저장되므로 이벤트 페이로드에 자격 증명이나 전송 비밀 정보를 포함하지 마십시오.

`orderingKey`는 선택 사항입니다. 서로 다른 소스에서 오는 전달 항목이 동일한 리소스에 대해 순서대로 유지되어야 할 때 안정적인 값을 사용하세요.

성공적인 요청은 `202 Accepted`, 불투명한 전달 `id`, 현재 상태 및 `Location` 헤더를 반환합니다. 해당 위치를 폴링(poll)하십시오:

```http
GET /api/agents/v1/events/{delivery_id}
Authorization: Bearer <SAME_REMOTE_AGENTS_API_KEY>
```

전송 상태는 `pending`, `leased`, `succeeded` 또는 `dead`일 수 있습니다. 상태 응답에는 시도 횟수와 타임스탬프, 그리고 완료 시 결과 또는 공개 오류 메시지가 포함됩니다. 저장된 페이로드, 순서 지정 키, 재시도 기록 또는 작업자 식별 정보는 노출되지 않습니다. 상태 접근 권한은 동일한 사용자, 테넌트 및 API 키 소스로 범위가 제한됩니다.

바인딩된 `continue`의 경우, `succeeded`는 요청된 작업이 완료되었음을 의미하는 것이 아니라 에이전트 턴(Agent turn)이 승인되었음을 의미합니다. 따라서 해당 상태는 `started`와 그 뒤를 잇는 `applied`, `completed_no_action`, `failed`, 또는 `cancelled` 중 정확히 하나로 구성되는 지속적인 `handling` 수명 주기를 노출합니다.

Action-aware 소스는 도구 이름과 선택적 인수 하위 집합을 포함하는 `expectedAction`을 포함할 수 있습니다. LibreChat은 해당 생성이 호스트가 관찰한 도구 증거와 계약이 일치하는 상태로 완료될 때만 `applied`를 보고합니다. 모델이 작성한 산문은 증거로 인정되지 않습니다. `fire`, `steer` 및 바인딩되지 않은 `continue` 전달은 `expectedAction`을 거부합니다.

성공적인 `fire` 결과에는 이후 `steer` 이벤트가 타겟팅할 수 있는 대화 및 생성 식별자가 포함됩니다.

### 이벤트 기반 자식 에이전트 (Event-Driven Child Agents) [#event-driven-child-agents]

외부 시스템은 소스 액터를 직접적인 하위 Agent에 바인딩한 다음, 이벤트 전반에 걸쳐 동일한 하위 대화를 계속할 수 있습니다. 바인딩된 하위 연속(child continuation)은 API 키 식별, 바인딩 소유권, 부모 관계 및 Agent 권한 부여 확인이 성공하면 자동으로 이루어지며, 별도의 기능 토글은 없습니다.

이후 턴을 전달할 동일한 API 키로 액터를 등록하세요:

```http
POST /api/agents/v1/events/bindings
Authorization: Bearer <REMOTE_AGENTS_API_KEY>
Idempotency-Key: championship-7-player-hanae
Content-Type: application/json

{
  "actorId": "hanae-kobayashi",
  "parentConversationId": "director-conversation-id",
  "parentMessageId": "director-message-id",
  "target": { "agentId": "agent_hanae" }
}
```

`actorId`는 최대 128자까지 포함할 수 있습니다. 부모는 일반 Agent 대화여야 하며, 대상은 해당 Agent의 직접적인 Subagent 중 하나이거나 허용된 self-spawn으로 구성되어야 합니다. 새로운 바인딩은 `201`을 반환하며, 멱등성 재시도(idempotent replay)는 `200`을 반환합니다. 두 응답 모두 `id`, `actorId`, `agentId`, `threadId`를 포함합니다.

반환된 바인딩 ID를 사용하여 이후 턴을 전송하세요:

```http
POST /api/agents/v1/events
Authorization: Bearer <SAME_REMOTE_AGENTS_API_KEY>
Idempotency-Key: game-12-ply-17-hanae
Content-Type: application/json

{
  "mode": "continue",
  "bindingId": "evtbind_...",
  "event": {
    "id": "game-12-ply-17",
    "type": "chess.turn.ready",
    "occurredAt": 1786968000000,
    "payload": { "gameId": "game-12", "expectedPly": 17 }
  },
  "input": "Your clock is running. Read the position and submit one legal move.",
  "expectedAction": {
    "tool": "submit_move",
    "arguments": { "gameId": "game-12" }
  }
}
```

LibreChat은 디스패치 직전 바인딩에서 하위 Agent, 스레드, 최신 브랜치 리프(leaf) 및 순서 지정 레인을 확인합니다. 호출자가 제공한 대상 및 순서 지정 필드는 바인딩된 연속(continuation)을 리디렉션할 수 없습니다. 요청의 `Idempotency-Key`는 전송 재시도, 생성 리싱(leasing), 지속 메시지, 실시간 활동 및 이후의 HITL 재개 전반에 걸쳐 해당 하위 턴에 대한 안정적인 공개 식별자가 됩니다.

각 바인딩에는 자동 지속형 메일함이 있습니다. 다음 이벤트는 현재 턴이 `applied`, `completed_no_action`, `failed` 또는 `cancelled` 상태에 도달할 때까지 대기열에 유지됩니다. 서로 다른 바인딩은 독립적으로 유지되며 병렬로 실행될 수 있습니다. 체크포인트 연속은 호환되는 초기화된 턴에 대해서만 시도됩니다. 체크포인트가 없거나 복원할 수 없는 경우, LibreChat은 수신 확인, 권한 부여 또는 예상 작업 확인을 약화시키지 않으면서 지속형 메시지 기록으로 대체합니다.

바운드 액터(bound actor)는 사용자에게 묻기(Ask User) 또는 도구 승인을 위해 일시 중지할 수 있습니다. LibreChat은 보류 중인 작업을 노출하기 전에 정확한 서명된 일시 중단 상태를 유지하며, 해당 액터 호출이 재개되거나 해결될 때까지 바인딩의 메일박스는 차단된 상태로 유지됩니다. 이벤트 액터(Event Actors)는 영구적인 MongoDB 체크포인터를 필요로 하며, `type: memory`와는 호환되지 않습니다. LibreChat은 생성 프로토콜 v2를 협상하고 체크포인트 또는 기록 연속성을 자동으로 선택합니다. 기존 프로토콜 v1 작업은 완료될 때까지 영구 기록 경로에 유지됩니다. 혼합 버전 배포 요구 사항은 [Generation Protocol Compatibility](/docs/configuration/redis#generation-protocol-compatibility)를 참조하세요.

### 관찰 이벤트 통합 (Coalescing Observational Events) [#coalescing-observational-events]

여러 `continue` 이벤트가 상호 교환 가능한 관측값임을 증명할 수 있는 소스에 동일한 소스 정의 `coalesce.key`를 부여할 수 있습니다:

```json
{
  "mode": "continue",
  "bindingId": "evtbind_...",
  "event": {
    "id": "championship-7-game-12-move-18",
    "type": "chess.move.completed",
    "occurredAt": 1786968000750,
    "payload": { "gameId": "game-12", "ply": 18 }
  },
  "input": "A tournament game advanced.",
  "coalesce": { "key": "championship-commentary" }
}
```

LibreChat은 최대 750ms 동안 호환되는 이벤트를 수집하며, 최대 8개의 이벤트와 총 512 KiB의 엔벨로프를 수집합니다. 자식 프로세스는 하나의 결정론적 배치 문서를 수신하지만, 각 소스 이벤트는 고유한 `Idempotency-Key`, 전달 기록 및 수신 확인을 유지합니다.

조치할 필요가 없는 관찰 결과에 대해서만 병합(coalescing)을 사용하십시오. `fire`, `steer`, 바인딩되지 않은 `continue`, 그리고 `expectedAction`이 포함된 전달 항목에 대해서는 거부됩니다. 명령, 승인, HITL 요청, 펜스 또는 개별 타이밍이 중요한 이벤트에는 사용하지 마십시오.

인증된 상위 대화에서 각 바인딩된 액터는 이를 소유한 상위 메시지 아래에 나타납니다. Subagent 패널을 통해 액터와 턴 간을 전환하고, 이전 활동을 로드하며, 턴을 확장하여 전체 바인딩된 활동을 확인할 수 있습니다. 이벤트 세부 정보에는 유형, 소스, 발생 시간 및 예상 작업이 포함됩니다. 원시 추론 텍스트를 제외하고 표시 가능한 실행 단계, 도구, 메시지 및 추론 마커가 포함됩니다. 상위 인덱스는 바인딩된 소스 창에서 최대 64개의 하위 스레드와 하위당 20개의 최근 작업을 반환하며, 완전함을 암시하는 대신 잘림(truncation)을 보고하고 응답을 96 KB로 제한합니다. 이는 상위, 사용자 및 테넌트 권한이 부여되며, 바인딩, 소스 키 ID, 임대 토큰 및 작업자 상태는 프로젝션에 포함되지 않습니다.

자식 스레드는 일반적인 대화 탐색에서 숨겨진 상태로 유지되며 사람의 채팅 경로에서는 읽기 전용으로 처리됩니다. 또한 부모의 임시 또는 만료 정책을 상속받으며, 직접적인 자식 수준은 하나로 제한됩니다. 바인딩 ID만으로는 액세스 권한이 부여되지 않으며, 연속(continuation)은 이를 생성한 사용자, 테넌트 및 API 키로 범위가 지정됩니다.

### 분리된 이벤트 액터 작업 (Detached Event Actor Actions) [#detached-event-actor-actions]

Event Actor 턴은 적격한 Action을 분리하여 내구성 있게 완료할 수 있습니다. Action이 실행되는 동안 전달은 처리 수명 주기 내에 유지되며, 내구성 있는 최종 증거가 원래 서명된 actor 호출을 재개하고, 호스트가 관찰한 결과 도구 증거만이 `expectedAction`을 충족할 수 있습니다. 재실행 및 경쟁 복제본은 동일한 예약된 Action을 두 번 시작할 수 없습니다. LibreChat이 외부 부작용이 시작되었는지 여부를 확인할 수 없는 경우, 무작위로 재시도하는 대신 해당 시작을 격리합니다.

LibreChat은 선택된 내장 생성 저장소가 지원을 알릴 때 이 내부 완료 작업을 자동으로 활성화합니다. 인메모리 저장소는 시작, 완료 및 연속 작업을 하나의 프로세스에서 실행하며 프로세스가 종료된 후에는 해당 작업을 복구할 수 없습니다. Redis 생성 스트림은 지속 가능한 재시작 복구 및 복제본 핸드오프를 추가합니다. 기능 소유의 전달 및 복구 기록은 혼합 버전 드레인(drain) 중에 이전 클레이머(claimer)에게는 보이지 않게 유지되며, 운영자가 관리하는 생산자 플래그는 없습니다.

## 토큰 사용량 추적 [#token-usage-tracking]

모든 Agent API 추론 요청은 토큰 사용량 설정이 구성된 경우 사용자의 잔액을 기준으로 토큰 사용량을 추적합니다. 스트리밍 및 비스트리밍 응답 모두 청구되는 모든 기본 Agent(primary-Agent) 및 하위 Agent(Subagent) 모델 호출을 최상위 합계로 집계합니다. 응답에는 식별 정보가 없는 `primary` 및 `subagent` 토큰 분석도 포함됩니다. 캐시 및 추론 토큰 세부 정보는 제공업체가 이를 보고하는 경우 포함됩니다.
