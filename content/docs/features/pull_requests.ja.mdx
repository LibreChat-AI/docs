チャットが添付されたワークスペースでコードを実行すると、ワーカーは現在チェックアウトしているgitブランチとコミットを報告します。LibreChatはそのブランチを使用して、サーバー上に保持されているトークン、またはユーザー自身の接続済みアカウントを使用して、一致するプルリクエスト（GitLabの場合はマージリクエスト）を検索し、以下の2箇所に表示します。

- **チャットヘッダー**: プルリクエストアイコン、CIのドット、プルリクエストのタイトルを含むチップです。ホバーまたはフォーカスするとカードが開きます。
- **サイドバーの会話リスト**: 行の末尾に同じアイコンとCIドットが表示されます。行には会話自体のタイトルが保持され、プルリクエストのタイトルはカード内にのみ表示されます。

プルリクエストは、GitHub（デフォルト）、GitLab、または Bitbucket Cloud から取得できます。1つのデプロイメントでは、1つのプロバイダーのみを使用します。

## 要件 [#requirements]

チャットでプルリクエストを表示するには、以下のすべての条件が満たされている必要があります：

1. LibreChatにはトークンおよびリポジトリスコープ（`allowedRepositories`または`allowAllRepositories`）が存在するか、ユーザーが自身の接続アカウントを使用します。[Setup](#setup)および[Per-user accounts](#per-user-accounts)を参照してください。
2. このチャットでは、単なるチャットではなく、**アタッチされたコードワークスペース**（コードワーカー）を使用します。
3. ワーカーは自身のブランチを報告します。これには `LibreChat-AI/code-interpreter` の PR #311 以降からビルドされたワーカーが必要であり、Code API 上で `CODEAPI_BRIDGE_LANE_GIT=true` が設定されている必要があります。詳細は [Code Interpreter](/docs/features/code_interpreter#attached-environments-and-pairing) を参照してください。

この機能はデフォルトで有効になっています。トークンやリポジトリのスコープがない場合、この機能は休止状態となり、すべてのチャットでエラーを表示することなく、プルリクエストは表示されません。`enabled: false` を設定すると、他の設定に関係なくこの機能は無効になります。

例外として、`token` が設定されているものの、対応する環境変数が空であるか欠落している場合があります。この場合、ルックアップは `NOT_CONFIGURED` となり、サイドバーの行には再試行ボタン付きの警告アイコンが表示されます。

## セットアップ [#setup]

### 1. プロバイダーとホストを選択する [#1-choose-the-provider-and-host]

`provider` はプルリクエストの保存先を選択します：

| `provider` | サービス | デフォルトの `host` |
| ------------------ | ------------------------------------------------------------------------------------------------------ | --------------- |
| `github` (デフォルト) | GitHub.com、GitHub Enterprise Server、または GitHub Enterprise Cloud のデータレジデンシーテナント (`*.ghe.com`) | `github.com` |
| `gitlab` | gitlab.com または自己管理型 GitLab 上のマージリクエスト | `gitlab.com` |
| `bitbucket` | Bitbucket Cloud のみ | `bitbucket.org` |

GitHub Enterprise Server、`*.ghe.com` テナント、またはセルフマネージドの GitLab の場合にのみ `host` を設定してください：

- これはホスト名であり、URLではありません。スキームやパスは含めず、例として `github.example.com` のように記述します。
- 明示的なポート（1から65535まで）を指定できます。例として `git.example.com:8443` などがあります。`:443` は https のデフォルトであるため、省略されます。
- GitHubでは、LibreChatは `github.com` に対して `api.github.com` を、`*.ghe.com` テナントに対して `api.<host>` を、そしてEnterprise Serverに対しては `https://<host>/api/v3` を呼び出します。GitLabでは、`https://<host>/api/v4` および `https://<host>/api/graphql` を呼び出します。
- Bitbucketは他のホストを受け入れません。`bitbucket.org` 以外の `host` を指定すると、トークンを他の場所に送信するのではなく、機能が無効になります。

```yaml filename="librechat.yaml"
endpoints:
  agents:
    pullRequests:
      provider: 'gitlab'
      host: 'gitlab.example.com'
      allowedRepositories:
        - 'platform/backend/api'
        - 'platform/frontend/*'
```

<Callout type="info" title="librechat.yaml からのみ読み込む">
  `provider`、`host`、および `oauth` は `librechat.yaml` からのみ読み込まれます。これらのキーに対するロール、グループ、ユーザー、およびテナントの設定オーバーライドは無視されます。これは、トークンの送信先およびユーザーがアクセスを許可するアプリを決定するためです。オーバーライドによってトークンを別のサービスにリダイレクトすることはできません。`token` や `allowedRepositories` などの他のキーは、引き続きプリンシパルごとに異なる設定が可能です。
</Callout>

### 2. トークンを作成する [#2-create-a-token]

サーバーのトークンは、自身のアカウントを接続していないすべてのユーザーに対して使用されます。

**GitHub**: 表示したいリポジトリのみに制限されたファイングレイン（きめ細かな）トークンを使用し、権限を**読み取り専用**に設定してください：

- プルリクエスト
- チェック
- 目次

<Callout type="warning" title="権限エラーのモード">
  **Checks**がない場合、一致したプルリクエストはすべて読み込みに失敗します。**Contents**がない場合、前回のコマンド実行時からブランチが更新されたチャットは読み込みに失敗します。これは、LibreChatがコミットを比較して一致を確認するためです。
</Callout>

**GitLab**: `read_api` スコープを持つ個人、グループ、またはプロジェクトのアクセストークン。

**Bitbucket Cloud**: リポジトリ、プロジェクト、またはワークスペースのアクセストークンを、Bearerトークンとして送信します。LibreChatはプルリクエスト、その差分統計(diffstat)、コミットステータス、およびマージベースを読み取るため、プルリクエストとリポジトリへの読み取りアクセス権を付与してください。

### 3. LibreChatにトークンを渡す [#3-give-librechat-the-token]

LibreChatは、以下の順序でトークンを検索します：

1. `token: "${MY_VAR}"` ( `librechat.yaml` 内)。これは環境変数の**参照**です。YAML 自体にはトークンは保持されず、リテラルのトークンはスキーマによって拒否されます。
2. `token` が設定されていない場合、以下の環境変数のうち最初に設定されているものが使用されます：

| プロバイダー | フォールバック変数（順番どおり） |
| --------- | ------------------------------------------------------- |
| GitHub    | `GITHUB_PULL_REQUEST_TOKEN`, `GITHUB_TOKEN`, `GH_TOKEN` |
| GitLab    | `GITLAB_PULL_REQUEST_TOKEN`, `GITLAB_TOKEN`             |
| Bitbucket | `BITBUCKET_PULL_REQUEST_TOKEN`                          |

3. トークンはどこにも存在しません：ユーザーが自身のアカウントを接続できない限り、この機能は休止状態のままとなります。

設定されているが解決されない（変数が空または欠落している）`token` は、`NOT_CONFIGURED` で失敗します。上記の変数にフォールバックすることは**ありません**。

<Callout type="info" title="GITHUB_TOKEN と GITLAB_TOKEN は一般的な名称です">
  デプロイメントですでにこれらがいずれかの用途で使用されている場合、リポジトリのスコープが設定されるとすぐにここで取得されます。共有を避けるには、`token` を明示的に設定するか、`*_PULL_REQUEST_TOKEN` 変数を使用してください。
</Callout>

### 4. 検索対象とするリポジトリを選択する [#4-choose-which-repositories-it-may-look-up]

ワーカーは自身のレポジトリを報告するため、サーバーはどのレポジトリに対してそのトークンを使用できるかを決定する必要があります。スコープがない場合、この機能は休止状態のままとなります。これには2つの方法があります。

- `allowedRepositories`: `owner/name` または `owner/*` エントリのリスト（最大256個）。マッチングはケースインセンシティブです。GitLabでは、エントリは `group/sub/name` や `group/sub/*` のようなネストされたグループパスである可能性があります。`*` は正確に1つのセグメントを表すため、`group/*` は `group/sub/name` にはマッチしません。`*/*`、`*`、`owner`、または `.` や `..` セグメントを含むエントリは、スキーマによって拒否されます。
- `allowAllRepositories: true`: トークンが読み取り可能なすべてのリポジトリを検索します。デフォルトは `false` です。

<Callout type="warning" title="セキュリティ: allowAllRepositories">
  これはデフォルトでオフになっています。なぜなら、リポジトリはサーバーからではなくワーカーから取得されるためです。これをオンにすると、コードを実行できるユーザーであれば誰でも、そのトークンが読み取り可能な任意のリポジトリにサーバーのトークンを向け、プルリクエストのタイトル、サイズ、チェックステータスを確認できるようになります。表示を許可するリポジトリのみにスコープを絞った、読み取り専用のトークンを使用してください。
</Callout>

### 5. 有効にする [#5-turn-it-on]

設定するスイッチはありません。トークンとリポジトリのスコープ、または動作する `oauth` アプリが存在すれば、この機能はすぐに有効になります。`enabled: false` を設定すると、他の設定に関わらず機能は無効になります。

### 最小限の例 [#minimal-examples]

GitHub。サーバー環境で `GITHUB_PULL_REQUEST_TOKEN` が設定されている必要があります：

```yaml filename="librechat.yaml"
endpoints:
  agents:
    pullRequests:
      allowedRepositories:
        - 'LibreChat-AI/LibreChat'
        - 'my-org/*'
```

GitHub Enterprise Server（明示的なトークン参照付き）:

```yaml filename="librechat.yaml"
endpoints:
  agents:
    pullRequests:
      host: 'github.example.com'
      token: '${GHES_PULL_REQUEST_TOKEN}'
      allowedRepositories: ['platform/*']
```

Bitbucket Cloud、`BITBUCKET_PULL_REQUEST_TOKEN` を設定した場合:

```yaml filename="librechat.yaml"
endpoints:
  agents:
    pullRequests:
      provider: 'bitbucket'
      allowedRepositories: ['my-workspace/*']
```

すべてのキーについては、[`pullRequests` リファレンス](/docs/configuration/librechat_yaml/object_structure/agents#pullrequests) を参照してください。

## ユーザーごとのアカウント [#per-user-accounts]

`oauth` を設定すると、各ユーザーは **Settings > Account** の **Pull request account** から、自身の GitHub、GitLab、または Bitbucket アカウントを接続できるようになります。これにより、サーバーのトークン、レート制限、リポジトリアクセスではなく、ユーザー自身のトークン、レート制限、リポジトリアクセスを使用してルックアップが実行されるようになります。

- 接続されたユーザーのトークンは、そのユーザーがすでに閲覧可能なものしか参照できないため、`allowedRepositories` の制限は適用されません。
- 接続していないユーザーは、引き続きリポジトリスコープ下でサーバーのトークンを使用します。サーバーのトークンがない場合、接続するまでプルリクエストは表示されません。
- `oauth`アプリが正常に動作していれば、サーバーのトークンやリポジトリのスコープがなくても、この機能は有効になります。
- **Disconnect** は、保存された権限を削除します。ユーザーはいつでも再度接続できます。
- 接続されたユーザーのトークンが、プロバイダーまたはキーストアのダウンにより更新できない場合、そのルックアップはプルリクエストが利用不可であると報告します。ユーザー自身のトークンよりも権限が低い可能性があるサーバー側のトークンにフォールバックすることは**ありません**。
- プロバイダーが更新を明確に拒否した場合（権限が取り消された場合）、接続は削除されます。その際、ユーザーは未接続として表示され、接続していない他のユーザーと同様に扱われます。
- Grantsは暗号化されて保存され、ユーザーおよびプロバイダーホストごとに1つずつ割り当てられます。`clientId`を別のアプリに変更すると、既存の接続は未接続として扱われるため、ユーザーは再度接続する必要があります。

### アプリの設定 [#configure-the-app]

```yaml filename="librechat.yaml"
endpoints:
  agents:
    pullRequests:
      oauth:
        clientId: '${GITHUB_PR_OAUTH_CLIENT_ID}'
        clientSecret: '${GITHUB_PR_OAUTH_CLIENT_SECRET}'
      # optional: the server token for users who have not connected
      allowedRepositories: ['my-org/*']
```

| Key | Default | Range | Description |
| --- | --- | --- | --- |
| `clientId` | required | | 環境変数の参照であり、値そのものは記載しません。 |
| `clientSecret` | required | | 環境変数の参照であり、値そのものは記載しません。 |
| `scope` | GitHubでは指定なし、GitLabでは`read_api`、Bitbucketでは利用側が個別に設定 | | 要求するスコープをスペース区切りで指定します。使用できるのは英字、数字、`_`、`:`、`.`、`-`、スペースのみで、最大256文字です。 |
| `flowTimeoutMinutes` | 10 | 1-60 | ユーザーがプロバイダーで接続を承認するまでに許容される時間（分）です。 |
| `requestTimeoutSeconds` | 10 | 1-60 | コードの交換やトークンの更新に許容される時間（秒）です。 |
| `retentionDays` | 180 | 1-3650 | 利用されないまま接続を保持する日数です。利用されるたびに延長されます。 |

いずれかの参照が解決されない場合、ユーザーは接続できず、サーバーのトークンのみが使用されます。接続フローには `JWT_SECRET` も必要であり、これはすべての LibreChat デプロイメントで設定されています。

このコールバックURLをアプリに登録してください。ここで `DOMAIN_SERVER` は、お使いのサーバーのパブリックURLです：

```
<DOMAIN_SERVER>/api/pull-requests/oauth/callback
```

## レプリカによるスケーリング [#scaling-with-replicas]

各レプリカは結果をメモリ内にキャッシュします。複数のレプリカを使用する場合は、`sharedCache: true` を設定することで、Redis を介して検索されたプルリクエストやレート制限のクールダウンを共有し、各レプリカが同じ回答に対してトークンを消費しないようにします。

- これは、デプロイメントがRedis (`USE_REDIS`) で実行されている場合にのみ有効になります。デフォルト: `false`。
- いずれの場合も、各レプリカは共有キャッシュの前に、独自のインメモリキャッシュを保持します。
- `sharedCacheTimeoutMs` (10-5000、デフォルト 250) は、各共有キャッシュの読み取りまたは書き込みの制限時間を設定します。Redis の応答が遅い場合はスキップされ、それを使用せずにルックアップが続行されます。
- `sharedCacheSlots`(64〜1000000、デフォルト 65536)は、共有キャッシュが使用する Redis キーの上限を設定します。この値は YAML からのみ読み込まれます。

```yaml filename="librechat.yaml"
endpoints:
  agents:
    pullRequests:
      allowedRepositories: ['my-org/*']
      sharedCache: true
      sharedCacheTimeoutMs: 250
```

## チューニング [#tuning]

ほとんどのデプロイメントでは、デフォルト設定で問題ありません。

| キー | 範囲 | デフォルト | 説明 |
| -------------------------- | --------- | ------- | -------------------------------------------------------------------------------------------------------------- |
| `cacheTtlSeconds` | 5-3600 | 30 | 結果を再利用する秒数。その後、プロバイダーに再度問い合わせます。失敗は最大10秒間記憶されます。 |
| `cacheMaxEntries` | 10-100000 | 500 | 資格情報ごとにキャッシュされる結果の数。上限を超えると、最も古いものから削除されます。 |
| `cacheMaxCredentials` | 1-10000 | 256 | デプロイメント全体で同時にキャッシュされる資格情報の数。上限を超えると、最も長く使われていないものが削除されます。 |
| `maxConcurrentLookups` | 1-16 | 4 | 1つのサイドバーリクエストが同時に実行するルックアップの数。リクエストをまたいで資格情報ごとにカウントされます。 |
| `batchTimeoutSeconds` | 1-120 | 20 | 1つのサイドバーリクエストが開いたままでいられる最長時間。 |
| `requestTimeoutSeconds` | 1-60 | 10 | 1つのプロバイダーリクエストにかけられる最長時間。低速なプロキシの背後にある場合は、この値を大きくしてください。 |
| `lookupTimeoutSeconds` | 1-120 | 30 | すべてのリクエストを合わせた、ルックアップ全体にかけられる最長時間。 |
| `maxCheckRunPages` | 1-50 | 10 | チェックが実行中と報告される前に読み取る、チェックラン（GitHub）またはコミットステータス（Bitbucket）のページ数。 |
| `maxCandidatePullRequests` | 1-100 | 10 | 再利用されるブランチ名と照合する際に、状態ごとに一覧表示されるプルリクエストの数。 |
| `maxCandidatePages` | 1-10 | 1 | 状態ごとに読み取る候補のページ数。各ページは1回のリクエストです。 |
| `maxHeadComparisons` | 0-20 | 3 | 検索を打ち切るまでに、チャットが最後に実行されたコミットと比較される候補の数。各比較は1回のリクエストです。 |

## ユーザーの表示画面 [#what-users-see]

### チャットヘッダーチップ [#chat-header-chip]

- **デスクトップ**: チップはヘッダーの左側、他の左側コントロールの隣に配置されます。プルリクエストのアイコンと、その角に CI のドットが表示され、続いてプルリクエストのタイトルが表示されます。チップにホバーまたはフォーカスすると、その下にカードが開きます。カードは、ポインターまたはキーボードのフォーカスがカード内にある限り、開いたままになります。
- **モバイル**: チップはありません。ヘッダーのオーバーフロー(三点)メニューに `PR #number`(GitLab では `MR !number`)の項目があり、同じカードをダイアログで開きます。
- ヘッダーは自動的に更新されます。チェックが実行中またはマージ可能性が計算中の場合は約20秒ごと、それ以外の場合は約60秒ごとに行われます。プルリクエストがマージされた、またはチェックが実行されていない状態でクローズされた場合は更新されません。

### サイドバーマーク [#sidebar-mark]

- プルリクエストのアイコンと、その CI ステータスを示すドットが、会話の行の末尾に表示されます。プルリクエストがある会話にのみ表示されます。
- 行のどこにマウスを乗せても、またマークにフォーカスしたりクリックしたりしても、マークの右側に同じカードが開きます。マークをクリックしても会話は開きません。
- サイドバーはポーリングを行いません。各行の情報はリストが最後に読み込まれた時点のままですが、ウィンドウがフォーカスを取り戻した際にデータが1分以上経過している場合は更新されます。
- プルリクエストが検出された後、更新に失敗してもそのカードと再試行の状態は保持されます。検出の前に検索が失敗した場合は、サイドバーの印は非表示のままになります。

### カード [#the-card]

カードには `PR #number`（GitLabの場合は `MR !number`）、緑色で `+additions`、赤色で `-deletions`、**Open in GitHub**、**Open in GitLab**、または **Open in Bitbucket** へのリンク、タイトル、そして2つのバッジが表示されます。

- **状態**: Open、Conflicts、Draft、Merged、Closed のいずれか。オープンなプルリクエストにマージコンフリクトがある場合は、Open の代わりに Conflicts と表示されます。
- **チェック**: Passing、Failing、Running、またはNone。GitLab では、現在のヘッドコミットに対して実行されたヘッドパイプラインのみがカウントされます。Bitbucket では、コミットステータスが対象となります。

### アイコンとドットの意味 [#icon-and-dot-meaning]

| 状況 | アイコンの色 | CIのドット |
| --- | --- | --- |
| オープン、コンフリクトなし、チェック成功 | 緑（マージ可能） | 緑 |
| オープン、コンフリクトなし、チェックなし | 緑 | なし |
| オープン、マージ可能性を計算中 | 中立 | チェックに依存 |
| オープン、マージコンフリクトあり | 赤（マージ不可） | チェックに依存 |
| ドラフト | 中立 | チェックに依存 |
| マージ済み | 紫 | なし |
| クローズ | 中立 | なし |

CI のドットの色: 成功は緑、失敗は赤、実行中は黄色（アンバー）です。チェックがない場合、またはプルリクエストがマージまたはクローズされた後は、ドットは表示されません。失敗したチェックは、まだ実行中のチェックより優先されます。読み取られた数より多くのチェック実行を含むロールアップが、成功として報告されることはありません。

## プルリクエストがどのようにマッチングされるか [#how-a-pull-request-is-matched]

1. ワーカーは、チャットが最後に実行されたリポジトリ、ブランチ、およびコミット（ヘッド）を報告します。
2. チャット自体のコマンド出力が、設定されたホスト上のそのリポジトリのプルリクエストにリンクしている場合（例えば `gh pr create` が出力するリンクなど）、そのプルリクエストのヘッドがチャットのブランチであれば、そのプルリクエストが直接読み込まれます。他のリポジトリや他のホストへのリンクは無視されます。
3. それ以外の場合、LibreChatはそのブランチのオープンなプルリクエストを最初にリストアップするため、再利用されたブランチ名でクローズされた履歴がオープンなものを隠すことはありません。次に、フォークからのオープンなプルリクエストを確認し、その後にクローズされたものを確認します。
4. 記録されたコミットがある場合、プルリクエストは、そのヘッドが当該コミットであるか、またはそのコミットに基づいている場合にのみカウントされます。これにより、削除および再利用されたブランチ名によって古いプルリクエストが表示されることを防ぎます。フォークからのプルリクエストは、誰でも同じ名前のフォークブランチを開くことができるため、記録されたコミットが含まれている場合にのみカウントされます。
5. まだコミットがないブランチ（新規の空のブランチ）は、何も一致しません。
6. 結果は、認証情報、リポジトリ、ブランチ、およびコミットごとにキャッシュされます。
7. GitHubでは、チェックランはプルリクエストの現在のヘッドに対して読み取られます。フォークからのプルリクエストの場合、チェックはそのフォークのリポジトリがスコープ内にある（リストされている、または `allowAllRepositories` が設定されている）場合にのみ、そのフォークから読み取られます。それ以外の場合はベースリポジトリが読み取られ、トークンがリスト外のフォークに渡されることはありません。

## 動作 [#behavior]

### レート制限 [#rate-limits]

- レート制限は1つのプロバイダーホスト上の認証情報に適用されるため、そのトークン配下のすべてのブランチに対する検索が一時停止されます。ユーザーごとのアカウントでは、各ユーザーの制限は個別のものとなります。
- 最小待機時間は10秒で、プロバイダーが指定する待機時間が適用されます（上限は1時間）。GitHubでは、待機時間が指定されていない場合の二次的な制限として60秒の待機が発生します。
- 一時停止中、ルックアップは `RATE_LIMITED` を返します。以前に検出されたプルリクエストは再試行状態を保持し、未検出の行は非表示のままになります。
- `sharedCache` を使用すると、1つのレプリカで開始された一時停止がすべてのレプリカに適用されます。

### ローリングアップデート [#rolling-upgrades]

- サイドバーは、スタートアップ設定でサーバーがその機能（`pullRequestsBatchVersion`）を持っていると示されている場合にのみ、バッチルートにリクエストを送信します。
- ルートを持たないレプリカが404を返す場合、クライアントは単一ルートへのフォールバックを行い、一度に1つの呼び出しを行うか、サーバーがアドバタイズした場合は `pullRequestsMaxConcurrentLookups` に従って呼び出しを行います。これは、アップグレードされたレプリカから新しい起動フラグを受け取ったクライアントが、その後ルートを持たないレプリカに到達した場合をカバーします。`/api/config` がフラグを持たないレプリカによって提供される場合、サイドバーはバッチルートを要求せず、行は空のままになります。そのため、サイドバーのマークに依存する前に、すべてのレプリカをアップグレードしてください。

### 設定されていない場合のデフォルト値 [#defaults-when-unset]

- トークンやリポジトリのスコープがなく、`oauth` アプリもない場合、この機能は休止状態となります。起動時の設定で何も通知されず、何も記録されず、何も表示されません。
- 設定でこの機能をオフにすると、既存のチャットは変更されず、クライアントは新しいルートを呼び出すことはありません。

## セキュリティモデル [#security-model]

- トークンはサーバー上に保持されます。ブラウザに送信されることは決してなく、エラーレスポンスにプロバイダーのレスポンステキスト、トークン、またはスタックトレースが含まれることもありません。
- サーバーのトークンは、スコープ内のリポジトリに対してのみ、かつ設定されたホスト上でのみ使用されます。スコープ外のフォークに送信されることは決してありません。
- `provider`、`host`、および `oauth` は `librechat.yaml` からのみ取得されるため、ロール、グループ、ユーザー、またはテナントのオーバーライドによって別のサービスにトークンを送信したり、アプリユーザーがアクセスを許可する対象を切り替えたりすることはできません。
- `/api/convos` ルックアップルートは、認証されたユーザーを必要とし、所有者スコープで制限されています。存在しない、期限切れである、または他のユーザーに属する会話は、プルリクエストがない会話と同じように扱われます。
- 公開しても問題のないリポジトリに限定した、読み取り専用のトークンを使用してください。

## トラブルシューティング [#troubleshooting]

初回の検出が行われる前は、プロバイダーの障害によってサイドバーに警告マークが表示されることはありません。デバッグログには、プロバイダーと限定された理由コードが記録されますが、リポジトリの識別情報やプロバイダーのペイロードは含まれません。以前に検出されたプルリクエストは、更新に失敗した場合でもそのカードが維持されます。

| 症状 | 考えられる原因 | 対処法 |
| ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------- |
| どこにもチップもサイドバーのマークも表示されない | トークンがない、リポジトリのスコープがない、または `enabled: false` になっている | [セットアップ](#setup) を確認してください。サインインした状態で `/api/config` を開き、`pullRequestsEnabled: true` があるか確認してください。 |
| 接続されたワークスペース内の一部のチャットにチップが表示されない | `allowedRepositories` にそのリポジトリが含まれていない | リポジトリを追加するか、所有者を `owner/*` として追加してください。スコープ外のリポジトリは、プルリクエストがない場合と同じように見えます。 |
| 一部のチャットにだけチップが表示される | ブランチを報告済みの、接続されたコードワークスペース上のチャットにのみレーンがある | Code API で `CODEAPI_BRIDGE_LANE_GIT=true` が設定されていること、およびコードインタープリター PR #311 以降から構築されたワーカーであることを確認してください。 |
| ヘッダーのチップは動作するが、サイドバーの行に何も表示されない | `/api/config` に `pullRequestsBatchVersion` がない（古いビルド、またはキャッシュされた古いタブ） | サーバーを再ビルドまたはアップグレードして再起動し、ハードリロードしてください。`pullRequestsBatchVersion: 1` を確認してください。 |
| 再試行付きの警告アイコン | 検索に失敗した（レート制限、プロバイダーのエラー、または `NOT_CONFIGURED`） | 再試行してください。継続する場合は、トークンとその権限を確認してください。 |
| `NOT_CONFIGURED` | `token` は設定されているが、その変数が空または存在しない | 変数を設定するか、`token` を削除してフォールバック変数を使用してください。 |
| すべての GitHub プルリクエストの読み込みに失敗する | トークンに Checks 権限がない | 読み取り専用の Checks を付与してください。 |
| ブランチが進んだ後にのみ失敗する | トークンに Contents 権限がなく、コミットを比較できない | 読み取り専用の Contents を付与してください。 |
| `RATE_LIMITED` が頻繁に発生する | 多数のユーザーがサーバートークンを共有している、またはレプリカごとにプロバイダーへ問い合わせている | `cacheTtlSeconds` を上げるか、`maxConcurrentLookups` を下げるか、Redis とともに `sharedCache: true` を設定するか、ユーザーが自分のアカウントを接続できるようにしてください。 |
| フォークからのプルリクエストにチェックが表示されない | フォークがスコープ外のため、チェックはベースリポジトリから読み取られている | フォークの所有者を `allowedRepositories` に追加するか、`allowAllRepositories: true` を設定してください。 |
| GitLab または Bitbucket で何も表示されない | `provider` が設定されていない、または `host` がプロジェクトの配置場所と一致していない | `provider` を設定してください。セルフマネージドの GitLab の場合は、`host` にそのホスト名を設定してください。Bitbucket はデフォルトの `bitbucket.org` ホストの場合のみ動作します。 |
| `gh pr create` が出力したリンクが検出されない | リンクがレーンのものと異なるホストまたはリポジトリを指している | `host` を確認してください。設定されたホスト上で、かつレーンのリポジトリへのリンクのみが対象になります。 |
| 接続済みユーザーに「unavailable」と表示される | プロバイダーまたはキーストアがユーザーのトークンを更新できなかった | 後で再試行してください。接続済みユーザーの検索では、サーバートークンへのフォールバックは行われません。 |
| 多数回再利用されたブランチ名でプルリクエストが見つからない | `maxCandidatePullRequests`、`maxCandidatePages`、または `maxHeadComparisons` が、その名前の再利用頻度に対して小さすぎるため、検索が一致するプルリクエストに到達する前に止まっている | これらの値を上げてください。 |
| プロキシ越しの検索が遅い、またはタイムアウトする | `requestTimeoutSeconds` が小さすぎる | 値を上げてください。`HTTPS_PROXY` と `NO_PROXY` を確認してください。 |

## API reference [#api-reference]

以下の `/api/convos` ルートは両方とも認証済みユーザーを必要とし、オーナー権限にスコープされています。スタートアップ設定エンドポイントはオーナー権限にスコープされていません。

### 特定の会話のプルリクエストを取得する [#get-one-conversations-pull-request]

`GET /api/convos/:conversationId/pull-request`

- **200**: `{ "pullRequest": null }` または `{ "pullRequest": { number, title, url, additions, deletions, state, isDraft, mergeable, checks } }`。
- `state` は `open`、`closed`、または `merged` です。`mergeable` は `clean`、`conflicting`、または `unknown` です。`checks` は `passing`、`failing`、`running`、または `none` です。
- **503**: `{ "error": "...", "code": "NOT_CONFIGURED" | "RATE_LIMITED" | "UPSTREAM_ERROR" }`.
- **404**: 無効な会話IDです。 **500**: 固定テキストによるストレージエラーです。

### 多くの会話のプルリクエストを取得する [#get-many-conversations-pull-requests]

`POST /api/convos/pull-requests`

- Body: `{ "conversationIds": ["..."] }`。1から50個のIDを指定します。重複は統合されます。それ以外は400エラーとなります。
- **200**: `{ "results": [ { "conversationId", "pullRequest" } | { "conversationId", "error": { "code" } } ] }`。リクエストされた順序で返されます。1つの検索が失敗しても、他の検索結果が隠されることはありません。
- トークンが不足している場合、それを必要とするエントリのみが失敗します。

### アカウント接続 [#account-connection]

これらのルートは `JWT_SECRET` が設定されている場合にのみ存在します。コールバックを除くすべてにおいて、認証されたユーザーが必要です。

- `GET /api/pull-requests/oauth/connect`: 接続を開始し、開くべきプロバイダーのページである `{ "url" }` を返します。
- `GET /api/pull-requests/oauth/callback`: プロバイダーがユーザーをリダイレクトして戻す場所。
- `GET /api/pull-requests/oauth/status`: ユーザーが接続されているかどうか。
- `DELETE /api/pull-requests/oauth`: ユーザーの接続を解除します。

### Startup config [#startup-config]

`GET /api/config` にはこれらのフィールドが含まれます。これらはサーバーによって設定されるものであり、ユーザー設定ではありません。

- `pullRequestsEnabled` (boolean)
- `pullRequestsBatchVersion` (`1`、機能が有効な場合にのみ存在)
- `pullRequestsMaxConcurrentLookups` (数値、機能が有効な場合のみ存在)
- `pullRequestsConnect`（`github`、`gitlab`、`bitbucket` のいずれか。ユーザーが自分のアカウントを接続できる場合にのみ存在）

上記のリストにあるエラーコードのみが安定しています。
