Model Context Protocol (MCP) è un protocollo aperto che standardizza il modo in cui le applicazioni forniscono contesto ai Large Language Models (LLMs). Pensa a MCP come all'**"USB-C dell'IA"**: proprio come l'USB-C fornisce uno standard di connessione universale per i dispositivi elettronici, MCP offre un modo standardizzato per connettere i modelli di IA a diversi strumenti, fonti di dati e servizi.

LibreChat sfrutta MCP per espandere drasticamente le capacità dei tuoi agenti AI, consentendoti di integrare qualsiasi cosa, dall'accesso al file system, browser web e API specializzate, fino a strumenti aziendali personalizzati.

## Perché MCP è importante [#why-mcp-matters]

Gli LLM sono limitati alle loro funzionalità integrate. Con MCP, LibreChat abbatte queste barriere:

- **Connessione a qualsiasi strumento o servizio** che fornisca un server MCP
- **Standardizzazione delle integrazioni** in modo da non dover modificare il codice di LibreChat per ogni strumento
- **Supporto per ambienti multi-utente** con autenticazione e isolamento adeguati
- **Aggiunta e aggiornamento dei server in fase di esecuzione** dal pannello Impostazioni MCP, senza modificare un file di configurazione o riavviare

## Come funziona MCP in LibreChat [#how-mcp-works-in-librechat]

LibreChat fornisce due modi per utilizzare i server MCP, sia nell'area chat che con gli agenti.

Puoi configurare i server MCP manualmente nel tuo file `librechat.yaml` oppure utilizzando [smithery.ai](https://smithery.ai) per trovare e installare server MCP in `librechat.yaml` ([vedi l'esempio qui sotto](#basic-configuration)). Ogni volta che aggiungi o modifichi un server in `librechat.yaml`, dovrai riavviare LibreChat per inizializzare le connessioni. I server aggiunti tramite il [pannello delle impostazioni MCP](#adding-mcp-servers-in-the-ui) diventano operativi senza necessità di riavvio. Un server creato dal pannello che utilizza OAuth viene registrato al momento del salvataggio, ma inizialmente risulta disconnesso: [autenticalo](#step-3-check-connection-status-and-authenticate) una volta per connetterlo.

### URL di callback OAuth [#oauth-callback-url]

Per i server MCP con OAuth abilitato, l'URL di callback di LibreChat è:

```text
${DOMAIN_SERVER}/api/mcp/<server-name>/oauth/callback
```

`<server-name>` è la chiave utilizzata sotto `mcpServers` in `librechat.yaml` o il nome del server creato nell'interfaccia utente delle impostazioni MCP. Ad esempio, un server chiamato `salesforce` con `DOMAIN_SERVER=https://chat.example.com` utilizza `https://chat.example.com/api/mcp/salesforce/oauth/callback`.

Registra esattamente questo URL di callback presso il provider OAuth. Le installazioni Docker locali solitamente utilizzano `http://localhost:3080` come URL di base.

### Nell'area chat [#in-chat-area]

![Il catalogo dei server MCP aperto dalla tavolozza del composer, che mostra lo stato di connessione di ciascun server](/images/mcp/mcp_servers_catalog.png)

LibreChat visualizza i server MCP configurati direttamente nell'area della chat quando si utilizzano gli endpoint tradizionali (OpenAI, Anthropic, Google, Bedrock, ecc.):

- Seleziona prima un endpoint non-agent e un modello compatibile con i tool
- I server MCP appaiono nella sezione **MCP Servers** della [tavolozza **+** del composer](/docs/features/composer#turn-on-tools-skills-and-mcp-servers), e ogni server selezionato viene mostrato come una chip nel composer
- Quando selezionati, tutti gli strumenti di quel server diventano disponibili per il tuo modello attuale
- Accesso rapido agli strumenti MCP senza creare un agente, consentendo l'utilizzo di più server contemporaneamente

Per escludere un server MCP dalla selezione regolare della chat, imposta [`chatMenu: false`](/docs/configuration/librechat_yaml/object_structure/mcp_servers#chatmenu) nella tua configurazione:

```yaml
mcpServers:
  internal-tools:
    command: npx
    args: ['-y', 'internal-mcp-server']
    chatMenu: false # Not selectable in regular chat
```

Questa impostazione viene applicata alle richieste di chat così come nel selettore, in modo che una selezione salvata obsoleta non possa continuare a utilizzare un server nascosto. Non rimuove il server dagli Agent salvati o da una Model Specs che lo assegna esplicitamente. LibreChat omette inoltre dal normale selettore di chat e dal percorso di richiesta i server che un utente può raggiungere solo tramite un Agent autorizzato.

### Con gli Agent [#with-agents]

I server MCP si integrano perfettamente con gli Agent di LibreChat:

1. Crea o modifica un agente
2. Apri **Add tools** nel Generatore di agenti (Agent Builder) e seleziona **MCP**
3. Seleziona un server MCP; ogni server appare come una singola voce di catalogo
4. Espandi il server selezionato per abilitare o disabilitare i singoli strumenti
5. Salva il tuo agente

![Strumenti MCP nel Generatore di Agenti](/images/mcp/mcp_ui_agent.png)

Questa organizzazione di livello superiore mantiene l'interfaccia gestibile: anche i server con oltre 20 strumenti (come Spotify) appaiono come singole voci che possono essere espanse per un controllo granulare.

### Configurazione di base [#basic-configuration]

Aggiungi manualmente i server MCP al tuo file `librechat.yaml`:

```yaml
mcpServers:
  # ClickHouse Cloud
  clickhouse-cloud:
    type: streamable-http
    url: https://mcp.clickhouse.cloud/mcp

  # File system access
  filesystem:
    command: npx
    args:
      - -y
      - '@modelcontextprotocol/server-filesystem'
      - /path/to/your/documents

  # Web browser automation
  puppeteer:
    command: npx
    args:
      - -y
      - '@modelcontextprotocol/server-puppeteer'

  # Production-ready cloud service
  business-api:
    type: streamable-http
    url: https://api.yourbusiness.com/mcp
    headers:
      X-User-ID: '{{LIBRECHAT_USER_ID}}'
      Authorization: 'Bearer ${API_TOKEN}'
    timeout: 30000
    serverInstructions: true
```

### Aggiunta di MCP Servers nell'interfaccia utente [#adding-mcp-servers-in-the-ui]

Puoi anche aggiungere e configurare i server MCP direttamente dall'interfaccia di LibreChat senza dover modificare alcun file di configurazione o riavviare il server.

#### Passaggio 1: Apri il pannello delle impostazioni MCP [#step-1-open-the-mcp-settings-panel]

![Pannello impostazioni MCP](/images/mcp/mcp_ui_settings_panel.png)

#### Passaggio 2: Compilare i dettagli del server [#step-2-fill-out-server-details]

Premi il pulsante **+** e inserisci il nome del server MCP, la descrizione, l'URL, il tipo di trasporto e il metodo di autenticazione, quindi fai clic su **Create**.

![Finestra di dialogo Aggiungi Server MCP](/images/mcp/mcp_ui_configure.png)

Il tuo nuovo server apparirà nel pannello MCP Settings con una notifica di conferma.

![MCP Server creato con successo](/images/mcp/mcp_ui_success_registered.png)

#### Passaggio 3: Controlla lo stato della connessione ed effettua l'autenticazione [#step-3-check-connection-status-and-authenticate]

Controlla l'[indicatore dello stato della connessione](#connection-status-indicators) per il tuo nuovo server. Se il server richiede l'autenticazione OAuth, lo stato verrà visualizzato come disconnesso. Seleziona il server MCP nella tavolozza **+** del composer per avviare la procedura di autenticazione.

![Stato della connessione - Disconnesso](/images/mcp/mcp_ui_unconnected.png)

Una volta avviato, l'indicatore di stato si aggiornerà per mostrare che l'autenticazione è in corso.

![Stato della connessione - Autenticazione in corso](/images/mcp/mcp_ui_authenticating.png)

#### Passaggio 4: Continua con OAuth [#step-4-continue-with-oauth]

LibreChat presenta una richiesta di conferma **Connect**. Controlla la destinazione e seleziona **Continue with OAuth** per aprire la pagina di autorizzazione del provider in una nuova scheda del browser. Completa lì la procedura di accesso e consenso del provider.

Se un flusso avviato in questo browser è in sospeso, LibreChat mantiene quel server in uno stato di autorizzazione/connessione anche se lo stato della connessione memorizzato nella cache indica ancora **Connected**. Il prompt non dovrebbe chiudersi semplicemente perché un vecchio stato riporta un'autorizzazione durevole; il successo terminale, il fallimento, il timeout o l'annullamento terminano il flusso in sospeso. Un flusso avviato in un'altra scheda o browser non ha alcuno stato locale in sospeso in questa vista.

![OAuth Continue Prompt](/images/mcp/mcp_ui_callback_confirm.png)

#### Passaggio 5: Autenticazione riuscita [#step-5-authentication-successful]

Dopo l'autenticazione, vedrai una conferma di successo. Questa finestra si chiuderà automaticamente e ti reindirizzerà a LibreChat.

![Autenticazione riuscita](/images/mcp/mcp_ui_success_redirect.png)

#### Passaggio 6: Server pronto per l'uso [#step-6-server-ready-for-use]

LibreChat riconosce l'autenticazione riuscita e seleziona automaticamente il server MCP da utilizzare all'interno della conversazione. Il server ora mostra un indicatore di stato connesso e appare come una chip selezionata nel composer.

![MCP Server Authenticated and Auto-Selected](/images/mcp/mcp_ui_done.png)

Il tuo nuovo server MCP è disponibile anche nell'Agent Builder, dove puoi aggiungere i suoi strumenti a qualsiasi agente e personalizzare quale sottoinsieme di strumenti è consentito.

![MCP Server disponibile nel Generatore di Agenti](/images/mcp/mcp_ui_agent.png)

#### Variabili di credenziali per i server creati tramite UI [#credential-variables-for-ui-created-servers]

Quando aggiungi un server MCP tramite l'interfaccia utente, puoi richiedere agli utenti di fornire le proprie chiavi API. Nella sezione Authentication della finestra di dialogo MCP Server Builder, seleziona "API Key" e spunta **"User provides key"**. Scegli il formato dell'intestazione (Bearer, Basic o Custom) e salva il server.

Dietro le quinte, LibreChat crea una voce `customUserVars` destinata alla destinazione chiamata `MCP_API_KEY_<hash>` e configura l'intestazione di autenticazione corrispondente. Il nome viene gestito automaticamente; gli utenti inseriscono comunque la propria chiave nella finestra di dialogo di selezione degli strumenti MCP o nel pannello delle impostazioni MCP. I server esistenti potrebbero mantenere il nome legacy `MCP_API_KEY` finché il loro limite di richiesta rimane invariato. Questo utilizza la stessa interfaccia utente per l'inserimento delle chiavi di [YAML-defined `customUserVars`](#user-provided-credentials).

La modifica dell'URL (incluso il percorso o la query), del proxy, del trasporto, del formato di autorizzazione, dell'intestazione di autenticazione personalizzata o del client/destinazione OAuth configurato di un server creato tramite interfaccia utente richiede che ogni utente inserisca una chiave per il nuovo perimetro. Le vecchie chiavi salvate non vengono inoltrate alla destinazione sostitutiva. Le modifiche estetiche, gli URL normalizzati equivalenti e le modifiche all'URL in uscita che riguardano solo il frammento preservano la chiave esistente. I server condivisi possono risolvere solo le variabili di credenziali dichiarate dalla loro configurazione attuale, pertanto un editor non può fare riferimento a un vecchio nome generato per recuperare una chiave precedente. Non è necessaria alcuna migrazione massiva delle credenziali. Aggiorna **ogni replica API**, incluse le repliche che gestiscono le richieste di modifica del server, prima di fare affidamento su questa protezione; un writer meno recente può ancora ricreare una configurazione non vincolata.

Quando una chiave API di amministratore o utente è configurata, LibreChat tratta il server come autenticato tramite chiave API e salta il rilevamento automatico OAuth. Una configurazione OAuth esplicita ha comunque la precedenza. Se un server con chiave API creato tramite interfaccia utente è stato salvato da una versione precedente di LibreChat e rimane bloccato su **OAuth Required**, modifica e salva il server una volta affinché i metadati di connessione memorizzati vengano aggiornati.

<Callout type="warning">
Per motivi di sicurezza, i server MCP creati tramite interfaccia utente (basati su DB) possono risolvere **solo** i segnaposto `customUserVars` (`{{VAR_NAME}}`). Le variabili d'ambiente lato server (`${ENV_VAR}`), i campi del profilo utente (`{{LIBRECHAT_USER_*}}`) e i token OIDC (`{{LIBRECHAT_OPENID_*}}`) sono intenzionalmente bloccati per impedire l'accesso non autorizzato ai segreti del server o ai dati di altri utenti. Per il supporto completo dei segnaposto, configura il server in `librechat.yaml`.
</Callout>

## Gestione del server MCP [#mcp-server-management]

LibreChat fornisce strumenti completi per la gestione delle connessioni ai server MCP, con monitoraggio dello stato della connessione e supporto per l'autenticazione e l'inizializzazione OAuth nell'interfaccia utente.

### Indicatori dello stato della connessione [#connection-status-indicators]

LibreChat visualizza icone di stato dinamiche che mostrano lo stato attuale di ogni server MCP nella tavolozza **+** del composer e nel pannello delle impostazioni:

![Icone di stato del server MCP](/images/mcp/mcp_server_status_icons.png)

**Tipi di stato:**

- **Connesso** (ingranaggio verde): il server è connesso e dispone di customUserVars configurabili
- **OAuth richiesto** (chiave ambra): Il server richiede l'autenticazione OAuth
- **Disconnesso** (spina arancione): Connessione al server fallita o persa
- **Inizializzazione** (caricatore blu): Il server si sta avviando o riconnettendo
- **Errore** (triangolo rosso): Il server ha riscontrato un errore
- **Annullamento** (x rossa): il flusso OAuth è in fase di annullamento

### Annullamento di OAuth dalla finestra di dialogo dello strumento Agente [#cancelling-oauth-from-the-agent-tool-dialog]

In **Agent Builder → Tool Library → MCP server configuration**, **Connect** diventa un'azione **Cancel** abilitata mentre il gestore del server condiviso segnala un flusso OAuth annullabile. Ciò include un flusso in sospeso rilevato da un altro pannello di LibreChat. Scegli **Cancel** per interrompere tale flusso, chiudere la richiesta OAuth locale e cancellare la sua selezione automatica degli strumenti in sospeso. Un risultato di connessione tardivo dopo l'annullamento non collega automaticamente gli strumenti in questa finestra di dialogo. Puoi scegliere nuovamente **Connect** per un nuovo tentativo. L'inizializzazione che non è annullabile mostra ancora il suo stato di occupato disabilitato invece di un'azione di annullamento.

### Inizializzazione del server [#server-initialization]

Puoi inizializzare o reinizializzare i server MCP direttamente dall'interfaccia:

**Un clic:**

- Inizializzazione con un clic selezionando il server nella sezione **MCP Servers** della tavolozza **+** del composer

  <Video src="/videos/mcp_one_click_init.mp4" title="Inizializzazione MCP con un clic" />

**Da MCPConfigDialog:**

- Scegli **Configure** sulla riga di un server MCP nella tavolozza **+** del composer per aprire il MCPConfigDialog
- Configura le variabili utente personalizzate e fai clic sul pulsante Authenticate/Initialize a seconda del tipo di autenticazione del server

       <Video src="/videos/mcp_config_dialog_auth.mp4" title="Autenticazione della finestra di configurazione MCP" />

  **Dal pannello impostazioni MCP:**

- Fai clic su qualsiasi server nella sezione dell'elenco dei server del pannello delle impostazioni MCP per accedere ai controlli di configurazione e inizializzazione
- Configura le variabili utente personalizzate e fai clic sul pulsante Authenticate/Initialize a seconda del tipo di autenticazione del server

  <Video src="/videos/mcp_settings_init.mp4" title="Inizializzazione del pannello impostazioni MCP" />

Gli errori di inizializzazione ora distinguono tra un server non raggiungibile, `customUserVars` mancanti, una connessione OAuth che deve essere autenticata nuovamente e un errore di inizializzazione generico. Utilizza le variabili mancanti nominate o l'azione di riautenticazione nel messaggio prima di riprovare; non è più necessario rimuovere e riaggiungere il server per questi casi.

Il caricamento passivo del catalogo consolida i tentativi di rilevamento OAuth e aumenta progressivamente l'intervallo tra i tentativi in caso di errore, in modo che un'integrazione disconnessa non riprovi il rilevamento a ogni richiesta. Le modifiche alle credenziali sono protette da "generation-fencing" tra le repliche, impedendo che un risultato di rilevamento precedente sovrascriva un'autenticazione più recente. Gli operatori possono regolare la policy di ripristino limitato sotto [`mcpSettings.catalogRecovery`](/docs/configuration/librechat_yaml/object_structure/mcp_settings#catalogrecovery); le impostazioni predefinite sono adatte alla maggior parte delle implementazioni.

Se un Agent richiede esplicitamente strumenti MCP ma nessuno di essi può essere risolto all'avvio dell'esecuzione, LibreChat interrompe l'esecuzione fornendo indicazioni sulla connessione e sull'accesso, invece di procedere silenziosamente senza tali strumenti.

I server MCP che emettono `notifications/tools/list_changed` possono aggiornare il loro catalogo di strumenti senza dover riavviare LibreChat. LibreChat recupera l'elenco corrente dalla connessione attiva, pubblica gli strumenti aggiunti e interrompe la pubblicizzazione degli strumenti rimossi dal server. Anche le riconnessioni sincronizzano il catalogo prima che la connessione venga considerata pronta. Gli aggiornamenti degli snapshot gestiti e l'individuazione dei server a freddo condividono un unico gate a tre operazioni a livello di processo. Una volta ammessa, ogni operazione rimane limitata dalla sua scadenza di elenco degli strumenti o di individuazione per server, incluso qualsiasi `initTimeout` più breve, in modo che il lavoro lento sul catalogo non possa occupare uno slot a tempo indeterminato.

Per i server HTTP streamable, una riconnessione può restituire brevemente un errore HTTP `409` quando il server mantiene ancora uno stream SSE standalone non aggiornato per la vecchia sessione. LibreChat tratta questo evento come transitorio, interrompe la sessione non aggiornata e ricostruisce la connessione automaticamente; non è necessaria alcuna azione da parte dell'operatore quando il ripristino ha successo. Se anche la connessione ricostruita fallisce, LibreChat continuerà a mostrare l'errore di connessione sottostante.

LibreChat classifica le risposte HTTP trasmissibili (Streamable) in base al tipo di media `Content-Type` analizzato, anziché tramite una corrispondenza di sottostringa. I parametri non possono far apparire una risposta non SSE come `text/event-stream`, pertanto gli errori di dimensione della risposta continuano attraverso il corretto percorso di gestione SSE o non SSE.

### Visibilità del pannello delle impostazioni MCP [#mcp-settings-panel-visibility]

Il pannello delle impostazioni MCP appare nella barra laterale destra quando LibreChat rileva server MCP che potrebbero richiedere l'intervento dell'utente durante la loro inizializzazione. Il pannello sarà visibile quando uno qualsiasi dei server configurati soddisfa uno di questi criteri:

- **Variabili utente personalizzate**: Il server ha `customUserVars` definite che possono contenere credenziali fornite dall'utente
- **Autenticazione OAuth**: Il server viene rilevato come richiedente l'autenticazione OAuth durante l'avvio
- **Inizializzazione manuale**: Il server ha `startup: false` configurato, il che richiede un'inizializzazione manuale

## Funzionalità specifiche di LibreChat [#librechat-specific-features]

L'implementazione MCP di LibreChat è progettata per ambienti multi-utente reali e altamente configurabili.

### Connessioni specifiche per l'utente [#user-specific-connections]

- Ogni utente ottiene la propria connessione isolata ai server MCP
- L'autenticazione utente e le autorizzazioni vengono rispettate
- I dati personali e il contesto rimangono privati

### Condivisione dei server MCP [#sharing-mcp-servers]

I server MCP partecipano al sistema di [controllo degli accessi granulare](/docs/features/access_control) di LibreChat. Oltre ai server definiti in `librechat.yaml` (che sono gestiti dagli amministratori e regolati dalle autorizzazioni della funzionalità [`interface.mcpServers`](/docs/configuration/librechat_yaml/object_structure/interface#mcpservers)), i server MCP creati dagli utenti hanno il proprio ACL e possono essere condivisi con **utenti**, **gruppi**, **ruoli** specifici o **pubblicamente**, a livello di Visualizzatore, Editor o Proprietario.

I feature flag `USE`, `CREATE`, `SHARE` e `SHARE_PUBLIC` sotto `interface.mcpServers` controllano chi è autorizzato a creare e condividere i server MCP. Consulta [Access Control](/docs/features/access_control) per sapere come si compongono i livelli di autorizzazione.

### Contesto Utente Dinamico [#dynamic-user-context]

I server MCP possono accedere alle informazioni dell'utente tramite segnaposto in **URL e intestazioni** (per trasporti SSE e HTTP Streamable):

```yaml
mcpServers:
  user-api:
    type: streamable-http
    url: https://api.example.com/users/{{LIBRECHAT_USER_USERNAME}}/mcp
    headers:
      X-User-ID: '{{LIBRECHAT_USER_ID}}'
      X-User-Email: '{{LIBRECHAT_USER_EMAIL}}'
      X-User-Role: '{{LIBRECHAT_USER_ROLE}}'
      Authorization: 'Bearer ${API_TOKEN}'
```

I segnaposto disponibili includono:

- `{{LIBRECHAT_USER_ID}}` - Identificativo utente univoco
- `{{LIBRECHAT_USER_EMAIL}}` - Indirizzo email dell'utente
- `{{LIBRECHAT_USER_ROLE}}` - Ruolo utente (admin, user, ecc.)
- `{{LIBRECHAT_USER_USERNAME}}` - Nome utente
- E molti altri (vedi [Configurazione dei Server MCP](/docs/configuration/librechat_yaml/object_structure/mcp_servers#headers) per l'elenco completo)

I server MCP definiti in YAML possono anche utilizzare i segnaposto `{{LIBRECHAT_OPENID_*}}`, `{{LIBRECHAT_GRAPH_*}}` e `{{LIBRECHAT_BODY_*}}`. I valori `{{LIBRECHAT_BODY_*}}` sono limitati alla richiesta (request-scoped), pertanto LibreChat crea connessioni per l'esecuzione attiva, le riutilizza tra le chiamate agli strumenti durante tale esecuzione e le elimina al termine della richiesta. I server limitati alla richiesta sono esclusi dalla cache persistente degli strumenti, in modo che le intestazioni e gli URL specifici della richiesta non vengano riutilizzati al di fuori dell'esecuzione attiva. Poiché il loro elenco di strumenti non può essere risolto prima dell'esistenza di una richiesta di chat, l'Agent Builder espone una selezione di strumenti di runtime per l'intero server e risolve i relativi strumenti al momento dell'esecuzione. Il completamento di OAuth memorizza l'autorizzazione ma rimanda la connessione fino a quando la prima esecuzione non fornisce il contesto della richiesta. I segnaposto User, OpenID e Graph sono limitati all'utente (user-scoped); i trasporti HTTP aggiornano le intestazioni risolte prima di ogni chiamata allo strumento senza richiedere autonomamente una riconnessione.

Gli operatori autorizzati possono utilizzare `Authorization: 'Bearer {{LIBRECHAT_OPENID_ACCESS_TOKEN}}'` su un server remoto definito in YAML per trasmettere il token di accesso OpenID live dell'utente. L'autenticazione tramite MCP OAuth esplicito, lo scambio per conto terzi (on-behalf-of) e le chiavi API dell'amministratore hanno la precedenza. Dopo un errore `401` o `403`, LibreChat può aggiornare la connessione una sola volta, ma non riesegue mai automaticamente la chiamata allo strumento rifiutata. Consulta il [riferimento ai segnaposto del server MCP](/docs/configuration/librechat_yaml/object_structure/mcp_servers#headers) per indicazioni sulla configurazione e sulla sicurezza.

`{{LIBRECHAT_GRAPH_ACCESS_TOKEN}}` scambia il token di accesso OpenID riutilizzabile dell'utente tramite il flusso on-behalf-of di Microsoft. [`GRAPH_API_SCOPES`](/docs/configuration/dotenv#microsoft-graph-api--entra-id-integration) imposta gli ambiti (scopes) richiesti separati da spazi e ha come valore predefinito `https://graph.microsoft.com/.default`. Questo è indipendente da `OPENID_GRAPH_SCOPES`, che configura la ricerca di persone e gruppi.

Il segnaposto `{{LIBRECHAT_BODY_PARENTMESSAGEID}}` viene popolato per le chat degli Agent nativi, le chiamate API degli Agent compatibili con OpenAI e le esecuzioni degli Assistants legacy. Open Responses non ha un'identità di messaggio padre equivalente e fallisce in modo chiuso (fails closed) quando un server MCP richiede tale valore. Consulta il [riferimento ai segnaposti del server MCP](/docs/configuration/librechat_yaml/object_structure/mcp_servers#headers).

### Istruzioni del Server [#server-instructions]

`serverInstructions` è una funzionalità di LibreChat che aggiunge dinamicamente istruzioni configurate quando viene selezionato un qualsiasi strumento da quel server MCP:

```yaml
mcpServers:
  filesystem:
    command: npx
    args: ['-y', '@modelcontextprotocol/server-filesystem', '/docs']
    serverInstructions: |
      When accessing files:
      - Always check file permissions first
      - Use absolute paths for reliability
      - Handle errors gracefully
```

Opzioni:

- `true`: Utilizza le istruzioni pubblicizzate dal server quando disponibili
- `false`: Disabilita le istruzioni
- `string`: Utilizza le istruzioni personalizzate letteralmente (mostrate sopra)

LibreChat conserva questa dichiarazione configurata separatamente dalle istruzioni recuperate durante l'ispezione del server. Una dichiarazione `true` rimane quindi abilitata durante l'ispezione e i ricaricamenti del registro memorizzato nella cache, mentre una stringa personalizzata rimane autorevole.

### Configurazione del timeout [#timeout-configuration]

Per operazioni MCP di lunga durata, configura timeout appropriati sia per l'inizializzazione che per le operazioni degli strumenti.

```yaml
mcpServers:
  data-processor:
    type: streamable-http
    url: https://api.example.com/mcp
    initTimeout: 15000 # 15 seconds for server initialization
    timeout: 60000 # 60 seconds for tool operations
```

**Nota**: Se le operazioni vengono ancora interrotte prematuramente, controlla la configurazione del tuo proxy (ad esempio, nginx, traefik, ecc.), che potrebbe interrompere le connessioni prima del previsto a causa dei timeout predefiniti.

Quando un utente preme **Stop** durante una chiamata a uno strumento Agent in primo piano, LibreChat inoltra il segnale di annullamento dell'esecuzione a MCP. Per i server HTTP streamable, l'SDK MCP invia `notifications/cancelled`; il server deve rispettare tale notifica per interrompere il proprio lavoro. Le chiamate in background scollegate mantengono intenzionalmente un ciclo di vita separato e non vengono annullate con il turno in primo piano.

### Credenziali fornite dall'utente [#user-provided-credentials]

Puoi consentire agli utenti di fornire le proprie credenziali per i server MCP tramite `customUserVars`. Ciò abilita un'autenticazione sicura e specifica per l'utente senza memorizzare le credenziali nei file di configurazione.

```yaml
mcpServers:
  my-api-server:
    type: streamable-http
    url: 'https://api.example.com/mcp'
    headers:
      X-Auth-Token: '{{MY_API_KEY}}' # Uses the user-provided value
    customUserVars:
      MY_API_KEY:
        title: 'API Key'
        description: "Enter your personal API key from <a href='https://example.com/keys' target='_blank'>your account settings</a>"
```

Gli utenti possono configurare queste credenziali:

- **Dall'area Chat**: Scegli **Configure** nella riga di un server MCP configurabile nella tavolozza **+** del composer
- **Dal pannello Impostazioni MCP**: Accedi a "MCP Settings" nel pannello di destra per gestire le credenziali per tutti i server configurati

#### Reinizializzazione dei server MCP con le credenziali utente [#reinitializing-mcp-servers-with-user-credentials]

Per i server MCP che richiedono credenziali specifiche dell'utente prima di poter essere utilizzati (ad esempio, i `PAT_TOKEN` nel [server MCP ufficiale di GitHub](https://github.com/github/github-mcp-server)), LibreChat consente agli utenti di fornire tali credenziali e quindi di reinizializzare il server MCP dall'interno dell'interfaccia utente senza riavviare l'intera applicazione:

1. Quando selezioni un MCP che utilizza `customUserVars`, sarai in grado di **Salvare** o **Revocare** il valore di una `customUserVar` per il server MCP selezionato direttamente dal Pannello MCP.
2. Dopo aver salvato un valore per una `customUserVar`, fai clic sul pulsante di reinizializzazione (un'icona con frecce circolari accanto a ciascun nome del server nel pannello MCP).
3. LibreChat tenterà di connettersi al server utilizzando le credenziali fornite e ti avviserà con una notifica toast se il processo di reinizializzazione ha avuto successo o è fallito.

> _Suggerimento: Se sai che un server richiederà credenziali non disponibili al primo avvio, puoi aggiungere `startup: false` alla sua configurazione. Questo indica a LibreChat di non tentare la connessione a quel server finché non viene reinizializzato manualmente nell'interfaccia utente._

**Esempio:**

```yaml
mcpServers:
  github-mcp:
    type: streamable-http
    url: 'https://api.githubcopilot.com/mcp/'
    headers:
      Authorization: '{{PAT_TOKEN}}'
    customUserVars:
      PAT_TOKEN:
        title: 'GitHub PAT Token'
        description: 'GitHub Personal Access Token'
    startup: false
```

### Autenticazione OAuth [#oauth-authentication]

LibreChat supporta l'autenticazione OAuth per i server MCP, seguendo le raccomandazioni di Anthropic per connessioni MCP sicure. OAuth fornisce un metodo standardizzato e sicuro per l'autenticazione senza dover memorizzare credenziali a lunga durata.

#### Flussi OAuth supportati [#supported-oauth-flows]

I server MCP di LibreChat supportano OAuth 2.0 con:

- **Authorization Code Flow with PKCE**: Consigliato per la massima sicurezza
- **Client Discovery**: Registrazione automatica del client quando supportata dal provider OAuth
- **Refresh Tokens**: Rinnovo automatico del token quando disponibile
- **Token endpoint discovery**: I client preconfigurati possono scoprire se il provider richiede le credenziali del client nel corpo della richiesta POST o in un'intestazione di autorizzazione HTTP Basic

Nel Builder MCP, **Token Exchange Method** offre **Auto**, **Default (POST request)** e **Basic authorization header**. Auto lascia il metodo non impostato in modo che LibreChat possa utilizzare i metadati del provider attendibile, ripiegando sull'autenticazione Basic quando il provider non pubblicizza un metodo.

#### Esempi di configurazione [#configuration-examples]

```yaml
mcpServers:
  # Public remote MCP server for PayPal, uses OAuth Client Discovery
  # ❌ Refresh Tokens: you may need to re-authenticate periodically
  # More info: https://developer.paypal.com/tools/mcp-server/
  paypal:
    type: 'sse'
    initTimeout: 150000 # higher timeout to allow for initial authentication
    url: 'https://mcp.paypal.com/sse'

  # Example self-hosted remote MCP server for Spotify, uses OAuth Client Discovery
  # ✅ Refresh Tokens: refreshes token for authentication automatically
  # Hosted on Cloudflare Workers, more info: https://github.com/LibreChat-AI/spotify-mcp
  spotify:
    type: 'streamable-http'
    initTimeout: 150000
    url: 'https://mcp-spotify-oauth-example.account.workers.dev/mcp'
```

#### Flusso di autenticazione OAuth [#oauth-authentication-flow]

Quando configuri per la prima volta un server MCP abilitato per OAuth:

1. **Connessione iniziale**: LibreChat tenta di connettersi al server MCP
2. **Autenticazione richiesta**: Se non esiste un token valido, vedrai uno stato di autenticazione OAuth per quel server nella tavolozza **+** del composer.
3. **Avvio dell'accesso**: Seleziona il server per iniziare il flusso OAuth
4. **Continua o usa un altro dispositivo**: Continua nel browser corrente, copia il link di autorizzazione o mostra un codice QR per aprirlo su un altro dispositivo
5. **Reindirizzamento del browser**: Completa l'autenticazione con il provider OAuth
6. **Gestione del ritorno**: LibreChat elabora automaticamente il callback OAuth una volta completata l'autenticazione
7. **Archiviazione dei token**: LibreChat archivia in modo sicuro i token per un utilizzo futuro
8. **Connessione stabilita**: Una volta effettuata l'autenticazione, il server MCP sarà connesso e potrai utilizzarlo nella tua chat

#### URL di callback OAuth [#oauth-callback-url-1]

Quando un server MCP utilizza OAuth, LibreChat espone un endpoint di callback a cui il provider OAuth reindirizza dopo un'autorizzazione riuscita.

L'URL di callback deve seguire questo formato:

`${baseUrl}/api/mcp/${serverName}/oauth/callback`

Dove `${serverName}` è la chiave del server MCP definita nella configurazione `librechat.yaml`. LibreChat gestisce il reindirizzamento a questo endpoint, completa lo scambio del token e associa le credenziali al server MCP corrispondente.

<Callout type="info" title="Esempio di URL di callback OAuth">
Data la seguente configurazione del server MCP:

```yaml
mcpServers:
  # Example self-hosted remote MCP server for Spotify, uses OAuth Client Discovery
  # ✅ Refresh Tokens: refreshes token for authentication automatically
  # Hosted on Cloudflare Workers, more info: https://github.com/LibreChat-AI/spotify-mcp
  spotify:
    type: 'streamable-http'
    initTimeout: 150000
    url: 'https://mcp-spotify-oauth-example.account.workers.dev/mcp'
```

L'URL di callback sarebbe `${baseUrl}/api/mcp/spotify/oauth/callback`.

</Callout>

Nota:

- L'URL di callback deve essere registrato esattamente presso il provider OAuth affinché il flusso funzioni.
- Altri percorsi come `/api/oauth/callback` o `/api/oauth/openid/callback` non sono validi per i flussi OAuth MCP.

#### Gestione dei token [#token-management]

LibreChat gestisce i token OAuth in modo intelligente:

- **Archiviazione sicura**: i token vengono crittografati e archiviati in modo sicuro
- **Aggiornamento automatico**: Quando i token di aggiornamento sono disponibili, LibreChat rinnova automaticamente i token di accesso scaduti
- **Ripristino silenzioso 401**: Se una connessione MCP OAuth riceve un rifiuto di autenticazione a metà sessione, LibreChat coordina un tentativo limitato di aggiornamento e riconnessione per utente e server. I chiamanti simultanei condividono il risultato di tale ripristino prima che LibreChat mostri una nuova richiesta di autenticazione.
- **Gestione delle sessioni**: Ogni utente mantiene le proprie sessioni OAuth per ambienti multi-utente

Se un flusso di un Agent salvato viene ricaricato o ripreso mentre una richiesta di autorizzazione MCP è ancora in sospeso, LibreChat ricostruisce tale richiesta dallo stato di generazione persistente. Le richieste completate, annullate, non riuscite o scadute non vengono ripristinate.

I client e i token OAuth memorizzati sono vincolati all'URL del server MCP e alle impostazioni del client/endpoint OAuth. La modifica di tali impostazioni richiede agli utenti di autenticarsi nuovamente. Quando si modifica un server creato tramite interfaccia utente che conserva un `client_secret` memorizzato, reinserire il secret quando si modifica un campo di associazione come l'URL del server, l'ID client, l'URL di autorizzazione, l'URL del token o il metodo di autenticazione del token.

Nelle distribuzioni scalate orizzontalmente, lo stato del flusso OAuth e la disponibilità del token associato possono essere riconciliati tra i pod di LibreChat. L'interfaccia utente segnala che un server è pronto solo dopo che l'inizializzazione post-OAuth ha avuto successo, anche quando il callback e il polling dello stato raggiungono pod diversi. I callback provenienti da tentativi superati vengono rifiutati.

Quando Redis è abilitato, le generazioni del catalogo MCP a livello di applicazione e le revisioni delle pubblicazioni vengono coordinate tra le repliche. Le distribuzioni Redis Cluster utilizzano chiavi di catalogo e aggiornamenti slot-safe, pertanto la sincronizzazione all'avvio e gli aggiornamenti di `tools/list_changed` non richiedono un layout Redis a nodo singolo.

Ogni utente riceverà una richiesta di autenticazione con il proprio login OAuth al primo utilizzo di un server MCP abilitato per OAuth. Ciò garantisce che i dettagli di connessione e autenticazione siano univoci per ogni utente, mantenendo la sicurezza e la privacy in ambienti multi-utente.

#### Tempistiche OAuth [#oauth-timing]

Il completamento di MCP OAuth utilizza il proprio timeout configurato dal server invece di riutilizzare l' `initTimeout` del server MCP. Per impostazione predefinita, LibreChat attende fino a 10 minuti che l'utente completi l'MCP OAuth e mantiene lo stato del flusso per 15 minuti.

Utilizza queste variabili d'ambiente quando un provider OAuth o un flusso di lavoro utente necessita di più tempo:

```bash filename=".env"
MCP_OAUTH_HANDLING_TIMEOUT=600000
MCP_OAUTH_FLOW_TTL=900000
```

`MCP_OAUTH_FLOW_TTL` è limitato in modo da superare `MCP_OAUTH_HANDLING_TIMEOUT`, così che i callback vicini alla scadenza possano ancora trovare il loro stato di flusso. La finestra di polling della server-card MCP segue il timeout di gestione configurato.

![Flusso di autenticazione OAuth specifico per l'utente](/images/agents/mcp_oauth_flow.png)

> Nota: i token mostrati durante l'avvio dell'app sono solo per l'inizializzazione a livello di app e non vengono utilizzati per le connessioni dei singoli utenti.

Esempio di aggiornamento automatico del token:

```bash
[MCP][spotify] Access token missing
[MCP][spotify] Attempting to refresh token
[MCP][spotify] Successfully refreshed and stored OAuth tokens
[MCP][spotify] ✓ Initialized
```

#### Best Practices [#best-practices]

1. **Usa OAuth quando disponibile**: Preferisci OAuth rispetto alle chiavi API per una maggiore sicurezza
2. **Configura i timeout appropriati**: Usa `MCP_OAUTH_HANDLING_TIMEOUT` e `MCP_OAUTH_FLOW_TTL` per le finestre di completamento OAuth; usa `initTimeout` per l'inizializzazione del server
3. **Monitoraggio della scadenza dei token**: Controlla i log per problemi di autenticazione
4. **Piano per la ri-autenticazione**: Alcuni provider non supportano i token di aggiornamento (refresh tokens)

## Trasporti del server [#server-transports]

I server MCP possono essere configurati per utilizzare diversi meccanismi di trasporto:

**Server STDIO**

- Funziona bene per ambienti locali e multiutente.
- Non scalabile per distribuzioni remote o cloud
- L'SDK MCP in bundle limita ogni singolo messaggio STDIO a 10 MB. Un singolo risultato di dimensioni superiori chiude il trasporto con un errore; questo limite è separato dalla dimensione totale di una sessione o di uno stream.

**Server-Sent Events (SSE) Server**

- Meccanismo di trasporto remoto, ma non raccomandato per l'ambiente di produzione

**Server HTTP Streamable**

- Utilizza HTTP POST per l'invio di messaggi e supporta le risposte in streaming
- Funziona come un processo indipendente in grado di gestire connessioni client multiple
- Supporta sia le richieste di base che lo streaming tramite Server-Sent Events (SSE)
- Alternativa più performante rispetto al trasporto legacy HTTP+SSE
- Supporta configurazioni server multi-utente appropriate

**Per ambienti di produzione**, si consigliano solo server MCP con ["Streamable HTTP" transports](https://modelcontextprotocol.io/specification/draft/basic/transports/streamable-http). A differenza di SSE, che mantiene connessioni a lunga durata, Streamable HTTP offre opzioni stateless più adatte a distribuzioni scalabili multi-utente.

LibreChat è all'avanguardia nell'implementazione di integrazioni server MCP flessibili e scalabili per supportare diversi scenari di utilizzo e aiutarti a costruire i flussi di lavoro AI di domani.
