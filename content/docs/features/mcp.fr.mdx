Le Model Context Protocol (MCP) est un protocole ouvert qui standardise la manière dont les applications fournissent du contexte aux Large Language Models (LLMs). Considérez le MCP comme le **« USB-C de l'IA »** - tout comme l'USB-C fournit une norme de connexion universelle pour les appareils électroniques, le MCP offre un moyen standardisé de connecter des modèles d'IA à divers outils, sources de données et services.

LibreChat tire parti de MCP pour étendre considérablement les capacités de vos agents IA, vous permettant d'intégrer tout ce qui va de l'accès au système de fichiers, aux navigateurs web et aux API spécialisées, jusqu'aux outils métier personnalisés.

## Pourquoi MCP est important [#why-mcp-matters]

Les LLM sont limités à leurs capacités intégrées. Avec MCP, LibreChat fait tomber ces barrières en :

- **Connexion à tout outil ou service** fournissant un serveur MCP
- **Standardisation des intégrations** afin que vous n'ayez pas besoin de modifier le code de LibreChat pour chaque outil
- **Prise en charge d'environnements multi-utilisateurs** avec une authentification et une isolation appropriées
- **Ajout et mise à jour de serveurs au moment de l'exécution** depuis le panneau des paramètres MCP, sans modifier de fichier de configuration ni redémarrer

## Comment MCP fonctionne dans LibreChat [#how-mcp-works-in-librechat]

LibreChat propose deux façons d'utiliser les serveurs MCP, soit dans la zone de chat, soit avec des agents.

Vous pouvez configurer les serveurs MCP manuellement dans votre fichier `librechat.yaml` ou en utilisant [smithery.ai](https://smithery.ai) pour trouver et installer des serveurs MCP dans `librechat.yaml` ([voir l'exemple ci-dessous](#basic-configuration)). Chaque fois que vous ajoutez ou modifiez un serveur dans `librechat.yaml`, vous devrez redémarrer LibreChat pour initialiser les connexions. Les serveurs ajoutés via le [panneau de paramètres MCP](#adding-mcp-servers-in-the-ui) prennent effet sans redémarrage. Un serveur créé via le panneau qui utilise OAuth est enregistré lors de l'enregistrement mais démarre déconnecté : [authentifiez-le](#step-3-check-connection-status-and-authenticate) une fois pour le connecter.

### URL de rappel OAuth [#oauth-callback-url]

Pour les serveurs MCP avec OAuth activé, l'URL de rappel LibreChat est :

```text
${DOMAIN_SERVER}/api/mcp/<server-name>/oauth/callback
```

`<server-name>` est la clé utilisée sous `mcpServers` dans `librechat.yaml` ou le nom du serveur créé dans l'interface des paramètres MCP. Par exemple, un serveur nommé `salesforce` avec `DOMAIN_SERVER=https://chat.example.com` utilise `https://chat.example.com/api/mcp/salesforce/oauth/callback`.

Enregistrez cette URL de rappel exacte auprès du fournisseur OAuth. Les installations Docker locales utilisent généralement `http://localhost:3080` comme URL de base.

### Dans la zone de chat [#in-chat-area]

![Le catalogue des serveurs MCP ouvert depuis la palette du compositeur, affichant l'état de connexion de chaque serveur](/images/mcp/mcp_servers_catalog.png)

LibreChat affiche les serveurs MCP configurés directement dans la zone de chat lors de l'utilisation des endpoints traditionnels (OpenAI, Anthropic, Google, Bedrock, etc.) :

- Sélectionnez d'abord n'importe quel endpoint non-agent, ainsi qu'un modèle compatible avec les outils
- Les serveurs MCP apparaissent dans la section **MCP Servers** de la [palette **+** du compositeur](/docs/features/composer#turn-on-tools-skills-and-mcp-servers), et chaque serveur sélectionné s'affiche sous forme de puce dans le compositeur.
- Une fois sélectionné, tous les outils de ce serveur deviennent disponibles pour votre modèle actuel.
- Accès rapide aux outils MCP sans créer d'agent, permettant l'utilisation simultanée de plusieurs serveurs

Pour exclure un serveur MCP de la sélection de chat habituelle, définissez [`chatMenu: false`](/docs/configuration/librechat_yaml/object_structure/mcp_servers#chatmenu) dans votre configuration :

```yaml
mcpServers:
  internal-tools:
    command: npx
    args: ['-y', 'internal-mcp-server']
    chatMenu: false # Not selectable in regular chat
```

Ce paramètre est appliqué aux requêtes de chat ainsi que dans le sélecteur, afin qu'une sélection enregistrée obsolète ne puisse pas continuer à utiliser un serveur masqué. Il ne supprime pas le serveur des Agents enregistrés ni d'un Model Specs qui l'assigne explicitement. LibreChat omet également du sélecteur de chat habituel et du chemin de requête les serveurs auxquels un utilisateur ne peut accéder que par le biais d'un Agent autorisé.

### Avec des Agents [#with-agents]

Les serveurs MCP s'intègrent parfaitement aux agents LibreChat :

1. Créer ou modifier un agent
2. Ouvrez **Add tools** dans le Agent Builder et sélectionnez **MCP**
3. Sélectionnez un serveur MCP ; chaque serveur apparaît comme une entrée de catalogue unique
4. Développez le serveur sélectionné pour activer ou désactiver des outils individuels
5. Enregistrez votre agent

![Outils MCP dans le générateur d'agents](/images/mcp/mcp_ui_agent.png)

Cette organisation de haut niveau permet de garder l'interface gérable - même les serveurs avec plus de 20 outils (comme Spotify) apparaissent sous forme d'entrées uniques qui peuvent être développées pour un contrôle granulaire.

### Configuration de base [#basic-configuration]

Ajoutez manuellement des serveurs MCP à votre fichier `librechat.yaml` :

```yaml
mcpServers:
  # ClickHouse Cloud
  clickhouse-cloud:
    type: streamable-http
    url: https://mcp.clickhouse.cloud/mcp

  # File system access
  filesystem:
    command: npx
    args:
      - -y
      - '@modelcontextprotocol/server-filesystem'
      - /path/to/your/documents

  # Web browser automation
  puppeteer:
    command: npx
    args:
      - -y
      - '@modelcontextprotocol/server-puppeteer'

  # Production-ready cloud service
  business-api:
    type: streamable-http
    url: https://api.yourbusiness.com/mcp
    headers:
      X-User-ID: '{{LIBRECHAT_USER_ID}}'
      Authorization: 'Bearer ${API_TOKEN}'
    timeout: 30000
    serverInstructions: true
```

### Ajout de serveurs MCP dans l'interface utilisateur [#adding-mcp-servers-in-the-ui]

Vous pouvez également ajouter et configurer des serveurs MCP directement depuis l'interface de LibreChat sans modifier de fichiers de configuration ni redémarrer le serveur.

#### Étape 1 : Ouvrir le panneau des paramètres MCP [#step-1-open-the-mcp-settings-panel]

Accédez au panneau **MCP Settings** depuis la barre latérale droite. Vous y verrez tous les serveurs MCP existants listés, ainsi qu'un bouton **+** pour en ajouter de nouveaux.

![Panneau des paramètres MCP](/images/mcp/mcp_ui_settings_panel.png)

#### Étape 2 : Remplir les détails du serveur [#step-2-fill-out-server-details]

Appuyez sur le bouton **+** et remplissez le nom de votre serveur MCP, sa description, son URL, son type de transport et sa méthode d'authentification, puis cliquez sur **Create**.

![Boîte de dialogue Ajouter un serveur MCP](/images/mcp/mcp_ui_configure.png)

Votre nouveau serveur apparaîtra dans le panneau MCP Settings avec une notification de confirmation.

![Serveur MCP créé avec succès](/images/mcp/mcp_ui_success_registered.png)

#### Étape 3 : Vérifier l'état de la connexion et s'authentifier [#step-3-check-connection-status-and-authenticate]

Consultez l' [indicateur d'état de connexion](#connection-status-indicators) pour votre nouveau serveur. Si le serveur nécessite une authentification OAuth, l'état s'affichera comme déconnecté. Sélectionnez le serveur MCP dans la palette **+** du compositeur pour lancer le processus d'authentification.

![État de la connexion - Déconnecté](/images/mcp/mcp_ui_unconnected.png)

Une fois lancé, l'indicateur de statut se mettra à jour pour indiquer que l'authentification est en cours.

![État de la connexion - Authentification en cours](/images/mcp/mcp_ui_authenticating.png)

#### Étape 4 : Continuer avec OAuth [#step-4-continue-with-oauth]

LibreChat présente une invite de confirmation **Connect**. Vérifiez la destination et sélectionnez **Continue with OAuth** pour ouvrir la page d'autorisation du fournisseur dans un nouvel onglet du navigateur. Terminez le processus de connexion et de consentement du fournisseur à cet endroit.

Si un flux démarré dans ce navigateur est en attente, LibreChat maintient ce serveur dans un état d'autorisation/connexion même si le statut de connexion mis en cache indique toujours **Connected**. L'invite ne doit pas se fermer simplement parce qu'un ancien statut signale une autorisation durable ; seul le succès, l'échec, le délai d'attente ou l'annulation du terminal met fin au flux en attente. Un flux démarré dans un autre onglet ou navigateur n'a pas d'état local en attente dans cette vue.

![Invite à continuer OAuth](/images/mcp/mcp_ui_callback_confirm.png)

#### Étape 5 : Authentification réussie [#step-5-authentication-successful]

Après l'authentification, vous verrez une confirmation de succès. Cette fenêtre se fermera automatiquement et vous redirigera vers LibreChat.

![Authentication Successful](/images/mcp/mcp_ui_success_redirect.png)

#### Étape 6 : Serveur prêt à l'emploi [#step-6-server-ready-for-use]

LibreChat reconnaît l'authentification réussie et sélectionne automatiquement le serveur MCP pour une utilisation au sein de votre conversation. Le serveur affiche désormais un indicateur de statut connecté et apparaît sous forme de puce sélectionnée dans le compositeur.

![Serveur MCP authentifié et sélectionné automatiquement](/images/mcp/mcp_ui_done.png)

Votre nouveau serveur MCP est également disponible dans l'Agent Builder, où vous pouvez ajouter ses outils à n'importe quel agent et personnaliser le sous-ensemble d'outils autorisés.

![Serveur MCP disponible dans le générateur d'agents](/images/mcp/mcp_ui_agent.png)

#### Variables d'identification pour les serveurs créés via l'interface utilisateur [#credential-variables-for-ui-created-servers]

Lors de l'ajout d'un serveur MCP via l'interface utilisateur, vous pouvez exiger que les utilisateurs fournissent leurs propres clés API. Dans la section Authentication de la boîte de dialogue MCP Server Builder, sélectionnez "API Key" et cochez **"User provides key"**. Choisissez le format d'en-tête (Bearer, Basic ou Custom) et enregistrez le serveur.

En coulisses, LibreChat crée une entrée `customUserVars` liée à la destination nommée `MCP_API_KEY_<hash>` et configure l'en-tête d'authentification correspondant. Le nom est géré automatiquement ; les utilisateurs saisissent toujours leur clé dans la boîte de dialogue de sélection d'outils MCP ou dans le panneau des paramètres MCP. Les serveurs existants peuvent conserver l'ancien nom `MCP_API_KEY` tant que leur limite de requête reste inchangée. Cela utilise la même interface utilisateur de saisie de clé que les [`customUserVars` définies dans le YAML](#user-provided-credentials).

La modification de l'URL (y compris le chemin ou la requête), du proxy, du transport, du format d'autorisation, de l'en-tête d'authentification personnalisé ou du client/destination OAuth configuré d'un serveur créé via l'interface utilisateur nécessite que chaque utilisateur saisisse une clé pour la nouvelle limite. Les anciennes clés enregistrées ne sont pas transférées vers cette destination de remplacement. Les modifications cosmétiques, les URL normalisées équivalentes et les modifications d'URL sortantes ne concernant que le fragment préservent la clé existante. Les serveurs partagés ne peuvent résoudre que les variables d'identification déclarées par leur configuration actuelle ; un éditeur ne peut donc pas référencer un ancien nom généré pour récupérer une clé précédente. Aucune migration massive des identifiants n'est nécessaire. Mettez à niveau **chaque réplique d'API**, y compris les répliques traitant les demandes de modification de serveur, avant de vous fier à cette protection ; un ancien rédacteur peut toujours recréer une configuration non liée.

Lorsqu'une clé API d'administrateur ou d'utilisateur est configurée, LibreChat traite le serveur comme étant authentifié par clé API et ignore la détection automatique OAuth. Une configuration OAuth explicite reste prioritaire. Si un serveur avec clé API créé via l'interface utilisateur a été enregistré par une ancienne version de LibreChat et reste bloqué sur **OAuth Required**, modifiez et enregistrez le serveur une fois afin que ses métadonnées de connexion stockées soient actualisées.

<Callout type="warning">
Pour des raisons de sécurité, les serveurs MCP créés via l'interface utilisateur (provenant de la base de données) ne peuvent **uniquement** résoudre les espaces réservés `customUserVars` (`{{VAR_NAME}}`). Les variables d'environnement côté serveur (`${ENV_VAR}`), les champs de profil utilisateur (`{{LIBRECHAT_USER_*}}`) et les jetons OIDC (`{{LIBRECHAT_OPENID_*}}`) sont intentionnellement bloqués pour empêcher tout accès non autorisé aux secrets du serveur ou aux données d'autres utilisateurs. Pour une prise en charge complète des espaces réservés, configurez le serveur dans `librechat.yaml` à la place.
</Callout>

## Gestion des serveurs MCP [#mcp-server-management]

LibreChat fournit des outils complets pour gérer les connexions aux serveurs MCP, avec un suivi de l'état de la connexion ainsi qu'une prise en charge de l'authentification et de l'initialisation OAuth dans l'interface utilisateur.

### Indicateurs d'état de la connexion [#connection-status-indicators]

LibreChat affiche des icônes d'état dynamiques indiquant l'état actuel de chaque serveur MCP dans la palette **+** du compositeur et dans le panneau des paramètres :

![Icônes d'état du serveur MCP](/images/mcp/mcp_server_status_icons.png)

**Types de statut :**

- **Connecté** (engrenage vert) : Le serveur est connecté et possède des customUserVars configurables
- **OAuth Required** (clé orange) : Le serveur nécessite une authentification OAuth
- **Déconnecté** (prise orange) : La connexion au serveur a échoué ou a été perdue
- **Initialisation** (chargeur bleu) : Le serveur démarre ou se reconnecte
- **Erreur** (triangle rouge) : Le serveur a rencontré une erreur
- **Annulation** (croix rouge) : Le flux OAuth est en cours d'annulation

### Annulation d'OAuth depuis la boîte de dialogue de l'outil Agent [#cancelling-oauth-from-the-agent-tool-dialog]

Dans **Agent Builder → Tool Library → MCP server configuration**, **Connect** devient une action **Cancel** activée tandis que le gestionnaire de serveur partagé signale un flux OAuth annulable. Cela inclut un flux en attente découvert depuis un autre panneau LibreChat. Choisissez **Cancel** pour arrêter ce flux, fermer l'invite OAuth locale et effacer sa sélection automatique d'outils en attente. Un résultat de connexion tardif après l'annulation n'attache pas automatiquement les outils dans cette boîte de dialogue. Vous pouvez choisir **Connect** à nouveau pour une nouvelle tentative. L'initialisation qui n'est pas annulable affiche toujours son état occupé désactivé plutôt qu'une action d'annulation.

### Initialisation du serveur [#server-initialization]

Vous pouvez initialiser ou réinitialiser les serveurs MCP directement depuis l'interface :

**En un clic :**

- Initialisation en un clic en sélectionnant le serveur dans la section **MCP Servers** de la palette **+** du compositeur

  <Video src="/videos/mcp_one_click_init.mp4" title="Initialisation MCP en un clic" />

**Depuis MCPConfigDialog :**

- Choisissez **Configure** sur la ligne d'un serveur MCP dans la palette **+** du compositeur pour ouvrir la MCPConfigDialog
- Configurez les variables utilisateur personnalisées et cliquez sur le bouton Authenticate/Initialize en fonction du type d'authentification du serveur.

       <Video src="/videos/mcp_config_dialog_auth.mp4" title="Authentification de la boîte de dialogue de configuration MCP" />

  **Depuis le panneau des paramètres MCP :**

- Cliquez sur n'importe quel serveur dans la section de liste des serveurs du panneau des paramètres MCP pour accéder aux contrôles de configuration et d'initialisation.
- Configurez les variables utilisateur personnalisées et cliquez sur le bouton Authenticate/Initialize en fonction du type d'authentification du serveur.

  <Video src="/videos/mcp_settings_init.mp4" title="Initialisation du panneau des paramètres MCP" />

Les échecs d'initialisation distinguent désormais un serveur inaccessible, des `customUserVars` manquantes, une connexion OAuth devant être réauthentifiée, et un échec d'initialisation générique. Utilisez les variables manquantes nommées ou l'action de réauthentification dans le message avant de réessayer ; le serveur n'a plus besoin d'être supprimé puis rajouté pour ces cas.

Le chargement passif du catalogue fusionne les tentatives de découverte OAuth et applique une interruption progressive après les échecs, afin qu'une intégration déconnectée ne retente pas la découverte à chaque requête. Les changements d'identifiants sont protégés par génération entre les répliques, empêchant un résultat de découverte plus ancien de remplacer une authentification plus récente. Les opérateurs peuvent ajuster la politique de récupération bornée sous [`mcpSettings.catalogRecovery`](/docs/configuration/librechat_yaml/object_structure/mcp_settings#catalogrecovery) ; les valeurs par défaut sont appropriées pour la plupart des déploiements.

Si un Agent attend explicitement des outils MCP mais qu'aucun ne peut être résolu au démarrage de l'exécution, LibreChat échoue l'exécution avec des conseils de connexion et d'accès au lieu de s'exécuter silencieusement sans ces outils.

Les serveurs MCP qui émettent `notifications/tools/list_changed` peuvent mettre à jour leur catalogue d'outils sans redémarrage de LibreChat. LibreChat récupère la liste actuelle depuis la connexion active, publie les outils ajoutés et cesse de proposer les outils que le serveur a supprimés. Les reconnexions synchronisent également le catalogue avant que la connexion ne soit considérée comme prête. Les actualisations de snapshots gérées et la découverte de serveurs à froid partagent un verrou de trois opérations à l'échelle du processus. Une fois admis, chaque opération reste limitée par son délai d'expiration de liste d'outils ou de découverte par serveur, y compris tout `initTimeout` plus court, afin qu'un travail de catalogue lent ne puisse pas bloquer un emplacement indéfiniment.

Pour les serveurs HTTP diffusables (Streamable), une reconnexion peut brièvement renvoyer un code HTTP `409` lorsque le serveur conserve encore un flux SSE autonome obsolète pour l'ancienne session. LibreChat traite cela comme un état transitoire, supprime la session obsolète et rétablit la connexion automatiquement ; aucune intervention de l'opérateur n'est nécessaire lorsque la récupération réussit. Si la connexion rétablie échoue également, LibreChat continue d'afficher l'erreur de connexion sous-jacente.

LibreChat classifie les réponses HTTP Streamable à partir du type de média `Content-Type` analysé plutôt que par une correspondance de sous-chaîne. Les paramètres ne peuvent pas faire passer une réponse non-SSE pour du `text/event-stream`, les erreurs de taille de réponse continuent donc via le chemin de traitement SSE ou non-SSE approprié.

### Visibilité du panneau des paramètres MCP [#mcp-settings-panel-visibility]

Le panneau des paramètres MCP apparaît dans la barre latérale droite lorsque LibreChat détecte des serveurs MCP susceptibles de nécessiter une intervention de l'utilisateur lors de leur initialisation. Le panneau sera visible lorsqu'un serveur configuré répond à l'un de ces critères :

- **Variables utilisateur personnalisées** : Le serveur possède des `customUserVars` définies qui peuvent contenir des identifiants fournis par l'utilisateur
- **Authentification OAuth** : Le serveur est détecté comme nécessitant une authentification OAuth lors du démarrage
- **Initialisation manuelle** : Le serveur a `startup: false` configuré, nécessitant une initialisation manuelle

## Fonctionnalités spécifiques à LibreChat [#librechat-specific-features]

L'implémentation MCP de LibreChat est conçue pour des environnements multi-utilisateurs réels et hautement configurables.

### Connexions spécifiques à l'utilisateur [#user-specific-connections]

- Chaque utilisateur dispose de sa propre connexion isolée aux serveurs MCP
- L'authentification et les permissions des utilisateurs sont respectées
- Les données personnelles et le contexte restent privés

### Partage des serveurs MCP [#sharing-mcp-servers]

Les serveurs MCP participent au système de [contrôle d'accès granulaire](/docs/features/access_control) de LibreChat. En plus des serveurs définis dans `librechat.yaml` (qui sont gérés par les administrateurs et régis par les autorisations de fonctionnalité [`interface.mcpServers`](/docs/configuration/librechat_yaml/object_structure/interface#mcpservers)), les serveurs MCP créés par les utilisateurs possèdent leur propre ACL et peuvent être partagés avec des **utilisateurs**, **groupes**, **rôles** spécifiques, ou **publiquement**, au niveau Lecteur, Éditeur ou Propriétaire.

Les indicateurs de fonctionnalité `USE`, `CREATE`, `SHARE` et `SHARE_PUBLIC` sous `interface.mcpServers` contrôlent qui est autorisé à créer et à partager des serveurs MCP. Consultez [Access Control](/docs/features/access_control) pour savoir comment les couches d'autorisation se composent.

### Contexte utilisateur dynamique [#dynamic-user-context]

Les serveurs MCP peuvent accéder aux informations utilisateur via des espaces réservés dans les **URLs et les en-têtes** (pour les transports SSE et HTTP diffusables) :

```yaml
mcpServers:
  user-api:
    type: streamable-http
    url: https://api.example.com/users/{{LIBRECHAT_USER_USERNAME}}/mcp
    headers:
      X-User-ID: '{{LIBRECHAT_USER_ID}}'
      X-User-Email: '{{LIBRECHAT_USER_EMAIL}}'
      X-User-Role: '{{LIBRECHAT_USER_ROLE}}'
      Authorization: 'Bearer ${API_TOKEN}'
```

Les espaces réservés disponibles incluent :

- `{{LIBRECHAT_USER_ID}}` - Identifiant utilisateur unique
- `{{LIBRECHAT_USER_EMAIL}}` - Adresse e-mail de l'utilisateur
- `{{LIBRECHAT_USER_ROLE}}` - Rôle de l'utilisateur (admin, user, etc.)
- `{{LIBRECHAT_USER_USERNAME}}` - Nom d'utilisateur
- Et bien plus encore (voir [Configuration des serveurs MCP](/docs/configuration/librechat_yaml/object_structure/mcp_servers#headers) pour la liste complète)

Les serveurs MCP définis en YAML peuvent également utiliser les espaces réservés `{{LIBRECHAT_OPENID_*}}`, `{{LIBRECHAT_GRAPH_*}}` et `{{LIBRECHAT_BODY_*}}`. Les valeurs `{{LIBRECHAT_BODY_*}}` sont limitées à la portée de la requête ; ainsi, LibreChat crée des connexions pour l'exécution active, les réutilise lors des appels d'outils au cours de cette exécution et les nettoie à la fin de la requête. Les serveurs limités à la portée de la requête sont exclus du cache d'outils persistant afin que les en-têtes et les URL spécifiques à la requête ne soient pas réutilisés en dehors de l'exécution active. Étant donné que leur liste d'outils ne peut pas être résolue avant l'existence d'une requête de chat, l'Agent Builder expose une sélection d'outils d'exécution pour le serveur complet et résout ses outils au moment de l'exécution. La finalisation de l'OAuth stocke l'autorisation mais diffère la connexion jusqu'à ce que la première exécution fournisse le contexte de la requête. Les espaces réservés User, OpenID et Graph sont limités à la portée de l'utilisateur ; les transports HTTP actualisent leurs en-têtes résolus avant chaque appel d'outil sans nécessiter de reconnexion par eux-mêmes.

Les opérateurs de confiance peuvent utiliser `Authorization: 'Bearer {{LIBRECHAT_OPENID_ACCESS_TOKEN}}'` sur un serveur distant défini dans le fichier YAML pour transmettre le jeton d'accès OpenID actif de l'utilisateur. L'authentification explicite MCP OAuth, l'échange pour le compte de (on-behalf-of) et l'authentification par clé API administrateur sont prioritaires. Après une erreur `401` ou `403`, LibreChat peut actualiser la connexion une fois, mais il ne rejoue jamais automatiquement l'appel d'outil rejeté. Consultez la [référence des espaces réservés pour serveur MCP](/docs/configuration/librechat_yaml/object_structure/mcp_servers#headers) pour obtenir des conseils sur la configuration et la sécurité.

`{{LIBRECHAT_GRAPH_ACCESS_TOKEN}}` échange le jeton d'accès OpenID réutilisable de l'utilisateur via le flux on-behalf-of de Microsoft. [`GRAPH_API_SCOPES`](/docs/configuration/dotenv#microsoft-graph-api--entra-id-integration) définit les étendues demandées séparées par des espaces et utilise `https://graph.microsoft.com/.default` par défaut. Ceci est indépendant de `OPENID_GRAPH_SCOPES`, qui configure la recherche de personnes et de groupes.

Le paramètre fictif `{{LIBRECHAT_BODY_PARENTMESSAGEID}}` est renseigné pour les conversations d'agents natifs, les appels d'API d'agents compatibles avec OpenAI et les exécutions d'Assistants hérités. Open Responses n'a pas d'équivalent d'identité de message parent et échoue par défaut lorsqu'un serveur MCP requiert cette valeur. Voir la [référence des paramètres fictifs des serveurs MCP](/docs/configuration/librechat_yaml/object_structure/mcp_servers#headers).

### Instructions du serveur [#server-instructions]

`serverInstructions` est une fonctionnalité de LibreChat qui ajoute dynamiquement des instructions configurées lorsqu'un outil provenant de ce serveur MCP est sélectionné :

```yaml
mcpServers:
  filesystem:
    command: npx
    args: ['-y', '@modelcontextprotocol/server-filesystem', '/docs']
    serverInstructions: |
      When accessing files:
      - Always check file permissions first
      - Use absolute paths for reliability
      - Handle errors gracefully
```

Options :

- `true` : Utiliser les instructions annoncées par le serveur lorsqu'elles sont disponibles
- `false` : Désactiver les instructions
- `string` : Utilisez les instructions personnalisées textuellement (indiquées ci-dessus)

LibreChat conserve cette déclaration configurée séparément des instructions récupérées lors de l'inspection du serveur. Une déclaration `true` reste donc activée lors de l'inspection et des rechargements du registre mis en cache, tandis qu'une chaîne personnalisée demeure prioritaire.

### Configuration du délai d'attente (Timeout) [#timeout-configuration]

Pour les opérations MCP de longue durée, configurez des délais d'attente appropriés à la fois pour l'initialisation et pour les opérations d'outils.

```yaml
mcpServers:
  data-processor:
    type: streamable-http
    url: https://api.example.com/mcp
    initTimeout: 15000 # 15 seconds for server initialization
    timeout: 60000 # 60 seconds for tool operations
```

**Note** : Si les opérations sont toujours interrompues prématurément, vérifiez la configuration de votre proxy (par exemple, nginx, traefik, etc.), qui pourrait couper les connexions trop tôt en raison des délais d'attente par défaut.

Lorsqu'un utilisateur appuie sur **Stop** pendant un appel d'outil Agent au premier plan, LibreChat transmet le signal d'annulation de l'exécution à MCP. Pour les serveurs HTTP diffusables (Streamable), le SDK MCP envoie `notifications/cancelled` ; le serveur doit honorer cette notification pour arrêter son propre travail. Les appels en arrière-plan détachés conservent intentionnellement un cycle de vie distinct et ne sont pas annulés avec le tour au premier plan.

### Identifiants fournis par l'utilisateur [#user-provided-credentials]

Vous pouvez permettre aux utilisateurs de fournir leurs propres identifiants pour les serveurs MCP via `customUserVars`. Cela permet une authentification sécurisée et spécifique à l'utilisateur sans stocker les identifiants dans les fichiers de configuration.

```yaml
mcpServers:
  my-api-server:
    type: streamable-http
    url: 'https://api.example.com/mcp'
    headers:
      X-Auth-Token: '{{MY_API_KEY}}' # Uses the user-provided value
    customUserVars:
      MY_API_KEY:
        title: 'API Key'
        description: "Enter your personal API key from <a href='https://example.com/keys' target='_blank'>your account settings</a>"
```

Les utilisateurs peuvent configurer ces identifiants :

- **Depuis la zone de chat** : Choisissez **Configure** sur la ligne d'un serveur MCP configurable dans la palette **+** du compositeur
- **Depuis le panneau des paramètres MCP** : Accédez à « MCP Settings » dans le panneau de droite pour gérer les identifiants de tous les serveurs configurés.

#### Réinitialisation des serveurs MCP avec les identifiants utilisateur [#reinitializing-mcp-servers-with-user-credentials]

Pour les serveurs MCP qui nécessitent des identifiants spécifiques à l'utilisateur avant de pouvoir être utilisés (par exemple, les `PAT_TOKEN` dans le [serveur MCP officiel de GitHub](https://github.com/github/github-mcp-server)), LibreChat permet aux utilisateurs de fournir ces identifiants, puis de réinitialiser le serveur MCP depuis l'interface utilisateur sans redémarrer toute l'application :

1. Lorsque vous sélectionnez un MCP qui utilise `customUserVars`, vous pourrez **Enregistrer** ou **Révoquer** la valeur d'une `customUserVar` pour le serveur MCP sélectionné depuis le panneau MCP.
2. Après avoir enregistré une valeur pour une `customUserVar`, cliquez sur le bouton de réinitialisation (une icône avec des flèches circulaires à côté de chaque nom de serveur dans le panneau MCP).
3. LibreChat tentera de se connecter au serveur en utilisant vos identifiants fournis et vous notifiera via une notification toast si le processus de réinitialisation a réussi ou échoué.

> _Astuce : Si vous savez qu'un serveur nécessitera des identifiants qui ne sont pas disponibles au premier démarrage, vous pouvez ajouter `startup: false` à sa configuration. Cela indique à LibreChat de ne pas tenter de se connecter à ce serveur tant qu'il n'est pas réinitialisé manuellement dans l'interface utilisateur._

**Exemple :**

```yaml
mcpServers:
  github-mcp:
    type: streamable-http
    url: 'https://api.githubcopilot.com/mcp/'
    headers:
      Authorization: '{{PAT_TOKEN}}'
    customUserVars:
      PAT_TOKEN:
        title: 'GitHub PAT Token'
        description: 'GitHub Personal Access Token'
    startup: false
```

### Authentification OAuth [#oauth-authentication]

LibreChat prend en charge l'authentification OAuth pour les serveurs MCP, conformément aux recommandations d'Anthropic pour des connexions MCP sécurisées. OAuth fournit un moyen standardisé et sécurisé de s'authentifier sans stocker d'identifiants à longue durée de vie.

#### Flux OAuth pris en charge [#supported-oauth-flows]

Les serveurs MCP de LibreChat prennent en charge OAuth 2.0 avec :

- **Flux de code d'autorisation avec PKCE** : Recommandé pour une sécurité maximale
- **Découverte du client** : Enregistrement automatique du client lorsqu'il est pris en charge par le fournisseur OAuth
- **Jetons de rafraîchissement (Refresh Tokens)** : Renouvellement automatique des jetons lorsqu'ils sont disponibles
- **Découverte du token endpoint** : Les clients préconfigurés peuvent découvrir si le fournisseur attend les identifiants client dans le corps de la requête POST ou dans un en-tête d'autorisation HTTP Basic

Dans le MCP Builder, **Token Exchange Method** propose **Auto**, **Default (POST request)** et **Basic authorization header**. Auto laisse la méthode non définie afin que LibreChat puisse utiliser les métadonnées du fournisseur de confiance, en revenant à l'authentification Basic lorsque le fournisseur n'annonce aucune méthode.

#### Exemples de configuration [#configuration-examples]

```yaml
mcpServers:
  # Public remote MCP server for PayPal, uses OAuth Client Discovery
  # ❌ Refresh Tokens: you may need to re-authenticate periodically
  # More info: https://developer.paypal.com/tools/mcp-server/
  paypal:
    type: 'sse'
    initTimeout: 150000 # higher timeout to allow for initial authentication
    url: 'https://mcp.paypal.com/sse'

  # Example self-hosted remote MCP server for Spotify, uses OAuth Client Discovery
  # ✅ Refresh Tokens: refreshes token for authentication automatically
  # Hosted on Cloudflare Workers, more info: https://github.com/LibreChat-AI/spotify-mcp
  spotify:
    type: 'streamable-http'
    initTimeout: 150000
    url: 'https://mcp-spotify-oauth-example.account.workers.dev/mcp'
```

#### Flux d'authentification OAuth [#oauth-authentication-flow]

Lorsque vous configurez pour la première fois un serveur MCP avec OAuth :

1. **Connexion initiale** : LibreChat tente de se connecter au serveur MCP
2. **Authentification requise** : Si aucun jeton valide n'existe, vous verrez un statut d'authentification OAuth pour ce serveur dans la palette **+** du compositeur.
3. **Démarrer la connexion** : Sélectionnez le serveur pour commencer le flux OAuth
4. **Continuer ou utiliser un autre appareil** : Continuez dans le navigateur actuel, copiez le lien d'autorisation ou affichez un code QR pour l'ouvrir sur un autre appareil
5. **Redirection du navigateur** : Terminez l'authentification avec le fournisseur OAuth
6. **Gestion du retour** : LibreChat traite automatiquement le rappel OAuth une fois que vous vous êtes authentifié
7. **Stockage des jetons** : LibreChat stocke les jetons de manière sécurisée pour une utilisation ultérieure
8. **Connexion établie** : Une fois authentifié, le serveur MCP sera connecté et vous pourrez l'utiliser dans votre chat

#### URL de rappel OAuth [#oauth-callback-url-1]

Lorsqu'un serveur MCP utilise OAuth, LibreChat expose un endpoint de rappel vers lequel le fournisseur OAuth redirige après une autorisation réussie.

L'URL de rappel doit suivre ce format :

`${baseUrl}/api/mcp/${serverName}/oauth/callback`

Où `${serverName}` est la clé du serveur MCP définie dans votre configuration `librechat.yaml`. LibreChat gère la redirection à ce endpoint, effectue l'échange de jetons et associe les identifiants au serveur MCP correspondant.

<Callout type="info" title="Exemple d'URL de rappel OAuth">
Étant donné la configuration de serveur MCP suivante :

```yaml
mcpServers:
  # Example self-hosted remote MCP server for Spotify, uses OAuth Client Discovery
  # ✅ Refresh Tokens: refreshes token for authentication automatically
  # Hosted on Cloudflare Workers, more info: https://github.com/LibreChat-AI/spotify-mcp
  spotify:
    type: 'streamable-http'
    initTimeout: 150000
    url: 'https://mcp-spotify-oauth-example.account.workers.dev/mcp'
```

L'URL de rappel serait `${baseUrl}/api/mcp/spotify/oauth/callback`.

</Callout>

Remarque :

- L'URL de rappel doit être enregistrée exactement auprès du fournisseur OAuth pour que le flux fonctionne.
- D'autres chemins tels que `/api/oauth/callback` ou `/api/oauth/openid/callback` ne sont pas valides pour les flux OAuth MCP.

#### Gestion des jetons [#token-management]

LibreChat gère les jetons OAuth de manière intelligente :

- **Stockage sécurisé** : Les jetons sont chiffrés et stockés de manière sécurisée
- **Actualisation automatique** : Lorsque des jetons d'actualisation sont disponibles, LibreChat renouvelle automatiquement les jetons d'accès expirés
- **Récupération silencieuse 401** : Si une connexion MCP OAuth reçoit un rejet d'authentification en cours de session, LibreChat coordonne une tentative de rafraîchissement et de reconnexion limitée par utilisateur et par serveur. Les appelants simultanés partagent ce résultat de récupération avant que LibreChat n'affiche une nouvelle invite d'authentification.
- **Gestion de session** : Chaque utilisateur conserve ses propres sessions OAuth pour les environnements multi-utilisateurs

Si un flux d'Agent enregistré est rechargé ou repris alors qu'une demande d'autorisation MCP est toujours en attente, LibreChat reconstruit cette demande à partir de l'état de génération durable. Les demandes terminées, annulées, ayant échoué ou expirées ne sont pas restaurées.

Les clients et jetons OAuth stockés sont liés à l'URL du serveur MCP et aux paramètres du client/endpoint OAuth. La modification de ces paramètres oblige les utilisateurs à s'authentifier à nouveau. Lors de la modification d'un serveur créé via l'interface utilisateur qui conserve un `client_secret` stocké, saisissez à nouveau le secret lors du changement d'un champ de liaison tel que l'URL du serveur, l'ID client, l'URL d'autorisation, l'URL du jeton ou la méthode d'authentification du jeton.

Dans les déploiements mis à l'échelle horizontalement, le statut du flux OAuth et la disponibilité des jetons liés peuvent être réconciliés entre les pods LibreChat. L'interface utilisateur signale qu'un serveur est prêt uniquement après la réussite de l'initialisation post-OAuth, même lorsque le rappel et l'interrogation du statut atteignent des pods différents. Les rappels provenant de tentatives obsolètes sont rejetés.

Lorsque Redis est activé, les générations de catalogue MCP au niveau de l'application et les révisions de publication sont coordonnées entre les réplicas. Les déploiements de Redis Cluster utilisent des clés de catalogue et des mises à jour sécurisées par slot, de sorte que la synchronisation au démarrage et les actualisations de `tools/list_changed` ne nécessitent pas une configuration Redis à nœud unique.

Chaque utilisateur sera invité à s'authentifier avec sa propre connexion OAuth lors de la première utilisation d'un serveur MCP compatible OAuth. Cela garantit que les détails de connexion et d'authentification sont uniques à chaque utilisateur, préservant ainsi la sécurité et la confidentialité dans les environnements multi-utilisateurs.

#### Synchronisation OAuth [#oauth-timing]

La complétion OAuth MCP utilise son propre délai d'attente configuré par le serveur au lieu de réutiliser le `initTimeout` du serveur MCP. Par défaut, LibreChat attend jusqu'à 10 minutes que l'utilisateur termine l'OAuth MCP et conserve l'état du flux pendant 15 minutes.

Utilisez ces variables d'environnement lorsqu'un fournisseur OAuth ou un flux de travail utilisateur nécessite plus de temps :

```bash filename=".env"
MCP_OAUTH_HANDLING_TIMEOUT=600000
MCP_OAUTH_FLOW_TTL=900000
```

`MCP_OAUTH_FLOW_TTL` est limité pour durer plus longtemps que `MCP_OAUTH_HANDLING_TIMEOUT`, afin que les rappels proches de l'échéance puissent toujours trouver leur état de flux. La fenêtre d'interrogation de la carte serveur MCP suit le délai de traitement configuré.

![Flux d'authentification OAuth spécifique à l'utilisateur](/images/agents/mcp_oauth_flow.png)

> Remarque : Les jetons affichés lors du démarrage de l'application servent uniquement à l'initialisation au niveau de l'application et ne sont pas utilisés pour les connexions des utilisateurs individuels.

Exemple de rafraîchissement automatique des jetons :

```bash
[MCP][spotify] Access token missing
[MCP][spotify] Attempting to refresh token
[MCP][spotify] Successfully refreshed and stored OAuth tokens
[MCP][spotify] ✓ Initialized
```

#### Meilleures pratiques [#best-practices]

1. **Utiliser OAuth lorsque disponible** : Préférez OAuth aux clés API pour une meilleure sécurité
2. **Configurer les délais d'attente appropriés** : Utilisez `MCP_OAUTH_HANDLING_TIMEOUT` et `MCP_OAUTH_FLOW_TTL` pour les fenêtres de finalisation OAuth ; utilisez `initTimeout` pour l'initialisation du serveur
3. **Surveiller l'expiration des jetons** : Vérifiez les journaux pour les problèmes d'authentification
4. **Plan de ré-authentification** : Certains fournisseurs ne prennent pas en charge les jetons d'actualisation (refresh tokens)

## Transports serveur [#server-transports]

Les serveurs MCP peuvent être configurés pour utiliser différents mécanismes de transport :

**Serveurs STDIO**

- Fonctionne bien pour les environnements locaux à utilisateur unique
- Non évolutif pour les déploiements distants ou dans le cloud
- Le SDK MCP fourni limite chaque message STDIO individuel à 10 Mo. Un résultat unique plus volumineux ferme le transport avec une erreur ; cette limite est distincte de la taille totale d'une session ou d'un flux.

**Serveurs Server-Sent Events (SSE)**

- Mécanisme de transport distant, mais non recommandé pour un environnement de production

**Serveurs HTTP Streamables**

- Utilise HTTP POST pour l'envoi de messages et prend en charge la diffusion de réponses en continu
- Fonctionne comme un processus indépendant capable de gérer plusieurs connexions client
- Prend en charge à la fois les requêtes de base et le streaming via Server-Sent Events (SSE)
- Alternative plus performante au transport HTTP+SSE hérité
- Prend en charge des configurations de serveur multi-utilisateurs appropriées

**Pour les environnements de production**, seuls les serveurs MCP utilisant des ["Streamable HTTP" transports](https://modelcontextprotocol.io/specification/draft/basic/transports/streamable-http) sont recommandés. Contrairement au SSE qui maintient des connexions longue durée, le Streamable HTTP offre des options sans état (stateless) mieux adaptées aux déploiements évolutifs multi-utilisateurs.

LibreChat est à la pointe de l'implémentation d'intégrations de serveurs MCP flexibles et évolutives pour prendre en charge divers scénarios d'utilisation et vous aider à construire les flux de travail IA de demain.
