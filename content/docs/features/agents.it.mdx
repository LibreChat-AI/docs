# Agenti: Crea assistenti AI personalizzati [#agents-build-custom-ai-assistants]

La funzionalità AI Agents di LibreChat fornisce un framework flessibile per creare assistenti AI personalizzati basati su vari provider di modelli.

Questa funzionalità è simile all'Assistants API di OpenAI e ai GPT di ChatGPT, ma con un supporto ai modelli più ampio e un'implementazione no-code, che ti consente di creare assistenti sofisticati con funzionalità specializzate.

## Introduzione [#getting-started]

Per creare un nuovo agente, seleziona "Agents" dal menu endpoint e apri il pannello Agent Builder che si trova nel Side Panel.

![Agents - Endpoints Menu](/images/agents/endpoints_menu.png)

Il modulo di creazione include:

- **Avatar**: Carica un avatar personalizzato per personalizzare il tuo agente
- **Name**: Scegli un nome distintivo per il tuo agente
- **Descrizione**: Dettagli opzionali sullo scopo del tuo agente
- **Istruzioni**: Istruzioni di sistema che definiscono il comportamento del tuo agente
- **Modello**: Seleziona tra i provider e i modelli disponibili
- **Conversation Starters**: Fino a quattro suggerimenti di prompt mostrati quando un utente avvia una nuova chat con l'agente

I controlli **Tools** e **Skills** aprono librerie ricercabili per funzionalità integrate, strumenti, server MCP, Actions e Skills. Seleziona un elemento per configurarlo, quindi salva l'agente.

**Gli agenti esistenti possono essere selezionati dal menu a discesa in alto nel Pannello Laterale.**

- **Anche tramite menzione con "@" nell'input della chat.**

![Agents - Mention](/images/agents/mention.png)

### Libreria di strumenti [#tool-library]

L'Agent Builder mantiene gli elementi abilitati in sezioni separate per **Tools** e **Skills**. Apri **Add tools** per cercare nel catalogo completo o filtrarlo per **Official**, **Tools**, **MCP** o **Actions**. **Made by you** raccoglie i server MCP e le Actions che hai creato, mentre **Favorites** mantiene gli elementi contrassegnati come preferiti disponibili tra i vari agenti. Ogni utente può salvare fino a 100 preferiti nella libreria degli strumenti.

Seleziona un elemento per configurarlo senza uscire dal builder. Il menu **Create new** appare solo quando l'utente ha l'autorizzazione per creare server MCP o Action. La rimozione di una funzionalità basata su file, come File Search, File Context o Code Interpreter, apre il relativo file manager quando ci sono ancora file allegati da revisionare. Una funzionalità basata su file rimane selezionata e viene preservata al salvataggio finché possiede ancora dei file; rimuovi o riassegna tali file prima di rimuovere la funzionalità stessa.

Le Skills utilizzano il proprio selettore e possono essere selezionate individualmente o abilitate come catalogo completo accessibile. Vedi [Skills](/docs/features/skills#agent-scope).

Gli operatori possono anche utilizzare [Agent Plugins](/docs/features/agent_plugins) sperimentali per raggruppare Skills di distribuzione e server MCP in pacchetti caricati all'avvio.

### Configurazione del modello [#model-configuration]

L'interfaccia dei parametri del modello consente di ottimizzare le risposte del tuo agente:

- Temperatura (scala 0-1 per la creatività della risposta)
- Token di contesto massimi
- Token di output massimi
- Dettaglio immagine (`low`, `auto`, o `high`) per input di immagini vision native
- Impostazioni aggiuntive specifiche del provider

Le istruzioni dell'agente possono utilizzare `{{current_date}}`, `{{current_datetime}}` e `{{iso_datetime}}`. LibreChat li risolve dall'inizio del turno logico acquisito dal server e mantiene tale timestamp stabile durante i cicli del provider, l'inizializzazione dei Subagent e la ripresa con intervento umano (human-in-the-loop). I primi due utilizzano il fuso orario della richiesta; `{{iso_datetime}}` rimane UTC.

I guasti di tipo "model-not-found" e i limiti di frequenza del provider riconosciuti forniscono una guida localizzata. Altri errori del provider mantengono il loro utile testo informativo, ma omettono gli URL di risoluzione dei problemi di LangChain prima che il messaggio venga salvato. Quando la [protezione dei contenuti vincolata al modello](/docs/configuration/librechat_yaml/object_structure/message_filter#source-aware-filters) è abilitata, il suo errore generico di protezione ha comunque la precedenza.

### Cronologia delle versioni [#version-history]

Gli utenti con accesso di modifica possono aprire la **Version History** (Cronologia delle versioni) dall'Agent Builder per esaminare le configurazioni salvate in una sequenza temporale. Ogni voce mostra quando è stata salvata e riassume i suoi strumenti e le sue funzionalità. Il ripristino di una voce precedente richiede una conferma e sostituisce la configurazione attuale dell'agente con quello stato salvato. Il salvataggio applica sempre le modifiche correnti dell'agente, anche quando la configurazione risultante corrisponde alla voce più recente della cronologia e LibreChat non aggiunge una voce duplicata.

### Conversation Starters [#conversation-starters]

I conversation starters offrono agli utenti un modo rapido per iniziare una chat con un agente. Ogni agente può memorizzarne fino a quattro.

1. Nell'Agent Builder, trova il campo **Conversation Starters**.
2. Digita un prompt e premi **Enter**, oppure seleziona il pulsante **+**. L'input viene disabilitato una volta aggiunti quattro suggerimenti iniziali.
3. Modifica uno starter salvato direttamente, oppure seleziona il suo pulsante **X** per rimuoverlo.
4. Salva l'agente.

Quando un utente apre una nuova chat con l'agente, gli starter appaiono come pulsanti nella schermata di chat vuota. Selezionandone uno, questo viene inviato immediatamente come primo messaggio. Se l'agente dispone di starter, questi hanno la precedenza su qualsiasi [`conversation_starters`](/docs/configuration/librechat_yaml/object_structure/model_specs#conversation_starters) definito nella Model Specs in uso. Gli starter appaiono anche nella finestra di dialogo dei dettagli del [Marketplace](#agent-marketplace) dell'agente.

## Funzionalità degli Agent [#agent-capabilities]

> **Nota:** Tutte le funzionalità possono essere attivate o disattivate tramite il file di configurazione `librechat.yaml`. Consulta [docs/configuration/librechat_yaml/object_structure/agents#capabilities](/docs/configuration/librechat_yaml/object_structure/agents#capabilities) per maggiori informazioni.

### Code Interpreter [#code-interpreter]

Quando abilitata, la funzionalità Code Interpreter consente al tuo agente di:

- Esegui codice in più linguaggi, inclusi:
  - Python, JavaScript, TypeScript, Go, C, C++, Java, PHP, Rust e Fortran
- Elabora file in modo sicuro tramite l'API Code Interpreter di LibreChat
- Esegui codice senza configurazione locale, impostazioni o deployment di sandbox
- Gestisci caricamenti e download di file senza interruzioni
- [Maggiori informazioni sull'API Code Interpreter](/docs/features/code_interpreter)
  - **Basato sul servizio open-source [code-interpreter](https://github.com/ClickHouse/code-interpreter) (self-hosted)**

Quando ogni file richiesto di Code Interpreter da una conversazione non riesce a essere ripristinato nella sandbox corrente, LibreChat interrompe l'Agent prima di invocare il modello e chiede all'utente di riallegare i file. Ciò impedisce che l'esecuzione prosegua con riferimenti ai file obsoleti o inaccessibili.

Quando i file di conversazione condividono lo stesso nome file per il Code Interpreter, LibreChat assegna destinazioni sandbox distinte e comunica all'Agent i percorsi risolti. Consulta [Seamless File Handling](/docs/features/code_interpreter#seamless-file-handling) per il comportamento in caso di collisioni e per le restrizioni rimanenti sui file privati multi-Agent.

#### Sessioni di codice stateful [#stateful-code-sessions]

Le sessioni di codice stateful consentono a un agente di riutilizzare un workspace sandbox tra diverse esecuzioni di codice. File, pacchetti installati e lo stato di lavoro vengono solitamente mantenuti, il che è utile per l'analisi iterativa e il lavoro su file in più passaggi. Nell'Agent Builder, il selettore **Stateful environment** controlla chi condivide tale workspace:

- **Area di lavoro utente (consigliato):** gli agenti stateful dell'utente che ha effettuato l'accesso condividono un'unica area di lavoro
- **Area di lavoro agente + utente:** ogni utente ottiene un'area di lavoro separata per ogni agente
- **Area di lavoro della conversazione:** ogni utente ottiene un'area di lavoro separata per ogni conversazione

Gli amministratori possono anche configurare backend denominati sotto [`statefulCodeSessions.environments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions). Quando presente, il selettore separato **Execution environment** sceglie la Code API gestita, la VM collegata all'operatore o il worker personale che possiede l'area di lavoro; **Deployment default** utilizza l'ambiente eseguibile predefinito configurato. L'ambito di condivisione di cui sopra rimane indipendente da tale scelta di backend.

Quando una distribuzione abilita i worker self-service, gli utenti con autorizzazione di gestione Code Environment possono aprire **Settings > Code environments** per associare un worker outbound `@librechat/code` sulla propria VM, selezionarlo nell'Agent Builder e revocarlo in seguito. Gli ambienti personali sono vincolati al proprietario e utilizzano lo stesso percorso per codice, shell e Programmatic Tool Calling. Consulta [Attached environments and pairing](/docs/features/code_interpreter#attached-environments-and-pairing) per la configurazione sperimentale e il modello di sicurezza.

All'interno di un workspace allegato, gli Agents possono elencare directory, leggere file, cercare testo, creare file ed eseguire Bash tramite il worker selezionato. Un nome Git e un'email specifici per ogni Agent possono identificare i commit effettuati senza dover fornire le credenziali del repository. Le distribuzioni possono limitare i nuovi worker personali con [`statefulCodeSessions.principalWorkers`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions).

Quando un worker collegato pubblicizza più radici di workspace, il compositore di chat richiede una selezione per ogni ambiente collegato utilizzato dall'Agent o dai suoi Subagent. La conversazione mantiene tali selezioni tra i vari turni e la ripresa dell'approvazione; LibreChat le convalida rispetto al worker attivo e blocca l'invio se un workspace richiesto è mancante o non disponibile. Un worker che pubblicizza esattamente un workspace viene selezionato automaticamente per una nuova conversazione. Vedi [Attached environments and pairing](/docs/features/code_interpreter#attached-environments-and-pairing) per dettagli e limitazioni attuali.

I nuovi Agent utilizzano inizialmente lo **Spazio di lavoro stateful predefinito** dell'utente che ha effettuato l'accesso, configurabile da **Impostazioni > Controllo dati > Esecuzione codice**. L'impostazione predefinita personale è **Spazio di lavoro utente** finché non viene modificata. L'aggiornamento di questa preferenza non altera gli Agent esistenti né abilita di per sé le Sessioni di codice stateful. Gli amministratori possono limitare gli ambiti disponibili con [`statefulCodeSessions.allowedEnvironments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions); quando un'impostazione predefinita personale salvata non è più consentita, i nuovi Agent utilizzano il primo ambito permesso.

<Callout type="warning" title="Altamente sperimentale">
  Le Stateful Code Sessions sono in una fase di sperimentazione iniziale. Il loro comportamento, la configurazione, le caratteristiche di persistenza e l'integrazione sottostante potrebbero cambiare sostanzialmente. Non considerare l'implementazione attuale come un contratto di produzione stabile.
</Callout>

Questa funzionalità è facoltativa (opt-in). Un amministratore deve aggiungere `stateful_code_sessions` alle [capacità dell'agente](/docs/configuration/librechat_yaml/object_structure/agents#capabilities) e configurare una rotta dedicata per il Code Interpreter stateful tramite [`LIBRECHAT_CODE_BASEURL_STATEFUL`](/docs/configuration/dotenv#stateful-code-interpreter-endpoint) o denominata [`statefulCodeSessions.environments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions). Il Code Interpreter deve essere abilitato sull'agente e l'opzione **Stateful code sessions** deve essere attivata nelle sue impostazioni avanzate.

Le richieste stateful non ripiegano sul normale endpoint stateless di Code Interpreter quando l'URL dedicato è mancante o incompatibile. Le sessioni stateful e stateless non condividono inoltre file attivi o pacchetti installati. L'area di lavoro stateful può essere ripristinata in qualsiasi momento, indipendentemente dal suo ambito. Negli ambienti gestiti di Code Interpreter, salva gli output importanti in `/mnt/data`; un'area di lavoro collegata è una directory separata di proprietà del worker. I caricamenti delle chat non vengono copiati per impostazione predefinita in tale directory collegata. Non fare affidamento sullo stato della sessione come archivio permanente per altri scopi.

Quando gli strumenti stateful `create_file` o `edit_file` creano file durante una risposta, il messaggio dell'assistente mostra una riga compatta **Workspace changes**. Espandila per esaminare i percorsi modificati univoci e scaricare ogni file tramite il flusso di file autenticato di LibreChat. Si tratta di un registro per messaggio dei file creati da tali strumenti, non di un'istantanea permanente dell'intero workspace; gli output stateless del Code Interpreter continuano a utilizzare la normale interfaccia di allegati in linea.

Per gli ambienti collegati, il composer può esporre **Ask before changes** (Chiedi prima delle modifiche), **Accept edits** (Accetta modifiche) e **Full access** (Accesso completo) come modalità di approvazione del codice a livello di conversazione. La disponibilità è limitata dallo schema di autorizzazione definito dall'amministratore dell'ambiente; la scelta di una modalità più permissiva non sostituisce mai le concessioni di ruolo, le regole esplicite degli strumenti, gli hook o i limiti della sandbox. Vedi [Attached-environment tool permissions](/docs/features/code_interpreter#attached-environment-tool-permissions).

### Ricerca file [#file-search]

La funzionalità File Search abilita:

- Funzionalità RAG (Retrieval-Augmented Generation)
- Ricerca semantica tra i documenti caricati
- Risposte basate sul contesto dei contenuti dei file
- Supporto per gli allegati di file sia a livello di agent che di chat thread

### Contesto del file [#file-context]

La funzionalità File Context consente al tuo agente di archiviare il testo estratto dai file come parte delle sue istruzioni di sistema:

- Estrai il testo mantenendo la struttura e la formattazione del documento
- Elabora layout complessi, inclusi testo a più colonne e contenuti misti
- Gestisci tabelle, equazioni e altri contenuti specializzati
- Lavorare con contenuti multilingue
- Il testo viene archiviato nelle istruzioni dell'agent nel database
- **Nessun servizio OCR richiesto** - Utilizza l'analisi del testo per impostazione predefinita con metodi di fallback
- **Migliorato tramite OCR** - Se l'OCR è configurato, la qualità dell'estrazione migliora per immagini e documenti scansionati
- Utilizza la stessa logica di elaborazione di "Carica come testo": **OCR > STT > analisi del testo**
- [Maggiori informazioni sulla configurazione OCR](/docs/features/ocr)

**Nota:** Il File Context include il testo estratto nelle istruzioni di sistema dell'agente. Per domande su documenti temporanei in conversazioni individuali, utilizza [Upload as Text](/docs/features/upload_as_text) dalla chat.

### Model Context Protocol (MCP) [#model-context-protocol-mcp]

MCP è un protocollo aperto che standardizza il modo in cui le applicazioni forniscono contesto ai Large Language Models (LLM), agendo come un adattatore universale per strumenti di IA e fonti di dati.

Per ulteriori informazioni, consulta la documentazione su [MCP](/docs/features/mcp).

#### Agenti con strumenti MCP [#agents-with-mcp-tools]

1. Configura i server MCP nel tuo file `librechat.yaml`
2. Riavvia LibreChat per inizializzare le connessioni
3. Crea o modifica un agente
4. Apri **Add tools** nel Generatore di agenti (Agent Builder) e seleziona **MCP**
5. Seleziona il/i server MCP che desideri aggiungere; ogni server appare come una singola voce
6. Salva le tue modifiche all'agente

In questo esempio, abbiamo aggiunto il **[server MCP di Spotify](https://github.com/LibreChat-AI/spotify-mcp)** a un agente.

![Agenti - MCP](/images/agents/mcp_tools_v2.png)

#### Gestione degli MCP Tools [#managing-mcp-tools]

Una volta aggiunto un server MCP a un agente, puoi ottimizzare quali strumenti specifici rendere disponibili:

- Dopo aver aggiunto un server MCP, espandilo per vedere tutti gli strumenti disponibili
- Seleziona/deseleziona i singoli strumenti secondo necessità
- Ad esempio, il server MCP di Spotify fornisce circa 20 strumenti (ricerca, controllo della riproduzione, gestione delle playlist, ecc.)
- Questo controllo granulare ti consente di limitare gli agenti solo agli strumenti di cui hanno bisogno

I server con ambito di richiesta che utilizzano `{{LIBRECHAT_BODY_*}}` non possono enumerare gli strumenti finché un'esecuzione della chat non fornisce tali valori. Agent Builder mostra quindi una selezione di runtime-tools per l'intero server invece di interruttori per singolo strumento; deselezionare tale opzione scollega il server. Dopo OAuth, LibreChat mantiene l'autorizzazione e attende la prima esecuzione idonea per connettersi.

Se un Agent seleziona esplicitamente strumenti MCP ma nessuno di essi può essere risolto all'avvio di un'esecuzione, LibreChat interrompe l'esecuzione fornendo indicazioni sulla connessione e sull'accesso invece di proseguire silenziosamente senza di essi. Riconnetti o autentica il server, verifica l'accesso agli strumenti e riprova l'esecuzione.

![Agenti - Strumenti MCP](/images/agents/mcp_agent_tools.png)

### Strumenti differiti [#deferred-tools]

Gli strumenti differiti (deferred tools) consentono agli agenti di avere accesso a molti strumenti MCP senza caricarli tutti preventivamente nel contesto dell'LLM. Al contrario, gli strumenti differiti sono rilevabili in fase di esecuzione tramite un meccanismo di **Ricerca Strumenti** (Tool Search).

Questo è particolarmente utile quando un agente ha accesso a molti server MCP con decine di strumenti: caricarli tutti consumerebbe una gran parte della finestra di contesto e degraderebbe la qualità della risposta.

**Come funziona:**

- Gli strumenti contrassegnati come "deferred" sono esclusi dal contesto iniziale dell'LLM
- Uno strumento `ToolSearch` viene aggiunto automaticamente, consentendo all'LLM di scoprire e caricare strumenti differiti su richiesta.
- Una volta scoperto, lo strumento è disponibile per il resto della conversazione

**Configurazione degli strumenti differiti:**

1. Apri l'Agent Builder e aggiungi gli strumenti MCP
2. Fai clic sul menu a discesa su qualsiasi strumento MCP
3. Attiva "Defer Loading" — gli strumenti differiti mostrano un'icona a forma di orologio

**Nota:** La funzionalità `deferred_tools` è abilitata per impostazione predefinita. Può essere attivata o disattivata tramite la configurazione degli agenti in [`librechat.yaml`](/docs/configuration/librechat_yaml/object_structure/agents#capabilities).

### Gruppi di attività [#activity-groups]

I gruppi di attività comprimono ogni blocco contiguo di ragionamento dell'Agent e chiamate a strumenti sotto un'intestazione generata su una riga, rendendo le esecuzioni lunghe più facili da scansionare. Gli amministratori li abilitano con `activityLabel` e possono utilizzare un modello più veloce, un altro endpoint configurato, un prompt personalizzato e limiti per singola esecuzione. La generazione dell'intestazione è una chiamata al modello separata i cui token e costi vengono registrati. Vedi [Agent Activity Groups](/docs/configuration/librechat_yaml/object_structure/shared_endpoint_settings#agent-activity-groups).

Gli amministratori possono abilitare in modo indipendente `activityPhaseLabel` per raggruppare due o più attività logiche in un riepilogo principale compresso prima della risposta finale. Ciò fornisce alle esecuzioni lunghe una struttura di livello superiore, preservando al contempo ogni singola attività secondaria. I riepiloghi di fase utilizzano il proprio modello, endpoint, prompt e limite per esecuzione, con fallback all'etichetta dell'attività e alle impostazioni di esecuzione.

Non appena una sequenza contigua contiene almeno due gruppi di strumenti etichettati completati, LibreChat li raggruppa nella stessa superficie della scheda di fase anche prima che arrivi un eventuale riepilogo di fase. L'etichetta figlia completata più recente funge da intestazione provvisoria, mentre il ragionamento in tempo reale e la chiamata allo strumento ancora in corso rimangono al di fuori del raggruppamento. La cronologia caricata utilizza lo stesso raggruppamento e un riepilogo di fase generato dal server in un secondo momento sostituisce l'intestazione provvisoria senza chiudere una scheda aperta dal lettore.

Quando [Smooth Streaming](/docs/features/smooth_streaming) è abilitato, un riepilogo principale appena generato ripiega fluidamente le attività visibili nel gruppo compresso. La cronologia caricata non riproduce questa transizione e LibreChat rispetta la preferenza di riduzione del movimento del dispositivo.

Il testo di avanzamento breve rimane all'interno della sua fase genitore. Quando l'Agent inizia una risposta sostanziale, LibreChat chiude la fase prima di quel testo, in modo che il risultato visibile all'utente rimanga al di fuori del riepilogo compresso. Un'esecuzione può creare più fasi genitore quando il ragionamento successivo o gli strumenti avviano un altro blocco di attività logica. I confini delle fasi persistenti vengono rielaborati quando le parti di contenuto malformate o omesse vengono compattate, in modo che il raggruppamento rimanga allineato dopo il ricaricamento.

I file prodotti all'interno di una fase rimangono visibili in una riga multimediale sotto la scheda compressa invece di essere nascosti al suo interno. I riferimenti alle immagini in Markdown che utilizzano un nome file semplice, `/mnt/data/...` o un percorso `sandbox:` vengono risolti negli allegati del turno corrispondente. Un file viene omesso dalla riga multimediale solo quando un'immagine inline al di fuori della fase compressa viene risolta correttamente, evitando duplicati senza fare affidamento su riferimenti non funzionanti.

Le schede degli agenti generici e degli strumenti MCP distinguono tra **Preparazione** (prima del passaggio dell'SDK, che può includere l'approvazione o altre attese) e **Chiamata** (passaggio dell'SDK al risultato). Le schede completate mostrano entrambi gli intervalli; l'intervallo di chiamata non corrisponde necessariamente alla durata dell'esecuzione dell'MCP a monte o di ClickHouse. I messaggi salvati in precedenza e le schede specializzate per Code, Bash, file e memoria mantengono una durata del passaggio di esecuzione chiaramente etichettata come **Tempo totale trascorso**. I passaggi interrotti, annullati, falliti e completati mantengono stati distinti, anche dopo il ricaricamento di una conversazione.

Mentre uno strumento è in esecuzione, i riquadri di dettaglio espansi di Bash, Execute Code e File Authoring seguono i comandi in streaming, il codice o il contenuto dell'anteprima fino in fondo. Lo scorrimento verso l'alto mette in pausa questo comportamento di inseguimento, in modo che la posizione di lettura corrente venga preservata.

L'output Bash viene visualizzato come testo in stile terminale. L'output lungo viene ridotto alle ultime 15 righe, dove solitamente appaiono gli errori; utilizza **Show more** e **Show less** per espanderlo o ridurlo, e il pulsante **Copy** per copiare l'output. Un comando che non ha prodotto alcun risultato mostra **No output**. Per i comandi eseguiti in un [attached workspace](/docs/features/code_interpreter#attached-environments-and-pairing), un comando fallito viene contrassegnato con il relativo motivo (**exit code N**, **terminated by** un segnale come `SIGKILL`, o **timed out**), e lo stderr viene formattato separatamente dallo stdout. Un comando completato è etichettato come **Ran command**, e un gruppo di strumenti che contiene una singola chiamata si apre direttamente sui dettagli di tale chiamata.

### Etichette di ragionamento in tempo reale [#live-reasoning-labels]

Le etichette di ragionamento in tempo reale sostituiscono un'intestazione generica **Thinking** o **Thoughts** con un breve orientamento che si evolve man mano che i flussi di ragionamento di primo livello diventano sufficientemente lunghi. L'etichetta aggiorna l'intestazione di ragionamento esistente sul posto; non aggiunge né riordina le parti del messaggio.

L'etichetta di ragionamento live più recente e il timer di risposta brillano mentre la generazione è attiva. Il ragionamento consolidato, le risposte dei fratelli precedenti e le etichette che non si trovano più nella parte finale live rimangono statici.

Gli amministratori abilitano questa funzione con `reasoningLabel` e possono scegliere un modello, un endpoint, un prompt, le soglie di aggiornamento e il limite di chiamate per esecuzione separati. Ogni revisione è un'ulteriore chiamata al modello i cui token e costi vengono registrati. Consulta [Live Reasoning Labels](/docs/configuration/librechat_yaml/object_structure/shared_endpoint_settings#live-reasoning-labels) per i valori predefiniti, la precedenza di routing e le considerazioni sulla privacy.

### Etichette di intento degli strumenti [#tool-intent-labels]

Le etichette di intent dei tool sostituiscono gli stati generici dei tool in tempo reale con una breve descrizione scritta dal modello per quella specifica chiamata. Gli amministratori devono aggiungere la funzionalità `tool_intents` [agent capability](/docs/configuration/librechat_yaml/object_structure/agents#capabilities). I tool nativi utilizzano le etichette automaticamente; nell'Agent Builder, espandi un server MCP e attiva **Intent label** per i singoli tool o per l'intero server.

Per i Model Specs, [`describeIntent`](/docs/configuration/librechat_yaml/object_structure/model_specs#describeintent) può abilitare ogni strumento idoneo o selezionare gli ID degli strumenti risolti. I campi intent si aggiungono allo schema dello strumento inviato al modello, quindi l'abilitazione selettiva può ridurre l'overhead dei token dello schema.

Le etichette di intento non si applicano agli strumenti MCP esclusivamente programmatici, poiché le chiamate effettuate all'interno del codice sandbox non visualizzano singole schede strumento. Un'esecuzione programmatica estesa mostra invece una traccia live compatta delle sue chiamate interne.

### Programmatic Tool Calling [#programmatic-tool-calling]

Il Programmatic Tool Calling (PTC) consente agli agenti di eseguire strumenti MCP selezionati dall'interno della sandbox del [Code Interpreter](/docs/features/code_interpreter) invece di chiamare ogni strumento direttamente dal modello. Il modello riceve uno strumento di orchestrazione basato su Code Interpreter, scrive codice in sandbox che richiama le funzioni degli strumenti generati e può utilizzare cicli, condizionali, tentativi ed elaborazione dei risultati prima di restituire una risposta.

Questo è utile per flussi di lavoro con strumenti multi-step come l'interrogazione di diverse risorse, la paginazione dei risultati, il confronto degli output o la trasformazione delle risposte degli strumenti prima che l'agente le spieghi.

**Configurazione degli strumenti programmatici:**

1. Abilita sia `programmatic_tools` che `execute_code` nelle [`librechat.yaml` capabilities degli agenti](/docs/configuration/librechat_yaml/object_structure/agents#capabilities).
2. Abilita Code Interpreter sull'agente.
3. Aggiungi strumenti MCP, espandi un server MCP e attiva **Programmatic** per singoli strumenti o per l'intero server. Gli strumenti Programmatic mostrano un'icona di codice.

L'Agent Builder mantiene gli interruttori Programmatic disabilitati finché non viene selezionato Code Interpreter. La rimozione di Code Interpreter cancella immediatamente le selezioni Programmatic dell'agente. Durante la creazione, l'aggiornamento, la duplicazione e il ripristino di una versione, il server rimuove anche le opzioni del chiamante programmatico ogni volta che la funzionalità `execute_code` o lo strumento Code Interpreter non sono disponibili; ciò consente di aprire e correggere agenti meno recenti e incoerenti senza mantenere una configurazione inutilizzabile.

**Nota:** `programmatic_tools` è una funzionalità opzionale e non è inclusa nell'elenco predefinito delle funzionalità degli agenti. PTC richiede inoltre una distribuzione di Code Interpreter con il componente Tool Call Server. In fase di runtime, LibreChat interseca la proiezione corrente delle funzionalità del chiamante con il suo registro degli strumenti attendibili, pertanto i dati dell'evento possono restringere la mappa disponibile ma non possono concedere uno strumento. Solo gli strumenti programmatici attivi e registrati possono essere chiamati dalla sandbox; le chiamate non registrate vengono rifiutate.

Espandi la scheda Code Interpreter durante un'esecuzione programmatica per visualizzare una traccia in stile terminale di ogni chiamata allo strumento interno, l'anteprima dei suoi argomenti, lo stato, la durata ed eventuali errori. La traccia è attiva per la sessione corrente del browser e non viene ripristinata dopo il ricaricamento della pagina.

### Background Tool Calls [#background-tool-calls]

Le chiamate agli strumenti in background consentono a un agente di avviare uno strumento Code Interpreter, MCP, Plugin o Action idoneo a lunga esecuzione e di continuare a lavorare. La chiamata iniziale restituisce immediatamente un riferimento all'attività. Per un agente salvato, i completamenti supportati vengono forniti automaticamente in una continuazione successiva per impostazione predefinita; `check_background_task` rimane disponibile per lo stato esplicito, il controllo, la raccolta di artefatti e il ripristino.

`check_background_task` riporta `started_at` e l'attuale `elapsed_ms` mentre il lavoro locale al processo è in esecuzione. Dopo il completamento, riporta anche `settled_at` e blocca `elapsed_ms` alla durata finale. Un risultato terminale recuperato dallo storage persistente può includere `settled_at` senza un orario di inizio o una durata trascorsa quando il timestamp di invio originale locale al processo non è disponibile.

Per utilizzare questa funzionalità, un amministratore deve aggiungere la capability dell'agente `run_in_background` [opt-in](/docs/configuration/librechat_yaml/object_structure/agents#capabilities). Successivamente, configura gli strumenti idonei nell'Agent Builder:

- **Code Interpreter:** Abilita Code Interpreter sull'agente. L'esecuzione di codice e i comandi shell diventano idonei per l'esecuzione in background per impostazione predefinita; disattiva **Background execution** nelle impostazioni dello strumento per rinunciarvi.
- **MCP:** Apri un server MCP e contrassegna singoli strumenti, o l'intero server, come **Background**.
- **Strumenti plugin:** Apri uno strumento idoneo e attiva **Esecuzione in background**.
- **Actions:** Attiva **Background execution** per un'Action per abilitare ogni operazione idonea in quell'Action. Le Action OAuth non espongono questo interruttore. Un'operazione viene esclusa anche quando il suo schema definisce già un parametro `run_in_background`, evitando un conflitto con il flag di dispatch di LibreChat.

Queste impostazioni consentono l'esecuzione in background ma non la forzano. Il modello decide per ogni chiamata se eseguire uno strumento idoneo in background.

Nelle chat di LibreChat, quando il codice in background termina, il suo stdout e i file generati appaiono nella chiamata al codice originale anziché nel polling successivo. I file generati vengono inoltre conservati per i turni successivi. Le continuazioni automatiche presentano il lavoro completato in una scheda attività di riattivazione comprimibile collegata all'attività originale.

Quando il server avvia quella continuazione dopo che l'esecuzione in primo piano precedente è già terminata, la conversazione aperta si collega alla nuova generazione e aggiorna l'output dell'attività completata senza richiedere un ricaricamento.

I risvegli per il completamento automatico sono abilitati a meno che un amministratore non imposti [`endpoints.agents.backgroundTasks.completionWakeups: false`](/docs/configuration/librechat_yaml/object_structure/agents#backgroundtasks), il che ripristina il comportamento basato solo sul polling. L'host può raggruppare diversi completamenti idonei di solo contenuto in un'unica continuazione. Le attività che producono un artefatto live richiedono ancora il polling sul processo che possiede l'esecuzione.

Gli amministratori possono anche scegliere di abilitare l'annullamento con ambito proprietario con [`endpoints.agents.backgroundTasks.ordinaryToolCancellation: true`](/docs/configuration/librechat_yaml/object_structure/agents#backgroundtasks). L'attività segnala che l'annullamento è stato richiesto finché l'invocazione sottostante non viene completata e la sua capacità rimane riservata durante tale intervallo. L'annullamento è cooperativo: uno strumento che ignora il segnale di interruzione potrebbe comunque essere completato con successo. Il controllo si applica agli strumenti in background locali al processo ordinario, incluso Bash collegato, ma non ai sottoagenti distaccati di proprietà indipendente.

Solo gli strumenti idonei espongono l'impostazione. L'esecuzione ordinaria in background è locale al processo e non sopravvive alla perdita del suo processo di lavoro. Una volta che un risultato del terminale di solo contenuto viene persistito, tuttavia, la consegna automatica è durevole e può continuare su un'altra replica. Il registro locale al processo delimita le attività in esecuzione e i payload dei risultati conservati per conversazione, utente e processo; espelle il lavoro completato quando è sicuro e restituisce un risultato di capacità limitata quando l'elaborazione in sospeso impedisce un'espulsione sicura. Se un'invocazione ignora l'annullamento, LibreChat smette di rinnovare il suo lease del produttore dopo un periodo di tolleranza di un minuto post-interruzione e ritira la consegna del completamento automatico senza contrassegnare erroneamente come scaduto il lavoro esterno incerto. I Subagent scollegati utilizzano un percorso separato per attività e trascrizioni durevoli con controlli live instradati tramite Redis; vedere [Thread dei Subagent scollegati](/docs/features/subagents#detached-subagent-threads).

### Richiedi input all'utente e approvazione dello strumento [#ask-user-and-tool-approval]

Lo strumento **Ask User** consente a un agente di mettere in pausa un'esecuzione per richiedere informazioni mancanti, presentare scelte o confermare come procedere. Una singola chiamata può raggruppare fino a quattro domande correlate. LibreChat presenta una domanda alla volta con i pulsanti Indietro, Avanti e passaggi di avanzamento cliccabili; le risposte rimangono disponibili mentre ci si sposta tra i passaggi e le risposte a selezione singola avanzano automaticamente senza invio. Il pulsante Invia appare nel passaggio finale dopo che ogni domanda ha ricevuto una risposta, mentre Salta rifiuta l'intero gruppo da qualsiasi passaggio. Ogni domanda accetta una risposta a testo libero o le scelte a selezione singola o multipla dell'agente. Mentre il modello prepara la chiamata, LibreChat trasmette le domande in una scheda di avanzamento; il modulo interattivo la sostituisce quando è pronto. Dopo un invio, la stessa esecuzione riprende con la mappa completa delle risposte. Aggiungi **Ask User** dal marketplace degli Strumenti; gli amministratori possono rimuovere la funzionalità predefinita `ask_user_question` per nasconderla.

Comprimere una scheda con più domande riporta il composer alla sua normale modalità di guida o coda, mentre la scheda in pausa rimane nel thread. La scheda può ancora essere espansa, a cui si può rispondere, che può essere saltata o interrotta. Una pausa su una singola domanda continua a utilizzare la modalità di risposta del composer focalizzato.

Le risposte inviate vengono salvate con l'azione di ripresa, pertanto l'interruzione durante l'inizializzazione dell'esecuzione ripresa non comporta l'eliminazione delle risposte accettate.

Dopo che un record di domanda viene stabilizzato, esso si comprime per impostazione predefinita in una voce di strumento su una sola riga, in modo che le risposte lunghe non dominino la trascrizione. Aprilo per rivedere le domande e le interruzioni di riga preservate nelle risposte. Anche la preferenza esistente **Auto-expand tool details** controlla questa visualizzazione stabilizzata; il modulo live rimane aperto finché è ancora richiesto un input.

Ogni domanda accetta un'intestazione facoltativa fino a 80 caratteri, un testo della domanda fino a 2.000 caratteri, un contesto di supporto facoltativo fino a 4.000 caratteri e fino a 12 scelte. Le etichette delle scelte sono limitate a 280 caratteri, i valori delle scelte a 500 caratteri e ogni risposta inviata a 16.000 caratteri.

Gli amministratori possono anche richiedere una revisione prima dell'esecuzione delle chiamate agli strumenti corrispondenti. A seconda dello strumento, gli utenti possono approvare, rifiutare, modificare gli argomenti o rispondere direttamente. Le esecuzioni in pausa vengono salvate tramite checkpoint in modo che possano riprendere dopo la decisione, anche su un'altra replica quando viene utilizzato il checkpointer MongoDB predefinito. L'approvazione degli strumenti a livello di distribuzione è disabilitata per impostazione predefinita, mentre un Agent che utilizza un ambiente Code collegato riceve la [ask-by-default safety policy](/docs/features/code_interpreter#attached-environment-tool-permissions) a meno che un amministratore non la disabiliti esplicitamente. Vedi [`toolApproval` e `checkpointer`](/docs/configuration/librechat_yaml/object_structure/agents#toolapproval).

Mentre il pannello di revisione del composer è aperto per un'approvazione in sospeso, la relativa scheda della conversazione mostra la richiesta come un record anziché duplicare i pulsanti di decisione. Esamina le chiamate nel pannello sopra la casella di messaggio e seleziona **Continue**. Comprimere il pannello dal chip del composer ripristina i controlli della scheda della conversazione mantenendo le tue decisioni; riaprirlo restituisce la revisione al pannello. Le schede per altre azioni mantengono i propri controlli.

### Skills [#skills]

Le Skills consentono agli agenti di caricare istruzioni riutilizzabili dalle definizioni `SKILL.md`. Possono essere selezionate manualmente dalla chat tramite `$`, scoperte automaticamente dal modello attraverso il catalogo delle skill, oppure applicate sempre a ogni turno. L'Agent Builder può anche abilitare la creazione di runtime standalone: un agente può creare una Skill senza ricevere il catalogo esistente, o modificare le Skills selezionate quando l'utente dispone dell'autorizzazione corrispondente.

Per i dettagli su creazione, invocazione e controllo degli accessi, consulta [Skills](/docs/features/skills).

### Memoria [#memory]

Lo strumento **Memory** consente a un agente di salvare, aggiornare o eliminare memorie utente strutturate quando l'utente chiede esplicitamente di ricordare o dimenticare qualcosa. Memory deve essere configurato per la distribuzione, consentito dal ruolo e dalle impostazioni di personalizzazione dell'utente e abilitato sull'agente.

Per impostazione predefinita, un agente utilizza il pool di memoria personale condiviso dell'utente. Attiva **Keep memories separate for this agent** per assegnargli una partizione privata per utente e per agente. L'agente isolato non vedrà le memorie condivise esistenti o le memorie create da altri agenti isolati. Gli utenti possono filtrare il pannello Memory per memorie personali o specifiche dell'agente. La lettura, la creazione o l'aggiornamento di una partizione dell'agente richiedono l'accesso corrente a tale agente; l'eliminazione può comunque ripulire una partizione dopo che il relativo agente è stato rimosso. Vedi [User Memory](/docs/features/memory#agent-memory).

### Artifacts [#artifacts]

La funzionalità Artifacts consente al tuo agente di generare e visualizzare contenuti interattivi:

- Crea componenti React, codice HTML e diagrammi Mermaid
- Visualizza il contenuto in un pannello dedicato accanto alla chat, che può essere espanso a schermo intero o aperto in una finestra del browser separata
- Configura le istruzioni specifiche per gli artifact a livello di agente
- [Maggiori informazioni su Artifacts](/docs/features/artifacts)

Quando abilitato, scegli una delle tre modalità di istruzione:

- **Normal**: Aggiunge le istruzioni standard per gli artefatti per React, HTML, SVG, Markdown e Mermaid.
- **shadcn/ui**: Aggiunge le istruzioni standard più una guida per la creazione di interfacce con la libreria di componenti shadcn/ui.
- **Custom**: Mantiene il rendering degli artefatti abilitato ma non inietta istruzioni predefinite per gli artefatti, lasciando il controllo completo alle istruzioni dell'agente.

La configurazione degli artifacts a livello di agente è l'approccio preferito, poiché consente un controllo più granulare rispetto alla configurazione legacy a livello di intera applicazione.

Se selezioni **Custom**, includi almeno il formato base dell'artifact nelle tue istruzioni.

Ecco un semplice esempio delle istruzioni minime necessarie:

````md
When creating content that should be displayed as an artifact, use the following format:

:::artifact{identifier="unique-identifier" type="mime-type" title="Artifact Title"}

```
Your artifact content here
```

:::

For the type attribute, use one of:

- "text/html" for HTML content
- "application/vnd.mermaid" for Mermaid diagrams
- "application/vnd.react" for React components
- "image/svg+xml" for SVG images
````

### Handoffs [#handoffs]

Gli Handoff consentono a un agente principale di trasferire una conversazione a un agente specializzato con il contesto pertinente. Nelle **Advanced settings**, apri la sezione di orchestrazione e aggiungi fino a 10 agenti di handoff. Ogni handoff configurato crea uno strumento di trasferimento che il modello può scegliere dinamicamente quando è necessaria la competenza dello specialista.

Per ogni passaggio di consegne (handoff), puoi aggiungere una descrizione che aiuti il modello a scegliere lo specialista giusto. Puoi anche fornire istruzioni di passthrough che descrivano quale contenuto l'agente principale debba generare per lo specialista e, facoltativamente, rinominare il parametro del contenuto dal suo valore predefinito, `instructions`. Gli handoff sono sempre disponibili nell'Agent Builder; a differenza di Agent Chain e Subagents, non richiedono che sia abilitata una funzionalità di endpoint. Le chiamate agli strumenti da parte degli agenti di handoff raggiungibili rimangono strutturate nei turni successivi, in modo che i provider ricevano una cronologia valida delle chiamate agli strumenti invece di testo appiattito.

### Subagenti [#subagents]

I Subagent consentono a un agente di delegare un compito specifico a un'esecuzione secondaria isolata o a un team di Agent salvato. Ogni elemento secondario ottiene un contesto e un'esecuzione di strumenti isolati, per poi restituire un risultato compatto al genitore, invece di riempire il contesto del genitore con ogni passaggio intermedio. Il lavoro secondario distaccato viene inoltre conservato come thread navigabile di sola lettura.

I Subagent sono diversi dalla Agent Chain: le chain eseguono il coordinamento di più agenti come partecipanti a un grafo, mentre i subagent vengono generati da un agente come chiamata di strumento per una delega con ambito limitato. LibreChat preserva lo storico strutturato delle chiamate di strumento necessario ai figli raggiungibili e ai membri del team salvati durante i turni successivi, mantenendo al contempo gli strumenti non disponibili fuori dall'esecuzione attiva. Per la configurazione e i limiti, vedere [Subagents](/docs/features/subagents).

### Impostazioni avanzate [#advanced-settings]

Impostazioni avanzate per il tuo agente (che si trovano nella vista Avanzate del modulo Agente) al di fuori delle "funzionalità" (capabilities).

#### Max Agent Steps [#max-agent-steps]

Questa impostazione ti consente di limitare il numero di passaggi che un agente può compiere in un "run", che si riferisce al ciclo dell'agente prima che venga fornita una risposta finale.

Se lasciato non configurato, il valore predefinito è 25 passaggi, ma puoi regolarlo in base alle tue esigenze. Per gli amministratori, è possibile impostare un valore predefinito globale così come un massimo globale nel file [`librechat.yaml`](/docs/configuration/librechat_yaml/object_structure/agents#recursionlimit).

Quando un turno utilizza il suo budget di passaggi completo, LibreChat conserva la risposta parziale e le chiamate agli strumenti invece di sostituirle con un errore. Il messaggio offre **Keep going**, che avvia un nuovo turno con un budget di strumenti rinnovato, e **Answer now**, che chiede all'agente di rispondere basandosi sul lavoro già completato senza ulteriori strumenti. Ignorare l'avviso influisce solo sulla visualizzazione corrente del browser.

Gli amministratori possono anche limitare gli argomenti delle chiamate a strumenti in streaming e gli eventi delta del modello con i [Agent stream circuit breakers](/docs/configuration/librechat_yaml/object_structure/agents#stream-circuit-breakers).

Uno "step" si riferisce a una richiesta API dell'IA o a un ciclo di utilizzo di strumenti (1 o più strumenti, a seconda di quante chiamate a strumenti l'LLM fornisce da una singola richiesta).

Una singola risposta senza strumenti equivale a 1 passaggio. Un singolo ciclo di utilizzo di uno strumento equivale solitamente a 3 passaggi:

1. Richiesta API -> 2. Utilizzo dello strumento (1 o molti strumenti) -> 3. Richiesta API di follow-up

## Gestione dei file [#file-management]

Gli Agents supportano diversi modi di lavorare con i file:

### Nell'interfaccia di chat [#in-chat-interface]

Quando chatti con un agente, hai quattro opzioni di caricamento:

1. **Carica immagini**
   - Carica immagini per il supporto nativo dei modelli vision
   - Invia le immagini direttamente al provider del modello

2. **Carica come testo** (richiede la funzionalità `context`)
   - Estrae e include il contenuto completo del documento nella conversazione
   - Utilizza l'analisi del testo per impostazione predefinita; migliorata tramite OCR se configurata
   - Il contenuto esiste solo nella conversazione corrente
   - Vedi [Upload as Text](/docs/features/upload_as_text)

3. **Caricamento per la ricerca di file** (richiede la funzionalità `file_search`, attivata su ON)
   - Utilizza la ricerca semantica (RAG) con vector store
   - Restituisce chunk pertinenti tramite l'uso di tool
   - Ottimale per documenti di grandi dimensioni/file multipli
   - Sub-ottimale per dati strutturati (CSV, Excel, JSON, ecc.)

4. **Caricamento per Code Interpreter** (richiede la funzionalità `execute_code`, attivata su ON)
   - Aggiunge file all'ambiente dell'interprete di codice
   - Ottimale per dati strutturati (CSV, Excel, JSON, ecc.)
   - Maggiori informazioni su [Code Interpreter](/docs/features/code_interpreter)

### In Agent Builder [#in-agent-builder]

Quando configuri un agente, puoi allegare file in diverse categorie:

1. **Caricamento immagini**: Per i contenuti visivi a cui l'agente può fare riferimento
2. **Caricamento per ricerca file**: Documenti per funzionalità RAG
3. **Code Interpreter Upload**: File per l'elaborazione del codice
4. **Contesto del file**: Documenti con testo estratto per integrare le istruzioni dell'agente

**File Context** utilizza la funzionalità `context` e funziona esattamente come ["Upload as Text"](/docs/features/upload_as_text): utilizza l'analisi del testo per impostazione predefinita ed è migliorata dall'OCR quando configurata. Il testo viene estratto al momento del caricamento e archiviato nelle istruzioni dell'agente. Questo è l'ideale per fornire agli agenti una conoscenza persistente da documenti, PDF, file di codice o immagini contenenti testo.

**Priorità di elaborazione:** OCR > STT > analisi del testo (uguale a Carica come testo)

**Nota:** Il testo estratto è incluso come parte delle istruzioni di sistema dell'agente.

## Condivisione e autorizzazioni [#sharing-and-permissions]

Gli agenti utilizzano il sistema di [controllo degli accessi](/docs/features/access_control) granulare di LibreChat. Ogni agente ha la propria Access Control List (ACL) e può essere condiviso con **utenti**, **gruppi**, **ruoli** specifici o **pubblicamente**, ciascuno con un livello di autorizzazione scelto.

I servizi affidabili possono anche gestire Agent, file allegati e Skills tramite la [Agent Management API](/docs/features/agents_api#agent-management-api) in versione beta. Gli amministratori associano ogni client macchina OIDC a un utente e a un tenant LibreChat esistenti; ogni richiesta eredita le funzionalità di ruolo e gli ACL delle risorse correnti di quell'utente, invece di ricevere un accesso amministrativo separato.

### Ruoli di accesso [#access-roles]

Quando si condivide un agente, al destinatario viene assegnato uno dei tre ruoli seguenti:

| Ruolo | Cosa può fare il beneficiario |
| ---------- | ----------------------------------------------------------------------------------------------------- |
| **Viewer** | Utilizzare l'agente nelle conversazioni; non può aprire il builder né vedere istruzioni, strumenti o file allegati |
| **Editor** | Visualizzare + modificare le istruzioni, il modello, gli strumenti e i file dell'agente |
| **Owner**  | Controllo completo: visualizzare, modificare, eliminare e ricondividere l'agente |

L'autore originale e gli amministratori mantengono sempre il controllo completo indipendentemente dall'ACL.

### Condivisione di un Agent [#sharing-an-agent]

1. Apri l'agente nel Builder di agenti
2. Fai clic sul pulsante **Share** nel piè di pagina (visibile quando sei l'autore, un amministratore o ti è stata concessa l'autorizzazione `SHARE` su quello specifico agent)
3. Cerca utenti, gruppi o ruoli nel selettore di persone e assegna a ciascuno un ruolo
4. Facoltativamente, attiva **Public** per rendere l'agente visibile a tutti sull'istanza (richiede l'autorizzazione alla funzionalità `SHARE_PUBLIC`)

Le schede degli agenti e le viste di destinazione mostrano il contatto di supporto configurato. Quando non ne viene impostato nessuno, LibreChat può ripiegare sul nome visualizzato del primo proprietario risolvibile, ma non espone l'indirizzo email del proprietario a meno che non sia stato configurato esplicitamente come contatto di supporto.

Le superfici di conversazione mantengono l'Agent come identità visibile e non ripiegano sul suo modello di supporto o sull'etichetta Model Specs.

Per tutti i dettagli su principal, bit di autorizzazione e su come gli ACL si compongono con le autorizzazioni delle funzionalità basate sui ruoli, consulta [Access Control](/docs/features/access_control).

### Agent Marketplace [#agent-marketplace]

L'**Agent Marketplace** consente agli utenti di esplorare gli agenti a loro disposizione. Aprilo da **Agent Marketplace** nella barra laterale; la voce appare solo per gli utenti il cui ruolo è autorizzato a utilizzare il Marketplace.

- **Sfoglia e cerca**: Gli agenti appaiono in una griglia. Usa il campo di ricerca per trovare gli agenti per nome o descrizione e le pillole delle categorie (come **Top Picks**, **All** o una categoria specifica) per restringere l'elenco.
- **Ordina**: Usa **Ordina per** per disporre gli agenti per **I più recenti** (impostazione predefinita), **I più vecchi**, **Popolari** (più aggiunti ai preferiti), o **Per nome del creatore**.
- **I miei agenti**: Attiva **I miei agenti** per mostrare solo gli agenti che hai creato. Attivandolo da **Scelte migliori** si passa a **Tutti**.
- **Viste condivisibili**: La ricerca, l'ordinamento e il filtro **My agents** vengono mantenuti nell'URL della pagina (`?q=`, `?sort=`, `?mine=1`), in modo che una vista filtrata possa essere aggiunta ai segnalibri o condivisa.

Seleziona una scheda agente per aprire la sua finestra di dialogo di dettaglio, che mostra la descrizione completa e i contatti dell'agente, insieme a queste azioni:

- **Pin** (Fissa) o **Unpin** (Rimuovi): Aggiungi l'agente ai tuoi agenti fissati o rimuovilo da essi.
- **Copia link**: Copia un link che avvia una nuova chat con l'agente.
- **Start Chat**: Avvia una nuova conversazione con l'agente.
- **Prova un avvio di conversazione**: Quando l'agente dispone di [conversation starters](#conversation-starters), selezionane uno per aprire una nuova chat con quel prompt già inserito nell'input del messaggio. Non viene inviato automaticamente, quindi puoi modificarlo prima.

Gli amministratori possono controllare l'accesso con l'impostazione [`interface.marketplace`](/docs/configuration/librechat_yaml/object_structure/interface#marketplace) e i permessi dei ruoli descritti in [Controllo Accessi](/docs/features/access_control).

### Controlli dell'amministratore [#administrator-controls]

Gli amministratori hanno accesso alle impostazioni di autorizzazione globali all'interno dell'interfaccia utente del generatore di agenti:

- Abilita/disabilita la condivisione degli agenti per tutti gli utenti
- Controlla le autorizzazioni di utilizzo degli agenti
- Gestisci i diritti di creazione degli agenti
- Configura le impostazioni a livello di piattaforma

In un deployment single-tenant non limitato (unscoped), il primo account creato per l'istanza è un amministratore. I deployment tenant-scoped non promuovono automaticamente il primo utente registrato; è necessario fornire gli amministratori del tenant tramite un flusso amministrativo attendibile. Se hai bisogno di aggiungere un amministratore manualmente, puoi [accedere a MongoDB](/docs/configuration/mongodb/mongodb_auth) e aggiornare il profilo dell'utente:

```
db.users.updateOne(
  { email: 'USER_EMAIL_ADDRESS' },
  { $set: { role: 'ADMIN' } }
)
```

L'uso degli agenti per tutti gli utenti può anche essere disabilitato tramite configurazione, [maggiori informazioni](/docs/configuration/librechat_yaml/object_structure/interface).

Le autorizzazioni a livello di funzionalità (chi può _utilizzare_, _creare_, _condividere_ o _condividere pubblicamente_ gli agenti) sono gestite dal [**Pannello di amministrazione di LibreChat**](/docs/features/admin_panel) per ogni ruolo, inclusi eventuali ruoli personalizzati. Il blocco [`interface.agents`](/docs/configuration/librechat_yaml/object_structure/interface#agents) in `librechat.yaml` può ancora impostare i valori predefiniti per il ruolo `USER` integrato all'avvio, ma il pannello di amministrazione è il metodo consigliato per modificarli in futuro.

### Condivisione a livello utente [#user-level-sharing]

I singoli utenti possono:

- Condividere i propri agenti con utenti, gruppi o ruoli specifici (se `SHARE` è abilitato per il loro ruolo)
- Rendi gli agenti visibili a tutti sull'istanza (se `SHARE_PUBLIC` è abilitato)
- Assegna a ogni destinatario un livello di accesso diverso (Viewer / Editor / Owner)
- Condividi nuovamente o revoca l'accesso in qualsiasi momento dalla finestra di dialogo di condivisione

## Steering e messaggi in coda [#steering-and-queued-messages]

Mentre un Agent sta rispondendo, puoi inviare un altro messaggio dal [composer](/docs/features/composer) in uno dei due modi seguenti:

- **Steer** inserisce il messaggio nell'esecuzione corrente al passaggio successivo dello strumento o dell'agente, in modo che l'agente possa regolare il proprio lavoro prima di terminare.
- **Queue** mantiene il messaggio e lo invia come un normale turno di follow-up dopo il completamento della risposta corrente.

Per le conversazioni con Agent salvate su un server corrente, i normali follow-up in coda vengono archiviati in MongoDB. LibreChat preserva il loro ordine FIFO e mantiene il testo, gli allegati, gli estratti citati e le Skills selezionate manualmente anche in caso di disconnessione dal browser, riavvio dell'app e passaggi tra repliche. L'elaborazione attende che la risposta precedente si stabilizzi prima di ammettere il turno successivo. Questa persistenza è automatica e non richiede alcun toggle in YAML o nelle variabili d'ambiente; i server più vecchi e le brevi finestre di avvio senza un'epoca di generazione attiva mantengono la coda di compatibilità lato client.

L'ammissione al server è serializzata all'interno di ogni corsia della coda di conversazione. Se l'evidenza del predecessore o la proprietà di versioni miste è ambigua, LibreChat mostra **Awaiting reconciliation** e blocca o interrompe il turno in coda interessato invece di tentare di indovinare e avviarlo fuori ordine.

**Steer sooner** chiede all'agente di prendere il messaggio nel punto sicuro successivo invece di attendere il passaggio dello strumento successivo. Se non è ancora sicuro mantenere alcun testo di risposta o attività dello strumento, LibreChat attende un breve periodo di tolleranza, scarta il tentativo silenzioso o basato solo sul ragionamento, inserisce il messaggio e riavvia il modello con tale istruzione. Una volta che il testo della risposta può essere mantenuto, LibreChat si ferma a un limite sicuro per il provider, preserva la risposta parziale, inserisce il messaggio e riprende la stessa risposta dell'assistente. Una chiamata a uno strumento in esecuzione non viene scartata o interrotta dallo steering; il messaggio viene applicato quando tale lavoro raggiunge un limite sicuro.

Usa **Stop** per terminare il ragionamento attivo e richiedere l'annullamento di una chiamata a uno strumento in primo piano. Stop inoltra l'annullamento per segnalare agli strumenti in primo piano compatibili; il lavoro in background distaccato mantiene il suo ciclo di vita indipendente. Usa il controllo dedicato nel composer, sceglilo dal menu del pulsante di invio o premi `Command/Ctrl + Shift + .`. L'azione ripiega sul normale steering quando la distribuzione non può interrompere il flusso attivo del provider.

In **Impostazioni → Chat**, **Durante la generazione, Invio** sceglie l'azione predefinita. Il menu del pulsante di invio può sovrascrivere tale scelta per un singolo messaggio, e **Dirigi prima con Invio** fa sì che Invio richieda quel punto di sicurezza precedente quando la direzione è l'impostazione predefinita.

I file e gli [estratti citati](/docs/features/message_actions#quote-excerpts) viaggiano insieme ai messaggi di steer, queue e interrupt. Le Skills selezionate manualmente rimangono in attesa per il turno completo successivo invece di essere allegate a uno steer durante l'esecuzione.

I "steer" in sospeso appaiono alla fine della risposta in streaming, dove rimarranno finché il server non li inserirà nell'esecuzione. La loro ricezione progredisce da **Sending** (Invio in corso) a **Delivered** (Consegnato), poi **Steer sooner requested** (Richiesta di steer anticipato) quando è stato richiesto un punto di sicurezza precedente, e infine **Applied** (Applicato) con un doppio segno di spunta nell'angolo in basso a destra del messaggio inline. Le ricevute confermate come applicate rimangono visibili dopo il ricaricamento e nelle viste di condivisione o ricerca; una consegna incerta o fallita non mostra mai un segno di spunta di conferma. Una volta riconosciuto, il menu del messaggio può recuperare lo steer per la modifica, convertirlo in un follow-up in coda, oppure annullarlo e ripristinare il suo testo e gli allegati nel compositore. LibreChat evita di sovrascrivere una bozza più recente; se il compositore non è più disponibile, conserva il messaggio recuperato nella coda. Uno steer fallito rimane disponibile per essere riprovato, modificato, messo in coda o rimosso.

I follow-up in coda appaiono in un elenco sopra il composer. Ognuno può essere modificato (**Edit message**), rimosso (**Remove message**), inviato immediatamente con **Send now**, o riordinato trascinando la sua maniglia o premendo i tasti freccia su di esso. I follow-up in coda possono anche essere convertiti in uno steer mentre l'esecuzione è ancora attiva o essere accelerati con **Steer sooner**. Gli steer in corso offrono la stessa accelerazione quando sono ancora in attesa di un limite di tool. La rimozione di un messaggio in coda supportato dal server annulla prima la sua origine persistente, quindi lo ripristina in un composer vuoto quando possibile. Se la risposta precedente viene interrotta o fallisce, LibreChat contrassegna il turno in coda interessato come fallito per la revisione invece di inviarlo silenziosamente.

Una conversazione può avere fino a 100 turni in coda attivi. Ogni turno in coda accetta fino a 16.000 caratteri e 10 file. Separatamente, un'esecuzione attiva accetta fino a 10 steer in sospeso; ogni steer può includere fino a 10 file ed è limitato da [`STEER_MAX_LENGTH`](/docs/configuration/dotenv#agent-conversation-controls). **Steer sooner** continua a utilizzare il percorso di steering live invece di spostare un turno in coda all'inizio della corsia FIFO persistente.

Le distribuzioni multi-replica basate su Redis negoziano automaticamente il protocollo di generazione v2. Segui la [guida alla compatibilità del protocollo di generazione](/docs/configuration/redis#generation-protocol-compatibility) durante l'aggiornamento da una versione precedente alla `v0.8.8-rc1`.

### Note [#notes]

- Le Instructions, i model parameters, gli attached files e i tools vengono mostrati all'utente solo se dispone delle autorizzazioni di modifica.
  - Un agent può divulgare qualsiasi dato allegato, che si tratti di istruzioni o file, attraverso la conversazione; pertanto, assicurati che le tue istruzioni siano robuste contro questo rischio prima di concedere l'accesso come Editor/Owner o di rendere pubblico l'agent.

- Gli Agents sono privati per gli autori a meno che non vengano condivisi

## Consegna degli eventi dell'agente [#agent-event-delivery]

LibreChat include un livello di distribuzione source-neutral per gli eventi asincroni degli Agent. Gli adattatori di proprietà della distribuzione possono normalizzare un webhook verificato, un messaggio in coda, un evento MCP, un evento di canale o un evento interno del prodotto in una nuova esecuzione dell'Agent (`fire`), un nuovo turno su un Agent salvato e un ramo esistenti (`continue`), o una mutazione di un'esecuzione attiva (`steer`). Gli adattatori rimangono responsabili dell'autenticazione della loro origine nativa, della sanificazione dei payload e della selezione di target affidabili prima dell'accodamento.

Gli [endpoint degli eventi dell'API Agents](/docs/features/agents_api#agent-events) in beta espongono l'accesso autenticato `fire`, `continue` e `steer` alle chiavi API dei Remote Agents. I sistemi esterni possono associare un attore sorgente a un Agent figlio diretto e continuare tale attore attraverso gli eventi senza un ulteriore interruttore di funzionalità. LibreChat deriva l'identità dell'utente, del tenant e della sorgente dalla chiave API, applica l'accesso all'Agent e i filtri sui contenuti, e richiede una chiave di idempotenza. Questo non è un ricevitore webhook generico non autenticato; gli adattatori specifici del provider devono comunque verificare le firme dei webhook nativi prima di richiamarlo.

La funzionalità sperimentale [Scheduled Chats](/docs/features/scheduled_chats) è il primo producer integrato di LibreChat per questo livello. Crea consegne `fire` ricorrenti per gli Agent salvati ed è disabilitata finché un amministratore non vi aderisce. I Subagent scollegati utilizzano automaticamente la consegna idempotente `continue` per riattivare un Agent genitore salvato dopo che un figlio ha terminato; i figli annullati e gli Agent genitore effimeri sono esclusi.

MongoDB archivia buste con versione limitata, chiavi di idempotenza, corsie di ordinamento, lease, cronologia dei tentativi, ricevute durevoli e messaggi non recapitabili (dead letters). I worker utilizzano una consegna "at-least-once" (almeno una volta) con richieste protette (fenced claims) e backoff esponenziale limitato; le ricevute di successo scadono dopo 90 giorni, mentre i messaggi non recapitabili richiedono un riaccodamento esplicito e autorizzato. Le consegne "Fire" creano una nuova conversazione. Le consegne "Continue" creano un nuovo turno sull'esatto ramo della conversazione e rimandano l'esecuzione mentre quel ramo è in esecuzione, in pausa o in fase di finalizzazione. Gli attori vincolati (bound actors) dispongono anche di una casella di posta automatica: un attore attende l'esito della gestione del suo turno corrente prima di inviare l'evento successivo, mentre attori diversi possono essere eseguiti in parallelo. Le consegne "Steer" devono identificare la conversazione e la generazione esistenti e utilizzare un'ammissione rigorosa, in modo che i tentativi ambigui non possano iniettare due volte la stessa istruzione.

Per le continuazioni vincolate, il successo del trasporto avvia un ciclo di vita di gestione durevole separato. Una consegna progredisce da `started` a `applied`, `completed_no_action`, `failed` o `cancelled`. Le origini possono richiedere uno strumento specifico e un sottoinsieme facoltativo di argomenti con `expectedAction`; LibreChat riporta `applied` solo in base all'evidenza dello strumento corrispondente osservata dall'host, mai dalla prosa scritta dal modello. Gli eventi osservativi compatibili possono condividere un batch `coalesce.key` limitato, mantenendo un record di idempotenza e una ricevuta per ogni evento di origine. La continuazione del checkpoint viene utilizzata quando compatibile, altrimenti ricorre allo storico dei messaggi durevole.

I Bound Event Actors possono mettersi in pausa per l'Ask User o per l'approvazione di uno strumento e riprendere l'esatta invocazione dell'attore firmato tramite la normale interfaccia human-in-the-loop di LibreChat. La casella di posta dell'attore rimane bloccata finché tale pausa non viene ripresa o risolta, impedendo a un evento successivo di sovrapporsi alla decisione. Questi attori richiedono il checkpointer durevole di MongoDB. LibreChat seleziona automaticamente la continuazione del checkpoint o la ricostruzione della cronologia durevole dallo stato dell'attore e dalla capacità di richiesta; il lavoro esistente del protocol-v1 rimane sul percorso della cronologia finché non viene esaurito.

Le Detached Actions avviate da Event Actors vengono abilitate automaticamente quando lo store di generazione integrato ne pubblicizza il supporto. L'actor rimane sospeso finché l'evidenza terminale non riprende la sua invocazione originale, pertanto un avvio in background da solo non soddisfa `expectedAction`. Lo store in-memory mantiene questo ciclo di vita coerente finché il suo processo rimane attivo. Redis aggiunge il ripristino duraturo dopo il riavvio e l'handoff delle repliche. Il lavoro di completamento di proprietà della Capability è isolato dai worker più vecchi durante uno svuotamento a versione mista; gli operatori non selezionano questo comportamento tramite un feature flag.

L'host di esecuzione chiama normalmente il listener associato al processo corrente. Configura [`endpoints.agents.eventDriven.selfUrl`](/docs/configuration/librechat_yaml/object_structure/agents#eventdriven) solo quando questo percorso di ammissione interno attendibile deve attraversare un'altra origine HTTP, come un front door TLS.

## Migrazione richiesta (v0.8.0-rc3+) [#migration-required-v080-rc3]

<Callout type="warning" title="Importante: Migrazione delle autorizzazioni degli agenti richiesta">
  A partire dalla versione v0.8.0-rc3, LibreChat utilizza un nuovo sistema di autorizzazioni basato su Access Control List (ACL) per gli agenti. Se stai effettuando l'aggiornamento da una versione precedente, devi eseguire la migrazione delle autorizzazioni degli agenti affinché quelli esistenti rimangano accessibili.
</Callout>

### Cosa fa la migrazione [#what-the-migration-does]

La migrazione delle autorizzazioni degli agenti trasforma i tuoi agenti da un semplice modello di proprietà a un sofisticato sistema basato su ACL con molteplici livelli di autorizzazione:

- **OWNER**: Controllo completo sull'agente
- **EDITOR**: Può visualizzare e modificare l'agente
- **VIEWER**: Accesso in sola lettura all'agente

Senza eseguire questa migrazione, gli agenti esistenti non saranno accessibili tramite i nuovi endpoint API che supportano i permessi.

### Esecuzione della migrazione [#running-the-migration]

Scegli il comando appropriato in base al tuo metodo di distribuzione:

#### 1. Per il `docker-compose.yml` predefinito (se utilizzi `docker compose up` per avviare l'app): [#1-for-the-default-docker-composeyml-if-you-use-docker-compose-up-to-start-the-app]

**Anteprima modifiche (dry run):**

```bash
docker compose exec api npm run migrate:agent-permissions:dry-run
```

**Esegui migrazione:**

```bash
docker compose exec api npm run migrate:agent-permissions
```

**Dimensione batch personalizzata (per dataset di grandi dimensioni):**

```bash
docker compose exec api npm run migrate:agent-permissions:batch
```

#### 2. Per il `deploy-compose.yml` [#2-for-the-deploy-composeyml]

Se hai seguito la [Ubuntu Docker Guide](/docs/remote/docker_linux):

**Anteprima modifiche (dry run):**

### Cosa succede durante la migrazione [#what-happens-during-migration]

- **Agenti Privati**: Rimangono accessibili solo ai loro creatori (ricevono l'autorizzazione OWNER)
- **Agenti Condivisi**: Se un agente è stato precedentemente condiviso, riceverà le voci ACL appropriate come Agente Pubblico (condiviso con tutti gli utenti)
- **Rilevamento di sistema**: LibreChat rileva automaticamente gli agenti non migrati all'avvio e visualizza un avviso

Puoi regolare le autorizzazioni dell'agente risultante tramite l'interfaccia utente dell'Agent Builder.

<Callout type="info" title="Nota">
  Lo stesso processo di migrazione si applica ai prompt. Se hai anche dei prompt esistenti, esegui la migrazione delle autorizzazioni dei prompt utilizzando gli stessi comandi, ma sostituisci `agent` con `prompt` nei nomi dei comandi.
</Callout>

## Cosa succede ora? [#whats-next]

Gli Agent di LibreChat inaugurano una nuova era per l'app, in cui le pipeline future potranno essere ottimizzate tramite Agent per attività e flussi di lavoro specifici all'interno della tua esperienza in LibreChat.

I futuri aggiornamenti includeranno:

- Miglioramenti generali all'attuale esperienza con gli Agent
- Orchestrazione multi-agente per flussi di lavoro complessi
- Capacità di personalizzare gli agenti per varie funzioni: titolazione (assegnazione del nome ai thread di chat), gestione della memoria (contesto/cronologia dell'utente) e miglioramento dei prompt (assistenza/previsioni sull'input)
- Più strumenti, parametri degli strumenti configurabili, creazione dinamica di strumenti.

Inoltre, l'aggiornamento introduce un nuovo paradigma per LibreChat, poiché la sua architettura sottostante fornisce un aggiornamento molto necessario per l'app, ottimizzando sia l'esperienza utente che le prestazioni complessive dell'app.

Per evidenziare un'ottimizzazione degna di nota, una generazione AI di circa 1000 token trasferirà circa 1 MB di dati utilizzando gli endpoint tradizionali (al momento della stesura, qualsiasi opzione di endpoint oltre ad Agents e AWS Bedrock).

Utilizzando un agente, la stessa generazione trasferirà circa 52 kb di dati, una riduzione del 95% nel trasferimento dati, il che rappresenta un carico decisamente inferiore sia per il server che per il dispositivo dell'utente.
