<Callout type="warning" title="Funkcja beta">
API Agents jest obecnie w fazie beta. Punkty końcowe (endpoints), formaty żądań/odpowiedzi oraz zachowanie mogą ulec zmianie w miarę naszych prac nad stabilnym wydaniem.
</Callout>

LibreChat udostępnia agentów zewnętrznym aplikacjom, skryptom i usługom za pośrednictwem interfejsów API wnioskowania (inference) oraz dostarczania zdarzeń (event-delivery).

## Przegląd [#overview]

API Agents zapewnia dwa interfejsy wnioskowania, uwierzytelnione dostarczanie zdarzeń oraz trasy zarządzania w wersji beta:

- **Zgodne z OpenAI Chat Completions** — `POST /api/agents/v1/chat/completions`
- **API otwartych odpowiedzi** — `POST /api/agents/v1/responses`
- **Zdarzenia agenta** — `POST /api/agents/v1/events`
- **Zarządzanie agentami** — `/api/agents/v1/agents`
- **Zarządzanie umiejętnościami** — `/api/agents/v1/skills`

Interfejsy wnioskowania obsługują uwierzytelnianie za pomocą API-key, opcjonalne uwierzytelnianie OIDC oraz odpowiedzi strumieniowe. Zdarzenia agentów (Agent Events) wykorzystują uwierzytelnianie za pomocą API-key dla Remote Agents, dzięki czemu LibreChat może powiązać każde dostarczenie ze stabilną tożsamością źródłową. Trasy zarządzania (Management routes) korzystają natomiast z listy dozwolonych wdrożeń (deployment allowlist), która wiąże klienta maszynowego OIDC z jednym istniejącym użytkownikiem i dzierżawcą (tenant) LibreChat.

LibreChat przyjmuje [Open Responses](https://www.openresponses.org/) jako swój główny framework API do obsługi agentów. Chociaż endpoint Chat Completions zapewnia wsteczną kompatybilność z istniejącymi narzędziami zgodnymi z OpenAI, endpoint Open Responses wyznacza przyszły kierunek rozwoju.

## Włączanie Agents API [#enabling-the-agents-api]

API Agents jest zabezpieczone za pomocą konfiguracji interfejsu `remoteAgents`. Wszystkie uprawnienia domyślnie mają wartość `false`.

```yaml filename="librechat.yaml"
interface:
  remoteAgents:
    use: true
    create: true
```

Zobacz [Interface Configuration — remoteAgents](/docs/configuration/librechat_yaml/object_structure/interface#remoteagents), aby zapoznać się ze wszystkimi dostępnymi opcjami.

**Uwaga:** Użytkownicy z uprawnieniami administratora mają domyślnie włączone wszystkie zdalne uprawnienia agenta.

### Specyfikacja OpenAPI i interaktywna dokumentacja [#openapi-specification-and-interactive-docs]

LibreChat może udostępniać publiczną specyfikację Agents API pod adresem `/api/openapi.json` oraz interaktywną dokumentację Swagger UI pod adresem `/api/docs`. Obie ścieżki są domyślnie wyłączone. Włącz je za pomocą ustawienia najwyższego poziomu `openapi`:

```yaml filename="librechat.yaml"
openapi:
  enabled: true
```

Specyfikacja obejmuje publiczne trasy wnioskowania (inference), zdarzeń (event), zarządzania Agentami oraz zarządzania Umiejętnościami (Skill), opisane na tej stronie. Pozostaw te trasy wyłączone, chyba że Twoje wdrożenie ma na celu udostępnienie dokumentacji API.

## Zarządzanie kluczami API [#api-key-management]

Gdy `remoteAgents.use` oraz `remoteAgents.create` są włączone, użytkownicy mogą generować klucze API z poziomu interfejsu LibreChat. Klucze te uwierzytelniają żądania kierowane do Agents API.

## Uwierzytelnianie [#authentication]

API Agents obsługuje dwie metody uwierzytelniania, których można używać niezależnie lub łącznie.

### Klucz API [#api-key]

Uwierzytelnianie za pomocą klucza API jest domyślnie włączone. Wygeneruj klucze API z poziomu interfejsu użytkownika LibreChat, gdy `remoteAgents.use` oraz `remoteAgents.create` zostaną włączone.

```bash
Authorization: Bearer <YOUR_API_KEY>
```

### Token OIDC Bearer [#oidc-bearer-token]

W scenariuszach typu machine-to-machine, w których Twoja infrastruktura posiada już dostawcę OIDC, możesz uwierzytelniać się bezpośrednio za pomocą tokenów OIDC Bearer bez użycia klucza API LibreChat.

Skonfiguruj uwierzytelnianie OIDC w `librechat.yaml`:

```yaml filename="librechat.yaml"
endpoints:
  agents:
    remoteApi:
      auth:
        apiKey:
          enabled: false
        oidc:
          enabled: true
          issuer: https://auth.example.com/realms/myrealm
          # jwksUri is optional and auto-discovered from issuer if omitted
          audience: my-client-id
```

Następnie wywołaj API za pomocą swojego tokena dostępu OIDC:

```bash
curl -X POST https://your-librechat-instance/api/agents/v1/responses \
  -H "Authorization: Bearer YOUR_OIDC_ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"model": "agent_abc123", "input": "Hello!"}'
```

<Callout type="info">
  Token OIDC musi należeć do użytkownika, który już istnieje w LibreChat. Dopasowanie wykorzystuje najpierw pole `sub`, a następnie, w razie braku dopasowania, `email`, `preferred_username` lub `upn`.
</Callout>

Zobacz [Agents Endpoint - remoteApi](/docs/configuration/librechat_yaml/object_structure/agents#remoteapi), aby zapoznać się ze wszystkimi opcjami konfiguracji.

<Callout type="warning" title="Zdarzenia agenta wymagają klucza API">
  Uwierzytelnianie wyłącznie przez OIDC nie jest obsługiwane dla endpointów Agent Events. Użyj klucza API Remote Agents podczas tworzenia powiązań (bindings), dodawania zdarzeń do kolejki oraz sprawdzania statusu dostarczenia.
</Callout>

## Zarządzanie Agentami przez API [#agent-management-api]

Beta API zarządzania Agentami pozwala usłudze zarządzać Agentami i przypisanymi do nich zasobami bez sesji przeglądarki. Jest ona uwierzytelniana niezależnie od wnioskowania (inference) i zdarzeń Agenta (Agent Events): akceptowane są wyłącznie tokeny maszynowe OIDC skonfigurowane w [`endpoints.agents.managementApi`](/docs/configuration/librechat_yaml/object_structure/agents#managementapi).

Każdy skonfigurowany klient OAuth jest powiązany z jednym istniejącym `userId` i `tenantId` w LibreChat. Po weryfikacji tokena każde żądanie jest wykonywane jako ten użytkownik i zachowuje jego bieżące uprawnienia roli, listy kontroli dostępu (ACL) dla Agentów i Umiejętności, ograniczenia dostawców, przyznane narzędzia, limity plików oraz izolację dzierżawcy. Powiązanie klienta nie czyni użytkownika administratorem ani nie zapewnia dostępu do zasobów, którymi użytkownik nie mógłby zarządzać w inny sposób.

### Trasy agentów [#agent-routes]

| Metoda   | Trasa                                      | Cel                                          |
| -------- | ------------------------------------------ | -------------------------------------------- |
| `POST`   | `/api/agents/v1/agents`                    | Utwórz Agenta                                |
| `GET`    | `/api/agents/v1/agents`                    | Wyświetl listę dostępnych Agentów            |
| `GET`    | `/api/agents/v1/agents/{id}`               | Odczytaj jednego dostępnego Agenta           |
| `PATCH`  | `/api/agents/v1/agents/{id}`               | Zaktualizuj Agenta                           |
| `DELETE` | `/api/agents/v1/agents/{id}`               | Usuń Agenta                                  |
| `POST`   | `/api/agents/v1/agents/{id}/files`         | Prześlij i dołącz plik zasobu Agenta         |
| `GET`    | `/api/agents/v1/agents/{id}/files`         | Wyświetl listę dostępnych plików Agenta      |
| `DELETE` | `/api/agents/v1/agents/{id}/files/{fileId}` | Usuń dołączony plik z Agenta                 |

Ładunki (payloads) tworzenia i aktualizacji Agentów używają tych samych zewnętrznie obsługiwanych pól, co Agent Builder, i odrzucają nieznane pola najwyższego poziomu. Tworzenie wymaga pola `model`; aktualizacja akceptuje tylko dostarczone pola. Odpowiedzi ujawniają obsługiwaną konfigurację Agenta oraz `id`, `provider`, dopuszczający wartość null `model`, `version`, `createdAt` i `updatedAt`, bez pól własności trwałości (persistence ownership).

Listy akceptują `limit` od 1 do 100, z wartością domyślną 20, oraz nieprzejrzysty `cursor`. Gdy `has_more` ma wartość true, przekaż zwróconą wartość `after` jako następny kursor; nie dekoduj ani nie konstruuj kursorów po stronie klienta.

```bash
curl https://your-librechat-instance/api/agents/v1/agents?limit=20 \
  -H "Authorization: Bearer YOUR_MACHINE_ACCESS_TOKEN"
```

```bash
curl -X POST https://your-librechat-instance/api/agents/v1/agents \
  -H "Authorization: Bearer YOUR_MACHINE_ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Release assistant",
    "provider": "openAI",
    "model": "gpt-5.6",
    "instructions": "Prepare concise release notes from verified changes."
  }'
```

Przesyłanie plików wykorzystuje `multipart/form-data` z jednym `file` oraz wartością `tool_resource`, taką jak `context`, `file_search` lub `execute_code`. LibreChat stosuje weryfikację możliwości wdrożenia, przyznania roli, limitu szybkości przesyłania, limitów na plik, liczby plików oraz łącznego rozmiaru przed dołączeniem zasobu. Usunięcie pliku wymaga uprawnień do edycji Agenta i nie osłabia podstawowych zasad autoryzacji plików.

### Trasy umiejętności (Skill Routes) [#skill-routes]

| Metoda  | Trasa                                                | Cel                                   |
| ------- | ---------------------------------------------------- | ------------------------------------- |
| `GET`   | `/api/agents/v1/skills`                              | Wyświetl dostępne umiejętności (Skills) |
| `GET`   | `/api/agents/v1/skills/{id}`                         | Odczytaj jedną dostępną umiejętność   |
| `PATCH` | `/api/agents/v1/skills/{id}`                         | Zaktualizuj metadane obsługiwanej umiejętności |
| `GET`   | `/api/agents/v1/skills/{id}/files`                   | Wyświetl pliki w umiejętności         |
| `GET`   | `/api/agents/v1/skills/{id}/files/{relativePath}`    | Odczytaj jeden plik umiejętności      |
| `PUT`   | `/api/agents/v1/skills/{id}/files/{relativePath}`    | Utwórz lub zastąp jeden obsługiwany plik |

Operacje na Skillach są ograniczone do Skillów widocznych dla przypisanego użytkownika. Odczyty wymagają dostępu do Skilla, podczas gdy zapisy metadanych lub plików wymagają odpowiednich uprawnień do edycji i tworzenia Skillów. Ścieżki są normalizowane w obrębie katalogu głównego Skilla; próby wyjścia poza katalog (traversal), nieobsługiwane pliki oraz zbyt duża zawartość są odrzucane.

### Błędy i uwierzytelnianie [#errors-and-authentication]

Odpowiedzi zarządzania wykorzystują ustrukturyzowane błędy z kodami `invalid_request`, `not_found`, `permission_denied`, `conflict` lub `internal_error`. Błędy autoryzacji zasobów mogą być zwracane jako `not_found`, aby wywołujący nie mogli sprawdzać niedostępnych identyfikatorów.

Tokeny maszynowe muszą być ważne, zgadzać się ze skonfigurowanym wystawcą, identyfikować jednego klienta z listy dozwolonych poprzez `azp` lub `client_id` oraz spełniać skonfigurowaną regułę podmiotu. Domyślnie tokeny muszą również zgadzać się ze skonfigurowaną grupą odbiorców (audience). W przypadku dostawców takich jak Amazon Cognito, którzy wydają tokeny dostępu maszynowego z `client_id` zamiast `aud`, należy ustawić `tokenUse: access`, pominąć `audience` i wymagać oczekiwanego zakresu OAuth za pomocą `requiredScopes`. Brak konfiguracji lub nieprawidłowe dane uwierzytelniające zwracają `401`; powiązane konto w trakcie usuwania zwraca `409`. Zobacz [`managementApi.auth.oidc`](/docs/configuration/librechat_yaml/object_structure/agents#managementapiauthoidc) oraz [`managementApi.auth.clients`](/docs/configuration/librechat_yaml/object_structure/agents#managementapiauthclients), aby zapoznać się z pełnymi regułami dotyczącymi oświadczeń (claims) i powiązań.

## Endpoints [#endpoints]

### Chat Completions (zgodne z OpenAI) [#chat-completions-openai-compatible]

```
POST /api/agents/v1/chat/completions
```

Użyj dowolnego SDK zgodnego z OpenAI, wskazując na swoją instancję LibreChat. Parametr `model` odpowiada identyfikatorowi agenta (agent ID).

**Przykład z użyciem curl:**
```bash
curl -X POST https://your-librechat-instance/api/agents/v1/chat/completions \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "agent_abc123",
    "messages": [
      {"role": "user", "content": "Hello, what can you help me with?"}
    ],
    "stream": true
  }'
```

**Przykład z użyciem OpenAI SDK (Python):**
```python
from openai import OpenAI

client = OpenAI(
    base_url="https://your-librechat-instance/api/agents/v1",
    api_key="YOUR_API_KEY"
)

response = client.chat.completions.create(
    model="agent_abc123",
    messages=[{"role": "user", "content": "Hello!"}],
    stream=True
)

for chunk in response:
    print(chunk.choices[0].delta.content, end="")
```

### Lista modeli [#list-models]

```
GET /api/agents/v1/models
```

Zwraca dostępne agenty jako modele. Przydatne do sprawdzania, które agenty są dostępne przy użyciu Twojego klucza API.

### API otwartych odpowiedzi (Open Responses API) [#open-responses-api]

```
POST /api/agents/v1/responses
```

Endpoint Open Responses jest zgodny ze [specyfikacją Open Responses](https://www.openresponses.org/), otwartym standardem wnioskowania zainicjowanym przez OpenAI i stworzonym przez społeczność AI open-source. Został zaprojektowany z myślą o przepływach pracy agentów, z natywną obsługą wnioskowania, użycia narzędzi, ustrukturyzowanych danych wyjściowych oraz strumieniowania zdarzeń semantycznych.

```bash
curl -X POST https://your-librechat-instance/api/agents/v1/responses \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "agent_abc123",
    "input": "What is the weather today?"
  }'
```

#### Narzędzia funkcji wywoływane przez wywołującego (Caller-Executed Function Tools) [#caller-executed-function-tools]

Endpoint Open Responses akceptuje standardowe narzędzia `function` dostarczone przez wywołującego. LibreChat udostępnia te definicje modelowi, ale ich nie wykonuje. Gdy model wybierze jedno z nich, odpowiedź zawiera element wyjściowy `function_call`, który wywołujący powinien wykonać.

Aby kontynuować, wyślij nowe żądanie, którego `input` powtarza zwrócony element `function_call`, a po nim następuje pasujący element `function_call_output`. To przekazanie jest bezstanowe: nie tworzy zawieszonego uruchomienia (suspended run), a sam `previous_response_id` nie może zastąpić powtórzonej wymiany narzędzi.

```json
{
  "model": "agent_abc123",
  "input": [
    {
      "type": "function_call",
      "call_id": "call_abc123",
      "name": "lookup_order",
      "arguments": "{\"order_id\":\"A-42\"}"
    },
    {
      "type": "function_call_output",
      "call_id": "call_abc123",
      "output": "{\"status\":\"shipped\"}"
    }
  ]
}
```

Nazwy narzędzi wywoływanych przez użytkownika (caller tools) mogą zawierać litery, cyfry, podkreślniki oraz myślniki. Nazwy muszą być unikalne i nie mogą zastępować narzędzi dostarczanych przez serwer. Narzędzie wywoływane przez użytkownika musi być jedynym wybranym narzędziem w swojej turze; jeśli model połączy je z narzędziami wykonywanymi przez serwer, LibreChat poprosi model o ponowne wykonanie narzędzia użytkownika w odosobnieniu.

W przypadku narzędzi agentów wykonywanych przez LibreChat, oba bezgłowe punkty końcowe wnioskowania (headless inference endpoints) wymuszają włączoną politykę [`endpoints.agents.toolApproval`](/docs/configuration/librechat_yaml/object_structure/agents#toolapproval), w tym `deny`, `ask` oraz programowe punkty zaczepienia (hooks). Wywołania te nie posiadają interaktywnego kanału zatwierdzania/wznawiania: `deny` oraz `ask` blokują narzędzie zamiast otwierać monit o zatwierdzenie. Skonfiguruj jawne zezwolenia (allows) tylko dla narzędzi, które klient API powinien móc uruchamiać bez nadzoru; gdy polityka jest wyłączona, jej punkty zaczepienia zatwierdzania nie są uruchamiane. Narzędzia funkcji wykonywane przez wywołującego pozostają w gestii wywołującego.

## Zdarzenia agenta [#agent-events]

Agent Events pozwalają uwierzytelnionemu kontrolerowi lub adapterowi źródłowemu dostarczać trwałe zadania do Agenta. Dostarczanie zdarzeń jest funkcją w fazie beta, a jej żądania, odpowiedzi oraz zachowanie w czasie wykonywania mogą ulec zmianie.

Punkty końcowe (endpoints) korzystają z uwierzytelnionego użytkownika, dzierżawy (tenant) oraz klucza API; docelowy Agent musi być widoczny dla tego użytkownika w ramach istniejących uprawnień Remote Agents. Żądania Agent Event również korzystają z dedykowanego zasobnika [`rateLimits.agentEvents`](/docs/configuration/librechat_yaml/object_structure/config#ratelimits).

### Dostarcz zdarzenie [#deliver-an-event]

```http
POST /api/agents/v1/events
Authorization: Bearer <REMOTE_AGENTS_API_KEY>
Idempotency-Key: webhook-42-resource-7
Content-Type: application/json

{
  "mode": "fire",
  "event": {
    "id": "resource-7-ready-3",
    "type": "resource.ready",
    "occurredAt": 1786967999000,
    "payload": { "resourceId": "resource-7" }
  },
  "target": { "agentId": "agent_abc123" },
  "input": "Resource resource-7 is ready. Inspect it and report the result.",
  "orderingKey": "resource-7"
}
```

Wyślij dokładnie jeden nagłówek `Idempotency-Key` i użyj go ponownie podczas ponawiania tej samej dostawy zdarzenia źródłowego do celu. Klucz musi zawierać od 1 do 256 liter, cyfr lub znaków `._~:/+=-`. Ponowne użycie klucza z inną treścią dostawy spowoduje zwrócenie konfliktu.

Wywołujący dostarcza `id` zdarzenia, `type`, `occurredAt` oraz oczyszczony `payload`. LibreChat zastępuje wszelkie dostarczone przez wywołującego `event.source` tożsamością uwierzytelnionego klucza API oraz wyznacza użytkownika, dzierżawcę (tenant), identyfikator żądania i czas otrzymania. Nie należy umieszczać poświadczeń ani sekretów transportowych w ładunkach (payloads) zdarzeń, ponieważ zaakceptowane dostarczenia są trwale zapisywane.

`orderingKey` jest opcjonalny. Użyj stabilnej wartości, gdy dostawy z różnych źródeł muszą pozostać uporządkowane dla tego samego zasobu.

Pomyślne żądanie zwraca `202 Accepted`, nieprzejrzysty `id` dostarczenia, jego bieżący status oraz nagłówek `Location`. Odpytuj tę lokalizację:

```http
GET /api/agents/v1/events/{delivery_id}
Authorization: Bearer <SAME_REMOTE_AGENTS_API_KEY>
```

Dostarczenie może mieć status `pending`, `leased`, `succeeded` lub `dead`. Odpowiedź o statusie zawiera próby i znaczniki czasu oraz wynik lub błąd publiczny po zakończeniu; nie ujawnia zapisanego ładunku (payload), klucza kolejności, historii ponownych prób ani tożsamości pracownika (worker). Dostęp do statusu jest ograniczony do tego samego użytkownika, dzierżawcy (tenant) i źródła klucza API.

W przypadku powiązanego `continue`, `succeeded` oznacza, że tura Agenta została przyjęta, a nie że żądana praca została zakończona. Jego status ujawnia zatem również trwały cykl życia `handling`: `started`, po którym następuje dokładnie jeden ze stanów: `applied`, `completed_no_action`, `failed` lub `cancelled`.

Źródła uwzględniające akcje (action-aware) mogą zawierać `expectedAction` z nazwą narzędzia i opcjonalnym podzbiorem argumentów. LibreChat zgłasza status `applied` tylko wtedy, gdy dana generacja zakończy się z dowodami użycia narzędzia zaobserwowanymi przez hosta, które są zgodne z kontraktem; tekst wygenerowany przez model nigdy nie jest akceptowany jako dowód. Dostarczenia typu `fire`, `steer` oraz niepowiązane `continue` odrzucają `expectedAction`.

Pomyślne wyniki `fire` zawierają identyfikator konwersacji i generacji, który może być celem późniejszego zdarzenia `steer`.

### Zdarzeniowe agenty podrzędne (Event-Driven Child Agents) [#event-driven-child-agents]

Zewnętrzny system może powiązać aktora źródłowego z bezpośrednim podrzędnym Agentem, a następnie kontynuować tę samą konwersację podrzędną w ramach różnych zdarzeń. Powiązane kontynuacje podrzędne są automatyczne po pomyślnym zakończeniu weryfikacji tożsamości klucza API, własności powiązania, relacji nadrzędnej oraz autoryzacji Agenta; nie ma osobnego przełącznika funkcji.

Zarejestruj aktora przy użyciu tego samego klucza API, który będzie dostarczał jego późniejsze tury:

```http
POST /api/agents/v1/events/bindings
Authorization: Bearer <REMOTE_AGENTS_API_KEY>
Idempotency-Key: championship-7-player-hanae
Content-Type: application/json

{
  "actorId": "hanae-kobayashi",
  "parentConversationId": "director-conversation-id",
  "parentMessageId": "director-message-id",
  "target": { "agentId": "agent_hanae" }
}
```

`actorId` może zawierać do 128 znaków. Rodzicem musi być zwykła konwersacja z Agentem, a cel musi być skonfigurowany jako jeden z bezpośrednich Subagentów tego Agenta lub dozwolony proces self-spawn. Nowe powiązanie zwraca `201`; idempotentne powtórzenie zwraca `200`. Obie odpowiedzi zawierają `id`, `actorId`, `agentId` oraz `threadId`.

Wyślij późniejsze tury z zwróconym identyfikatorem powiązania (binding ID):

```http
POST /api/agents/v1/events
Authorization: Bearer <SAME_REMOTE_AGENTS_API_KEY>
Idempotency-Key: game-12-ply-17-hanae
Content-Type: application/json

{
  "mode": "continue",
  "bindingId": "evtbind_...",
  "event": {
    "id": "game-12-ply-17",
    "type": "chess.turn.ready",
    "occurredAt": 1786968000000,
    "payload": { "gameId": "game-12", "expectedPly": 17 }
  },
  "input": "Your clock is running. Read the position and submit one legal move.",
  "expectedAction": {
    "tool": "submit_move",
    "arguments": { "gameId": "game-12" }
  }
}
```

LibreChat rozwiązuje podrzędnego Agenta, wątek, najnowszy liść gałęzi oraz ścieżkę kolejkowania z powiązania bezpośrednio przed wysłaniem. Dostarczone przez wywołującego pola celu i kolejkowania nie mogą przekierować powiązanej kontynuacji. Nagłówek `Idempotency-Key` żądania staje się stabilną publiczną tożsamością dla tej podrzędnej tury w ramach ponownych prób dostarczenia, dzierżawy generowania, utrwalonych wiadomości, aktywności na żywo oraz późniejszego wznowienia HITL.

Każde powiązanie posiada automatyczną trwałą skrzynkę odbiorczą. Jego następne zdarzenie pozostaje w kolejce, dopóki bieżąca tura nie osiągnie stanu `applied`, `completed_no_action`, `failed` lub `cancelled`; różne powiązania pozostają niezależne i mogą działać równolegle. Kontynuacja punktu kontrolnego (checkpoint) jest podejmowana tylko dla kompatybilnej zainicjowanej tury. Jeśli punkt kontrolny brakuje lub nie można go przywrócić, LibreChat powraca do trwałej historii wiadomości bez osłabiania kontroli odbioru, autoryzacji lub oczekiwanych działań.

Powiązany aktor (bound actor) może wstrzymać działanie w oczekiwaniu na interakcję "Ask User" lub zatwierdzenie narzędzia. LibreChat utrwala dokładne podpisane zawieszenie przed ujawnieniem oczekującej akcji, a skrzynka odbiorcza powiązania pozostaje zablokowana, dopóki to samo wywołanie aktora nie zostanie wznowione lub zakończone. Event Actors wymagają trwałego punktu kontrolnego MongoDB; `type: memory` nie jest kompatybilny. LibreChat negocjuje protokół generowania v2 i automatycznie wybiera punkt kontrolny lub kontynuację historii. Istniejące zadania w protokole v1 pozostają na ścieżce trwałej historii, dopóki nie zostaną wyczerpane. Zobacz [Generation Protocol Compatibility](/docs/configuration/redis#generation-protocol-compatibility), aby zapoznać się z wymaganiami dotyczącymi wdrożeń z mieszanymi wersjami.

### Łączenie zdarzeń obserwacyjnych [#coalescing-observational-events]

Źródła, które mogą potwierdzić, że kilka powiązanych zdarzeń `continue` to wymienne obserwacje, mogą przypisać im ten sam zdefiniowany przez źródło `coalesce.key`:

```json
{
  "mode": "continue",
  "bindingId": "evtbind_...",
  "event": {
    "id": "championship-7-game-12-move-18",
    "type": "chess.move.completed",
    "occurredAt": 1786968000750,
    "payload": { "gameId": "game-12", "ply": 18 }
  },
  "input": "A tournament game advanced.",
  "coalesce": { "key": "championship-commentary" }
}
```

LibreChat zbiera kompatybilne zdarzenia przez maksymalnie 750 ms, przy czym limit wynosi 8 zdarzeń i 512 KiB łącznych kopert. Element podrzędny otrzymuje jeden deterministyczny dokument wsadowy, ale każde zdarzenie źródłowe zachowuje własny `Idempotency-Key`, rekord dostarczenia oraz potwierdzenie odbioru.

Używaj koalescencji tylko dla obserwacji, które nie wymagają podjęcia działań. Jest ona odrzucana w przypadku `fire`, `steer`, niepowiązanych `continue` oraz dostarczeń z `expectedAction`; nie używaj jej dla poleceń, zatwierdzeń, żądań HITL, ogrodzeń (fences) ani zdarzeń, których indywidualny czas ma znaczenie.

W uwierzytelnionej konwersacji nadrzędnej każdy powiązany aktor pojawia się pod wiadomością nadrzędną, do której należy. Panel Subagent umożliwia przełączanie się między aktorami i turami, ładowanie wcześniejszej aktywności oraz rozwijanie tury w celu wyświetlenia pełnej powiązanej aktywności. Szczegóły zdarzenia obejmują typ, źródło, czas wystąpienia oraz oczekiwaną akcję. Widoczne kroki uruchomieniowe, narzędzia, wiadomości i znaczniki rozumowania są uwzględnione bez surowego tekstu rozumowania. Indeks nadrzędny zwraca maksymalnie 64 wątki podrzędne i 20 ostatnich zadań na wątek podrzędny z ograniczonego okna źródłowego, zgłasza obcięcie zamiast sugerować kompletność i ogranicza odpowiedź do 96 KB. Jest on autoryzowany na poziomie nadrzędnym, użytkownika i dzierżawcy; powiązania, identyfikatory kluczy źródłowych, tokeny dzierżawy i stan procesu roboczego nie są uwzględnione w projekcji.

Wątek podrzędny pozostaje ukryty przed standardową nawigacją konwersacji i jest dostępny tylko do odczytu dla ścieżek czatu użytkownika, dziedziczy politykę tymczasowości lub wygaśnięcia rodzica oraz jest ograniczony do jednego poziomu bezpośredniego potomstwa. Sam identyfikator powiązania (binding ID) nie zapewnia dostępu; kontynuacje są ograniczone do użytkownika, dzierżawcy (tenant) oraz klucza API, które je utworzyły.

### Akcje aktora zdarzeń w trybie odłączonym (Detached Event Actor) [#detached-event-actor-actions]

Tury Event Actor mogą odłączać kwalifikujące się Akcje i wykonywać je w sposób trwały. Dostarczenie pozostaje w cyklu obsługi podczas działania Akcji; trwałe dowody końcowe wznawiają pierwotne podpisane wywołanie aktora, a tylko wynikowe dowody narzędzia zaobserwowane przez hosta mogą spełnić `expectedAction`. Powtórzenia i konkurujące repliki nie mogą uruchomić tej samej zarezerwowanej Akcji dwukrotnie. Jeśli LibreChat nie może ustalić, czy wystąpił zewnętrzny efekt uboczny, poddaje uruchomienie kwarantannie zamiast ponawiać je w ciemno.

LibreChat automatycznie umożliwia tę wewnętrzną pracę nad uzupełnianiem, gdy wybrany wbudowany magazyn generowania zgłasza taką obsługę. Magazyn działający w pamięci uruchamia procesy inicjacji, uzupełniania i kontynuacji w ramach jednego procesu i nie jest w stanie odzyskać tej pracy po jego zakończeniu. Strumienie generowania Redis dodają trwałe odzyskiwanie po restarcie i przekazywanie replik. Rekordy dostarczania i odzyskiwania należące do danej funkcji pozostają niewidoczne dla starszych elementów zgłaszających podczas opróżniania w środowisku o mieszanych wersjach; nie istnieje flaga producenta zarządzana przez operatora.

## Śledzenie zużycia tokenów [#token-usage-tracking]

Wszystkie żądania wnioskowania przez API Agentów śledzą zużycie tokenów względem salda użytkownika, gdy skonfigurowano wydatki na tokeny. Zarówno w przypadku odpowiedzi strumieniowych, jak i niestrumieniowych, wszystkie rozliczane wywołania modeli głównego Agenta (primary-Agent) oraz podagentów (Subagent) są sumowane w ramach całkowitych wartości najwyższego poziomu. Odpowiedź zawiera również zestawienia tokenów `primary` oraz `subagent` bez identyfikatorów. Szczegóły dotyczące tokenów pamięci podręcznej (cache) i wnioskowania (reasoning-token) są uwzględniane, jeśli dostawca je raportuje.
