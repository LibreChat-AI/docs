## Introduzione [#introduction]

L'API Code Interpreter di LibreChat fornisce un modo sicuro e semplice per eseguire codice e gestire file attraverso una semplice interfaccia API. Che tu la stia utilizzando tramite gli Agent di LibreChat o integrandola direttamente nelle tue applicazioni, l'API offre un potente ambiente sandbox per l'esecuzione di codice in molteplici linguaggi di programmazione.

<Callout type="info" title="Open source">
  Il Code Interpreter di LibreChat è basato su [**ClickHouse/code-interpreter**](https://github.com/ClickHouse/code-interpreter), un servizio di esecuzione di codice in sandbox open-source (Apache 2.0). Eseguilo in self-hosting e punta LibreChat alla tua istanza.
</Callout>

## Introduzione [#getting-started]

1. Distribuisci il servizio [code-interpreter](https://github.com/ClickHouse/code-interpreter) (Docker Compose o Helm, consulta il README del repository)
2. Punta LibreChat verso di esso con `LIBRECHAT_CODE_BASEURL`
3. Configura l'autenticazione [LibreChat JWT](#self-hosted-jwt-authentication) per l'attuale servizio open-source, oppure imposta `LIBRECHAT_CODE_API_KEY` per un deployment compatibile con API-key.
4. Per sperimentare con le sessioni Agent stateful, distribuisci un percorso Code Interpreter con profilo `stateful` separato e configura `LIBRECHAT_CODE_BASEURL_STATEFUL` o [`statefulCodeSessions.environments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions) denominato.
5. Inizia a eseguire codice e a generare file in modo sicuro tramite gli Agents di LibreChat o il pulsante "Run Code"

## Caratteristiche Principali [#key-features]

### Lingue supportate [#supported-languages]

Esegui codice in molteplici linguaggi di programmazione:

- Python, Node.js (JS/TS), Go, C/C++, Java, PHP, Rust, Fortran, Rscript

### Gestione fluida dei file [#seamless-file-handling]

- Carica file per l'elaborazione
- Scarica gli output generati
- Gestione sicura dei file
- Organizzazione dei file basata sulla sessione

LibreChat ripristina i file di conversazione referenziati in ambienti Code Interpreter gestiti prima dell'esecuzione di un Agent. Se il recupero di tutti i file Code Interpreter richiesti fallisce, l'esecuzione si interrompe prima dell'invocazione del modello e richiede all'utente di riallegare i file invece di continuare con riferimenti obsoleti. In un workspace allegato selezionato, i caricamenti della chat **non** vengono copiati nel workspace dell'utente e i file del workspace e gli strumenti Bash non possono aprirli lì. Se il worker pubblicizza Programmatic Bash con file relay, tale strumento vedrà invece i caricamenti messi in stage sotto `$LIBRECHAT_CODE_DATA_DIR` per la durata della sua esecuzione.

I caricamenti tramite Code API si riprendono dai limiti di frequenza `429` rispettando l'intestazione `Retry-After`, riaprendo il flusso sorgente per ogni tentativo e condividendo un budget di attesa limitato. Gli amministratori possono regolare il recupero per utente e per percorso con [`codeApiUploadConcurrency` e `codeApiMaxRetryWaitMs`](/docs/configuration/librechat_yaml/object_structure/agents#code-api-upload-recovery).

Quando gli input di una conversazione vengono montati nella stessa destinazione sandbox, LibreChat risolve il conflitto prima dell'esecuzione. I file di conversazione condivisi vengono assegnati prima dei file privati dell'Agent; all'interno di ciascun ambito, la scrittura del contenuto più recente mantiene la destinazione originale. I percorsi in conflitto vengono appiattiti quando necessario o ricevono un suffisso derivato dall'identità, e i percorsi `/mnt/data/...` risolti vengono inclusi nel contesto del file dell'Agent. Ciò copre anche un caricamento e un output generato che condividono lo stesso nome file, in modo che un singolo conflitto non causi il rifiuto di ogni successiva esecuzione del Code Interpreter nella conversazione. I riferimenti seed duplicati che risolvono comunque in una destinazione già reclamata vengono ignorati invece di causare il fallimento dell'intera richiesta.

Le immagini della sandbox vengono trasferite in finestre delimitate. Imposta [`LIBRECHAT_CODE_SANDBOX_OUTPUT_MAX_SIZE`](/docs/configuration/dotenv#code-interpreter) in modo che corrisponda a `SANDBOX_OUTPUT_MAX_SIZE` del worker; LibreChat deriva la finestra immagine sicura più ampia da quel budget e può apprendere un limite per servizio più piccolo dopo una lettura fallita. Utilizza `LIBRECHAT_CODE_IMAGE_CHUNK_BYTES` solo quando è necessario un override esatto della finestra. Gli artefatti generati scaricati in precedenza vengono riutilizzati all'interno della richiesta quando possibile, evitando un'altra lettura dalla sandbox.

In un grafo multi-Agent, assegna nomi di file distinti ai file privati dei diversi Agent. Ogni Agent risolve i propri percorsi di file privati prima che il grafo combini i loro input, quindi file privati genuinamente diversi che richiedono indipendentemente la stessa destinazione non possono ancora essere rinominati in modo coerente al momento dell'unione; la prima destinazione inserita ha la precedenza.

### Programmatic Tool Calling [#programmatic-tool-calling]

Il Programmatic Tool Calling consente agli Agenti LibreChat di instradare gli strumenti MCP selezionati attraverso la sandbox del Code Interpreter. Invece di chiedere al modello di richiamare direttamente ogni strumento, LibreChat fornisce uno strumento di orchestrazione basato su Code Interpreter; il codice sandbox generato può richiamare stub di strumenti registrati, utilizzare cicli e condizionali, elaborare risultati intermedi e restituire una risposta finale.

Il sandbox non riceve ancora l'accesso alla rete generale. Le chiamate agli strumenti vengono gestite tramite il Code Interpreter Tool Call Server. LibreChat interseca la proiezione delle funzionalità del chiamante in tempo reale con il suo registro attendibile, in modo che possano essere chiamati solo gli strumenti programmatici attivi già registrati per l'Agent e una richiesta non possa espandere il proprio accesso.

Gli strumenti programmatici richiedono Code Interpreter sull'Agent. I loro interruttori rimangono disabilitati finché non viene selezionato Code Interpreter, e la rimozione di Code Interpreter cancella le selezioni programmatiche esistenti. LibreChat rimuove inoltre le opzioni di chiamata programmatica non aggiornate dalle operazioni di creazione, aggiornamento, duplicazione e ripristino della versione dell'Agent quando `execute_code` o lo strumento Code Interpreter non sono disponibili.

Durante un'esecuzione programmatica, espandi la scheda Code Interpreter per visualizzare una traccia in tempo reale in stile terminale delle chiamate agli strumenti interni, con anteprime limitate degli argomenti, stati, durate ed errori. Questa traccia aiuta a ispezionare il programma mentre è in esecuzione, ma non viene mantenuta dopo il ricaricamento della pagina.

### Esecuzione di codice in background [#background-code-execution]

L'esecuzione in background consente a un Agent di inviare codice a lunga esecuzione o operazioni shell e continuare la conversazione. Per gli Agent salvati, i completamenti basati solo su contenuto supportati vengono recapitati automaticamente in una continuazione di follow-up per impostazione predefinita. `check_background_task` rimane disponibile per lo stato esplicito, il controllo, gli artefatti live e il ripristino. Nella chat di LibreChat, al termine del lavoro, stdout e i file generati appaiono nella chiamata al codice originale e vengono mantenuti per i turni successivi. I completamenti in background e i controlli espliciti visualizzano schede attività con stato, stato di consegna e risultati leggibili; il risultato originale esatto rimane disponibile per essere copiato. L'intestazione della chat raggruppa le attività in esecuzione e quelle recenti e offre controlli individuali o di interruzione totale quando consentito dalla politica di cancellazione della distribuzione.

Questa funzionalità è facoltativa a livello di deployment. Aggiungi `run_in_background` insieme a `execute_code` nelle [funzionalità dell'endpoint Agents](/docs/configuration/librechat_yaml/object_structure/agents#capabilities), quindi abilita Code Interpreter sull'agente. L'esecuzione del codice e le chiamate alla shell diventano automaticamente idonee per l'esecuzione in background; disattiva **Background execution** nelle impostazioni dello strumento Code Interpreter quando un agente deve rinunciare a questa opzione. Il modello decide comunque per ogni chiamata se inviare il lavoro idoneo in background.

L'esecuzione in background ordinaria rimane locale al processo e non sopravvive alla perdita del suo worker dell'app. Una volta che un risultato del terminale di solo contenuto viene salvato, la sua consegna automatica è durevole e può continuare su un'altra replica; le attività con un artefatto attivo richiedono ancora il polling sull'esecuzione proprietaria. Imposta [`endpoints.agents.backgroundTasks.completionWakeups: false`](/docs/configuration/librechat_yaml/object_structure/agents#backgroundtasks) per richiedere il polling per ogni risultato. L'invio in background non estende il limite di esecuzione del servizio Code Interpreter; si applica comunque il normale timeout lato server della distribuzione.

Con [`ordinaryToolCancellation: true`](/docs/configuration/librechat_yaml/object_structure/agents#backgroundtasks), i proprietari possono richiedere l'annullamento cooperativo degli strumenti di codice in background ordinari, incluso Bash allegato. L'attività rimane attiva e consuma capacità finché l'invocazione non si stabilizza; uno strumento che ignora l'annullamento potrebbe comunque essere completato.

### Sessioni di codice stateful [#stateful-code-sessions]

Le sessioni di codice stateful consentono a un agente LibreChat di riutilizzare un singolo spazio di lavoro sandbox di Code Interpreter tra diverse esecuzioni. File, pacchetti installati e stato di lavoro vengono solitamente mantenuti, rendendo più efficienti l'analisi iterativa e la generazione di file in più passaggi. Ogni agente seleziona un ambito di spazio di lavoro:

- **Area di lavoro utente (consigliata):** un'area di lavoro per l'utente che ha effettuato l'accesso, condivisa tra gli agenti con stato abilitato
- **Area di lavoro agente + utente:** un'area di lavoro per ogni combinazione di utente e agente
- **Area di lavoro della conversazione:** un'area di lavoro per ogni utente e conversazione

Per gli Agent creati di recente, l'ambito iniziale deriva da **Settings > Data Controls > Code execution > Default stateful workspace**. L'impostazione personale è predefinita su **User workspace**; modificarla non altera gli Agent esistenti né abilita le sessioni stateful. Gli amministratori della distribuzione possono limitare gli ambiti selezionabili con [`statefulCodeSessions.allowedEnvironments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions). Se un'impostazione predefinita personale salvata non è più disponibile, i nuovi Agent utilizzeranno il primo ambito consentito; un Agent esistente abilitato con un ambito ora non consentito deve essere riconfigurato prima di poter essere eseguito.

L'ambito dell'area di lavoro è separato dal suo backend di esecuzione. Quando gli amministratori configurano [`statefulCodeSessions.environments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions) denominati, l'Agent Builder aggiunge un selettore **Ambiente di esecuzione**:

- **Gestito:** una Code API stateful gestita dal deployment
- **Allegato:** un bridge remoto Code API compatibile che delega il lavoro a un worker `@librechat/code` in uscita, come una VM gestita da un operatore
- **Personale:** un worker `@librechat/code` vincolato al proprietario, associato da un utente autorizzato tramite le impostazioni di LibreChat
- **Deployment default:** l'ambiente configurato contrassegnato come predefinito

<Callout type="warning" title="Altamente sperimentale">
  Le Stateful Code Sessions sono in una fase di sperimentazione iniziale. Il loro comportamento, la configurazione, le caratteristiche di persistenza e l'integrazione sottostante potrebbero cambiare sostanzialmente. Non considerare l'implementazione attuale come un contratto di produzione stabile.
</Callout>

Questa funzionalità è facoltativa (opt-in). Abilita `execute_code` e `stateful_code_sessions` nelle [funzionalità dell'endpoint Agents](/docs/configuration/librechat_yaml/object_structure/agents#capabilities), configura una rotta stateful dedicata con [`LIBRECHAT_CODE_BASEURL_STATEFUL`](/docs/configuration/dotenv#stateful-code-interpreter-endpoint) o ambienti denominati, abilita Code Interpreter sull'agente, quindi attiva **Stateful code sessions** e scegli il relativo backend di esecuzione e l'ambito dell'area di lavoro nelle impostazioni avanzate.

Le richieste stateful falliscono in modalità "closed" quando l'ambiente selezionato è mancante, inaccessibile o incompatibile; LibreChat non le invia a `LIBRECHAT_CODE_BASEURL` né sceglie silenziosamente un altro backend denominato. Quando non sono configurati ambienti denominati, `LIBRECHAT_CODE_BASEURL_STATEFUL` rimane la rotta stateful. Gli agenti stateless continuano a utilizzare l'endpoint normale. LibreChat invia anche `X-CodeAPI-Expected-Profile: stateful`, quindi il servizio dedicato deve pubblicizzare il profilo `stateful`.

Le sessioni stateful e stateless non condividono un workspace attivo. Il workspace stateful può essere ripristinato in qualsiasi momento, indipendentemente dall'ambito selezionato. Negli ambienti Code Interpreter gestiti, salva gli output importanti in `/mnt/data` e non fare affidamento sullo stato della sessione come memoria permanente. Un workspace collegato è una directory separata di proprietà del worker; i caricamenti non vengono inseriti lì per impostazione predefinita.

I file creati tramite le chiamate stateful `create_file` e `edit_file` appaiono nel messaggio dell'assistente sotto una riga espandibile **Workspace changes**. Questa elenca ogni percorso modificato univocamente per quella risposta e fornisce un'azione di download autenticato. I download utilizzano il flusso di file persistente di LibreChat quando disponibile e, in alternativa, un fallback sicuro di Code Interpreter. La riga è un registro degli output creati, non un'istantanea durevole dell'area di lavoro; gli output stateless continuano ad apparire come normali allegati inline.

#### Ambienti collegati e pairing [#attached-environments-and-pairing]

Gli ambienti collegati richiedono una build sperimentale corrispondente del remote-bridge per il Code Interpreter. Il bridge rimane il confine autenticato per policy, coda e risultati di LibreChat, mentre il worker `@librechat/code` si connette in uscita dalla macchina collegata; la macchina non necessita di una porta worker pubblica in entrata. LibreChat non effettua il prewarm degli ambienti collegati.

Un operatore può fissare un ambiente collegato di proprietà della distribuzione a un worker con `workerId` e può aggiungere `pairing.workerId` quando LibreChat deve emettere un codice di accoppiamento amministratore per quella stessa rotta. `pairing.tokenEnv` indica la variabile d'ambiente contenente il token dell'amministratore del bridge; il segreto stesso non deve mai essere inserito nel YAML. I piani di controllo accoppiati richiedono HTTPS al di fuori dello sviluppo in loopback.

Per i worker self-service, configura un control plane collegato di proprietà del deployment con `pairing.allowPrincipalWorkers: true` e `pairing.tokenEnv`. Può omettere entrambi gli ID worker ed esistere solo come control plane di registrazione; tale voce non è selezionabile per l'esecuzione e non può essere il valore predefinito del deployment.

Gli utenti con autorizzazione di gestione Code Environment possono quindi aprire **Settings > Code environments**, assegnare un nome all'ambiente, scegliere un control plane approvato e selezionare **Connect VM**. LibreChat mostra un comando `librechat-code pair ...` monouso e a breve termine. Eseguilo sulla VM dell'utente, quindi avvia `@librechat/code` con `LIBRECHAT_CODE_SANDBOX_ENDPOINT` puntato al servizio sandbox di quella macchina. L'interfaccia utente elenca gli ambienti dell'utente e consente di revocarli e rimuoverli in seguito; i file della sandbox rimangono sulla VM.

Gli amministratori possono limitare l'iscrizione con [`statefulCodeSessions.principalWorkers`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions). L'iscrizione è abilitata per impostazione predefinita con un massimo di cinque ambienti registrati per utente quando questo blocco viene omesso. Il conteggio include i worker offline su ogni control plane. La configurazione di deployment rappresenta il limite massimo: la configurazione specifica del principal può ridurlo o disabilitarlo, ma non può aumentarlo. L'inasprimento della policy non revoca le macchine già registrate.

Gli ambienti personali sono vincolati all'utente autenticato e al tenant, protetti dagli ACL di Code Environment e assegnati solo a ID convalidati dal server e URL di base approvati. LibreChat non espone al client il token dell'amministratore del bridge o URL dell'operatore arbitrari. La rimozione di un ambiente revoca le credenziali del worker prima di eliminare la voce nel registro, e l'eliminazione dell'utente pianifica la stessa revoca e pulizia con una riconciliazione in background per i tentativi interrotti. La rotta del worker selezionata si applica in modo coerente a Code Interpreter, shell, accesso ai file generati e Programmatic Tool Calling.

Gli Agent che utilizzano un workspace collegato possono elencare il suo albero delle directory, leggere file, cercare contenuti nei file, creare o modificare file ed eseguire Bash sul worker selezionato. Le citazioni dei file utilizzano percorsi relativi al workspace, i file creati appaiono nella riga **Workspace changes** della risposta e gli errori degli strumenti preservano la diagnostica HTTP limitata del worker. Un Agent può anche memorizzare un nome e un'email Git per ogni Agent per i commit creati in quel workspace; questi valori configurano solo l'autore e non forniscono credenziali per il repository.

Nella chat, un comando Bash di un workspace allegato fallito mostra il suo codice di uscita, il segnale di terminazione o il timeout, e il suo stderr è formattato separatamente dallo stdout. Consulta [Activity Groups](/docs/features/agents#activity-groups) per sapere come viene visualizzato l'output di Bash.

Per mostrare la pull request GitHub di una conversazione nell'intestazione della chat e nella barra laterale, il worker collegato deve segnalare il suo branch git. Ciò richiede un worker compilato a partire dalla PR #311 o successiva di `LibreChat-AI/code-interpreter` e `CODEAPI_BRIDGE_LANE_GIT=true` impostato sulla Code API (non su LibreChat). Vedi [Conversation Pull Requests](/docs/features/pull_requests).

Un worker collegato pubblicizza le radici dell'area di lavoro (workspace roots) che rende disponibili. Il composer consente all'utente di selezionare un'area di lavoro per ogni ambiente collegato raggiungibile tramite l'Agent o i suoi Subagent; un'unica area di lavoro non ambigua viene selezionata automaticamente per una nuova conversazione. LibreChat memorizza queste selezioni nella conversazione, le riconvalida rispetto al worker attivo prima dell'esecuzione e le mantiene fisse durante le pause di approvazione e le esecuzioni riprese. L'invio viene bloccato quando una selezione richiesta manca o non è disponibile e LibreChat non sostituisce mai silenziosamente un'altra area di lavoro. All'inizio di un'esecuzione, LibreChat può caricare le istruzioni del repository dall'area di lavoro selezionata in modo che l'Agent segua le linee guida di quel repository; gli amministratori possono limitare l'individuazione con [`repositoryInstructions.timeoutMs`](/docs/configuration/librechat_yaml/object_structure/agents#repositoryinstructions). Gli strumenti nativi per file e Bash dell'area di lavoro possono utilizzare una radice pubblicizzata anche quando il worker non supporta sessioni di runtime riutilizzabili. Il Bash programmatico consapevole dell'area di lavoro è disponibile su Code API e build di worker compatibili quando la configurazione dello strumento programmatico dell'Agent lo consente, il worker collegato autorizzato è pronto e pubblicizza `programmaticLanguages: ['bash']`, e sia l'area di lavoro selezionata che il worker consentono `execute_command`. LibreChat passa l'ID dell'area di lavoro convalidato dal server e l'ID dell'istanza dell'area di lavoro della conversazione, quando presente, allo strumento programmatico; gli argomenti del modello non possono sostituire tale selezione. Senza queste funzionalità, il Bash programmatico è disabilitato; utilizzare il Bash diretto per i comandi consapevoli dell'area di lavoro. Quando il worker supporta il relay dei file, i caricamenti della chat vengono messi in staging separatamente sotto `$LIBRECHAT_CODE_DATA_DIR` per l'esecuzione programmatica, non copiati nell'area di lavoro selezionata. **Stop** annulla un comando BYOM in corso sensibile ai segnali senza invalidare l'area di lavoro per i comandi successivi; il lavoro scollegato mantiene il suo ciclo di vita di annullamento separato.

Per un ambiente di esecuzione collegato, l'Agent Builder può impostare un **Workspace default** su una root attualmente pubblicizzata. Questo viene convalidato rispetto all'ambiente collegato e utilizzato per inizializzare nuove conversazioni per quell'Agent. Scegli **Last used** per utilizzare la preferenza locale del browser dell'utente che ha effettuato l'accesso per quell'Agent e quell'ambiente; si tratta solo di un suggerimento di comodità, mai di una concessione di autorizzazione o di un vincolo di conversazione. La modifica dell'ambiente di esecuzione cancella un valore predefinito esplicito e una root salvata che non è più pubblicizzata rimane visibile ma non può essere selezionata finché non viene riconfigurata.

#### Modifiche all'area di lavoro delle chat salvate [#saved-chat-workspace-changes]

Per impostazione predefinita, la decisione sull'area di lavoro (workspace) allegata a una conversazione salvata è bloccata. Con [`statefulCodeSessions.conversationMoves.enabled`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions) abilitato, il proprietario può spostarsi esplicitamente su un'altra area di lavoro autorizzata o recuperare un'area di lavoro mancante. Il recupero preserva la cronologia della chat, **non** i file dell'area di lavoro persa. L'impostazione `allowAttachDetach: true` consente inoltre al proprietario di allegare un'area di lavoro a una chat salvata non di programmazione o di abbandonare un'area di lavoro allegata per continuare una chat normale; l'abilitazione dei soli spostamenti non abilita l'allegazione/distacco. Queste transizioni non possono avvenire mentre è in corso una generazione e vengono riconvalidate sul server. Aggiorna tutte le repliche API e abilita `CODE_ENVIRONMENT_DECISION_VERSION=1` prima di aderire. Senza questi interruttori, il comportamento esistente di sola conversazione bloccata e spostamento rimane invariato.

Bash collegato utilizza un timeout di 30 secondi per impostazione predefinita. Un ambiente può esporre un budget richiedibile dal modello più ampio con [`configSchema.limits.maxCommandTimeoutMs`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions), fino al limite massimo del protocollo di cinque minuti. Il timeout richiesto non supera mai il limite di distribuzione. Gli amministratori possono limitare separatamente i tentativi di capacità con [`configSchema.limits.maxQueueWaitMs`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions); questa attesa in coda non annulla un comando ammesso o in esecuzione. Per consentire tentativi di ammissione **individuali** più lunghi, utilizzare `configSchema.limits.maxRequestTimeoutMs` solo dopo che la Code API ha rispettato la tolleranza di coda per richiesta e dopo aver verificato il timeout del proxy più breve sulla rotta attiva. L'opzione `configSchema.limits.minCommandAdmissionMs` riserva 10 secondi per impostazione predefinita (valido da 1 a 300 secondi) per l'ammissione prima di un comando. Il timeout Bash pubblicizzato viene adattato al budget della richiesta dopo questa riserva e ulteriori 10 secondi per l'assestamento e la consegna. Questo budget non sostituisce `maxQueueWaitMs`.

#### Corsie Linked-worktree [#linked-worktree-lanes]

Gli ambienti collegati possono scegliere di utilizzare la [pianificazione delle richieste per worktree](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions) con `configSchema.workspaces.linkedWorktrees: true`. Per prima cosa aggiorna LibreChat, quindi distribuisci un bridge Code API compatibile e avvia il worker con `--linked-worktree-lanes`; abilita l'impostazione YAML solo dopo che quel worker ha annunciato `git_linked_worktree`. Le richieste che puntano strutturalmente a `.worktrees/<name>/` utilizzano la corsia (lane) di quel worktree senza modificare i percorsi relativi al checkout mostrati all'Agent. Per Bash, passa la directory del worktree nell'argomento `cwd` dello strumento; eseguire `cd .worktrees/<name>` all'interno del comando rimane nella corsia principale (root lane). Anche le operazioni sulla root del checkout, le azioni sull'ambiente e le istanze dell'area di lavoro della conversazione rimangono con ambito root. Senza questa attivazione, tutte le richieste mantengono la loro pianificazione esistente a livello di intero checkout.

#### Corrispondenza e conflitti di modifica dell'area di lavoro [#workspace-edit-matching-and-conflicts]

`edit_file` accetta un `replace_all` di primo livello per una singola sostituzione `old_text`/`new_text`, oppure un flag per singola voce quando viene fornito un batch di `edits`. Senza di esso, ogni `old_text` deve risolversi in una singola posizione. Un batch fornito deve essere non vuoto e valido; LibreChat rifiuta un valore `edits` vuoto o malformato invece di ripiegare sui campi di sostituzione di primo livello. I batch in formato JSON stringificato e i flag di sostituzione booleani validi vengono normalizzati prima dell'approvazione nativa dello strumento, in modo che l'anteprima e l'esecuzione utilizzino le stesse modifiche canoniche, incluse le riscritture degli hook revisionati. Le modifiche a skill-file e managed-sandbox supportano la sostituzione di tutte le corrispondenze entro i limiti di dimensione e numero di corrispondenze di LibreChat; gli workspace allegati richiedono un worker che supporti `replace_all` e rifiutano le richieste non supportate prima dell'invio.

Sui worker collegati che pubblicizzano `tolerant_match`, le modifiche e le anteprime protette tentano prima la corrispondenza esatta, poi strategie tolleranti agli spazi bianchi per spazi finali, CRLF, spostamenti di rientro o spazi bianchi normalizzati. Gli amministratori possono richiedere corrispondenze esatte con [`configSchema.edits.tolerantMatching: false`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions). I messaggi di successo identificano la corrispondenza non esatta o le sostituzioni multiple. I batch falliti sono atomici: non viene scritto nulla e LibreChat riporta motivi limitati per singola modifica, conteggi, numeri di riga candidati o un avviso di file modificato senza inoltrare testo arbitrario del worker o estratti di file.

Queste funzionalità di attached-worker richiedono una Code API compatibile e build di worker che implementino [Code Interpreter #271](https://github.com/LibreChat-AI/code-interpreter/pull/271). LibreChat invia i nuovi campi solo dopo la negoziazione delle funzionalità. Con le build meno recenti, il formato della richiesta e il comportamento di corrispondenza rimangono invariati; il solo aggiornamento di LibreChat non abilita le modifiche tolleranti (tolerant attached edits) o `replace_all`.

#### Autorizzazioni degli strumenti dell'ambiente collegato [#attached-environment-tool-permissions]

Gli ambienti allegati e personali utilizzano una policy di approvazione "chiedi per impostazione predefinita" per la scrittura di file e l'esecuzione di comandi o codice. Le operazioni di sola lettura e di ricerca continuano a seguire la normale policy degli strumenti della distribuzione. Se l'amministratore espone una delle due categorie tramite [`configSchema.permissions`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions), gli utenti con autorizzazione di gestione di Code Environment possono scegliere tra i valori consentiti **Allow**, **Ask** o **Deny** in **Settings > Code environments**. Le impostazioni mancanti, non aggiornate o non consentite ripiegano in sicurezza su **Ask**.

Il composer mostra una **Modalità di approvazione del codice** a livello di conversazione ogni volta che l'ambiente allegato selezionato la supporta:

- **Ask before changes** chiede conferma prima di modifiche ai file o comandi.
- **Accept edits** consente le modifiche ai file, ma continua a chiedere conferma prima di eseguire i comandi.
- **Accesso completo** consente entrambe le categorie senza prompt di routine.

La modalità selezionata accompagna tale conversazione e viene incrociata con i valori consentiti dalla distribuzione e con la policy dell'ambiente. **Full access** appare solo quando sia `fileWrite` che `commandExecution` consentono `allow`; non aggira l'isolamento della sandbox, le concessioni di ruolo, le regole esplicite di `ask` o `deny` dell'endpoint, la conferma dei file Skill o gli hook di approvazione.

Un'importazione di conversazione non può selezionare una modalità di approvazione del codice per il suo destinatario. Le nuove conversazioni importate o copiate in blocco utilizzano la preferenza/impostazione predefinita del destinatario secondo la policy corrente; gli aggiornamenti in blocco preservano qualsiasi scelta archiviata localmente. Le conversazioni esistenti non vengono reimpostate retroattivamente e la selezione esplicita di una modalità in LibreChat la mantiene comunque.

Questi controlli coprono gli strumenti di creazione file, l'esecuzione di shell e codice, i controlli di compilazione e la Programmatic Tool Calling. Le scritture su file Skill persistenti richiedono comunque una conferma quando la creazione di Skill è abilitata, anche quando le normali scritture su file sono consentite. Le impostazioni non modificano l'isolamento della VM, il networking, i mount, l'esecuzione privilegiata, l'ingresso, l'uscita o l'accesso ai segreti.

L'impostazione esplicita [`toolApproval.enabled: false`](/docs/configuration/librechat_yaml/object_structure/agents#toolapproval) della distribuzione è un override di emergenza che disabilita questa base di riferimento. Senza tale override, un chiamante che non è in grado di presentare e riprendere le richieste di approvazione fallisce con chiusura (fails closed) invece di eseguire silenziosamente uno strumento in un ambiente collegato.

L'accoppiamento autentica il trasporto del worker remoto; non costituisce un confine di sandbox. Mantieni l'endpoint di esecuzione locale del worker su loopback o su una rete privata e utilizza una modalità di isolamento appropriata per il codice non attendibile.

Mentre un'esecuzione è attiva, i riquadri dei dettagli del codice espanso e della shell seguono gli argomenti trasmessi verso il basso. Lo scorrimento verso l'alto mette in pausa il comportamento di inseguimento, consentendoti di esaminare l'output precedente senza che il riquadro sposti la visualizzazione.

## Utilizzo dell'API [#using-the-api]

### In LibreChat [#in-librechat]

L'API ha un supporto di prima classe in LibreChat attraverso questi metodi principali:

1. **[AI Agents](/docs/features/agents#code-interpreter)**: Abilita Code Interpreter nella configurazione del tuo agente per consentirgli di eseguire codice ed elaborare file automaticamente.

2. **Esecuzione manuale**: Utilizza il pulsante "Run Code" nei blocchi di codice all'interno dell'interfaccia di chat, come mostrato qui:

3. **[Programmatic Tool Calling](/docs/features/agents#programmatic-tool-calling)**: Abilita la funzionalità `programmatic_tools` e contrassegna gli strumenti MCP selezionati come Programmatic in modo che gli agenti possano orchestrare tali strumenti da codice in sandbox.

4. **[Background Tool Calls](/docs/features/agents#background-tool-calls)**: Consenti a un agente di inviare codice idoneo in background e di continuare mentre viene eseguito.

5. **[Stateful Code Sessions](/docs/features/agents#stateful-code-sessions)**: Riutilizza in via sperimentale un workspace con ambito utente, agente-e-utente o conversazione durante le esecuzioni di codice di un agente.

![Code Interpreter in LibreChat](/images/agents/run_code.png)

### Configura la chiave API [#set-up-api-key]

- **Configurazione per utente:** Inserisci la tua chiave API in LibreChat quando richiesto.
- **Configurazione globale:** Imposta `LIBRECHAT_CODE_API_KEY` nel file `.env` di LibreChat per fornire una chiave unica per tutti gli utenti.

L'attuale servizio [ClickHouse/code-interpreter](https://github.com/ClickHouse/code-interpreter) utilizza l'autenticazione JWT di LibreChat al di fuori della modalità locale. Le chiavi API rimangono disponibili per distribuzioni di Code Interpreter compatibili.

### Autenticazione JWT self-hosted [#self-hosted-jwt-authentication]

Con l'autenticazione JWT, LibreChat firma un bearer token a breve durata per l'utente autenticato a ogni richiesta di Code Interpreter. Il servizio Code Interpreter verifica la chiave pubblica corrispondente e utilizza il contesto dell'utente e del tenant firmato per isolare file e sessioni. La chiave di firma privata rimane in LibreChat; Code Interpreter riceve solo il suo verificatore pubblico.

Configura LibreChat con:

```env
CODEAPI_AUTH_PROVIDER=librechat-jwt
CODEAPI_JWT_PRIVATE_KEY="-----BEGIN PRIVATE KEY-----\n...\n-----END PRIVATE KEY-----"
CODEAPI_JWT_ALGORITHM=EdDSA
CODEAPI_JWT_KID=lc-codeapi-2026-05
CODEAPI_JWT_ISSUER=librechat
CODEAPI_JWT_AUDIENCE=codeapi
CODEAPI_JWT_TTL_SECONDS=300
CODEAPI_JWT_MINT_CACHE_SECONDS=30
CODEAPI_JWT_SINGLE_TENANT_ID=legacy
```

`CODEAPI_JWT_PRIVATE_KEY_BASE64` può contenere invece un PEM codificato in base64, e `CODEAPI_JWT_PRIVATE_JWK_JSON` accetta una JWK privata. LibreChat supporta la firma Ed25519 (`EdDSA`, l'impostazione predefinita) e RSA (`RS256`). Consulta il [riferimento delle variabili d'ambiente](/docs/configuration/dotenv#code-interpreter-jwt-authentication) per ogni impostazione lato LibreChat.

Configura Code Interpreter con il verifier corrispondente:

```env
LOCAL_MODE=false
CODEAPI_AUTH_PROVIDER=librechat-jwt
CODEAPI_JWT_ISSUER=librechat
CODEAPI_JWT_AUDIENCE=codeapi
CODEAPI_JWT_ALLOWED_ALGS=EdDSA
CODEAPI_JWT_JWKS_JSON={"keys":[{"kty":"OKP","crv":"Ed25519","x":"...","kid":"lc-codeapi-2026-05","alg":"EdDSA"}]}
CODEAPI_JWT_SINGLE_TENANT_ID=legacy
```

L'issuer, l'audience, il key ID, l'algoritmo e la chiave pubblica devono corrispondere al signer di LibreChat. Code Interpreter può anche caricare le chiavi del verificatore da `CODEAPI_JWT_PUBLIC_KEY` più `CODEAPI_JWT_KID`, oppure da `CODEAPI_JWT_PUBLIC_KEYS_DIR`; un JWKS inline è comodo per la rotazione. Mantieni il TTL del token uguale o inferiore a `CODEAPI_JWT_MAX_TTL_SECONDS` del servizio Code Interpreter, che è impostato per impostazione predefinita e limitato a 300 secondi.

Per un checkout locale, il repository Code Interpreter include un helper che genera chiavi di firma Ed25519 e di execution-manifest corrispondenti e aggiorna entrambi i file `.env`:

```bash
node scripts/setup-local-auth-env.js --librechat /path/to/LibreChat
```

Le distribuzioni single-tenant possono lasciare `CODEAPI_JWT_SINGLE_TENANT_ID=legacy`, ma il valore deve corrispondere su entrambi i servizi. Le distribuzioni multi-tenant dovrebbero fornire un contesto tenant autenticato e abilitare `TENANT_ISOLATION_STRICT=true` in LibreChat oltre a `CODEAPI_TENANT_ISOLATION_STRICT=true` in Code Interpreter. La modalità rigorosa (strict mode) rifiuta le richieste prive di contesto tenant invece di utilizzare il fallback single-tenant.

### Integrazione API Diretta [#direct-api-integration]

Il servizio self-hosted corrente richiede un bearer token che soddisfi il contratto di claim JWT di LibreChat. Un'integrazione diretta deve generare token a breve durata compatibili e inviarli nell'header `Authorization: Bearer <token>`. Le distribuzioni compatibili con API-key accettano invece la chiave configurata nell'header `x-api-key`. Non utilizzare mai la modalità locale senza autenticazione di Code Interpreter su un endpoint pubblico o di produzione.

### URL di base self-hosted [#self-hosted-base-url]

Imposta `LIBRECHAT_CODE_BASEURL` per puntare LibreChat alla tua istanza di [code-interpreter](https://github.com/ClickHouse/code-interpreter) self-hosted, quindi configura l'[autenticazione JWT](#self-hosted-jwt-authentication). Per un servizio compatibile con API-key, imposta invece `LIBRECHAT_CODE_API_KEY`. Le sessioni Agent stateful, in uno stato altamente sperimentale, richiedono una rotta `stateful`-profile separata configurata tramite [`LIBRECHAT_CODE_BASEURL_STATEFUL`](/docs/configuration/dotenv#stateful-code-interpreter-endpoint) o denominata [`statefulCodeSessions.environments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions).

## Funzionalità principali [#core-functionality]

### Esecuzione del codice [#code-execution]

- Esegui snippet di codice nei linguaggi supportati
- Ricevi l'output stdout/stderr
- Ottieni statistiche di esecuzione (utilizzo della memoria, tempo CPU)
- Gestione degli argomenti del programma
- Accedi allo stato di esecuzione e ai risultati

### Operazioni sui file [#file-operations]

- Caricamento file di input
- Scarica gli output generati
- Visualizza in anteprima i file Office generati, inclusi le presentazioni PowerPoint `.pptx` e i modelli `.potx`, oltre a CSV, testo e artefatti simili a PDF inline quando LibreChat è in grado di estrarli/renderizzarli in sicurezza
- Visualizza immagini PNG, JPEG, GIF e WebP restituite dallo strumento `read_file` di un Agent come artefatti visualizzabili
- Elenca i file disponibili
- Elimina i file non necessari
- Gestisci le sessioni dei file

Le anteprime degli artefatti generati sono intenzionalmente limitate nelle dimensioni. Imposta [`FILE_PREVIEW_MAX_EXTRACT_BYTES`](/docs/configuration/dotenv#inline-file-previews) nel file `.env` di LibreChat per modificare il limite di dimensione del file sorgente per l'estrazione dell'anteprima in linea; i file più grandi rimarranno disponibili per il download.

Le immagini della Sandbox restituite tramite `read_file` hanno un limite inline di 1 MiB. Le immagini più grandi rimangono nella sandbox per l'elaborazione con `bash_tool`. `LIBRECHAT_CODE_IMAGE_CHUNK_BYTES` controlla solo la dimensione del chunk di trasporto utilizzato durante la lettura delle immagini idonee; non aumenta il limite inline.

<Callout type="warning" title="Controllo aggiornamento per output di codice legacy">
  Le distribuzioni che hanno rigenerato lo stesso nome file di Code Interpreter prima dell'aggiunta dell'indice univoco per i file di output potrebbero presentare record MongoDB duplicati che impediscono la creazione dell'indice. Visualizza un'anteprima della riparazione con `npm run migrate:code-file-duplicates:dry-run`, quindi applicala con `npm run migrate:code-file-duplicates`. La migrazione mantiene il nome file canonico più recente, rinomina i record più vecchi con suffissi numerici e crea l'indice univoco dopo un'esecuzione corretta.
</Callout>

### Limitazioni [#limitations]
- Il codice non può accedere alla rete
- È possibile generare solo 10 file per esecuzione
- I limiti delle risorse (RAM per esecuzione, dimensione del caricamento file e quote di richiesta) dipendono da come si esegue il provisioning e la configurazione del proprio deployment.

## Open Source & Self-Hosting [#open-source--self-hosting]

Il servizio Code Interpreter è open source sotto licenza Apache 2.0 su [ClickHouse/code-interpreter](https://github.com/ClickHouse/code-interpreter). Mantenere l'esecuzione del codice come servizio separato mantiene l'applicazione core LibreChat leggera: distribuisci l'infrastruttura sandbox solo quando ne hai bisogno e puoi scalarla indipendentemente dall'applicazione di chat.

Il servizio viene eseguito come un insieme di componenti scalabili in modo indipendente (un API gateway, worker in sandbox e un file server) e supporta modalità di isolamento avanzate (NsJail o una microVM tramite libkrun) in modo da poter eseguire codice non attendibile in sicurezza. Consulta il README del repository per le istruzioni di distribuzione con Docker Compose e Helm.
