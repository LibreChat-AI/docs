**RAG（Retrieval-Augmented Generation）API** は、LibreChat にアップロードされたファイルをインデックス化し、質問に関連性の高い箇所を返す独立したサービスです。これにより、モデルは学習データだけでなく、お手持ちのドキュメントに基づいて回答できるようになります。

これは LangChain 上に構築された Python FastAPI アプリで、埋め込みベクトルは pgvector 拡張機能を備えた PostgreSQL に保存されます。

**設定方法については、[RAG API の構成](/docs/configuration/rag_api)を参照してください。**

LibreChatでは、RAGは[エージェント](/docs/features/agents#file-search)の**ファイル検索**機能(`file_search`)を支えています。エージェントのファイル検索に添付されたファイル、またはファイル検索を選択した実行に添付されたファイルは、RAG APIによってインデックス化され、必要に応じて検索されます。他のチャットエンドポイントではRAGのインデックス作成や検索は使用されませんが、後述するとおり、テキスト抽出のためにRAG APIを使用する場合があります。

RAG API は、LibreChat がアップロードファイルからテキストを抽出するために使用できる `/text` ルートも公開しています。適用されるタイミングについては、[Upload as Text](/docs/features/upload_as_text#what-happens-under-the-hood) を参照してください。

## 仕組み [#how-it-works]

1. **インデックス作成。** ファイルを検索可能にする必要がある場合（エージェントの File Search へのアップロード時、または最初にチャットの実行で File Search が添付ファイルに使用される時）、LibreChat はファイルを RAG API に送信します。RAG API はテキストを重複を含むチャンクに分割し（`CHUNK_SIZE` と `CHUNK_OVERLAP`）、設定されたプロバイダーを使用して各チャンクをエンベディングに変換し、そのベクトルを pgvector に保存します。
2. **検索（Retrieval）。** モデルがファイル検索を呼び出すと、検索クエリを作成します。LibreChat は RAG API に対し、添付された各ファイルから最も近い 5 件のチャンクを要求し、その後、全体で最も近い 10 件を保持します。
3. **回答。** それらのチャンクは、ファイル名と関連性スコアとともにモデルに返され、モデルはそれに基づいて回答します。[ファイル引用](/docs/configuration/librechat_yaml/object_structure/interface#filecitations)が有効になっている場合、レスポンスで使用したファイルを引用することができます。

LibreChatでファイルを削除すると、そのベクトルもRAG APIから削除されます。

検索は、クエリと意味的に近い箇所だけを見つけ出すため、大規模な文書の中から特定の事実を調べる場合に最も効果を発揮します。文書全体を一度に必要とする質問、たとえば要約のような場合は、[Upload as Text](/docs/features/upload_as_text) の方がより良い結果が得られることが多いです。

## RAGとは？ [#what-is-rag]

Retrieval-Augmented Generation（RAG）は、言語モデルを外部の知識ソースに基づかせる手法です。モデルが学習時に得た知識だけに頼るのではなく、アプリケーションがまず当該ソースから関連する断片を検索し、それをプロンプトに追加します。そのうえでモデルは、それらの情報をもとに回答を生成します。知識はモデルの外部に置かれるため、再学習を行うことなく、文書の追加や更新が可能です。
