## 소개 [#introduction]

LibreChat의 Code Interpreter API는 간단한 API 인터페이스를 통해 코드를 실행하고 파일을 관리할 수 있는 안전하고 간편한 방법을 제공합니다. LibreChat의 Agents를 통해 사용하든 애플리케이션에 직접 통합하든, 이 API는 여러 프로그래밍 언어로 코드를 실행할 수 있는 강력한 샌드박스 환경을 제공합니다.

## 시작하기 [#getting-started]

1. [code-interpreter](https://github.com/ClickHouse/code-interpreter) 서비스를 배포하세요(Docker Compose 또는 Helm 사용, 저장소의 README 참조)
2. `LIBRECHAT_CODE_BASEURL`을 사용하여 LibreChat이 해당 경로를 가리키도록 설정하세요.
3. 현재 오픈 소스 서비스를 위해 [LibreChat JWT authentication](#self-hosted-jwt-authentication)을 구성하거나, API 키 호환 배포를 위해 `LIBRECHAT_CODE_API_KEY`를 설정하세요.
4. 상태 유지(stateful) 에이전트 세션을 실험하려면 별도의 `stateful` 프로필 Code Interpreter 경로를 배포하고 `LIBRECHAT_CODE_BASEURL_STATEFUL` 또는 명명된 [`statefulCodeSessions.environments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions)를 구성하세요.
5. LibreChat의 에이전트 또는 "Run Code" 버튼을 통해 안전하게 코드를 실행하고 파일을 생성하세요.

## 주요 기능 [#key-features]

### 지원되는 언어 [#supported-languages]

여러 프로그래밍 언어로 코드 실행:

- Python, Node.js (JS/TS), Go, C/C++, Java, PHP, Rust, Fortran, Rscript

### 원활한 파일 처리 [#seamless-file-handling]

- 처리를 위해 파일 업로드
- 생성된 출력물 다운로드
- 안전한 파일 관리
- 세션 기반 파일 구성

LibreChat은 에이전트 실행 전에 참조된 대화 파일을 관리형 Code Interpreter 환경으로 복원합니다. 필요한 모든 Code Interpreter 파일의 복구에 실패하면, 실행은 모델 호출 전에 중단되며 사용자에게 오래된 참조로 계속 진행하는 대신 파일을 다시 첨부하도록 요청합니다. 선택된 첨부 작업 공간에서 채팅 업로드는 사용자의 작업 공간으로 복사되지 **않으며**, 작업 공간 파일 및 Bash 도구는 해당 위치에서 파일을 열 수 없습니다. 워커가 파일 릴레이와 함께 Programmatic Bash를 알리는 경우, 해당 도구는 실행 기간 동안 `$LIBRECHAT_CODE_DATA_DIR` 아래에 스테이징된 업로드를 대신 확인합니다.

Code API 업로드는 `Retry-After`를 준수하고, 각 시도마다 소스 스트림을 다시 열며, 제한된 대기 예산을 공유함으로써 `429` 속도 제한으로부터 복구합니다. 관리자는 [`codeApiUploadConcurrency` 및 `codeApiMaxRetryWaitMs`](/docs/configuration/librechat_yaml/object_structure/agents#code-api-upload-recovery)를 사용하여 사용자별, 경로별 복구 설정을 조정할 수 있습니다.

대화 입력이 동일한 샌드박스 대상에 마운트될 때, LibreChat은 실행 전에 충돌을 해결합니다. 공유 대화 파일은 에이전트 전용 파일보다 먼저 할당되며, 각 범위 내에서 가장 최신 콘텐츠 쓰기가 원래 대상을 유지합니다. 충돌하는 경로는 필요에 따라 평탄화되거나 식별자 기반의 접미사가 추가되며, 해결된 `/mnt/data/...` 경로는 에이전트의 파일 컨텍스트에 포함됩니다. 이는 동일한 파일 이름을 공유하는 업로드와 생성된 출력에도 적용되므로, 하나의 충돌로 인해 대화 내의 이후 모든 Code Interpreter 실행이 거부되지 않습니다. 이미 점유된 대상으로 확인되는 중복 시드 참조는 전체 요청을 실패하게 만드는 대신 건너뜁니다.

샌드박스 이미지는 제한된 윈도우 내에서 전송됩니다. [`LIBRECHAT_CODE_SANDBOX_OUTPUT_MAX_SIZE`](/docs/configuration/dotenv#code-interpreter)를 워커의 `SANDBOX_OUTPUT_MAX_SIZE`와 일치하도록 설정하세요. LibreChat은 해당 예산에서 가장 안전한 최대 이미지 윈도우를 도출하며, 읽기 실패가 한 번 발생하면 더 작은 서비스별 제한을 학습할 수 있습니다. 정확한 윈도우 재정의가 필요한 경우에만 `LIBRECHAT_CODE_IMAGE_CHUNK_BYTES`를 사용하세요. 이전에 다운로드한 생성 아티팩트는 가능한 경우 요청 내에서 재사용되어, 샌드박스를 다시 읽는 과정을 방지합니다.

다중 에이전트 그래프(multi-Agent graph)에서는 서로 다른 에이전트가 사용하는 비공개 파일에 고유한 파일 이름을 지정하십시오. 각 에이전트는 그래프가 입력을 결합하기 전에 자신의 비공개 파일 경로를 확인하므로, 독립적으로 동일한 대상 경로를 사용하는 서로 다른 비공개 파일은 병합 시점에 일관되게 이름을 변경할 수 없습니다. 따라서 먼저 시드(seeded)된 대상 경로가 우선권을 갖습니다.

### 보안 및 편의성 [#security--convenience]

- 안전한 샌드박스 실행 환경
- 강력한 격리 모드 (NsJail 또는 libkrun을 통한 microVM)
- 최종 사용자에게는 로컬 설정이 필요하지 않습니다
- 세션 기반의 격리된 파일 저장소

### Programmatic Tool Calling [#programmatic-tool-calling]

Programmatic Tool Calling을 사용하면 LibreChat 에이전트가 선택된 MCP 도구를 Code Interpreter 샌드박스를 통해 라우팅할 수 있습니다. 모델에게 각 도구를 직접 호출하도록 요청하는 대신, LibreChat은 Code Interpreter 기반의 오케스트레이션 도구를 제공합니다. 생성된 샌드박스 코드는 등록된 도구 스텁을 호출하고, 루프와 조건문을 사용하며, 중간 결과를 처리하고, 최종 답변을 반환할 수 있습니다.

샌드박스는 여전히 일반적인 네트워크 액세스를 수신하지 않습니다. 도구 호출은 Code Interpreter Tool Call Server를 통해 중개됩니다. LibreChat은 실시간 호출자 기능 프로젝션을 신뢰할 수 있는 레지스트리와 교차 검사하므로, 에이전트에 이미 등록된 활성 프로그래밍 도구만 호출할 수 있으며 요청이 자체적으로 액세스 권한을 확장할 수는 없습니다.

프로그래밍 방식 도구(Programmatic tools)를 사용하려면 에이전트에서 Code Interpreter가 활성화되어 있어야 합니다. Code Interpreter를 선택하기 전까지 해당 토글은 비활성화 상태로 유지되며, Code Interpreter를 제거하면 기존에 선택된 프로그래밍 방식 도구 설정이 초기화됩니다. 또한 LibreChat은 `execute_code` 또는 Code Interpreter 도구를 사용할 수 없는 경우, 에이전트 생성, 업데이트, 복제 및 버전 복원 작업에서 유효하지 않은 프로그래밍 방식 호출자 옵션을 제거합니다.

프로그래밍 방식의 실행 중에 Code Interpreter 카드를 확장하면, 제한된 인수 미리보기, 상태, 지속 시간 및 실패가 포함된 내부 도구 호출의 실시간 터미널 스타일 추적을 확인할 수 있습니다. 이 추적은 프로그램이 실행되는 동안 프로그램을 검사하는 데 도움이 되지만, 페이지를 새로 고치면 유지되지 않습니다.

### Background Code Execution [#background-code-execution]

백그라운드 실행을 통해 에이전트는 장시간 실행되는 코드나 셸 작업을 전달하고 대화를 계속할 수 있습니다. 저장된 에이전트의 경우, 지원되는 콘텐츠 전용 완료(content-only completions)는 기본적으로 후속 연속 대화에서 자동으로 전달됩니다. `check_background_task`는 명시적인 상태 확인, 제어, 실시간 아티팩트 및 복구를 위해 계속 사용할 수 있습니다. LibreChat 채팅에서 작업이 완료되면 stdout과 생성된 파일이 원래 코드 호출에 나타나며 이후 턴을 위해 유지됩니다. 백그라운드 완료 및 명시적 확인은 상태, 전달 상태 및 읽기 가능한 결과가 포함된 작업 카드를 렌더링하며, 정확한 원본 결과는 복사할 수 있도록 유지됩니다. 채팅 헤더는 실행 중인 작업과 최근 작업을 그룹화하며, 배포의 취소 정책에 따라 허용되는 경우 개별 또는 전체 중지 제어 기능을 제공합니다.

이 기능은 배포 수준에서 선택적으로 사용할 수 있습니다. [Agents endpoint capabilities](/docs/configuration/librechat_yaml/object_structure/agents#capabilities)의 `execute_code`와 함께 `run_in_background`를 추가한 다음, 에이전트에서 Code Interpreter를 활성화하세요. 코드 실행 및 셸 호출은 자동으로 백그라운드 실행 대상이 됩니다. 에이전트가 이를 사용하지 않도록 하려면 Code Interpreter 도구 설정에서 **Background execution**을 끄십시오. 모델은 여전히 호출 시마다 적격한 작업을 백그라운드에서 처리할지 여부를 결정합니다.

일반적인 백그라운드 실행은 프로세스 로컬 상태로 유지되며 앱 워커가 종료되면 함께 소멸합니다. 콘텐츠 전용 터미널 결과가 영구 저장되면 해당 자동 전달은 내구성을 갖게 되며 다른 복제본에서 계속될 수 있습니다. 라이브 아티팩트가 포함된 작업은 여전히 소유 실행(owning run)에 대한 폴링이 필요합니다. 모든 결과에 대해 폴링을 요구하려면 [`endpoints.agents.backgroundTasks.completionWakeups: false`](/docs/configuration/librechat_yaml/object_structure/agents#backgroundtasks)를 설정하십시오. 백그라운드 디스패치는 Code Interpreter 서비스의 실행 제한을 확장하지 않으며, 배포의 일반적인 서버 측 타임아웃이 여전히 적용됩니다.

[`ordinaryToolCancellation: true`](/docs/configuration/librechat_yaml/object_structure/agents#backgroundtasks)를 설정하면, 소유자는 첨부된 Bash를 포함한 일반적인 백그라운드 Code 도구의 협력적 취소를 요청할 수 있습니다. 작업은 호출이 완료될 때까지 활성 상태로 유지되며 용량을 소비합니다. 취소 요청을 무시하는 도구는 계속해서 완료될 수 있습니다.

### 상태 유지 코드 세션 (Stateful Code Sessions) [#stateful-code-sessions]

Stateful code sessions을 사용하면 LibreChat Agent가 실행 간에 하나의 Code Interpreter 샌드박스 작업 공간을 재사용할 수 있습니다. 파일, 설치된 패키지 및 작업 상태가 일반적으로 유지되므로 반복적인 분석과 다단계 파일 생성이 더 효율적입니다. 각 에이전트는 다음 중 하나의 작업 공간 범위를 선택합니다:

- **사용자 작업 공간(권장):** 상태 유지(stateful)가 활성화된 에이전트 전반에서 로그인한 사용자를 위한 단일 작업 공간
- **에이전트 + 사용자 작업 공간:** 각 사용자와 에이전트 조합을 위한 하나의 작업 공간
- **대화 작업 공간:** 각 사용자와 대화마다 하나의 작업 공간

새로 생성된 Agent의 경우, 초기 범위는 **Settings > Data Controls > Code execution > Default stateful workspace**에서 설정됩니다. 개인 설정의 기본값은 **User workspace**이며, 이를 변경해도 기존 Agent가 수정되거나 상태 저장 세션이 활성화되지는 않습니다. 배포 관리자는 [`statefulCodeSessions.allowedEnvironments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions)를 사용하여 선택 가능한 범위를 제한할 수 있습니다. 저장된 개인 기본값을 사용할 수 없게 되면, 새 Agent는 허용된 첫 번째 범위를 사용합니다. 허용되지 않는 범위로 설정된 기존 활성 Agent는 실행하기 전에 재구성해야 합니다.

작업 공간(workspace) 범위는 실행 백엔드와 분리되어 있습니다. 관리자가 명명된 [`statefulCodeSessions.environments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions)를 구성하면, Agent Builder에 **실행 환경(Execution environment)** 선택기가 추가됩니다:

- **Managed:** 배포에 의해 운영되는 상태 저장(stateful) Code API
- **첨부됨:** 운영자가 관리하는 VM과 같이 아웃바운드 `@librechat/code` 워커에 작업을 위임하는 호환 가능한 Code API 원격 브리지
- **개인용:** LibreChat 설정에서 인증된 사용자가 연결한 소유자 전용 `@librechat/code` 워커
- **배포 기본값:** 기본값으로 표시된 구성된 환경 하나

<Callout type="warning" title="매우 실험적인 기능">
  Stateful Code Sessions는 초기 실험 단계에 있습니다. 해당 기능의 동작, 구성, 지속성 특성 및 기반 통합 방식은 크게 변경될 수 있습니다. 현재 구현을 안정적인 프로덕션 계약으로 간주하지 마십시오.
</Callout>

이 기능은 선택 사항입니다. [Agents endpoint capabilities](/docs/configuration/librechat_yaml/object_structure/agents#capabilities)에서 `execute_code` 및 `stateful_code_sessions`를 활성화하고, [`LIBRECHAT_CODE_BASEURL_STATEFUL`](/docs/configuration/dotenv#stateful-code-interpreter-endpoint) 또는 명명된 환경으로 전용 상태 저장 경로를 구성한 다음, 에이전트에서 Code Interpreter를 활성화하십시오. 그 후 고급 설정에서 **Stateful code sessions**를 켜고 실행 백엔드와 작업 공간 범위를 선택하십시오.

Stateful 요청은 선택된 환경이 누락되었거나, 액세스할 수 없거나, 호환되지 않을 경우 실패하며(fail closed); LibreChat은 이를 `LIBRECHAT_CODE_BASEURL`로 전송하거나 다른 명명된 백엔드를 자동으로 선택하지 않습니다. 명명된 환경이 구성되어 있지 않은 경우, `LIBRECHAT_CODE_BASEURL_STATEFUL`이 계속해서 stateful 경로로 유지됩니다. Stateless 에이전트는 일반 endpoint를 계속 사용합니다. 또한 LibreChat은 `X-CodeAPI-Expected-Profile: stateful` 헤더를 전송하므로, 전용 서비스는 반드시 `stateful` 프로필을 광고해야 합니다.

Stateful 및 stateless 세션은 라이브 워크스페이스를 공유하지 않습니다. Stateful 워크스페이스는 선택된 범위와 관계없이 언제든지 초기화될 수 있습니다. 관리형 Code Interpreter 환경에서는 중요한 출력물을 `/mnt/data` 아래에 저장해야 하며, 그 외의 경우에는 세션 상태를 영구 저장소로 의존하지 마십시오. 연결된 워크스페이스는 별도의 워커 소유 디렉터리이며, 업로드된 파일은 기본적으로 해당 위치에 배치되지 않습니다.

상태 유지형 `create_file` 및 `edit_file` 호출로 작성된 파일은 어시스턴트 메시지 아래의 확장 가능한 **Workspace changes** 행에 나타납니다. 이 행은 해당 응답에 대해 변경된 각 고유 경로를 나열하고 인증된 다운로드 작업을 제공합니다. 다운로드는 사용 가능한 경우 LibreChat의 지속적 파일 흐름을 사용하며, 그렇지 않은 경우 보안 Code Interpreter 대체 기능을 사용합니다. 이 행은 작성된 출력의 기록이며 영구적인 작업 공간 스냅샷이 아닙니다. 상태 비저장 출력은 계속해서 일반 인라인 첨부 파일로 표시됩니다.

#### 연결된 환경 및 페어링 [#attached-environments-and-pairing]

연결된 환경에는 일치하는 실험적 Code Interpreter remote-bridge 빌드가 필요합니다. 브리지는 LibreChat의 인증된 정책, 대기열 및 결과 경계로 유지되며, `@librechat/code` 워커는 연결된 머신에서 아웃바운드로 연결됩니다. 머신에 인바운드 공용 워커 포트가 필요하지는 않습니다. LibreChat은 연결된 환경을 미리 예열(prewarm)하지 않습니다.

운영자는 배포 소유의 연결된 환경을 `workerId`를 사용하여 특정 워커에 고정할 수 있으며, LibreChat이 해당 경로에 대해 관리자 페어링 코드를 발급해야 할 때 `pairing.workerId`를 추가할 수 있습니다. `pairing.tokenEnv`는 브리지 관리자 토큰이 포함된 환경 변수의 이름을 지정하며, 비밀 값 자체는 절대 YAML에 포함되어서는 안 됩니다. 페어링된 컨트롤 플레인은 루프백 개발 환경 외부에서 HTTPS를 요구합니다.

셀프 서비스 워커의 경우, `pairing.allowPrincipalWorkers: true` 및 `pairing.tokenEnv`를 사용하여 배포 소유의 연결된 제어 평면(control plane)을 구성하십시오. 이는 워커 ID를 모두 생략하고 등록 전용 제어 평면으로만 존재할 수 있습니다. 이러한 항목은 실행 대상으로 선택할 수 없으며 배포 기본값으로 설정할 수 없습니다.

Code Environment 관리 권한이 있는 사용자는 **Settings > Code environments**를 열어 환경 이름을 지정하고, 승인된 컨트롤 플레인을 선택한 다음 **Connect VM**을 선택할 수 있습니다. LibreChat은 짧은 시간 동안만 유효한 일회성 `librechat-code pair ...` 명령어를 표시합니다. 이 명령어를 사용자의 VM에서 실행한 다음, `LIBRECHAT_CODE_SANDBOX_ENDPOINT`가 해당 머신의 샌드박스 서비스를 가리키도록 설정하여 `@librechat/code`를 시작하세요. UI에는 사용자의 환경 목록이 표시되며, 나중에 이를 취소하거나 제거할 수 있습니다. 샌드박스 파일은 VM에 그대로 유지됩니다.

관리자는 [`statefulCodeSessions.principalWorkers`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions)를 통해 등록을 제한할 수 있습니다. 이 블록이 생략되면 등록은 기본적으로 활성화되며, 사용자당 최대 5개의 환경을 등록할 수 있습니다. 이 수에는 모든 제어 평면(control plane)의 오프라인 워커가 포함됩니다. 배포 구성이 상한선 역할을 합니다. 즉, 주체별(principal-specific) 구성으로 이를 낮추거나 비활성화할 수는 있지만, 상한선을 높일 수는 없습니다. 정책을 강화하더라도 이미 등록된 머신이 해지되지는 않습니다.

개인 환경은 인증된 사용자 및 테넌트에 귀속되며, Code Environment ACL에 의해 보호되고, 서버에서 검증된 ID와 승인된 기본 URL만 할당받습니다. LibreChat은 브리지 관리자 토큰이나 임의의 운영자 URL을 클라이언트에 노출하지 않습니다. 환경을 제거하면 레지스트리 항목을 삭제하기 전에 작업자 자격 증명이 취소되며, 사용자 삭제 시에도 동일한 취소 및 정리 작업이 예약되고 중단된 시도에 대해서는 백그라운드 조정이 수행됩니다. 선택된 작업자 경로는 Code Interpreter, 셸, 생성된 파일 액세스 및 프로그래밍 방식 도구 호출(Programmatic Tool Calling)에 일관되게 적용됩니다.

첨부된 워크스페이스를 사용하는 에이전트는 해당 디렉터리 트리를 나열하고, 파일을 읽고, 파일 내용을 검색하고, 파일을 생성하거나 편집하며, 선택된 워커에서 Bash를 실행할 수 있습니다. 파일 인용은 워크스페이스 상대 경로를 사용하며, 작성된 파일은 응답의 **Workspace changes** 행에 나타나고, 도구 실패 시 워커의 제한된 HTTP 진단 정보가 보존됩니다. 에이전트는 해당 워크스페이스에서 생성된 커밋을 위해 에이전트별 Git 이름과 이메일을 저장할 수도 있습니다. 이 값들은 작성자 정보만 구성하며 저장소 자격 증명을 제공하지는 않습니다.

채팅에서 실패한 워크스페이스 연결 Bash 명령은 종료 코드, 종료 신호 또는 타임아웃을 표시하며, stderr은 stdout과 별도로 스타일이 지정됩니다. Bash 출력이 표시되는 방식에 대한 자세한 내용은 [Activity Groups](/docs/features/agents#activity-groups)를 참조하세요.

연결된 워커는 자신이 제공하는 작업 공간 루트를 알립니다. 컴포저(composer)를 통해 사용자는 에이전트나 그 하위 에이전트를 통해 접근 가능한 각 연결된 환경에 대해 하나의 작업 공간을 선택할 수 있으며, 새로운 대화의 경우 단일하고 명확한 작업 공간이 자동으로 선택됩니다. LibreChat은 이러한 선택 사항을 대화에 저장하고, 실행 전 라이브 워커를 대상으로 재검증하며, 승인 대기 및 재개된 실행 전반에 걸쳐 이를 고정 상태로 유지합니다. 필수 선택 사항이 누락되었거나 사용할 수 없는 경우 전송이 차단되며, LibreChat은 다른 작업 공간으로 임의로 대체하지 않습니다. 실행 시작 시 LibreChat은 선택된 작업 공간에서 저장소 지침을 로드하여 에이전트가 해당 저장소의 지침을 따르도록 할 수 있습니다. 관리자는 [`repositoryInstructions.timeoutMs`](/docs/configuration/librechat_yaml/object_structure/agents#repositoryinstructions)를 사용하여 검색 범위를 제한할 수 있습니다. 네이티브 파일 및 Bash 작업 공간 도구는 워커가 재사용 가능한 런타임 세션을 지원하지 않는 경우에도 광고된 루트를 사용할 수 있습니다. 작업 공간 인식 프로그래밍 방식의 Bash는 에이전트의 프로그래밍 도구 구성이 허용하고, 승인된 연결 워커가 준비되어 `programmaticLanguages: ['bash']`를 알리며, 선택된 작업 공간과 워커가 모두 `execute_command`를 허용하는 경우 호환되는 Code API 및 워커 빌드에서 사용할 수 있습니다. LibreChat은 서버에서 검증된 작업 공간 ID와 대화 작업 공간 인스턴스 ID(있는 경우)를 프로그래밍 도구에 전달하며, 모델 인수는 해당 선택을 대체할 수 없습니다. 이러한 기능이 없으면 프로그래밍 방식의 Bash는 비활성화됩니다. 작업 공간 인식 명령에는 직접 Bash를 사용하십시오. 워커가 파일 릴레이를 지원하는 경우, 채팅 업로드는 프로그래밍 실행을 위해 `$LIBRECHAT_CODE_DATA_DIR` 하위에 별도로 준비되며 선택된 작업 공간으로 복사되지 않습니다. **중지(Stop)**는 이후 명령을 위해 작업 공간을 무효화하지 않고 신호 인식 중인 진행 중인 BYOM 명령을 취소합니다. 분리된 작업은 별도의 취소 수명 주기를 유지합니다.

연결된 실행 환경의 경우, Agent Builder는 **Workspace default**를 현재 광고 중인 루트 중 하나로 설정할 수 있습니다. 이는 연결된 환경에 대해 검증되며 해당 Agent의 새로운 대화를 초기화하는 데 사용됩니다. **Last used**를 선택하면 해당 Agent 및 환경에 대해 로그인한 사용자의 브라우저 로컬 기본 설정을 사용합니다. 이는 편의를 위한 힌트일 뿐이며, 권한 부여나 대화 바인딩과는 무관합니다. 실행 환경을 변경하면 명시적 기본값이 지워지며, 더 이상 광고되지 않는 저장된 루트는 계속 표시되지만 다시 구성될 때까지 선택할 수 없습니다.

#### 저장된 채팅 작업 공간 변경 사항 [#saved-chat-workspace-changes]

기본적으로 저장된 대화의 첨부된 워크스페이스 결정은 봉인되어 있습니다. [`statefulCodeSessions.conversationMoves.enabled`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions)가 활성화되면, 소유자는 명시적으로 다른 승인된 워크스페이스로 이동하거나 누락된 워크스페이스를 복구할 수 있습니다. 복구는 대화 기록을 보존하며, 손실된 워크스페이스의 파일은 보존하지 **않습니다**. `allowAttachDetach: true`를 설정하면 소유자가 코딩이 아닌 저장된 대화에 워크스페이스를 추가하거나, 첨부된 워크스페이스를 떠나 일반 대화를 계속할 수 있습니다. 이동 기능만 활성화해서는 연결/분리 기능을 사용할 수 없습니다. 이러한 전환은 생성이 진행 중일 때는 수행할 수 없으며 서버에서 재검증됩니다. 이 기능을 선택하기 전에 모든 API 복제본을 업그레이드하고 `CODE_ENVIRONMENT_DECISION_VERSION=1`을 활성화하십시오. 해당 스위치를 설정하지 않으면 기존의 이동 전용 및 봉인된 대화 동작은 변경되지 않습니다.

Attached Bash는 기본적으로 30초 타임아웃을 사용합니다. 환경 설정에서 [`configSchema.limits.maxCommandTimeoutMs`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions)를 사용하여 최대 5분의 프로토콜 상한선까지 더 큰 모델 요청 가능 예산을 노출할 수 있습니다. 요청된 타임아웃은 배포 제한을 초과할 수 없습니다. 관리자는 [`configSchema.limits.maxQueueWaitMs`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions)를 사용하여 용량 재시도 횟수를 별도로 제한할 수 있습니다. 이 대기열 대기 시간은 승인되었거나 실행 중인 명령을 취소하지 않습니다. 더 긴 **개별** 승인 시도를 허용하려면, Code API가 요청별 대기열 허용량을 준수하고 라이브 경로의 최단 프록시 타임아웃이 확인된 후에만 `configSchema.limits.maxRequestTimeoutMs`를 사용하십시오. 선택 사항인 `configSchema.limits.minCommandAdmissionMs`는 명령 전 승인을 위해 기본적으로 10초(1~300초 유효)를 예약합니다. 광고된 Bash 타임아웃은 이 예약 시간과 정산 및 전달을 위한 추가 10초를 제외한 후 요청 예산에 맞춰 조정됩니다. 이 예산은 `maxQueueWaitMs`를 대체하지 않습니다.

#### Linked-worktree lanes [#linked-worktree-lanes]

연결된 환경은 `configSchema.workspaces.linkedWorktrees: true`를 사용하여 [per-worktree request scheduling](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions)을 선택할 수 있습니다. 먼저 LibreChat을 업그레이드한 다음, 호환되는 Code API 브리지를 배포하고 `--linked-worktree-lanes` 옵션으로 워커를 시작하세요. 해당 워커가 `git_linked_worktree`를 알린 후에만 YAML 설정을 활성화하십시오. `.worktrees/<name>/`를 구조적으로 타겟팅하는 요청은 에이전트에게 표시되는 체크아웃 상대 경로를 변경하지 않고 해당 워크트리의 레인을 사용합니다. Bash의 경우, 도구의 `cwd` 인수에 워크트리 디렉토리를 전달하십시오. 명령 내에서 `cd .worktrees/<name>`을 실행해도 루트 레인에 유지됩니다. 체크아웃 루트 작업, 환경 작업 및 대화 작업 공간 인스턴스 또한 루트 범위로 유지됩니다. 이 옵션을 선택하지 않으면 모든 요청은 기존의 체크아웃 전체 스케줄링을 유지합니다.

#### 작업 공간 편집 일치 및 충돌 [#workspace-edit-matching-and-conflicts]

`edit_file`는 단일 `old_text`/`new_text` 교체를 위한 최상위 `replace_all`을 허용하거나, `edits` 배치가 제공될 때 항목별 플래그를 허용합니다. 이를 사용하지 않으면 각 `old_text`는 하나의 위치로 확인되어야 합니다. 제공된 배치는 비어 있지 않고 유효해야 합니다. LibreChat은 최상위 교체 필드로 대체하는 대신 비어 있거나 잘못된 형식의 `edits` 값을 거부합니다. 유효한 JSON 문자열 배치와 불리언 교체 플래그는 네이티브 도구 승인 전에 정규화되므로, 미리보기와 실행은 검토된 훅 재작성을 포함하여 동일한 정식 편집 내용을 사용합니다. Skill-file 및 관리형 샌드박스 편집은 LibreChat의 크기 및 일치 횟수 제한 내에서 모든 일치 항목의 교체를 지원하며, 연결된 작업 공간은 `replace_all`을 알리는 워커가 필요하며 디스패치 전에 지원되지 않는 요청을 거부합니다.

`tolerant_match`를 광고하는 연결된 워커(attached workers)에서, 편집 및 보호된 미리보기는 먼저 정확한 일치를 시도한 다음, 후행 공백, CRLF, 들여쓰기 변경 또는 정규화된 공백에 대해 공백 허용 전략을 사용합니다. 관리자는 [`configSchema.edits.tolerantMatching: false`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions)를 통해 정확한 일치를 요구할 수 있습니다. 성공 메시지는 비정확한 일치 또는 다중 교체를 식별합니다. 실패한 배치는 원자적(atomic)으로 처리됩니다. 즉, 아무것도 기록되지 않으며, LibreChat은 임의의 워커 텍스트나 파일 발췌문을 전달하지 않고 편집별 이유, 개수, 후보 줄 번호 또는 파일 변경 경고를 제한적으로 보고합니다.

이러한 attached-worker 기능은 [Code Interpreter #271](https://github.com/LibreChat-AI/code-interpreter/pull/271)을 구현하는 호환 가능한 Code API 및 worker 빌드가 필요합니다. LibreChat은 기능 협상(capability negotiation) 이후에만 새로운 필드를 전송합니다. 이전 빌드에서는 요청 형식과 일치 동작이 변경되지 않은 상태로 유지되므로, LibreChat만 업그레이드해서는 허용 가능한(tolerant) attached 편집이나 `replace_all`을 사용할 수 없습니다.

#### Attached-environment 도구 권한 [#attached-environment-tool-permissions]

Attached 및 personal 환경은 파일 쓰기 및 명령 또는 코드 실행에 대해 기본적으로 승인을 요청하는 정책을 사용합니다. 읽기 전용 및 검색 작업은 배포의 일반적인 도구 정책에 따라 계속됩니다. 관리자가 [`configSchema.permissions`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions)를 통해 두 범주 중 하나를 노출하는 경우, Code Environment 관리 권한이 있는 사용자는 **Settings > Code environments**에서 허용된 **Allow**, **Ask** 또는 **Deny** 값 중 하나를 선택할 수 있습니다. 설정이 누락되었거나, 오래되었거나, 허용되지 않은 경우 안전하게 **Ask**로 대체됩니다.

선택한 첨부 환경이 지원할 때마다 컴포저에 대화 수준의 **Code approval mode**가 표시됩니다:

- **Ask before changes**는 파일 수정이나 명령 실행 전에 확인을 요청합니다.
- **Accept edits**는 파일 편집을 허용하지만 명령을 실행하기 전에 계속해서 확인을 요청합니다.
- **Full access**는 정기적인 프롬프트 없이 두 범주를 모두 허용합니다.

선택된 모드는 해당 대화와 함께 이동하며, 배포의 허용된 값 및 환경 정책과 교차 검증됩니다. **Full access**는 `fileWrite`와 `commandExecution` 모두에서 `allow`가 허용될 때만 나타납니다. 이는 샌드박스 격리, 역할 권한, 명시적인 endpoint `ask` 또는 `deny` 규칙, Skill-file 확인, 또는 승인 후크를 우회하지 않습니다.

대화 가져오기(import) 시 수신자에 대한 코드 승인 모드(Code approval mode)를 선택할 수 없습니다. 새로 가져오거나 대량 복사된 대화는 현재 정책에 따라 수신자의 기본 설정/기본값을 사용하며, 대량 업데이트는 로컬에 저장된 선택 사항을 유지합니다. 기존 대화는 소급하여 재설정되지 않으며, LibreChat에서 모드를 명시적으로 선택하면 해당 설정이 계속 유지됩니다.

이러한 제어 기능은 파일 작성 도구, 셸 및 코드 실행, 컴파일 검사, 그리고 프로그래밍 방식의 도구 호출(Programmatic Tool Calling)을 다룹니다. 일반적인 파일 쓰기가 허용되는 경우에도, Skill 작성이 가능할 때는 영구 Skill 파일에 대한 쓰기 작업에 여전히 확인이 필요합니다. 이 설정들은 VM 격리, 네트워킹, 마운트, 권한 있는 실행, 인그레스(ingress), 이그레스(egress) 또는 비밀 접근 권한을 변경하지 않습니다.

배포의 명시적인 [`toolApproval.enabled: false`](/docs/configuration/librechat_yaml/object_structure/agents#toolapproval) 설정은 이 기준을 비활성화하는 긴급 재정의입니다. 해당 재정의가 없으면, 승인 요청을 제시하고 재개할 수 없는 호출자는 연결된 환경의 도구를 조용히 실행하는 대신 실패(fail closed)하게 됩니다.

페어링은 원격 워커 전송을 인증할 뿐, 샌드박스 경계 역할을 하지는 않습니다. 워커의 로컬 실행 endpoint는 루프백이나 사설 네트워크로 유지하고, 신뢰할 수 없는 코드에 대해서는 적절한 격리 모드를 사용하십시오.

실행이 활성화되어 있는 동안, 확장된 코드 및 셸 세부 정보 창은 스트리밍되는 인수를 따라 하단으로 이동합니다. 위로 스크롤하면 이 따라가기 동작이 일시 중지되므로, 창이 뷰포트를 강제로 이동시키지 않고도 이전 출력을 검토할 수 있습니다.

## API 사용하기 [#using-the-api]

### LibreChat에서 [#in-librechat]

LibreChat은 다음의 주요 방법을 통해 API를 일급 지원합니다:

1. **[AI Agents](/docs/features/agents#code-interpreter)**: 에이전트 구성에서 Code Interpreter를 활성화하여 코드를 실행하고 파일을 자동으로 처리할 수 있도록 합니다.

2. **수동 실행**: 아래와 같이 채팅 인터페이스 내 코드 블록에 있는 "Run Code" 버튼을 사용하세요:

3. **[Programmatic Tool Calling](/docs/features/agents#programmatic-tool-calling)**: `programmatic_tools` 기능을 활성화하고 선택한 MCP 도구를 Programmatic으로 표시하여 에이전트가 샌드박스 환경의 코드에서 해당 도구를 오케스트레이션할 수 있도록 합니다.

4. **[Background Tool Calls](/docs/features/agents#background-tool-calls)**: 에이전트가 적격한 코드를 백그라운드에서 실행하도록 지시하고, 코드가 실행되는 동안 계속 작업을 진행할 수 있게 합니다.

5. **[Stateful Code Sessions](/docs/features/agents#stateful-code-sessions)**: 사용자, 에이전트 및 사용자, 또는 대화 범위의 작업 공간을 에이전트의 코드 실행 전반에 걸쳐 실험적으로 재사용합니다.

![LibreChat의 코드 인터프리터](/images/agents/run_code.png)

### API 키 설정 [#set-up-api-key]

- **사용자별 설정:** 메시지가 표시되면 LibreChat에 API 키를 입력하세요.
- **전역 설정:** LibreChat의 `.env` 파일에 `LIBRECHAT_CODE_API_KEY`를 설정하여 모든 사용자가 하나의 키를 공유하도록 합니다.

현재 [ClickHouse/code-interpreter](https://github.com/ClickHouse/code-interpreter) 서비스는 로컬 모드 외부에서 LibreChat JWT 인증을 사용합니다. API 키는 호환되는 Code Interpreter 배포를 위해 계속 사용할 수 있습니다.

### 자체 호스팅 JWT 인증 [#self-hosted-jwt-authentication]

JWT 인증을 사용하면, LibreChat은 각 Code Interpreter 요청 시 인증된 사용자를 위해 단기 베어러 토큰에 서명합니다. Code Interpreter 서비스는 일치하는 공개 키를 검증하고 서명된 사용자 및 테넌트 컨텍스트를 사용하여 파일과 세션을 격리합니다. 개인 서명 키는 LibreChat 내에 유지되며, Code Interpreter는 공개 검증 키만 수신합니다.

다음과 같이 LibreChat을 구성하세요:

```env
CODEAPI_AUTH_PROVIDER=librechat-jwt
CODEAPI_JWT_PRIVATE_KEY="-----BEGIN PRIVATE KEY-----\n...\n-----END PRIVATE KEY-----"
CODEAPI_JWT_ALGORITHM=EdDSA
CODEAPI_JWT_KID=lc-codeapi-2026-05
CODEAPI_JWT_ISSUER=librechat
CODEAPI_JWT_AUDIENCE=codeapi
CODEAPI_JWT_TTL_SECONDS=300
CODEAPI_JWT_MINT_CACHE_SECONDS=30
CODEAPI_JWT_SINGLE_TENANT_ID=legacy
```

`CODEAPI_JWT_PRIVATE_KEY_BASE64`는 대신 base64로 인코딩된 PEM을 담을 수 있으며, `CODEAPI_JWT_PRIVATE_JWK_JSON`은 비공개 JWK를 허용합니다. LibreChat은 Ed25519(`EdDSA`, 기본값) 및 RSA(`RS256`) 서명을 지원합니다. 모든 LibreChat 측 설정에 대해서는 [환경 변수 참조](/docs/configuration/dotenv#code-interpreter-jwt-authentication)를 확인하세요.

해당 검증기(verifier)를 사용하여 Code Interpreter를 구성하세요:

```env
LOCAL_MODE=false
CODEAPI_AUTH_PROVIDER=librechat-jwt
CODEAPI_JWT_ISSUER=librechat
CODEAPI_JWT_AUDIENCE=codeapi
CODEAPI_JWT_ALLOWED_ALGS=EdDSA
CODEAPI_JWT_JWKS_JSON={"keys":[{"kty":"OKP","crv":"Ed25519","x":"...","kid":"lc-codeapi-2026-05","alg":"EdDSA"}]}
CODEAPI_JWT_SINGLE_TENANT_ID=legacy
```

발급자(issuer), 대상(audience), 키 ID(key ID), 알고리즘(algorithm) 및 공개 키(public key)는 LibreChat의 서명자와 일치해야 합니다. Code Interpreter는 `CODEAPI_JWT_PUBLIC_KEY`와 `CODEAPI_JWT_KID`를 사용하거나 `CODEAPI_JWT_PUBLIC_KEYS_DIR`에서 검증자 키를 로드할 수도 있습니다. 인라인 JWKS는 키 교체(rotation)에 편리합니다. 토큰 TTL은 Code Interpreter 서비스의 `CODEAPI_JWT_MAX_TTL_SECONDS` 이하로 유지하십시오. 이 값은 기본적으로 300초로 설정되어 있으며 최대 300초로 제한됩니다.

로컬 체크아웃의 경우, Code Interpreter 저장소에는 일치하는 Ed25519 서명 및 실행 매니페스트 키를 생성하고 두 `.env` 파일을 모두 업데이트하는 도우미가 포함되어 있습니다:

```bash
node scripts/setup-local-auth-env.js --librechat /path/to/LibreChat
```

단일 테넌트 배포의 경우 `CODEAPI_JWT_SINGLE_TENANT_ID=legacy`를 그대로 둘 수 있지만, 두 서비스 모두에서 값이 일치해야 합니다. 다중 테넌트 배포의 경우 인증된 테넌트 컨텍스트를 제공하고 LibreChat에서 `TENANT_ISOLATION_STRICT=true`를, Code Interpreter에서 `CODEAPI_TENANT_ISOLATION_STRICT=true`를 활성화해야 합니다. 엄격 모드(Strict mode)는 단일 테넌트 폴백을 사용하는 대신 테넌트 컨텍스트가 없는 요청을 거부합니다.

### 직접 API 통합 [#direct-api-integration]

현재 자체 호스팅되는 서비스는 LibreChat JWT 클레임 계약을 충족하는 bearer 토큰을 요구합니다. 직접 통합하려면 호환되는 단기 토큰을 생성하여 `Authorization: Bearer <token>` 헤더로 전송해야 합니다. API 키 호환 배포는 대신 `x-api-key` 헤더에 구성된 키를 허용합니다. 공개 또는 프로덕션 endpoint에서 Code Interpreter의 인증이 없는 로컬 모드를 절대 사용하지 마십시오.

### 자체 호스팅 기본 URL [#self-hosted-base-url]

`LIBRECHAT_CODE_BASEURL`을 설정하여 LibreChat이 자체 호스팅된 [code-interpreter](https://github.com/ClickHouse/code-interpreter) 인스턴스를 가리키도록 한 다음, [JWT 인증](#self-hosted-jwt-authentication)을 구성하세요. API 키 호환 서비스의 경우, 대신 `LIBRECHAT_CODE_API_KEY`를 설정하세요. 매우 실험적인 상태 유지(stateful) Agent 세션은 [`LIBRECHAT_CODE_BASEURL_STATEFUL`](/docs/configuration/dotenv#stateful-code-interpreter-endpoint)을 통해 구성되거나 [`statefulCodeSessions.environments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions)로 명명된 별도의 `stateful` 프로필 경로가 필요합니다.

## 핵심 기능 [#core-functionality]

### 코드 실행 [#code-execution]

- 지원되는 언어로 코드 스니펫 실행
- stdout/stderr 출력 수신
- 실행 통계(메모리 사용량, CPU 시간) 가져오기
- 프로그램 인자 처리
- 실행 상태 및 결과에 액세스

### 파일 작업 [#file-operations]

- 입력 파일 업로드
- 생성된 출력물 다운로드
- LibreChat이 안전하게 추출/렌더링할 수 있는 경우, PowerPoint `.pptx` 프레젠테이션 및 `.potx` 템플릿을 포함한 Office 파일, 그리고 CSV, 텍스트 및 PDF와 유사한 아티팩트를 인라인으로 미리보기합니다.
- Agent의 `read_file` 도구에 의해 반환된 PNG, JPEG, GIF 및 WebP 이미지를 볼 수 있는 아티팩트로 표시합니다.
- 사용 가능한 파일 목록
- 불필요한 파일 삭제
- 파일 세션 관리

생성된 아티팩트 미리보기는 의도적으로 크기가 제한되어 있습니다. 인라인 미리보기 추출을 위한 소스 파일 크기 제한을 변경하려면 LibreChat의 `.env`에서 [`FILE_PREVIEW_MAX_EXTRACT_BYTES`](/docs/configuration/dotenv#inline-file-previews)를 설정하세요. 더 큰 파일은 계속해서 다운로드할 수 있습니다.

`read_file`을 통해 반환되는 샌드박스 이미지는 1 MiB의 인라인 제한이 있습니다. 더 큰 이미지는 `bash_tool`을 통한 처리를 위해 샌드박스 내에 유지됩니다. `LIBRECHAT_CODE_IMAGE_CHUNK_BYTES`는 적격 이미지를 읽는 동안 사용되는 전송 청크 크기만 제어하며, 인라인 제한을 높이지는 않습니다.

<Callout type="warning" title="레거시 코드 출력에 대한 업그레이드 확인">
  고유한 출력 파일 인덱스가 추가되기 전에 동일한 Code Interpreter 파일 이름을 재생성했던 배포의 경우, 인덱스 생성을 방해하는 중복된 MongoDB 레코드가 있을 수 있습니다. `npm run migrate:code-file-duplicates:dry-run`으로 복구 작업을 미리 확인한 다음, `npm run migrate:code-file-duplicates`를 사용하여 적용하십시오. 이 마이그레이션은 가장 최신의 표준 파일 이름을 유지하고, 이전 레코드의 이름을 숫자 접미사를 붙여 변경하며, 성공적으로 실행된 후 고유 인덱스를 생성합니다.
</Callout>

### 제한 사항 [#limitations]
- 코드는 네트워크에 액세스할 수 없습니다
- 실행당 최대 10개의 파일만 생성할 수 있습니다.
- 리소스 제한(실행당 RAM, 파일 업로드 크기 및 요청 할당량)은 배포를 프로비저닝하고 구성하는 방식에 따라 달라집니다.

## 사용 사례 [#use-cases]

- **코드 테스트**: 여러 언어로 된 코드 스니펫을 테스트합니다
- **File Processing**: 프로그래밍 방식으로 파일 변환 및 분석
- **AI Applications**: AI가 생성한 코드를 안전하게 실행
- **Development Tools**: 대화형 코딩 환경 구축
- **Objective Logic**: 코드 로직과 정확성을 검증하여 AI 모델을 개선합니다.

## 오픈 소스 및 셀프 호스팅 [#open-source--self-hosting]

Code Interpreter 서비스는 [ClickHouse/code-interpreter](https://github.com/ClickHouse/code-interpreter)에서 Apache 2.0 라이선스로 오픈 소스화되어 있습니다. 코드 실행을 별도의 서비스로 유지하면 핵심 LibreChat 애플리케이션을 가볍게 유지할 수 있습니다. 즉, 필요할 때만 샌드박스 인프라를 배포하면 되며, 채팅 앱과 독립적으로 확장할 수 있습니다.

이 서비스는 독립적으로 확장 가능한 구성 요소(API 게이트웨이, 샌드박스 워커, 파일 서버) 세트로 실행되며, 신뢰할 수 없는 코드를 안전하게 실행할 수 있도록 강력한 격리 모드(NsJail 또는 libkrun을 통한 microVM)를 지원합니다. Docker Compose 및 Helm 배포 지침은 저장소의 README를 참조하세요.

## 결론 [#conclusion]

Code Interpreter API는 격리된 샌드박스 환경에서 코드를 실행하고 파일을 관리할 수 있는 안전하고 편리한 방법을 제공합니다. LibreChat의 Agents를 통해 사용하든 애플리케이션에 직접 통합하든, 코드 실행 요구 사항을 위한 강력한 솔루션을 제공합니다.

상세한 기술 사양, 배포 가이드 및 API 참조는 [code-interpreter repository](https://github.com/ClickHouse/code-interpreter)를 참조하세요.
