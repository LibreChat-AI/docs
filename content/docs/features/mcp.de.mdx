Das Model Context Protocol (MCP) ist ein offenes Protokoll, das standardisiert, wie Anwendungen Large Language Models (LLMs) Kontext bereitstellen. Betrachten Sie MCP als den **"USB-C der KI"** – so wie USB-C einen universellen Verbindungsstandard für elektronische Geräte bietet, stellt MCP eine standardisierte Möglichkeit dar, KI-Modelle mit verschiedenen Tools, Datenquellen und Diensten zu verbinden.

LibreChat nutzt MCP, um die Fähigkeiten Ihrer KI-Agenten drastisch zu erweitern. Dies ermöglicht Ihnen die Integration von allem, von Dateisystemzugriffen, Webbrowsern und spezialisierten APIs bis hin zu benutzerdefinierten Geschäftstools.

## Warum MCP wichtig ist [#why-mcp-matters]

LLMs sind auf ihre eingebauten Fähigkeiten beschränkt. Mit MCP bricht LibreChat diese Mauern auf, indem es:

- **Verbindung zu jedem Tool oder Dienst**, der einen MCP-Server bereitstellt
- **Standardisierung von Integrationen**, damit Sie den Code von LibreChat nicht für jedes Tool bearbeiten müssen
- **Unterstützung von Multi-User-Umgebungen** mit ordnungsgemäßer Authentifizierung und Isolierung
- **Hinzufügen und Aktualisieren von Servern zur Laufzeit** über das MCP-Einstellungsfenster, ohne eine Konfigurationsdatei zu bearbeiten oder einen Neustart durchzuführen

## Wie MCP in LibreChat funktioniert [#how-mcp-works-in-librechat]

LibreChat bietet zwei Möglichkeiten, MCP-Server zu verwenden: entweder im Chat-Bereich oder mit Agents.

Sie können MCP-Server manuell in Ihrer `librechat.yaml` Datei konfigurieren oder [smithery.ai](https://smithery.ai) verwenden, um MCP-Server zu finden und in die `librechat.yaml` zu installieren ([siehe Beispiel unten](#basic-configuration)). Jedes Mal, wenn Sie einen Server in der `librechat.yaml` hinzufügen oder bearbeiten, müssen Sie LibreChat neu starten, um die Verbindungen zu initialisieren. Server, die über das [MCP-Einstellungs-Panel](#adding-mcp-servers-in-the-ui) hinzugefügt wurden, werden ohne Neustart wirksam. Ein über das Panel erstellter Server, der OAuth verwendet, wird beim Speichern registriert, startet jedoch im getrennten Zustand: [Authentifizieren Sie ihn](#step-3-check-connection-status-and-authenticate) einmal, um ihn zu verbinden.

### OAuth Callback URL [#oauth-callback-url]

Für OAuth-aktivierte MCP-Server lautet die LibreChat-Callback-URL:

```text
${DOMAIN_SERVER}/api/mcp/<server-name>/oauth/callback
```

`<server-name>` ist der Schlüssel, der unter `mcpServers` in `librechat.yaml` verwendet wird, oder der Name des Servers, der in der MCP-Einstellungsoberfläche erstellt wurde. Zum Beispiel verwendet ein Server namens `salesforce` mit `DOMAIN_SERVER=https://chat.example.com` die Adresse `https://chat.example.com/api/mcp/salesforce/oauth/callback`.

Registrieren Sie diese exakte Callback-URL beim OAuth-Anbieter. Lokale Docker-Installationen verwenden normalerweise `http://localhost:3080` als Basis-URL.

### Im Chat-Bereich [#in-chat-area]

![Der MCP Servers-Katalog, geöffnet über die Composer-Palette, zeigt den Verbindungsstatus jedes Servers](/images/mcp/mcp_servers_catalog.png)

LibreChat zeigt konfigurierte MCP-Server direkt im Chat-Bereich an, wenn traditionelle endpoints (OpenAI, Anthropic, Google, Bedrock, etc.) verwendet werden:

- Wählen Sie zuerst einen beliebigen Nicht-Agent-endpoint und ein tool-kompatibles Modell aus
- MCP-Server erscheinen im Bereich **MCP Servers** der [**+**-Palette des Composers](/docs/features/composer#turn-on-tools-skills-and-mcp-servers), und jeder ausgewählte Server wird als Chip im Composer angezeigt.
- Wenn ausgewählt, werden alle Tools von diesem Server für Ihr aktuelles Modell verfügbar.
- Schneller Zugriff auf MCP-Tools, ohne einen Agenten erstellen zu müssen, wodurch mehrere Server gleichzeitig verwendet werden können

Um einen MCP Server aus der regulären Chat-Auswahl herauszuhalten, setzen Sie [`chatMenu: false`](/docs/configuration/librechat_yaml/object_structure/mcp_servers#chatmenu) in Ihrer Konfiguration:

```yaml
mcpServers:
  internal-tools:
    command: npx
    args: ['-y', 'internal-mcp-server']
    chatMenu: false # Not selectable in regular chat
```

Diese Einstellung wird sowohl bei Chat-Anfragen als auch in der Auswahl erzwungen, sodass eine veraltete gespeicherte Auswahl nicht weiterhin einen ausgeblendeten Server verwenden kann. Sie entfernt den Server nicht aus gespeicherten Agents oder aus einer Model Specs, die ihn explizit zuweist. LibreChat lässt zudem Server, die ein Benutzer nur über einen autorisierten Agent erreichen kann, aus der regulären Chat-Auswahl und dem Anfragepfad weg.

### Mit Agents [#with-agents]

MCP-Server lassen sich nahtlos in LibreChat-Agents integrieren:

1. Einen Agenten erstellen oder bearbeiten
2. Öffnen Sie **Add tools** im Agent Builder und wählen Sie **MCP** aus.
3. Wählen Sie einen MCP-Server aus; jeder Server erscheint als einzelner Katalogeintrag
4. Erweitern Sie den ausgewählten Server, um einzelne Tools zu aktivieren oder zu deaktivieren
5. Speichere deinen Agenten

![MCP-Tools im Agent Builder](/images/mcp/mcp_ui_agent.png)

Diese übergeordnete Organisation hält die Benutzeroberfläche übersichtlich – selbst Server mit über 20 Tools (wie Spotify) erscheinen als einzelne Einträge, die für eine detaillierte Steuerung erweitert werden können.

### Grundlegende Konfiguration [#basic-configuration]

Fügen Sie MCP-Server manuell zu Ihrer `librechat.yaml` Datei hinzu:

```yaml
mcpServers:
  # ClickHouse Cloud
  clickhouse-cloud:
    type: streamable-http
    url: https://mcp.clickhouse.cloud/mcp

  # File system access
  filesystem:
    command: npx
    args:
      - -y
      - '@modelcontextprotocol/server-filesystem'
      - /path/to/your/documents

  # Web browser automation
  puppeteer:
    command: npx
    args:
      - -y
      - '@modelcontextprotocol/server-puppeteer'

  # Production-ready cloud service
  business-api:
    type: streamable-http
    url: https://api.yourbusiness.com/mcp
    headers:
      X-User-ID: '{{LIBRECHAT_USER_ID}}'
      Authorization: 'Bearer ${API_TOKEN}'
    timeout: 30000
    serverInstructions: true
```

### Hinzufügen von MCP-Servern in der UI [#adding-mcp-servers-in-the-ui]

Sie können MCP-Server auch direkt über die LibreChat-Benutzeroberfläche hinzufügen und konfigurieren, ohne Konfigurationsdateien bearbeiten oder den Server neu starten zu müssen.

#### Schritt 1: Öffnen Sie das MCP-Einstellungsfenster [#step-1-open-the-mcp-settings-panel]

Navigieren Sie über die rechte Seitenleiste zum Bereich **MCP Settings**. Hier sehen Sie alle vorhandenen MCP-Server aufgelistet, zusammen mit einer **+**-Schaltfläche, um neue hinzuzufügen.

![MCP-Einstellungsbereich](/images/mcp/mcp_ui_settings_panel.png)

#### Schritt 2: Serverdetails ausfüllen [#step-2-fill-out-server-details]

Drücken Sie die **+**-Taste und geben Sie Ihren MCP-Servernamen, die Beschreibung, die URL, den Transporttyp und die Authentifizierungsmethode ein, und klicken Sie dann auf **Create**.

![Dialog zum Hinzufügen eines MCP-Servers](/images/mcp/mcp_ui_configure.png)

Ihr neuer Server wird im MCP Settings-Bereich mit einer Bestätigungsmeldung angezeigt.

![MCP Server erfolgreich erstellt](/images/mcp/mcp_ui_success_registered.png)

#### Schritt 3: Verbindungsstatus prüfen und authentifizieren [#step-3-check-connection-status-and-authenticate]

Überprüfen Sie die [Verbindungsstatusanzeige](#connection-status-indicators) für Ihren neuen Server. Wenn der Server eine OAuth-Authentifizierung erfordert, wird der Status als getrennt angezeigt. Wählen Sie den MCP Server in der **+**-Palette des Composers aus, um den Authentifizierungsprozess zu starten.

![Verbindungsstatus - Getrennt](/images/mcp/mcp_ui_unconnected.png)

Sobald der Vorgang gestartet wurde, aktualisiert sich die Statusanzeige, um anzuzeigen, dass die Authentifizierung läuft.

![Verbindungsstatus - Authentifizierung](/images/mcp/mcp_ui_authenticating.png)

#### Schritt 4: Mit OAuth fortfahren [#step-4-continue-with-oauth]

LibreChat zeigt eine **Connect**-Bestätigungsaufforderung an. Überprüfen Sie das Ziel und wählen Sie **Continue with OAuth**, um die Autorisierungsseite des Anbieters in einem neuen Browser-Tab zu öffnen. Schließen Sie dort den Anmelde- und Zustimmungsprozess des Anbieters ab.

Wenn ein in diesem Browser gestarteter Flow ausstehend ist, hält LibreChat diesen Server im Status „authorizing/connecting“ (autorisierend/verbindend), selbst wenn der zwischengespeicherte Verbindungsstatus weiterhin **Connected** (Verbunden) anzeigt. Die Eingabeaufforderung sollte nicht allein deshalb geschlossen werden, weil ein alter Status eine dauerhafte Autorisierung meldet; erst der terminale Erfolg, Fehler, Timeout oder Abbruch beendet den ausstehenden Flow. Ein in einem anderen Tab oder Browser gestarteter Flow hat in dieser Ansicht keinen lokalen ausstehenden Status.

![OAuth Continue Prompt](/images/mcp/mcp_ui_callback_confirm.png)

#### Schritt 5: Authentifizierung erfolgreich [#step-5-authentication-successful]

Nach der Authentifizierung sehen Sie eine Erfolgsbestätigung. Dieses Fenster schließt sich automatisch und leitet Sie zurück zu LibreChat.

![Authentifizierung erfolgreich](/images/mcp/mcp_ui_success_redirect.png)

#### Schritt 6: Server bereit zur Verwendung [#step-6-server-ready-for-use]

LibreChat erkennt die erfolgreiche Authentifizierung an und wählt automatisch den MCP Server zur Verwendung innerhalb Ihrer Konversation aus. Der Server zeigt nun eine Verbindungsstatusanzeige an und erscheint als ausgewählter Chip im Composer.

![MCP Server authentifiziert und automatisch ausgewählt](/images/mcp/mcp_ui_done.png)

Ihr neuer MCP-Server ist auch im Agent Builder verfügbar, wo Sie dessen Tools zu jedem Agenten hinzufügen und anpassen können, welche Teilmenge an Tools zulässig ist.

![MCP Server im Agent Builder verfügbar](/images/mcp/mcp_ui_agent.png)

#### Anmeldeinformationen-Variablen für über die Benutzeroberfläche erstellte Server [#credential-variables-for-ui-created-servers]

Wenn Sie einen MCP Server über die Benutzeroberfläche hinzufügen, können Sie von Benutzern verlangen, ihre eigenen API-Schlüssel anzugeben. Wählen Sie im Bereich „Authentication“ des Dialogfelds „MCP Server Builder“ die Option „API Key“ und aktivieren Sie das Kontrollkästchen **„User provides key“**. Wählen Sie das Header-Format (Bearer, Basic oder Custom) und speichern Sie den Server.

Im Hintergrund erstellt LibreChat einen zielgebundenen `customUserVars`-Eintrag namens `MCP_API_KEY_<hash>` und konfiguriert den entsprechenden Authentifizierungs-Header. Der Name wird automatisch verwaltet; Benutzer geben ihren Schlüssel weiterhin im MCP Tool Select Dialog oder im MCP Settings-Panel ein. Bestehende Server behalten möglicherweise den Legacy-Namen `MCP_API_KEY` bei, solange ihre Anforderungsgrenze unverändert bleibt. Dies verwendet dieselbe UI zur Schlüsseleingabe wie [YAML-definierte `customUserVars`](#user-provided-credentials).

Das Ändern der URL (einschließlich Pfad oder Query), des Proxys, des Transports, des Autorisierungsformats, des benutzerdefinierten Auth-Headers oder des konfigurierten OAuth-Clients/Ziels eines über die UI erstellten Servers erfordert, dass jeder Benutzer einen Schlüssel für die neue Grenze eingibt. Alte gespeicherte Schlüssel werden nicht an das neue Ziel weitergeleitet. Kosmetische Änderungen, äquivalente normalisierte URLs und Änderungen an ausgehenden URLs, die nur das Fragment betreffen, behalten den bestehenden Schlüssel bei. Gemeinsam genutzte Server können nur Anmeldevariablen auflösen, die durch ihre aktuelle Konfiguration deklariert sind, sodass ein Editor nicht auf einen alten generierten Namen verweisen kann, um einen früheren Schlüssel wiederherzustellen. Es ist keine Massenmigration von Anmeldedaten erforderlich. Aktualisieren Sie **jede API-Replik**, einschließlich der Replikate, die Server-Bearbeitungsanfragen bedienen, bevor Sie sich auf diesen Schutz verlassen; ein älterer Writer kann weiterhin eine ungebundene Konfiguration neu erstellen.

Wenn ein Administrator- oder Benutzer-API-Schlüssel konfiguriert ist, behandelt LibreChat den Server als API-Schlüssel-authentifiziert und überspringt die automatische OAuth-Erkennung. Eine explizite OAuth-Konfiguration hat weiterhin Vorrang. Falls ein über die Benutzeroberfläche erstellter API-Schlüssel-Server von einer älteren LibreChat-Version gespeichert wurde und im Status **OAuth Required** hängen bleibt, bearbeiten und speichern Sie den Server einmal, damit seine gespeicherten Verbindungsmetadaten aktualisiert werden.

<Callout type="warning">
Aus Sicherheitsgründen können über die Benutzeroberfläche erstellte (aus der Datenbank stammende) MCP-Server **nur** `customUserVars`-Platzhalter (`{{VAR_NAME}}`) auflösen. Serverseitige Umgebungsvariablen (`${ENV_VAR}`), Benutzerprofilfelder (`{{LIBRECHAT_USER_*}}`) und OIDC-Token (`{{LIBRECHAT_OPENID_*}}`) sind absichtlich blockiert, um unbefugten Zugriff auf Server-Geheimnisse oder Daten anderer Benutzer zu verhindern. Für die vollständige Unterstützung von Platzhaltern konfigurieren Sie den Server stattdessen in der `librechat.yaml`.
</Callout>

## MCP Server-Verwaltung [#mcp-server-management]

LibreChat bietet umfassende Tools zur Verwaltung von MCP Server-Verbindungen mit Verbindungsstatus-Tracking sowie Unterstützung für OAuth-Authentifizierung und Initialisierung in der UI.

### Verbindungsstatus-Anzeigen [#connection-status-indicators]

LibreChat zeigt dynamische Statussymbole an, die den aktuellen Status jedes MCP Servers in der **+**-Palette des Composers und im Einstellungsbereich anzeigen:

![MCP Server-Status-Symbole](/images/mcp/mcp_server_status_icons.png)

**Status-Typen:**

- **Verbunden** (grünes Zahnrad): Der Server ist verbunden und verfügt über konfigurierbare customUserVars
- **OAuth erforderlich** (bernsteinfarbener Schlüssel): Server erfordert OAuth-Authentifizierung
- **Getrennt** (oranger Stecker): Serververbindung fehlgeschlagen oder unterbrochen
- **Initialisierung** (blauer Ladebalken): Der Server startet oder stellt die Verbindung wieder her
- **Fehler** (rotes Dreieck): Der Server ist auf einen Fehler gestoßen
- **Abbrechen** (rotes x): Der OAuth-Ablauf wird abgebrochen

### Abbrechen von OAuth über den Agent Tool Dialog [#cancelling-oauth-from-the-agent-tool-dialog]

Unter **Agent Builder → Tool Library → MCP server configuration** wird **Connect** zu einer aktivierten **Cancel**-Aktion, während der gemeinsam genutzte Server-Manager einen abbrechbaren OAuth-Flow meldet. Dies umfasst einen ausstehenden Flow, der von einem anderen LibreChat-Panel erkannt wurde. Wählen Sie **Cancel**, um diesen Flow zu stoppen, die lokale OAuth-Eingabeaufforderung zu schließen und die ausstehende automatische Tool-Auswahl zu löschen. Ein verspätetes Verbindungsergebnis nach dem Abbruch fügt in diesem Dialog nicht automatisch Tools hinzu. Sie können **Connect** erneut wählen, um einen neuen Versuch zu starten. Eine Initialisierung, die nicht abbrechbar ist, zeigt weiterhin ihren deaktivierten Status „beschäftigt“ anstelle einer Abbruchaktion.

Sie können MCP-Server direkt über die Benutzeroberfläche initialisieren oder neu initialisieren:

**Ein Klick:**

- Ein-Klick-Initialisierung durch Auswahl des Servers im Bereich **MCP Servers** der **+**-Palette des Composers

  <Video src="/videos/mcp_one_click_init.mp4" title="MCP-Initialisierung mit einem Klick" />

**Von MCPConfigDialog:**

- Wählen Sie **Configure** in der Zeile eines MCP-Servers in der **+**-Palette des Composers, um den MCPConfigDialog zu öffnen.
- Konfigurieren Sie benutzerdefinierte Variablen und klicken Sie je nach Authentifizierungstyp des Servers auf die Schaltfläche Authenticate/Initialize.

       <Video src="/videos/mcp_config_dialog_auth.mp4" title="Authentifizierungsdialog für MCP-Konfiguration" />

  **Über das MCP-Einstellungsfeld:**

- Klicken Sie auf einen beliebigen Server im Bereich der Serverliste im MCP Settings Panel, um auf die Konfigurations- und Initialisierungssteuerelemente zuzugreifen.
- Konfigurieren Sie benutzerdefinierte Variablen und klicken Sie je nach Authentifizierungstyp des Servers auf die Schaltfläche Authenticate/Initialize.

  <Video src="/videos/mcp_settings_init.mp4" title="Initialisierung des MCP-Einstellungsbereichs" />

Initialisierungsfehler unterscheiden nun zwischen einem nicht erreichbaren Server, fehlenden `customUserVars`, einer OAuth-Verbindung, die erneut authentifiziert werden muss, und einem allgemeinen Initialisierungsfehler. Verwenden Sie die benannten fehlenden Variablen oder die erneute Authentifizierungsaktion in der Meldung, bevor Sie es erneut versuchen; der Server muss für diese Fälle nicht mehr entfernt und neu hinzugefügt werden.

Passive Katalog-Ladevorgänge führen OAuth-Erkennungsversuche zusammen und reduzieren die Frequenz nach Fehlern schrittweise, sodass eine getrennte Integration nicht bei jeder Anfrage eine erneute Erkennung versucht. Anmeldeinformationsänderungen sind über Replikate hinweg durch eine Generierungssperre geschützt, wodurch verhindert wird, dass ein älteres Erkennungsergebnis eine neuere Authentifizierung überschreibt. Betreiber können die Richtlinie zur begrenzten Wiederherstellung unter [`mcpSettings.catalogRecovery`](/docs/configuration/librechat_yaml/object_structure/mcp_settings#catalogrecovery) anpassen; die Standardeinstellungen sind für die meisten Bereitstellungen geeignet.

Wenn ein Agent explizit MCP Tools erwartet, aber beim Start der Ausführung keine aufgelöst werden können, bricht LibreChat die Ausführung mit Hinweisen zur Verbindung und zum Zugriff ab, anstatt sie stillschweigend ohne diese Tools auszuführen.

MCP-Server, die `notifications/tools/list_changed` aussenden, können ihren Tool-Katalog aktualisieren, ohne dass ein Neustart von LibreChat erforderlich ist. LibreChat ruft die aktuelle Liste von der Live-Verbindung ab, veröffentlicht hinzugefügte Tools und beendet die Bereitstellung von Tools, die der Server entfernt hat. Auch bei Wiederverbindungen wird der Katalog synchronisiert, bevor die Verbindung als bereit eingestuft wird. Verwaltete Snapshot-Aktualisierungen und die Erkennung kalter Server teilen sich ein prozessweites Drei-Operationen-Gate. Sobald eine Operation zugelassen ist, bleibt sie durch ihre Tool-Listen- oder Server-spezifische Erkennungsfrist begrenzt, einschließlich eines eventuell kürzeren `initTimeout`, sodass langsame Katalogvorgänge einen Slot nicht unbegrenzt belegen können.

Bei streamfähigen HTTP-Servern kann ein Wiederverbindungsversuch kurzzeitig einen HTTP-`409`-Fehler zurückgeben, wenn der Server noch einen veralteten, eigenständigen SSE-Stream für die alte Sitzung hält. LibreChat behandelt dies als vorübergehend, beendet die veraltete Sitzung und baut die Verbindung automatisch neu auf; bei erfolgreicher Wiederherstellung ist kein Eingreifen des Bedieners erforderlich. Sollte die neu aufgebaute Verbindung ebenfalls fehlschlagen, zeigt LibreChat weiterhin den zugrunde liegenden Verbindungsfehler an.

LibreChat klassifiziert Streamable HTTP-Antworten anhand des geparsten `Content-Type` Medientyps anstatt durch einen Teilstring-Abgleich. Parameter können eine Nicht-SSE-Antwort nicht als `text/event-stream` erscheinen lassen, daher werden Fehler bei der Antwortgröße weiterhin über den korrekten SSE- oder Nicht-SSE-Verarbeitungspfad geleitet.

### Sichtbarkeit des MCP-Einstellungsbereichs [#mcp-settings-panel-visibility]

Das MCP-Einstellungs-Panel erscheint in der rechten Seitenleiste, wenn LibreChat MCP-Server erkennt, die während ihrer Initialisierung möglicherweise ein Eingreifen des Benutzers erfordern. Das Panel wird sichtbar, wenn ein konfigurierter Server eines der folgenden Kriterien erfüllt:

- **Benutzerdefinierte Benutzervariablen**: Der Server hat `customUserVars` definiert, die vom Benutzer bereitgestellte Anmeldeinformationen enthalten können
- **OAuth-Authentifizierung**: Der Server erkennt beim Start, dass eine OAuth-Authentifizierung erforderlich ist
- **Manuelle Initialisierung**: Der Server ist mit `startup: false` konfiguriert, was eine manuelle Initialisierung erfordert

## LibreChat-spezifische Funktionen [#librechat-specific-features]

Die MCP-Implementierung von LibreChat ist für hochgradig konfigurierbare Multi-User-Umgebungen in der Praxis konzipiert.

### Benutzerspezifische Verbindungen [#user-specific-connections]

- Jeder Benutzer erhält seine eigene isolierte Verbindung zu MCP-Servern
- Benutzerauthentifizierung und Berechtigungen werden berücksichtigt
- Persönliche Daten und Kontext bleiben privat

### Teilen von MCP-Servern [#sharing-mcp-servers]

MCP-Server nehmen am [granularen Zugriffskontrollsystem](/docs/features/access_control) von LibreChat teil. Zusätzlich zu den in `librechat.yaml` definierten Servern (die von Administratoren verwaltet werden und den Funktionsberechtigungen von [`interface.mcpServers`](/docs/configuration/librechat_yaml/object_structure/interface#mcpservers) unterliegen), verfügen von Benutzern erstellte MCP-Server über eine eigene ACL und können für bestimmte **Benutzer**, **Gruppen**, **Rollen** oder **öffentlich** freigegeben werden, wobei die Berechtigungsstufen Viewer (Betrachter), Editor (Bearbeiter) oder Owner (Eigentümer) zur Verfügung stehen.

Die Feature-Flags `USE`, `CREATE`, `SHARE` und `SHARE_PUBLIC` unter `interface.mcpServers` steuern, wer überhaupt MCP-Server erstellen und teilen darf. Siehe [Access Control](/docs/features/access_control) für Informationen darüber, wie sich die Berechtigungsebenen zusammensetzen.

### Dynamischer Benutzerkontext [#dynamic-user-context]

MCP-Server können über Platzhalter in **URLs und Headern** (für SSE- und Streamable HTTP-Transporte) auf Benutzerinformationen zugreifen:

```yaml
mcpServers:
  user-api:
    type: streamable-http
    url: https://api.example.com/users/{{LIBRECHAT_USER_USERNAME}}/mcp
    headers:
      X-User-ID: '{{LIBRECHAT_USER_ID}}'
      X-User-Email: '{{LIBRECHAT_USER_EMAIL}}'
      X-User-Role: '{{LIBRECHAT_USER_ROLE}}'
      Authorization: 'Bearer ${API_TOKEN}'
```

Zu den verfügbaren Platzhaltern gehören:

- `{{LIBRECHAT_USER_ID}}` - Eindeutige Benutzerkennung
- `{{LIBRECHAT_USER_EMAIL}}` - E-Mail-Adresse des Benutzers
- `{{LIBRECHAT_USER_ROLE}}` - Benutzerrolle (admin, user, etc.)
- `{{LIBRECHAT_USER_USERNAME}}` - Benutzername
- Und viele mehr (siehe [MCP Servers Configuration](/docs/configuration/librechat_yaml/object_structure/mcp_servers#headers) für die vollständige Liste)

YAML-definierte MCP-Server können auch `{{LIBRECHAT_OPENID_*}}`-, `{{LIBRECHAT_GRAPH_*}}`- und `{{LIBRECHAT_BODY_*}}`-Platzhalter verwenden. `{{LIBRECHAT_BODY_*}}`-Werte sind auf den Request beschränkt, sodass LibreChat Verbindungen für den aktiven Lauf erstellt, sie über Tool-Aufrufe in diesem Lauf hinweg wiederverwendet und sie bereinigt, wenn der Request endet. Request-bezogene Server sind vom persistenten Tool-Cache ausgeschlossen, damit Request-spezifische Header und URLs nicht außerhalb des aktiven Laufs wiederverwendet werden. Da ihre Tool-Liste nicht aufgelöst werden kann, bevor eine Chat-Anfrage existiert, stellt der Agent Builder eine Laufzeit-Tool-Auswahl für den gesamten Server bereit und löst dessen Tools zur Laufzeit auf. Der Abschluss von OAuth speichert die Autorisierung, stellt die Verbindung jedoch erst her, wenn der erste Lauf den Request-Kontext bereitstellt. User-, OpenID- und Graph-Platzhalter sind auf den Benutzer beschränkt; HTTP-Transporte aktualisieren ihre aufgelösten Header vor jedem Tool-Aufruf, ohne dass eine erneute Verbindung erforderlich ist.

Vertrauenswürdige Betreiber können `Authorization: 'Bearer {{LIBRECHAT_OPENID_ACCESS_TOKEN}}'` auf einem in YAML definierten Remote-Server verwenden, um das Live-OpenID-Zugriffstoken des Benutzers weiterzuleiten. Explizites MCP-OAuth, On-Behalf-Of-Austausch und die Authentifizierung über Administrator-API-Schlüssel haben Vorrang. Nach einem `401` oder `403` kann LibreChat die Verbindung einmal aktualisieren, aber der abgelehnte Tool-Aufruf wird niemals automatisch wiederholt. Siehe die [Referenz für MCP-Server-Platzhalter](/docs/configuration/librechat_yaml/object_structure/mcp_servers#headers) für Einrichtungs- und Sicherheitshinweise.

`{{LIBRECHAT_GRAPH_ACCESS_TOKEN}}` tauscht das wiederverwendbare OpenID-Zugriffstoken des Benutzers über den Microsoft On-Behalf-Of-Flow aus. [`GRAPH_API_SCOPES`](/docs/configuration/dotenv#microsoft-graph-api--entra-id-integration) legt die angeforderten, durch Leerzeichen getrennten Scopes fest und verwendet standardmäßig `https://graph.microsoft.com/.default`. Dies ist unabhängig von `OPENID_GRAPH_SCOPES`, welches die Personen- und Gruppensuche konfiguriert.

Der `{{LIBRECHAT_BODY_PARENTMESSAGEID}}` Platzhalter wird für native Agent-Chats, OpenAI-kompatible Agents API-Aufrufe und Legacy-Assistants-Ausführungen ausgefüllt. Open Responses hat keine äquivalente übergeordnete Nachrichtenidentität und schlägt fehl, wenn ein MCP-Server diesen Wert erfordert. Siehe die [Referenz für MCP-Server-Platzhalter](/docs/configuration/librechat_yaml/object_structure/mcp_servers#headers).

### Server-Anweisungen [#server-instructions]

`serverInstructions` ist eine LibreChat-Funktion, die dynamisch konfigurierte Anweisungen hinzufügt, sobald ein Tool von diesem MCP-Server ausgewählt wird:

```yaml
mcpServers:
  filesystem:
    command: npx
    args: ['-y', '@modelcontextprotocol/server-filesystem', '/docs']
    serverInstructions: |
      When accessing files:
      - Always check file permissions first
      - Use absolute paths for reliability
      - Handle errors gracefully
```

Optionen:

- `true`: Verwende die vom Server bereitgestellten Anweisungen, sofern verfügbar
- `false`: Anweisungen deaktivieren
- `string`: Verwenden Sie die benutzerdefinierten Anweisungen wortwörtlich (wie oben gezeigt)

LibreChat bewahrt diese konfigurierte Deklaration getrennt von den Anweisungen auf, die während der Überprüfung des Servers abgerufen werden. Eine `true`-Deklaration bleibt daher über die Überprüfung und zwischengespeicherte Registry-Neuladevorgänge hinweg aktiviert, während eine benutzerdefinierte Zeichenfolge maßgeblich bleibt.

### Timeout-Konfiguration [#timeout-configuration]

Konfigurieren Sie für lang andauernde MCP-Vorgänge geeignete Timeouts sowohl für die Initialisierung als auch für Tool-Operationen.

```yaml
mcpServers:
  data-processor:
    type: streamable-http
    url: https://api.example.com/mcp
    initTimeout: 15000 # 15 seconds for server initialization
    timeout: 60000 # 60 seconds for tool operations
```

**Hinweis**: Falls Vorgänge weiterhin vorzeitig abgebrochen werden, überprüfen Sie Ihre Proxy-Konfiguration (z. B. nginx, traefik usw.), da diese aufgrund von Standard-Timeouts möglicherweise Verbindungen vorzeitig trennt.

Wenn ein Benutzer während eines Agent-Tool-Aufrufs im Vordergrund auf **Stop** drückt, leitet LibreChat das Signal zum Abbruch der Ausführung an MCP weiter. Bei streamfähigen HTTP-Servern sendet das MCP SDK `notifications/cancelled`; der Server muss diese Benachrichtigung berücksichtigen, um seine eigene Arbeit zu beenden. Losgelöste Hintergrundaufrufe behalten absichtlich einen separaten Lebenszyklus bei und werden nicht mit dem Vordergrund-Turn abgebrochen.

### Vom Benutzer bereitgestellte Anmeldedaten [#user-provided-credentials]

Sie können Benutzern erlauben, ihre eigenen Anmeldedaten für MCP-Server über `customUserVars` bereitzustellen. Dies ermöglicht eine sichere, benutzerspezifische Authentifizierung, ohne Anmeldedaten in Konfigurationsdateien speichern zu müssen.

```yaml
mcpServers:
  my-api-server:
    type: streamable-http
    url: 'https://api.example.com/mcp'
    headers:
      X-Auth-Token: '{{MY_API_KEY}}' # Uses the user-provided value
    customUserVars:
      MY_API_KEY:
        title: 'API Key'
        description: "Enter your personal API key from <a href='https://example.com/keys' target='_blank'>your account settings</a>"
```

Benutzer können diese Anmeldedaten konfigurieren:

- **Vom Chat-Bereich**: Wählen Sie **Konfigurieren** in der Zeile eines konfigurierbaren MCP-Servers in der **+**-Palette des Composers
- **Vom MCP-Einstellungsbereich**: Greifen Sie im rechten Bereich auf „MCP Settings“ zu, um die Anmeldedaten für alle konfigurierten Server zu verwalten.

#### Neuinitialisierung von MCP-Servern mit Benutzeranmeldeinformationen [#reinitializing-mcp-servers-with-user-credentials]

Für MCP-Server, die benutzerspezifische Anmeldedaten erfordern, bevor sie verwendet werden können (z. B. `PAT_TOKEN`s im [offiziellen MCP-Server von GitHub](https://github.com/github/github-mcp-server)), ermöglicht LibreChat es Benutzern, diese Anmeldedaten bereitzustellen und den MCP-Server anschließend direkt über die Benutzeroberfläche neu zu initialisieren, ohne die gesamte Anwendung neu starten zu müssen:

1. Wenn Sie einen MCP auswählen, der `customUserVars` verwendet, können Sie den Wert einer `customUserVar` für den ausgewählten MCP-Server direkt über das MCP-Panel **speichern** (**Save**) oder **widerrufen** (**Revoke**).
2. Nachdem Sie einen Wert für eine `customUserVar` gespeichert haben, klicken Sie auf die Schaltfläche zum Neuinitialisieren (ein Symbol mit kreisförmigen Pfeilen neben jedem Servernamen im MCP Panel).
3. LibreChat wird versuchen, eine Verbindung zum Server unter Verwendung Ihrer bereitgestellten Anmeldedaten herzustellen, und Sie über eine Toast-Benachrichtigung darüber informieren, ob der Neuinitialisierungsprozess erfolgreich war oder fehlgeschlagen ist.

> _Tipp: Wenn Sie wissen, dass ein Server Anmeldedaten erfordert, die beim ersten Start nicht verfügbar sind, können Sie `startup: false` zu seiner Konfiguration hinzufügen. Dies weist LibreChat an, nicht zu versuchen, eine Verbindung zu diesem Server herzustellen, bis er manuell in der Benutzeroberfläche neu initialisiert wird._

**Beispiel:**

```yaml
mcpServers:
  github-mcp:
    type: streamable-http
    url: 'https://api.githubcopilot.com/mcp/'
    headers:
      Authorization: '{{PAT_TOKEN}}'
    customUserVars:
      PAT_TOKEN:
        title: 'GitHub PAT Token'
        description: 'GitHub Personal Access Token'
    startup: false
```

### OAuth-Authentifizierung [#oauth-authentication]

LibreChat unterstützt OAuth-Authentifizierung für MCP-Server, gemäß der Empfehlung von Anthropic für sichere MCP-Verbindungen. OAuth bietet eine standardisierte, sichere Methode zur Authentifizierung, ohne dass langlebige Anmeldeinformationen gespeichert werden müssen.

#### Unterstützte OAuth-Flows [#supported-oauth-flows]

LibreChat MCP-Server unterstützen OAuth 2.0 mit:

- **Authorization Code Flow with PKCE**: Empfohlen für maximale Sicherheit
- **Client Discovery**: Automatische Client-Registrierung, wenn vom OAuth-Anbieter unterstützt
- **Refresh Tokens**: Automatische Token-Erneuerung, sofern verfügbar
- **Token endpoint discovery**: Vorkonfigurierte Clients können ermitteln, ob der Anbieter Client-Anmeldeinformationen im POST-Body oder in einem HTTP Basic Authorization-Header erwartet.

Im MCP Builder bietet die **Token Exchange Method** die Optionen **Auto**, **Default (POST request)** und **Basic authorization header**. Auto lässt die Methode nicht festgelegt, sodass LibreChat vertrauenswürdige Anbieter-Metadaten verwenden kann, wobei auf die Basic-Authentifizierung zurückgegriffen wird, wenn der Anbieter keine Methode angibt.

#### Konfigurationsbeispiele [#configuration-examples]

```yaml
mcpServers:
  # Public remote MCP server for PayPal, uses OAuth Client Discovery
  # ❌ Refresh Tokens: you may need to re-authenticate periodically
  # More info: https://developer.paypal.com/tools/mcp-server/
  paypal:
    type: 'sse'
    initTimeout: 150000 # higher timeout to allow for initial authentication
    url: 'https://mcp.paypal.com/sse'

  # Example self-hosted remote MCP server for Spotify, uses OAuth Client Discovery
  # ✅ Refresh Tokens: refreshes token for authentication automatically
  # Hosted on Cloudflare Workers, more info: https://github.com/LibreChat-AI/spotify-mcp
  spotify:
    type: 'streamable-http'
    initTimeout: 150000
    url: 'https://mcp-spotify-oauth-example.account.workers.dev/mcp'
```

#### OAuth-Authentifizierungsablauf [#oauth-authentication-flow]

Wenn Sie zum ersten Mal einen OAuth-fähigen MCP-Server konfigurieren:

1. **Anfängliche Verbindung**: LibreChat versucht, eine Verbindung zum MCP Server herzustellen
2. **Authentifizierung erforderlich**: Wenn kein gültiges Token vorhanden ist, sehen Sie einen OAuth-Authentifizierungsstatus für diesen Server in der **+**-Palette des Composers.
3. **Anmeldung starten**: Wählen Sie den Server aus, um den OAuth-Ablauf zu beginnen
4. **Fortfahren oder ein anderes Gerät verwenden**: Fahren Sie im aktuellen Browser fort, kopieren Sie den Autorisierungslink oder lassen Sie sich einen QR-Code anzeigen, um diesen auf einem anderen Gerät zu öffnen
5. **Browser-Weiterleitung**: Schließen Sie die Authentifizierung beim OAuth-Anbieter ab
6. **Rückgabe-Verarbeitung**: LibreChat verarbeitet den OAuth-Callback automatisch, sobald Sie sich authentifiziert haben
7. **Token-Speicherung**: LibreChat speichert die Tokens sicher für die zukünftige Verwendung
8. **Verbindung hergestellt**: Sobald Sie sich authentifiziert haben, wird der MCP Server verbunden und Sie können ihn in Ihrem Chat verwenden

#### OAuth Callback-URL [#oauth-callback-url-1]

Wenn ein MCP-Server OAuth verwendet, stellt LibreChat einen Callback-endpoint bereit, zu dem der OAuth-Anbieter nach erfolgreicher Autorisierung weiterleitet.

Die Callback-URL muss folgendem Format entsprechen:

`${baseUrl}/api/mcp/${serverName}/oauth/callback`

Wobei `${serverName}` der MCP-Server-Schlüssel ist, der in Ihrer `librechat.yaml`-Konfiguration definiert wurde. LibreChat übernimmt die Weiterleitung an diesem endpoint, schließt den Token-Austausch ab und verknüpft die Anmeldedaten mit dem entsprechenden MCP-Server.

<Callout type="info" title="Beispiel für OAuth-Callback-URL">
Gegeben die folgende MCP server Konfiguration:

```yaml
mcpServers:
  # Example self-hosted remote MCP server for Spotify, uses OAuth Client Discovery
  # ✅ Refresh Tokens: refreshes token for authentication automatically
  # Hosted on Cloudflare Workers, more info: https://github.com/LibreChat-AI/spotify-mcp
  spotify:
    type: 'streamable-http'
    initTimeout: 150000
    url: 'https://mcp-spotify-oauth-example.account.workers.dev/mcp'
```

Die Callback-URL wäre `${baseUrl}/api/mcp/spotify/oauth/callback`.

</Callout>

Hinweis:

- Die Callback-URL muss exakt beim OAuth-Anbieter registriert sein, damit der Ablauf funktioniert.
- Andere Pfade wie `/api/oauth/callback` oder `/api/oauth/openid/callback` sind für MCP OAuth-Abläufe nicht gültig.

#### Token-Verwaltung [#token-management]

LibreChat verarbeitet OAuth-Token intelligent:

- **Sichere Speicherung**: Tokens werden verschlüsselt und sicher gespeichert
- **Automatische Aktualisierung**: Wenn Refresh-Tokens verfügbar sind, erneuert LibreChat automatisch abgelaufene Access-Tokens.
- **Stumme 401-Wiederherstellung**: Wenn eine OAuth MCP-Verbindung während einer Sitzung eine Authentifizierungsablehnung erhält, koordiniert LibreChat einen begrenzten Aktualisierungs- und Wiederverbindungsversuch pro Benutzer und Server. Gleichzeitige Aufrufer teilen sich dieses Wiederherstellungsergebnis, bevor LibreChat eine neue Authentifizierungsaufforderung anzeigt.
- **Sitzungsverwaltung**: Jeder Benutzer unterhält seine eigenen OAuth-Sitzungen für Multi-User-Umgebungen

Wenn ein gespeicherter Agent-Stream neu geladen oder fortgesetzt wird, während eine MCP-Autorisierungsaufforderung noch aussteht, rekonstruiert LibreChat diese Aufforderung aus dem persistenten Generierungsstatus. Abgeschlossene, abgebrochene, fehlgeschlagene oder abgelaufene Aufforderungen werden nicht wiederhergestellt.

Gespeicherte OAuth-Clients und -Token sind an die MCP-Server-URL sowie die OAuth-Client-/endpoint-Einstellungen gebunden. Das Ändern dieser Einstellungen erfordert eine erneute Authentifizierung der Benutzer. Wenn Sie einen über die Benutzeroberfläche erstellten Server bearbeiten, der ein gespeichertes `client_secret` beibehält, geben Sie das Secret erneut ein, wenn Sie ein Bindungsfeld wie die Server-URL, die Client-ID, die Autorisierungs-URL, die Token-URL oder die Token-Authentifizierungsmethode ändern.

Bei horizontal skalierten Bereitstellungen können der Status des OAuth-Flows und die Bereitschaft gebundener Token über LibreChat-Pods hinweg abgeglichen werden. Die Benutzeroberfläche meldet einen Server erst dann als bereit, wenn die Initialisierung nach dem OAuth erfolgreich war, selbst wenn der Callback und die Statusabfrage unterschiedliche Pods erreichen. Callbacks von überholten Versuchen werden abgelehnt.

Wenn Redis aktiviert ist, werden MCP-Kataloggenerierungen und Publikationsrevisionen auf Anwendungsebene über Replikate hinweg koordiniert. Redis Cluster-Bereitstellungen verwenden Slot-sichere Katalogschlüssel und -aktualisierungen, sodass für die Start-Synchronisierung und `tools/list_changed`-Aktualisierungen kein Single-Node Redis-Layout erforderlich ist.

Jeder Benutzer wird bei der ersten Verwendung eines OAuth-fähigen MCP-Servers dazu aufgefordert, sich mit seinem eigenen OAuth-Login zu authentifizieren. Dies stellt sicher, dass Verbindungs- und Authentifizierungsdetails für jeden Benutzer eindeutig sind, wodurch Sicherheit und Datenschutz in Umgebungen mit mehreren Benutzern gewahrt bleiben.

#### OAuth-Timing [#oauth-timing]

Die MCP OAuth-Vervollständigung verwendet ihr eigenes, vom Server konfiguriertes Timeout, anstatt das `initTimeout` des MCP-Servers wiederzuverwenden. Standardmäßig wartet LibreChat bis zu 10 Minuten darauf, dass ein Benutzer die MCP OAuth abschließt, und behält den Flow-Status für 15 Minuten bei.

Verwenden Sie diese Umgebungsvariablen, wenn ein OAuth-Anbieter oder Benutzer-Workflow mehr Zeit benötigt:

```bash filename=".env"
MCP_OAUTH_HANDLING_TIMEOUT=600000
MCP_OAUTH_FLOW_TTL=900000
```

`MCP_OAUTH_FLOW_TTL` wird so begrenzt, dass es `MCP_OAUTH_HANDLING_TIMEOUT` überdauert, damit Callbacks nahe der Frist ihren Flow-Status weiterhin finden können. Das Polling-Fenster der MCP-Server-Karte folgt dem konfigurierten Handling-Timeout.

![Benutzerspezifischer OAuth-Authentifizierungsablauf](/images/agents/mcp_oauth_flow.png)

> Hinweis: Die beim App-Start angezeigten Tokens dienen nur der Initialisierung auf App-Ebene und werden nicht für individuelle Benutzerverbindungen verwendet.

Beispiel für die automatische Token-Aktualisierung:

```bash
[MCP][spotify] Access token missing
[MCP][spotify] Attempting to refresh token
[MCP][spotify] Successfully refreshed and stored OAuth tokens
[MCP][spotify] ✓ Initialized
```

#### Bewährte Methoden [#best-practices]

1. **OAuth verwenden, wenn verfügbar**: Bevorzugen Sie OAuth gegenüber API-Schlüsseln für eine bessere Sicherheit
2. **Geeignete Timeouts konfigurieren**: Verwenden Sie `MCP_OAUTH_HANDLING_TIMEOUT` und `MCP_OAUTH_FLOW_TTL` für OAuth-Abschlussfenster; verwenden Sie `initTimeout` für die Serverinitialisierung
3. **Token-Ablauf überwachen**: Überprüfen Sie die Protokolle auf Authentifizierungsprobleme
4. **Plan für die erneute Authentifizierung**: Einige Anbieter unterstützen keine Refresh-Tokens

## Server-Transporte [#server-transports]

MCP-Server können so konfiguriert werden, dass sie verschiedene Transportmechanismen verwenden:

**STDIO-Server**

- Eignet sich gut für lokale Einzelbenutzerumgebungen
- Nicht skalierbar für Remote- oder Cloud-Bereitstellungen
- Das gebündelte MCP SDK begrenzt jede einzelne STDIO-Nachricht auf 10 MB. Ein größeres Einzelergebnis schließt den Transport mit einem Fehler; dieses Limit ist unabhängig von der Gesamtgröße einer Sitzung oder eines Streams.

**Server-Sent Events (SSE) Server**

- Remote-Transport-Mechanismus, aber nicht für die Produktionsumgebung empfohlen

**Streamable HTTP-Server**

- Verwendet HTTP POST zum Senden von Nachrichten und unterstützt Streaming-Antworten
- Arbeitet als unabhängiger Prozess, der mehrere Client-Verbindungen verarbeiten kann
- Unterstützt sowohl einfache Anfragen als auch Streaming über Server-Sent Events (SSE)
- Leistungsfähigere Alternative zum herkömmlichen HTTP+SSE-Transport
- Unterstützt ordnungsgemäße Multi-User-Serverkonfigurationen

**Für Produktionsumgebungen** werden nur MCP-Server mit ["Streamable HTTP"-Transporten](https://modelcontextprotocol.io/specification/draft/basic/transports/streamable-http) empfohlen. Im Gegensatz zu SSE, das langlebige Verbindungen aufrechterhält, bietet Streamable HTTP zustandslose Optionen, die sich besser für skalierbare Multi-User-Bereitstellungen eignen.

LibreChat ist führend bei der Implementierung flexibler, skalierbarer MCP-Server-Integrationen, um vielfältige Nutzungsszenarien zu unterstützen und Ihnen dabei zu helfen, die KI-Workflows von morgen zu erstellen.
