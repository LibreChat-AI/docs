# Agenci: Tworzenie własnych asystentów AI [#agents-build-custom-ai-assistants]

Funkcja AI Agents w LibreChat zapewnia elastyczny framework do tworzenia niestandardowych asystentów AI obsługiwanych przez różnych dostawców modeli.

Ta funkcja jest podobna do OpenAI Assistants API oraz GPTs w ChatGPT, ale oferuje szersze wsparcie dla modeli i implementację bez użycia kodu (no-code), co pozwala na tworzenie zaawansowanych asystentów ze specjalistycznymi możliwościami.

## Wprowadzenie [#getting-started]

Aby utworzyć nowego agenta, wybierz "Agents" z menu endpoint i otwórz panel Agent Builder znajdujący się w panelu bocznym (Side Panel).

![Agenci - Menu endpointów](/images/agents/endpoints_menu.png)

Formularz tworzenia zawiera:

- **Avatar**: Prześlij własny awatar, aby spersonalizować swojego agenta
- **Nazwa**: Wybierz charakterystyczną nazwę dla swojego agenta
- **Opis**: Opcjonalne szczegóły dotyczące celu Twojego agenta
- **Instructions**: Instrukcje systemowe, które definiują zachowanie Twojego agenta
- **Model**: Wybierz spośród dostępnych dostawców i modeli
- **Conversation Starters**: Do czterech sugerowanych promptów wyświetlanych, gdy użytkownik rozpoczyna nowy czat z agentem

Kontrolki **Tools** i **Skills** otwierają przeszukiwalne biblioteki wbudowanych funkcji, narzędzi, serwerów MCP, akcji (Actions) oraz umiejętności (Skills). Wybierz element, aby go skonfigurować, a następnie zapisz agenta.

**Istniejące agenty można wybrać z górnego menu rozwijanego w Panelu bocznym.**

- **Również poprzez wzmiankę za pomocą "@" w polu wprowadzania czatu.**

![Agenci - Wzmianka](/images/agents/mention.png)

### Biblioteka narzędzi [#tool-library]

Kreator Agentów (Agent Builder) utrzymuje włączone elementy w oddzielnych sekcjach **Narzędzia** (Tools) i **Umiejętności** (Skills). Otwórz **Dodaj narzędzia** (Add tools), aby przeszukać pełny katalog lub przefiltrować go według kategorii **Oficjalne** (Official), **Narzędzia** (Tools), **MCP** lub **Akcje** (Actions). Sekcja **Stworzone przez Ciebie** (Made by you) gromadzi serwery MCP oraz Akcje, które utworzyłeś, podczas gdy **Ulubione** (Favorites) przechowuje oznaczone gwiazdką elementy, dzięki czemu są one dostępne dla wszystkich agentów. Każdy użytkownik może zapisać do 100 ulubionych elementów w bibliotece narzędzi.

Wybierz element, aby go skonfigurować bez opuszczania kreatora. Menu **Create new** pojawia się tylko wtedy, gdy użytkownik ma uprawnienia do tworzenia serwerów MCP lub Akcji (Actions). Usunięcie funkcji opartej na plikach, takiej jak File Search, File Context lub Code Interpreter, otwiera menedżer plików, jeśli nadal istnieją załączone pliki wymagające sprawdzenia. Funkcja oparta na plikach pozostaje zaznaczona i jest zachowywana przy zapisie, dopóki posiada przypisane pliki; usuń lub przypisz ponownie te pliki przed usunięciem samej funkcji.

Umiejętności (Skills) korzystają z własnego selektora i mogą być wybierane indywidualnie lub włączane jako cały dostępny katalog. Zobacz [Skills](/docs/features/skills#agent-scope).

Operatorzy mogą również korzystać z eksperymentalnych [Agent Plugins](/docs/features/agent_plugins), aby łączyć umiejętności wdrożeniowe (Skills) i serwery MCP w pakiety ładowane podczas uruchamiania.

### Konfiguracja modelu [#model-configuration]

Interfejs parametrów modelu umożliwia dostrajanie odpowiedzi twojego agenta:

- Temperature (skala 0-1 dla kreatywności odpowiedzi)
- Maksymalna liczba tokenów kontekstu
- Maksymalna liczba tokenów wyjściowych
- Szczegółowość obrazu (`low`, `auto` lub `high`) dla natywnych wejść obrazu typu vision
- Dodatkowe ustawienia specyficzne dla dostawcy

Instrukcje agenta mogą wykorzystywać `{{current_date}}`, `{{current_datetime}}` oraz `{{iso_datetime}}`. LibreChat rozwiązuje je na podstawie zarejestrowanego przez serwer początku tury logicznej i utrzymuje ten znacznik czasu jako stały w trakcie pętli dostawcy, inicjalizacji Subagent oraz wznawiania przez człowieka (human-in-the-loop). Pierwsze dwa używają strefy czasowej żądania; `{{iso_datetime}}` pozostaje w formacie UTC.

Rozpoznane błędy typu model-not-found oraz błędy limitu szybkości (rate-limit) dostawcy wyświetlają zlokalizowane wskazówki. Inne błędy dostawcy zachowują przydatny tekst dostawcy, ale pomijają adresy URL rozwiązywania problemów LangChain przed utrwaleniem wiadomości. Gdy [model-bound content protection](/docs/configuration/librechat_yaml/object_structure/message_filter#source-aware-filters) jest włączone, jego ogólny błąd ochrony nadal ma pierwszeństwo.

### Historia wersji [#version-history]

Użytkownicy z dostępem do edycji mogą otworzyć **Version History** (Historię wersji) w kreatorze Agent Builder, aby przejrzeć zapisane konfiguracje na osi czasu. Każdy wpis pokazuje, kiedy został zapisany oraz podsumowuje użyte narzędzia i możliwości. Przywrócenie wcześniejszego wpisu wymaga potwierdzenia i zastępuje bieżącą konfigurację agenta tym zapisanym stanem. Zapisywanie zawsze stosuje bieżące zmiany agenta, nawet jeśli wynikowa konfiguracja jest zgodna z najnowszym wpisem w historii, a LibreChat nie dodaje zduplikowanego wpisu.

### Rozmówcy (Conversation Starters) [#conversation-starters]

Początkowe komunikaty (conversation starters) dają użytkownikom szybki sposób na rozpoczęcie czatu z agentem. Każdy agent może przechowywać ich maksymalnie cztery.

1. W Agent Builder znajdź pole **Conversation Starters**.
2. Wpisz prompt i naciśnij **Enter** lub wybierz przycisk **+**. Pole wprowadzania zostanie zablokowane po dodaniu czterech elementów startowych.
3. Edytuj zapisany starter w miejscu lub wybierz jego przycisk **X**, aby go usunąć.
4. Zapisz agenta.

Gdy użytkownik otwiera nowy czat z agentem, startery pojawiają się jako przyciski na pustym ekranie czatu. Wybranie jednego z nich powoduje jego natychmiastowe wysłanie jako pierwszej wiadomości. Jeśli agent posiada startery, mają one pierwszeństwo przed wszelkimi [`conversation_starters`](/docs/configuration/librechat_yaml/object_structure/model_specs#conversation_starters) zdefiniowanymi w używanej specyfikacji modelu (Model Specs). Startery pojawiają się również w oknie szczegółów agenta w [Marketplace](#agent-marketplace).

## Możliwości agenta [#agent-capabilities]

> **Uwaga:** Wszystkie możliwości można przełączać za pomocą pliku konfiguracyjnego `librechat.yaml`. Więcej informacji znajduje się w [docs/configuration/librechat_yaml/object_structure/agents#capabilities](/docs/configuration/librechat_yaml/object_structure/agents#capabilities).

### Code Interpreter [#code-interpreter]

Po włączeniu, funkcja Code Interpreter pozwala Twojemu agentowi na:

- Wykonuj kod w wielu językach, w tym:
  - Python, JavaScript, TypeScript, Go, C, C++, Java, PHP, Rust oraz Fortran
- Przetwarzaj pliki bezpiecznie za pomocą API Code Interpreter w LibreChat
- Uruchamiaj kod bez lokalnej konfiguracji, ustawień czy wdrażania środowiska piaskownicy (sandbox)
- Płynna obsługa przesyłania i pobierania plików
- [Więcej informacji o API Code Interpreter](/docs/features/code_interpreter)
  - **Obsługiwane przez usługę open-source [code-interpreter](https://github.com/ClickHouse/code-interpreter) (hostowaną samodzielnie)**

Gdy którykolwiek z wymaganych plików Code Interpreter z konwersacji nie zostanie przywrócony w bieżącym środowisku piaskownicy (sandbox), LibreChat zatrzymuje Agenta przed wywołaniem modelu i prosi użytkownika o ponowne dołączenie plików. Zapobiega to kontynuowaniu działania z nieaktualnymi lub niedostępnymi odwołaniami do plików.

Gdy pliki konwersacji mają tę samą nazwę pliku w Code Interpreter, LibreChat przypisuje im odrębne miejsca docelowe w piaskownicy (sandbox) i przekazuje Agentowi rozpoznane ścieżki. Zobacz [Seamless File Handling](/docs/features/code_interpreter#seamless-file-handling), aby dowiedzieć się więcej o zachowaniu w przypadku kolizji oraz o pozostałych ograniczeniach dotyczących prywatnych plików w środowisku multi-Agent.

#### Stanowe sesje kodu [#stateful-code-sessions]

Sesje kodu typu stateful pozwalają agentowi na ponowne wykorzystanie środowiska piaskownicy (sandbox) w trakcie wykonywania kodu. Pliki, zainstalowane pakiety oraz stan pracy są zazwyczaj zachowywane, co jest przydatne w przypadku analizy iteracyjnej oraz wieloetapowej pracy z plikami. W kreatorze Agent Builder selektor **Stateful environment** określa, kto współdzieli to środowisko:

- **Obszar roboczy użytkownika (zalecane):** stanowe agenty zalogowanego użytkownika współdzielą jeden obszar roboczy
- **Obszar roboczy agenta + użytkownika:** każdy użytkownik otrzymuje oddzielny obszar roboczy dla każdego agenta
- **Obszar roboczy konwersacji:** każdy użytkownik otrzymuje oddzielny obszar roboczy dla każdej konwersacji

Administratorzy mogą również konfigurować nazwane backendy w sekcji [`statefulCodeSessions.environments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions). Gdy są one obecne, osobny selektor **Execution environment** pozwala wybrać zarządzane API kodu (Code API), maszynę wirtualną podłączoną do operatora lub osobistego pracownika (worker), który posiada przestrzeń roboczą; **Deployment default** używa skonfigurowanego domyślnego środowiska wykonywalnego. Zakres udostępniania powyżej pozostaje niezależny od tego wyboru backendu.

Gdy wdrożenie umożliwia korzystanie z samoobsługowych workerów, użytkownicy z uprawnieniami do zarządzania Code Environment mogą otworzyć **Settings > Code environments**, aby sparować wychodzącego workera `@librechat/code` na własnej maszynie wirtualnej, wybrać go w Agent Builderze, a później cofnąć jego uprawnienia. Środowiska osobiste są przypisane do właściciela i korzystają z tej samej ścieżki dla kodu, powłoki (shell) oraz Programmatic Tool Calling. Zobacz [Attached environments and pairing](/docs/features/code_interpreter#attached-environments-and-pairing), aby zapoznać się z eksperymentalną konfiguracją i modelem bezpieczeństwa.

W ramach dołączonego obszaru roboczego (workspace), Agenci mogą wyświetlać katalogi, czytać pliki, przeszukiwać tekst, tworzyć pliki oraz uruchamiać Bash za pośrednictwem wybranego procesu roboczego (worker). Indywidualna nazwa i adres e-mail Git przypisane do Agenta mogą identyfikować dokonane tam commity bez konieczności podawania danych uwierzytelniających repozytorium. Wdrożenia mogą ograniczać liczbę nowych osobistych procesów roboczych za pomocą [`statefulCodeSessions.principalWorkers`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions).

Gdy podłączony worker zgłasza wiele katalogów głównych obszaru roboczego (workspace roots), kompozytor czatu wymaga dokonania wyboru dla każdego podłączonego środowiska używanego przez Agenta lub jego Podagenty. Konwersacja zachowuje te wybory pomiędzy turami oraz wznawianiem zatwierdzeń; LibreChat weryfikuje je w odniesieniu do aktywnego workera i blokuje wysyłanie, jeśli wymagany obszar roboczy jest brakujący lub niedostępny. Worker, który zgłasza dokładnie jeden obszar roboczy, jest wybierany automatycznie dla nowej konwersacji. Zobacz [Attached environments and pairing](/docs/features/code_interpreter#attached-environments-and-pairing), aby uzyskać szczegółowe informacje oraz poznać bieżące ograniczenia.

Nowi Agenci początkowo korzystają z **Domyślnego stanowego obszaru roboczego** zalogowanego użytkownika, dostępnego w **Ustawienia > Kontrola danych > Wykonywanie kodu**. Osobistym ustawieniem domyślnym jest **Obszar roboczy użytkownika**, dopóki nie zostanie ono zmienione. Aktualizacja tej preferencji nie zmienia istniejących Agentów ani nie włącza samodzielnie Stanowych sesji kodu. Administratorzy mogą ograniczyć dostępne zakresy za pomocą [`statefulCodeSessions.allowedEnvironments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions); gdy zapisane osobiste ustawienie domyślne przestaje być dozwolone, nowi Agenci korzystają z pierwszego dozwolonego zakresu.

<Callout type="warning" title="Wysoce eksperymentalne">
  Stateful Code Sessions znajdują się w fazie wczesnych eksperymentów. Ich zachowanie, konfiguracja, charakterystyka trwałości oraz podstawowa integracja mogą ulec znaczącym zmianom. Nie należy traktować obecnej implementacji jako stabilnego kontraktu produkcyjnego.
</Callout>

Ta funkcja jest opcjonalna (opt-in). Administrator musi dodać `stateful_code_sessions` do [możliwości agenta](/docs/configuration/librechat_yaml/object_structure/agents#capabilities) i skonfigurować dedykowaną trasę dla stanowego interpretera kodu (Stateful Code Interpreter) poprzez [`LIBRECHAT_CODE_BASEURL_STATEFUL`](/docs/configuration/dotenv#stateful-code-interpreter-endpoint) lub nazwane [`statefulCodeSessions.environments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions). Interpreter kodu musi być włączony dla agenta, a opcja **Stateful code sessions** musi być aktywna w jego ustawieniach zaawansowanych (Advanced settings).

Żądania stanowe (stateful) nie przełączają się automatycznie na standardowy bezstanowy (stateless) endpoint Code Interpreter, gdy dedykowany adres URL jest niedostępny lub niekompatybilny. Sesje stanowe i bezstanowe nie współdzielą również aktywnych plików ani zainstalowanych pakietów. Przestrzeń robocza (workspace) stanowa może zostać zresetowana w dowolnym momencie, niezależnie od jej zakresu. W zarządzanych środowiskach Code Interpreter ważne dane wyjściowe należy zapisywać w katalogu `/mnt/data`; podłączona przestrzeń robocza jest oddzielnym katalogiem należącym do procesu roboczego (worker). Przesłane w czacie pliki nie są domyślnie kopiowane do tego podłączonego katalogu. Nie należy polegać na stanie sesji jako trwałym magazynie danych.

Kiedy stanowe narzędzia `create_file` lub `edit_file` tworzą pliki podczas generowania odpowiedzi, wiadomość asystenta wyświetla kompaktowy wiersz **Workspace changes**. Rozwiń go, aby przejrzeć unikalne zmienione ścieżki i pobrać każdy plik za pośrednictwem uwierzytelnionego przepływu plików LibreChat. Jest to rejestr plików utworzonych przez te narzędzia dla poszczególnych wiadomości, a nie trwały zrzut całego obszaru roboczego; bezstanowe dane wyjściowe Code Interpreter nadal korzystają ze zwykłego interfejsu załączników w tekście.

W przypadku podłączonych środowisk, kompozytor może udostępnić opcje **Ask before changes** (Pytaj przed zmianami), **Accept edits** (Akceptuj edycje) oraz **Full access** (Pełny dostęp) jako tryb zatwierdzania kodu na poziomie konwersacji. Dostępność jest ograniczona przez zdefiniowany przez administratora schemat uprawnień środowiska; wybór bardziej permisywnego trybu nigdy nie nadpisuje uprawnień roli, jawnych reguł narzędzi, hooków ani ograniczeń piaskownicy (sandbox). Zobacz [Attached-environment tool permissions](/docs/features/code_interpreter#attached-environment-tool-permissions).

### Wyszukiwanie plików [#file-search]

Funkcja File Search umożliwia:

- Funkcjonalność RAG (Retrieval-Augmented Generation)
- Wyszukiwanie semantyczne w przesłanych dokumentach
- Odpowiedzi uwzględniające kontekst na podstawie zawartości plików
- Obsługa załączników plików zarówno na poziomie agenta, jak i wątku czatu

### Kontekst pliku [#file-context]

Funkcja File Context umożliwia Twojemu agentowi przechowywanie wyodrębnionego tekstu z plików jako części jego instrukcji systemowych:

- Wyodrębnij tekst, zachowując strukturę i formatowanie dokumentu
- Przetwarzaj złożone układy, w tym tekst wielokolumnowy i treści mieszane
- Obsługa tabel, równań i innych specjalistycznych treści
- Praca z treściami wielojęzycznymi
- Tekst jest przechowywany w instrukcjach agenta w bazie danych
- **Nie jest wymagana usługa OCR** – Domyślnie wykorzystuje parsowanie tekstu z metodami zastępczymi
- **Ulepszone przez OCR** - Jeśli OCR jest skonfigurowany, jakość ekstrakcji poprawia się dla obrazów i zeskanowanych dokumentów
- Wykorzystuje tę samą logikę przetwarzania co „Prześlij jako tekst”: **OCR > STT > parsowanie tekstu**
- [Więcej informacji o konfiguracji OCR](/docs/features/ocr)

**Uwaga:** Kontekst pliku zawiera wyodrębniony tekst w instrukcjach systemowych agenta. W przypadku pytań dotyczących dokumentów tymczasowych w poszczególnych konwersacjach, użyj opcji [Upload as Text](/docs/features/upload_as_text) bezpośrednio z poziomu czatu.

### Model Context Protocol (MCP) [#model-context-protocol-mcp]

MCP to otwarty protokół, który standaryzuje sposób, w jaki aplikacje dostarczają kontekst dużym modelom językowym (LLM), działając jak uniwersalny adapter dla narzędzi AI i źródeł danych.

Aby uzyskać więcej informacji, zobacz dokumentację dotyczącą [MCP](/docs/features/mcp).

#### Agenci z narzędziami MCP [#agents-with-mcp-tools]

1. Skonfiguruj serwery MCP w pliku `librechat.yaml`
2. Zrestartuj LibreChat, aby zainicjować połączenia
3. Utwórz lub edytuj agenta
4. Otwórz **Add tools** w Agent Builder i wybierz **MCP**
5. Wybierz serwer(y) MCP, które chcesz dodać; każdy serwer pojawia się jako pojedynczy wpis
6. Zapisz zmiany w agencie

W tym przykładzie dodaliśmy **[serwer Spotify MCP](https://github.com/LibreChat-AI/spotify-mcp)** do agenta.

![Agenci - MCP](/images/agents/mcp_tools_v2.png)

#### Zarządzanie narzędziami MCP [#managing-mcp-tools]

Gdy serwer MCP zostanie dodany do agenta, możesz precyzyjnie dostosować, które konkretne narzędzia będą dostępne:

- Po dodaniu serwera MCP, rozwiń go, aby zobaczyć wszystkie dostępne narzędzia
- Zaznacz/odznacz poszczególne narzędzia w razie potrzeby
- Na przykład serwer MCP Spotify udostępnia około 20 narzędzi (wyszukiwanie, sterowanie odtwarzaniem, zarządzanie playlistami itp.)
- Ta szczegółowa kontrola pozwala ograniczyć agentom dostęp tylko do narzędzi, których potrzebują

Serwery o zasięgu żądania (request-scoped), które używają `{{LIBRECHAT_BODY_*}}`, nie mogą wyliczyć narzędzi, dopóki sesja czatu nie dostarczy tych wartości. Dlatego Agent Builder pokazuje jeden wybór narzędzi uruchomieniowych (runtime-tools) dla całego serwera zamiast przełączników dla każdego narzędzia; wyczyszczenie tego wyboru powoduje odłączenie serwera. Po autoryzacji OAuth, LibreChat zachowuje autoryzację i czeka na pierwsze kwalifikujące się uruchomienie, aby nawiązać połączenie.

Jeśli Agent jawnie wybierze narzędzia MCP, ale żadne z nich nie może zostać rozpoznane w momencie rozpoczęcia uruchomienia, LibreChat zatrzymuje uruchomienie, wyświetlając wskazówki dotyczące połączenia i dostępu, zamiast kontynuować pracę bez nich w sposób niezauważalny. Należy ponownie połączyć się lub uwierzytelnić serwer, zweryfikować dostęp do narzędzi i ponowić uruchomienie.

### Odroczone narzędzia [#deferred-tools]

Odroczone narzędzia (deferred tools) pozwalają agentom na dostęp do wielu narzędzi MCP bez konieczności ładowania ich wszystkich do kontekstu LLM z wyprzedzeniem. Zamiast tego, odroczone narzędzia są wykrywalne w czasie wykonywania za pomocą mechanizmu **Wyszukiwania narzędzi** (Tool Search).

Jest to szczególnie przydatne, gdy agent ma dostęp do wielu serwerów MCP z dziesiątkami narzędzi — załadowanie ich wszystkich zajęłoby znaczną część okna kontekstowego i obniżyło jakość odpowiedzi.

**Jak to działa:**

- Narzędzia oznaczone jako "deferred" są wykluczone z początkowego kontekstu LLM
- Narzędzie `ToolSearch` jest dodawane automatycznie, umożliwiając LLM odkrywanie i ładowanie odroczonych narzędzi na żądanie.
- Po wykryciu narzędzie jest dostępne przez resztę konwersacji

**Konfigurowanie odroczonych narzędzi (deferred tools):**

1. Otwórz Agent Builder i dodaj narzędzia MCP
2. Kliknij menu rozwijane przy dowolnym narzędziu MCP
3. Przełącz „Defer Loading” (odroczone ładowanie) — odroczone narzędzia wyświetlają ikonę zegara

**Uwaga:** Funkcja `deferred_tools` jest domyślnie włączona. Można ją przełączać za pomocą konfiguracji agentów w pliku [`librechat.yaml`](/docs/configuration/librechat_yaml/object_structure/agents#capabilities).

### Grupy aktywności [#activity-groups]

Grupy aktywności zwijają każdy ciągły blok rozumowania agenta i wywołań narzędzi pod wygenerowanym nagłówkiem jednowierszowym, co ułatwia przeglądanie długich przebiegów. Administratorzy włączają je za pomocą `activityLabel` i mogą użyć szybszego modelu, innego skonfigurowanego endpoint, własnego promptu oraz limitów na uruchomienie. Generowanie nagłówka jest osobnym wywołaniem modelu, którego tokeny i koszt są rejestrowane. Zobacz [Agent Activity Groups](/docs/configuration/librechat_yaml/object_structure/shared_endpoint_settings#agent-activity-groups).

Administratorzy mogą niezależnie włączyć `activityPhaseLabel`, aby zawinąć dwie lub więcej logicznych aktywności w zwinięte podsumowanie nadrzędne przed udzieleniem ostatecznej odpowiedzi. Zapewnia to długim procesom bardziej ogólny zarys przy jednoczesnym zachowaniu każdej aktywności podrzędnej. Podsumowania faz wykorzystują własny model, endpoint, prompt oraz limit na uruchomienie, z mechanizmem fallback do etykiety aktywności (activity-label) i ustawień uruchomienia.

Gdy tylko ciągły przebieg zawiera co najmniej dwie ukończone, oznaczone grupy narzędzi, LibreChat zwija je do tej samej powierzchni karty fazy, jeszcze zanim nadejdzie opcjonalne podsumowanie fazy. Najnowsza ukończona etykieta podrzędna pełni funkcję tymczasowego nagłówka, podczas gdy aktywne wnioskowanie i trwające wywołanie narzędzia pozostają poza zwiniętym obszarem. Załadowana historia wykorzystuje to samo grupowanie, a późniejsze podsumowanie fazy wygenerowane przez serwer zastępuje tymczasowy nagłówek bez zamykania karty otwartej przez czytelnika.

Gdy [Smooth Streaming](/docs/features/smooth_streaming) jest włączone, nowo wygenerowane podsumowanie nadrzędne płynnie zwija widoczne aktywności do zwiniętej grupy. Załadowana historia nie odtwarza tego przejścia, a LibreChat respektuje ustawienie urządzenia dotyczące ograniczenia ruchu (reduced-motion).

Krótki tekst postępu pozostaje wewnątrz swojej fazy nadrzędnej. Gdy Agent rozpoczyna zasadniczą odpowiedź, LibreChat zamyka fazę przed tym tekstem, dzięki czemu wynik widoczny dla użytkownika pozostaje poza zwiniętym podsumowaniem. Jeden przebieg może utworzyć wiele faz nadrzędnych, gdy późniejsze wnioskowanie lub narzędzia rozpoczynają kolejny logiczny blok aktywności. Utrwalone granice faz są przeliczane, gdy błędne lub pominięte części zawartości są kompaktowane, dzięki czemu grupowanie pozostaje wyrównane po przeładowaniu.

Pliki utworzone wewnątrz fazy pozostają widoczne w wierszu multimediów pod zwiniętą kartą, zamiast być w niej ukryte. Odwołania do obrazów w formacie Markdown używające samej nazwy pliku, ścieżki `/mnt/data/...` lub `sandbox:` są rozwiązywane do pasujących załączników w turze. Plik jest pomijany w wierszu multimediów tylko wtedy, gdy obraz wbudowany poza zwiniętą fazą zostanie poprawnie rozwiązany, co zapobiega powielaniu bez polegania na błędnych odwołaniach.

Karty ogólnych agentów i narzędzi MCP rozróżniają fazę **Przygotowania** (przed przekazaniem do SDK, co może obejmować zatwierdzenie lub inne oczekiwanie) od fazy **Wywołania** (przekazanie do SDK aż do uzyskania wyniku). Ukończone karty pokazują oba interwały; interwał wywołania niekoniecznie odpowiada czasowi wykonania po stronie MCP lub ClickHouse. Wcześniej zapisane wiadomości oraz wyspecjalizowane karty Code, Bash, plików i pamięci zachowują wyraźnie oznaczoną wartość **Całkowity czas** trwania kroku wykonania. Zatrzymane, anulowane, nieudane i ukończone kroki zachowują odrębne statusy, również po przeładowaniu konwersacji.

Podczas działania narzędzia, rozwinięte panele szczegółów Bash, Execute Code oraz File Authoring podążają za przesyłanymi strumieniowo poleceniami, kodem lub podglądem zawartości do samego dołu. Przewinięcie w górę wstrzymuje to zachowanie, dzięki czemu bieżąca pozycja czytania zostaje zachowana.

Dane wyjściowe Bash są renderowane jako tekst w stylu terminala. Długie dane wyjściowe są zwijane do ostatnich 15 linii, w których zazwyczaj pojawiają się błędy; użyj **Pokaż więcej** i **Pokaż mniej**, aby je rozwinąć lub zwinąć, oraz przycisku **Kopiuj**, aby skopiować dane wyjściowe. Polecenie, które nie wyświetliło niczego, pokazuje **Brak danych wyjściowych**. W przypadku poleceń uruchamianych w [podłączonym obszarze roboczym](/docs/features/code_interpreter#attached-environments-and-pairing), nieudane polecenie jest oznaczone przyczyną (**kod wyjścia N**, **przerwano przez** sygnał taki jak `SIGKILL` lub **przekroczono limit czasu**), a stderr jest stylizowany oddzielnie od stdout. Zakończone polecenie jest oznaczone jako **Uruchomiono polecenie**, a grupa narzędzi zawierająca pojedyncze wywołanie otwiera się bezpośrednio ze szczegółami tego wywołania.

### Etykiety rozumowania na żywo [#live-reasoning-labels]

Etykiety rozumowania na żywo (live reasoning labels) zastępują ogólny nagłówek **Thinking** lub **Thoughts** krótką orientacją, która ewoluuje w miarę pojawiania się wystarczająco długich strumieni rozumowania najwyższego poziomu. Etykieta aktualizuje istniejący nagłówek rozumowania w miejscu jego wystąpienia; nie dodaje ani nie zmienia kolejności części wiadomości.

Najnowsza etykieta rozumowania na żywo oraz licznik czasu odpowiedzi migoczą, gdy trwa generowanie. Ustalony proces rozumowania, odpowiedzi starszych elementów oraz etykiety, które nie znajdują się już na końcu strumienia, pozostają statyczne.

Administratorzy włączają tę funkcję za pomocą `reasoningLabel` i mogą wybrać osobny model, endpoint, prompt, progi aktualizacji oraz limit wywołań na uruchomienie. Każda rewizja jest dodatkowym wywołaniem modelu, którego tokeny i koszt są rejestrowane. Zobacz [Live Reasoning Labels](/docs/configuration/librechat_yaml/object_structure/shared_endpoint_settings#live-reasoning-labels), aby uzyskać informacje o wartościach domyślnych, pierwszeństwie routingu i kwestiach prywatności.

### Etykiety intencji narzędzi [#tool-intent-labels]

Etykiety intencji narzędzi zastępują ogólne statusy narzędzi działających w czasie rzeczywistym krótkim opisem napisanym przez model dla danego wywołania. Administratorzy muszą dodać funkcję [agent capability](/docs/configuration/librechat_yaml/object_structure/agents#capabilities) typu `tool_intents`. Natywne narzędzia używają etykiet automatycznie; w kreatorze Agent Builder rozwiń serwer MCP i włącz **Intent label** dla poszczególnych narzędzi lub całego serwera.

W przypadku Model Specs, [`describeIntent`](/docs/configuration/librechat_yaml/object_structure/model_specs#describeintent) może włączyć każde kwalifikujące się narzędzie lub wybrać określone identyfikatory narzędzi. Pola intencji (intent fields) są dodawane do schematu narzędzi wysyłanego do modelu, więc selektywne włączanie może zmniejszyć narzut tokenów schematu.

Etykiety intencji nie mają zastosowania do narzędzi MCP działających wyłącznie programowo, ponieważ wywołania wykonywane wewnątrz kodu w piaskownicy (sandbox) nie renderują pojedynczych kart narzędzi. Rozszerzone wykonanie programowe wyświetla zamiast tego kompaktowy ślad na żywo (live trace) jego wewnętrznych wywołań.

### Programmatic Tool Calling [#programmatic-tool-calling]

Programmatic Tool Calling (PTC) pozwala agentom na wykonywanie wybranych narzędzi MCP z poziomu piaskownicy [Code Interpreter](/docs/features/code_interpreter), zamiast wywoływania każdego narzędzia bezpośrednio z modelu. Model otrzymuje narzędzie orkiestracji oparte na Code Interpreterze, pisze kod w piaskownicy, który wywołuje wygenerowane funkcje narzędzi, oraz może używać pętli, instrukcji warunkowych, ponownych prób i przetwarzania wyników przed zwróceniem odpowiedzi.

Jest to przydatne w wieloetapowych przepływach pracy narzędzi, takich jak odpytywanie kilku zasobów, stronicowanie wyników, porównywanie danych wyjściowych lub przekształcanie odpowiedzi narzędzi, zanim agent je wyjaśni.

**Konfigurowanie narzędzi programowych:**

1. Włącz zarówno `programmatic_tools`, jak i `execute_code` w [możliwościach agentów w `librechat.yaml`](/docs/configuration/librechat_yaml/object_structure/agents#capabilities).
2. Włącz Code Interpreter dla agenta.
3. Dodaj narzędzia MCP, rozszerz serwer MCP i przełącz opcję **Programmatic** dla poszczególnych narzędzi lub dla całego serwera. Narzędzia typu Programmatic są oznaczone ikoną kodu.

Kreator Agentów utrzymuje przełączniki programowe (Programmatic) wyłączone, dopóki nie zostanie wybrany Code Interpreter. Usunięcie Code Interpreter natychmiast czyści wybory programowe agenta. Podczas tworzenia, aktualizacji, duplikowania i przywracania wersji, serwer usuwa również opcje wywołań programowych, gdy funkcja `execute_code` lub narzędzie Code Interpreter są niedostępne; pozwala to na otwieranie i poprawianie starszych, niespójnych Agentów bez zachowywania bezużytecznej konfiguracji.

**Uwaga:** `programmatic_tools` jest funkcją opcjonalną i nie znajduje się na domyślnej liście możliwości agentów. PTC wymaga również wdrożenia Code Interpreter wraz z komponentem Tool Call Server. W czasie wykonywania LibreChat dokonuje przecięcia bieżącej projekcji możliwości obiektu wywołującego z zaufanym rejestrem narzędzi, więc dane zdarzenia mogą zawęzić dostępną mapę, ale nie mogą przyznać uprawnień do narzędzia. Z poziomu piaskownicy (sandbox) można wywoływać tylko aktywne, zarejestrowane narzędzia programistyczne; niezarejestrowane wywołania są odrzucane.

Rozwiń kartę Code Interpreter podczas uruchomienia programowego, aby zobaczyć ślad w stylu terminala dla każdego wywołania narzędzia wewnętrznego, podgląd jego argumentów, status, czas trwania oraz wszelkie błędy. Ślad jest dostępny na żywo podczas bieżącej sesji przeglądarki i nie jest przywracany po odświeżeniu strony.

### Wywołania narzędzi w tle [#background-tool-calls]

Wywołania narzędzi w tle (background tool calls) pozwalają agentowi na uruchomienie długotrwałego, kwalifikującego się narzędzia typu Code Interpreter, MCP, Plugin lub Action i kontynuowanie pracy. Początkowe wywołanie zwraca natychmiast odniesienie do zadania. W przypadku zapisanego agenta, obsługiwane uzupełnienia są domyślnie dostarczane automatycznie w ramach kontynuacji; `check_background_task` pozostaje dostępne w celu uzyskania jawnego statusu, kontroli, zbierania artefaktów oraz odzyskiwania danych.

`check_background_task` raportuje `started_at` oraz bieżące `elapsed_ms` podczas wykonywania pracy lokalnej procesu. Po zakończeniu raportuje również `settled_at` i zamraża `elapsed_ms` na wartości czasu trwania. Wynik końcowy odzyskany z trwałej pamięci może zawierać `settled_at` bez czasu rozpoczęcia lub czasu trwania, gdy oryginalny znacznik czasu wysłania lokalnego dla procesu jest niedostępny.

Aby skorzystać z tej funkcji, administrator musi dodać opcjonalną funkcję agenta `run_in_background` [agent capability](/docs/configuration/librechat_yaml/object_structure/agents#capabilities). Następnie należy skonfigurować odpowiednie narzędzia w Kreatorze Agentów (Agent Builder):

- **Code Interpreter:** Włącz Code Interpreter dla agenta. Wykonywanie kodu i polecenia powłoki stają się domyślnie kwalifikowalne do działania w tle; wyłącz **Background execution** w ustawieniach narzędzia, aby zrezygnować z tej opcji.
- **MCP:** Otwórz serwer MCP i oznacz poszczególne narzędzia lub cały serwer jako **Background**.
- **Narzędzia wtyczek:** Otwórz odpowiednie narzędzie i włącz **Background execution**.
- **Akcje:** Włącz **Wykonywanie w tle** (Background execution) dla Akcji, aby wyrazić zgodę na każdą kwalifikującą się operację w ramach tej Akcji. Akcje OAuth nie udostępniają tego przełącznika. Operacja jest również wykluczona, gdy jej własny schemat definiuje już parametr `run_in_background`, co pozwala uniknąć kolizji z flagą wysyłania (dispatch) LibreChat.

Te ustawienia umożliwiają wykonywanie w tle, ale go nie wymuszają. Model decyduje przy każdym wywołaniu, czy uruchomić kwalifikujące się narzędzie w tle.

W czacie LibreChat, gdy kod działający w tle kończy pracę, jego stdout oraz wygenerowane pliki pojawiają się przy oryginalnym wywołaniu kodu, a nie w późniejszym odpytaniu. Wygenerowane pliki są również zachowywane dla kolejnych tur rozmowy. Automatyczne kontynuacje prezentują ukończoną pracę w zwijanej karcie zadania „wake-up”, powiązanej z oryginalnym zadaniem.

Gdy serwer uruchamia tę kontynuację po zakończeniu poprzedniego działania na pierwszym planie, otwarta konwersacja dołącza się do nowej generacji i odświeża wynik ukończonego zadania bez konieczności przeładowania.

Automatyczne wybudzanie uzupełniania (completion wakeups) jest włączone, chyba że administrator ustawi [`endpoints.agents.backgroundTasks.completionWakeups: false`](/docs/configuration/librechat_yaml/object_structure/agents#backgroundtasks), co przywraca zachowanie oparte wyłącznie na odpytywaniu (poll-only). Host może łączyć kilka kwalifikujących się uzupełnień typu „tylko zawartość” w jedną kontynuację. Zadania generujące aktywny artefakt nadal wymagają odpytywania procesu, do którego należy dany przebieg (run).

Administratorzy mogą również zdecydować się na anulowanie w zakresie właściciela za pomocą [`endpoints.agents.backgroundTasks.ordinaryToolCancellation: true`](/docs/configuration/librechat_yaml/object_structure/agents#backgroundtasks). Zadanie zgłasza, że zażądano anulowania, dopóki podstawowe wywołanie nie zostanie zakończone, a jego przepustowość pozostaje zarezerwowana w tym przedziale czasowym. Anulowanie jest kooperacyjne: narzędzie, które ignoruje sygnał przerwania, może nadal zakończyć się pomyślnie. Kontrola ta ma zastosowanie do zwykłych narzędzi działających w tle w ramach procesu lokalnego, w tym do dołączonego Bash, ale nie do niezależnie posiadanych odłączonych Subagents.

Tylko kwalifikujące się narzędzia udostępniają to ustawienie. Zwykłe wykonywanie w tle jest lokalne dla procesu i nie przetrwa utraty swojego procesu roboczego. Jednakże, gdy wynik terminala zawierający tylko treść zostanie utrwalony, automatyczne dostarczanie staje się trwałe i może być kontynuowane na innej replice. Rejestr lokalny dla procesu ogranicza uruchomione zadania i zachowane ładunki wyników na konwersację, użytkownika i proces; usuwa zakończone prace, gdy jest to bezpieczne, i zwraca wynik o ograniczonej pojemności, gdy oczekujące przetwarzanie uniemożliwia bezpieczne usunięcie. Jeśli wywołanie ignoruje anulowanie, LibreChat przestaje odnawiać dzierżawę producenta po jednominutowym okresie karencji po przerwaniu i wycofuje automatyczne dostarczanie zakończenia bez błędnego oznaczania niepewnej pracy zewnętrznej jako przekroczonej w czasie. Odłączone subagenty (Detached Subagents) korzystają z oddzielnej ścieżki trwałych zadań i transkrypcji z kontrolą na żywo kierowaną przez Redis; zobacz [Detached Subagent Threads](/docs/features/subagents#detached-subagent-threads).

### Zapytaj użytkownika i zatwierdzenie narzędzia [#ask-user-and-tool-approval]

Narzędzie **Ask User** pozwala agentowi wstrzymać działanie, aby poprosić o brakujące informacje, przedstawić opcje wyboru lub potwierdzić sposób postępowania. Jedno wywołanie może zgrupować do czterech powiązanych pytań. LibreChat prezentuje jedno pytanie na raz z przyciskami Wstecz, Dalej oraz klikalnymi krokami postępu; odpowiedzi pozostają dostępne podczas przechodzenia między krokami, a odpowiedzi jednokrotnego wyboru są zatwierdzane automatycznie bez konieczności przesyłania. Przycisk Prześlij pojawia się w ostatnim kroku, gdy każde pytanie otrzyma odpowiedź, podczas gdy Pomiń odrzuca całą partię z dowolnego kroku. Każde pytanie akceptuje odpowiedź w formie dowolnego tekstu lub opcje jedno- bądź wielokrotnego wyboru przygotowane przez agenta. Podczas gdy model przygotowuje wywołanie, LibreChat przesyła pytania do karty postępu; interaktywny formularz zastępuje ją, gdy jest gotowy. Po przesłaniu odpowiedzi, to samo uruchomienie jest wznawiane z kompletną mapą odpowiedzi. Dodaj **Ask User** z marketplace'u Narzędzi; administratorzy mogą usunąć domyślną funkcjonalność `ask_user_question`, aby ją ukryć.

Zwinięcie karty z wieloma pytaniami przywraca kompozytor do normalnego trybu sterowania lub kolejkowania, podczas gdy wstrzymana karta pozostaje w wątku. Kartę nadal można rozwinąć, odpowiedzieć na nią, pominąć ją lub zatrzymać. Wstrzymanie pojedynczego pytania nadal korzysta z trybu odpowiedzi skupionego kompozytora.

Przesłane odpowiedzi są utrwalane wraz z akcją wznawiania (resume), więc zatrzymanie w trakcie inicjalizacji wznawianego uruchomienia nie powoduje odrzucenia zaakceptowanych odpowiedzi.

Po zatwierdzeniu rekordu pytania, domyślnie zwija się on do jednowierszowego wpisu narzędzia, aby długie odpowiedzi nie dominowały w transkrypcji. Otwórz go, aby przejrzeć pytania i zachowane podziały wierszy w odpowiedziach. Istniejące ustawienie **Auto-expand tool details** również kontroluje ten widok po zatwierdzeniu; aktywny formularz pozostaje otwarty, dopóki dane wejściowe są nadal wymagane.

Każde pytanie akceptuje opcjonalny nagłówek o długości do 80 znaków, treść pytania do 2000 znaków, opcjonalny kontekst pomocniczy do 4000 znaków oraz do 12 opcji wyboru. Etykiety opcji są ograniczone do 280 znaków, wartości opcji do 500 znaków, a każda przesłana odpowiedź do 16 000 znaków.

Administratorzy mogą również wymagać zatwierdzenia przed uruchomieniem dopasowanych wywołań narzędzi (tool calls). W zależności od narzędzia, użytkownicy mogą zatwierdzać, odrzucać, edytować argumenty lub odpowiadać bezpośrednio. Wstrzymane uruchomienia są zapisywane w punktach kontrolnych (checkpointed), dzięki czemu mogą zostać wznowione po podjęciu decyzji, w tym na innej replice, gdy używany jest domyślny mechanizm punktów kontrolnych MongoDB. Zatwierdzanie narzędzi w całej wdrożonej instancji jest domyślnie wyłączone, podczas gdy Agent korzystający z dołączonego środowiska Code podlega [zasadom bezpieczeństwa ask-by-default](/docs/features/code_interpreter#attached-environment-tool-permissions), chyba że administrator wyraźnie je wyłączy. Zobacz [`toolApproval` i `checkpointer`](/docs/configuration/librechat_yaml/object_structure/agents#toolapproval).

Gdy panel recenzji kompozytora jest otwarty w oczekiwaniu na zatwierdzenie, odpowiednia karta wątku wyświetla żądanie jako rekord, zamiast powielać przyciski decyzji. Przejrzyj wywołania w panelu nad polem wiadomości i wybierz **Continue**. Zwinięcie panelu za pomocą chipa kompozytora przywraca kontrolki karty wątku z zachowaniem Twoich decyzji; ponowne otwarcie przekazuje recenzję z powrotem do panelu. Karty dla innych akcji zachowują własne kontrolki.

### Umiejętności [#skills]

Umiejętności (Skills) pozwalają agentom wczytywać instrukcje wielokrotnego użytku z definicji `SKILL.md`. Można je wybierać ręcznie z poziomu czatu za pomocą `$`, mogą być automatycznie wykrywane przez model za pośrednictwem katalogu umiejętności lub zawsze stosowane w każdej turze. Kreator Agentów (Agent Builder) może również włączyć samodzielne tworzenie w czasie wykonywania: agent może utworzyć umiejętność bez otrzymywania istniejącego katalogu lub edytować wybrane umiejętności, gdy użytkownik posiada odpowiednie uprawnienia.

Szczegółowe informacje na temat tworzenia, wywoływania i kontroli dostępu znajdują się w sekcji [Skills](/docs/features/skills).

### Pamięć [#memory]

Narzędzie **Memory** pozwala agentowi zapisywać, aktualizować lub usuwać ustrukturyzowane wspomnienia użytkownika, gdy ten wyraźnie poprosi o zapamiętanie lub zapomnienie czegoś. Funkcja Memory musi być skonfigurowana dla danego wdrożenia, dozwolona przez rolę użytkownika i ustawienia personalizacji oraz włączona w agencie.

Domyślnie agent korzysta ze współdzielonej osobistej puli pamięci użytkownika. Włącz opcję **Keep memories separate for this agent**, aby zapewnić mu prywatną partycję dla każdego użytkownika i każdego agenta z osobna. Odizolowany agent nie będzie widział istniejących współdzielonych wspomnień ani wspomnień utworzonych przez inne odizolowane agenty. Użytkownicy mogą filtrować panel Memory według wspomnień osobistych lub specyficznych dla agenta. Odczytywanie, tworzenie lub aktualizowanie partycji agenta wymaga bieżącego dostępu do tego agenta; usunięcie może nadal wyczyścić partycję po usunięciu powiązanego z nią agenta. Zobacz [User Memory](/docs/features/memory#agent-memory).

### Artifacts [#artifacts]

Funkcja Artifacts umożliwia Twojemu agentowi generowanie i wyświetlanie interaktywnych treści:

- Twórz komponenty React, kod HTML oraz diagramy Mermaid
- Wyświetlaj zawartość w dedykowanym panelu obok czatu, który można rozwinąć do pełnego ekranu lub otworzyć w osobnym oknie przeglądarki
- Skonfiguruj instrukcje specyficzne dla artefaktów na poziomie agenta
- [Więcej informacji o Artifacts](/docs/features/artifacts)

Po włączeniu wybierz jeden z trzech trybów instrukcji:

- **Normal**: Dodaje standardowe instrukcje artefaktów dla React, HTML, SVG, Markdown i Mermaid.
- **shadcn/ui**: Dodaje standardowe instrukcje oraz wskazówki dotyczące budowania interfejsów przy użyciu biblioteki komponentów shadcn/ui.
- **Custom**: Utrzymuje włączone renderowanie artefaktów, ale nie wstrzykuje żadnych wbudowanych instrukcji dotyczących artefaktów, dając pełną kontrolę własnym instrukcjom agenta.

Konfiguracja artefaktów na poziomie agenta jest preferowanym podejściem, ponieważ pozwala na bardziej szczegółową kontrolę w porównaniu do starszej konfiguracji dla całej aplikacji.

Jeśli wybierzesz **Custom**, uwzględnij w swoich instrukcjach co najmniej podstawowy format artefaktu.

Oto prosty przykład minimalnych instrukcji, które są wymagane:

````md
When creating content that should be displayed as an artifact, use the following format:

:::artifact{identifier="unique-identifier" type="mime-type" title="Artifact Title"}

```
Your artifact content here
```

:::

For the type attribute, use one of:

- "text/html" for HTML content
- "application/vnd.mermaid" for Mermaid diagrams
- "application/vnd.react" for React components
- "image/svg+xml" for SVG images
````

### Przekazania [#handoffs]

Przekazania (handoffs) pozwalają głównemu agentowi na przeniesienie konwersacji do agenta specjalistycznego wraz z odpowiednim kontekstem. W **Advanced settings** otwórz sekcję orchestration i dodaj do 10 agentów przekazujących. Każde skonfigurowane przekazanie tworzy narzędzie transferu, które model może wybrać dynamicznie, gdy potrzebna jest wiedza specjalisty.

Dla każdego przekazania (handoff) możesz dodać opis, który pomoże modelowi wybrać odpowiedniego specjalistę. Możesz również podać instrukcje przekazywania (passthrough instructions), opisujące, jakie treści główny agent powinien wygenerować dla specjalisty, oraz opcjonalnie zmienić nazwę parametru zawartości z domyślnego `instructions`. Przekazania są zawsze dostępne w kreatorze agentów (Agent Builder); w przeciwieństwie do Agent Chain i Subagents, nie wymagają one włączenia funkcji endpoint. Wywołania narzędzi od dostępnych agentów przekazujących pozostają ustrukturyzowane w późniejszych turach, dzięki czemu dostawcy otrzymują poprawną historię wywołań narzędzi zamiast spłaszczonego tekstu.

### Łańcuch agentów [#agent-chain]

Funkcja Agent Chain umożliwia podejście Mixture-of-Agents (MoA), pozwalając na tworzenie sekwencji agentów, którzy współpracują ze sobą:

- Twórz łańcuchy wyspecjalizowanych agentów do złożonych zadań
- Każdy agent w łańcuchu może uzyskiwać dostęp do wyników poprzednich agentów
- Skonfiguruj maksymalną liczbę kroków dla łańcucha agenta
- **Uwaga:** Uzyskaj dostęp do tej funkcji z panelu Advanced Settings w kreatorze Agent Builder.
- **Uwaga:** Ta funkcja jest obecnie w fazie beta i może ulec zmianie
  - Obecny limit agentów, które można łączyć w łańcuch, wynosi 10, ale w przyszłości może to być konfigurowalne.

### Subagenci [#subagents]

Subagenci pozwalają agentowi delegować ukierunkowane zadanie do odizolowanego uruchomienia podrzędnego lub zapisanego zespołu Agentów. Każdy element podrzędny otrzymuje odizolowany kontekst i wykonanie narzędzi, a następnie zwraca do elementu nadrzędnego zwięzły wynik, zamiast zapełniać kontekst nadrzędny każdym krokiem pośrednim. Odłączona praca podrzędna jest również zachowywana jako nawigowalny wątek tylko do odczytu.

Subagenci różnią się od Agent Chain: łańcuchy uruchomieniowe koordynują wielu agentów jako uczestników grafu, podczas gdy subagenci są tworzeni przez agenta jako wywołanie narzędzia w celu delegowania zadań o określonym zakresie. LibreChat zachowuje ustrukturyzowaną historię wywołań narzędzi, potrzebną osiągalnym podrzędnym agentom i zapisanym członkom zespołu w kolejnych turach, jednocześnie wykluczając niedostępne narzędzia z aktywnego uruchomienia. Informacje na temat konfiguracji i limitów znajdują się w sekcji [Subagents](/docs/features/subagents).

### Zaawansowane ustawienia [#advanced-settings]

Zaawansowane ustawienia dla Twojego agenta (znajdujące się w widoku Advanced formularza Agent) poza „capabilities”.

#### Maksymalna liczba kroków agenta [#max-agent-steps]

To ustawienie pozwala ograniczyć liczbę kroków, które agent może wykonać w ramach „uruchomienia” (run), co odnosi się do pętli agenta przed udzieleniem ostatecznej odpowiedzi.

Jeśli pozostanie nieskonfigurowane, wartością domyślną jest 25 kroków, ale możesz dostosować to ustawienie do swoich potrzeb. Administratorzy mogą ustawić globalną wartość domyślną, a także globalne maksimum w pliku [`librechat.yaml`](/docs/configuration/librechat_yaml/object_structure/agents#recursionlimit).

Gdy tura wykorzystuje swój pełny budżet kroków, LibreChat zachowuje częściową odpowiedź oraz wywołania narzędzi zamiast zastępować je błędem. Wiadomość oferuje opcje **Keep going**, która rozpoczyna nową turę ze świeżym budżetem narzędzi, oraz **Answer now**, która prosi agenta o udzielenie odpowiedzi na podstawie dotychczas wykonanej pracy bez użycia kolejnych narzędzi. Odrzucenie powiadomienia wpływa tylko na bieżący widok przeglądarki.

Administratorzy mogą również ograniczać strumieniowe argumenty wywołań narzędzi (tool-call) oraz zdarzenia delta modelu za pomocą [Agent stream circuit breakers](/docs/configuration/librechat_yaml/object_structure/agents#stream-circuit-breakers).

„Krok” (step) odnosi się do żądania API AI lub rundy użycia narzędzi (jednego lub wielu, w zależności od tego, ile wywołań narzędzi LLM dostarczy w ramach pojedynczego żądania).

Pojedyncza odpowiedź bez użycia narzędzi to 1 krok. Pojedyncza runda użycia narzędzi to zazwyczaj 3 kroki:

1. Żądanie API -> 2. Użycie narzędzia (1 lub wiele narzędzi) -> 3. Kolejne żądanie API

## Zarządzanie plikami [#file-management]

Agenci obsługują wiele sposobów pracy z plikami:

### W interfejsie czatu [#in-chat-interface]

Podczas rozmowy z agentem masz cztery opcje przesyłania plików:

1. **Przesyłanie obrazów**
   - Przesyła obrazy w celu zapewnienia natywnej obsługi modeli wizyjnych
   - Wysyła obrazy bezpośrednio do dostawcy modelu

2. **Prześlij jako tekst** (wymaga możliwości `context`)
   - Wyodrębnia i dołącza pełną treść dokumentu do konwersacji
   - Domyślnie używa parsowania tekstu; rozszerzone o OCR, jeśli skonfigurowano
   - Treść istnieje tylko w bieżącej konwersacji
   - Zobacz [Prześlij jako tekst](/docs/features/upload_as_text)

3. **Przesyłanie do wyszukiwania plików** (wymaga funkcji `file_search`, włączonej przełącznikiem ON)
   - Wykorzystuje wyszukiwanie semantyczne (RAG) z magazynami wektorowymi
   - Zwraca odpowiednie fragmenty poprzez użycie narzędzi
   - Optymalne dla dużych dokumentów/wielu plików
   - Suboptymalne dla danych ustrukturyzowanych (CSV, Excel, JSON itp.)

4. **Przesyłanie dla Code Interpreter** (wymaga włączonej funkcji `execute_code`)
   - Dodaje pliki do środowiska interpretera kodu
   - Optymalne dla danych ustrukturyzowanych (CSV, Excel, JSON itp.)
   - Więcej informacji na temat [Code Interpreter](/docs/features/code_interpreter)

### W Kreatorze Agentów [#in-agent-builder]

Podczas konfigurowania agenta możesz dołączać pliki w różnych kategoriach:

1. **Przesyłanie obrazów**: W przypadku treści wizualnych, do których agent może się odwoływać
2. **Przesyłanie plików do wyszukiwania**: Dokumenty dla funkcji RAG
3. **Przesyłanie plików do Code Interpreter**: Pliki do przetwarzania kodu
4. **Kontekst pliku**: Dokumenty z wyodrębnionym tekstem w celu uzupełnienia instrukcji agenta

**File Context** wykorzystuje funkcję `context` i działa dokładnie tak samo jak ["Prześlij jako tekst"](/docs/features/upload_as_text) – domyślnie korzysta z analizy tekstu, a po skonfigurowaniu jest wspomagany przez OCR. Tekst jest wyodrębniany w momencie przesyłania i przechowywany w instrukcjach agenta. Jest to idealne rozwiązanie, aby zapewnić agentom trwałą wiedzę z dokumentów, plików PDF, plików kodu lub obrazów zawierających tekst.

**Priorytet przetwarzania:** OCR > STT > parsowanie tekstu (tak samo jak Prześlij jako tekst)

**Uwaga:** Wyodrębniony tekst jest zawarty jako część instrukcji systemowych agenta.

## Udostępnianie i uprawnienia [#sharing-and-permissions]

Agenci korzystają z granularnego systemu [kontroli dostępu](/docs/features/access_control) LibreChat. Każdy agent posiada własną listę kontroli dostępu (ACL) i może być udostępniany konkretnym **użytkownikom**, **grupom**, **rolom** lub **publicznie**, przy czym dla każdego z nich można wybrać poziom uprawnień.

Zaufane usługi mogą również zarządzać Agentami, załączonymi plikami i Umiejętnościami poprzez wersję beta [Agent Management API](/docs/features/agents_api#agent-management-api). Administratorzy przypisują każdego klienta maszynowego OIDC do jednego istniejącego użytkownika i dzierżawcy LibreChat; każde żądanie dziedziczy bieżące uprawnienia roli i listy ACL zasobów tego użytkownika, zamiast otrzymywać oddzielny dostęp administracyjny.

### Role dostępu [#access-roles]

Podczas udostępniania agenta, odbiorcy przypisywana jest jedna z trzech ról:

| Rola | Co może zrobić użytkownik (grantee) |
| ---------- | ----------------------------------------------------------------------------------------------------- |
| **Viewer** | Używanie agenta w konwersacjach; brak możliwości otwarcia kreatora lub podejrzenia instrukcji, narzędzi czy załączonych plików |
| **Editor** | Wyświetlanie + modyfikowanie instrukcji, modelu, narzędzi i plików agenta |
| **Owner**  | Pełna kontrola: wyświetlanie, edytowanie, usuwanie i ponowne udostępnianie agenta |

Oryginalny autor i administratorzy zawsze zachowują pełną kontrolę, niezależnie od ACL.

### Udostępnianie Agenta [#sharing-an-agent]

1. Otwórz agenta w Agent Builder
2. Kliknij przycisk **Share** w stopce (widoczny, gdy jesteś autorem, administratorem lub otrzymałeś uprawnienie `SHARE` dla tego konkretnego agenta)
3. Wyszukaj użytkowników, grupy lub role w selektorze osób i przypisz każdemu z nich rolę
4. Opcjonalnie przełącz **Public** (Publiczny), aby uczynić agenta widocznym dla wszystkich użytkowników instancji (wymaga uprawnienia funkcji `SHARE_PUBLIC`).

Karty agentów i widoki strony głównej wyświetlają skonfigurowany kontakt wsparcia. Gdy nie jest on ustawiony, LibreChat może użyć nazwy wyświetlanej pierwszego możliwego do zidentyfikowania właściciela, ale nie ujawnia adresu e-mail właściciela, chyba że został on wyraźnie skonfigurowany jako kontakt wsparcia.

Powierzchnie konwersacji utrzymują Agenta jako widoczną tożsamość i nie powracają do jego modelu bazowego ani etykiety Model Specs.

Aby uzyskać szczegółowe informacje na temat podmiotów (principals), bitów uprawnień oraz sposobu, w jaki listy ACL współdziałają z uprawnieniami funkcji opartymi na rolach, zobacz [Access Control](/docs/features/access_control).

### Rynek Agentów [#agent-marketplace]

**Agent Marketplace** pozwala użytkownikom przeglądać dostępne dla nich agenty. Otwórz go z poziomu **Agent Marketplace** na pasku bocznym; wpis ten pojawia się tylko dla użytkowników, których rola pozwala na korzystanie z Marketplace.

- **Przeglądanie i wyszukiwanie**: Agenci są wyświetlani w formie siatki. Użyj pola wyszukiwania, aby znaleźć agentów według nazwy lub opisu, oraz przycisków kategorii (takich jak **Top Picks**, **All** lub konkretna kategoria), aby zawęzić listę.
- **Sortowanie**: Użyj **Sortuj według**, aby uporządkować agentów według **Najnowsze** (domyślnie), **Najstarsze**, **Popularne** (najczęściej przypinane) lub **Według nazwy twórcy**.
- **Moi agenci**: Włącz **Moi agenci**, aby wyświetlić tylko stworzonych przez siebie agentów. Włączenie tej opcji w sekcji **Najlepsze wybory** przełączy widok na **Wszystkie**.
- **Udostępnialne widoki**: Wyszukiwanie, sortowanie oraz filtr **My agents** są zachowywane w adresie URL strony (`?q=`, `?sort=`, `?mine=1`), dzięki czemu przefiltrowany widok można dodać do zakładek lub udostępnić.

Wybierz kartę agenta, aby otworzyć okno dialogowe ze szczegółami, które zawiera pełny opis i dane kontaktowe agenta, wraz z następującymi akcjami:

- **Przypnij** lub **Odepnij**: Dodaj agenta do swoich przypiętych agentów lub usuń go z nich.
- **Kopiuj link**: Skopiuj link, który rozpoczyna nowy czat z agentem.
- **Start Chat**: Rozpocznij nową konwersację z agentem.
- **Wypróbuj starter rozmowy**: Gdy agent posiada [conversation starters](#conversation-starters), wybierz jeden z nich, aby otworzyć nowy czat z tym promptem już wprowadzonym w polu wiadomości. Nie jest on wysyłany automatycznie, więc możesz go najpierw edytować.

Administratorzy mogą kontrolować dostęp za pomocą ustawienia [`interface.marketplace`](/docs/configuration/librechat_yaml/object_structure/interface#marketplace) oraz uprawnień ról opisanych w sekcji [Kontrola dostępu](/docs/features/access_control).

### Kontrola administratora [#administrator-controls]

Administratorzy mają dostęp do globalnych ustawień uprawnień w interfejsie użytkownika kreatora agentów:

- Włącz/wyłącz udostępnianie agentów dla wszystkich użytkowników
- Kontroluj uprawnienia do korzystania z agentów
- Zarządzaj uprawnieniami do tworzenia agentów
- Skonfiguruj ustawienia dla całej platformy

W nieskopowanym wdrożeniu jednonajemcowym (single-tenant), pierwsze konto utworzone dla instancji jest administratorem. Wdrożenia z zakresem najemcy (tenant-scoped) nie promują automatycznie pierwszego zarejestrowanego użytkownika; administratorów najemców należy przydzielać poprzez zaufany proces administracyjny. Jeśli musisz dodać administratora ręcznie, możesz [uzyskać dostęp do MongoDB](/docs/configuration/mongodb/mongodb_auth) i zaktualizować profil użytkownika:

```
db.users.updateOne(
  { email: 'USER_EMAIL_ADDRESS' },
  { $set: { role: 'ADMIN' } }
)
```

Użycie agentów dla wszystkich użytkowników można również wyłączyć poprzez konfigurację, [więcej informacji](/docs/configuration/librechat_yaml/object_structure/interface).

Uprawnienia na poziomie funkcji (kto może _używać_, _tworzyć_, _udostępniać_ lub _udostępniać publicznie_ agentów) są zarządzane z poziomu [**Panelu Administratora LibreChat**](/docs/features/admin_panel) dla każdej roli, w tym dla wszelkich ról niestandardowych. Blok [`interface.agents`](/docs/configuration/librechat_yaml/object_structure/interface#agents) w pliku `librechat.yaml` nadal może służyć do ustawiania wartości domyślnych dla wbudowanej roli `USER` podczas uruchamiania, jednak panel administratora jest zalecanym sposobem ich edycji w przyszłości.

### Udostępnianie na poziomie użytkownika [#user-level-sharing]

Indywidualni użytkownicy mogą:

- Udostępniaj ich agentów określonym użytkownikom, grupom lub rolom (jeśli `SHARE` jest włączone dla ich roli)
- Uczyń agentów widocznymi dla wszystkich użytkowników instancji (jeśli `SHARE_PUBLIC` jest włączone)
- Przyznaj każdemu odbiorcy inny poziom dostępu (Viewer / Editor / Owner)
- Udostępniaj ponownie lub cofaj dostęp w dowolnym momencie z poziomu okna dialogowego udostępniania

## Sterowanie i kolejkowanie wiadomości [#steering-and-queued-messages]

Podczas gdy Agent odpowiada, możesz wysłać kolejną wiadomość z [composer](/docs/features/composer) na dwa sposoby:

- **Steer** wstawia wiadomość do bieżącego uruchomienia w następnym kroku narzędzia lub agenta, dzięki czemu agent może dostosować swoją pracę przed zakończeniem.
- **Queue** przechowuje wiadomość i wysyła ją jako zwykłą kolejną turę po zakończeniu bieżącej odpowiedzi.

W przypadku zapisanych konwersji Agentów na bieżącym serwerze, zwykłe kolejkowane odpowiedzi są przechowywane w MongoDB. LibreChat zachowuje ich kolejność FIFO oraz przenosi ich tekst, załączniki, cytowane fragmenty i ręcznie wybrane Skills pomiędzy rozłączeniami przeglądarki, restartami aplikacji i przekazaniami replik. Przetwarzanie czeka na zakończenie poprzedniej odpowiedzi przed dopuszczeniem kolejnej tury. Ta trwałość jest automatyczna i nie posiada przełącznika w YAML ani w zmiennych środowiskowych; starsze serwery i krótkie okna uruchomienia bez aktywnej epoki generowania zachowują kolejkę kompatybilności po stronie klienta.

Przyjmowanie zgłoszeń przez serwer jest serializowane w ramach każdego pasa kolejki konwersacji. Jeśli dowody dotyczące poprzednika lub własność mieszanej wersji są niejednoznaczne, LibreChat wyświetla komunikat **Awaiting reconciliation** i blokuje lub przerywa przetwarzanie danej kolejki zamiast zgadywać i uruchamiać ją w niewłaściwej kolejności.

**Steer sooner** prosi agenta o przejęcie wiadomości w następnym bezpiecznym punkcie, zamiast czekać na kolejny krok narzędzia. Jeśli żaden tekst odpowiedzi ani aktywność narzędzia nie są jeszcze bezpieczne do zachowania, LibreChat czeka przez krótki okres karencji, odrzuca próbę milczenia lub samych procesów rozumowania, wstawia wiadomość i restartuje model z tą instrukcją. Gdy tekst odpowiedzi może zostać zachowany, LibreChat zatrzymuje się na bezpiecznej dla dostawcy granicy, zachowuje częściową odpowiedź, wstawia wiadomość i wznawia tę samą odpowiedź asystenta. Trwające wywołanie narzędzia nie jest odrzucane ani przerywane przez sterowanie; wiadomość ma zastosowanie, gdy praca ta osiągnie bezpieczną granicę.

Użyj **Stop**, aby zakończyć aktywne wnioskowanie i zażądać anulowania wywołania narzędzia działającego na pierwszym planie. Stop przekazuje sygnał anulowania do narzędzi obsługujących przerwania; odłączone zadania w tle zachowują swój niezależny cykl życia. Użyj dedykowanego przycisku w komponencie, wybierz go z menu przycisku wysyłania lub naciśnij `Command/Ctrl + Shift + .`. Akcja ta zmienia się w zwykłe sterowanie, gdy wdrożenie nie może przerwać aktywnego strumienia dostawcy.

W sekcji **Ustawienia → Czat**, opcja **Podczas generowania, Enter spowoduje** wybiera domyślną akcję. Menu przycisku wysyłania może nadpisać ten wybór dla pojedynczej wiadomości, a opcja **Wcześniejsze sterowanie po naciśnięciu Enter** sprawia, że naciśnięcie Enter żąda wcześniejszego bezpiecznego punktu, gdy sterowanie jest ustawione jako domyślne.

Pliki oraz [cytowane fragmenty](/docs/features/message_actions#quote-excerpts) są przesyłane wraz z komunikatami steer, queue oraz interrupt. Ręcznie wybrane Skills pozostają w kolejce na następną pełną turę, zamiast być dołączane do trwającego w trakcie działania steer.

Oczekujące sterowania (steers) pojawiają się na końcu strumieniowej odpowiedzi, w miejscu, w którym zostaną umieszczone, dopóki serwer nie wprowadzi ich do przebiegu. Proces ich dostarczania przebiega od **Sending** (Wysyłanie) do **Delivered** (Dostarczono), następnie **Steer sooner requested** (Zażądano wcześniejszego sterowania), gdy zażądano wcześniejszego bezpiecznego punktu, a na końcu **Applied** (Zastosowano) z podwójnym znacznikiem wyboru w prawym dolnym rogu wiadomości w tekście. Potwierdzone zastosowane potwierdzenia pozostają widoczne po przeładowaniu oraz w widokach udostępniania lub wyszukiwania; niepewne lub nieudane dostarczenie nigdy nie wyświetla znacznika potwierdzenia. Po potwierdzeniu, menu wiadomości pozwala odzyskać sterowanie w celu edycji, przekonwertować je na zakolejkowaną wiadomość uzupełniającą lub anulować je i przywrócić jego tekst oraz załączniki do edytora. LibreChat unika nadpisywania nowszego szkicu; jeśli edytor nie jest już dostępny, zachowuje odzyskaną wiadomość w kolejce. Nieudane sterowanie pozostaje dostępne do ponowienia, edycji, zakolejkowania lub usunięcia.

Kolejka zadań (queued follow-ups) pojawia się na liście nad polem wprowadzania wiadomości. Każdy element można edytować (**Edit message**), usunąć (**Remove message**), wysłać natychmiast za pomocą **Send now** lub zmienić jego kolejność poprzez przeciągnięcie uchwytu lub użycie klawiszy strzałek. Kolejki zadań można również przekształcić w sterowanie (steer), gdy uruchomienie jest nadal aktywne, lub przyspieszyć za pomocą **Steer sooner**. Sterowanie w trakcie wykonywania (in-flight steers) oferuje taką samą opcję przyspieszenia, gdy oczekuje na granicę narzędzia. Usunięcie wiadomości z kolejki wspieranej przez serwer najpierw anuluje jej trwałe źródło, a następnie, jeśli to możliwe, przywraca ją do pustego pola wprowadzania. Jeśli poprzednia odpowiedź zostanie przerwana lub zakończy się niepowodzeniem, LibreChat oznacza daną turę w kolejce jako nieudaną do sprawdzenia, zamiast wysyłać ją automatycznie.

Konwersacja może mieć do 100 aktywnych zakolejkowanych tur. Każda zakolejkowana tura akceptuje do 16 000 znaków i 10 plików. Osobno, jeden aktywny przebieg akceptuje do 10 oczekujących sterowań (steers); każde sterowanie może zawierać do 10 plików i jest ograniczone przez [`STEER_MAX_LENGTH`](/docs/configuration/dotenv#agent-conversation-controls). **Steer sooner** nadal korzysta ze ścieżki sterowania na żywo, zamiast przenosić zakolejkowaną turę na początek trwałej kolejki FIFO.

Wdrożenia wieloreplikowe oparte na Redis automatycznie negocjują protokół generowania v2. Postępuj zgodnie ze [wskazówkami dotyczącymi zgodności protokołu generowania](/docs/configuration/redis#generation-protocol-compatibility) podczas aktualizacji z wersji starszej niż `v0.8.8-rc1`.

### Uwagi [#notes]

- Instrukcje, parametry modelu, załączone pliki oraz narzędzia są widoczne dla użytkownika tylko wtedy, gdy posiada on uprawnienia do edycji.
  - Agent może ujawnić wszelkie załączone dane, niezależnie od tego, czy są to instrukcje czy pliki, poprzez konwersację, dlatego upewnij się, że Twoje instrukcje są na to odporne, zanim przyznasz dostęp typu Editor/Owner lub udostępnisz agenta publicznie.
- Tylko oryginalni autorzy, administratorzy oraz użytkownicy z uprawnieniami właściciela (Owner) mogą usuwać udostępnione agenty.
- Agenci są prywatni dla autorów, chyba że zostaną udostępnieni

## Dostarczanie zdarzeń agenta [#agent-event-delivery]

LibreChat zawiera neutralną źródłowo warstwę dostarczania dla asynchronicznych zdarzeń Agentów. Adaptery należące do wdrożenia mogą normalizować zweryfikowany webhook, komunikat kolejki, zdarzenie MCP, zdarzenie kanału lub wewnętrzne zdarzenie produktu do nowego uruchomienia Agenta (`fire`), nowej tury w istniejącym zapisanym Agencie i gałęzi (`continue`) lub mutacji aktywnego uruchomienia (`steer`). Adaptery pozostają odpowiedzialne za uwierzytelnianie swojego natywnego źródła, oczyszczanie ładunków (payloads) oraz wybór zaufanych celów przed dodaniem do kolejki.

Beta [punktów końcowych zdarzeń Agents API](/docs/features/agents_api#agent-events) udostępniają uwierzytelniony dostęp `fire`, `continue` oraz `steer` dla kluczy API Remote Agents. Systemy zewnętrzne mogą powiązać aktora źródłowego z bezpośrednim Agentem podrzędnym i kontynuować działanie tego aktora w ramach zdarzeń bez konieczności włączania dodatkowych funkcji. LibreChat wywodzi tożsamość użytkownika, dzierżawcy (tenant) oraz źródła z klucza API, wymusza dostęp do Agenta i filtry treści, a także wymaga klucza idempotencji. Nie jest to nieuwierzytelniony, ogólny odbiornik webhooków; adaptery specyficzne dla dostawcy muszą nadal weryfikować natywne sygnatury webhooków przed wywołaniem tego punktu końcowego.

Eksperymentalna funkcja [Scheduled Chats](/docs/features/scheduled_chats) to pierwszy wbudowany w LibreChat producent dla tej warstwy. Tworzy ona cykliczne dostarczenia typu `fire` dla zapisanych Agentów i jest wyłączona, dopóki administrator nie wyrazi na to zgody. Odłączone Subagenty automatycznie używają idempotentnego dostarczenia typu `continue`, aby wybudzić zapisanego nadrzędnego Agenta po zakończeniu działania podrzędnego; anulowane procesy podrzędne oraz efemeryczni nadrzędni Agenci są wykluczeni.

MongoDB przechowuje ograniczone wersjonowane koperty, klucze idempotentności, pasy kolejkowania, dzierżawy, historię ponownych prób, trwałe potwierdzenia oraz wiadomości niedoręczalne (dead letters). Pracownicy (workers) stosują dostarczanie typu at-least-once z ogrodzonymi żądaniami (fenced claims) i ograniczonym wykładniczym wycofywaniem (bounded exponential backoff); pomyślne potwierdzenia wygasają po 90 dniach, podczas gdy wiadomości niedoręczalne wymagają jawnego, zaufanego ponownego kolejkowania. Dostarczenia typu Fire tworzą nową konwersację. Dostarczenia typu Continue tworzą nową turę w dokładnie tej samej gałęzi konwersacji i są odraczane, gdy ta gałąź jest uruchomiona, wstrzymana lub finalizowana. Powiązane podmioty (bound actors) posiadają również automatyczną skrzynkę odbiorczą: jeden podmiot czeka na wynik obsługi swojej bieżącej tury przed wysłaniem kolejnego zdarzenia, podczas gdy różne podmioty mogą działać równolegle. Dostarczenia typu Steer muszą identyfikować istniejącą konwersację i generację oraz stosować ścisłe przyjmowanie (strict admission), aby niejednoznaczne ponowne próby nie mogły wprowadzić tej samej instrukcji dwukrotnie.

W przypadku powiązanych kontynuacji, pomyślny transport rozpoczyna oddzielny trwały cykl obsługi. Dostarczenie przechodzi ze stanu `started` do `applied`, `completed_no_action`, `failed` lub `cancelled`. Źródła mogą wymagać konkretnego narzędzia i opcjonalnego podzbioru argumentów za pomocą `expectedAction`; LibreChat zgłasza `applied` tylko na podstawie dowodów użycia narzędzia zaobserwowanych przez hosta, nigdy na podstawie tekstu napisanego przez model. Kompatybilne zdarzenia obserwacyjne mogą współdzielić ograniczoną partię `coalesce.key`, zachowując jednocześnie jeden rekord idempotencji i potwierdzenie dla każdego zdarzenia źródłowego. Kontynuacja punktu kontrolnego (checkpoint) jest używana, gdy jest to kompatybilne, w przeciwnym razie system powraca do trwałej historii wiadomości.

Bound Event Actors mogą wstrzymywać działanie w oczekiwaniu na Ask User lub zatwierdzenie narzędzia i wznawiać dokładnie to samo wywołanie podpisanego aktora za pośrednictwem standardowego interfejsu human-in-the-loop w LibreChat. Skrzynka odbiorcza aktora pozostaje zablokowana do momentu wznowienia lub zakończenia wstrzymania, co zapobiega wyprzedzeniu decyzji przez późniejsze zdarzenie. Ci aktorzy wymagają trwałego mechanizmu sprawdzania punktów kontrolnych (checkpointer) w MongoDB. LibreChat automatycznie wybiera kontynuację punktu kontrolnego lub rekonstrukcję trwałej historii na podstawie stanu aktora i możliwości żądania; istniejące zadania w protokole protocol-v1 pozostają na ścieżce historii do momentu ich wyczerpania.

Odłączone akcje (Detached Actions) uruchamiane przez podmioty zdarzeń (Event Actors) są włączane automatycznie, gdy wbudowany magazyn generowania zgłasza ich obsługę. Podmiot pozostaje zawieszony do momentu, aż dowód końcowy (terminal evidence) wznowi jego pierwotne wywołanie, więc samo uruchomienie w tle nie spełnia warunku `expectedAction`. Magazyn w pamięci (in-memory store) utrzymuje spójność tego cyklu życia, dopóki proces pozostaje aktywny. Redis dodaje trwałe odzyskiwanie po restarcie i przekazywanie replik. Praca związana z ukończeniem zadań przez możliwości (Capability-owned completion work) jest izolowana od starszych procesów roboczych podczas usuwania wersji mieszanych; operatorzy nie wybierają tego zachowania za pomocą flagi funkcji.

Host wykonawczy zazwyczaj wywołuje powiązany odbiornik bieżącego procesu. Skonfiguruj [`endpoints.agents.eventDriven.selfUrl`](/docs/configuration/librechat_yaml/object_structure/agents#eventdriven) tylko wtedy, gdy ta zaufana wewnętrzna ścieżka przyjmowania żądań musi przechodzić przez inne źródło HTTP, takie jak brama TLS.

## Podsumowanie [#recap]

1. Wybierz "Agents" z menu rozwijanego endpoint.
2. Otwórz panel Agent Builder
3. Wypełnij wymagane szczegóły agenta

## Wymagana migracja (v0.8.0-rc3+) [#migration-required-v080-rc3]

<Callout type="warning" title="Ważne: Wymagana migracja uprawnień agenta">
  Począwszy od wersji v0.8.0-rc3, LibreChat wykorzystuje nowy system uprawnień oparty na listach kontroli dostępu (ACL) dla agentów. Jeśli aktualizujesz system z wcześniejszej wersji, musisz uruchomić migrację uprawnień agentów, aby istniejący agenci pozostali dostępni.
</Callout>

### Co robi migracja [#what-the-migration-does]

Migracja uprawnień agentów przenosi Twoich agentów z prostego modelu własności do zaawansowanego systemu opartego na ACL z wieloma poziomami uprawnień:

- **OWNER**: Pełna kontrola nad agentem
- **EDITOR**: Może przeglądać i modyfikować agenta
- **VIEWER**: Dostęp tylko do odczytu do agenta

Bez przeprowadzenia tej migracji, istniejące agenty będą niedostępne przez nowe endpoint obsługujące uprawnienia.

### Uruchamianie migracji [#running-the-migration]

Wybierz odpowiednią komendę w zależności od metody wdrożenia:

#### 1. Dla domyślnego `docker-compose.yml` (jeśli używasz `docker compose up` do uruchomienia aplikacji): [#1-for-the-default-docker-composeyml-if-you-use-docker-compose-up-to-start-the-app]

**Podgląd zmian (dry run):**

```bash
docker compose exec api npm run migrate:agent-permissions:dry-run
```

**Wykonaj migrację:**

```bash
docker compose exec api npm run migrate:agent-permissions
```

**Niestandardowy rozmiar partii (dla dużych zbiorów danych):**

```bash
docker compose exec api npm run migrate:agent-permissions:batch
```

#### 2. Dla `deploy-compose.yml` [#2-for-the-deploy-composeyml]

Jeśli postępowałeś zgodnie z [Przewodnikiem Docker dla Ubuntu](/docs/remote/docker_linux):

**Podgląd zmian (dry run):**

```bash
docker exec -it LibreChat-API /bin/sh -c "cd .. && npm run migrate:agent-permissions:dry-run"
```

**Wykonaj migrację:**

```bash
docker exec -it LibreChat-API /bin/sh -c "cd .. && npm run migrate:agent-permissions"
```

**Niestandardowy rozmiar partii (dla dużych zbiorów danych):**

```bash
docker exec -it LibreChat-API /bin/sh -c "cd .. && npm run migrate:agent-permissions:batch"
```

#### 3. Do lokalnego programowania (z katalogu głównego projektu): [#3-for-local-development-from-project-root]

**Podgląd zmian (dry run):**

```bash
npm run migrate:agent-permissions:dry-run
```

**Wykonaj migrację:**

```bash
npm run migrate:agent-permissions
```

**Niestandardowy rozmiar partii (dla dużych zbiorów danych):**

```bash
npm run migrate:agent-permissions:batch
```

### Co dzieje się podczas migracji [#what-happens-during-migration]

- **Prywatni Agenci**: Pozostają dostępne tylko dla swoich twórców (otrzymują uprawnienie OWNER)
- **Udostępnione Agenty**: Jeśli agent został wcześniej udostępniony, otrzyma odpowiednie wpisy ACL jako Agent Publiczny (udostępniony wszystkim użytkownikom)
- **Wykrywanie systemu**: LibreChat automatycznie wykrywa niezmigrowane agenty podczas uruchamiania i wyświetla ostrzeżenie

Możesz dostosować uprawnienia wynikowego agenta za pomocą interfejsu Agent Builder UI.

<Callout type="info" title="Uwaga">
  Ten sam proces migracji dotyczy promptów. Jeśli posiadasz również istniejące prompty, uruchom migrację uprawnień promptów, używając tych samych poleceń, ale zastępując `agent` przez `prompt` w nazwach poleceń.
</Callout>

## Co dalej? [#whats-next]

Agenci LibreChat wprowadzają nową erę dla aplikacji, w której przyszłe potoki mogą być usprawniane za pomocą Agentów do określonych zadań i przepływów pracy w całym środowisku LibreChat.

Przyszłe aktualizacje będą obejmować:

- Ogólne ulepszenia bieżącego środowiska Agentów
- Orkiestracja wielu agentów dla złożonych przepływów pracy
- Możliwość dostosowywania agentów do różnych funkcji: tytułowania (nadawanie nazw wątkom czatu), zarządzania pamięcią (kontekst/historia użytkownika) oraz ulepszania promptów (wsparcie wprowadzania danych/przewidywania)
- Więcej narzędzi, konfigurowalne parametry narzędzi, dynamiczne tworzenie narzędzi.

Ponadto aktualizacja wprowadza nowy paradygmat dla LibreChat, ponieważ jego podstawowa architektura zapewnia bardzo potrzebne odświeżenie aplikacji, optymalizując zarówno komfort użytkowania, jak i ogólną wydajność aplikacji.

Aby wyróżnić jedną istotną optymalizację, generowanie przez AI około 1000 tokenów spowoduje przesłanie około 1 MB danych przy użyciu tradycyjnych endpoint (w momencie pisania tego tekstu, każdej opcji endpoint poza Agents i AWS Bedrock).

Używając agenta, ta sama generacja przesyła około 52 kb danych, co stanowi 95% redukcję transferu danych, a to oznacza znacznie mniejsze obciążenie serwera oraz urządzenia użytkownika.
