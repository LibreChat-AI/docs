## はじめに [#introduction]

LibreChatのCode Interpreter APIは、シンプルなAPIインターフェースを通じて、安全かつ手軽にコードを実行し、ファイルを管理する方法を提供します。LibreChatのAgentsを通じて使用する場合でも、アプリケーションに直接統合する場合でも、このAPIは複数のプログラミング言語でコードを実行するための強力なサンドボックス環境を提供します。

</Callout>

## はじめに [#getting-started]

1. [code-interpreter](https://github.com/ClickHouse/code-interpreter) サービスをデプロイします（Docker Compose または Helm を使用。リポジトリの README を参照してください）
2. `LIBRECHAT_CODE_BASEURL` を使用して LibreChat をそこへ向けてください。
3. 現在のオープンソースサービス向けに [LibreChat JWT authentication](#self-hosted-jwt-authentication) を設定するか、APIキー互換のデプロイメント用に `LIBRECHAT_CODE_API_KEY` を設定してください。
4. ステートフルなAgentセッションを試すには、個別の `stateful` プロファイルのCode Interpreterルートをデプロイし、`LIBRECHAT_CODE_BASEURL_STATEFUL` または名前付きの [`statefulCodeSessions.environments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions) を設定してください。
5. LibreChatのAgentsまたは「Run Code」ボタンを使用して、安全にコードの実行やファイルの生成を開始します。

## 主な機能 [#key-features]

### 対応言語 [#supported-languages]

複数のプログラミング言語でコードを実行する:

- Python, Node.js (JS/TS), Go, C/C++, Java, PHP, Rust, Fortran, Rscript

### シームレスなファイル処理 [#seamless-file-handling]

- 処理のためにファイルをアップロード
- 生成された出力をダウンロード
- 安全なファイル管理
- セッションベースのファイル整理

LibreChatは、エージェントの実行前に、参照された会話ファイルを管理されたCode Interpreter環境に復元します。必要なCode Interpreterファイルがすべて復元に失敗した場合、実行はモデル呼び出しの前に停止し、古い参照のまま続行するのではなく、ユーザーにファイルの再添付を求めます。選択された添付ワークスペースでは、チャットのアップロードファイルはユーザーのワークスペースにコピーされ**ません**。また、ワークスペース内のファイルツールやBashツールでそれらを開くこともできません。ワーカーがファイルリレー付きのProgrammatic Bashをアドバタイズしている場合、そのツールは実行期間中、`$LIBRECHAT_CODE_DATA_DIR`配下にステージングされたアップロードファイルを参照します。

Code APIのアップロードは、`Retry-After`を尊重し、試行ごとにソースストリームを再オープンし、制限付きの待機予算を共有することで、`429`レート制限から回復します。管理者は、[`codeApiUploadConcurrency`および`codeApiMaxRetryWaitMs`](/docs/configuration/librechat_yaml/object_structure/agents#code-api-upload-recovery)を使用して、ユーザーごと、ルートごとの回復設定を調整できます。

会話の入力が同じサンドボックスの送信先にマウントされる場合、LibreChatは実行前に競合を解決します。共有会話ファイルはエージェント専用ファイルよりも先に割り当てられます。各スコープ内では、最新のコンテンツ書き込みが元の送信先を保持します。競合するパスは必要に応じてフラット化されるか、識別子由来のサフィックスが付与され、解決された `/mnt/data/...` パスがエージェントのファイルコンテキストに含まれます。これには、同じファイル名を共有するアップロードと生成された出力も含まれるため、1つの競合によって会話内のその後のCode Interpreterの実行がすべて拒否されることはありません。すでに要求済みの送信先に解決される重複したシード参照は、リクエスト全体を失敗させるのではなくスキップされます。

Sandboxイメージは、制限付きウィンドウ内で転送されます。[`LIBRECHAT_CODE_SANDBOX_OUTPUT_MAX_SIZE`](/docs/configuration/dotenv#code-interpreter) をワーカーの `SANDBOX_OUTPUT_MAX_SIZE` と一致するように設定してください。LibreChatはその予算から最大の安全なイメージウィンドウを導出し、読み取りに1度失敗した後は、より小さなサービスごとの制限を学習できます。`LIBRECHAT_CODE_IMAGE_CHUNK_BYTES` は、正確なウィンドウのオーバーライドが必要な場合にのみ使用してください。以前にダウンロードされた生成済みアーティファクトは、可能な限りリクエスト内で再利用され、再度Sandboxから読み取ることを回避します。

マルチエージェントグラフでは、異なるAgent専用のファイルにはそれぞれ異なるファイル名を付けてください。各Agentはグラフがそれらの入力を結合する前に自身のプライベートなファイルパスを解決するため、独立して同じ宛先を指定している実質的に異なるプライベートファイルは、マージ時に一貫して名前を変更することがまだできません。最初にシードされた宛先が優先されます。

### セキュリティと利便性 [#security--convenience]

- 安全なサンドボックス化された実行環境
- 強力な分離モード (NsJail または libkrun による microVM)
- エンドユーザー向けのローカルセットアップは不要です
- セッションベースの分離されたファイルストレージ

### Programmatic Tool Calling [#programmatic-tool-calling]

Programmatic Tool Calling（プログラムによるツール呼び出し）を使用すると、LibreChatのAgentは選択したMCPツールをCode Interpreterのサンドボックス経由でルーティングできるようになります。モデルに各ツールを直接呼び出すよう指示する代わりに、LibreChatはCode Interpreterによってバックアップされたオーケストレーションツールを提供します。生成されたサンドボックスコードは、登録されたツールスタブの呼び出し、ループや条件分岐の使用、中間結果の処理を行い、最終的な回答を返すことができます。

サンドボックスは依然として一般的なネットワークアクセスを受け取りません。ツール呼び出しは、Code Interpreter Tool Call Server を介して仲介されます。LibreChat は、ライブの呼び出し元機能プロジェクションと信頼されたレジストリを照合するため、エージェントに対して既に登録されているアクティブなプログラムツールのみが呼び出し可能であり、リクエストが自身のアクセス権を拡張することはできません。

Programmatic tools（プログラムツール）を使用するには、AgentでCode Interpreterを有効にする必要があります。Code Interpreterが選択されるまで、これらのトグルは無効のままとなり、Code Interpreterを削除すると既存のProgrammaticの選択内容はクリアされます。また、`execute_code` または Code Interpreterツールが利用できない場合、LibreChatはAgentの作成、更新、複製、およびバージョン復元操作から、無効となったprogrammatic callerオプションを削除します。

プログラム実行中、Code Interpreterカードを展開すると、ツール呼び出しの内部トレースをターミナル形式でリアルタイムに確認できます。これには、引数のプレビュー（制限付き）、ステータス、実行時間、および失敗の内容が含まれます。このトレースは実行中のプログラムを調査するのに役立ちますが、ページをリロードすると保持されません。

### Background Code Execution [#background-code-execution]

バックグラウンド実行により、エージェントは長時間実行されるコードやシェル作業をディスパッチし、会話を継続することができます。保存されたエージェントの場合、サポートされているコンテンツのみの完了は、デフォルトでフォローアップの継続として自動的に配信されます。`check_background_task` は、明示的なステータス、制御、ライブアーティファクト、およびリカバリのために引き続き利用可能です。LibreChatのチャットでは、作業が完了すると、stdoutと生成されたファイルが元のコード呼び出しに表示され、後続のターンでも保持されます。バックグラウンドでの完了と明示的なチェックは、ステータス、配信状態、および読み取り可能な結果を含むタスクカードをレンダリングします。元の正確な結果はコピー可能な状態で残ります。チャットヘッダーは、実行中および最近のタスクをグループ化し、デプロイメントのキャンセルポリシーで許可されている場合に、個別の制御またはすべて停止する制御を提供します。

この機能は、デプロイメントレベルでオプトインする必要があります。[Agents endpoint capabilities](/docs/configuration/librechat_yaml/object_structure/agents#capabilities) の `execute_code` と並べて `run_in_background` を追加し、エージェントで Code Interpreter を有効にしてください。コード実行とシェル呼び出しは自動的にバックグラウンド実行の対象となります。エージェントがオプトアウトすべき場合は、Code Interpreter ツールの設定で **Background execution** をオフにしてください。モデルは、対象となる作業をバックグラウンドで実行するかどうかを呼び出しごとに判断します。

通常のバックグラウンド実行はプロセスローカルのままであり、アプリワーカーが失われると存続しません。コンテンツのみのターミナル結果が永続化されると、その自動配信は永続的となり、別のレプリカで継続される可能性があります。ライブアーティファクトを持つタスクは、引き続き所有する実行環境でのポーリングを必要とします。すべての結果に対してポーリングを要求するには、[`endpoints.agents.backgroundTasks.completionWakeups: false`](/docs/configuration/librechat_yaml/object_structure/agents#backgroundtasks) を設定してください。バックグラウンドディスパッチは、Code Interpreterサービスの実行制限を延長するものではありません。デプロイメントの通常のサーバーサイドタイムアウトが引き続き適用されます。

[`ordinaryToolCancellation: true`](/docs/configuration/librechat_yaml/object_structure/agents#backgroundtasks) を使用すると、所有者は添付されたBashを含む、通常のバックグラウンドCodeツールの協調的なキャンセルを要求できます。タスクは呼び出しが完了するまでアクティブなままとなり、容量を消費します。キャンセルを無視するツールは、そのまま完了する場合があります。

### ステートフルなコードセッション [#stateful-code-sessions]

Stateful code sessions（ステートフルなコードセッション）により、LibreChat Agentは実行間でCode Interpreterのサンドボックスワークスペースを再利用できるようになります。ファイル、インストール済みのパッケージ、および作業状態が通常引き継がれるため、反復的な分析や複数ステップのファイル生成がより効率的になります。各エージェントは、以下のいずれかのワークスペーススコープを選択します。

- **ユーザーワークスペース（推奨）:** ステートフルが有効なエージェント全体で、サインインしたユーザーに対して1つのワークスペースを提供します。
- **エージェント + ユーザーワークスペース:** 各ユーザーとエージェントの組み合わせにつき1つのワークスペース
- **Conversation workspace:** 各ユーザーおよび各会話につき1つのワークスペース

新しく作成されたAgentの初期スコープは、**設定 > データコントロール > コード実行 > デフォルトのステートフルワークスペース**から取得されます。個人の設定はデフォルトで**ユーザーワークスペース**になっています。これを変更しても、既存のAgentが変更されたり、ステートフルセッションが有効になったりすることはありません。デプロイメント管理者は、[`statefulCodeSessions.allowedEnvironments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions)を使用して、選択可能なスコープを制限できます。保存された個人のデフォルトが利用できなくなった場合、新しいAgentは許可された最初のスコープを使用します。許可されなくなったスコープを持つ既存の有効なAgentは、実行する前に再設定する必要があります。

ワークスペースのスコープは、その実行バックエンドとは分離されています。管理者が名前付きの [`statefulCodeSessions.environments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions) を設定すると、Agent Builder に **Execution environment** セレクターが追加されます。

- **Managed:** デプロイメントによって運用されるステートフルな Code API
- **添付:** オペレーターが管理するVMなどのアウトバウンドの `@librechat/code` ワーカーに作業を委託する、互換性のあるCode APIリモートブリッジ
- **Personal:** 認可されたユーザーがLibreChatの設定を通じてペアリングした、オーナーに紐づく `@librechat/code` ワーカー
- **Deployment default:** デフォルトとしてマークされた設定済みの環境

<Callout type="warning" title="非常に実験的">
  Stateful Code Sessionsは初期の実験段階にあります。その動作、設定、永続性の特性、および基盤となる統合は大幅に変更される可能性があります。現在の実装を安定した本番環境向けの契約として扱わないでください。
</Callout>

この機能はオプトイン形式です。[Agents endpoint capabilities](/docs/configuration/librechat_yaml/object_structure/agents#capabilities) で `execute_code` および `stateful_code_sessions` を有効にし、[`LIBRECHAT_CODE_BASEURL_STATEFUL`](/docs/configuration/dotenv#stateful-code-interpreter-endpoint) または名前付き環境を使用して専用のステートフルルートを設定し、エージェントで Code Interpreter を有効にした上で、詳細設定（Advanced settings）から **Stateful code sessions** をオンにし、実行バックエンドとワークスペーススコープを選択してください。

Statefulリクエストは、選択された環境が見つからない、アクセスできない、または互換性がない場合に失敗（fail closed）します。LibreChatはそれらを`LIBRECHAT_CODE_BASEURL`に送信したり、別の名前付きバックエンドを自動的に選択したりすることはありません。名前付き環境が設定されていない場合、`LIBRECHAT_CODE_BASEURL_STATEFUL`が引き続きステートフルなルートとなります。ステートレスなエージェントは、通常のendpointを引き続き使用します。また、LibreChatは`X-CodeAPI-Expected-Profile: stateful`を送信するため、専用サービスは`stateful`プロファイルをアドバタイズする必要があります。

Stateful（ステートフル）およびstateless（ステートレス）セッションは、ライブワークスペースを共有しません。Statefulワークスペースは、選択されたスコープに関係なく、いつでもリセットされる可能性があります。管理されたCode Interpreter環境では、重要な出力は `/mnt/data` 配下に保存し、それ以外のセッション状態を永続的なストレージとして信頼しないでください。アタッチされたワークスペースは、ワーカーが所有する別のディレクトリであり、アップロードされたファイルはデフォルトではそこに配置されません。

statefulな `create_file` および `edit_file` 呼び出しによって作成されたファイルは、アシスタントメッセージ内の展開可能な **Workspace changes** 行に表示されます。ここには、その応答で変更された各固有のパスがリストされ、認証済みのダウンロードアクションが提供されます。ダウンロードには、利用可能な場合はLibreChatの永続化されたファイルフローが使用され、それ以外の場合は安全なCode Interpreterフォールバックが使用されます。この行は作成された出力の記録であり、永続的なワークスペースのスナップショットではありません。ステートレスな出力は、引き続き通常のインライン添付ファイルとして表示されます。

#### 接続された環境とペアリング [#attached-environments-and-pairing]

Attached environmentsには、対応する実験的なCode Interpreter remote-bridgeビルドが必要です。bridgeはLibreChatの認証済みポリシー、キュー、および結果の境界として機能し、`@librechat/code`ワーカーは接続されたマシンからアウトバウンドで接続します。そのため、マシン側でインバウンドのパブリックワーカーポートを開放する必要はありません。LibreChatはAttached environmentsを事前起動（prewarm）しません。

オペレーターは、デプロイメント所有の接続済み環境を `workerId` を使用して特定のワーカーに固定でき、LibreChatが同じルートに対して管理者ペアリングコードを発行する必要がある場合は `pairing.workerId` を追加できます。`pairing.tokenEnv` は、ブリッジ管理者トークンを含む環境変数を指定します。シークレット自体を YAML に含めてはなりません。ペアリングされたコントロールプレーンには、ループバック開発環境以外では HTTPS が必須です。

セルフサービスワーカーの場合は、`pairing.allowPrincipalWorkers: true` および `pairing.tokenEnv` を使用して、デプロイメント所有の接続済みコントロールプレーンを設定してください。これはワーカーIDの両方を省略し、登録用コントロールプレーンとしてのみ存在させることも可能です。そのようなエントリは実行用として選択できず、デプロイメントのデフォルトにすることもできません。

Code Environment管理権限を持つユーザーは、**Settings > Code environments**を開き、環境に名前を付け、承認済みのコントロールプレーンを選択して、**Connect VM**を選択できます。LibreChatは、短期間有効な一度限りの`librechat-code pair ...`コマンドを表示します。これをユーザーのVM上で実行し、`LIBRECHAT_CODE_SANDBOX_ENDPOINT`がそのマシンのサンドボックスサービスを指すように設定して、`@librechat/code`を開始します。UIにはユーザーの環境が一覧表示され、後から取り消しや削除を行うことができます。サンドボックスファイルはVM上に残ります。

管理者は [`statefulCodeSessions.principalWorkers`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions) を使用して登録を制限できます。このブロックを省略した場合、登録はデフォルトで有効になり、ユーザーごとに最大5つの環境が登録されます。このカウントには、すべてのコントロールプレーンにわたるオフラインのワーカーも含まれます。デプロイメント設定が上限となり、プリンシパル固有の設定でこれを引き下げたり無効にしたりすることは可能ですが、引き上げることはできません。ポリシーを厳格化しても、すでに登録されているマシンが取り消されることはありません。

パーソナル環境は、認証されたユーザーとテナントに紐付けられ、Code Environment ACLによって保護されており、サーバーで検証されたIDと承認済みのベースURLのみが割り当てられます。LibreChatは、ブリッジ管理者トークンや任意のオペレーターURLをクライアントに公開しません。環境を削除すると、レジストリからエントリが削除される前にワーカーの認証情報が無効化されます。また、ユーザーが削除されると、同様の無効化とクリーンアップがスケジュールされ、中断された試行に対してはバックグラウンドでの照合が行われます。選択されたワーカーのルートは、Code Interpreter、シェル、生成されたファイルへのアクセス、およびプログラムによるツール呼び出し（Programmatic Tool Calling）に一貫して適用されます。

ワークスペースをアタッチしたAgentは、そのディレクトリツリーの一覧表示、ファイルの読み取り、ファイル内容の検索、ファイルの作成や編集、および選択したワーカー上でのBashの実行が可能です。ファイルの引用にはワークスペース相対パスが使用され、作成されたファイルはレスポンスの **Workspace changes** 行に表示されます。また、ツールが失敗した場合は、ワーカーの制限されたHTTP診断情報が保持されます。Agentは、そのワークスペース内で作成されたコミット用に、AgentごとのGit名とメールアドレスを保存することもできます。これらの値は作成者の設定のみに使用され、リポジトリの認証情報を提供するものではありません。

チャット内でBashコマンドの実行に失敗した場合、その終了コード、終了シグナル、またはタイムアウトが表示され、stderrはstdoutとは別にスタイルが適用されます。Bashの出力がどのように表示されるかについては、[Activity Groups](/docs/features/agents#activity-groups) を参照してください。

チャットヘッダーとサイドバーに会話のGitHubプルリクエストを表示するには、接続されたワーカーが自身のgitブランチを報告する必要があります。これには、`LibreChat-AI/code-interpreter` のPR #311以降からビルドされたワーカーが必要であり、Code API（LibreChat側ではありません）で `CODEAPI_BRIDGE_LANE_GIT=true` が設定されている必要があります。詳細は [Conversation Pull Requests](/docs/features/pull_requests) を参照してください。

接続されたワーカーは、利用可能なワークスペースのルートをアドバタイズします。コンポーザーを使用すると、ユーザーはAgentまたはそのサブエージェントを通じて到達可能な各接続環境に対して1つのワークスペースを選択できます。新しい会話では、単一の明確なワークスペースが自動的に選択されます。LibreChatはこれらの選択を会話に保存し、実行前にライブワーカーに対して再検証を行い、承認待ちや再開された実行の間もそれらを固定します。必要な選択が欠落しているか利用できない場合、送信はブロックされ、LibreChatが別のワークスペースに勝手に置き換えることはありません。実行開始時に、LibreChatは選択されたワークスペースからリポジトリの指示を読み込み、Agentがそのリポジトリのガイダンスに従うようにすることができます。管理者は [`repositoryInstructions.timeoutMs`](/docs/configuration/librechat_yaml/object_structure/agents#repositoryinstructions) を使用して検出を制限できます。ネイティブのファイルツールおよびBashワークスペースツールは、ワーカーが再利用可能なランタイムセッションをサポートしていない場合でも、アドバタイズされたルートを使用できます。ワークスペース対応のプログラム可能なBashは、Agentのプログラムツール設定で許可されており、認証された接続ワーカーの準備が整っており、かつ `programmaticLanguages: ['bash']` をアドバタイズしており、さらに選択されたワークスペースとワーカーの両方が `execute_command` を許可している場合に、互換性のあるCode APIおよびワーカービルドで利用可能です。LibreChatは、サーバーで検証されたワークスペースIDと会話ワークスペースインスタンスID（存在する場合）をプログラムツールに渡します。モデルの引数がその選択を置き換えることはできません。これらの機能がない場合、プログラム可能なBashは無効になります。ワークスペース対応のコマンドには直接Bashを使用してください。ワーカーがファイルリレーをサポートしている場合、チャットのアップロードはプログラム実行のために `$LIBRECHAT_CODE_DATA_DIR` 配下に個別にステージングされ、選択されたワークスペースにはコピーされません。**停止（Stop）**は、後のコマンドのためにワークスペースを無効にすることなく、シグナル対応の実行中のBYOMコマンドをキャンセルします。分離された作業は、個別のキャンセルライフサイクルを保持します。

接続された実行環境に対して、Agent Builderは現在アドバタイズされているルートのいずれかを**ワークスペースのデフォルト**として設定できます。これは接続された環境に対して検証され、そのAgentの新しい会話を初期化するために使用されます。**最後に使用したもの**を選択すると、そのAgentと環境に対してサインインしているユーザーのブラウザローカルの設定が使用されます。これはあくまで利便性のためのヒントであり、認可の付与や会話のバインディングを行うものではありません。実行環境を変更すると明示的なデフォルトはクリアされ、アドバタイズされなくなった保存済みルートは表示されたままになりますが、再設定されるまで選択することはできません。

#### 保存済みチャットワークスペースの変更 [#saved-chat-workspace-changes]

デフォルトでは、保存された会話に添付されたワークスペースの決定は固定（sealed）されています。[`statefulCodeSessions.conversationMoves.enabled`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions) を有効にすると、所有者は明示的に別の許可されたワークスペースへ移動したり、失われたワークスペースを復旧したりできます。復旧によってチャット履歴は保持されますが、失われたワークスペースのファイルは保持され**ません**。`allowAttachDetach: true` を設定すると、さらに所有者は保存済みのコーディング以外のチャットにワークスペースを添付したり、添付されたワークスペースから離れて通常のチャットを継続したりできるようになります。移動を有効にするだけでは、添付/切り離しは有効になりません。これらの移行は生成の実行中には行えず、サーバー上で再検証されます。すべてのAPIレプリカをアップグレードし、オプトインする前に `CODE_ENVIRONMENT_DECISION_VERSION=1` を有効にしてください。これらのスイッチを使用しない場合、既存の移動のみ可能な動作および固定された会話の動作は変更されません。

Attached Bashはデフォルトで30秒のタイムアウトを使用します。環境は[`configSchema.limits.maxCommandTimeoutMs`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions)を使用して、プロトコルの上限である5分まで、より大きなモデル要求可能予算を公開できます。要求されたタイムアウトがデプロイメントの制限を超えることはありません。管理者は[`configSchema.limits.maxQueueWaitMs`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions)を使用して、容量の再試行を個別に制限できます。このキュー待機は、承認済みまたは実行中のコマンドをキャンセルするものではありません。より長い**個別の**承認試行を許可するには、Code APIがリクエストごとのキュー許容量を尊重し、ライブルート上の最短のプロキシタイムアウトが検証された後にのみ、`configSchema.limits.maxRequestTimeoutMs`を使用してください。オプションの`configSchema.limits.minCommandAdmissionMs`は、コマンド前の承認のためにデフォルトで10秒（1〜300秒で有効）を予約します。アドバタイズされるBashタイムアウトは、この予約と、決済および配信のための追加の10秒を差し引いた後のリクエスト予算に合わせて調整されます。この予算は`maxQueueWaitMs`に代わるものではありません。

#### Linked-worktree lanes [#linked-worktree-lanes]

アタッチされた環境では、`configSchema.workspaces.linkedWorktrees: true` を設定することで、[ワークツリーごとのリクエストスケジューリング](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions)を選択できます。まずLibreChatをアップグレードし、互換性のあるCode APIブリッジをデプロイしてから、`--linked-worktree-lanes` を指定してワーカーを起動してください。YAML設定を有効にするのは、そのワーカーが `git_linked_worktree` をアドバタイズした後に行ってください。構造的に `.worktrees/<name>/` をターゲットとするリクエストは、エージェントに表示されるチェックアウト相対パスを変更することなく、そのワークツリーのレーンを使用します。Bashの場合、ツールの `cwd` 引数にワークツリーディレクトリを渡してください。コマンド内で `cd .worktrees/<name>` を実行しても、ルートレーンに留まります。チェックアウトルート操作、環境アクション、および会話ワークスペースインスタンスも同様にルートスコープに留まります。このオプトインを行わない場合、すべてのリクエストは既存のチェックアウト全体のスケジューリングを維持します。

#### ワークスペース編集の照合と競合 [#workspace-edit-matching-and-conflicts]

`edit_file` は、単一の `old_text`/`new_text` 置換のためのトップレベルの `replace_all`、または `edits` バッチが提供される際の各エントリごとのフラグを受け入れます。これがない場合、各 `old_text` は一意の場所に解決される必要があります。提供されるバッチは空ではなく、有効である必要があります。LibreChat は、空または不正な形式の `edits` 値を受け取った場合、トップレベルの置換フィールドにフォールバックするのではなく、拒否します。有効な JSON 文字列化されたバッチおよびブール型の置換フラグは、ネイティブツールの承認前に正規化されるため、プレビューと実行では、レビュー済みのフック書き換えを含め、同一の正規化された編集が使用されます。Skill-file および管理されたサンドボックスでの編集は、LibreChat のサイズおよび一致回数の制限内でのすべての一致の置換をサポートしています。添付されたワークスペースでは、`replace_all` をアドバタイズするワーカーが必要であり、サポートされていないリクエストはディスパッチ前に拒否されます。

`tolerant_match`をアドバタイズする接続済みワーカーでは、編集および保護されたプレビューは、まず完全一致を試み、次に末尾の空白、CRLF、インデントのずれ、または正規化された空白に対する空白許容戦略を試みます。管理者は [`configSchema.edits.tolerantMatching: false`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions) を使用して完全一致を必須にすることができます。成功メッセージは、非完全一致または複数箇所の置換が行われたことを示します。失敗したバッチはアトミック（不可分）に処理されます。つまり、何も書き込まれず、LibreChatは任意のワーカーテキストやファイル抜粋を転送することなく、編集ごとの制限された理由、カウント、候補行番号、またはファイル変更の警告を報告します。

これらのattached-worker機能には、[Code Interpreter #271](https://github.com/LibreChat-AI/code-interpreter/pull/271)を実装した互換性のあるCode APIおよびworkerビルドが必要です。LibreChatは、機能のネゴシエーション後にのみ新しいフィールドを送信します。古いビルドでは、リクエスト形式とマッチング動作は変更されません。LibreChatをアップグレードするだけでは、許容範囲のattached editsや`replace_all`は有効になりません。

#### Attached-environment tool permissions [#attached-environment-tool-permissions]

Attached および personal 環境では、ファイルの書き込みやコマンドまたはコードの実行に対して、デフォルトで「確認を求める（ask-by-default）」承認ポリシーが適用されます。読み取り専用操作および検索操作は、デプロイメントの通常のツールポリシーに従って継続されます。管理者が [`configSchema.permissions`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions) を通じていずれかのカテゴリを公開している場合、Code Environment 管理権限を持つユーザーは、**Settings > Code environments** にて、許可された **Allow**（許可）、**Ask**（確認）、**Deny**（拒否）の値から選択できます。設定が欠落している、古い、または許可されていない場合は、安全のために **Ask** にフォールバックされます。

選択された添付環境がサポートしている場合、コンポーザーには会話レベルの **Code approval mode** が表示されます：

- **Ask before changes** は、ファイルの編集やコマンドの実行前に確認を求めます。
- **Accept edits** は、ファイルの編集を許可しますが、コマンドを実行する前に引き続き確認を求めます。
- **Full access** は、ルーチンのプロンプトなしで両方のカテゴリを許可します。

選択されたモードはその会話に引き継がれ、デプロイメントで許可された値および環境ポリシーと照合されます。**Full access**は、`fileWrite`と`commandExecution`の両方が`allow`を許可している場合にのみ表示されます。これは、サンドボックスの分離、ロールの付与、明示的なendpointの`ask`または`deny`ルール、Skillファイルの確認、あるいは承認フックをバイパスするものではありません。

会話のインポートでは、その受信者に対してCode approval modeを選択することはできません。新しくインポートされた会話や一括コピーされた会話は、現在のポリシーに基づき、受信者の設定またはデフォルトを使用します。一括更新では、ローカルに保存された選択内容が保持されます。既存の会話が遡ってリセットされることはなく、LibreChatで明示的にモードを選択した場合は、その設定が引き続き保持されます。

これらのコントロールは、ファイル作成ツール、シェルおよびコード実行、コンパイルチェック、およびプログラムによるツール呼び出し（Programmatic Tool Calling）を対象としています。通常のファイル書き込みが許可されている場合でも、スキル作成機能が有効なときは、永続的なスキルファイルへの書き込みには引き続き確認が必要です。これらの設定は、VMの分離、ネットワーク、マウント、特権実行、イングレス、エグレス、またはシークレットアクセスを変更するものではありません。

デプロイメントの明示的な [`toolApproval.enabled: false`](/docs/configuration/librechat_yaml/object_structure/agents#toolapproval) 設定は、このベースラインを無効にする緊急オーバーライドです。このオーバーライドがない場合、承認リクエストを提示および再開できない呼び出し元は、アタッチされた環境のツールをサイレントに実行するのではなく、失敗して終了（fails closed）します。

ペアリングはリモートワーカーのトランスポートを認証するものであり、サンドボックスの境界ではありません。ワーカーのローカル実行 endpoint はループバックまたはプライベートネットワーク上に維持し、信頼できないコードに対しては適切な分離モードを使用してください。

実行がアクティブな間、展開されたコードおよびシェルの詳細ペインは、ストリーミングされる引数に合わせて自動的に最下部までスクロールします。上方向にスクロールするとこの追従動作が一時停止されるため、ペインによって表示領域が勝手に移動されることなく、以前の出力を確認できます。

## APIの使用 [#using-the-api]

### LibreChatにて [#in-librechat]

LibreChatでは、以下の主要な方法を通じてAPIがファーストクラスでサポートされています。

1. **[AI Agents](/docs/features/agents#code-interpreter)**: エージェントの設定で Code Interpreter を有効にすると、コードを実行してファイルを自動的に処理できるようになります。

2. **手動実行**: チャットインターフェース内のコードブロックにある「Run Code」ボタンを使用します（以下を参照）。

3. **[Programmatic Tool Calling](/docs/features/agents#programmatic-tool-calling)**: `programmatic_tools` 機能を有効にし、選択した MCP ツールを Programmatic としてマークすることで、エージェントがサンドボックス化されたコードからそれらのツールをオーケストレーションできるようにします。

4. **[Background Tool Calls](/docs/features/agents#background-tool-calls)**: エージェントが適切なコードをバックグラウンドで実行し、その実行中も処理を継続できるようにします。

5. **[Stateful Code Sessions](/docs/features/agents#stateful-code-sessions)**: ユーザー単位、エージェントとユーザーの組み合わせ単位、または会話単位のワークスペースを、エージェントのコード実行間で実験的に再利用します。

![LibreChatでのコードインタープリター](/images/agents/run_code.png)

### APIキーの設定 [#set-up-api-key]

- **ユーザーごとのセットアップ:** プロンプトが表示されたら、LibreChatにAPIキーを入力してください。
- **グローバル設定:** LibreChatの `.env` で `LIBRECHAT_CODE_API_KEY` を設定すると、すべてのユーザーに対して1つのキーを提供できます。

現在の [ClickHouse/code-interpreter](https://github.com/ClickHouse/code-interpreter) サービスは、ローカルモード以外では LibreChat JWT 認証を使用します。API キーは、互換性のある Code Interpreter デプロイメントで引き続き利用可能です。

### セルフホスト型 JWT 認証 [#self-hosted-jwt-authentication]

JWT認証を使用すると、LibreChatは各Code Interpreterリクエストにおいて、認証済みユーザーに対して短期間有効なベアラートークンに署名します。Code Interpreterサービスは一致する公開鍵を検証し、署名されたユーザーおよびテナントコンテキストを使用してファイルとセッションを分離します。秘密の署名鍵はLibreChat内に保持され、Code Interpreterは公開検証鍵のみを受け取ります。

LibreChatの設定方法:

```env
CODEAPI_AUTH_PROVIDER=librechat-jwt
CODEAPI_JWT_PRIVATE_KEY="-----BEGIN PRIVATE KEY-----\n...\n-----END PRIVATE KEY-----"
CODEAPI_JWT_ALGORITHM=EdDSA
CODEAPI_JWT_KID=lc-codeapi-2026-05
CODEAPI_JWT_ISSUER=librechat
CODEAPI_JWT_AUDIENCE=codeapi
CODEAPI_JWT_TTL_SECONDS=300
CODEAPI_JWT_MINT_CACHE_SECONDS=30
CODEAPI_JWT_SINGLE_TENANT_ID=legacy
```

`CODEAPI_JWT_PRIVATE_KEY_BASE64` には代わりにbase64エンコードされたPEMを保持させることができ、`CODEAPI_JWT_PRIVATE_JWK_JSON` はプライベートJWKを受け入れます。LibreChatはEd25519（デフォルトの `EdDSA`）およびRSA（`RS256`）署名をサポートしています。LibreChat側のすべての設定については、[環境変数リファレンス](/docs/configuration/dotenv#code-interpreter-jwt-authentication) を参照してください。

対応するベリファイアを使用して Code Interpreter を設定します:

```env
LOCAL_MODE=false
CODEAPI_AUTH_PROVIDER=librechat-jwt
CODEAPI_JWT_ISSUER=librechat
CODEAPI_JWT_AUDIENCE=codeapi
CODEAPI_JWT_ALLOWED_ALGS=EdDSA
CODEAPI_JWT_JWKS_JSON={"keys":[{"kty":"OKP","crv":"Ed25519","x":"...","kid":"lc-codeapi-2026-05","alg":"EdDSA"}]}
CODEAPI_JWT_SINGLE_TENANT_ID=legacy
```

発行者、オーディエンス、キーID、アルゴリズム、および公開鍵は、LibreChatの署名者と一致している必要があります。Code Interpreterは、`CODEAPI_JWT_PUBLIC_KEY`と`CODEAPI_JWT_KID`、または`CODEAPI_JWT_PUBLIC_KEYS_DIR`から検証用キーを読み込むことも可能です。インラインのJWKSはローテーションに便利です。トークンのTTLは、Code Interpreterサービスの`CODEAPI_JWT_MAX_TTL_SECONDS`以下に維持してください。この値はデフォルトで300秒であり、上限も300秒に設定されています。

ローカルでのチェックアウトの場合、Code Interpreterリポジトリには、対応するEd25519署名キーと実行マニフェストキーを生成し、両方の `.env` ファイルを更新するヘルパーが含まれています。

```bash
node scripts/setup-local-auth-env.js --librechat /path/to/LibreChat
```

シングルテナント環境でのデプロイでは `CODEAPI_JWT_SINGLE_TENANT_ID=legacy` のままでも構いませんが、その値は両方のサービスで一致している必要があります。マルチテナント環境でのデプロイでは、認証されたテナントコンテキストを提供し、LibreChatで `TENANT_ISOLATION_STRICT=true` を、Code Interpreterで `CODEAPI_TENANT_ISOLATION_STRICT=true` をそれぞれ有効にする必要があります。Strictモードでは、シングルテナントのフォールバックを使用する代わりに、テナントコンテキストのないリクエストを拒否します。

### 直接API統合 [#direct-api-integration]

現在のセルフホスト型サービスは、LibreChatのJWTクレーム契約を満たすベアラートークンを必要とします。直接統合を行う場合は、互換性のある短命トークンを発行し、`Authorization: Bearer <token>` ヘッダーで送信する必要があります。一方、APIキー互換のデプロイメントでは、設定されたキーを `x-api-key` ヘッダーで受け入れます。公開エンドポイントや本番環境のエンドポイントでは、Code Interpreterの認証不要なローカルモードを決して使用しないでください。

### セルフホストのベースURL [#self-hosted-base-url]

`LIBRECHAT_CODE_BASEURL` を設定して、LibreChat をセルフホスト型の [code-interpreter](https://github.com/ClickHouse/code-interpreter) インスタンスに向け、その後 [JWT 認証](#self-hosted-jwt-authentication) を設定します。API キー互換サービスの場合は、代わりに `LIBRECHAT_CODE_API_KEY` を設定してください。非常に実験的なステートフルな Agent セッションには、[`LIBRECHAT_CODE_BASEURL_STATEFUL`](/docs/configuration/dotenv#stateful-code-interpreter-endpoint) を通じて設定された個別の `stateful` プロファイルルート、または名前付きの [`statefulCodeSessions.environments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions) が必要です。

## コア機能 [#core-functionality]

### Code Execution [#code-execution]

- サポートされている言語でコードスニペットを実行する
- stdout/stderr出力を受信する
- 実行統計（メモリ使用量、CPU時間）を取得する
- プログラム引数を処理する
- 実行ステータスと結果へのアクセス

### ファイル操作 [#file-operations]

- 入力ファイルをアップロード
- 生成された出力をダウンロード
- LibreChatが安全に抽出・レンダリングできる場合、PowerPointの `.pptx` プレゼンテーションや `.potx` テンプレート、CSV、テキスト、PDFのようなアーティファクトを含む、生成されたOfficeファイルをインラインでプレビューします。
- Agentの `read_file` ツールによって返されたPNG、JPEG、GIF、およびWebP画像を、閲覧可能なアーティファクトとして表示します。
- 利用可能なファイルの一覧を表示
- 不要なファイルを削除
- ファイルセッションの管理

生成されたアーティファクトのプレビューは、意図的にサイズ制限が設けられています。インラインプレビュー抽出のソースファイルサイズ制限を変更するには、LibreChatの`.env`で[`FILE_PREVIEW_MAX_EXTRACT_BYTES`](/docs/configuration/dotenv#inline-file-previews)を設定してください。これより大きいファイルは、引き続きダウンロード可能です。

`read_file` を通じて返されるサンドボックス内の画像には、1 MiB のインライン制限があります。これより大きい画像は、`bash_tool` で処理するためにサンドボックス内に保持されます。`LIBRECHAT_CODE_IMAGE_CHUNK_BYTES` は、対象となる画像を読み取る際に使用される転送チャンクサイズのみを制御するものであり、インライン制限を引き上げるものではありません。

<Callout type="warning" title="レガシーコード出力のアップグレードチェック">
  一意の出力ファイルインデックスが追加される前に、同じ Code Interpreter のファイル名を再生成したデプロイメントでは、インデックスの構築を妨げる重複した MongoDB レコードが存在する可能性があります。`npm run migrate:code-file-duplicates:dry-run` で修復のプレビューを行い、その後 `npm run migrate:code-file-duplicates` で適用してください。このマイグレーションでは、最新の正規ファイル名が保持され、古いレコードには数値のサフィックスが付けられて名前が変更されます。実行が成功した後に、一意のインデックスが構築されます。
</Callout>

### 制限事項 [#limitations]
- コードはネットワークにアクセスできません
- 1回の実行につき最大10ファイルまで生成可能です
- リソース制限（実行あたりのRAM、ファイルアップロードサイズ、リクエストクォータ）は、デプロイメントのプロビジョニングおよび設定方法に依存します。

## ユースケース [#use-cases]

- **コードのテスト**: 複数の言語でコードスニペットをテストします
- **File Processing**: プログラムでファイルを変換および分析する
- **AI Applications**: AIが生成したコードを安全に実行
- **Development Tools**: インタラクティブなコーディング環境を構築する
- **Objective Logic**: コードのロジックと正確性を検証し、AIモデルを改善する

## オープンソースとセルフホスティング [#open-source--self-hosting]

Code Interpreterサービスは、Apache 2.0ライセンスの下で[ClickHouse/code-interpreter](https://github.com/ClickHouse/code-interpreter)にてオープンソースとして公開されています。コード実行を独立したサービスとして維持することで、LibreChatのコアアプリケーションを軽量に保つことができます。つまり、サンドボックスインフラストラクチャが必要な場合にのみデプロイすればよく、チャットアプリとは独立してスケーリングすることが可能です。

このサービスは、独立してスケーリング可能なコンポーネント（APIゲートウェイ、サンドボックス化されたワーカー、ファイルサーバー）のセットとして実行され、強力な分離モード（NsJailまたはlibkrunを介したmicroVM）をサポートしているため、信頼できないコードを安全に実行できます。Docker ComposeおよびHelmのデプロイ手順については、リポジトリのREADMEを参照してください。

## 結論 [#conclusion]

Code Interpreter APIは、分離されたサンドボックス内でコードを実行し、ファイルを管理するための安全で便利な方法を提供します。LibreChatのAgentsを通じて使用する場合でも、アプリケーションに直接統合する場合でも、コード実行のニーズに対して堅牢なソリューションを提供します。

詳細な技術仕様、デプロイガイド、およびAPIリファレンスについては、[code-interpreter repository](https://github.com/ClickHouse/code-interpreter)を参照してください。
