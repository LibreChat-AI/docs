---
 

LibreChatには、ユーザーが安全かつ簡単にサインアップおよびログインできるユーザー認証システムが備わっています。このシステムはスケーラブルであり、パフォーマンスやセキュリティを損なうことなく、多数の同時接続ユーザーを処理することが可能です。

デフォルトでは、メールアドレスによるサインアップとログインが有効になっており、ユーザーはメールアドレスとパスワードを使用してアカウントを作成できます。また、パスワードを忘れた場合にはリセットすることも可能です。

さらに、当システムはGoogle、GitHub、Discord、OpenIDなど、さまざまなプラットフォームからのソーシャルログインを統合できます。これにより、ユーザーは新しいアカウントを作成したり、別のパスワードを覚えたりすることなく、これらのプラットフォーム上の既存のアカウントを使用してログインできるようになります。

詳細については、こちらで提供されている設定ガイドを参照してください： [Authentication](/docs/configuration/authentication)

<Callout type="warning" title="重要">
- スコープなしのシングルテナントデプロイを初めて実行する際は、ログインページの **Sign up** をクリックしてアカウントを作成してください。その最初のアカウントが管理者となり、インスタンス上のすべての管理権限を保持します。テナントスコープのデプロイでは、最初に登録されたユーザーが自動的に昇格されることはありません。信頼された管理フローを通じてテナント管理者をプロビジョニングしてください。ユーザー、グループ、ロール、リソースACL、およびシステムレベルの管理者権限を網羅した完全な認可モデルについては、[Access Control](/docs/features/access_control) を参照してください。
- スコープ外のシングルテナントデプロイメントの場合、最初のアカウントはローカルアカウント（メールアドレスとパスワード）にすることをお勧めします。
</Callout>

**関連項目:** [Access Control](/docs/features/access_control)、ユーザー、グループ、ロールのためのLibreChatのきめ細やかな権限システム。エージェント、プロンプト、MCPサーバー、および機能レベルの権限のリソースごとの共有をカバーしています。

## 二要素認証 [#two-factor-authentication]

ローカルアカウントおよびLDAPアカウントは、**Settings > Account > Two-factor authentication** から第2要素（認証アプリからのワンタイムコードおよびバックアップコード）を追加できます。IDプロバイダー（OAuth、OpenID Connect、SAML）を通じてサインインするアカウントは、そのプロバイダーのMFAを使用します。

管理者は `ENFORCE_TWO_FACTOR_AUTHENTICATION=true` を設定することで、2FAを必須にすることができます。2FAを設定していないユーザーは、サインイン後に **Two-Factor Authentication Required**（二要素認証必須）画面が表示され、LibreChatを利用する前にセットアップを完了する必要があります。一度強制されると、無効化コントロールには **Required by administrator**（管理者により必須化）と表示され、2FAをオフにすることはできなくなります。詳細は [Required Two-Factor Authentication](/docs/configuration/authentication#required-two-factor-authentication) を参照してください。

## Passkeys [#passkeys]

管理者が有効にしている場合、ローカルアカウントのユーザーはパスワードの代わりに**パスキーでサインイン**を使用して、デバイスの画面ロック、パスワードマネージャー、またはセキュリティキーでサインインできます。パスキーの追加と削除は**設定 > アカウント > パスキー**から行えます。どちらの操作も、最初にアカウントのパスワードが求められます。アカウントで2FA（二要素認証）が有効になっている場合、パスキーでのサインイン後にもコードの入力が求められます。設定方法については、[パスキー](/docs/configuration/authentication/passkeys)を参照してください。

## メールアドレスの変更 [#changing-your-email-address]

ローカルアカウントのユーザーは、**Settings > Account > Email address** に移動し、**Change** を選択することで、登録済みのメールアドレスを変更できます。**Change email address** ダイアログで、新しいメールアドレスと現在のパスワードを入力し、**Send verification link** を選択してください。

- 変更は、**新しい**アドレスに送信されたリンクを開いた後にのみ有効になります。このリンクは1回限り有効で、デフォルトでは15分後に期限切れとなります。
- **現在**のメールアドレスには、変更がリクエストされた時点でセキュリティ通知が送信されます。変更が確認されると、両方のアドレスに「メールアドレスが変更されました」という通知が送信されます。
- 新しいアドレスは他のアカウントに属していてはならず、設定されている場合は、デプロイメントで許可されている登録ドメイン内のものである必要があります。
- リンクを開く前にパスワードを変更すると、そのリンクは無効になります。新しいリンクをリクエストしてください。

このオプションは、サーバーがメールを送信でき、かつこの機能が有効になっている場合にのみ表示されます。[メールアドレスの変更](/docs/configuration/authentication/email#email-address-change)を参照してください。

## 2FA管理の試行制限 [#2fa-management-attempt-limits]

二要素認証の設定は、アカウントレベルで試行回数の制限を共有しています。デフォルトでは**5分間に7回のリクエスト**までとなっており、これには有効化、検証、確認、無効化、およびバックアップコードの再生成が含まれます。成功したリクエストも試行回数としてカウントされます。新しいセッションを開始しても、同じテナントおよびアカウントに対して別の制限枠が作成されることはありません。

予算が上限に達した場合、LibreChatは係数の確認やアカウント設定の変更を行う前に、HTTP `429` を返します。設定UIでは、サーバーの `Retry-After` 値を使用していつ再試行できるかが説明されるか、そのヘッダーが利用できない場合は一般的な待機・再試行メッセージが表示されます。再送信する前に待機してください。レート制限（スロットリング）されたリクエストは、コードがチェックされて無効と判断されたことを意味するものではありません。サインイン時の個別の2FAチャレンジは、既存のログイン制限を保持します。

管理者は、デプロイメントの YAML 内で [`rateLimits.twoFactorManagement.requestsPerFiveMinutes`](/docs/configuration/librechat_yaml/object_structure/config#ratelimits) を調整できます。これには `3` 以上の整数を指定する必要があり、3回の呼び出しによるセットアップシーケンスを許可します。この制限を `0` で無効にすることはできません。マルチプロセス環境でのデプロイメントでは、デプロイメント全体で予算を共有するために Redis が必要です。Redis がない場合、各 API プロセスは個別にリクエスト数をカウントします。

## サインイン状態の維持 [#staying-signed-in]

LibreChatを使用するにはアカウントが必要です。チャットのための匿名モードやゲストモードは存在しないため、ログインせずに会話を開始することはできません。唯一の例外は閲覧です。管理者が `ALLOW_SHARED_LINKS_PUBLIC=true` を設定している場合、[共有リンク](/docs/features/shareable_links) を持っている人は誰でもアカウントなしでその会話を閲覧できます。ただし、閲覧のみが可能です。

セッションの持続時間は2つの設定によって決定され、どちらも設定可能です：

- `SESSION_EXPIRY`: アクセストークンの有効期間。デフォルトは **15分** です。
- `REFRESH_TOKEN_EXPIRY`: 全体的なサインイン状態の保持期間。デフォルトは **7日間** です。

LibreChatの使用中、短いアクセストークンはバックグラウンドで自動的に更新されるため、15分という数値は再ログインを求められる頻度ではありません。サインアウトされる場合は通常、リフレッシュトークンの有効期限が切れたか、ブラウザがリフレッシュクッキーを破棄したことを意味します。

更新のたびに新しいリフレッシュトークンが返されますが、これは同じセッションに対して署名されており、そのセッションの元の有効期限を引き継ぎます。したがって、`REFRESH_TOKEN_EXPIRY` は最後にアクティブだった時ではなく、ログインした時点から計測されます。アクティブな状態を維持しても有効期限は延長されず、期間が終了するとサインアウトされます。

予期せずログアウトされてしまう場合は、`REFRESH_TOKEN_EXPIRY` の値を上げてください。両方の変数は [.env reference](/docs/configuration/dotenv) に記載されています。

<Callout type="info" title="OpenIDトークンの再利用はセッションの所有者を変更します">

上記はすべて、LibreChatが独自に発行するリフレッシュトークンについて説明しています。[`OPENID_REUSE_TOKENS=true`](/docs/configuration/authentication/OAuth2-OIDC/token-reuse) を設定すると、クッキーには代わりにOpenIDプロバイダーのリフレッシュトークンが保持されるようになり、そのプロバイダーの有効期間、ローテーション、および失効ポリシーによってセッションの終了タイミングが決定されます。`REFRESH_TOKEN_EXPIRY` は、期限切れや失効したIdP認証情報を延長するものではありません。セッションポリシーを変更する場合は、プロバイダー側で行ってください。

</Callout>
