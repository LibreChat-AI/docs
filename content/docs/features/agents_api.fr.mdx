<Callout type="warning" title="Fonctionnalité bêta">
L'API Agents est actuellement en version bêta. Les endpoints, les formats de requête/réponse et le comportement peuvent changer à mesure que nous progressons vers une version stable.
</Callout>

LibreChat expose les agents à des applications, scripts et services externes via des API d'inférence et de diffusion d'événements.

## Vue d'ensemble [#overview]

L'API Agents fournit deux interfaces d'inférence, une livraison d'événements authentifiée et des routes de gestion bêta :

- **Chat Completions compatibles avec OpenAI** — `POST /api/agents/v1/chat/completions`
- **API de réponses ouvertes** — `POST /api/agents/v1/responses`
- **Événements d'agent** — `POST /api/agents/v1/events`
- **Gestion des agents** — `/api/agents/v1/agents`
- **Gestion des compétences** — `/api/agents/v1/skills`

Les interfaces d'inférence prennent en charge l'authentification par clé API, l'authentification OIDC optionnelle et les réponses en streaming. Les Agent Events utilisent l'authentification par clé API des Remote Agents afin que LibreChat puisse lier chaque livraison à une identité source stable. Les routes de gestion utilisent quant à elles une liste d'autorisation de déploiement qui lie un client machine OIDC à un utilisateur et un tenant LibreChat existants.

LibreChat adopte [Open Responses](https://www.openresponses.org/) comme cadre d'API principal pour servir les agents. Bien que le endpoint Chat Completions assure une rétrocompatibilité avec les outils existants compatibles avec OpenAI, le endpoint Open Responses représente l'orientation future.

## Activation de l'API Agents [#enabling-the-agents-api]

L'API Agents est protégée par la configuration de l'interface `remoteAgents`. Toutes les autorisations sont définies par défaut sur `false`.

```yaml filename="librechat.yaml"
interface:
  remoteAgents:
    use: true
    create: true
```

Voir [Interface Configuration — remoteAgents](/docs/configuration/librechat_yaml/object_structure/interface#remoteagents) pour toutes les options disponibles.

**Note :** Les utilisateurs administrateurs ont toutes les permissions d'agent distant activées par défaut.

### Spécification OpenAPI et documentation interactive [#openapi-specification-and-interactive-docs]

LibreChat peut servir la spécification de l'API publique des Agents sur `/api/openapi.json` et la documentation interactive Swagger UI sur `/api/docs`. Les deux routes sont désactivées par défaut. Activez-les avec le paramètre de premier niveau `openapi` :

```yaml filename="librechat.yaml"
openapi:
  enabled: true
```

La spécification couvre les routes publiques d'inférence, d'événement, de gestion des Agents et de gestion des Skills décrites sur cette page. Gardez les routes désactivées à moins que votre déploiement n'ait l'intention d'exposer la documentation de l'API.

## Gestion des clés API [#api-key-management]

Une fois que `remoteAgents.use` et `remoteAgents.create` sont activés, les utilisateurs peuvent générer des clés API depuis l'interface utilisateur de LibreChat. Ces clés authentifient les requêtes vers l'API Agents.

## Authentification [#authentication]

L'API Agents prend en charge deux méthodes d'authentification qui peuvent être utilisées indépendamment ou conjointement.

### Clé API [#api-key]

L'authentification par clé API est activée par défaut. Générez des clés API depuis l'interface utilisateur de LibreChat une fois que `remoteAgents.use` et `remoteAgents.create` sont activés.

```bash
Authorization: Bearer <YOUR_API_KEY>
```

### Jeton porteur OIDC [#oidc-bearer-token]

Pour les scénarios machine-à-machine où votre infrastructure dispose déjà d'un fournisseur OIDC, vous pouvez vous authentifier directement avec des jetons Bearer OIDC sans clé API LibreChat.

Configurez l'authentification OIDC dans `librechat.yaml` :

```yaml filename="librechat.yaml"
endpoints:
  agents:
    remoteApi:
      auth:
        apiKey:
          enabled: false
        oidc:
          enabled: true
          issuer: https://auth.example.com/realms/myrealm
          # jwksUri is optional and auto-discovered from issuer if omitted
          audience: my-client-id
```

Ensuite, appelez l'API avec votre jeton d'accès OIDC :

```bash
curl -X POST https://your-librechat-instance/api/agents/v1/responses \
  -H "Authorization: Bearer YOUR_OIDC_ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"model": "agent_abc123", "input": "Hello!"}'
```

<Callout type="info">
  Le jeton OIDC doit appartenir à un utilisateur qui existe déjà dans LibreChat. La correspondance utilise d'abord la revendication `sub`, puis se rabat sur `email`, `preferred_username` ou `upn`.
</Callout>

Voir [Agents Endpoint - remoteApi](/docs/configuration/librechat_yaml/object_structure/agents#remoteapi) pour toutes les options de configuration.

<Callout type="warning" title="Les événements d'agent nécessitent une clé API">
  L'authentification OIDC uniquement n'est pas prise en charge pour les endpoints Agent Events. Utilisez une clé API Remote Agents lors de la création de liaisons, de la mise en file d'attente d'événements et de l'interrogation du statut de livraison.
</Callout>

## API de gestion des agents [#agent-management-api]

L'API de gestion des Agents en version bêta permet à un service de gérer les Agents et leurs ressources associées sans session de navigateur. Elle est authentifiée indépendamment de l'inférence et des événements d'Agent (Agent Events) : seuls les jetons machine OIDC configurés sous [`endpoints.agents.managementApi`](/docs/configuration/librechat_yaml/object_structure/agents#managementapi) sont acceptés.

Chaque client OAuth configuré est lié à un `userId` et un `tenantId` LibreChat existants. Après la vérification du jeton, chaque requête est exécutée en tant qu'utilisateur et conserve les capacités de rôle actuelles de l'utilisateur, les ACL des Agents et des Skills, les restrictions de fournisseur, les autorisations d'outils, les limites de fichiers et l'isolation des tenants. Une liaison de client ne fait pas de l'utilisateur un administrateur et n'accorde pas l'accès à des ressources que l'utilisateur ne peut pas gérer par ailleurs.

### Routes d'agent [#agent-routes]

| Méthode | Route | Objectif |
| -------- | ------------------------------------------ | -------------------------------------------- |
| `POST`   | `/api/agents/v1/agents`                    | Créer un Agent |
| `GET`    | `/api/agents/v1/agents`                    | Lister les Agents accessibles |
| `GET`    | `/api/agents/v1/agents/{id}`               | Lire un Agent accessible |
| `PATCH`  | `/api/agents/v1/agents/{id}`               | Mettre à jour un Agent |
| `DELETE` | `/api/agents/v1/agents/{id}`               | Supprimer un Agent |
| `POST`   | `/api/agents/v1/agents/{id}/files`         | Téléverser et joindre un fichier de ressource à l'Agent |
| `GET`    | `/api/agents/v1/agents/{id}/files`         | Lister les fichiers joints accessibles par l'Agent |
| `DELETE` | `/api/agents/v1/agents/{id}/files/{fileId}` | Supprimer un fichier joint de l'Agent |

Les charges utiles de création et de mise à jour d'un Agent utilisent les mêmes champs pris en charge en externe que l'Agent Builder et rejettent les champs de premier niveau inconnus. La création nécessite un `model` ; la mise à jour n'accepte que les champs fournis. Les réponses exposent la configuration de l'Agent prise en charge ainsi que `id`, `provider`, `model` (pouvant être nul), `version`, `createdAt` et `updatedAt`, sans les champs de propriété de persistance.

Les listes acceptent un `limit` allant de 1 à 100, avec une valeur par défaut de 20, ainsi qu'un `cursor` opaque. Lorsque `has_more` est vrai, passez la valeur `after` renvoyée comme curseur suivant ; ne décodez pas et ne construisez pas de curseurs dans les clients.

```bash
curl https://your-librechat-instance/api/agents/v1/agents?limit=20 \
  -H "Authorization: Bearer YOUR_MACHINE_ACCESS_TOKEN"
```

```bash
curl -X POST https://your-librechat-instance/api/agents/v1/agents \
  -H "Authorization: Bearer YOUR_MACHINE_ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Release assistant",
    "provider": "openAI",
    "model": "gpt-5.6",
    "instructions": "Prepare concise release notes from verified changes."
  }'
```

Les téléchargements de fichiers utilisent `multipart/form-data` avec un `file` et une valeur `tool_resource` telle que `context`, `file_search` ou `execute_code`. LibreChat applique les vérifications de capacité de déploiement, d'octroi de rôle, de limite de taux de téléchargement, par fichier, de nombre de fichiers et de taille globale avant de joindre la ressource. La suppression d'un fichier nécessite un accès en modification à l'Agent et n'affaiblit pas les règles d'autorisation de fichier sous-jacentes.

### Routes de compétences [#skill-routes]

| Méthode | Route | Objectif |
| ------- | ---------------------------------------------------- | ------------------------------------- |
| `GET`   | `/api/agents/v1/skills`                              | Lister les Skills accessibles |
| `GET`   | `/api/agents/v1/skills/{id}`                         | Lire un Skill accessible |
| `PATCH` | `/api/agents/v1/skills/{id}`                         | Mettre à jour les métadonnées d'un Skill pris en charge |
| `GET`   | `/api/agents/v1/skills/{id}/files`                   | Lister les fichiers dans le Skill |
| `GET`   | `/api/agents/v1/skills/{id}/files/{relativePath}`    | Lire un fichier de Skill |
| `PUT`   | `/api/agents/v1/skills/{id}/files/{relativePath}`    | Créer ou remplacer un fichier pris en charge |

Les opérations sur les Skills sont limitées aux Skills visibles par l'utilisateur lié. Les lectures nécessitent un accès aux Skills, tandis que les écritures de métadonnées ou de fichiers nécessitent les autorisations correspondantes de modification et de création de Skills. Les chemins sont normalisés sous la racine du Skill ; le parcours de répertoires, les fichiers non pris en charge et le contenu trop volumineux sont rejetés.

### Erreurs et authentification [#errors-and-authentication]

Les réponses de gestion utilisent des erreurs structurées avec les codes `invalid_request`, `not_found`, `permission_denied`, `conflict` ou `internal_error`. Les échecs d'autorisation de ressources peuvent être renvoyés sous forme de `not_found` afin que les appelants ne puissent pas sonder les identifiants inaccessibles.

Les jetons machine doivent être valides (non expirés), correspondre à l'émetteur configuré, identifier un client autorisé via `azp` ou `client_id`, et satisfaire la règle de sujet configurée. Par défaut, les jetons doivent également correspondre à l'audience configurée. Pour les fournisseurs tels qu'Amazon Cognito qui émettent des jetons d'accès machine avec `client_id` au lieu de `aud`, définissez `tokenUse: access`, omettez `audience`, et exigez la portée OAuth attendue avec `requiredScopes`. Une configuration manquante ou des identifiants invalides renvoient `401` ; un compte lié en cours de suppression renvoie `409`. Consultez [`managementApi.auth.oidc`](/docs/configuration/librechat_yaml/object_structure/agents#managementapiauthoidc) et [`managementApi.auth.clients`](/docs/configuration/librechat_yaml/object_structure/agents#managementapiauthclients) pour les règles complètes de revendication et de liaison.

## Endpoints [#endpoints]

### Chat Completions (compatibles avec OpenAI) [#chat-completions-openai-compatible]

```
POST /api/agents/v1/chat/completions
```

Utilisez n'importe quel SDK compatible avec OpenAI en le pointant vers votre instance LibreChat. Le paramètre `model` correspond à un ID d'agent.

**Exemple avec curl :**
```bash
curl -X POST https://your-librechat-instance/api/agents/v1/chat/completions \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "agent_abc123",
    "messages": [
      {"role": "user", "content": "Hello, what can you help me with?"}
    ],
    "stream": true
  }'
```

**Exemple avec le SDK OpenAI (Python) :**
```python
from openai import OpenAI

client = OpenAI(
    base_url="https://your-librechat-instance/api/agents/v1",
    api_key="YOUR_API_KEY"
)

response = client.chat.completions.create(
    model="agent_abc123",
    messages=[{"role": "user", "content": "Hello!"}],
    stream=True
)

for chunk in response:
    print(chunk.choices[0].delta.content, end="")
```

### Lister les modèles [#list-models]

```
GET /api/agents/v1/models
```

Renvoie les agents disponibles en tant que modèles. Utile pour découvrir quels agents sont accessibles avec votre clé API.

### API des réponses ouvertes [#open-responses-api]

```
POST /api/agents/v1/responses
```

L'endpoint Open Responses suit la [spécification Open Responses](https://www.openresponses.org/), un standard d'inférence ouvert initié par OpenAI et construit par la communauté de l'IA open-source. Il est conçu pour les flux de travail agentiques avec une prise en charge native du raisonnement, de l'utilisation d'outils, des sorties structurées et des événements sémantiques en streaming.

```bash
curl -X POST https://your-librechat-instance/api/agents/v1/responses \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "agent_abc123",
    "input": "What is the weather today?"
  }'
```

#### Outils de fonction exécutés par l'appelant [#caller-executed-function-tools]

L'endpoint Open Responses accepte les outils `function` standards fournis par l'appelant. LibreChat expose ces définitions au modèle mais ne les exécute pas. Lorsque le modèle en sélectionne un, la réponse contient un élément de sortie `function_call` que l'appelant doit exécuter.

Pour continuer, envoyez une nouvelle requête dont l'élément `input` rejoue l'élément `function_call` renvoyé, suivi d'un élément `function_call_output` correspondant. Ce transfert est sans état : il ne crée pas d'exécution suspendue, et `previous_response_id` seul ne peut pas remplacer l'échange d'outils rejoué.

```json
{
  "model": "agent_abc123",
  "input": [
    {
      "type": "function_call",
      "call_id": "call_abc123",
      "name": "lookup_order",
      "arguments": "{\"order_id\":\"A-42\"}"
    },
    {
      "type": "function_call_output",
      "call_id": "call_abc123",
      "output": "{\"status\":\"shipped\"}"
    }
  ]
}
```

Les noms des outils appelants peuvent contenir des lettres, des chiffres, des underscores et des traits d'union. Les noms doivent être uniques et ne peuvent pas remplacer un outil fourni par le serveur. Un outil exécuté par l'appelant doit être le seul outil sélectionné lors de son tour ; si le modèle le mélange avec des outils exécutés par le serveur, LibreChat demande au modèle de réessayer l'outil appelant seul.

Pour les outils d'agent exécutés par LibreChat, les deux points de terminaison d'inférence sans interface (headless) appliquent une politique [`endpoints.agents.toolApproval`](/docs/configuration/librechat_yaml/object_structure/agents#toolapproval) activée, incluant `deny`, `ask` et les hooks programmatiques. Ces appels ne disposent d'aucun canal interactif d'approbation/reprise : `deny` et `ask` bloquent l'outil au lieu d'ouvrir une invite d'approbation. Configurez des autorisations explicites uniquement pour les outils que le client API doit pouvoir exécuter sans surveillance ; lorsque la politique est désactivée, ses hooks d'approbation ne s'exécutent pas. Les outils de fonction exécutés par l'appelant restent sous la responsabilité de l'appelant.

## Événements d'agent [#agent-events]

Les Agent Events permettent à un contrôleur authentifié ou à un adaptateur source de transmettre un travail durable à un Agent. La distribution d'événements est une fonctionnalité en version bêta et son comportement en matière de requête, de réponse et d'exécution est susceptible de changer.

Les endpoints utilisent l'utilisateur authentifié, le tenant et la clé API ; l'Agent cible doit être visible pour cet utilisateur selon les permissions existantes des Remote Agents. Les requêtes Agent Event utilisent également le bucket dédié [`rateLimits.agentEvents`](/docs/configuration/librechat_yaml/object_structure/config#ratelimits).

### Délivrer un événement [#deliver-an-event]

```http
POST /api/agents/v1/events
Authorization: Bearer <REMOTE_AGENTS_API_KEY>
Idempotency-Key: webhook-42-resource-7
Content-Type: application/json

{
  "mode": "fire",
  "event": {
    "id": "resource-7-ready-3",
    "type": "resource.ready",
    "occurredAt": 1786967999000,
    "payload": { "resourceId": "resource-7" }
  },
  "target": { "agentId": "agent_abc123" },
  "input": "Resource resource-7 is ready. Inspect it and report the result.",
  "orderingKey": "resource-7"
}
```

Envoyez exactement un en-tête `Idempotency-Key` et réutilisez-le lors de la nouvelle tentative de livraison du même événement source vers la cible. La clé doit contenir entre 1 et 256 lettres, chiffres ou les caractères `._~:/+=-`. La réutilisation d'une clé avec un contenu de livraison différent renvoie un conflit.

L'appelant fournit l' `id`, le `type`, `occurredAt` et le `payload` nettoyé de l'événement. LibreChat remplace tout `event.source` fourni par l'appelant par l'identité de la clé API authentifiée et déduit l'utilisateur, le locataire (tenant), l'ID de requête et l'heure de réception. Ne placez pas d'identifiants ou de secrets de transport dans les charges utiles (payloads) d'événements, car les livraisons acceptées sont persistées.

`orderingKey` est facultatif. Utilisez une valeur stable lorsque les livraisons provenant de différentes sources doivent rester ordonnées pour la même ressource.

Une requête réussie renvoie `202 Accepted`, un `id` de livraison opaque, son statut actuel et un en-tête `Location`. Interrogez cet emplacement :

```http
GET /api/agents/v1/events/{delivery_id}
Authorization: Bearer <SAME_REMOTE_AGENTS_API_KEY>
```

La livraison peut être `pending`, `leased`, `succeeded` ou `dead`. La réponse de statut inclut les tentatives et les horodatages ainsi qu'un résultat ou une erreur publique une fois réglée ; elle n'expose pas la charge utile stockée, la clé de commande, l'historique des tentatives ou l'identité du travailleur. L'accès au statut est limité au même utilisateur, au même locataire et à la même source de clé API.

Pour un `continue` lié, `succeeded` signifie que le tour de l'Agent a été admis, et non que le travail demandé est terminé. Son statut expose donc également un cycle de vie `handling` durable : `started`, suivi exactement de l'un des états suivants : `applied`, `completed_no_action`, `failed` ou `cancelled`.

Les sources sensibles aux actions peuvent inclure une `expectedAction` avec un nom d'outil et un sous-ensemble d'arguments optionnel. LibreChat rapporte `applied` uniquement lorsque cette génération exacte se termine avec une preuve d'outil observée par l'hôte correspondant au contrat ; la prose rédigée par le modèle n'est jamais acceptée comme preuve. Les envois `fire`, `steer` et `continue` non liés rejettent `expectedAction`.

Les résultats `fire` réussis incluent l'identité de la conversation et de la génération qu'un événement `steer` ultérieur peut cibler.

### Agents enfants pilotés par les événements [#event-driven-child-agents]

Un système externe peut lier un acteur source à un Agent enfant direct, puis poursuivre cette même conversation enfant à travers les événements. Les continuations d'enfants liés sont automatiques une fois que les vérifications de l'identité par clé API, de la propriété de liaison, de la relation parentale et de l'autorisation de l'Agent ont réussi ; il n'y a pas de commutateur de fonctionnalité distinct.

Enregistrez l'acteur avec la même clé API que celle qui fournira ses tours ultérieurs :

```http
POST /api/agents/v1/events/bindings
Authorization: Bearer <REMOTE_AGENTS_API_KEY>
Idempotency-Key: championship-7-player-hanae
Content-Type: application/json

{
  "actorId": "hanae-kobayashi",
  "parentConversationId": "director-conversation-id",
  "parentMessageId": "director-message-id",
  "target": { "agentId": "agent_hanae" }
}
```

`actorId` peut contenir jusqu'à 128 caractères. Le parent doit être une conversation d'Agent ordinaire, et la cible doit être configurée comme l'un des Sous-agents directs de cet Agent ou comme un auto-spawn autorisé. Une nouvelle liaison renvoie `201` ; une relecture idempotente renvoie `200`. Les deux réponses incluent `id`, `actorId`, `agentId` et `threadId`.

Envoyez les tours ultérieurs avec l'ID de liaison renvoyé :

```http
POST /api/agents/v1/events
Authorization: Bearer <SAME_REMOTE_AGENTS_API_KEY>
Idempotency-Key: game-12-ply-17-hanae
Content-Type: application/json

{
  "mode": "continue",
  "bindingId": "evtbind_...",
  "event": {
    "id": "game-12-ply-17",
    "type": "chess.turn.ready",
    "occurredAt": 1786968000000,
    "payload": { "gameId": "game-12", "expectedPly": 17 }
  },
  "input": "Your clock is running. Read the position and submit one legal move.",
  "expectedAction": {
    "tool": "submit_move",
    "arguments": { "gameId": "game-12" }
  }
}
```

LibreChat résout l'Agent enfant, le fil de discussion, la dernière feuille de branche et la voie de commande à partir de la liaison immédiatement avant la répartition. Les champs de cible et de commande fournis par l'appelant ne peuvent pas rediriger une continuation liée. La clé `Idempotency-Key` de la requête devient l'identité publique stable pour ce tour enfant à travers les tentatives de livraison, la location de génération, les messages persistés, l'activité en direct et une reprise HITL ultérieure.

Chaque liaison dispose d'une boîte aux lettres durable automatique. Son événement suivant reste en file d'attente jusqu'à ce que le tour actuel atteigne `applied`, `completed_no_action`, `failed` ou `cancelled` ; les différentes liaisons restent indépendantes et peuvent s'exécuter en parallèle. La continuation par point de contrôle n'est tentée que pour un tour initialisé compatible. Si un point de contrôle est manquant ou ne peut pas être restauré, LibreChat revient à l'historique des messages durables sans affaiblir les vérifications de réception, d'autorisation ou d'action attendue.

Un acteur lié peut se mettre en pause pour une demande utilisateur (Ask User) ou une approbation d'outil. LibreChat conserve la suspension signée exacte avant d'exposer l'action en attente, et la boîte aux lettres de la liaison reste bloquée jusqu'à ce que cette même invocation d'acteur reprenne ou se termine. Les Event Actors nécessitent le checkpointer durable MongoDB ; `type: memory` n'est pas compatible. LibreChat négocie le protocole de génération v2 et sélectionne automatiquement le point de contrôle ou la continuation de l'historique. Le travail existant sous le protocole v1 reste sur le chemin de l'historique durable jusqu'à son épuisement. Voir [Generation Protocol Compatibility](/docs/configuration/redis#generation-protocol-compatibility) pour les exigences de déploiement en version mixte.

### Fusion des événements observationnels [#coalescing-observational-events]

Les sources capables de prouver que plusieurs événements `continue` liés sont des observations interchangeables peuvent leur attribuer la même `coalesce.key` définie par la source :

```json
{
  "mode": "continue",
  "bindingId": "evtbind_...",
  "event": {
    "id": "championship-7-game-12-move-18",
    "type": "chess.move.completed",
    "occurredAt": 1786968000750,
    "payload": { "gameId": "game-12", "ply": 18 }
  },
  "input": "A tournament game advanced.",
  "coalesce": { "key": "championship-commentary" }
}
```

LibreChat collecte les événements compatibles pendant une durée maximale de 750 ms, avec au plus 8 événements et 512 KiB d'enveloppes combinées. L'enfant reçoit un document de lot déterministe, mais chaque événement source conserve sa propre `Idempotency-Key`, son enregistrement de livraison et son accusé de réception.

Utilisez la coalescence uniquement pour les observations sans action requise. Elle est rejetée pour `fire`, `steer`, `continue` non lié, et les livraisons avec `expectedAction` ; ne l'utilisez pas pour les commandes, les approbations, les demandes HITL, les clôtures ou les événements dont le timing individuel est important.

Dans la conversation parente authentifiée, chaque acteur lié apparaît sous son message parent propriétaire. Le panneau Subagent permet de basculer entre les acteurs et les tours, de charger une activité antérieure et de développer un tour pour afficher son activité liée complète. Les détails de l'événement incluent le type, la source, l'heure de survenance et l'action attendue. Les étapes d'exécution, les outils, les messages et les marqueurs de raisonnement visibles sont inclus sans le texte de raisonnement brut. L'index parent renvoie au maximum 64 fils de discussion enfants et 20 tâches récentes par enfant à partir d'une fenêtre source liée, signale une troncature au lieu d'impliquer une exhaustivité, et limite la réponse à 96 Ko. Il est autorisé au niveau du parent, de l'utilisateur et du locataire ; les liaisons, les identifiants de clé source, les jetons de bail et l'état du travailleur ne sont pas inclus dans la projection.

Le thread enfant reste masqué de la navigation de conversation normale et est en lecture seule pour les routes de chat humaines, hérite de la politique temporaire ou d'expiration du parent, et est limité à un niveau d'enfant direct. Un ID de liaison seul ne donne pas accès ; les continuations sont limitées à l'utilisateur, au locataire et à la clé API qui les ont créées.

### Actions de l'acteur d'événement détaché [#detached-event-actor-actions]

Les tours d'acteur d'événement peuvent détacher des Actions éligibles et les exécuter de manière durable. La livraison reste dans son cycle de vie de traitement pendant que l'Action s'exécute ; une preuve terminale durable reprend l'invocation originale de l'acteur signé, et seule la preuve d'outil observée par l'hôte résultante peut satisfaire `expectedAction`. Les relectures et les répliques concurrentes ne peuvent pas lancer deux fois la même Action réservée. Si LibreChat ne peut pas déterminer si un effet secondaire externe a commencé, il met le lancement en quarantaine au lieu de le réessayer aveuglément.

LibreChat active automatiquement ce travail de complétion interne lorsque le magasin de génération intégré sélectionné annonce sa prise en charge. Le magasin en mémoire exécute le lancement, la complétion et la continuation dans un seul processus et ne peut pas récupérer ce travail après la fermeture du processus. Les flux de génération Redis ajoutent une récupération durable après redémarrage et un transfert de réplica. Les enregistrements de livraison et de récupération appartenant à la fonctionnalité restent invisibles pour les anciens demandeurs lors d'un drainage de version mixte ; il n'existe aucun indicateur de producteur géré par l'opérateur.

## Suivi de l'utilisation des jetons [#token-usage-tracking]

Toutes les requêtes d'inférence de l'API Agents suivent l'utilisation des jetons par rapport au solde de l'utilisateur lorsque la dépense de jetons est configurée. Les réponses en streaming et non-streaming agrègent chaque appel de modèle d'Agent principal et de sous-agent facturé dans les totaux de haut niveau. La réponse inclut également des ventilations de jetons `primary` et `subagent` sans identité. Les détails des jetons de cache et de raisonnement sont inclus lorsque le fournisseur les signale.

## Feuille de route [#roadmap]

- **Open Responses comme interface principale** — Nous prévoyons d'étendre l'endpoint Open Responses avec une prise en charge complète des boucles agentiques, de l'orchestration d'outils et des événements sémantiques en streaming.
- **Anthropic Messages API** — Nous pourrions ajouter la prise en charge du format Anthropic Messages API en tant qu'interface supplémentaire à l'avenir.
