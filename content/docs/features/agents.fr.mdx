# Agents : Créez des assistants IA personnalisés [#agents-build-custom-ai-assistants]

La fonctionnalité d'agents IA de LibreChat fournit un cadre flexible pour créer des assistants IA personnalisés alimentés par divers fournisseurs de modèles.

Cette fonctionnalité est similaire à l'Assistants API d'OpenAI et aux GPT de ChatGPT, mais avec une prise en charge de modèles plus large et une implémentation sans code, vous permettant de créer des assistants sophistiqués dotés de capacités spécialisées.

## Démarrage [#getting-started]

Pour créer un nouvel agent, sélectionnez "Agents" dans le menu endpoint et ouvrez le panneau Agent Builder situé dans le Side Panel.

![Agents - Menu des endpoints](/images/agents/endpoints_menu.png)

Le formulaire de création comprend :

- **Avatar** : Téléchargez un avatar personnalisé pour personnaliser votre agent
- **Nom** : Choisissez un nom distinctif pour votre agent
- **Description** : Détails optionnels sur l'objectif de votre agent
- **Instructions** : Instructions système qui définissent le comportement de votre agent
- **Modèle** : Sélectionnez parmi les fournisseurs et modèles disponibles
- **Conversation Starters** : Jusqu'à quatre suggestions de prompts affichées lorsqu'un utilisateur démarre une nouvelle conversation avec l'agent

Les contrôles **Tools** et **Skills** ouvrent des bibliothèques consultables pour les fonctionnalités intégrées, les outils, les serveurs MCP, les Actions et les Skills. Sélectionnez un élément pour le configurer, puis enregistrez l'agent.

**Les agents existants peuvent être sélectionnés depuis le menu déroulant en haut du panneau latéral.**

- **Également par mention avec "@" dans la zone de saisie du chat.**

![Agents - Mention](/images/agents/mention.png)

### Bibliothèque d'outils [#tool-library]

Le générateur d'agents conserve les éléments activés dans des sections **Outils** et **Compétences** distinctes. Ouvrez **Ajouter des outils** pour parcourir le catalogue complet ou le filtrer par **Officiel**, **Outils**, **MCP** ou **Actions**. **Créé par vous** rassemble les serveurs MCP et les Actions que vous avez créés, tandis que **Favoris** permet de garder les éléments marqués d'une étoile accessibles sur tous les agents. Chaque utilisateur peut enregistrer jusqu'à 100 favoris dans la bibliothèque d'outils.

Sélectionnez un élément pour le configurer sans quitter le constructeur. Le menu **Create new** n'apparaît que lorsque l'utilisateur a la permission de créer des serveurs MCP ou des Actions. La suppression d'une fonctionnalité basée sur des fichiers telle que File Search, File Context ou Code Interpreter ouvre son gestionnaire de fichiers lorsque des fichiers joints doivent encore être examinés. Une fonctionnalité basée sur des fichiers reste sélectionnée et est préservée lors de l'enregistrement tant qu'elle possède encore des fichiers ; supprimez ou réattribuez ces fichiers avant de supprimer la fonctionnalité elle-même.

Les Skills utilisent leur propre sélecteur et peuvent être sélectionnés individuellement ou activés en tant que catalogue complet accessible. Voir [Skills](/docs/features/skills#agent-scope).

Les opérateurs peuvent également utiliser des [Agent Plugins](/docs/features/agent_plugins) expérimentaux pour regrouper les Skills de déploiement et les serveurs MCP dans des packages chargés au démarrage.

### Configuration du modèle [#model-configuration]

L'interface des paramètres du modèle permet d'affiner les réponses de votre agent :

- Température (échelle de 0 à 1 pour la créativité des réponses)
- Nombre maximal de jetons de contexte
- Nombre maximal de jetons de sortie
- Détail de l'image (`low`, `auto`, ou `high`) pour les entrées d'image vision natives
- Paramètres supplémentaires spécifiques au fournisseur

Les instructions des agents peuvent utiliser `{{current_date}}`, `{{current_datetime}}` et `{{iso_datetime}}`. LibreChat les résout à partir du début du tour logique capturé par le serveur et maintient cet horodatage stable à travers les boucles des fournisseurs, l'initialisation des sous-agents et la reprise par l'humain dans la boucle (human-in-the-loop). Les deux premiers utilisent le fuseau horaire de la requête ; `{{iso_datetime}}` reste en UTC.

Les échecs de type « model-not-found » et les limites de débit (« rate-limit ») des fournisseurs reconnus affichent des conseils localisés. Les autres erreurs des fournisseurs conservent leur texte utile, mais omettent les URL de dépannage de LangChain avant que le message ne soit persisté. Lorsque la [protection de contenu liée au modèle](/docs/configuration/librechat_yaml/object_structure/message_filter#source-aware-filters) est activée, son erreur générique de protection reste prioritaire.

### Historique des versions [#version-history]

Les utilisateurs disposant d'un accès en modification peuvent ouvrir l'**Historique des versions** depuis le Constructeur d'agents pour inspecter les configurations enregistrées dans une chronologie. Chaque entrée indique quand elle a été enregistrée et résume ses outils et capacités. La restauration d'une entrée antérieure nécessite une confirmation et remplace la configuration actuelle de l'agent par cet état enregistré. L'enregistrement applique toujours les modifications actuelles de l'agent, même lorsque la configuration résultante correspond à la dernière entrée de l'historique et que LibreChat n'ajoute pas d'entrée en double.

### Conversation Starters [#conversation-starters]

Les « conversation starters » offrent aux utilisateurs un moyen rapide de commencer une discussion avec un agent. Chaque agent peut en stocker jusqu'à quatre.

1. Dans le Agent Builder, trouvez le champ **Conversation Starters**.
2. Saisissez une invite et appuyez sur **Entrée**, ou sélectionnez le bouton **+**. La saisie est désactivée une fois que quatre éléments de démarrage ont été ajoutés.
3. Modifiez un starter enregistré directement, ou sélectionnez son bouton **X** pour le supprimer.
4. Enregistrer l'agent.

Lorsqu'un utilisateur ouvre une nouvelle discussion avec l'agent, les starters apparaissent sous forme de boutons sur l'écran de discussion vide. En sélectionner un l'envoie immédiatement comme premier message. Si l'agent possède des starters, ils prévalent sur tout [`conversation_starters`](/docs/configuration/librechat_yaml/object_structure/model_specs#conversation_starters) défini dans le Model Specs utilisé. Les starters apparaissent également dans la boîte de dialogue de détails du [Marketplace](#agent-marketplace) de l'agent.

## Capacités des agents [#agent-capabilities]

> **Remarque :** Toutes les fonctionnalités peuvent être activées ou désactivées via le fichier de configuration `librechat.yaml`. Consultez [docs/configuration/librechat_yaml/object_structure/agents#capabilities](/docs/configuration/librechat_yaml/object_structure/agents#capabilities) pour plus d'informations.

### Code Interpreter [#code-interpreter]

Lorsqu'elle est activée, la fonctionnalité Code Interpreter permet à votre agent de :

- Exécutez du code dans plusieurs langages, notamment :
  - Python, JavaScript, TypeScript, Go, C, C++, Java, PHP, Rust et Fortran
- Traitez les fichiers de manière sécurisée via l'API Code Interpreter de LibreChat
- Exécutez du code sans configuration locale, paramétrage ou déploiement de sandbox
- Gérez les téléchargements et les envois de fichiers en toute transparence
- [Plus d'informations sur l'API Code Interpreter](/docs/features/code_interpreter)
  - **Propulsé par le service open-source [code-interpreter](https://github.com/ClickHouse/code-interpreter) (auto-hébergé)**

Lorsque tous les fichiers requis pour l'interpréteur de code d'une conversation ne parviennent pas à être restaurés dans le sandbox actuel, LibreChat arrête l'Agent avant d'invoquer le modèle et demande à l'utilisateur de joindre à nouveau les fichiers. Cela empêche l'exécution de se poursuivre avec des références de fichiers obsolètes ou inaccessibles.

Lorsque des fichiers de conversation partagent un nom de fichier pour le Code Interpreter, LibreChat leur assigne des destinations sandbox distinctes et indique à l'Agent les chemins résolus. Consultez [Seamless File Handling](/docs/features/code_interpreter#seamless-file-handling) pour en savoir plus sur le comportement en cas de collision et sur la limitation restante concernant les fichiers privés multi-Agent.

#### Sessions de code avec état [#stateful-code-sessions]

Les sessions de code avec état (stateful) permettent à un agent de réutiliser un espace de travail sandbox entre les exécutions de code. Les fichiers, les paquets installés et l'état de travail sont généralement conservés, ce qui est utile pour l'analyse itérative et le travail sur des fichiers en plusieurs étapes. Dans le générateur d'agents (Agent Builder), le sélecteur **Stateful environment** contrôle qui partage cet espace de travail :

- **Espace de travail utilisateur (recommandé) :** les agents avec état de l'utilisateur connecté partagent un seul espace de travail
- **Espace de travail agent + utilisateur :** chaque utilisateur dispose d'un espace de travail distinct pour chaque agent
- **Espace de travail de conversation :** chaque utilisateur dispose d'un espace de travail distinct pour chaque conversation

Les administrateurs peuvent également configurer des backends nommés sous [`statefulCodeSessions.environments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions). Lorsqu'ils sont présents, le sélecteur **Execution environment** distinct choisit l'API de code gérée, la machine virtuelle attachée à l'opérateur ou le worker personnel qui possède l'espace de travail ; **Deployment default** utilise l'environnement exécutable par défaut configuré. La portée de partage ci-dessus reste indépendante de ce choix de backend.

Lorsqu'un déploiement active les workers en libre-service, les utilisateurs disposant de l'autorisation de gestion des Code Environments peuvent ouvrir **Settings > Code environments** pour coupler un worker sortant `@librechat/code` sur leur propre VM, le sélectionner dans l'Agent Builder, et le révoquer ultérieurement. Les environnements personnels sont liés au propriétaire et utilisent la même route pour le code, le shell et le Programmatic Tool Calling. Voir [Attached environments and pairing](/docs/features/code_interpreter#attached-environments-and-pairing) pour la configuration expérimentale et le modèle de sécurité.

Au sein d'un espace de travail attaché, les Agents peuvent lister des répertoires, lire des fichiers, rechercher du texte, créer des fichiers et exécuter Bash via le worker sélectionné. Un nom et une adresse e-mail Git par Agent permettent d'identifier les commits effectués sans avoir à fournir d'identifiants de dépôt. Les déploiements peuvent limiter les nouveaux workers personnels avec [`statefulCodeSessions.principalWorkers`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions).

Lorsqu'un worker attaché annonce plusieurs racines d'espace de travail, le compositeur de chat nécessite une sélection pour chaque environnement attaché utilisé par l'Agent ou ses sous-agents. La conversation conserve ces sélections au fil des tours et de la reprise après approbation ; LibreChat les valide auprès du worker en direct et bloque l'envoi si un espace de travail requis est manquant ou indisponible. Un worker qui annonce exactement un espace de travail est sélectionné automatiquement pour une nouvelle conversation. Voir [Attached environments and pairing](/docs/features/code_interpreter#attached-environments-and-pairing) pour plus de détails et les limitations actuelles.

Les nouveaux Agents utilisent initialement l'**Espace de travail avec état par défaut** de l'utilisateur connecté, défini dans **Paramètres > Contrôle des données > Exécution de code**. La valeur par défaut personnelle est **Espace de travail utilisateur** jusqu'à ce qu'elle soit modifiée. La mise à jour de cette préférence ne modifie pas les Agents existants et n'active pas les Sessions de code avec état par elle-même. Les administrateurs peuvent restreindre les portées disponibles avec [`statefulCodeSessions.allowedEnvironments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions) ; lorsqu'une valeur par défaut personnelle enregistrée n'est plus autorisée, les nouveaux Agents utilisent la première portée autorisée.

<Callout type="warning" title="Hautement expérimental">
  Les Stateful Code Sessions sont dans une phase d'expérimentation précoce. Leur comportement, leur configuration, leurs caractéristiques de persistance et leur intégration sous-jacente peuvent changer de manière substantielle. Ne considérez pas l'implémentation actuelle comme un contrat de production stable.
</Callout>

Cette fonctionnalité est optionnelle (opt-in). Un administrateur doit ajouter `stateful_code_sessions` aux [capacités des agents](/docs/configuration/librechat_yaml/object_structure/agents#capabilities) et configurer une route dédiée pour l'interprète de code avec état via [`LIBRECHAT_CODE_BASEURL_STATEFUL`](/docs/configuration/dotenv#stateful-code-interpreter-endpoint) ou nommée [`statefulCodeSessions.environments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions). L'interprète de code doit être activé sur l'agent, et les **Sessions de code avec état** (Stateful code sessions) doivent être activées dans ses paramètres avancés.

Les requêtes avec état (stateful) ne reviennent pas à l'endpoint normal sans état (stateless) de Code Interpreter lorsque l'URL dédiée est manquante ou incompatible. Les sessions avec état et sans état ne partagent pas non plus les fichiers en direct ou les paquets installés. L'espace de travail avec état peut être réinitialisé à tout moment, quelle que soit sa portée. Dans les environnements gérés de Code Interpreter, enregistrez les sorties importantes sous `/mnt/data` ; un espace de travail attaché est un répertoire distinct appartenant au worker. Les téléchargements de chat ne sont pas copiés dans ce répertoire attaché par défaut. Ne vous fiez pas autrement à l'état de la session comme stockage durable.

Lorsque les outils `create_file` ou `edit_file` avec état créent des fichiers pendant une réponse, le message de l'assistant affiche une ligne compacte **Workspace changes**. Développez-la pour examiner les chemins modifiés uniques et télécharger chaque fichier via le flux de fichiers authentifié de LibreChat. Il s'agit d'un enregistrement par message des fichiers créés par ces outils, et non d'un instantané durable de l'espace de travail complet ; les sorties de l'interpréteur de code sans état continuent d'utiliser l'interface de pièces jointes intégrée habituelle.

Pour les environnements attachés, le compositeur peut exposer **Ask before changes**, **Accept edits** et **Full access** en tant que mode d'approbation de code au niveau de la conversation. La disponibilité est limitée par le schéma d'autorisation défini par l'administrateur de l'environnement ; le choix d'un mode plus permissif ne remplace jamais les attributions de rôles, les règles d'outils explicites, les hooks ou les limites du sandbox. Voir [Attached-environment tool permissions](/docs/features/code_interpreter#attached-environment-tool-permissions).

### Recherche de fichiers [#file-search]

La fonctionnalité File Search permet :

- Fonctionnalité RAG (Retrieval-Augmented Generation)
- Recherche sémantique dans les documents téléchargés
- Réponses contextuelles basées sur le contenu des fichiers
- Prise en charge des pièces jointes au niveau de l'agent et du fil de discussion

### Contexte de fichier [#file-context]

La fonctionnalité File Context permet à votre agent de stocker le texte extrait de fichiers en tant que partie de ses instructions système :

- Extraire le texte tout en conservant la structure et la mise en forme du document
- Traiter des mises en page complexes, y compris du texte en colonnes multiples et du contenu mixte
- Gérer les tableaux, les équations et autres contenus spécialisés
- Travailler avec du contenu multilingue
- Le texte est stocké dans les instructions de l'agent dans la base de données
- **Aucun service OCR requis** - Utilise l'analyse de texte par défaut avec des méthodes de secours
- **Amélioré par OCR** - Si l'OCR est configuré, la qualité d'extraction s'améliore pour les images et les documents numérisés
- Utilise la même logique de traitement que « Télécharger en tant que texte » : **OCR > STT > analyse de texte**
- [Plus d'informations sur la configuration de l'OCR](/docs/features/ocr)

**Note :** Le contexte de fichier inclut le texte extrait dans les instructions système de l'agent. Pour des questions sur des documents temporaires dans des conversations individuelles, utilisez [Upload as Text](/docs/features/upload_as_text) depuis le chat.

### Model Context Protocol (MCP) [#model-context-protocol-mcp]

MCP est un protocole ouvert qui standardise la manière dont les applications fournissent du contexte aux Large Language Models (LLMs), agissant comme un adaptateur universel pour les outils d'IA et les sources de données.

Pour plus d'informations, consultez la documentation sur [MCP](/docs/features/mcp).

#### Agents avec des outils MCP [#agents-with-mcp-tools]

1. Configurez les serveurs MCP dans votre fichier `librechat.yaml`
2. Redémarrez LibreChat pour initialiser les connexions
3. Créer ou modifier un agent
4. Ouvrez **Add tools** dans le Agent Builder et sélectionnez **MCP**
5. Sélectionnez le(s) serveur(s) MCP que vous souhaitez ajouter ; chaque serveur apparaît comme une entrée unique
6. Enregistrez vos modifications apportées à l'agent

Dans cet exemple, nous avons ajouté le **[serveur MCP Spotify](https://github.com/LibreChat-AI/spotify-mcp)** à un agent.

![Agents - MCP](/images/agents/mcp_tools_v2.png)

#### Gestion des outils MCP [#managing-mcp-tools]

Une fois qu'un serveur MCP est ajouté à un agent, vous pouvez affiner les outils spécifiques qui sont disponibles :

- Après avoir ajouté un serveur MCP, développez-le pour voir tous les outils disponibles
- Cochez/décochez les outils individuels selon vos besoins
- Par exemple, le serveur MCP Spotify fournit environ 20 outils (recherche, contrôle de lecture, gestion de playlist, etc.)
- Ce contrôle granulaire vous permet de limiter les agents aux seuls outils dont ils ont besoin

Les serveurs à portée de requête qui utilisent `{{LIBRECHAT_BODY_*}}` ne peuvent pas énumérer les outils tant qu'une exécution de chat ne fournit pas ces valeurs. L'Agent Builder affiche donc une sélection d'outils d'exécution pour l'ensemble du serveur au lieu de bascules par outil ; effacer cette sélection détache le serveur. Après l'OAuth, LibreChat conserve l'autorisation et attend la première exécution éligible pour se connecter.

Si un Agent sélectionne explicitement des outils MCP mais qu'aucun ne peut être résolu au démarrage d'une exécution, LibreChat arrête l'exécution avec des conseils de connexion et d'accès au lieu de continuer silencieusement sans eux. Reconnectez ou authentifiez le serveur, vérifiez l'accès aux outils et réessayez l'exécution.

![Agents - Outils MCP](/images/agents/mcp_agent_tools.png)

En savoir plus :

- [Configuration des serveurs MCP](/docs/features/mcp)
- [Introduction au Model Context Protocol](https://modelcontextprotocol.io/introduction)

### Outils différés [#deferred-tools]

Les outils différés permettent aux agents d'accéder à de nombreux outils MCP sans avoir à tous les charger dans le contexte du LLM au préalable. Au lieu de cela, les outils différés sont détectables au moment de l'exécution via un mécanisme de **Recherche d'outils** (Tool Search).

Ceci est particulièrement utile lorsqu'un agent a accès à de nombreux serveurs MCP dotés de dizaines d'outils ; les charger tous consommerait une grande partie de la fenêtre de contexte et dégraderait la qualité des réponses.

**Comment ça fonctionne :**

- Les outils marqués comme « deferred » sont exclus du contexte initial du LLM.
- Un outil `ToolSearch` est automatiquement ajouté, permettant au LLM de découvrir et de charger des outils différés à la demande.
- Une fois découvert, l'outil est disponible pour le reste de la conversation

**Configuration des outils différés :**

1. Ouvrez le Agent Builder et ajoutez des outils MCP
2. Cliquez sur le menu déroulant de n'importe quel outil MCP
3. Activer « Defer Loading » — les outils différés affichent une icône d'horloge

**Remarque :** La fonctionnalité `deferred_tools` est activée par défaut. Elle peut être activée ou désactivée via la configuration des agents dans [`librechat.yaml`](/docs/configuration/librechat_yaml/object_structure/agents#capabilities).

### Groupes d'activité [#activity-groups]

Les groupes d'activité réduisent chaque bloc contigu de raisonnement d'Agent et d'appels d'outils sous un en-tête généré sur une seule ligne, facilitant ainsi la lecture des longues exécutions. Les administrateurs peuvent les activer avec `activityLabel` et utiliser un modèle plus rapide, un autre endpoint configuré, un prompt personnalisé et des limites par exécution. La génération de l'en-tête est un appel de modèle distinct dont les jetons et le coût sont enregistrés. Voir [Agent Activity Groups](/docs/configuration/librechat_yaml/object_structure/shared_endpoint_settings#agent-activity-groups).

Les administrateurs peuvent activer indépendamment `activityPhaseLabel` pour regrouper deux activités logiques ou plus dans un résumé parent réduit avant la réponse finale. Cela donne aux exécutions longues un aperçu de haut niveau tout en préservant chaque activité enfant. Les résumés de phase utilisent leur propre modèle, endpoint, prompt et limite par exécution, avec une solution de repli vers les paramètres de l'activity-label et de l'exécution.

Dès qu'une exécution contiguë contient au moins deux groupes d'outils étiquetés terminés, LibreChat les replie dans la même surface de carte de phase, même avant l'arrivée d'un résumé de phase optionnel. L'étiquette enfant terminée la plus récente sert d'en-tête provisoire, tandis que le raisonnement en direct et l'appel d'outil toujours en cours restent en dehors du repli. L'historique chargé utilise le même regroupement, et un résumé de phase généré ultérieurement par le serveur remplace l'en-tête provisoire sans fermer une carte ouverte par le lecteur.

Lorsque [Smooth Streaming](/docs/features/smooth_streaming) est activé, un résumé parent nouvellement généré replie en douceur les activités visibles dans le groupe réduit. L'historique chargé ne rejoue pas cette transition, et LibreChat respecte la préférence de réduction des mouvements de l'appareil.

Le texte de progression court reste à l'intérieur de sa phase parente. Lorsque l'Agent commence une réponse substantielle, LibreChat ferme la phase avant ce texte afin que le résultat destiné à l'utilisateur reste en dehors du résumé réduit. Une exécution peut créer plusieurs phases parentes lorsque le raisonnement ultérieur ou les outils entament un autre bloc d'activité logique. Les limites de phase persistées sont réinitialisées lorsque des parties de contenu mal formées ou omises sont compactées, de sorte que le regroupement reste aligné après le rechargement.

Les fichiers produits au cours d'une phase restent visibles dans une ligne multimédia sous la carte réduite au lieu d'être masqués à l'intérieur. Les références d'image Markdown utilisant un nom de fichier brut, `/mnt/data/...` ou un chemin `sandbox:` se résolvent en pièces jointes correspondantes. Un fichier n'est omis de la ligne multimédia que lorsqu'une image en ligne située en dehors de la phase réduite se résout correctement, évitant ainsi les doublons sans se fier à des références corrompues.

Les cartes d'outils Generic Agent et MCP distinguent la phase de **Préparation** (avant le transfert au SDK, qui peut inclure une approbation ou une autre attente) de la phase d'**Appel** (transfert au SDK jusqu'au résultat). Les cartes terminées affichent les deux intervalles ; l'intervalle d'appel ne correspond pas nécessairement à la durée d'exécution du MCP en amont ou de ClickHouse. Les messages enregistrés précédemment ainsi que les cartes spécialisées Code, Bash, fichier et mémoire conservent une durée d'exécution de l'étape clairement étiquetée **Temps total écoulé**. Les étapes arrêtées, annulées, échouées et terminées conservent des statuts distincts, y compris après le rechargement d'une conversation.

Pendant l'exécution d'un outil, les volets de détails développés pour Bash, Execute Code et File Authoring suivent les commandes, le code ou le contenu de prévisualisation diffusés en continu vers le bas. Faire défiler vers le haut suspend ce comportement de suivi afin que la position de lecture actuelle soit préservée.

La sortie Bash est rendue sous forme de texte de style terminal. Les sorties longues sont réduites à leurs 15 dernières lignes, là où les erreurs apparaissent généralement ; utilisez **Show more** et **Show less** pour les développer ou les réduire, et le bouton **Copy** pour copier la sortie. Une commande qui n'a rien affiché indique **No output**. Pour les commandes exécutées dans un [espace de travail attaché](/docs/features/code_interpreter#attached-environments-and-pairing), une commande ayant échoué est marquée avec sa raison (**exit code N**, **terminated by** un signal tel que `SIGKILL`, ou **timed out**), et stderr est stylisé séparément de stdout. Une commande terminée est étiquetée **Ran command**, et un groupe d'outils contenant un appel unique s'ouvre directement sur les détails de cet appel.

### Étiquettes de raisonnement en direct [#live-reasoning-labels]

Les étiquettes de raisonnement en direct remplacent un en-tête générique **Thinking** ou **Thoughts** par une courte orientation qui évolue au fur et à mesure que les flux de raisonnement de haut niveau deviennent suffisamment longs. L'étiquette met à jour l'en-tête de raisonnement existant sur place ; elle n'ajoute ni ne réorganise les parties du message.

L'étiquette de raisonnement en direct la plus récente et le minuteur de réponse scintillent pendant que la génération est active. Le raisonnement stabilisé, les réponses des frères et sœurs plus anciens et les étiquettes qui ne sont plus à la fin du flux en direct restent statiques.

Les administrateurs activent cette fonctionnalité avec `reasoningLabel` et peuvent choisir un modèle, un endpoint, un prompt, des seuils de mise à jour et une limite d'appels par exécution distincts. Chaque révision constitue un appel de modèle supplémentaire dont les jetons et le coût sont enregistrés. Consultez [Live Reasoning Labels](/docs/configuration/librechat_yaml/object_structure/shared_endpoint_settings#live-reasoning-labels) pour les valeurs par défaut, la priorité de routage et les considérations relatives à la confidentialité.

### Étiquettes d'intention des outils [#tool-intent-labels]

Les étiquettes d'intention d'outil remplacent les statuts d'outils en direct génériques par une courte description rédigée par le modèle pour cet appel spécifique. Les administrateurs doivent ajouter la fonctionnalité d'agent `tool_intents` [agent capability](/docs/configuration/librechat_yaml/object_structure/agents#capabilities) pour l'activer. Les outils natifs utilisent automatiquement les étiquettes ; dans le constructeur d'agent (Agent Builder), développez un serveur MCP et activez **Intent label** pour des outils individuels ou pour l'ensemble du serveur.

Pour les Model Specs, [`describeIntent`](/docs/configuration/librechat_yaml/object_structure/model_specs#describeintent) peut activer chaque outil éligible ou sélectionner des IDs d'outils résolus. Les champs d'intention s'ajoutent au schéma d'outil envoyé au modèle, donc une activation sélective peut réduire la surcharge de jetons du schéma.

Les étiquettes d'intention (intent labels) ne s'appliquent pas aux outils MCP purement programmatiques, car les appels effectués au sein du code sandbox n'affichent pas de cartes d'outils individuelles. Une exécution programmatique étendue affiche plutôt une trace en direct compacte de ses appels internes.

### Appel d'outils programmatique [#programmatic-tool-calling]

Programmatic Tool Calling (PTC) permet aux agents d'exécuter des outils MCP sélectionnés depuis l'intérieur du bac à sable [Code Interpreter](/docs/features/code_interpreter) au lieu d'appeler chaque outil directement depuis le modèle. Le modèle reçoit un outil d'orchestration basé sur Code Interpreter, écrit du code en bac à sable qui appelle les fonctions d'outils générées, et peut utiliser des boucles, des conditions, des tentatives et le traitement des résultats avant de renvoyer une réponse.

Ceci est utile pour les flux de travail d'outils en plusieurs étapes, tels que l'interrogation de plusieurs ressources, la pagination des résultats, la comparaison des sorties ou la transformation des réponses des outils avant que l'agent ne les explique.

**Configuration des outils programmatiques :**

1. Activez à la fois `programmatic_tools` et `execute_code` dans les [`librechat.yaml` agents capabilities](/docs/configuration/librechat_yaml/object_structure/agents#capabilities).
2. Activez l'interpréteur de code sur l'agent.
3. Ajoutez des outils MCP, étendez un serveur MCP et activez **Programmatic** pour des outils individuels ou pour le serveur complet. Les outils Programmatic affichent une icône de code.

Le générateur d'agents (Agent Builder) maintient les options programmatiques désactivées tant que Code Interpreter n'est pas sélectionné. La suppression de Code Interpreter efface immédiatement les sélections programmatiques de l'agent. Lors de la création, de la mise à jour, de la duplication et de la restauration de version, le serveur supprime également les options d'appel programmatique lorsque la capacité `execute_code` ou l'outil Code Interpreter n'est pas disponible ; cela permet aux anciens agents incohérents d'être ouverts et corrigés sans conserver une configuration inutilisable.

**Note :** `programmatic_tools` est une option et n'est pas inclus dans la liste des capacités par défaut des agents. PTC nécessite également un déploiement de Code Interpreter avec le composant Tool Call Server. Au moment de l'exécution, LibreChat croise la projection actuelle des capacités de l'appelant avec son registre d'outils approuvés, de sorte que les données d'événement peuvent restreindre la carte disponible mais ne peuvent pas accorder un outil. Seuls les outils programmatiques actifs et enregistrés peuvent être appelés depuis le sandbox ; les appels non enregistrés sont rejetés.

Développez la carte Code Interpreter lors d'une exécution programmatique pour voir une trace de style terminal de chaque appel d'outil interne, son aperçu des arguments, son statut, sa durée et toute défaillance. La trace est en direct pour la session de navigateur actuelle et n'est pas restaurée après un rechargement de page.

### Appels d'outils en arrière-plan [#background-tool-calls]

Les appels d'outils en arrière-plan permettent à un agent de démarrer un outil Code Interpreter, MCP, Plugin ou Action éligible et de longue durée, tout en continuant à travailler. L'appel initial renvoie immédiatement une référence de tâche. Pour un Agent enregistré, les complétions prises en charge sont transmises automatiquement dans une continuation de suivi par défaut ; `check_background_task` reste disponible pour le statut explicite, le contrôle, la collecte d'artefacts et la récupération.

`check_background_task` rapporte `started_at` et le `elapsed_ms` actuel pendant l'exécution d'un travail local au processus. Après la finalisation, il rapporte également `settled_at` et fige `elapsed_ms` à la durée totale. Un résultat terminal récupéré depuis un stockage durable peut inclure `settled_at` sans heure de début ni durée écoulée lorsque l'horodatage de répartition local au processus d'origine n'est pas disponible.

Pour utiliser cette fonctionnalité, un administrateur doit ajouter la capacité d'agent `run_in_background` [agent capability](/docs/configuration/librechat_yaml/object_structure/agents#capabilities) avec consentement. Configurez ensuite les outils éligibles dans le générateur d'agents (Agent Builder) :

- **Code Interpreter :** Activez Code Interpreter sur l'agent. L'exécution de code et les commandes shell deviennent éligibles à l'exécution en arrière-plan par défaut ; désactivez **Background execution** dans ses paramètres d'outil pour refuser cette option.
- **MCP :** Ouvrez un serveur MCP et marquez des outils individuels, ou le serveur complet, comme **Background**.
- **Outils de plugin :** Ouvrez un outil éligible et activez **Background execution**.
- **Actions :** Activez l'**exécution en arrière-plan** pour une Action afin d'inclure toutes les opérations éligibles de cette Action. Les Actions OAuth n'exposent pas ce commutateur. Une opération est également exclue lorsque son propre schéma définit déjà un paramètre `run_in_background`, évitant ainsi un conflit avec l'indicateur de répartition de LibreChat.

Ces paramètres permettent l'exécution en arrière-plan mais ne l'imposent pas. Le modèle décide pour chaque appel s'il doit exécuter un outil éligible en arrière-plan.

Dans le chat LibreChat, lorsque le code en arrière-plan se termine, sa sortie standard (stdout) et les fichiers générés apparaissent sur l'appel de code original plutôt que lors du sondage ultérieur. Les fichiers générés sont également conservés pour les tours suivants. Les continuations automatiques présentent le travail terminé dans une carte de tâche de réveil pliable liée à la tâche originale.

Lorsque le serveur démarre cette continuation après que l'exécution en premier plan précédente soit terminée, la conversation ouverte se rattache à la nouvelle génération et actualise la sortie de la tâche terminée sans nécessiter de rechargement.

Les réveils de complétion automatique sont activés à moins qu'un administrateur ne définisse [`endpoints.agents.backgroundTasks.completionWakeups: false`](/docs/configuration/librechat_yaml/object_structure/agents#backgroundtasks), ce qui rétablit le comportement basé uniquement sur l'interrogation (poll-only). L'hôte peut regrouper plusieurs complétions de contenu éligibles en une seule continuation. Les tâches qui produisent un artefact en direct nécessitent toujours une interrogation sur le processus qui détient l'exécution.

Les administrateurs peuvent également opter pour l'annulation à portée du propriétaire avec [`endpoints.agents.backgroundTasks.ordinaryToolCancellation: true`](/docs/configuration/librechat_yaml/object_structure/agents#backgroundtasks). La tâche signale qu'une annulation a été demandée jusqu'à ce que l'invocation sous-jacente soit terminée, et sa capacité reste réservée pendant cet intervalle. L'annulation est coopérative : un outil qui ignore le signal d'abandon peut tout de même se terminer avec succès. Ce contrôle s'applique aux outils d'arrière-plan ordinaires locaux au processus, y compris Bash attaché, mais pas aux sous-agents détachés possédés indépendamment.

Seuls les outils éligibles exposent ce paramètre. L'exécution ordinaire en arrière-plan est locale au processus et ne survit pas à la perte de son processus de travail. Cependant, une fois qu'un résultat de terminal contenant uniquement du contenu est persisté, la livraison automatique est durable et peut se poursuivre sur une autre réplique. Le registre local au processus limite les tâches en cours d'exécution et les charges utiles de résultats conservées par conversation, utilisateur et processus ; il évince le travail terminé lorsque cela est sûr et renvoie un résultat de capacité limitée lorsque le traitement en attente empêche une éviction sûre. Si une invocation ignore l'annulation, LibreChat cesse de renouveler son bail de producteur après une période de grâce d'une minute suivant l'abandon et retire la livraison automatique de l'achèvement sans marquer à tort le travail externe incertain comme ayant expiré. Les sous-agents détachés (Detached Subagents) utilisent un chemin de tâche et de transcription durable distinct avec des contrôles en direct routés par Redis ; voir [Detached Subagent Threads](/docs/features/subagents#detached-subagent-threads).

### Demander l'approbation de l'utilisateur et de l'outil [#ask-user-and-tool-approval]

L'outil **Ask User** permet à un agent de suspendre une exécution pour demander des informations manquantes, présenter des choix ou confirmer la marche à suivre. Un seul appel peut regrouper jusqu'à quatre questions connexes. LibreChat présente une question à la fois avec des boutons Précédent, Suivant et des étapes de progression cliquables ; les réponses restent disponibles lors de la navigation entre les étapes, et les réponses à sélection unique permettent de passer automatiquement à l'étape suivante sans soumission manuelle. Le bouton Soumettre apparaît à la dernière étape une fois que chaque question a reçu une réponse, tandis que Ignorer permet de refuser l'ensemble du lot depuis n'importe quelle étape. Chaque question accepte une réponse libre ou les choix à sélection unique ou multiple définis par l'agent. Pendant que le modèle prépare l'appel, LibreChat diffuse les questions dans une carte de progression ; le formulaire interactif la remplace lorsqu'il est prêt. Après une soumission, la même exécution reprend avec la carte complète des réponses. Ajoutez **Ask User** depuis la place de marché des Tools ; les administrateurs peuvent supprimer la capacité par défaut `ask_user_question` pour la masquer.

Réduire une carte à questions multiples ramène le compositeur à son mode normal de pilotage ou de file d'attente, tandis que la carte en pause demeure dans le fil de discussion. La carte peut toujours être développée, recevoir une réponse, être ignorée ou arrêtée. Une pause sur une question unique continue d'utiliser le mode de réponse du compositeur focalisé.

Les réponses soumises sont conservées avec l'action resume, donc arrêter pendant l'initialisation de l'exécution reprise ne supprime pas les réponses acceptées.

Une fois qu'un enregistrement de question est stabilisé, il se réduit par défaut en une entrée d'outil sur une seule ligne afin que les réponses longues ne dominent pas la transcription. Ouvrez-le pour examiner les questions et les sauts de ligne préservés dans les réponses. La préférence existante **Auto-expand tool details** contrôle également cette vue stabilisée ; le formulaire en direct reste ouvert tant qu'une saisie est encore requise.

Chaque question accepte un titre optionnel allant jusqu'à 80 caractères, un texte de question allant jusqu'à 2 000 caractères, un contexte de support optionnel allant jusqu'à 4 000 caractères, et jusqu'à 12 choix. Les étiquettes de choix sont limitées à 280 caractères, les valeurs de choix à 500 caractères, et chaque réponse soumise à 16 000 caractères.

Les administrateurs peuvent également exiger une révision avant l'exécution des appels d'outils correspondants. Selon l'outil, les utilisateurs peuvent approuver, rejeter, modifier les arguments ou répondre directement. Les exécutions en pause sont placées dans des points de contrôle afin de pouvoir reprendre après la décision, y compris sur une autre réplique lorsque le checkpointer MongoDB par défaut est utilisé. L'approbation des outils à l'échelle du déploiement est désactivée par défaut, tandis qu'un Agent utilisant un environnement de Code attaché reçoit la [politique de sécurité ask-by-default](/docs/features/code_interpreter#attached-environment-tool-permissions) à moins qu'un administrateur ne la désactive explicitement. Voir [`toolApproval` et `checkpointer`](/docs/configuration/librechat_yaml/object_structure/agents#toolapproval).

Pendant que le panneau de révision du compositeur est ouvert pour une approbation en attente, la carte de fil de discussion correspondante affiche la demande sous forme d'enregistrement plutôt que de dupliquer les boutons de décision. Examinez les appels dans le panneau au-dessus de la zone de message et sélectionnez **Continue**. La réduction du panneau à partir du chip du compositeur restaure les contrôles de la carte de fil de discussion avec vos décisions conservées ; le rouvrir redonne le contrôle de la révision au panneau. Les cartes pour d'autres actions conservent leurs propres contrôles.

### Compétences [#skills]

Les Skills permettent aux agents de charger des instructions réutilisables à partir de définitions `SKILL.md`. Elles peuvent être sélectionnées manuellement depuis le chat avec `$`, découvertes automatiquement par le modèle via le catalogue de Skills, ou appliquées systématiquement à chaque tour. L'Agent Builder peut également activer la création autonome lors de l'exécution : un agent peut créer une Skill sans recevoir le catalogue existant, ou modifier les Skills sélectionnées lorsque l'utilisateur dispose de l'autorisation correspondante.

Pour plus de détails sur la création, l'invocation et le contrôle d'accès, consultez [Skills](/docs/features/skills).

### Mémoire [#memory]

L'outil **Memory** permet à un agent d'enregistrer, de mettre à jour ou de supprimer des souvenirs structurés de l'utilisateur lorsque celui-ci demande explicitement de se souvenir ou d'oublier quelque chose. Memory doit être configuré pour le déploiement, autorisé par le rôle et les paramètres de personnalisation de l'utilisateur, et activé sur l'agent.

Par défaut, un agent utilise le pool de mémoire personnelle partagée de l'utilisateur. Activez **Keep memories separate for this agent** pour lui donner une partition privée par utilisateur et par agent. L'agent isolé ne verra pas les mémoires partagées existantes ni les mémoires créées par d'autres agents isolés. Les utilisateurs peuvent filtrer le panneau Memory par mémoires personnelles ou spécifiques à l'agent. La lecture, la création ou la mise à jour d'une partition d'agent nécessite un accès actuel à cet agent ; la suppression peut toujours nettoyer une partition après que son agent a été retiré. Voir [User Memory](/docs/features/memory#agent-memory).

### Artifacts [#artifacts]

La fonctionnalité Artifacts permet à votre agent de générer et d'afficher du contenu interactif :

- Créer des composants React, du code HTML et des diagrammes Mermaid
- Affichez le contenu dans un panneau dédié à côté du chat, qui peut être agrandi en plein écran ou ouvert dans sa propre fenêtre de navigateur
- Configurez les instructions spécifiques aux artefacts au niveau de l'agent
- [Plus d'informations sur les Artifacts](/docs/features/artifacts)

Lorsqu'il est activé, choisissez l'un des trois modes d'instruction :

- **Normal** : Ajoute les instructions d'artefact standard pour React, HTML, SVG, Markdown et Mermaid.
- **shadcn/ui** : Ajoute les instructions standard ainsi que des conseils pour la création d'interfaces avec la bibliothèque de composants shadcn/ui.
- **Custom** : Maintient le rendu des artefacts activé mais n'injecte aucune instruction d'artefact intégrée, donnant ainsi un contrôle total aux instructions propres à l'agent.

La configuration des artifacts au niveau de l'agent est l'approche privilégiée, car elle permet un contrôle plus granulaire par rapport à la configuration héritée à l'échelle de l'application.

Si vous sélectionnez **Custom**, incluez au minimum le format d'artefact de base dans vos instructions.

Voici un exemple simple des instructions minimales nécessaires :

````md
When creating content that should be displayed as an artifact, use the following format:

:::artifact{identifier="unique-identifier" type="mime-type" title="Artifact Title"}

```
Your artifact content here
```

:::

For the type attribute, use one of:

- "text/html" for HTML content
- "application/vnd.mermaid" for Mermaid diagrams
- "application/vnd.react" for React components
- "image/svg+xml" for SVG images
````

### Transferts [#handoffs]

Les transferts permettent à un agent principal de transférer une conversation à un agent spécialisé avec le contexte pertinent. Dans **Advanced settings**, ouvrez la section orchestration et ajoutez jusqu'à 10 agents de transfert. Chaque transfert configuré crée un outil de transfert que le modèle peut choisir dynamiquement lorsque l'expertise du spécialiste est requise.

Pour chaque transfert, vous pouvez ajouter une description qui aide le modèle à choisir le bon spécialiste. Vous pouvez également fournir des instructions de transmission décrivant quel contenu l'agent principal doit générer pour le spécialiste et, éventuellement, renommer le paramètre de contenu par défaut, `instructions`. Les transferts sont toujours disponibles dans le Agent Builder ; contrairement à Agent Chain et aux sous-agents, ils ne nécessitent pas l'activation d'une capacité d'endpoint. Les appels d'outils provenant d'agents de transfert accessibles restent structurés lors des tours ultérieurs, de sorte que les fournisseurs reçoivent un historique d'appels d'outils valide au lieu d'un texte aplati.

### Chaîne d'agents [#agent-chain]

- Créez des chaînes d'agents spécialisés pour des tâches complexes
- Chaque agent de la chaîne peut accéder aux sorties des agents précédents
- Configurer le nombre maximal d'étapes pour la chaîne de l'agent
- **Remarque :** Accédez à cette fonctionnalité depuis le panneau Advanced Settings dans le Agent Builder
- **Note :** Cette fonctionnalité est actuellement en version bêta et peut être sujette à des changements.
  - Le maximum actuel d'agents pouvant être enchaînés est de 10, mais cela pourrait être configurable à l'avenir.

### Sous-agents [#subagents]

Les Subagents permettent à un agent de déléguer une tâche ciblée à une exécution enfant isolée ou à une équipe d'Agents enregistrée. Chaque enfant bénéficie d'un contexte et d'une exécution d'outils isolés, puis renvoie un résultat compact au parent au lieu de saturer le contexte du parent avec chaque étape intermédiaire. Le travail détaché de l'enfant est également conservé sous forme de fil de discussion navigable en lecture seule.

Les Subagents sont différents de l'Agent Chain : les chaînes d'exécution coordonnent plusieurs agents en tant que participants à un graphe, tandis que les subagents sont générés par un agent en tant qu'appel d'outil pour une délégation ciblée. LibreChat préserve l'historique structuré des appels d'outils nécessaire aux enfants accessibles et aux membres d'équipe enregistrés lors des tours ultérieurs, tout en excluant les outils indisponibles de l'exécution active. Pour la configuration et les limites, consultez [Subagents](/docs/features/subagents).

### Paramètres avancés [#advanced-settings]

Paramètres avancés pour votre agent (situés dans la vue Advanced du formulaire Agent) en dehors des « capabilities ».

#### Étapes maximales de l'agent [#max-agent-steps]

Ce paramètre vous permet de limiter le nombre d'étapes qu'un agent peut effectuer lors d'une « exécution » (run), ce qui fait référence à la boucle de l'agent avant qu'une réponse finale ne soit donnée.

S'il n'est pas configuré, la valeur par défaut est de 25 étapes, mais vous pouvez l'ajuster selon vos besoins. Pour les administrateurs, vous pouvez définir une valeur par défaut globale ainsi qu'un maximum global dans le fichier [`librechat.yaml`](/docs/configuration/librechat_yaml/object_structure/agents#recursionlimit).

Lorsqu'un tour utilise son budget d'étapes complet, LibreChat conserve la réponse partielle et les appels d'outils au lieu de les remplacer par une erreur. Le message propose **Keep going**, qui démarre un nouveau tour avec un budget d'outils actualisé, et **Answer now**, qui demande à l'agent de répondre à partir du travail déjà effectué sans outils supplémentaires. Ignorer la notification n'affecte que la vue actuelle du navigateur.

Les administrateurs peuvent également limiter les arguments d'appels d'outils en streaming et les événements delta du modèle avec les [disjoncteurs de flux d'agent](/docs/configuration/librechat_yaml/object_structure/agents#stream-circuit-breakers).

Une « étape » (step) fait référence soit à une requête d'API d'IA, soit à un cycle d'utilisation d'outils (un ou plusieurs outils, selon le nombre d'appels d'outils fournis par le LLM à partir d'une seule requête).

Une réponse unique sans outil correspond à 1 étape. Un cycle singulier d'utilisation d'outil correspond généralement à 3 étapes :

1. Requête API -> 2. Utilisation d'outils (1 ou plusieurs outils) -> 3. Requête API de suivi

## Gestion des fichiers [#file-management]

Les Agents prennent en charge plusieurs façons de travailler avec des fichiers :

### Dans l'interface de chat [#in-chat-interface]

Lorsque vous discutez avec un agent, vous disposez de quatre options de téléchargement :

1. **Télécharger des images**
   - Téléverse des images pour la prise en charge native des modèles de vision
   - Envoie les images directement au fournisseur de modèle

2. **Télécharger en tant que texte** (nécessite la capacité `context`)
   - Extrait et inclut le contenu complet du document dans la conversation
   - Utilise l'analyse de texte par défaut ; amélioré par l'OCR si configuré
   - Le contenu n'existe que dans la conversation actuelle
   - Voir [Upload as Text](/docs/features/upload_as_text)

3. **Téléchargement pour la recherche de fichiers** (nécessite la fonctionnalité `file_search`, activée)
   - Utilise la recherche sémantique (RAG) avec des magasins de vecteurs
   - Renvoie des segments pertinents via l'utilisation d'outils
   - Optimal pour les documents volumineux/fichiers multiples
   - Sous-optimal pour les données structurées (CSV, Excel, JSON, etc.)

4. **Téléchargement pour Code Interpreter** (nécessite la fonctionnalité `execute_code`, activée)
   - Ajoute des fichiers à l'environnement de l'interpréteur de code
   - Optimal pour les données structurées (CSV, Excel, JSON, etc.)
   - Plus d'informations sur [Code Interpreter](/docs/features/code_interpreter)

### Dans Agent Builder [#in-agent-builder]

Lors de la configuration d'un agent, vous pouvez joindre des fichiers dans différentes catégories :

1. **Téléchargement d'images** : Pour le contenu visuel auquel l'agent peut se référer
2. **Téléchargement pour la recherche de fichiers** : Documents pour les capacités de RAG
3. **Code Interpreter Upload** : Fichiers pour le traitement de code
4. **Contexte du fichier** : Documents avec du texte extrait pour compléter les instructions de l'agent

**File Context** utilise la capacité `context` et fonctionne exactement comme ["Upload as Text"](/docs/features/upload_as_text) - il utilise l'analyse de texte par défaut et est amélioré par l'OCR lorsqu'il est configuré. Le texte est extrait au moment du téléchargement et stocké dans les instructions de l'agent. C'est idéal pour donner aux agents des connaissances persistantes à partir de documents, de PDF, de fichiers de code ou d'images contenant du texte.

**Priorité de traitement :** OCR > STT > analyse de texte (identique à Téléverser en tant que texte)

**Remarque :** Le texte extrait est inclus dans les instructions système de l'agent.

## Partage et autorisations [#sharing-and-permissions]

Les Agents utilisent le système de [contrôle d'accès](/docs/features/access_control) granulaire de LibreChat. Chaque agent possède sa propre liste de contrôle d'accès (ACL) et peut être partagé avec des **utilisateurs**, **groupes**, **rôles** spécifiques, ou **publiquement**, chacun avec un niveau de permission choisi.

Les services de confiance peuvent également gérer les Agents, les fichiers joints et les Skills via l'API bêta [Agent Management API](/docs/features/agents_api#agent-management-api). Les administrateurs lient chaque client machine OIDC à un utilisateur et un tenant LibreChat existants ; chaque requête hérite des capacités de rôle et des ACL de ressources actuelles de cet utilisateur plutôt que de recevoir un accès administratif distinct.

### Rôles d'accès [#access-roles]

Lors du partage d'un agent, le bénéficiaire se voit attribuer l'un des trois rôles suivants :

| Rôle | Ce que le bénéficiaire peut faire |
| ---------- | ----------------------------------------------------------------------------------------------------- |
| **Viewer** | Utiliser l'agent dans les conversations ; ne peut pas ouvrir le constructeur ni voir les instructions, les outils ou les fichiers joints |
| **Editor** | Voir + modifier les instructions, le modèle, les outils et les fichiers de l'agent |
| **Owner** | Contrôle total : voir, modifier, supprimer et repartager l'agent |

L'auteur original et les administrateurs conservent toujours un contrôle total, indépendamment de l'ACL.

### Partage d'un Agent [#sharing-an-agent]

1. Ouvrez l'agent dans le Agent Builder
2. Cliquez sur le bouton **Share** dans le pied de page (visible lorsque vous êtes l'auteur, un administrateur, ou que vous avez reçu la permission `SHARE` sur cet agent spécifique)
3. Recherchez des utilisateurs, des groupes ou des rôles dans le sélecteur de personnes et attribuez un rôle à chacun.
4. Activez éventuellement **Public** pour rendre l'agent visible à tous sur l'instance (nécessite l'autorisation de fonctionnalité `SHARE_PUBLIC`)

Les cartes d'agent et les vues de page d'accueil affichent le contact de support configuré. Lorsqu'aucun n'est défini, LibreChat peut utiliser par défaut le nom d'affichage du premier propriétaire identifiable, mais ne divulgue pas l'adresse e-mail du propriétaire à moins qu'elle n'ait été explicitement configurée comme contact de support.

Les surfaces de conversation conservent l'Agent comme identité visible et ne reviennent pas à son modèle de support ou à son étiquette Model Specs.

Pour plus de détails sur les principaux, les bits de permission et la manière dont les ACL se combinent avec les permissions de fonctionnalités basées sur les rôles, consultez [Access Control](/docs/features/access_control).

### Place de marché des agents [#agent-marketplace]

Le **Agent Marketplace** permet aux utilisateurs de parcourir les agents qui leur sont accessibles. Ouvrez-le depuis **Agent Marketplace** dans la barre latérale ; l'entrée n'apparaît que pour les utilisateurs dont le rôle est autorisé à utiliser le Marketplace.

- **Parcourir et rechercher** : Les agents apparaissent dans une grille. Utilisez le champ de recherche pour trouver des agents par nom ou par description, et les pilules de catégorie (telles que **Top Picks**, **All**, ou une catégorie spécifique) pour restreindre la liste.
- **Trier** : Utilisez **Trier par** pour classer les agents par **Plus récent d'abord** (par défaut), **Plus ancien d'abord**, **Populaire** (les plus épinglés), ou **Par nom de créateur**.
- **Mes agents** : Activez **Mes agents** pour afficher uniquement les agents que vous avez créés. L'activer depuis **Meilleurs choix** bascule vers **Tous**.
- **Vues partageables** : La recherche, le tri et le filtre **Mes agents** sont conservés dans l'URL de la page (`?q=`, `?sort=`, `?mine=1`), de sorte qu'une vue filtrée puisse être mise en favori ou partagée.

Sélectionnez une carte d'agent pour ouvrir sa boîte de dialogue de détails, qui affiche la description complète et les coordonnées de l'agent, ainsi que les actions suivantes :

- **Épingler** ou **Désépingler** : Ajoutez l'agent à, ou retirez-le de, vos agents épinglés.
- **Copier le lien** : Copiez un lien qui démarre une nouvelle discussion avec l'agent.
- **Démarrer une discussion** : Ouvrez une nouvelle conversation avec l'agent.
- **Essayez un amorceur de conversation** : Lorsqu'un agent dispose de [conversation starters](#conversation-starters), sélectionnez-en un pour ouvrir une nouvelle discussion avec cette invite déjà présente dans la zone de saisie du message. Elle n'est pas envoyée automatiquement, vous pouvez donc la modifier au préalable.

Les administrateurs peuvent contrôler l'accès avec le paramètre [`interface.marketplace`](/docs/configuration/librechat_yaml/object_structure/interface#marketplace) et les autorisations de rôle décrites dans [Access Control](/docs/features/access_control).

### Contrôles administrateur [#administrator-controls]

Les administrateurs ont accès aux paramètres de permission globaux dans l'interface utilisateur du générateur d'agents :

- Activer/désactiver le partage d'agents pour tous les utilisateurs
- Contrôler les autorisations d'utilisation des agents
- Gérer les droits de création d'agents
- Configurer les paramètres à l'échelle de la plateforme

Dans un déploiement mono-locataire non délimité, le premier compte créé pour l'instance est un administrateur. Les déploiements délimités par locataire ne promeuvent pas automatiquement leur premier utilisateur enregistré ; provisionnez les administrateurs de locataire via un flux administratif approuvé. Si vous avez besoin d'ajouter un administrateur manuellement, vous pouvez [accéder à MongoDB](/docs/configuration/mongodb/mongodb_auth) et mettre à jour le profil de l'utilisateur :

```
db.users.updateOne(
  { email: 'USER_EMAIL_ADDRESS' },
  { $set: { role: 'ADMIN' } }
)
```

L'utilisation d'agents pour tous les utilisateurs peut également être désactivée via la configuration, [plus d'informations](/docs/configuration/librechat_yaml/object_structure/interface).

Les autorisations au niveau des fonctionnalités (qui peut _utiliser_, _créer_, _partager_ ou _partager publiquement_ des agents) sont gérées depuis le [**Panneau d'administration LibreChat**](/docs/features/admin_panel) pour chaque rôle, y compris les rôles personnalisés. Le bloc [`interface.agents`](/docs/configuration/librechat_yaml/object_structure/interface#agents) dans `librechat.yaml` peut toujours définir des valeurs par défaut pour le rôle `USER` intégré au démarrage, mais le panneau d'administration est la méthode recommandée pour les modifier à l'avenir.

### Partage au niveau de l'utilisateur [#user-level-sharing]

Les utilisateurs individuels peuvent :

- Partager leurs agents avec des utilisateurs, groupes ou rôles spécifiques (si `SHARE` est activé pour leur rôle)
- Rendre les agents visibles pour tout le monde sur l'instance (si `SHARE_PUBLIC` est activé)
- Attribuez à chaque destinataire un niveau d'accès différent (Viewer / Editor / Owner)
- Partagez à nouveau ou révoquez l'accès à tout moment depuis la boîte de dialogue de partage

## Pilotage et messages en file d'attente [#steering-and-queued-messages]

Pendant qu'un Agent répond, vous pouvez envoyer un autre message depuis le [composer](/docs/features/composer) de deux manières :

- **Steer** insère le message dans l'exécution actuelle à sa prochaine étape d'outil ou d'agent, afin que l'agent puisse ajuster son travail avant de terminer.
- **Queue** conserve le message et l'envoie comme un tour de suivi normal une fois que la réponse actuelle est terminée.

Pour les conversations avec des Agents enregistrées sur un serveur actuel, les suivis mis en file d'attente ordinaires sont stockés dans MongoDB. LibreChat préserve leur ordre FIFO et conserve leur texte, leurs pièces jointes, leurs extraits cités et leurs Skills sélectionnés manuellement malgré les déconnexions du navigateur, les redémarrages de l'application et les transferts de réplicas. Le traitement attend que la réponse précédente soit stabilisée avant d'admettre le tour suivant. Cette durabilité est automatique et ne nécessite aucun basculement dans le fichier YAML ou les variables d'environnement ; les serveurs plus anciens et les fenêtres de démarrage courtes sans époque de génération active conservent la file d'attente de compatibilité côté client.

L'admission au serveur est sérialisée au sein de chaque file d'attente de conversation. Si les preuves de prédécesseur ou la propriété de versions mixtes sont ambiguës, LibreChat affiche **Awaiting reconciliation** et bloque ou fait échouer le tour mis en file d'attente concerné au lieu de deviner et de le démarrer dans le désordre.

**Steer sooner** demande à l'agent de prendre le message au prochain point sûr au lieu d'attendre la prochaine étape de l'outil. Si aucun texte de réponse ou activité d'outil n'est encore sûr à conserver, LibreChat attend pendant une courte période de grâce, ignore la tentative silencieuse ou basée uniquement sur le raisonnement, insère le message et redémarre le modèle avec cette instruction. Une fois que le texte de réponse peut être conservé, LibreChat s'arrête à une limite sûre pour le fournisseur, préserve la réponse partielle, insère le message et reprend la même réponse de l'assistant. Un appel d'outil en cours n'est ni ignoré ni interrompu par le pilotage ; le message s'applique lorsque ce travail atteint une limite sûre.

Utilisez **Stop** pour mettre fin au raisonnement actif et demander l'annulation d'un appel d'outil au premier plan. Stop transmet l'annulation aux outils au premier plan sensibles aux signaux ; les tâches en arrière-plan conservent leur cycle de vie indépendant. Utilisez la commande dédiée du compositeur, choisissez-la dans le menu du bouton d'envoi, ou appuyez sur `Command/Ctrl + Shift + .`. L'action revient à un pilotage ordinaire lorsque le déploiement ne peut pas interrompre le flux du fournisseur actif.

Sous **Paramètres → Chat**, **Pendant la génération, Entrée va** choisit l'action par défaut. Le menu du bouton d'envoi peut outrepasser ce choix pour un message individuel, et **Diriger plus tôt avec Entrée** fait en sorte que la touche Entrée demande ce point de sécurité plus tôt lorsque la direction est activée par défaut.

Les fichiers et les [extraits cités](/docs/features/message_actions#quote-excerpts) accompagnent les messages de type steer, queue et interrupt. Les Skills sélectionnés manuellement restent en attente pour le tour complet suivant au lieu d'être joints à un steer en cours d'exécution.

Les steers en attente apparaissent à la fin de la réponse en streaming, là où ils atterriront, jusqu'à ce que le serveur les insère dans l'exécution. Leur réception progresse de **Sending** à **Delivered**, puis **Steer sooner requested** lorsqu'un point de sécurité plus précoce a été demandé, et enfin **Applied** avec une double coche en bas à droite du message en ligne. Les reçus confirmés comme appliqués restent visibles après un rechargement ainsi que dans les vues de partage ou de recherche ; une livraison incertaine ou échouée n'affiche jamais de coche de confirmation. Une fois accusé de réception, le menu du message permet de récupérer le steer pour le modifier, de le convertir en suivi mis en file d'attente, ou de l'annuler pour restaurer son texte et ses pièces jointes dans le compositeur. LibreChat évite d'écraser un brouillon plus récent ; si le compositeur n'est plus disponible, il conserve le message récupéré dans la file d'attente à la place. Un steer ayant échoué reste disponible pour être réessayé, modifié, mis en file d'attente ou supprimé.

Les suivis en file d'attente apparaissent dans une liste au-dessus du champ de saisie. Chacun peut être modifié (**Edit message**), supprimé (**Remove message**), envoyé immédiatement avec **Send now**, ou réordonné en faisant glisser sa poignée ou en utilisant les touches fléchées. Les suivis en file d'attente peuvent également être convertis en une orientation (steer) pendant que l'exécution est toujours active, ou être accélérés avec **Steer sooner**. Les orientations en cours offrent la même option d'accélération lorsqu'elles sont en attente d'une limite d'outil. La suppression d'un message en file d'attente sauvegardé sur le serveur annule d'abord sa source durable, puis le restaure dans un champ de saisie vide lorsque cela est possible. Si la réponse précédente est interrompue ou échoue, LibreChat marque le tour en file d'attente concerné comme ayant échoué pour examen au lieu de l'envoyer silencieusement.

Une conversation peut comporter jusqu'à 100 tours en file d'attente actifs. Chaque tour en file d'attente accepte jusqu'à 16 000 caractères et 10 fichiers. Par ailleurs, une exécution active accepte jusqu'à 10 orientations (steers) en attente ; chaque orientation peut inclure jusqu'à 10 fichiers et est limitée par [`STEER_MAX_LENGTH`](/docs/configuration/dotenv#agent-conversation-controls). **Steer sooner** continue d'utiliser le chemin d'orientation en direct plutôt que de déplacer un tour en file d'attente vers le début de la file FIFO durable.

Les déploiements multi-réplicas basés sur Redis négocient automatiquement le protocole de génération v2. Suivez les [conseils de compatibilité du protocole de génération](/docs/configuration/redis#generation-protocol-compatibility) lors de la mise à niveau depuis une version antérieure à `v0.8.8-rc1`.

### Notes [#notes]

- Les Instructions, les paramètres du modèle, les fichiers joints et les outils ne sont exposés à l'utilisateur que s'il dispose des autorisations de modification.
  - Un agent peut divulguer toute donnée jointe, qu'il s'agisse d'instructions ou de fichiers, au cours d'une conversation. Assurez-vous donc que vos instructions sont robustes face à ce risque avant d'accorder un accès Éditeur/Propriétaire ou de rendre l'agent public.
- Seuls les auteurs originaux, les administrateurs et les bénéficiaires disposant de l'autorisation Owner peuvent supprimer des agents partagés.
- Les Agents sont privés pour leurs auteurs sauf s'ils sont partagés

## Livraison d'événements d'agent [#agent-event-delivery]

LibreChat inclut une couche de distribution neutre vis-à-vis de la source pour les événements asynchrones des Agents. Les adaptateurs appartenant au déploiement peuvent normaliser un webhook vérifié, un message de file d'attente, un événement MCP, un événement de canal ou un événement interne du produit en une nouvelle exécution d'Agent (`fire`), un nouveau tour sur un Agent et une branche existants et enregistrés (`continue`), ou une mutation d'une exécution active (`steer`). Les adaptateurs restent responsables de l'authentification de leur source native, de la désinfection des charges utiles et de la sélection des cibles de confiance avant la mise en file d'attente.

Les [points de terminaison d'événements de l'API Agents](/docs/features/agents_api#agent-events) en version bêta exposent un accès authentifié `fire`, `continue` et `steer` aux clés API des Remote Agents. Les systèmes externes peuvent lier un acteur source à un Agent enfant direct et poursuivre cet acteur à travers les événements sans bascule de fonctionnalité supplémentaire. LibreChat déduit l'utilisateur, le locataire et l'identité source à partir de la clé API, applique l'accès aux Agents et les filtres de contenu, et exige une clé d'idempotence. Il ne s'agit pas d'un récepteur de webhook général non authentifié ; les adaptateurs spécifiques aux fournisseurs doivent toujours vérifier les signatures de webhook natives avant de l'appeler.

La fonctionnalité expérimentale [Scheduled Chats](/docs/features/scheduled_chats) est le premier producteur intégré de LibreChat pour cette couche. Elle crée des livraisons `fire` récurrentes pour les Agents enregistrés et est désactivée jusqu'à ce qu'un administrateur l'active. Les sous-agents détachés utilisent automatiquement une livraison `continue` idempotente pour réveiller un Agent parent enregistré après qu'un enfant a terminé ; les enfants annulés et les Agents parents éphémères sont exclus.

MongoDB stocke des enveloppes versionnées bornées, des clés d'idempotence, des files d'attente ordonnées, des baux, l'historique des tentatives, des reçus durables et des lettres mortes. Les workers utilisent une livraison au moins une fois avec des revendications protégées et un backoff exponentiel borné ; les reçus réussis expirent après 90 jours, tandis que les lettres mortes nécessitent une remise en file d'attente explicite et approuvée. Les livraisons « Fire » créent une nouvelle conversation. Les livraisons « Continue » créent un nouveau tour sur la branche de conversation exacte et sont différées pendant que cette branche est en cours d'exécution, en pause ou en cours de finalisation. Les acteurs liés disposent également d'une boîte aux lettres automatique : un acteur attend le résultat du traitement de son tour actuel avant de distribuer l'événement suivant, tandis que différents acteurs peuvent s'exécuter en parallèle. Les livraisons « Steer » doivent identifier la conversation et la génération existantes et utiliser une admission stricte afin que les tentatives ambiguës ne puissent pas injecter deux fois la même instruction.

Pour les continuations liées, le succès du transport démarre un cycle de vie de traitement durable distinct. Une livraison progresse de `started` à `applied`, `completed_no_action`, `failed` ou `cancelled`. Les sources peuvent exiger un outil précis et un sous-ensemble d'arguments optionnels avec `expectedAction` ; LibreChat rapporte `applied` uniquement à partir de preuves d'outils correspondantes observées par l'hôte, jamais à partir de texte rédigé par le modèle. Les événements observationnels compatibles peuvent partager un lot `coalesce.key` délimité tout en conservant un enregistrement d'idempotence et un reçu par événement source. La continuation par point de contrôle est utilisée lorsqu'elle est compatible, et revient sinon à l'historique des messages durables.

Les Bound Event Actors peuvent se mettre en pause pour une demande d'intervention de l'utilisateur (Ask User) ou une approbation d'outil, puis reprendre l'invocation exacte de l'acteur signé via l'interface habituelle de LibreChat pour l'interaction humaine (human-in-the-loop). La boîte aux lettres de l'acteur reste bloquée jusqu'à ce que cette pause reprenne ou soit résolue, empêchant un événement ultérieur de devancer la décision. Ces acteurs nécessitent le checkpointer durable MongoDB. LibreChat sélectionne automatiquement la continuation de point de contrôle ou la reconstruction de l'historique durable à partir de l'état de l'acteur et de la capacité de la requête ; le travail existant sous le protocole protocol-v1 reste sur le chemin de l'historique jusqu'à son épuisement.

Les Actions détachées lancées par des Event Actors sont activées automatiquement lorsque le magasin de génération intégré annonce sa prise en charge. L'acteur reste suspendu jusqu'à ce qu'une preuve terminale reprenne son invocation initiale ; par conséquent, un lancement en arrière-plan seul ne satisfait pas `expectedAction`. Le magasin en mémoire maintient ce cycle de vie cohérent tant que son processus reste actif. Redis ajoute une récupération durable après redémarrage et un transfert de réplica. Le travail d'achèvement appartenant à la fonctionnalité est isolé des anciens workers lors d'un drainage en version mixte ; les opérateurs ne sélectionnent pas ce comportement via un indicateur de fonctionnalité (feature flag).

L'hôte d'exécution appelle normalement l'écouteur lié au processus actuel. Configurez [`endpoints.agents.eventDriven.selfUrl`](/docs/configuration/librechat_yaml/object_structure/agents#eventdriven) uniquement lorsque ce chemin d'admission interne approuvé doit traverser une autre origine HTTP, telle qu'une porte d'entrée TLS.

## Migration requise (v0.8.0-rc3+) [#migration-required-v080-rc3]

<Callout type="warning" title="Important : Migration des permissions d'agent requise">
  À partir de la version v0.8.0-rc3, LibreChat utilise un nouveau système de permissions basé sur une liste de contrôle d'accès (ACL) pour les agents. Si vous effectuez une mise à niveau depuis une version antérieure, vous devez exécuter la migration des permissions des agents pour que les agents existants restent accessibles.
</Callout>

### Ce que fait la migration [#what-the-migration-does]

La migration des permissions d'agent fait passer vos agents d'un modèle de propriété simple à un système sophistiqué basé sur des ACL avec plusieurs niveaux de permission :

- **OWNER**: Contrôle total sur l'agent
- **EDITOR** : Peut voir et modifier l'agent
- **VIEWER** : Accès en lecture seule à l'agent

Sans exécuter cette migration, les agents existants seront inaccessibles via les nouveaux endpoints d'API prenant en charge les permissions.

### Exécution de la migration [#running-the-migration]

Choisissez la commande appropriée en fonction de votre méthode de déploiement :

#### 1. Pour le `docker-compose.yml` par défaut (si vous utilisez `docker compose up` pour démarrer l'application) : [#1-for-the-default-docker-composeyml-if-you-use-docker-compose-up-to-start-the-app]

**Prévisualiser les changements (simulation) :**

```bash
docker compose exec api npm run migrate:agent-permissions:dry-run
```

### Ce qui se passe pendant la migration [#what-happens-during-migration]

- **Agents privés** : Restent accessibles uniquement à leurs créateurs (reçoivent l'autorisation OWNER)
- **Agents partagés** : Si un agent a été précédemment partagé, il recevra les entrées ACL appropriées en tant qu'Agent public (partagé avec tous les utilisateurs)
- **Détection du système** : LibreChat détecte automatiquement les agents non migrés au démarrage et affiche un avertissement

Vous pouvez ajuster les permissions de l'agent résultant via l'interface utilisateur du Agent Builder.

<Callout type="info" title="Note">
  Le même processus de migration s'applique aux prompts. Si vous avez également des prompts existants, exécutez la migration des permissions de prompt en utilisant les mêmes commandes, mais remplacez `agent` par `prompt` dans les noms des commandes.
</Callout>

## Quelle est la prochaine étape ? [#whats-next]

Les Agents LibreChat marquent le début d'une nouvelle ère pour l'application, où les futurs pipelines pourront être rationalisés grâce à des Agents dédiés à des tâches et des flux de travail spécifiques tout au long de votre expérience dans LibreChat.

Les futures mises à jour incluront :

- Améliorations générales de l'expérience Agent actuelle
- Orchestration multi-agents pour des flux de travail complexes
- Capacité de personnaliser les agents pour diverses fonctions : titrage (nommage des fils de discussion), gestion de la mémoire (contexte/historique de l'utilisateur) et amélioration des prompts (assistance/prédictions de saisie)
- Plus d'outils, paramètres d'outils configurables, création d'outils dynamique.

De plus, cette mise à jour introduit un nouveau paradigme pour LibreChat, car son architecture sous-jacente apporte un rafraîchissement indispensable à l'application, optimisant à la fois l'expérience utilisateur et les performances globales de l'application.

Pour souligner une optimisation notable, une génération d'IA d'environ 1000 tokens transférera environ 1 Mo de données en utilisant les endpoints traditionnels (au moment de la rédaction, toute option d'endpoint autre que Agents et AWS Bedrock).

En utilisant un agent, la même génération transférera environ 52 ko de données, soit une réduction de 95 % du transfert de données, ce qui représente une charge bien moindre pour le serveur et l'appareil de l'utilisateur.

Les AI Agents dans LibreChat offrent un moyen puissant de créer des assistants spécialisés sans connaissances en programmation, tout en conservant la flexibilité de travailler avec vos modèles et fournisseurs d'IA préférés.
