<Callout type="warning" title="Funzionalità Beta">
L'API Agents è attualmente in beta. Gli endpoint, i formati di richiesta/risposta e il comportamento potrebbero cambiare man mano che procediamo verso una versione stabile.
</Callout>

LibreChat espone gli agenti ad applicazioni, script e servizi esterni tramite API di inferenza e di distribuzione degli eventi.

## Panoramica [#overview]

L'API Agents fornisce due interfacce di inferenza, la consegna di eventi autenticati e percorsi di gestione beta:

- **Chat Completions compatibili con OpenAI** — `POST /api/agents/v1/chat/completions`
- **API Risposte Aperte** — `POST /api/agents/v1/responses`
- **Eventi Agente** — `POST /api/agents/v1/events`
- **Gestione Agenti** — `/api/agents/v1/agents`
- **Gestione delle Skill** — `/api/agents/v1/skills`

Le interfacce di inferenza supportano l'autenticazione tramite API-key, l'autenticazione OIDC opzionale e le risposte in streaming. Gli Agent Events utilizzano l'autenticazione tramite API-key per i Remote Agents, in modo che LibreChat possa associare ogni consegna a un'identità di origine stabile. Le rotte di gestione utilizzano invece una allowlist di deployment che associa un client macchina OIDC a un utente e tenant LibreChat esistenti.

LibreChat sta adottando [Open Responses](https://www.openresponses.org/) come framework API principale per gestire gli agenti. Sebbene l'endpoint Chat Completions fornisca compatibilità con le versioni precedenti per gli strumenti compatibili con OpenAI, l'endpoint Open Responses rappresenta la direzione futura.

## Abilitazione dell'API Agents [#enabling-the-agents-api]

L'API Agents è protetta dietro la configurazione dell'interfaccia `remoteAgents`. Tutte le autorizzazioni sono impostate su `false` per impostazione predefinita.

```yaml filename="librechat.yaml"
interface:
  remoteAgents:
    use: true
    create: true
```

Vedi [Interface Configuration — remoteAgents](/docs/configuration/librechat_yaml/object_structure/interface#remoteagents) per tutte le opzioni disponibili.

**Nota:** Gli utenti amministratori hanno tutti i permessi di agente remoto abilitati per impostazione predefinita.

### Specifica OpenAPI e documentazione interattiva [#openapi-specification-and-interactive-docs]

LibreChat può fornire la specifica pubblica dell'API Agents su `/api/openapi.json` e la documentazione interattiva Swagger UI su `/api/docs`. Entrambi i percorsi sono disabilitati per impostazione predefinita. Abilitali con l'impostazione di primo livello `openapi`:

```yaml filename="librechat.yaml"
openapi:
  enabled: true
```

La specifica copre le route pubbliche di inferenza, eventi, gestione degli Agent e gestione delle Skill descritte in questa pagina. Mantieni le route disabilitate a meno che la tua distribuzione non intenda esporre la documentazione dell'API.

## Gestione delle API Key [#api-key-management]

Una volta abilitati `remoteAgents.use` e `remoteAgents.create`, gli utenti possono generare chiavi API dall'interfaccia utente di LibreChat. Queste chiavi autenticano le richieste all'API degli Agent.

## Autenticazione [#authentication]

L'API Agents supporta due metodi di autenticazione che possono essere utilizzati indipendentemente o insieme.

### Chiave API [#api-key]

L'autenticazione tramite API key è abilitata per impostazione predefinita. Genera le API key dall'interfaccia utente di LibreChat una volta che `remoteAgents.use` e `remoteAgents.create` sono stati abilitati.

```bash
Authorization: Bearer <YOUR_API_KEY>
```

### OIDC Bearer Token [#oidc-bearer-token]

Per scenari machine-to-machine in cui la tua infrastruttura dispone già di un provider OIDC, puoi autenticarti direttamente con token Bearer OIDC senza una chiave API di LibreChat.

Configura l'autenticazione OIDC in `librechat.yaml`:

```yaml filename="librechat.yaml"
endpoints:
  agents:
    remoteApi:
      auth:
        apiKey:
          enabled: false
        oidc:
          enabled: true
          issuer: https://auth.example.com/realms/myrealm
          # jwksUri is optional and auto-discovered from issuer if omitted
          audience: my-client-id
```

Quindi chiama l'API con il tuo token di accesso OIDC:

```bash
curl -X POST https://your-librechat-instance/api/agents/v1/responses \
  -H "Authorization: Bearer YOUR_OIDC_ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"model": "agent_abc123", "input": "Hello!"}'
```

<Callout type="info">
  Il token OIDC deve appartenere a un utente già esistente in LibreChat. La corrispondenza utilizza prima il claim `sub`, quindi ricorre a `email`, `preferred_username` o `upn`.
</Callout>

Vedi [Agents Endpoint - remoteApi](/docs/configuration/librechat_yaml/object_structure/agents#remoteapi) per tutte le opzioni di configurazione.

<Callout type="warning" title="Gli eventi dell'agente richiedono una chiave API">
  L'autenticazione basata esclusivamente su OIDC non è supportata per gli endpoint degli Agent Events. Utilizza una chiave API per i Remote Agents durante la creazione di binding, l'accodamento di eventi e il polling dello stato di consegna.
</Callout>

## API di gestione degli agenti [#agent-management-api]

L'API di gestione degli Agent in beta consente a un servizio di gestire gli Agent e le relative risorse collegate senza una sessione del browser. È autenticata indipendentemente dall'inferenza e dagli Agent Events: vengono accettati solo i token macchina OIDC configurati sotto [`endpoints.agents.managementApi`](/docs/configuration/librechat_yaml/object_structure/agents#managementapi).

Ogni client OAuth configurato è associato a un `userId` e a un `tenantId` di LibreChat esistenti. Dopo la verifica del token, ogni richiesta viene eseguita come quell'utente e mantiene le funzionalità del ruolo corrente dell'utente, gli ACL di Agent e Skill, le restrizioni del provider, le concessioni di strumenti, i limiti dei file e l'isolamento del tenant. Un'associazione client non rende l'utente un amministratore né garantisce l'accesso a risorse che l'utente non può gestire altrimenti.

### Percorsi degli Agenti [#agent-routes]

| Metodo   | Rotta                                      | Scopo                                        |
| -------- | ------------------------------------------ | -------------------------------------------- |
| `POST`   | `/api/agents/v1/agents`                    | Crea un Agent                                |
| `GET`    | `/api/agents/v1/agents`                    | Elenca gli Agent accessibili                 |
| `GET`    | `/api/agents/v1/agents/{id}`               | Leggi un singolo Agent accessibile           |
| `PATCH`  | `/api/agents/v1/agents/{id}`               | Aggiorna un Agent                            |
| `DELETE` | `/api/agents/v1/agents/{id}`               | Elimina un Agent                             |
| `POST`   | `/api/agents/v1/agents/{id}/files`         | Carica e allega un file di risorsa all'Agent |
| `GET`    | `/api/agents/v1/agents/{id}/files`         | Elenca i file allegati accessibili all'Agent |
| `DELETE` | `/api/agents/v1/agents/{id}/files/{fileId}` | Rimuovi un file allegato dall'Agent          |

I payload di creazione e aggiornamento degli Agent utilizzano gli stessi campi supportati esternamente dell'Agent Builder e rifiutano i campi di primo livello sconosciuti. La creazione richiede un `model`; l'aggiornamento accetta solo i campi forniti. Le risposte espongono la configurazione dell'Agent supportata più `id`, `provider`, `model` (che può essere nullo), `version`, `createdAt` e `updatedAt`, senza i campi di proprietà della persistenza.

Gli elenchi accettano un `limit` da 1 a 100, con un valore predefinito di 20, e un `cursor` opaco. Quando `has_more` è true, passa il valore `after` restituito come cursore successivo; non decodificare o costruire cursori nei client.

```bash
curl https://your-librechat-instance/api/agents/v1/agents?limit=20 \
  -H "Authorization: Bearer YOUR_MACHINE_ACCESS_TOKEN"
```

```bash
curl -X POST https://your-librechat-instance/api/agents/v1/agents \
  -H "Authorization: Bearer YOUR_MACHINE_ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Release assistant",
    "provider": "openAI",
    "model": "gpt-5.6",
    "instructions": "Prepare concise release notes from verified changes."
  }'
```

Il caricamento di file utilizza `multipart/form-data` con un `file` e un valore `tool_resource` come `context`, `file_search` o `execute_code`. LibreChat applica i controlli relativi alla capacità di deployment, alla concessione del ruolo, al limite di velocità di caricamento, per singolo file, al conteggio dei file e alla dimensione aggregata prima di allegare la risorsa. La rimozione di un file richiede l'accesso in modifica all'Agent e non indebolisce le regole di autorizzazione dei file sottostanti.

### Percorsi delle Skill [#skill-routes]

| Metodo  | Rotta                                                | Scopo                                 |
| ------- | ---------------------------------------------------- | ------------------------------------- |
| `GET`   | `/api/agents/v1/skills`                              | Elenca le Skill accessibili           |
| `GET`   | `/api/agents/v1/skills/{id}`                         | Legge una Skill accessibile           |
| `PATCH` | `/api/agents/v1/skills/{id}`                         | Aggiorna i metadati della Skill supportata |
| `GET`   | `/api/agents/v1/skills/{id}/files`                   | Elenca i file nella Skill             |
| `GET`   | `/api/agents/v1/skills/{id}/files/{relativePath}`    | Legge un file della Skill             |
| `PUT`   | `/api/agents/v1/skills/{id}/files/{relativePath}`    | Crea o sostituisce un file supportato |

Le operazioni sulle Skill sono limitate alle Skill visibili all'utente associato. La lettura richiede l'accesso alla Skill, mentre i metadati o la scrittura di file richiedono i corrispondenti permessi di modifica e di creazione della Skill. I percorsi vengono normalizzati al di sotto della root della Skill; il traversal, i file non supportati e i contenuti di dimensioni eccessive vengono rifiutati.

### Errori e Autenticazione [#errors-and-authentication]

Le risposte di gestione utilizzano errori strutturati con codici `invalid_request`, `not_found`, `permission_denied`, `conflict` o `internal_error`. I fallimenti dell'autorizzazione alle risorse possono essere restituiti come `not_found` in modo che i chiamanti non possano sondare ID inaccessibili.

I token macchina devono essere non scaduti, corrispondere all'emittente configurato, identificare un client presente nella lista consentita tramite `azp` o `client_id` e soddisfare la regola del soggetto configurata. Per impostazione predefinita, i token devono anche corrispondere al pubblico (audience) configurato. Per provider come Amazon Cognito che emettono token di accesso macchina con `client_id` invece di `aud`, impostare `tokenUse: access`, omettere `audience` e richiedere l'ambito OAuth previsto con `requiredScopes`. Una configurazione mancante o credenziali non valide restituiscono `401`; un account vincolato in fase di eliminazione restituisce `409`. Consultare [`managementApi.auth.oidc`](/docs/configuration/librechat_yaml/object_structure/agents#managementapiauthoidc) e [`managementApi.auth.clients`](/docs/configuration/librechat_yaml/object_structure/agents#managementapiauthclients) per le regole complete su claim e vincoli.

## Endpoint [#endpoints]

### Chat Completions (compatibile con OpenAI) [#chat-completions-openai-compatible]

```
POST /api/agents/v1/chat/completions
```

Utilizza qualsiasi SDK compatibile con OpenAI puntandolo alla tua istanza LibreChat. Il parametro `model` corrisponde a un ID agente.

**Esempio con curl:**
```bash
curl -X POST https://your-librechat-instance/api/agents/v1/chat/completions \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "agent_abc123",
    "messages": [
      {"role": "user", "content": "Hello, what can you help me with?"}
    ],
    "stream": true
  }'
```

**Esempio con OpenAI SDK (Python):**
```python
from openai import OpenAI

client = OpenAI(
    base_url="https://your-librechat-instance/api/agents/v1",
    api_key="YOUR_API_KEY"
)

response = client.chat.completions.create(
    model="agent_abc123",
    messages=[{"role": "user", "content": "Hello!"}],
    stream=True
)

for chunk in response:
    print(chunk.choices[0].delta.content, end="")
```

### Elenco modelli [#list-models]

```
GET /api/agents/v1/models
```

Restituisce gli agenti disponibili come modelli. Utile per scoprire quali agenti sono accessibili con la tua API key.

### API per le risposte aperte [#open-responses-api]

```
POST /api/agents/v1/responses
```

L'endpoint Open Responses segue la [specifica Open Responses](https://www.openresponses.org/), uno standard di inferenza aperto avviato da OpenAI e costruito dalla comunità AI open-source. È progettato per flussi di lavoro agentici con supporto nativo per ragionamento, utilizzo di strumenti, output strutturati ed eventi semantici in streaming.

```bash
curl -X POST https://your-librechat-instance/api/agents/v1/responses \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "agent_abc123",
    "input": "What is the weather today?"
  }'
```

#### Strumenti di funzione eseguiti dal chiamante (Caller-Executed Function Tools) [#caller-executed-function-tools]

L'endpoint Open Responses accetta strumenti `function` standard forniti dal chiamante. LibreChat espone queste definizioni al modello ma non le esegue. Quando il modello ne seleziona una, la risposta contiene un elemento di output `function_call` che il chiamante deve eseguire.

Per continuare, invia una nuova richiesta il cui `input` riproduca l'elemento `function_call` restituito, seguito da un elemento `function_call_output` corrispondente. Questo passaggio è senza stato: non crea un'esecuzione sospesa e il solo `previous_response_id` non può sostituire lo scambio di strumenti riprodotto.

```json
{
  "model": "agent_abc123",
  "input": [
    {
      "type": "function_call",
      "call_id": "call_abc123",
      "name": "lookup_order",
      "arguments": "{\"order_id\":\"A-42\"}"
    },
    {
      "type": "function_call_output",
      "call_id": "call_abc123",
      "output": "{\"status\":\"shipped\"}"
    }
  ]
}
```

I nomi dei tool del chiamante possono contenere lettere, numeri, trattini bassi e trattini. I nomi devono essere univoci e non possono sostituire un tool fornito dal server. Un tool eseguito dal chiamante deve essere l'unico tool selezionato nel suo turno; se il modello lo combina con tool eseguiti dal server, LibreChat chiede al modello di riprovare il tool del chiamante da solo.

Per gli strumenti Agente eseguiti da LibreChat, entrambi gli endpoint di inferenza headless applicano una policy [`endpoints.agents.toolApproval`](/docs/configuration/librechat_yaml/object_structure/agents#toolapproval) abilitata, che include `deny`, `ask` e hook programmatici. Queste chiamate non dispongono di un canale interattivo di approvazione/ripresa: `deny` e `ask` bloccano lo strumento invece di aprire una richiesta di approvazione. Configura permessi espliciti solo per gli strumenti che il client API deve poter eseguire senza supervisione; quando la policy è disabilitata, i suoi hook di approvazione non vengono eseguiti. Gli strumenti funzione eseguiti dal chiamante rimangono sotto la responsabilità del chiamante stesso.

## Eventi Agente [#agent-events]

Gli Agent Events consentono a un controller autenticato o a un adattatore di origine di fornire lavoro durevole a un Agent. La consegna degli eventi è una funzionalità beta e il suo comportamento in termini di richiesta, risposta e runtime potrebbe subire modifiche.

Gli endpoint utilizzano l'utente autenticato, il tenant e la chiave API; l'Agent di destinazione deve essere visibile a tale utente secondo le autorizzazioni esistenti per i Remote Agents. Le richieste di Agent Event utilizzano inoltre il bucket dedicato [`rateLimits.agentEvents`](/docs/configuration/librechat_yaml/object_structure/config#ratelimits).

### Invia un evento [#deliver-an-event]

```http
POST /api/agents/v1/events
Authorization: Bearer <REMOTE_AGENTS_API_KEY>
Idempotency-Key: webhook-42-resource-7
Content-Type: application/json

{
  "mode": "fire",
  "event": {
    "id": "resource-7-ready-3",
    "type": "resource.ready",
    "occurredAt": 1786967999000,
    "payload": { "resourceId": "resource-7" }
  },
  "target": { "agentId": "agent_abc123" },
  "input": "Resource resource-7 is ready. Inspect it and report the result.",
  "orderingKey": "resource-7"
}
```

Invia esattamente un header `Idempotency-Key` e riutilizzalo quando riprovi la stessa consegna da evento sorgente a destinazione. La chiave deve contenere 1-256 lettere, numeri o i caratteri `._~:/+=-`. Il riutilizzo di una chiave con un contenuto di consegna diverso restituisce un conflitto.

Il chiamante fornisce l' `id` dell'evento, il `type`, `occurredAt` e il `payload` sanificato. LibreChat sostituisce qualsiasi `event.source` fornito dal chiamante con l'identità della chiave API autenticata e deriva l'utente, il tenant, l'ID della richiesta e l'orario di ricezione. Non inserire credenziali o segreti di trasporto nei payload degli eventi poiché le consegne accettate vengono persistite.

`orderingKey` è facoltativo. Utilizzare un valore stabile quando le consegne da fonti diverse devono rimanere ordinate per la stessa risorsa.

Una richiesta riuscita restituisce `202 Accepted`, un `id` di consegna opaco, il suo stato attuale e un'intestazione `Location`. Esegui il polling di quella posizione:

```http
GET /api/agents/v1/events/{delivery_id}
Authorization: Bearer <SAME_REMOTE_AGENTS_API_KEY>
```

La consegna può essere `pending`, `leased`, `succeeded` o `dead`. La risposta sullo stato include tentativi e timestamp, oltre a un risultato o a un errore pubblico una volta completata; non espone il payload memorizzato, la chiave di ordinamento, la cronologia dei tentativi o l'identità del worker. L'accesso allo stato è limitato allo stesso utente, tenant e origine della chiave API.

Per un `continue` vincolato, `succeeded` significa che il turno dell'Agente è stato ammesso, non che il lavoro richiesto sia terminato. Il suo stato espone quindi anche un ciclo di vita `handling` durevole: `started`, seguito da esattamente uno tra `applied`, `completed_no_action`, `failed` o `cancelled`.

Le fonti che riconoscono le azioni possono includere un `expectedAction` con un nome di strumento e un sottoinsieme facoltativo di argomenti. LibreChat segnala `applied` solo quando quella specifica generazione termina con prove dello strumento osservate dall'host che corrispondono al contratto; la prosa redatta dal modello non viene mai accettata come prova. Le consegne `fire`, `steer` e `continue` non vincolate rifiutano `expectedAction`.

I risultati `fire` riusciti includono l'identità della conversazione e della generazione che un successivo evento `steer` può prendere come riferimento.

### Agenti Child basati su eventi [#event-driven-child-agents]

Un sistema esterno può associare un attore sorgente a un Agent figlio diretto, per poi proseguire la stessa conversazione con il figlio attraverso vari eventi. Le continuazioni dei figli associati sono automatiche una volta che i controlli sull'identità della API-key, la proprietà dell'associazione, la relazione con il genitore e l'autorizzazione dell'Agent hanno avuto esito positivo; non esiste un interruttore di funzionalità separato.

Registra l'attore con la stessa API key che fornirà i suoi turni successivi:

```http
POST /api/agents/v1/events/bindings
Authorization: Bearer <REMOTE_AGENTS_API_KEY>
Idempotency-Key: championship-7-player-hanae
Content-Type: application/json

{
  "actorId": "hanae-kobayashi",
  "parentConversationId": "director-conversation-id",
  "parentMessageId": "director-message-id",
  "target": { "agentId": "agent_hanae" }
}
```

`actorId` può contenere fino a 128 caratteri. Il genitore deve essere una normale conversazione di un Agent e la destinazione deve essere configurata come uno dei Subagent diretti di quell'Agent o come un self-spawn consentito. Un nuovo binding restituisce `201`; un replay idempotente restituisce `200`. Entrambe le risposte includono `id`, `actorId`, `agentId` e `threadId`.

Invia i turni successivi con l'ID di binding restituito:

```http
POST /api/agents/v1/events
Authorization: Bearer <SAME_REMOTE_AGENTS_API_KEY>
Idempotency-Key: game-12-ply-17-hanae
Content-Type: application/json

{
  "mode": "continue",
  "bindingId": "evtbind_...",
  "event": {
    "id": "game-12-ply-17",
    "type": "chess.turn.ready",
    "occurredAt": 1786968000000,
    "payload": { "gameId": "game-12", "expectedPly": 17 }
  },
  "input": "Your clock is running. Read the position and submit one legal move.",
  "expectedAction": {
    "tool": "submit_move",
    "arguments": { "gameId": "game-12" }
  }
}
```

LibreChat risolve l'Agent figlio, il thread, la foglia del ramo più recente e la corsia di ordinamento dal binding immediatamente prima dell'invio. I campi target e di ordinamento forniti dal chiamante non possono reindirizzare una continuazione vincolata. L' `Idempotency-Key` della richiesta diventa l'identità pubblica stabile per quel turno figlio durante i tentativi di consegna, il leasing di generazione, i messaggi persistenti, l'attività live e un successivo ripristino HITL.

Ogni binding dispone di una casella di posta durevole automatica. Il suo evento successivo rimane in coda finché il turno corrente non raggiunge `applied`, `completed_no_action`, `failed` o `cancelled`; i diversi binding rimangono indipendenti e possono essere eseguiti in parallelo. Il ripristino del checkpoint viene tentato solo per un turno inizializzato compatibile. Se un checkpoint manca o non può essere ripristinato, LibreChat ripiega sulla cronologia dei messaggi durevoli senza indebolire i controlli di ricezione, autorizzazione o azione prevista.

Un attore vincolato può mettersi in pausa per l'opzione "Chiedi all'utente" (Ask User) o per l'approvazione di uno strumento. LibreChat mantiene la sospensione firmata esatta prima di esporre l'azione in sospeso, e la mailbox del binding rimane bloccata finché quella stessa invocazione dell'attore non riprende o si conclude. Gli Event Actor richiedono il checkpointer durevole di MongoDB; `type: memory` non è compatibile. LibreChat negozia il protocollo di generazione v2 e seleziona automaticamente il checkpoint o la continuazione della cronologia. Il lavoro esistente con il protocollo v1 rimane sul percorso della cronologia durevole finché non viene esaurito. Vedi [Generation Protocol Compatibility](/docs/configuration/redis#generation-protocol-compatibility) per i requisiti di distribuzione con versioni miste.

### Coalescing Observational Events [#coalescing-observational-events]

Le fonti in grado di dimostrare che diversi eventi `continue` vincolati sono osservazioni intercambiabili possono assegnare loro lo stesso `coalesce.key` definito dalla fonte:

```json
{
  "mode": "continue",
  "bindingId": "evtbind_...",
  "event": {
    "id": "championship-7-game-12-move-18",
    "type": "chess.move.completed",
    "occurredAt": 1786968000750,
    "payload": { "gameId": "game-12", "ply": 18 }
  },
  "input": "A tournament game advanced.",
  "coalesce": { "key": "championship-commentary" }
}
```

LibreChat raccoglie eventi compatibili per un massimo di 750 ms, con al massimo 8 eventi e 512 KiB di buste combinate. Il figlio riceve un documento batch deterministico, ma ogni evento sorgente mantiene la propria `Idempotency-Key`, il record di consegna e la ricevuta.

Usa il coalescing solo per osservazioni non azionabili. È rifiutato per `fire`, `steer`, `continue` non vincolati e consegne con `expectedAction`; non usarlo per comandi, approvazioni, richieste HITL, recinzioni (fences) o eventi la cui tempistica individuale è importante.

Nella conversazione padre autenticata, ogni attore vincolato appare sotto il messaggio padre di appartenenza. Il pannello Subagent può passare da un attore all'altro e tra i turni, caricare attività precedenti ed espandere un turno per mostrare la sua intera attività vincolata. I dettagli dell'evento includono il tipo, la fonte, l'orario di occorrenza e l'azione prevista. I passaggi di esecuzione visibili, gli strumenti, i messaggi e i marcatori di ragionamento sono inclusi senza il testo di ragionamento grezzo. L'indice padre restituisce al massimo 64 thread figli e 20 attività recenti per figlio da una finestra di origine vincolata, segnala il troncamento invece di implicare la completezza e limita la risposta a 96 KB. È autorizzato a livello di padre, utente e tenant; i binding, gli ID delle chiavi di origine, i token di lease e lo stato del worker non sono inclusi nella proiezione.

Il thread figlio rimane nascosto dalla normale navigazione delle conversazioni e in sola lettura per i percorsi di chat umani, eredita la politica temporanea o di scadenza del genitore ed è limitato a un livello di figlio diretto. Un ID di associazione da solo non garantisce l'accesso; le continuazioni sono limitate all'utente, al tenant e alla chiave API che le ha create.

### Azioni dell'Attore di Eventi Scollegato [#detached-event-actor-actions]

I turn dell'Event Actor possono separare le Action idonee e completarle in modo durevole. La consegna rimane nel suo ciclo di vita di gestione mentre l'Action è in esecuzione; l'evidenza terminale durevole riprende l'invocazione originale dell'actor firmato e solo l'evidenza dello strumento osservata dall'host risultante può soddisfare `expectedAction`. I replay e le repliche in competizione non possono avviare due volte la stessa Action riservata. Se LibreChat non è in grado di determinare se un effetto collaterale esterno sia iniziato, mette in quarantena l'avvio invece di riprovarlo ciecamente.

LibreChat abilita automaticamente questo lavoro di completamento interno quando l'archivio di generazione integrato selezionato ne dichiara il supporto. L'archivio in-memory esegue l'avvio, il completamento e la continuazione in un unico processo e non può recuperare tale lavoro dopo l'uscita dal processo. I flussi di generazione Redis aggiungono un ripristino durevole al riavvio e un passaggio di consegne tra repliche. I record di consegna e recupero di proprietà della funzionalità rimangono invisibili ai richiedenti meno recenti durante uno svuotamento a versione mista; non esiste alcun flag del produttore gestito dall'operatore.

## Monitoraggio dell'utilizzo dei token [#token-usage-tracking]

Tutte le richieste di inferenza dell'API degli Agents tracciano l'utilizzo dei token rispetto al saldo dell'utente quando la spesa dei token è configurata. Sia le risposte in streaming che quelle non in streaming aggregano ogni chiamata al modello del primary-Agent e del Subagent fatturata nei totali di primo livello. La risposta include anche suddivisioni dei token `primary` e `subagent` prive di identità. I dettagli sui token di cache e di ragionamento sono inclusi laddove il provider li riporta.
