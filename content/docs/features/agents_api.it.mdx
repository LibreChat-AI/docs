Punta qualsiasi SDK di OpenAI alla tua istanza, passa l'ID di un agente come modello e otterrai l'intera configurazione dell'agente (istruzioni, strumenti, file) tramite un'API familiare. Usala per integrare un agente in uno script, in un job di CI o in un altro prodotto.

## Ottieni una API key [#get-an-api-key]

Apri **Impostazioni**, vai su **Dati e privacy** e individua **Agent API Keys** nella sezione **API keys**. Fai clic su **Gestisci**, quindi su **Crea API Key**, assegna un nome, scegli una scadenza (da 7 giorni fino a 1 anno, oppure mai) e copia subito la chiave: viene mostrata una sola volta.

Una chiave agisce per tuo conto. Tutto ciò che puoi raggiungere tramite l'API è raggiungibile anche da chiunque possieda la chiave, quindi elimina le chiavi che non utilizzi più. Eliminare una chiave interrompe immediatamente le applicazioni che la utilizzano.

Se non vedi la sezione, il tuo ruolo non ha ricevuto l'accesso all'API degli Agenti.

## Quali agenti puoi chiamare [#which-agents-you-can-call]

Puoi chiamare gli agenti di tua proprietà o condivisi con te. Per un agente di proprietà di un altro utente, il proprietario deve concederti l'accesso tramite il pulsante **Accesso remoto** (l'icona del globo) nel footer del Costruttore di agenti. Questo è separato dalla normale condivisione: poter chattare con un agente in LibreChat non ti consente di richiamarlo tramite API.

Devi l'ID dell'agente, che è mostrato in **Impostazioni avanzate** nel builder con un pulsante di copia. `GET /api/agents/v1/models` elenca gli agenti che la tua chiave può chiamare, e `GET /api/agents/v1/models/{model}` ne restituisce uno.

## Completamenti di chat [#chat-completions]

`POST /api/agents/v1/chat/completions` segue il formato OpenAI Chat Completions, quindi i client OpenAI esistenti funzionano semplicemente cambiando l'URL di base:

```python
from openai import OpenAI

client = OpenAI(
    base_url="https://your-librechat-instance/api/agents/v1",
    api_key="YOUR_API_KEY",
)

stream = client.chat.completions.create(
    model="agent_abc123",
    messages=[{"role": "user", "content": "Summarize yesterday's open tickets."}],
    stream=True,
)

for chunk in stream:
    print(chunk.choices[0].delta.content or "", end="")
```

La stessa richiesta con curl:

```bash
curl https://your-librechat-instance/api/agents/v1/chat/completions \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "agent_abc123",
    "messages": [{"role": "user", "content": "Hello"}],
    "stream": true
  }'
```

## Open Responses [#open-responses]

`POST /api/agents/v1/responses` implementa la specifica [Open Responses](https://www.openresponses.org/), progettata per i carichi di lavoro degli agenti: ragionamento, chiamate agli strumenti ed eventi in streaming fanno parte del formato e non sono aggiunti in un secondo momento. Questa è l'interfaccia su cui LibreChat sta costruendo in futuro, quindi è preferibile utilizzarla per le nuove integrazioni.

```bash
curl https://your-librechat-instance/api/agents/v1/responses \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model": "agent_abc123", "input": "What changed in the last release?"}'
```

`GET /api/agents/v1/responses/{id}` restituisce una risposta memorizzata, e `GET /api/agents/v1/responses/models` elenca gli agenti disponibili qui.

### Le tue funzioni personalizzate [#your-own-function-tools]

Puoi passare strumenti `function` standard in una richiesta Responses. LibreChat li mostra al modello ma non li esegue: quando il modello ne sceglie uno, la risposta contiene un elemento `function_call`, e la funzione va eseguita da te. Per continuare, invia una nuova richiesta il cui `input` ripete quell'elemento `function_call`, seguito da un `function_call_output` con lo stesso `call_id`:

```json
{
  "model": "agent_abc123",
  "input": [
    { "type": "function_call", "call_id": "call_abc123", "name": "lookup_order", "arguments": "{\"order_id\":\"A-42\"}" },
    { "type": "function_call_output", "call_id": "call_abc123", "output": "{\"status\":\"shipped\"}" }
  ]
}
```

Nessuno stato viene mantenuto aperto tra le due richieste, e `previous_response_id` da solo non basta: è necessario rieseguire la chiamata e il suo output. I nomi degli strumenti possono contenere lettere, numeri, trattini bassi e trattini, devono essere univoci e non possono sovrapporsi a uno degli strumenti propri dell'agente. Un turno che richiama uno dei tuoi strumenti non può contemporaneamente richiamare gli strumenti dell'agente; al modello viene chiesto di riprovare.

### Approvazione degli strumenti tramite API [#tool-approval-over-the-api]

Se il tuo amministratore richiede l'approvazione per alcuni strumenti, le chiamate API non possono fermarsi per chiedere a qualcuno. Gli strumenti che richiederebbero un'approvazione, oppure quelli negati, vengono invece bloccati. Gli amministratori dovrebbero consentire esplicitamente gli strumenti che un client non presidiato è destinato a eseguire.

## Eventi Agente [#agent-events]

Gli Agent Events permettono a un altro sistema di affidare un'attività a un agente e di tornare in seguito per vedere cosa è successo. Questa funzionalità è in beta. Gli eventi utilizzano la tua chiave API per Agents, che identifica te e l'origine; le configurazioni basate solo su OIDC non possono utilizzarli. Hanno anche un proprio limite di frequenza, [`rateLimits.agentEvents`](/docs/configuration/librechat_yaml/object_structure/config#ratelimits).

Un evento viene ricevuto in una delle tre modalità:

- `fire` avvia una nuova conversazione con l'agente.
- `continue` aggiunge un turno a un agente figlio che hai associato in precedenza (vedi sotto).
- `steer` aggiunge indicazioni a un'esecuzione ancora in corso, identificata dalla conversazione e dalla generazione restituite da un `fire`.

```http
POST /api/agents/v1/events
Authorization: Bearer <REMOTE_AGENTS_API_KEY>
Idempotency-Key: webhook-42-resource-7
Content-Type: application/json

{
  "mode": "fire",
  "event": {
    "id": "resource-7-ready-3",
    "type": "resource.ready",
    "occurredAt": 1786967999000,
    "payload": { "resourceId": "resource-7" }
  },
  "target": { "agentId": "agent_abc123" },
  "input": "Resource resource-7 is ready. Inspect it and report the result.",
  "orderingKey": "resource-7"
}
```

Ogni richiesta deve includere una sola `Idempotency-Key` (da 1 a 256 lettere, numeri o `._~:/+=-`). Riutilizzala quando ripeti la stessa consegna; riutilizzarla per contenuti diversi genera un conflitto. LibreChat imposta l'origine dell'evento in base alla tua chiave API e ignora qualsiasi origine che invii. Il payload viene memorizzato, quindi non inserirvi dati sensibili. Usa `orderingKey` quando gli eventi riguardanti la stessa entità devono essere gestiti in ordine.

La risposta è `202 Accepted` con un ID di consegna e una `Location` da interrogare con la stessa chiave:

```http
GET /api/agents/v1/events/{delivery_id}
Authorization: Bearer <SAME_REMOTE_AGENTS_API_KEY>
```

Una consegna può essere `pending`, `leased`, `succeeded` o `dead`. Per un `continue` vincolato, `succeeded` indica solo che il turno è stato avviato. Il suo stato `handling` passa quindi da `started` a uno tra `applied`, `completed_no_action`, `failed` o `cancelled`. Se invii un `expectedAction` (il nome di uno strumento e, facoltativamente, alcuni dei suoi argomenti), `applied` significa che LibreChat ha rilevato la chiamata di quello strumento con argomenti corrispondenti; ciò che il modello scrive nel testo non viene preso in considerazione.

Gli eventi dell'agente non sono un ricevitore di webhook pubblico. Se gli eventi provengono da un provider che firma i propri webhook, verifica la firma nel tuo adattatore prima di inoltrarli.

### Agenti figli guidati dagli eventi [#event-driven-child-agents]

Per mantenere una conversazione in corso con un agente figlio attraverso molti eventi, associalo una sola volta, quindi invia eventi `continue` alla associazione:

```http
POST /api/agents/v1/events/bindings
Authorization: Bearer <REMOTE_AGENTS_API_KEY>
Idempotency-Key: championship-7-player-hanae
Content-Type: application/json

{
  "actorId": "hanae-kobayashi",
  "parentConversationId": "director-conversation-id",
  "parentMessageId": "director-message-id",
  "target": { "agentId": "agent_hanae" }
}
```

Il genitore deve essere una normale conversazione con un agente, e il destinatario deve essere uno dei sottoagenti diretti di tale agente (oppure l'agente stesso, se è consentito l'auto-spawn). `actorId` può contenere fino a 128 caratteri. Un nuovo binding restituisce `201` e una riproduzione restituisce `200`, entrambi con l'`id` del binding. I turni successivi fanno riferimento ad esso:

```json
{
  "mode": "continue",
  "bindingId": "evtbind_...",
  "event": { "id": "game-12-ply-17", "type": "chess.turn.ready", "occurredAt": 1786968000000, "payload": { "gameId": "game-12" } },
  "input": "Your clock is running. Submit one legal move.",
  "expectedAction": { "tool": "submit_move", "arguments": { "gameId": "game-12" } }
}
```

Ogni binding elabora un evento alla volta: il successivo attende finché il turno corrente non raggiunge uno stato di gestione finale, mentre binding diversi vengono eseguiti in parallelo. Un child collegato può mettersi in pausa per Ask User o per l'approvazione di uno strumento; i suoi eventi successivi attendono finché qualcuno non risponde in LibreChat. Questo richiede il checkpointer MongoDB durevole (quello predefinito). Nella conversazione padre, ogni child collegato appare come una riga sotto il messaggio che possiede il binding e apre il pannello dell'attività dei subagent.

Un binding funziona solo con la API key, l'utente e il tenant che lo hanno creato. Il thread figlio resta escluso dall'elenco delle chat ed è di sola lettura nell'app.

Per gli eventi che sono semplici osservazioni, come "una partita è avanzata", assegnate lo stesso `coalesce.key` e LibreChat raggruppa fino a 8 di questi eventi (entro 750 ms e 512 KiB) in un unico turno. Ogni evento riceve comunque la propria ricevuta. Non raggruppate comandi, approvazioni o qualsiasi elemento con un `expectedAction`.

## API di gestione degli agenti [#agent-management-api]

L'Agent Management API consente a un servizio attendibile di creare, modificare ed eliminare agenti e competenze senza una sessione del browser. È in beta e utilizza una propria autenticazione: token OIDC di macchina provenienti da client che l'amministratore elenca in [`managementApi`](/docs/configuration/librechat_yaml/object_structure/agents#managementapi). Ogni client è associato a un unico utente e tenant LibreChat esistente, e ogni richiesta agisce come quell'utente, con i suoi permessi e il suo accesso. Non rende nessuno amministratore.

| Metodo | Percorso | Scopo |
| -------- | -------------------------------------------- | ---------------------------------- |
| `POST` | `/api/agents/v1/agents` | Creare un agente |
| `GET` | `/api/agents/v1/agents` | Elencare gli agenti accessibili |
| `GET` | `/api/agents/v1/agents/{id}` | Leggere un agente |
| `PATCH` | `/api/agents/v1/agents/{id}` | Aggiornare un agente |
| `DELETE` | `/api/agents/v1/agents/{id}` | Eliminare un agente |
| `POST` | `/api/agents/v1/agents/{id}/files` | Caricare e allegare un file |
| `GET` | `/api/agents/v1/agents/{id}/files` | Elencare i file allegati |
| `DELETE` | `/api/agents/v1/agents/{id}/files/{fileId}` | Rimuovere un file allegato |
| `GET` | `/api/agents/v1/skills` | Elencare le skill accessibili |
| `POST` | `/api/agents/v1/skills` | Creare una skill |
| `GET` | `/api/agents/v1/skills/{id}` | Leggere una skill |
| `PATCH` | `/api/agents/v1/skills/{id}` | Aggiornare una skill |
| `DELETE` | `/api/agents/v1/skills/{id}` | Eliminare una skill |
| `GET` | `/api/agents/v1/skills/{id}/files` | Elencare i file di una skill |
| `GET` | `/api/agents/v1/skills/{id}/files/{path}` | Leggere un file di una skill |
| `PUT` | `/api/agents/v1/skills/{id}/files/{path}` | Creare o sostituire un file di una skill |
| `DELETE` | `/api/agents/v1/skills/{id}/files/{path}` | Eliminare un file di una skill |

```bash
curl -X POST https://your-librechat-instance/api/agents/v1/agents \
  -H "Authorization: Bearer YOUR_MACHINE_ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Release assistant",
    "provider": "openAI",
    "model": "gpt-5.6",
    "instructions": "Prepare concise release notes from verified changes."
  }'
```

Agent payloads take the same fields as the Agent Builder and reject unknown ones; `model` is required on create. Lists take `limit` (1 to 100, default 20) and a `cursor`; when `has_more` is true, pass the returned `after` as the next cursor. File uploads are `multipart/form-data` with one `file` and a `tool_resource` such as `context`, `file_search`, or `execute_code`, subject to the usual upload limits.

Skill create accetta `name`, `description`, `body` e, facoltativamente, `displayTitle`, `frontmatter`, `category` e `alwaysApply`. Gli aggiornamenti devono inviare la versione corrente della skill come `expectedVersion`, in modo che due autori non possano sovrascriversi a vicenda in silenzio.

Gli errori utilizzano i codici `invalid_request`, `not_found`, `permission_denied`, `conflict` e `internal_error`. Una risorsa a cui non puoi accedere può essere restituita come `not_found`. Credenziali errate o mancanti restituiscono `401`.

Se l'amministratore lo abilita, una descrizione OpenAPI delle route di gestione viene servita all'indirizzo `/api/openapi.json`, con la documentazione interattiva disponibile a `/api/docs`. Non copre l'inferenza né gli eventi. Vedi [`openapi`](/docs/configuration/librechat_yaml/object_structure/config#openapi).

## Utilizzo e fatturazione [#usage-and-billing]

Le richieste API vengono conteggiate nel tuo saldo di token esattamente come le chat nell'app. I totali di utilizzo nella risposta includono le chiamate ai subagent, con una suddivisione separata `primary` e `subagent`, oltre ai token di cache e di ragionamento quando il provider li segnala. Vedi [Token Usage](/docs/configuration/token_usage).

## Setup [#setup]

L'API degli agenti è disattivata per gli utenti standard finché un amministratore non concede i permessi Remote Agents al loro ruolo, sia nel [Pannello di amministrazione](/docs/features/admin_panel) sia tramite [`interface.remoteAgents`](/docs/configuration/librechat_yaml/object_structure/interface#remoteagents). Gli amministratori li hanno per impostazione predefinita. L'autenticazione tramite chiave API è attiva per impostazione predefinita; per accettare token dal proprio provider OIDC invece delle chiavi o insieme a esse, consulta [`remoteApi`](/docs/configuration/librechat_yaml/object_structure/agents#remoteapi). L'API di gestione viene configurata separatamente in [`managementApi`](/docs/configuration/librechat_yaml/object_structure/agents#managementapi), mentre le impostazioni per la consegna degli eventi si trovano in [`eventDriven`](/docs/configuration/librechat_yaml/object_structure/agents#eventdriven).
