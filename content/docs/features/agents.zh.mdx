# Agents: 构建自定义 AI 助手 [#agents-build-custom-ai-assistants]

LibreChat 的 AI Agents 功能提供了一个灵活的框架，用于创建由各种模型提供商驱动的自定义 AI 助手。

此功能类似于 OpenAI 的 Assistants API 和 ChatGPT 的 GPTs，但具有更广泛的模型支持和无需代码的实现方式，让您可以构建具备专业能力的复杂助手。

## 入门指南 [#getting-started]

要创建一个新的 Agent，请从 endpoint 菜单中选择“Agents”，并打开侧边栏（Side Panel）中的 Agent Builder 面板。

![Agents - Endpoints Menu](/images/agents/endpoints_menu.png)

创建表单包含：

- **Avatar**: 上传自定义头像以个性化您的智能体
- **Name**: 为您的智能体选择一个独特的名称
- **Description**: 关于您 Agent 用途的可选详细信息
- **Instructions**: 定义代理行为的系统指令
- **Model**: 从可用的提供商和模型中选择
- **Conversation Starters**: 当用户与智能体开始新对话时显示的多达四个建议提示词

**Tools** 和 **Skills** 控件可打开包含内置功能、工具、MCP 服务器、Actions 和 Skills 的可搜索库。选择一个项目进行配置，然后保存该 agent。

**可以通过侧边栏顶部的下拉菜单选择现有的 Agent。**

- **也可以在聊天输入框中使用“@”提及。**

![Agents - Mention](/images/agents/mention.png)

### 工具库 [#tool-library]

Agent Builder 将启用的项目保留在独立的 **Tools** 和 **Skills** 部分中。打开 **Add tools** 以搜索完整目录，或按 **Official**、**Tools**、**MCP** 或 **Actions** 进行筛选。**Made by you** 收集了您创建的 MCP 服务器和 Actions，而 **Favorites** 则保留了已加星标的项目，以便在不同 Agent 之间使用。每位用户最多可保存 100 个工具库收藏。

选择一个项目即可在不离开构建器的情况下对其进行配置。**Create new** 菜单仅在用户拥有创建 MCP 服务器或 Actions 的权限时才会显示。移除基于文件的功能（例如 File Search、File Context 或 Code Interpreter）时，如果仍有需要审核的附加文件，系统会打开其文件管理器。只要基于文件的功能仍拥有文件，它就会保持选中状态并在保存时被保留；在移除该功能本身之前，请先移除或重新分配这些文件。

Skills 使用它们自己的选择器，可以单独选择，也可以作为完整的可访问目录启用。请参阅 [Skills](/docs/features/skills#agent-scope)。

运营商还可以使用实验性的 [Agent Plugins](/docs/features/agent_plugins) 将部署的 Skills 和 MCP 服务器打包到启动时加载的包中。

### 模型配置 [#model-configuration]

模型参数界面允许对您的智能体响应进行微调：

- Temperature (0-1 刻度，用于控制响应的创造性)
- 最大上下文 token 数
- 最大输出令牌数
- 针对原生视觉图像输入的图像细节（`low`、`auto` 或 `high`）
- 其他特定于提供商的设置

智能体指令可以使用 `{{current_date}}`、`{{current_datetime}}` 和 `{{iso_datetime}}`。LibreChat 会从服务器捕获的逻辑轮次开始时间解析这些变量，并在提供商循环、子智能体初始化以及人工介入恢复的过程中保持该时间戳稳定。前两个变量使用请求的时区；`{{iso_datetime}}` 则保持为 UTC 时间。

识别出的 model-not-found 和 provider rate-limit 故障会呈现本地化的指导信息。其他 provider 错误会保留其有用的 provider 文本，但在消息持久化之前会省略 LangChain 故障排除 URL。当启用了 [model-bound content protection](/docs/configuration/librechat_yaml/object_structure/message_filter#source-aware-filters) 时，其通用的受保护错误仍然具有最高优先级。

### 版本历史 [#version-history]

拥有编辑权限的用户可以从 Agent Builder 打开 **Version History**，以在时间轴中查看已保存的配置。每个条目都会显示保存时间，并概述其工具和功能。恢复之前的条目需要确认，并将当前的 Agent 配置替换为该已保存的状态。保存操作始终会应用 Agent 当前的更改，即使生成的配置与最新的历史记录条目匹配，LibreChat 也不会添加重复的条目。

### 对话启动器 [#conversation-starters]

对话启动器为用户提供了一种快速开始与智能体聊天的方式。每个智能体最多可以存储四个启动器。

1. 在 Agent Builder 中，找到 **Conversation Starters** 字段。
2. 输入提示词并按 **Enter** 键，或点击 **+** 按钮。当添加了四个启动项后，输入框将被禁用。
3. 直接编辑已保存的 starter，或点击其 **X** 按钮将其移除。
4. 保存该智能体。

当用户与 Agent 开启新对话时，启动器（starters）会以按钮形式显示在空白聊天界面上。选择其中一个按钮会立即将其作为第一条消息发送。如果 Agent 拥有启动器，它们将优先于当前所用 Model Specs 中定义的 [`conversation_starters`](/docs/configuration/librechat_yaml/object_structure/model_specs#conversation_starters)。启动器也会显示在 Agent 的 [Marketplace](#agent-marketplace) 详情对话框中。

## 智能体功能 (Agent Capabilities) [#agent-capabilities]

> **注意：** 所有功能均可通过 `librechat.yaml` 配置文件进行切换。更多信息请参阅 [docs/configuration/librechat_yaml/object_structure/agents#capabilities](/docs/configuration/librechat_yaml/object_structure/agents#capabilities)。

### Code Interpreter [#code-interpreter]

启用后，Code Interpreter 功能允许您的智能体执行以下操作：

- 在多种语言中执行代码，包括：
  - Python, JavaScript, TypeScript, Go, C, C++, Java, PHP, Rust 和 Fortran
- 通过 LibreChat Code Interpreter API 安全地处理文件
- 无需本地设置、配置或沙盒部署即可运行代码
- 无缝处理文件上传和下载
- [关于 Code Interpreter API 的更多信息](/docs/features/code_interpreter)
  - 由开源 [code-interpreter](https://github.com/ClickHouse/code-interpreter) 服务（自托管）提供支持

当对话中所有必需的 Code Interpreter 文件都无法恢复到当前沙箱时，LibreChat 会在调用模型之前停止 Agent，并要求用户重新附加文件。这可以防止运行过程在引用陈旧或无法访问的文件的情况下继续进行。

当对话文件共享同一个 Code Interpreter 文件名时，LibreChat 会分配不同的沙盒目标路径，并告知 Agent 解析后的路径。有关冲突行为以及多 Agent 私有文件剩余限制的详细信息，请参阅 [无缝文件处理](/docs/features/code_interpreter#seamless-file-handling)。

#### 有状态代码会话 [#stateful-code-sessions]

有状态代码会话允许智能体在多次代码执行中复用沙盒工作区。文件、已安装的包和工作状态通常会保留，这对于迭代分析和多步骤文件处理非常有用。在 Agent Builder 中，**Stateful environment** 选择器用于控制谁可以共享该工作区：

- **用户工作区（推荐）：** 已登录用户的有状态智能体共享同一个工作区
- **Agent + user workspace:** 每个用户为每个 Agent 拥有一个独立的工作区
- **对话工作区：** 每个用户在每次对话中都会获得一个独立的工作区

管理员也可以在 [`statefulCodeSessions.environments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions) 下配置命名后端。当配置存在时，独立的 **Execution environment**（执行环境）选择器将用于选择托管的 Code API、操作员附加的虚拟机或拥有工作区的个人 worker；**Deployment default**（部署默认值）则使用配置的默认可执行环境。上述共享范围与该后端选择保持独立。

当部署启用了自助服务 worker 时，拥有 Code Environment 管理权限的用户可以打开 **Settings > Code environments**，将出站的 `@librechat/code` worker 与其自己的虚拟机（VM）配对，在 Agent Builder 中选择它，并可在稍后撤销。个人环境与所有者绑定，并为代码、Shell 和程序化工具调用（Programmatic Tool Calling）使用相同的路由。有关实验性设置和安全模型，请参阅 [Attached environments and pairing](/docs/features/code_interpreter#attached-environments-and-pairing)。

在附加的工作区内，Agents 可以列出目录、读取文件、搜索文本、创建文件，并通过选定的 worker 运行 Bash。每个 Agent 都可以设置专属的 Git 用户名和邮箱，以便在无需提供仓库凭据的情况下标识在那里提交的记录。部署时可以通过 [`statefulCodeSessions.principalWorkers`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions) 来限制新的个人 worker。

当附加的 worker 通告多个工作区根目录时，聊天编辑器需要为 Agent 或其子 Agent 使用的每个附加环境进行一次选择。对话会在多轮交互和批准恢复期间保留这些选择；LibreChat 会根据实时 worker 对其进行验证，如果缺少必要的工作区或工作区不可用，则会阻止发送。如果 worker 仅通告一个工作区，则会自动为新对话选中该工作区。有关详细信息和当前限制，请参阅 [Attached environments and pairing](/docs/features/code_interpreter#attached-environments-and-pairing)。

新创建的 Agents 最初会使用登录用户在 **Settings > Data Controls > Code execution** 中设置的 **Default stateful workspace**。在更改之前，个人默认设置均为 **User workspace**。更新此偏好设置不会更改现有的 Agents，也不会自动启用 Stateful Code Sessions。管理员可以通过 [`statefulCodeSessions.allowedEnvironments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions) 来限制可用的作用域；当已保存的个人默认设置不再被允许时，新的 Agents 将使用第一个被允许的作用域。

<Callout type="warning" title="高度实验性">
  Stateful Code Sessions 目前处于早期实验阶段。其行为、配置、持久化特性以及底层集成可能会发生重大变化。请勿将当前的实现视为稳定的生产环境契约。
</Callout>

此功能为可选功能。管理员必须将 `stateful_code_sessions` 添加到 [agent capabilities](/docs/configuration/librechat_yaml/object_structure/agents#capabilities) 中，并通过 [`LIBRECHAT_CODE_BASEURL_STATEFUL`](/docs/configuration/dotenv#stateful-code-interpreter-endpoint) 或指定的 [`statefulCodeSessions.environments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions) 配置专用的有状态代码解释器路由。必须在 Agent 上启用代码解释器，并且必须在其高级设置下开启 **Stateful code sessions**。

有状态请求在缺少专用 URL 或不兼容时，不会回退到正常的无状态 Code Interpreter endpoint。有状态会话和无状态会话也不共享实时文件或已安装的包。有状态工作区可能会随时重置，无论其范围如何。在托管的 Code Interpreter 环境中，请将重要输出保存到 `/mnt/data` 下；附加的工作区是一个独立的、由 worker 拥有的目录。聊天上传的文件默认不会复制到该附加目录中。此外，请勿将会话状态作为持久存储使用。

当有状态的 `create_file` 或 `edit_file` 工具在响应期间创建文件时，助手消息会显示一个紧凑的 **Workspace changes** 行。展开该行即可查看已更改的唯一路径，并通过 LibreChat 的身份验证文件流下载每个文件。这是这些工具所创建文件的逐条消息记录，而非完整工作区的持久快照；无状态的 Code Interpreter 输出将继续使用常规的内联附件界面。

对于已连接的环境，composer 可以将 **Ask before changes**（更改前询问）、**Accept edits**（接受编辑）和 **Full access**（完全访问）作为对话级别的代码批准模式进行公开。其可用性受限于环境管理员定义的权限方案；选择更宽松的模式绝不会覆盖角色授权、显式工具规则、钩子或沙盒边界。请参阅 [Attached-environment tool permissions](/docs/features/code_interpreter#attached-environment-tool-permissions)。

### 文件搜索 [#file-search]

File Search 功能支持：

- RAG (Retrieval-Augmented Generation) 功能
- 对上传的文档进行语义搜索
- 基于文件内容的上下文感知响应
- 在 Agent 和聊天会话级别均支持文件附件

### 文件上下文 [#file-context]

File Context 功能允许您的 agent 将从文件中提取的文本存储为其系统指令的一部分：

- 在保持文档结构和格式的同时提取文本
- 处理复杂的布局，包括多栏文本和混合内容
- 处理表格、公式以及其他专业内容
- 处理多语言内容
- 文本存储在数据库中代理的 instructions 中。
- **无需 OCR 服务** - 默认使用文本解析，并提供回退方法
- **由 OCR 增强** - 如果配置了 OCR，图像和扫描文档的提取质量将会提高
- 使用与“作为文本上传”相同的处理逻辑：**OCR > STT > 文本解析**
- [关于 OCR 配置的更多信息](/docs/features/ocr)

**注意：** 文件上下文包含提取到智能体系统指令中的文本。对于单个对话中的临时文档提问，请改用聊天界面中的 [Upload as Text](/docs/features/upload_as_text)。

### Model Context Protocol (MCP) [#model-context-protocol-mcp]

MCP 是一个开放协议，它标准化了应用程序向大语言模型 (LLMs) 提供上下文的方式，充当了 AI 工具和数据源的通用适配器。

有关更多信息，请参阅 [MCP](/docs/features/mcp) 的相关文档。

#### 带有 MCP 工具的 Agents [#agents-with-mcp-tools]

1. 在您的 `librechat.yaml` 文件中配置 MCP 服务器
2. 重启 LibreChat 以初始化连接
3. 创建或编辑一个 Agent
4. 在 Agent Builder 中打开 **Add tools** 并选择 **MCP**
5. 选择您想要添加的 MCP 服务器；每个服务器将作为一个单独的条目显示
6. 保存您对 Agent 所做的更改

在此示例中，我们已将 **[Spotify MCP server](https://github.com/LibreChat-AI/spotify-mcp)** 添加到了一个 agent 中。

![Agents - MCP](/images/agents/mcp_tools_v2.png)

#### 管理 MCP Tools [#managing-mcp-tools]

一旦将 MCP 服务器添加到智能体中，您可以微调哪些特定工具可用：

- 添加 MCP 服务器后，展开它以查看所有可用工具
- 根据需要勾选或取消勾选单个工具
- 例如，Spotify MCP server 提供了约 20 种工具（搜索、播放控制、播放列表管理等）。
- 这种细粒度的控制允许您将智能体限制在仅使用它们所需的工具上。

使用 `{{LIBRECHAT_BODY_*}}` 的请求作用域服务器在聊天运行提供这些值之前无法枚举工具。因此，Agent Builder 会显示一个针对整个服务器的运行时工具选择，而不是每个工具的切换开关；清除该选择将断开服务器连接。OAuth 完成后，LibreChat 会保留授权，并等待第一次符合条件的运行以进行连接。

如果 Agent 明确选择了 MCP 工具，但在运行开始时无法解析任何工具，LibreChat 将停止运行并提供连接和访问指导，而不是在没有这些工具的情况下静默继续。请重新连接或验证服务器身份，检查工具访问权限，然后重试运行。

### 延迟工具 [#deferred-tools]

延迟工具（Deferred tools）允许智能体访问许多 MCP 工具，而无需预先将它们全部加载到 LLM 上下文中。相反，延迟工具可以通过**工具搜索（Tool Search）**机制在运行时被发现。

当代理（agent）可以访问许多拥有数十个工具的 MCP 服务器时，这一点尤其有用——因为加载所有这些工具会消耗大量的上下文窗口，并降低响应质量。

**工作原理：**

- 标记为 "deferred" 的工具将从初始 LLM 上下文中排除。
- 系统会自动添加一个 `ToolSearch` 工具，允许 LLM 按需发现并加载延迟加载的工具。
- 一旦被发现，该工具将在对话的剩余部分中可用。

**配置延迟工具 (deferred tools)：**

1. 打开 Agent Builder 并添加 MCP tools
2. 点击任意 MCP 工具上的下拉菜单
3. 切换“延迟加载” — 延迟的工具会显示一个时钟图标

**注意：** `deferred_tools` 功能默认处于启用状态。可以通过 [`librechat.yaml` 代理配置](/docs/configuration/librechat_yaml/object_structure/agents#capabilities) 进行切换。

### 活动组 [#activity-groups]

活动组（Activity groups）将每个连续的 Agent 推理和工具调用块折叠在生成的单行标题下，使长运行过程更易于浏览。管理员可以通过 `activityLabel` 启用此功能，并可以使用更快的模型、另一个已配置的 endpoint、自定义提示词以及单次运行限制。标题生成是一个独立的模型调用，其 token 和成本会被记录。请参阅 [Agent Activity Groups](/docs/configuration/librechat_yaml/object_structure/shared_endpoint_settings#agent-activity-groups)。

管理员可以独立启用 `activityPhaseLabel`，以便在最终回答之前将两个或多个逻辑活动包装在折叠的父级摘要中。这为长运行提供了更高级别的概要，同时保留了每个子活动。阶段摘要使用其自己的模型、endpoint、提示词和单次运行上限，并会回退到活动标签和运行设置。

一旦连续运行包含至少两个已完成的标记工具组，LibreChat 就会在可选的阶段摘要到达之前，将它们折叠到同一个阶段卡片表面中。最新的已完成子标签将作为临时标题，而实时推理和仍在进行中的工具调用则保留在折叠区域之外。加载的历史记录使用相同的分组方式，后续由服务器生成的阶段摘要将替换临时标题，且不会关闭读者已打开的卡片。

当启用 [Smooth Streaming](/docs/features/smooth_streaming) 时，新生成的父级摘要会将可见的活动平滑地折叠进折叠组中。已加载的历史记录不会重播此过渡效果，且 LibreChat 会遵循设备的“减少动画”偏好设置。

简短的进度文本会保留在其父阶段内。当 Agent 开始生成实质性回答时，LibreChat 会在该文本之前关闭该阶段，以便面向用户的最终结果保持在折叠摘要之外。当后续的推理或工具调用开启另一个逻辑活动块时，单次运行可以创建多个父阶段。当格式错误或缺失的内容部分被压缩时，持久化的阶段边界会进行重置，从而确保在重新加载后分组依然保持对齐。

在阶段内生成的文件会显示在折叠卡片下方的媒体行中，而不是隐藏在卡片内部。使用裸文件名、`/mnt/data/...` 或 `sandbox:` 路径的 Markdown 图像引用会解析为匹配的对话附件。只有当折叠阶段之外的内联图像成功解析时，文件才会被从媒体行中省略，从而在不依赖损坏引用的情况下防止重复。

通用 Agent 和 MCP 工具卡片区分了**准备中 (Preparing)**（SDK 移交前，可能包括审批或其他等待）和**调用中 (Calling)**（SDK 移交至结果）。已完成的卡片会显示这两个时间间隔；调用间隔不一定等于上游 MCP 或 ClickHouse 的执行时长。之前保存的消息以及专门的 Code、Bash、文件和内存卡片保留了清晰标注的**总耗时 (Total elapsed)** 运行步骤时长。已停止、已取消、失败和已完成的步骤会保留不同的状态，即使在重新加载对话后也是如此。

当工具正在运行时，展开的 Bash、Execute Code 和 File Authoring 详细信息面板会跟随流式传输的命令、代码或预览内容滚动到底部。向上滚动将暂停此跟随行为，从而保留当前的阅读位置。

Bash 输出将呈现为终端样式文本。过长的输出会被折叠，仅显示最后 15 行（通常是错误出现的位置）；使用 **Show more** 和 **Show less** 来展开或折叠它，并使用 **Copy** 按钮来复制输出。未打印任何内容的命令会显示 **No output**。对于在 [attached workspace](/docs/features/code_interpreter#attached-environments-and-pairing) 中运行的命令，失败的命令会标注其原因（**exit code N**、**terminated by** 信号如 `SIGKILL`，或 **timed out**），且 stderr 的样式与 stdout 不同。已完成的命令会标注为 **Ran command**，而包含单个调用的工具组会直接展开以显示该调用的详细信息。

### 实时推理标签 [#live-reasoning-labels]

实时推理标签将通用的 **Thinking** 或 **Thoughts** 标题替换为一段简短的导向说明，该说明会随着足够长的顶层推理流而演变。该标签会原地更新现有的推理标题；它不会添加或重新排序消息部分。

最新的实时推理标签和响应计时器在生成过程中会闪烁。已完成的推理、较早的同级响应以及不再处于实时末尾的标签将保持静态。

管理员可通过 `reasoningLabel` 启用此功能，并可选择单独的模型、endpoint、提示词、更新阈值以及单次运行调用上限。每次修订都是一次额外的模型调用，其 token 和成本都会被记录。有关默认值、路由优先级和隐私注意事项，请参阅 [Live Reasoning Labels](/docs/configuration/librechat_yaml/object_structure/shared_endpoint_settings#live-reasoning-labels)。

### 工具意图标签 [#tool-intent-labels]

工具意图标签（Tool intent labels）用模型为特定调用编写的简短描述取代了通用的实时工具状态。管理员必须添加可选的 `tool_intents` [agent capability](/docs/configuration/librechat_yaml/object_structure/agents#capabilities)。原生工具会自动使用标签；在 Agent Builder 中，展开一个 MCP 服务器并为单个工具或整个服务器开启 **Intent label**。

对于 Model Specs，[`describeIntent`](/docs/configuration/librechat_yaml/object_structure/model_specs#describeintent) 可以启用所有符合条件的工具，或选择已解析的工具 ID。Intent 字段会添加到发送给模型的工具 schema 中，因此选择性启用可以减少 schema 的 token 开销。

意图标签（Intent labels）不适用于仅限编程的 MCP 工具，因为在沙盒代码内进行的调用不会渲染单独的工具卡片。扩展后的编程执行会显示其内部调用的紧凑实时追踪。

### 程序化工具调用 [#programmatic-tool-calling]

程序化工具调用 (PTC) 允许智能体从 [Code Interpreter](/docs/features/code_interpreter) 沙盒内部执行选定的 MCP 工具，而不是直接从模型调用每个工具。模型会接收一个由 Code Interpreter 支持的编排工具，编写沙盒代码来调用生成的工具函数，并可以在返回答案之前使用循环、条件判断、重试和结果处理。

这对于多步工具工作流非常有用，例如查询多个资源、对结果进行分页、比较输出，或在智能体解释工具响应之前对其进行转换。

**配置编程工具：**

1. 在 [`librechat.yaml` agents capabilities](/docs/configuration/librechat_yaml/object_structure/agents#capabilities) 中同时启用 `programmatic_tools` 和 `execute_code`。
2. 在智能体上启用 Code Interpreter。
3. 添加 MCP 工具，扩展 MCP 服务器，并为单个工具或整个服务器切换 **Programmatic**（编程）模式。编程工具会显示一个代码图标。

在选择 Code Interpreter 之前，Agent Builder 会保持 Programmatic 开关为禁用状态。移除 Code Interpreter 会立即清除该 Agent 的 Programmatic 选择。在创建、更新、复制和版本恢复时，如果 `execute_code` 功能或 Code Interpreter 工具不可用，服务器也会自动剔除 programmatic 调用者选项；这使得旧的、不一致的 Agents 可以在不保留不可用配置的情况下被打开并修正。

**注意：** `programmatic_tools` 为可选功能，默认不包含在智能体能力列表中。PTC 还需要部署带有 Tool Call Server 组件的 Code Interpreter。在运行时，LibreChat 会将当前的调用者能力投影与其受信任的工具注册表进行交集运算，因此事件数据可以缩小可用映射范围，但不能授予工具权限。只有处于活动状态且已注册的 programmatic_tools 才能从沙盒中调用；未注册的调用将被拒绝。

在程序化运行期间展开 Code Interpreter 卡片，即可查看每个内部工具调用的终端风格追踪记录，包括其参数预览、状态、持续时间以及任何失败信息。该追踪记录仅在当前浏览器会话中实时显示，页面刷新后不会恢复。

### 后台工具调用 [#background-tool-calls]

后台工具调用允许智能体启动一个长时间运行且符合条件的 Code Interpreter、MCP、Plugin 或 Action 工具，并继续执行其他任务。初始调用会立即返回一个任务引用。对于已保存的 Agent，受支持的补全内容默认会自动通过后续的延续操作进行交付；`check_background_task` 仍然可用于显式查询状态、控制、收集工件以及恢复任务。

`check_background_task` 会在进程本地任务运行时报告 `started_at` 和当前的 `elapsed_ms`。任务结算后，它还会报告 `settled_at` 并将 `elapsed_ms` 固定在完成时的持续时间。当原始的进程本地调度时间戳不可用时，从持久化存储中恢复的最终结果可能仅包含 `settled_at`，而不包含开始时间和经过时长。

要使用此功能，管理员必须添加选择加入的 `run_in_background` [agent capability](/docs/configuration/librechat_yaml/object_structure/agents#capabilities)。然后在 Agent Builder 中配置符合条件的工具：

- **Code Interpreter:** 在智能体上启用 Code Interpreter。代码执行和 shell 命令默认符合后台运行条件；若要禁用，请在其工具设置中关闭 **Background execution**。
- **MCP:** 打开一个 MCP 服务器，并将单个工具或整个服务器标记为 **Background**。
- **插件工具：** 打开一个符合条件的工具并开启 **Background execution**。
- **操作 (Actions)：** 为一个操作开启 **后台执行 (Background execution)**，即可选择加入该操作中所有符合条件的任务。OAuth 操作不会显示此开关。当操作自身的 schema 已经定义了 `run_in_background` 参数时，该操作也会被排除，以避免与 LibreChat 的调度标志发生冲突。

这些设置允许后台执行，但不会强制执行。模型会针对每次调用自行决定是否在后台运行符合条件的工具。

在 LibreChat 聊天中，当后台代码执行完毕时，其 stdout 和生成的文件会显示在原始代码调用处，而不是后续的轮询中。生成的文件也会被持久化以供后续轮次使用。自动续写功能会将完成的工作呈现在一个可折叠的唤醒任务卡片中，并链接到原始任务。

当服务器在之前的后台运行结束后启动该延续任务时，打开的对话会附加到新的生成任务上，并刷新已完成的任务输出，而无需重新加载。

除非管理员设置了 [`endpoints.agents.backgroundTasks.completionWakeups: false`](/docs/configuration/librechat_yaml/object_structure/agents#backgroundtasks)（这将恢复为仅轮询行为），否则自动完成唤醒功能处于启用状态。主机可能会将多个符合条件的纯内容完成任务合并为一次延续。生成实时工件的任务仍然需要对拥有该运行的进程进行轮询。

管理员还可以选择启用所有者范围内的取消功能，配置项为 [`endpoints.agents.backgroundTasks.ordinaryToolCancellation: true`](/docs/configuration/librechat_yaml/object_structure/agents#backgroundtasks)。该任务会报告已请求取消，直到底层调用结束，且在此期间其容量保持占用状态。取消是协作式的：忽略中止信号的工具仍可能成功完成。此控制适用于普通的进程内后台工具（包括已附加的 Bash），但不适用于独立拥有的已分离子代理（Subagents）。

只有符合条件的工具才会公开此设置。普通的后台执行是进程局部的，且无法在工作进程丢失后存活。然而，一旦仅包含内容的终端结果被持久化，自动交付就是持久的，并可能在另一个副本上继续。进程局部注册表限制了每个对话、用户和进程中正在运行的任务及保留的结果负载；它会在安全时驱逐已完成的工作，并在挂起的处理阻止安全驱逐时返回作用域容量结果。如果调用忽略了取消请求，LibreChat 将在中止后的一分钟宽限期后停止续订其生产者租约，并停止自动完成交付，而不会错误地将不确定的外部工作标记为超时。分离式子代理（Detached Subagents）使用单独的持久任务和记录路径，并配有 Redis 路由的实时控制；请参阅 [分离式子代理线程](/docs/features/subagents#detached-subagent-threads)。

### 询问用户与工具批准 [#ask-user-and-tool-approval]

**Ask User** 工具允许智能体暂停运行，以请求缺失的信息、提供选项或确认后续操作。一次调用最多可组合四个相关问题。LibreChat 每次显示一个问题，并提供“上一步”、“下一步”以及可点击的进度步骤；在步骤间切换时，已填写的答案会保留，单选答案在选择后会自动推进而无需提交。“提交”按钮会在所有问题都得到回答后的最后一步出现，而“跳过”按钮则可在任何步骤拒绝整批问题。每个问题都接受自由文本回答，或智能体提供的单选/多选选项。当模型准备调用时，LibreChat 会将问题流式传输到进度卡片中；准备就绪后，交互式表单将替换该卡片。提交后，同一运行将携带完整的答案映射恢复执行。您可以从 Tools 市场添加 **Ask User**；管理员可以移除默认的 `ask_user_question` 功能以将其隐藏。

折叠多问题卡片会将输入框恢复为正常的引导或排队模式，而暂停的卡片将保留在对话中。该卡片仍然可以被展开、回答、跳过或停止。单问题暂停模式将继续使用聚焦的输入框回答模式。

提交的答案会随恢复操作一同持久化，因此在恢复运行初始化时停止操作不会丢弃已接受的答案。

在问题记录稳定后，它默认会折叠为单行工具条目，以免长答案占据过多的对话记录空间。您可以将其展开以查看问题以及答案中保留的换行符。现有的 **Auto-expand tool details** 首选项同样控制此稳定视图；当仍需要输入时，实时表单将保持打开状态。

每个问题均可包含一个最多 80 个字符的可选标题、最多 2,000 个字符的问题文本、最多 4,000 个字符的可选支持性上下文，以及最多 12 个选项。选项标签限制为 280 个字符，选项值限制为 500 个字符，每个提交的答案限制为 16,000 个字符。

管理员还可以要求在匹配的工具调用运行前进行审核。根据工具的不同，用户可以批准、拒绝、编辑参数或直接响应。暂停的运行会被设置检查点，以便在做出决定后可以恢复，包括在使用默认 MongoDB 检查点时在另一个副本上恢复。部署范围内的工具批准默认处于禁用状态，而使用附加代码环境的 Agent 会接收 [ask-by-default 安全策略](/docs/features/code_interpreter#attached-environment-tool-permissions)，除非管理员明确将其禁用。请参阅 [`toolApproval` 和 `checkpointer`](/docs/configuration/librechat_yaml/object_structure/agents#toolapproval)。

当 Composer 审查面板因待处理的审批而打开时，相应的对话卡片会以记录形式显示请求，而不是重复显示决策按钮。请在消息框上方的面板中查看调用并选择 **Continue**。从 Composer 芯片折叠面板会恢复对话卡片的控件并保留您的决策；重新打开它则会将审查权交还给面板。其他操作的卡片将保留其各自的控件。

### Skills [#skills]

Skills 允许智能体从 `SKILL.md` 定义中加载可重用的指令。它们可以通过在聊天中输入 `$` 手动选择，由模型通过技能目录自动发现，或者在每一轮对话中始终应用。Agent Builder 还支持独立的运行时创作：智能体可以在不接收现有目录的情况下创建 Skill，或者在用户拥有相应权限时编辑已选定的 Skills。

有关创作、调用和访问控制的详细信息，请参阅 [Skills](/docs/features/skills)。

### Memory [#memory]

**Memory** 工具允许智能体在用户明确要求记住或忘记某事时，保存、更新或删除结构化的用户记忆。必须为部署配置 Memory，并由用户的角色和个性化设置允许，且在智能体上启用该功能。

默认情况下，Agent 使用用户共享的个人记忆池。开启 **Keep memories separate for this agent** 可为其提供每个用户、每个 Agent 独立的私有分区。该隔离的 Agent 将无法查看现有的共享记忆或其他隔离 Agent 创建的记忆。用户可以在“记忆”面板中按个人记忆或特定于 Agent 的记忆进行筛选。读取、创建或更新 Agent 分区需要当前对该 Agent 的访问权限；删除操作仍可在 Agent 被移除后清理其分区。请参阅 [User Memory](/docs/features/memory#agent-memory)。

### Artifacts [#artifacts]

Artifacts 功能使您的 agent 能够生成并显示交互式内容：

- 创建 React 组件、HTML 代码和 Mermaid 图表
- 在聊天旁边的专用面板中显示内容，该面板可以展开为全屏，或在单独的浏览器窗口中打开
- 在 Agent 级别配置特定于 Artifact 的指令
- [关于 Artifacts 的更多信息](/docs/features/artifacts)

启用后，请选择以下三种指令模式之一：

- **Normal**: 添加针对 React、HTML、SVG、Markdown 和 Mermaid 的标准 artifact 指令。
- **shadcn/ui**：添加了标准说明以及使用 shadcn/ui 组件库构建界面的指南。
- **Custom**：保持 Artifact 渲染功能开启，但不注入任何内置的 Artifact 指令，从而让智能体自身的指令拥有完全的控制权。

在 Agent 级别配置 artifacts 是首选方法，因为它相比传统的全局配置提供了更细粒度的控制。

如果您选择 **Custom**，请至少在您的指令中包含基本的 artifact 格式。

以下是一个所需最小指令的简单示例：

````md
When creating content that should be displayed as an artifact, use the following format:

:::artifact{identifier="unique-identifier" type="mime-type" title="Artifact Title"}

```
Your artifact content here
```

:::

For the type attribute, use one of:

- "text/html" for HTML content
- "application/vnd.mermaid" for Mermaid diagrams
- "application/vnd.react" for React components
- "image/svg+xml" for SVG images
````

### Handoffs [#handoffs]

Handoffs 允许主要 agent 将对话转移给具有相关上下文的专家 agent。在 **Advanced settings** 中，打开 orchestration 部分并添加最多 10 个 handoff agents。每个配置的 handoff 都会创建一个 transfer tool，当需要专家 agent 的专业知识时，模型可以动态选择该工具。

对于每次移交，您可以添加一段描述，帮助模型选择合适的专家。您还可以提供传递指令（passthrough instructions），描述主代理应为专家生成什么内容，并可选择将 `instructions` 参数重命名为其他名称。移交功能在 Agent Builder 中始终可用；与 Agent Chain 和 Subagents 不同，它们不需要启用 endpoint 功能。来自可达移交代理的工具调用在后续对话中保持结构化，因此提供商接收到的是有效的工具调用历史记录，而非扁平化的文本。

### Agent Chain [#agent-chain]

Agent Chain 功能支持代理混合 (Mixture-of-Agents, MoA) 方法，允许您创建一系列协同工作的代理：

- 为复杂任务创建专业智能体链
- 链中的每个 agent 都可以访问先前 agent 的输出
- 配置代理链的最大步数
- **注意：** 从 Agent Builder 中的 Advanced Settings 面板访问此功能。
- **注意：** 此功能目前处于测试阶段，可能会有所变动
  - 当前可链接的智能体最大数量为 10 个，但未来可能会支持配置。

此功能为 LibreChat 引入了分层的 Mixture-of-Agents 架构，其中每个智能体都将上一层所有智能体的输出作为辅助信息来生成其响应，正如 [同名“Mixture-of-Agents”论文](https://arxiv.org/abs/2406.04692) 中所述。

### 子代理 (Subagents) [#subagents]

Subagents 允许 Agent 将特定的任务委托给独立的子运行或已保存的 Agent 团队。每个子任务都会获得隔离的上下文和工具执行环境，随后仅向父级返回精简的结果，而不会用所有中间步骤填满父级的上下文。分离的子任务工作也会被保留为可导航、只读的对话线程。

子代理（Subagents）与代理链（Agent Chain）不同：代理链将多个代理作为图的参与者进行协调，而子代理则是由代理作为工具调用（tool call）生成的，用于范围受限的委托。LibreChat 保留了可达子节点和已保存团队成员在后续轮次中所需的结构化工具调用历史记录，同时将不可用的工具排除在当前运行之外。有关设置和限制，请参阅 [Subagents](/docs/features/subagents)。

### 高级设置 [#advanced-settings]

代理的高级设置（位于代理表单的“高级”视图中），不包含“能力”（capabilities）部分。

#### 最大代理步骤 (Max Agent Steps) [#max-agent-steps]

此设置允许您限制代理在一次“运行”（run）中可以采取的步骤数量，这指的是在给出最终响应之前的代理循环。

如果未进行配置，默认值为 25 步，但您可以根据需要进行调整。对于管理员，您可以在 [`librechat.yaml`](/docs/configuration/librechat_yaml/object_structure/agents#recursionlimit) 文件中设置全局默认值以及全局最大值。

当一个回合用尽其完整的步骤预算时，LibreChat 会保留部分响应和工具调用，而不是用错误信息替换它们。该消息提供 **Keep going**（继续），它将以新的工具预算开启一个新回合；以及 **Answer now**（立即回答），它要求智能体根据已完成的工作进行回答，不再使用更多工具。关闭该通知仅影响当前的浏览器视图。

管理员还可以通过 [Agent stream circuit breakers](/docs/configuration/librechat_yaml/object_structure/agents#stream-circuit-breakers) 来限制流式工具调用参数和模型增量事件。

“步骤”（step）是指一次 AI API 请求或一轮工具使用（根据 LLM 在单次请求中提供的工具调用数量，可能涉及 1 个或多个工具）。

单次非工具响应为 1 步。单轮工具使用通常为 3 步：

1. API 请求 -> 2. 工具使用（1 个或多个工具） -> 3. 后续 API 请求

## 文件管理 [#file-management]

Agents 支持多种处理文件的方式：

### 在聊天界面中 [#in-chat-interface]

与智能体聊天时，你有四种上传选项：

1. **上传图片**
   - 上传图片以实现对原生视觉模型的支持
   - 将图像直接发送给模型提供商

2. **作为文本上传** (需要 `context` 功能)
   - 在对话中提取并包含完整的文档内容
   - 默认使用文本解析；如果已配置，则通过 OCR 增强。
   - 内容仅存在于当前对话中
   - 请参阅 [Upload as Text](/docs/features/upload_as_text)

3. **用于文件搜索的上传**（需要 `file_search` 功能，且已开启）
   - 使用带有向量存储的语义搜索 (RAG)
   - 通过工具使用返回相关数据块
   - 非常适合大型文档/多个文件
   - 对于结构化数据（CSV、Excel、JSON 等）效果不佳

4. **代码解释器上传**（需要 `execute_code` 功能，并已开启）
   - 将文件添加到代码解释器环境
   - 最适合处理结构化数据（CSV、Excel、JSON 等）
   - 更多关于 [Code Interpreter](/docs/features/code_interpreter) 的信息

### 在 Agent Builder 中 [#in-agent-builder]

在配置 Agent 时，您可以附加不同类别的文件：

1. **图像上传**：用于智能体可以引用的视觉内容
2. **文件搜索上传 (File Search Upload)**：用于 RAG 功能的文档
3. **Code Interpreter Upload**: 用于代码处理的文件
4. **文件上下文**: 包含提取文本的文档，用于补充 Agent 指令

**File Context** 使用 `context` 功能，其工作方式与 ["Upload as Text"](/docs/features/upload_as_text) 完全相同——默认使用文本解析，并在配置后通过 OCR 增强。文本在上传时被提取并存储在 agent 的指令中。这非常适合为 agent 提供来自文档、PDF、代码文件或包含文本的图像的持久知识。

**处理优先级：** OCR > STT > 文本解析（与“作为文本上传”相同）

**注意：** 提取的文本将作为智能体系统指令的一部分包含在内。

## 共享与权限 [#sharing-and-permissions]

Agents 使用 LibreChat 的细粒度 [access control](/docs/features/access_control) 系统。每个 Agent 都有其自己的访问控制列表 (ACL)，并且可以与特定的 **users**、**groups**、**roles** 共享，或者 **publicly**（公开）共享，每种共享方式都可以设置特定的权限级别。

受信任的服务也可以通过测试版 [Agent Management API](/docs/features/agents_api#agent-management-api) 管理 Agent、附加文件和 Skills。管理员将每个 OIDC 机器客户端绑定到一个现有的 LibreChat 用户和租户；每个请求都会继承该用户当前的角色权限和资源 ACL，而不是获得单独的管理员访问权限。

### 访问角色 [#access-roles]

当共享 Agent 时，受让人会被分配以下三种角色之一：

| 角色 | 被授权者可以做什么 |
| ---------- | ----------------------------------------------------------------------------------------------------- |
| **Viewer** | 在对话中使用该 agent；无法打开构建器，也无法查看指令、工具或附件 |
| **Editor** | 查看 + 修改该 agent 的指令、模型、工具和文件 |
| **Owner**  | 完全控制：查看、编辑、删除和重新共享该 agent |

无论 ACL 如何设置，原始作者和管理员始终保留完全控制权。

### 共享 Agent [#sharing-an-agent]

1. 在 Agent Builder 中打开该 agent
2. 点击页脚中的 **Share** 按钮（当你是创建者、管理员，或已被授予该特定 agent 的 `SHARE` 权限时可见）
3. 在人员选择器中搜索用户、组或角色，并为每个对象分配一个角色
4. 您可以选择性地切换 **Public**（公开）开关，使该 Agent 对实例上的所有用户可见（需要 `SHARE_PUBLIC` 功能权限）。

智能体卡片和落地页视图会显示配置的支持联系人。当未设置支持联系人时，LibreChat 可以回退显示第一个可解析的所有者的显示名称，但除非明确配置为支持联系人，否则不会公开所有者的电子邮件地址。

对话界面将 Agent 作为可见身份，而不会回退到其底层模型或 Model Specs 标签。

有关主体、权限位以及 ACL 如何与基于角色的功能权限组合的完整详细信息，请参阅 [Access Control](/docs/features/access_control)。

### Agent Marketplace [#agent-marketplace]

**Agent Marketplace** 允许用户浏览可用的 Agent。从侧边栏中的 **Agent Marketplace** 打开它；该入口仅对角色被允许使用 Marketplace 的用户可见。

- **浏览与搜索**：智能体以网格形式显示。使用搜索栏按名称或描述查找智能体，并使用分类标签（例如 **精选 (Top Picks)**、**全部 (All)** 或特定类别）来筛选列表。
- **排序**：使用 **排序方式** 按 **最新优先**（默认）、**最早优先**、**热门**（置顶次数最多）或 **按创建者名称** 对智能体进行排序。
- **我的智能体**：开启**我的智能体**以仅显示您创建的智能体。从**精选推荐**中开启此项会切换回**全部**。
- **可共享视图**：搜索、排序和 **My agents** 筛选器会保留在页面 URL 中（`?q=`、`?sort=`、`?mine=1`），因此筛选后的视图可以被收藏或共享。

选择一张智能体卡片以打开其详情对话框，其中会显示完整的描述和智能体的联系方式，以及以下操作：

- **固定**或**取消固定**：将智能体添加至您的已固定智能体，或从中移除。
- **复制链接**：复制一个可启动与该智能体进行新对话的链接。
- **Start Chat**: 开启与代理的新对话。
- **尝试对话启动器**：当智能体拥有 [conversation starters](#conversation-starters) 时，选择其中一个即可开启新对话，该提示词将预先填入消息输入框中。它不会自动发送，因此你可以先进行编辑。

管理员可以通过 [`interface.marketplace`](/docs/configuration/librechat_yaml/object_structure/interface#marketplace) 设置以及 [访问控制](/docs/features/access_control) 中描述的角色权限来控制访问权限。

### 管理员控制 [#administrator-controls]

管理员可以在 agent builder UI 中访问全局权限设置：

- 启用/禁用所有用户的智能体共享功能
- 控制 Agent 使用权限
- 管理智能体创建权限
- 配置平台范围的设置

在非作用域的单租户部署中，为该实例创建的第一个账户即为管理员。租户作用域部署不会自动提升其第一个注册用户；请通过受信任的管理流程配置租户管理员。如果您需要手动添加管理员，可以[访问 MongoDB](/docs/configuration/mongodb/mongodb_auth) 并更新用户的个人资料：

```
db.users.updateOne(
  { email: 'USER_EMAIL_ADDRESS' },
  { $set: { role: 'ADMIN' } }
)
```

也可以通过配置禁用所有用户的代理功能，[更多信息](/docs/configuration/librechat_yaml/object_structure/interface)。

功能级权限（谁可以_使用_、_创建_、_共享_或_公开共享_ Agent）可在 [**LibreChat Admin Panel**](/docs/features/admin_panel) 中针对每个角色（包括任何自定义角色）进行管理。`librechat.yaml` 中的 [`interface.agents`](/docs/configuration/librechat_yaml/object_structure/interface#agents) 代码块仍然可以在启动时为内置的 `USER` 角色设定默认值，但建议今后通过管理面板进行编辑。

### 用户级共享 [#user-level-sharing]

个人用户可以：

- 与特定用户、群组或角色共享他们的 Agent（如果其角色已启用 `SHARE` 功能）
- 使智能体对实例上的所有人可见（如果启用了 `SHARE_PUBLIC`）
- 为每位接收者授予不同的访问权限（Viewer / Editor / Owner）
- 随时可以通过共享对话框重新共享或撤销访问权限

## 引导与排队消息 [#steering-and-queued-messages]

当 Agent 正在响应时，你可以通过以下两种方式从 [composer](/docs/features/composer) 发送另一条消息：

- **Steer** 会将消息插入到当前运行的下一个工具或智能体步骤中，以便智能体在完成工作前进行调整。
- **Queue** 会保留该消息，并在当前响应完成后将其作为正常的后续轮次发送。

对于当前服务器上已保存的 Agent 对话，普通的排队后续消息会存储在 MongoDB 中。LibreChat 会保留其先进先出 (FIFO) 的顺序，并在浏览器断开连接、应用重启和副本切换时，保留其文本、附件、引用的摘录以及手动选择的 Skills。处理过程会等待前一个响应完成后，再进行下一轮对话。这种持久性是自动实现的，无需 YAML 或环境变量开关；较旧的服务器以及没有活动生成纪元 (generation epoch) 的短启动窗口将保留客户端兼容性队列。

服务器准入在每个对话队列通道内进行序列化处理。如果前序证据或混合版本所有权不明确，LibreChat 将显示 **Awaiting reconciliation**（等待协调），并阻止或终止受影响的排队轮次，而不是进行猜测并导致乱序启动。

**Steer sooner** 要求智能体在下一个安全点接收消息，而不是等待下一个工具步骤。如果此时还没有可保留的回答文本或工具活动，LibreChat 会等待一段短暂的宽限期，丢弃静默或仅推理的尝试，插入消息，并使用该指令重启模型。一旦可以保留回答文本，LibreChat 会在提供商的安全边界处停止，保留部分响应，插入消息，并恢复相同的助手响应。正在运行的工具调用不会被 steering 丢弃或中断；该消息将在相关工作达到安全边界时生效。

使用 **Stop** 来结束正在进行的推理并请求取消前台工具调用。Stop 会将取消信号转发给支持信号的前台工具；分离的后台任务将保持其独立的生命周期。请使用专用的编辑器控件，从发送按钮菜单中选择它，或按下 `Command/Ctrl + Shift + .`。当部署无法中断活动的提供商流时，该操作将回退为普通的引导控制。

在 **Settings → Chat** 中，**While generating, Enter will** 用于选择默认操作。发送按钮菜单可以覆盖单条消息的该选择，而 **Steer sooner on Enter** 则会在启用引导（steering）作为默认操作时，让 Enter 键请求更早的安全点。

文件和 [引用摘录](/docs/features/message_actions#quote-excerpts) 会随 steer、queue 和 interrupt 消息一同传输。手动选择的 Skills 会保持在暂存状态以供下一次完整轮次使用，而不是附加在运行中的 steer 消息上。

待处理的 steer 会出现在流式回复的末尾，即它们最终落位的地方，直到服务器将其插入运行中。其接收状态会从 **Sending**（发送中）变为 **Delivered**（已送达），接着是 **Steer sooner requested**（已请求提前引导，当请求了更早的安全点时），最后变为 **Applied**（已应用），并在行内消息的右下角显示双勾号。确认已应用的接收回执在页面重新加载后，以及在分享或搜索视图中依然可见；不确定或发送失败的 steer 不会显示确认勾号。一旦确认，消息菜单可以回收该 steer 进行编辑、将其转换为排队的后续消息，或者取消它并将文本和附件恢复到输入框中。LibreChat 会避免覆盖更新的草稿；如果输入框已不可用，它会将回收的消息保留在队列中。失败的 steer 仍可进行重试、编辑、排队或移除。

排队的后续消息会显示在输入框上方的一个列表中。每一条消息都可以进行编辑（**Edit message**）、移除（**Remove message**）、通过 **Send now** 立即发送，或者通过拖动其句柄或按键盘上的箭头键进行重新排序。在运行仍处于活跃状态时，排队的后续消息也可以转换为引导（steer），或者通过 **Steer sooner** 进行升级。正在运行的引导在等待工具边界时也提供相同的升级选项。移除服务器支持的排队消息时，会先取消其持久化源，并在可能的情况下将其恢复为空的输入框。如果前序响应被中止或失败，LibreChat 会将受影响的排队轮次标记为失败以供审查，而不是静默发送。

一个对话最多可以有 100 个处于排队状态的活跃轮次。每个排队轮次最多可接受 16,000 个字符和 10 个文件。另外，一个活跃运行最多可接受 10 个待处理的引导（steer）；每个引导最多可包含 10 个文件，并受 [`STEER_MAX_LENGTH`](/docs/configuration/dotenv#agent-conversation-controls) 限制。**立即引导（Steer sooner）** 继续使用实时引导路径，而不是将排队轮次移动到持久化 FIFO 队列的最前端。

基于 Redis 的多副本部署会自动协商 generation protocol v2。在从早于 `v0.8.8-rc1` 的版本升级时，请遵循 [generation protocol compatibility guidance](/docs/configuration/redis#generation-protocol-compatibility)。

### 注意事项 [#notes]

- 只有拥有编辑权限的用户才能查看指令、模型参数、附加文件和工具。
  - Agent 可能会通过对话泄露任何附加的数据（无论是指令还是文件），因此在授予 Editor/Owner 权限或将 Agent 公开之前，请确保您的指令能够有效防范此类风险。
- 只有原始作者、管理员以及拥有所有者权限的被授权人才能删除共享的 Agent。
- 除非已共享，否则 Agent 仅对作者本人可见。

## 代理事件交付 [#agent-event-delivery]

LibreChat 包含一个用于异步 Agent 事件的源中立交付层。部署拥有的适配器可以将经过验证的 webhook、队列消息、MCP 事件、通道事件或内部产品事件标准化为新的 Agent 运行 (`fire`)、现有已保存 Agent 和分支上的新轮次 (`continue`)，或对活动运行的变更 (`steer`)。适配器负责验证其原生来源、清理有效负载，并在入队前选择受信任的目标。

测试版 [Agents API 事件端点](/docs/features/agents_api#agent-events) 为 Remote Agents API 密钥提供了经过身份验证的 `fire`、`continue` 和 `steer` 访问权限。外部系统可以将源参与者（source actor）绑定到直接子 Agent，并在跨事件中延续该参与者，而无需额外的功能开关。LibreChat 从 API 密钥中获取用户、租户和源身份，强制执行 Agent 访问和内容过滤器，并要求提供幂等性密钥。这不是一个未经身份验证的通用 Webhook 接收器；特定于提供商的适配器在调用它之前仍必须验证原生 Webhook 签名。

实验性的 [Scheduled Chats](/docs/features/scheduled_chats) 功能是 LibreChat 在此层级上的首个内置生产者。它为已保存的 Agents 创建周期性的 `fire` 投递，且在管理员选择启用之前处于禁用状态。分离的 Subagents 会自动使用幂等的 `continue` 投递，以便在子 Agent 完成任务后唤醒已保存的父 Agent；已取消的子 Agent 和临时的父 Agent 将被排除在外。

MongoDB 存储有界版本化信封、幂等键、排序通道、租约、重试历史记录、持久回执和死信。Worker 使用带有围栏声明和有界指数退避的至少一次投递机制；成功的回执在 90 天后过期，而死信则需要显式的受信任重新排队。Fire 投递会创建新的对话。Continue 投递会在确切的对话分支上创建新的轮次，并在该分支运行、暂停或结束时进行延迟处理。绑定 Actor 还有一个自动邮箱：一个 Actor 会等待其当前轮次的处理结果，然后再分发下一个事件，而不同的 Actor 可以并行运行。Steer 投递必须识别现有的对话和生成，并使用严格的准入机制，以确保模糊的重试不会两次注入相同的指令。

对于绑定延续（bound continuations），传输成功会启动一个独立的持久化处理生命周期。交付状态会从 `started` 演变为 `applied`、`completed_no_action`、`failed` 或 `cancelled`。源可以要求使用 `expectedAction` 指定确切的工具和可选的参数子集；LibreChat 仅在观察到主机匹配的工具执行证据时才会报告 `applied`，绝不会根据模型生成的文本进行报告。兼容的观测事件可以共享一个有界的 `coalesce.key` 批次，同时为每个源事件保留一条幂等记录和回执。在兼容时使用检查点延续，否则将回退到持久化消息历史记录。

绑定事件参与者（Bound Event Actors）可以在“询问用户”（Ask User）或工具审批时暂停，并通过 LibreChat 的常规人机交互界面恢复精确的签名参与者调用。参与者的邮箱将保持阻塞状态，直到该暂停恢复或处理完毕，从而防止后续事件覆盖当前的决策。这些参与者需要使用持久化的 MongoDB 检查点（checkpointer）。LibreChat 会根据参与者状态和请求能力自动选择检查点延续或持久化历史记录重建；现有的 protocol-v1 工作将保留在历史路径上，直到其处理完毕。

由事件参与者（Event Actors）启动的独立操作（Detached Actions）在内置生成存储（generation store）宣告支持时会自动启用。参与者将保持挂起状态，直到终端证据（terminal evidence）恢复其原始调用，因此仅后台启动并不能满足 `expectedAction`。内存存储在进程存活期间保持此生命周期的一致性。Redis 增加了持久化的重启恢复和副本切换功能。能力所属的完成工作在混合版本排空（mixed-version drain）期间与旧工作进程隔离；操作员无需通过功能标志（feature flag）来选择此行为。

执行主机通常会调用当前进程绑定的监听器。仅当此受信任的内部准入路径必须穿过另一个 HTTP 源（例如 TLS 前端）时，才配置 [`endpoints.agents.eventDriven.selfUrl`](/docs/configuration/librechat_yaml/object_structure/agents#eventdriven)。

2. 打开 Agent Builder 面板

## 需要迁移 (v0.8.0-rc3+) [#migration-required-v080-rc3]

<Callout type="warning" title="重要提示：需要进行 Agent 权限迁移">
  从 v0.8.0-rc3 版本开始，LibreChat 为 agent 使用了基于访问控制列表 (ACL) 的新权限系统。如果您是从早期版本升级，则必须运行 agent 权限迁移，以确保现有的 agent 仍然可以访问。
</Callout>

### 迁移执行的操作 [#what-the-migration-does]

代理权限迁移将您的代理从简单的所有权模型转换为具有多个权限级别的复杂的基于 ACL 的系统：

- **OWNER**: 对 Agent 的完全控制权
- **EDITOR**: 可以查看并修改该 Agent
- **VIEWER**: 对 Agent 的只读访问权限

如果不运行此迁移，现有的 Agent 将无法通过新的具备权限感知能力的 API endpoint 进行访问。

### 运行迁移 [#running-the-migration]

根据您的部署方式选择相应的命令：

#### 1. 对于默认的 `docker-compose.yml`（如果您使用 `docker compose up` 来启动应用）： [#1-for-the-default-docker-composeyml-if-you-use-docker-compose-up-to-start-the-app]

**预览更改（试运行）：**

```bash
docker compose exec api npm run migrate:agent-permissions:dry-run
```

**执行迁移：**

```bash
docker compose exec api npm run migrate:agent-permissions
```

**自定义批处理大小（针对大型数据集）：**

```bash
docker compose exec api npm run migrate:agent-permissions:batch
```

#### 2. 针对 `deploy-compose.yml` [#2-for-the-deploy-composeyml]

如果您按照 [Ubuntu Docker Guide](/docs/remote/docker_linux) 操作：

**预览更改（试运行）：**

```bash
docker exec -it LibreChat-API /bin/sh -c "cd .. && npm run migrate:agent-permissions:dry-run"
```

**执行迁移：**

```bash
docker exec -it LibreChat-API /bin/sh -c "cd .. && npm run migrate:agent-permissions"
```

**自定义批处理大小（针对大型数据集）：**

```bash
docker exec -it LibreChat-API /bin/sh -c "cd .. && npm run migrate:agent-permissions:batch"
```

#### 3. 用于本地开发（从项目根目录）： [#3-for-local-development-from-project-root]

**预览更改（试运行）：**

```bash
npm run migrate:agent-permissions:dry-run
```

**执行迁移：**

```bash
npm run migrate:agent-permissions
```

**自定义批处理大小（针对大型数据集）：**

```bash
npm run migrate:agent-permissions:batch
```

### 迁移过程中会发生什么 [#what-happens-during-migration]

- **私有 Agent**：仅对其创建者可见（获得 OWNER 权限）
- **共享智能体 (Shared Agents)**：如果一个智能体之前已被共享，它将作为公共智能体（共享给所有用户）接收相应的 ACL 条目。
- **系统检测**：LibreChat 会在启动时自动检测未迁移的智能体并显示警告

您可以通过 Agent Builder UI 调整生成的智能体权限。

<Callout type="info" title="注意">
  同样的迁移过程也适用于 prompts。如果您还有现有的 prompts，请使用相同的命令运行 prompt 权限迁移，但需将命令名称中的 `agent` 替换为 `prompt`。
</Callout>

## 下一步是什么？ [#whats-next]

LibreChat Agents 为该应用开启了一个新时代，未来可以通过针对特定任务和工作流程的 Agents 来简化您在 LibreChat 中的使用体验。

未来的更新将包括：

- 对当前 Agent 体验的常规改进
- 用于复杂工作流的多智能体编排
- 能够为各种功能自定义 Agent：标题生成（聊天会话命名）、记忆管理（用户上下文/历史记录）以及提示词增强（输入辅助/预测）
- 更多工具，可配置的工具参数，动态工具创建。

此外，此次更新为 LibreChat 引入了一种全新的范式，其底层架构为应用程序提供了急需的更新，在优化用户体验的同时也提升了整体应用性能。

为了强调一项显著的优化，使用传统 endpoint（在撰写本文时，指 Agents 和 AWS Bedrock 之外的任何 endpoint 选项）生成约 1000 个 token 的 AI 内容，将传输约 1 MB 的数据。

使用 Agent 时，同样的生成过程仅会传输约 52 kb 的数据，数据传输量减少了 95%，这大大减轻了服务器和用户设备的负载。
