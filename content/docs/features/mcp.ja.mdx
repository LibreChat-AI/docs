Model Context Protocol (MCP) は、アプリケーションが大規模言語モデル（LLMs）にコンテキストを提供する方法を標準化するオープンプロトコルです。MCPは**「AIのUSB-C」**のようなものだと考えてください。USB-Cが電子機器に対して普遍的な接続規格を提供するのと同様に、MCPはAIモデルを多様なツール、データソース、およびサービスに接続するための標準化された方法を提供します。

LibreChatはMCPを活用することで、AIエージェントの機能を劇的に拡張し、ファイルシステムへのアクセスやWebブラウザ、専門的なAPIからカスタムビジネスツールに至るまで、あらゆるものを統合できるようにします。

## なぜ MCP が重要なのか [#why-mcp-matters]

LLMsは組み込みの機能に制限されています。MCPを使用することで、LibreChatは以下の方法でこれらの壁を取り払います：

- **MCPサーバー**を提供するあらゆるツールやサービスへの接続
- **統合の標準化**により、ツールごとにLibreChatのコードを編集する必要がなくなります
- **マルチユーザー環境のサポート**（適切な認証と分離機能付き）
- **実行時にサーバーを追加および更新する**（設定ファイルや再起動なしで、MCP設定パネルから直接行えます）

## LibreChatにおけるMCPの仕組み [#how-mcp-works-in-librechat]

LibreChatでは、MCPサーバーを使用する方法として、チャットエリア内での使用とエージェントとの使用の2通りを提供しています。

MCPサーバーは、`librechat.yaml`ファイルで手動設定するか、[smithery.ai](https://smithery.ai)を使用してMCPサーバーを検索し、`librechat.yaml`にインストールすることができます（[以下の例](#basic-configuration)を参照）。`librechat.yaml`でサーバーを追加または編集するたびに、接続を初期化するためにLibreChatを再起動する必要があります。[MCP設定パネル](#adding-mcp-servers-in-the-ui)から追加されたサーバーは、再起動なしで反映されます。パネルで作成されたOAuthを使用するサーバーは、保存時に登録されますが、最初は切断された状態です。[接続して認証](#step-3-check-connection-status-and-authenticate)を行ってください。

### OAuth コールバック URL [#oauth-callback-url]

OAuthが有効なMCPサーバーの場合、LibreChatのコールバックURLは以下の通りです：

```text
${DOMAIN_SERVER}/api/mcp/<server-name>/oauth/callback
```

`<server-name>` は、`librechat.yaml` 内の `mcpServers` で使用されるキー、または MCP 設定 UI で作成されたサーバー名です。例えば、`DOMAIN_SERVER=https://chat.example.com` を持つ `salesforce` という名前のサーバーの場合、`https://chat.example.com/api/mcp/salesforce/oauth/callback` を使用します。

この正確なコールバックURLをOAuthプロバイダーに登録してください。ローカルのDockerインストールでは、通常ベースURLとして `http://localhost:3080` を使用します。

### チャットエリア内 [#in-chat-area]

![コンポーザーパレットから開かれたMCP Serversカタログ。各サーバーの接続状態が表示されている](/images/mcp/mcp_servers_catalog.png)

LibreChatは、従来のendpoint（OpenAI、Anthropic、Google、Bedrockなど）を使用する際、設定済みのMCPサーバーをチャットエリアに直接表示します：

- 最初にエージェント以外のendpointを選択し、ツール対応モデルを選択してください。
- MCPサーバーは、[コンポーザーの **+** パレット](/docs/features/composer#turn-on-tools-skills-and-mcp-servers)の **MCP Servers** セクションに表示され、選択された各サーバーはコンポーザー上にチップとして表示されます。
- 選択すると、そのサーバーのすべてのツールが現在のモデルで使用可能になります。
- エージェントを作成することなくMCPツールに素早くアクセスでき、複数のサーバーを同時に使用可能

MCPサーバーを通常のチャット選択から除外するには、設定で [`chatMenu: false`](/docs/configuration/librechat_yaml/object_structure/mcp_servers#chatmenu) を指定します：

```yaml
mcpServers:
  internal-tools:
    command: npx
    args: ['-y', 'internal-mcp-server']
    chatMenu: false # Not selectable in regular chat
```

この設定はチャットリクエストおよびピッカーの両方に適用されるため、古い保存済み選択項目が非表示のサーバーを使用し続けることはできません。これは、保存されたAgentや、明示的にサーバーを割り当てているModel Specsからサーバーを削除するものではありません。また、LibreChatは、ユーザーが認証されたAgentを通じてのみアクセス可能なサーバーを、通常のチャットピッカーおよびリクエストパスから除外します。

### エージェントを使用する場合 [#with-agents]

MCPサーバーはLibreChatのAgentとシームレスに統合されます：

1. エージェントを作成または編集する
2. Agent Builderで **Add tools** を開き、**MCP** を選択します。
3. MCPサーバーを選択します。各サーバーは単一のカタログエントリとして表示されます。
4. 選択したサーバーを展開して、個々のツールを有効または無効にします
5. エージェントを保存

![Agent Builder内のMCPツール](/images/mcp/mcp_ui_agent.png)

この高レベルな構成により、インターフェースが整理された状態に保たれます。20以上のツールを持つサーバー（Spotifyなど）であっても単一のエントリとして表示され、展開することで詳細な制御が可能です。

### 基本設定 [#basic-configuration]

`librechat.yaml` ファイルに MCP サーバーを手動で追加します：

```yaml
mcpServers:
  # ClickHouse Cloud
  clickhouse-cloud:
    type: streamable-http
    url: https://mcp.clickhouse.cloud/mcp

  # File system access
  filesystem:
    command: npx
    args:
      - -y
      - '@modelcontextprotocol/server-filesystem'
      - /path/to/your/documents

  # Web browser automation
  puppeteer:
    command: npx
    args:
      - -y
      - '@modelcontextprotocol/server-puppeteer'

  # Production-ready cloud service
  business-api:
    type: streamable-http
    url: https://api.yourbusiness.com/mcp
    headers:
      X-User-ID: '{{LIBRECHAT_USER_ID}}'
      Authorization: 'Bearer ${API_TOKEN}'
    timeout: 30000
    serverInstructions: true
```

### UIでMCPサーバーを追加する [#adding-mcp-servers-in-the-ui]

設定ファイルを編集したりサーバーを再起動したりすることなく、LibreChatのインターフェースから直接MCPサーバーを追加および設定することも可能です。

右側のサイドバーから **MCP Settings** パネルに移動します。ここに既存の MCP サーバーが一覧表示されており、**+** ボタンから新しいサーバーを追加できます。

![MCP 設定パネル](/images/mcp/mcp_ui_settings_panel.png)

#### Step 2: サーバーの詳細を入力する [#step-2-fill-out-server-details]

**+** ボタンを押し、MCPサーバー名、説明、URL、トランスポートタイプ、認証方法を入力してから、**Create** をクリックします。

![Add MCP Server Dialog](/images/mcp/mcp_ui_configure.png)

新しいサーバーがMCP設定パネルに表示され、確認のトースト通知が表示されます。

![MCP Server Created Successfully](/images/mcp/mcp_ui_success_registered.png)

#### ステップ 3: 接続ステータスを確認して認証する [#step-3-check-connection-status-and-authenticate]

新しいサーバーの[接続ステータスインジケーター](#connection-status-indicators)を確認してください。サーバーがOAuth認証を必要とする場合、ステータスは切断済みとして表示されます。コンポーザーの **+** パレットでMCPサーバーを選択し、認証フローを開始してください。

![Connection Status - Disconnected](/images/mcp/mcp_ui_unconnected.png)

開始されると、ステータスインジケーターが更新され、認証が進行中であることが表示されます。

![Connection Status - Authenticating](/images/mcp/mcp_ui_authenticating.png)

#### ステップ 4: OAuth で続行する [#step-4-continue-with-oauth]

LibreChatは**Connect**の確認プロンプトを表示します。宛先を確認し、**Continue with OAuth**を選択して、ブラウザの新しいタブでプロバイダーの認証ページを開きます。そこでプロバイダーのサインインおよび同意フローを完了してください。

このブラウザで開始されたフローが保留中の場合、LibreChatはキャッシュされた接続ステータスが**Connected**と表示されていても、そのサーバーを認証中/接続中の状態に維持します。古いステータスが永続的な認証を報告しているという理由だけでプロンプトを閉じるべきではありません。保留中のフローは、最終的な成功、失敗、タイムアウト、またはキャンセルによって終了します。別のタブやブラウザで開始されたフローには、このビューにおけるローカルな保留状態は存在しません。

![OAuth Continue Prompt](/images/mcp/mcp_ui_callback_confirm.png)

#### ステップ 5: 認証成功 [#step-5-authentication-successful]

認証が完了すると、成功の確認画面が表示されます。このウィンドウは自動的に閉じられ、LibreChatにリダイレクトされます。

![Authentication Successful](/images/mcp/mcp_ui_success_redirect.png)

#### ステップ 6: サーバーの使用準備完了 [#step-6-server-ready-for-use]

LibreChatは認証の成功を認識し、会話内で使用するMCPサーバーを自動的に選択します。サーバーは接続済みステータスインジケーターを表示し、コンポーザー上で選択されたチップとして表示されます。

![MCP Server Authenticated and Auto-Selected](/images/mcp/mcp_ui_done.png)

新しいMCPサーバーはAgent Builderでも利用可能であり、そこから任意のエージェントにツールを追加したり、許可するツールのサブセットをカスタマイズしたりすることができます。

![MCP Server Available in Agent Builder](/images/mcp/mcp_ui_agent.png)

#### UIで作成されたサーバーの認証情報変数 [#credential-variables-for-ui-created-servers]

UIを通じてMCPサーバーを追加する際、ユーザーに独自のAPIキーの入力を求めることができます。MCP Server BuilderダイアログのAuthenticationセクションで「API Key」を選択し、**「User provides key」**にチェックを入れます。ヘッダー形式（Bearer、Basic、またはCustom）を選択してサーバーを保存してください。

舞台裏では、LibreChatは `MCP_API_KEY_<hash>` という名前の宛先バインドされた `customUserVars` エントリを作成し、一致する認証ヘッダーを構成します。名前は自動的に管理されますが、ユーザーは引き続きMCPツール選択ダイアログまたはMCP設定パネルでキーを入力します。既存のサーバーは、リクエスト境界が変更されない限り、レガシーな `MCP_API_KEY` 名を保持する場合があります。これは、[YAMLで定義された `customUserVars`](#user-provided-credentials) と同じキー入力UIを使用します。

UIで作成されたサーバーのURL（パスやクエリを含む）、プロキシ、トランスポート、認証形式、カスタム認証ヘッダー、または設定済みのOAuthクライアント/送信先を変更する場合、各ユーザーは新しい境界に対してキーを入力する必要があります。以前に保存されたキーは、その置き換えられた送信先には転送されません。見た目上の編集、等価な正規化URL、およびフラグメントのみの送信URLの編集では、既存のキーが保持されます。共有サーバーは現在の設定で宣言された資格情報変数のみを解決できるため、エディタは以前のキーを復元するために古い生成名を参照することはできません。一括での資格情報移行は不要です。この保護機能に依存する前に、サーバー編集リクエストを処理するレプリカを含む**すべてのAPIレプリカ**をアップグレードしてください。古いライターは、依然としてバインドされていない設定を再作成できてしまう可能性があります。

管理者またはユーザーのAPIキーが設定されている場合、LibreChatはサーバーをAPIキー認証済みとして扱い、OAuthの自動検出をスキップします。明示的なOAuth設定が依然として優先されます。古いLibreChatバージョンで作成・保存されたUI作成のAPIキーサーバーが**OAuth Required**のまま動かなくなった場合は、サーバーを一度編集して保存し、保存されている接続メタデータを更新してください。

<Callout type="warning">
セキュリティ上の理由から、UIで作成された（DBソースの）MCPサーバーは、`customUserVars` プレースホルダー（`{{VAR_NAME}}`）**のみ**を解決できます。サーバー側の環境変数（`${ENV_VAR}`）、ユーザープロファイルフィールド（`{{LIBRECHAT_USER_*}}`）、およびOIDCトークン（`{{LIBRECHAT_OPENID_*}}`）は、サーバーのシークレットや他のユーザーのデータへの不正アクセスを防ぐために意図的にブロックされています。すべてのプレースホルダーをサポートするには、代わりに `librechat.yaml` でサーバーを設定してください。
</Callout>

## MCP Server Management [#mcp-server-management]

LibreChatは、接続ステータスの追跡、およびUI内でのOAuth認証と初期化サポートを備えた、MCPサーバー接続を管理するための包括的なツールを提供します。

### 接続ステータスインジケーター [#connection-status-indicators]

LibreChatは、コンポーザーの **+** パレットおよび設定パネルにおいて、各MCPサーバーの現在の状態を示す動的なステータスアイコンを表示します：

![MCP Server Status Icons](/images/mcp/mcp_server_status_icons.png)

**ステータスタイプ:**

- **Connected** (緑色の歯車): サーバーは接続されており、設定可能な customUserVars を持っています
- **OAuth Required** (amber key): サーバーはOAuth認証を必要とします
- **Disconnected**（オレンジ色のプラグ）：サーバー接続に失敗したか、接続が切断されました
- **Initializing** (青いローダー): サーバーが起動中、または再接続中です
- **エラー** (赤い三角形): サーバーでエラーが発生しました
- **キャンセル** (赤い x): OAuth フローがキャンセルされています

### エージェントツールダイアログからのOAuthのキャンセル [#cancelling-oauth-from-the-agent-tool-dialog]

**Agent Builder → Tool Library → MCP server configuration** において、共有サーバーマネージャーがキャンセル可能なOAuthフローを報告している間、**Connect** は有効な **Cancel** アクションに切り替わります。これには、別の LibreChat パネルから検出された保留中のフローも含まれます。**Cancel** を選択すると、そのフローを停止し、ローカルのOAuthプロンプトを閉じ、保留中のツール自動選択をクリアします。キャンセル後に接続結果が遅れて届いた場合でも、このダイアログでツールが自動的にアタッチされることはありません。再度 **Connect** を選択することで、新しい試行を行うことができます。キャンセル不可能な初期化処理の場合は、キャンセルアクションではなく、無効化されたビジー状態が表示されます。

### サーバーの初期化 [#server-initialization]

インターフェースから直接MCPサーバーを初期化または再初期化できます：

**ワンクリック:**

- コンポーザーの **+** パレットにある **MCP Servers** セクションでサーバーを選択することで、ワンクリックで初期化できます。

  <Video src="/videos/mcp_one_click_init.mp4" title="ワンクリックMCP初期化" />

**MCPConfigDialog より:**

- コンポーザーの **+** パレットにある MCP サーバーの行で **Configure** を選択し、MCPConfigDialog を開きます。
- カスタムユーザー変数を設定し、サーバーの認証タイプに応じて「Authenticate/Initialize」ボタンをクリックします。

       <Video src="/videos/mcp_config_dialog_auth.mp4" title="MCP設定ダイアログの認証" />

  **MCP設定パネルから:**

- MCP Settings Panelのサーバーリストセクションにある任意のサーバーをクリックして、設定および初期化コントロールにアクセスします。
- カスタムユーザー変数を設定し、サーバーの認証タイプに応じて「Authenticate/Initialize」ボタンをクリックします。

  <Video src="/videos/mcp_settings_init.mp4" title="MCP設定パネルの初期化" />

初期化エラーにおいて、サーバーへの到達不能、`customUserVars` の欠落、再認証が必要なOAuth接続、および一般的な初期化エラーが区別されるようになりました。再試行する前に、メッセージ内に指定された不足変数を使用するか、再認証アクションを実行してください。これらのケースにおいて、サーバーを削除して再追加する必要はなくなりました。

パッシブカタログの読み込みは、OAuthの検出試行を統合し、失敗後には段階的にバックオフを行うため、切断された統合がリクエストのたびに検出を再試行することはありません。認証情報の変更はレプリカ間で世代ごとにフェンシング（保護）されるため、古い検出結果が新しい認証を上書きすることはありません。オペレーターは [`mcpSettings.catalogRecovery`](/docs/configuration/librechat_yaml/object_structure/mcp_settings#catalogrecovery) で制限付きリカバリポリシーを調整できますが、デフォルト設定はほとんどのデプロイメントに適しています。

エージェントが明示的にMCPツールを必要としているにもかかわらず、実行開始時にツールを解決できない場合、LibreChatはそれらのツールなしで黙って実行するのではなく、接続およびアクセスに関するガイダンスを表示して実行を失敗させます。

`notifications/tools/list_changed` を送信する MCP サーバーは、LibreChat を再起動することなくツールカタログを更新できます。LibreChat はライブ接続から現在のリストを取得し、追加されたツールを公開し、サーバーが削除したツールの広告を停止します。再接続時にも、接続が準備完了と見なされる前にカタログが同期されます。管理されたスナップショットの更新とコールドサーバーの検出は、プロセス全体で共通の3操作ゲートを共有します。一度許可されると、各操作はツールリストまたはサーバーごとの検出期限（短い方の `initTimeout` を含む）によって制限されるため、低速なカタログ処理がスロットを無期限に占有することはありません。

ストリーミング可能なHTTPサーバーの場合、サーバーが古いセッションの古いスタンドアロンSSEストリームを保持していると、再接続時に一時的にHTTP `409` が返されることがあります。LibreChatはこれを一時的なものとして扱い、古いセッションを破棄して自動的に接続を再構築します。復旧が成功した場合、オペレーターによる操作は不要です。再構築された接続も失敗した場合、LibreChatは引き続き根本的な接続エラーを表示します。

LibreChatは、ストリーミング可能なHTTPレスポンスを、部分文字列の一致ではなく、解析された `Content-Type` メディアタイプに基づいて分類します。パラメータによって非SSEレスポンスを `text/event-stream` であるかのように見せかけることはできないため、レスポンスサイズの制限エラーは、適切なSSEまたは非SSEの処理パスを通じて継続されます。

### MCP 設定パネルの表示設定 [#mcp-settings-panel-visibility]

LibreChatが初期化中にユーザーの介入を必要とする可能性のあるMCPサーバーを検出すると、MCP設定パネルが右側のサイドバーに表示されます。設定されたサーバーがいずれかの基準を満たしている場合、このパネルが表示されます：

- **Custom User Variables**: サーバーには、ユーザーが提供した認証情報を含む可能性のある `customUserVars` が定義されています。
- **OAuth Authentication**: 起動時にサーバーがOAuth認証を必要としていることが検出されました
- **手動初期化**: サーバーが `startup: false` に設定されているため、手動での初期化が必要です。

## LibreChat固有の機能 [#librechat-specific-features]

LibreChatのMCP実装は、高度に設定可能で、実世界のマルチユーザー環境向けに設計されています。

### ユーザー固有の接続 (User-Specific Connections) [#user-specific-connections]

- 各ユーザーは、MCPサーバーへの独自の分離された接続を取得します。
- ユーザー認証と権限が尊重されます
- 個人データとコンテキストは非公開のまま保持されます

### MCPサーバーの共有 [#sharing-mcp-servers]

MCPサーバーは、LibreChatの[きめ細かなアクセス制御](/docs/features/access_control)システムに参加します。`librechat.yaml`で定義されたサーバー（管理者が管理し、[`interface.mcpServers`](/docs/configuration/librechat_yaml/object_structure/interface#mcpservers)機能の権限によって制御されます）に加え、ユーザーが作成したMCPサーバーには独自のACLがあり、特定の**ユーザー**、**グループ**、**ロール**、または**公開**に対して、閲覧者（Viewer）、編集者（Editor）、または所有者（Owner）レベルで共有できます。

`interface.mcpServers` 配下の `USE`、`CREATE`、`SHARE`、および `SHARE_PUBLIC` フィーチャーフラグは、MCPサーバーの作成および共有を誰に許可するかを制御します。権限レイヤーの構成方法については、[Access Control](/docs/features/access_control) を参照してください。

### 動的なユーザーコンテキスト [#dynamic-user-context]

MCPサーバーは、**URLおよびヘッダー**内のプレースホルダーを通じてユーザー情報にアクセスできます（SSEおよびStreamable HTTPトランスポートの場合）：

```yaml
mcpServers:
  user-api:
    type: streamable-http
    url: https://api.example.com/users/{{LIBRECHAT_USER_USERNAME}}/mcp
    headers:
      X-User-ID: '{{LIBRECHAT_USER_ID}}'
      X-User-Email: '{{LIBRECHAT_USER_EMAIL}}'
      X-User-Role: '{{LIBRECHAT_USER_ROLE}}'
      Authorization: 'Bearer ${API_TOKEN}'
```

利用可能なプレースホルダーは以下の通りです：

- `{{LIBRECHAT_USER_ID}}` - 一意のユーザー識別子
- `{{LIBRECHAT_USER_EMAIL}}` - ユーザーのメールアドレス
- `{{LIBRECHAT_USER_ROLE}}` - ユーザーロール (admin, user など)
- `{{LIBRECHAT_USER_USERNAME}}` - ユーザー名
- その他多数（完全なリストについては、[MCP Servers Configuration](/docs/configuration/librechat_yaml/object_structure/mcp_servers#headers) を参照してください）

YAMLで定義されたMCPサーバーでは、`{{LIBRECHAT_OPENID_*}}`、`{{LIBRECHAT_GRAPH_*}}`、および`{{LIBRECHAT_BODY_*}}`のプレースホルダーも使用できます。`{{LIBRECHAT_BODY_*}}`の値はリクエストスコープであるため、LibreChatはアクティブな実行のために接続を作成し、その実行内のツール呼び出し間でそれらを再利用し、リクエスト終了時にクリーンアップします。リクエストスコープのサーバーは永続的なツールキャッシュから除外されるため、リクエスト固有のヘッダーやURLがアクティブな実行外で再利用されることはありません。チャットリクエストが存在する前にツールリストを解決できないため、Agent Builderはサーバー全体に対して1つのランタイムツール選択を公開し、実行時にツールを解決します。OAuthを完了すると認証情報は保存されますが、最初の実行でリクエストコンテキストが提供されるまで接続は延期されます。User、OpenID、およびGraphのプレースホルダーはユーザースコープであり、HTTPトランスポートはそれ自体で再接続を必要とすることなく、各ツール呼び出しの前に解決済みのヘッダーを更新します。

信頼されたオペレーターは、YAMLで定義されたリモートサーバー上で `Authorization: 'Bearer {{LIBRECHAT_OPENID_ACCESS_TOKEN}}'` を使用することで、ユーザーのライブOpenIDアクセストークンをパススルーできます。明示的なMCP OAuth、代理（on-behalf-of）交換、および管理者APIキー認証が優先されます。`401` または `403` エラーが発生した後、LibreChatは接続を一度だけ再試行できますが、拒否されたツール呼び出しを自動的に再実行することはありません。設定およびセキュリティに関するガイダンスについては、[MCPサーバープレースホルダーのリファレンス](/docs/configuration/librechat_yaml/object_structure/mcp_servers#headers)を参照してください。

`{{LIBRECHAT_GRAPH_ACCESS_TOKEN}}` は、Microsoftのon-behalf-ofフローを通じてユーザーの再利用可能なOpenIDアクセストークンを交換します。[`GRAPH_API_SCOPES`](/docs/configuration/dotenv#microsoft-graph-api--entra-id-integration) は、要求するスコープをスペース区切りで設定し、デフォルト値は `https://graph.microsoft.com/.default` です。これは、ユーザーやグループの検索を設定する `OPENID_GRAPH_SCOPES` とは独立しています。

`{{LIBRECHAT_BODY_PARENTMESSAGEID}}` プレースホルダーは、ネイティブの Agent チャット、OpenAI 互換の Agents API 呼び出し、およびレガシーな Assistants の実行に対して値が入力されます。Open Responses には同等の親メッセージ ID が存在せず、MCP サーバーがその値を要求した場合は失敗（fails closed）します。詳細は [MCP サーバーのプレースホルダーリファレンス](/docs/configuration/librechat_yaml/object_structure/mcp_servers#headers) を参照してください。

### Server Instructions [#server-instructions]

`serverInstructions` は、MCPサーバーのツールが選択された際に、設定された指示を動的に追加するLibreChatの機能です。

```yaml
mcpServers:
  filesystem:
    command: npx
    args: ['-y', '@modelcontextprotocol/server-filesystem', '/docs']
    serverInstructions: |
      When accessing files:
      - Always check file permissions first
      - Use absolute paths for reliability
      - Handle errors gracefully
```

オプション:

- `true`: 利用可能な場合はサーバーによってアドバタイズされた指示を使用します
- `false`: 指示を無効化
- `string`: カスタム指示をそのまま（上記のように）使用します

LibreChatは、この設定された宣言を、サーバーの検査中に取得された指示とは別に保持します。したがって、`true`の宣言は検査やキャッシュされたレジストリの再読み込みの間も有効なままとなり、カスタム文字列は引き続き権威あるものとして扱われます。

### タイムアウト設定 [#timeout-configuration]

長時間実行されるMCP操作については、初期化とツール操作の両方に対して適切なタイムアウトを設定してください。

```yaml
mcpServers:
  data-processor:
    type: streamable-http
    url: https://api.example.com/mcp
    initTimeout: 15000 # 15 seconds for server initialization
    timeout: 60000 # 60 seconds for tool operations
```

**注意**: 操作が途中で中断される場合は、プロキシ設定（nginx、traefikなど）を確認してください。デフォルトのタイムアウト設定により、接続が早期に切断されている可能性があります。

ユーザーがフォアグラウンドの Agent ツール呼び出し中に **Stop** を押すと、LibreChat は実行キャンセルシグナルを MCP に転送します。Streamable HTTP サーバーの場合、MCP SDK は `notifications/cancelled` を送信します。サーバーは自身の作業を停止するために、その通知を尊重する必要があります。デタッチされたバックグラウンド呼び出しは意図的に個別のライフサイクルを維持しており、フォアグラウンドのターンと一緒にキャンセルされることはありません。

### ユーザー提供の認証情報 [#user-provided-credentials]

`customUserVars` を通じて、ユーザーがMCPサーバー用の独自の認証情報を入力できるように設定できます。これにより、設定ファイルに認証情報を保存することなく、ユーザー固有の安全な認証が可能になります。

```yaml
mcpServers:
  my-api-server:
    type: streamable-http
    url: 'https://api.example.com/mcp'
    headers:
      X-Auth-Token: '{{MY_API_KEY}}' # Uses the user-provided value
    customUserVars:
      MY_API_KEY:
        title: 'API Key'
        description: "Enter your personal API key from <a href='https://example.com/keys' target='_blank'>your account settings</a>"
```

ユーザーはこれらの認証情報を設定できます：

- **チャットエリアから**: コンポーザーの **+** パレットにある、設定可能な MCP サーバーの行で **Configure** を選択します。
- **MCP設定パネルから**: 右側のパネルにある「MCP Settings」にアクセスして、設定済みのすべてのサーバーの認証情報を管理します。

#### ユーザー認証情報を使用した MCP サーバーの再初期化 [#reinitializing-mcp-servers-with-user-credentials]

使用前にユーザー固有の認証情報が必要なMCPサーバー（例：[GitHub公式MCPサーバー](https://github.com/github/github-mcp-server)の `PAT_TOKEN` など）について、LibreChatでは、アプリケーション全体を再起動することなく、UI内からこれらの認証情報を提供し、MCPサーバーを再初期化することができます。

1. `customUserVars`を使用するMCPを選択すると、MCPパネル内から選択したMCPサーバーの`customUserVar`の値を**保存**または**取り消し**できるようになります。
2. `customUserVar` の値を保存した後、再初期化ボタン（MCPパネル内の各サーバー名の横にある、円形の矢印アイコン）をクリックしてください。
3. LibreChatは、提供された認証情報を使用してサーバーへの接続を試み、再初期化プロセスが成功したか失敗したかをトースト通知でお知らせします。

> _ヒント: サーバーが初回起動時に利用できない認証情報を必要とすることがわかっている場合は、その設定に `startup: false` を追加できます。これにより、UI上で手動で再初期化されるまで、LibreChatはそのサーバーへの接続を試みないようになります。_

**例:**

```yaml
mcpServers:
  github-mcp:
    type: streamable-http
    url: 'https://api.githubcopilot.com/mcp/'
    headers:
      Authorization: '{{PAT_TOKEN}}'
    customUserVars:
      PAT_TOKEN:
        title: 'GitHub PAT Token'
        description: 'GitHub Personal Access Token'
    startup: false
```

### OAuth 認証 [#oauth-authentication]

LibreChatは、Anthropicの安全なMCP接続に関する推奨事項に従い、MCPサーバーのOAuth認証をサポートしています。OAuthは、長期的な認証情報を保存することなく認証を行うための、標準化された安全な方法を提供します。

#### サポートされている OAuth フロー [#supported-oauth-flows]

LibreChat MCP servers support OAuth 2.0 with:

- **Authorization Code Flow with PKCE**: 最大限のセキュリティのために推奨
- **クライアント検出**: OAuthプロバイダーがサポートしている場合、自動的にクライアント登録を行います
- **Refresh Tokens**: 利用可能な場合の自動トークン更新
- **トークンエンドポイントの検出**: 事前に設定されたクライアントは、プロバイダーがクライアント資格情報をPOSTボディで期待しているか、HTTP Basic認証ヘッダーで期待しているかを検出できます。

MCP Builderでは、**Token Exchange Method**（トークン交換メソッド）として **Auto**、**Default (POST request)**、**Basic authorization header** を選択できます。**Auto** を選択するとメソッドは未設定のままとなり、LibreChatが信頼されたプロバイダーのメタデータを使用します。プロバイダーがメソッドを通知しない場合は、Basic認証にフォールバックします。

#### 設定例 [#configuration-examples]

```yaml
mcpServers:
  # Public remote MCP server for PayPal, uses OAuth Client Discovery
  # ❌ Refresh Tokens: you may need to re-authenticate periodically
  # More info: https://developer.paypal.com/tools/mcp-server/
  paypal:
    type: 'sse'
    initTimeout: 150000 # higher timeout to allow for initial authentication
    url: 'https://mcp.paypal.com/sse'

  # Example self-hosted remote MCP server for Spotify, uses OAuth Client Discovery
  # ✅ Refresh Tokens: refreshes token for authentication automatically
  # Hosted on Cloudflare Workers, more info: https://github.com/LibreChat-AI/spotify-mcp
  spotify:
    type: 'streamable-http'
    initTimeout: 150000
    url: 'https://mcp-spotify-oauth-example.account.workers.dev/mcp'
```

#### OAuth 認証フロー [#oauth-authentication-flow]

OAuthが有効なMCPサーバーを初めて設定する際は、以下の通りです：

1. **初期接続**: LibreChatはMCPサーバーへの接続を試みます
2. **認証が必要**: 有効なトークンが存在しない場合、コンポーザーの **+** パレット内にそのサーバーのOAuth認証ステータスが表示されます。
3. **サインインを開始**: サーバーを選択してOAuthフローを開始します
4. **続行するか、別のデバイスを使用する**: 現在のブラウザで続行するか、認証リンクをコピーするか、QRコードを表示して別のデバイスで開きます
5. **ブラウザリダイレクト**: OAuthプロバイダーでの認証を完了します
6. **Return Handling**: LibreChatは、認証が完了すると自動的にOAuthコールバックを処理します。
7. **トークンストレージ**: LibreChatは将来の使用のためにトークンを安全に保存します
8. **接続が確立されました**: 認証が完了すると、MCPサーバーが接続され、チャットで使用できるようになります。

#### OAuth コールバック URL [#oauth-callback-url-1]

MCPサーバーがOAuthを使用する場合、LibreChatは認証成功後にOAuthプロバイダーがリダイレクトするコールバックendpointを公開します。

コールバックURLは以下の形式に従う必要があります：

`${baseUrl}/api/mcp/${serverName}/oauth/callback`

`${serverName}` は、`librechat.yaml` 設定で定義された MCP サーバーキーです。LibreChat はこの endpoint でリダイレクトを処理し、トークン交換を完了させ、認証情報を対応する MCP サーバーに関連付けます。

<Callout type="info" title="OAuthコールバックURLの例">
以下のMCPサーバー設定を前提とします：

```yaml
mcpServers:
  # Example self-hosted remote MCP server for Spotify, uses OAuth Client Discovery
  # ✅ Refresh Tokens: refreshes token for authentication automatically
  # Hosted on Cloudflare Workers, more info: https://github.com/LibreChat-AI/spotify-mcp
  spotify:
    type: 'streamable-http'
    initTimeout: 150000
    url: 'https://mcp-spotify-oauth-example.account.workers.dev/mcp'
```

コールバックURLは `${baseUrl}/api/mcp/spotify/oauth/callback` となります。

</Callout>

注:

- フローを機能させるには、コールバックURLをOAuthプロバイダーに正確に登録する必要があります。
- `/api/oauth/callback` や `/api/oauth/openid/callback` といった他のパスは、MCP OAuth フローでは無効です。

#### トークン管理 [#token-management]

LibreChatはOAuthトークンをインテリジェントに処理します：

- **安全なストレージ**: トークンは暗号化され、安全に保存されます
- **自動更新**: リフレッシュトークンが利用可能な場合、LibreChatは期限切れのアクセストークンを自動的に更新します。
- **Silent 401 Recovery**: OAuth MCP接続がセッション中に認証拒否を受け取った場合、LibreChatはユーザーおよびサーバーごとに1回限りの制限付きリフレッシュと再接続の試行を調整します。同時実行されている呼び出し元は、LibreChatが新しい認証プロンプトを表示する前に、そのリカバリ結果を共有します。
- **セッション管理**: 各ユーザーは、マルチユーザー環境向けに独自のOAuthセッションを保持します

保存されたAgentのストリームが、MCPの承認プロンプトが保留中の状態で再読み込みまたは再開された場合、LibreChatはそのプロンプトを永続的な生成状態から再構築します。完了、キャンセル、失敗、または期限切れとなったプロンプトは復元されません。

保存されたOAuthクライアントとトークンは、MCPサーバーのURLおよびOAuthクライアント/endpoint設定に紐付けられています。これらの設定を変更すると、ユーザーは再度認証を行う必要があります。保存された `client_secret` を保持するUI作成済みのサーバーを編集する際は、サーバーURL、クライアントID、認可URL、トークンURL、またはトークン認証方法などのバインディングフィールドを変更する際に、シークレットを再入力してください。

水平スケーリングされたデプロイメントでは、OAuthフローのステータスとバインドトークンの準備状況をLibreChatポッド間で調整できます。UIは、コールバックとステータス確認が異なるポッドに到達した場合でも、OAuth後の初期化が成功した後にのみサーバーを準備完了として報告します。置き換えられた試行からのコールバックは拒否されます。

Redisが有効な場合、アプリケーションレベルのMCPカタログ生成と公開リビジョンは、レプリカ間で調整されます。Redis Clusterのデプロイメントではスロットセーフなカタログキーと更新を使用するため、起動時の同期や `tools/list_changed` のリフレッシュにシングルノードのRedisレイアウトは必要ありません。

各ユーザーは、OAuthが有効なMCPサーバーを初めて使用する際に、自身のOAuthログインで認証するように求められます。これにより、接続および認証の詳細が各ユーザー固有のものとなり、マルチユーザー環境におけるセキュリティとプライバシーが維持されます。

#### OAuthのタイミング [#oauth-timing]

MCP OAuthの完了には、MCPサーバーの `initTimeout` を再利用するのではなく、サーバー側で設定された独自のタイムアウトが使用されます。デフォルトでは、LibreChatはユーザーがMCP OAuthを完了するまで最大10分間待機し、フローの状態を15分間保持します。

OAuthプロバイダーやユーザーワークフローでより多くの時間が必要な場合は、これらの環境変数を使用してください：

```bash filename=".env"
MCP_OAUTH_HANDLING_TIMEOUT=600000
MCP_OAUTH_FLOW_TTL=900000
```

`MCP_OAUTH_FLOW_TTL` は `MCP_OAUTH_HANDLING_TIMEOUT` よりも長く存続するように制限されているため、期限に近いコールバックであってもフロー状態を保持できます。MCP server-card のポーリングウィンドウは、設定された処理タイムアウトに従います。

> 注: アプリ起動時に表示されるトークンはアプリレベルの初期化のみを目的としており、個々のユーザー接続には使用されません。

自動トークン更新の例:

```bash
[MCP][spotify] Access token missing
[MCP][spotify] Attempting to refresh token
[MCP][spotify] Successfully refreshed and stored OAuth tokens
[MCP][spotify] ✓ Initialized
```

#### ベストプラクティス [#best-practices]

1. **OAuthが利用可能な場合はそれを使用する**: セキュリティ向上のため、APIキーよりもOAuthを優先してください
2. **適切なタイムアウトを設定する**: OAuth完了ウィンドウには `MCP_OAUTH_HANDLING_TIMEOUT` および `MCP_OAUTH_FLOW_TTL` を使用し、サーバーの初期化には `initTimeout` を使用してください。
3. **トークンの有効期限を監視**: 認証の問題がないかログを確認してください
4. **再認証の計画**: 一部のプロバイダーはリフレッシュトークンをサポートしていません

## Server Transports [#server-transports]

MCPサーバーは、異なるトランスポートメカニズムを使用するように設定できます：

**STDIO サーバー**

- ローカルのシングルユーザー環境に適しています
- リモート環境やクラウド環境へのデプロイにはスケーラビリティがありません
- 同梱されているMCP SDKは、個々のSTDIOメッセージを10 MBに制限しています。これを超える単一の結果が返されると、トランスポートはエラーで終了します。この制限は、セッションやストリームの合計サイズとは別個のものです。

**Server-Sent Events (SSE) サーバー**

- リモートトランスポートメカニズムですが、本番環境での使用は推奨されません。

**ストリーミング可能なHTTPサーバー**

- メッセージの送信にHTTP POSTを使用し、ストリーミングレスポンスをサポートします
- 複数のクライアント接続を処理できる独立したプロセスとして動作します
- Server-Sent Events (SSE) を介した基本的なリクエストとストリーミングの両方をサポートしています。
- レガシーな HTTP+SSE トランスポートに代わる、より高性能な代替手段
- 適切なマルチユーザーサーバー構成をサポートします

**本番環境では**、["Streamable HTTP" トランスポート](https://modelcontextprotocol.io/specification/draft/basic/transports/streamable-http) を使用する MCP サーバーのみが推奨されます。長時間の接続を維持する SSE とは異なり、Streamable HTTP はスケーラブルなマルチユーザー環境のデプロイに適したステートレスなオプションを提供します。

LibreChatは、多様な利用シナリオをサポートし、未来のAIワークフローを構築するために、柔軟でスケーラブルなMCPサーバー統合の実装において最前線に立っています。
