Discord Agent Channels let people use a LibreChat agent from a Discord server. An administrator connects an organization-owned Discord application, then an administrator who can also share the agent binds a server text channel to it. Each person links their own LibreChat account and grants consent before running the agent.

<Callout type="warning" title="Unreleased implementation documentation">
  This page describes Discord Agent Channels before they are released. The implementation is
  unreleased and may change, and the Compose overlays, Helm values, images and settings below
  may not exist in the version you run. Use matching API and channel-gateway images that
  include the feature; enabling the configuration below does not add it to an older build.
  [Discord social login](/docs/configuration/authentication/OAuth2-OIDC/discord) is a separate
  integration.
</Callout>

## Requirements

- A Discord application and bot that your organization controls, plus permission to manage the intended Discord server.
- A LibreChat agent, and an administrator who can manage installations and share that agent. Managing installations needs the `access:admin` and `manage:agents` capabilities, which users with the `ADMIN` role have; see [Admin capabilities](/docs/configuration/access_control#admin-capabilities).
- For everyone who runs the agent: current access to it, permission to use Agents and Remote Agents (see the [Agents API](/docs/features/agents_api)), and finished two-factor enrollment if your deployment enforces it.
- Transaction-capable MongoDB, such as a replica set. A standalone MongoDB instance cannot perform the required channel writes, and the default Docker Compose and Helm MongoDB are standalone.
- Public HTTPS URLs for LibreChat and the Discord gateway. The gateway must reach LibreChat over a private URL.
- The same private `CHANNEL_SERVICE_TOKEN` on the API and gateway, at least 32 characters long. Preserve the database and LibreChat's `CREDS_KEY` and `CREDS_IV` together during backup and recovery, or stored application credentials cannot be decrypted.

Discord runs in its own gateway process, separate from any Slack channel gateway, and does not require configuring Slack.

<Callout type="info" title="Conversation isolation is not Discord privacy">
  Each person's agent execution uses their own LibreChat access. Other members who can read
  the Discord channel can still read messages posted there. Choose an appropriate channel
  and do not put secrets in prompts.
</Callout>

## Enable Discord policy

Merge this into your existing `librechat.yaml`, preserving its other settings:

```yaml filename="librechat.yaml"
endpoints:
  agents:
    remoteApi:
      background:
        enabled: true
    channels:
      enabled: true
      discord:
        enabled: true
        publicUrl: https://discord.example.com
        gateway:
          enabled: false
          messageContent: false
        dm:
          enabled: false
```

The `channels.enabled` and `discord.enabled` switches enable Discord policy. Each run calls the Responses API as the person who linked their account, using a key that LibreChat creates for that run. So `remoteApi.background.enabled` must be `true` (stored background Responses), and Remote Agents API-key authentication must stay on: do not set `remoteApi.auth.apiKey.enabled` to `false`. See the [Agents API](/docs/features/agents_api) for Remote Agents access and authentication.

`discord.publicUrl` is the public HTTPS base of the Discord gateway, not the LibreChat browser URL. LibreChat builds the interactions endpoint as:

```text
https://discord.example.com/discord/<applicationId>/interactions
```

A base with a prefix, such as `https://example.com/chat-discord`, needs a proxy that removes `/chat-discord` before forwarding to the gateway. The gateway receives `/discord/<applicationId>/interactions`. Keep request bodies and Discord signature headers unchanged. Expose only `/discord/` publicly; health, metrics, and internal service routes belong on the private network.

Configure LibreChat's public `DOMAIN_SERVER` and `DOMAIN_CLIENT` separately. Copy the OAuth callback URL from LibreChat's setup screen rather than constructing it from the gateway URL.

## Deploy the gateway

Bot tokens and OAuth client secrets are entered through LibreChat's authenticated application setup. Do not put them in gateway environment variables, Helm values, screenshots, or support logs. The Discord social-login variables `DISCORD_CLIENT_ID`, `DISCORD_CLIENT_SECRET`, and `DISCORD_CALLBACK_URL` do not configure Agent Channels.

### Docker Compose

From a LibreChat checkout containing the Discord overlays, set a `LIBRECHAT_IMAGE_TAG` whose API and channel-gateway images include Discord Agent Channels, and add `CHANNEL_SERVICE_TOKEN` to the `.env` file next to the compose files, filled from your secret manager if you use one. With the stock files, the API reads that file through its `./.env` mount and Compose passes the same value to the gateway, so a token exported only in your shell reaches the gateway but not the API. The Discord overlay also mounts `./librechat.yaml` read-only into the API, so keep the policy from above in that file.

The stock Compose MongoDB is standalone and cannot perform the required channel writes. The example below opts in to `docker-compose.mongo-replica.yml`, which turns the bundled MongoDB into a single-node replica set. It reuses the existing data directory and is not a high-availability setup: read the comments at the top of that file, back up and stop an existing stack first, and do not apply it blindly to a populated standalone database. If you already use an external replica set, replace this overlay with your existing Compose override that sets the API's `MONGO_URI`.

After preparing the database, validate and start the Compose deployment:

```bash
docker compose -f docker-compose.yml -f docker-compose.discord.yml \
  -f docker-compose.mongo-replica.yml --profile channels config --quiet
docker compose -f docker-compose.yml -f docker-compose.discord.yml \
  -f docker-compose.mongo-replica.yml --profile channels up -d
```

For source builds, add `-f docker-compose.discord-build.yml` after the Discord overlay and use `up -d --build`. The Discord overlay binds its HTTP listener to loopback on port 3082 by default, configurable with `DISCORD_GATEWAY_PORT`. Put your HTTPS proxy in front of that listener.

Before saving the interactions endpoint in Discord, check that the gateway's private `GET /readyz` returns 200, for example `http://127.0.0.1:3082/readyz` on the Docker host. If the gateway container keeps restarting, its logs show `channel_service_authentication_failed` when the API rejects the token: confirm both sides use the same value of at least 32 characters.

### Helm

For Kubernetes, enable `channelGateway.discord.enabled` in the LibreChat Helm chart. Its Deployment, Service, and optional Ingress are separate from Slack. The shared `channelGateway.image`, `internalUrl`, and `existingSecretName` settings supply the gateway image, private API URL, and service token. Check these before installing; the chart enforces some of them when it renders:

- `image.tag` set to a tag that includes Discord Agent Channels. The chart refuses to render without it, and `channelGateway.image.tag` defaults to it.
- A credentials Secret named by `channelGateway.existingSecretName`, or by `global.librechat.existingSecretName` when that is empty. The chart refuses to render without a name but cannot check the contents: the Secret must contain `CHANNEL_SERVICE_TOKEN` with the same value LibreChat reads, so add the key to the Secret the API already uses without replacing its other keys.
- Transaction-capable MongoDB. The chart refuses shared gateways with the bundled standalone MongoDB, so set `mongodb.architecture=replicaset` or point `MONGO_URI` at an external replica set.
- `channelGateway.discord.ingress.host`, which the chart requires when the Ingress is enabled. The Ingress routes only the public `/discord/` path.

Deliver the policy from above through `librechat.configYamlContent` or `librechat.existingConfigYaml`. `internalUrl` is empty by default, which derives the in-cluster LibreChat Service URL.

## Connect an application and server

1. Create an application and bot in the [Discord Developer Portal](https://discord.com/developers/applications). In the bot settings, enable **Require OAuth2 Code Grant**; LibreChat rejects an application without it. With it on, a plain Developer Portal invite link cannot add the bot, so add it with **Connect server** in step 6. Keep the bot token and OAuth client secret private.
2. In LibreChat, open **Settings > Account > Discord**. Add the displayed **OAuth callback URL** to the application's OAuth2 redirect URLs in Discord.
3. Choose **Add application**, then enter the application ID, bot token, and OAuth client secret. LibreChat verifies the application and bot identity. Saving credentials does not install the bot or register commands automatically.
4. Copy the displayed **Interactions endpoint URL** into the Developer Portal. Discord verifies the endpoint with a signed request. If verification fails, check your proxy and gateway; do not disable signature checks.
5. Choose **Register or update /librechat commands**. This explicitly upserts `/librechat` without replacing other command names. It supports server-installed applications in server and bot-DM contexts. Global command changes can take time to appear.
6. Choose **Connect server** and authorize the intended server in Discord. LibreChat requests the `bot`, `applications.commands`, and `guilds` scopes and, by default, the View Channel, Send Messages, Read Message History, and Send Messages in Threads permissions (`botPermissions` under `endpoints.agents.channels.discord`); review them before you authorize. Keep the initiating LibreChat session open. If a popup is blocked, allow it and refresh the server status before starting another attempt. The server should show **Connected**.

Successful credential verification does not prove that a server is connected or that the bot can write in a particular channel. Complete the binding and personal-link steps below.

## Bind a text channel to an agent

1. Open the agent's **Channels** surface and select **Discord**.
2. Choose a connected server and enter a regular text channel ID. Enable Discord Developer Mode to use **Copy Channel ID**.
3. Give the bot **View Channel**, **Send Messages**, and **Read Message History** in that channel, including its role and channel permission overwrites.
4. Check the current binding and choose **Connect channel**. If another agent owns the destination, review the replacement confirmation.

One application/server/channel destination has one active agent binding. Threads inherit their parent text-channel binding; direct messages use an explicit selection. Neither is bound separately. Forum channels and other parent-channel types are unsupported.

If LibreChat cannot confirm a save or removal, use **Check current binding** before trying another change. A lost response can follow a successful write. Replacing a binding closes the previous binding and requires new personal consent.

## Link your account and run the agent

In the bound server channel, run `/librechat link`. Open the private account-link URL, sign in to the intended LibreChat account, and review the consent request. Return to the original Discord channel, run `/librechat link` again, and choose **Confirm account** when prompted.

Each person completes this flow independently. Browser consent alone does not authorize an earlier prompt. Send a fresh prompt after confirming in Discord. A confirmed link lasts 30 days by default (`linkLifetimeMs` under `endpoints.agents.channels`), after which the person links again.

| Command | Purpose |
| --- | --- |
| `/librechat ask prompt:...` | Start a run using the agent for this destination |
| `/librechat status` | Inspect your current run privately |
| `/librechat cancel` | Request cancellation of your current run |
| `/librechat link` | Start or confirm account linking in a server channel |
| `/librechat select code:...` | Select an agent in a bot DM using a code from LibreChat |

Agent output goes to the destination where you asked. Review links require your LibreChat authorization. When an answer exceeds the delivery limit (`maxDeliveryParts` under `endpoints.agents.channels`, 100 messages by default), the bot shortens it and says so; an authorized session link is included when available, including a link button for a one-message limit. Attachments are not delivered through this integration.

Feedback buttons appear only when a [Langfuse](/docs/configuration/langfuse) feedback score destination is configured. They apply to the delivered answer and the requesting account. Revoking consent, replacing a binding, or removing current source access prevents stale controls from granting new authority.

### Native threads

Use a public or private thread beneath the bound text channel. The bot needs **View Channel**, **Read Message History**, and **Send Messages in Threads**. Private threads require current membership or the applicable thread-management permission for both the bot and the acting user. Archived or locked threads are refused; LibreChat does not reopen them automatically.

Slash asks and explicit bot mentions in the same thread continue the same person's conversation. Another person has a separate conversation. Server text asks outside a thread start a fresh conversation per event.

Replies remain in the thread. Losing thread access never redirects an answer to the parent channel. After replacing the parent agent binding, start a new thread. An existing thread stays tied to its original binding and is refused after the replacement; it does not switch agents.

### Bot mentions

Slash commands use signed HTTP interactions and do not need the WebSocket Gateway. To accept explicit bot mentions in supported server channels and threads, enable:

```yaml filename="librechat.yaml (under endpoints.agents.channels.discord)"
gateway:
  enabled: true
  messageContent: false
```

An implicit reply mention is insufficient. The integration does not forward every server message to the agent. Discord can include content for explicit bot mentions without privileged Message Content intent. Set `messageContent: true` only when needed, and enable or obtain approval for the corresponding intent in the Developer Portal.

### Direct messages

Enable `endpoints.agents.channels.discord.dm.enabled: true` to allow private agent selection and new DM execution. Signed DM slash commands do not need `discord.gateway.enabled`; ordinary DM messages require both switches.

After confirming a server account link:

1. Open **Settings > Account** and find **Discord Direct Messages** under **Your channel account links**. Its **Use in Direct Messages** buttons appear only when `dm.enabled` is on and you have an active Discord account link; otherwise the section says what is missing.
2. Choose **Use in Direct Messages** for the intended agent, Discord account, server, and application.
3. Choose **Generate Code**.
4. In a direct message with that Discord app, run `/librechat select` and enter the value in its `code` option.
5. After confirmation, use `/librechat ask` in the DM, or send an ordinary message if Gateway ingestion is enabled.

Keep the code private and use it before its displayed expiration (10 minutes by default, `dm.codeTtlMs`). Generating another code invalidates the previous unused code for the same account and application. Replaying a used code cannot extend the selection or replace a newer one. A selection expires 24 hours after you confirm it by default (`dm.selectionTtlMs`, at most 7 days) and never outlives your server account link; after that, generate a new code.

A selection retains the original server-channel authority and account consent. It does not bypass permissions because the destination is a DM. Revoke it from account settings when finished. Revoked, expired, or replaced selections cannot start new work, and changing the selected agent does not transfer old conversations or controls to the replacement.

Turning off `dm.enabled` blocks new DM execution. Existing response metadata and authorized controls can still settle, while any new output must pass current selection and source-permission checks.

## Health and diagnostics

Each application card in **Settings > Account > Discord** shows the last recorded bot-token result and its timestamp, or an unknown status when no usable observation is available. An accepted token does not confirm the OAuth client secret, channel permissions, or command delivery. The card reports past evidence; opening it does not perform a live Discord check. Use **Update credentials** when Discord has rejected the token.

If saving a credential observation fails, the gateway retries after 30 seconds by default, even when the bot is idle, while it still owns the application lease. Set `endpoints.agents.channels.discord.health.observationRetryMs` to change this delay (1,000 to 600,000 milliseconds), then restart the API and gateway to load the new setting. The delay cannot exceed `observationTtlMs` in the same `health` section, the observation lifetime that defaults to 3,600,000 milliseconds (one hour). Until a save succeeds, the application card keeps its previous status and timestamp.

Deploy matching API and gateway versions. During an upgrade, stop the gateway and start the matching gateway version once the updated API is ready. Mixed API and gateway versions are not supported.

Operators can read `/healthz/detail` on the private gateway listener for aggregate worker, credential, permission, and native Gateway health. `/metrics` exposes Prometheus metrics, including the `channel_gateway_discord_` families. Keep both endpoints private alongside `/livez`, `/healthz`, and `/readyz`; expose only the configured `/discord` interaction paths to Discord.

Detailed health reflects observations on that gateway replica and can become unknown or degraded when evidence is absent or stale. It does not probe Discord or change readiness. `/readyz` remains the serving-readiness check, and `/livez` remains the process-liveness check; a ready gateway can still report a problem with an application's credentials, permissions, or native connection.

## Troubleshooting

| Symptom | Check |
| --- | --- |
| Agent channels require a database with transaction support | Configure MongoDB as a replica set or use another supported transaction-capable deployment; the stock Docker Compose and Helm MongoDB are standalone. Do not bypass transaction checks. |
| The gateway container keeps restarting | Confirm `CHANNEL_SERVICE_TOKEN` is identical on the API and gateway and at least 32 characters long. The gateway logs `channel_service_authentication_failed` when the API rejects it. |
| Discord rejects the interactions endpoint | Confirm public HTTPS reachability, the exact application path, preserved raw request bytes and signature headers, a running gateway whose private `/readyz` returns 200, and an accurate clock on the gateway host (signed requests more than 5 minutes off are rejected). |
| Commands are missing | Explicitly register commands, allow time for global propagation, and check the application and installation context. |
| Server authorization fails | Check Require OAuth2 Code Grant, the exact callback URL, the initiating browser session, and the Discord account's server-management permission. |
| A channel cannot be bound | Check the server/channel pair, supported text-channel type, bot permissions, and your LibreChat agent-sharing and installation-management access. |
| Account linking appears incomplete | Return to the original Discord channel and confirm the same account, then send a fresh prompt. A person who has not finished required two-factor enrollment cannot complete the link. |
| Mentions or ordinary DMs are ignored | Check `gateway.enabled`, the destination binding or DM selection, explicit mention behavior, and current consent. Signed slash commands use a separate ingress path that stays active while a failed Gateway session is delayed; execution and delivery still require valid bot credentials and permissions. |
| A saved operation is uncertain | Refresh or check its current state. Do not blindly repeat it or delete deduplication records. |
| Replies stop after permission or credential changes | Restore the required access or update credentials, then check the current binding and consent. Old revisions do not regain authority automatically. |
| An agent stops answering in a DM, or asks you to link again | Account links last 30 days and DM selections 24 hours by default. Link again, then generate a new DM code. |

A failed native Gateway session delays only that application's next native reconnect. The application keeps its lease and REST workers, so signed slash command processing, private replies, and run delivery remain active while the Gateway waits. They still require valid bot credentials and permissions. Fatal failures (rejected bot credentials, invalid shard configuration or intents, identity mismatches, and startup or IDENTIFY-budget failures) wait 30 seconds, then double up to 15 minutes. Ordinary transient failures use jittered delays capped at 60 seconds. The delay is tracked per application on the gateway replica that owns it. It starts over when a session that was verified healthy for two minutes fails, when you save credentials in LibreChat, when the replica stops owning the application, and when the gateway restarts. These delays are configurable with `fatalRetryMinMs`, `fatalRetryMaxMs`, `retryMaxMs`, and `resetAfterMs` under `endpoints.agents.channels.discord.gateway.recovery`. Fix settings in the Discord Developer Portal or rotate credentials in LibreChat rather than repeatedly restarting the gateway to clear a delay.

A native session must reach READY within its startup deadline, derived from `gateway.handshakeTimeoutMs`, `gateway.readyTimeoutMs`, and the shard count (45 seconds for one shard at the defaults). A missed deadline or a refused IDENTIFY marks native health as failing and uses the longer retry schedule. It does not mark the bot token or permissions as invalid; the metric `channel_gateway_discord_gateway_stop_total` records the `startup` reason.

The gateway checks Discord's session-start budget before opening a connection and before each IDENTIFY. An exhausted or malformed budget sends no IDENTIFY. A startup deadline can expire before HELLO arrives, spending no IDENTIFY but still using the longer retry schedule, so recovery after a prolonged Discord outage can lag by up to `fatalRetryMaxMs`. Reducing that limit trades faster recovery for more session-start attempts. Do not share a bot token with another deployment, since one process cannot account for the other's IDENTIFY usage.

## Rotation, rollback, and removal

Use **Update credentials** to rotate application credentials. Blank secret fields retain their current values; stored secrets are not returned to the browser. Disconnecting a server stops new work for that installation. Reconnect through fresh OAuth authorization, then recreate bindings and consent.

For rollback, disable `endpoints.agents.channels.discord.enabled` and apply the configuration through your deployment procedure. Leave the shared `channels.enabled` setting enabled if Slack must keep working. Remove Discord public ingress and stop the Discord gateway with its normal termination signal. A native connection still waiting for READY can add up to `gateway.handshakeTimeoutMs` (10 seconds by default) to shutdown; allow outstanding REST work and status writes to settle as well. Keep the API available long enough to inspect and cancel outstanding work. Cancellation cannot undo messages or external actions that already completed.

Preserve MongoDB, encryption keys, run receipts, and replay records. Roll back API and gateway images together. Older gateways reject unsupported saved delivery plans; do not delete records to force replay. Keep Discord disabled when reverting to a release without Discord support.

To uninstall, remove bindings and disconnect servers in LibreChat, revoke personal links and DM selections, then remove the gateway deployment and its public route. Remove the bot from Discord. LibreChat has no action that deletes a stored application, so its encrypted record stays in storage; if the application is no longer used elsewhere, reset its bot token and OAuth client secret in the Developer Portal to invalidate them. Historical Discord messages follow the server's retention policy; removing the bot does not delete them.
