# Agents: Eigene KI-Assistenten erstellen [#agents-build-custom-ai-assistants]

Die AI Agents-Funktion von LibreChat bietet ein flexibles Framework zur Erstellung benutzerdefinierter KI-Assistenten, die von verschiedenen Modellanbietern betrieben werden.

Diese Funktion ähnelt der Assistants API von OpenAI und den GPTs von ChatGPT, bietet jedoch eine breitere Modellunterstützung und eine No-Code-Implementierung, mit der Sie hochentwickelte Assistenten mit spezialisierten Fähigkeiten erstellen können.

## Erste Schritte [#getting-started]

Um einen neuen Agenten zu erstellen, wählen Sie „Agents“ aus dem endpoint-Menü und öffnen Sie das Agent Builder-Panel, das sich in der Seitenleiste (Side Panel) befindet.

![Agents - Endpoints-Menü](/images/agents/endpoints_menu.png)

Das Erstellungsformular enthält:

- **Avatar**: Laden Sie einen benutzerdefinierten Avatar hoch, um Ihren Agenten zu personalisieren
- **Name**: Wählen Sie einen unverwechselbaren Namen für Ihren Agenten
- **Beschreibung**: Optionale Details zum Zweck Ihres Agenten
- **Anweisungen**: Systemanweisungen, die das Verhalten Ihres Agenten definieren
- **Modell**: Wählen Sie aus den verfügbaren Anbietern und Modellen
- **Conversation Starters**: Bis zu vier vorgeschlagene Prompts, die angezeigt werden, wenn ein Benutzer einen neuen Chat mit dem Agenten beginnt

Die **Tools**- und **Skills**-Steuerelemente öffnen durchsuchbare Bibliotheken für integrierte Funktionen, Tools, MCP-Server, Actions und Skills. Wählen Sie ein Element aus, um es zu konfigurieren, und speichern Sie anschließend den Agenten.

**Bestehende Agents können über das obere Dropdown-Menü im Seitenbereich ausgewählt werden.**

- **Auch durch Erwähnung mit „@“ in der Chat-Eingabe.**

![Agents - Mention](/images/agents/mention.png)

### Tool Library [#tool-library]

Der Agent Builder hält aktivierte Elemente in separaten **Tools**- und **Skills**-Abschnitten. Öffnen Sie **Add tools**, um den vollständigen Katalog zu durchsuchen oder ihn nach **Official**, **Tools**, **MCP** oder **Actions** zu filtern. **Made by you** sammelt von Ihnen erstellte MCP-Server und Actions, während **Favorites** markierte Elemente für alle Agents verfügbar hält. Jeder Benutzer kann bis zu 100 Favoriten in der Tool-Bibliothek speichern.

Wählen Sie ein Element aus, um es zu konfigurieren, ohne den Builder zu verlassen. Das Menü **Create new** erscheint nur, wenn der Benutzer die Berechtigung hat, MCP Server oder Actions zu erstellen. Das Entfernen einer dateibasierten Funktion wie File Search, File Context oder Code Interpreter öffnet deren Dateimanager, wenn noch angehängte Dateien überprüft werden müssen. Eine dateibasierte Funktion bleibt ausgewählt und wird beim Speichern beibehalten, solange sie noch Dateien besitzt; entfernen oder verschieben Sie diese Dateien, bevor Sie die Funktion selbst entfernen.

Skills verwenden ihre eigene Auswahl und können einzeln ausgewählt oder als vollständiger zugänglicher Katalog aktiviert werden. Siehe [Skills](/docs/features/skills#agent-scope).

Betreiber können auch experimentelle [Agent Plugins](/docs/features/agent_plugins) verwenden, um Bereitstellungs-Skills und MCP-Server in beim Start geladene Pakete zu bündeln.

### Modellkonfiguration [#model-configuration]

Die Benutzeroberfläche für Modellparameter ermöglicht die Feinabstimmung der Antworten Ihres Agenten:

- Temperatur (0-1 Skala für die Kreativität der Antwort)
- Maximale Kontext-Tokens
- Maximale Ausgabetokens
- Bilddetail (`low`, `auto` oder `high`) für native Vision-Bildeingaben
- Zusätzliche anbieterspezifische Einstellungen

Agent-Anweisungen können `{{current_date}}`, `{{current_datetime}}` und `{{iso_datetime}}` verwenden. LibreChat löst diese vom servererfassten Beginn des logischen Turns auf und hält diesen Zeitstempel über Provider-Schleifen, Subagent-Initialisierung und Human-in-the-Loop-Wiederaufnahme hinweg stabil. Die ersten beiden verwenden die Zeitzone der Anfrage; `{{iso_datetime}}` bleibt UTC.

Erkannte „model-not-found“-Fehler und Ratenbegrenzungsfehler des Providers liefern lokalisierte Hinweise. Andere Provider-Fehler behalten ihren nützlichen Provider-Text bei, lassen jedoch LangChain-Fehlerbehebungs-URLs weg, bevor die Nachricht gespeichert wird. Wenn [model-bound content protection](/docs/configuration/librechat_yaml/object_structure/message_filter#source-aware-filters) aktiviert ist, hat dessen allgemeiner Schutzfehler weiterhin Vorrang.

### Versionsverlauf [#version-history]

Benutzer mit Bearbeitungszugriff können im Agent Builder den **Versionsverlauf** öffnen, um gespeicherte Konfigurationen in einer Zeitachse zu überprüfen. Jeder Eintrag zeigt an, wann er gespeichert wurde, und fasst die verwendeten Tools und Funktionen zusammen. Das Wiederherstellen eines früheren Eintrags erfordert eine Bestätigung und ersetzt die aktuelle Agentenkonfiguration durch den gespeicherten Zustand. Das Speichern übernimmt immer die aktuellen Änderungen des Agenten, selbst wenn die resultierende Konfiguration mit dem neuesten Verlaufseintrag übereinstimmt; LibreChat fügt in diesem Fall keinen doppelten Eintrag hinzu.

### Gesprächsstarter [#conversation-starters]

Konversationsstarter bieten Benutzern eine schnelle Möglichkeit, einen Chat mit einem Agenten zu beginnen. Jeder Agent kann bis zu vier davon speichern.

1. Suchen Sie im Agent Builder das Feld **Conversation Starters**.
2. Geben Sie eine Eingabeaufforderung ein und drücken Sie **Enter**, oder wählen Sie die **+**-Schaltfläche. Die Eingabe wird deaktiviert, sobald vier Starter hinzugefügt wurden.
3. Bearbeiten Sie einen gespeicherten Starter direkt oder wählen Sie die **X**-Schaltfläche, um ihn zu entfernen.
4. Speichere den Agenten.

Wenn ein Benutzer einen neuen Chat mit dem Agenten öffnet, erscheinen die Starter als Schaltflächen auf dem leeren Chat-Bildschirm. Durch Auswahl einer Schaltfläche wird diese sofort als erste Nachricht gesendet. Wenn der Agent über Starter verfügt, haben diese Vorrang vor allen [`conversation_starters`](/docs/configuration/librechat_yaml/object_structure/model_specs#conversation_starters), die in der verwendeten Model Specs definiert sind. Starter erscheinen auch im Detaildialog des [Marketplace](#agent-marketplace) des Agenten.

## Agent-Funktionen [#agent-capabilities]

> **Hinweis:** Alle Funktionen können über die Konfigurationsdatei `librechat.yaml` ein- oder ausgeschaltet werden. Weitere Informationen finden Sie unter [docs/configuration/librechat_yaml/object_structure/agents#capabilities](/docs/configuration/librechat_yaml/object_structure/agents#capabilities).

### Code Interpreter [#code-interpreter]

Wenn aktiviert, ermöglicht die Code Interpreter-Funktion Ihrem Agenten:

- Führen Sie Code in mehreren Sprachen aus, einschließlich:
  - Python, JavaScript, TypeScript, Go, C, C++, Java, PHP, Rust und Fortran
- Verarbeiten Sie Dateien sicher über die LibreChat Code Interpreter API
- Führen Sie Code ohne lokale Einrichtung, Konfiguration oder Sandbox-Bereitstellung aus
- Verarbeite Datei-Uploads und -Downloads nahtlos
- [Weitere Informationen zur Code Interpreter API](/docs/features/code_interpreter)
  - **Unterstützt durch den Open-Source [code-interpreter](https://github.com/ClickHouse/code-interpreter) Dienst (selbst gehostet)**

Wenn jede erforderliche Code Interpreter-Datei aus einer Konversation nicht in der aktuellen Sandbox wiederhergestellt werden kann, stoppt LibreChat den Agenten, bevor das Modell aufgerufen wird, und fordert den Benutzer auf, die Dateien erneut anzuhängen. Dies verhindert, dass der Vorgang mit veralteten oder nicht zugänglichen Dateireferenzen fortgesetzt wird.

Wenn Konversationsdateien denselben Dateinamen für den Code Interpreter verwenden, weist LibreChat unterschiedliche Sandbox-Ziele zu und teilt dem Agenten die aufgelösten Pfade mit. Siehe [Seamless File Handling](/docs/features/code_interpreter#seamless-file-handling) für das Verhalten bei Kollisionen und die verbleibende Einschränkung für private Dateien bei Multi-Agenten.

#### Stateful Code Sessions [#stateful-code-sessions]

Stateful Code-Sessions ermöglichen es einem Agenten, einen Sandbox-Arbeitsbereich über mehrere Code-Ausführungen hinweg wiederzuverwenden. Dateien, installierte Pakete und der Arbeitszustand bleiben in der Regel erhalten, was für iterative Analysen und mehrstufige Dateiarbeiten nützlich ist. Im Agent Builder steuert die Auswahl **Stateful environment**, wer diesen Arbeitsbereich teilt:

- **Benutzerarbeitsbereich (empfohlen):** Die zustandsbehafteten Agents des angemeldeten Benutzers teilen sich einen Arbeitsbereich
- **Agent + Benutzer-Arbeitsbereich:** Jeder Benutzer erhält einen separaten Arbeitsbereich für jeden Agenten
- **Konversations-Arbeitsbereich:** Jeder Benutzer erhält einen separaten Arbeitsbereich für jede Konversation

Administratoren können unter [`statefulCodeSessions.environments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions) auch benannte Backends konfigurieren. Wenn diese vorhanden sind, wählt der separate **Execution environment**-Selektor die verwaltete Code-API, die mit dem Operator verbundene VM oder den persönlichen Worker aus, der den Arbeitsbereich besitzt; **Deployment default** verwendet die konfigurierte Standard-Ausführungsumgebung. Der oben genannte Freigabebereich bleibt unabhängig von dieser Backend-Wahl.

Wenn eine Bereitstellung Self-Service-Worker aktiviert, können Benutzer mit der Berechtigung zur Verwaltung von Code-Umgebungen unter **Settings > Code environments** einen ausgehenden `@librechat/code`-Worker auf ihrer eigenen VM koppeln, ihn im Agent Builder auswählen und später wieder widerrufen. Persönliche Umgebungen sind an den Eigentümer gebunden und verwenden denselben Pfad für Code, Shell und Programmatic Tool Calling. Siehe [Attached environments and pairing](/docs/features/code_interpreter#attached-environments-and-pairing) für das experimentelle Setup und das Sicherheitsmodell.

Innerhalb eines angehängten Arbeitsbereichs können Agents Verzeichnisse auflisten, Dateien lesen, Text durchsuchen, Dateien erstellen und Bash über den ausgewählten Worker ausführen. Ein Agent-spezifischer Git-Name und eine E-Mail-Adresse können Commits identifizieren, die dort vorgenommen wurden, ohne dass Repository-Anmeldeinformationen bereitgestellt werden müssen. Bereitstellungen können neue persönliche Worker mit [`statefulCodeSessions.principalWorkers`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions) einschränken.

Wenn ein verbundener Worker mehrere Workspace-Roots ankündigt, erfordert der Chat-Composer eine Auswahl für jede verbundene Umgebung, die vom Agent oder seinen Subagents verwendet wird. Die Konversation behält diese Auswahlen über mehrere Turns und die Wiederaufnahme der Genehmigung hinweg bei; LibreChat validiert sie gegenüber dem aktiven Worker und blockiert das Senden, falls ein erforderlicher Workspace fehlt oder nicht verfügbar ist. Ein Worker, der genau einen Workspace ankündigt, wird für eine neue Konversation automatisch ausgewählt. Siehe [Attached environments and pairing](/docs/features/code_interpreter#attached-environments-and-pairing) für Details und aktuelle Einschränkungen.

Neue Agents verwenden zunächst den **Standard-Zustandsbereich (Stateful Workspace)** des angemeldeten Benutzers unter **Einstellungen > Datenkontrolle > Codeausführung**. Der persönliche Standardwert ist **Benutzer-Workspace**, sofern er nicht geändert wurde. Das Aktualisieren dieser Einstellung ändert keine bestehenden Agents und aktiviert nicht von sich aus Stateful Code Sessions. Administratoren können die verfügbaren Bereiche mit [`statefulCodeSessions.allowedEnvironments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions) einschränken; wenn ein gespeicherter persönlicher Standardwert nicht mehr zulässig ist, verwenden neue Agents den ersten erlaubten Bereich.

<Callout type="warning" title="Hochgradig experimentell">
  Stateful Code Sessions befinden sich in einer frühen experimentellen Phase. Ihr Verhalten, ihre Konfiguration, ihre Persistenzeigenschaften und die zugrunde liegende Integration können sich grundlegend ändern. Betrachten Sie die aktuelle Implementierung nicht als stabilen Produktionsvertrag.
</Callout>

Diese Funktion ist optional (opt-in). Ein Administrator muss `stateful_code_sessions` zu den [Agent-Funktionen](/docs/configuration/librechat_yaml/object_structure/agents#capabilities) hinzufügen und eine dedizierte Route für den zustandsbehafteten Code Interpreter über [`LIBRECHAT_CODE_BASEURL_STATEFUL`](/docs/configuration/dotenv#stateful-code-interpreter-endpoint) oder die benannten [`statefulCodeSessions.environments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions) konfigurieren. Der Code Interpreter muss für den Agenten aktiviert sein, und **Stateful code sessions** müssen unter dessen erweiterten Einstellungen (Advanced settings) eingeschaltet werden.

Stateful-Anfragen greifen nicht auf den normalen zustandslosen Code Interpreter-endpoint zurück, wenn die dedizierte URL fehlt oder inkompatibel ist. Stateful- und stateless-Sitzungen teilen sich zudem keine Live-Dateien oder installierten Pakete. Der stateful-Arbeitsbereich kann jederzeit zurückgesetzt werden, unabhängig von seinem Gültigkeitsbereich. Speichern Sie in verwalteten Code Interpreter-Umgebungen wichtige Ausgaben unter `/mnt/data`; ein angehängter Arbeitsbereich ist ein separates, vom Worker verwaltetes Verzeichnis. Chat-Uploads werden standardmäßig nicht in dieses angehängte Verzeichnis kopiert. Verlassen Sie sich ansonsten nicht auf den Sitzungsstatus als dauerhaften Speicher.

Wenn zustandsbehaftete `create_file`- oder `edit_file`-Tools während einer Antwort Dateien erstellen, zeigt die Assistenten-Nachricht eine kompakte Zeile für **Workspace-Änderungen** an. Erweitern Sie diese, um die eindeutig geänderten Pfade zu überprüfen und jede Datei über den authentifizierten Datei-Workflow von LibreChat herunterzuladen. Dies ist eine nachrichtenbezogene Aufzeichnung der von diesen Tools erstellten Dateien und kein dauerhafter Schnappschuss des gesamten Arbeitsbereichs; zustandslose Code Interpreter-Ausgaben verwenden weiterhin die reguläre Inline-Anhang-Schnittstelle.

Für angehängte Umgebungen kann der Composer **Vor Änderungen fragen**, **Bearbeitungen akzeptieren** und **Vollzugriff** als Code-Genehmigungsmodus auf Konversationsebene bereitstellen. Die Verfügbarkeit ist durch das vom Administrator der Umgebung definierte Berechtigungsschema begrenzt; die Wahl eines freizügigeren Modus setzt niemals Rollenzuweisungen, explizite Tool-Regeln, Hooks oder Sandbox-Grenzen außer Kraft. Siehe [Attached-environment tool permissions](/docs/features/code_interpreter#attached-environment-tool-permissions).

### Dateisuche [#file-search]

Die File Search-Funktion ermöglicht:

- RAG (Retrieval-Augmented Generation) Funktionalität
- Semantische Suche in hochgeladenen Dokumenten
- Kontextbezogene Antworten basierend auf Dateiinhalten
- Unterstützung für Dateianhänge sowohl auf Agenten- als auch auf Chat-Thread-Ebene

### Dateikontext [#file-context]

Die Funktion „Dateikontext“ (File Context) ermöglicht es Ihrem Agenten, extrahierten Text aus Dateien als Teil seiner Systemanweisungen zu speichern:

- Extrahieren Sie Text unter Beibehaltung der Dokumentstruktur und Formatierung
- Verarbeitung komplexer Layouts, einschließlich mehrspaltigem Text und gemischten Inhalten
- Verarbeitung von Tabellen, Gleichungen und anderen spezialisierten Inhalten
- Arbeiten mit mehrsprachigen Inhalten
- Der Text wird in den Anweisungen des Agents in der Datenbank gespeichert.
- **Kein OCR-Dienst erforderlich** – Verwendet standardmäßig Text-Parsing mit Fallback-Methoden
- **Durch OCR verbessert** – Wenn OCR konfiguriert ist, verbessert sich die Extraktionsqualität für Bilder und gescannte Dokumente
- Verwendet die gleiche Verarbeitungslogik wie "Upload as Text": **OCR > STT > Text-Parsing**
- [Weitere Informationen zur OCR-Konfiguration](/docs/features/ocr)

**Hinweis:** Der Dateikontext enthält extrahierten Text in den Systemanweisungen des Agenten. Für temporäre Dokumentenfragen in einzelnen Unterhaltungen verwenden Sie stattdessen [Upload as Text](/docs/features/upload_as_text) aus dem Chat.

### Model Context Protocol (MCP) [#model-context-protocol-mcp]

MCP ist ein offenes Protokoll, das standardisiert, wie Anwendungen Large Language Models (LLMs) Kontext bereitstellen, und fungiert dabei als universeller Adapter für KI-Tools und Datenquellen.

Weitere Informationen finden Sie in der Dokumentation zu [MCP](/docs/features/mcp).

#### Agents mit MCP Tools [#agents-with-mcp-tools]

1. Konfigurieren Sie MCP-Server in Ihrer `librechat.yaml` Datei
2. Starten Sie LibreChat neu, um die Verbindungen zu initialisieren.
3. Einen Agenten erstellen oder bearbeiten
4. Öffnen Sie **Add tools** im Agent Builder und wählen Sie **MCP** aus.
5. Wählen Sie den/die MCP-Server aus, die Sie hinzufügen möchten; jeder Server erscheint als einzelner Eintrag
6. Speichern Sie Ihre Änderungen am Agenten

In diesem Beispiel haben wir den **[Spotify MCP server](https://github.com/LibreChat-AI/spotify-mcp)** zu einem Agenten hinzugefügt.

![Agents - MCP](/images/agents/mcp_tools_v2.png)

#### Verwalten von MCP Tools [#managing-mcp-tools]

Sobald ein MCP Server zu einem Agenten hinzugefügt wurde, können Sie genau festlegen, welche spezifischen Tools verfügbar sein sollen:

- Nachdem Sie einen MCP Server hinzugefügt haben, klappen Sie ihn aus, um alle verfügbaren Tools zu sehen.
- Aktiviere/deaktiviere einzelne Tools nach Bedarf
- Zum Beispiel stellt der Spotify MCP Server etwa 20 Tools bereit (Suche, Wiedergabesteuerung, Playlist-Verwaltung usw.)
- Diese granulare Steuerung ermöglicht es Ihnen, Agents auf die Tools zu beschränken, die sie tatsächlich benötigen.

Anforderungsbezogene Server, die `{{LIBRECHAT_BODY_*}}` verwenden, können Tools erst auflisten, wenn ein Chat-Durchlauf diese Werte bereitstellt. Der Agent Builder zeigt daher eine Laufzeit-Tool-Auswahl für den gesamten Server anstelle von Umschaltern pro Tool; das Löschen dieser Auswahl trennt den Server. Nach OAuth behält LibreChat die Autorisierung bei und wartet bis zum ersten geeigneten Durchlauf, um die Verbindung herzustellen.

Wenn ein Agent explizit MCP-Tools auswählt, diese jedoch beim Start eines Laufs nicht aufgelöst werden können, stoppt LibreChat den Lauf mit Hinweisen zur Verbindung und zum Zugriff, anstatt ohne sie stillschweigend fortzufahren. Stellen Sie die Verbindung zum Server wieder her oder authentifizieren Sie sich, überprüfen Sie den Tool-Zugriff und starten Sie den Lauf erneut.

![Agents - MCP Tools](/images/agents/mcp_agent_tools.png)

Mehr erfahren:

- [MCP-Server konfigurieren](/docs/features/mcp)
- [Einführung in das Model Context Protocol](https://modelcontextprotocol.io/introduction)

### Zurückgestellte Tools [#deferred-tools]

Deferred Tools ermöglichen es Agenten, auf viele MCP Tools zuzugreifen, ohne diese vorab vollständig in den LLM-Kontext zu laden. Stattdessen sind Deferred Tools zur Laufzeit über einen **Tool Search**-Mechanismus auffindbar.

Dies ist besonders nützlich, wenn ein Agent Zugriff auf viele MCP Server mit Dutzenden von Tools hat – das Laden aller Tools würde einen großen Teil des Kontextfensters beanspruchen und die Antwortqualität verschlechtern.

**So funktioniert es:**

- Tools, die als "deferred" markiert sind, werden vom anfänglichen LLM-Kontext ausgeschlossen.
- Ein `ToolSearch`-Tool wird automatisch hinzugefügt, wodurch das LLM in der Lage ist, verzögerte Tools bei Bedarf zu entdecken und zu laden.
- Sobald das Tool entdeckt wurde, steht es für den Rest der Konversation zur Verfügung.

**Konfiguration von deferred tools:**

1. Öffnen Sie den Agent Builder und fügen Sie MCP Tools hinzu
2. Klicken Sie auf das Dropdown-Menü bei einem beliebigen MCP tool
3. „Defer Loading“ umschalten — verzögerte Tools zeigen ein Uhr-Symbol

**Hinweis:** Die `deferred_tools`-Funktion ist standardmäßig aktiviert. Sie kann über die [`librechat.yaml` Agenten-Konfiguration](/docs/configuration/librechat_yaml/object_structure/agents#capabilities) umgeschaltet werden.

### Aktivitätsgruppen [#activity-groups]

Aktivitätsgruppen fassen jeden zusammenhängenden Block von Agent-Überlegungen und Tool-Aufrufen unter einer generierten einzeiligen Überschrift zusammen, wodurch lange Abläufe leichter zu überblicken sind. Administratoren aktivieren diese mit `activityLabel` und können ein schnelleres Modell, einen anderen konfigurierten endpoint, einen benutzerdefinierten Prompt sowie Limits pro Durchlauf verwenden. Die Generierung der Überschrift ist ein separater Modellaufruf, dessen Tokens und Kosten aufgezeichnet werden. Siehe [Agent Activity Groups](/docs/configuration/librechat_yaml/object_structure/shared_endpoint_settings#agent-activity-groups).

Administratoren können `activityPhaseLabel` unabhängig aktivieren, um zwei oder mehr logische Aktivitäten vor der endgültigen Antwort in einer eingeklappten übergeordneten Zusammenfassung zu bündeln. Dies verleiht langen Abläufen eine übergeordnete Gliederung, während jede untergeordnete Aktivität erhalten bleibt. Phasen-Zusammenfassungen verwenden ihr eigenes Modell, ihren eigenen endpoint, ihren eigenen Prompt und ihr eigenes Limit pro Durchlauf, wobei auf die Einstellungen für activity-label und den Durchlauf zurückgegriffen wird.

Sobald ein zusammenhängender Ablauf mindestens zwei abgeschlossene, markierte Tool-Gruppen enthält, fasst LibreChat diese auf derselben Phasen-Kartenoberfläche zusammen, noch bevor eine optionale Phasenzusammenfassung eintrifft. Das neueste abgeschlossene untergeordnete Label fungiert als vorläufige Überschrift, während laufende Überlegungen und der noch in Bearbeitung befindliche Tool-Aufruf außerhalb der Zusammenfassung bleiben. Der geladene Verlauf verwendet dieselbe Gruppierung, und eine spätere, vom Server generierte Phasenzusammenfassung ersetzt die vorläufige Überschrift, ohne eine vom Leser geöffnete Karte zu schließen.

Wenn [Smooth Streaming](/docs/features/smooth_streaming) aktiviert ist, faltet eine neu generierte übergeordnete Zusammenfassung die sichtbaren Aktivitäten flüssig in die eingeklappte Gruppe zusammen. Geladener Verlauf wiederholt diesen Übergang nicht, und LibreChat respektiert die Einstellung des Geräts zur Reduzierung von Bewegungen (reduced-motion preference).

Kurzer Fortschrittstext verbleibt innerhalb seiner übergeordneten Phase. Wenn der Agent mit einer substanziellen Antwort beginnt, schließt LibreChat die Phase vor diesem Text, sodass das für den Benutzer sichtbare Ergebnis außerhalb der eingeklappten Zusammenfassung bleibt. Ein Durchlauf kann mehrere übergeordnete Phasen erstellen, wenn spätere Überlegungen oder Tools einen weiteren logischen Aktivitätsblock beginnen. Persistente Phasengrenzen werden neu ausgerichtet, wenn fehlerhafte oder ausgelassene Inhaltsbestandteile komprimiert werden, sodass die Gruppierung nach dem Neuladen konsistent bleibt.

Dateien, die innerhalb einer Phase erstellt wurden, bleiben in einer Medienzeile unterhalb der eingeklappten Karte sichtbar, anstatt darin verborgen zu sein. Markdown-Bildreferenzen, die einen reinen Dateinamen, `/mnt/data/...` oder einen `sandbox:`-Pfad verwenden, werden zu passenden Anhängen des Turns aufgelöst. Eine Datei wird nur dann aus der Medienzeile weggelassen, wenn ein Inline-Bild außerhalb der eingeklappten Phase erfolgreich aufgelöst wird, wodurch Duplikate verhindert werden, ohne sich auf fehlerhafte Referenzen zu verlassen.

Allgemeine Agenten- und MCP-Tool-Karten unterscheiden zwischen **Vorbereitung** (vor der SDK-Übergabe, was Genehmigungen oder andere Wartezeiten beinhalten kann) und **Aufruf** (SDK-Übergabe bis zum Ergebnis). Abgeschlossene Karten zeigen beide Intervalle an; das Aufrufintervall entspricht nicht notwendigerweise der Dauer der vorgelagerten MCP- oder ClickHouse-Ausführung. Früher gespeicherte Nachrichten sowie spezialisierte Code-, Bash-, Datei- und Speicherkarten behalten eine klar gekennzeichnete **Gesamtverstrichene** Laufschrittdauer bei. Gestoppte, abgebrochene, fehlgeschlagene und abgeschlossene Schritte behalten ihre jeweiligen Status bei, auch nach einem Neuladen der Konversation.

Während ein Tool ausgeführt wird, folgen die erweiterten Detailbereiche für Bash, Code ausführen und Dateierstellung den gestreamten Befehlen, dem Code oder dem Vorschaubereich bis zum Ende. Durch das Scrollen nach oben wird dieses automatische Mitlaufen pausiert, sodass die aktuelle Leseposition beibehalten wird.

Bash-Ausgaben werden als Text im Terminal-Stil gerendert. Lange Ausgaben werden auf die letzten 15 Zeilen eingekürzt, in denen normalerweise Fehler auftreten; verwenden Sie **Mehr anzeigen** und **Weniger anzeigen**, um sie zu erweitern oder einzuklappen, und die **Kopieren**-Schaltfläche, um die Ausgabe zu kopieren. Ein Befehl, der nichts ausgegeben hat, zeigt **Keine Ausgabe** an. Für Befehle, die in einem [angehängten Arbeitsbereich](/docs/features/code_interpreter#attached-environments-and-pairing) ausgeführt werden, wird ein fehlgeschlagener Befehl mit seinem Grund markiert (**Exit-Code N**, **beendet durch** ein Signal wie `SIGKILL` oder **Zeitüberschreitung**), und stderr wird separat von stdout formatiert. Ein abgeschlossener Befehl wird als **Befehl ausgeführt** gekennzeichnet, und eine Tool-Gruppe, die einen einzelnen Aufruf enthält, öffnet sich direkt mit den Details dieses Aufrufs.

### Live Reasoning Labels [#live-reasoning-labels]

Live-Reasoning-Labels ersetzen eine allgemeine **Thinking**- oder **Thoughts**-Überschrift durch eine kurze Orientierungshilfe, die sich weiterentwickelt, sobald ausreichend lange Reasoning-Streams auf oberster Ebene vorliegen. Das Label aktualisiert die bestehende Reasoning-Überschrift an Ort und Stelle; es fügt keine Nachrichtenteile hinzu und ordnet sie auch nicht neu an.

Das neueste Live-Reasoning-Label und der Antwort-Timer schimmern, während die Generierung aktiv ist. Abgeschlossenes Reasoning, Antworten älterer Geschwister-Threads und Labels, die sich nicht mehr am Live-Ende befinden, bleiben statisch.

Administratoren aktivieren dies mit `reasoningLabel` und können ein separates Modell, einen endpoint, einen Prompt, Aktualisierungsschwellenwerte sowie ein Limit für Aufrufe pro Durchlauf wählen. Jede Revision ist ein zusätzlicher Modellaufruf, dessen Token und Kosten aufgezeichnet werden. Siehe [Live Reasoning Labels](/docs/configuration/librechat_yaml/object_structure/shared_endpoint_settings#live-reasoning-labels) für Standardwerte, Routing-Prioritäten und Datenschutzaspekte.

### Tool Intent Labels [#tool-intent-labels]

Tool-Intent-Labels ersetzen generische Live-Tool-Status durch eine kurze Beschreibung, die vom Modell für den jeweiligen Aufruf verfasst wird. Administratoren müssen die Opt-in-Funktion `tool_intents` als [Agent-Fähigkeit](/docs/configuration/librechat_yaml/object_structure/agents#capabilities) hinzufügen. Native Tools verwenden Labels automatisch; erweitern Sie im Agent Builder einen MCP-Server und aktivieren Sie **Intent label** für einzelne Tools oder den gesamten Server.

Für Model Specs kann [`describeIntent`](/docs/configuration/librechat_yaml/object_structure/model_specs#describeintent) jedes berechtigte Tool aktivieren oder ausgewählte Tool-IDs bestimmen. Intent-Felder ergänzen das an das Modell gesendete Tool-Schema, sodass eine selektive Aktivierung den Schema-Token-Overhead reduzieren kann.

Intent-Labels gelten nicht für reine programmatische MCP-Tools, da Aufrufe innerhalb von Sandbox-Code keine einzelnen Tool-Karten rendern. Eine erweiterte programmatische Ausführung zeigt stattdessen eine kompakte Live-Ablaufverfolgung ihrer internen Aufrufe.

### Programmatischer Tool-Aufruf [#programmatic-tool-calling]

Programmatic Tool Calling (PTC) ermöglicht es Agenten, ausgewählte MCP Tools innerhalb der [Code Interpreter](/docs/features/code_interpreter) Sandbox auszuführen, anstatt jedes Tool direkt vom Modell aufrufen zu lassen. Das Modell erhält ein durch den Code Interpreter unterstütztes Orchestrierungstool, schreibt isolierten Code, der generierte Tool-Funktionen aufruft, und kann Schleifen, Bedingungen, Wiederholungsversuche und Ergebnisverarbeitung nutzen, bevor eine Antwort zurückgegeben wird.

Dies ist nützlich für mehrstufige Tool-Workflows, wie zum Beispiel das Abfragen mehrerer Ressourcen, das Paginieren durch Ergebnisse, das Vergleichen von Ausgaben oder das Transformieren von Tool-Antworten, bevor der Agent diese erklärt.

**Konfiguration programmatischer Tools:**

1. Aktiviere sowohl `programmatic_tools` als auch `execute_code` in den [`librechat.yaml` agents capabilities](/docs/configuration/librechat_yaml/object_structure/agents#capabilities).
2. Aktiviere Code Interpreter für den Agenten.
3. Fügen Sie MCP-Tools hinzu, erweitern Sie einen MCP-Server und schalten Sie **Programmatic** für einzelne Tools oder für den gesamten Server um. Programmatic-Tools zeigen ein Code-Symbol an.

Der Agent Builder hält programmatische Umschalter deaktiviert, bis Code Interpreter ausgewählt wird. Das Entfernen von Code Interpreter löscht sofort die programmatischen Auswahlen des Agenten. Beim Erstellen, Aktualisieren, Duplizieren und Wiederherstellen von Versionen entfernt der Server außerdem programmatische Aufruferoptionen, wann immer die `execute_code`-Fähigkeit oder das Code Interpreter-Tool nicht verfügbar ist; dies ermöglicht es, ältere, inkonsistente Agenten zu öffnen und zu korrigieren, ohne eine unbrauchbare Konfiguration beizubehalten.

**Hinweis:** `programmatic_tools` ist optional und nicht in der Standard-Funktionsliste für Agents enthalten. PTC erfordert außerdem eine Code Interpreter-Bereitstellung mit der Tool Call Server-Komponente. Zur Laufzeit schneidet LibreChat die aktuelle Caller-Capability-Projektion mit seinem vertrauenswürdigen Tool-Register, sodass Ereignisdaten die verfügbare Zuordnung zwar einschränken, aber kein Tool gewähren können. Nur aktive, registrierte programmatische Tools können aus der Sandbox aufgerufen werden; nicht registrierte Aufrufe werden abgelehnt.

Erweitern Sie die Code Interpreter-Karte während eines programmatischen Laufs, um eine terminalartige Ablaufverfolgung jedes internen Tool-Aufrufs, dessen Argument-Vorschau, Status, Dauer und etwaige Fehler zu sehen. Die Ablaufverfolgung ist für die aktuelle Browsersitzung live und wird nach einem Neuladen der Seite nicht wiederhergestellt.

### Hintergrund-Tool-Aufrufe [#background-tool-calls]

Hintergrund-Tool-Aufrufe ermöglichen es einem Agenten, einen lang laufenden, geeigneten Code Interpreter, MCP, Plugin oder Action-Tool zu starten und weiterzuarbeiten. Der ursprüngliche Aufruf kehrt sofort mit einer Aufgabenreferenz zurück. Bei einem gespeicherten Agenten werden unterstützte Vervollständigungen standardmäßig automatisch in einer nachfolgenden Fortsetzung zugestellt; `check_background_task` bleibt für expliziten Status, Steuerung, Artefakt-Sammlung und Wiederherstellung verfügbar.

`check_background_task` meldet `started_at` und die aktuelle `elapsed_ms`, während prozesslokale Arbeit ausgeführt wird. Nach Abschluss meldet es außerdem `settled_at` und friert `elapsed_ms` bei der abgeschlossenen Dauer ein. Ein aus dem persistenten Speicher wiederhergestelltes Endergebnis kann `settled_at` ohne Startzeit oder verstrichene Dauer enthalten, wenn der ursprüngliche prozesslokale Dispatch-Zeitstempel nicht verfügbar ist.

Um diese Funktion zu nutzen, muss ein Administrator die Opt-in-`run_in_background` [Agent-Fähigkeit](/docs/configuration/librechat_yaml/object_structure/agents#capabilities) hinzufügen. Konfigurieren Sie anschließend die geeigneten Tools im Agent Builder:

- **Code Interpreter:** Aktivieren Sie den Code Interpreter für den Agenten. Code-Ausführung und Shell-Befehle sind standardmäßig für die Hintergrundausführung berechtigt; deaktivieren Sie **Background execution** in den Werkzeugeinstellungen, um dies zu unterbinden.
- **MCP:** Öffnen Sie einen MCP-Server und markieren Sie einzelne Tools oder den gesamten Server als **Background**.
- **Plugin tools:** Öffnen Sie ein geeignetes Tool und aktivieren Sie **Background execution**.
- **Aktionen:** Aktivieren Sie die **Hintergrundausführung** für eine Aktion, um sich für jeden berechtigten Vorgang in dieser Aktion anzumelden. OAuth-Aktionen bieten diesen Schalter nicht. Ein Vorgang ist außerdem ausgeschlossen, wenn sein eigenes Schema bereits einen `run_in_background`-Parameter definiert, um eine Kollision mit dem Dispatch-Flag von LibreChat zu vermeiden.

Diese Einstellungen erlauben die Hintergrundausführung, erzwingen sie jedoch nicht. Das Modell entscheidet pro Aufruf selbst, ob ein geeignetes Tool im Hintergrund ausgeführt werden soll.

In LibreChat-Chats erscheinen stdout und generierte Dateien nach Abschluss von Hintergrundcode beim ursprünglichen Code-Aufruf anstatt beim späteren Abruf. Generierte Dateien werden zudem für nachfolgende Interaktionen beibehalten. Automatische Fortsetzungen präsentieren die abgeschlossene Arbeit in einer einklappbaren „Wake-up“-Aufgabenkarte, die mit der ursprünglichen Aufgabe verknüpft ist.

Wenn der Server diese Fortsetzung startet, nachdem der vorangegangene Vordergrundprozess bereits abgeschlossen wurde, wird die offene Konversation an die neue Generation angehängt und die Ausgabe der abgeschlossenen Aufgabe aktualisiert, ohne dass ein Neuladen erforderlich ist.

Automatische Vervollständigungs-Wakeups sind aktiviert, es sei denn, ein Administrator setzt [`endpoints.agents.backgroundTasks.completionWakeups: false`](/docs/configuration/librechat_yaml/object_structure/agents#backgroundtasks), wodurch das reine Abrufverhalten (Poll-only) wiederhergestellt wird. Der Host kann mehrere infrage kommende Vervollständigungen, die nur Inhalte enthalten, zu einer Fortsetzung zusammenfassen. Aufgaben, die ein Live-Artefakt erzeugen, erfordern weiterhin ein Polling des Prozesses, dem die Ausführung untersteht.

Administratoren können sich auch für eine Abbruchfunktion mit Eigentümer-Berechtigung entscheiden, indem sie [`endpoints.agents.backgroundTasks.ordinaryToolCancellation: true`](/docs/configuration/librechat_yaml/object_structure/agents#backgroundtasks) setzen. Die Aufgabe meldet, dass ein Abbruch angefordert wurde, bis der zugrunde liegende Aufruf abgeschlossen ist, und ihre Kapazität bleibt während dieses Zeitraums reserviert. Der Abbruch erfolgt kooperativ: Ein Tool, das das Abbruchsignal ignoriert, kann dennoch erfolgreich abgeschlossen werden. Die Steuerung gilt für gewöhnliche prozesslokale Hintergrund-Tools, einschließlich angehängter Bash-Instanzen, jedoch nicht für unabhängig verwaltete, losgelöste Subagents.

Nur berechtigte Tools zeigen die Einstellung an. Die gewöhnliche Hintergrundausführung ist prozesslokal und überlebt den Verlust ihres Worker-Prozesses nicht. Sobald jedoch ein reines Terminalergebnis gespeichert wurde, ist die automatische Zustellung dauerhaft und kann auf einem anderen Replikat fortgesetzt werden. Die prozesslokale Registrierung begrenzt laufende Aufgaben und gespeicherte Ergebnis-Payloads pro Konversation, Benutzer und Prozess; sie entfernt abgeschlossene Arbeiten, wenn dies sicher ist, und gibt ein bereichsbegrenztes Kapazitätsergebnis zurück, wenn ausstehende Verarbeitungen eine sichere Entfernung verhindern. Wenn ein Aufruf einen Abbruch ignoriert, beendet LibreChat die Erneuerung seines Producer-Lease nach einer einminütigen Nachfrist nach dem Abbruch und stellt die automatische Zustellung der Fertigstellung ein, ohne ungewisse externe Arbeiten fälschlicherweise als zeitlich abgelaufen zu markieren. Detached Subagents verwenden einen separaten dauerhaften Aufgaben- und Transkriptpfad mit Redis-gerouteten Live-Steuerungen; siehe [Detached Subagent Threads](/docs/features/subagents#detached-subagent-threads).

### Benutzer und Tool-Genehmigung anfordern [#ask-user-and-tool-approval]

Das **Ask User**-Tool ermöglicht es einem Agenten, einen Durchlauf zu pausieren, um fehlende Informationen anzufordern, Auswahlmöglichkeiten zu präsentieren oder zu bestätigen, wie weiter verfahren werden soll. Ein Aufruf kann bis zu vier zusammengehörige Fragen gruppieren. LibreChat präsentiert jeweils eine Frage mit Zurück-, Weiter-Schaltflächen und anklickbaren Fortschrittsschritten; Antworten bleiben beim Wechseln zwischen den Schritten erhalten, und Antworten bei Einzelauswahl führen automatisch zum nächsten Schritt, ohne dass eine Übermittlung erforderlich ist. Die Schaltfläche „Absenden“ erscheint im letzten Schritt, nachdem jede Frage beantwortet wurde, während „Überspringen“ den gesamten Stapel von jedem Schritt aus ablehnt. Jede Frage akzeptiert eine freie Antwort oder die vom Agenten vorgegebenen Einzel- oder Mehrfachauswahlmöglichkeiten. Während das Modell den Aufruf vorbereitet, streamt LibreChat die Fragen in eine Fortschrittskarte; das interaktive Formular ersetzt diese, sobald es bereit ist. Nach einer Übermittlung wird derselbe Durchlauf mit der vollständigen Antwortzuordnung fortgesetzt. Fügen Sie **Ask User** über den Tools-Marktplatz hinzu; Administratoren können die standardmäßige `ask_user_question`-Funktion entfernen, um sie auszublenden.

Das Zusammenklappen einer Karte mit mehreren Fragen versetzt den Composer zurück in seinen normalen Steer-or-Queue-Modus, während die pausierte Karte im Thread verbleibt. Die Karte kann weiterhin erweitert, beantwortet, übersprungen oder gestoppt werden. Eine Pause mit einer einzelnen Frage verwendet weiterhin den fokussierten Composer-Antwortmodus.

Übermittelte Antworten werden mit der resume-Aktion gespeichert, sodass ein Abbruch während der Initialisierung des fortgesetzten Laufs bereits akzeptierte Antworten nicht verwirft.

Nachdem ein Fragen-Datensatz abgeschlossen ist, wird er standardmäßig auf einen einzeiligen Tool-Eintrag reduziert, damit lange Antworten nicht das Transkript dominieren. Öffnen Sie ihn, um die Fragen und die beibehaltenen Zeilenumbrüche in den Antworten zu überprüfen. Die bestehende Einstellung **Auto-expand tool details** steuert ebenfalls diese abgeschlossene Ansicht; das Live-Formular bleibt geöffnet, solange noch eine Eingabe erforderlich ist.

Jede Frage akzeptiert eine optionale Überschrift mit bis zu 80 Zeichen, einen Fragetext mit bis zu 2.000 Zeichen, optionalen unterstützenden Kontext mit bis zu 4.000 Zeichen sowie bis zu 12 Auswahlmöglichkeiten. Die Bezeichnungen der Auswahlmöglichkeiten sind auf 280 Zeichen, die Werte der Auswahlmöglichkeiten auf 500 Zeichen und jede übermittelte Antwort auf 16.000 Zeichen begrenzt.

Administratoren können auch eine Überprüfung verlangen, bevor passende Tool-Aufrufe ausgeführt werden. Je nach Tool können Benutzer diese genehmigen, ablehnen, Argumente bearbeiten oder direkt antworten. Pausierte Ausführungen werden mit Checkpoints versehen, sodass sie nach der Entscheidung fortgesetzt werden können, auch auf einem anderen Replikat, wenn der standardmäßige MongoDB-Checkpointer verwendet wird. Die deployment-weite Tool-Genehmigung ist standardmäßig deaktiviert, während ein Agent, der eine angehängte Code-Umgebung verwendet, die [ask-by-default Sicherheitsrichtlinie](/docs/features/code_interpreter#attached-environment-tool-permissions) erhält, es sei denn, ein Administrator deaktiviert diese explizit. Siehe [`toolApproval` und `checkpointer`](/docs/configuration/librechat_yaml/object_structure/agents#toolapproval).

Während das Prüfungsfenster des Composers für eine ausstehende Genehmigung geöffnet ist, zeigt die entsprechende Thread-Karte die Anfrage als Datensatz an, anstatt die Entscheidungsschaltflächen zu duplizieren. Überprüfen Sie die Aufrufe im Fenster über dem Nachrichtenfeld und wählen Sie **Continue**. Das Einklappen des Fensters über den Composer-Chip stellt die Steuerelemente der Thread-Karte wieder her, wobei Ihre Entscheidungen beibehalten werden; ein erneutes Öffnen übergibt die Prüfung zurück an das Fenster. Karten für andere Aktionen behalten ihre eigenen Steuerelemente bei.

### Skills [#skills]

Skills ermöglichen es Agenten, wiederverwendbare Anweisungen aus `SKILL.md`-Definitionen zu laden. Sie können manuell im Chat mit `$` ausgewählt, vom Modell automatisch über den Skill-Katalog entdeckt oder bei jedem Turn immer angewendet werden. Der Agent Builder kann auch die eigenständige Laufzeit-Erstellung ermöglichen: Ein Agent kann einen Skill erstellen, ohne den bestehenden Katalog zu erhalten, oder ausgewählte Skills bearbeiten, wenn der Benutzer über die entsprechende Berechtigung verfügt.

Für Details zur Erstellung, zum Aufruf und zur Zugriffskontrolle siehe [Skills](/docs/features/skills).

### Memory [#memory]

Das **Memory**-Tool ermöglicht es einem Agenten, strukturierte Benutzermemoranden zu speichern, zu aktualisieren oder zu löschen, wenn der Benutzer ihn explizit dazu auffordert, sich etwas zu merken oder zu vergessen. Memory muss für die Bereitstellung konfiguriert, durch die Rollen- und Personalisierungseinstellungen des Benutzers erlaubt und auf dem Agenten aktiviert sein.

Standardmäßig verwendet ein Agent den geteilten persönlichen Speicherpool des Benutzers. Aktiviere **Keep memories separate for this agent**, um ihm eine private Partition pro Benutzer und pro Agent zuzuweisen. Der isolierte Agent sieht keine bestehenden geteilten Speicherinhalte oder Speicherinhalte, die von anderen isolierten Agenten erstellt wurden. Benutzer können das Memory-Panel nach persönlichen oder agentspezifischen Speicherinhalten filtern. Das Lesen, Erstellen oder Aktualisieren einer Agent-Partition erfordert den aktuellen Zugriff auf diesen Agent; das Löschen kann eine Partition weiterhin bereinigen, nachdem der zugehörige Agent entfernt wurde. Siehe [User Memory](/docs/features/memory#agent-memory).

### Artifacts [#artifacts]

Die Artifacts-Funktion ermöglicht es Ihrem Agenten, interaktive Inhalte zu generieren und anzuzeigen:

- Erstellen Sie React-Komponenten, HTML-Code und Mermaid-Diagramme
- Inhalte in einem eigenen Bereich neben dem Chat anzeigen, der auf Vollbild erweitert oder in einem eigenen Browserfenster geöffnet werden kann
- Konfigurieren Sie artefaktspezifische Anweisungen auf Agentenebene
- [Weitere Informationen zu Artifacts](/docs/features/artifacts)

Wenn aktiviert, wählen Sie einen von drei Anweisungsmodi:

- **Normal**: Fügt die Standard-Artifact-Anweisungen für React, HTML, SVG, Markdown und Mermaid hinzu.
- **shadcn/ui**: Fügt die Standardanweisungen sowie Anleitungen zum Erstellen von Benutzeroberflächen mit der shadcn/ui-Komponentenbibliothek hinzu.
- **Custom**: Behält das Artifact-Rendering bei, fügt jedoch keine integrierten Artifact-Anweisungen hinzu, wodurch die eigenen Anweisungen des Agenten die volle Kontrolle behalten.

Die Konfiguration von Artefakten auf Agentenebene ist der bevorzugte Ansatz, da sie im Vergleich zur älteren anwendungsweiten Konfiguration eine präzisere Steuerung ermöglicht.

Wenn Sie **Custom** auswählen, fügen Sie mindestens das grundlegende Artefakt-Format in Ihre Anweisungen ein.

Hier ist ein einfaches Beispiel für die minimal erforderlichen Anweisungen:

````md
When creating content that should be displayed as an artifact, use the following format:

:::artifact{identifier="unique-identifier" type="mime-type" title="Artifact Title"}

```
Your artifact content here
```

:::

For the type attribute, use one of:

- "text/html" for HTML content
- "application/vnd.mermaid" for Mermaid diagrams
- "application/vnd.react" for React components
- "image/svg+xml" for SVG images
````

### Übergaben [#handoffs]

Handoffs ermöglichen es einem primären Agenten, eine Konversation mit dem relevanten Kontext an einen spezialisierten Agenten zu übergeben. Öffnen Sie in den **Advanced settings** den Bereich für die Orchestrierung und fügen Sie bis zu 10 Handoff-Agenten hinzu. Jede konfigurierte Übergabe erstellt ein Transfer-Tool, das das Modell dynamisch auswählen kann, wenn die Expertise des Spezialisten benötigt wird.

For each handoff, you can add a description that helps the model choose the right specialist. You can also provide passthrough instructions describing what content the primary agent should generate for the specialist and optionally rename the content parameter from its default, `instructions`. Handoffs are always available in the Agent Builder; unlike Agent Chain and Subagents, they do not require an endpoint capability to be enabled. Tool calls from reachable handoff agents remain structured in later turns, so providers receive valid tool-call history instead of flattened text.

### Agent-Kette [#agent-chain]

- Konfiguriere die maximale Anzahl an Schritten für die Agent-Chain
- **Hinweis:** Greifen Sie über das Panel „Advanced Settings“ im Agent Builder auf diese Funktion zu.
- **Hinweis:** Diese Funktion befindet sich derzeit in der Beta-Phase und kann sich noch ändern.

Diese Funktion führt eine geschichtete Mixture-of-Agents-Architektur in LibreChat ein, bei der jeder Agent alle Ausgaben der Agenten aus der vorherigen Schicht als zusätzliche Informationen für die Generierung seiner Antwort verwendet, wie im [gleichnamigen "Mixture-of-Agents"-Paper](https://arxiv.org/abs/2406.04692) beschrieben.

### Subagents [#subagents]

Subagents ermöglichen es einem Agenten, eine fokussierte Aufgabe an einen isolierten untergeordneten Lauf oder ein gespeichertes Agenten-Team zu delegieren. Jedes untergeordnete Element erhält einen isolierten Kontext sowie eine isolierte Tool-Ausführung und gibt anschließend ein kompaktes Ergebnis an das übergeordnete Element zurück, anstatt den Kontext des übergeordneten Elements mit jedem Zwischenschritt zu füllen. Die losgelöste Arbeit des untergeordneten Elements bleibt zudem als navigierbarer Thread im Nur-Lese-Modus erhalten.

Subagents unterscheiden sich von Agent Chain: Chains koordinieren mehrere Agenten als Teilnehmer in einem Graphen, während Subagents von einem Agenten als Tool-Aufruf für eine begrenzte Delegation gestartet werden. LibreChat bewahrt den strukturierten Verlauf der Tool-Aufrufe, der für erreichbare untergeordnete Agenten und gespeicherte Teammitglieder über spätere Turns hinweg benötigt wird, während nicht verfügbare Tools aus dem aktiven Lauf herausgehalten werden. Informationen zur Einrichtung und zu den Limits finden Sie unter [Subagents](/docs/features/subagents).

### Erweiterte Einstellungen [#advanced-settings]

Erweiterte Einstellungen für Ihren Agenten (zu finden in der Ansicht „Erweitert“ des Agenten-Formulars) außerhalb der „Funktionen“ (capabilities).

#### Maximale Agenten-Schritte [#max-agent-steps]

Diese Einstellung ermöglicht es Ihnen, die Anzahl der Schritte zu begrenzen, die ein Agent in einem „Run“ ausführen kann. Dies bezieht sich auf die Agenten-Schleife, bevor eine endgültige Antwort gegeben wird.

Wenn dies nicht konfiguriert wird, liegt der Standardwert bei 25 Schritten, Sie können diesen jedoch an Ihre Bedürfnisse anpassen. Als Administrator können Sie sowohl einen globalen Standardwert als auch ein globales Maximum in der Datei [`librechat.yaml`](/docs/configuration/librechat_yaml/object_structure/agents#recursionlimit) festlegen.

Wenn ein Turn sein vollständiges Schritt-Budget ausschöpft, bewahrt LibreChat die Teilantwort und die Tool-Aufrufe auf, anstatt sie durch einen Fehler zu ersetzen. Die Nachricht bietet **Keep going** an, was einen neuen Turn mit einem frischen Tool-Budget startet, sowie **Answer now**, was den Agenten auffordert, basierend auf der bereits geleisteten Arbeit ohne weitere Tools zu antworten. Das Schließen des Hinweises wirkt sich nur auf die aktuelle Browseransicht aus.

Administratoren können außerdem gestreamte Tool-Call-Argumente und Model-Delta-Ereignisse mit [Agent stream circuit breakers](/docs/configuration/librechat_yaml/object_structure/agents#stream-circuit-breakers) begrenzen.

Ein „Schritt“ (step) bezieht sich entweder auf eine AI-API-Anfrage oder eine Runde der Tool-Nutzung (1 oder mehrere Tools, abhängig davon, wie viele Tool-Aufrufe das LLM aus einer einzelnen Anfrage bereitstellt).

Eine einzelne Antwort ohne Tool-Nutzung entspricht 1 Schritt. Eine einzelne Runde der Tool-Nutzung besteht normalerweise aus 3 Schritten:

1. API-Anfrage -> 2. Tool-Nutzung (1 oder mehrere Tools) -> 3. Nachfolgende API-Anfrage

## Dateiverwaltung [#file-management]

Agents unterstützen mehrere Möglichkeiten, mit Dateien zu arbeiten:

### In der Chat-Oberfläche [#in-chat-interface]

Wenn Sie mit einem Agenten chatten, haben Sie vier Upload-Optionen:

1. **Bilder hochladen**
   - Lädt Bilder für native Vision-Modellunterstützung hoch
   - Sendet Bilder direkt an den Model-Provider

2. **Als Text hochladen** (erfordert `context`-Fähigkeit)
   - Extrahiert und fügt den vollständigen Dokumentinhalt in die Konversation ein
   - Verwendet standardmäßig Text-Parsing; erweitert durch OCR, falls konfiguriert
   - Inhalt existiert nur in der aktuellen Konversation
   - Siehe [Upload as Text](/docs/features/upload_as_text)

3. **Upload für die Dateisuche** (erfordert die `file_search`-Funktion, eingeschaltet)
   - Nutzt semantische Suche (RAG) mit Vektorspeichern
   - Gibt relevante Chunks über Tool-Nutzung zurück
   - Optimal für große Dokumente/mehrere Dateien
   - Nicht optimal für strukturierte Daten (CSV, Excel, JSON, etc.)

4. **Upload für Code Interpreter** (erfordert die aktivierte `execute_code`-Funktion)
   - Fügt Dateien zur Code-Interpreter-Umgebung hinzu
   - Optimal für strukturierte Daten (CSV, Excel, JSON, etc.)
   - Weitere Informationen zum [Code Interpreter](/docs/features/code_interpreter)

### Im Agent Builder [#in-agent-builder]

Beim Konfigurieren eines Agents können Sie Dateien in verschiedenen Kategorien anhängen:

1. **Bild-Upload**: Für visuelle Inhalte, auf die der Agent verweisen kann
2. **Dateisuche-Upload**: Dokumente für RAG-Funktionen
3. **Code Interpreter Upload**: Dateien für die Code-Verarbeitung
4. **Dateikontext**: Dokumente mit extrahiertem Text zur Ergänzung von Agenten-Anweisungen

**Dateikontext** nutzt die `context`-Funktion und funktioniert genau wie ["Als Text hochladen"](/docs/features/upload_as_text) – standardmäßig wird Text-Parsing verwendet, das bei entsprechender Konfiguration durch OCR erweitert wird. Der Text wird zum Zeitpunkt des Hochladens extrahiert und in den Anweisungen des Agenten gespeichert. Dies ist ideal, um Agenten dauerhaftes Wissen aus Dokumenten, PDFs, Codedateien oder Bildern mit Text zur Verfügung zu stellen.

**Verarbeitungspriorität:** OCR > STT > Text-Parsing (identisch mit „Als Text hochladen“)

**Hinweis:** Der extrahierte Text ist Teil der Systemanweisungen des Agenten.

## Teilen und Berechtigungen [#sharing-and-permissions]

Agents nutzen das granulare [Access Control](/docs/features/access_control) System von LibreChat. Jeder Agent verfügt über eine eigene Access Control List (ACL) und kann für bestimmte **Benutzer**, **Gruppen**, **Rollen** oder **öffentlich** freigegeben werden, jeweils mit einer gewählten Berechtigungsstufe.

Vertrauenswürdige Dienste können zudem Agents, angehängte Dateien und Skills über die Beta [Agent Management API](/docs/features/agents_api#agent-management-api) verwalten. Administratoren binden jeden OIDC-Maschinen-Client an einen bestehenden LibreChat-Benutzer und -Mandanten; jede Anfrage erbt die aktuellen Rollenberechtigungen und Ressourcen-ACLs dieses Benutzers, anstatt einen separaten administrativen Zugriff zu erhalten.

### Zugriffsrollen [#access-roles]

Wenn ein Agent geteilt wird, wird dem Empfänger eine von drei Rollen zugewiesen:

| Rolle | Was der Berechtigte tun kann |
| ---------- | ----------------------------------------------------------------------------------------------------- |
| **Viewer** | Den Agenten in Unterhaltungen verwenden; kann den Builder nicht öffnen und keine Anweisungen, Tools oder angehängten Dateien sehen |
| **Editor** | Anzeigen + Ändern der Anweisungen, des Modells, der Tools und der Dateien des Agenten |
| **Owner** | Volle Kontrolle: Anzeigen, Bearbeiten, Löschen und erneutes Teilen des Agenten |

Der ursprüngliche Autor und die Administratoren behalten unabhängig von der ACL immer die volle Kontrolle.

### Teilen eines Agents [#sharing-an-agent]

1. Öffnen Sie den Agenten im Agent Builder
2. Klicken Sie auf die Schaltfläche **Share** in der Fußzeile (sichtbar, wenn Sie der Ersteller oder ein Administrator sind oder die `SHARE`-Berechtigung für diesen spezifischen Agenten erhalten haben).
3. Suchen Sie in der Personenauswahl nach Benutzern, Gruppen oder Rollen und weisen Sie jedem eine Rolle zu
4. Optional kannst du **Public** aktivieren, um den Agenten für alle auf der Instanz sichtbar zu machen (erfordert die `SHARE_PUBLIC` Funktionsberechtigung).

Agent-Karten und Landing-Views zeigen den konfigurierten Support-Kontakt an. Wenn keiner festgelegt ist, kann LibreChat auf den Anzeigenamen des ersten auflösbaren Eigentümers zurückgreifen, legt jedoch die E-Mail-Adresse des Eigentümers nicht offen, es sei denn, sie wurde explizit als Support-Kontakt konfiguriert.

Konversationsoberflächen behalten den Agenten als sichtbare Identität bei und greifen nicht auf das zugrunde liegende Modell oder das Model-spec-Label zurück.

Für vollständige Details zu Principals, Berechtigungsbits und wie ACLs mit rollenbasierten Funktionsberechtigungen kombiniert werden, siehe [Access Control](/docs/features/access_control).

### Agent Marketplace [#agent-marketplace]

Der **Agent Marketplace** ermöglicht es Benutzern, die ihnen zur Verfügung stehenden Agents zu durchsuchen. Öffnen Sie ihn über **Agent Marketplace** in der Seitenleiste; der Eintrag erscheint nur für Benutzer, deren Rolle die Nutzung des Marketplace erlaubt.

- **Durchsuchen und suchen**: Agents werden in einem Raster angezeigt. Verwenden Sie das Suchfeld, um Agents nach Name oder Beschreibung zu finden, und die Kategorie-Buttons (wie **Top Picks**, **All** oder eine bestimmte Kategorie), um die Liste einzugrenzen.
- **Sortieren**: Verwenden Sie **Sortieren nach**, um Agents nach **Neueste zuerst** (Standard), **Älteste zuerst**, **Beliebt** (am häufigsten angeheftet) oder **Nach Erstellername** zu ordnen.
- **Meine Agents**: Aktivieren Sie **Meine Agents**, um nur die von Ihnen erstellten Agents anzuzeigen. Das Aktivieren über **Top-Empfehlungen** schaltet auf **Alle** um.
- **Freigabefähige Ansichten**: Suche, Sortierung und der Filter **My agents** werden in der Seiten-URL beibehalten (`?q=`, `?sort=`, `?mine=1`), sodass eine gefilterte Ansicht als Lesezeichen gespeichert oder geteilt werden kann.

Wählen Sie eine Agentenkarte aus, um deren Detaildialog zu öffnen, der die vollständige Beschreibung und den Kontakt des Agenten sowie die folgenden Aktionen anzeigt:

- **Pin** (Anheften) oder **Unpin** (Lösen): Füge den Agenten zu deinen angehefteten Agenten hinzu oder entferne ihn daraus.
- **Link kopieren**: Kopieren Sie einen Link, der einen neuen Chat mit dem Agenten startet.
- **Start Chat**: Starten Sie eine neue Unterhaltung mit dem Agenten.
- **Einen Gesprächsstarter ausprobieren**: Wenn der Agent über [conversation starters](#conversation-starters) verfügt, wählen Sie einen aus, um einen neuen Chat zu öffnen, bei dem dieser Prompt bereits in der Nachrichteneingabe steht. Er wird nicht automatisch gesendet, sodass Sie ihn vorher bearbeiten können.

Administratoren können den Zugriff mit der Einstellung [`interface.marketplace`](/docs/configuration/librechat_yaml/object_structure/interface#marketplace) und den unter [Zugriffskontrolle](/docs/features/access_control) beschriebenen Rollenberechtigungen steuern.

### Administratoren-Steuerelemente [#administrator-controls]

Administratoren haben Zugriff auf globale Berechtigungseinstellungen innerhalb der Benutzeroberfläche des Agent Builders:

- Agent-Freigabe für alle Benutzer aktivieren/deaktivieren
- Berechtigungen für die Agent-Nutzung steuern
- Rechte zur Erstellung von Agenten verwalten
- Konfigurieren plattformweiter Einstellungen

In einer nicht bereichsbezogenen Single-Tenant-Bereitstellung ist das erste für die Instanz erstellte Konto ein Administrator. Tenant-scoped Bereitstellungen stufen ihren ersten registrierten Benutzer nicht automatisch hoch; stellen Sie Tenant-Administratoren über einen vertrauenswürdigen administrativen Prozess bereit. Wenn Sie manuell einen Administrator hinzufügen müssen, können Sie auf [MongoDB zugreifen](/docs/configuration/mongodb/mongodb_auth) und das Profil des Benutzers aktualisieren:

```
db.users.updateOne(
  { email: 'USER_EMAIL_ADDRESS' },
  { $set: { role: 'ADMIN' } }
)
```

Die Verwendung von Agents für alle Benutzer kann ebenfalls über die Konfiguration deaktiviert werden, [weitere Informationen](/docs/configuration/librechat_yaml/object_structure/interface).

Berechtigungen auf Funktionsebene (wer Agents _verwenden_, _erstellen_, _teilen_ oder _öffentlich teilen_ darf) werden über das [**LibreChat Admin Panel**](/docs/features/admin_panel) für jede Rolle verwaltet, einschließlich aller benutzerdefinierten Rollen. Der [`interface.agents`](/docs/configuration/librechat_yaml/object_structure/interface#agents)-Block in der `librechat.yaml` kann weiterhin beim Start Standardwerte für die integrierte `USER`-Rolle festlegen, aber das Admin Panel ist der empfohlene Weg, um diese zukünftig zu bearbeiten.

### Teilen auf Benutzerebene [#user-level-sharing]

Einzelne Benutzer können:

- Teilen Sie ihre Agents mit bestimmten Benutzern, Gruppen oder Rollen (sofern `SHARE` für ihre Rolle aktiviert ist)
- Mache Agents für jeden auf der Instanz sichtbar (wenn `SHARE_PUBLIC` aktiviert ist)
- Weisen Sie jedem Empfänger eine unterschiedliche Zugriffsebene zu (Viewer / Editor / Owner)
- Teilen Sie Inhalte erneut oder widerrufen Sie den Zugriff jederzeit über den Dialog zum Teilen.

## Steuerung und Warteschlangen-Nachrichten [#steering-and-queued-messages]

Während ein Agent antwortet, können Sie auf zwei Arten eine weitere Nachricht über den [composer](/docs/features/composer) senden:

- **Steer** fügt die Nachricht in den aktuellen Durchlauf beim nächsten Tool- oder Agent-Schritt ein, sodass der Agent seine Arbeit vor dem Abschluss anpassen kann.
- **Queue** hält die Nachricht zurück und sendet sie als normalen Folge-Turn, nachdem die aktuelle Antwort abgeschlossen ist.

Für gespeicherte Agent-Konversationen auf einem aktuellen Server werden gewöhnliche, in die Warteschlange eingereihte Follow-ups in MongoDB gespeichert. LibreChat bewahrt deren FIFO-Reihenfolge und überträgt deren Text, Anhänge, zitierte Auszüge und manuell ausgewählte Skills über Browser-Verbindungsabbrüche, App-Neustarts und Replica-Handoffs hinweg. Die Verarbeitung wartet, bis die vorherige Antwort abgeschlossen ist, bevor der nächste Turn zugelassen wird. Diese Dauerhaftigkeit ist automatisch und erfordert keinen YAML- oder Umgebungsschalter; ältere Server und kurze Startfenster ohne eine aktive Generation-Epoche behalten die clientseitige Kompatibilitätswarteschlange bei.

Die Server-Zulassung wird innerhalb jeder Konversations-Warteschlangenspur serialisiert. Wenn die Nachweis-Vorgeschichte oder die Besitzverhältnisse bei gemischten Versionen mehrdeutig sind, zeigt LibreChat **Awaiting reconciliation** an und blockiert oder verwirft den betroffenen Warteschlangen-Turn, anstatt zu raten und ihn in der falschen Reihenfolge zu starten.

**Steer sooner** weist den Agenten an, die Nachricht am nächsten sicheren Punkt entgegenzunehmen, anstatt auf den nächsten Tool-Schritt zu warten. Wenn noch kein Antworttext oder keine Tool-Aktivität sicher beibehalten werden kann, wartet LibreChat eine kurze Karenzzeit ab, verwirft den stummen oder nur auf Schlussfolgerungen basierenden Versuch, fügt die Nachricht ein und startet das Modell mit dieser Anweisung neu. Sobald Antworttext beibehalten werden kann, hält LibreChat an einer für den Anbieter sicheren Grenze an, bewahrt die Teilantwort auf, fügt die Nachricht ein und setzt dieselbe Assistentenantwort fort. Ein laufender Tool-Aufruf wird durch das Steuern nicht verworfen oder unterbrochen; die Nachricht wird angewendet, sobald diese Arbeit eine sichere Grenze erreicht.

Verwenden Sie **Stop**, um aktives Reasoning zu beenden und den Abbruch eines Tool-Aufrufs im Vordergrund anzufordern. Stop leitet den Abbruch an signalfähige Tools im Vordergrund weiter; losgelöste Hintergrundprozesse behalten ihren unabhängigen Lebenszyklus bei. Verwenden Sie das dedizierte Composer-Steuerelement, wählen Sie es aus dem Menü der Senden-Schaltfläche oder drücken Sie `Command/Ctrl + Shift + .`. Die Aktion greift auf die gewöhnliche Steuerung zurück, wenn die Bereitstellung den aktiven Provider-Stream nicht unterbrechen kann.

Unter **Einstellungen → Chat** legt **Während der Generierung bewirkt die Eingabetaste** die Standardaktion fest. Das Menü der Senden-Schaltfläche kann diese Wahl für eine einzelne Nachricht überschreiben, und **Früheres Steuern bei Eingabetaste** sorgt dafür, dass die Eingabetaste den früheren sicheren Punkt anfordert, wenn Steuern die Standardeinstellung ist.

Dateien und [zitierte Auszüge](/docs/features/message_actions#quote-excerpts) werden mit Steer-, Queue- und Interrupt-Nachrichten übertragen. Manuell ausgewählte Skills bleiben für den nächsten vollständigen Turn bereitgestellt, anstatt an einen laufenden Steer-Vorgang angehängt zu werden.

Ausstehende Steer erscheinen am Ende der Streaming-Antwort, wo sie verbleiben, bis der Server sie in den Ablauf einfügt. Ihr Empfang schreitet von **Sending** zu **Delivered** fort, dann zu **Steer sooner requested**, wenn ein früherer sicherer Punkt angefordert wurde, und schließlich zu **Applied** mit einem doppelten Häkchen am unteren rechten Rand der Inline-Nachricht. Bestätigte angewendete Empfangsbestätigungen bleiben nach dem Neuladen sowie in Freigabe- oder Suchansichten sichtbar; bei unsicherer oder fehlgeschlagener Zustellung wird niemals ein bestätigendes Häkchen angezeigt. Sobald die Nachricht bestätigt wurde, kann das Nachrichtenmenü den Steer zur Bearbeitung zurückfordern, ihn in ein in die Warteschlange eingereihtes Follow-up umwandeln oder ihn abbrechen und seinen Text sowie die Anhänge im Composer wiederherstellen. LibreChat vermeidet das Überschreiben eines neueren Entwurfs; falls der Composer nicht mehr verfügbar ist, wird die zurückgeforderte Nachricht stattdessen in der Warteschlange beibehalten. Ein fehlgeschlagener Steer bleibt verfügbar, um ihn erneut zu versuchen, zu bearbeiten, in die Warteschlange einzureihen oder zu entfernen.

In der Warteschlange befindliche Follow-ups erscheinen in einer Liste oberhalb des Composers. Jedes davon kann bearbeitet (**Edit message**), entfernt (**Remove message**), mit **Send now** sofort gesendet oder durch Ziehen am Griff oder durch Drücken der Pfeiltasten neu angeordnet werden. In der Warteschlange befindliche Follow-ups können auch in eine Steuerung (Steer) umgewandelt werden, während der Durchlauf noch aktiv ist, oder mit **Steer sooner** eskaliert werden. Laufende Steuerungen bieten die gleiche Eskalationsmöglichkeit, solange sie noch auf eine Tool-Grenze warten. Das Entfernen einer servergestützten Nachricht aus der Warteschlange bricht zuerst deren dauerhafte Quelle ab und stellt sie dann, wenn möglich, in einem leeren Composer wieder her. Wenn die vorangegangene Antwort abgebrochen wird oder fehlschlägt, markiert LibreChat den betroffenen Warteschlangen-Turn als fehlgeschlagen, damit er überprüft werden kann, anstatt ihn stillschweigend zu senden.

Eine Konversation kann bis zu 100 aktive, in der Warteschlange befindliche Turns enthalten. Jeder in der Warteschlange befindliche Turn akzeptiert bis zu 16.000 Zeichen und 10 Dateien. Unabhängig davon akzeptiert ein aktiver Run bis zu 10 ausstehende Steers; jeder Steer kann bis zu 10 Dateien enthalten und ist durch [`STEER_MAX_LENGTH`](/docs/configuration/dotenv#agent-conversation-controls) begrenzt. **Steer sooner** verwendet weiterhin den Live-Steering-Pfad, anstatt einen in der Warteschlange befindlichen Turn an den Anfang der dauerhaften FIFO-Spur zu verschieben.

Redis-gestützte Multi-Replica-Bereitstellungen verhandeln das Generation Protocol v2 automatisch. Befolgen Sie die [Anleitung zur Kompatibilität des Generation Protocols](/docs/configuration/redis#generation-protocol-compatibility), wenn Sie von einer Version älter als `v0.8.8-rc1` aktualisieren.

### Hinweise [#notes]

- Anweisungen, Modellparameter, angehängte Dateien und Tools werden dem Benutzer nur dann angezeigt, wenn er über Bearbeitungsberechtigungen verfügt.
  - Ein Agent kann alle angehängten Daten, seien es Anweisungen oder Dateien, während einer Unterhaltung preisgeben. Stellen Sie daher sicher, dass Ihre Anweisungen robust dagegen sind, bevor Sie Editor/Owner-Zugriff gewähren oder den Agenten öffentlich machen.
- Nur ursprüngliche Ersteller, Administratoren und Berechtigte mit Eigentümer-Rechten können geteilte Agents löschen.
- Agents sind für Autoren privat, sofern sie nicht geteilt werden

## Agent Event Delivery [#agent-event-delivery]

LibreChat enthält eine quellneutrale Bereitstellungsschicht für asynchrone Agent-Ereignisse. Bereitstellungseigene Adapter können einen verifizierten Webhook, eine Warteschlangennachricht, ein MCP-Ereignis, ein Kanalereignis oder ein internes Produktereignis in einen neuen Agent-Lauf (`fire`), eine neue Runde für einen bestehenden gespeicherten Agenten und Zweig (`continue`) oder eine Mutation eines aktiven Laufs (`steer`) normalisieren. Adapter bleiben dafür verantwortlich, ihre native Quelle zu authentifizieren, Payloads zu bereinigen und vertrauenswürdige Ziele auszuwählen, bevor sie diese in die Warteschlange einreihen.

Die Beta [Agents API event endpoints](/docs/features/agents_api#agent-events) stellen authentifizierten `fire`-, `continue`- und `steer`-Zugriff für Remote Agents API-Schlüssel bereit. Externe Systeme können einen Quell-Akteur an einen direkten untergeordneten Agenten binden und diesen Akteur über Ereignisse hinweg fortsetzen, ohne dass ein zusätzlicher Funktionsschalter erforderlich ist. LibreChat leitet den Benutzer, den Mandanten und die Quellidentität aus dem API-Schlüssel ab, erzwingt den Agenten-Zugriff sowie Inhaltsfilter und erfordert einen Idempotenz-Schlüssel. Dies ist kein nicht authentifizierter Allzweck-Webhook-Empfänger; anbieterspezifische Adapter müssen weiterhin native Webhook-Signaturen verifizieren, bevor sie diesen aufrufen.

Die experimentelle Funktion [Scheduled Chats](/docs/features/scheduled_chats) ist der erste integrierte Producer von LibreChat für diese Ebene. Sie erstellt wiederkehrende `fire`-Zustellungen für gespeicherte Agents und ist deaktiviert, bis ein Administrator sie aktiviert. Losgelöste Subagents verwenden automatisch eine idempotente `continue`-Zustellung, um einen gespeicherten übergeordneten Agent zu wecken, nachdem ein untergeordneter Agent abgeschlossen wurde; abgebrochene untergeordnete Agents und kurzlebige übergeordnete Agents sind davon ausgeschlossen.

MongoDB speichert begrenzte versionierte Envelopes, Idempotenz-Schlüssel, Ordering Lanes, Leases, Wiederholungsverläufe, dauerhafte Empfangsbestätigungen und Dead Letters. Worker verwenden eine At-least-once-Zustellung mit Fenced Claims und begrenztem exponentiellem Backoff; erfolgreiche Empfangsbestätigungen laufen nach 90 Tagen ab, während Dead Letters eine explizite, vertrauenswürdige Wiedereinreihung erfordern. Fire-Zustellungen erstellen eine neue Konversation. Continue-Zustellungen erstellen einen neuen Turn auf dem exakten Konversationszweig und warten, während dieser Zweig läuft, pausiert ist oder abgeschlossen wird. Gebundene Akteure verfügen zudem über ein automatisches Postfach: Ein Akteur wartet auf das Ergebnis der Bearbeitung seines aktuellen Turns, bevor das nächste Ereignis versendet wird, während verschiedene Akteure parallel laufen können. Steer-Zustellungen müssen die bestehende Konversation und Generation identifizieren und eine strikte Zulassung verwenden, damit mehrdeutige Wiederholungen nicht dieselbe Anweisung zweimal einschleusen können.

Bei gebundenen Fortsetzungen (bound continuations) startet ein erfolgreicher Transport einen separaten, dauerhaften Verarbeitungslebenszyklus. Eine Zustellung schreitet von `started` zu `applied`, `completed_no_action`, `failed` oder `cancelled` fort. Quellen können mit `expectedAction` ein exaktes Tool und eine optionale Teilmenge von Argumenten erfordern; LibreChat meldet `applied` nur bei vom Host beobachteten, übereinstimmenden Tool-Nachweisen, niemals aufgrund von durch das Modell geschriebener Prosa. Kompatible Beobachtungsereignisse können sich einen begrenzten `coalesce.key`-Batch teilen, während sie pro Quellereignis einen Idempotenz-Datensatz und eine Empfangsbestätigung beibehalten. Die Checkpoint-Fortsetzung wird verwendet, wenn sie kompatibel ist, andernfalls wird auf den dauerhaften Nachrichtenverlauf zurückgegriffen.

Bound Event Actors können für "Ask User" oder Tool-Genehmigungen pausieren und den exakt signierten Actor-Aufruf über die normale Human-in-the-Loop-Schnittstelle von LibreChat fortsetzen. Das Postfach des Actors bleibt blockiert, bis diese Pause fortgesetzt oder abgeschlossen wird, wodurch verhindert wird, dass ein späteres Ereignis die Entscheidung überholt. Diese Actors erfordern den persistenten MongoDB-Checkpointer. LibreChat wählt die Checkpoint-Fortsetzung oder die Rekonstruktion der persistenten Historie automatisch basierend auf dem Actor-Status und der Anforderungsfähigkeit aus; bestehende protocol-v1-Arbeiten verbleiben auf dem Verlaufspfad, bis sie vollständig abgearbeitet sind.

Von Event-Akteuren gestartete Detached Actions werden automatisch aktiviert, wenn der integrierte Generation-Store Unterstützung dafür anzeigt. Der Akteur bleibt ausgesetzt, bis ein terminaler Nachweis seine ursprüngliche Aufrufung fortsetzt, daher reicht ein Hintergrundstart allein nicht aus, um `expectedAction` zu erfüllen. Der In-Memory-Store hält diesen Lebenszyklus konsistent, solange sein Prozess aktiv bleibt. Redis fügt eine dauerhafte Neustart-Wiederherstellung und eine Replika-Übergabe hinzu. Die von der Capability gesteuerte Abschlussarbeit wird während eines Mixed-Version-Drains von älteren Workern isoliert; Operatoren wählen dieses Verhalten nicht über ein Feature-Flag aus.

Der Ausführungshost ruft normalerweise den gebundenen Listener des aktuellen Prozesses auf. Konfigurieren Sie [`endpoints.agents.eventDriven.selfUrl`](/docs/configuration/librechat_yaml/object_structure/agents#eventdriven) nur dann, wenn dieser vertrauenswürdige interne Zulassungspfad einen anderen HTTP-Ursprung durchlaufen muss, wie beispielsweise ein TLS-Frontend.

## Best Practices [#best-practices]

- Geben Sie klare, spezifische Anweisungen für Ihren Agenten
- Überlegen Sie sorgfältig, welche Tools für Ihren Anwendungsfall erforderlich sind.

- Überprüfen Sie die Berechtigungseinstellungen, bevor Sie Agents teilen
- Testen Sie Ihren Agenten gründlich, bevor Sie ihn für andere Benutzer bereitstellen.

## Zusammenfassung [#recap]

1. Wählen Sie „Agents“ aus dem endpoint-Dropdown-Menü
2. Öffnen Sie das Agent Builder-Panel
3. Füllen Sie die erforderlichen Agent-Details aus
4. Konfigurieren Sie die gewünschten Funktionen (Code Interpreter, File Search, File Context, etc.)
5. Füge notwendige Tools und Dateien hinzu
6. Legen Sie bei Bedarf Freigabeberechtigungen fest
7. Erstellen und verwenden Sie Ihren Agenten

Beim Chatten mit Agents können Sie:

- Verwenden Sie „Upload as Text“, um den vollständigen Dokumentinhalt in Unterhaltungen einzubeziehen (standardmäßige Textanalyse, erweitert durch OCR)
- Verwenden Sie "Upload for File Search" für die semantische Suche über Dokumente (erfordert RAG API)
- Fügen Sie Dateien zum „Dateikontext“ (File Context) des Agenten hinzu, um den vollständigen Inhalt einer Datei als Teil der Systemanweisungen des Agenten einzubeziehen.

## Migration erforderlich (v0.8.0-rc3+) [#migration-required-v080-rc3]

<Callout type="warning" title="Wichtig: Migration der Agenten-Berechtigungen erforderlich">
  Ab Version v0.8.0-rc3 verwendet LibreChat ein neues, auf Access Control Lists (ACL) basierendes Berechtigungssystem für Agents. Wenn Sie von einer früheren Version aktualisieren, müssen Sie die Agent-Berechtigungsmigration für bestehende Agents ausführen, damit diese weiterhin zugänglich bleiben.
</Callout>

### Was die Migration bewirkt [#what-the-migration-does]

Die Migration der Agentenberechtigungen stellt Ihre Agenten von einem einfachen Eigentumsmodell auf ein ausgefeiltes ACL-basiertes System mit mehreren Berechtigungsstufen um:

- **OWNER**: Volle Kontrolle über den Agenten
- **EDITOR**: Kann den Agenten anzeigen und bearbeiten
- **VIEWER**: Schreibgeschützter Zugriff auf den Agenten

Ohne die Durchführung dieser Migration sind bestehende Agents über die neuen berechtigungsbewussten API-endpoints nicht zugänglich.

### Ausführen der Migration [#running-the-migration]

Wählen Sie den entsprechenden Befehl basierend auf Ihrer Bereitstellungsmethode:

#### 1. Für die standardmäßige `docker-compose.yml` (falls Sie `docker compose up` verwenden, um die App zu starten): [#1-for-the-default-docker-composeyml-if-you-use-docker-compose-up-to-start-the-app]

**Änderungen in der Vorschau anzeigen (Testlauf):**

```bash
docker compose exec api npm run migrate:agent-permissions:dry-run
```

**Migration ausführen:**

```bash
docker compose exec api npm run migrate:agent-permissions
```

**Benutzerdefinierte Batch-Größe (für große Datensätze):**

```bash
docker compose exec api npm run migrate:agent-permissions:batch
```

#### 2. Für die `deploy-compose.yml` [#2-for-the-deploy-composeyml]

Wenn Sie dem [Ubuntu Docker Guide](/docs/remote/docker_linux) gefolgt sind:

**Änderungen in der Vorschau anzeigen (Testlauf):**

```bash
docker exec -it LibreChat-API /bin/sh -c "cd .. && npm run migrate:agent-permissions:dry-run"
```

**Migration ausführen:**

```bash
docker exec -it LibreChat-API /bin/sh -c "cd .. && npm run migrate:agent-permissions"
```

**Benutzerdefinierte Batch-Größe (für große Datensätze):**

```bash
docker exec -it LibreChat-API /bin/sh -c "cd .. && npm run migrate:agent-permissions:batch"
```

#### 3. Für die lokale Entwicklung (vom Projektstammverzeichnis aus): [#3-for-local-development-from-project-root]

**Änderungen in der Vorschau anzeigen (Testlauf):**

```bash
npm run migrate:agent-permissions:dry-run
```

**Migration ausführen:**

```bash
npm run migrate:agent-permissions
```

**Benutzerdefinierte Batch-Größe (für große Datensätze):**

```bash
npm run migrate:agent-permissions:batch
```

### Was während der Migration passiert [#what-happens-during-migration]

- **Private Agents**: Bleiben nur für ihre Ersteller zugänglich (erhalten OWNER-Berechtigung)
- **Shared Agents**: Wenn ein Agent zuvor geteilt wurde, erhält er entsprechende ACL-Einträge als Public Agent (für alle Benutzer freigegeben)
- **Systemerkennung**: LibreChat erkennt beim Start automatisch nicht migrierte Agents und zeigt eine Warnung an.

Sie können die resultierenden Agentenberechtigungen über die Agent Builder UI anpassen.

<Callout type="info" title="Hinweis">
  Der gleiche Migrationsprozess gilt für Prompts. Wenn Sie auch bestehende Prompts haben, führen Sie die Migration der Prompt-Berechtigungen mit denselben Befehlen durch, ersetzen Sie jedoch `agent` durch `prompt` in den Befehlsnamen.
</Callout>

## Was kommt als Nächstes? [#whats-next]

LibreChat Agents läuten eine neue Ära für die App ein, in der zukünftige Pipelines durch Agents für spezifische Aufgaben und Workflows in Ihrer gesamten Erfahrung mit LibreChat optimiert werden können.

Zukünftige Updates werden Folgendes beinhalten:

- Allgemeine Verbesserungen der aktuellen Agent-Erfahrung
- Multi-Agent-Orchestrierung für komplexe Workflows
- Möglichkeit, Agenten für verschiedene Funktionen anzupassen: Titulierung (Benennung von Chat-Threads), Speicherverwaltung (Benutzerkontext/-verlauf) und Prompt-Optimierung (Eingabeunterstützung/-vorhersagen)
- Mehr Tools, konfigurierbare Tool-Parameter, dynamische Tool-Erstellung.

Darüber hinaus führt das Update ein neues Paradigma für LibreChat ein, da die zugrunde liegende Architektur eine dringend benötigte Auffrischung für die App bietet, wodurch sowohl die Benutzererfahrung als auch die allgemeine App-Leistung optimiert werden.

Um eine bemerkenswerte Optimierung hervorzuheben: Eine KI-Generierung von etwa 1000 Tokens überträgt bei Verwendung herkömmlicher endpoints (zum Zeitpunkt der Erstellung dieses Textes jede endpoint-Option außer Agents und AWS Bedrock) etwa 1 MB an Daten.

Bei Verwendung eines Agents überträgt dieselbe Generierung etwa 52 kb an Daten, was einer Reduzierung der Datenübertragung um 95 % entspricht und somit den Server sowie das Gerät des Benutzers deutlich weniger belastet.

---

KI-Agenten in LibreChat bieten eine leistungsstarke Möglichkeit, spezialisierte Assistenten ohne Programmierkenntnisse zu erstellen, während gleichzeitig die Flexibilität gewahrt bleibt, mit Ihren bevorzugten KI-Modellen und -Anbietern zu arbeiten.
