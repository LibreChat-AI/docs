Model Context Protocol (MCP) 是一种开放协议，旨在标准化应用程序向大语言模型 (LLMs) 提供上下文的方式。可以将 MCP 视为 **“AI 界的 USB-C”** —— 正如 USB-C 为电子设备提供了通用的连接标准一样，MCP 也提供了一种标准化的方式，将 AI 模型连接到各种工具、数据源和服务。

LibreChat 利用 MCP 极大地扩展了您的 AI 智能体的能力，使您能够集成从文件系统访问、网络浏览器、专用 API 到自定义业务工具等一切内容。

## 为什么 MCP 很重要 [#why-mcp-matters]

LLMs 仅限于其内置能力。通过 MCP，LibreChat 打破了这些壁垒，实现了：

- **连接到任何提供** MCP server 的工具或服务
- **标准化集成**，这样您就不需要为每个工具编辑 LibreChat 的代码
- **支持多用户环境**，并具备适当的身份验证和隔离机制
- **在运行时添加和更新服务器**，无需编辑配置文件或重启，即可通过 MCP 设置面板完成

## LibreChat 中 MCP 的工作原理 [#how-mcp-works-in-librechat]

LibreChat 提供了两种使用 MCP 服务器的方式，既可以在聊天区域中使用，也可以与智能体（agents）配合使用。

您可以在 `librechat.yaml` 文件中手动配置 MCP 服务器，或者使用 [smithery.ai](https://smithery.ai) 查找并将 MCP 服务器安装到 `librechat.yaml` 中（[见下方示例](#basic-configuration)）。每当您在 `librechat.yaml` 中添加或编辑服务器时，都需要重启 LibreChat 以初始化连接。通过 [MCP 设置面板](#adding-mcp-servers-in-the-ui)添加的服务器无需重启即可生效。通过面板创建并使用 OAuth 的服务器在保存时即已注册，但初始状态为未连接：请[进行身份验证](#step-3-check-connection-status-and-authenticate)以建立连接。

### OAuth 回调 URL [#oauth-callback-url]

对于启用了 OAuth 的 MCP 服务器，LibreChat 回调 URL 为：

```text
${DOMAIN_SERVER}/api/mcp/<server-name>/oauth/callback
```

`<server-name>` 是 `librechat.yaml` 中 `mcpServers` 下使用的键，或者是 MCP 设置 UI 中创建的服务器名称。例如，一个名为 `salesforce` 且配置了 `DOMAIN_SERVER=https://chat.example.com` 的服务器，其回调地址为 `https://chat.example.com/api/mcp/salesforce/oauth/callback`。

请将此确切的回调 URL 注册到 OAuth 提供商。本地 Docker 安装通常使用 `http://localhost:3080` 作为基础 URL。

### 在聊天区域中 [#in-chat-area]

![从 composer 面板打开的 MCP Servers 目录，显示每个服务器的连接状态](/images/mcp/mcp_servers_catalog.png)

当使用传统 endpoint（OpenAI、Anthropic、Google、Bedrock 等）时，LibreChat 会直接在聊天区域显示已配置的 MCP 服务器：

- 首先选择任何非 Agent endpoint，以及一个兼容工具的模型
- MCP 服务器会显示在 [composer 的 **+** 面板](/docs/features/composer#turn-on-tools-skills-and-mcp-servers)中的 **MCP Servers** 部分，每个选定的服务器都会以芯片（chip）的形式显示在 composer 上。
- 选中后，来自该服务器的所有工具都将可供您当前的模型使用
- 无需创建智能体即可快速访问 MCP 工具，并允许同时使用多个服务器

若要将 MCP server 从常规聊天选择中排除，请在您的配置中设置 [`chatMenu: false`](/docs/configuration/librechat_yaml/object_structure/mcp_servers#chatmenu)：

```yaml
mcpServers:
  internal-tools:
    command: npx
    args: ['-y', 'internal-mcp-server']
    chatMenu: false # Not selectable in regular chat
```

此设置在聊天请求以及选择器中强制执行，因此过期的已保存选择无法继续使用已隐藏的服务器。它不会从已保存的 Agents 或明确指定该服务器的 Model Specs 中移除该服务器。LibreChat 还会从常规聊天选择器和请求路径中省略用户只能通过已授权 Agent 访问的服务器。

### 使用 Agents [#with-agents]

MCP servers 可以与 LibreChat Agents 无缝集成：

1. 创建或编辑一个 Agent
2. 在 Agent Builder 中打开 **Add tools** 并选择 **MCP**
3. 选择一个 MCP 服务器；每个服务器都显示为一个单独的目录条目
4. 展开选定的服务器以启用或禁用单个工具
5. 保存您的智能体

![Agent Builder 中的 MCP 工具](/images/mcp/mcp_ui_agent.png)

这种更高级别的组织方式使界面易于管理——即使是拥有 20 多个工具的服务器（例如 Spotify）也会显示为单个条目，可以展开以进行精细控制。

### 基础配置 [#basic-configuration]

手动将 MCP 服务器添加到您的 `librechat.yaml` 文件中：

```yaml
mcpServers:
  # ClickHouse Cloud
  clickhouse-cloud:
    type: streamable-http
    url: https://mcp.clickhouse.cloud/mcp

  # File system access
  filesystem:
    command: npx
    args:
      - -y
      - '@modelcontextprotocol/server-filesystem'
      - /path/to/your/documents

  # Web browser automation
  puppeteer:
    command: npx
    args:
      - -y
      - '@modelcontextprotocol/server-puppeteer'

  # Production-ready cloud service
  business-api:
    type: streamable-http
    url: https://api.yourbusiness.com/mcp
    headers:
      X-User-ID: '{{LIBRECHAT_USER_ID}}'
      Authorization: 'Bearer ${API_TOKEN}'
    timeout: 30000
    serverInstructions: true
```

### 在 UI 中添加 MCP 服务器 [#adding-mcp-servers-in-the-ui]

您也可以直接从 LibreChat 界面添加和配置 MCP 服务器，而无需编辑任何配置文件或重启服务器。

#### 第 1 步：打开 MCP 设置面板 [#step-1-open-the-mcp-settings-panel]

从右侧边栏导航至 **MCP Settings** 面板。你将在此处看到所有现有的 MCP 服务器列表，以及用于添加新服务器的 **+** 按钮。

![MCP 设置面板](/images/mcp/mcp_ui_settings_panel.png)

#### 第 2 步：填写服务器详细信息 [#step-2-fill-out-server-details]

点击 **+** 按钮并填写您的 MCP 服务器名称、描述、URL、传输类型和身份验证方法，然后点击 **Create**。

![添加 MCP 服务器对话框](/images/mcp/mcp_ui_configure.png)

您的新服务器将出现在 MCP Settings 面板中，并伴有确认提示。

![MCP Server Created Successfully](/images/mcp/mcp_ui_success_registered.png)

#### 第 3 步：检查连接状态并进行身份验证 [#step-3-check-connection-status-and-authenticate]

查看新服务器的 [connection status indicator](#connection-status-indicators)。如果服务器需要 OAuth 身份验证，状态将显示为已断开连接。在组合器的 **+** 面板中选择该 MCP 服务器以开始身份验证流程。

![连接状态 - 已断开](/images/mcp/mcp_ui_unconnected.png)

一旦启动，状态指示器将更新以显示身份验证正在进行中。

![连接状态 - 正在验证](/images/mcp/mcp_ui_authenticating.png)

#### 第 4 步：继续使用 OAuth [#step-4-continue-with-oauth]

LibreChat 会显示一个 **Connect** 确认提示。请检查目标并选择 **Continue with OAuth**，以便在新的浏览器标签页中打开提供商的授权页面。在页面中完成提供商的登录和授权流程。

如果在一个浏览器中启动的流程处于挂起状态，即使缓存的连接状态仍显示为 **Connected**，LibreChat 也会使该服务器保持在授权/连接状态。提示不应仅仅因为旧的状态报告了持久授权而关闭；只有终端成功、失败、超时或取消才会结束挂起流程。在另一个标签页或浏览器中启动的流程在此视图中没有本地挂起状态。

![OAuth Continue Prompt](/images/mcp/mcp_ui_callback_confirm.png)

#### 第 5 步：身份验证成功 [#step-5-authentication-successful]

身份验证成功后，您将看到确认信息。此窗口将自动关闭并重定向回 LibreChat。

![Authentication Successful](/images/mcp/mcp_ui_success_redirect.png)

#### 第 6 步：服务器准备就绪 [#step-6-server-ready-for-use]

LibreChat 会确认认证成功，并自动选择 MCP 服务器以供您在对话中使用。此时，服务器会显示已连接的状态指示器，并作为选定的标签（chip）出现在输入框中。

![MCP Server Authenticated and Auto-Selected](/images/mcp/mcp_ui_done.png)

您新的 MCP 服务器也可在 Agent Builder 中使用，您可以在其中将工具添加到任何 Agent，并自定义允许使用的工具子集。

![MCP Server Available in Agent Builder](/images/mcp/mcp_ui_agent.png)

#### UI 创建服务器的凭据变量 [#credential-variables-for-ui-created-servers]

通过 UI 添加 MCP 服务器时，您可以要求用户提供他们自己的 API 密钥。在 MCP 服务器构建器对话框的 Authentication 部分，选择 "API Key" 并勾选 **"User provides key"**。选择标头格式（Bearer、Basic 或 Custom）并保存服务器。

在后台，LibreChat 会创建一个名为 `MCP_API_KEY_<hash>` 的目标绑定 `customUserVars` 条目，并配置相应的身份验证标头。该名称由系统自动管理；用户仍需在 MCP 工具选择对话框或 MCP 设置面板中输入其密钥。现有的服务器可能会保留旧版的 `MCP_API_KEY` 名称，同时其请求边界保持不变。此功能使用与 [YAML 定义的 `customUserVars`](#user-provided-credentials) 相同的密钥输入 UI。

更改 UI 创建的服务器 URL（包括路径或查询参数）、代理、传输方式、授权格式、自定义授权标头或已配置的 OAuth 客户端/目标时，需要每位用户为新边界输入密钥。旧的已保存密钥不会转发到该替换目标。外观上的编辑、等效的规范化 URL 以及仅针对片段的出站 URL 编辑会保留现有密钥。共享服务器只能解析其当前配置所声明的凭据变量，因此编辑器无法引用旧的生成名称来恢复之前的密钥。无需进行批量凭据迁移。在依赖此保护机制之前，请升级**每一个 API 副本**（包括处理服务器编辑请求的副本）；旧版本的写入程序仍可能重新创建未绑定的配置。

当配置了管理员或用户 API key 时，LibreChat 会将服务器视为 API-key 认证，并跳过 OAuth 自动检测。显式的 OAuth 配置仍然具有优先权。如果通过 UI 创建的 API-key 服务器是由旧版本的 LibreChat 保存的，并且仍然卡在 **OAuth Required** 状态，请编辑并保存该服务器一次，以便刷新其存储的连接元数据。

<Callout type="warning">
出于安全考虑，UI 创建的（源自数据库的）MCP 服务器**仅**能解析 `customUserVars` 占位符 (`{{VAR_NAME}}`)。服务器端环境变量 (`${ENV_VAR}`)、用户个人资料字段 (`{{LIBRECHAT_USER_*}}`) 以及 OIDC 令牌 (`{{LIBRECHAT_OPENID_*}}`) 会被刻意拦截，以防止未经授权访问服务器密钥或其他用户的数据。如需完整的占位符支持，请改在 `librechat.yaml` 中配置服务器。
</Callout>

## MCP Server Management [#mcp-server-management]

LibreChat 提供了全面的工具来管理 MCP 服务器连接，并在 UI 中支持连接状态跟踪以及 OAuth 身份验证和初始化。

### 连接状态指示器 [#connection-status-indicators]

LibreChat 会在组合框的 **+** 面板和设置面板中显示动态状态图标，以展示每个 MCP 服务器的当前状态：

![MCP Server Status Icons](/images/mcp/mcp_server_status_icons.png)

**状态类型：**

- **已连接** (绿色齿轮)：服务器已连接并具有可配置的 customUserVars
- **OAuth Required** (amber key): 服务器需要 OAuth 身份验证
- **已断开连接**（橙色插头图标）：服务器连接失败或丢失
- **初始化中** (蓝色加载器)：服务器正在启动或重新连接
- **错误**（红色三角形）：服务器遇到错误
- **取消**（红色 x）：OAuth 流程正在被取消

### 从 Agent 工具对话框取消 OAuth [#cancelling-oauth-from-the-agent-tool-dialog]

在 **Agent Builder → Tool Library → MCP server configuration** 中，当共享服务器管理器报告一个可取消的 OAuth 流程时，**Connect** 会变为可用的 **Cancel** 操作。这包括从另一个 LibreChat 面板发现的待处理流程。选择 **Cancel** 可停止该流程、关闭本地 OAuth 提示并清除其待处理的工具自动选择。取消后的延迟连接结果不会在此对话框中自动附加工具。您可以再次选择 **Connect** 进行新的尝试。不可取消的初始化操作仍会显示其禁用的忙碌状态，而不是取消操作。

### 服务器初始化 [#server-initialization]

您可以直接从界面初始化或重新初始化 MCP 服务器：

**一键：**

- 通过在 composer 的 **+** 面板的 **MCP Servers** 部分选择服务器，实现一键初始化

  <Video src="/videos/mcp_one_click_init.mp4" title="一键 MCP 初始化" />

**来自 MCPConfigDialog：**

- 在组合器的 **+** 面板中，选择 MCP 服务器所在行的 **Configure**，以打开 MCPConfigDialog。
- 配置自定义用户变量，并根据服务器身份验证类型点击 Authenticate/Initialize 按钮

       <Video src="/videos/mcp_config_dialog_auth.mp4" title="MCP 配置对话框身份验证" />

  **来自 MCP 设置面板：**

- 点击 MCP 设置面板中服务器列表部分的任意服务器，即可访问配置和初始化控件。
- 配置自定义用户变量，并根据服务器身份验证类型点击 Authenticate/Initialize 按钮

  <Video src="/videos/mcp_settings_init.mp4" title="MCP 设置面板初始化" />

初始化失败现在可以区分无法访问的服务器、缺失的 `customUserVars`、必须重新认证的 OAuth 连接以及一般的初始化失败。在重试之前，请使用消息中指出的缺失变量或重新认证操作；对于这些情况，无需再删除并重新添加服务器。

被动目录加载会合并 OAuth 发现尝试，并在失败后逐步退避，因此断开连接的集成不会在每次请求时都重试发现。凭据更改在副本之间进行生成隔离（generation-fenced），防止旧的发现结果覆盖较新的身份验证。操作员可以在 [`mcpSettings.catalogRecovery`](/docs/configuration/librechat_yaml/object_structure/mcp_settings#catalogrecovery) 下调整有界恢复策略；默认设置适用于大多数部署。

如果一个 Agent 明确需要 MCP 工具，但在运行开始时无法解析任何工具，LibreChat 将会终止运行并提供连接和访问指导，而不是在没有这些工具的情况下静默运行。

发送 `notifications/tools/list_changed` 的 MCP 服务器可以在无需重启 LibreChat 的情况下更新其工具目录。LibreChat 会从实时连接中获取当前列表，发布新增工具，并停止通告服务器已移除的工具。在连接被视为就绪之前，重新连接也会同步目录。受管理的快照刷新和冷服务器发现共享一个进程范围内的三操作门控。一旦准入，每个操作都会受到其工具列表或单服务器发现截止时间的限制，包括任何更短的 `initTimeout`，因此缓慢的目录工作无法无限期地占用槽位。

对于可流式传输的 HTTP 服务器，当服务器仍为旧会话保留陈旧的 SSE 流时，重新连接可能会短暂返回 HTTP `409`。LibreChat 会将其视为瞬态错误，自动销毁陈旧会话并重建连接；如果恢复成功，则无需操作员进行任何干预。如果重建后的连接依然失败，LibreChat 将继续抛出底层的连接错误。

LibreChat 通过解析 `Content-Type` 媒体类型来对可流式传输的 HTTP 响应进行分类，而不是通过子字符串匹配。参数无法使非 SSE 响应表现为 `text/event-stream`，因此响应大小错误会继续通过正确的 SSE 或非 SSE 处理路径进行处理。

### MCP 设置面板可见性 [#mcp-settings-panel-visibility]

当 LibreChat 检测到 MCP 服务器在初始化过程中可能需要用户干预时，MCP 设置面板会出现在右侧边栏中。当任何已配置的服务器满足以下条件之一时，该面板将可见：

- **自定义用户变量 (Custom User Variables)**：服务器定义了 `customUserVars`，其中可能包含用户提供的凭据
- **OAuth Authentication**: 服务器在启动时被检测到需要 OAuth 身份验证
- **手动初始化**：服务器已配置 `startup: false`，需要手动进行初始化

## LibreChat 特有功能 [#librechat-specific-features]

LibreChat 的 MCP 实现专为高度可配置、真实世界的多用户环境而设计。

### 用户特定连接 [#user-specific-connections]

- 每个用户都拥有各自独立的 MCP 服务器连接
- 用户身份验证和权限受到尊重
- 个人数据和上下文保持私密

### 共享 MCP Servers [#sharing-mcp-servers]

MCP 服务器参与 LibreChat 的 [granular access control](/docs/features/access_control) 系统。除了在 `librechat.yaml` 中定义的服务器（由管理员管理并受 [`interface.mcpServers`](/docs/configuration/librechat_yaml/object_structure/interface#mcpservers) 功能权限控制）之外，用户创建的 MCP 服务器拥有自己的 ACL，并可以以查看者 (Viewer)、编辑者 (Editor) 或所有者 (Owner) 级别与特定的**用户**、**组**、**角色**或**公开**共享。

`interface.mcpServers` 下的 `USE`、`CREATE`、`SHARE` 和 `SHARE_PUBLIC` 功能标志控制了谁被允许创建和共享 MCP 服务器。请参阅 [Access Control](/docs/features/access_control) 以了解权限层级是如何组合的。

### 动态用户上下文 [#dynamic-user-context]

MCP 服务器可以通过 **URL 和标头**中的占位符访问用户信息（适用于 SSE 和 Streamable HTTP 传输）：

```yaml
mcpServers:
  user-api:
    type: streamable-http
    url: https://api.example.com/users/{{LIBRECHAT_USER_USERNAME}}/mcp
    headers:
      X-User-ID: '{{LIBRECHAT_USER_ID}}'
      X-User-Email: '{{LIBRECHAT_USER_EMAIL}}'
      X-User-Role: '{{LIBRECHAT_USER_ROLE}}'
      Authorization: 'Bearer ${API_TOKEN}'
```

可用的占位符包括：

- `{{LIBRECHAT_USER_ID}}` - 唯一用户标识符
- `{{LIBRECHAT_USER_EMAIL}}` - 用户的电子邮件地址
- `{{LIBRECHAT_USER_ROLE}}` - 用户角色 (admin, user 等)
- `{{LIBRECHAT_USER_USERNAME}}` - 用户名
- 以及更多（请参阅 [MCP Servers Configuration](/docs/configuration/librechat_yaml/object_structure/mcp_servers#headers) 获取完整列表）

YAML 定义的 MCP 服务器也可以使用 `{{LIBRECHAT_OPENID_*}}`、`{{LIBRECHAT_GRAPH_*}}` 和 `{{LIBRECHAT_BODY_*}}` 占位符。`{{LIBRECHAT_BODY_*}}` 的值是请求作用域的，因此 LibreChat 会为当前运行创建连接，在运行期间的工具调用中复用这些连接，并在请求结束时进行清理。请求作用域的服务器会被排除在持久化工具缓存之外，以确保请求特定的标头和 URL 不会在当前运行之外被复用。由于它们的工具列表无法在聊天请求存在之前解析，Agent Builder 会为整个服务器公开一个运行时工具选择，并在运行时解析其工具。完成 OAuth 会存储授权信息，但会推迟连接，直到首次运行提供请求上下文为止。用户、OpenID 和 Graph 占位符是用户作用域的；HTTP 传输会在每次工具调用前刷新其解析后的标头，而无需自行重新连接。

受信任的操作员可以在 YAML 定义的远程服务器上使用 `Authorization: 'Bearer {{LIBRECHAT_OPENID_ACCESS_TOKEN}}'` 来透传用户的实时 OpenID 访问令牌。显式 MCP OAuth、代表交换（on-behalf-of exchange）以及管理员 API 密钥认证具有优先权。在收到 `401` 或 `403` 错误后，LibreChat 可以刷新一次连接，但绝不会自动重试被拒绝的工具调用。有关设置和安全指南，请参阅 [MCP server placeholder reference](/docs/configuration/librechat_yaml/object_structure/mcp_servers#headers)。

`{{LIBRECHAT_GRAPH_ACCESS_TOKEN}}` 通过 Microsoft on-behalf-of 流程交换用户的可重用 OpenID 访问令牌。[`GRAPH_API_SCOPES`](/docs/configuration/dotenv#microsoft-graph-api--entra-id-integration) 用于设置请求的以空格分隔的作用域，默认值为 `https://graph.microsoft.com/.default`。这与配置人员和组搜索的 `OPENID_GRAPH_SCOPES` 是相互独立的。

`{{LIBRECHAT_BODY_PARENTMESSAGEID}}` 占位符适用于原生 Agent 聊天、兼容 OpenAI 的 Agents API 调用以及旧版 Assistants 运行。Open Responses 没有等效的父消息标识，当 MCP 服务器需要该值时会失败并关闭。请参阅 [MCP 服务器占位符参考](/docs/configuration/librechat_yaml/object_structure/mcp_servers#headers)。

### 服务器指令 [#server-instructions]

`serverInstructions` 是 LibreChat 的一项功能，当选中来自该 MCP server 的任何工具时，它会自动动态添加已配置的指令：

```yaml
mcpServers:
  filesystem:
    command: npx
    args: ['-y', '@modelcontextprotocol/server-filesystem', '/docs']
    serverInstructions: |
      When accessing files:
      - Always check file permissions first
      - Use absolute paths for reliability
      - Handle errors gracefully
```

选项：

- `true`：在可用时使用服务器通告的指令
- `false`：禁用指令
- `string`：按原样使用自定义指令（如上所示）

LibreChat 将此配置的声明与检查服务器时获取的指令分离开来。因此，`true` 声明在检查和缓存的注册表重新加载过程中保持启用状态，而自定义字符串则保持权威性。

### 超时配置 [#timeout-configuration]

对于长时间运行的 MCP 操作，请为初始化和工具操作配置适当的超时时间。

```yaml
mcpServers:
  data-processor:
    type: streamable-http
    url: https://api.example.com/mcp
    initTimeout: 15000 # 15 seconds for server initialization
    timeout: 60000 # 60 seconds for tool operations
```

**注意**：如果操作仍然被中断，请检查您的代理配置（例如 nginx、traefik 等），这些配置可能会因默认超时设置而过早断开连接。

当用户在前端 Agent 工具调用期间按下 **Stop** 时，LibreChat 会将运行取消信号转发给 MCP。对于可流式传输的 HTTP 服务器，MCP SDK 会发送 `notifications/cancelled`；服务器必须响应此通知以停止其自身的工作。分离的后台调用会特意保持独立的生命周期，并且不会随前端轮次一起被取消。

### 用户提供的凭据 [#user-provided-credentials]

您可以通过 `customUserVars` 允许用户为 MCP 服务器提供他们自己的凭据。这实现了安全、特定于用户的身份验证，而无需将凭据存储在配置文件中。

```yaml
mcpServers:
  my-api-server:
    type: streamable-http
    url: 'https://api.example.com/mcp'
    headers:
      X-Auth-Token: '{{MY_API_KEY}}' # Uses the user-provided value
    customUserVars:
      MY_API_KEY:
        title: 'API Key'
        description: "Enter your personal API key from <a href='https://example.com/keys' target='_blank'>your account settings</a>"
```

用户可以配置这些凭据：

- **从聊天区域**：在编辑器 **+** 面板中，选择可配置 MCP 服务器行上的 **Configure**
- **从 MCP 设置面板**：在右侧面板中访问“MCP Settings”以管理所有已配置服务器的凭据

#### 使用用户凭据重新初始化 MCP Servers [#reinitializing-mcp-servers-with-user-credentials]

对于在使用前需要用户特定凭据的 MCP 服务器（例如 [GitHub 官方 MCP 服务器](https://github.com/github/github-mcp-server) 中的 `PAT_TOKEN`），LibreChat 允许用户在 UI 界面内提供这些凭据，并重新初始化 MCP 服务器，而无需重启整个应用程序：

1. 当您选择一个使用 `customUserVars` 的 MCP 时，您将能够在 MCP 面板中为所选的 MCP 服务器 **保存 (Save)** 或 **撤销 (Revoke)** `customUserVar` 的值。
2. 在保存 `customUserVar` 的值后，请点击重新初始化按钮（MCP 面板中每个服务器名称旁带有循环箭头的图标）。
3. LibreChat 将尝试使用您提供的凭据连接到服务器，并通过提示消息通知您重新初始化过程是成功还是失败。

> _提示：如果您知道某个服务器在首次启动时无法获取所需的凭据，可以在其配置中添加 `startup: false`。这会告知 LibreChat 在 UI 中手动重新初始化该服务器之前，不要尝试连接它。_

**示例：**

```yaml
mcpServers:
  github-mcp:
    type: streamable-http
    url: 'https://api.githubcopilot.com/mcp/'
    headers:
      Authorization: '{{PAT_TOKEN}}'
    customUserVars:
      PAT_TOKEN:
        title: 'GitHub PAT Token'
        description: 'GitHub Personal Access Token'
    startup: false
```

### OAuth 身份验证 [#oauth-authentication]

LibreChat 支持为 MCP 服务器进行 OAuth 身份验证，遵循 Anthropic 关于安全 MCP 连接的建议。OAuth 提供了一种标准化的安全方式来进行身份验证，而无需存储长期凭据。

#### 支持的 OAuth 流程 [#supported-oauth-flows]

LibreChat MCP 服务器支持以下 OAuth 2.0：

- **Authorization Code Flow with PKCE**：推荐用于实现最高安全性
- **客户端发现 (Client Discovery)**：在 OAuth 提供商支持时自动进行客户端注册
- **Refresh Tokens**: 当可用时自动更新令牌
- **Token endpoint discovery**: 预配置的客户端可以发现提供程序是期望在 POST 正文中提供客户端凭据，还是在 HTTP Basic 授权标头中提供。

在 MCP Builder 中，**Token Exchange Method** 提供 **Auto**、**Default (POST request)** 和 **Basic authorization header**。**Auto** 会将该方法留空，以便 LibreChat 可以使用受信任的提供商元数据，并在提供商未声明方法时回退到 Basic 身份验证。

#### 配置示例 [#configuration-examples]

```yaml
mcpServers:
  # Public remote MCP server for PayPal, uses OAuth Client Discovery
  # ❌ Refresh Tokens: you may need to re-authenticate periodically
  # More info: https://developer.paypal.com/tools/mcp-server/
  paypal:
    type: 'sse'
    initTimeout: 150000 # higher timeout to allow for initial authentication
    url: 'https://mcp.paypal.com/sse'

  # Example self-hosted remote MCP server for Spotify, uses OAuth Client Discovery
  # ✅ Refresh Tokens: refreshes token for authentication automatically
  # Hosted on Cloudflare Workers, more info: https://github.com/LibreChat-AI/spotify-mcp
  spotify:
    type: 'streamable-http'
    initTimeout: 150000
    url: 'https://mcp-spotify-oauth-example.account.workers.dev/mcp'
```

#### OAuth 身份验证流程 [#oauth-authentication-flow]

当你首次配置启用了 OAuth 的 MCP 服务器时：

1. **初始连接**: LibreChat 尝试连接到 MCP 服务器
2. **需要身份验证**：如果不存在有效的令牌，您将在组合框的 **+** 面板中看到该服务器的 OAuth 身份验证状态。
3. **开始登录**：选择服务器以启动 OAuth 流程
4. **继续或使用其他设备**：在当前浏览器中继续，复制授权链接，或显示二维码以在其他设备上打开
5. **浏览器重定向**：使用 OAuth 提供商完成身份验证
6. **返回处理**: 一旦您完成身份验证，LibreChat 会自动处理 OAuth 回调。
7. **Token Storage**: LibreChat 安全地存储令牌以供将来使用
8. **连接已建立**：一旦您完成身份验证，MCP server 将会连接，您就可以在聊天中使用它了

#### OAuth 回调 URL [#oauth-callback-url-1]

当 MCP server 使用 OAuth 时，LibreChat 会暴露一个回调 endpoint，OAuth 提供商在授权成功后会重定向到该地址。

回调 URL 必须遵循以下格式：

`${baseUrl}/api/mcp/${serverName}/oauth/callback`

其中 `${serverName}` 是你在 `librechat.yaml` 配置文件中定义的 MCP 服务器键名。LibreChat 会在此 endpoint 处理重定向，完成令牌交换，并将凭据与相应的 MCP 服务器关联。

<Callout type="info" title="OAuth 回调 URL 示例">
给定以下 MCP server 配置：

```yaml
mcpServers:
  # Example self-hosted remote MCP server for Spotify, uses OAuth Client Discovery
  # ✅ Refresh Tokens: refreshes token for authentication automatically
  # Hosted on Cloudflare Workers, more info: https://github.com/LibreChat-AI/spotify-mcp
  spotify:
    type: 'streamable-http'
    initTimeout: 150000
    url: 'https://mcp-spotify-oauth-example.account.workers.dev/mcp'
```

回调 URL 将会是 `${baseUrl}/api/mcp/spotify/oauth/callback`。

</Callout>

注意：

- 必须在 OAuth 提供商处准确注册回调 URL，流程才能正常工作。
- 其他路径（例如 `/api/oauth/callback` 或 `/api/oauth/openid/callback`）不适用于 MCP OAuth 流程。

#### 令牌管理 [#token-management]

LibreChat 会智能处理 OAuth 令牌：

- **安全存储**：令牌经过加密并安全存储
- **自动刷新**：当存在刷新令牌时，LibreChat 会自动更新过期的访问令牌
- **静默 401 恢复**：如果 MCP OAuth 连接在会话期间收到身份验证拒绝，LibreChat 会为每个用户和服务器协调一次有界的刷新和重连尝试。并发调用者将在 LibreChat 弹出新的身份验证提示之前共享该恢复结果。
- **会话管理**：在多用户环境中，每个用户维护其各自的 OAuth 会话

如果已保存的 Agent 流在 MCP 授权提示仍处于挂起状态时被重新加载或恢复，LibreChat 将根据持久化生成状态重建该提示。已完成、已取消、已失败或已过期的提示不会被恢复。

存储的 OAuth 客户端和令牌绑定到 MCP 服务器 URL 以及 OAuth 客户端/endpoint 设置。更改这些设置需要用户重新进行身份验证。在编辑保留了存储的 `client_secret` 的 UI 创建的服务器时，如果更改了绑定字段（例如服务器 URL、客户端 ID、授权 URL、令牌 URL 或令牌身份验证方法），则需要重新输入该密钥。

在水平扩展的部署中，OAuth 流程状态和绑定令牌的就绪状态可以在多个 LibreChat pod 之间进行协调。即使回调和状态轮询到达不同的 pod，UI 也仅在 OAuth 后初始化成功后才会将服务器报告为就绪。来自被取代尝试的回调将被拒绝。

当启用 Redis 时，应用层级的 MCP 目录生成和发布修订会在各个副本之间进行协调。Redis Cluster 部署使用槽位安全（slot-safe）的目录键和更新，因此启动同步和 `tools/list_changed` 刷新不需要单节点 Redis 布局。

当用户首次使用启用了 OAuth 的 MCP 服务器时，系统会提示每位用户使用其自己的 OAuth 登录信息进行身份验证。这确保了连接和身份验证详细信息对每位用户都是唯一的，从而在多用户环境中维护了安全性和隐私。

#### OAuth 时序 [#oauth-timing]

MCP OAuth 完成过程使用其自身服务器配置的超时时间，而不是复用 MCP 服务器的 `initTimeout`。默认情况下，LibreChat 会等待最多 10 分钟以供用户完成 MCP OAuth，并将流程状态保留 15 分钟。

当 OAuth 提供商或用户工作流需要更多时间时，请使用这些环境变量：

```bash filename=".env"
MCP_OAUTH_HANDLING_TIMEOUT=600000
MCP_OAUTH_FLOW_TTL=900000
```

`MCP_OAUTH_FLOW_TTL` 的值会被强制设定为大于 `MCP_OAUTH_HANDLING_TIMEOUT`，以确保在截止时间附近的回调仍能找到其流程状态。MCP 服务器卡片轮询窗口遵循配置的处理超时时间。

![用户特定的 OAuth 认证流程](/images/agents/mcp_oauth_flow.png)

> 注意：应用启动期间显示的 token 仅用于应用级别的初始化，不会用于单个用户连接。

自动令牌刷新的示例：

```bash
[MCP][spotify] Access token missing
[MCP][spotify] Attempting to refresh token
[MCP][spotify] Successfully refreshed and stored OAuth tokens
[MCP][spotify] ✓ Initialized
```

#### 最佳实践 [#best-practices]

1. **尽可能使用 OAuth**：优先选择 OAuth 而非 API 密钥，以获得更好的安全性
2. **配置适当的超时时间**：使用 `MCP_OAUTH_HANDLING_TIMEOUT` 和 `MCP_OAUTH_FLOW_TTL` 来设置 OAuth 完成窗口；使用 `initTimeout` 来设置服务器初始化超时。
3. **监控令牌过期**: 检查日志以查找身份验证问题
4. **重新认证计划**：部分提供商不支持刷新令牌

## Server Transports [#server-transports]

MCP servers 可以配置为使用不同的传输机制：

**STDIO 服务器**

- 适用于本地单用户环境
- 不适用于远程或云端部署的扩展
- 捆绑的 MCP SDK 将每个单独的 STDIO 消息限制为 10 MB。如果单个结果超过此大小，传输将会因错误而关闭；此限制与会话或流的总大小无关。

**Server-Sent Events (SSE) 服务器**

- 远程传输机制，但不建议在生产环境中使用

**可流式传输的 HTTP 服务器**

- 使用 HTTP POST 发送消息并支持流式响应
- 作为一个可以处理多个客户端连接的独立进程运行
- 支持基础请求以及通过服务器发送事件 (SSE) 进行流式传输
- 比旧版 HTTP+SSE 传输性能更高的替代方案
- 支持适当的多用户服务器配置

**对于生产环境**，仅推荐使用具有 ["Streamable HTTP" 传输方式](https://modelcontextprotocol.io/specification/draft/basic/transports/streamable-http) 的 MCP 服务器。与维持长连接的 SSE 不同，Streamable HTTP 提供了更适合可扩展、多用户部署的无状态选项。

LibreChat 处于实现灵活、可扩展的 MCP 服务器集成的最前沿，旨在支持多样化的使用场景，并帮助您构建未来的 AI 工作流。
