# Agentes: Crie Assistentes de IA Personalizados [#agents-build-custom-ai-assistants]

O recurso de AI Agents do LibreChat oferece uma estrutura flexível para a criação de assistentes de IA personalizados, alimentados por diversos provedores de modelos.

Este recurso é semelhante à Assistants API da OpenAI e aos GPTs do ChatGPT, mas com suporte a uma gama mais ampla de modelos e uma implementação sem código (no-code), permitindo que você crie assistentes sofisticados com capacidades especializadas.

## Primeiros Passos [#getting-started]

Para criar um novo agente, selecione "Agents" no menu de endpoint e abra o painel Agent Builder encontrado no Side Panel.

![Agentes - Menu de endpoints](/images/agents/endpoints_menu.png)

O formulário de criação inclui:

- **Avatar**: Faça upload de um avatar personalizado para personalizar seu agente
- **Nome**: Escolha um nome distinto para o seu agente
- **Description**: Detalhes opcionais sobre o propósito do seu agente
- **Instruções**: Instruções de sistema que definem o comportamento do seu agente
- **Modelo**: Selecione a partir dos provedores e modelos disponíveis
- **Conversation Starters**: Até quatro prompts sugeridos exibidos quando um usuário inicia um novo chat com o agente

Os controles de **Tools** e **Skills** abrem bibliotecas pesquisáveis para recursos integrados, ferramentas, servidores MCP, Actions e Skills. Selecione um item para configurá-lo e, em seguida, salve o agente.

**Agentes existentes podem ser selecionados no menu suspenso superior do Painel Lateral.**

- **Também por menção com "@" na entrada de chat.**

![Agentes - Menção](/images/agents/mention.png)

### Biblioteca de Ferramentas [#tool-library]

O Agent Builder mantém itens habilitados em seções separadas de **Tools** e **Skills**. Abra **Add tools** para pesquisar no catálogo completo ou filtrá-lo por **Official**, **Tools**, **MCP** ou **Actions**. **Made by you** reúne servidores MCP e Actions que você criou, enquanto **Favorites** mantém itens marcados como favoritos disponíveis em todos os agentes. Cada usuário pode salvar até 100 favoritos na biblioteca de ferramentas.

Selecione um item para configurá-lo sem sair do construtor. O menu **Create new** aparece apenas quando o usuário tem permissão para criar servidores MCP ou Actions. Remover uma funcionalidade baseada em arquivos, como File Search, File Context ou Code Interpreter, abre seu gerenciador de arquivos quando arquivos anexados ainda precisam ser revisados. Uma funcionalidade baseada em arquivos permanece selecionada e é preservada ao salvar enquanto ainda possuir arquivos; remova ou reatribua esses arquivos antes de remover a própria funcionalidade.

As Skills usam seu próprio seletor e podem ser selecionadas individualmente ou habilitadas como o catálogo completo acessível. Veja [Skills](/docs/features/skills#agent-scope).

Operadores também podem usar [Agent Plugins](/docs/features/agent_plugins) experimentais para agrupar Skills de implantação e servidores MCP em pacotes carregados na inicialização.

### Configuração de Modelo [#model-configuration]

A interface de parâmetros do modelo permite o ajuste fino das respostas do seu agente:

- Temperatura (escala de 0 a 1 para a criatividade da resposta)
- Tokens de contexto máximos
- Máximo de tokens de saída
- Detalhe da imagem (`low`, `auto` ou `high`) para entradas de imagem com visão nativa
- Configurações adicionais específicas do provedor

As instruções do agente podem usar `{{current_date}}`, `{{current_datetime}}` e `{{iso_datetime}}`. O LibreChat as resolve a partir do início do turno lógico capturado pelo servidor e mantém esse timestamp estável durante os loops do provedor, inicialização de Subagent e retomada com intervenção humana (human-in-the-loop). Os dois primeiros usam o fuso horário da solicitação; `{{iso_datetime}}` permanece em UTC.

Falhas reconhecidas de "model-not-found" e de limite de taxa do provedor exibem orientações localizadas. Outros erros do provedor mantêm seu texto útil do provedor, mas omitem URLs de solução de problemas do LangChain antes que a mensagem seja persistida. Quando a [proteção de conteúdo vinculada ao modelo](/docs/configuration/librechat_yaml/object_structure/message_filter#source-aware-filters) está habilitada, seu erro genérico de proteção ainda tem precedência.

### Histórico de Versões [#version-history]

Usuários com acesso de edição podem abrir o **Version History** a partir do Agent Builder para inspecionar as configurações salvas em uma linha do tempo. Cada entrada mostra quando foi salva e resume suas ferramentas e capacidades. Restaurar uma entrada anterior requer confirmação e substitui a configuração atual do agente por aquele estado salvo. Salvar sempre aplica as alterações atuais do Agent, mesmo quando a configuração resultante corresponde à entrada de histórico mais recente e o LibreChat não adiciona uma entrada duplicada.

### Conversation Starters [#conversation-starters]

Os conversation starters oferecem aos usuários uma maneira rápida de iniciar um chat com um agente. Cada agente pode armazenar até quatro.

1. No Agent Builder, encontre o campo **Conversation Starters**.
2. Digite um prompt e pressione **Enter**, ou selecione o botão **+**. A entrada é desativada assim que quatro iniciadores são adicionados.
3. Edite um starter salvo diretamente, ou selecione o botão **X** para removê-lo.
4. Salve o agente.

Quando um usuário inicia um novo chat com o agente, os starters aparecem como botões na tela de chat vazia. Selecionar um deles o envia imediatamente como a primeira mensagem. Se o agente possuir starters, eles terão precedência sobre quaisquer [`conversation_starters`](/docs/configuration/librechat_yaml/object_structure/model_specs#conversation_starters) definidos no Model Specs em uso. Os starters também aparecem na caixa de diálogo de detalhes do [Marketplace](#agent-marketplace) do agente.

## Capacidades dos Agentes [#agent-capabilities]

> **Nota:** Todas as capacidades podem ser alternadas através do arquivo de configuração `librechat.yaml`. Veja [docs/configuration/librechat_yaml/object_structure/agents#capabilities](/docs/configuration/librechat_yaml/object_structure/agents#capabilities) para mais informações.

### Code Interpreter [#code-interpreter]

Quando ativado, o recurso Code Interpreter permite que seu agente:

- Execute código em várias linguagens, incluindo:
  - Python, JavaScript, TypeScript, Go, C, C++, Java, PHP, Rust e Fortran
- Processe arquivos de forma segura através da API de Code Interpreter do LibreChat
- Execute código sem configuração local, definições ou implantação de sandbox
- Gerencie uploads e downloads de arquivos de forma integrada
- [Mais informações sobre a API do Code Interpreter](/docs/features/code_interpreter)
  - **Desenvolvido pelo serviço de código aberto [code-interpreter](https://github.com/ClickHouse/code-interpreter) (auto-hospedado)**

Quando todos os arquivos necessários do Code Interpreter de uma conversa falham ao serem restaurados no sandbox atual, o LibreChat interrompe o Agent antes de invocar o modelo e solicita que o usuário anexe os arquivos novamente. Isso evita que a execução continue com referências de arquivos obsoletas ou inacessíveis.

Quando arquivos de conversa compartilham um nome de arquivo no Code Interpreter, o LibreChat atribui destinos de sandbox distintos e informa ao Agent os caminhos resolvidos. Consulte [Seamless File Handling](/docs/features/code_interpreter#seamless-file-handling) para o comportamento de colisão e a limitação restante de arquivos privados multi-Agent.

#### Sessões de Código Stateful [#stateful-code-sessions]

Sessões de código com estado (stateful) permitem que um agente reutilize um workspace de sandbox entre execuções de código. Arquivos, pacotes instalados e o estado de trabalho geralmente são mantidos, o que é útil para análises iterativas e trabalho com arquivos em várias etapas. No Agent Builder, o seletor **Stateful environment** controla quem compartilha esse workspace:

- **Espaço de trabalho do usuário (recomendado):** os agentes com estado do usuário conectado compartilham um único espaço de trabalho
- **Espaço de trabalho do agente + usuário:** cada usuário recebe um espaço de trabalho separado para cada agente
- **Área de trabalho da conversa:** cada usuário obtém uma área de trabalho separada para cada conversa

Administradores também podem configurar backends nomeados em [`statefulCodeSessions.environments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions). Quando presentes, o seletor **Execution environment** separado escolhe a Code API gerenciada, a VM anexada ao operador ou o worker pessoal que possui o workspace; **Deployment default** usa o ambiente executável padrão configurado. O escopo de compartilhamento acima permanece independente dessa escolha de backend.

Quando uma implantação habilita workers de autoatendimento, usuários com permissão de gerenciamento de Code Environment podem abrir **Settings > Code environments** para parear um worker de saída `@librechat/code` em sua própria VM, selecioná-lo no Agent Builder e revogá-lo posteriormente. Ambientes pessoais são vinculados ao proprietário e usam a mesma rota para código, shell e Programmatic Tool Calling. Consulte [Attached environments and pairing](/docs/features/code_interpreter#attached-environments-and-pairing) para a configuração experimental e o modelo de segurança.

Dentro de um workspace anexado, os Agents podem listar diretórios, ler arquivos, pesquisar texto, criar arquivos e executar Bash através do worker selecionado. Um nome e e-mail Git por Agent podem identificar commits feitos ali sem a necessidade de fornecer credenciais de repositório. Implantações podem limitar novos workers pessoais com [`statefulCodeSessions.principalWorkers`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions).

Quando um worker conectado anuncia múltiplas raízes de workspace, o compositor de chat requer uma seleção para cada ambiente conectado usado pelo Agent ou seus Subagents. A conversa retém essas seleções entre turnos e retomadas de aprovação; o LibreChat as valida em relação ao worker ativo e bloqueia o envio caso um workspace necessário esteja ausente ou indisponível. Um worker que anuncia exatamente um workspace é selecionado automaticamente para uma nova conversa. Veja [Attached environments and pairing](/docs/features/code_interpreter#attached-environments-and-pairing) para detalhes e limitações atuais.

Novos Agents usam inicialmente o **Default stateful workspace** do usuário conectado em **Settings > Data Controls > Code execution**. O padrão pessoal é **User workspace** até que seja alterado. Atualizar essa preferência não altera Agents existentes nem habilita Stateful Code Sessions por si só. Administradores podem restringir os escopos disponíveis com [`statefulCodeSessions.allowedEnvironments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions); quando um padrão pessoal salvo não é mais permitido, novos Agents usam o primeiro escopo permitido.

<Callout type="warning" title="Altamente experimental">
  As Stateful Code Sessions estão em uma fase inicial de experimentação. Seu comportamento, configuração, características de persistência e integração subjacente podem mudar substancialmente. Não trate a implementação atual como um contrato de produção estável.
</Callout>

Este recurso é opcional (opt-in). Um administrador deve adicionar `stateful_code_sessions` às [capacidades do agente](/docs/configuration/librechat_yaml/object_structure/agents#capabilities) e configurar uma rota dedicada de Interpretador de Código com estado através de [`LIBRECHAT_CODE_BASEURL_STATEFUL`](/docs/configuration/dotenv#stateful-code-interpreter-endpoint) ou nomeada [`statefulCodeSessions.environments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions). O Interpretador de Código deve estar habilitado no agente, e **Stateful code sessions** deve estar ativado nas suas configurações Avançadas.

Requisições com estado (stateful) não retornam para o endpoint normal sem estado (stateless) do Code Interpreter quando a URL dedicada está ausente ou é incompatível. Sessões com estado e sem estado também não compartilham arquivos ativos ou pacotes instalados. O workspace com estado pode ser redefinido a qualquer momento, independentemente do seu escopo. Em ambientes gerenciados do Code Interpreter, salve saídas importantes em `/mnt/data`; um workspace anexado é um diretório separado de propriedade do worker. Uploads de chat não são copiados para esse diretório anexado por padrão. Não confie no estado da sessão como armazenamento durável para outros fins.

Quando as ferramentas `create_file` ou `edit_file` com estado criam arquivos durante uma resposta, a mensagem do assistente exibe uma linha compacta de **Alterações no Workspace**. Expanda-a para revisar os caminhos alterados exclusivos e baixar cada arquivo através do fluxo de arquivos autenticado do LibreChat. Este é um registro por mensagem dos arquivos criados por essas ferramentas, não um snapshot durável do workspace completo; as saídas do Code Interpreter sem estado continuam usando a interface de anexo em linha regular.

Para ambientes conectados, o composer pode expor **Ask before changes** (Perguntar antes de alterações), **Accept edits** (Aceitar edições) e **Full access** (Acesso total) como um modo de aprovação de código em nível de conversa. A disponibilidade é limitada pelo esquema de permissões definido pelo administrador do ambiente; escolher um modo mais permissivo nunca substitui concessões de função, regras de ferramentas explícitas, hooks ou limites de sandbox. Veja [Attached-environment tool permissions](/docs/features/code_interpreter#attached-environment-tool-permissions).

### File Search [#file-search]

A funcionalidade File Search permite:

- Funcionalidade de RAG (Retrieval-Augmented Generation)
- Busca semântica em documentos enviados
- Respostas com reconhecimento de contexto baseadas no conteúdo de arquivos
- Suporte a anexos de arquivos tanto em nível de agente quanto de thread de chat

### Contexto de Arquivo [#file-context]

A funcionalidade de File Context permite que seu agente armazene texto extraído de arquivos como parte de suas instruções de sistema:

- Extraia texto mantendo a estrutura e a formatação do documento
- Processar layouts complexos, incluindo texto em várias colunas e conteúdo misto
- Lidar com tabelas, equações e outros conteúdos especializados
- Trabalhe com conteúdo multilíngue
- O texto é armazenado nas instruções do agente no banco de dados
- **Nenhum serviço de OCR necessário** - Usa análise de texto por padrão com métodos de fallback
- **Aprimorado por OCR** - Se o OCR estiver configurado, a qualidade da extração melhora para imagens e documentos digitalizados
- Usa a mesma lógica de processamento que "Upload as Text": **OCR > STT > text parsing**
- [Mais informações sobre a configuração de OCR](/docs/features/ocr)

**Nota:** O File Context inclui texto extraído nas instruções de sistema do agente. Para perguntas sobre documentos temporários em conversas individuais, use [Upload as Text](/docs/features/upload_as_text) a partir do chat.

### Model Context Protocol (MCP) [#model-context-protocol-mcp]

MCP é um protocolo aberto que padroniza como as aplicações fornecem contexto para Large Language Models (LLMs), atuando como um adaptador universal para ferramentas de IA e fontes de dados.

Para mais informações, consulte a documentação sobre [MCP](/docs/features/mcp).

#### Agentes com MCP Tools [#agents-with-mcp-tools]

1. Configure servidores MCP no seu arquivo `librechat.yaml`
2. Reinicie o LibreChat para inicializar as conexões
3. Criar ou editar um agente
4. Abra **Add tools** no Agent Builder e selecione **MCP**
5. Selecione o(s) servidor(es) MCP que você deseja adicionar; cada servidor aparece como uma única entrada
6. Salve suas alterações no agente

Neste exemplo, adicionamos o **[Spotify MCP server](https://github.com/LibreChat-AI/spotify-mcp)** a um agente.

![Agentes - MCP](/images/agents/mcp_tools_v2.png)

#### Gerenciando Ferramentas MCP [#managing-mcp-tools]

Assim que um servidor MCP for adicionado a um agente, você poderá ajustar quais ferramentas específicas estarão disponíveis:

- Após adicionar um servidor MCP, expanda-o para ver todas as ferramentas disponíveis
- Marque/desmarque ferramentas individuais conforme necessário
- Por exemplo, o servidor MCP do Spotify fornece cerca de 20 ferramentas (pesquisa, controle de reprodução, gerenciamento de playlists, etc.)
- Esse controle granular permite que você limite os agentes apenas às ferramentas de que eles precisam

Servidores com escopo de solicitação que usam `{{LIBRECHAT_BODY_*}}` não podem enumerar ferramentas até que uma execução de chat forneça esses valores. Portanto, o Agent Builder mostra uma seleção de ferramentas de tempo de execução para o servidor completo em vez de alternadores por ferramenta; limpar essa seleção desconecta o servidor. Após o OAuth, o LibreChat mantém a autorização e aguarda até a primeira execução elegível para conectar.

Se um Agent selecionar explicitamente ferramentas MCP, mas nenhuma puder ser resolvida quando uma execução for iniciada, o LibreChat interrompe a execução com orientações de conexão e acesso em vez de continuar silenciosamente sem elas. Reconecte ou autentique o servidor, verifique o acesso à ferramenta e tente executar novamente.

![Agentes - Ferramentas MCP](/images/agents/mcp_agent_tools.png)

### Ferramentas Diferidas [#deferred-tools]

Ferramentas adiadas (deferred tools) permitem que agentes tenham acesso a muitas ferramentas MCP sem carregá-las todas no contexto do LLM antecipadamente. Em vez disso, as ferramentas adiadas são detectáveis em tempo de execução por meio de um mecanismo de **Busca de Ferramentas** (Tool Search).

Isso é especialmente útil quando um agente tem acesso a muitos servidores MCP com dezenas de ferramentas — carregá-las todas consumiria uma grande parte da janela de contexto e degradaria a qualidade da resposta.

**Como funciona:**

- Ferramentas marcadas como "deferred" são excluídas do contexto inicial do LLM
- Uma ferramenta `ToolSearch` é adicionada automaticamente, permitindo que o LLM descubra e carregue ferramentas adiadas sob demanda.
- Uma vez descoberta, a ferramenta fica disponível para o restante da conversa

**Configurando ferramentas adiadas (deferred tools):**

1. Abra o Agent Builder e adicione ferramentas MCP
2. Clique no menu suspenso em qualquer ferramenta MCP
3. Alternar "Adiar Carregamento" — ferramentas adiadas exibem um ícone de relógio

**Nota:** A funcionalidade `deferred_tools` está habilitada por padrão. Ela pode ser alternada através da configuração de agentes no [`librechat.yaml`](/docs/configuration/librechat_yaml/object_structure/agents#capabilities).

### Grupos de Atividade [#activity-groups]

Os grupos de atividade recolhem cada bloco contíguo de raciocínio do Agent e chamadas de ferramenta sob um cabeçalho gerado de uma linha, tornando execuções longas mais fáceis de analisar. Os administradores os habilitam com `activityLabel` e podem usar um modelo mais rápido, outro endpoint configurado, um prompt personalizado e limites por execução. A geração do cabeçalho é uma chamada de modelo separada cujos tokens e custo são registrados. Veja [Agent Activity Groups](/docs/configuration/librechat_yaml/object_structure/shared_endpoint_settings#agent-activity-groups).

Administradores podem habilitar independentemente `activityPhaseLabel` para agrupar duas ou mais atividades lógicas em um resumo pai recolhido antes da resposta final. Isso fornece a execuções longas um esboço de nível superior, preservando cada atividade filha. Os resumos de fase usam seu próprio modelo, endpoint, prompt e limite por execução, com fallback para o rótulo da atividade e as configurações de execução.

Assim que uma execução contígua contém pelo menos dois grupos de ferramentas rotulados e concluídos, o LibreChat os agrupa na mesma superfície de cartão de fase, mesmo antes da chegada de um resumo de fase opcional. O rótulo filho concluído mais recente atua como o cabeçalho provisório, enquanto o raciocínio em tempo real e a chamada de ferramenta ainda em andamento permanecem fora do agrupamento. O histórico carregado utiliza o mesmo agrupamento, e um resumo de fase gerado pelo servidor posteriormente substitui o cabeçalho provisório sem fechar um cartão que o leitor tenha aberto.

Quando o [Smooth Streaming](/docs/features/smooth_streaming) está ativado, um resumo pai recém-gerado recolhe suavemente as atividades visíveis para dentro do grupo colapsado. O histórico carregado não reproduz essa transição, e o LibreChat respeita a preferência de redução de movimento do dispositivo.

O texto de progresso curto permanece dentro de sua fase pai. Quando o Agent inicia uma resposta substancial, o LibreChat fecha a fase antes desse texto para que o resultado exibido ao usuário permaneça fora do resumo recolhido. Uma execução pode criar múltiplas fases pai quando raciocínios posteriores ou ferramentas iniciam outro bloco de atividade lógica. Os limites de fase persistidos são rebaseados quando partes de conteúdo malformadas ou omitidas são compactadas, de modo que o agrupamento permaneça alinhado após a recarga.

Arquivos produzidos dentro de uma fase permanecem visíveis em uma linha de mídia abaixo do card recolhido, em vez de ficarem ocultos dentro dele. Referências de imagem em Markdown usando um nome de arquivo simples, `/mnt/data/...` ou caminho `sandbox:` são resolvidas para anexos de turno correspondentes. Um arquivo é omitido da linha de mídia apenas quando uma imagem inline fora da fase recolhida é resolvida com sucesso, evitando duplicatas sem confiar em referências quebradas.

Os cards de Agente Genérico e de ferramentas MCP distinguem **Preparando** (antes da transferência do SDK, que pode incluir aprovação ou outra espera) de **Chamando** (transferência do SDK para o resultado). Cards concluídos mostram ambos os intervalos; o intervalo de chamada não é necessariamente a duração da execução do MCP upstream ou do ClickHouse. Mensagens salvas anteriormente e cards especializados de Código, Bash, arquivo e memória retêm uma duração de etapa de execução de **Tempo total decorrido** claramente rotulada. Etapas interrompidas, canceladas, falhas e concluídas retêm status distintos, inclusive após o recarregamento de uma conversa.

Enquanto uma ferramenta está em execução, os painéis de detalhes expandidos de Bash, Execute Code e File Authoring acompanham os comandos, código ou conteúdo de visualização transmitidos até o final. Rolar para cima pausa esse comportamento de acompanhamento para que a posição de leitura atual seja preservada.

A saída do Bash é renderizada como texto em estilo de terminal. Saídas longas são recolhidas nas suas últimas 15 linhas, onde os erros geralmente aparecem; use **Show more** e **Show less** para expandir ou recolher, e o botão **Copy** para copiar a saída. Um comando que não imprimiu nada mostra **No output**. Para comandos executados em um [attached workspace](/docs/features/code_interpreter#attached-environments-and-pairing), um comando com falha é marcado com seu motivo (**exit code N**, **terminated by** um sinal como `SIGKILL`, ou **timed out**), e o stderr é estilizado separadamente do stdout. Um comando finalizado é rotulado como **Ran command**, e um grupo de ferramentas que contém uma única chamada abre diretamente nos detalhes dessa chamada.

### Rótulos de Raciocínio em Tempo Real [#live-reasoning-labels]

Rótulos de raciocínio em tempo real substituem um cabeçalho genérico de **Thinking** ou **Thoughts** por uma orientação curta que evolui conforme fluxos de raciocínio de nível superior suficientemente longos. O rótulo atualiza o cabeçalho de raciocínio existente no local; ele não adiciona nem reordena partes da mensagem.

O rótulo de raciocínio em tempo real mais recente e o temporizador de resposta exibem um efeito de brilho (shimmer) enquanto a geração está ativa. O raciocínio concluído, as respostas de irmãos anteriores e os rótulos que não estão mais na extremidade em tempo real permanecem estáticos.

Administradores habilitam isso com `reasoningLabel` e podem escolher um modelo, endpoint, prompt, limites de atualização e limite de chamadas por execução separados. Cada revisão é uma chamada de modelo adicional cujos tokens e custo são registrados. Veja [Live Reasoning Labels](/docs/configuration/librechat_yaml/object_structure/shared_endpoint_settings#live-reasoning-labels) para padrões, precedência de roteamento e considerações de privacidade.

### Rótulos de Intenção de Ferramenta [#tool-intent-labels]

Os rótulos de intenção de ferramenta (tool intent labels) substituem status genéricos de ferramentas em tempo real por uma breve descrição escrita pelo modelo para aquela chamada específica. Os administradores devem adicionar a capacidade de agente `tool_intents` [agent capability](/docs/configuration/librechat_yaml/object_structure/agents#capabilities). Ferramentas nativas usam rótulos automaticamente; no Construtor de Agentes (Agent Builder), expanda um servidor MCP e ative **Intent label** para ferramentas individuais ou para o servidor completo.

Para Model Specs, [`describeIntent`](/docs/configuration/librechat_yaml/object_structure/model_specs#describeintent) pode habilitar todas as ferramentas elegíveis ou selecionar IDs de ferramentas resolvidos. Os campos de intenção (intent) são adicionados ao esquema da ferramenta enviado ao modelo, portanto, a habilitação seletiva pode reduzir a sobrecarga de tokens do esquema.

Rótulos de intenção (intent labels) não se aplicam a ferramentas MCP exclusivamente programáticas, pois as chamadas feitas dentro do código em sandbox não renderizam cartões de ferramenta individuais. Uma execução programática expandida mostra, em vez disso, um rastreamento ao vivo compacto de suas chamadas internas.

### Programmatic Tool Calling [#programmatic-tool-calling]

O Programmatic Tool Calling (PTC) permite que agentes executem ferramentas MCP selecionadas de dentro do sandbox do [Code Interpreter](/docs/features/code_interpreter) em vez de chamar cada ferramenta diretamente do modelo. O modelo recebe uma ferramenta de orquestração baseada no Code Interpreter, escreve código em sandbox que chama funções de ferramenta geradas e pode usar loops, condicionais, novas tentativas e processamento de resultados antes de retornar uma resposta.

Isso é útil para fluxos de trabalho de ferramentas com várias etapas, como consultar diversos recursos, paginar resultados, comparar saídas ou transformar respostas de ferramentas antes que o agente as explique.

**Configurando ferramentas programáticas:**

1. Enable both `programmatic_tools` and `execute_code` in the [`librechat.yaml` agents capabilities](/docs/configuration/librechat_yaml/object_structure/agents#capabilities).
2. Habilite o Code Interpreter no agente.
3. Adicione ferramentas MCP, expanda um servidor MCP e alterne **Programmatic** para ferramentas individuais ou para o servidor completo. Ferramentas Programmatic exibem um ícone de código.

O Agent Builder mantém as opções Programmatic desativadas até que o Code Interpreter seja selecionado. Remover o Code Interpreter limpa imediatamente as seleções Programmatic do agente. Ao criar, atualizar, duplicar e restaurar versões, o servidor também remove as opções de chamador programático sempre que a capacidade `execute_code` ou a ferramenta Code Interpreter estiver indisponível; isso permite que Agents antigos e inconsistentes sejam abertos e corrigidos sem preservar uma configuração inutilizável.

**Nota:** `programmatic_tools` é opcional e não está incluído na lista de capacidades de agentes padrão. O PTC também requer uma implementação do Code Interpreter com o componente Tool Call Server. Em tempo de execução, o LibreChat cruza a projeção de capacidade do chamador atual com seu registro de ferramentas confiáveis, portanto, os dados do evento podem restringir o mapa disponível, mas não podem conceder uma ferramenta. Apenas ferramentas programáticas ativas e registradas podem ser chamadas a partir do sandbox; chamadas não registradas são rejeitadas.

Expanda o card do Code Interpreter durante uma execução programática para ver um rastreamento em estilo terminal de cada chamada de ferramenta interna, sua prévia de argumentos, status, duração e qualquer falha. O rastreamento é ao vivo para a sessão atual do navegador e não é restaurado após uma recarga da página.

### Chamadas de Ferramentas em Segundo Plano [#background-tool-calls]

Chamadas de ferramenta em segundo plano permitem que um agente inicie uma ferramenta de Code Interpreter, MCP, Plugin ou Action elegível de longa execução e continue trabalhando. A chamada inicial retorna imediatamente com uma referência de tarefa. Para um Agent salvo, as conclusões suportadas são entregues automaticamente em uma continuação de acompanhamento por padrão; `check_background_task` permanece disponível para status explícito, controle, coleta de artefatos e recuperação.

`check_background_task` relata `started_at` e o `elapsed_ms` atual enquanto o trabalho local do processo está em execução. Após a conclusão, ele também relata `settled_at` e congela `elapsed_ms` na duração finalizada. Um resultado terminal recuperado do armazenamento durável pode incluir `settled_at` sem um horário de início ou duração decorrida quando o timestamp de despacho local do processo original não estiver disponível.

Para usar este recurso, um administrador deve adicionar a capacidade de agente `run_in_background` [agent capability](/docs/configuration/librechat_yaml/object_structure/agents#capabilities). Em seguida, configure as ferramentas elegíveis no Construtor de Agentes:

- **Code Interpreter:** Habilite o Code Interpreter no agente. A execução de código e os comandos de shell tornam-se elegíveis para execução em segundo plano por padrão; desative **Background execution** nas configurações da ferramenta para optar por não utilizá-la.
- **MCP:** Abra um servidor MCP e marque ferramentas individuais, ou o servidor completo, como **Background**.
- **Ferramentas de plugin:** Abra uma ferramenta elegível e ative a **Execução em segundo plano**.
- **Ações:** Ative a **Execução em segundo plano** para uma Ação para optar por incluir todas as operações elegíveis nessa Ação. Ações OAuth não expõem este interruptor. Uma operação também é excluída quando seu próprio esquema já define um parâmetro `run_in_background`, evitando uma colisão com a flag de despacho do LibreChat.

Essas configurações permitem a execução em segundo plano, mas não a forçam. O modelo decide, a cada chamada, se deve executar uma ferramenta elegível em segundo plano.

No chat do LibreChat, quando o código em segundo plano termina, seu stdout e os arquivos gerados aparecem na chamada de código original em vez de na sondagem posterior. Os arquivos gerados também são persistidos para turnos subsequentes. As continuações automáticas apresentam o trabalho concluído em um cartão de tarefa de "wake-up" recolhível, vinculado à tarefa original.

Quando o servidor inicia essa continuação após a execução em primeiro plano anterior ter sido concluída, a conversa aberta é anexada à nova geração e atualiza a saída da tarefa concluída sem a necessidade de recarregar.

As ativações de conclusão automática são habilitadas, a menos que um administrador defina [`endpoints.agents.backgroundTasks.completionWakeups: false`](/docs/configuration/librechat_yaml/object_structure/agents#backgroundtasks), o que restaura o comportamento apenas por sondagem (poll-only). O host pode agrupar várias conclusões elegíveis apenas de conteúdo em uma única continuação. Tarefas que produzem um artefato ativo ainda exigem sondagem no processo que possui a execução.

Administradores também podem optar pelo cancelamento com escopo de proprietário com [`endpoints.agents.backgroundTasks.ordinaryToolCancellation: true`](/docs/configuration/librechat_yaml/object_structure/agents#backgroundtasks). A tarefa relata que o cancelamento foi solicitado até que a invocação subjacente seja concluída, e sua capacidade permanece reservada durante esse intervalo. O cancelamento é cooperativo: uma ferramenta que ignora o sinal de abortar ainda pode ser concluída com êxito. O controle se aplica a ferramentas de segundo plano locais de processo comuns, incluindo Bash anexado, mas não a Subagentes desanexados de propriedade independente.

Apenas ferramentas elegíveis expõem a configuração. A execução comum em segundo plano é local ao processo e não sobrevive à perda de seu processo de trabalho. No entanto, uma vez que um resultado de terminal apenas de conteúdo é persistido, a entrega automática é durável e pode continuar em outra réplica. O registro local ao processo limita as tarefas em execução e os payloads de resultados retidos por conversa, usuário e processo; ele remove trabalhos concluídos quando seguro e retorna um resultado de capacidade com escopo quando o processamento pendente impede a remoção segura. Se uma invocação ignorar o cancelamento, o LibreChat para de renovar sua concessão de produtor após um período de carência de um minuto pós-interrupção e retira a entrega de conclusão automática sem marcar falsamente trabalhos externos incertos como expirados. Subagentes Desconectados (Detached Subagents) usam um caminho de tarefa e transcrição durável separado com controles ao vivo roteados via Redis; veja [Detached Subagent Threads](/docs/features/subagents#detached-subagent-threads).

### Solicitar Aprovação do Usuário e da Ferramenta [#ask-user-and-tool-approval]

A ferramenta **Ask User** permite que um agente pause uma execução para solicitar informações ausentes, apresentar opções ou confirmar como proceder. Uma única chamada pode agrupar até quatro perguntas relacionadas. O LibreChat apresenta uma pergunta de cada vez com botões Voltar, Próximo e etapas de progresso clicáveis; as respostas permanecem disponíveis ao alternar entre as etapas, e respostas de seleção única avançam automaticamente sem a necessidade de envio. O botão Enviar aparece na etapa final após todas as perguntas terem uma resposta, enquanto o botão Pular recusa todo o lote a partir de qualquer etapa. Cada pergunta aceita uma resposta de formato livre ou as opções de seleção única ou múltipla do agente. Enquanto o modelo prepara a chamada, o LibreChat transmite as perguntas para um cartão de progresso; o formulário interativo o substitui quando estiver pronto. Após um envio, a mesma execução é retomada com o mapa de respostas completo. Adicione o **Ask User** a partir do marketplace de Tools; administradores podem remover a capacidade padrão `ask_user_question` para ocultá-la.

Recolher um cartão de múltiplas perguntas retorna o compositor ao seu modo normal de direcionamento ou fila, enquanto o cartão pausado permanece no tópico. O cartão ainda pode ser expandido, respondido, ignorado ou interrompido. Uma pausa de pergunta única continua a usar o modo de resposta do compositor focado.

As respostas enviadas são persistidas com a ação de retomar, portanto, parar enquanto a execução retomada é inicializada não descarta as respostas aceitas.

Após um registro de pergunta ser concluído, ele é recolhido para uma entrada de ferramenta de uma linha por padrão, para que respostas longas não dominem a transcrição. Abra-o para revisar as perguntas e as quebras de linha preservadas nas respostas. A preferência existente **Auto-expand tool details** também controla essa visualização concluída; o formulário ativo permanece aberto enquanto a entrada ainda for necessária.

Cada pergunta aceita um título opcional de até 80 caracteres, texto da pergunta de até 2.000 caracteres, contexto de suporte opcional de até 4.000 caracteres e até 12 opções. Os rótulos das opções são limitados a 280 caracteres, os valores das opções a 500 caracteres e cada resposta enviada a 16.000 caracteres.

Administradores também podem exigir revisão antes que chamadas de ferramentas correspondentes sejam executadas. Dependendo da ferramenta, os usuários podem aprovar, rejeitar, editar argumentos ou responder diretamente. Execuções pausadas são salvas em pontos de verificação (checkpoints) para que possam ser retomadas após a decisão, inclusive em outra réplica quando o checkpointer padrão do MongoDB é utilizado. A aprovação de ferramentas em toda a implantação é desativada por padrão, enquanto um Agent usando um ambiente de Code anexado recebe a [política de segurança ask-by-default](/docs/features/code_interpreter#attached-environment-tool-permissions), a menos que um administrador a desative explicitamente. Veja [`toolApproval` e `checkpointer`](/docs/configuration/librechat_yaml/object_structure/agents#toolapproval).

Enquanto o painel de revisão do compositor estiver aberto para uma aprovação pendente, o cartão de thread correspondente mostra a solicitação como um registro, em vez de duplicar os botões de decisão. Revise as chamadas no painel acima da caixa de mensagem e selecione **Continue**. Recolher o painel a partir do chip do compositor restaura os controles do cartão de thread com suas decisões mantidas; reabri-lo devolve a revisão ao painel. Cartões para outras ações mantêm seus próprios controles.

### Skills [#skills]

Skills permitem que agentes carreguem instruções reutilizáveis a partir de definições em `SKILL.md`. Elas podem ser selecionadas manualmente no chat com `$`, descobertas automaticamente pelo modelo através do catálogo de skills ou aplicadas sempre em cada turno. O Agent Builder também pode habilitar a criação de runtime independente: um agente pode criar uma Skill sem receber o catálogo existente ou editar Skills selecionadas quando o usuário tiver a permissão correspondente.

### Memória [#memory]

A ferramenta **Memory** permite que um agente salve, atualize ou exclua memórias estruturadas do usuário quando este solicita explicitamente que ele se lembre ou esqueça algo. O Memory deve ser configurado para a implantação, permitido pela função e pelas configurações de personalização do usuário e ativado no agente.

Por padrão, um agente utiliza o pool de memória pessoal compartilhado do usuário. Ative **Keep memories separate for this agent** para fornecer a ele uma partição privada por usuário e por agente. O agente isolado não verá memórias compartilhadas existentes ou memórias criadas por outros agentes isolados. Os usuários podem filtrar o painel de Memória por memórias pessoais ou específicas do agente. Ler, criar ou atualizar uma partição de Agente requer acesso atual a esse Agente; a exclusão ainda pode limpar uma partição após a remoção do seu Agente. Veja [User Memory](/docs/features/memory#agent-memory).

### Artifacts [#artifacts]

A funcionalidade de Artifacts permite que seu agente gere e exiba conteúdo interativo:

- Crie componentes React, código HTML e diagramas Mermaid
- Exibir conteúdo em um painel dedicado ao lado do chat, que pode ser expandido para tela cheia ou aberto em sua própria janela do navegador
- Configure instruções específicas para artefatos no nível do agente
- [Mais informações sobre Artifacts](/docs/features/artifacts)

Quando ativado, escolha um dos três modos de instrução:

- **Normal**: Adiciona as instruções de artefato padrão para React, HTML, SVG, Markdown e Mermaid.
- **shadcn/ui**: Adiciona as instruções padrão, além de orientações para a criação de interfaces com a biblioteca de componentes shadcn/ui.
- **Custom**: Mantém a renderização de artefatos ativada, mas não injeta instruções internas de artefatos, dando controle total às instruções do próprio agente.

Configurar artifacts no nível do agente é a abordagem preferida, pois permite um controle mais granular em comparação com a configuração legada de todo o aplicativo.

Se você selecionar **Custom**, inclua no mínimo o formato básico de artefato em suas instruções.

Aqui está um exemplo simples das instruções mínimas necessárias:

````md
When creating content that should be displayed as an artifact, use the following format:

:::artifact{identifier="unique-identifier" type="mime-type" title="Artifact Title"}

```
Your artifact content here
```

:::

For the type attribute, use one of:

- "text/html" for HTML content
- "application/vnd.mermaid" for Mermaid diagrams
- "application/vnd.react" for React components
- "image/svg+xml" for SVG images
````

### Handoffs [#handoffs]

As transferências (handoffs) permitem que um agente principal transfira uma conversa para um agente especialista com o contexto relevante. Em **Advanced settings**, abra a seção de orquestração e adicione até 10 agentes de transferência. Cada transferência configurada cria uma ferramenta de transferência que o modelo pode escolher dinamicamente quando a especialidade do especialista for necessária.

Para cada transferência (handoff), você pode adicionar uma descrição que ajuda o modelo a escolher o especialista certo. Você também pode fornecer instruções de passagem (passthrough instructions) descrevendo qual conteúdo o agente principal deve gerar para o especialista e, opcionalmente, renomear o parâmetro de conteúdo de seu padrão, `instructions`. As transferências estão sempre disponíveis no Agent Builder; diferentemente do Agent Chain e dos Subagents, elas não exigem que uma capacidade de endpoint esteja habilitada. As chamadas de ferramentas de agentes de transferência alcançáveis permanecem estruturadas em turnos posteriores, para que os provedores recebam um histórico de chamadas de ferramentas válido em vez de texto simples.

### Subagentes [#subagents]

Subagents permitem que um agente delegue uma tarefa focada a uma execução filha isolada ou a uma equipe de Agentes salva. Cada filho obtém contexto e execução de ferramentas isolados, retornando então um resultado compacto ao pai, em vez de preencher o contexto do pai com cada etapa intermediária. O trabalho do filho desvinculado também é preservado como um thread navegável e somente para visualização.

Subagentes são diferentes de Agent Chain: cadeias de execução coordenam múltiplos agentes como participantes de um grafo, enquanto subagentes são gerados por um agente como uma chamada de ferramenta para delegação de escopo. O LibreChat preserva o histórico estruturado de chamadas de ferramenta necessário para filhos alcançáveis e membros de equipe salvos em turnos posteriores, mantendo ferramentas indisponíveis fora da execução ativa. Para configuração e limites, veja [Subagents](/docs/features/subagents).

### Configurações Avançadas [#advanced-settings]

Configurações avançadas para seu agente (encontradas na visualização Advanced do formulário de Agent) fora de "capabilities."

#### Max Agent Steps [#max-agent-steps]

Esta configuração permite limitar o número de passos que um agente pode realizar em uma "execução" (run), o que se refere ao loop do agente antes que uma resposta final seja fornecida.

Se deixado sem configuração, o padrão é 25 passos, mas você pode ajustar isso para atender às suas necessidades. Para administradores, é possível definir um padrão global, bem como um máximo global no arquivo [`librechat.yaml`](/docs/configuration/librechat_yaml/object_structure/agents#recursionlimit).

Quando um turno utiliza seu orçamento completo de etapas, o LibreChat preserva a resposta parcial e as chamadas de ferramenta em vez de substituí-las por um erro. A mensagem oferece **Keep going** (Continuar), que inicia um novo turno com um orçamento de ferramentas renovado, e **Answer now** (Responder agora), que solicita que o agente responda a partir do trabalho já concluído sem utilizar mais ferramentas. Dispensar o aviso afeta apenas a visualização atual do navegador.

Administradores também podem limitar argumentos de chamadas de ferramenta transmitidos (streamed) e eventos de delta do modelo com [Agent stream circuit breakers](/docs/configuration/librechat_yaml/object_structure/agents#stream-circuit-breakers).

Um "step" refere-se a uma requisição de API de IA ou a uma rodada de uso de ferramentas (1 ou várias ferramentas, dependendo de quantas chamadas de ferramenta o LLM fornecer a partir de uma única requisição).

Uma resposta única, sem ferramentas, é 1 passo. Uma rodada singular de uso de ferramentas geralmente consiste em 3 passos:

1. Requisição de API -> 2. Uso de Ferramentas (1 ou muitas ferramentas) -> 3. Requisição de API de Acompanhamento

## Gerenciamento de Arquivos [#file-management]

Os Agents suportam várias maneiras de trabalhar com arquivos:

### Na Interface de Chat [#in-chat-interface]

Ao conversar com um agente, você tem quatro opções de upload:

1. **Fazer upload de imagens**
   - Faz upload de imagens para suporte nativo a modelos de visão
   - Envia imagens diretamente para o provedor do modelo

2. **Upload como Texto** (requer a capacidade `context`)
   - Extrai e inclui o conteúdo completo do documento na conversa
   - Usa análise de texto por padrão; aprimorado por OCR se configurado
   - O conteúdo existe apenas na conversa atual
   - Veja [Upload as Text](/docs/features/upload_as_text)

3. **Upload para File Search** (requer a capacidade `file_search`, ativada)
   - Usa busca semântica (RAG) com armazenamentos de vetores
   - Retorna blocos relevantes via uso de ferramentas
   - Ideal para documentos grandes/múltiplos arquivos
   - Sub-ótimo para dados estruturados (CSV, Excel, JSON, etc.)

4. **Upload para Code Interpreter** (requer a funcionalidade `execute_code`, ativada)
   - Adiciona arquivos ao ambiente do interpretador de código
   - Ideal para dados estruturados (CSV, Excel, JSON, etc.)
   - Mais informações sobre o [Code Interpreter](/docs/features/code_interpreter)

### No Agent Builder [#in-agent-builder]

Ao configurar um agente, você pode anexar arquivos em diferentes categorias:

1. **Upload de Imagem**: Para conteúdo visual que o agente pode referenciar
2. **Upload de Pesquisa de Arquivos**: Documentos para capacidades de RAG
3. **Code Interpreter Upload**: Arquivos para processamento de código
4. **Contexto de Arquivo**: Documentos com texto extraído para complementar as instruções do agente

**File Context** usa a capacidade `context` e funciona exatamente como ["Upload as Text"](/docs/features/upload_as_text) - ele usa análise de texto por padrão e é aprimorado por OCR quando configurado. O texto é extraído no momento do upload e armazenado nas instruções do agente. Isso é ideal para fornecer aos agentes conhecimento persistente a partir de documentos, PDFs, arquivos de código ou imagens com texto.

**Prioridade de processamento:** OCR > STT > análise de texto (o mesmo que Upload como Texto)

**Nota:** O texto extraído é incluído como parte das instruções de sistema do agente.

## Compartilhamento e Permissões [#sharing-and-permissions]

Os Agents utilizam o sistema granular de [controle de acesso](/docs/features/access_control) do LibreChat. Cada agent possui sua própria Lista de Controle de Acesso (ACL) e pode ser compartilhado com **usuários**, **grupos**, **funções** específicos ou **publicamente**, cada um em um nível de permissão escolhido.

Serviços confiáveis também podem gerenciar Agents, arquivos anexados e Skills através da [Agent Management API](/docs/features/agents_api#agent-management-api) em beta. Administradores vinculam cada cliente de máquina OIDC a um usuário e tenant existente do LibreChat; cada solicitação herda as capacidades de função e ACLs de recursos atuais daquele usuário, em vez de receber acesso administrativo separado.

### Funções de Acesso [#access-roles]

Ao compartilhar um agente, é atribuída ao beneficiário uma de três funções:

| Função | O que o beneficiário pode fazer |
| ---------- | ----------------------------------------------------------------------------------------------------- |
| **Viewer** | Usar o agente em conversas; não pode abrir o construtor nem ver instruções, ferramentas ou arquivos anexados |
| **Editor** | Visualizar + modificar as instruções, modelo, ferramentas e arquivos do agente |
| **Owner** | Controle total: visualizar, editar, excluir e compartilhar novamente o agente |

O autor original e os administradores sempre mantêm controle total, independentemente da ACL.

### Compartilhando um Agent [#sharing-an-agent]

1. Abra o agente no Agent Builder
2. Clique no botão **Share** no rodapé (visível quando você é o autor, um administrador ou recebeu a permissão `SHARE` naquele agente específico)
3. Pesquise por usuários, grupos ou funções no seletor de pessoas e atribua uma função a cada um
4. Opcionalmente, alterne **Public** para tornar o agente visível para todos na instância (requer a permissão de recurso `SHARE_PUBLIC`)

Os cartões de agente e as visualizações de página inicial exibem o contato de suporte configurado. Quando nenhum é definido, o LibreChat pode recorrer ao nome de exibição do primeiro proprietário identificável, mas não expõe o endereço de e-mail do proprietário, a menos que tenha sido configurado explicitamente como o contato de suporte.

As superfícies de conversa mantêm o Agent como a identidade visível e não recorrem ao seu modelo de suporte ou ao rótulo de model-spec.

Para detalhes completos sobre principais, bits de permissão e como ACLs se compõem com permissões de recursos baseadas em funções, veja [Access Control](/docs/features/access_control).

### Agent Marketplace [#agent-marketplace]

O **Agent Marketplace** permite que os usuários naveguem pelos agentes disponíveis para eles. Abra-o a partir de **Agent Marketplace** na barra lateral; a entrada aparece apenas para usuários cujo cargo tem permissão para usar o Marketplace.

- **Navegar e pesquisar**: Os agentes aparecem em uma grade. Use o campo de pesquisa para encontrar agentes por nome ou descrição, e os seletores de categoria (como **Top Picks**, **All** ou uma categoria específica) para filtrar a lista.
- **Ordenar**: Use **Ordenar por** para organizar os agentes por **Mais recentes primeiro** (o padrão), **Mais antigos primeiro**, **Popular** (mais fixados) ou **Por nome do criador**.
- **Meus agentes**: Ative **Meus agentes** para mostrar apenas os agentes que você criou. Ativá-lo em **Principais escolhas** alterna para **Todos**.
- **Visualizações compartilháveis**: A pesquisa, a ordenação e o filtro **My agents** são mantidos na URL da página (`?q=`, `?sort=`, `?mine=1`), portanto, uma visualização filtrada pode ser adicionada aos favoritos ou compartilhada.

Selecione um card de agente para abrir sua caixa de diálogo de detalhes, que mostra a descrição completa e o contato do agente, juntamente com estas ações:

- **Fixar** ou **Desfixar**: Adicione o agente aos seus agentes fixados ou remova-o deles.
- **Copiar Link**: Copia um link que inicia um novo chat com o agente.
- **Start Chat**: Inicie uma nova conversa com o agente.
- **Experimente um iniciador de conversa**: Quando o agente tiver [conversation starters](#conversation-starters), selecione um para abrir um novo chat com esse prompt já na entrada de mensagem. Ele não é enviado automaticamente, então você pode editá-lo primeiro.

Administradores podem controlar o acesso com a configuração [`interface.marketplace`](/docs/configuration/librechat_yaml/object_structure/interface#marketplace) e as permissões de função descritas em [Controle de Acesso](/docs/features/access_control).

### Controles do Administrador [#administrator-controls]

Os administradores têm acesso às configurações globais de permissão dentro da interface do usuário do construtor de agentes:

- Habilitar/desabilitar o compartilhamento de agentes para todos os usuários
- Controlar permissões de uso de agentes
- Gerenciar direitos de criação de agentes
- Configure as definições de toda a plataforma

Em uma implantação de locatário único (single-tenant) sem escopo, a primeira conta criada para a instância é um administrador. Implantações com escopo de locatário (tenant-scoped) não promovem automaticamente o primeiro usuário registrado; provisione administradores de locatário por meio de um fluxo administrativo confiável. Se você precisar adicionar um administrador manualmente, você pode [acessar o MongoDB](/docs/configuration/mongodb/mongodb_auth) e atualizar o perfil do usuário:

```
db.users.updateOne(
  { email: 'USER_EMAIL_ADDRESS' },
  { $set: { role: 'ADMIN' } }
)
```

O uso de agentes para todos os usuários também pode ser desativado via configuração, [mais informações](/docs/configuration/librechat_yaml/object_structure/interface).

As permissões em nível de recurso (quem pode _usar_, _criar_, _compartilhar_ ou _compartilhar publicamente_ agentes) são gerenciadas a partir do [**Painel de Administração do LibreChat**](/docs/features/admin_panel) em cada função, incluindo quaisquer funções personalizadas. O bloco [`interface.agents`](/docs/configuration/librechat_yaml/object_structure/interface#agents) no `librechat.yaml` ainda pode definir padrões para a função `USER` integrada na inicialização, mas o painel de administração é a forma recomendada para editá-los daqui em diante.

### Compartilhamento em Nível de Usuário [#user-level-sharing]

Usuários individuais podem:

- Compartilhe seus agentes com usuários, grupos ou funções específicos (se `SHARE` estiver habilitado para a função deles)
- Tornar os agentes visíveis para todos na instância (se `SHARE_PUBLIC` estiver habilitado)
- Conceda a cada destinatário um nível de acesso diferente (Visualizador / Editor / Proprietário)
- Compartilhe novamente ou revogue o acesso a qualquer momento a partir da caixa de diálogo de compartilhamento

## Steering e Mensagens em Fila [#steering-and-queued-messages]

Enquanto um Agent está respondendo, você pode enviar outra mensagem a partir do [composer](/docs/features/composer) de duas maneiras:

- **Steer** insere a mensagem na execução atual no seu próximo passo de ferramenta ou agente, para que o agente possa ajustar seu trabalho antes de finalizar.
- **Queue** retém a mensagem e a envia como um turno de acompanhamento normal após a conclusão da resposta atual.

Para conversas de Agentes salvas em um servidor atual, os acompanhamentos (follow-ups) em fila comuns são armazenados no MongoDB. O LibreChat preserva sua ordem FIFO e mantém seu texto, anexos, trechos citados e Skills selecionadas manualmente entre desconexões do navegador, reinicializações do aplicativo e transferências de réplicas. O processamento aguarda a conclusão da resposta anterior antes de admitir o próximo turno. Essa durabilidade é automática e não possui alternância no YAML ou no ambiente; servidores mais antigos e janelas de inicialização curtas sem uma época de geração ativa retêm a fila de compatibilidade do lado do cliente.

A admissão do servidor é serializada dentro de cada fila de conversação. Se a evidência do predecessor ou a propriedade de versão mista for ambígua, o LibreChat exibe **Awaiting reconciliation** e bloqueia ou falha o turno enfileirado afetado em vez de tentar adivinhar e iniciá-lo fora de ordem.

**Steer sooner** solicita que o agente aceite a mensagem no próximo ponto seguro, em vez de aguardar a próxima etapa da ferramenta. Se nenhum texto de resposta ou atividade de ferramenta puder ser mantido ainda, o LibreChat aguarda por um curto período de carência, descarta a tentativa silenciosa ou apenas de raciocínio, insere a mensagem e reinicia o modelo com essa instrução. Assim que o texto da resposta puder ser mantido, o LibreChat para em um limite seguro do provedor, preserva a resposta parcial, insere a mensagem e retoma a mesma resposta do assistente. Uma chamada de ferramenta em execução não é descartada ou interrompida pelo direcionamento (steering); a mensagem é aplicada quando esse trabalho atinge um limite seguro.

Use **Stop** para encerrar o raciocínio ativo e solicitar o cancelamento de uma chamada de ferramenta em primeiro plano. O Stop encaminha o cancelamento para sinalizar ferramentas em primeiro plano compatíveis; tarefas em segundo plano desanexadas mantêm seu ciclo de vida independente. Use o controle dedicado do composer, escolha-o no menu do botão de envio ou pressione `Command/Ctrl + Shift + .`. A ação recorre ao direcionamento comum quando a implementação não consegue interromper o fluxo do provedor ativo.

Em **Configurações → Chat**, **Ao gerar, Enter irá** escolhe a ação padrão. O menu do botão de envio pode substituir essa escolha para uma mensagem individual, e **Direcionar mais cedo ao pressionar Enter** faz com que o Enter solicite aquele ponto de segurança anterior quando o direcionamento for o padrão.

Arquivos e [trechos citados](/docs/features/message_actions#quote-excerpts) acompanham mensagens de steer, queue e interrupt. Skills selecionadas manualmente permanecem em estágio para o próximo turno completo, em vez de serem anexadas a um steer durante a execução.

Os steers pendentes aparecem no final da resposta em streaming, onde permanecerão até que o servidor os insira na execução. O recebimento progride de **Sending** (Enviando) para **Delivered** (Entregue), depois **Steer sooner requested** (Direcionamento antecipado solicitado) quando um ponto seguro anterior foi solicitado e, finalmente, **Applied** (Aplicado) com uma marca de verificação dupla no canto inferior direito da mensagem inline. Os recibos confirmados como aplicados permanecem visíveis após a recarga e em visualizações de compartilhamento ou pesquisa; entregas incertas ou falhas nunca exibem uma marca de verificação de confirmação. Uma vez reconhecido, o menu da mensagem pode recuperar o steer para edição, convertê-lo em um acompanhamento na fila ou cancelá-lo e restaurar seu texto e anexos para o compositor. O LibreChat evita sobrescrever um rascunho mais recente; se o compositor não estiver mais disponível, ele preserva a mensagem recuperada na fila. Um steer com falha permanece disponível para tentar novamente, editar, colocar na fila ou remover.

Os acompanhamentos na fila aparecem em uma lista acima do compositor. Cada um pode ser editado (**Edit message**), removido (**Remove message**), enviado imediatamente com **Send now**, ou reordenado arrastando sua alça ou pressionando as teclas de seta sobre ele. Os acompanhamentos na fila também podem ser convertidos em um steer enquanto a execução ainda estiver ativa ou escalados com **Steer sooner**. Steers em andamento oferecem a mesma escalação quando ainda estão aguardando um limite de ferramenta. Remover uma mensagem na fila com suporte do servidor primeiro cancela sua fonte durável e, em seguida, restaura-a para um compositor vazio quando possível. Se a resposta anterior for abortada ou falhar, o LibreChat marca o turno na fila afetado como falho para revisão, em vez de enviá-lo silenciosamente.

Uma conversa pode ter até 100 turnos ativos na fila. Cada turno na fila aceita até 16.000 caracteres e 10 arquivos. Separadamente, uma execução ativa aceita até 10 direcionamentos (steers) pendentes; cada direcionamento pode incluir até 10 arquivos e é limitado por [`STEER_MAX_LENGTH`](/docs/configuration/dotenv#agent-conversation-controls). **Steer sooner** continua a usar o caminho de direcionamento em tempo real em vez de mover um turno da fila para a frente da linha FIFO durável.

Implantações com múltiplas réplicas baseadas em Redis negociam o protocolo de geração v2 automaticamente. Siga a [orientação de compatibilidade do protocolo de geração](/docs/configuration/redis#generation-protocol-compatibility) ao atualizar de uma versão anterior à `v0.8.8-rc1`.

### Notas [#notes]

- Instruções, parâmetros de modelo, arquivos anexados e ferramentas só são expostos ao usuário se ele tiver permissões de edição.
  - Um agente pode vazar quaisquer dados anexados, sejam instruções ou arquivos, através da conversa, portanto, certifique-se de que suas instruções sejam robustas contra isso antes de conceder acesso de Editor/Proprietário ou tornar o agente público.
- Apenas autores originais, administradores e beneficiários com permissão de Owner podem excluir agentes compartilhados
- Agentes são privados para os autores, a menos que sejam compartilhados

## Entrega de Eventos de Agente [#agent-event-delivery]

O LibreChat inclui uma camada de entrega neutra em relação à origem para eventos assíncronos de Agent. Adaptadores de propriedade da implantação podem normalizar um webhook verificado, mensagem de fila, evento MCP, evento de canal ou evento interno do produto em uma nova execução de Agent (`fire`), um novo turno em um Agent salvo e ramificação existentes (`continue`), ou uma mutação de uma execução ativa (`steer`). Os adaptadores permanecem responsáveis por autenticar sua origem nativa, higienizar payloads e selecionar destinos confiáveis antes de enfileirar.

Os [endpoints de eventos da API de Agents](/docs/features/agents_api#agent-events) em beta expõem acesso autenticado `fire`, `continue` e `steer` para chaves de API de Remote Agents. Sistemas externos podem vincular um ator de origem a um Agent filho direto e continuar esse ator através de eventos sem a necessidade de um recurso adicional. O LibreChat deriva a identidade do usuário, do tenant e da origem a partir da chave de API, impõe o acesso ao Agent e filtros de conteúdo, e requer uma chave de idempotência. Este não é um receptor de webhook de propósito geral não autenticado; adaptadores específicos de provedores ainda devem verificar as assinaturas nativas de webhook antes de chamá-lo.

O recurso experimental [Scheduled Chats](/docs/features/scheduled_chats) é o primeiro produtor integrado do LibreChat para esta camada. Ele cria entregas `fire` recorrentes para Agents salvos e permanece desativado até que um administrador o habilite. Subagents desvinculados usam automaticamente a entrega `continue` idempotente para despertar um Agent pai salvo após a conclusão de um filho; filhos cancelados e Agents pais efêmeros são excluídos.

O MongoDB armazena envelopes versionados limitados, chaves de idempotência, faixas de ordenação, leases, histórico de tentativas, recibos duráveis e mensagens mortas (dead letters). Os workers utilizam entrega pelo menos uma vez (at-least-once) com reivindicações cercadas (fenced claims) e recuo exponencial limitado; recibos bem-sucedidos expiram após 90 dias, enquanto mensagens mortas exigem um reencaminhamento confiável explícito. Entregas do tipo "Fire" criam uma nova conversa. Entregas do tipo "Continue" criam um novo turno na ramificação exata da conversa e são adiadas enquanto essa ramificação estiver em execução, pausada ou finalizando. Atores vinculados também possuem uma caixa de entrada automática: um ator aguarda o resultado do processamento do seu turno atual antes de despachar o próximo evento, enquanto diferentes atores podem ser executados em paralelo. Entregas do tipo "Steer" devem identificar a conversa e a geração existentes e usar admissão estrita para que tentativas ambíguas não possam injetar a mesma instrução duas vezes.

Para continuações vinculadas, o sucesso do transporte inicia um ciclo de vida de processamento durável separado. Uma entrega progride de `started` para `applied`, `completed_no_action`, `failed` ou `cancelled`. As fontes podem exigir uma ferramenta exata e um subconjunto opcional de argumentos com `expectedAction`; o LibreChat relata `applied` apenas a partir de evidências de ferramentas correspondentes observadas pelo host, nunca a partir de prosa escrita pelo modelo. Eventos observacionais compatíveis podem compartilhar um lote `coalesce.key` delimitado, mantendo um registro de idempotência e um recibo por evento de origem. A continuação de ponto de verificação (checkpoint) é usada quando compatível e, caso contrário, recorre ao histórico de mensagens durável.

Bound Event Actors podem pausar para "Ask User" ou aprovação de ferramenta e retomar a invocação exata do actor assinado através da interface normal de human-in-the-loop do LibreChat. A caixa de correio (mailbox) do actor permanece bloqueada até que essa pausa seja retomada ou resolvida, impedindo que um evento posterior ultrapasse a decisão. Esses actors exigem o checkpointer durável do MongoDB. O LibreChat seleciona automaticamente a continuação de checkpoint ou a reconstrução de histórico durável a partir do estado do actor e da capacidade da requisição; o trabalho existente do protocol-v1 permanece no caminho do histórico até que seja esvaziado.

Ações destacadas (Detached Actions) iniciadas por Event Actors são habilitadas automaticamente quando o armazenamento de geração integrado anuncia suporte. O actor permanece suspenso até que a evidência terminal retome sua invocação original, portanto, um lançamento em segundo plano por si só não satisfaz `expectedAction`. O armazenamento em memória mantém esse ciclo de vida coerente enquanto seu processo permanece ativo. O Redis adiciona recuperação de reinicialização durável e transferência de réplica. O trabalho de conclusão de propriedade da capacidade é isolado de workers mais antigos durante um esvaziamento de versão mista; os operadores não selecionam esse comportamento com uma feature flag.

O host de execução normalmente chama o listener vinculado ao processo atual. Configure [`endpoints.agents.eventDriven.selfUrl`](/docs/configuration/librechat_yaml/object_structure/agents#eventdriven) apenas quando este caminho de admissão interno confiável precisar atravessar outra origem HTTP, como um front door TLS.

## Migração Necessária (v0.8.0-rc3+) [#migration-required-v080-rc3]

<Callout type="warning" title="Importante: Migração de Permissões de Agente Necessária">
  A partir da versão v0.8.0-rc3, o LibreChat utiliza um novo sistema de permissões baseado em Lista de Controle de Acesso (ACL) para agentes. Se você estiver atualizando de uma versão anterior, você deve executar a migração de permissões de agentes para que os agentes existentes permaneçam acessíveis.
</Callout>

### O que a migração faz [#what-the-migration-does]

A migração de permissões de agentes transita seus agentes de um modelo simples de propriedade para um sistema sofisticado baseado em ACL com múltiplos níveis de permissão:

- **OWNER**: Controle total sobre o agente
- **EDITOR**: Pode visualizar e modificar o agente
- **VIEWER**: Acesso somente leitura ao agente

Sem executar esta migração, os agentes existentes ficarão inacessíveis através dos novos endpoints da API com reconhecimento de permissões.

### Executando a Migração [#running-the-migration]

Escolha o comando apropriado com base no seu método de implantação:

#### 1. Para o `docker-compose.yml` padrão (se você usa `docker compose up` para iniciar o aplicativo): [#1-for-the-default-docker-composeyml-if-you-use-docker-compose-up-to-start-the-app]

**Visualizar alterações (dry run):**

```bash
docker compose exec api npm run migrate:agent-permissions:dry-run
```

**Executar migração:**

```bash
docker compose exec api npm run migrate:agent-permissions
```

**Tamanho de lote personalizado (para grandes conjuntos de dados):**

```bash
docker compose exec api npm run migrate:agent-permissions:batch
```

#### 2. Para o `deploy-compose.yml` [#2-for-the-deploy-composeyml]

Se você seguiu o [Ubuntu Docker Guide](/docs/remote/docker_linux):

**Visualizar alterações (dry run):**

```bash
docker exec -it LibreChat-API /bin/sh -c "cd .. && npm run migrate:agent-permissions:dry-run"
```

**Executar migração:**

```bash
docker exec -it LibreChat-API /bin/sh -c "cd .. && npm run migrate:agent-permissions"
```

**Tamanho de lote personalizado (para grandes conjuntos de dados):**

```bash
docker exec -it LibreChat-API /bin/sh -c "cd .. && npm run migrate:agent-permissions:batch"
```

#### 3. Para desenvolvimento local (a partir da raiz do projeto): [#3-for-local-development-from-project-root]

**Visualizar alterações (dry run):**

```bash
npm run migrate:agent-permissions:dry-run
```

**Executar migração:**

```bash
npm run migrate:agent-permissions
```

**Tamanho de lote personalizado (para grandes conjuntos de dados):**

```bash
npm run migrate:agent-permissions:batch
```

### O que acontece durante a migração [#what-happens-during-migration]

- **Agentes Privados**: Permanecem acessíveis apenas aos seus criadores (recebem permissão de OWNER)
- **Agentes Compartilhados**: Se um agente foi compartilhado anteriormente, ele receberá entradas de ACL apropriadas como um Agente Público (compartilhado com todos os usuários)
- **Detecção do Sistema**: O LibreChat detecta automaticamente agentes não migrados na inicialização e exibe um aviso

Você pode ajustar as permissões do agente resultante através da interface do Agent Builder.

<Callout type="info" title="Nota">
  O mesmo processo de migração se aplica aos prompts. Se você também tiver prompts existentes, execute a migração de permissões de prompt usando os mesmos comandos, mas substitua `agent` por `prompt` nos nomes dos comandos.
</Callout>

- Capacidade de personalizar agentes para várias funções: titulação (nomeação de tópicos de chat), gerenciamento de memória (contexto/histórico do usuário) e aprimoramento de prompts (assistência/previsões de entrada)
- Mais ferramentas, parâmetros de ferramenta configuráveis, criação dinâmica de ferramentas.

Além disso, a atualização introduz um novo paradigma para o LibreChat, já que sua arquitetura subjacente proporciona uma renovação muito necessária para o aplicativo, otimizando tanto a experiência do usuário quanto o desempenho geral do aplicativo.

Para destacar uma otimização notável, uma geração de IA de aproximadamente 1000 tokens transferirá cerca de 1 MB de dados usando endpoints tradicionais (no momento em que este artigo foi escrito, qualquer opção de endpoint além de Agents e AWS Bedrock).

Ao usar um agente, a mesma geração transferirá cerca de 52 kb de dados, uma redução de 95% na transferência de dados, o que representa uma carga muito menor no servidor e no dispositivo do usuário.

---

Agentes de IA no LibreChat oferecem uma maneira poderosa de criar assistentes especializados sem conhecimento em programação, mantendo a flexibilidade para trabalhar com seus modelos e provedores de IA preferidos.
