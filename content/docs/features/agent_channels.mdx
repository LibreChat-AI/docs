<Callout type="warning" title="Beta Integration Contract">
Agent Channels are a beta integration and are disabled by default. The standalone TypeScript Slack gateway lives in `packages/channel-gateway` in the LibreChat repository. Enabling Channels does not start that process or install a Slack app.
</Callout>

Agent Channels connect external messaging events to [background Agent Responses](/docs/features/background_responses). Channel routes manage identity, admission, leases, delivery receipts, artifacts, and feedback. They are **not an alternative model-execution endpoint**: a compatible gateway submits execution through `/api/agents/v1/responses` using a server-provisioned, bound credential.

## Configuration and prerequisites

Choose organization workspaces for one centrally configured Slack app and UI-managed workspace installations. The YAML example below is the manual single-connection setup; the shared-workspace deployment options also enable Channels and background Responses automatically.

```yaml filename="endpoints / agents"
endpoints:
  agents:
    remoteApi:
      background:
        enabled: true
    channels:
      enabled: true
      transport: socket_mode
      nativeSessions: false
      lifecycleReactions: false
      signatureToleranceSeconds: 300
      socketReconnectDelayMs: 5000
```

Both enablement settings default to `false`. Users need both Agent use and Remote Agents use permissions. Channel setup also requires Agent sharing permission or existing administrator management access; sharing access does not require permission to edit the Agent. Configure `DOMAIN_CLIENT` for trusted owner-review and account-link URLs. Configure a strong `CHANNEL_SERVICE_TOKEN` for the gateway-to-LibreChat service boundary; keep it server-side and distribute it only to a trusted integration process over a secure channel. It is not a browser token or a general Agent API key.

The `transport` option accepts `socket_mode` (default) or `webhook`. This selects the generated Slack manifest; it does not deploy a receiver. Webhook manifests require an HTTPS `gatewayUrl` without credentials, a query, or a fragment. The gateway loads this policy from LibreChat before selecting ingress. `SLACK_TRANSPORT` is an optional deployment assertion; if supplied, it must match the server-selected mode. Missing or unsupported gateway policy prevents startup.

### Database requirement

Durable Channels and stored background Responses require MongoDB transactions. Use a MongoDB replica set or another verified transaction-capable deployment. Standalone MongoDB and FerretDB 2.7 can run ordinary LibreChat, but cannot enable this durable feature. Unsupported channel writes return `transactions_unavailable`; the Agent builder explains the setup requirement. Transactional reads use the primary even when the connection normally prefers secondary reads.

API-key authentication must remain enabled for the gateway's bound execution credential. Linking does not grant Remote Agents permissions, Agent access, new tools or offline access to connected services.

See the [channel configuration reference](/docs/configuration/librechat_yaml/object_structure/agents#channels) for limits and defaults.

## Organization workspaces

A deployment operator configures one Slack app once. Organization administrators then connect workspaces in LibreChat; members link their personal accounts in Slack. Installing an app does not give members access to an Agent or its tools. In a tenant-aware deployment, installations and routing belong to the active tenant. One app/workspace installation has one tenant owner; another tenant cannot claim an active installation.

### One-time operator setup

1. Create a Slack app, or use your deployment's existing app. Enable HTTP Events API delivery and interactivity, rather than Socket Mode. Configure these public HTTPS URLs:

   | Setting | URL |
   | --- | --- |
   | OAuth redirect | `https://chat.example.com/api/channels/workspaces/oauth/callback` |
   | Events API | `https://slack.example.com/slack/events` |
   | Interactivity | `https://slack.example.com/slack/interactions` |

   Use your configured `DOMAIN_SERVER`, including its application base path, for the OAuth URL. The shared deployment opt-in requires this value explicitly; it is not inferred from the gateway hostname. `DOMAIN_CLIENT` is the browser landing origin. The gateway callback URLs have no tenant or connection suffix. Expose only its Slack callback paths; keep gateway health and metrics private.
2. Request bot scopes `app_mentions:read`, `chat:write`, `reactions:read`, `reactions:write`, `files:write`, `im:write` and `im:history`. Subscribe to `app_mention`, `message.im`, `reaction_added`, `reaction_removed` and `agent_session_stopped`. Enable the app's messages tab. Keep token rotation and organization-wide installation disabled: this implementation accepts workspace bot grants, including individual workspaces in Enterprise Grid, and rejects rotating or organization-wide grants.
3. To install into other workspaces, complete Slack's [distribution setup](https://docs.slack.dev/app-management/distribution/). Slack workspace approval policies still apply. Store the app's ID, client ID, client secret and signing secret in the deployment's secret manager. Organization administrators never need these values or access to deployment environment variables.
4. Configure a transaction-capable database and a private `CHANNEL_SERVICE_TOKEN` shared by the API and gateway. Keep API-key authentication enabled for bound execution; retain normal Agent and Remote Agents permission controls.

For Docker Compose, put the four app settings in the normal uncommitted `.env`:

```dotenv
SLACK_APP_ID=<app ID>
SLACK_CLIENT_ID=<client ID>
SLACK_CLIENT_SECRET=<client secret>
SLACK_SIGNING_SECRET=<signing secret>
SLACK_GATEWAY_URL=https://slack.example.com
CHANNEL_SERVICE_TOKEN=<private random token, at least 32 characters>
DOMAIN_SERVER=https://chat.example.com
DOMAIN_CLIENT=https://chat.example.com
LIBRECHAT_IMAGE_TAG=<published release containing organization workspaces>
```

From a fresh LibreChat setup with `.env` and `librechat.yaml` prepared, start the release-matched application and shared gateway:

```sh
docker compose -f docker-compose.yml -f docker-compose.channels.yml \
  -f docker-compose.slack-workspaces.yml -f docker-compose.mongo-replica.yml \
  --profile channels up -d api meilisearch channel-gateway
```

The replica overlay is for a **fresh local database**; read [Existing local data](#existing-local-data) before converting an existing installation. Omit that overlay when you already use a verified transaction-capable external database and supply its normal connection configuration. Use the same Compose project and files for subsequent commands. This does not configure a public reverse proxy or a trusted certificate; route the two Slack paths to the gateway on port 8080 through your normal ingress.

The shared overlay supplies `SLACK_WORKSPACES_ENABLED=true`, which enables webhook Channels, shared app installation and stored background Responses while retaining unrelated YAML policy, limits and explicit API authentication settings. Supplied nonempty app environment values override the corresponding app fields in YAML. With the flag unset or false, YAML continues to control the feature. Choosing shared setup changes the deployment's channel transport to webhook; existing bound connections must use matching webhook configuration. Manual Socket Mode remains available when using the manual setup instead.

No `CHANNEL_ID`, `CHANNEL_TENANT_ID` or app-level `SLACK_APP_TOKEN` is needed in shared mode. The gateway receives its service token and private runtime policy; app client credentials stay in LibreChat, and installed bot tokens are encrypted in the database. For an unreleased source checkout, add `docker-compose.channels-build.yml` and use `up -d --build` rather than expecting an unpublished release image. `npm run backend:dev` still starts only the application; for a source gateway process, omit the bound IDs and app-level token and provide the internal API URL and service token.

### Connect and use a workspace

1. As an organization administrator, open **Settings → Account → Organization Slack workspaces → Connect a Slack workspace**. Approve installation in Slack. Cancel from LibreChat if you do not want to finish; closing Account settings retires an unfinished attempt.
2. Save the Agent, then open **Channels → Add → Organization workspace** and choose the connected workspace. Routing changes require organization administration and permission to share the Agent.
3. Choose **Workspace default** for new direct messages and mentions without a channel-specific assignment, or enter a **Specific Slack channel** ID. If another Agent is already assigned, confirm **Use this agent instead**. Existing conversations keep their original Agent.
4. Activate the connection, invite the bot to the Slack channel and mention it, or send it a direct message. Each member follows **Link your account**, signs into LibreChat, accepts there, then confirms from the same Slack account. Requests use that member's current Agent and tool permissions; installation does not authorize tools or grant offline access to connected services.

### Disconnect and remove

- **Agent Builder → Channels → Manage connection → Remove** removes an assignment for new conversations. Deleting the connection also removes its assignments atomically; existing threads retain their original identity and cannot silently move to another Agent. Disabling a connection stops execution without replacing its routing choices.
- **Settings → Account → Your channel account links** lets a member revoke their own identity link.
- **Settings → Account → Organization Slack workspaces → Disconnect workspace** retires the installation's access in LibreChat. It does not uninstall the app in Slack. A later installation gets a fresh identity, so old connections do not resume automatically. Reconnect an active installation to update its grant; disconnect it first if you want to retire existing connections.
- Removing the configuring person does not delete the organization's installation. Their personal links and credentials are cleaned up, and their Agent connections are retired through the normal channel cleanup.
- To stop the optional service, run the same Compose file list and project with `stop channel-gateway`, or set `channelGateway.enabled: false` and remove the shared opt-in from Helm/API configuration. Ordinary LibreChat can continue. Database topology is independent: do not remove an external replica configuration or convert existing data merely to stop the gateway.

## Set up a manual Slack app connection

1. Save the Agent, then select **Channels → Add** in the Agent builder. Choose per-user or owner-only mode and continue. You need permission to share the Agent.
2. Copy the read-only Slack app manifest into Slack's app setup and install the app into your workspace. Make any app changes in Slack's app settings.
3. Under **Add Credentials**, enter the matching Slack app ID and bot token. For webhooks, also enter its signing secret. Activate the connection. LibreChat verifies the bot identity and stores credentials encrypted; normal setup responses do not return those secrets.
4. Copy the connection ID from the connection details. Configure and start the gateway as described below. It must be able to reach the active connection before startup can complete.
5. Invite the bot to a Slack channel and mention it. Each sender completes their own account-link flow before their request can run.

Browser setup routes live under `/api/agents/{agentId}/channels`: list/create, read `/{channelId}/manifest`, update `/{channelId}`, and delete `/{channelId}`. These use authenticated Agent authorization, not the management API machine-token contract. The create body is `{ "type": "slack", "credentialMode": "per_user" }` (or `shared`). Activation updates use a `slack` object with `appId`, `botToken`, and optional `signingSecret`. To disable a channel, update its status to `disabled`.

## Run the Slack gateway

The gateway is a separate Node.js 24+ process, not an in-process LibreChat plugin. It uses Slack's official Node SDKs and calls LibreChat over HTTP; it does not connect directly to MongoDB or require a general-purpose Agent API key. Manual single-connection mode binds one process to one tenant and connection. Shared mode omits those IDs and serves all installed workspaces with a bounded worker pool.

From a LibreChat source checkout containing `packages/channel-gateway`:

```sh
npm ci
npm run build:packages
npm run build --workspace @librechat/channel-gateway
node --env-file=/secure/channel-gateway.env packages/channel-gateway/dist/main.cjs
```

`npm run backend:dev` starts only LibreChat; it does not start the gateway. Build the application using LibreChat's normal development setup and run the gateway separately. If you reuse the application's `.env`, set the gateway port explicitly: `PORT=8080 node --env-file=.env packages/channel-gateway/dist/main.cjs`. This avoids binding the gateway to the application's port.

Supply the environment file through your normal secret-management process. Do not commit it. A Socket Mode configuration is:

```dotenv filename="channel-gateway.env"
LIBRECHAT_INTERNAL_URL=http://127.0.0.1:3080
CHANNEL_SERVICE_TOKEN=<same server-side token configured in LibreChat>
CHANNEL_TENANT_ID=_
CHANNEL_ID=<connection ID from the Agent builder>
SLACK_TRANSPORT=socket_mode
SLACK_APP_TOKEN=<app-level token with connections:write>
```

`LIBRECHAT_INTERNAL_URL` must be reachable from the gateway process. For example, `127.0.0.1` refers to the gateway's own container when running inside a container. Use the exact tenant ID for a multi-tenant deployment; use `_` only for a single-tenant deployment without a tenant ID. The gateway obtains the bot token and signing secret from LibreChat's authenticated connection bundle, so those values do not need separate gateway environment variables.

For Socket Mode, enable Socket Mode for the same Slack app and create an app-level token with `connections:write`. Keep that token only in the gateway's secret configuration. No public callback URL is needed, but the gateway needs outbound access to Slack and LibreChat.

For webhooks, set `SLACK_TRANSPORT=webhook` instead and omit `SLACK_APP_TOKEN`. Put the gateway behind HTTPS and set these Slack request URLs, replacing the placeholders with the configured, URL-encoded IDs:

```text
Events:       https://gateway.example.com/slack/events/<tenantId>/<channelId>
Interactivity: https://gateway.example.com/slack/interactions/<tenantId>/<channelId>
```

The webhook receiver verifies Slack signatures using the connection's signing secret. Keep LibreChat's channel service routes private to trusted integrations. Expose only the required Slack callback paths publicly; keep health and metrics endpoints on an internal network.

### Docker Compose

The optional `docker-compose.channels.yml` overlay pulls release-matched LibreChat and gateway images. Set `LIBRECHAT_IMAGE_TAG` in `.env` to the release tag you are installing (including `-rcN` for a release candidate); both images use that same tag. If omitted, both use the latest stable release. Images are published for Linux AMD64 and ARM64 when the corresponding LibreChat release is published. A tag predating Agent Channels does not contain a gateway image. The separate `docker-compose.mongo-replica.yml` overlay initializes a single local MongoDB replica member and waits for a writable primary before the application starts. The gateway waits for application health, then authenticates its channel binding and selected Slack transport. Neither service is added to the default stack automatically.

For a **fresh local database**, run these commands from the LibreChat repository root:

1. Prepare `.env` and `librechat.yaml` using the normal LibreChat setup and the channel policy above. Set `LIBRECHAT_IMAGE_TAG` to the published LibreChat release containing Channels. Generate a private service token with `openssl rand -hex 32` and set `CHANNEL_SERVICE_TOKEN` in `.env`. Keep the same Compose files and project name on subsequent commands.
2. Pull and start the application and its dependencies:

   ```sh
   docker compose -f docker-compose.yml -f docker-compose.channels.yml \
     -f docker-compose.mongo-replica.yml up -d --pull always api meilisearch
   ```

3. Sign in, save an Agent, and [set up its Slack channel](#set-up-a-manual-slack-app-connection). Enter the bot token in the Agent builder. Set `CHANNEL_ID` in `.env` to the resulting connection ID. `CHANNEL_TENANT_ID` defaults to `_` for an ordinary OSS installation; supply the actual tenant ID for a tenant-scoped installation. For Socket Mode, also set `SLACK_APP_TOKEN` to the matching app-level token with `connections:write`.
4. Start the gateway:

   ```sh
   docker compose -f docker-compose.yml -f docker-compose.channels.yml \
     -f docker-compose.mongo-replica.yml --profile channels up -d --pull always channel-gateway
   ```

5. Check readiness and startup errors:

   ```sh
   docker compose -f docker-compose.yml -f docker-compose.channels.yml \
     -f docker-compose.mongo-replica.yml --profile channels ps -a
   docker compose -f docker-compose.yml -f docker-compose.channels.yml \
     -f docker-compose.mongo-replica.yml --profile channels logs --tail=100 api mongodb-init channel-gateway
   ```

`mongodb-init` exiting with status 0 is expected. The application and gateway should be running and healthy. A successful Slack credential activation does not prove the gateway is connected: check health and perform a real mention. Missing service/app bindings prevent gateway startup.

The overlay points `LIBRECHAT_INTERNAL_URL` at `http://api:${PORT:-3080}` on the Compose network. The gateway listens on container port `8080`, with no published host ports. Socket Mode needs no inbound port; webhooks need an HTTPS reverse proxy forwarding the required callback paths to `channel-gateway:8080`. The gateway runs as a non-root user with a read-only filesystem and dropped capabilities.

For an existing external transaction-capable database, omit the local MongoDB replica overlay and provide the application connection through your normal Compose override. The base Compose file sets the API service's `MONGO_URI`, so changing only `.env` does not replace that service environment entry. Never run the local initializer against an external database.

A separate gateway environment file can be supplied through `--env-file .env --env-file /secure/channel-gateway.env`. Keep `CHANNEL_SERVICE_TOKEN` identical in LibreChat's own `.env`; Compose substitution does not update the file mounted into the application.

For development or an unreleased checkout, add `-f docker-compose.channels-build.yml` immediately after `-f docker-compose.channels.yml` on **every** Compose command. This explicitly builds both services from the checkout instead of using release images. Use `up -d --build` instead of `up -d --pull always` on that path. The normal release path needs no local Node.js installation or image build.

To build only the gateway image, use the repository root as its build context:

```sh
docker build -f packages/channel-gateway/Dockerfile \
  -t librechat-channel-gateway:local .
```

#### Existing local data

Back up the database, stop LibreChat and every gateway/worker that writes to it, then stop the database before applying the replica overlay. Retain the existing `data-node` directory; do not delete it or remove its volume. Start with that same data directory and the overlays above. Initialization preserves existing documents and only initializes an unconfigured local `rs0` member at `mongodb:27017`. It refuses a different replica configuration rather than silently reconfiguring it. Verify existing users/history before enabling the gateway, and retain the overlay on future restarts.

A single local replica member enables transactions but does not provide high availability. The overlay follows the base development Compose authentication/network settings; it is not a production replica-set recipe. For authenticated, multi-member or production deployments, use the [MongoDB conversion procedure](https://www.mongodb.com/docs/manual/tutorial/convert-standalone-to-replica-set/) and your deployment's backup/security practices.

### Gateway settings

| Environment variable | Default | Purpose |
| --- | --- | --- |
| `PORT` | `8080` | Gateway HTTP port |
| `LISTEN_HOST` | `0.0.0.0` | Listen address; use loopback for a host-only local process |
| `LIBRECHAT_INTERNAL_URL` | `http://localhost:3080` | LibreChat service origin |
| `CHANNEL_SERVICE_TOKEN` | Required | Shared server-side service-boundary token |
| `CHANNEL_TENANT_ID` | Required | Exact connection tenant; `_` for single-tenant deployments |
| `CHANNEL_ID` | Required | Connection ID, not the Slack channel ID or Agent ID |
| `SLACK_TRANSPORT` | Server policy | Optional assertion: `webhook` or `socket_mode`; must match the server policy |
| `SLACK_APP_TOKEN` | Required for Socket Mode | App-level token for the same Slack app |
| `APP_TITLE` | `LibreChat` | Application name in browser-review button labels, such as “Open in LibreChat” |
| `API_CALL_TIMEOUT_MS` | `10000` | Timeout for individual service and Slack API calls |
| `AGENT_INVOKE_TIMEOUT_MS` | `120000` | Timeout for initial background Response submission, not the full Agent run |

`SLACK_API_BASE_URL` defaults to `https://slack.com/api/`; leave it unchanged outside controlled tests. Ingress mode, native sessions, lifecycle reactions, signature tolerance and reconnect pacing come from `endpoints.agents.channels` in `librechat.yaml`, not process feature flags. Actor-bound durable execution cannot be disabled.

The process exposes `/livez` for HTTP-process liveness, `/readyz` and `/healthz` for actual startup/transport readiness, and `/metrics` for Prometheus metrics. An observed ingress-mode or Socket app-binding mismatch makes the gateway unready. Restart gateway replicas after changing ingress mode or Socket app identity. A successful connection activation confirms Slack credentials, not that a gateway is running or connected. Check gateway health and perform a real mention before treating setup as complete.

### Native Agent UI and final replies

By default, a stable working message provides Stop and, when needed, Review controls. Answers are posted after generation, rather than repeatedly replacing a growing reply. Formatting includes code, tables, links, file attachments, and qualified cost/time details; unavailable costs are not estimated.

To opt into Slack's native Agent sessions, enable Agent mode in the Slack app, add the `assistant:write` bot scope and `agent_session_stopped` event subscription, and reinstall the app. These are additional to the basic generated manifest. Then set `endpoints.agents.channels.nativeSessions: true` in `librechat.yaml`. Without the required permissions or Stop subscription, the gateway falls back to durable progress controls. See [Slack Agent sessions](https://docs.slack.dev/ai/agent-sessions/) for app configuration.

Native sessions show processing or waiting-for-input status and return to active when the canonical run finishes. Completed answers can include Helpful/Not helpful controls. Optional lifecycle reactions use `endpoints.agents.channels.lifecycleReactions: true`, are separate from native sessions and require the reaction permissions already present in the basic manifest. Neither an acknowledgement nor a reaction proves a tool completed; Stop requests cancellation of the sender's authorized work, not another participant's run.

## Kubernetes and Helm

The LibreChat Helm chart supports a shared workspace gateway or a manually bound gateway. For manual single-connection setup, first select a published LibreChat release containing Channels through `image.tag` and upgrade the application with the gateway disabled. Configure the channel/background policy above in your existing `librechat.yaml`, then create and activate the connection in the Agent builder. Enable the gateway after obtaining its connection ID.

Enabling the gateway requires an explicit `image.tag` selecting a published LibreChat release containing Channels; the chart refuses to silently use its older application-version default. The gateway image tag defaults to that same selected release. Earlier releases have no gateway image. A custom `channelGateway.image.tag` is available for deliberate image overrides.

### Shared workspace deployment

Select a release containing organization workspaces and provide an existing Secret with `CHANNEL_SERVICE_TOKEN`, `SLACK_APP_ID`, `SLACK_CLIENT_ID`, `SLACK_CLIENT_SECRET` and `SLACK_SIGNING_SECRET`. The service token is shared with LibreChat; the four app settings are referenced only by its API pod. You may use separate gateway-service and app Secrets. Existing explicit API environment entries take precedence over generated Secret references.

```yaml filename="shared-workspace-values.yaml"
image:
  tag: <published-release-containing-organization-workspaces>
channelGateway:
  enabled: true
  mode: shared
  replicaCount: 2
  existingSecretName: gateway-service-credentials
  slackAppSecretName: slack-app-credentials
  ingress:
    enabled: true
    host: slack.example.com
    tls:
      - hosts: [slack.example.com]
        secretName: slack-gateway-tls
```

Set `DOMAIN_SERVER` and `DOMAIN_CLIENT` through the application's normal environment settings. Use a transaction-capable database; the chart does not convert MongoDB topology. Shared mode supplies the app enablement flag and derives `SLACK_GATEWAY_URL` from its ingress host unless explicitly configured in `librechat.configEnv`. It omits connection IDs, tenant IDs and the Socket Mode token. Shared replicas use rolling updates and the existing durable claims; `mode: single` requires one replica and uses replacement updates. Configure the Slack app's public URLs as above, then use Account settings and Agent Builder; no per-workspace Helm values or pods are required.

### Manual connection deployment

```yaml filename="channel-values.yaml"
image:
  tag: <published-release-containing-channels>
channelGateway:
  enabled: true
  channelId: <connection-ID-from-Agent-builder>
  tenantId: "_"
  # Defaults to global.librechat.existingSecretName.
  existingSecretName: librechat-credentials-env
```

For branding, `channelGateway.appTitle` defaults to `librechat.configEnv.APP_TITLE`, then `LibreChat`. Set it explicitly when the API obtains `APP_TITLE` through a Secret or `global.librechat.env`, or choose a shorter gateway title if the application name is not compatible. Gateway titles must be nonempty after trimming, at most 40 UTF-16 characters, and contain no `<`, `>`, `|` or control characters. Helm rejects incompatible inherited titles before deployment; the application can keep its existing longer name.

For manual Socket Mode, the existing Secret must contain `CHANNEL_SERVICE_TOKEN` matching LibreChat's server configuration and `SLACK_APP_TOKEN` for the matching app. By default, the application's existing Secret supplies the same service token to LibreChat. The gateway references only these individual keys, not all provider/database credentials. If you choose a separate gateway Secret, keep its service token identical to the API's. Rotate through your normal secret-management process and restart the API and gateway after rotation; changing an existing Secret does not automatically restart pods.

The gateway derives the API URL from the chart's internal Service and port. Override `channelGateway.internalUrl` for a deliberately different service boundary. Configure gateway resources and annotations through `channelGateway`. Pod identity, `enableServiceLinks`, DNS, host aliases, image pull secrets, node selectors, tolerations and affinity follow the chart's shared platform settings. The configured ServiceAccount is reused while the gateway keeps its Kubernetes API token automount disabled. Manual single mode installs one gateway with replacement updates, so an upgrade may briefly interrupt Slack connectivity; it does not create another channel or Slack app.

For webhook transport, set the server policy to `webhook`, configure its public HTTPS gateway URL and clear `channelGateway.slackAppTokenKey`. Enable the dedicated gateway Ingress using your installed ingress controller and a trusted TLS certificate:

```yaml filename="channel-values.yaml"
channelGateway:
  slackAppTokenKey: ""
  ingress:
    enabled: true
    host: gateway.example.com
    # Empty inherits ingress.className; set this for a different controller.
    className: nginx
    annotations: {}
    tls:
      - hosts: [gateway.example.com]
        secretName: gateway-tls
```

Combine these settings with the enabled gateway and explicit application release above. Set the server's `gatewayUrl` to `https://gateway.example.com`, with no path prefix. The new Ingress routes only `/slack/events` and `/slack/interactions` to the gateway Service on port 8080; its health and metrics routes remain private. It can share the application's hostname: the more specific Slack paths route to the gateway while the existing application Ingress keeps its own backend. Gateway annotations are separate so application rewrite rules cannot silently change callback paths. The gateway Ingress requires Kubernetes 1.19+.

The chart does not install an ingress controller or issue a TLS certificate. Configure TLS through the example Secret, your normal certificate controller/annotations, or an existing HTTPS termination layer. Slack needs a publicly trusted HTTPS endpoint. If you manage a separate external Ingress or need a custom base-path rewrite, leave `channelGateway.ingress.enabled: false` and route the callback paths to the rendered gateway Service yourself; do not add them as paths on the main application Ingress, whose backend is LibreChat. Socket Mode needs no public ingress.

By default, the gateway runs without an automatically mounted Kubernetes API token, as a non-root user with a read-only filesystem and dropped capabilities. The chart's global pod/container security contexts are honored for platform-specific overrides. Gateway version labels follow its selected image tag. `/livez` drives liveness and `/readyz` drives readiness. Startup before the API or channel is available fails closed; Kubernetes retries the process, and it becomes ready after validating the shared app policy or its bound active connection and transport.

**The chart does not configure or convert MongoDB topology.** Supply a transaction-capable database before enabling Channels. The default standalone database cannot run this feature. See the [Helm database configuration](/docs/local/helm_chart) for external database credentials. Normal LibreChat remains usable without enabling Channels.

After applying the values through your normal Helm upgrade, check the gateway Deployment, pod events, logs and readiness. Missing Secret keys block pod startup; incorrect credentials or channel bindings prevent readiness. Finish with a real Slack mention and account linking rather than treating a successful Helm release as proof of integration.

## Rich Agent messages

An Agent can return semantic presentation data in its final answer. The gateway validates the document and converts it deterministically to Slack Block Kit; it does not accept arbitrary Slack JSON, callback IDs, approval controls, file identifiers or modal definitions. Ordinary Markdown remains unchanged. This works in both ordinary threads and native Agent sessions, without a new OAuth scope or a configuration migration.

To enable this behavior for an Agent, add the following to its instructions using the existing Agent editor (or include it in a request when testing):

> When a chart, table, image or card would help, write a short readable answer followed by exactly one final, top-level fenced code block named `librechat-presentation`. Its JSON must be `{ "version": 1, "blocks": [...] }`. Use only the semantic components described below; never emit raw Slack blocks or interactive callback IDs. Use ordinary Markdown for other answers. Use public HTTPS URLs for images and links. The gateway generates complete text fallbacks from the data, so do not repeat every value in the introductory answer.

For example, ask the Agent to compare the following measured results and show both a chart and a table. Its final answer can be:

````text
Latency fell from 20 ms to 17 ms.

```librechat-presentation
{
  "version": 1,
  "blocks": [
    {
      "type": "chart",
      "title": "Latency",
      "chart": {
        "type": "line",
        "axis_config": { "categories": ["Mon", "Tue"], "y_label": "ms" },
        "series": [{ "name": "p95", "data": [{ "label": "Mon", "value": 20 }, { "label": "Tue", "value": 17 }] }]
      }
    },
    { "type": "table", "title": "Measurements", "columns": ["Day", "p95 (ms)"], "rows": [["Mon", 20], ["Tue", 17]] }
  ]
}
```
````

| Semantic component                  | Fields and constraints                                                                                                                                                                                                                            |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `text`, `header`, `context`, `code` | `text` string; maximum 3000, 150, 2000 and 3000 Unicode characters respectively. Text components use literal text, so mentions cannot grant interaction authority. Use ordinary Markdown outside the document for formatted prose.                |
| `divider`                           | No additional fields.                                                                                                                                                                                                                             |
| `image`                             | `url`, `alt`, optional `title` (150 characters). HTTPS URLs only; alt text is required (2000 characters). The gateway never fetches remote media.                                                                                                 |
| `card`                              | Required `title` (150), optional `subtitle` (150), `body` (200), `image: {url, alt}`, and up to three `links: [{label, url}]`. Labels are at most 75 characters. Links navigate only; they cannot run an Agent action.                            |
| `carousel`                          | `cards`: 1–10 cards.                                                                                                                                                                                                                              |
| `table`                             | `title` (150), `columns`: 1–20 labels (150 each), `rows`: 1–200 rectangular rows of strings or finite numbers. Maximum 20,000 characters across cells including headers. Numeric cells retain numeric sorting.                                    |
| `chart`                             | `title` (50), `chart` as described below.                                                                                                                                                                                                         |
| `container`                         | `title` (150), `blocks`: 1–10 text, header, context, code, divider or image components.                                                                                                                                                           |
| `layout`                            | `title` (150), `rows`: 1–5 arrays of 1–3 components, including containers. Charts, tables and carousels each occupy their own row. Layouts cannot nest. The gateway makes the title visible and generates explicit compatibility fallback blocks. |

Charts support `line`, `bar` and `area` with `axis_config: {categories, x_label?, y_label?}` and `series: [{name, data: [{label, value}]}]`. Categories have 1–20 distinct labels; each series must have exactly one point per category. Series names are distinct; at most 12 series are allowed. Names and labels are at most 20 characters, axis titles 50. Values must be finite; negative values are supported. Pie charts instead use `chart: {type: "pie", segments: [{label, value}]}` with 1–12 distinct labels and positive finite values.

A document has at most 40 components and the final answer must fit the 128,000-byte presentation parsing boundary. Malformed, incomplete, quoted, ambiguous or unrecognized documents stay on the ordinary text path. The gateway isolates components into messages, counts nested blocks, enforces two charts and 20,000 table characters per message, and preserves every value and link in generated text. Components which exceed Slack's nested block or serialized payload limits become text. The server's existing `maxDeliveryParts` policy still applies, with an explicit shortening notice when needed.

The gateway freezes versioned blocks and text together before posting. Retries replay that plan. A definitive Slack `invalid_blocks` or `invalid_attachments` rejection permits a text-only retry; ambiguous network outcomes retain the existing reconciliation behavior. Clients that cannot render layouts receive the generated stable fallback blocks.

This is rich **message** support. Existing app-owned Stop, approval, question and feedback workflows remain responsible for interactions. New input forms, App Home, modals, Work Objects, plan/task execution controls and embedded video are not exposed to Agent output. Authorized file attachments continue through the existing artifact delivery path. Slack may limit newer blocks by client or app availability; automated tests cover SDK payloads and rejection fallback, while live rendering requires a configured Slack workspace.

## Identity and permissions

### Shared versus per-user credentials

`per_user` binds each linked Slack actor to that actor's existing LibreChat account. Current tenant membership, account state, role capabilities, Agent permissions, and tool/provider credentials are evaluated for that user.

`shared` does **not** make the Agent public to every Slack participant. Linking is restricted to the channel creator's LibreChat account; execution uses that explicitly linked principal's authority. Do not treat the activator's API key, a Slack display name, an email assertion, or another participant's thread history as consent for a new actor.

Each actor/link revision has its own execution lane. Sharing a Slack thread does not share a LibreChat conversation or expose another actor's files, OAuth state, approvals, usage, or trace session. A different actor cannot inherit the first participant's pending question or approve its tool call. Mode/revision changes, unlinking, account removal, Agent access revocation, and key revocation invalidate old authority rather than silently remapping it.

### Account linking

On the first mention, the gateway sends the actor a private linking prompt. Open its trusted LibreChat URL, sign in, preview the request, and accept it. Return to Slack and mention the bot again to receive the exact-account confirmation, then confirm it there. The next mention can run. The gateway does not replay the original request after linking, and browser acceptance alone does not activate the link.

Manage and revoke your links in Account settings. A link can become unavailable when the channel or account is no longer eligible; you can still withdraw that consent. Restoring eligibility does not reactivate a link you explicitly revoked.

Browser endpoints under `/api/channels/links` support preview, acceptance, listing, and revocation. Mutations require the normal authenticated browser and same-origin checks. Ticket lifetime defaults to 10 minutes; accepted links default to 30 days. Never post a bearer credential or provider OAuth URL into Slack.

## Delivery recovery

The gateway preserves each frozen delivery operation and its receipt. A required operation whose provider result is unknown holds its actor lane: retrying blindly could post the same answer twice. Stopping a worker or requesting cancellation does not prove whether Slack accepted an earlier request.

### Reconcile a verified provider result

1. Pause gateway processing for the affected channel while investigating. Keep the channel enabled and preserve its actor link and source authority; disabling these is not a recovery bypass.
2. Inspect the frozen run plan and retained receipt. Verify in the provider that the exact operation reached the intended channel or thread. Record its message key or file ID, matching the retained attempt and any upload checkpoint. If the result cannot be verified, leave the receipt unknown and the lane held.
3. After the old lease expires, use `POST /api/channels/service/:channelId/runs/claim` with `{ "owner": "<dedicated recovery owner>" }`, normal private service authentication and tenant binding. Verify that the returned run ID is the run being investigated; claims select eligible work and do not take a target run ID. Use the returned current fence, renewing it through `POST /renew` as needed. An expired or replaced worker's fence cannot reconcile the run.
4. Submit the confirmed receipt through the private channel API. These endpoints confirm existing attempts; they do not send messages, replace the frozen plan, reset attempts or accept a retryable outcome.

All paths below are relative to `/api/channels/service/:channelId/runs/:runId`. Send the channel service bearer token and the configured tenant header, using the same internal service URL as the gateway. Preserve the complete fence returned by the claim.

For a delivery operation, `POST /delivery/reconcile`:

```json
{
  "fence": { "runId": "<run ID>", "owner": "<current recovery owner>", "epoch": 1 },
  "receipt": {
    "operationId": "<frozen operation ID>",
    "outcome": "confirmed",
    "attempts": 1,
    "externalMessageKey": "<provider channel ID>:<provider message timestamp>"
  }
}
```

Replace every illustrative value with the actual current fence and retained attempt count; do not assume the example epoch is current. Supply `externalFileId` for a verified file operation as required by its frozen operation and checkpoint. Existing provider identities are immutable; reconciliation cannot replace them with a different message or file.

For a progress update, `POST /progress/reconcile` with the current `fence`, the retained progress `revision`, and a `receipt` containing `outcome: "confirmed"`, the retained `attempts` and verified `externalMessageKey`. The message identity remains fixed across progress revisions.

Once every required delivery operation is confirmed, `POST /commit` with the current `fence` to complete delivery and release the actor lane. Resume normal gateway processing afterward. If any required result remains uncertain, keep the run held rather than resending or recreating it. Optional exhausted effects follow the gateway's bounded recovery policy and do not justify replaying a required answer.

## Gateway protocol boundary

Service requests use `Authorization: Bearer <CHANNEL_SERVICE_TOKEN>` and the exact tenant/channel context. For routes without a tenant path parameter, send the channel's exact tenant in `x-tenant-id`; do not choose a tenant from untrusted message text. The service token permits this integration boundary, not arbitrary user impersonation. Never put it in client-side code, Slack messages, tracing payloads, or public logs. The credential bundle endpoint returns secrets to the trusted gateway and must not be exposed as a public discovery API.

| Stage | Route under `/api/channels` | Responsibility |
| --- | --- | --- |
| Configuration | `GET /service/slack/{tenantId}/{channelId}` | Read the active channel and encrypted-at-rest credentials through an authenticated service boundary |
| Identity | `/service/{channelId}/identity/{externalUserId}` and its ticket/confirm operations | Resolve explicit actor linking; never infer a principal from thread history |
| Admission | `POST /service/{channelId}/runs` | Admit an idempotent event with verified team/app/actor identity |
| Ownership | `POST /service/{channelId}/runs/claim`, then `/{runId}/renew` or `/{runId}/yield` | Claim, renew, or safely yield the exact polling lease |
| Execution preparation | `POST /service/{channelId}/runs/{runId}/response/prepare` | Obtain the bound execution credential, request, and stable request key |
| Response binding | `POST /service/{channelId}/runs/{runId}/response/bind` | Bind the returned Responses identity to the admitted run |
| Progress and result | `/{runId}/advance`, `/{runId}/progress/*`, `/{runId}/plan`, `/{runId}/delivery/*`, `/{runId}/commit` | Project canonical state and record fenced delivery effects |
| Review projection | `POST /service/{channelId}/runs/{runId}/review` | Reauthorize the original actor; obtain the browser fallback and, for the exact external channel, the current private question/tool-review payload |
| Review decision | `POST /service/{channelId}/runs/{runId}/review/decision` | Submit the current actor's decision to the same canonical Response, using its immutable decision receipt and resume preflight |
| Artifacts | `POST /service/{channelId}/runs/{runId}/artifacts/{artifactId}` | Read only an artifact bound to the authorized run |
| Stop | `POST /service/{channelId}/runs/stop-thread` or `/{runId}/cancel` | Cancel only the authorized actor lane/run |
| Feedback | `POST /service/{channelId}/reactions` | Apply authenticated, deduplicated reaction events to confirmed delivered replies |

Run-relative paths in the table are beneath `/service/{channelId}/runs`. Lease mutations carry the exact server-issued `{ runId, owner, epoch }` fence. Treat stale leases, changed authority, and ambiguous delivery outcomes as protocol states to reconcile, not permission to mint a new run or blindly resend a Slack message.

A gateway can yield a Responses-bound polling turn only after its progress writes and renewal loop have drained. The backend invalidates that polling fence and enforces a one-second reclaim cooldown; the next claim increments the epoch. This does not release the actor lane, cancel the provider, change the Response, or erase delivery evidence. Inflight or unknown remote writes cannot yield. If a host does not support yield or the request is uncertain, retain ordinary lease-expiry recovery instead of starting a new execution.

Execution preparation returns an `apiKey`, `requestKey`, optional retained `responseId`, and a Responses `request` with the Agent ID, admitted input, `background: true`, `store: true`, and any authorized continuation. Submit that request to `/api/agents/v1/responses` using the bound key and `Idempotency-Key: <requestKey>`, then bind the returned response ID. Do not substitute a creator's unrestricted key, change the actor/Agent, or send the input to a channel bookkeeping route to execute it.

The gateway owns Slack event verification, retry/deduplication, native message formatting, rate-limit handling, and delivery receipt reconciliation. Preserve exact event identifiers and timestamps. For feedback events, `eventTimestampUs` is an integer timestamp in microseconds; do not round it to milliseconds. Report confirmed, failed, or ambiguous side effects accurately before advancing delivery state.

## Review, files, feedback, and privacy

The public run snapshot contains only an opaque action descriptor. A review request with the original verified actor, current channel revision, and exact `externalChannelId` can obtain minimal private question/tool-approval details. The backend derives the owner and Response from the run and checks the current actor link and source grant; it does not accept an arbitrary user ID. The gateway must show these details only to that actor, not publicly in a shared thread. Slack can use ephemeral choice buttons and private modals. Native tool approval is for the individual call only; unsupported/richer forms retain the browser fallback.

Decision requests include that same actor, revision, external channel, and the existing Responses `decision` body. Backend decision receipts, expiry/conflict checks, full authorization preflight, and same-Response resume remain authoritative. A Slack click alone is not permission to resume work. Provider OAuth URLs remain exclusively in the authenticated browser review flow. See the [background Responses lifecycle](/docs/features/background_responses#review-a-required-action).

The gateway uses private Slack controls for supported questions and individual tool approvals/declines. Tool names and argument previews, when supplied by the authorized review projection, remain private to that actor. Successful submission closes the modal and sends a private acknowledgement; it does not force a separate browser receipt page or claim the tool finished. Provider sign-in and unsupported review forms still open the authenticated browser flow. The Agent's existing approval policy determines whether a tool needs approval; connecting Slack does not make every tool manual or bypass that policy.

A saved decision whose queue publication failed remains retryable with the exact immutable decision; it cannot be replaced by a different answer. Keep Stop available while work remains active and update public progress only through the fenced delivery protocol.

Artifacts are scoped to the authorized run and actor. User-submitted rows do not count as server-generated provenance for artifacts or trace links. Limits default to five files and 10 MiB per file. One `artifactReadTimeoutMs` budget (30 seconds by default) covers catalog queries, storage reads and final authorization rather than restarting for every file. Limits resolution is separately capped at 60 seconds, and its elapsed time counts against the selected budget once available. An expired budget omits artifacts while retaining the answer for authorized text delivery.

New plain-text answer files require more than `artifactAnswerFileThresholdBytes` UTF-8 bytes (6,000 by default); fenced answers also qualify. This threshold controls new projections, while saved descriptors retain their content identity and still require current authorization, retention and maximum-size checks. Do not replace an unavailable artifact with another actor's file or an unauthenticated internal download URL. Usage and cost summaries identify incomplete or unavailable coverage instead of presenting a partial subtotal as the complete thread total.

Reaction feedback maps only to confirmed delivered assistant messages. It does not overwrite the browser's feedback field. Export is constrained by recorded sampling/destination provenance and current export policy. Temporary-chat provenance is retained; an old mapping without that provenance is not treated as a permanent chat. A policy change can suppress export even when the original trace was sampled.

## Operational limits

Disabling a channel or changing its credential mode retires old authority; it does not undo external tool effects. Stop can remain pending until the exact provider is drained and canonical cancellation/cleanup completes. A gateway must poll/reconcile canonical state rather than interpreting an acknowledgement as terminal completion.

With the process-local job store, restarting the API while a tool approval is pending makes the review unavailable. The request stays held for reconciliation and a stale approval does not execute the tool. Durable checkpoint storage alone does not recreate the missing live execution state. Completed history and subsequent thread continuation survive restart.

The gateway package is built from the LibreChat source tree; it is not published as an npm package. This integration does not promise arbitrary chat-platform support, automatic migration of legacy thread-wide identity, or restart-survival of an in-memory OAuth waiter. A restart can require a new browser sign-in; uncertain continuation must not be reported as completed or retried as new work. Legacy thread read/write bookkeeping is not a substitute for actor-scoped runs.
