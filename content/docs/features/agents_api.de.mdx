<Callout type="warning" title="Beta-Funktion">
Die Agents API befindet sich derzeit in der Beta-Phase. Endpoints, Anfrage-/Antwortformate und das Verhalten können sich ändern, während wir auf eine stabile Version hinarbeiten.
</Callout>

LibreChat stellt Agenten über Inferenz- und Ereignisübermittlungs-APIs für externe Anwendungen, Skripte und Dienste bereit.

## Übersicht [#overview]

Die Agents API bietet zwei Inferenz-Schnittstellen, authentifizierte Ereignisübermittlung und Beta-Verwaltungsrouten:

- **OpenAI-kompatible Chat Completions** — `POST /api/agents/v1/chat/completions`
- **Open Responses API** — `POST /api/agents/v1/responses`
- **Agent-Ereignisse** — `POST /api/agents/v1/events`
- **Agentenverwaltung** — `/api/agents/v1/agents`
- **Skill-Verwaltung** — `/api/agents/v1/skills`

Die Inferenz-Schnittstellen unterstützen API-Key-Authentifizierung, optionale OIDC-Authentifizierung und Streaming-Antworten. Agent Events verwenden die Remote Agents API-Key-Authentifizierung, damit LibreChat jede Zustellung an eine stabile Quellidentität binden kann. Management-Routen verwenden stattdessen eine Deployment-Allowlist, die einen OIDC-Machine-Client an einen existierenden LibreChat-Benutzer und -Mandanten bindet.

LibreChat führt [Open Responses](https://www.openresponses.org/) als primäres API-Framework für die Bereitstellung von Agenten ein. Während der Chat Completions endpoint Abwärtskompatibilität mit bestehenden OpenAI-kompatiblen Tools bietet, stellt der Open Responses endpoint die zukünftige Ausrichtung dar.

## Aktivieren der Agents API [#enabling-the-agents-api]

Die Agents API ist hinter der `remoteAgents` Schnittstellenkonfiguration geschützt. Alle Berechtigungen sind standardmäßig auf `false` gesetzt.

```yaml filename="librechat.yaml"
interface:
  remoteAgents:
    use: true
    create: true
```

Siehe [Interface Configuration — remoteAgents](/docs/configuration/librechat_yaml/object_structure/interface#remoteagents) für alle verfügbaren Optionen.

**Hinweis:** Admin-Benutzer haben standardmäßig alle Berechtigungen für Remote-Agents aktiviert.

### OpenAPI-Spezifikation und interaktive Dokumentation [#openapi-specification-and-interactive-docs]

LibreChat kann die öffentliche Agents API-Spezifikation unter `/api/openapi.json` und die interaktive Swagger UI-Dokumentation unter `/api/docs` bereitstellen. Beide Routen sind standardmäßig deaktiviert. Aktivieren Sie diese mit der `openapi`-Einstellung auf oberster Ebene:

```yaml filename="librechat.yaml"
openapi:
  enabled: true
```

Die Spezifikation deckt die auf dieser Seite beschriebenen Routen für öffentliche Inferenz, Ereignisse, Agentenverwaltung und Skill-Verwaltung ab. Lassen Sie die Routen deaktiviert, es sei denn, Ihre Bereitstellung soll die API-Dokumentation offenlegen.

## API Key Management [#api-key-management]

Sobald `remoteAgents.use` und `remoteAgents.create` aktiviert sind, können Benutzer API-Schlüssel über die LibreChat-Benutzeroberfläche generieren. Diese Schlüssel authentifizieren Anfragen an die Agents API.

## Authentifizierung [#authentication]

Die Agents API unterstützt zwei Authentifizierungsmethoden, die unabhängig voneinander oder zusammen verwendet werden können.

### API-Schlüssel [#api-key]

Die API-Schlüssel-Authentifizierung ist standardmäßig aktiviert. Generieren Sie API-Schlüssel über die LibreChat-Benutzeroberfläche, sobald `remoteAgents.use` und `remoteAgents.create` aktiviert sind.

```bash
Authorization: Bearer <YOUR_API_KEY>
```

### OIDC Bearer Token [#oidc-bearer-token]

Für Machine-to-Machine-Szenarien, bei denen Ihre Infrastruktur bereits über einen OIDC-Anbieter verfügt, können Sie sich direkt mit OIDC-Bearer-Tokens ohne einen LibreChat API-Key authentifizieren.

Konfigurieren Sie die OIDC-Authentifizierung in `librechat.yaml`:

```yaml filename="librechat.yaml"
endpoints:
  agents:
    remoteApi:
      auth:
        apiKey:
          enabled: false
        oidc:
          enabled: true
          issuer: https://auth.example.com/realms/myrealm
          # jwksUri is optional and auto-discovered from issuer if omitted
          audience: my-client-id
```

Rufen Sie dann die API mit Ihrem OIDC-Zugriffstoken auf:

```bash
curl -X POST https://your-librechat-instance/api/agents/v1/responses \
  -H "Authorization: Bearer YOUR_OIDC_ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"model": "agent_abc123", "input": "Hello!"}'
```

<Callout type="info">
  Das OIDC-Token muss zu einem Benutzer gehören, der bereits in LibreChat existiert. Der Abgleich erfolgt zuerst über den `sub`-Claim und greift dann auf `email`, `preferred_username` oder `upn` zurück.
</Callout>

Siehe [Agents Endpoint - remoteApi](/docs/configuration/librechat_yaml/object_structure/agents#remoteapi) für alle Konfigurationsoptionen.

<Callout type="warning" title="Agent-Ereignisse erfordern einen API-Schlüssel">
  Die OIDC-only Authentifizierung wird für die Agent Events Endpunkte nicht unterstützt. Verwenden Sie einen Remote Agents API-Schlüssel beim Erstellen von Bindings, beim Einreihen von Events und beim Abrufen des Zustellungsstatus.
</Callout>

## Agent Management API [#agent-management-api]

Die Beta-Agent-Management-API ermöglicht es einem Dienst, Agents und deren zugehörige Ressourcen ohne Browsersitzung zu verwalten. Sie wird unabhängig von Inferenz und Agent-Ereignissen authentifiziert: Es werden nur OIDC-Maschinen-Token akzeptiert, die unter [`endpoints.agents.managementApi`](/docs/configuration/librechat_yaml/object_structure/agents#managementapi) konfiguriert sind.

Jeder konfigurierte OAuth-Client ist an eine bestehende LibreChat `userId` und `tenantId` gebunden. Nach der Token-Verifizierung wird jede Anfrage als dieser Benutzer ausgeführt und behält die aktuellen Rollenberechtigungen, Agent- und Skill-ACLs, Anbieterbeschränkungen, Tool-Berechtigungen, Dateilimits und die Mandantentrennung des Benutzers bei. Eine Client-Bindung macht den Benutzer nicht zum Administrator und gewährt keinen Zugriff auf Ressourcen, die der Benutzer nicht ohnehin verwalten kann.

### Agent-Routen [#agent-routes]

| Methode  | Route                                      | Zweck                                        |
| -------- | ------------------------------------------ | -------------------------------------------- |
| `POST`   | `/api/agents/v1/agents`                    | Einen Agenten erstellen                      |
| `GET`    | `/api/agents/v1/agents`                    | Zugängliche Agenten auflisten                |
| `GET`    | `/api/agents/v1/agents/{id}`               | Einen zugänglichen Agenten lesen             |
| `PATCH`  | `/api/agents/v1/agents/{id}`               | Einen Agenten aktualisieren                  |
| `DELETE` | `/api/agents/v1/agents/{id}`               | Einen Agenten löschen                        |
| `POST`   | `/api/agents/v1/agents/{id}/files`         | Eine Ressourcen-Datei für den Agenten hochladen und anhängen |
| `GET`    | `/api/agents/v1/agents/{id}/files`         | Die zugänglichen angehängten Dateien des Agenten auflisten |
| `DELETE` | `/api/agents/v1/agents/{id}/files/{fileId}` | Eine angehängte Datei vom Agenten entfernen  |

Die Payloads zum Erstellen und Aktualisieren von Agents verwenden dieselben extern unterstützten Felder wie der Agent Builder und lehnen unbekannte Felder auf oberster Ebene ab. Das Erstellen erfordert ein `model`; das Aktualisieren akzeptiert nur die bereitgestellten Felder. Die Antworten legen die unterstützte Agent-Konfiguration sowie `id`, `provider`, das nullbare `model`, `version`, `createdAt` und `updatedAt` offen, ohne Felder für die Persistenz-Eigentümerschaft.

Listen akzeptieren `limit` von 1 bis 100, standardmäßig 20, sowie einen undurchsichtigen `cursor`. Wenn `has_more` wahr ist, übergeben Sie den zurückgegebenen `after`-Wert als nächsten Cursor; dekodieren oder konstruieren Sie keine Cursor in Clients.

```bash
curl https://your-librechat-instance/api/agents/v1/agents?limit=20 \
  -H "Authorization: Bearer YOUR_MACHINE_ACCESS_TOKEN"
```

```bash
curl -X POST https://your-librechat-instance/api/agents/v1/agents \
  -H "Authorization: Bearer YOUR_MACHINE_ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Release assistant",
    "provider": "openAI",
    "model": "gpt-5.6",
    "instructions": "Prepare concise release notes from verified changes."
  }'
```

Datei-Uploads verwenden `multipart/form-data` mit einer `file` und einem `tool_resource`-Wert wie `context`, `file_search` oder `execute_code`. LibreChat wendet die Bereitstellungsfähigkeit, Rollenzuweisung, Upload-Ratenbegrenzung sowie Prüfungen pro Datei, Dateianzahl und Gesamtgröße an, bevor die Ressource angehängt wird. Das Entfernen einer Datei erfordert Bearbeitungszugriff auf den Agenten und schwächt nicht die zugrunde liegenden Datei-Autorisierungsregeln.

### Skill-Routen [#skill-routes]

| Methode | Route | Zweck |
| ------- | ---------------------------------------------------- | ------------------------------------- |
| `GET`   | `/api/agents/v1/skills`                              | Verfügbare Skills auflisten |
| `GET`   | `/api/agents/v1/skills/{id}`                         | Einen verfügbaren Skill lesen |
| `PATCH` | `/api/agents/v1/skills/{id}`                         | Metadaten eines unterstützten Skills aktualisieren |
| `GET`   | `/api/agents/v1/skills/{id}/files`                   | Dateien im Skill auflisten |
| `GET`   | `/api/agents/v1/skills/{id}/files/{relativePath}`    | Eine Skill-Datei lesen |
| `PUT`   | `/api/agents/v1/skills/{id}/files/{relativePath}`    | Eine unterstützte Datei erstellen oder ersetzen |

Skill-Operationen sind auf Skills beschränkt, die für den gebundenen Benutzer sichtbar sind. Lesezugriffe erfordern Skill-Zugriff, während Metadaten- oder Dateischreibvorgänge die entsprechenden Bearbeitungs- und Skill-Authoring-Berechtigungen erfordern. Pfade werden unterhalb des Skill-Roots normalisiert; Traversierung, nicht unterstützte Dateien und zu große Inhalte werden abgelehnt.

### Fehler und Authentifizierung [#errors-and-authentication]

Management-Antworten verwenden strukturierte Fehler mit den Codes `invalid_request`, `not_found`, `permission_denied`, `conflict` oder `internal_error`. Fehler bei der Ressourcenautorisierung können als `not_found` zurückgegeben werden, damit Aufrufer keine unzugänglichen IDs ausspähen können.

Maschinen-Tokens müssen gültig sein, mit dem konfigurierten Aussteller übereinstimmen, einen auf der Zulassungsliste stehenden Client über `azp` oder `client_id` identifizieren und die konfigurierte Subjekt-Regel erfüllen. Standardmäßig müssen Tokens auch mit der konfigurierten Zielgruppe (Audience) übereinstimmen. Für Anbieter wie Amazon Cognito, die Maschinen-Zugriffstokens mit `client_id` anstelle von `aud` ausstellen, setzen Sie `tokenUse: access`, lassen Sie `audience` weg und fordern Sie den erwarteten OAuth-Scope mit `requiredScopes` an. Fehlende Konfiguration oder ungültige Anmeldeinformationen führen zu einem `401`-Fehler; ein gebundenes Konto, das gerade gelöscht wird, führt zu einem `409`-Fehler. Siehe [`managementApi.auth.oidc`](/docs/configuration/librechat_yaml/object_structure/agents#managementapiauthoidc) und [`managementApi.auth.clients`](/docs/configuration/librechat_yaml/object_structure/agents#managementapiauthclients) für die vollständigen Anspruchs- und Bindungsregeln.

## Endpoints [#endpoints]

### Chat Completions (OpenAI-kompatibel) [#chat-completions-openai-compatible]

```
POST /api/agents/v1/chat/completions
```

Verwenden Sie ein beliebiges OpenAI-kompatibles SDK, indem Sie es auf Ihre LibreChat-Instanz verweisen. Der `model`-Parameter entspricht einer Agenten-ID.

**Beispiel mit curl:**
```bash
curl -X POST https://your-librechat-instance/api/agents/v1/chat/completions \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "agent_abc123",
    "messages": [
      {"role": "user", "content": "Hello, what can you help me with?"}
    ],
    "stream": true
  }'
```

**Beispiel mit OpenAI SDK (Python):**
```python
from openai import OpenAI

client = OpenAI(
    base_url="https://your-librechat-instance/api/agents/v1",
    api_key="YOUR_API_KEY"
)

response = client.chat.completions.create(
    model="agent_abc123",
    messages=[{"role": "user", "content": "Hello!"}],
    stream=True
)

for chunk in response:
    print(chunk.choices[0].delta.content, end="")
```

### Modelle auflisten [#list-models]

```
GET /api/agents/v1/models
```

Gibt verfügbare Agents als Modelle zurück. Nützlich, um herauszufinden, welche Agents mit Ihrem API-Schlüssel zugänglich sind.

### Open Responses API [#open-responses-api]

```
POST /api/agents/v1/responses
```

Der Open Responses endpoint folgt der [Open Responses specification](https://www.openresponses.org/), einem offenen Inferenzstandard, der von OpenAI initiiert und von der Open-Source-KI-Community entwickelt wurde. Er ist für agentenbasierte Workflows konzipiert und bietet native Unterstützung für Reasoning, Tool-Nutzung, strukturierte Ausgaben und das Streaming semantischer Ereignisse.

```bash
curl -X POST https://your-librechat-instance/api/agents/v1/responses \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "agent_abc123",
    "input": "What is the weather today?"
  }'
```

#### Vom Aufrufer ausgeführte Funktionstools [#caller-executed-function-tools]

Der Open Responses endpoint akzeptiert standardmäßige `function` tools, die vom Aufrufer bereitgestellt werden. LibreChat stellt diese Definitionen für das Modell bereit, führt sie jedoch nicht aus. Wenn das Modell eine Funktion auswählt, enthält die Antwort ein `function_call` Ausgabe-Element, das vom Aufrufer ausgeführt werden muss.

Um fortzufahren, senden Sie eine neue Anfrage, deren `input` das zurückgegebene `function_call`-Element gefolgt von einem passenden `function_call_output`-Element wiederholt. Diese Übergabe ist zustandslos: Sie erstellt keinen unterbrochenen Run, und `previous_response_id` allein kann den wiederholten Tool-Austausch nicht ersetzen.

```json
{
  "model": "agent_abc123",
  "input": [
    {
      "type": "function_call",
      "call_id": "call_abc123",
      "name": "lookup_order",
      "arguments": "{\"order_id\":\"A-42\"}"
    },
    {
      "type": "function_call_output",
      "call_id": "call_abc123",
      "output": "{\"status\":\"shipped\"}"
    }
  ]
}
```

Namen von Caller-Tools dürfen Buchstaben, Zahlen, Unterstriche und Bindestriche enthalten. Namen müssen eindeutig sein und dürfen kein vom Server bereitgestelltes Tool ersetzen. Ein von einem Caller ausgeführtes Tool muss das einzige Tool sein, das in seinem Durchgang ausgewählt wird; wenn das Modell es mit vom Server ausgeführten Tools mischt, fordert LibreChat das Modell auf, das Caller-Tool erneut und allein auszuführen.

Für von LibreChat ausgeführte Agent-Tools erzwingen beide Headless-Inferenz-Endpunkte eine aktivierte [`endpoints.agents.toolApproval`](/docs/configuration/librechat_yaml/object_structure/agents#toolapproval)-Richtlinie, einschließlich `deny`, `ask` und programmatischer Hooks. Diese Aufrufe verfügen über keinen interaktiven Genehmigungs-/Fortsetzungskanal: `deny` und `ask` blockieren das Tool, anstatt eine Genehmigungsaufforderung zu öffnen. Konfigurieren Sie explizite Freigaben nur für Tools, die der API-Client unbeaufsichtigt ausführen können soll; wenn die Richtlinie deaktiviert ist, werden deren Genehmigungs-Hooks nicht ausgeführt. Vom Aufrufer ausgeführte Funktions-Tools bleiben in der Verantwortung des Aufrufers.

## Agent-Ereignisse [#agent-events]

Agent Events ermöglichen es einem authentifizierten Controller oder Quell-Adapter, dauerhafte Arbeit an einen Agenten zu übermitteln. Die Event-Zustellung ist eine Beta-Funktion; ihr Anfrage-, Antwort- und Laufzeitverhalten kann sich noch ändern.

Die endpoints verwenden den authentifizierten Benutzer, den Mandanten und den API-Schlüssel; der Ziel-Agent muss für diesen Benutzer unter den bestehenden Remote Agents-Berechtigungen sichtbar sein. Agent Event-Anfragen verwenden außerdem den dedizierten [`rateLimits.agentEvents`](/docs/configuration/librechat_yaml/object_structure/config#ratelimits)-Bucket.

### Ein Ereignis übermitteln [#deliver-an-event]

```http
POST /api/agents/v1/events
Authorization: Bearer <REMOTE_AGENTS_API_KEY>
Idempotency-Key: webhook-42-resource-7
Content-Type: application/json

{
  "mode": "fire",
  "event": {
    "id": "resource-7-ready-3",
    "type": "resource.ready",
    "occurredAt": 1786967999000,
    "payload": { "resourceId": "resource-7" }
  },
  "target": { "agentId": "agent_abc123" },
  "input": "Resource resource-7 is ready. Inspect it and report the result.",
  "orderingKey": "resource-7"
}
```

Senden Sie genau einen `Idempotency-Key` Header und verwenden Sie diesen erneut, wenn Sie dieselbe Zustellung eines Quellereignisses an ein Ziel wiederholen. Der Schlüssel muss 1-256 Buchstaben, Zahlen oder die Zeichen `._~:/+=-` enthalten. Die Wiederverwendung eines Schlüssels mit unterschiedlichem Zustellungsinhalt führt zu einem Konflikt.

Der Aufrufer liefert die Event-`id`, den `type`, `occurredAt` und die bereinigte `payload`. LibreChat ersetzt jede vom Aufrufer bereitgestellte `event.source` durch die authentifizierte API-Key-Identität und leitet den Benutzer, den Tenant, die Request-ID sowie die Empfangszeit ab. Platzieren Sie keine Anmeldeinformationen oder Transport-Geheimnisse in Event-Payloads, da akzeptierte Zustellungen dauerhaft gespeichert werden.

`orderingKey` ist optional. Verwenden Sie einen stabilen Wert, wenn Lieferungen aus verschiedenen Quellen für dieselbe Ressource in der Reihenfolge bleiben müssen.

Eine erfolgreiche Anfrage gibt `202 Accepted`, eine undurchsichtige Zustellungs-`id`, ihren aktuellen Status sowie einen `Location`-Header zurück. Fragen Sie diesen Standort ab:

```http
GET /api/agents/v1/events/{delivery_id}
Authorization: Bearer <SAME_REMOTE_AGENTS_API_KEY>
```

Die Zustellung kann `pending`, `leased`, `succeeded` oder `dead` sein. Die Statusantwort enthält Versuche und Zeitstempel sowie ein Ergebnis oder einen öffentlichen Fehler, sobald der Vorgang abgeschlossen ist; sie legt weder die gespeicherte Nutzlast, den Sortierschlüssel, den Wiederholungsverlauf noch die Worker-Identität offen. Der Statuszugriff ist auf denselben Benutzer, Mandanten und API-Schlüssel-Ursprung beschränkt.

Für ein gebundenes `continue` bedeutet `succeeded`, dass der Agent-Turn zugelassen wurde, nicht, dass die angeforderte Arbeit abgeschlossen ist. Sein Status legt daher auch einen dauerhaften `handling`-Lebenszyklus offen: `started`, gefolgt von genau einem der Zustände `applied`, `completed_no_action`, `failed` oder `cancelled`.

Aktionsbewusste Quellen können eine `expectedAction` mit einem Tool-Namen und einer optionalen Teilmenge von Argumenten enthalten. LibreChat meldet `applied` nur dann, wenn genau diese Generierung abgeschlossen ist und die vom Host beobachteten Tool-Nachweise mit dem Vertrag übereinstimmen; vom Modell verfasste Texte werden niemals als Beweis akzeptiert. `fire`-, `steer`- und ungebundene `continue`-Übermittlungen lehnen `expectedAction` ab.

Erfolgreiche `fire`-Ergebnisse beinhalten die Konversations- und Generierungsidentität, auf die ein späteres `steer`-Ereignis abzielen kann.

### Ereignisgesteuerte Child Agents [#event-driven-child-agents]

Ein externes System kann einen Quell-Akteur an einen direkten untergeordneten Agent binden und dann dieselbe untergeordnete Konversation über Ereignisse hinweg fortsetzen. Gebundene untergeordnete Fortsetzungen erfolgen automatisch, nachdem die Überprüfungen für die API-Key-Identität, die Bindungs-Eigentümerschaft, die Eltern-Beziehung und die Agent-Autorisierung erfolgreich waren; es gibt keinen separaten Funktionsschalter.

Registrieren Sie den Akteur mit demselben API-Schlüssel, der auch seine späteren Turns übermitteln wird:

```http
POST /api/agents/v1/events/bindings
Authorization: Bearer <REMOTE_AGENTS_API_KEY>
Idempotency-Key: championship-7-player-hanae
Content-Type: application/json

{
  "actorId": "hanae-kobayashi",
  "parentConversationId": "director-conversation-id",
  "parentMessageId": "director-message-id",
  "target": { "agentId": "agent_hanae" }
}
```

`actorId` kann bis zu 128 Zeichen enthalten. Das übergeordnete Element muss eine gewöhnliche Agent-Konversation sein, und das Ziel muss als einer der direkten Subagents dieses Agenten oder als erlaubter Self-Spawn konfiguriert sein. Eine neue Bindung gibt `201` zurück; ein idempotentes Replay gibt `200` zurück. Beide Antworten enthalten `id`, `actorId`, `agentId` und `threadId`.

Senden Sie spätere Turns mit der zurückgegebenen Bindungs-ID:

```http
POST /api/agents/v1/events
Authorization: Bearer <SAME_REMOTE_AGENTS_API_KEY>
Idempotency-Key: game-12-ply-17-hanae
Content-Type: application/json

{
  "mode": "continue",
  "bindingId": "evtbind_...",
  "event": {
    "id": "game-12-ply-17",
    "type": "chess.turn.ready",
    "occurredAt": 1786968000000,
    "payload": { "gameId": "game-12", "expectedPly": 17 }
  },
  "input": "Your clock is running. Read the position and submit one legal move.",
  "expectedAction": {
    "tool": "submit_move",
    "arguments": { "gameId": "game-12" }
  }
}
```

LibreChat löst den untergeordneten Agent, den Thread, das neueste Branch-Leaf und die Ordering-Lane unmittelbar vor dem Dispatch aus der Bindung auf. Vom Aufrufer bereitgestellte Ziel- und Ordering-Felder können eine gebundene Fortsetzung nicht umleiten. Der `Idempotency-Key` der Anfrage wird zur stabilen öffentlichen Identität für diesen untergeordneten Turn über Zustellungswiederholungen, Generation-Leasing, persistierte Nachrichten, Live-Aktivitäten und eine spätere HITL-Wiederaufnahme hinweg.

Jede Bindung verfügt über ein automatisches, dauerhaftes Postfach. Das nächste Ereignis bleibt in der Warteschlange, bis der aktuelle Durchgang `applied`, `completed_no_action`, `failed` oder `cancelled` erreicht; verschiedene Bindungen bleiben unabhängig und können parallel ausgeführt werden. Die Fortsetzung eines Checkpoints wird nur für einen kompatiblen, initialisierten Durchgang versucht. Wenn ein Checkpoint fehlt oder nicht wiederhergestellt werden kann, greift LibreChat auf den dauerhaften Nachrichtenverlauf zurück, ohne dabei die Prüfungen für Empfang, Autorisierung oder erwartete Aktionen abzuschwächen.

Ein gebundener Akteur kann für „Ask User“ oder eine Tool-Genehmigung pausieren. LibreChat speichert die exakte signierte Unterbrechung dauerhaft, bevor die ausstehende Aktion offengelegt wird, und das Postfach der Bindung bleibt blockiert, bis derselbe Akteur-Aufruf fortgesetzt oder abgeschlossen wird. Event-Akteure erfordern den dauerhaften MongoDB-Checkpointer; `type: memory` ist nicht kompatibel. LibreChat verhandelt das Generierungsprotokoll v2 und wählt automatisch zwischen Checkpoint oder Verlaufskontinuität. Bestehende Arbeiten mit dem Protokoll v1 verbleiben auf dem Pfad des dauerhaften Verlaufs, bis sie abgeschlossen sind. Siehe [Generation Protocol Compatibility](/docs/configuration/redis#generation-protocol-compatibility) für Anforderungen bei Bereitstellungen mit gemischten Versionen.

### Zusammenführen von Beobachtungsereignissen [#coalescing-observational-events]

Quellen, die belegen können, dass mehrere gebundene `continue`-Ereignisse austauschbare Beobachtungen sind, können denselben quellendefinierten `coalesce.key` erhalten:

```json
{
  "mode": "continue",
```

LibreChat sammelt kompatible Ereignisse für bis zu 750 ms, mit maximal 8 Ereignissen und 512 KiB an kombinierten Envelopes. Das untergeordnete Element empfängt ein deterministisches Batch-Dokument, aber jedes Quellereignis behält seinen eigenen `Idempotency-Key`, Zustellungsnachweis und Empfangsbeleg.

Verwenden Sie Coalescing nur für nicht handlungsrelevante Beobachtungen. Es wird für `fire`, `steer`, ungebundenes `continue` sowie Lieferungen mit `expectedAction` abgelehnt; verwenden Sie es nicht für Befehle, Genehmigungen, HITL-Anfragen, Fences oder Ereignisse, bei denen das individuelle Timing eine Rolle spielt.

In der authentifizierten übergeordneten Konversation erscheint jeder gebundene Akteur unter seiner zugehörigen übergeordneten Nachricht. Das Subagent-Panel kann zwischen Akteuren und Turns wechseln, frühere Aktivitäten laden und einen Turn erweitern, um dessen vollständige gebundene Aktivität anzuzeigen. Ereignisdetails umfassen den Typ, die Quelle, den Zeitpunkt des Auftretens und die erwartete Aktion. Sichtbare Run-Steps, Tools, Nachrichten und Reasoning-Marker sind enthalten, ohne den rohen Reasoning-Text. Der übergeordnete Index gibt maximal 64 untergeordnete Threads und 20 aktuelle Aufgaben pro Kind aus einem begrenzten Quellfenster zurück, meldet eine Kürzung, anstatt Vollständigkeit zu implizieren, und begrenzt die Antwort auf 96 KB. Er ist übergeordnet-, benutzer- und mandantenautorisiert; Bindungen, Quellschlüssel-IDs, Lease-Token und Worker-Status sind in der Projektion nicht enthalten.

Der untergeordnete Thread bleibt von der normalen Konversationsnavigation verborgen und ist für menschliche Chat-Routen schreibgeschützt. Er erbt die temporäre oder Ablaufrichtlinie des übergeordneten Threads und ist auf eine direkte untergeordnete Ebene beschränkt. Eine Bindungs-ID allein gewährt keinen Zugriff; Continuations sind auf den Benutzer, den Mandanten und den API-Schlüssel beschränkt, von denen sie erstellt wurden.

### Aktionen des losgelösten Event-Akteurs [#detached-event-actor-actions]

Event Actor-Turns können berechtigte Actions abtrennen und diese dauerhaft abschließen. Die Zustellung verbleibt in ihrem Verarbeitungslebenszyklus, während die Action ausgeführt wird; ein dauerhafter terminaler Nachweis setzt den ursprünglichen signierten Actor-Aufruf fort, und nur der resultierende, vom Host beobachtete Tool-Nachweis kann `expectedAction` erfüllen. Wiederholungen und konkurrierende Replikate können dieselbe reservierte Action nicht zweimal starten. Wenn LibreChat nicht feststellen kann, ob ein externer Seiteneffekt begonnen hat, stellt es den Start unter Quarantäne, anstatt ihn blind erneut zu versuchen.

LibreChat ermöglicht diese interne Vervollständigungsarbeit automatisch, wenn der ausgewählte integrierte Generierungsspeicher Unterstützung dafür anzeigt. Der In-Memory-Speicher führt Start, Vervollständigung und Fortsetzung in einem Prozess aus und kann diese Arbeit nach dem Beenden des Prozesses nicht wiederherstellen. Redis-Generierungs-Streams fügen dauerhafte Neustart-Wiederherstellung und Replica-Handoff hinzu. Zuständigkeitsbasierte Zustellungs- und Wiederherstellungsdatensätze bleiben für ältere Claimer während eines Mixed-Version-Drains unsichtbar; es gibt kein vom Operator verwaltetes Producer-Flag.

## Token-Nutzungsverfolgung [#token-usage-tracking]

Alle API-Inferenzanfragen für Agents erfassen die Token-Nutzung basierend auf dem Guthaben des Benutzers, sofern die Token-Abrechnung konfiguriert ist. Sowohl bei Streaming- als auch bei Nicht-Streaming-Antworten werden alle abgerechneten Aufrufe des primären Agents und der Subagent-Modelle in den Gesamtsummen auf oberster Ebene aggregiert. Die Antwort enthält zudem identitätsfreie Aufschlüsselungen der `primary`- und `subagent`-Token. Details zu Cache- und Reasoning-Token werden einbezogen, sofern der Anbieter diese bereitstellt.
