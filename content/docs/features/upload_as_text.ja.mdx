# ファイルをテキストとしてアップロード [#upload-files-as-text]

PDF、コードファイル、またはスプレッドシートをAIに渡して、単に「これを読んで」と伝えたいと思ったことはありませんか？LibreChatの統合アップローダーは、ファイルの種類と選択されたendpointに基づいて、ファイルをプロバイダーにルーティングするか、自動的にテキストを抽出します。

ファイルを添付すると、LibreChatがそのファイルからテキストを抽出し、その内容全体が会話に直接貼り付けられます。AIはプラグインやベクトルデータベース、追加のサービス設定を必要とすることなく、その内容をすべて読み取ることができます。箱から出してすぐに動作します。

<Callout type="info" title="セットアップ不要">
  Upload as Textは、あらゆるLibreChatインスタンスですぐに動作します。組み込みのテキスト解析を使用するため、OCR、RAGパイプライン、または外部サービスを必要とせずに開始できます。
</Callout>

---

## How to use it [#how-to-use-it]

<Steps>
  <Step>
    ### パレットを開く [#open-the-palette]

    [メッセージコンポーザー](/docs/features/composer#add-files)の **+** をクリックします。ファイルをコンポーザーにドラッグ＆ドロップすることもできます。
  </Step>
  <Step>
    ### ソースを選択 [#choose-a-source]

    **Attach**セクションで、**From Local Computer**を選択するか、設定されている場合は**From SharePoint**を選択します。デフォルトのアップローダーでは、モデルやツールの送信先を選択するように求められることはありません。

    管理者が [`legacyFileUploadUX`](/docs/configuration/librechat_yaml/object_structure/file_config#legacyfileuploadux) を有効にしている場合は、アップロード先を自分で選択できます。**More upload options** を選択し、**Upload as Text** を選択してください。
  </Step>
  <Step>
    ### ファイルを選択 [#choose-your-file]

    ファイルを選択します。LibreChatは、ファイルタイプとendpointの機能に基づいて、ネイティブプロバイダー配信、テキスト抽出、またはツール専用ストレージを選択します。
  </Step>
  <Step>
    ### 質問する [#ask-your-question]

    通常通りプロンプトを入力してください。選択されたFile SearchおよびCodeツールは、必要な場合にのみファイルを受け取ります。
  </Step>
</Steps>

複数のファイルを選択した場合、LibreChatは個別の重複ファイルやファイルごとのサイズ制限を超過したファイルをスキップし、スキップされたファイル名を通知で表示した上で、有効なファイルのアップロードを継続します。ファイル数および合計バッチサイズの制限は、残ったファイルに対しても引き続き適用されます。残ったバッチがいずれかの制限を超えた場合、そのバッチ全体が拒否されます。単一ファイルの動作に変更はありません。

<Callout type="warn" title="オプションが表示されませんか？">
  `legacyFileUploadUX` が有効な状態で、**その他のアップロードオプション**の下に **テキストとしてアップロード** が表示されない場合、管理者が `context` 機能を無効にしている可能性があります。この機能はデフォルトでオンになっていますが、機能リストがカスタマイズされている場合は、`context` を明示的に含める必要があります。以下の [設定セクション](#the-context-capability) を参照してください。
</Callout>

## 長いテキストをファイルとして貼り付ける [#paste-long-text-as-a-file]

通常のメッセージコンポーザーにおいて、LibreChatは2,500文字を超える貼り付けを「テキストとしてアップロード」された添付ファイルに変換できます。これにより、長い貼り付け内容を入力欄から除外しながら、会話コンテキストを通じてその内容をモデルに提供し続けることが可能です。最初の添付ファイルには `pasted-text.txt` という名前が付けられ、それ以降の貼り付けテキストによる添付ファイルには番号付きの名前が付けられます。

ブラウザローカルの **Paste long text as a file**（長いテキストをファイルとして貼り付け）設定は、**Settings > Chat > Sending** でデフォルトで有効になっています。短い貼り付けや、エージェントの **Ask User** フォームへの回答中に貼り付けられたテキストは、インラインのままとなります。コンテキストのアップロードが利用できない場合も、テキストはインラインのままです。添付ファイルのアップロードが失敗した場合、LibreChatは新しいドラフトを上書きすることなく可能であれば、コンポーザーにテキストを復元します。

貼り付けられたテキストの添付ファイルは、他の「テキストとしてアップロード」されるファイルと同じファイルサイズ、トークン、および [`fileTokenLimit`](#token-limits-and-truncation) のルールに従います。

## 内部の仕組み [#what-happens-under-the-hood]

アップロードがテキストとしてルーティングされる際、LibreChatは生のバイトデータをそのままプロンプトに投入することはありません。クリーンで読み取り可能なテキストを抽出するために、処理パイプラインを実行します：

1. **MIME type detection** — LibreChatは、アップロードされたファイルの種類（PDF、画像、音声、ソースコードなど）をMIMEタイプを検査することで確認します。
2. **メソッドの選択** — ファイルの種類と利用可能なサービスに基づいて、以下の優先順位で最適な抽出メソッドを選択します。

<Tabs items={["優先順位", "決定の例"]}>
  <Tabs.Tab>
    | 優先度 | メソッド | 使用されるタイミング |
    |----------|--------|---------------|
    | 1番目 | **OCR** | ファイルが画像またはスキャンされたドキュメントであり、_かつ_ OCRが設定されている場合 |
    | 2番目 | **STT** (Speech-to-Text) | ファイルが音声であり、_かつ_ STTが設定されている場合 |
    | 3番目 | **テキスト解析** | ファイルが既知のテキストMIMEタイプと一致する場合 |
    | 4番目 | **フォールバック** | 上記のいずれにも一致しない場合 — とにかくテキスト解析を試みる |
  </Tabs.Tab>
  <Tabs.Tab>
    **OCRが設定されたインスタンス上の `.pdf` ファイル:**
    → OCRが実行されます。スキャンされたドキュメントや複雑なレイアウトに最適です。

    **デフォルトインスタンス上の `.pdf`（OCRなし）：**
    → テキスト解析で処理されます。デジタル作成されたPDFに対しては良好に動作します。

    **`.py` Python ファイル:**
    → 直接テキスト解析へ。ソースコードはすでにテキストであるため、変換は不要です。

    **STTが設定されたインスタンス上の `.mp3` ファイル:**
    → Speech-to-Text（音声認識）機能により、会話用のテキストに書き起こされます。

    **OCRが設定されていない `.png` スクリーンショット:**
    → テキスト解析にフォールバックします（結果は限定的です。画像用にOCRを設定することを検討してください）。
  </Tabs.Tab>
</Tabs>

3. **トークンの切り詰め** — 抽出されたテキストは `fileTokenLimit`（デフォルト: 100,000トークン）に合わせてトリミングされるため、モデルのコンテキストウィンドウを超えることはありません。
4. **プロンプトインジェクション** — テキストは、あなたのメッセージと並んで会話コンテキストに含まれます。

Upload as Text（テキストとしてアップロード）の添付ファイルをプレビューまたはダウンロードする際、LibreChatはファイルレコードに保存された抽出済みテキストを提供します。OCRやその他のパーサーによってテキストが生成され、ストリーミングする元のバックアップファイルが存在しない場合でも、ダウンロードには `.txt` ファイル名が使用されます。

## サポートされているファイル形式 [#which-files-are-supported]

<Tabs items={["テキストとコード", "ドキュメント", "画像", "オーディオ"]}>
  <Tabs.Tab>
    これらは直接解析されます。すでにテキストであるため、変換は不要です。

    - プレーンテキスト (`.txt`)、Markdown (`.md`)、CSV、JSON、XML、HTML、CSS
    - プログラミング言語 — Python, JavaScript, TypeScript, Java, C#, PHP, Ruby, Go, Rust, Kotlin, Swift, Scala, Perl, Lua
    - 設定ファイル — YAML, TOML, INI
    - シェルスクリプト、SQLファイル
  </Tabs.Tab>
  <Tabs.Tab>
    テキスト解析はこれらを標準で処理します。OCRが設定されている場合は、複雑なレイアウトに対してより高い精度を実現するためにOCRが処理を引き継ぎます。

    - **PDF** — デジタルおよびスキャン済み（スキャン済みのPDFはOCRを利用すると効果的です）
    - **Word** — `.docx`, `.doc`
    - **PowerPoint** — `.pptx`, `.potx`, `.ppt`
    - **Excel** — `.xlsx`, `.xls`
    - **EPUB** ブック
  </Tabs.Tab>
  <Tabs.Tab>
    画像から有用なテキストを生成するには **OCRが必要** です。これがない場合、結果の精度は低くなります。

    - JPEG、PNG、GIF、WebP
    - HEIC、HEIF（Apple形式）
    - スクリーンショット、文書の写真、スキャンされたページ
  </Tabs.Tab>
  <Tabs.Tab>
    音声ファイルには **STT** の設定が必須です。フォールバック機能はないため、音声を「テキスト解析」することはできません。

    - MP3、WAV、OGG、FLAC
    - M4A, WebM
    - 音声録音、ポッドキャストクリップ
  </Tabs.Tab>
</Tabs>

LibreChatは、Linux上のChrome（`application/x-shellscript`）やlibmagic（`text/x-shellscript`）によって報告されるシェルスクリプトのMIMEバリアントを、エンドポイントの許可リストをチェックする前に正規の`application/x-sh`に正規化します。カスタムの[`supportedMimeTypes`](/docs/configuration/librechat_yaml/object_structure/file_config#supportedmimetypes-3)ルールでは、引き続き`application/x-sh`を許可する必要があります。

## 統合されたアップロードとツールプロビジョニング [#unified-uploads-and-tool-provisioning]

デフォルトでは、1つの添付ファイルアクションが古い宛先選択機能を置き換えます。LibreChatはファイルがどのようにモデルに到達するかを決定し、ツールは必要に応じて遅延的にプロビジョニングされます：

<Cards>
  <Card title="モデルコンテキスト" href="#what-happens-under-the-hood">
    サポートされているファイルは、MIMEタイプ、endpointの機能、およびデプロイ設定に応じて、ネイティブプロバイダーによる配信または抽出されたテキストを通じてモデルに到達します。
  </Card>
  <Card title="ファイル検索（RAG）用のアップロード" href="/docs/features/rag_api">
    File Searchが選択されている場合、LibreChatは実行時にツールが必要な場合にのみ、対象となる添付ファイルをインデックス化します。
  </Card>
  <Card title="標準アップロード" href="/docs/features/agents">
    Codeが選択されている場合、LibreChatは実行時に必要な場合にのみ、対象となる添付ファイルをCode環境で利用できるようにします。
  </Card>
</Cards>

オペレーターは、[`fileConfig.legacyFileUploadUX`](/docs/configuration/librechat_yaml/object_structure/file_config#legacyfileuploadux) を使用して以前の送信先選択機能を復元したり、[`defaultLLMDeliveryPath`](/docs/configuration/librechat_yaml/object_structure/file_config#defaultllmdeliverypath) を使用して自動ルーティングを制御したりできます。

**一般的なルーティング:**

| 状況 | 最適なオプション |
|-----------|-------------|
| _"この5ページの契約書を読んで要約して"_ | ネイティブPDF配信または抽出テキスト |
| _"50個のPDFがある。価格について言及している箇所を探して"_ | Lazy File Searchプロビジョニング |
| _"このスクリーンショットには何が写っている？"_ | ネイティブ画像配信 |
| _"このPythonスクリプトを実行して"_ | Lazy Codeプロビジョニング |
| _"このコードファイルにバグがないかレビューして"_ | 抽出テキスト |

## `context` 機能 [#the-context-capability]

内部的には、Upload as Textは**`context` capability**によって駆動されています。これが、チャットUIにこの機能を表示するかどうかを制御しています。

<Callout type="info">
  `context` 機能は **デフォルトで有効** になっています。管理者が機能リストをカスタマイズし、誤ってこの機能を除外してしまった場合にのみ、この設定を調整する必要があります。
</Callout>

```yaml title="librechat.yaml"
endpoints:
  agents:
    capabilities:
      - "context"  # This is what enables "Upload as Text"
```

同じ `context` 機能は、**Agent File Context**（Agent Builder を通じてファイルをアップロードし、エージェントのシステム指示にテキストを埋め込む機能）も支えています。違いは、そのテキストが最終的に _どこ_ に配置されるかという点です。

| | テキストとしてアップロード | エージェントのファイルコンテキスト |
|---|---|---|
| **場所** | チャット入力（任意の会話） | Agent Builder パネル |
| **スコープ** | 現在の会話のみ | エージェントの指示に永続的に保持 |
| **ユースケース** | ドキュメントに関する単発の質問 | 知識を組み込んだ専門エージェントの構築 |

## トークン制限と切り捨て (Truncation) [#token-limits-and-truncation]

ファイルが長すぎてモデルのコンテキストウィンドウに収まらない場合、LibreChatは抽出されたテキストを切り詰めて制限内に収めます。これは自動的に行われるため、ユーザーが気にする必要はありませんが、仕組みを理解しておくと役立ちます。

```yaml title="librechat.yaml"
fileConfig:
  fileTokenLimit: 100000  # Default: 100,000 tokens
```

<Callout type="warn" title="切り詰め（Truncation）はコンテンツの損失を意味します">
  ファイルが制限を超えると、テキストの末尾が切り捨てられます。回答が不完全になる場合は、これが原因である可能性があります。`fileTokenLimit` を増やすことは可能ですが、値を大きくするとメッセージあたりのトークン消費量が増加し、コストが増大するだけでなく、モデル自体のコンテキスト制限に達する可能性があることに留意してください。
</Callout>

**経験則:**
- 100kトークン ≈ 300ページの書籍1冊分（ほとんどのユースケースで十分な量）
- 非常に大きなファイルを扱う場合は、すべてをコンテキストに詰め込むのではなく、関連するセクションのみを取得する [File Search (RAG)](/docs/features/rag_api) の利用を検討してください。

## オプション: OCRによる抽出の強化 [#optional-boosting-extraction-with-ocr]

テキスト解析は、デジタル作成されたドキュメント（Wordから保存されたPDF、コードファイル、プレーンテキスト）では問題なく動作します。しかし、**スキャンされたドキュメント、ページの写真、またはテキストを含む画像**をアップロードする場合、組み込みのパーサーでは良好な結果が得られません。

そこでOCRの出番です。設定が完了すると、LibreChatはOCRの恩恵を受けるファイルタイプに対して自動的にOCRを使用します。ユーザー側で特別な操作を行う必要はありません。

<Accordions>
  <Accordion title="管理者にOCRの設定を依頼する方法">
    [OCR configuration docs](/docs/features/ocr) を参照するように伝えてください。要約は以下の通りです：

    ```yaml title="librechat.yaml"
    ocr:
      strategy: "mistral_ocr"
      apiKey: "${OCR_API_KEY}"
      baseURL: "https://api.mistral.ai/v1"
      mistralModel: "mistral-ocr-latest"
    ```

    設定が完了すると、OCRは画像やスキャンされたPDFを自動的に処理します。ユーザー側での操作は一切不要です。
  </Accordion>
  <Accordion title="管理者にSTT（音声ファイル用）の設定を依頼する方法">
    音声アップロードの文字起こしを行うには、管理者がSpeech-to-Textサービスを設定する必要があります。[STT設定リファレンス](/docs/configuration/librechat_yaml/object_structure/file_config#stt)を参照してください。
  </Accordion>
</Accordions>

## ファイル処理設定リファレンス [#file-handling-configuration-reference]

このセクションは、どのファイルタイプをどのメソッドで処理するかを制御したい管理者向けです。デフォルト設定で十分に機能するため、動作を微調整したい場合のみ変更してください。

<Accordions>
  <Accordion title="librechat.yaml設定の完全な例">
    ```yaml title="librechat.yaml"
    fileConfig:
      # Max tokens extracted from a single file before truncation
      fileTokenLimit: 100000

      # Files matching these MIME patterns use OCR (if configured)
      ocr:
        supportedMimeTypes:
          - "^image/(jpeg|gif|png|webp|heic|heif)$"
          - "^application/pdf$"
          - "^application/vnd\\.openxmlformats-officedocument\\.(wordprocessingml\\.document|presentationml\\.presentation|spreadsheetml\\.sheet)$"
          - "^application/vnd\\.ms-(word|powerpoint|excel)$"
          - "^application/epub\\+zip$"

      # Files matching these MIME patterns use text parsing
      text:
        supportedMimeTypes:
          - "^text/(plain|markdown|csv|json|xml|html|css|javascript|typescript|x-python|x-java|x-csharp|x-php|x-ruby|x-go|x-rust|x-kotlin|x-swift|x-scala|x-perl|x-lua|x-shell|x-sql|x-yaml|x-toml)$"

      # Files matching these MIME patterns use STT (if configured)
      stt:
        supportedMimeTypes:
          - "^audio/(mp3|mpeg|mpeg3|wav|wave|x-wav|ogg|vorbis|mp4|x-m4a|flac|x-flac|webm)$"
    ```

    **優先順位の注意:** OCR > STT > テキスト解析 > フォールバック。

    完全なリファレンスについては、[File Config Object Structure](/docs/configuration/librechat_yaml/object_structure/file_config) を参照してください。
  </Accordion>
</Accordions>

## トラブルシューティング [#troubleshooting]

<Accordions>
  <Accordion title="「テキストとしてアップロード」オプションが表示されない">
    `context` 機能が設定から削除された可能性があります。管理者に連絡して再度追加してもらってください。

    ```yaml
    endpoints:
      agents:
        capabilities:
          - "context"
    ```
  </Accordion>
  <Accordion title="ファイルの内容が正しくないか、ほとんど空です">
    確認すべき事項がいくつかあります：
    - **スキャンされたPDF / 画像** — これらを適切にテキスト抽出するにはOCRが必要です。OCRがない場合、パーサーはゴミデータや何も返さない可能性があります。管理者に[OCRの設定](/docs/features/ocr)を依頼してください。
    - **Audio files** — これらにはSTTが必要です。音声に対するテキストのフォールバックはありません。
    - **破損したファイル** — ファイルが破損していないことを確認するために、ローカルで開いてみてください。
    - **サポートされていない形式** — MIMEタイプが設定されたパターンと一致しない場合、LibreChatはテキスト解析によるフォールバックを試みますが、バイナリ形式では機能しない可能性があります。
  </Accordion>
  <Accordion title="サポートされていないファイル形式のため、アップロードが拒否されました">
    LibreChatは、アップロードエラー時に拒否されたMIMEタイプを返します。アクティブなendpointの[`fileConfig.endpoints.<endpoint>.supportedMimeTypes`](/docs/configuration/librechat_yaml/object_structure/file_config#supportedmimetypes-3)パターンを確認し、許可したい正規のタイプを許可してください。シェルスクリプトの場合は `application/x-sh` を使用してください。LibreChatは、一般的な `application/x-shellscript` および `text/x-shellscript` のバリエーションを照合前に正規化します。
  </Accordion>
  <Accordion title="AIがファイルの一部を読み込めていないようです">
    ファイルが `fileTokenLimit` を超えた可能性があります。テキストは切り詰められました。

    **オプション:**
    - `librechat.yaml` の `fileTokenLimit` を増やすよう管理者に依頼してください。
    - 代わりに [File Search (RAG)](/docs/features/rag_api) を使用してください。これはファイル全体を読み込むのではなく、関連するチャンクを取得します。
    - ファイルを小さなパーツに分割し、個別にアップロードしてください。
  </Accordion>
  <Accordion title="画像はアップロードされますが、AIがその中のテキストを読み取れません">
    OCRがない場合、画像はテキスト解析を通じて処理されますが、これでは画像内のテキストを実際に「見る」ことはできません。これを機能させるにはOCRの設定が必要です。[OCR for Documents](/docs/features/ocr) を参照してください。

    あるいは、標準のファイルアップロード機能を使用して**ビジョンモデル**を利用してください。モデル自体が画像内のテキストを読み取ることができます。
  </Accordion>
</Accordions>
