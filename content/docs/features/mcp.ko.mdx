Model Context Protocol (MCP)은 애플리케이션이 대규모 언어 모델(LLM)에 컨텍스트를 제공하는 방식을 표준화하는 개방형 프로토콜입니다. MCP를 **"AI의 USB-C"**라고 생각해보세요. USB-C가 전자 기기를 위한 범용 연결 표준을 제공하는 것처럼, MCP는 AI 모델을 다양한 도구, 데이터 소스 및 서비스에 연결하는 표준화된 방법을 제공합니다.

LibreChat은 MCP를 활용하여 AI 에이전트의 기능을 획기적으로 확장하며, 파일 시스템 액세스, 웹 브라우저, 특수 API부터 맞춤형 비즈니스 도구에 이르기까지 모든 것을 통합할 수 있도록 지원합니다.

## MCP가 중요한 이유 [#why-mcp-matters]

LLM은 내장된 기능에 제한이 있습니다. MCP를 통해 LibreChat은 다음과 같은 방식으로 이러한 장벽을 허뭅니다:

- **MCP 서버를 제공하는 모든 도구 또는 서비스에 연결**
- **통합 표준화**를 통해 각 도구마다 LibreChat의 코드를 수정할 필요가 없습니다.
- **다중 사용자 환경 지원** (적절한 인증 및 격리 기능 포함)
- **런타임에 서버 추가 및 업데이트** (설정 파일 편집이나 재시작 없이 MCP 설정 패널에서 수행)

## LibreChat에서 MCP가 작동하는 방식 [#how-mcp-works-in-librechat]

LibreChat은 채팅 영역 또는 에이전트와 함께 MCP 서버를 사용할 수 있는 두 가지 방법을 제공합니다.

`librechat.yaml` 파일에서 MCP 서버를 수동으로 구성하거나 [smithery.ai](https://smithery.ai)를 사용하여 MCP 서버를 찾아 `librechat.yaml`에 설치할 수 있습니다([아래 예시 참조](#basic-configuration)). `librechat.yaml`에 서버를 추가하거나 수정할 때마다 연결을 초기화하려면 LibreChat을 재시작해야 합니다. [MCP 설정 패널](#adding-mcp-servers-in-the-ui)을 통해 추가된 서버는 재시작 없이 즉시 적용됩니다. 패널에서 생성된 OAuth 사용 서버는 저장 시 등록되지만 처음에는 연결되지 않은 상태로 시작됩니다. [연결하려면 인증](#step-3-check-connection-status-and-authenticate)을 수행하십시오.

### OAuth 콜백 URL [#oauth-callback-url]

OAuth가 활성화된 MCP 서버의 경우, LibreChat 콜백 URL은 다음과 같습니다:

```text
${DOMAIN_SERVER}/api/mcp/<server-name>/oauth/callback
```

`<server-name>`는 `librechat.yaml`의 `mcpServers` 아래에 사용되는 키이거나 MCP 설정 UI에서 생성된 서버 이름입니다. 예를 들어, `DOMAIN_SERVER=https://chat.example.com`으로 설정된 `salesforce`라는 이름의 서버는 `https://chat.example.com/api/mcp/salesforce/oauth/callback`을 사용합니다.

OAuth 제공업체에 이 정확한 콜백 URL을 등록하세요. 로컬 Docker 설치는 일반적으로 `http://localhost:3080`을 기본 URL로 사용합니다.

### 채팅 영역에서 [#in-chat-area]

![컴포저 팔레트에서 열린 MCP Servers 카탈로그로, 각 서버의 연결 상태를 보여줍니다](/images/mcp/mcp_servers_catalog.png)

LibreChat은 전통적인 endpoint(OpenAI, Anthropic, Google, Bedrock 등)를 사용할 때 구성된 MCP 서버를 채팅 영역에 직접 표시합니다:

- 먼저 에이전트가 아닌 endpoint를 선택하고, 도구(tool)와 호환되는 모델을 선택하세요.
- MCP 서버는 [composer의 **+** 팔레트](/docs/features/composer#turn-on-tools-skills-and-mcp-servers)에 있는 **MCP Servers** 섹션에 나타나며, 선택된 각 서버는 composer에 칩 형태로 표시됩니다.
- 선택하면 해당 서버의 모든 도구를 현재 모델에서 사용할 수 있게 됩니다.
- 에이전트를 생성하지 않고도 MCP 도구에 빠르게 액세스하여 여러 서버를 동시에 사용할 수 있습니다.

MCP 서버를 일반 채팅 선택 항목에서 제외하려면, 설정에서 [`chatMenu: false`](/docs/configuration/librechat_yaml/object_structure/mcp_servers#chatmenu)로 지정하세요:

```yaml
mcpServers:
  internal-tools:
    command: npx
    args: ['-y', 'internal-mcp-server']
    chatMenu: false # Not selectable in regular chat
```

이 설정은 채팅 요청 및 선택기(picker) 모두에 적용되므로, 저장된 이전 선택 항목이 숨겨진 서버를 계속 사용할 수 없습니다. 이 설정은 저장된 Agent나 해당 서버를 명시적으로 할당하는 Model Specs에서 서버를 제거하지는 않습니다. 또한 LibreChat은 사용자가 승인된 Agent를 통해서만 접근할 수 있는 서버를 일반 채팅 선택기 및 요청 경로에서 생략합니다.

### 에이전트 사용 시 [#with-agents]

MCP 서버는 LibreChat 에이전트와 원활하게 통합됩니다:

1. 에이전트 생성 또는 편집
2. Agent Builder에서 **Add tools**를 열고 **MCP**를 선택하세요.
3. MCP 서버를 선택하세요; 각 서버는 단일 카탈로그 항목으로 표시됩니다.
4. 선택한 서버를 확장하여 개별 도구를 활성화하거나 비활성화하세요
5. 에이전트 저장

![MCP Tools in Agent Builder](/images/mcp/mcp_ui_agent.png)

이러한 상위 수준의 구성은 인터페이스를 관리하기 쉽게 유지합니다. 20개 이상의 도구(예: Spotify)를 가진 서버조차도 단일 항목으로 표시되며, 이를 확장하여 세부적인 제어를 수행할 수 있습니다.

### 기본 구성 [#basic-configuration]

`librechat.yaml` 파일에 MCP 서버를 수동으로 추가하세요:

```yaml
mcpServers:
  # ClickHouse Cloud
  clickhouse-cloud:
    type: streamable-http
    url: https://mcp.clickhouse.cloud/mcp

  # File system access
  filesystem:
    command: npx
    args:
      - -y
      - '@modelcontextprotocol/server-filesystem'
      - /path/to/your/documents

  # Web browser automation
  puppeteer:
    command: npx
    args:
      - -y
      - '@modelcontextprotocol/server-puppeteer'

  # Production-ready cloud service
  business-api:
    type: streamable-http
    url: https://api.yourbusiness.com/mcp
    headers:
      X-User-ID: '{{LIBRECHAT_USER_ID}}'
      Authorization: 'Bearer ${API_TOKEN}'
    timeout: 30000
    serverInstructions: true
```

### UI에서 MCP 서버 추가하기 [#adding-mcp-servers-in-the-ui]

구성 파일을 편집하거나 서버를 재시작할 필요 없이 LibreChat 인터페이스에서 직접 MCP 서버를 추가하고 구성할 수도 있습니다.

#### 1단계: MCP 설정 패널 열기 [#step-1-open-the-mcp-settings-panel]

오른쪽 사이드바에서 **MCP Settings** 패널로 이동하세요. 여기에 기존 MCP 서버 목록과 새로운 서버를 추가할 수 있는 **+** 버튼이 표시됩니다.

![MCP 설정 패널](/images/mcp/mcp_ui_settings_panel.png)

#### 2단계: 서버 세부 정보 입력 [#step-2-fill-out-server-details]

**+** 버튼을 누르고 MCP 서버 이름, 설명, URL, 전송 유형, 인증 방식을 입력한 다음 **Create**를 클릭하세요.

![Add MCP Server Dialog](/images/mcp/mcp_ui_configure.png)

새 서버가 MCP 설정 패널에 나타나며 확인 토스트 메시지가 표시됩니다.

![MCP Server Created Successfully](/images/mcp/mcp_ui_success_registered.png)

#### 3단계: 연결 상태 확인 및 인증 [#step-3-check-connection-status-and-authenticate]

새 서버의 [연결 상태 표시기](#connection-status-indicators)를 확인하세요. 서버에 OAuth 인증이 필요한 경우, 상태가 연결 끊김으로 표시됩니다. 컴포저의 **+** 팔레트에서 MCP 서버를 선택하여 인증 절차를 시작하세요.

![연결 상태 - 연결 끊김](/images/mcp/mcp_ui_unconnected.png)

시작되면 상태 표시기가 업데이트되어 인증이 진행 중임을 나타냅니다.

![Connection Status - Authenticating](/images/mcp/mcp_ui_authenticating.png)

#### 4단계: OAuth로 계속하기 [#step-4-continue-with-oauth]

LibreChat은 **Connect** 확인 프롬프트를 표시합니다. 대상을 검토하고 **Continue with OAuth**를 선택하여 새 브라우저 탭에서 공급자의 인증 페이지를 엽니다. 해당 페이지에서 공급자의 로그인 및 동의 절차를 완료하십시오.

이 브라우저에서 시작된 흐름(flow)이 보류 중인 경우, 캐시된 연결 상태가 **Connected**라고 표시되더라도 LibreChat은 해당 서버를 인증/연결 중 상태로 유지합니다. 이전 상태가 지속적인 인증을 보고한다는 이유만으로 프롬프트가 닫혀서는 안 되며, 터미널의 성공, 실패, 시간 초과 또는 취소 시에만 보류 중인 흐름이 종료됩니다. 다른 탭이나 브라우저에서 시작된 흐름은 이 보기에서 로컬 보류 상태를 가지지 않습니다.

![OAuth Continue Prompt](/images/mcp/mcp_ui_callback_confirm.png)

#### 5단계: 인증 성공 [#step-5-authentication-successful]

인증이 완료되면 성공 확인 메시지가 표시됩니다. 이 창은 자동으로 닫히며 LibreChat으로 다시 리디렉션됩니다.

![Authentication Successful](/images/mcp/mcp_ui_success_redirect.png)

#### 6단계: 서버 사용 준비 완료 [#step-6-server-ready-for-use]

LibreChat은 성공적인 인증을 확인하고 대화 내에서 사용할 MCP 서버를 자동으로 선택합니다. 이제 서버에 연결됨 상태 표시기가 나타나며, 작성기(composer)에 선택된 칩으로 표시됩니다.

![MCP Server Authenticated and Auto-Selected](/images/mcp/mcp_ui_done.png)

새로운 MCP 서버는 Agent Builder에서도 사용할 수 있으며, 여기서 해당 도구를 모든 에이전트에 추가하고 허용할 도구의 하위 집합을 사용자 지정할 수 있습니다.

![MCP Server Available in Agent Builder](/images/mcp/mcp_ui_agent.png)

#### UI에서 생성된 서버를 위한 자격 증명 변수 [#credential-variables-for-ui-created-servers]

UI를 통해 MCP 서버를 추가할 때, 사용자가 자신의 API 키를 제공하도록 요구할 수 있습니다. MCP Server Builder 대화 상자의 Authentication 섹션에서 "API Key"를 선택하고 **"User provides key"**를 체크하세요. 헤더 형식(Bearer, Basic 또는 Custom)을 선택한 다음 서버를 저장합니다.

Behind the scenes, LibreChat creates a destination-bound `customUserVars` entry named `MCP_API_KEY_<hash>` and configures the matching authentication header. The name is managed automatically; users still enter their key in the MCP Tool Select Dialog or MCP Settings panel. Existing servers may retain the legacy `MCP_API_KEY` name while their request boundary is unchanged. This uses the same key-entry UI as [YAML-defined `customUserVars`](#user-provided-credentials).

UI에서 생성된 서버의 URL(경로 또는 쿼리 포함), 프록시, 전송(transport), 인증 형식, 사용자 지정 인증 헤더 또는 구성된 OAuth 클라이언트/대상 변경 시, 각 사용자는 새로운 경계에 대한 키를 입력해야 합니다. 이전에 저장된 키는 교체된 대상으로 전달되지 않습니다. 외관상의 수정, 동일한 정규화된 URL, 그리고 프래그먼트만 변경되는 아웃바운드 URL 수정은 기존 키를 유지합니다. 공유 서버는 현재 구성에 선언된 자격 증명 변수만 확인할 수 있으므로, 편집자가 이전 키를 복구하기 위해 이전에 생성된 이름을 참조할 수는 없습니다. 별도의 대량 자격 증명 마이그레이션은 필요하지 않습니다. 이 보호 기능을 사용하기 전에 서버 편집 요청을 처리하는 복제본을 포함하여 **모든 API 복제본**을 업그레이드하십시오. 이전 버전의 작성자는 여전히 바인딩되지 않은 구성을 다시 생성할 수 있습니다.

관리자 또는 사용자 API 키가 구성되면, LibreChat은 서버를 API 키 인증 방식으로 처리하며 OAuth 자동 감지를 건너뜁니다. 명시적인 OAuth 구성이 여전히 우선순위를 갖습니다. 이전 LibreChat 버전에서 생성된 UI 기반 API 키 서버가 **OAuth Required** 상태에서 멈춰 있다면, 해당 서버를 편집하고 저장하여 저장된 연결 메타데이터를 새로 고침하세요.

<Callout type="warning">
보안을 위해 UI에서 생성된(DB 기반) MCP 서버는 `customUserVars` 플레이스홀더(`{{VAR_NAME}}`)만 해결할 수 **있습니다**. 서버 측 환경 변수(`${ENV_VAR}`), 사용자 프로필 필드(`{{LIBRECHAT_USER_*}}`) 및 OIDC 토큰(`{{LIBRECHAT_OPENID_*}}`)은 서버 비밀 정보나 다른 사용자의 데이터에 대한 무단 액세스를 방지하기 위해 의도적으로 차단되었습니다. 모든 플레이스홀더를 지원하려면 대신 `librechat.yaml`에서 서버를 구성하십시오.
</Callout>

### Smithery를 사용하여 MCP 서버 추가하기 [#adding-mcp-servers-with-smithery]

Smithery.ai는 LibreChat을 위한 MCP 서버를 검색하고 설치하는 간소화된 방법을 제공합니다. 시작하려면 다음 단계를 따르세요:

#### 1단계: MCP 서버 검색 [#step-1-search-for-mcp-servers]

[smithery.ai](https://smithery.ai)를 방문하여 LibreChat 인스턴스에 추가하려는 MCP 서버를 검색하세요.

검색 결과에서 MCP 서버를 클릭하여 세부 정보와 사용 가능한 도구를 확인하세요.

![MCP Server Details Page](/images/mcp/mcp_smithery_mcp_server.png)

#### 3단계: LibreChat 설정하기 [#step-3-configure-for-librechat]

**Connect** 섹션의 **Auto** 탭으로 이동하여 원하는 클라이언트로 **LibreChat**을 선택하세요.

![LibreChat 통합 설정](/images/mcp/mcp_smithery_librechat.png)

#### 4단계: MCP Server 설치 [#step-4-install-the-mcp-server]

생성된 명령어를 복사하여 터미널에서 실행하면 MCP 서버가 설치됩니다.

![Installation Command](/images/mcp/mcp_smithery_copy.png)

#### 5단계: 재시작 및 확인 [#step-5-restart-and-verify]

이제 MCP 서버가 설치되었으며 `librechat.yaml`에서 구성할 수 있습니다. LibreChat을 재시작하여 연결을 초기화하고 새로운 MCP 서버를 사용해 보세요.

## MCP Server Management [#mcp-server-management]

LibreChat은 UI에서 연결 상태 추적과 OAuth 인증 및 초기화 지원을 통해 MCP 서버 연결을 관리하기 위한 포괄적인 도구를 제공합니다.

### 연결 상태 표시기 [#connection-status-indicators]

LibreChat은 컴포저의 **+** 팔레트와 설정 패널에서 각 MCP 서버의 현재 상태를 보여주는 동적 상태 아이콘을 표시합니다:

![MCP Server Status Icons](/images/mcp/mcp_server_status_icons.png)

**상태 유형:**

- **연결됨** (녹색 톱니바퀴): 서버가 연결되었으며 구성 가능한 customUserVars를 가지고 있습니다.
- **OAuth Required** (amber key): 서버에 OAuth 인증이 필요합니다
- **연결 끊김** (주황색 플러그): 서버 연결에 실패했거나 연결이 끊어졌습니다.
- **Initializing** (파란색 로더): 서버가 시작 중이거나 재연결 중입니다.
- **오류** (빨간색 삼각형): 서버에서 오류가 발생했습니다
- **취소 중** (빨간색 x): OAuth 흐름이 취소되고 있습니다

### 에이전트 도구 대화 상자에서 OAuth 취소하기 [#cancelling-oauth-from-the-agent-tool-dialog]

**Agent Builder → Tool Library → MCP server configuration**에서, 공유 서버 관리자가 취소 가능한 OAuth 흐름을 보고하면 **Connect**는 활성화된 **Cancel** 작업으로 변경됩니다. 여기에는 다른 LibreChat 패널에서 발견된 보류 중인 흐름이 포함됩니다. **Cancel**을 선택하여 해당 흐름을 중지하고, 로컬 OAuth 프롬프트를 닫으며, 보류 중인 도구 자동 선택을 지우십시오. 취소 후 뒤늦게 연결 결과가 도착하더라도 이 대화 상자에서 도구가 자동으로 연결되지는 않습니다. 새로운 시도를 위해 **Connect**를 다시 선택할 수 있습니다. 취소할 수 없는 초기화 작업은 취소 작업 대신 비활성화된 '사용 중(busy)' 상태를 계속 표시합니다.

### 서버 초기화 [#server-initialization]

인터페이스에서 직접 MCP 서버를 초기화하거나 재초기화할 수 있습니다:

**원클릭:**

- 컴포저의 **+** 팔레트 내 **MCP Servers** 섹션에서 서버를 선택하여 원클릭으로 초기화할 수 있습니다.

  <Video src="/videos/mcp_one_click_init.mp4" title="원클릭 MCP 초기화" />

**MCPConfigDialog에서:**

- 컴포저의 **+** 팔레트에 있는 MCP 서버 행에서 **Configure**를 선택하여 MCPConfigDialog를 엽니다.
- 사용자 지정 변수를 구성하고 서버 인증 유형에 따라 Authenticate/Initialize 버튼을 클릭하세요.

       <Video src="/videos/mcp_config_dialog_auth.mp4" title="MCP 설정 대화 상자 인증" />

  **MCP 설정 패널에서:**

- MCP 설정 패널의 서버 목록 섹션에서 서버를 클릭하여 구성 및 초기화 제어에 액세스하세요.
- 사용자 지정 변수를 구성하고 서버 인증 유형에 따라 Authenticate/Initialize 버튼을 클릭하세요.

  <Video src="/videos/mcp_settings_init.mp4" title="MCP 설정 패널 초기화" />

이제 초기화 실패 시 연결할 수 없는 서버, 누락된 `customUserVars`, 다시 인증해야 하는 OAuth 연결, 그리고 일반적인 초기화 실패를 구분합니다. 재시도하기 전에 메시지에 명시된 누락된 변수나 재인증 작업을 수행하십시오. 이러한 경우 더 이상 서버를 제거했다가 다시 추가할 필요가 없습니다.

수동 카탈로그 로드는 OAuth 검색 시도를 통합하고 실패 후 점진적으로 재시도 간격을 늘리므로(back off), 연결이 끊긴 통합이 모든 요청마다 검색을 재시도하지 않습니다. 자격 증명 변경은 복제본 간에 세대별로 격리(generation-fenced)되어, 이전 검색 결과가 최신 인증을 덮어쓰는 것을 방지합니다. 운영자는 [`mcpSettings.catalogRecovery`](/docs/configuration/librechat_yaml/object_structure/mcp_settings#catalogrecovery)에서 제한된 복구 정책을 조정할 수 있으며, 기본값은 대부분의 배포 환경에 적합합니다.

에이전트가 MCP 도구를 명시적으로 요구하지만 실행 시작 시 해결할 수 있는 도구가 없는 경우, LibreChat은 해당 도구 없이 조용히 실행하는 대신 연결 및 액세스 지침과 함께 실행을 실패 처리합니다.

`notifications/tools/list_changed`를 내보내는 MCP 서버는 LibreChat을 재시작하지 않고도 도구 카탈로그를 업데이트할 수 있습니다. LibreChat은 라이브 연결에서 현재 목록을 가져와 추가된 도구를 게시하고, 서버에서 제거된 도구는 더 이상 광고하지 않습니다. 재연결 시에도 연결이 준비된 것으로 간주되기 전에 카탈로그를 동기화합니다. 관리형 스냅샷 새로 고침과 콜드 서버 검색은 프로세스 전체에서 세 가지 작업으로 구성된 게이트를 공유합니다. 일단 승인되면 각 작업은 더 짧은 `initTimeout`을 포함하여 도구 목록 또는 서버별 검색 제한 시간 내에 제한되므로, 느린 카탈로그 작업이 슬롯을 무기한 점유할 수 없습니다.

Streamable HTTP 서버의 경우, 서버가 이전 세션에 대한 오래된(stale) 독립형 SSE 스트림을 여전히 유지하고 있을 때 재연결 시 잠시 HTTP `409`를 반환할 수 있습니다. LibreChat은 이를 일시적인 현상으로 간주하여 오래된 세션을 종료하고 연결을 자동으로 재구축합니다. 복구가 성공하면 운영자의 별도 조치는 필요하지 않습니다. 재구축된 연결조차 실패할 경우, LibreChat은 계속해서 근본적인 연결 오류를 노출합니다.

LibreChat은 부분 문자열 일치 방식이 아닌, 파싱된 `Content-Type` 미디어 타입을 기반으로 Streamable HTTP 응답을 분류합니다. 매개변수를 사용하여 SSE가 아닌 응답을 `text/event-stream`처럼 보이게 할 수는 없으므로, 응답 크기 오류는 올바른 SSE 또는 비 SSE 처리 경로를 통해 계속 진행됩니다.

### MCP 설정 패널 표시 여부 [#mcp-settings-panel-visibility]

LibreChat이 초기화 과정에서 사용자 개입이 필요할 수 있는 MCP 서버를 감지하면 오른쪽 사이드바에 MCP 설정 패널이 나타납니다. 구성된 서버가 다음 기준 중 하나를 충족하면 해당 패널이 표시됩니다:

- **사용자 지정 변수(Custom User Variables)**: 서버에 `customUserVars`가 정의되어 있으며, 여기에는 사용자가 제공한 자격 증명이 포함될 수 있습니다.
- **OAuth Authentication**: 서버가 시작되는 동안 OAuth 인증이 필요한 것으로 감지되었습니다.
- **수동 초기화**: 서버가 `startup: false`로 설정되어 있어 수동 초기화가 필요합니다.

## LibreChat 전용 기능 [#librechat-specific-features]

LibreChat의 MCP 구현은 고도로 구성 가능하며, 실제 환경의 다중 사용자 환경을 위해 설계되었습니다.

### 사용자별 연결 (User-Specific Connections) [#user-specific-connections]

- 각 사용자는 MCP 서버에 대한 자신만의 격리된 연결을 갖습니다.
- 사용자 인증 및 권한이 준수됩니다
- 개인 데이터와 컨텍스트는 비공개로 유지됩니다

### MCP 서버 공유하기 [#sharing-mcp-servers]

MCP 서버는 LibreChat의 [세분화된 액세스 제어](/docs/features/access_control) 시스템에 참여합니다. `librechat.yaml`에 정의된 서버(관리자가 관리하며 [`interface.mcpServers`](/docs/configuration/librechat_yaml/object_structure/interface#mcpservers) 기능 권한의 적용을 받음) 외에도, 사용자가 생성한 MCP 서버는 자체적인 ACL을 가지며 특정 **사용자**, **그룹**, **역할** 또는 **공개**로 공유할 수 있고, 뷰어(Viewer), 편집자(Editor) 또는 소유자(Owner) 수준으로 설정할 수 있습니다.

`interface.mcpServers` 하위의 `USE`, `CREATE`, `SHARE`, `SHARE_PUBLIC` 기능 플래그는 MCP 서버를 생성하고 공유할 수 있는 권한을 제어합니다. 권한 계층이 어떻게 구성되는지에 대한 자세한 내용은 [Access Control](/docs/features/access_control)을 참조하세요.

### 동적 사용자 컨텍스트 [#dynamic-user-context]

MCP 서버는 **URL 및 헤더**의 플레이스홀더를 통해 사용자 정보에 액세스할 수 있습니다(SSE 및 Streamable HTTP 전송의 경우):

```yaml
mcpServers:
  user-api:
    type: streamable-http
    url: https://api.example.com/users/{{LIBRECHAT_USER_USERNAME}}/mcp
    headers:
      X-User-ID: '{{LIBRECHAT_USER_ID}}'
      X-User-Email: '{{LIBRECHAT_USER_EMAIL}}'
      X-User-Role: '{{LIBRECHAT_USER_ROLE}}'
      Authorization: 'Bearer ${API_TOKEN}'
```

사용 가능한 플레이스홀더는 다음과 같습니다:

- `{{LIBRECHAT_USER_ID}}` - 고유 사용자 식별자
- `{{LIBRECHAT_USER_EMAIL}}` - 사용자의 이메일 주소
- `{{LIBRECHAT_USER_ROLE}}` - 사용자 역할 (admin, user 등)
- `{{LIBRECHAT_USER_USERNAME}}` - 사용자 이름
- 그리고 더 많은 항목 (전체 목록은 [MCP Servers Configuration](/docs/configuration/librechat_yaml/object_structure/mcp_servers#headers) 참조)

YAML로 정의된 MCP 서버는 `{{LIBRECHAT_OPENID_*}}`, `{{LIBRECHAT_GRAPH_*}}`, 그리고 `{{LIBRECHAT_BODY_*}}` 플레이스홀더를 사용할 수도 있습니다. `{{LIBRECHAT_BODY_*}}` 값은 요청 범위(request-scoped)로 지정되므로, LibreChat은 활성 실행(active run)을 위한 연결을 생성하고, 해당 실행 내의 도구 호출 전반에서 이를 재사용하며, 요청이 종료될 때 연결을 정리합니다. 요청 범위 서버는 영구 도구 캐시에서 제외되므로, 요청별 헤더와 URL이 활성 실행 외부에서 재사용되지 않습니다. 채팅 요청이 존재하기 전에는 도구 목록을 확인할 수 없기 때문에, Agent Builder는 전체 서버에 대해 하나의 런타임 도구 선택을 노출하고 실행 시점에 도구를 확인합니다. OAuth를 완료하면 인증 정보는 저장되지만, 첫 번째 실행에서 요청 컨텍스트가 제공될 때까지 연결은 지연됩니다. 사용자(User), OpenID, Graph 플레이스홀더는 사용자 범위(user-scoped)로 지정되며, HTTP 전송은 연결을 직접 다시 맺을 필요 없이 각 도구 호출 전에 확인된 헤더를 새로 고칩니다.

신뢰할 수 있는 운영자는 YAML로 정의된 원격 서버에서 `Authorization: 'Bearer {{LIBRECHAT_OPENID_ACCESS_TOKEN}}'`을 사용하여 사용자의 실시간 OpenID 액세스 토큰을 전달할 수 있습니다. 명시적 MCP OAuth, 대리 교환(on-behalf-of exchange) 및 관리자 API 키 인증이 우선합니다. `401` 또는 `403` 오류 발생 후, LibreChat은 연결을 한 번 새로 고칠 수 있지만 거부된 도구 호출을 자동으로 재시도하지는 않습니다. 설정 및 보안 지침은 [MCP 서버 플레이스홀더 참조](/docs/configuration/librechat_yaml/object_structure/mcp_servers#headers)를 확인하세요.

`{{LIBRECHAT_GRAPH_ACCESS_TOKEN}}`은 Microsoft on-behalf-of 흐름을 통해 사용자의 재사용 가능한 OpenID 액세스 토큰을 교환합니다. [`GRAPH_API_SCOPES`](/docs/configuration/dotenv#microsoft-graph-api--entra-id-integration)는 요청할 공백으로 구분된 범위를 설정하며, 기본값은 `https://graph.microsoft.com/.default`입니다. 이는 사람 및 그룹 검색을 구성하는 `OPENID_GRAPH_SCOPES`와는 독립적입니다.

`{{LIBRECHAT_BODY_PARENTMESSAGEID}}` 플레이스홀더는 네이티브 Agent 채팅, OpenAI 호환 Agents API 호출, 그리고 레거시 Assistants 실행을 위해 채워집니다. Open Responses에는 이에 상응하는 상위 메시지 식별자가 없으며, MCP 서버가 해당 값을 요구할 경우 실패(fails closed) 처리됩니다. [MCP 서버 플레이스홀더 참조](/docs/configuration/librechat_yaml/object_structure/mcp_servers#headers)를 확인하세요.

### Server Instructions [#server-instructions]

`serverInstructions`는 MCP 서버의 도구가 선택될 때 구성된 지침을 동적으로 추가하는 LibreChat 기능입니다:

```yaml
mcpServers:
  filesystem:
    command: npx
    args: ['-y', '@modelcontextprotocol/server-filesystem', '/docs']
    serverInstructions: |
      When accessing files:
      - Always check file permissions first
      - Use absolute paths for reliability
      - Handle errors gracefully
```

옵션:

- `true`: 서버에서 제공하는 지침이 있을 경우 해당 지침을 사용합니다.
- `false`: 지침 비활성화
- `string`: 사용자 지정 지침을 그대로(위에 표시된 대로) 사용합니다.

LibreChat은 서버를 검사하는 동안 가져온 지침과 별도로 이 구성된 선언을 보존합니다. 따라서 `true` 선언은 검사 및 캐시된 레지스트리 재로드 전반에 걸쳐 활성화된 상태로 유지되며, 사용자 지정 문자열은 권한 있는 상태로 유지됩니다.

### 시간 초과(Timeout) 설정 [#timeout-configuration]

장시간 실행되는 MCP 작업의 경우, 초기화 및 도구 작업 모두에 적절한 타임아웃을 구성하십시오.

```yaml
mcpServers:
  data-processor:
    type: streamable-http
    url: https://api.example.com/mcp
    initTimeout: 15000 # 15 seconds for server initialization
    timeout: 60000 # 60 seconds for tool operations
```

**참고**: 작업이 계속 중단되는 경우, 기본 시간 초과 설정으로 인해 연결을 조기에 끊을 수 있는 프록시 구성(예: nginx, traefik 등)을 확인하십시오.

사용자가 포그라운드 Agent 도구 호출 중에 **Stop**을 누르면, LibreChat은 실행 취소 신호를 MCP로 전달합니다. Streamable HTTP 서버의 경우, MCP SDK는 `notifications/cancelled`를 전송하며, 서버는 자체 작업을 중단하기 위해 해당 알림을 준수해야 합니다. 분리된(Detached) 백그라운드 호출은 의도적으로 별도의 수명 주기를 유지하며 포그라운드 턴과 함께 취소되지 않습니다.

### 사용자 제공 자격 증명 [#user-provided-credentials]

`customUserVars`를 통해 사용자가 MCP 서버에 대한 자신의 자격 증명을 직접 제공하도록 허용할 수 있습니다. 이를 통해 구성 파일에 자격 증명을 저장하지 않고도 안전한 사용자별 인증이 가능합니다.

```yaml
mcpServers:
  my-api-server:
    type: streamable-http
    url: 'https://api.example.com/mcp'
    headers:
      X-Auth-Token: '{{MY_API_KEY}}' # Uses the user-provided value
    customUserVars:
      MY_API_KEY:
        title: 'API Key'
        description: "Enter your personal API key from <a href='https://example.com/keys' target='_blank'>your account settings</a>"
```

사용자는 다음 자격 증명을 구성할 수 있습니다:

- **채팅 영역에서**: 컴포저의 **+** 팔레트에 있는 구성 가능한 MCP 서버 행에서 **Configure**를 선택하세요.
- **MCP 설정 패널에서**: 오른쪽 패널의 "MCP Settings"에 액세스하여 구성된 모든 서버의 자격 증명을 관리하세요.

#### 사용자 자격 증명으로 MCP 서버 재초기화하기 [#reinitializing-mcp-servers-with-user-credentials]

사용하기 전에 사용자별 자격 증명이 필요한 MCP 서버(예: [GitHub 공식 MCP 서버](https://github.com/github/github-mcp-server)의 `PAT_TOKEN`)의 경우, LibreChat을 사용하면 사용자가 이러한 자격 증명을 제공하고 전체 애플리케이션을 재시작하지 않고도 UI 내에서 MCP 서버를 다시 초기화할 수 있습니다:

1. `customUserVars`를 사용하는 MCP를 선택하면, MCP 패널 내에서 선택한 MCP 서버에 대한 `customUserVar` 값을 **저장(Save)**하거나 **취소(Revoke)**할 수 있습니다.
2. `customUserVar`에 대한 값을 저장한 후, 재초기화(reinitialize) 버튼(MCP 패널의 각 서버 이름 옆에 있는 원형 화살표 아이콘)을 클릭하세요.
3. LibreChat은 제공하신 자격 증명을 사용하여 서버 연결을 시도하며, 재초기화 프로세스의 성공 또는 실패 여부를 토스트 메시지로 알려드립니다.

> _팁: 서버가 최초 시작 시 사용할 수 없는 자격 증명을 요구할 것임을 알고 있다면, 해당 구성에 `startup: false`를 추가할 수 있습니다. 이는 LibreChat이 UI에서 수동으로 다시 초기화될 때까지 해당 서버에 연결을 시도하지 않도록 지시합니다._

**예시:**

```yaml
mcpServers:
  github-mcp:
    type: streamable-http
    url: 'https://api.githubcopilot.com/mcp/'
    headers:
      Authorization: '{{PAT_TOKEN}}'
    customUserVars:
      PAT_TOKEN:
        title: 'GitHub PAT Token'
        description: 'GitHub Personal Access Token'
    startup: false
```

### OAuth 인증 [#oauth-authentication]

LibreChat은 Anthropic의 안전한 MCP 연결 권장 사항에 따라 MCP 서버에 대한 OAuth 인증을 지원합니다. OAuth는 장기 자격 증명을 저장하지 않고도 인증할 수 있는 표준화되고 안전한 방법을 제공합니다.

#### 지원되는 OAuth 흐름 [#supported-oauth-flows]

LibreChat MCP 서버는 다음을 통해 OAuth 2.0을 지원합니다:

- **PKCE를 사용한 인증 코드 흐름(Authorization Code Flow with PKCE)**: 최대 보안을 위해 권장됨
- **Client Discovery**: OAuth 제공업체에서 지원하는 경우 자동 클라이언트 등록
- **Refresh Tokens**: 사용 가능한 경우 자동 토큰 갱신
- **토큰 엔드포인트 검색(Token endpoint discovery)**: 미리 구성된 클라이언트는 공급자가 POST 본문에 클라이언트 자격 증명을 기대하는지, 아니면 HTTP Basic 인증 헤더를 기대하는지 검색할 수 있습니다.

MCP Builder에서 **Token Exchange Method**는 **Auto**, **Default (POST request)**, 그리고 **Basic authorization header**를 제공합니다. **Auto**는 메서드를 설정하지 않은 상태로 두어 LibreChat이 신뢰할 수 있는 제공자 메타데이터를 사용할 수 있게 하며, 제공자가 메서드를 알리지 않을 경우 Basic 인증으로 대체합니다.

#### 구성 예시 [#configuration-examples]

```yaml
mcpServers:
  # Public remote MCP server for PayPal, uses OAuth Client Discovery
  # ❌ Refresh Tokens: you may need to re-authenticate periodically
  # More info: https://developer.paypal.com/tools/mcp-server/
  paypal:
    type: 'sse'
    initTimeout: 150000 # higher timeout to allow for initial authentication
    url: 'https://mcp.paypal.com/sse'

  # Example self-hosted remote MCP server for Spotify, uses OAuth Client Discovery
  # ✅ Refresh Tokens: refreshes token for authentication automatically
  # Hosted on Cloudflare Workers, more info: https://github.com/LibreChat-AI/spotify-mcp
  spotify:
    type: 'streamable-http'
    initTimeout: 150000
    url: 'https://mcp-spotify-oauth-example.account.workers.dev/mcp'
```

#### OAuth 인증 흐름 [#oauth-authentication-flow]

OAuth가 활성화된 MCP 서버를 처음 구성할 때:

1. **초기 연결**: LibreChat이 MCP 서버에 연결을 시도합니다.
2. **인증 필요**: 유효한 토큰이 없는 경우, 컴포저의 **+** 팔레트에서 해당 서버에 대한 OAuth 인증 상태를 확인할 수 있습니다.
3. **로그인 시작**: OAuth 흐름을 시작할 서버를 선택하세요
4. **계속하거나 다른 기기 사용**: 현재 브라우저에서 계속하거나, 인증 링크를 복사하거나, QR 코드를 표시하여 다른 기기에서 엽니다.
5. **브라우저 리디렉션**: OAuth 제공업체를 통한 인증 완료
6. **Return Handling**: LibreChat은 인증이 완료되면 OAuth 콜백을 자동으로 처리합니다.
7. **토큰 저장**: LibreChat은 향후 사용을 위해 토큰을 안전하게 저장합니다.
8. **연결 완료**: 인증이 완료되면 MCP 서버가 연결되며, 채팅에서 이를 사용할 수 있습니다.

#### OAuth 콜백 URL [#oauth-callback-url-1]

MCP 서버가 OAuth를 사용할 때, LibreChat은 OAuth 제공자가 성공적인 인증 후 리디렉션하는 콜백 endpoint를 노출합니다.

콜백 URL은 다음 형식을 따라야 합니다:

`${baseUrl}/api/mcp/${serverName}/oauth/callback`

여기서 `${serverName}`은 `librechat.yaml` 구성에 정의된 MCP 서버 키입니다. LibreChat은 이 endpoint에서 리디렉션을 처리하고, 토큰 교환을 완료하며, 자격 증명을 해당 MCP 서버와 연결합니다.

<Callout type="info" title="OAuth 콜백 URL 예시">
다음 MCP 서버 구성을 고려할 때:

```yaml
mcpServers:
  # Example self-hosted remote MCP server for Spotify, uses OAuth Client Discovery
  # ✅ Refresh Tokens: refreshes token for authentication automatically
  # Hosted on Cloudflare Workers, more info: https://github.com/LibreChat-AI/spotify-mcp
  spotify:
    type: 'streamable-http'
    initTimeout: 150000
    url: 'https://mcp-spotify-oauth-example.account.workers.dev/mcp'
```

콜백 URL은 `${baseUrl}/api/mcp/spotify/oauth/callback`이 됩니다.

</Callout>

참고:

- OAuth 흐름이 작동하려면 콜백 URL을 OAuth 제공업체에 정확하게 등록해야 합니다.
- `/api/oauth/callback` 또는 `/api/oauth/openid/callback`과 같은 다른 경로는 MCP OAuth 흐름에 유효하지 않습니다.

#### 토큰 관리 [#token-management]

LibreChat은 OAuth 토큰을 지능적으로 처리합니다:

- **보안 저장소**: 토큰은 암호화되어 안전하게 저장됩니다
- **자동 새로 고침**: 새로 고침 토큰(refresh tokens)을 사용할 수 있는 경우, LibreChat은 만료된 액세스 토큰을 자동으로 갱신합니다.
- **Silent 401 Recovery**: OAuth MCP 연결이 세션 도중 인증 거부를 수신하면, LibreChat은 사용자 및 서버당 1회에 한해 제한된 새로 고침 및 재연결 시도를 조정합니다. LibreChat이 새로운 인증 프롬프트를 표시하기 전에 동시 호출자들은 해당 복구 결과를 공유합니다.
- **세션 관리**: 각 사용자는 다중 사용자 환경을 위해 자체 OAuth 세션을 유지합니다.

저장된 Agent 스트림이 MCP 승인 프롬프트가 대기 중인 상태에서 다시 로드되거나 재개되면, LibreChat은 지속적인 생성 상태로부터 해당 프롬프트를 재구성합니다. 완료, 취소, 실패 또는 만료된 프롬프트는 복원되지 않습니다.

저장된 OAuth 클라이언트와 토큰은 MCP 서버 URL 및 OAuth 클라이언트/endpoint 설정에 바인딩됩니다. 해당 설정을 변경하면 사용자는 다시 인증해야 합니다. 저장된 `client_secret`을 유지하는 UI 생성 서버를 편집할 때는 서버 URL, 클라이언트 ID, 권한 부여 URL, 토큰 URL 또는 토큰 인증 방식과 같은 바인딩 필드를 변경할 때 비밀 값을 다시 입력하십시오.

수평적으로 확장된 배포 환경에서, OAuth 흐름 상태와 바인딩된 토큰의 준비 상태는 LibreChat 파드(pod) 간에 조정될 수 있습니다. UI는 콜백과 상태 폴링이 서로 다른 파드에 도달하더라도, OAuth 이후 초기화가 성공한 후에만 서버가 준비된 것으로 보고합니다. 대체된 시도에서 발생한 콜백은 거부됩니다.

Redis가 활성화되면, 애플리케이션 수준의 MCP 카탈로그 생성 및 게시 수정 사항이 복제본 간에 조정됩니다. Redis Cluster 배포는 슬롯 안전(slot-safe) 카탈로그 키와 업데이트를 사용하므로, 시작 동기화 및 `tools/list_changed` 새로 고침 시 단일 노드 Redis 레이아웃이 필요하지 않습니다.

각 사용자는 OAuth가 활성화된 MCP 서버를 처음 사용할 때 자신의 OAuth 로그인으로 인증하라는 메시지를 받게 됩니다. 이는 연결 및 인증 세부 정보가 각 사용자마다 고유하게 유지되도록 보장하며, 다중 사용자 환경에서 보안과 개인정보 보호를 유지합니다.

#### OAuth 타이밍 [#oauth-timing]

MCP OAuth 완료는 MCP 서버 `initTimeout`을 재사용하는 대신 자체적으로 구성된 서버 타임아웃을 사용합니다. 기본적으로 LibreChat은 사용자가 MCP OAuth를 완료할 때까지 최대 10분 동안 대기하며, 흐름 상태를 15분 동안 유지합니다.

OAuth 제공업체나 사용자 워크플로우에 더 많은 시간이 필요할 때 다음 환경 변수를 사용하세요:

```bash filename=".env"
MCP_OAUTH_HANDLING_TIMEOUT=600000
MCP_OAUTH_FLOW_TTL=900000
```

`MCP_OAUTH_FLOW_TTL`은 `MCP_OAUTH_HANDLING_TIMEOUT`보다 길게 유지되도록 제한되므로, 마감 시간에 가까운 콜백도 여전히 자신의 흐름 상태를 찾을 수 있습니다. MCP 서버 카드 폴링 창은 구성된 처리 시간 제한을 따릅니다.

![사용자별 OAuth 인증 흐름](/images/agents/mcp_oauth_flow.png)

> 참고: 앱 시작 중에 표시되는 토큰은 앱 수준의 초기화만을 위한 것이며 개별 사용자 연결에는 사용되지 않습니다.

자동 토큰 갱신 예시:

```bash
[MCP][spotify] Access token missing
[MCP][spotify] Attempting to refresh token
[MCP][spotify] Successfully refreshed and stored OAuth tokens
[MCP][spotify] ✓ Initialized
```

#### 모범 사례 [#best-practices]

1. **OAuth 사용 가능 시 사용**: 보안 강화를 위해 API 키보다 OAuth를 우선적으로 사용하세요
2. **적절한 타임아웃 구성**: OAuth 완료 창에는 `MCP_OAUTH_HANDLING_TIMEOUT` 및 `MCP_OAUTH_FLOW_TTL`을 사용하고, 서버 초기화에는 `initTimeout`을 사용하세요.
3. **토큰 만료 모니터링**: 인증 문제에 대한 로그 확인
4. **재인증 계획**: 일부 제공업체는 새로 고침 토큰(refresh tokens)을 지원하지 않습니다.

## Server Transports [#server-transports]

MCP 서버는 다양한 전송 메커니즘을 사용하도록 구성할 수 있습니다:

**STDIO 서버**

- 로컬, 단일 사용자 환경에 적합합니다
- 원격 또는 클라우드 배포에 확장 가능하지 않음
- 번들로 제공되는 MCP SDK는 각 개별 STDIO 메시지를 10MB로 제한합니다. 이보다 큰 단일 결과는 전송을 오류와 함께 종료시킵니다. 이 제한은 세션이나 스트림의 전체 크기와는 별개입니다.

**Server-Sent Events (SSE) 서버**

- 원격 전송 메커니즘이지만 프로덕션 환경에는 권장되지 않습니다.

**스트리밍 가능한 HTTP 서버**

- 메시지 전송을 위해 HTTP POST를 사용하며 응답 스트리밍을 지원합니다
- 여러 클라이언트 연결을 처리할 수 있는 독립적인 프로세스로 작동합니다
- Server-Sent Events (SSE)를 통한 기본 요청 및 스트리밍을 모두 지원합니다.
- 기존 HTTP+SSE 전송 방식보다 성능이 뛰어난 대안
- 적절한 다중 사용자 서버 구성을 지원합니다

**운영 환경(production environments)**의 경우, ["Streamable HTTP" 전송 방식](https://modelcontextprotocol.io/specification/draft/basic/transports/streamable-http)을 사용하는 MCP 서버만 권장됩니다. 장기 실행 연결을 유지하는 SSE와 달리, Streamable HTTP는 확장 가능한 다중 사용자 배포에 더 적합한 상태 비저장(stateless) 옵션을 제공합니다.

LibreChat은 유연하고 확장 가능한 MCP 서버 통합을 구현하는 데 앞장서고 있으며, 다양한 사용 시나리오를 지원하고 미래의 AI 워크플로우를 구축할 수 있도록 돕습니다.
