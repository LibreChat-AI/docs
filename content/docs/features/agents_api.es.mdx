<Callout type="warning" title="Funcionalidad beta">
La API de Agents se encuentra actualmente en fase beta. Los endpoint, los formatos de solicitud/respuesta y el comportamiento pueden cambiar a medida que iteramos hacia una versión estable.
</Callout>

LibreChat expone agentes a aplicaciones, scripts y servicios externos a través de APIs de inferencia y entrega de eventos.

## Descripción general [#overview]

La API de Agents proporciona dos interfaces de inferencia, entrega de eventos autenticada y rutas de gestión beta:

- **Chat Completions compatibles con OpenAI** — `POST /api/agents/v1/chat/completions`
- **API de respuestas abiertas** — `POST /api/agents/v1/responses`
- **Eventos de Agente** — `POST /api/agents/v1/events`
- **Gestión de agentes** — `/api/agents/v1/agents`
- **Gestión de habilidades** — `/api/agents/v1/skills`

Las interfaces de inferencia admiten autenticación mediante API-key, autenticación OIDC opcional y respuestas en streaming. Los Agent Events utilizan la autenticación mediante API-key de Remote Agents para que LibreChat pueda vincular cada entrega a una identidad de origen estable. Las rutas de gestión, en cambio, utilizan una lista de permitidos de despliegue que vincula un cliente de máquina OIDC a un usuario y tenant de LibreChat existentes.

LibreChat está adoptando [Open Responses](https://www.openresponses.org/) como su framework de API principal para servir agentes. Si bien el endpoint Chat Completions proporciona compatibilidad con versiones anteriores para herramientas existentes compatibles con OpenAI, el endpoint Open Responses representa la dirección futura.

## Habilitación de la Agents API [#enabling-the-agents-api]

La API de Agents está protegida detrás de la configuración de interfaz `remoteAgents`. Todos los permisos están configurados de forma predeterminada en `false`.

```yaml filename="librechat.yaml"
interface:
  remoteAgents:
    use: true
    create: true
```

Consulta [Interface Configuration — remoteAgents](/docs/configuration/librechat_yaml/object_structure/interface#remoteagents) para ver todas las opciones disponibles.

**Nota:** Los usuarios administradores tienen todos los permisos de agente remoto habilitados de forma predeterminada.

### Especificación OpenAPI y documentación interactiva [#openapi-specification-and-interactive-docs]

LibreChat puede servir la especificación de la API de Agents pública en `/api/openapi.json` y la documentación interactiva de Swagger UI en `/api/docs`. Ambas rutas están deshabilitadas de forma predeterminada. Habilítelas con la configuración de nivel superior `openapi`:

```yaml filename="librechat.yaml"
openapi:
  enabled: true
```

La especificación cubre las rutas públicas de inferencia, eventos, gestión de agentes y gestión de habilidades descritas en esta página. Mantenga las rutas deshabilitadas a menos que su despliegue pretenda exponer la documentación de la API.

## Gestión de API Key [#api-key-management]

Una vez que `remoteAgents.use` y `remoteAgents.create` estén habilitados, los usuarios pueden generar claves de API desde la interfaz de usuario de LibreChat. Estas claves autentican las solicitudes a la API de Agents.

## Autenticación [#authentication]

La API de Agents admite dos métodos de autenticación que pueden utilizarse de forma independiente o conjunta.

### Clave de API [#api-key]

La autenticación mediante API key está habilitada de forma predeterminada. Genera API keys desde la interfaz de usuario de LibreChat una vez que `remoteAgents.use` y `remoteAgents.create` estén habilitados.

```bash
Authorization: Bearer <YOUR_API_KEY>
```

### Token de portador OIDC [#oidc-bearer-token]

Para escenarios de máquina a máquina donde su infraestructura ya cuenta con un proveedor OIDC, puede autenticarse directamente con tokens Bearer OIDC sin necesidad de una clave de API de LibreChat.

Configure la autenticación OIDC en `librechat.yaml`:

```yaml filename="librechat.yaml"
endpoints:
  agents:
    remoteApi:
      auth:
        apiKey:
          enabled: false
        oidc:
          enabled: true
          issuer: https://auth.example.com/realms/myrealm
          # jwksUri is optional and auto-discovered from issuer if omitted
          audience: my-client-id
```

Luego, llama a la API con tu token de acceso OIDC:

```bash
curl -X POST https://your-librechat-instance/api/agents/v1/responses \
  -H "Authorization: Bearer YOUR_OIDC_ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"model": "agent_abc123", "input": "Hello!"}'
```

<Callout type="info">
  El token OIDC debe pertenecer a un usuario que ya exista en LibreChat. La coincidencia utiliza primero la reclamación `sub` y, si no, recurre a `email`, `preferred_username` o `upn`.
</Callout>

Consulte [Agents Endpoint - remoteApi](/docs/configuration/librechat_yaml/object_structure/agents#remoteapi) para ver todas las opciones de configuración.

<Callout type="warning" title="Los eventos de agente requieren una clave API">
  La autenticación exclusiva mediante OIDC no es compatible con los endpoints de Agent Events. Utilice una clave de API de Remote Agents al crear enlaces, poner eventos en cola y consultar el estado de entrega.
</Callout>

## API de Gestión de Agentes [#agent-management-api]

La API de gestión de Agents en versión beta permite que un servicio gestione Agents y sus recursos adjuntos sin necesidad de una sesión de navegador. Se autentica de forma independiente a la inferencia y a los Agent Events: solo se aceptan tokens de máquina OIDC configurados bajo [`endpoints.agents.managementApi`](/docs/configuration/librechat_yaml/object_structure/agents#managementapi).

Cada cliente OAuth configurado está vinculado a un `userId` y `tenantId` de LibreChat existentes. Tras la verificación del token, cada solicitud se ejecuta como ese usuario y mantiene las capacidades de rol actuales del usuario, las ACL de Agentes y Skills, las restricciones de proveedor, las concesiones de herramientas, los límites de archivos y el aislamiento de inquilinos. Un enlace de cliente no convierte al usuario en administrador ni otorga acceso a recursos que el usuario no pueda gestionar de otro modo.

### Rutas de Agentes [#agent-routes]

| Método   | Ruta                                       | Propósito                                    |
| -------- | ------------------------------------------ | -------------------------------------------- |
| `POST`   | `/api/agents/v1/agents`                    | Crear un Agent                               |
| `GET`    | `/api/agents/v1/agents`                    | Listar Agents accesibles                     |
| `GET`    | `/api/agents/v1/agents/{id}`               | Leer un Agent accesible                      |
| `PATCH`  | `/api/agents/v1/agents/{id}`               | Actualizar un Agent                          |
| `DELETE` | `/api/agents/v1/agents/{id}`               | Eliminar un Agent                            |
| `POST`   | `/api/agents/v1/agents/{id}/files`         | Subir y adjuntar un archivo de recurso al Agent |
| `GET`    | `/api/agents/v1/agents/{id}/files`         | Listar los archivos adjuntos accesibles del Agent |
| `DELETE` | `/api/agents/v1/agents/{id}/files/{fileId}` | Eliminar un archivo adjunto del Agent        |

Las cargas útiles (payloads) de creación y actualización de agentes utilizan los mismos campos soportados externamente que el Agent Builder y rechazan los campos de nivel superior desconocidos. La creación requiere un `model`; la actualización solo acepta los campos proporcionados. Las respuestas exponen la configuración del agente soportada además de `id`, `provider`, `model` (anulable), `version`, `createdAt` y `updatedAt`, sin los campos de propiedad de persistencia.

Las listas aceptan un `limit` de 1 a 100, con un valor predeterminado de 20, y un `cursor` opaco. Cuando `has_more` es true, pase el valor `after` devuelto como el siguiente cursor; no decodifique ni construya cursores en los clientes.

```bash
curl https://your-librechat-instance/api/agents/v1/agents?limit=20 \
  -H "Authorization: Bearer YOUR_MACHINE_ACCESS_TOKEN"
```

```bash
curl -X POST https://your-librechat-instance/api/agents/v1/agents \
  -H "Authorization: Bearer YOUR_MACHINE_ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Release assistant",
    "provider": "openAI",
    "model": "gpt-5.6",
    "instructions": "Prepare concise release notes from verified changes."
  }'
```

Las cargas de archivos utilizan `multipart/form-data` con un `file` y un valor de `tool_resource` como `context`, `file_search` o `execute_code`. LibreChat aplica las comprobaciones de capacidad de despliegue, concesión de roles, límite de tasa de carga, por archivo, recuento de archivos y tamaño agregado antes de adjuntar el recurso. Eliminar un archivo requiere acceso de edición al Agent y no debilita las reglas de autorización de archivos subyacentes.

### Rutas de habilidades [#skill-routes]

| Método  | Ruta                                                 | Propósito                             |
| ------- | ---------------------------------------------------- | ------------------------------------- |
| `GET`   | `/api/agents/v1/skills`                              | Listar habilidades accesibles        |
| `GET`   | `/api/agents/v1/skills/{id}`                         | Leer una habilidad accesible          |
| `PATCH` | `/api/agents/v1/skills/{id}`                         | Actualizar metadatos de habilidad soportada |
| `GET`   | `/api/agents/v1/skills/{id}/files`                   | Listar archivos en la habilidad       |
| `GET`   | `/api/agents/v1/skills/{id}/files/{relativePath}`    | Leer un archivo de habilidad          |
| `PUT`   | `/api/agents/v1/skills/{id}/files/{relativePath}`    | Crear o reemplazar un archivo soportado |

Las operaciones de Skill están limitadas a los Skills visibles para el usuario vinculado. Las lecturas requieren acceso al Skill, mientras que los metadatos o las escrituras de archivos requieren los permisos correspondientes de edición y de creación de Skills. Las rutas se normalizan debajo de la raíz del Skill; el recorrido de directorios, los archivos no compatibles y el contenido de gran tamaño son rechazados.

### Errores y autenticación [#errors-and-authentication]

Las respuestas de gestión utilizan errores estructurados con los códigos `invalid_request`, `not_found`, `permission_denied`, `conflict` o `internal_error`. Los fallos de autorización de recursos pueden devolverse como `not_found` para que los llamadores no puedan sondear IDs inaccesibles.

Los tokens de máquina deben estar vigentes, coincidir con el emisor configurado, identificar a un cliente incluido en la lista de permitidos a través de `azp` o `client_id`, y satisfacer la regla de sujeto configurada. De forma predeterminada, los tokens también deben coincidir con la audiencia configurada. Para proveedores como Amazon Cognito que emiten tokens de acceso de máquina con `client_id` en lugar de `aud`, establezca `tokenUse: access`, omita `audience` y requiera el ámbito OAuth esperado con `requiredScopes`. Una configuración faltante o credenciales no válidas devuelven `401`; una cuenta vinculada que está siendo eliminada devuelve `409`. Consulte [`managementApi.auth.oidc`](/docs/configuration/librechat_yaml/object_structure/agents#managementapiauthoidc) y [`managementApi.auth.clients`](/docs/configuration/librechat_yaml/object_structure/agents#managementapiauthclients) para conocer las reglas completas de reclamaciones y vinculación.

## Endpoints [#endpoints]

### Chat Completions (compatibles con OpenAI) [#chat-completions-openai-compatible]

```
POST /api/agents/v1/chat/completions
```

Utilice cualquier SDK compatible con OpenAI apuntándolo a su instancia de LibreChat. El parámetro `model` corresponde a un ID de agente.

**Ejemplo con curl:**
```bash
curl -X POST https://your-librechat-instance/api/agents/v1/chat/completions \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "agent_abc123",
    "messages": [
      {"role": "user", "content": "Hello, what can you help me with?"}
    ],
    "stream": true
  }'
```

**Ejemplo con el SDK de OpenAI (Python):**
```python
from openai import OpenAI

client = OpenAI(
    base_url="https://your-librechat-instance/api/agents/v1",
    api_key="YOUR_API_KEY"
)

response = client.chat.completions.create(
    model="agent_abc123",
    messages=[{"role": "user", "content": "Hello!"}],
    stream=True
)

for chunk in response:
    print(chunk.choices[0].delta.content, end="")
```

### Listar modelos [#list-models]

```
GET /api/agents/v1/models
```

Devuelve los agentes disponibles como modelos. Útil para descubrir qué agentes son accesibles con su clave de API.

### API de respuestas abiertas [#open-responses-api]

```
POST /api/agents/v1/responses
```

El endpoint Open Responses sigue la [especificación Open Responses](https://www.openresponses.org/), un estándar de inferencia abierto iniciado por OpenAI y construido por la comunidad de IA de código abierto. Está diseñado para flujos de trabajo de agentes con soporte nativo para razonamiento, uso de herramientas, salidas estructuradas y transmisión de eventos semánticos.

```bash
curl -X POST https://your-librechat-instance/api/agents/v1/responses \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "agent_abc123",
    "input": "What is the weather today?"
  }'
```

#### Herramientas de función ejecutadas por el llamador (Caller-Executed Function Tools) [#caller-executed-function-tools]

El endpoint Open Responses acepta herramientas de tipo `function` estándar proporcionadas por quien realiza la llamada. LibreChat expone estas definiciones al modelo pero no las ejecuta. Cuando el modelo selecciona una, la respuesta contiene un elemento de salida `function_call` para que quien realiza la llamada lo ejecute.

Para continuar, envíe una nueva solicitud cuyo `input` reproduzca el elemento `function_call` devuelto, seguido de un elemento `function_call_output` correspondiente. Esta transferencia no tiene estado: no crea una ejecución suspendida, y `previous_response_id` por sí solo no puede reemplazar el intercambio de herramientas reproducido.

```json
{
  "model": "agent_abc123",
  "input": [
    {
      "type": "function_call",
      "call_id": "call_abc123",
      "name": "lookup_order",
      "arguments": "{\"order_id\":\"A-42\"}"
    },
    {
      "type": "function_call_output",
      "call_id": "call_abc123",
      "output": "{\"status\":\"shipped\"}"
    }
  ]
}
```

Los nombres de las herramientas del llamador (caller tool) pueden contener letras, números, guiones bajos y guiones. Los nombres deben ser únicos y no pueden reemplazar una herramienta proporcionada por el servidor. Una herramienta ejecutada por el llamador debe ser la única herramienta seleccionada en su turno; si el modelo la mezcla con herramientas ejecutadas por el servidor, LibreChat le pide al modelo que vuelva a intentar la herramienta del llamador por sí sola.

Para las herramientas de Agente ejecutadas por LibreChat, ambos endpoints de inferencia headless aplican una política habilitada de [`endpoints.agents.toolApproval`](/docs/configuration/librechat_yaml/object_structure/agents#toolapproval), incluyendo `deny`, `ask` y hooks programáticos. Estas llamadas no tienen un canal interactivo de aprobación/reanudación: `deny` y `ask` bloquean la herramienta en lugar de abrir un prompt de aprobación. Configure permisos explícitos solo para las herramientas que el cliente de la API deba poder ejecutar sin supervisión; cuando la política está deshabilitada, sus hooks de aprobación no se ejecutan. Las herramientas de función ejecutadas por el llamador siguen siendo responsabilidad del llamador.

## Eventos de Agente [#agent-events]

Los Agent Events permiten que un controlador autenticado o un adaptador de origen entreguen trabajo duradero a un Agent. La entrega de eventos es una funcionalidad en fase beta y su comportamiento de solicitud, respuesta y tiempo de ejecución puede cambiar.

Los endpoints utilizan el usuario autenticado, el tenant y la API key; el Agent de destino debe ser visible para ese usuario bajo los permisos de Remote Agents existentes. Las solicitudes de Agent Event también utilizan el bucket dedicado [`rateLimits.agentEvents`](/docs/configuration/librechat_yaml/object_structure/config#ratelimits).

### Entregar un evento [#deliver-an-event]

```http
POST /api/agents/v1/events
Authorization: Bearer <REMOTE_AGENTS_API_KEY>
Idempotency-Key: webhook-42-resource-7
Content-Type: application/json

{
  "mode": "fire",
  "event": {
    "id": "resource-7-ready-3",
    "type": "resource.ready",
    "occurredAt": 1786967999000,
    "payload": { "resourceId": "resource-7" }
  },
  "target": { "agentId": "agent_abc123" },
  "input": "Resource resource-7 is ready. Inspect it and report the result.",
  "orderingKey": "resource-7"
}
```

Envíe exactamente un encabezado `Idempotency-Key` y reutilícelo al reintentar la misma entrega de evento de origen a destino. La clave debe contener de 1 a 256 letras, números o los caracteres `._~:/+=-`. Reutilizar una clave con un contenido de entrega diferente devuelve un conflicto.

El llamador proporciona el `id`, `type`, `occurredAt` y el `payload` saneado del evento. LibreChat reemplaza cualquier `event.source` proporcionado por el llamador con la identidad de la clave de API autenticada y deriva el usuario, el inquilino (tenant), el ID de solicitud y el tiempo de recepción. No coloque credenciales ni secretos de transporte en los payloads de los eventos, ya que las entregas aceptadas se persisten.

`orderingKey` es opcional. Utilice un valor estable cuando las entregas de diferentes fuentes deban permanecer ordenadas para el mismo recurso.

Una solicitud exitosa devuelve `202 Accepted`, un `id` de entrega opaco, su estado actual y un encabezado `Location`. Realiza un sondeo (poll) a esa ubicación:

```http
GET /api/agents/v1/events/{delivery_id}
Authorization: Bearer <SAME_REMOTE_AGENTS_API_KEY>
```

La entrega puede ser `pending`, `leased`, `succeeded` o `dead`. La respuesta de estado incluye intentos y marcas de tiempo, además de un resultado o error público cuando se completa; no expone la carga útil almacenada, la clave de ordenamiento, el historial de reintentos ni la identidad del trabajador. El acceso al estado está limitado al mismo usuario, inquilino y fuente de clave API.

Para un `continue` vinculado, `succeeded` significa que se admitió el turno del Agente, no que el trabajo solicitado haya finalizado. Por lo tanto, su estado también expone un ciclo de vida de `handling` duradero: `started`, seguido exactamente por uno de los siguientes: `applied`, `completed_no_action`, `failed` o `cancelled`.

Las fuentes que reconocen acciones pueden incluir un `expectedAction` con un nombre de herramienta y un subconjunto de argumentos opcional. LibreChat informa `applied` solo cuando esa generación exacta finaliza con evidencia de la herramienta observada por el host que coincide con el contrato; la prosa redactada por el modelo nunca se acepta como prueba. Las entregas de `fire`, `steer` y `continue` sin enlazar rechazan `expectedAction`.

Los resultados exitosos de `fire` incluyen la identidad de la conversación y la generación a la que un evento `steer` posterior puede dirigirse.

### Agentes secundarios basados en eventos [#event-driven-child-agents]

Un sistema externo puede vincular un actor de origen a un Agente hijo directo y, posteriormente, continuar esa misma conversación secundaria a través de eventos. Las continuaciones de hijos vinculados son automáticas una vez que se verifican con éxito la identidad de la API-key, la propiedad de la vinculación, la relación jerárquica y la autorización del Agente; no existe un interruptor de función independiente.

Registre el actor con la misma API key que entregará sus turnos posteriores:

```http
POST /api/agents/v1/events/bindings
Authorization: Bearer <REMOTE_AGENTS_API_KEY>
Idempotency-Key: championship-7-player-hanae
Content-Type: application/json

{
  "actorId": "hanae-kobayashi",
  "parentConversationId": "director-conversation-id",
  "parentMessageId": "director-message-id",
  "target": { "agentId": "agent_hanae" }
}
```

`actorId` puede contener hasta 128 caracteres. El padre debe ser una conversación de Agent ordinaria, y el destino debe estar configurado como uno de los Subagents directos de ese Agent o como un self-spawn permitido. Un nuevo binding devuelve `201`; una repetición idempotente devuelve `200`. Ambas respuestas incluyen `id`, `actorId`, `agentId` y `threadId`.

Enviar turnos posteriores con el ID de enlace devuelto:

```http
POST /api/agents/v1/events
Authorization: Bearer <SAME_REMOTE_AGENTS_API_KEY>
Idempotency-Key: game-12-ply-17-hanae
Content-Type: application/json

{
  "mode": "continue",
  "bindingId": "evtbind_...",
  "event": {
    "id": "game-12-ply-17",
    "type": "chess.turn.ready",
    "occurredAt": 1786968000000,
    "payload": { "gameId": "game-12", "expectedPly": 17 }
  },
  "input": "Your clock is running. Read the position and submit one legal move.",
  "expectedAction": {
    "tool": "submit_move",
    "arguments": { "gameId": "game-12" }
  }
}
```

LibreChat resuelve el Agente hijo, el hilo, la última hoja de la rama y el carril de ordenamiento desde el enlace inmediatamente antes del envío. Los campos de destino y ordenamiento proporcionados por el llamador no pueden redirigir una continuación vinculada. La `Idempotency-Key` de la solicitud se convierte en la identidad pública estable para ese turno hijo a través de reintentos de entrega, arrendamiento de generación, mensajes persistidos, actividad en vivo y una reanudación HITL posterior.

Cada binding tiene un buzón duradero automático. Su siguiente evento permanece en cola hasta que el turno actual alcanza `applied`, `completed_no_action`, `failed` o `cancelled`; los diferentes bindings permanecen independientes y pueden ejecutarse en paralelo. La continuación desde un punto de control (checkpoint) solo se intenta para un turno inicializado compatible. Si falta un punto de control o no se puede restaurar, LibreChat recurre al historial de mensajes duraderos sin debilitar las comprobaciones de recepción, autorización o acciones esperadas.

Un actor vinculado puede pausar para solicitar la intervención del usuario o la aprobación de una herramienta. LibreChat persiste la suspensión firmada exacta antes de exponer la acción pendiente, y el buzón del enlace permanece bloqueado hasta que esa misma invocación del actor se reanude o se resuelva. Los Event Actors requieren el checkpointer duradero de MongoDB; `type: memory` no es compatible. LibreChat negocia el protocolo de generación v2 y selecciona automáticamente el punto de control o la continuación del historial. El trabajo existente del protocolo v1 permanece en la ruta de historial duradero hasta que se agote. Consulte [Generation Protocol Compatibility](/docs/configuration/redis#generation-protocol-compatibility) para conocer los requisitos de implementación de versiones mixtas.

### Coalescing Observational Events [#coalescing-observational-events]

Las fuentes que pueden demostrar que varios eventos `continue` vinculados son observaciones intercambiables pueden asignarles el mismo `coalesce.key` definido por la fuente:

```json
{
  "mode": "continue",
  "bindingId": "evtbind_...",
  "event": {
    "id": "championship-7-game-12-move-18",
    "type": "chess.move.completed",
    "occurredAt": 1786968000750,
    "payload": { "gameId": "game-12", "ply": 18 }
  },
  "input": "A tournament game advanced.",
  "coalesce": { "key": "championship-commentary" }
}
```

LibreChat recopila eventos compatibles durante un máximo de 750 ms, con un límite de 8 eventos y 512 KiB de sobres combinados. El hijo recibe un documento de lote determinista, pero cada evento de origen conserva su propia `Idempotency-Key`, registro de entrega y recibo.

Utilice la coalescencia solo para observaciones que no requieran acción. Se rechaza para `fire`, `steer`, `continue` sin enlazar y entregas con `expectedAction`; no la utilice para comandos, aprobaciones, solicitudes HITL, cercas (fences) o eventos cuyo tiempo individual sea importante.

En la conversación principal autenticada, cada actor vinculado aparece debajo de su mensaje principal propietario. El panel de Subagent puede alternar entre actores y turnos, cargar actividad anterior y expandir un turno para mostrar su actividad vinculada completa. Los detalles del evento incluyen el tipo, la fuente, el momento de ocurrencia y la acción esperada. Se incluyen los pasos de ejecución, herramientas, mensajes y marcadores de razonamiento visibles, sin el texto de razonamiento sin procesar. El índice principal devuelve como máximo 64 hilos secundarios y 20 tareas recientes por hijo desde una ventana de fuente vinculada, informa sobre la truncación en lugar de implicar integridad, y limita la respuesta a 96 KB. Está autorizado por padre, usuario e inquilino; los enlaces, los ID de clave de fuente, los tokens de arrendamiento y el estado del trabajador no se incluyen en la proyección.

El hilo secundario permanece oculto de la navegación de conversación normal y es de solo lectura para las rutas de chat humanas, hereda la política temporal o de expiración del padre y está limitado a un nivel de hijo directo. Un ID de vinculación por sí solo no otorga acceso; las continuaciones están limitadas al usuario, al inquilino y a la API key que las creó.

### Acciones del Actor de Eventos Desacoplado [#detached-event-actor-actions]

Los turnos de Event Actor pueden separar las Acciones elegibles y completarlas de forma duradera. La entrega permanece en su ciclo de vida de gestión mientras la Acción se ejecuta; la evidencia terminal duradera reanuda la invocación original del actor firmado, y solo la evidencia de la herramienta observada por el host resultante puede satisfacer `expectedAction`. Las repeticiones y las réplicas en competencia no pueden lanzar la misma Acción reservada dos veces. Si LibreChat no puede determinar si comenzó un efecto secundario externo, pone en cuarentena el lanzamiento en lugar de reintentarlo a ciegas.

LibreChat habilita este trabajo de finalización interna automáticamente cuando el almacén de generación integrado seleccionado anuncia soporte. El almacén en memoria ejecuta el inicio, la finalización y la continuación en un solo proceso y no puede recuperar ese trabajo después de que el proceso finaliza. Los flujos de generación de Redis añaden recuperación de reinicio duradera y transferencia de réplicas. Los registros de entrega y recuperación propiedad de la capacidad permanecen invisibles para los reclamantes más antiguos durante un drenaje de versión mixta; no existe un indicador de productor gestionado por el operador.

## Seguimiento del uso de tokens [#token-usage-tracking]

Todas las solicitudes de inferencia de la API de Agents rastrean el uso de tokens contra el saldo del usuario cuando el gasto de tokens está configurado. Tanto las respuestas en streaming como las que no lo son agregan cada llamada de modelo de Agent principal y Subagent facturada a los totales de nivel superior. La respuesta también incluye desgloses de tokens `primary` y `subagent` sin identidad. Los detalles de los tokens de caché y de razonamiento se incluyen cuando el proveedor los informa.
