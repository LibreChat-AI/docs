La API de Agentes permite que el código externo a LibreChat se comunique con tus agentes. Apunta cualquier SDK de OpenAI a tu instancia, pasa el ID de un agente como modelo y obtendrás la configuración completa del agente (instrucciones, herramientas y archivos) a través de una API conocida. Úsala para integrar un agente en un script, en un trabajo de CI o en otro producto.

## Obtener una API key [#get-an-api-key]

Abre **Configuración**, ve a **Datos y privacidad** y busca **Claves de API de agentes** en **Claves de API**. Haz clic en **Administrar** y luego en **Crear clave de API**, asígnale un nombre, elige una fecha de expiración (de 7 días hasta 1 año, o nunca) y copia la clave de inmediato: solo se muestra una vez.

Una clave actúa como tú. Cualquier cosa a la que puedas acceder a través de la API también será accesible para cualquiera que tenga la clave, así que elimina las claves que ya no utilices. Eliminar una clave corta de inmediato el acceso a las aplicaciones que la usan.

Si no ves la sección, tu rol no tiene acceso a la API de Agents.

## Qué agentes puedes llamar [#which-agents-you-can-call]

Puedes llamar a los agentes que te pertenecen o que se han compartido contigo. Para los agentes de otras personas, el propietario debe concederte acceso mediante el botón **Acceso remoto** (el icono del globo) en el pie de página del Constructor de agentes. Esto es independiente del uso compartido normal: poder chatear con un agente en LibreChat no te permite llamarlo a través de la API.

Necesitas el ID del agente, que se muestra en **Advanced Settings** en el builder con un botón de copiar. `GET /api/agents/v1/models` lista los agentes a los que puede llamar tu clave, y `GET /api/agents/v1/models/{model}` devuelve uno.

## Completaciones de chat [#chat-completions]

`POST /api/agents/v1/chat/completions` sigue el formato de Chat Completions de OpenAI, por lo que los clientes existentes de OpenAI funcionan simplemente cambiando la URL base:

```python
from openai import OpenAI

client = OpenAI(
    base_url="https://your-librechat-instance/api/agents/v1",
    api_key="YOUR_API_KEY",
)

stream = client.chat.completions.create(
    model="agent_abc123",
    messages=[{"role": "user", "content": "Summarize yesterday's open tickets."}],
    stream=True,
)

for chunk in stream:
    print(chunk.choices[0].delta.content or "", end="")
```

La misma solicitud con curl:

```bash
curl https://your-librechat-instance/api/agents/v1/chat/completions \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "agent_abc123",
    "messages": [{"role": "user", "content": "Hello"}],
    "stream": true
  }'
```

## Respuestas Abiertas [#open-responses]

`POST /api/agents/v1/responses` implementa la especificación [Open Responses](https://www.openresponses.org/), diseñada para cargas de trabajo de agentes: el razonamiento, las llamadas a herramientas y los eventos en streaming forman parte del propio formato y no son añadidos posteriormente. Esta es la interfaz sobre la que LibreChat está construyendo en adelante, por lo que se recomienda usarla para las nuevas integraciones.

```bash
curl https://your-librechat-instance/api/agents/v1/responses \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model": "agent_abc123", "input": "What changed in the last release?"}'
```

`GET /api/agents/v1/responses/{id}` devuelve una respuesta almacenada, y `GET /api/agents/v1/responses/models` enumera los agentes disponibles aquí.

### Tus propias herramientas de función [#your-own-function-tools]

Puedes pasar herramientas `function` estándar en una solicitud de Responses. LibreChat las muestra al modelo, pero no las ejecuta: cuando el modelo elige una, la respuesta contiene un elemento `function_call`, y tú ejecutas la función por tu cuenta. Para continuar, envía una nueva solicitud cuyo `input` repita ese elemento `function_call` seguido de un `function_call_output` con el mismo `call_id`:

```json
{
  "model": "agent_abc123",
  "input": [
    { "type": "function_call", "call_id": "call_abc123", "name": "lookup_order", "arguments": "{\"order_id\":\"A-42\"}" },
    { "type": "function_call_output", "call_id": "call_abc123", "output": "{\"status\":\"shipped\"}" }
  ]
}
```

No se mantiene nada abierto entre las dos solicitudes, y `previous_response_id` por sí solo no es suficiente; debes repetir la llamada y su salida. Los nombres de las herramientas pueden usar letras, números, guiones bajos y guiones, deben ser únicos y no pueden sobrescribir una de las herramientas propias del agente. Un turno que llama a una de tus herramientas no puede llamar al mismo tiempo a las herramientas del agente; se le pide al modelo que lo vuelva a intentar.

### Aprobación de herramientas a través de la API [#tool-approval-over-the-api]

Si tu administrador exige aprobación para algunas herramientas, las llamadas a la API no pueden detenerse para pedir la confirmación de nadie. Las herramientas que requerirían aprobación, o que han sido denegadas, se bloquean en su lugar. Los administradores deben permitir explícitamente las herramientas que un cliente desatendido está destinado a ejecutar.

## Eventos de Agente [#agent-events]

Los Eventos de Agente permiten que otro sistema le asigne trabajo a un agente y regrese más tarde para ver qué sucedió. Esta función está en beta. Los eventos usan tu clave de API de Agentes, que te identifica a ti y a la fuente; las configuraciones que usan solo OIDC no pueden utilizarlos. Además, tienen su propio límite de tasa, [`rateLimits.agentEvents`](/docs/configuration/librechat_yaml/object_structure/config#ratelimits).

Un evento llega en uno de tres modos:

- `fire` inicia una nueva conversación con el agente.
- `continue` añade un turno a un agente hijo que vinculaste anteriormente (ver más abajo).
- `steer` añade orientación a una ejecución que todavía está en curso, identificada por la conversación y la generación que devolvió un `fire`.

```http
POST /api/agents/v1/events
Authorization: Bearer <REMOTE_AGENTS_API_KEY>
Idempotency-Key: webhook-42-resource-7
Content-Type: application/json

{
  "mode": "fire",
  "event": {
    "id": "resource-7-ready-3",
    "type": "resource.ready",
    "occurredAt": 1786967999000,
    "payload": { "resourceId": "resource-7" }
  },
  "target": { "agentId": "agent_abc123" },
  "input": "Resource resource-7 is ready. Inspect it and report the result.",
  "orderingKey": "resource-7"
}
```

Cada solicitud necesita una `Idempotency-Key` (de 1 a 256 letras, números o `._~:/+=-`). Reutilízala cuando reintentes la misma entrega; reutilizarla para contenido distinto es un conflicto. LibreChat establece el origen del evento a partir de tu clave de API e ignora cualquier origen que envíes. El payload se almacena, así que mantén los secretos fuera de él. Usa `orderingKey` cuando los eventos sobre el mismo elemento deban procesarse en orden.

La respuesta es `202 Accepted` con un ID de entrega y una `Location` para consultar con la misma clave:

```http
GET /api/agents/v1/events/{delivery_id}
Authorization: Bearer <SAME_REMOTE_AGENTS_API_KEY>
```

Una entrega puede tener el estado `pending`, `leased`, `succeeded` o `dead`. En el caso de un `continue` vinculado, `succeeded` solo significa que el turno se ha iniciado. Su estado `handling` pasa entonces de `started` a uno de los siguientes: `applied`, `completed_no_action`, `failed` o `cancelled`. Si envías un `expectedAction` (el nombre de una herramienta y, opcionalmente, algunos de sus argumentos), `applied` significa que LibreChat ha visto que esa herramienta se llamó con los argumentos coincidentes; lo que el modelo diga en el texto no cuenta.

Los eventos de agentes no son un receptor de webhooks público. Si los eventos provienen de un proveedor que firma sus webhooks, verifica la firma en tu propio adaptador antes de reenviarlos.

### Agentes hijos impulsados por eventos [#event-driven-child-agents]

Para mantener una conversación en curso con un agente hijo a lo largo de muchos eventos, vincúlalo una vez y luego envía eventos `continue` al vínculo:

```http
POST /api/agents/v1/events/bindings
Authorization: Bearer <REMOTE_AGENTS_API_KEY>
Idempotency-Key: championship-7-player-hanae
Content-Type: application/json

{
  "actorId": "hanae-kobayashi",
  "parentConversationId": "director-conversation-id",
  "parentMessageId": "director-message-id",
  "target": { "agentId": "agent_hanae" }
}
```

El padre debe ser una conversación normal con un agente, y el destino debe ser uno de los subagentes directos de ese agente (o el propio agente, si se permite la autogeneración). `actorId` admite hasta 128 caracteres. Un nuevo enlace devuelve `201` y una repetición devuelve `200`, ambos con el `id` del enlace. Los turnos posteriores hacen referencia a él:

```json
{
  "mode": "continue",
  "bindingId": "evtbind_...",
  "event": { "id": "game-12-ply-17", "type": "chess.turn.ready", "occurredAt": 1786968000000, "payload": { "gameId": "game-12" } },
  "input": "Your clock is running. Submit one legal move.",
  "expectedAction": { "tool": "submit_move", "arguments": { "gameId": "game-12" } }
}
```

Cada enlace procesa un evento a la vez: el siguiente espera hasta que el turno actual tenga un estado de manejo final, mientras que los distintos enlaces se ejecutan en paralelo. Un hijo vinculado puede pausarse para Ask User o para la aprobación de una herramienta; sus eventos posteriores esperan hasta que alguien responda en LibreChat. Esto requiere el checkpointer durable de MongoDB (el predeterminado). En la conversación principal, cada hijo vinculado aparece como una fila debajo del mensaje que posee el enlace y abre el panel de actividad del subagente.

Un enlace solo funciona con la clave de API, el usuario y el tenant que lo crearon. El hilo secundario permanece fuera de la lista de chats y es de solo lectura en la aplicación.

Para los eventos que son solo observaciones, como "una partida avanzó", asígnales la misma `coalesce.key` y LibreChat agrupa hasta 8 de ellos (dentro de 750 ms y 512 KiB) en un solo turno. Cada evento sigue teniendo su propio recibo. No agrupes comandos, aprobaciones ni cualquier evento que tenga un `expectedAction`.

## API de Gestión de Agentes [#agent-management-api]

La API de gestión de agentes permite a un servicio de confianza crear, modificar y eliminar agentes y habilidades sin una sesión de navegador. Está en beta y utiliza su propia autenticación: tokens OIDC de máquina procedentes de clientes que el administrador enumera en [`managementApi`](/docs/configuration/librechat_yaml/object_structure/agents#managementapi). Cada cliente está vinculado a un usuario de LibreChat existente y a un tenant, y cada solicitud actúa como ese usuario, con sus permisos y accesos. No convierte a nadie en administrador.

| Método   | Ruta                                         | Propósito                          |
| -------- | -------------------------------------------- | ---------------------------------- |
| `POST`   | `/api/agents/v1/agents`                      | Crear un agente                    |
| `GET`    | `/api/agents/v1/agents`                      | Listar los agentes accesibles      |
| `GET`    | `/api/agents/v1/agents/{id}`                 | Leer un agente                     |
| `PATCH`  | `/api/agents/v1/agents/{id}`                 | Actualizar un agente               |
| `DELETE` | `/api/agents/v1/agents/{id}`                 | Eliminar un agente                 |
| `POST`   | `/api/agents/v1/agents/{id}/files`           | Subir y adjuntar un archivo        |
| `GET`    | `/api/agents/v1/agents/{id}/files`           | Listar los archivos adjuntos       |
| `DELETE` | `/api/agents/v1/agents/{id}/files/{fileId}`  | Desvincular un archivo             |
| `GET`    | `/api/agents/v1/skills`                      | Listar las habilidades accesibles  |
| `POST`   | `/api/agents/v1/skills`                      | Crear una habilidad                |
| `GET`    | `/api/agents/v1/skills/{id}`                 | Leer una habilidad                 |
| `PATCH`  | `/api/agents/v1/skills/{id}`                 | Actualizar una habilidad           |
| `DELETE` | `/api/agents/v1/skills/{id}`                 | Eliminar una habilidad             |
| `GET`    | `/api/agents/v1/skills/{id}/files`           | Listar los archivos de una habilidad |
| `GET`    | `/api/agents/v1/skills/{id}/files/{path}`    | Leer un archivo de habilidad       |
| `PUT`    | `/api/agents/v1/skills/{id}/files/{path}`    | Crear o reemplazar un archivo de habilidad |
| `DELETE` | `/api/agents/v1/skills/{id}/files/{path}`    | Eliminar un archivo de habilidad   |

```bash
curl -X POST https://your-librechat-instance/api/agents/v1/agents \
  -H "Authorization: Bearer YOUR_MACHINE_ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Release assistant",
    "provider": "openAI",
    "model": "gpt-5.6",
    "instructions": "Prepare concise release notes from verified changes."
  }'
```

Agent payloads take the same fields as the Agent Builder and reject unknown ones; `model` is required on create. Lists take `limit` (1 to 100, default 20) and a `cursor`; when `has_more` is true, pass the returned `after` as the next cursor. File uploads are `multipart/form-data` with one `file` and a `tool_resource` such as `context`, `file_search`, or `execute_code`, subject to the usual upload limits.

Skill create takes `name`, `description`, `body`, and optionally `displayTitle`, `frontmatter`, `category`, and `alwaysApply`. Updates must send the skill's current version as `expectedVersion`, so two writers cannot overwrite each other silently.

Los errores usan los códigos `invalid_request`, `not_found`, `permission_denied`, `conflict` y `internal_error`. Un recurso al que no tienes acceso puede devolverse como `not_found`. Las credenciales incorrectas o ausentes devuelven `401`.

Si el administrador lo habilita, se sirve una descripción OpenAPI de las rutas de gestión en `/api/openapi.json`, con documentación interactiva en `/api/docs`. No cubre la inferencia ni los eventos. Consulte [`openapi`](/docs/configuration/librechat_yaml/object_structure/config#openapi).

## Uso y facturación [#usage-and-billing]

Las solicitudes a la API se descuentan de tu saldo de tokens exactamente igual que los chats en la aplicación. Los totales de uso en la respuesta incluyen las llamadas a subagentes, con un desglose separado en `primary` y `subagent`, además de los tokens de caché y de razonamiento cuando el proveedor los informa. Consulta [Token Usage](/docs/configuration/token_usage).

## Configuración [#setup]

La API de Agentes está desactivada para los usuarios normales hasta que un administrador conceda los permisos de Agentes Remotos a su rol, ya sea en el [Panel de administración](/docs/features/admin_panel) o mediante [`interface.remoteAgents`](/docs/configuration/librechat_yaml/object_structure/interface#remoteagents). Los administradores la tienen activada por defecto. La autenticación con clave de API está activada por defecto; para aceptar tokens de su propio proveedor OIDC en lugar de claves o junto con ellas, consulte [`remoteApi`](/docs/configuration/librechat_yaml/object_structure/agents#remoteapi). La API de Gestión se configura por separado en [`managementApi`](/docs/configuration/librechat_yaml/object_structure/agents#managementapi), y los ajustes de entrega de eventos se encuentran en [`eventDriven`](/docs/configuration/librechat_yaml/object_structure/agents#eventdriven).
