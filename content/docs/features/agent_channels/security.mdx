Agent Channels put an agent where many people can talk to it, so every decision about access is made by LibreChat, per person, at the moment a request arrives. Connecting a bot to Slack never widens what anyone can do in LibreChat.

## Permissions by role

Each step of setup needs a different permission. Use this table to check that the right people have them before you start.

| Task | Who can do it | What they need |
| --- | --- | --- |
| Deploy the gateway | Deployment operator | Access to the server configuration and secrets. No LibreChat role is involved. |
| Register Slack apps and connect workspaces | Organization administrator | The `access:admin` and `manage:agents` capabilities, which the `ADMIN` role has. Both are required. |
| Grant bot management access | Organization administrator | The same capabilities as above |
| Assign an agent to a bot | Agent owner or bot manager | The **Remote Agents** use permission, **share** access to the agent, and management access to the bot (or administrator capabilities) |
| Change or remove an assignment | The person who created the connection | Only the connection's creator can change its assignments. |
| Use the bot | Anyone in the Slack workspace, or only the owner for a **Channel owner only** connection | An active, linked LibreChat account whose role can use **Agents** and **Remote Agents**, and [Remote Access](#remote-access-to-the-agent) to the agent |

<Callout type="warning" title="Turn on Remote Agents for your users">
Channel requests run through the same Responses API as the [Agents API](/docs/features/agents_api), so the **Remote Agents** use permission is required. The default `USER` role does not have it. Grant it in the [Admin Panel](/docs/features/admin_panel), or seed it with [`interface.remoteAgents.use`](/docs/configuration/librechat_yaml/object_structure/interface#remoteagents). Without it, the Channels section is hidden in the Agent Builder and linked users cannot run the agent.
</Callout>

### Remote Access to the agent

Channel requests check the same per-agent access as the [Agents API](/docs/features/agents_api), which is separate from normal sharing. Being able to chat with an agent in LibreChat is not enough:

- People who can **share** the agent, including its owner, always have access.
- Everyone else needs to be granted access with the **Remote Access** button (the globe icon) in the Agent Builder footer.

Grant Remote Access to the users, groups, or roles who will talk to the bot. Without it, they can link their account, but their requests are refused.

### Bot managers

In organization workspaces, administrators decide who may attach agents to each installed bot. Open the workspace's **Manage access** button to add people in the **Manage bot access** dialog. Up to 50 managers are allowed per installation by default (`maxBotManagers`).

Bot management lets someone assign agents through that bot and nothing else. It does not grant permission to share agents or to administer the installation, and people who only talk to the bot do not need it. Removing a manager does not stop the assignments they already made.

## What runs as whom

A request always runs as the linked LibreChat user who sent it:

- **Tools and connections are personal.** MCP servers, OAuth connections, and API keys are the sender's own. If a tool needs a sign-in, the sender completes it in LibreChat.
- **Approvals are personal.** Only the sender sees the private review controls for their request, and only they can approve, decline, or stop it.
- **Files stay with their owner.** Files the agent attaches to a reply are scoped to that run and that person. Someone else in the thread cannot use them to reach the sender's data.
- **Usage is personal.** Cost and token usage count against the sender's account, exactly as if they had used the agent in LibreChat.

The agent's own [approval policy](/docs/features/agents) still applies. Connecting Slack does not make every tool require approval, and it never skips an approval the agent would ask for in LibreChat.

## Account links

Linking requires two confirmations: accepting the link while signed in to LibreChat, then selecting **Confirm account** from the same Slack account. A link that was accepted in the browser but never confirmed in Slack cannot run anything.

A link stops working when:

- It expires (30 days by default, `linkLifetimeMs`).
- The person disconnects it in **Settings → Account → Your channel account links**.
- The connection is disabled, deleted, reconfigured, or its identity mode changes.
- The person's account is deactivated, their role loses the **Agents** or **Remote Agents** use permission, or they lose Remote Access to the agent.
- The person must still complete a required two-factor authentication enrollment.

When access changes while a request is running, the run is retired instead of continuing under the old permissions. Linking never grants new tools, new agent access, or offline access to connected services.

## Secrets and credentials

| Secret | Where it lives | Notes |
| --- | --- | --- |
| Slack client secret and signing secret (organization apps) | Encrypted in the LibreChat database | Entered by an administrator in the UI. They are not environment variables or YAML settings. |
| Bot tokens | Encrypted in the LibreChat database | Issued by Slack during installation, or pasted into the manual setup wizard. The gateway receives them over the private API. |
| `CHANNEL_SERVICE_TOKEN` | Server-side environment of LibreChat and the gateway | At least 32 characters, identical on both sides. It authenticates the gateway only and cannot act as a browser session or general API key. |
| `SLACK_APP_TOKEN` | Gateway environment only | Needed only for manual Socket Mode connections. |

Keep the gateway's health and metrics endpoints, and LibreChat's private channel API, on an internal network. Only the Slack callback paths need to be public.

## Request verification

- **Webhook signatures.** The gateway verifies every Slack request signature and rejects timestamps older than five minutes (`signatureToleranceSeconds`). Keep server clocks synchronized.
- **Installation matching.** Events must come from the installed workspace and app. Messages from bots, including the bot itself, are ignored.
- **Private controls.** Approvals and questions are shown only to the person who made the request, and every click is checked again by LibreChat before anything resumes. A Slack button press alone is never treated as permission.
- **Links stay in LibreChat.** Provider sign-in pages and unsupported forms always open in the authenticated LibreChat browser flow, never inside Slack.

## Data in the messaging app

Answers are posted to Slack, so they are visible to everyone who can read that conversation, and they follow your Slack workspace's retention rules. Consider this before assigning an agent with access to sensitive data to a busy channel. A channel-specific assignment lets you use a different, more limited agent in shared channels.

LibreChat stores each run, its response, and its delivery receipts so that requests can be recovered and audited. When feedback collection is enabled, thumbs-up and thumbs-down reactions on the bot's replies are recorded as feedback for that run.
