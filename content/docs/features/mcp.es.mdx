Model Context Protocol (MCP) es un protocolo abierto que estandariza la forma en que las aplicaciones proporcionan contexto a los Large Language Models (LLMs). Piense en MCP como el **"USB-C de la IA"**: así como el USB-C proporciona un estándar de conexión universal para dispositivos electrónicos, MCP ofrece una forma estandarizada de conectar modelos de IA a diversas herramientas, fuentes de datos y servicios.

LibreChat aprovecha MCP para expandir drásticamente lo que sus agentes de IA pueden hacer, permitiéndole integrar desde acceso al sistema de archivos, navegadores web y APIs especializadas, hasta herramientas empresariales personalizadas.

## Por qué es importante MCP [#why-mcp-matters]

Los LLMs están limitados a sus capacidades integradas. Con MCP, LibreChat derriba estos muros al:

- **Conectarse a cualquier herramienta o servicio** que proporcione un servidor MCP
- **Estandarización de integraciones** para que no necesites editar el código de LibreChat para cada herramienta
- **Soporte para entornos multiusuario** con autenticación y aislamiento adecuados
- **Agregar y actualizar servidores en tiempo de ejecución** desde el panel de configuración de MCP, sin editar un archivo de configuración ni reiniciar

## Cómo funciona MCP en LibreChat [#how-mcp-works-in-librechat]

LibreChat ofrece dos formas de utilizar servidores MCP, ya sea en el área de chat o con agentes.

Puede configurar servidores MCP manualmente en su archivo `librechat.yaml` o utilizando [smithery.ai](https://smithery.ai) para buscar e instalar servidores MCP en `librechat.yaml` ([vea el ejemplo a continuación](#basic-configuration)). Cada vez que agregue o edite un servidor en `librechat.yaml`, deberá reiniciar LibreChat para inicializar las conexiones. Los servidores agregados a través del [panel de configuración de MCP](#adding-mcp-servers-in-the-ui) surten efecto sin necesidad de reiniciar. Un servidor creado desde el panel que utiliza OAuth se registra al guardar, pero comienza desconectado: [autentíquelo](#step-3-check-connection-status-and-authenticate) una vez para conectarlo.

### URL de devolución de llamada OAuth [#oauth-callback-url]

Para servidores MCP con OAuth habilitado, la URL de callback de LibreChat es:

```text
${DOMAIN_SERVER}/api/mcp/<server-name>/oauth/callback
```

`<server-name>` es la clave utilizada bajo `mcpServers` en `librechat.yaml` o el nombre del servidor creado en la interfaz de usuario de configuración de MCP. Por ejemplo, un servidor llamado `salesforce` con `DOMAIN_SERVER=https://chat.example.com` utiliza `https://chat.example.com/api/mcp/salesforce/oauth/callback`.

Registre esta URL de callback exacta con el proveedor de OAuth. Las instalaciones locales de Docker generalmente usan `http://localhost:3080` como URL base.

### En el área de chat [#in-chat-area]

![El catálogo de MCP Servers abierto desde la paleta del compositor, mostrando el estado de conexión de cada servidor](/images/mcp/mcp_servers_catalog.png)

LibreChat muestra los servidores MCP configurados directamente en el área de chat cuando se utilizan endpoints tradicionales (OpenAI, Anthropic, Google, Bedrock, etc.):

- Seleccione primero cualquier endpoint que no sea de agente y un modelo compatible con herramientas
- Los servidores MCP aparecen en la sección **MCP Servers** de la [paleta **+** del compositor](/docs/features/composer#turn-on-tools-skills-and-mcp-servers), y cada servidor seleccionado se muestra como una ficha (chip) en el compositor.
- Cuando se selecciona, todas las herramientas de ese servidor pasan a estar disponibles para su modelo actual
- Acceso rápido a herramientas MCP sin necesidad de crear un agente, permitiendo el uso de múltiples servidores a la vez

Para mantener un servidor MCP fuera de la selección regular de chat, establezca [`chatMenu: false`](/docs/configuration/librechat_yaml/object_structure/mcp_servers#chatmenu) en su configuración:

```yaml
mcpServers:
  internal-tools:
    command: npx
    args: ['-y', 'internal-mcp-server']
    chatMenu: false # Not selectable in regular chat
```

Esta configuración se aplica tanto en las solicitudes de chat como en el selector, por lo que una selección guardada obsoleta no puede seguir utilizando un servidor oculto. Esto no elimina el servidor de los Agents guardados ni de un Model Specs que lo asigne explícitamente. LibreChat también omite de la ruta de solicitud y del selector de chat regular aquellos servidores a los que un usuario solo puede acceder a través de un Agent autorizado.

### Con Agentes [#with-agents]

Los servidores MCP se integran perfectamente con los Agents de LibreChat:

1. Crear o editar un agente
2. Abre **Add tools** en el Agent Builder y selecciona **MCP**
3. Seleccione un servidor MCP; cada servidor aparece como una única entrada de catálogo
4. Expanda el servidor seleccionado para habilitar o deshabilitar herramientas individuales
5. Guarda tu agente

![Herramientas MCP en el Generador de Agentes](/images/mcp/mcp_ui_agent.png)

Esta organización de nivel superior mantiene la interfaz manejable; incluso los servidores con más de 20 herramientas (como Spotify) aparecen como entradas únicas que pueden expandirse para un control granular.

### Configuración básica [#basic-configuration]

Agregue servidores MCP a su archivo `librechat.yaml` manualmente:

```yaml
mcpServers:
  # ClickHouse Cloud
  clickhouse-cloud:
    type: streamable-http
    url: https://mcp.clickhouse.cloud/mcp

  # File system access
  filesystem:
    command: npx
    args:
      - -y
      - '@modelcontextprotocol/server-filesystem'
      - /path/to/your/documents

  # Web browser automation
  puppeteer:
    command: npx
    args:
      - -y
      - '@modelcontextprotocol/server-puppeteer'

  # Production-ready cloud service
  business-api:
    type: streamable-http
    url: https://api.yourbusiness.com/mcp
    headers:
      X-User-ID: '{{LIBRECHAT_USER_ID}}'
      Authorization: 'Bearer ${API_TOKEN}'
    timeout: 30000
    serverInstructions: true
```

### Agregar servidores MCP en la UI [#adding-mcp-servers-in-the-ui]

También puede agregar y configurar servidores MCP directamente desde la interfaz de LibreChat sin necesidad de editar archivos de configuración ni reiniciar el servidor.

#### Paso 1: Abrir el panel de configuración de MCP [#step-1-open-the-mcp-settings-panel]

Navega al panel de **MCP Settings** desde la barra lateral derecha. Verás cualquier servidor MCP existente listado aquí, junto con un botón **+** para añadir nuevos.

![Panel de configuración de MCP](/images/mcp/mcp_ui_settings_panel.png)

#### Paso 2: Completar los detalles del servidor [#step-2-fill-out-server-details]

Presiona el botón **+** y completa el nombre de tu servidor MCP, descripción, URL, tipo de transporte y método de autenticación, luego haz clic en **Create**.

![Cuadro de diálogo Agregar servidor MCP](/images/mcp/mcp_ui_configure.png)

Su nuevo servidor aparecerá en el panel de MCP Settings con una notificación de confirmación.

![MCP Server Created Successfully](/images/mcp/mcp_ui_success_registered.png)

#### Paso 3: Comprobar el estado de la conexión y autenticarse [#step-3-check-connection-status-and-authenticate]

Revise el [indicador de estado de conexión](#connection-status-indicators) para su nuevo servidor. Si el servidor requiere autenticación OAuth, el estado aparecerá como desconectado. Seleccione el servidor MCP en la paleta **+** del compositor para iniciar el flujo de autenticación.

![Estado de la conexión - Desconectado](/images/mcp/mcp_ui_unconnected.png)

Una vez iniciado, el indicador de estado se actualizará para mostrar que la autenticación está en curso.

![Estado de la conexión - Autenticando](/images/mcp/mcp_ui_authenticating.png)

#### Paso 4: Continuar con OAuth [#step-4-continue-with-oauth]

LibreChat presenta un aviso de confirmación de **Connect**. Revisa el destino y selecciona **Continue with OAuth** para abrir la página de autorización del proveedor en una nueva pestaña del navegador. Completa el flujo de inicio de sesión y consentimiento del proveedor allí.

Si un flujo iniciado en este navegador está pendiente, LibreChat mantiene ese servidor en un estado de autorización/conexión incluso si el estado de conexión en caché todavía indica **Connected**. El aviso no debería cerrarse simplemente porque un estado antiguo informe una autorización duradera; el éxito terminal, el fallo, el tiempo de espera o la cancelación finalizan el flujo pendiente. Un flujo iniciado en otra pestaña o navegador no tiene un estado pendiente local en esta vista.

![OAuth Continue Prompt](/images/mcp/mcp_ui_callback_confirm.png)

#### Paso 5: Autenticación exitosa [#step-5-authentication-successful]

Después de autenticarte, verás una confirmación de éxito. Esta ventana se cerrará automáticamente y te redirigirá de vuelta a LibreChat.

![Autenticación exitosa](/images/mcp/mcp_ui_success_redirect.png)

#### Paso 6: Servidor listo para su uso [#step-6-server-ready-for-use]

LibreChat reconoce la autenticación exitosa y selecciona automáticamente el servidor MCP para su uso dentro de su conversación. El servidor ahora muestra un indicador de estado conectado y aparece como un chip seleccionado en el compositor.

![Servidor MCP autenticado y seleccionado automáticamente](/images/mcp/mcp_ui_done.png)

Su nuevo servidor MCP también está disponible en el Agent Builder, donde puede añadir sus herramientas a cualquier agente y personalizar qué subconjunto de herramientas está permitido.

![MCP Server disponible en el Generador de agentes](/images/mcp/mcp_ui_agent.png)

#### Variables de credenciales para servidores creados en la UI [#credential-variables-for-ui-created-servers]

Al agregar un servidor MCP a través de la interfaz de usuario, puede requerir que los usuarios proporcionen sus propias claves de API. En la sección Authentication del cuadro de diálogo MCP Server Builder, seleccione "API Key" y marque **"User provides key"**. Elija el formato de encabezado (Bearer, Basic o Custom) y guarde el servidor.

Detrás de escena, LibreChat crea una entrada `customUserVars` vinculada al destino llamada `MCP_API_KEY_<hash>` y configura el encabezado de autenticación correspondiente. El nombre se gestiona automáticamente; los usuarios siguen ingresando su clave en el cuadro de diálogo de selección de herramientas MCP o en el panel de configuración de MCP. Los servidores existentes pueden conservar el nombre heredado `MCP_API_KEY` mientras su límite de solicitud permanezca sin cambios. Esto utiliza la misma interfaz de usuario de entrada de claves que las [`customUserVars` definidas en YAML](#user-provided-credentials).

Cambiar la URL (incluyendo la ruta o consulta), proxy, transporte, formato de autorización, encabezado de autenticación personalizado o cliente/destino OAuth configurado de un servidor creado en la interfaz de usuario requiere que cada usuario ingrese una clave para el nuevo límite. Las claves guardadas antiguas no se reenvían a ese destino de reemplazo. Las ediciones cosméticas, las URLs normalizadas equivalentes y las ediciones de URL de salida que solo afectan a fragmentos conservan la clave existente. Los servidores compartidos solo pueden resolver variables de credenciales declaradas por su configuración actual, por lo que un editor no puede hacer referencia a un nombre generado anteriormente para recuperar una clave previa. No se necesita una migración masiva de credenciales. Actualice **cada réplica de API**, incluidas las réplicas que atienden solicitudes de edición de servidor, antes de confiar en esta protección; un escritor más antiguo aún puede recrear una configuración sin límites.

Cuando se configura una clave de API de administrador o de usuario, LibreChat trata el servidor como autenticado mediante clave de API y omite la detección automática de OAuth. Una configuración explícita de OAuth sigue teniendo prioridad. Si un servidor con clave de API creada desde la interfaz de usuario fue guardado por una versión anterior de LibreChat y permanece bloqueado en **OAuth Required**, edite y guarde el servidor una vez para que sus metadatos de conexión almacenados se actualicen.

<Callout type="warning">
Por seguridad, los servidores MCP creados desde la interfaz de usuario (con origen en la base de datos) **solo** pueden resolver marcadores de posición `customUserVars` (`{{VAR_NAME}}`). Las variables de entorno del lado del servidor (`${ENV_VAR}`), los campos del perfil de usuario (`{{LIBRECHAT_USER_*}}`) y los tokens OIDC (`{{LIBRECHAT_OPENID_*}}`) están bloqueados intencionalmente para evitar el acceso no autorizado a secretos del servidor o a los datos de otros usuarios. Para obtener compatibilidad total con marcadores de posición, configure el servidor en `librechat.yaml` en su lugar.
</Callout>

## Gestión de servidores MCP [#mcp-server-management]

LibreChat proporciona herramientas integrales para gestionar conexiones de servidores MCP con seguimiento del estado de conexión y soporte para autenticación e inicialización OAuth en la interfaz de usuario.

### Indicadores de estado de conexión [#connection-status-indicators]

LibreChat muestra iconos de estado dinámicos que indican el estado actual de cada servidor MCP en la paleta **+** del compositor y en el panel de configuración:

![Iconos de estado del servidor MCP](/images/mcp/mcp_server_status_icons.png)

**Tipos de estado:**

- **Conectado** (engranaje verde): El servidor está conectado y tiene customUserVars configurables
- **OAuth Required** (llave ámbar): El servidor requiere autenticación OAuth
- **Desconectado** (enchufe naranja): La conexión con el servidor falló o se perdió
- **Inicializando** (cargador azul): El servidor se está iniciando o reconectando
- **Error** (triángulo rojo): El servidor encontró un error
- **Cancelando** (x roja): El flujo de OAuth está siendo cancelado

### Cancelar OAuth desde el diálogo de herramientas del agente [#cancelling-oauth-from-the-agent-tool-dialog]

En **Agent Builder → Tool Library → MCP server configuration**, **Connect** se convierte en una acción **Cancel** habilitada mientras el administrador de servidores compartido informa de un flujo OAuth cancelable. Esto incluye un flujo pendiente descubierto desde otro panel de LibreChat. Elija **Cancel** para detener ese flujo, cerrar el aviso de OAuth local y borrar su selección automática de herramientas pendiente. Un resultado de conexión tardío después de la cancelación no adjunta automáticamente las herramientas en este diálogo. Puede elegir **Connect** de nuevo para un nuevo intento. La inicialización que no es cancelable sigue mostrando su estado de ocupado deshabilitado en lugar de una acción de cancelación.

Los fallos de inicialización ahora distinguen entre un servidor inalcanzable, la falta de `customUserVars`, una conexión OAuth que debe ser autenticada de nuevo y un fallo de inicialización genérico. Utilice las variables faltantes nombradas o la acción de reautenticación en el mensaje antes de volver a intentarlo; ya no es necesario eliminar y volver a añadir el servidor para estos casos.

Las cargas de catálogo pasivo consolidan los intentos de descubrimiento de OAuth y retroceden progresivamente tras los fallos, de modo que una integración desconectada no reintente el descubrimiento en cada solicitud. Los cambios de credenciales están protegidos por generación entre réplicas, lo que evita que un resultado de descubrimiento antiguo sobrescriba una autenticación más reciente. Los operadores pueden ajustar la política de recuperación limitada en [`mcpSettings.catalogRecovery`](/docs/configuration/librechat_yaml/object_structure/mcp_settings#catalogrecovery); los valores predeterminados son adecuados para la mayoría de las implementaciones.

Si un Agent espera explícitamente herramientas MCP pero ninguna puede resolverse al inicio de la ejecución, LibreChat falla la ejecución con una guía de conexión y acceso en lugar de ejecutarse silenciosamente sin esas herramientas.

Los servidores MCP que emiten `notifications/tools/list_changed` pueden actualizar su catálogo de herramientas sin necesidad de reiniciar LibreChat. LibreChat obtiene la lista actual desde la conexión activa, publica las herramientas añadidas y deja de anunciar las herramientas que el servidor eliminó. Las reconexiones también sincronizan el catálogo antes de que la conexión sea considerada como lista. Las actualizaciones de instantáneas gestionadas y la detección de servidores en frío comparten una puerta de tres operaciones a nivel de proceso. Una vez admitida, cada operación permanece limitada por su lista de herramientas o por el plazo de detección por servidor, incluyendo cualquier `initTimeout` más corto, por lo que el trabajo lento del catálogo no puede ocupar un espacio indefinidamente.

Para servidores HTTP transmitibles (Streamable), una reconexión puede devolver brevemente un `409` HTTP cuando el servidor aún mantiene una transmisión SSE independiente obsoleta para la sesión anterior. LibreChat trata esto como algo transitorio, cierra la sesión obsoleta y reconstruye la conexión automáticamente; no se requiere ninguna acción por parte del operador cuando la recuperación tiene éxito. Si la conexión reconstruida también falla, LibreChat continúa mostrando el error de conexión subyacente.

LibreChat clasifica las respuestas HTTP transmitibles (Streamable) a partir del tipo de medio `Content-Type` analizado en lugar de una coincidencia de subcadena. Los parámetros no pueden hacer que una respuesta que no sea SSE parezca ser `text/event-stream`, por lo que los errores de tamaño de respuesta continúan a través de la ruta de manejo correcta de SSE o no SSE.

### Visibilidad del panel de configuración de MCP [#mcp-settings-panel-visibility]

El panel de configuración de MCP aparece en la barra lateral derecha cuando LibreChat detecta servidores MCP que podrían requerir la intervención del usuario durante su inicialización. El panel será visible cuando cualquier servidor configurado cumpla con uno de estos criterios:

- **Variables de usuario personalizadas**: El servidor tiene `customUserVars` definidas, las cuales pueden contener credenciales proporcionadas por el usuario
- **Autenticación OAuth**: Se detecta que el servidor requiere autenticación OAuth durante el inicio
- **Inicialización manual**: El servidor tiene configurado `startup: false`, lo que requiere una inicialización manual

## Características específicas de LibreChat [#librechat-specific-features]

La implementación de MCP de LibreChat está diseñada para entornos multiusuario del mundo real altamente configurables.

### Conexiones específicas de usuario [#user-specific-connections]

- Cada usuario obtiene su propia conexión aislada a los servidores MCP
- Se respetan la autenticación de usuario y los permisos.
- Los datos personales y el contexto permanecen privados

### Compartir servidores MCP [#sharing-mcp-servers]

Los servidores MCP participan en el sistema de [control de acceso granular](/docs/features/access_control) de LibreChat. Además de los servidores definidos en `librechat.yaml` (que son gestionados por administradores y se rigen por los permisos de la función [`interface.mcpServers`](/docs/configuration/librechat_yaml/object_structure/interface#mcpservers)), los servidores MCP creados por los usuarios tienen su propia ACL y pueden compartirse con **usuarios**, **grupos**, **roles** específicos o **públicamente**, con nivel de Lector, Editor o Propietario.

Las flags de características `USE`, `CREATE`, `SHARE` y `SHARE_PUBLIC` bajo `interface.mcpServers` controlan quién tiene permitido crear y compartir servidores MCP en general. Consulta [Access Control](/docs/features/access_control) para ver cómo se componen las capas de permisos.

### Contexto de usuario dinámico [#dynamic-user-context]

Los servidores MCP pueden acceder a la información del usuario a través de marcadores de posición en **URLs y encabezados** (para transportes SSE y HTTP transmitibles):

```yaml
mcpServers:
  user-api:
    type: streamable-http
    url: https://api.example.com/users/{{LIBRECHAT_USER_USERNAME}}/mcp
    headers:
      X-User-ID: '{{LIBRECHAT_USER_ID}}'
      X-User-Email: '{{LIBRECHAT_USER_EMAIL}}'
      X-User-Role: '{{LIBRECHAT_USER_ROLE}}'
      Authorization: 'Bearer ${API_TOKEN}'
```

Los marcadores de posición disponibles incluyen:

- `{{LIBRECHAT_USER_ID}}` - Identificador único de usuario
- `{{LIBRECHAT_USER_EMAIL}}` - Dirección de correo electrónico del usuario
- `{{LIBRECHAT_USER_ROLE}}` - Rol de usuario (admin, user, etc.)
- `{{LIBRECHAT_USER_USERNAME}}` - Nombre de usuario
- Y muchos más (consulta [Configuración de servidores MCP](/docs/configuration/librechat_yaml/object_structure/mcp_servers#headers) para ver la lista completa)

Los servidores MCP definidos en YAML también pueden usar marcadores de posición `{{LIBRECHAT_OPENID_*}}`, `{{LIBRECHAT_GRAPH_*}}` y `{{LIBRECHAT_BODY_*}}`. Los valores de `{{LIBRECHAT_BODY_*}}` tienen un alcance de solicitud (request-scoped), por lo que LibreChat crea conexiones para la ejecución activa, las reutiliza en las llamadas a herramientas durante esa ejecución y las limpia cuando finaliza la solicitud. Los servidores con alcance de solicitud se excluyen de la caché persistente de herramientas para que los encabezados y URLs específicos de la solicitud no se reutilicen fuera de la ejecución activa. Debido a que su lista de herramientas no puede resolverse antes de que exista una solicitud de chat, el Agent Builder expone una selección de herramientas en tiempo de ejecución para el servidor completo y resuelve sus herramientas en tiempo de ejecución. Completar OAuth almacena la autorización pero pospone la conexión hasta que la primera ejecución proporcione el contexto de la solicitud. Los marcadores de posición de usuario, OpenID y Graph tienen un alcance de usuario (user-scoped); los transportes HTTP actualizan sus encabezados resueltos antes de cada llamada a herramienta sin requerir una reconexión por sí mismos.

Los operadores de confianza pueden usar `Authorization: 'Bearer {{LIBRECHAT_OPENID_ACCESS_TOKEN}}'` en un servidor remoto definido en YAML para transmitir el token de acceso OpenID en vivo del usuario. La autenticación explícita mediante OAuth de MCP, el intercambio en nombre de (on-behalf-of) y la clave de API del administrador tienen prioridad. Después de un `401` o `403`, LibreChat puede actualizar la conexión una vez, pero nunca vuelve a intentar automáticamente la llamada a la herramienta rechazada. Consulta la [referencia de marcadores de posición del servidor MCP](/docs/configuration/librechat_yaml/object_structure/mcp_servers#headers) para obtener orientación sobre la configuración y la seguridad.

`{{LIBRECHAT_GRAPH_ACCESS_TOKEN}}` intercambia el token de acceso OpenID reutilizable del usuario a través del flujo on-behalf-of de Microsoft. [`GRAPH_API_SCOPES`](/docs/configuration/dotenv#microsoft-graph-api--entra-id-integration) establece los ámbitos solicitados separados por espacios y tiene como valor predeterminado `https://graph.microsoft.com/.default`. Esto es independiente de `OPENID_GRAPH_SCOPES`, que configura la búsqueda de personas y grupos.

El marcador de posición `{{LIBRECHAT_BODY_PARENTMESSAGEID}}` se completa para chats de agentes nativos, llamadas a la API de agentes compatibles con OpenAI y ejecuciones de Assistants heredadas. Open Responses no tiene una identidad de mensaje principal equivalente y falla de forma cerrada cuando un servidor MCP requiere ese valor. Consulta la [referencia de marcadores de posición del servidor MCP](/docs/configuration/librechat_yaml/object_structure/mcp_servers#headers).

### Instrucciones del servidor [#server-instructions]

`serverInstructions` es una funcionalidad de LibreChat que añade dinámicamente instrucciones configuradas cuando se selecciona cualquier herramienta de ese servidor MCP:

```yaml
mcpServers:
  filesystem:
    command: npx
    args: ['-y', '@modelcontextprotocol/server-filesystem', '/docs']
    serverInstructions: |
      When accessing files:
      - Always check file permissions first
      - Use absolute paths for reliability
      - Handle errors gracefully
```

Opciones:

- `true`: Usar las instrucciones anunciadas por el servidor cuando estén disponibles
- `false`: Deshabilitar instrucciones
- `string`: Utilice las instrucciones personalizadas literalmente (mostradas arriba)

LibreChat conserva esta declaración configurada por separado de las instrucciones obtenidas durante la inspección del servidor. Por lo tanto, una declaración `true` permanece habilitada a través de la inspección y las recargas del registro en caché, mientras que una cadena personalizada sigue siendo autoritativa.

### Configuración de tiempo de espera [#timeout-configuration]

Para operaciones MCP de larga duración, configure los tiempos de espera (timeouts) adecuados tanto para la inicialización como para las operaciones de herramientas.

```yaml
mcpServers:
  data-processor:
    type: streamable-http
    url: https://api.example.com/mcp
    initTimeout: 15000 # 15 seconds for server initialization
    timeout: 60000 # 60 seconds for tool operations
```

**Nota**: Si las operaciones siguen interrumpiéndose, verifica la configuración de tu proxy (por ejemplo, nginx, traefik, etc.), ya que podría estar cerrando las conexiones prematuramente debido a los tiempos de espera predeterminados.

Cuando un usuario presiona **Stop** durante una llamada a una herramienta de agente en primer plano, LibreChat reenvía la señal de cancelación de ejecución a MCP. Para servidores HTTP transmitibles (Streamable), el SDK de MCP envía `notifications/cancelled`; el servidor debe respetar esa notificación para detener su propio trabajo. Las llamadas en segundo plano desconectadas mantienen intencionalmente un ciclo de vida separado y no se cancelan con el turno en primer plano.

### Credenciales proporcionadas por el usuario [#user-provided-credentials]

Puede permitir que los usuarios proporcionen sus propias credenciales para los servidores MCP a través de `customUserVars`. Esto permite una autenticación segura y específica para cada usuario sin necesidad de almacenar credenciales en los archivos de configuración.

```yaml
mcpServers:
  my-api-server:
    type: streamable-http
    url: 'https://api.example.com/mcp'
    headers:
      X-Auth-Token: '{{MY_API_KEY}}' # Uses the user-provided value
    customUserVars:
      MY_API_KEY:
        title: 'API Key'
        description: "Enter your personal API key from <a href='https://example.com/keys' target='_blank'>your account settings</a>"
```

Los usuarios pueden configurar estas credenciales:

- **Desde el área de chat**: Elija **Configure** en la fila de un servidor MCP configurable en la paleta **+** del compositor
- **Desde el panel de configuración de MCP**: Acceda a "MCP Settings" en el panel derecho para gestionar las credenciales de todos los servidores configurados.

#### Reinicialización de servidores MCP con credenciales de usuario [#reinitializing-mcp-servers-with-user-credentials]

Para los servidores MCP que requieren credenciales específicas del usuario antes de poder ser utilizados (por ejemplo, `PAT_TOKEN` en el [servidor MCP oficial de GitHub](https://github.com/github/github-mcp-server)), LibreChat permite a los usuarios proporcionar estas credenciales y luego reinicializar el servidor MCP desde la interfaz de usuario sin necesidad de reiniciar toda la aplicación:

1. Cuando seleccionas un MCP que utiliza `customUserVars`, podrás **Guardar** o **Revocar** el valor de una `customUserVar` para el servidor MCP seleccionado desde el Panel MCP.
2. Después de guardar un valor para una `customUserVar`, haga clic en el botón de reinicialización (un icono con flechas circulares junto a cada nombre de servidor en el MCP Panel).
3. LibreChat intentará conectarse al servidor utilizando sus credenciales proporcionadas y le notificará mediante una notificación emergente si el proceso de reinicialización ha tenido éxito o ha fallado.

> _Consejo: Si sabe que un servidor requerirá credenciales que no están disponibles en el primer inicio, puede añadir `startup: false` a su configuración. Esto le indica a LibreChat que no intente conectarse a ese servidor hasta que sea reinicializado manualmente en la interfaz de usuario._

**Ejemplo:**

```yaml
mcpServers:
  github-mcp:
    type: streamable-http
    url: 'https://api.githubcopilot.com/mcp/'
    headers:
      Authorization: '{{PAT_TOKEN}}'
    customUserVars:
      PAT_TOKEN:
        title: 'GitHub PAT Token'
        description: 'GitHub Personal Access Token'
    startup: false
```

### Autenticación OAuth [#oauth-authentication]

LibreChat admite la autenticación OAuth para servidores MCP, siguiendo la recomendación de Anthropic para conexiones MCP seguras. OAuth proporciona una forma estandarizada y segura de autenticarse sin almacenar credenciales de larga duración.

#### Flujos de OAuth compatibles [#supported-oauth-flows]

Los servidores MCP de LibreChat admiten OAuth 2.0 con:

- **Authorization Code Flow with PKCE**: Recomendado para una seguridad máxima
- **Descubrimiento de cliente**: Registro automático de cliente cuando es compatible con el proveedor OAuth
- **Refresh Tokens**: Renovación automática de tokens cuando esté disponible
- **Detección del endpoint de tokens**: Los clientes preconfigurados pueden detectar si el proveedor espera las credenciales del cliente en el cuerpo de la solicitud POST o en un encabezado de autorización HTTP Basic

En el MCP Builder, **Token Exchange Method** ofrece **Auto**, **Default (POST request)** y **Basic authorization header**. Auto deja el método sin configurar para que LibreChat pueda utilizar los metadatos del proveedor de confianza, recurriendo a la autenticación Basic cuando el proveedor no anuncia un método.

#### Ejemplos de configuración [#configuration-examples]

```yaml
mcpServers:
  # Public remote MCP server for PayPal, uses OAuth Client Discovery
  # ❌ Refresh Tokens: you may need to re-authenticate periodically
  # More info: https://developer.paypal.com/tools/mcp-server/
  paypal:
    type: 'sse'
    initTimeout: 150000 # higher timeout to allow for initial authentication
    url: 'https://mcp.paypal.com/sse'

  # Example self-hosted remote MCP server for Spotify, uses OAuth Client Discovery
  # ✅ Refresh Tokens: refreshes token for authentication automatically
  # Hosted on Cloudflare Workers, more info: https://github.com/LibreChat-AI/spotify-mcp
  spotify:
    type: 'streamable-http'
    initTimeout: 150000
    url: 'https://mcp-spotify-oauth-example.account.workers.dev/mcp'
```

#### Flujo de autenticación OAuth [#oauth-authentication-flow]

Cuando configura por primera vez un servidor MCP habilitado para OAuth:

1. **Conexión inicial**: LibreChat intenta conectarse al servidor MCP
2. **Autenticación requerida**: Si no existe un token válido, verás un estado de autenticación OAuth para ese servidor en la paleta **+** del compositor.
3. **Iniciar sesión**: Seleccione el servidor para comenzar el flujo OAuth
4. **Continuar o usar otro dispositivo**: Continúe en el navegador actual, copie el enlace de autorización o muestre un código QR para abrirlo en otro dispositivo
5. **Redirección del navegador**: Complete la autenticación con el proveedor OAuth
6. **Gestión de retorno**: LibreChat procesa automáticamente la devolución de llamada (callback) de OAuth una vez que te has autenticado
7. **Almacenamiento de tokens**: LibreChat almacena de forma segura los tokens para su uso futuro
8. **Conexión establecida**: Una vez que te hayas autenticado, el servidor MCP estará conectado y podrás usarlo en tu chat

#### URL de devolución de llamada OAuth [#oauth-callback-url-1]

Cuando un servidor MCP utiliza OAuth, LibreChat expone un endpoint de callback al que el proveedor de OAuth redirige después de una autorización exitosa.

La URL de callback debe seguir este formato:

`${baseUrl}/api/mcp/${serverName}/oauth/callback`

Donde `${serverName}` es la clave del servidor MCP definida en su configuración `librechat.yaml`. LibreChat gestiona la redirección en este endpoint, completa el intercambio de tokens y asocia las credenciales con el servidor MCP correspondiente.

<Callout type="info" title="Ejemplo de URL de devolución de llamada OAuth">
Dada la siguiente configuración del servidor MCP:

```yaml
mcpServers:
  # Example self-hosted remote MCP server for Spotify, uses OAuth Client Discovery
  # ✅ Refresh Tokens: refreshes token for authentication automatically
  # Hosted on Cloudflare Workers, more info: https://github.com/LibreChat-AI/spotify-mcp
  spotify:
    type: 'streamable-http'
    initTimeout: 150000
    url: 'https://mcp-spotify-oauth-example.account.workers.dev/mcp'
```

La URL de callback sería `${baseUrl}/api/mcp/spotify/oauth/callback`.

</Callout>

Nota:

- La URL de callback debe registrarse exactamente con el proveedor de OAuth para que el flujo funcione.
- Otras rutas como `/api/oauth/callback` o `/api/oauth/openid/callback` no son válidas para los flujos de OAuth de MCP.

#### Gestión de tokens [#token-management]

LibreChat gestiona los tokens OAuth de forma inteligente:

- **Almacenamiento seguro**: Los tokens se cifran y almacenan de forma segura
- **Actualización automática**: Cuando los tokens de actualización están disponibles, LibreChat renueva automáticamente los tokens de acceso caducados
- **Recuperación silenciosa 401**: Si una conexión MCP OAuth recibe un rechazo de autenticación a mitad de la sesión, LibreChat coordina un intento limitado de actualización y reconexión por usuario y servidor. Los llamadores concurrentes comparten ese resultado de recuperación antes de que LibreChat muestre un nuevo aviso de autenticación.
- **Gestión de sesiones**: Cada usuario mantiene sus propias sesiones OAuth para entornos multiusuario

Si un flujo de Agent guardado se recarga o reanuda mientras una solicitud de autorización de MCP sigue pendiente, LibreChat reconstruye dicha solicitud a partir del estado de generación persistente. Las solicitudes completadas, canceladas, fallidas o caducadas no se restauran.

Los clientes y tokens de OAuth almacenados están vinculados a la URL del servidor MCP y a la configuración del cliente/endpoint de OAuth. Cambiar esa configuración requiere que los usuarios se autentiquen de nuevo. Al editar un servidor creado desde la interfaz de usuario que conserva un `client_secret` almacenado, vuelva a ingresar el secreto al cambiar un campo de vinculación como la URL del servidor, el ID de cliente, la URL de autorización, la URL de token o el método de autenticación de token.

En implementaciones escaladas horizontalmente, el estado del flujo OAuth y la disponibilidad del token vinculado pueden reconciliarse entre los pods de LibreChat. La interfaz de usuario informa que un servidor está listo solo después de que la inicialización posterior a OAuth tiene éxito, incluso cuando la devolución de llamada (callback) y la consulta de estado llegan a pods diferentes. Las devoluciones de llamada de intentos reemplazados son rechazadas.

Cuando Redis está habilitado, las generaciones de catálogos MCP a nivel de aplicación y las revisiones de publicación se coordinan entre las réplicas. Las implementaciones de Redis Cluster utilizan claves de catálogo y actualizaciones seguras para los slots, por lo que la sincronización de inicio y las actualizaciones de `tools/list_changed` no requieren un diseño de Redis de nodo único.

Se solicitará a cada usuario que se autentique con su propio inicio de sesión OAuth cuando utilice por primera vez un servidor MCP habilitado para OAuth. Esto garantiza que los detalles de conexión y autenticación sean únicos para cada usuario, manteniendo la seguridad y la privacidad en entornos multiusuario.

#### Temporización de OAuth [#oauth-timing]

La finalización de OAuth de MCP utiliza su propio tiempo de espera configurado en el servidor en lugar de reutilizar el `initTimeout` del servidor MCP. De forma predeterminada, LibreChat espera hasta 10 minutos a que el usuario complete el OAuth de MCP y mantiene el estado del flujo durante 15 minutos.

Utilice estas variables de entorno cuando un proveedor de OAuth o un flujo de trabajo de usuario necesite más tiempo:

```bash filename=".env"
MCP_OAUTH_HANDLING_TIMEOUT=600000
MCP_OAUTH_FLOW_TTL=900000
```

`MCP_OAUTH_FLOW_TTL` se ajusta para que dure más que `MCP_OAUTH_HANDLING_TIMEOUT`, de modo que las devoluciones de llamada cercanas al límite de tiempo aún puedan encontrar su estado de flujo. La ventana de sondeo de la tarjeta de servidor MCP sigue el tiempo de espera de manejo configurado.

![Flujo de autenticación OAuth específico del usuario](/images/agents/mcp_oauth_flow.png)

> Nota: Los tokens que se muestran durante el inicio de la aplicación son solo para la inicialización a nivel de aplicación y no se utilizan para las conexiones de usuarios individuales.

Ejemplo de actualización automática de tokens:

```bash
[MCP][spotify] Access token missing
[MCP][spotify] Attempting to refresh token
[MCP][spotify] Successfully refreshed and stored OAuth tokens
[MCP][spotify] ✓ Initialized
```

#### Mejores prácticas [#best-practices]

1. **Use OAuth when available**: Prefiera OAuth en lugar de claves de API para una mayor seguridad
2. **Configurar tiempos de espera adecuados**: Utilice `MCP_OAUTH_HANDLING_TIMEOUT` y `MCP_OAUTH_FLOW_TTL` para las ventanas de finalización de OAuth; utilice `initTimeout` para la inicialización del servidor
3. **Monitorear la expiración de tokens**: Revisar los registros en busca de problemas de autenticación
4. **Plan para la reautenticación**: Algunos proveedores no admiten tokens de actualización

## Transportes del servidor [#server-transports]

Los servidores MCP pueden configurarse para utilizar diferentes mecanismos de transporte:

**Servidores STDIO**

- Funciona bien para entornos locales de un solo usuario
- No es escalable para implementaciones remotas o en la nube
- El SDK de MCP incluido limita cada mensaje STDIO individual a 10 MB. Un resultado único mayor cierra el transporte con un error; este límite es independiente del tamaño total de una sesión o flujo.

**Servidores de eventos enviados por el servidor (SSE)**

- Mecanismo de transporte remoto, pero no recomendado para entornos de producción

**Servidores HTTP transmitibles**

- Utiliza HTTP POST para enviar mensajes y admite respuestas en streaming
- Funciona como un proceso independiente que puede manejar múltiples conexiones de cliente
- Admite tanto solicitudes básicas como streaming a través de Server-Sent Events (SSE)
- Alternativa de mayor rendimiento al transporte heredado HTTP+SSE
- Admite configuraciones de servidor multiusuario adecuadas

**Para entornos de producción**, solo se recomiendan los servidores MCP con [transporte "Streamable HTTP"](https://modelcontextprotocol.io/specification/draft/basic/transports/streamable-http). A diferencia de SSE, que mantiene conexiones de larga duración, Streamable HTTP ofrece opciones sin estado que son más adecuadas para implementaciones escalables y multiusuario.
