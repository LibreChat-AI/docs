# Panneau d'administration LibreChat [#librechat-admin-panel]

Le **Panneau d'administration LibreChat** est une interface de gestion autonome basée sur navigateur pour LibreChat. Il se connecte à la même base de données que LibreChat lui-même et fournit une interface graphique pour les tâches administratives qui alimentent le [contrôle d'accès granulaire](/docs/features/access_control) : administration des utilisateurs et des groupes, gestion des rôles, remplacements de configuration étendus aux rôles ou aux groupes, et octroi de capacités au niveau du système.

<Callout type="info" title="Statut : Aperçu">
  Le panneau d'administration est disponible pour les tests dès maintenant et constitue la future interface de gestion qui s'appuie sur les API d'administration introduites dans [LibreChat v0.8.5](/changelog/v0.8.5). Le code source, les problèmes et les versions se trouvent sur [github.com/ClickHouse/librechat-admin-panel](https://github.com/ClickHouse/librechat-admin-panel).
</Callout>

## Ce qu'il fait [#what-it-does]

Le panneau d'administration est un client léger : toutes les données résident dans la base de données de LibreChat, et chaque action passe par les endpoints versionnés `/api/admin/*` sur le serveur API de LibreChat. Il offre aux administrateurs un emplacement unique pour :

- **Gérer la configuration** : affichez et modifiez chaque paramètre de LibreChat via un formulaire dynamique basé sur un schéma. Les nouveaux champs ajoutés au schéma de configuration apparaissent automatiquement, sans nécessiter de nouvelle version du panneau d'administration.
- **Appliquer des remplacements par principal** : limitez les remplacements de configuration à des rôles ou des groupes spécifiques, avec une cascade basée sur la priorité qui détermine la valeur finale résolue que chaque utilisateur voit lors de la connexion.
- **Administrer les utilisateurs** : lister, rechercher et consulter chaque compte sur l'instance.
- **Gérer les groupes** : créer et supprimer des groupes, ajouter/supprimer des membres, et utiliser les groupes en tant que principaux de premier ordre dans les ACL et les remplacements (overrides).
- **Gérer les rôles** : créez des rôles personnalisés au-delà des rôles intégrés `USER` / `ADMIN`, modifiez leur matrice de permissions de fonctionnalités et attribuez des utilisateurs aux rôles.
- **Attribution de systèmes de droits** : déléguez des capacités d'administration (par ex. `manage:users`, `read:usage`, `manage:mcpservers`) à des utilisateurs, groupes ou rôles spécifiques sans leur accorder le statut d'administrateur complet.
- **Authentification** : connectez-vous avec un compte administrateur local LibreChat, ou via OpenID SSO / SAML / les fournisseurs OAuth pris en charge lorsque ceux-ci sont activés sur l'instance LibreChat.

Pour le modèle de permission sous-jacent (principaux, ACL de ressources, capacités et comment les couches se composent), consultez la page [Access Control](/docs/features/access_control).

## Architecture [#architecture]

```
┌──────────────────┐         ┌──────────────────┐         ┌──────────────┐
│  Admin Panel     │ ───────▶│  LibreChat API   │ ───────▶│   MongoDB    │
│  (Bun + Vite)    │  HTTPS  │  /api/admin/*    │         │  (shared DB) │
└──────────────────┘         └──────────────────┘         └──────────────┘
       │                             │
       │ OAuth/OIDC/SAML redirect    │ Verifies admin access
       └─────────────────────────────┘
```

Le panneau d'administration s'exécute en tant que service distinct ; il ne partage pas de processus avec LibreChat. Les capacités d'administration sont vérifiées du côté de LibreChat via l'autorisation système `access:admin` ou le rôle `SystemRoles.ADMIN`, de sorte que le panneau ne peut pas s'octroyer lui-même des privilèges qu'il ne devrait pas avoir.

La surface de l'API d'administration exposée par LibreChat est :

| Montage | Objectif |
| ----------------------------------------- | --------------------------------------------------------- |
| `POST /api/admin/login` &nbsp; `/oauth/*` | Points de terminaison d'authentification spécifiques à l'admin (local + SSO) |
| `GET /api/admin/verify`                   | Valide la session administrateur |
| `/api/admin/users`                        | Liste et recherche des utilisateurs |
| `/api/admin/groups`                       | CRUD des groupes + gestion des membres |
| `/api/admin/roles`                        | CRUD des rôles personnalisés + édition des permissions + gestion des membres |
| `/api/admin/grants`                       | Octrois de capacités système (assigner/révoquer/lister) |
| `/api/admin/config`                       | Configuration de base + remplacements par principal |

## Démarrage [#getting-started]

### Prérequis [#prerequisites]

- Une instance LibreChat en cours d'exécution sur la **v0.8.5 ou une version ultérieure** (les API d'administration ne sont pas disponibles dans les versions antérieures)
- Accès réseau depuis le conteneur/hôte admin-panel vers l'API LibreChat
- Un compte administrateur sur LibreChat : soit le premier utilisateur enregistré dans un déploiement mono-locataire non délimité (auto-admin), un utilisateur avec `role: 'ADMIN'` défini dans Mongo, ou un principal auquel la capacité `access:admin` a été accordée. Les déploiements délimités par locataire doivent provisionner leurs administrateurs via un flux administratif approuvé.

### Inclus avec LibreChat (recommandé) [#bundled-with-librechat-recommended]

Si vous exécutez LibreChat avec son [`docker-compose.yml`](https://github.com/LibreChat-AI/LibreChat/blob/main/docker-compose.yml) ou [`deploy-compose.yml`](https://github.com/LibreChat-AI/LibreChat/blob/main/deploy-compose.yml) officiel, le panneau d'administration est fourni en tant que service et démarre automatiquement avec LibreChat -- aucun déploiement séparé n'est nécessaire.

| Fichier Compose | URL du panneau d'administration | Comment il est servi |
| ------------------------------ | ------------------------ | ----------------------------------------------------------------- |
| `docker-compose.yml` (par défaut) | `http://localhost:3000`  | Publié sur un port hôte (`ADMIN_PANEL_PORT`, par défaut `3000`)     |
| `deploy-compose.yml`           | `http://admin.localhost` | Routé via le proxy inverse nginx inclus sur un sous-domaine     |

Définissez le secret de session du panneau dans le fichier `.env` de LibreChat avant de démarrer la stack ; les fichiers compose le transmettent en tant que `SESSION_SECRET` du panneau :

```bash filename=".env"
# Min 32 characters. Generate with: openssl rand -hex 32
ADMIN_PANEL_SESSION_SECRET=replace-with-a-32-char-random-string

# Optional: host port for the default docker-compose
# ADMIN_PANEL_PORT=3000

# Optional: set true when the panel is served over HTTPS
# ADMIN_PANEL_SESSION_COOKIE_SECURE=false
```

Les fichiers compose connectent automatiquement le reste : `API_SERVER_URL` pointe vers le service `api`, `VITE_API_BASE_URL` suit `DOMAIN_CLIENT` pour les redirections OAuth côté navigateur, et `ADMIN_PANEL_URL` est défini afin que LibreChat renvoie les administrateurs vers le panneau après une connexion SSO. Pour désactiver cette option, supprimez le service `admin-panel` ou protégez-le derrière une entrée [`profiles`](https://docs.docker.com/compose/how-tos/profiles/) de Compose.

<Callout type="info" title="admin.localhost sur un domaine réel">
  Les navigateurs modernes résolvent `*.localhost` (y compris `admin.localhost`) vers `127.0.0.1`, donc l'URL de deploy-compose fonctionne sans modification du fichier hosts. Pour un domaine réel, faites pointer un enregistrement DNS vers l'hôte, mettez à jour le `server_name` `admin.localhost` dans `client/nginx.conf`, et définissez `ADMIN_PANEL_URL` en conséquence.
</Callout>

### Standalone (déploiement séparé) [#standalone-separate-deployment]

Pour héberger le panneau d'administration séparément -- pointé vers une instance LibreChat s'exécutant ailleurs -- utilisez l'image publiée depuis GHCR :

```bash
# 1. Create an env file
cp .env.example .env

# 2. Edit .env and set at minimum:
#    SESSION_SECRET=<random string, min 32 characters>
#    VITE_API_BASE_URL=http://host.docker.internal:3080

# 3. Start it
docker compose up -d   # http://localhost:3000
docker compose down    # stop
```

`docker run` autonome :

```bash
docker run -p 3000:3000 \
  --add-host=host.docker.internal:host-gateway \
  -e SESSION_SECRET=replace-with-32-char-random-string \
  -e VITE_API_BASE_URL=http://host.docker.internal:3080 \
  ghcr.io/clickhouse/librechat-admin-panel:latest
```

<Callout type="warning" title="Mise en réseau Docker">
  À l'intérieur d'un conteneur, `localhost` fait référence au conteneur lui-même, et non à votre hôte. Lorsque LibreChat s'exécute sur le même hôte, pointez `VITE_API_BASE_URL` vers `http://host.docker.internal:3080` (Linux : ajoutez `--add-host=host.docker.internal:host-gateway`). En production, utilisez le nom DNS public/interne de votre API LibreChat.
</Callout>

### Exécuter localement pour le développement [#run-locally-for-development]

```bash
git clone https://github.com/ClickHouse/librechat-admin-panel.git
cd librechat-admin-panel
cp .env.example .env    # then edit
bun install
bun dev                 # http://localhost:3000
```

## Variables d'environnement [#environment-variables]

| Variable | Required | Default | Description |
| ------------------------------- | --------------------- | --------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `SESSION_SECRET` | **Oui** en production | Alternative de développement codée en dur lors de l'exécution de `bun dev` ; **aucune valeur par défaut** dans l'image Docker | Clé de chiffrement de session. Doit comporter au moins 32 caractères. |
| `VITE_API_BASE_URL` | **Oui** dans Docker | `http://localhost:3080` (développement local uniquement) | URL du serveur API de LibreChat vue par le navigateur, utilisée pour les redirections OAuth. |
| `API_SERVER_URL` | Non | Utilise `VITE_API_BASE_URL` par défaut | URL côté serveur pour les appels API de LibreChat. Utile lorsque le serveur du panneau d'administration accède à LibreChat via une URL différente de celle du navigateur (par ex. service Kubernetes interne vs nom d'hôte public). |
| `PORT` | Non | `3000` | Port sur lequel le panneau d'administration écoute. |
| `ADMIN_PANEL_SESSION_SECRET` | **Oui** | _non défini_ | Variable côté LibreChat mappée sur la `SESSION_SECRET` du panneau d'administration pour le service de panneau d'administration intégré. Générez une valeur unique d'au moins 32 caractères avant de démarrer le panneau. |
| `ADMIN_PANEL_PORT` | Non | `3000` | Port hôte exposé par le service de panneau d'administration intégré dans le `docker-compose.yml` par défaut. |
| `ADMIN_SSO_ONLY` | Non | `false` | Masque le formulaire e-mail/mot de passe, forçant une connexion SSO uniquement. |
| `ADMIN_SESSION_IDLE_TIMEOUT_MS` | Non | `1800000` (30 min) | Délai d'inactivité de la session en millisecondes. |
| `SESSION_COOKIE_SECURE` | Non | `true` en production | Indique si le cookie de session nécessite HTTPS. |
| `ADMIN_PANEL_METRICS_SECRET` | Non | _non défini_ | Jeton Bearer requis pour scraper le endpoint Prometheus `/metrics`. Le endpoint renvoie `401` lorsqu'il n'est pas défini ou en cas de non-concordance. |

Dans les piles Docker fournies avec LibreChat, le panneau d'administration s'exécute en tant que service `admin-panel`. Le fichier `docker-compose.yml` par défaut l'expose sur `ADMIN_PANEL_PORT` ; `deploy-compose.yml` le dirige via nginx sur `http://admin.localhost` et définit `ADMIN_PANEL_URL` pour le service API. Le panneau refuse de démarrer tant que `ADMIN_PANEL_SESSION_SECRET` n'est pas configuré.

### URL de redirection LibreChat [#librechat-redirect-url]

Lorsque le panneau d'administration est hébergé sur une URL distincte de LibreChat, définissez `ADMIN_PANEL_URL` dans l'environnement de l'API LibreChat. Utilisez l'URL de base externe du panneau d'administration, incluant tout préfixe de chemin, et omettez la barre oblique finale :

```bash filename=".env"
ADMIN_PANEL_URL=https://admin.example.com/admin
```

Lorsqu'il est défini, LibreChat affiche également un lien **Admin Panel** aux administrateurs sous **Settings -> General**. Les utilisateurs non administrateurs ne voient pas ce lien.

Pour les déploiements Helm, définissez `librechat.adminPanelUrl` dans votre fichier values. Le chart le rend sous la forme `ADMIN_PANEL_URL` pour le flux OAuth d'administration de LibreChat :

```yaml filename="values.yaml"
librechat:
  adminPanelUrl: https://admin.example.com/admin
```

Pour OpenID SSO, enregistrez `${DOMAIN_SERVER}/api/admin/oauth/openid/callback` auprès de votre fournisseur d'identité.

### Contrôles du cache [#cache-controls]

Ceux-ci reflètent les variables d'environnement de cache de LibreChat. Les variantes `ADMIN_PANEL_*` sont prioritaires et reviennent aux équivalents partagés de LibreChat lorsqu'elles ne sont pas définies.

| Variable | Objectif |
| --------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| `STATIC_CACHE_MAX_AGE` / `ADMIN_PANEL_STATIC_CACHE_MAX_AGE`     | `max-age` du navigateur en secondes pour les ressources hachées dans `/assets/` (par défaut 172800 = 2 jours). |
| `STATIC_CACHE_S_MAX_AGE` / `ADMIN_PANEL_STATIC_CACHE_S_MAX_AGE` | `s-maxage` du CDN en secondes (par défaut 86400 = 1 jour). |
| `INDEX_CACHE_CONTROL` / `ADMIN_PANEL_INDEX_CACHE_CONTROL`       | En-tête `Cache-Control` pour la réponse HTML de l'index. |
| `INDEX_PRAGMA` / `ADMIN_PANEL_INDEX_PRAGMA`                     | En-tête `Pragma` pour la réponse HTML de l'index. |
| `INDEX_EXPIRES` / `ADMIN_PANEL_INDEX_EXPIRES`                   | En-tête `Expires` pour la réponse HTML de l'index. |

## Authentification [#authentication]

Le panneau d'administration réutilise la pile d'authentification de LibreChat et ne possède pas sa propre base de données d'utilisateurs. Deux chemins de connexion sont pris en charge :

- **Comptes locaux** : nom d'utilisateur/mot de passe pour tout utilisateur LibreChat dont le compte réussit la vérification d'accès administrateur.
- **Single sign-on** : OpenID Connect, SAML, et les fournisseurs OAuth sociaux déjà configurés sur votre instance LibreChat. Définissez `ADMIN_SSO_ONLY=true` pour masquer entièrement le formulaire de mot de passe.

L'accès administrateur est vérifié côté serveur par LibreChat pour chaque requête. Le compte doit soit :

1. Avoir `role: 'ADMIN'` dans MongoDB, **ou**
2. Détenir l'autorisation système `access:admin` (attribuée à un autre mandataire via le panneau d'administration lui-même ; voir [System Grants](/docs/features/access_control#layer-3-system-grants-admin-capabilities)).

Les sessions sont basées sur des cookies, chiffrées avec `SESSION_SECRET`, et expirent en cas d'inactivité selon `ADMIN_SESSION_IDLE_TIMEOUT_MS`.

La SSO d'administration Google demande un accès hors ligne et un consentement afin que le panneau puisse actualiser un jeton d'administration LibreChat expiré sans forcer une nouvelle connexion immédiate. Configurez à la fois `GOOGLE_CLIENT_ID` et `GOOGLE_CLIENT_SECRET`, et enregistrez `${DOMAIN_SERVER}/api/admin/oauth/google/callback` auprès de Google. Chaque actualisation revérifie l'identité du fournisseur du compte, l'état de bannissement, le domaine d'e-mail autorisé, le locataire et l'accès administrateur actuel ; la perte de l'accès met fin à la session d'administration.

## Gestion de la configuration [#configuration-management]

Le panneau affiche la configuration de LibreChat sous forme de formulaire dynamique piloté par le schéma de configuration. Cela présente deux propriétés utiles :

- **Compatible avec les versions futures** : lorsqu'une nouvelle configuration est ajoutée à LibreChat, le panneau la détecte automatiquement à partir du schéma. Aucune mise à jour ou redéploiement du panneau d'administration n'est nécessaire.
- **Remplacements en couches** : la configuration de base (issue de `librechat.yaml`) peut être masquée par des remplacements par mandant (principal) limités à un rôle ou à un groupe. Lorsqu'un utilisateur se connecte, les remplacements sont résolus par ordre de priorité et fusionnés sur la base pour produire la configuration effective que l'utilisateur voit.

<Callout type="warning" title="Les serveurs MCP basés sur des processus restent dans le YAML">
  Les serveurs MCP qui utilisent `type: stdio` ou des champs de processus tels que `command`, `args`, `env`, `cwd` ou `stderr` sont gérés par l'opérateur. Configurez-les uniquement dans `librechat.yaml` ; l'API d'administration rejette les tentatives de création ou de modification de ces derniers, et les remplacements (overrides) ne peuvent ni les remplacer ni les supprimer. La configuration des serveurs MCP distants reste disponible via le système de remplacement habituel.
</Callout>

<Callout type="warning" title="Les en-têtes de passerelle Langfuse restent dans YAML">
  Les `langfuse.headers` au niveau du déploiement peuvent contenir des identifiants de proxy et ne constituent pas une surface de configuration prise en charge par Mongo. Configurez-les dans `librechat.yaml` ; l'API d'administration rejette l'ensemble du mappage ainsi que les chemins d'en-tête individuels. Voir [Authenticated Proxies and Gateways](/docs/configuration/langfuse#authenticated-proxies-and-gateways).
</Callout>

Ceci est la surface derrière le [système de remplacement de configuration par mandant basé sur une base de données](https://github.com/LibreChat-AI/LibreChat/pull/12354) de LibreChat. Cas d'utilisation typiques :

- Donner à un groupe "Research" une valeur `recursionLimit` plus élevée et des endpoints supplémentaires
- Permettre à un rôle "FinanceAdmins" de gérer les serveurs MCP distants tandis que les utilisateurs réguliers peuvent uniquement les utiliser
- Restreindre les permissions d' `interface` aux groupes de contractants externes

Les administrateurs peuvent également utiliser le tableau de bord [Admin Insights](/docs/features/insights) (optionnel) pour examiner l'activité MongoDB au niveau du tenant. Définissez `ENABLE_INSIGHTS=true`, puis accordez à la fois `access:admin` et `read:insights` à un compte possédant le rôle `ADMIN`.

### Remplacement de la validation [#override-validation]

Les écritures de remplacement (`PUT /api/admin/config/:principalType/:principalId` et `PATCH .../fields`) sont validées par rapport au même schéma que `librechat.yaml`, et appliquées par-dessus la configuration de base du déploiement. Une écriture qui produirait une configuration invalide est rejetée avec une erreur HTTP 400 et rien n'est enregistré :

```json
{
  "error": "Invalid config override",
  "code": "CONFIG_OVERRIDE_INVALID",
  "issues": [{ "path": "interface.fileSearch", "code": "invalid_type" }]
}
```

Chaque problème ne comporte que le chemin par points et un code stable (un code de problème de schéma tel que `invalid_type`, ou `missing_merge_key`, `duplicate_merge_key`, `indexed_merge_key_write`, `union_dropped_key` ou `invalid_document`), jamais la valeur soumise. Un correctif de champ n'est rejeté que pour les problèmes qu'il touche ou introduit ; ainsi, une ancienne valeur invalide ailleurs dans la même substitution ne le bloque pas.

Les remplacements stockés qui sont devenus invalides, par exemple après une mise à jour qui renforce le schéma, ne sont pas fatals. Lorsque la configuration est résolue, les champs invalides sont supprimés, la valeur sous-jacente (généralement la valeur de base `librechat.yaml`) s'applique, et le serveur enregistre un avertissement par champ :

```text
[mergeConfigOverrides] Ignoring invalid override "<path>" for <principalType>/<principalId> (<code>)
```

Vérifiez les logs pour ces lignes après la mise à jour, puis corrigez ou supprimez les champs listés dans le panneau. Un thème de remplacement qui ne respecte pas les [règles de thème](/docs/configuration/librechat_yaml/object_structure/theme#validation) revient au thème de base de la même manière.

### Délégation par section [#section-scoped-delegation]

Les autorisations de configuration peuvent être larges (`read:configs`, `manage:configs`) ou limitées à une section de haut niveau (`read:configs:<section>`, `manage:configs:<section>`). Un lecteur limité à une section reçoit une réponse de configuration filtrée contenant uniquement les sections autorisées au lieu de se voir refuser la totalité de la requête. Les autorisations de gestion au niveau d'une section impliquent un accès en lecture à la même section ; un accès de gestion large implique un accès en lecture large.

Les exemples incluent `read:configs:interface`, `manage:configs:endpoints` et `manage:configs:langfuse`. Les utilisateurs délégués ont toujours besoin de `access:admin` pour accéder à l'interface d'administration. Chaque mutation de création, de correction (patch), de suppression logique (tombstone) ou de suppression du profil de base `__base__` nécessite un accès `manage:configs` étendu ; la gestion par section s'applique aux remplacements de rôles, de groupes et d'utilisateurs.

### Secrets stockés [#stored-secrets]

Lorsque les champs secrets enregistrés sont écrits via l'API de configuration administrateur, LibreChat chiffre les valeurs littérales au repos et ne renvoie que des aperçus masqués générés par le serveur. Cela couvre actuellement Langfuse, OCR, la synthèse vocale, la recherche web, les Assistants, Azure Assistants, et chaque `endpoints.custom[].apiKey`. Omettre un secret lors d'une modification ultérieure préserve la valeur stockée.

Les références d'environnement prises en charge restent des références lisibles pour les champs qui les autorisent. Les clés API des endpoint personnalisés conservent également les valeurs `${ENV_VAR}` et `user_provided` au lieu de les chiffrer. La gestion des secrets est basée sur le registre : les valeurs arbitraires dans les cartes génériques telles que les en-têtes personnalisés ou la configuration MCP ne sont pas automatiquement chiffrées ; continuez donc à utiliser des références d'environnement ou le mécanisme d'identification dédié à la fonctionnalité à ces endroits.
