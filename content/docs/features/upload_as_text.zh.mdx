# 将文件作为文本上传 [#upload-files-as-text]

有没有想过把 PDF、代码文件或电子表格交给 AI，然后直接说一句_“阅读此内容”_？LibreChat 的统一上传器会根据文件类型和所选的 endpoint，自动将文件路由至提供商或提取其文本。

您上传一个文件，LibreChat 会从中提取文本，并将全部内容直接粘贴到您的对话中。AI 随后即可阅读其中的每一个字——无需插件、无需向量数据库，也无需配置额外的服务。它开箱即用。

<Callout type="info" title="无需任何设置">
  “Upload as Text”功能可在任何 LibreChat 实例上立即使用。它使用内置的文本解析功能——你无需 OCR、RAG 管道或任何外部服务即可开始使用。
</Callout>

---

## 如何使用 [#how-to-use-it]

<Steps>
  <Step>
    ### 打开面板 [#open-the-palette]

    点击 [message composer](/docs/features/composer#add-files) 中的 **+**。你也可以将文件拖拽到 composer 中。
  </Step>
  <Step>
    ### 选择一个来源 [#choose-a-source]

    在 **Attach** 部分，选择 **From Local Computer**，或者在配置后选择 **From SharePoint**。默认上传器不会要求您选择模型或工具目标。

    如果您的管理员启用了 [`legacyFileUploadUX`](/docs/configuration/librechat_yaml/object_structure/file_config#legacyfileuploadux)，您可以自行选择目标位置：选择 **More upload options**，然后选择 **Upload as Text**。
  </Step>
  <Step>
    ### 选择您的文件 [#choose-your-file]

    选择文件。LibreChat 会根据文件类型和 endpoint 的功能，选择原生提供商交付、文本提取或仅工具存储方式。
  </Step>
  <Step>
    ### 提出您的问题 [#ask-your-question]

    像往常一样输入您的提示词。选定的 File Search 和 Code 工具仅在需要时才会接收文件。
  </Step>
</Steps>

当您选择多个文件时，LibreChat 会跳过重复文件和超过单文件大小限制的文件，在通知中列出被跳过的文件名，并继续上传有效文件。文件数量和总批次大小限制仍然适用于剩余的文件；如果剩余的批次超过了其中任何一个限制，则整个批次将被拒绝。单文件上传的行为保持不变。

<Callout type="warn" title="没看到该选项？">
  当启用 `legacyFileUploadUX` 后，如果 **更多上传选项** 下没有出现 **作为文本上传**，则说明 `context` 功能可能已被管理员禁用。该功能默认开启，但如果自定义了功能列表，则需要显式包含 `context`。请参阅下方的 [配置部分](#the-context-capability)。
</Callout>

## 将长文本作为文件粘贴 [#paste-long-text-as-a-file]

在常规消息编辑器中，LibreChat 可以将超过 2,500 个字符的粘贴内容转换为“作为文本上传”的附件。这样既能避免将大段粘贴内容留在输入框中，又能通过对话上下文将内容提供给模型。第一个附件命名为 `pasted-text.txt`；后续的粘贴文本附件将获得带编号的名称。

浏览器本地的 **Paste long text as a file**（将长文本粘贴为文件）设置在 **Settings > Chat > Sending** 下默认处于启用状态。较短的粘贴内容以及在回答 Agent 的 **Ask User** 表单时粘贴的文本将保持为内联形式。如果上下文上传功能不可用，文本也会保持为内联形式。如果附件上传失败，LibreChat 会在不覆盖较新草稿的情况下，将文本恢复到输入框中。

粘贴的文本附件遵循与“作为文本上传”文件相同的文件大小、Token 和 [`fileTokenLimit`](#token-limits-and-truncation) 规则。

## 底层工作原理 [#what-happens-under-the-hood]

当上传内容被路由至文本处理时，LibreChat 不会将原始字节直接转储到提示词中。它会通过一个处理流水线来提取清晰、可读的文本：

1. **MIME type detection** — LibreChat 通过检查文件的 MIME 类型来识别您上传的文件种类（PDF、图像、音频、源代码等）。
2. **方法选择** — 根据文件类型和可用的服务，它会使用以下优先级选择最佳提取方法：

<Tabs items={["优先级顺序", "决策示例"]}>
  <Tabs.Tab>
    | 优先级 | 方法 | 使用场景 |
    |----------|--------|---------------|
    | 第一 | **OCR** | 文件为图像或扫描文档，_且_已配置 OCR |
    | 第二 | **STT** (语音转文字) | 文件为音频，_且_已配置 STT |
    | 第三 | **文本解析** | 文件匹配已知的文本 MIME 类型 |
    | 第四 | **回退** | 以上均不匹配 — 仍尝试进行文本解析 |
  </Tabs.Tab>
  <Tabs.Tab>
    **在配置了 OCR 的实例上使用 `.pdf`：**
    → OCR 将会启动。非常适合扫描文档和复杂布局。

    **在默认实例上的 `.pdf` 文件（无 OCR）：**
    → 由文本解析处理。对于数字生成的 PDF 文件效果良好。

    **一个 `.py` Python 文件：**
    → 直接进行文本解析。源代码本身就是文本——无需转换。

    **在配置了 STT 的实例上使用 `.mp3` 文件：**
    → Speech-to-Text 会将其转录为对话文本。

    **一张未配置 OCR 的 `.png` 截图：**
    → 回退到文本解析（结果有限 —— 请考虑为图像设置 OCR）。
  </Tabs.Tab>
</Tabs>

3. **Token truncation** — 提取的文本会被截断至 `fileTokenLimit`（默认值：100,000 tokens），以防止超出模型的上下文窗口。
4. **Prompt injection** — 该文本会被包含在对话上下文中，与您的消息并列。

当您预览或下载“作为文本上传”(Upload as Text) 的附件时，LibreChat 会提供随文件记录存储的提取文本。即使 OCR 或其他解析器生成了存储的文本且没有原始备份文件可供流式传输，下载时也会使用 `.txt` 文件名。

## 支持哪些文件 [#which-files-are-supported]

<Tabs items={["文本与代码", "文档", "图像", "音频"]}>
  <Tabs.Tab>
    这些内容会被直接解析——它们本身就是文本，因此无需转换。

    - 纯文本 (`.txt`)、Markdown (`.md`)、CSV、JSON、XML、HTML、CSS
    - 编程语言 — Python, JavaScript, TypeScript, Java, C#, PHP, Ruby, Go, Rust, Kotlin, Swift, Scala, Perl, Lua
    - 配置文件 — YAML, TOML, INI
    - Shell 脚本, SQL 文件
  </Tabs.Tab>
  <Tabs.Tab>
    文本解析开箱即用地处理这些内容。如果配置了 OCR，它将接管处理过程，以在复杂布局上获得更高的准确性。

    - **PDF** — 数字版和扫描版（扫描版 PDF 可通过 OCR 获得更好的效果）
    - **Word** — `.docx`, `.doc`
    - **PowerPoint** — `.pptx`, `.potx`, `.ppt`
    - **Excel** — `.xlsx`, `.xls`
    - **EPUB** 电子书
  </Tabs.Tab>
  <Tabs.Tab>
    图像**需要 OCR** 才能生成有用的文本。如果没有它，结果将会很差。

    - JPEG, PNG, GIF, WebP
    - HEIC, HEIF (Apple 格式)
    - 截图、文档照片、扫描页面
  </Tabs.Tab>
  <Tabs.Tab>
    音频文件**需要配置 STT**。没有回退机制——音频无法被“文本解析”。

    - MP3, WAV, OGG, FLAC
    - M4A, WebM
    - 语音录音，播客片段
  </Tabs.Tab>
</Tabs>

LibreChat 会将 Chrome 在 Linux 上报告的 shell 脚本 MIME 变体（`application/x-shellscript`）以及 libmagic 报告的变体（`text/x-shellscript`）标准化为规范的 `application/x-sh`，然后再检查 endpoint 允许列表。自定义的 [`supportedMimeTypes`](/docs/configuration/librechat_yaml/object_structure/file_config#supportedmimetypes-3) 规则仍必须允许 `application/x-sh`。

## 统一上传与工具配置 [#unified-uploads-and-tool-provisioning]

默认情况下，一个附件操作会替换旧的目标选择器。LibreChat 会决定文件如何到达模型，而工具则是按需（lazily）配置的：

<Cards>
  <Card title="模型上下文" href="#what-happens-under-the-hood">
    根据 MIME 类型、endpoint 能力和部署配置，受支持的文件通过原生提供商交付或提取文本的方式传达给模型。
  </Card>
  <Card title="用于文件搜索 (RAG) 的上传" href="/docs/features/rag_api">
    当选中 File Search 时，LibreChat 仅在运行需要该工具时才会索引符合条件的附件。
  </Card>
  <Card title="标准上传" href="/docs/features/agents">
    当选择 Code 时，LibreChat 仅在运行需要时才将符合条件的附件提供给 Code 环境。
  </Card>
</Cards>

运维人员可以通过 [`fileConfig.legacyFileUploadUX`](/docs/configuration/librechat_yaml/object_structure/file_config#legacyfileuploadux) 恢复早期的目标选择器，或通过 [`defaultLLMDeliveryPath`](/docs/configuration/librechat_yaml/object_structure/file_config#defaultllmdeliverypath) 控制自动路由。

**典型路由：**

| 情况 | 最佳选项 |
|-----------|-------------|
| _"阅读这份 5 页的合同并进行总结"_ | 原生 PDF 交付或提取文本 |
| _"我有 50 份 PDF，找出其中提到定价的内容"_ | 懒加载文件搜索 (Lazy File Search) 配置 |
| _"这张截图里有什么？"_ | 原生图像交付 |
| _"运行这段 Python 脚本"_ | 懒加载代码 (Lazy Code) 配置 |
| _"检查这个代码文件中的错误"_ | 提取文本 |

## `context` 功能 [#the-context-capability]

在底层，Upload as Text 由 **`context` 功能**驱动。这决定了该功能是否会在您的聊天界面中显示。

<Callout type="info">
  `context` 功能**默认处于启用状态**。只有当您的管理员自定义了功能列表并意外将其遗漏时，您才需要对此进行调整。
</Callout>

```yaml title="librechat.yaml"
endpoints:
  agents:
    capabilities:
      - "context"  # This is what enables "Upload as Text"
```

相同的 `context` 功能也支持 **Agent File Context**（通过 Agent Builder 上传文件，将文本嵌入到 Agent 的系统指令中）。不同之处在于文本最终存储的_位置_：

| | 上传为文本 | Agent 文件上下文 |
|---|---|---|
| **位置** | 聊天输入框（任何对话） | Agent 构建器面板 |
| **范围** | 仅限当前对话 | 在 Agent 的指令中持久存在 |
| **用例** | 一次性文档提问 | 构建内置知识的专用 Agent |

## Token 限制与截断 [#token-limits-and-truncation]

当文件过长而无法放入模型的上下文窗口时，LibreChat 会截断提取的文本以保持在限制范围内。此过程会自动发生——您无需担心，但了解其工作原理很有帮助。

```yaml title="librechat.yaml"
fileConfig:
  fileTokenLimit: 100000  # Default: 100,000 tokens
```

<Callout type="warn" title="截断意味着内容丢失">
  如果您的文件超过了限制，文本会在末尾被截断。如果您收到的回答不完整，原因可能就在于此。您可以增加 `fileTokenLimit`，但请记住，更大的数值意味着每条消息会消耗更多的 token——这会增加成本，并可能达到模型自身的上下文限制。
</Callout>

**经验法则：**
- 100k tokens ≈ 一本 300 页的书（足以满足大多数使用场景）
- 如果您正在处理非常大的文件，请考虑使用 [File Search (RAG)](/docs/features/rag_api) —— 它只会检索相关部分，而不是将所有内容都塞入上下文。

## 可选：使用 OCR 增强提取效果 [#optional-boosting-extraction-with-ocr]

文本解析对于数字创建的文档（从 Word 保存的 PDF、代码文件、纯文本）效果良好。但如果您上传的是**扫描文档、页面照片或带有文字的图像**，内置解析器的效果将不尽如人意。

这就是 OCR 发挥作用的地方。配置完成后，LibreChat 会自动对适用的文件类型使用 OCR——作为用户，你无需进行任何额外操作。

<Accordions>
  <Accordion title="如何告知您的管理员设置 OCR">
    请引导他们查看 [OCR configuration docs](/docs/features/ocr)。简而言之：

    ```yaml title="librechat.yaml"
    ocr:
      strategy: "mistral_ocr"
      apiKey: "${OCR_API_KEY}"
      baseURL: "https://api.mistral.ai/v1"
      mistralModel: "mistral-ocr-latest"
    ```

    一旦配置完成，OCR 将自动处理图像和扫描的 PDF 文件——用户端无需进行任何更改。
  </Accordion>
  <Accordion title="如何告知管理员设置 STT（用于音频文件）">
    若要转录上传的音频，管理员需要配置语音转文字（Speech-to-Text）服务。请参阅 [STT 配置参考](/docs/configuration/librechat_yaml/object_structure/file_config#stt)。
  </Accordion>
</Accordions>

## 文件处理配置参考 [#file-handling-configuration-reference]

本节适用于希望控制哪些文件类型由哪种方法处理的管理员。默认设置已经足够好——只有在您需要微调行为时才需要修改此部分。

<Accordions>
  <Accordion title="完整的 fileConfig 示例">
    ```yaml title="librechat.yaml"
    fileConfig:
      # Max tokens extracted from a single file before truncation
      fileTokenLimit: 100000

      # Files matching these MIME patterns use OCR (if configured)
      ocr:
        supportedMimeTypes:
          - "^image/(jpeg|gif|png|webp|heic|heif)$"
          - "^application/pdf$"
          - "^application/vnd\\.openxmlformats-officedocument\\.(wordprocessingml\\.document|presentationml\\.presentation|spreadsheetml\\.sheet)$"
          - "^application/vnd\\.ms-(word|powerpoint|excel)$"
          - "^application/epub\\+zip$"

      # Files matching these MIME patterns use text parsing
      text:
        supportedMimeTypes:
          - "^text/(plain|markdown|csv|json|xml|html|css|javascript|typescript|x-python|x-java|x-csharp|x-php|x-ruby|x-go|x-rust|x-kotlin|x-swift|x-scala|x-perl|x-lua|x-shell|x-sql|x-yaml|x-toml)$"

      # Files matching these MIME patterns use STT (if configured)
      stt:
        supportedMimeTypes:
          - "^audio/(mp3|mpeg|mpeg3|wav|wave|x-wav|ogg|vorbis|mp4|x-m4a|flac|x-flac|webm)$"
    ```

    **优先级提醒：** OCR > STT > 文本解析 > 回退 (fallback)。

    有关完整参考，请参阅 [File Config Object Structure](/docs/configuration/librechat_yaml/object_structure/file_config)。
  </Accordion>
</Accordions>

## 故障排除 [#troubleshooting]

<Accordions>
  <Accordion title="“作为文本上传”选项未显示">
    `context` 功能可能已从您的配置中移除。请联系您的管理员将其添加回来：

    ```yaml
    endpoints:
      agents:
        capabilities:
          - "context"
    ```
  </Accordion>
  <Accordion title="文件内容看起来不正确或大部分为空">
    需要检查的几点：
    - **扫描版 PDF / 图片** — 这些文件需要 OCR 才能正确提取文本。如果没有 OCR，解析器可能会返回乱码或空结果。请联系您的管理员[配置 OCR](/docs/features/ocr)。
    - **音频文件** — 这些文件需要 STT。音频没有文本回退方案。
    - **文件损坏** — 尝试在本地打开文件，以确保其未损坏。
    - **不支持的格式** — 如果 MIME 类型与任何已配置的模式不匹配，LibreChat 会尝试回退到文本解析，这对于二进制格式可能无法正常工作。
  </Accordion>
  <Accordion title="上传因文件类型不受支持而被拒绝">
    LibreChat 会在上传错误中返回被拒绝的 MIME 类型。请检查当前活跃 endpoint 的 [`fileConfig.endpoints.<endpoint>.supportedMimeTypes`](/docs/configuration/librechat_yaml/object_structure/file_config#supportedmimetypes-3) 模式，并允许你打算接受的规范类型。对于 shell 脚本，请使用 `application/x-sh`；LibreChat 会在匹配前将常见的 `application/x-shellscript` 和 `text/x-shellscript` 变体进行标准化处理。
  </Accordion>
  <Accordion title="AI 似乎遗漏了我文件的一部分">
    您的文件可能超过了 `fileTokenLimit`。文本已被截断。

    **选项：**
    - 请联系您的管理员增加 `librechat.yaml` 中的 `fileTokenLimit`。
    - 请改用 [File Search (RAG)](/docs/features/rag_api)，它会检索相关的数据块，而不是加载整个文件。
    - 将文件拆分为较小的部分并分别上传
  </Accordion>
  <Accordion title="图片已上传但 AI 无法读取其中的文字">
    如果没有 OCR，图像将通过文本解析进行处理，这实际上无法“看到”图像中的文本。你需要配置 OCR 才能实现此功能。请参阅 [OCR for Documents](/docs/features/ocr)。

    或者，使用带有标准文件上传功能的 **vision model** —— 模型本身即可读取图像中的文本。
  </Accordion>
</Accordions>
