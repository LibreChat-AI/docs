# Agentes: Construye asistentes de IA personalizados [#agents-build-custom-ai-assistants]

La función de AI Agents de LibreChat proporciona un marco flexible para crear asistentes de IA personalizados impulsados por varios proveedores de modelos.

Esta función es similar a la Assistants API de OpenAI y a los GPTs de ChatGPT, pero con un soporte de modelos más amplio y una implementación sin código (no-code), lo que le permite crear asistentes sofisticados con capacidades especializadas.

## Primeros pasos [#getting-started]

Para crear un nuevo agente, seleccione "Agents" en el menú de endpoint y abra el panel Agent Builder que se encuentra en el Side Panel.

![Agentes - Menú de endpoints](/images/agents/endpoints_menu.png)

El formulario de creación incluye:

- **Avatar**: Sube un avatar personalizado para personalizar tu agente
- **Name**: Elija un nombre distintivo para su agente
- **Descripción**: Detalles opcionales sobre el propósito de tu agente
- **Instructions**: Instrucciones del sistema que definen el comportamiento de tu agente
- **Model**: Seleccione entre los proveedores y modelos disponibles
- **Conversation Starters**: Hasta cuatro prompts sugeridos que se muestran cuando un usuario inicia un nuevo chat con el agente

Los controles de **Tools** y **Skills** abren bibliotecas con capacidad de búsqueda para funciones integradas, herramientas, servidores MCP, Actions y Skills. Seleccione un elemento para configurarlo y, a continuación, guarde el agente.

**Los agentes existentes pueden seleccionarse desde el menú desplegable superior del Panel Lateral.**

- **También mediante mención con "@" en la entrada del chat.**

![Agents - Mention](/images/agents/mention.png)

### Biblioteca de herramientas [#tool-library]

El Agent Builder mantiene los elementos habilitados en secciones separadas de **Tools** y **Skills**. Abra **Add tools** para buscar en el catálogo completo o filtrarlo por **Official**, **Tools**, **MCP** o **Actions**. **Made by you** recopila los servidores MCP y las Actions que usted creó, mientras que **Favorites** mantiene los elementos marcados como favoritos disponibles en todos los agentes. Cada usuario puede guardar hasta 100 favoritos en la biblioteca de herramientas.

Seleccione un elemento para configurarlo sin salir del generador. El menú **Create new** solo aparece cuando el usuario tiene permiso para crear servidores MCP o Actions. Eliminar una capacidad respaldada por archivos, como File Search, File Context o Code Interpreter, abre su administrador de archivos cuando todavía hay archivos adjuntos que deben revisarse. Una capacidad respaldada por archivos permanece seleccionada y se conserva al guardar mientras siga siendo propietaria de archivos; elimine o reasigne esos archivos antes de eliminar la capacidad en sí.

Las Skills utilizan su propio selector y pueden seleccionarse individualmente o habilitarse como el catálogo completo accesible. Consulta [Skills](/docs/features/skills#agent-scope).

Los operadores también pueden usar [Agent Plugins](/docs/features/agent_plugins) experimentales para agrupar Skills de despliegue y servidores MCP en paquetes cargados al inicio.

### Configuración del modelo [#model-configuration]

La interfaz de parámetros del modelo permite ajustar con precisión las respuestas de su agente:

- Temperatura (escala de 0 a 1 para la creatividad de la respuesta)
- Tokens de contexto máximo
- Máximo de tokens de salida
- Detalle de imagen (`low`, `auto` o `high`) para entradas de imagen de visión nativa
- Configuraciones adicionales específicas del proveedor

Las instrucciones del agente pueden usar `{{current_date}}`, `{{current_datetime}}` y `{{iso_datetime}}`. LibreChat los resuelve desde el inicio del turno lógico capturado por el servidor y mantiene esa marca de tiempo estable a través de los bucles del proveedor, la inicialización de Subagent y la reanudación con intervención humana (human-in-the-loop). Los dos primeros utilizan la zona horaria de la solicitud; `{{iso_datetime}}` permanece en UTC.

Los fallos reconocidos de "model-not-found" (modelo no encontrado) y de límite de tasa del proveedor muestran orientación localizada. Otros errores del proveedor conservan su texto útil, pero omiten las URLs de solución de problemas de LangChain antes de que el mensaje se guarde. Cuando la [protección de contenido vinculada al modelo](/docs/configuration/librechat_yaml/object_structure/message_filter#source-aware-filters) está habilitada, su error genérico de protección sigue teniendo prioridad.

### Historial de versiones [#version-history]

Los usuarios con acceso de edición pueden abrir el **Version History** desde el Agent Builder para inspeccionar las configuraciones guardadas en una línea de tiempo. Cada entrada muestra cuándo se guardó y resume sus herramientas y capacidades. Restaurar una entrada anterior requiere confirmación y reemplaza la configuración actual del agente con ese estado guardado. Guardar siempre aplica los cambios actuales del agente, incluso cuando la configuración resultante coincide con la entrada del historial más reciente y LibreChat no añade una entrada duplicada.

### Iniciadores de conversación [#conversation-starters]

Los conversation starters ofrecen a los usuarios una forma rápida de comenzar un chat con un agente. Cada agente puede almacenar hasta cuatro.

1. En el Agent Builder, busca el campo **Conversation Starters**.
2. Escribe un prompt y presiona **Enter**, o selecciona el botón **+**. La entrada se deshabilita una vez que se añaden cuatro iniciadores.
3. Edita un starter guardado directamente, o selecciona su botón **X** para eliminarlo.
4. Guarda el agente.

Cuando un usuario abre un nuevo chat con el agente, los iniciadores aparecen como botones en la pantalla de chat vacía. Seleccionar uno lo envía inmediatamente como el primer mensaje. Si el agente tiene iniciadores, estos tienen prioridad sobre cualquier [`conversation_starters`](/docs/configuration/librechat_yaml/object_structure/model_specs#conversation_starters) definido en el Model Specs en uso. Los iniciadores también aparecen en el diálogo de detalles del [Marketplace](#agent-marketplace) del agente.

## Capacidades de los agentes [#agent-capabilities]

> **Nota:** Todas las capacidades pueden activarse o desactivarse a través del archivo de configuración `librechat.yaml`. Consulta [docs/configuration/librechat_yaml/object_structure/agents#capabilities](/docs/configuration/librechat_yaml/object_structure/agents#capabilities) para obtener más información.

### Intérprete de código [#code-interpreter]

Cuando está habilitada, la capacidad de Code Interpreter permite a su agente:

- Ejecute código en múltiples lenguajes, incluyendo:
  - Python, JavaScript, TypeScript, Go, C, C++, Java, PHP, Rust y Fortran
- Procese archivos de forma segura a través de la API de Code Interpreter de LibreChat
- Ejecute código sin necesidad de configuración local, ajustes o despliegue de sandbox
- Gestiona la carga y descarga de archivos sin problemas
- [Más información sobre la API de Code Interpreter](/docs/features/code_interpreter)
  - **Con tecnología del servicio [code-interpreter](https://github.com/ClickHouse/code-interpreter) de código abierto (autoalojado)**

Cuando todos los archivos de Code Interpreter requeridos de una conversación no logran restaurarse en el sandbox actual, LibreChat detiene al Agent antes de invocar al modelo y le pide al usuario que vuelva a adjuntar los archivos. Esto evita que la ejecución continúe con referencias a archivos obsoletos o inaccesibles.

Cuando los archivos de conversación comparten un nombre de archivo de Code Interpreter, LibreChat asigna destinos de sandbox distintos y le indica al Agent las rutas resueltas. Consulta [Seamless File Handling](/docs/features/code_interpreter#seamless-file-handling) para conocer el comportamiento ante colisiones y la limitación restante de archivos privados multi-Agent.

#### Sesiones de código con estado [#stateful-code-sessions]

Las sesiones de código con estado (stateful) permiten que un agente reutilice un espacio de trabajo en un entorno aislado (sandbox) a través de varias ejecuciones de código. Los archivos, los paquetes instalados y el estado de trabajo generalmente se mantienen, lo cual es útil para el análisis iterativo y el trabajo con archivos en múltiples pasos. En el Agent Builder, el selector **Stateful environment** controla quién comparte ese espacio de trabajo:

- **Espacio de trabajo del usuario (recomendado):** los agentes con estado del usuario que ha iniciado sesión comparten un mismo espacio de trabajo
- **Espacio de trabajo de agente + usuario:** cada usuario obtiene un espacio de trabajo separado para cada agente
- **Área de trabajo de la conversación:** cada usuario obtiene un área de trabajo independiente para cada conversación

Los administradores también pueden configurar backends con nombre bajo [`statefulCodeSessions.environments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions). Cuando están presentes, el selector de **Execution environment** independiente elige la API de código gestionada, la máquina virtual adjunta al operador o el trabajador personal que posee el espacio de trabajo; **Deployment default** utiliza el entorno ejecutable predeterminado configurado. El ámbito de uso compartido anterior permanece independiente de esa elección de backend.

Cuando una implementación habilita trabajadores de autoservicio, los usuarios con permiso de gestión de Code Environment pueden abrir **Settings > Code environments** para vincular un trabajador saliente `@librechat/code` en su propia VM, seleccionarlo en el Agent Builder y revocarlo más tarde. Los entornos personales están vinculados al propietario y utilizan la misma ruta para código, shell y Programmatic Tool Calling. Consulta [Attached environments and pairing](/docs/features/code_interpreter#attached-environments-and-pairing) para conocer la configuración experimental y el modelo de seguridad.

Dentro de un workspace adjunto, los Agents pueden listar directorios, leer archivos, buscar texto, crear archivos y ejecutar Bash a través del worker seleccionado. Un nombre y correo electrónico de Git por cada Agent pueden identificar las confirmaciones (commits) realizadas allí sin necesidad de proporcionar credenciales de repositorio. Las implementaciones pueden limitar los nuevos workers personales con [`statefulCodeSessions.principalWorkers`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions).

Cuando un worker adjunto anuncia múltiples raíces de espacio de trabajo, el compositor de chat requiere una selección para cada entorno adjunto utilizado por el Agente o sus Subagentes. La conversación conserva esas selecciones a través de los turnos y la reanudación de aprobaciones; LibreChat las valida contra el worker activo y bloquea el envío si falta un espacio de trabajo requerido o no está disponible. Un worker que anuncia exactamente un espacio de trabajo se selecciona automáticamente para una nueva conversación. Consulta [Attached environments and pairing](/docs/features/code_interpreter#attached-environments-and-pairing) para obtener detalles y conocer las limitaciones actuales.

Los nuevos Agents utilizan inicialmente el **Default stateful workspace** del usuario que ha iniciado sesión, desde **Settings > Data Controls > Code execution**. El valor predeterminado personal es **User workspace** hasta que se modifique. Actualizar esta preferencia no altera los Agents existentes ni habilita Stateful Code Sessions por sí solo. Los administradores pueden restringir los ámbitos disponibles con [`statefulCodeSessions.allowedEnvironments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions); cuando un valor predeterminado personal guardado ya no está permitido, los nuevos Agents utilizan el primer ámbito permitido.

<Callout type="warning" title="Altamente experimental">
  Las Stateful Code Sessions se encuentran en una fase de experimentación temprana. Su comportamiento, configuración, características de persistencia e integración subyacente pueden cambiar sustancialmente. No trate la implementación actual como un contrato de producción estable.
</Callout>

Esta función es opcional. Un administrador debe añadir `stateful_code_sessions` a las [capacidades del agente](/docs/configuration/librechat_yaml/object_structure/agents#capabilities) y configurar una ruta dedicada de Code Interpreter con estado a través de [`LIBRECHAT_CODE_BASEURL_STATEFUL`](/docs/configuration/dotenv#stateful-code-interpreter-endpoint) o mediante [`statefulCodeSessions.environments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions). Code Interpreter debe estar habilitado en el agente, y **Stateful code sessions** debe estar activado en sus ajustes avanzados.

Las solicitudes con estado (stateful) no recurren al endpoint normal sin estado (stateless) de Code Interpreter cuando la URL dedicada falta o es incompatible. Las sesiones con estado y sin estado tampoco comparten archivos activos ni paquetes instalados. El espacio de trabajo con estado puede reiniciarse en cualquier momento, independientemente de su alcance. En entornos gestionados de Code Interpreter, guarde los resultados importantes en `/mnt/data`; un espacio de trabajo adjunto es un directorio independiente propiedad del trabajador. Las cargas de chat no se copian en ese directorio adjunto de forma predeterminada. No confíe en el estado de la sesión como almacenamiento duradero para otros fines.

Cuando las herramientas con estado `create_file` o `edit_file` crean archivos durante una respuesta, el mensaje del asistente muestra una fila compacta de **Cambios en el espacio de trabajo** (Workspace changes). Expándala para revisar las rutas únicas modificadas y descargar cada archivo a través del flujo de archivos autenticado de LibreChat. Este es un registro por mensaje de los archivos creados por esas herramientas, no una instantánea duradera del espacio de trabajo completo; las salidas del Intérprete de código sin estado continúan utilizando la interfaz de archivos adjuntos en línea habitual.

Para entornos adjuntos, el composer puede exponer **Ask before changes** (Preguntar antes de realizar cambios), **Accept edits** (Aceptar ediciones) y **Full access** (Acceso completo) como un modo de aprobación de código a nivel de conversación. La disponibilidad está limitada por el esquema de permisos definido por el administrador del entorno; elegir un modo más permisivo nunca anula las concesiones de roles, las reglas explícitas de herramientas, los hooks o los límites del sandbox. Consulta [Attached-environment tool permissions](/docs/features/code_interpreter#attached-environment-tool-permissions).

### Búsqueda de archivos [#file-search]

La capacidad de File Search permite:

- Funcionalidad RAG (Retrieval-Augmented Generation)
- Búsqueda semántica en documentos subidos
- Respuestas con reconocimiento de contexto basadas en el contenido de los archivos
- Soporte para archivos adjuntos tanto a nivel de agente como de hilo de chat

### Contexto de archivo [#file-context]

La funcionalidad de File Context permite que su agente almacene texto extraído de archivos como parte de sus instrucciones del sistema:

- Extraer texto manteniendo la estructura y el formato del documento
- Procesar diseños complejos, incluyendo texto en varias columnas y contenido mixto
- Manejar tablas, ecuaciones y otro contenido especializado
- Trabajar con contenido multilingüe
- El texto se almacena en las instrucciones del agente en la base de datos
- **No se requiere servicio de OCR** - Utiliza análisis de texto de forma predeterminada con métodos de respaldo
- **Mejorado por OCR** - Si OCR está configurado, la calidad de extracción mejora para imágenes y documentos escaneados
- Utiliza la misma lógica de procesamiento que "Upload as Text": **OCR > STT > text parsing**
- [Más información sobre la configuración de OCR](/docs/features/ocr)

**Nota:** El contexto de archivo incluye texto extraído en las instrucciones del sistema del agente. Para preguntas sobre documentos temporales en conversaciones individuales, utilice [Cargar como texto](/docs/features/upload_as_text) desde el chat.

### Model Context Protocol (MCP) [#model-context-protocol-mcp]

MCP es un protocolo abierto que estandariza cómo las aplicaciones proporcionan contexto a los Large Language Models (LLMs), actuando como un adaptador universal para herramientas de IA y fuentes de datos.

Para más información, consulta la documentación sobre [MCP](/docs/features/mcp).

#### Agentes con herramientas MCP [#agents-with-mcp-tools]

1. Configure los servidores MCP en su archivo `librechat.yaml`
2. Reinicia LibreChat para inicializar las conexiones
3. Crear o editar un agente
4. Abre **Add tools** en el Agent Builder y selecciona **MCP**
5. Seleccione el/los servidor(es) MCP que desea añadir; cada servidor aparece como una única entrada
6. Guarda tus cambios en el agente

En este ejemplo, hemos añadido el **[servidor MCP de Spotify](https://github.com/LibreChat-AI/spotify-mcp)** a un agente.

![Agentes - MCP](/images/agents/mcp_tools_v2.png)

#### Gestión de herramientas MCP [#managing-mcp-tools]

Una vez que se añade un servidor MCP a un agente, puede ajustar con precisión qué herramientas específicas están disponibles:

- Después de agregar un servidor MCP, expándalo para ver todas las herramientas disponibles
- Marque/desmarque las herramientas individuales según sea necesario
- Por ejemplo, el servidor MCP de Spotify proporciona ~20 herramientas (búsqueda, control de reproducción, gestión de listas de reproducción, etc.)
- Este control granular le permite limitar a los agentes solo a las herramientas que necesitan

Los servidores con ámbito de solicitud que utilizan `{{LIBRECHAT_BODY_*}}` no pueden enumerar herramientas hasta que una ejecución de chat proporcione esos valores. Por lo tanto, el Agent Builder muestra una selección de herramientas en tiempo de ejecución para todo el servidor en lugar de interruptores por herramienta; borrar esa selección desconecta el servidor. Después de OAuth, LibreChat mantiene la autorización y espera hasta la primera ejecución elegible para conectarse.

Si un Agent selecciona explícitamente herramientas MCP pero ninguna puede ser resuelta al iniciar una ejecución, LibreChat detiene la ejecución con una guía de conexión y acceso en lugar de continuar silenciosamente sin ellas. Vuelva a conectar o autenticar el servidor, verifique el acceso a la herramienta y reintente la ejecución.

### Herramientas diferidas [#deferred-tools]

Las herramientas diferidas (deferred tools) permiten que los agentes tengan acceso a muchas herramientas MCP sin cargarlas todas en el contexto del LLM por adelantado. En su lugar, las herramientas diferidas se pueden descubrir en tiempo de ejecución mediante un mecanismo de **Búsqueda de herramientas** (Tool Search).

Esto es especialmente útil cuando un agente tiene acceso a muchos servidores MCP con docenas de herramientas; cargarlas todas consumiría una gran parte de la ventana de contexto y degradaría la calidad de la respuesta.

**Cómo funciona:**

- Las herramientas marcadas como "deferred" se excluyen del contexto inicial del LLM
- Una herramienta `ToolSearch` se añade automáticamente, permitiendo al LLM descubrir y cargar herramientas diferidas bajo demanda.
- Una vez descubierta, la herramienta estará disponible para el resto de la conversación

**Configuración de herramientas diferidas:**

1. Abre el Agent Builder y añade herramientas MCP
2. Haz clic en el menú desplegable de cualquier herramienta MCP
3. Alternar "Defer Loading" (Diferir carga) — las herramientas diferidas muestran un icono de reloj

**Nota:** La capacidad `deferred_tools` está habilitada de forma predeterminada. Puede activarse o desactivarse a través de la configuración de agentes en [`librechat.yaml`](/docs/configuration/librechat_yaml/object_structure/agents#capabilities).

### Grupos de actividad [#activity-groups]

Los grupos de actividad contraen cada bloque contiguo de razonamiento del Agente y llamadas a herramientas bajo un encabezado generado de una sola línea, lo que facilita el escaneo de ejecuciones largas. Los administradores los habilitan con `activityLabel` y pueden usar un modelo más rápido, otro endpoint configurado, un prompt personalizado y límites por ejecución. La generación del encabezado es una llamada de modelo independiente cuyos tokens y costo se registran. Consulta [Agent Activity Groups](/docs/configuration/librechat_yaml/object_structure/shared_endpoint_settings#agent-activity-groups).

Los administradores pueden habilitar de forma independiente `activityPhaseLabel` para agrupar dos o más actividades lógicas en un resumen principal contraído antes de la respuesta final. Esto proporciona a las ejecuciones largas un esquema de alto nivel mientras se conserva cada actividad secundaria. Los resúmenes de fase utilizan su propio modelo, endpoint, prompt y límite por ejecución, con respaldo a la configuración de la etiqueta de actividad y de ejecución.

Tan pronto como una ejecución contigua contiene al menos dos grupos de herramientas etiquetados y completados, LibreChat los pliega en la misma superficie de tarjeta de fase incluso antes de que llegue un resumen de fase opcional. La etiqueta secundaria completada más reciente actúa como encabezado provisional, mientras que el razonamiento en vivo y la llamada a la herramienta aún en curso permanecen fuera del pliegue. El historial cargado utiliza la misma agrupación, y un resumen de fase generado por el servidor posteriormente reemplaza el encabezado provisional sin cerrar una tarjeta que el lector haya abierto.

Cuando [Smooth Streaming](/docs/features/smooth_streaming) está habilitado, un resumen principal recién generado pliega suavemente las actividades visibles en el grupo contraído. El historial cargado no reproduce esta transición, y LibreChat respeta la preferencia de reducción de movimiento del dispositivo.

El texto de progreso breve permanece dentro de su fase principal. Cuando el Agent comienza una respuesta sustancial, LibreChat cierra la fase antes de ese texto para que el resultado visible para el usuario permanezca fuera del resumen contraído. Una ejecución puede crear múltiples fases principales cuando razonamientos posteriores o herramientas inician otro bloque de actividad lógica. Los límites de fase persistidos se reajustan cuando las partes de contenido mal formadas u omitidas se compactan, de modo que la agrupación permanezca alineada después de recargar.

Los archivos producidos dentro de una fase permanecen visibles en una fila de medios debajo de la tarjeta contraída en lugar de quedar ocultos dentro de ella. Las referencias de imágenes en Markdown que utilizan un nombre de archivo simple, `/mnt/data/...` o una ruta `sandbox:` se resuelven como archivos adjuntos del turno correspondiente. Un archivo solo se omite de la fila de medios cuando una imagen en línea fuera de la fase contraída se resuelve correctamente, lo que evita duplicados sin confiar en referencias rotas.

Las tarjetas de herramientas de Generic Agent y MCP distinguen entre **Preparando** (antes de la transferencia al SDK, lo cual puede incluir aprobación u otra espera) y **Llamando** (transferencia al SDK hasta el resultado). Las tarjetas completadas muestran ambos intervalos; el intervalo de llamada no es necesariamente la duración de la ejecución del MCP ascendente o de ClickHouse. Los mensajes guardados anteriormente y las tarjetas especializadas de Code, Bash, archivo y memoria conservan una duración de paso de ejecución claramente etiquetada como **Total transcurrido**. Los pasos detenidos, cancelados, fallidos y completados conservan estados distintos, incluso después de recargar una conversación.

Mientras se ejecuta una herramienta, los paneles de detalles expandidos de Bash, Execute Code y File Authoring siguen los comandos transmitidos, el código o el contenido de vista previa hasta la parte inferior. Desplazarse hacia arriba pausa ese comportamiento de seguimiento para que se preserve la posición de lectura actual.

La salida de Bash se renderiza como texto con estilo de terminal. La salida larga se contrae a sus últimas 15 líneas, donde suelen aparecer los errores; utilice **Show more** y **Show less** para expandirla o contraerla, y el botón **Copy** para copiar la salida. Un comando que no imprimió nada muestra **No output**. Para los comandos ejecutados en un [espacio de trabajo adjunto](/docs/features/code_interpreter#attached-environments-and-pairing), un comando fallido se marca con su motivo (**exit code N**, **terminated by** una señal como `SIGKILL`, o **timed out**), y stderr se estiliza por separado de stdout. Un comando finalizado se etiqueta como **Ran command**, y un grupo de herramientas que contiene una sola llamada se abre directamente en los detalles de esa llamada.

### Etiquetas de razonamiento en vivo [#live-reasoning-labels]

Las etiquetas de razonamiento en vivo reemplazan un encabezado genérico de **Thinking** o **Thoughts** con una breve orientación que evoluciona a medida que los flujos de razonamiento de nivel superior son lo suficientemente largos. La etiqueta actualiza el encabezado de razonamiento existente en el mismo lugar; no añade ni reordena partes del mensaje.

La etiqueta de razonamiento en vivo más reciente y el temporizador de respuesta brillan mientras la generación está activa. El razonamiento consolidado, las respuestas de hermanos anteriores y las etiquetas que ya no están en la parte final en vivo permanecen estáticos.

Los administradores habilitan esto con `reasoningLabel` y pueden elegir un modelo, endpoint, prompt, umbrales de actualización y límite de llamadas por ejecución independientes. Cada revisión es una llamada de modelo adicional cuyos tokens y costo se registran. Consulta [Live Reasoning Labels](/docs/configuration/librechat_yaml/object_structure/shared_endpoint_settings#live-reasoning-labels) para conocer los valores predeterminados, la precedencia de enrutamiento y las consideraciones de privacidad.

### Etiquetas de intención de herramientas [#tool-intent-labels]

Las etiquetas de intención de herramienta reemplazan los estados genéricos de herramientas en vivo con una breve descripción escrita por el modelo para esa llamada específica. Los administradores deben añadir la capacidad de agente `tool_intents` [agent capability](/docs/configuration/librechat_yaml/object_structure/agents#capabilities). Las herramientas nativas utilizan etiquetas automáticamente; en el Agent Builder, expanda un servidor MCP y active **Intent label** para herramientas individuales o para el servidor completo.

Para Model Specs, [`describeIntent`](/docs/configuration/librechat_yaml/object_structure/model_specs#describeintent) puede habilitar cada herramienta elegible o seleccionar IDs de herramientas resueltos. Los campos de intención se añaden al esquema de herramientas enviado al modelo, por lo que la habilitación selectiva puede reducir la sobrecarga de tokens del esquema.

Las etiquetas de intención no se aplican a las herramientas MCP exclusivamente programáticas porque las llamadas realizadas dentro del código del sandbox no renderizan tarjetas de herramientas individuales. Una ejecución programática expandida muestra, en su lugar, un seguimiento en vivo compacto de sus llamadas internas.

### Programmatic Tool Calling [#programmatic-tool-calling]

Programmatic Tool Calling (PTC) permite a los agentes ejecutar herramientas MCP seleccionadas desde dentro del sandbox de [Code Interpreter](/docs/features/code_interpreter) en lugar de llamar a cada herramienta directamente desde el modelo. El modelo recibe una herramienta de orquestación respaldada por Code Interpreter, escribe código en el sandbox que llama a las funciones de herramientas generadas, y puede utilizar bucles, condicionales, reintentos y procesamiento de resultados antes de devolver una respuesta.

Esto es útil para flujos de trabajo de herramientas de varios pasos, como consultar varios recursos, paginar resultados, comparar salidas o transformar las respuestas de las herramientas antes de que el agente las explique.

**Configuración de herramientas programáticas:**

1. Enable both `programmatic_tools` and `execute_code` in the [`librechat.yaml` agents capabilities](/docs/configuration/librechat_yaml/object_structure/agents#capabilities).
2. Habilita el Code Interpreter en el agente.
3. Agregue herramientas MCP, expanda un servidor MCP y alterne **Programmatic** para herramientas individuales o para el servidor completo. Las herramientas Programmatic muestran un icono de código.

El Agent Builder mantiene los interruptores Programmatic deshabilitados hasta que se selecciona Code Interpreter. Eliminar Code Interpreter borra inmediatamente las selecciones Programmatic del agente. Al crear, actualizar, duplicar y restaurar versiones, el servidor también elimina las opciones de llamada programática siempre que la capacidad `execute_code` o la herramienta Code Interpreter no estén disponibles; esto permite que los agentes antiguos inconsistentes se abran y corrijan sin conservar una configuración inutilizable.

**Nota:** `programmatic_tools` es opcional y no está incluido en la lista de capacidades de agentes predeterminada. PTC también requiere un despliegue de Code Interpreter con el componente Tool Call Server. En tiempo de ejecución, LibreChat intersecta la proyección de capacidad del llamador actual con su registro de herramientas de confianza, por lo que los datos del evento pueden restringir el mapa disponible pero no pueden otorgar una herramienta. Solo las herramientas programáticas activas y registradas pueden ser llamadas desde el sandbox; las llamadas no registradas son rechazadas.

Expanda la tarjeta de Code Interpreter durante una ejecución programática para ver un seguimiento al estilo de terminal de cada llamada a herramienta interna, su vista previa de argumentos, estado, duración y cualquier error. El seguimiento está activo para la sesión actual del navegador y no se restaura después de recargar la página.

### Llamadas a herramientas en segundo plano [#background-tool-calls]

Las llamadas a herramientas en segundo plano permiten que un agente inicie una herramienta de Code Interpreter, MCP, Plugin o Action elegible de larga duración y continúe trabajando. La llamada inicial devuelve inmediatamente una referencia de tarea. Para un agente guardado, las finalizaciones admitidas se entregan automáticamente en una continuación de seguimiento de forma predeterminada; `check_background_task` permanece disponible para el estado explícito, el control, la recopilación de artefactos y la recuperación.

`check_background_task` informa `started_at` y el `elapsed_ms` actual mientras se ejecuta el trabajo local del proceso. Después de la finalización, también informa `settled_at` y congela `elapsed_ms` en la duración completada. Un resultado terminal recuperado del almacenamiento duradero puede incluir `settled_at` sin una hora de inicio o duración transcurrida cuando la marca de tiempo de despacho local del proceso original no está disponible.

Para utilizar esta función, un administrador debe añadir la capacidad de agente `run_in_background` [agent capability](/docs/configuration/librechat_yaml/object_structure/agents#capabilities). Luego, configure las herramientas elegibles en el Agent Builder:

- **Code Interpreter:** Habilite Code Interpreter en el agente. La ejecución de código y los comandos de shell se vuelven elegibles para ejecutarse en segundo plano de forma predeterminada; desactive **Background execution** en la configuración de sus herramientas para optar por no participar.
- **MCP:** Abra un servidor MCP y marque herramientas individuales, o el servidor completo, como **Background**.
- **Herramientas de plugins:** Abra una herramienta elegible y active **Background execution**.
- **Acciones:** Active la **Ejecución en segundo plano** para una Acción con el fin de habilitar todas las operaciones elegibles dentro de dicha Acción. Las Acciones OAuth no exponen este interruptor. Una operación también se excluye cuando su propio esquema ya define un parámetro `run_in_background`, evitando una colisión con el indicador de despacho de LibreChat.

Estos ajustes permiten la ejecución en segundo plano, pero no la fuerzan. El modelo decide en cada llamada si ejecutar una herramienta elegible en segundo plano.

En el chat de LibreChat, cuando el código en segundo plano termina, su stdout y los archivos generados aparecen en la llamada de código original en lugar de en la consulta posterior. Los archivos generados también se conservan para los turnos subsiguientes. Las continuaciones automáticas presentan el trabajo completado en una tarjeta de tarea de reactivación plegable vinculada a la tarea original.

Cuando el servidor inicia esa continuación después de que la ejecución en primer plano precedente ya haya finalizado, la conversación abierta se adjunta a la nueva generación y actualiza la salida de la tarea completada sin necesidad de recargar.

Las activaciones de finalización automática están habilitadas a menos que un administrador establezca [`endpoints.agents.backgroundTasks.completionWakeups: false`](/docs/configuration/librechat_yaml/object_structure/agents#backgroundtasks), lo cual restaura el comportamiento de solo sondeo. El host puede agrupar varias finalizaciones de solo contenido elegibles en una continuación. Las tareas que producen un artefacto en vivo aún requieren sondeo en el proceso que posee la ejecución.

Los administradores también pueden optar por la cancelación con ámbito de propietario con [`endpoints.agents.backgroundTasks.ordinaryToolCancellation: true`](/docs/configuration/librechat_yaml/object_structure/agents#backgroundtasks). La tarea informa que se solicitó la cancelación hasta que la invocación subyacente se estabiliza, y su capacidad permanece reservada durante ese intervalo. La cancelación es cooperativa: una herramienta que ignora la señal de abortar aún puede completarse con éxito. El control se aplica a las herramientas en segundo plano locales del proceso ordinario, incluido Bash adjunto, pero no a los subagentes separados de propiedad independiente.

Solo las herramientas elegibles exponen esta configuración. La ejecución en segundo plano ordinaria es local al proceso y no sobrevive a la pérdida de su proceso de trabajo. Sin embargo, una vez que se persiste un resultado de terminal de solo contenido, la entrega automática es duradera y puede continuar en otra réplica. El registro local al proceso limita las tareas en ejecución y las cargas útiles de resultados retenidos por conversación, usuario y proceso; desalojar el trabajo finalizado cuando es seguro y devuelve un resultado de capacidad con alcance cuando el procesamiento pendiente impide un desalojo seguro. Si una invocación ignora la cancelación, LibreChat deja de renovar su concesión de productor después de un período de gracia de un minuto tras la interrupción y retira la entrega de finalización automática sin marcar falsamente como agotado el tiempo de espera del trabajo externo incierto. Los Subagents separados (Detached Subagents) utilizan una ruta de tarea y transcripción duradera independiente con controles en vivo enrutados por Redis; consulte [Hilos de Subagents separados](/docs/features/subagents#detached-subagent-threads).

### Solicitar al usuario y aprobación de herramientas [#ask-user-and-tool-approval]

La herramienta **Ask User** permite que un agente pause una ejecución para solicitar información faltante, presentar opciones o confirmar cómo proceder. Una sola llamada puede agrupar hasta cuatro preguntas relacionadas. LibreChat presenta una pregunta a la vez con botones de Atrás, Siguiente y pasos de progreso en los que se puede hacer clic; las respuestas permanecen disponibles mientras se navega entre los pasos, y las respuestas de selección única avanzan automáticamente sin necesidad de enviar. El botón Enviar aparece en el paso final una vez que cada pregunta tiene una respuesta, mientras que Omitir rechaza todo el lote desde cualquier paso. Cada pregunta acepta una respuesta de formato libre o las opciones de selección única o múltiple del agente. Mientras el modelo prepara la llamada, LibreChat transmite las preguntas a una tarjeta de progreso; el formulario interactivo la reemplaza cuando está listo. Después de una presentación, la misma ejecución se reanuda con el mapa de respuestas completo. Agregue **Ask User** desde el mercado de Tools; los administradores pueden eliminar la capacidad predeterminada `ask_user_question` para ocultarla.

Contraer una tarjeta de preguntas múltiples devuelve al compositor a su modo normal de dirigir o poner en cola, mientras que la tarjeta pausada permanece en el hilo. La tarjeta aún puede expandirse, responderse, omitirse o detenerse. Una pausa de una sola pregunta continúa utilizando el modo de respuesta del compositor enfocado.

Las respuestas enviadas se persisten con la acción de reanudar, por lo que detenerse mientras se inicializa la ejecución reanudada no descarta las respuestas aceptadas.

Después de que un registro de pregunta se establece, se contrae de forma predeterminada a una entrada de herramienta de una sola línea para que las respuestas largas no dominen la transcripción. Ábrelo para revisar las preguntas y los saltos de línea preservados en las respuestas. La preferencia existente **Auto-expand tool details** también controla esta vista establecida; el formulario en vivo permanece abierto mientras todavía se requiera información.

Cada pregunta acepta un encabezado opcional de hasta 80 caracteres, un texto de pregunta de hasta 2,000 caracteres, un contexto de apoyo opcional de hasta 4,000 caracteres y hasta 12 opciones. Las etiquetas de las opciones están limitadas a 280 caracteres, los valores de las opciones a 500 caracteres y cada respuesta enviada a 16,000 caracteres.

Los administradores también pueden requerir una revisión antes de que se ejecuten las llamadas a herramientas coincidentes. Dependiendo de la herramienta, los usuarios pueden aprobar, rechazar, editar argumentos o responder directamente. Las ejecuciones pausadas se guardan en puntos de control para que puedan reanudarse después de la decisión, incluso en otra réplica cuando se utiliza el punto de control de MongoDB predeterminado. La aprobación de herramientas a nivel de despliegue está desactivada de forma predeterminada, mientras que un Agente que utiliza un entorno de Código adjunto recibe la [política de seguridad ask-by-default](/docs/features/code_interpreter#attached-environment-tool-permissions) a menos que un administrador la deshabilite explícitamente. Consulte [`toolApproval` y `checkpointer`](/docs/configuration/librechat_yaml/object_structure/agents#toolapproval).

Mientras el panel de revisión del compositor está abierto para una aprobación pendiente, la tarjeta del hilo correspondiente muestra la solicitud como un registro en lugar de duplicar los botones de decisión. Revise las llamadas en el panel sobre el cuadro de mensaje y seleccione **Continue**. Contraer el panel desde el chip del compositor restaura los controles de la tarjeta del hilo con sus decisiones retenidas; volver a abrirlo devuelve la revisión al panel. Las tarjetas para otras acciones mantienen sus propios controles.

### Habilidades [#skills]

Las Skills permiten a los agentes cargar instrucciones reutilizables desde definiciones en `SKILL.md`. Pueden seleccionarse manualmente desde el chat con `$`, ser descubiertas automáticamente por el modelo a través del catálogo de skills, o aplicarse siempre en cada turno. El Agent Builder también puede habilitar la creación en tiempo de ejecución de forma independiente: un agente puede crear una Skill sin recibir el catálogo existente, o editar las Skills seleccionadas cuando el usuario tiene el permiso correspondiente.

Para obtener detalles sobre la creación, invocación y control de acceso, consulta [Skills](/docs/features/skills).

### Memoria [#memory]

La herramienta **Memory** permite que un agente guarde, actualice o elimine recuerdos estructurados del usuario cuando este solicita explícitamente recordar u olvidar algo. Memory debe estar configurada para el despliegue, permitida por el rol y la configuración de personalización del usuario, y habilitada en el agente.

De forma predeterminada, un agente utiliza el grupo de memoria personal compartido del usuario. Activa **Keep memories separate for this agent** para darle una partición privada por usuario y por agente. El agente aislado no verá las memorias compartidas existentes ni las memorias creadas por otros agentes aislados. Los usuarios pueden filtrar el panel de Memory por memorias personales o específicas del agente. Leer, crear o actualizar una partición de agente requiere acceso actual a ese agente; la eliminación aún puede limpiar una partición después de que su agente haya sido eliminado. Consulta [User Memory](/docs/features/memory#agent-memory).

### Artifacts [#artifacts]

La funcionalidad Artifacts permite que tu agente genere y muestre contenido interactivo:

- Crear componentes de React, código HTML y diagramas de Mermaid
- Muestra el contenido en un panel dedicado junto al chat, el cual puede expandirse a pantalla completa o abrirse en su propia ventana del navegador
- Configurar instrucciones específicas para artefactos a nivel de agente
- [Más información sobre Artifacts](/docs/features/artifacts)

Cuando esté habilitado, elija uno de los tres modos de instrucción:

- **Normal**: Añade las instrucciones de artefactos estándar para React, HTML, SVG, Markdown y Mermaid.
- **shadcn/ui**: Añade las instrucciones estándar además de orientación para construir interfaces con la biblioteca de componentes shadcn/ui.
- **Custom**: Mantiene el renderizado de artefactos habilitado pero no inyecta instrucciones de artefactos integradas, lo que otorga control total a las propias instrucciones del agente.

Configurar artifacts a nivel de agente es el enfoque preferido, ya que permite un control más granular en comparación con la configuración heredada de toda la aplicación.

Si seleccionas **Custom**, incluye como mínimo el formato básico de artefacto en tus instrucciones.

Aquí tienes un ejemplo sencillo de las instrucciones mínimas necesarias:

````md
When creating content that should be displayed as an artifact, use the following format:

:::artifact{identifier="unique-identifier" type="mime-type" title="Artifact Title"}

```
Your artifact content here
```

:::

For the type attribute, use one of:

- "text/html" for HTML content
- "application/vnd.mermaid" for Mermaid diagrams
- "application/vnd.react" for React components
- "image/svg+xml" for SVG images
````

### Handoffs [#handoffs]

Las transferencias (handoffs) permiten que un agente principal transfiera una conversación a un agente especialista con el contexto relevante. En **Advanced settings**, abre la sección de orquestación y añade hasta 10 agentes de transferencia. Cada transferencia configurada crea una herramienta de transferencia que el modelo puede elegir dinámicamente cuando se necesite la experiencia del especialista.

Para cada transferencia, puede añadir una descripción que ayude al modelo a elegir al especialista adecuado. También puede proporcionar instrucciones de paso (passthrough instructions) que describan qué contenido debe generar el agente principal para el especialista y, opcionalmente, renombrar el parámetro de contenido desde su valor predeterminado, `instructions`. Las transferencias siempre están disponibles en el Agent Builder; a diferencia de Agent Chain y Subagents, no requieren que se habilite una capacidad de endpoint. Las llamadas a herramientas de los agentes de transferencia alcanzables permanecen estructuradas en turnos posteriores, por lo que los proveedores reciben un historial de llamadas a herramientas válido en lugar de texto plano.

### Cadena de agentes [#agent-chain]

La funcionalidad Agent Chain permite un enfoque de Mixture-of-Agents (MoA), lo que le permite crear una secuencia de agentes que trabajan juntos:

- Crea cadenas de agentes especializados para tareas complejas
- Cada agente en la cadena puede acceder a las salidas de los agentes anteriores
- Configurar el número máximo de pasos para la cadena del agente
- **Nota:** Acceda a esta función desde el panel de Advanced Settings en el Agent Builder
- **Nota:** Esta función se encuentra actualmente en fase beta y puede estar sujeta a cambios
  - El máximo actual de agentes que se pueden encadenar es 10, pero esto podría ser configurable en el futuro.

### Subagentes [#subagents]

Los Subagents permiten que un agente delegue una tarea específica a una ejecución secundaria aislada o a un equipo de Agent guardado. Cada hijo obtiene un contexto y una ejecución de herramientas aislados, y luego devuelve un resultado compacto al padre en lugar de llenar el contexto del padre con cada paso intermedio. El trabajo secundario separado también se conserva como un hilo navegable de solo lectura.

Los Subagents son diferentes a Agent Chain: las cadenas ejecutan múltiples agentes como participantes de un grafo, mientras que los subagents son generados por un agente como una llamada de herramienta para una delegación con alcance limitado. LibreChat preserva el historial estructurado de llamadas de herramientas necesario para los hijos alcanzables y los miembros del equipo guardados en turnos posteriores, mientras mantiene las herramientas no disponibles fuera de la ejecución activa. Para la configuración y los límites, consulte [Subagents](/docs/features/subagents).

### Configuración avanzada [#advanced-settings]

Configuración avanzada para su agente (que se encuentra en la vista Advanced del formulario de Agente) fuera de "capabilities".

#### Pasos máximos del agente [#max-agent-steps]

Esta configuración le permite limitar el número de pasos que un agente puede realizar en una "ejecución" (run), lo cual se refiere al bucle del agente antes de que se proporcione una respuesta final.

Si se deja sin configurar, el valor predeterminado es 25 pasos, pero puede ajustarlo según sus necesidades. Para los administradores, es posible establecer un valor predeterminado global, así como un máximo global, en el archivo [`librechat.yaml`](/docs/configuration/librechat_yaml/object_structure/agents#recursionlimit).

Cuando un turno utiliza su presupuesto completo de pasos, LibreChat conserva la respuesta parcial y las llamadas a herramientas en lugar de reemplazarlas con un error. El mensaje ofrece **Keep going** (Continuar), que inicia un nuevo turno con un presupuesto de herramientas renovado, y **Answer now** (Responder ahora), que solicita al agente que responda a partir del trabajo ya completado sin utilizar más herramientas. Descartar el aviso solo afecta a la vista actual del navegador.

Los administradores también pueden limitar los argumentos de llamadas a herramientas transmitidos y los eventos delta del modelo con [Agent stream circuit breakers](/docs/configuration/librechat_yaml/object_structure/agents#stream-circuit-breakers).

Un "paso" (step) se refiere ya sea a una solicitud de API de IA o a una ronda de uso de herramientas (1 o varias herramientas, dependiendo de cuántas llamadas a herramientas proporcione el LLM a partir de una sola solicitud).

Una respuesta única, sin herramientas, es 1 paso. Una ronda singular de uso de herramientas suele ser de 3 pasos:

1. Solicitud de API -> 2. Uso de herramientas (1 o muchas herramientas) -> 3. Solicitud de API de seguimiento

## Gestión de archivos [#file-management]

Los Agents admiten múltiples formas de trabajar con archivos:

### En la interfaz de chat [#in-chat-interface]

Al chatear con un agente, tienes cuatro opciones de carga:

1. **Subir imágenes**
   - Sube imágenes para soporte nativo de modelos de visión
   - Envía imágenes directamente al proveedor del modelo

2. **Subir como texto** (requiere la capacidad `context`)
   - Extrae e incluye el contenido completo del documento en la conversación
   - Utiliza análisis de texto de forma predeterminada; mejorado mediante OCR si está configurado
   - El contenido solo existe en la conversación actual
   - Consulta [Upload as Text](/docs/features/upload_as_text)

3. **Carga para búsqueda de archivos** (requiere la capacidad `file_search`, activada)
   - Utiliza búsqueda semántica (RAG) con almacenes vectoriales
   - Devuelve fragmentos relevantes mediante el uso de herramientas
   - Óptimo para documentos grandes/múltiples archivos
   - Subóptimo para datos estructurados (CSV, Excel, JSON, etc.)

4. **Carga para Code Interpreter** (requiere la capacidad `execute_code`, activada)
   - Añade archivos al entorno del intérprete de código
   - Óptimo para datos estructurados (CSV, Excel, JSON, etc.)
   - Más información sobre [Code Interpreter](/docs/features/code_interpreter)

### En Agent Builder [#in-agent-builder]

Al configurar un agente, puede adjuntar archivos en diferentes categorías:

1. **Carga de imágenes**: Para contenido visual que el agente puede referenciar
2. **Carga de búsqueda de archivos**: Documentos para capacidades de RAG
3. **Carga de Code Interpreter**: Archivos para procesamiento de código
4. **Contexto de archivo**: Documentos con texto extraído para complementar las instrucciones del agente

**File Context** utiliza la capacidad `context` y funciona exactamente igual que ["Upload as Text"](/docs/features/upload_as_text): utiliza el análisis de texto de forma predeterminada y se mejora mediante OCR cuando está configurado. El texto se extrae en el momento de la carga y se almacena en las instrucciones del agente. Esto es ideal para proporcionar a los agentes conocimiento persistente a partir de documentos, archivos PDF, archivos de código o imágenes con texto.

**Prioridad de procesamiento:** OCR > STT > análisis de texto (igual que Cargar como texto)

**Nota:** El texto extraído se incluye como parte de las instrucciones del sistema del agente.

## Compartir y permisos [#sharing-and-permissions]

Los agentes utilizan el sistema de [control de acceso](/docs/features/access_control) granular de LibreChat. Cada agente tiene su propia Lista de Control de Acceso (ACL) y puede compartirse con **usuarios**, **grupos**, **roles** específicos o **públicamente**, cada uno con un nivel de permiso elegido.

Los servicios de confianza también pueden gestionar Agents, archivos adjuntos y Skills a través de la beta [Agent Management API](/docs/features/agents_api#agent-management-api). Los administradores vinculan cada cliente de máquina OIDC a un usuario y tenant de LibreChat existente; cada solicitud hereda las capacidades de rol y las ACL de recursos actuales de ese usuario en lugar de recibir un acceso administrativo independiente.

### Roles de acceso [#access-roles]

Al compartir un agente, al beneficiario se le asigna uno de tres roles:

| Rol | Qué puede hacer el beneficiario |
| ---------- | ----------------------------------------------------------------------------------------------------- |
| **Viewer** | Usar el agente en conversaciones; no puede abrir el constructor ni ver instrucciones, herramientas o archivos adjuntos |
| **Editor** | Ver + modificar las instrucciones, el modelo, las herramientas y los archivos del agente |
| **Owner**  | Control total: ver, editar, eliminar y volver a compartir el agente |

El autor original y los administradores siempre conservan el control total independientemente de la ACL.

### Compartir un Agent [#sharing-an-agent]

1. Abre el agente en el Agent Builder
2. Haz clic en el botón **Share** en el pie de página (visible cuando eres el autor, un administrador o se te ha concedido el permiso `SHARE` en ese agente específico)
3. Busque usuarios, grupos o roles en el selector de personas y asígnele un rol a cada uno
4. Opcionalmente, activa **Public** para hacer que el agente sea visible para todos en la instancia (requiere el permiso de función `SHARE_PUBLIC`).

Las tarjetas de agente y las vistas de inicio muestran el contacto de soporte configurado. Cuando no se ha establecido ninguno, LibreChat puede recurrir al nombre para mostrar del primer propietario resoluble, pero no expone la dirección de correo electrónico del propietario a menos que se haya configurado explícitamente como el contacto de soporte.

Las superficies de conversación mantienen al Agent como la identidad visible y no recurren a su modelo de respaldo ni a la etiqueta de Model Specs.

Para obtener detalles completos sobre los principales, los bits de permiso y cómo las ACL se combinan con los permisos de funciones basados en roles, consulte [Access Control](/docs/features/access_control).

### Agent Marketplace [#agent-marketplace]

El **Agent Marketplace** permite a los usuarios explorar los agentes disponibles para ellos. Ábrelo desde **Agent Marketplace** en la barra lateral; la entrada solo aparece para los usuarios cuyo rol tiene permitido usar el Marketplace.

- **Explorar y buscar**: Los agentes aparecen en una cuadrícula. Utilice el campo de búsqueda para encontrar agentes por nombre o descripción, y las etiquetas de categoría (como **Top Picks**, **All** o una categoría específica) para filtrar la lista.
- **Ordenar**: Utilice **Ordenar por** para organizar los agentes por **Más recientes primero** (el valor predeterminado), **Más antiguos primero**, **Popular** (más fijados) o **Por nombre del creador**.
- **Mis agentes**: Activa **Mis agentes** para mostrar solo los agentes que has creado. Al activarlo desde **Selecciones destacadas**, se cambia a **Todos**.
- **Vistas compartibles**: La búsqueda, la ordenación y el filtro **My agents** se mantienen en la URL de la página (`?q=`, `?sort=`, `?mine=1`), por lo que una vista filtrada puede guardarse en marcadores o compartirse.

Seleccione una tarjeta de agente para abrir su diálogo de detalles, el cual muestra la descripción completa y el contacto del agente, junto con estas acciones:

- **Fijar** o **Desfijar**: Añade el agente a, o elimínalo de, tus agentes fijados.
- **Copiar enlace**: Copia un enlace que inicia un nuevo chat con el agente.
- **Iniciar Chat**: Abre una nueva conversación con el agente.
- **Prueba un iniciador de conversación**: Cuando el agente tiene [conversation starters](#conversation-starters), selecciona uno para abrir un nuevo chat con ese mensaje ya en la entrada de texto. No se envía automáticamente, por lo que puedes editarlo primero.

Los administradores pueden controlar el acceso con la configuración [`interface.marketplace`](/docs/configuration/librechat_yaml/object_structure/interface#marketplace) y los permisos de rol descritos en [Control de acceso](/docs/features/access_control).

### Controles de administrador [#administrator-controls]

Los administradores tienen acceso a la configuración de permisos globales dentro de la interfaz de usuario del generador de agentes:

- Habilitar/deshabilitar el uso compartido de agentes para todos los usuarios
- Controlar los permisos de uso de agentes
- Gestionar los derechos de creación de agentes
- Configurar los ajustes de toda la plataforma

En una implementación de inquilino único sin ámbito (unscoped), la primera cuenta creada para la instancia es un administrador. Las implementaciones con ámbito de inquilino (tenant-scoped) no promocionan automáticamente a su primer usuario registrado; aprovisione a los administradores de inquilino a través de un flujo administrativo de confianza. Si necesita agregar un administrador manualmente, puede [acceder a MongoDB](/docs/configuration/mongodb/mongodb_auth) y actualizar el perfil del usuario:

```
db.users.updateOne(
  { email: 'USER_EMAIL_ADDRESS' },
  { $set: { role: 'ADMIN' } }
)
```

El uso de agentes para todos los usuarios también se puede deshabilitar a través de la configuración, [más información](/docs/configuration/librechat_yaml/object_structure/interface).

Los permisos a nivel de función (quién puede _usar_, _crear_, _compartir_ o _compartir públicamente_ agentes) se gestionan desde el [**LibreChat Admin Panel**](/docs/features/admin_panel) en cada rol, incluyendo cualquier rol personalizado. El bloque [`interface.agents`](/docs/configuration/librechat_yaml/object_structure/interface#agents) en `librechat.yaml` todavía puede establecer valores predeterminados para el rol `USER` integrado al inicio, pero el panel de administración es la forma recomendada para editarlos de ahora en adelante.

### Uso compartido a nivel de usuario [#user-level-sharing]

Los usuarios individuales pueden:

- Compartir sus agentes con usuarios, grupos o roles específicos (si `SHARE` está habilitado para su rol)
- Hacer que los agentes sean visibles para todos en la instancia (si `SHARE_PUBLIC` está habilitado)
- Otorgue a cada destinatario un nivel de acceso diferente (Viewer / Editor / Owner)
- Vuelva a compartir o revoque el acceso en cualquier momento desde el diálogo de compartir

## Steering y mensajes en cola [#steering-and-queued-messages]

Mientras un Agent está respondiendo, puedes enviar otro mensaje desde el [composer](/docs/features/composer) de dos maneras:

- **Steer** inserta el mensaje en la ejecución actual en su siguiente paso de herramienta o agente, para que el agente pueda ajustar su trabajo antes de finalizar.
- **Queue** retiene el mensaje y lo envía como un turno de seguimiento normal una vez que se completa la respuesta actual.

Para las conversaciones de Agentes guardadas en un servidor actual, los seguimientos en cola ordinarios se almacenan en MongoDB. LibreChat preserva su orden FIFO y conserva su texto, archivos adjuntos, extractos citados y Skills seleccionadas manualmente a través de desconexiones del navegador, reinicios de la aplicación y transferencias de réplicas. El procesamiento espera a que la respuesta precedente se estabilice antes de admitir el siguiente turno. Esta durabilidad es automática y no tiene ningún interruptor en YAML o en el entorno; los servidores más antiguos y las ventanas de inicio cortas sin una época de generación activa conservan la cola de compatibilidad del lado del cliente.

La admisión al servidor se serializa dentro de cada carril de cola de conversación. Si la evidencia del predecesor o la propiedad de versiones mixtas es ambigua, LibreChat muestra **Awaiting reconciliation** y bloquea o falla el turno en cola afectado en lugar de adivinar e iniciarlo fuera de orden.

**Steer sooner** le pide al agente que tome el mensaje en el siguiente punto seguro en lugar de esperar al siguiente paso de la herramienta. Si aún no es seguro conservar el texto de respuesta o la actividad de la herramienta, LibreChat espera durante un breve período de gracia, descarta el intento silencioso o de solo razonamiento, inserta el mensaje y reinicia el modelo con esa instrucción. Una vez que se puede conservar el texto de la respuesta, LibreChat se detiene en un límite seguro para el proveedor, preserva la respuesta parcial, inserta el mensaje y reanuda la misma respuesta del asistente. Una llamada a una herramienta en ejecución no se descarta ni se interrumpe por la dirección (steering); el mensaje se aplica cuando ese trabajo llega a un límite seguro.

Usa **Stop** para finalizar el razonamiento activo y solicitar la cancelación de una llamada a una herramienta en primer plano. Stop reenvía la cancelación para señalar a las herramientas en primer plano que admiten señales; el trabajo en segundo plano separado mantiene su ciclo de vida independiente. Usa el control dedicado del compositor, elígelo desde el menú del botón de envío o presiona `Command/Ctrl + Shift + .`. La acción recurre a la dirección ordinaria cuando el despliegue no puede interrumpir el flujo del proveedor activo.

En **Settings → Chat**, **While generating, Enter will** elige la acción predeterminada. El menú del botón de envío puede anular esa elección para un mensaje individual, y **Steer sooner on Enter** hace que Enter solicite ese punto seguro anterior cuando la dirección (steering) es la opción predeterminada.

Los archivos y los [fragmentos citados](/docs/features/message_actions#quote-excerpts) viajan con los mensajes de steer, queue e interrupt. Las Skills seleccionadas manualmente permanecen en espera para el siguiente turno completo en lugar de adjuntarse a un steer durante la ejecución.

Los steers pendientes aparecen al final de la respuesta en streaming, donde aterrizarán, hasta que el servidor los inserte en la ejecución. Su recepción progresa de **Sending** a **Delivered**, luego a **Steer sooner requested** cuando se solicitó un punto seguro anterior, y finalmente a **Applied** con una doble marca de verificación en el borde inferior derecho del mensaje en línea. Los recibos confirmados como aplicados permanecen visibles después de recargar y en las vistas de compartir o búsqueda; una entrega incierta o fallida nunca muestra una marca de verificación de confirmación. Una vez reconocido, el menú del mensaje puede reclamar el steer para editarlo, convertirlo en un seguimiento en cola, o cancelarlo y restaurar su texto y archivos adjuntos al compositor. LibreChat evita sobrescribir un borrador más reciente; si el compositor ya no está disponible, conserva el mensaje reclamado en la cola. Un steer fallido permanece disponible para reintentar, editar, poner en cola o eliminar.

Los seguimientos en cola aparecen en una lista sobre el compositor. Cada uno puede editarse (**Edit message**), eliminarse (**Remove message**), enviarse de inmediato con **Send now**, o reordenarse arrastrando su controlador o presionando las teclas de flecha sobre él. Los seguimientos en cola también pueden convertirse en una dirección (steer) mientras la ejecución sigue activa o escalarse con **Steer sooner**. Las direcciones en curso ofrecen la misma escalada cuando aún están esperando un límite de herramienta. Eliminar un mensaje en cola respaldado por el servidor primero cancela su fuente duradera y luego lo restaura a un compositor vacío cuando es posible. Si la respuesta precedente se aborta o falla, LibreChat marca el turno en cola afectado como fallido para su revisión en lugar de enviarlo silenciosamente.

Una conversación puede tener hasta 100 turnos en cola activos. Cada turno en cola acepta hasta 16,000 caracteres y 10 archivos. Por separado, una ejecución activa acepta hasta 10 directrices (steers) pendientes; cada directriz puede incluir hasta 10 archivos y está limitada por [`STEER_MAX_LENGTH`](/docs/configuration/dotenv#agent-conversation-controls). **Steer sooner** continúa utilizando la ruta de dirección en vivo en lugar de mover un turno en cola al frente del carril FIFO duradero.

Las implementaciones de múltiples réplicas respaldadas por Redis negocian automáticamente el protocolo de generación v2. Siga la [guía de compatibilidad del protocolo de generación](/docs/configuration/redis#generation-protocol-compatibility) al actualizar desde una versión anterior a `v0.8.8-rc1`.

### Notas [#notes]

- Las instrucciones, los parámetros del modelo, los archivos adjuntos y las herramientas solo se muestran al usuario si tiene permisos de edición.
  - Un agente puede filtrar cualquier dato adjunto, ya sean instrucciones o archivos, a través de la conversación, así que asegúrese de que sus instrucciones sean robustas contra esto antes de otorgar acceso de Editor/Propietario o hacer que el agente sea público.
- Solo los autores originales, los administradores y los usuarios con permiso de Propietario pueden eliminar agentes compartidos
- Los Agents son privados para sus autores a menos que se compartan

## Entrega de eventos de agentes [#agent-event-delivery]

LibreChat incluye una capa de entrega neutral respecto a la fuente para eventos de Agentes asíncronos. Los adaptadores propiedad del despliegue pueden normalizar un webhook verificado, un mensaje de cola, un evento MCP, un evento de canal o un evento interno del producto en una nueva ejecución de Agente (`fire`), un nuevo turno en un Agente guardado y una rama existentes (`continue`), o una mutación de una ejecución activa (`steer`). Los adaptadores siguen siendo responsables de autenticar su fuente nativa, sanitizar las cargas útiles y seleccionar destinos de confianza antes de ponerlos en cola.

Los [endpoints de eventos de la API de Agents](/docs/features/agents_api#agent-events) en versión beta exponen acceso autenticado mediante `fire`, `continue` y `steer` a las claves de API de Remote Agents. Los sistemas externos pueden vincular un actor de origen a un Agente hijo directo y continuar ese actor a través de eventos sin necesidad de un interruptor de función adicional. LibreChat deriva la identidad del usuario, el inquilino y el origen a partir de la clave de API, aplica el acceso al Agente y los filtros de contenido, y requiere una clave de idempotencia. Este no es un receptor de webhook de propósito general sin autenticación; los adaptadores específicos del proveedor aún deben verificar las firmas de webhook nativas antes de realizar la llamada.

La función experimental [Scheduled Chats](/docs/features/scheduled_chats) es el primer productor integrado de LibreChat para esta capa. Crea entregas `fire` recurrentes para Agentes guardados y está deshabilitada hasta que un administrador decida activarla. Los Subagentes separados utilizan automáticamente la entrega `continue` idempotente para reactivar un Agente padre guardado después de que un hijo finaliza; los hijos cancelados y los Agentes padre efímeros están excluidos.

MongoDB almacena sobres versionados acotados, claves de idempotencia, carriles de ordenamiento, concesiones (leases), historial de reintentos, recibos duraderos y mensajes fallidos (dead letters). Los trabajadores utilizan una entrega al menos una vez (at-least-once) con reclamaciones protegidas (fenced claims) y retroceso exponencial acotado; los recibos exitosos caducan después de 90 días, mientras que los mensajes fallidos requieren una reencolación confiable explícita. Las entregas de tipo "Fire" crean una nueva conversación. Las entregas de tipo "Continue" crean un nuevo turno en la rama exacta de la conversación y se difieren mientras esa rama esté ejecutándose, pausada o finalizando. Los actores vinculados también tienen un buzón automático: un actor espera el resultado del manejo de su turno actual antes de despachar el siguiente evento, mientras que diferentes actores pueden ejecutarse en paralelo. Las entregas de tipo "Steer" deben identificar la conversación y generación existentes y utilizar una admisión estricta para que los reintentos ambiguos no puedan inyectar la misma instrucción dos veces.

Para las continuaciones vinculadas, el éxito del transporte inicia un ciclo de vida de manejo duradero independiente. Una entrega progresa de `started` a `applied`, `completed_no_action`, `failed` o `cancelled`. Las fuentes pueden requerir una herramienta exacta y un subconjunto de argumentos opcionales con `expectedAction`; LibreChat informa `applied` solo a partir de evidencia de herramientas coincidentes observadas por el host, nunca a partir de prosa escrita por el modelo. Los eventos de observación compatibles pueden compartir un lote `coalesce.key` delimitado mientras conservan un registro de idempotencia y un recibo por evento de origen. La continuación de puntos de control (checkpoint) se utiliza cuando es compatible y, de lo contrario, recurre al historial de mensajes duradero.

Los Bound Event Actors pueden pausar para esperar la intervención del usuario (Ask User) o la aprobación de herramientas y reanudar la invocación exacta del actor firmado a través de la interfaz normal de humano en el bucle (human-in-the-loop) de LibreChat. El buzón del actor permanece bloqueado hasta que esa pausa se reanuda o se resuelve, evitando que un evento posterior se adelante a la decisión. Estos actores requieren el checkpointer duradero de MongoDB. LibreChat selecciona automáticamente la continuación del punto de control o la reconstrucción del historial duradero a partir del estado del actor y la capacidad de solicitud; el trabajo existente de protocol-v1 permanece en la ruta del historial hasta que se agota.

Las Acciones Desacopladas (Detached Actions) iniciadas por Actores de Eventos se habilitan automáticamente cuando el almacén de generación integrado anuncia su compatibilidad. El actor permanece suspendido hasta que la evidencia terminal reanuda su invocación original, por lo que un lanzamiento en segundo plano por sí solo no satisface `expectedAction`. El almacén en memoria mantiene este ciclo de vida coherente mientras su proceso permanezca activo. Redis añade recuperación de reinicio duradera y transferencia de réplicas. El trabajo de finalización propiedad de la capacidad se aísla de los trabajadores más antiguos durante un drenaje de versión mixta; los operadores no seleccionan este comportamiento con un indicador de función (feature flag).

El host de ejecución normalmente llama al listener vinculado del proceso actual. Configure [`endpoints.agents.eventDriven.selfUrl`](/docs/configuration/librechat_yaml/object_structure/agents#eventdriven) solo cuando esta ruta de admisión interna confiable deba atravesar otro origen HTTP, como una puerta de enlace TLS.

## Migración requerida (v0.8.0-rc3+) [#migration-required-v080-rc3]

<Callout type="warning" title="Importante: Se requiere la migración de permisos de agente">
  A partir de la versión v0.8.0-rc3, LibreChat utiliza un nuevo sistema de permisos basado en listas de control de acceso (ACL) para los agentes. Si está actualizando desde una versión anterior, debe ejecutar la migración de permisos de agentes para que los agentes existentes sigan siendo accesibles.
</Callout>

### Qué hace la migración [#what-the-migration-does]

La migración de permisos de agentes transiciona a sus agentes de un modelo de propiedad simple a un sistema sofisticado basado en ACL con múltiples niveles de permisos:

- **OWNER**: Control total sobre el agente
- **EDITOR**: Puede ver y modificar el agente
- **VIEWER**: Acceso de solo lectura al agente

Sin ejecutar esta migración, los agentes existentes no serán accesibles a través de los nuevos endpoint de la API con reconocimiento de permisos.

### Ejecución de la migración [#running-the-migration]

Elija el comando apropiado según su método de despliegue:

#### 1. Para el `docker-compose.yml` predeterminado (si utiliza `docker compose up` para iniciar la aplicación): [#1-for-the-default-docker-composeyml-if-you-use-docker-compose-up-to-start-the-app]

**Vista previa de cambios (simulacro):**

```bash
docker compose exec api npm run migrate:agent-permissions:dry-run
```

**Ejecutar migración:**

```bash
docker compose exec api npm run migrate:agent-permissions
```

**Tamaño de lote personalizado (para conjuntos de datos grandes):**

```bash
docker compose exec api npm run migrate:agent-permissions:batch
```

#### 2. Para el `deploy-compose.yml` [#2-for-the-deploy-composeyml]

Si seguiste la [Guía de Docker para Ubuntu](/docs/remote/docker_linux):

**Vista previa de cambios (simulacro):**

```bash
docker exec -it LibreChat-API /bin/sh -c "cd .. && npm run migrate:agent-permissions:dry-run"
```

**Ejecutar migración:**

```bash
docker exec -it LibreChat-API /bin/sh -c "cd .. && npm run migrate:agent-permissions"
```

**Tamaño de lote personalizado (para conjuntos de datos grandes):**

```bash
docker exec -it LibreChat-API /bin/sh -c "cd .. && npm run migrate:agent-permissions:batch"
```

#### 3. Para desarrollo local (desde la raíz del proyecto): [#3-for-local-development-from-project-root]

**Vista previa de cambios (simulacro):**

```bash
npm run migrate:agent-permissions:dry-run
```

**Ejecutar migración:**

```bash
npm run migrate:agent-permissions
```

**Tamaño de lote personalizado (para conjuntos de datos grandes):**

```bash
npm run migrate:agent-permissions:batch
```

### Qué sucede durante la migración [#what-happens-during-migration]

- **Agentes Privados**: Permanecen accesibles solo para sus creadores (reciben permiso de OWNER)
- **Agentes compartidos**: Si un agente fue compartido previamente, recibirá las entradas de ACL correspondientes como un Agente Público (compartido con todos los usuarios)
- **Detección del sistema**: LibreChat detecta automáticamente los agentes no migrados al iniciarse y muestra una advertencia

Puedes ajustar los permisos del agente resultante a través de la interfaz de usuario del Agent Builder.

<Callout type="info" title="Nota">
  El mismo proceso de migración se aplica a los prompts. Si también tienes prompts existentes, ejecuta la migración de permisos de prompts usando los mismos comandos, pero reemplaza `agent` con `prompt` en los nombres de los comandos.
</Callout>

## ¿Qué sigue? [#whats-next]

Los Agents de LibreChat marcan el comienzo de una nueva era para la aplicación, donde los futuros pipelines podrán optimizarse mediante Agents para tareas y flujos de trabajo específicos a lo largo de su experiencia en LibreChat.

Las futuras actualizaciones incluirán:

- Mejoras generales a la experiencia actual de los Agentes
- Orquestación multi-agente para flujos de trabajo complejos
- Capacidad para personalizar agentes para diversas funciones: titulación (nombramiento de hilos de chat), gestión de memoria (contexto/historial del usuario) y mejora de prompts (asistencia/predicciones de entrada)
- Más herramientas, parámetros de herramientas configurables, creación dinámica de herramientas.

Además, la actualización introduce un nuevo paradigma para LibreChat, ya que su arquitectura subyacente proporciona una renovación muy necesaria para la aplicación, optimizando tanto la experiencia del usuario como el rendimiento general de la misma.

Para destacar una optimización notable, una generación de IA de aproximadamente 1000 tokens transferirá cerca de 1 MB de datos utilizando endpoints tradicionales (al momento de escribir esto, cualquier opción de endpoint además de Agents y AWS Bedrock).

Al usar un agente, la misma generación transferirá alrededor de 52 kb de datos, una reducción del 95% en la transferencia de datos, lo que supone una carga mucho menor tanto para el servidor como para el dispositivo del usuario.

---

Los AI Agents en LibreChat ofrecen una forma potente de crear asistentes especializados sin necesidad de conocimientos de programación, manteniendo al mismo tiempo la flexibilidad para trabajar con sus modelos y proveedores de IA preferidos.
