## Introducción [#introduction]

La API de Code Interpreter de LibreChat proporciona una forma segura y sencilla de ejecutar código y gestionar archivos a través de una interfaz de API simple. Ya sea que la utilices a través de los Agents de LibreChat o la integres directamente en tus aplicaciones, la API ofrece un potente entorno de sandbox para ejecutar código en múltiples lenguajes de programación.

<Callout type="info" title="Código abierto">

</Callout>

## Primeros pasos [#getting-started]

1. Despliegue el servicio [code-interpreter](https://github.com/ClickHouse/code-interpreter) (Docker Compose o Helm, consulte el README del repositorio)
2. Apunte LibreChat hacia él con `LIBRECHAT_CODE_BASEURL`
3. Configure la [autenticación JWT de LibreChat](#self-hosted-jwt-authentication) para el servicio de código abierto actual, o establezca `LIBRECHAT_CODE_API_KEY` para un despliegue compatible con claves de API.
4. Para experimentar con sesiones de Agente con estado (stateful), despliegue una ruta de Intérprete de Código con perfil `stateful` independiente y configure `LIBRECHAT_CODE_BASEURL_STATEFUL` o [`statefulCodeSessions.environments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions) con nombre.
5. Comience a ejecutar código y generar archivos de forma segura a través de los Agents de LibreChat o el botón "Run Code"

## Características clave [#key-features]

### Idiomas admitidos [#supported-languages]

Ejecutar código en múltiples lenguajes de programación:

- Python, Node.js (JS/TS), Go, C/C++, Java, PHP, Rust, Fortran, Rscript

### Gestión de archivos sin interrupciones [#seamless-file-handling]

- Subir archivos para su procesamiento
- Descargar resultados generados
- Gestión segura de archivos
- Organización de archivos basada en sesiones

LibreChat restaura los archivos de conversación referenciados en entornos de Code Interpreter gestionados antes de la ejecución de un Agente. Si todos los archivos de Code Interpreter requeridos fallan en la recuperación, la ejecución se detiene antes de la invocación del modelo y solicita al usuario que vuelva a adjuntar los archivos en lugar de continuar con referencias obsoletas. En un espacio de trabajo adjunto seleccionado, las cargas de chat **no** se copian en el espacio de trabajo del usuario, y las herramientas de espacio de trabajo y Bash no pueden abrirlas allí. Si el trabajador anuncia Programmatic Bash con retransmisión de archivos (file relay), esa herramienta verá en su lugar las cargas almacenadas bajo `$LIBRECHAT_CODE_DATA_DIR` durante la duración de su ejecución.

Las cargas de la API de código se recuperan de los límites de tasa `429` respetando `Retry-After`, reabriendo el flujo de origen para cada intento y compartiendo un presupuesto de espera limitado. Los administradores pueden ajustar la recuperación por usuario y por ruta con [`codeApiUploadConcurrency` y `codeApiMaxRetryWaitMs`](/docs/configuration/librechat_yaml/object_structure/agents#code-api-upload-recovery).

Cuando las entradas de la conversación se montan en el mismo destino de sandbox, LibreChat resuelve la colisión antes de la ejecución. Los archivos de conversación compartidos se asignan antes que los archivos privados del Agente; dentro de cada ámbito, la escritura de contenido más reciente mantiene el destino original. Las rutas conflictivas se aplanan cuando es necesario o reciben un sufijo derivado de la identidad, y las rutas `/mnt/data/...` resueltas se incluyen en el contexto de archivo del Agente. Esto también cubre el caso en que una carga y una salida generada comparten un nombre de archivo, de modo que una colisión no rechace cada ejecución posterior del Intérprete de Código en la conversación. Las referencias de semilla duplicadas que aún se resuelven en un destino ya reclamado se omiten en lugar de hacer fallar la solicitud completa.

Las imágenes del Sandbox se transfieren en ventanas delimitadas. Establezca [`LIBRECHAT_CODE_SANDBOX_OUTPUT_MAX_SIZE`](/docs/configuration/dotenv#code-interpreter) para que coincida con el `SANDBOX_OUTPUT_MAX_SIZE` del worker; LibreChat deriva la ventana de imagen segura más grande a partir de ese presupuesto y puede aprender un límite por servicio más pequeño después de una lectura fallida. Utilice `LIBRECHAT_CODE_IMAGE_CHUNK_BYTES` solo cuando se requiera una anulación exacta de la ventana. Los artefactos generados descargados previamente se reutilizan dentro de la solicitud cuando es posible, evitando otra lectura del sandbox.

En un grafo de múltiples Agentes, asigne nombres de archivo distintos a los archivos privados de diferentes Agentes. Cada Agente resuelve sus rutas de archivo privadas antes de que el grafo combine sus entradas, por lo que los archivos privados genuinamente diferentes que reclaman de forma independiente el mismo destino aún no pueden renombrarse de manera consistente al momento de la fusión; el primer destino sembrado es el que prevalece.

### Seguridad y Conveniencia [#security--convenience]

- Entorno de ejecución aislado y seguro (sandboxed)
- Modos de aislamiento fuerte (NsJail o microVM mediante libkrun)
- No se requiere configuración local para los usuarios finales
- Almacenamiento de archivos aislado basado en sesiones

### Programmatic Tool Calling [#programmatic-tool-calling]

Programmatic Tool Calling permite que los agentes de LibreChat enruten herramientas MCP seleccionadas a través del sandbox de Code Interpreter. En lugar de pedirle al modelo que llame a cada herramienta directamente, LibreChat proporciona una herramienta de orquestación respaldada por Code Interpreter; el código de sandbox generado puede llamar a stubs de herramientas registrados, utilizar bucles y condicionales, procesar resultados intermedios y devolver una respuesta final.

El sandbox todavía no recibe acceso general a la red. Las llamadas a herramientas se gestionan a través del Code Interpreter Tool Call Server. LibreChat intersecta la proyección de capacidad del llamador en vivo con su registro de confianza, por lo que solo se pueden llamar herramientas programáticas activas ya registradas para el Agent y una solicitud no puede expandir su propio acceso.

Las herramientas programáticas requieren Code Interpreter en el Agent. Sus interruptores permanecen desactivados hasta que se selecciona Code Interpreter, y eliminar Code Interpreter borra las selecciones programáticas existentes. LibreChat también elimina las opciones de llamadas programáticas obsoletas de las operaciones de creación, actualización, duplicación y restauración de versiones del Agent cuando `execute_code` o la herramienta Code Interpreter no están disponibles.

Durante una ejecución programática, expande la tarjeta de Code Interpreter para ver un seguimiento en tiempo real, al estilo de una terminal, de las llamadas a herramientas internas con vistas previas de argumentos limitadas, estados, duraciones y fallos. Este seguimiento ayuda a inspeccionar el programa mientras se ejecuta, pero no se conserva tras recargar la página.

### Ejecución de código en segundo plano [#background-code-execution]

La ejecución en segundo plano permite que un Agent envíe código de larga duración o trabajo de shell y continúe la conversación. Para los Agents guardados, las finalizaciones de solo contenido compatibles se entregan automáticamente en una continuación de seguimiento de forma predeterminada. `check_background_task` sigue estando disponible para obtener el estado explícito, control, artefactos en vivo y recuperación. En el chat de LibreChat, cuando el trabajo finaliza, stdout y los archivos generados aparecen en la llamada de código original y se conservan para los turnos posteriores. Las finalizaciones en segundo plano y las comprobaciones explícitas renderizan tarjetas de tarea con el estado, el estado de entrega y resultados legibles; el resultado original exacto permanece disponible para copiar. El encabezado del chat agrupa las tareas en ejecución y recientes, y ofrece controles individuales o para detener todo cuando la política de cancelación del despliegue lo permite.

Esta función es opcional a nivel de despliegue. Agregue `run_in_background` junto a `execute_code` en las [capacidades del endpoint de Agents](/docs/configuration/librechat_yaml/object_structure/agents#capabilities), luego habilite Code Interpreter en el agente. La ejecución de código y las llamadas al shell se vuelven elegibles para ejecutarse en segundo plano automáticamente; desactive **Background execution** en la configuración de la herramienta Code Interpreter cuando un agente deba optar por no participar. El modelo aún decide por cada llamada si enviar el trabajo elegible al segundo plano.

La ejecución en segundo plano ordinaria sigue siendo local al proceso y no sobrevive a la pérdida de su trabajador de la aplicación. Una vez que se persiste un resultado de terminal de solo contenido, su entrega automática es duradera y puede continuar en otra réplica; las tareas con un artefacto activo aún requieren sondeo en la ejecución propietaria. Establezca [`endpoints.agents.backgroundTasks.completionWakeups: false`](/docs/configuration/librechat_yaml/object_structure/agents#backgroundtasks) para requerir sondeo para cada resultado. El despacho en segundo plano no extiende el límite de ejecución del servicio Code Interpreter; el tiempo de espera normal del lado del servidor de la implementación sigue aplicándose.

Con [`ordinaryToolCancellation: true`](/docs/configuration/librechat_yaml/object_structure/agents#backgroundtasks), los propietarios pueden solicitar la cancelación cooperativa de herramientas de código en segundo plano ordinarias, incluido Bash adjunto. La tarea permanece activa y consume capacidad hasta que la invocación se estabiliza; una herramienta que ignore la cancelación aún podría completarse.

### Sesiones de código con estado [#stateful-code-sessions]

Las sesiones de código con estado permiten que un agente de LibreChat reutilice un espacio de trabajo de sandbox de Code Interpreter a través de varias ejecuciones. Los archivos, los paquetes instalados y el estado de trabajo generalmente se mantienen, lo que hace que el análisis iterativo y la generación de archivos en varios pasos sean más eficientes. Cada agente selecciona un ámbito de espacio de trabajo:

- **Espacio de trabajo del usuario (recomendado):** un espacio de trabajo para el usuario que ha iniciado sesión en todos los agentes con estado habilitado
- **Espacio de trabajo de agente + usuario:** un espacio de trabajo para cada combinación de usuario y agente
- **Área de trabajo de conversación:** un área de trabajo para cada usuario y conversación

Para los Agents recién creados, el ámbito inicial proviene de **Settings > Data Controls > Code execution > Default stateful workspace**. La configuración personal tiene como valor predeterminado **User workspace**; cambiarlo no modifica los Agents existentes ni habilita sesiones con estado. Los administradores de despliegue pueden restringir los ámbitos seleccionables con [`statefulCodeSessions.allowedEnvironments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions). Si un valor predeterminado personal guardado deja de estar disponible, los nuevos Agents utilizarán el primer ámbito permitido; un Agent habilitado existente con un ámbito ahora no permitido debe ser reconfigurado antes de poder ejecutarse.

El ámbito del espacio de trabajo es independiente de su backend de ejecución. Cuando los administradores configuran [`statefulCodeSessions.environments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions) con nombre, el Creador de Agentes añade un selector de **Entorno de ejecución**:

- **Managed:** una API de código con estado operada por el despliegue
- **Adjunto:** un puente remoto de API de código compatible que delega el trabajo a un trabajador `@librechat/code` saliente, como una máquina virtual gestionada por un operador
- **Personal:** un trabajador `@librechat/code` vinculado al propietario y emparejado por un usuario autorizado a través de la configuración de LibreChat
- **Deployment default:** el entorno configurado marcado como predeterminado

<Callout type="warning" title="Altamente experimental">
  Las Stateful Code Sessions se encuentran en una fase de experimentación temprana. Su comportamiento, configuración, características de persistencia e integración subyacente pueden cambiar sustancialmente. No trate la implementación actual como un contrato de producción estable.
</Callout>

Esta función es opcional. Habilite `execute_code` y `stateful_code_sessions` en las [capacidades del endpoint de Agents](/docs/configuration/librechat_yaml/object_structure/agents#capabilities), configure una ruta con estado dedicada con [`LIBRECHAT_CODE_BASEURL_STATEFUL`](/docs/configuration/dotenv#stateful-code-interpreter-endpoint) o entornos con nombre, habilite Code Interpreter en el agente, luego active **Stateful code sessions** y elija su backend de ejecución y ámbito de espacio de trabajo en la configuración avanzada.

Las solicitudes con estado (stateful) fallan de forma segura (fail closed) cuando el entorno seleccionado falta, es inaccesible o es incompatible; LibreChat no las envía a `LIBRECHAT_CODE_BASEURL` ni elige silenciosamente otro backend nombrado. Cuando no hay entornos nombrados configurados, `LIBRECHAT_CODE_BASEURL_STATEFUL` sigue siendo la ruta con estado. Los agentes sin estado (stateless) continúan utilizando el endpoint normal. LibreChat también envía `X-CodeAPI-Expected-Profile: stateful`, por lo que el servicio dedicado debe anunciar el perfil `stateful`.

Las sesiones con estado (stateful) y sin estado (stateless) no comparten un espacio de trabajo activo. El espacio de trabajo con estado puede reiniciarse en cualquier momento, independientemente del ámbito seleccionado. En entornos de Code Interpreter gestionados, guarde los resultados importantes en `/mnt/data` y no confíe en el estado de la sesión como almacenamiento duradero. Un espacio de trabajo adjunto es un directorio independiente propiedad del trabajador; las subidas no se colocan allí de forma predeterminada.

Los archivos creados por llamadas con estado `create_file` y `edit_file` aparecen en el mensaje del asistente bajo una fila expandible de **Workspace changes**. Esta enumera cada ruta modificada de forma única para esa respuesta y proporciona una acción de descarga autenticada. Las descargas utilizan el flujo de archivos persistido de LibreChat cuando está disponible y, de lo contrario, un respaldo seguro de Code Interpreter. La fila es un registro de las salidas creadas, no una instantánea duradera del espacio de trabajo; las salidas sin estado continúan apareciendo como archivos adjuntos en línea regulares.

#### Entornos adjuntos y emparejamiento [#attached-environments-and-pairing]

Attached environments require a matching experimental Code Interpreter remote-bridge build. The bridge remains LibreChat's authenticated policy, queue, and result boundary, while the `@librechat/code` worker connects outbound from the attached machine; the machine does not need an inbound public worker port. LibreChat does not prewarm attached environments.

Un operador puede fijar un entorno adjunto propiedad de la implementación a un trabajador con `workerId`, y puede añadir `pairing.workerId` cuando LibreChat deba emitir un código de emparejamiento de administrador para esa misma ruta. `pairing.tokenEnv` nombra la variable de entorno que contiene el token de administrador del puente; el secreto en sí nunca debe incluirse en el YAML. Los planos de control emparejados requieren HTTPS fuera del desarrollo en loopback.

Para los workers de autoservicio, configure un plano de control adjunto propiedad del despliegue con `pairing.allowPrincipalWorkers: true` y `pairing.tokenEnv`. Puede omitir tanto los IDs de los workers como existir únicamente como un plano de control de inscripción; dicha entrada no es seleccionable para la ejecución y no puede ser el valor predeterminado del despliegue.

Los usuarios con permiso de gestión de Code Environment pueden abrir **Settings > Code environments**, asignar un nombre al entorno, elegir un plano de control aprobado y seleccionar **Connect VM**. LibreChat mostrará un comando `librechat-code pair ...` de un solo uso y corta duración. Ejecútelo en la VM del usuario y luego inicie `@librechat/code` con `LIBRECHAT_CODE_SANDBOX_ENDPOINT` apuntando al servicio sandbox de esa máquina. La interfaz de usuario enumera los entornos del usuario y permite revocarlos y eliminarlos más tarde; los archivos del sandbox permanecen en la VM.

Los administradores pueden limitar la inscripción con [`statefulCodeSessions.principalWorkers`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions). La inscripción está habilitada de forma predeterminada con un máximo de cinco entornos registrados por usuario cuando se omite este bloque. El recuento incluye trabajadores fuera de línea en cada plano de control. La configuración de despliegue es el límite máximo: la configuración específica del principal puede reducirlo o deshabilitarlo, pero no puede aumentarlo. Restringir la política no revoca las máquinas que ya están registradas.

Los entornos personales están vinculados al usuario autenticado y al inquilino, protegidos por ACL de Code Environment y asignados únicamente con IDs validados por el servidor y URLs base aprobadas. LibreChat no expone el token del administrador del puente ni URLs de operador arbitrarias al cliente. Eliminar un entorno revoca su credencial de trabajador antes de borrar la entrada del registro, y la eliminación de un usuario programa la misma revocación y limpieza con una reconciliación en segundo plano para los intentos interrumpidos. La ruta del trabajador seleccionada se aplica de manera consistente a Code Interpreter, shell, acceso a archivos generados y Programmatic Tool Calling.

Los agentes que utilizan un workspace adjunto pueden listar su árbol de directorios, leer archivos, buscar contenido en archivos, crear o editar archivos y ejecutar Bash en el worker seleccionado. Las citas de archivos utilizan rutas relativas al workspace, los archivos creados aparecen en la fila **Workspace changes** de la respuesta, y los fallos de las herramientas preservan los diagnósticos HTTP delimitados del worker. Un agente también puede almacenar un nombre y correo electrónico de Git por agente para los commits creados en ese workspace; estos valores configuran únicamente la autoría y no proporcionan credenciales de repositorio.

En el chat, un comando Bash de workspace adjunto que ha fallado muestra su código de salida, señal de terminación o tiempo de espera, y su stderr se presenta con un estilo diferente al de stdout. Consulta [Activity Groups](/docs/features/agents#activity-groups) para ver cómo se muestra la salida de Bash.

Un trabajador adjunto anuncia las raíces del espacio de trabajo que pone a disposición. El compositor permite al usuario seleccionar un espacio de trabajo para cada entorno adjunto accesible a través del Agent o sus Subagents; se selecciona automáticamente un único espacio de trabajo inequívoco para una nueva conversación. LibreChat almacena estas selecciones en la conversación, las revalida frente al trabajador activo antes de la ejecución y las mantiene fijas durante las pausas de aprobación y las ejecuciones reanudadas. El envío se bloquea cuando falta una selección requerida o no está disponible, y LibreChat nunca sustituye silenciosamente otro espacio de trabajo. Al inicio de una ejecución, LibreChat puede cargar instrucciones del repositorio desde el espacio de trabajo seleccionado para que el Agent siga la guía de ese repositorio; los administradores pueden limitar la detección con [`repositoryInstructions.timeoutMs`](/docs/configuration/librechat_yaml/object_structure/agents#repositoryinstructions). Las herramientas nativas de archivo y Bash del espacio de trabajo pueden utilizar una raíz anunciada incluso cuando el trabajador no admite sesiones de tiempo de ejecución reutilizables. Programmatic Bash con reconocimiento del espacio de trabajo está disponible en las compilaciones de Code API y trabajadores compatibles cuando la configuración de herramientas programáticas del Agent lo permite, el trabajador adjunto autorizado está listo y anuncia `programmaticLanguages: ['bash']`, y tanto el espacio de trabajo seleccionado como el trabajador permiten `execute_command`. LibreChat pasa el ID del espacio de trabajo validado por el servidor y el ID de instancia del espacio de trabajo de la conversación, cuando están presentes, a la herramienta programática; los argumentos del modelo no pueden reemplazar esa selección. Sin estas capacidades, Programmatic Bash está deshabilitado; utilice Bash directo para comandos con reconocimiento del espacio de trabajo. Cuando el trabajador admite retransmisión de archivos, las cargas de chat se preparan por separado bajo `$LIBRECHAT_CODE_DATA_DIR` para la ejecución programática, no se copian en el espacio de trabajo seleccionado. **Stop** cancela un comando BYOM en curso que reconoce señales sin invalidar el espacio de trabajo para comandos posteriores; el trabajo separado conserva su propio ciclo de vida de cancelación.

Para un entorno de ejecución adjunto, el Agent Builder puede establecer un **Workspace default** (predeterminado del espacio de trabajo) a una raíz anunciada actualmente. Se valida contra ese entorno adjunto y se utiliza para inicializar nuevas conversaciones para ese Agent. Elija **Last used** (Último utilizado) para usar la preferencia local del navegador del usuario que ha iniciado sesión para ese Agent y entorno; es solo una sugerencia de conveniencia, nunca una concesión de autorización o vinculación de conversación. Cambiar el entorno de ejecución borra un valor predeterminado explícito, y una raíz guardada que ya no se anuncia permanece visible pero no puede seleccionarse hasta que se vuelva a configurar.

#### Cambios en el área de trabajo de chats guardados [#saved-chat-workspace-changes]

De forma predeterminada, la decisión de espacio de trabajo adjunto de una conversación guardada está sellada. Con [`statefulCodeSessions.conversationMoves.enabled`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions) habilitado, el propietario puede moverse explícitamente a otro espacio de trabajo autorizado o recuperar un espacio de trabajo perdido. La recuperación preserva el historial del chat, **no** los archivos del espacio de trabajo perdido. Configurar `allowAttachDetach: true` permite además que el propietario adjunte un espacio de trabajo a un chat guardado que no sea de programación o abandonar un espacio de trabajo adjunto para continuar con un chat normal; habilitar los movimientos por sí solo no habilita adjuntar/separar. Estas transiciones no pueden realizarse mientras se está ejecutando una generación y son revalidadas en el servidor. Actualice todas las réplicas de la API y habilite `CODE_ENVIRONMENT_DECISION_VERSION=1` antes de optar por participar. Sin estos interruptores, el comportamiento existente de solo movimiento y conversación sellada permanece sin cambios.

Bash adjunto utiliza un tiempo de espera de 30 segundos de forma predeterminada. Un entorno puede exponer un presupuesto solicitable por el modelo más amplio con [`configSchema.limits.maxCommandTimeoutMs`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions), hasta el límite del protocolo de cinco minutos. El tiempo de espera solicitado nunca supera el límite de despliegue. Los administradores pueden limitar por separado los reintentos de capacidad con [`configSchema.limits.maxQueueWaitMs`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions); esta espera en cola no cancela un comando admitido o en ejecución. Para permitir intentos de admisión **individuales** más largos, utilice `configSchema.limits.maxRequestTimeoutMs` solo después de que la Code API respete la asignación de cola por solicitud y se verifique el tiempo de espera de proxy más corto en la ruta activa. El parámetro opcional `configSchema.limits.minCommandAdmissionMs` reserva 10 segundos por defecto (válido de 1 a 300 segundos) para la admisión antes de un comando. El tiempo de espera de Bash anunciado se ajusta al presupuesto de la solicitud después de esta reserva y otros 10 segundos para la resolución y entrega. Este presupuesto no reemplaza a `maxQueueWaitMs`.

#### Carriles de linked-worktree [#linked-worktree-lanes]

Los entornos adjuntos pueden optar por la [programación de solicitudes por worktree](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions) con `configSchema.workspaces.linkedWorktrees: true`. Primero actualice LibreChat, luego despliegue un puente de Code API compatible e inicie el worker con `--linked-worktree-lanes`; habilite la configuración YAML solo después de que ese worker anuncie `git_linked_worktree`. Las solicitudes que se dirigen estructuralmente a `.worktrees/<name>/` utilizan el carril (lane) de ese worktree sin cambiar las rutas relativas al checkout que se muestran al Agent. Para Bash, pase el directorio del worktree en el argumento `cwd` de la herramienta; ejecutar `cd .worktrees/<name>` dentro del comando permanece en el carril raíz. Las operaciones en la raíz del checkout, las acciones del entorno y las instancias del espacio de trabajo de la conversación también permanecen con ámbito en la raíz. Sin esta opción, todas las solicitudes mantienen su programación existente en todo el checkout.

#### Coincidencia de edición y conflictos en el Workspace [#workspace-edit-matching-and-conflicts]

`edit_file` acepta un `replace_all` de nivel superior para un reemplazo único de `old_text`/`new_text`, o un flag por entrada cuando se proporciona un lote de `edits`. Sin él, cada `old_text` debe resolverse en una única ubicación. Un lote proporcionado debe ser válido y no estar vacío; LibreChat rechaza un valor de `edits` vacío o mal formado en lugar de recurrir a los campos de reemplazo de nivel superior. Los lotes serializados en JSON y los flags de reemplazo booleanos válidos se normalizan antes de la aprobación de la herramienta nativa, por lo que la vista previa y la ejecución utilizan las mismas ediciones canónicas, incluyendo las reescrituras de hooks revisadas. Las ediciones en Skill-file y en el sandbox gestionado admiten el reemplazo de todas las coincidencias dentro de los límites de tamaño y recuento de coincidencias de LibreChat; los espacios de trabajo adjuntos requieren un worker que admita `replace_all` y rechazan las solicitudes no compatibles antes del envío.

En los workers adjuntos que anuncian `tolerant_match`, las ediciones y las vistas previas protegidas intentan primero una coincidencia exacta y, posteriormente, estrategias tolerantes a espacios en blanco para espacios finales, CRLF, cambios de sangría o espacios en blanco normalizados. Los administradores pueden requerir coincidencias exactas con [`configSchema.edits.tolerantMatching: false`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions). Los mensajes de éxito identifican coincidencias no exactas o reemplazos múltiples. Los lotes fallidos son atómicos: no se escribe nada y LibreChat informa razones delimitadas por edición, conteos, números de línea candidatos o una advertencia de archivo modificado sin reenviar texto arbitrario del worker ni extractos de archivos.

Estas funciones de worker adjunto requieren una API de código y compilaciones de worker compatibles que implementen [Code Interpreter #271](https://github.com/LibreChat-AI/code-interpreter/pull/271). LibreChat solo envía los nuevos campos después de la negociación de capacidades. Con compilaciones más antiguas, el formato de solicitud y el comportamiento de coincidencia permanecen sin cambios; actualizar LibreChat por sí solo no habilita las ediciones adjuntas tolerantes ni `replace_all`.

#### Permisos de herramientas del entorno adjunto [#attached-environment-tool-permissions]

Los entornos adjuntos y personales utilizan una política de aprobación de "preguntar por defecto" para la escritura de archivos y la ejecución de comandos o código. Las operaciones de solo lectura y búsqueda continúan bajo la política de herramientas regular del despliegue. Si el administrador expone cualquiera de las dos categorías a través de [`configSchema.permissions`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions), los usuarios con permiso de gestión de Code Environment pueden elegir entre los valores permitidos **Allow**, **Ask** o **Deny** en **Settings > Code environments**. Los ajustes faltantes, obsoletos o no permitidos recurren de forma segura a **Ask**.

El compositor muestra un **Modo de aprobación de código** a nivel de conversación siempre que el entorno adjunto seleccionado lo admita:

- **Ask before changes** solicita confirmación antes de realizar ediciones de archivos o ejecutar comandos.
- **Accept edits** permite ediciones de archivos pero continúa preguntando antes de ejecutar comandos.
- **Acceso completo** permite ambas categorías sin avisos rutinarios.

El modo seleccionado viaja con esa conversación y se intersecta con los valores permitidos del despliegue y la política del entorno. **Full access** solo aparece cuando tanto `fileWrite` como `commandExecution` permiten `allow`; no omite el aislamiento del sandbox, las concesiones de roles, las reglas explícitas de `ask` o `deny` del endpoint, la confirmación de Skill-file ni los hooks de aprobación.

Una importación de conversación no puede seleccionar un modo de aprobación de código para su destinatario. Las conversaciones nuevas importadas o copiadas de forma masiva utilizan la preferencia/valor predeterminado del destinatario según la política actual; las actualizaciones masivas conservan cualquier elección almacenada localmente. Las conversaciones existentes no se restablecen retroactivamente, y seleccionar explícitamente un modo en LibreChat sigue persistiendo dicha elección.

Estos controles cubren herramientas de creación de archivos, ejecución de shell y código, comprobaciones de compilación y Programmatic Tool Calling. Las escrituras en archivos de Skill persistentes aún requieren confirmación cuando la creación de Skill está disponible, incluso cuando se permiten las escrituras de archivos ordinarias. La configuración no cambia el aislamiento de VM, las redes, los montajes, la ejecución privilegiada, la entrada, la salida o el acceso a secretos.

El ajuste explícito [`toolApproval.enabled: false`](/docs/configuration/librechat_yaml/object_structure/agents#toolapproval) de la implementación es una anulación de emergencia que deshabilita esta línea base. Sin esa anulación, una llamada que no pueda presentar y reanudar solicitudes de aprobación fallará de forma cerrada en lugar de ejecutar silenciosamente una herramienta de entorno adjunto.

El emparejamiento autentica el transporte del trabajador remoto; no es un límite de entorno aislado (sandbox). Mantenga el endpoint de ejecución local del trabajador en loopback o en una red privada y utilice un modo de aislamiento adecuado para código no confiable.

Mientras una ejecución está activa, los paneles de detalles de código y shell expandidos siguen los argumentos transmitidos hasta la parte inferior. Desplazarse hacia arriba pausa el comportamiento de seguimiento para que pueda inspeccionar la salida anterior sin que el panel desplace la vista.

## Uso de la API [#using-the-api]

### En LibreChat [#in-librechat]

La API tiene soporte de primera clase en LibreChat a través de estos métodos principales:

1. **[Agentes de IA](/docs/features/agents#code-interpreter)**: Habilite el Code Interpreter en la configuración de su agente para permitirle ejecutar código y procesar archivos automáticamente.

2. **Ejecución manual**: Utilice el botón "Run Code" en los bloques de código dentro de la interfaz de chat, como se muestra aquí:

3. **[Programmatic Tool Calling](/docs/features/agents#programmatic-tool-calling)**: Habilite la capacidad `programmatic_tools` y marque las herramientas MCP seleccionadas como Programmatic para que los agentes puedan orquestar dichas herramientas desde código en entorno aislado (sandboxed).

4. **[Background Tool Calls](/docs/features/agents#background-tool-calls)**: Permite que un agente ejecute código elegible en segundo plano y continúe mientras este se procesa.

5. **[Stateful Code Sessions](/docs/features/agents#stateful-code-sessions)**: Reutilice de forma experimental un espacio de trabajo con ámbito de usuario, de agente y usuario, o de conversación a través de las ejecuciones de código de un agente.

![Intérprete de código en LibreChat](/images/agents/run_code.png)

### Configurar la API key [#set-up-api-key]

- **Configuración por usuario:** Ingrese su clave de API en LibreChat cuando se le solicite.
- **Configuración global:** Establezca `LIBRECHAT_CODE_API_KEY` en el archivo `.env` de LibreChat para proporcionar una clave para todos los usuarios.

El servicio actual de [ClickHouse/code-interpreter](https://github.com/ClickHouse/code-interpreter) utiliza la autenticación JWT de LibreChat fuera del modo local. Las API keys siguen estando disponibles para despliegues de Code Interpreter compatibles.

### Autenticación JWT autohospedada [#self-hosted-jwt-authentication]

Con la autenticación JWT, LibreChat firma un token de portador de corta duración para el usuario autenticado en cada solicitud de Code Interpreter. El servicio de Code Interpreter verifica la clave pública correspondiente y utiliza el contexto del usuario y del inquilino firmado para aislar los archivos y las sesiones. La clave privada de firma permanece en LibreChat; Code Interpreter solo recibe su verificador público.

Configure LibreChat con:

```env
CODEAPI_AUTH_PROVIDER=librechat-jwt
CODEAPI_JWT_PRIVATE_KEY="-----BEGIN PRIVATE KEY-----\n...\n-----END PRIVATE KEY-----"
CODEAPI_JWT_ALGORITHM=EdDSA
CODEAPI_JWT_KID=lc-codeapi-2026-05
CODEAPI_JWT_ISSUER=librechat
CODEAPI_JWT_AUDIENCE=codeapi
CODEAPI_JWT_TTL_SECONDS=300
CODEAPI_JWT_MINT_CACHE_SECONDS=30
CODEAPI_JWT_SINGLE_TENANT_ID=legacy
```

`CODEAPI_JWT_PRIVATE_KEY_BASE64` puede contener un PEM codificado en base64, y `CODEAPI_JWT_PRIVATE_JWK_JSON` acepta un JWK privado. LibreChat admite la firma con Ed25519 (`EdDSA`, el valor predeterminado) y RSA (`RS256`). Consulta la [referencia de variables de entorno](/docs/configuration/dotenv#code-interpreter-jwt-authentication) para ver todos los ajustes del lado de LibreChat.

Configure el Code Interpreter con el verifier correspondiente:

```env
LOCAL_MODE=false
CODEAPI_AUTH_PROVIDER=librechat-jwt
CODEAPI_JWT_ISSUER=librechat
CODEAPI_JWT_AUDIENCE=codeapi
CODEAPI_JWT_ALLOWED_ALGS=EdDSA
CODEAPI_JWT_JWKS_JSON={"keys":[{"kty":"OKP","crv":"Ed25519","x":"...","kid":"lc-codeapi-2026-05","alg":"EdDSA"}]}
CODEAPI_JWT_SINGLE_TENANT_ID=legacy
```

El emisor, la audiencia, el ID de clave, el algoritmo y la clave pública deben coincidir con el firmante de LibreChat. Code Interpreter también puede cargar claves de verificación desde `CODEAPI_JWT_PUBLIC_KEY` más `CODEAPI_JWT_KID`, o desde `CODEAPI_JWT_PUBLIC_KEYS_DIR`; un JWKS en línea es conveniente para la rotación. Mantenga el TTL del token en o por debajo del `CODEAPI_JWT_MAX_TTL_SECONDS` del servicio de Code Interpreter, que tiene un valor predeterminado y un límite máximo de 300 segundos.

Para una instalación local, el repositorio de Code Interpreter incluye una herramienta auxiliar que genera claves Ed25519 de firma y de manifiesto de ejecución coincidentes, y actualiza ambos archivos `.env`:

```bash
node scripts/setup-local-auth-env.js --librechat /path/to/LibreChat
```

Las implementaciones de inquilino único (single-tenant) pueden dejar `CODEAPI_JWT_SINGLE_TENANT_ID=legacy`, pero el valor debe coincidir en ambos servicios. Las implementaciones multi-inquilino (multi-tenant) deben proporcionar un contexto de inquilino autenticado y habilitar `TENANT_ISOLATION_STRICT=true` en LibreChat además de `CODEAPI_TENANT_ISOLATION_STRICT=true` en Code Interpreter. El modo estricto rechaza las solicitudes sin contexto de inquilino en lugar de utilizar la alternativa de inquilino único.

### Integración directa de API [#direct-api-integration]

El servicio autohospedado actual espera un token bearer que satisfaga su contrato de reclamación JWT de LibreChat. Una integración directa debe generar tokens de corta duración compatibles y enviarlos en el encabezado `Authorization: Bearer <token>`. Las implementaciones compatibles con API-key aceptan, en su lugar, su clave configurada en el encabezado `x-api-key`. Nunca utilice el modo local sin autenticación de Code Interpreter en un endpoint público o de producción.

### URL base autoalojada [#self-hosted-base-url]

Establezca `LIBRECHAT_CODE_BASEURL` para apuntar LibreChat a su instancia de [code-interpreter](https://github.com/ClickHouse/code-interpreter) autohospedada, luego configure la [autenticación JWT](#self-hosted-jwt-authentication). Para un servicio compatible con API-key, establezca `LIBRECHAT_CODE_API_KEY` en su lugar. Las sesiones de agente con estado altamente experimentales requieren una ruta de perfil `stateful` separada configurada a través de [`LIBRECHAT_CODE_BASEURL_STATEFUL`](/docs/configuration/dotenv#stateful-code-interpreter-endpoint) o denominada [`statefulCodeSessions.environments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions).

## Funcionalidad principal [#core-functionality]

### Ejecución de código [#code-execution]

- Ejecutar fragmentos de código en lenguajes compatibles
- Recibir salida stdout/stderr
- Obtener estadísticas de ejecución (uso de memoria, tiempo de CPU)
- Gestionar argumentos del programa
- Acceder al estado de ejecución y a los resultados

### Operaciones de archivos [#file-operations]

- Subir archivos de entrada
- Descargar resultados generados
- Obtenga una vista previa de archivos de Office generados, incluyendo presentaciones de PowerPoint `.pptx` y plantillas `.potx`, además de artefactos tipo CSV, texto y PDF directamente cuando LibreChat pueda extraerlos/renderizarlos de forma segura
- Mostrar imágenes PNG, JPEG, GIF y WebP devueltas por la herramienta `read_file` de un agente como artefactos visualizables
- Listar archivos disponibles
- Eliminar archivos innecesarios
- Gestionar sesiones de archivos

Las vistas previas de artefactos generados están limitadas en tamaño intencionalmente. Configure [`FILE_PREVIEW_MAX_EXTRACT_BYTES`](/docs/configuration/dotenv#inline-file-previews) en el archivo `.env` de LibreChat para cambiar el límite de tamaño del archivo fuente para la extracción de vistas previas en línea; los archivos más grandes seguirán estando disponibles para su descarga.

Las imágenes del Sandbox devueltas a través de `read_file` tienen un límite en línea de 1 MiB. Las imágenes más grandes permanecen en el sandbox para su procesamiento con `bash_tool`. `LIBRECHAT_CODE_IMAGE_CHUNK_BYTES` controla únicamente el tamaño del fragmento de transporte utilizado al leer imágenes elegibles; no aumenta el límite en línea.

<Callout type="warning" title="Verificación de actualización para salidas de código heredado">
  Las implementaciones que regeneraron el mismo nombre de archivo de Code Interpreter antes de que se añadiera el índice único de archivos de salida pueden tener registros duplicados en MongoDB que impiden la creación del índice. Previsualice la reparación con `npm run migrate:code-file-duplicates:dry-run`, luego aplíquela con `npm run migrate:code-file-duplicates`. La migración conserva el nombre de archivo canónico más reciente, renombra los registros antiguos con sufijos numéricos y construye el índice único después de una ejecución exitosa.
</Callout>

### Limitaciones [#limitations]
- El código no puede acceder a la red
- Solo se pueden generar 10 archivos por ejecución
- Los límites de recursos (RAM por ejecución, tamaño de carga de archivos y cuotas de solicitud) dependen de cómo aprovisione y configure su despliegue.

## Casos de uso [#use-cases]

- **Pruebas de código**: Pruebe fragmentos de código en múltiples lenguajes
- **Procesamiento de archivos**: Transforme y analice archivos mediante programación
- **Aplicaciones de IA**: Ejecute código generado por IA de forma segura
- **Herramientas de desarrollo**: Cree entornos de programación interactivos
- **Lógica del objetivo**: Verificar la lógica y la exactitud del código, mejorando los modelos de IA

## Código abierto y autoalojamiento [#open-source--self-hosting]

El servicio de Code Interpreter es de código abierto bajo la licencia Apache 2.0 en [ClickHouse/code-interpreter](https://github.com/ClickHouse/code-interpreter). Mantener la ejecución de código como un servicio separado permite que la aplicación principal de LibreChat sea ligera: solo despliegas la infraestructura de sandbox cuando la necesitas, y puedes escalarla independientemente de la aplicación de chat.

El servicio se ejecuta como un conjunto de componentes escalables de forma independiente (una puerta de enlace API, trabajadores en entorno aislado y un servidor de archivos) y admite modos de aislamiento robustos (NsJail o una microVM a través de libkrun) para que pueda ejecutar código no confiable de manera segura. Consulte el README del repositorio para obtener instrucciones de despliegue con Docker Compose y Helm.

## Conclusión [#conclusion]

La API de Code Interpreter proporciona una forma segura y conveniente de ejecutar código y gestionar archivos en un entorno aislado (sandbox). Ya sea que la utilices a través de los Agents de LibreChat o la integres directamente en tus aplicaciones, ofrece una solución robusta para las necesidades de ejecución de código.

Para obtener especificaciones técnicas detalladas, guías de despliegue y la referencia de la API, consulte el [code-interpreter repository](https://github.com/ClickHouse/code-interpreter).
