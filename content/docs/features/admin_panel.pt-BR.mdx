# Painel de Administração do LibreChat [#librechat-admin-panel]

O **LibreChat Admin Panel** é uma interface de gerenciamento independente baseada em navegador para o LibreChat. Ele se conecta ao mesmo banco de dados que o próprio LibreChat e fornece uma GUI para as tarefas administrativas que impulsionam o [granular access control](/docs/features/access_control): administração de usuários e grupos, gerenciamento de funções, substituições de configuração com escopo para funções ou grupos e concessões de recursos em nível de sistema.

<Callout type="info" title="Status: Prévia">
  O painel de administração é distribuído como o serviço `admin-panel` em `docker-compose.yml` e `deploy-compose.yml` e é construído sobre as APIs de administração introduzidas no [LibreChat v0.8.5](/changelog/v0.8.5). O código-fonte, as issues e as releases estão disponíveis em [github.com/ClickHouse/librechat-admin-panel](https://github.com/ClickHouse/librechat-admin-panel).
</Callout>

## O que ele faz [#what-it-does]

O painel de administração é um cliente leve: todos os dados residem no banco de dados do LibreChat, e cada ação passa pelos endpoints versionados `/api/admin/*` no servidor da API do LibreChat. Ele oferece aos administradores um local único para:

- **Gerenciar configuração**: visualize e edite todas as configurações do LibreChat por meio de um formulário dinâmico baseado em esquema. Novos campos adicionados ao esquema de configuração aparecem automaticamente, sem a necessidade de lançamento de painel administrativo.
- **Aplicar substituições por principal**: limite as substituições de configuração a funções, grupos ou usuários específicos, com uma cascata baseada em prioridade que determina o valor final resolvido que cada usuário vê no login.
- **Administrar usuários**: listar, pesquisar e visualizar todas as contas na instância.
- **Gerenciar grupos**: crie e exclua grupos, adicione/remova membros e use grupos como principais de primeira classe em ACLs e substituições (overrides).
- **Gerenciar funções**: crie funções personalizadas além das nativas `USER` / `ADMIN`, edite sua matriz de permissões de recursos e atribua usuários a funções.
- **Concessões do sistema de permissões**: delegue capacidades administrativas (por exemplo, `manage:users`, `read:usage`, `manage:mcpservers`) a usuários, grupos ou funções específicos sem torná-los administradores completos.
- **Autenticar**: faça login com uma conta de administrador local do LibreChat, ou via SSO OpenID / SAML / provedores OAuth suportados quando estes estiverem habilitados na instância do LibreChat.

Para o modelo de permissão subjacente (principais, ACLs de recursos, capacidades e como as camadas se compõem), consulte a página [Access Control](/docs/features/access_control).

## Arquitetura [#architecture]

```
┌──────────────────┐         ┌──────────────────┐         ┌──────────────┐
│  Admin Panel     │ ───────▶│  LibreChat API   │ ───────▶│   MongoDB    │
│  (Bun + Vite)    │  HTTPS  │  /api/admin/*    │         │  (shared DB) │
└──────────────────┘         └──────────────────┘         └──────────────┘
       │                             │
       │ OAuth/OIDC/SAML redirect    │ Verifies admin access
       └─────────────────────────────┘
```

O painel de administração é executado como um serviço separado; ele não compartilha um processo com o LibreChat. As capacidades de administração são verificadas no lado do LibreChat por meio da permissão do sistema `access:admin` ou da função `SystemRoles.ADMIN`, portanto, o painel não pode conceder a si mesmo privilégios que não deveria ter.

A superfície da API de administrador exposta pelo LibreChat é:

| Montagem | Finalidade |
| ----------------------------------------- | ------------------------------------------------------------------------------- |
| `POST /api/admin/login` &nbsp; `/oauth/*` | Endpoints de autenticação específicos do administrador (local + SSO) |
| `GET /api/admin/verify` | Valida a sessão do administrador |
| `/api/admin/users` | Listagem e pesquisa de usuários |
| `/api/admin/groups` | CRUD de grupos + gerenciamento de membros |
| `/api/admin/roles` | CRUD de funções personalizadas + edição de permissões + gerenciamento de membros |
| `/api/admin/grants` | Concessões de capacidades do sistema (atribuir/revogar/listar) |
| `/api/admin/config` | Configuração base + substituições de configuração por principal |
| `/api/admin/skills` | Sincronização de skills do GitHub: status, execução e credenciais de sincronização |
| `/api/admin/code-environments` | Parear e revogar workers de ambientes de código (`manage:code_environments`) |
| `/api/admin/langfuse` | Leitura, atualização e teste da conexão com o Langfuse, além de links de sessão por conversa |
| `/api/admin/audit-log` | Log de auditoria de concessões (`read:audit_log`) |

Os endpoints de log de auditoria são `GET /` (listagem), `GET /export.csv` (exportação em CSV), `GET /verify` (verificação de integridade) e `GET /:id` (entrada individual). Eles exigem `access:admin` e `read:audit_log`. O log é somente de anexação (append-only), portanto não há capacidade de gerenciamento nem endpoint de escrita.

## Primeiros Passos [#getting-started]

### Pré-requisitos [#prerequisites]

- Uma instância do LibreChat em execução na **v0.8.5 ou posterior** (as APIs de administrador não estão disponíveis em versões anteriores)
- Acesso de rede do container/host do admin-panel para a API do LibreChat
- Uma conta de administrador no LibreChat: ou o primeiro usuário registrado em uma implantação de locatário único sem escopo (auto-admin), um usuário com `role: 'ADMIN'` definido no Mongo, ou um principal ao qual foi concedida a capacidade `access:admin`. Implantações com escopo de locatário devem provisionar seus administradores por meio de um fluxo administrativo confiável.

### Empacotado com o LibreChat (recomendado) [#bundled-with-librechat-recommended]

Se você executa o LibreChat com seu [`docker-compose.yml`](https://github.com/LibreChat-AI/LibreChat/blob/main/docker-compose.yml) oficial ou com o [`deploy-compose.yml`](https://github.com/LibreChat-AI/LibreChat/blob/main/deploy-compose.yml), o painel de administração é incluído como um serviço e é iniciado automaticamente junto com o LibreChat, sem necessidade de uma implantação separada.

| Arquivo Compose | URL do painel de administração | Como é servido |
| --------------- | ------------------------------ | -------------- |
| `docker-compose.yml` (padrão) | `http://localhost:3000` | Publicado em uma porta do host (`ADMIN_PANEL_PORT`, padrão `3000`) |
| `deploy-compose.yml` | `http://admin.localhost` | Roteado pelo proxy reverso nginx incluído, em um subdomínio |

Defina o segredo de sessão do painel no `.env` do LibreChat antes de iniciar a stack; os arquivos compose o transmitem como o `SESSION_SECRET` do painel:

```bash filename=".env"
# Min 32 characters. Generate with: openssl rand -hex 32
ADMIN_PANEL_SESSION_SECRET=replace-with-a-32-char-random-string

# Optional: host port for the default docker-compose
# ADMIN_PANEL_PORT=3000

# Optional: set true when the panel is served over HTTPS
# ADMIN_PANEL_SESSION_COOKIE_SECURE=false
```

Os arquivos compose conectam o restante automaticamente: `API_SERVER_URL` aponta para o serviço `api`, `VITE_API_BASE_URL` segue `DOMAIN_CLIENT` para redirecionamentos de OAuth voltados ao navegador, e `ADMIN_PANEL_URL` é definido para que o LibreChat retorne os administradores ao painel após o SSO. Para optar por não utilizar, remova o serviço `admin-panel` ou proteja-o atrás de uma entrada de [`profiles`](https://docs.docker.com/compose/how-tos/profiles/) do Compose.

<Callout type="info" title="admin.localhost em um domínio real">
  Navegadores modernos resolvem `*.localhost` (incluindo `admin.localhost`) para `127.0.0.1`, portanto a URL do deploy-compose funciona sem alterações no arquivo hosts. Para um domínio real, aponte um registro DNS para o host, atualize o `server_name` `admin.localhost` em `client/nginx.conf` e defina `ADMIN_PANEL_URL` para corresponder.
</Callout>

### Standalone (implantação separada) [#standalone-separate-deployment]

Para hospedar o painel de administração por conta própria, apontando para uma instância do LibreChat executando em outro lugar, use a imagem publicada no registro do LibreChat (`registry.librechat.ai/librechat-ai/librechat-admin-panel:latest`, a imagem utilizada pelos arquivos compose incluídos):

```bash
# 1. Create an env file
cp .env.example .env

# 2. Edit .env and set at minimum:
#    SESSION_SECRET=<random string, min 32 characters>
#    VITE_API_BASE_URL=http://host.docker.internal:3080

# 3. Start it
docker compose up -d   # http://localhost:3000
docker compose down    # stop
```

`docker run` autônomo:

```bash
docker run -p 3000:3000 \
  --add-host=host.docker.internal:host-gateway \
  -e SESSION_SECRET=replace-with-32-char-random-string \
  -e VITE_API_BASE_URL=http://host.docker.internal:3080 \
  registry.librechat.ai/librechat-ai/librechat-admin-panel:latest
```

<Callout type="warning" title="Rede no Docker">
  Dentro de um container, `localhost` refere-se ao próprio container, não ao seu host. Quando o LibreChat é executado no mesmo host, aponte `VITE_API_BASE_URL` para `http://host.docker.internal:3080` (Linux: adicione `--add-host=host.docker.internal:host-gateway`). Em produção, use o nome DNS público/interno da sua API do LibreChat.
</Callout>

### Executar Localmente para Desenvolvimento [#run-locally-for-development]

```bash
git clone https://github.com/ClickHouse/librechat-admin-panel.git
cd librechat-admin-panel
cp .env.example .env    # then edit
bun install
bun dev                 # http://localhost:3000
```

## Variáveis de Ambiente [#environment-variables]

| Variável | Obrigatória | Padrão | Descrição |
| -------- | ----------- | ------ | --------- |
| `SESSION_SECRET` | **Sim** em produção | Fallback fixo para desenvolvimento ao executar `bun dev`; **sem padrão** na imagem Docker | Chave de criptografia da sessão. Deve ter pelo menos 32 caracteres. |
| `VITE_API_BASE_URL` | **Sim** no Docker | `http://localhost:3080` (somente desenvolvimento local) | URL do servidor de API do LibreChat voltada para o navegador, usada para redirecionamentos do OAuth. |
| `API_SERVER_URL` | Não | Usa `VITE_API_BASE_URL` como fallback | URL do lado do servidor para as chamadas à API do LibreChat. Útil quando o servidor do painel administrativo acessa o LibreChat por uma URL diferente da usada pelo navegador (por exemplo, serviço interno do Kubernetes versus nome de host público). |
| `PORT` | Não | `3000` | Porta na qual o painel administrativo escuta. |
| `ADMIN_PANEL_SESSION_SECRET` | **Sim** | _não definida_ | Variável do lado do LibreChat mapeada para o `SESSION_SECRET` do painel administrativo no serviço do painel incluído. Gere um valor exclusivo com pelo menos 32 caracteres antes de iniciar o painel. |
| `ADMIN_PANEL_PORT` | Não | `3000` | Porta do host exposta pelo serviço do painel administrativo incluído no `docker-compose.yml` padrão. |
| `ADMIN_SSO_ONLY` | Não | `false` | Oculta o formulário de e-mail e senha, forçando o login somente por SSO. |
| `ADMIN_SESSION_IDLE_TIMEOUT_MS` | Não | `1800000` (30 min) | Tempo limite de inatividade da sessão, em milissegundos. |
| `SESSION_COOKIE_SECURE` | Não | `true` em produção | Define se o cookie de sessão exige HTTPS. |
| `ADMIN_PANEL_METRICS_SECRET` | Não | _não definida_ | Token Bearer exigido para coletar o endpoint `/metrics` do Prometheus. O endpoint retorna `401` quando não está definido ou não corresponde. |

Nos stacks Docker integrados do LibreChat, o painel administrativo é executado como um serviço `admin-panel`. O `docker-compose.yml` padrão o expõe na `ADMIN_PANEL_PORT`; o `deploy-compose.yml` o roteia através do nginx em `http://admin.localhost` e define a `ADMIN_PANEL_URL` para o serviço de API. O painel se recusa a iniciar até que a `ADMIN_PANEL_SESSION_SECRET` seja configurada.

### URL de redirecionamento do LibreChat [#librechat-redirect-url]

Quando o painel administrativo estiver hospedado em uma URL separada do LibreChat, defina `ADMIN_PANEL_URL` no ambiente da API do LibreChat. Use a URL base externa do painel administrativo, incluindo qualquer prefixo de caminho, e omita a barra final:

```bash filename=".env"
ADMIN_PANEL_URL=https://admin.example.com/admin
```

Quando definido, o LibreChat também exibe um link para o **Painel de Administração** aos administradores em **Configurações > Geral**. Usuários não administradores não veem o link.

Para implantações via Helm, defina `librechat.adminPanelUrl` no seu arquivo values. O chart o renderiza como `ADMIN_PANEL_URL` para o fluxo de OAuth do painel administrativo do LibreChat:

```yaml filename="values.yaml"
librechat:
  adminPanelUrl: https://admin.example.com/admin
```

Para OpenID SSO, registre `${DOMAIN_SERVER}/api/admin/oauth/openid/callback` com seu provedor de identidade.

### Controles de Cache [#cache-controls]

Estes espelham as variáveis de ambiente de cache do LibreChat. As variantes `ADMIN_PANEL_*` têm precedência, recorrendo aos equivalentes compartilhados do LibreChat quando não definidas.

| Variável | Propósito |
| --------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| `STATIC_CACHE_MAX_AGE` / `ADMIN_PANEL_STATIC_CACHE_MAX_AGE`     | `max-age` do navegador em segundos para ativos com hash em `/assets/` (padrão 172800 = 2 dias). |
| `STATIC_CACHE_S_MAX_AGE` / `ADMIN_PANEL_STATIC_CACHE_S_MAX_AGE` | `s-maxage` da CDN em segundos (padrão 86400 = 1 dia). |
| `INDEX_CACHE_CONTROL` / `ADMIN_PANEL_INDEX_CACHE_CONTROL`       | Cabeçalho `Cache-Control` para a resposta do índice HTML. |
| `INDEX_PRAGMA` / `ADMIN_PANEL_INDEX_PRAGMA`                     | Cabeçalho `Pragma` para a resposta do índice HTML. |
| `INDEX_EXPIRES` / `ADMIN_PANEL_INDEX_EXPIRES`                   | Cabeçalho `Expires` para a resposta do índice HTML. |

## Autenticação [#authentication]

O painel de administração reutiliza a pilha de autenticação do LibreChat e não possui seu próprio banco de dados de usuários. Dois caminhos de login são suportados:

- **Contas locais**: nome de usuário/senha para qualquer usuário do LibreChat cuja conta passe na verificação de acesso de administrador.
- **Single sign-on**: OpenID Connect, SAML e os provedores OAuth sociais já configurados na sua instância do LibreChat. Defina `ADMIN_SSO_ONLY=true` para ocultar o formulário de senha completamente.

O acesso de administrador é verificado no lado do servidor pelo LibreChat para cada solicitação. A conta deve:

1. Tenha `role: 'ADMIN'` no MongoDB, **ou**
2. Possuir a permissão de sistema `access:admin` (atribuída a outro principal através do próprio painel de administração; veja [System Grants](/docs/features/access_control#layer-3-system-grants-admin-capabilities)).

As sessões são baseadas em cookies, criptografadas com `SESSION_SECRET` e expiram por inatividade conforme `ADMIN_SESSION_IDLE_TIMEOUT_MS`.

O SSO de administrador do Google solicita acesso offline e consentimento para que o painel possa atualizar um token de administrador do LibreChat expirado sem forçar um novo login imediato. Configure tanto `GOOGLE_CLIENT_ID` quanto `GOOGLE_CLIENT_SECRET` e registre `${DOMAIN_SERVER}/api/admin/oauth/google/callback` no Google. Cada atualização verifica novamente a identidade do provedor da conta, o estado de banimento, o domínio de e-mail permitido, o tenant e o acesso de administrador atual; perder o acesso encerra a sessão de administrador.

## Gerenciamento de Configuração [#configuration-management]

O painel renderiza a configuração do LibreChat como um formulário dinâmico orientado pelo esquema de configuração. Isso possui duas propriedades úteis:

- **Compatível com versões futuras**: quando o LibreChat lança um novo campo de configuração, o painel o detecta automaticamente a partir do esquema. Nenhuma atualização ou reimplantação do painel de administração é necessária.
- **Sobreposições em camadas**: a configuração base (do `librechat.yaml`) pode ser sobreposta por substituições por principal, com escopo de função, grupo ou usuário. Quando um usuário faz login, os documentos aplicáveis são mesclados em uma ordem fixa: primeiro o perfil Base, independentemente de sua prioridade; em seguida, prioridade crescente; depois função antes de grupo, e grupo antes de usuário; e, por fim, a ordem de criação. Um novo perfil gravado sem prioridade recebe o padrão do seu tipo de principal (função 10, grupo 20, usuário 100, Base 0), e uma gravação que omite a prioridade mantém a armazenada.
- **Credenciais criptografadas**: as credenciais de servidores MCP, as chaves de grupos do Azure e as chaves de pesquisa na web armazenadas por meio da API de administração são criptografadas em repouso e retornadas somente como prévias mascaradas. Uma gravação que mantém uma chave armazenada, mas altera o destino para o qual ela é enviada (como uma URL de servidor ou uma URL base), deve informar a chave novamente.
- **Referências de ambiente**: As referências `${ENV_VAR}` em substituições são limitadas aos nomes que o `librechat.yaml` já referencia, às credenciais de endpoint integradas e aos nomes listados em `CONFIG_OVERRIDE_ENV_ALLOWLIST`. Qualquer outra referência é rejeitada na gravação.

<Callout type="warning" title="Servidores MCP baseados em processo permanecem no YAML">
  Servidores MCP que usam `type: stdio` ou campos de processo, como `command`, `args`, `env`, `cwd` ou `stderr`, são de propriedade do operador. Configure-os somente no `librechat.yaml`; a API de administração rejeita tentativas de criá-los ou modificá-los, e as substituições não podem substituir nem remover esses servidores. A configuração de servidores MCP remotos continua disponível pelo sistema normal de substituições.
</Callout>

<Callout type="warning" title="Cabeçalhos do gateway Langfuse permanecem no YAML">
  Os `langfuse.headers` em nível de implantação podem conter credenciais de proxy e não são uma superfície de configuração baseada no Mongo. Configure-os em `librechat.yaml`; a API de administração rejeita o mapa inteiro e também os caminhos de cabeçalho individuais. Consulte [Proxies e Gateways Autenticados](/docs/configuration/langfuse#authenticated-proxies-and-gateways).
</Callout>

Esta é a superfície por trás do [sistema de substituição de configuração por principal baseado em banco de dados](https://github.com/LibreChat-AI/LibreChat/pull/12354) do LibreChat. Casos de uso típicos:

- Dê a um grupo "Research" um `recursionLimit` maior e endpoints adicionais
- Permita que uma função "FinanceAdmins" gerencie servidores MCP remotos, enquanto usuários comuns apenas possam utilizá-los
- Limitar permissões de `interface` mais rigorosas a grupos de contratados externos

Os administradores também podem usar o painel [Admin Insights](/docs/features/insights), opcional, para revisar a atividade do MongoDB com escopo por tenant. Defina `ENABLE_INSIGHTS=true`; quem pode revisar quais Agents é descrito em [Admin Insights](/docs/features/insights#access-requirements).

### Substituir Validação [#override-validation]

As gravações de substituição (`PUT /api/admin/config/:principalType/:principalId` e `PATCH .../fields`) são validadas em relação ao mesmo esquema do `librechat.yaml`, aplicadas sobre a configuração base da implantação. Uma gravação que produziria uma configuração inválida é rejeitada com HTTP 400 e nada é salvo:

```json
{
  "error": "Invalid config override",
  "code": "CONFIG_OVERRIDE_INVALID",
  "issues": [{ "path": "interface.fileSearch", "code": "invalid_type" }]
}
```

Cada problema carrega apenas o caminho de pontos (dot-path) e um código estável (um código de problema de esquema como `invalid_type`, ou `missing_merge_key`, `duplicate_merge_key`, `indexed_merge_key_write`, `union_dropped_key` ou `invalid_document`), nunca o valor enviado. Um patch de campo só é rejeitado por problemas que ele toca ou introduz, portanto, um valor inválido mais antigo em outro lugar na mesma substituição (override) não o bloqueia.

Substituições armazenadas que se tornaram inválidas, por exemplo, após uma atualização que restringe o esquema, não são fatais. Quando a configuração é resolvida, os campos inválidos são descartados, o valor abaixo deles (geralmente o valor base do `librechat.yaml`) é aplicado e o servidor registra um aviso por campo:

```text
[mergeConfigOverrides] Ignoring invalid override "<path>" for <principalType>/<principalId> (<code>)
```

Verifique os logs em busca destas linhas após a atualização e, em seguida, corrija ou remova os campos listados no painel. Um tema de substituição que não segue as [regras de tema](/docs/configuration/librechat_yaml/object_structure/theme#validation) retorna ao tema base da mesma forma.

### Delegação com Escopo de Seção [#section-scoped-delegation]

As permissões de configuração podem ser amplas (`read:configs`, `manage:configs`) ou limitadas a uma seção de nível superior (`read:configs:<section>`, `manage:configs:<section>`). Um leitor com escopo de seção recebe uma resposta de configuração filtrada contendo apenas as seções autorizadas, em vez de ter a solicitação inteira negada. Permissões de gerenciamento em nível de seção implicam acesso de leitura à mesma seção; acesso amplo de gerenciamento implica acesso amplo de leitura.

Exemplos incluem `read:configs:interface`, `manage:configs:endpoints` e `manage:configs:langfuse`. Usuários delegados ainda precisam de `access:admin` para acessar a interface de administração. Toda mutação de criação, patch, tombstone ou exclusão do perfil base `__base__` requer `manage:configs` amplo; o gerenciamento com escopo de seção se aplica a substituições de função, grupo e usuário.

### Segredos Armazenados [#stored-secrets]

Quando campos secretos registrados são gravados por meio da API de configuração de administrador, o LibreChat criptografa valores literais em repouso e retorna apenas visualizações mascaradas geradas pelo servidor. Isso atualmente abrange Langfuse, OCR, fala, pesquisa na web, Assistants, Azure Assistants e cada `endpoints.custom[].apiKey`. Omitir um segredo durante uma edição posterior preserva o valor armazenado.

Referências de ambiente suportadas permanecem como referências legíveis para campos que as permitem. Chaves de API de endpoint personalizadas também preservam valores `${ENV_VAR}` e `user_provided` em vez de criptografá-los. O tratamento de segredos é baseado em registro: valores arbitrários em mapas genéricos, como cabeçalhos personalizados ou configuração de MCP, não são criptografados automaticamente, portanto, continue a usar referências de ambiente ou o mecanismo de credenciais dedicado do recurso nesses casos.

## Configuration Read APIs e Relatórios de Escrita [#configuration-read-apis-and-write-reports]

Chamadores autorizados podem inspecionar os recursos de implantação com `GET /api/admin/config/meta`, as opções de escopo/modelo com `/catalog`, o status das referências de ambiente com `/env-status`, a configuração efetiva da requisição com `/effective` e a configuração resolvida de um principal com `/resolved/:principalType/:principalId`. As leituras mantêm suas fronteiras de autorização e de mascaramento de segredos.

`POST /api/admin/config/:principalType/:principalId/changes` oferece suporte a alterações atômicas por perfil. Inspecione o relatório de gravação: os locais aplicados e os ignorados são distintos, e caminhos exclusivos de implantação podem ser ignorados sem rejeitar o lote inteiro. As leituras de documentos armazenados também podem informar campos ignorados; a ausência de um relatório não comprova que nenhum campo foi ignorado.

As operações de coleção com chave suportadas podem ocultar um endpoint personalizado pelo nome, juntamente com suas Model Specs, ou redefini-lo para herdar a configuração. As operações de renomeação suportadas e as dicas de renomeação carregam segredos registrados e lápides com chave; renomear uma chave bruta não é um substituto para essa operação.

`POST /api/admin/config/reload` recarrega a configuração local e transmite a invalidação. Ele pode retornar `503` depois que o recarregamento local for bem-sucedido, caso a transmissão entre instâncias falhe. Esse resultado não é um rollback e não garante que todas as réplicas tenham sido recarregadas. Consulte o [guia de atualização](/docs/configuration/upgrade#admin-configuration-and-secrets) para ver o limite da re-derivação de endpoints opcional.

### Partições de Tenant nas Leituras de Configuração [#tenant-partitions-in-configuration-reads]

Previews de perfil de grupo/usuário e a configuração efetiva do usuário são resolvidas no tenant do alvo, incluindo o perfil Base desse tenant e os perfis de função/grupo aplicáveis. Um chamador com escopo de tenant não pode acessar outro tenant. Nomes de função referem-se à partição do chamador: um administrador sem escopo altera funções da plataforma e seus membros, perfis, concessões e entradas de ACL, e não as funções de mesmo nome de todos os tenants.
