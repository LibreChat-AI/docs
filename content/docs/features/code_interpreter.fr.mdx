Le Code Interpreter exécute du code dans un bac à sable isolé. Les agents l'utilisent pour effectuer des calculs qu'ils devraient sinon deviner, analyser un tableur que vous avez téléversé, convertir des fichiers ou produire des graphiques et des documents. Vous pouvez également exécuter vous-même un bloc de code d'un message de conversation à l'aide de **Run Code**.

Le bac à sable est un service distinct, [ClickHouse/code-interpreter](https://github.com/ClickHouse/code-interpreter) (open source, Apache 2.0), que votre administrateur déploie à côté de LibreChat. Il prend en charge Python, Node.js (JavaScript et TypeScript), Go, C et C++, Java, PHP, Rust et Fortran.

## Donner à un agent l'exécution de code [#give-an-agent-code-execution]

Dans le Constructeur d'agents, sélectionnez **Ajouter** à côté de **Outils**, puis ajoutez **Exécuter du code**. Enregistrez l'agent. À partir de ce moment, l'agent décide quand exécuter du code ; vous n'avez pas besoin de le demander explicitement, bien que « utilise du code pour vérifier ceci » soit utile lorsque vous souhaitez une réponse exacte.

Pendant l'exécution du code, le message affiche une ligne repliable intitulée **Starting sandbox environment** la première fois, puis **Analyzing**, et **Finished analyzing** lorsque l'exécution est terminée. Développez-la pour voir le code écrit par l'agent ainsi que sa **Output**.

## Travailler avec des fichiers [#working-with-files]

Attachez un fichier et choisissez **Upload to Code Environment** pour le rendre disponible dans le bac à sable pour cette conversation. Les fichiers que vous ajoutez sous les paramètres Run Code de l'agent sont disponibles dans chaque conversation avec cet agent. Avant chaque exécution, LibreChat restaure les fichiers de la conversation dans le bac à sable ; si aucun des fichiers nécessaires à l'exécution ne peut être restauré, l'exécution s'arrête et vous demande de les joindre à nouveau, au lieu de travailler à partir de copies obsolètes.

Les fichiers générés par le code reviennent sous forme de lignes dans le message. Cliquez sur une ligne pour l'ouvrir dans le panneau [Artifacts](/docs/features/artifacts), ou pour le télécharger. Les fichiers HTML, Markdown, texte brut, code source, CSV et Office (Word, Excel, OpenDocument, présentations et modèles PowerPoint) bénéficient d'un aperçu intégré. Les fichiers plus volumineux ne sont pas prévisualisés et restent disponibles uniquement en téléchargement ; la limite par défaut est de 2 MiB de fichier source. Les images que l'agent lit depuis le bac à sable (PNG, JPEG, GIF, WebP) s'affichent directement dans le message jusqu'à 1 MiB ; les images plus grandes restent dans le bac à sable, où l'agent peut toujours les traiter.

## Exécuter un bloc de code vous-même [#run-a-code-block-yourself]

Les blocs de code dans les messages du chat affichent un bouton **Run Code** à côté du bouton **Copy code** lorsque le langage du bloc peut être exécuté par le bac à sable (Python, JavaScript, TypeScript, Go, C, C++, D, Java, PHP, Rust ou Fortran). Cliquez dessus et la sortie apparaît sous le bloc. Cela fonctionne dans toutes les conversations, pas seulement avec les agents.

## Code de longue durée [#long-running-code]

Si votre administrateur a activé les outils en arrière-plan, les paramètres d'exécution de code de l'agent affichent **Exécution en arrière-plan**, activée par défaut. L'agent peut lancer un code long, continuer à vous répondre, puis récupérer la sortie et les fichiers une fois l'exécution terminée ; par défaut, le résultat arrive automatiquement dans un message de suivi. Désactivez ce paramètre pour les agents qui doivent toujours attendre la fin de leur code.

La mémoire, le temps CPU, la taille des fichiers envoyés et l'accès réseau sont définis par la personne qui gère le service de bac à sable, et non par LibreChat. Si le code échoue avec une erreur de ressources, demandez à votre administrateur quelles sont les limites.

## Sessions de code avec état [#stateful-code-sessions]

Par défaut, chaque exécution est sans état : ne comptez pas sur la survie des variables ou des paquets installés d'une exécution à la suivante. Les sessions de code avec état, une fonctionnalité expérimentale que votre administrateur doit activer, donnent à un agent un espace de travail qui conserve ses fichiers sous `/mnt/data` entre les exécutions. Chaque exécution démarre toujours un nouveau processus, et l'espace de travail peut être réinitialisé à tout moment ; considérez-le donc comme une zone de travail temporaire plutôt que comme un espace de stockage.

Activez les **Sessions de code avec état** dans les paramètres Run Code de l'agent, puis sélectionnez un **Environnement avec état** :

- **Espace de travail utilisateur (recommandé)** : un espace de travail unique pour vous, partagé par tous les agents avec état que vous utilisez.
- **Espace de travail de l'agent et de l'utilisateur** : un espace de travail distinct pour chaque agent.
- **Espace de conversation** : un espace de travail neuf pour chaque conversation.

Les nouveaux agents démarrent avec la portée définie sous **Paramètres > Données et confidentialité > Exécution de code > Espace de travail avec état par défaut** ; modifier ce paramètre n'affecte pas les agents existants. Les fichiers que l'agent crée ou modifie dans un espace de travail avec état sont listés dans une ligne **Modifications de l'espace de travail** sous sa réponse, avec un lien de téléchargement pour chacun.

## Exécution de code sur votre propre machine [#running-code-on-your-own-machine]

Les administrateurs peuvent également proposer des environnements de code : une machine virtuelle ou une station de travail exécutant le worker `@librechat/code`, qui se connecte à LibreChat. Dans ce cas, le Constructeur d'agents affiche un sélecteur **Environnement d'exécution**, et **Machines disponibles dans les nouvelles discussions** permet à un agent de proposer plusieurs machines afin que chaque nouvelle discussion puisse en choisir une avec **Choisir une autre machine**.

Si vous disposez de l'autorisation de gérer les environnements de code, ajoutez le vôtre dans **Paramètres > Données et confidentialité > Exécution de code > Environnements de code** : donnez-lui un nom, sélectionnez **Connecter la VM**, puis exécutez sur votre machine la commande unique qui s'affiche. Si votre administrateur a activé la configuration par navigateur, la commande de configuration peut à la place ouvrir une page **Approuver la configuration de la machine**, où vous confirmez la demande tout en étant connecté.

Sur une machine attachée, l'agent peut parcourir, lire, rechercher et modifier des fichiers, ainsi qu'exécuter des commandes shell dans l'espace de travail sélectionné. Les pièces jointes que vous envoyez dans le chat sont copiées dans `.librechat/attachments` de cet espace de travail avant que l'agent ne démarre. Comme ces actions modifient une machine réelle, le compositeur affiche un **Mode d'approbation du code** pour la conversation :

- **Demander avant les modifications** : demande confirmation avant toute modification de fichier et toute exécution de commande.
- **Accepter les modifications** : modifie les fichiers sans demander de confirmation, mais demande toujours avant d'exécuter des commandes.
- **Accès complet** : modifie des fichiers et exécute des commandes sans demandes de confirmation de routine. Les limites du bac à sable sur la machine s'appliquent toujours.

Les modes que vous pouvez choisir dépendent de la politique de votre administrateur. Associer une machine authentifie le worker auprès de LibreChat ; cela n'isole rien en soi. Isolez donc le worker comme vous le feriez pour toute machine qui exécute du code non fiable.

## Appel des outils MCP depuis le code [#calling-mcp-tools-from-code]

Avec l'appel programmatique d'outils (Programmatic Tool Calling), un agent peut appeler certains outils MCP depuis l'intérieur du bac à sable (sandbox) : il écrit un script qui boucle sur des entrées, appelle des outils, filtre les résultats et ne renvoie que ce qui compte. Cela évite un aller-retour par le modèle pour chaque appel d'outil. Les interrupteurs Programmatic restent désactivés tant que l'agent n'a pas Run Code, et leur suppression de Run Code les réinitialise. Pendant l'exécution du script, développez sa ligne pour suivre la trace **Tool calls** ; cette trace n'est pas conservée après un rechargement de la page. Seuls les outils enregistrés auprès de l'agent peuvent être appelés de cette manière. Consultez [Programmatic Tool Calling](/docs/features/agents#programmatic-tool-calling) pour savoir comment marquer les outils.

## Configuration [#setup]

L'exécution de code nécessite qu'un administrateur déploie le service Code Interpreter et configure LibreChat pour l'utiliser ; tant que ce n'est pas fait, les exécutions échouent. Le bouton **Run Code** et la capacité de l'agent peuvent également être désactivés par rôle. L'exécution en arrière-plan, les sessions avec état et les environnements de code sont chacun optionnels. Voir [Configuration de Code Interpreter](/docs/configuration/tools/code_interpreter).
