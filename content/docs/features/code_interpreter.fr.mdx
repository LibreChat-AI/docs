## Introduction [#introduction]

L'API Code Interpreter de LibreChat offre un moyen sécurisé et sans tracas d'exécuter du code et de gérer des fichiers via une interface API simple. Que vous l'utilisiez via les Agents de LibreChat ou que vous l'intégriez directement dans vos applications, l'API offre un environnement sandbox puissant pour exécuter du code dans plusieurs langages de programmation.

</Callout>

## Démarrage [#getting-started]

1. Déployez le service [code-interpreter](https://github.com/ClickHouse/code-interpreter) (Docker Compose ou Helm, consultez le README du dépôt)
2. Pointez LibreChat vers celui-ci avec `LIBRECHAT_CODE_BASEURL`
3. Configurez [l'authentification JWT de LibreChat](#self-hosted-jwt-authentication) pour le service open-source actuel, ou définissez `LIBRECHAT_CODE_API_KEY` pour un déploiement compatible avec les clés API.
4. Pour expérimenter avec les sessions d'Agent avec état, déployez une route Code Interpreter avec un profil `stateful` distinct et configurez `LIBRECHAT_CODE_BASEURL_STATEFUL` ou les [`statefulCodeSessions.environments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions) nommés.
5. Commencez à exécuter du code et à générer des fichiers de manière sécurisée via les Agents de LibreChat ou le bouton "Run Code"

## Fonctionnalités clés [#key-features]

### Langues prises en charge [#supported-languages]

Exécutez du code dans plusieurs langages de programmation :

- Python, Node.js (JS/TS), Go, C/C++, Java, PHP, Rust, Fortran, Rscript

### Gestion transparente des fichiers [#seamless-file-handling]

- Téléverser des fichiers pour traitement
- Télécharger les sorties générées
- Gestion sécurisée des fichiers
- Organisation des fichiers basée sur la session

LibreChat restaure les fichiers de conversation référencés dans des environnements Code Interpreter gérés avant l'exécution d'un Agent. Si la récupération de tous les fichiers Code Interpreter requis échoue, l'exécution s'arrête avant l'invocation du modèle et demande à l'utilisateur de joindre à nouveau les fichiers plutôt que de continuer avec des références obsolètes. Dans un espace de travail joint sélectionné, les téléchargements du chat ne sont **pas** copiés dans l'espace de travail de l'utilisateur, et les outils de fichier et Bash de l'espace de travail ne peuvent pas les y ouvrir. Si le worker annonce Programmatic Bash avec relais de fichiers, cet outil voit plutôt les téléchargements mis en zone de transit sous `$LIBRECHAT_CODE_DATA_DIR` pour la durée de son exécution.

Les téléchargements de l'API Code récupèrent des limites de débit `429` en respectant `Retry-After`, en rouvrant le flux source pour chaque tentative et en partageant un budget d'attente limité. Les administrateurs peuvent ajuster la récupération par utilisateur et par route avec [`codeApiUploadConcurrency` et `codeApiMaxRetryWaitMs`](/docs/configuration/librechat_yaml/object_structure/agents#code-api-upload-recovery).

Lorsque les entrées de conversation sont montées vers la même destination de sandbox, LibreChat résout la collision avant l'exécution. Les fichiers de conversation partagés sont assignés avant les fichiers privés de l'Agent ; au sein de chaque portée, l'écriture de contenu la plus récente conserve la destination d'origine. Les chemins conflictuels sont aplatis si nécessaire ou reçoivent un suffixe dérivé de l'identité, et les chemins `/mnt/data/...` résolus sont inclus dans le contexte de fichier de l'Agent. Cela couvre également un téléchargement et une sortie générée qui partagent le même nom de fichier, afin qu'une collision ne rejette pas toutes les exécutions ultérieures de l'interpréteur de code dans la conversation. Les références de seed en double qui pointent toujours vers une destination déjà réclamée sont ignorées au lieu de faire échouer la requête complète.

Les images du Sandbox sont transférées dans des fenêtres délimitées. Définissez [`LIBRECHAT_CODE_SANDBOX_OUTPUT_MAX_SIZE`](/docs/configuration/dotenv#code-interpreter) pour qu'il corresponde à la valeur `SANDBOX_OUTPUT_MAX_SIZE` du worker ; LibreChat déduit la plus grande fenêtre d'image sécurisée à partir de ce budget et peut apprendre une limite plus petite par service après une lecture échouée. Utilisez `LIBRECHAT_CODE_IMAGE_CHUNK_BYTES` uniquement lorsqu'une substitution exacte de la fenêtre est requise. Les artefacts générés précédemment téléchargés sont réutilisés au sein de la requête lorsque cela est possible, évitant ainsi une nouvelle lecture du sandbox.

Dans un graphe multi-Agent, donnez des noms de fichiers distincts aux fichiers privés des différents Agents. Chaque Agent résout ses chemins de fichiers privés avant que le graphe ne combine leurs entrées ; par conséquent, des fichiers privés réellement différents qui revendiquent indépendamment la même destination ne peuvent pas encore être renommés de manière cohérente au moment de la fusion ; la première destination amorcée l'emporte.

### Sécurité et commodité [#security--convenience]

- Environnement d'exécution sécurisé et isolé (sandboxed)
- Modes d'isolation renforcés (NsJail ou microVM via libkrun)
- Aucune configuration locale requise pour les utilisateurs finaux
- Stockage de fichiers isolé, basé sur la session

### Appel d'outils programmatique [#programmatic-tool-calling]

L'appel d'outils programmatique (Programmatic Tool Calling) permet aux agents LibreChat d'acheminer les outils MCP sélectionnés via le bac à sable (sandbox) de l'interpréteur de code (Code Interpreter). Au lieu de demander au modèle d'appeler chaque outil directement, LibreChat fournit un outil d'orchestration basé sur l'interpréteur de code ; le code généré dans le bac à sable peut appeler des stubs d'outils enregistrés, utiliser des boucles et des conditions, traiter des résultats intermédiaires et renvoyer une réponse finale.

Le sandbox ne reçoit toujours pas d'accès réseau général. Les appels d'outils sont relayés par le Code Interpreter Tool Call Server. LibreChat croise la projection des capacités de l'appelant en direct avec son registre de confiance, de sorte que seuls les outils programmatiques actifs déjà enregistrés pour l'Agent peuvent être appelés et qu'une requête ne peut pas étendre son propre accès.

Les outils programmatiques nécessitent Code Interpreter sur l'Agent. Leurs commutateurs restent désactivés tant que Code Interpreter n'est pas sélectionné, et la suppression de Code Interpreter efface les sélections programmatiques existantes. LibreChat supprime également les options d'appelant programmatique obsolètes lors des opérations de création, de mise à jour, de duplication et de restauration de version d'un Agent lorsque `execute_code` ou l'outil Code Interpreter est indisponible.

Lors d'une exécution programmatique, développez la carte Code Interpreter pour voir une trace en direct, de type terminal, des appels d'outils internes avec des aperçus d'arguments limités, des statuts, des durées et des échecs. Cette trace aide à inspecter le programme pendant son exécution, mais elle n'est pas conservée après un rechargement de la page.

### Exécution de code en arrière-plan [#background-code-execution]

L'exécution en arrière-plan permet à un Agent de lancer du code ou des tâches shell de longue durée et de poursuivre la conversation. Pour les Agents enregistrés, les complétions de contenu prises en charge sont livrées automatiquement dans une suite de suivi par défaut. `check_background_task` reste disponible pour obtenir le statut explicite, le contrôle, les artefacts en direct et la récupération. Dans le chat LibreChat, lorsque le travail est terminé, stdout et les fichiers générés apparaissent sur l'appel de code original et sont conservés pour les tours suivants. Les complétions en arrière-plan et les vérifications explicites affichent des cartes de tâche avec le statut, l'état de livraison et des résultats lisibles ; le résultat original exact reste disponible pour être copié. L'en-tête du chat regroupe les tâches en cours et récentes et propose des contrôles individuels ou d'arrêt global lorsque la politique d'annulation du déploiement le permet.

Cette fonctionnalité est optionnelle au niveau du déploiement. Ajoutez `run_in_background` aux côtés de `execute_code` dans les [capacités du endpoint Agents](/docs/configuration/librechat_yaml/object_structure/agents#capabilities), puis activez l'interpréteur de code (Code Interpreter) sur l'agent. L'exécution de code et les appels shell deviennent automatiquement éligibles à l'arrière-plan ; désactivez **Background execution** dans les paramètres de l'outil Code Interpreter lorsqu'un agent doit s'en exclure. Le modèle décide toujours, pour chaque appel, s'il doit envoyer le travail éligible en arrière-plan.

L'exécution en arrière-plan ordinaire reste locale au processus et ne survit pas à la perte de son worker d'application. Une fois qu'un résultat de terminal contenant uniquement du contenu est persisté, sa livraison automatique est durable et peut se poursuivre sur une autre réplique ; les tâches avec un artefact actif nécessitent toujours une interrogation (polling) sur l'exécution propriétaire. Définissez [`endpoints.agents.backgroundTasks.completionWakeups: false`](/docs/configuration/librechat_yaml/object_structure/agents#backgroundtasks) pour exiger une interrogation pour chaque résultat. La répartition en arrière-plan ne prolonge pas la limite d'exécution du service Code Interpreter ; le délai d'attente côté serveur normal du déploiement s'applique toujours.

Avec [`ordinaryToolCancellation: true`](/docs/configuration/librechat_yaml/object_structure/agents#backgroundtasks), les propriétaires peuvent demander l'annulation coopérative des outils de code d'arrière-plan ordinaires, y compris Bash attaché. La tâche reste active et consomme de la capacité jusqu'à ce que l'invocation soit terminée ; un outil qui ignore l'annulation peut tout de même se terminer.

### Sessions de code avec état [#stateful-code-sessions]

Les sessions de code avec état permettent à un Agent LibreChat de réutiliser un espace de travail sandbox Code Interpreter entre les exécutions. Les fichiers, les paquets installés et l'état de fonctionnement sont généralement conservés, ce qui rend l'analyse itérative et la génération de fichiers en plusieurs étapes plus efficaces. Chaque agent sélectionne une portée d'espace de travail :

- **Espace de travail utilisateur (recommandé) :** un espace de travail pour l'utilisateur connecté à travers les agents avec état activé
- **Espace de travail agent + utilisateur :** un espace de travail pour chaque combinaison d'utilisateur et d'agent
- **Espace de travail de conversation :** un espace de travail pour chaque utilisateur et chaque conversation

Pour les Agents nouvellement créés, la portée initiale provient de **Paramètres > Contrôles des données > Exécution de code > Espace de travail avec état par défaut**. Le paramètre personnel est défini par défaut sur **Espace de travail utilisateur** ; le modifier ne modifie pas les Agents existants et n'active pas les sessions avec état. Les administrateurs de déploiement peuvent restreindre les portées sélectionnables avec [`statefulCodeSessions.allowedEnvironments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions). Si une valeur par défaut personnelle enregistrée devient indisponible, les nouveaux Agents utilisent la première portée autorisée ; un Agent activé existant avec une portée désormais non autorisée doit être reconfiguré avant de pouvoir s'exécuter.

La portée de l'espace de travail est distincte de son backend d'exécution. Lorsque les administrateurs configurent des [`statefulCodeSessions.environments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions) nommés, le Constructeur d'agents ajoute un sélecteur d'**Environnement d'exécution** :

- **Managed :** une API de code avec état exploitée par le déploiement
- **Ci-joint :** un pont distant compatible avec l'API Code qui délègue le travail à un worker `@librechat/code` sortant, tel qu'une machine virtuelle gérée par un opérateur
- **Personnel :** un worker `@librechat/code` lié au propriétaire et associé par un utilisateur autorisé via les paramètres de LibreChat
- **Déploiement par défaut :** l'environnement configuré marqué comme étant celui par défaut

<Callout type="warning" title="Hautement expérimental">
  Les Stateful Code Sessions sont dans une phase d'expérimentation précoce. Leur comportement, leur configuration, leurs caractéristiques de persistance et leur intégration sous-jacente peuvent changer de manière substantielle. Ne considérez pas l'implémentation actuelle comme un contrat de production stable.
</Callout>

Cette fonctionnalité est optionnelle. Activez `execute_code` et `stateful_code_sessions` dans les [capacités de l'endpoint Agents](/docs/configuration/librechat_yaml/object_structure/agents#capabilities), configurez une route avec état dédiée avec [`LIBRECHAT_CODE_BASEURL_STATEFUL`](/docs/configuration/dotenv#stateful-code-interpreter-endpoint) ou des environnements nommés, activez l'interpréteur de code sur l'agent, puis activez **Stateful code sessions** et choisissez son backend d'exécution ainsi que la portée de l'espace de travail dans les paramètres avancés.

Les requêtes avec état (stateful) échouent par défaut lorsque l'environnement sélectionné est manquant, inaccessible ou incompatible ; LibreChat ne les envoie pas à `LIBRECHAT_CODE_BASEURL` et ne choisit pas silencieusement un autre backend nommé. Lorsqu'aucun environnement nommé n'est configuré, `LIBRECHAT_CODE_BASEURL_STATEFUL` demeure la route avec état. Les agents sans état (stateless) continuent d'utiliser l'endpoint normal. LibreChat envoie également `X-CodeAPI-Expected-Profile: stateful`, le service dédié doit donc annoncer le profil `stateful`.

Les sessions avec état (stateful) et sans état (stateless) ne partagent pas d'espace de travail actif. L'espace de travail avec état peut être réinitialisé à tout moment, indépendamment de sa portée sélectionnée. Dans les environnements Code Interpreter gérés, enregistrez les sorties importantes sous `/mnt/data` et ne comptez pas sur l'état de la session comme stockage durable. Un espace de travail attaché est un répertoire distinct appartenant au worker ; les téléchargements n'y sont pas placés par défaut.

Les fichiers créés par les appels `create_file` et `edit_file` avec état apparaissent dans le message de l'assistant sous une ligne **Workspace changes** extensible. Elle liste chaque chemin modifié de manière unique pour cette réponse et fournit une action de téléchargement authentifiée. Les téléchargements utilisent le flux de fichiers persistants de LibreChat lorsqu'il est disponible, et une solution de secours sécurisée Code Interpreter dans le cas contraire. La ligne constitue un enregistrement des sorties créées, et non un instantané durable de l'espace de travail ; les sorties sans état continuent d'apparaître sous forme de pièces jointes intégrées classiques.

#### Environnements attachés et appairage [#attached-environments-and-pairing]

Attached environments require a matching experimental Code Interpreter remote-bridge build. The bridge remains LibreChat's authenticated policy, queue, and result boundary, while the `@librechat/code` worker connects outbound from the attached machine; the machine does not need an inbound public worker port. LibreChat does not prewarm attached environments.

Un opérateur peut épingler un environnement attaché appartenant à un déploiement sur un worker spécifique avec `workerId`, et peut ajouter `pairing.workerId` lorsque LibreChat doit générer un code de jumelage administrateur pour cette même route. `pairing.tokenEnv` nomme la variable d'environnement contenant le jeton d'administrateur du pont ; le secret lui-même ne doit jamais figurer dans le YAML. Les plans de contrôle jumelés nécessitent HTTPS en dehors du développement en loopback.

Pour les workers en libre-service, configurez un plan de contrôle attaché appartenant au déploiement avec `pairing.allowPrincipalWorkers: true` et `pairing.tokenEnv`. Il peut omettre les deux ID de worker et exister uniquement en tant que plan de contrôle d'inscription ; une telle entrée n'est pas sélectionnable pour l'exécution et ne peut pas être la valeur par défaut du déploiement.

Les utilisateurs disposant de l'autorisation de gestion des Code Environments peuvent ensuite ouvrir **Settings > Code environments**, nommer un environnement, choisir un plan de contrôle approuvé et sélectionner **Connect VM**. LibreChat affiche une commande éphémère à usage unique `librechat-code pair ...`. Exécutez-la sur la VM de l'utilisateur, puis démarrez `@librechat/code` avec `LIBRECHAT_CODE_SANDBOX_ENDPOINT` pointant vers le service sandbox de cette machine. L'interface utilisateur liste les environnements de l'utilisateur et permet de les révoquer et de les supprimer ultérieurement ; les fichiers sandbox restent sur la VM.

Les administrateurs peuvent limiter l'inscription avec [`statefulCodeSessions.principalWorkers`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions). L'inscription est activée par défaut avec au plus cinq environnements enregistrés par utilisateur lorsque ce bloc est omis. Le décompte inclut les workers hors ligne sur chaque plan de contrôle. La configuration de déploiement constitue le plafond : une configuration spécifique au principal peut l'abaisser ou le désactiver, mais ne peut pas l'augmenter. Le renforcement de la politique ne révoque pas les machines déjà enregistrées.

Les environnements personnels sont liés à l'utilisateur authentifié et au locataire, protégés par des ACL d'environnement de code, et se voient attribuer uniquement des identifiants validés par le serveur et des URL de base approuvées. LibreChat n'expose pas le jeton d'administrateur de pont ou des URL d'opérateur arbitraires au client. La suppression d'un environnement révoque ses identifiants de travailleur avant de supprimer l'entrée du registre, et la suppression d'un utilisateur planifie la même révocation et le même nettoyage avec une réconciliation en arrière-plan pour les tentatives interrompues. La route de travailleur sélectionnée s'applique de manière cohérente à l'interpréteur de code, au shell, à l'accès aux fichiers générés et à l'appel d'outils programmatiques.

Les Agents utilisant un espace de travail attaché peuvent lister son arborescence de répertoires, lire des fichiers, rechercher dans le contenu des fichiers, créer ou modifier des fichiers et exécuter Bash sur le worker sélectionné. Les citations de fichiers utilisent des chemins relatifs à l'espace de travail, les fichiers créés apparaissent dans la ligne **Workspace changes** de la réponse, et les échecs d'outils préservent les diagnostics HTTP limités du worker. Un Agent peut également stocker un nom et une adresse e-mail Git par Agent pour les commits créés dans cet espace de travail ; ces valeurs configurent uniquement la paternité et ne fournissent pas d'identifiants de dépôt.

Dans le chat, une commande Bash jointe à un espace de travail qui a échoué affiche son code de sortie, son signal de terminaison ou son délai d'expiration, et son stderr est stylisé séparément du stdout. Voir [Activity Groups](/docs/features/agents#activity-groups) pour savoir comment la sortie Bash est affichée.

Pour afficher la pull request GitHub d'une conversation dans l'en-tête du chat et la barre latérale, le worker attaché doit signaler sa branche git. Cela nécessite un worker construit à partir de la PR #311 ou ultérieure de `LibreChat-AI/code-interpreter` et que `CODEAPI_BRIDGE_LANE_GIT=true` soit défini sur le Code API (et non sur LibreChat). Voir [Conversation Pull Requests](/docs/features/pull_requests).

Un worker attaché annonce les racines d'espace de travail qu'il met à disposition. Le compositeur permet à l'utilisateur de sélectionner un espace de travail pour chaque environnement attaché accessible via l'Agent ou ses sous-agents ; un espace de travail unique et non ambigu est sélectionné automatiquement pour une nouvelle conversation. LibreChat stocke ces sélections dans la conversation, les revalide auprès du worker actif avant l'exécution et les maintient fixes pendant les pauses d'approbation et les exécutions reprises. L'envoi est bloqué lorsqu'une sélection requise est manquante ou indisponible, et LibreChat ne substitue jamais silencieusement un autre espace de travail. Au début d'une exécution, LibreChat peut charger les instructions du dépôt depuis l'espace de travail sélectionné afin que l'Agent suive les directives de ce dépôt ; les administrateurs peuvent limiter la découverte avec [`repositoryInstructions.timeoutMs`](/docs/configuration/librechat_yaml/object_structure/agents#repositoryinstructions). Les outils natifs de fichier et de Bash pour l'espace de travail peuvent utiliser une racine annoncée même lorsque le worker ne prend pas en charge les sessions d'exécution réutilisables. Le Bash programmatique conscient de l'espace de travail est disponible sur les versions compatibles de l'API Code et du worker lorsque la configuration de l'outil programmatique de l'Agent le permet, que le worker attaché autorisé est prêt et annonce `programmaticLanguages: ['bash']`, et que l'espace de travail sélectionné ainsi que le worker autorisent `execute_command`. LibreChat transmet l'ID de l'espace de travail validé par le serveur et l'ID de l'instance d'espace de travail de la conversation, lorsqu'ils sont présents, à l'outil programmatique ; les arguments du modèle ne peuvent pas remplacer cette sélection. Sans ces capacités, le Bash programmatique est désactivé ; utilisez le Bash direct pour les commandes conscientes de l'espace de travail. Lorsque le worker prend en charge le relais de fichiers, les téléchargements de chat sont mis en zone de transit séparément sous `$LIBRECHAT_CODE_DATA_DIR` pour l'exécution programmatique, et ne sont pas copiés dans l'espace de travail sélectionné. **Stop** annule une commande BYOM en cours sensible aux signaux sans invalider l'espace de travail pour les commandes ultérieures ; le travail détaché conserve son propre cycle de vie d'annulation.

Pour un environnement d'exécution attaché, l'Agent Builder peut définir un **Workspace default** (répertoire de travail par défaut) sur l'une des racines actuellement annoncées. Il est validé par rapport à cet environnement attaché et utilisé pour initialiser les nouvelles conversations pour cet Agent. Choisissez **Last used** (Dernière utilisation) pour utiliser la préférence locale du navigateur de l'utilisateur connecté pour cet Agent et cet environnement ; il s'agit uniquement d'une indication pratique, jamais d'une autorisation ou d'une liaison de conversation. La modification de l'environnement d'exécution efface une valeur par défaut explicite, et une racine enregistrée qui n'est plus annoncée reste visible mais ne peut pas être sélectionnée tant qu'elle n'est pas reconfigurée.

#### Changements de l'espace de travail des conversations enregistrées [#saved-chat-workspace-changes]

Par défaut, la décision d'espace de travail attaché d'une conversation enregistrée est scellée. Avec [`statefulCodeSessions.conversationMoves.enabled`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions) activé, le propriétaire peut explicitement passer à un autre espace de travail autorisé ou récupérer un espace de travail manquant. La récupération préserve l'historique de discussion, **pas** les fichiers de l'espace de travail perdu. Définir `allowAttachDetach: true` permet en outre au propriétaire d'attacher un espace de travail à une discussion non liée au code enregistrée ou de quitter un espace de travail attaché pour poursuivre une discussion normale ; l'activation des déplacements seuls n'active pas l'attachement/détachement. Ces transitions ne peuvent pas avoir lieu pendant qu'une génération est en cours et sont revalidées sur le serveur. Mettez à niveau toutes les répliques d'API et activez `CODE_ENVIRONMENT_DECISION_VERSION=1` avant d'opter pour cette option. Sans ces commutateurs, le comportement existant de déplacement uniquement et de conversation scellée reste inchangé.

Le Bash attaché utilise un délai d'attente de 30 secondes par défaut. Un environnement peut exposer un budget de requête de modèle plus important avec [`configSchema.limits.maxCommandTimeoutMs`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions), jusqu'au plafond de protocole de cinq minutes. Le délai d'attente demandé ne dépasse jamais la limite de déploiement. Les administrateurs peuvent limiter séparément les tentatives de mise en file d'attente avec [`configSchema.limits.maxQueueWaitMs`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions) ; cette attente en file ne permet pas d'annuler une commande admise ou en cours d'exécution. Pour autoriser des tentatives d'admission **individuelles** plus longues, utilisez `configSchema.limits.maxRequestTimeoutMs` uniquement après que l'API Code respecte l'allocation de file d'attente par requête et que le délai d'attente de proxy le plus court sur la route active soit vérifié. L'option `configSchema.limits.minCommandAdmissionMs` réserve 10 secondes par défaut (valide de 1 à 300 secondes) pour l'admission avant une commande. Le délai d'attente Bash annoncé est ajusté au budget de la requête après cette réserve et 10 secondes supplémentaires pour le règlement et la livraison. Ce budget ne remplace pas `maxQueueWaitMs`.

#### Voies de worktree liés [#linked-worktree-lanes]

Les environnements attachés peuvent opter pour la planification de requêtes [par worktree](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions) avec `configSchema.workspaces.linkedWorktrees: true`. Mettez d'abord à niveau LibreChat, puis déployez un pont Code API compatible et démarrez le worker avec `--linked-worktree-lanes` ; n'activez le paramètre YAML qu'après que ce worker a annoncé `git_linked_worktree`. Les requêtes qui ciblent structurellement `.worktrees/<name>/` utilisent la voie (lane) de ce worktree sans modifier les chemins relatifs à l'extraction (checkout) affichés à l'Agent. Pour Bash, passez le répertoire du worktree dans l'argument `cwd` de l'outil ; exécuter `cd .worktrees/<name>` à l'intérieur de la commande reste dans la voie racine. Les opérations sur la racine de l'extraction, les actions sur l'environnement et les instances d'espace de travail de conversation restent également limitées à la racine. Sans cette option, toutes les requêtes conservent leur planification existante à l'échelle de l'extraction.

#### Correspondance et conflits lors de la modification de l'espace de travail [#workspace-edit-matching-and-conflicts]

`edit_file` accepte un `replace_all` de haut niveau pour un remplacement unique `old_text`/`new_text`, ou un indicateur par entrée lorsqu'un lot `edits` est fourni. Sans cela, chaque `old_text` doit correspondre à un seul emplacement. Un lot fourni doit être non vide et valide ; LibreChat rejette une valeur `edits` vide ou mal formée au lieu de revenir aux champs de remplacement de haut niveau. Les lots sérialisés en JSON et les indicateurs de remplacement booléens valides sont normalisés avant l'approbation native de l'outil, de sorte que l'aperçu et l'exécution utilisent les mêmes modifications canoniques, y compris les réécritures de hooks examinées. Les modifications de Skill-file et de managed-sandbox prennent en charge le remplacement de toutes les correspondances dans les limites de taille et de nombre de correspondances de LibreChat ; les espaces de travail joints nécessitent un worker annonçant `replace_all` et rejettent les demandes non prises en charge avant la répartition.

Sur les workers attachés annonçant `tolerant_match`, les modifications et les aperçus protégés tentent d'abord une correspondance exacte, puis des stratégies de tolérance aux espaces pour les espaces de fin de ligne, les CRLF, les décalages d'indentation ou les espaces normalisés. Les administrateurs peuvent exiger des correspondances exactes avec [`configSchema.edits.tolerantMatching: false`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions). Les messages de succès identifient les correspondances non exactes ou les remplacements multiples. Les lots ayant échoué sont atomiques : rien n'est écrit, et LibreChat signale des raisons limitées par modification, des décomptes, des numéros de ligne candidats ou un avertissement de fichier modifié sans transmettre de texte de worker arbitraire ou d'extraits de fichier.

Ces fonctionnalités de worker attaché nécessitent une API Code et des builds de worker compatibles implémentant [Code Interpreter #271](https://github.com/LibreChat-AI/code-interpreter/pull/271). LibreChat n'envoie les nouveaux champs qu'après la négociation des capacités. Avec les builds plus anciens, le format de requête et le comportement de correspondance restent inchangés ; la mise à jour de LibreChat seule n'active pas les modifications attachées tolérantes ou `replace_all`.

#### Autorisations des outils pour l'environnement attaché [#attached-environment-tool-permissions]

Les environnements attachés et personnels utilisent une politique d'approbation « demander par défaut » pour l'écriture de fichiers et l'exécution de commandes ou de code. Les opérations de lecture seule et de recherche continuent de suivre la politique d'outils habituelle du déploiement. Si l'administrateur expose l'une ou l'autre catégorie via [`configSchema.permissions`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions), les utilisateurs disposant de l'autorisation de gestion des environnements de code peuvent choisir parmi les valeurs autorisées **Autoriser**, **Demander** ou **Refuser** sous **Paramètres > Environnements de code**. Les paramètres manquants, obsolètes ou non autorisés reviennent par sécurité à **Demander**.

Le compositeur affiche un **Mode d'approbation de code** au niveau de la conversation chaque fois que l'environnement joint sélectionné le prend en charge :

- **Ask before changes** demande une confirmation avant d'effectuer des modifications de fichiers ou d'exécuter des commandes.
- **Accept edits** autorise les modifications de fichiers mais continue de demander confirmation avant l'exécution des commandes.
- **Accès complet** autorise les deux catégories sans invites systématiques.

Le mode sélectionné accompagne cette conversation et est recoupé avec les valeurs autorisées du déploiement et la politique d'environnement. **Full access** (Accès complet) n'apparaît que lorsque `fileWrite` et `commandExecution` autorisent tous deux `allow` ; cela ne contourne pas l'isolation du sandbox, les attributions de rôles, les règles explicites `ask` ou `deny` de l'endpoint, la confirmation des fichiers Skill, ou les hooks d'approbation.

Une importation de conversation ne peut pas sélectionner de mode d'approbation de code pour son destinataire. Les nouvelles conversations importées ou copiées en masse utilisent la préférence/le paramètre par défaut du destinataire selon la politique actuelle ; les mises à jour en masse conservent tout choix stocké localement. Les conversations existantes ne sont pas réinitialisées rétroactivement, et la sélection explicite d'un mode dans LibreChat le conserve toujours.

Ces contrôles couvrent les outils de création de fichiers, l'exécution de shell et de code, les vérifications de compilation et l'appel de fonctions programmatiques (Programmatic Tool Calling). Les écritures dans les fichiers de compétences (Skill) persistants nécessitent toujours une confirmation lorsque la création de compétences est activée, même lorsque les écritures de fichiers ordinaires sont autorisées. Les paramètres ne modifient pas l'isolation de la VM, la mise en réseau, les montages, l'exécution privilégiée, l'entrée, la sortie ou l'accès aux secrets.

Le paramètre explicite [`toolApproval.enabled: false`](/docs/configuration/librechat_yaml/object_structure/agents#toolapproval) du déploiement est une commande de secours qui désactive cette base de référence. Sans cette commande, un appelant incapable de présenter et de reprendre les demandes d'approbation échoue par défaut au lieu d'exécuter silencieusement un outil d'environnement attaché.

Le jumelage authentifie le transport du worker distant ; ce n'est pas une limite de sandbox. Maintenez l'endpoint d'exécution local du worker sur loopback ou sur un réseau privé et utilisez un mode d'isolation approprié pour le code non fiable.

Pendant qu'une exécution est active, les volets de détails du code et du shell développés suivent les arguments diffusés en continu jusqu'en bas. Faire défiler vers le haut suspend le comportement de suivi afin que vous puissiez inspecter les sorties précédentes sans que le volet ne déplace la fenêtre d'affichage.

2. **Exécution manuelle** : Utilisez le bouton "Run Code" dans les blocs de code au sein de l'interface de chat, comme indiqué ici :

3. **[Appel d'outils programmatique](/docs/features/agents#programmatic-tool-calling)** : Activez la fonctionnalité `programmatic_tools` et marquez les outils MCP sélectionnés comme étant programmatiques afin que les agents puissent orchestrer ces outils à partir de code en bac à sable (sandboxed).

### Configurer la clé API [#set-up-api-key]

- **Configuration par utilisateur :** Saisissez votre clé API dans LibreChat lorsque vous y êtes invité.
- **Configuration globale :** Définissez `LIBRECHAT_CODE_API_KEY` dans le fichier `.env` de LibreChat pour fournir une clé unique à tous les utilisateurs.

Le service actuel [ClickHouse/code-interpreter](https://github.com/ClickHouse/code-interpreter) utilise l'authentification JWT de LibreChat en dehors du mode local. Les clés API restent disponibles pour les déploiements de Code Interpreter compatibles.

### Authentification JWT auto-hébergée [#self-hosted-jwt-authentication]

Avec l'authentification JWT, LibreChat signe un jeton bearer à courte durée de vie pour l'utilisateur authentifié à chaque requête Code Interpreter. Le service Code Interpreter vérifie la clé publique correspondante et utilise le contexte de l'utilisateur et du locataire signé pour isoler les fichiers et les sessions. La clé de signature privée reste dans LibreChat ; Code Interpreter ne reçoit que son vérificateur public.

Configurez LibreChat avec :

```env
CODEAPI_AUTH_PROVIDER=librechat-jwt
CODEAPI_JWT_PRIVATE_KEY="-----BEGIN PRIVATE KEY-----\n...\n-----END PRIVATE KEY-----"
CODEAPI_JWT_ALGORITHM=EdDSA
CODEAPI_JWT_KID=lc-codeapi-2026-05
CODEAPI_JWT_ISSUER=librechat
CODEAPI_JWT_AUDIENCE=codeapi
CODEAPI_JWT_TTL_SECONDS=300
CODEAPI_JWT_MINT_CACHE_SECONDS=30
CODEAPI_JWT_SINGLE_TENANT_ID=legacy
```

`CODEAPI_JWT_PRIVATE_KEY_BASE64` peut contenir une clé PEM encodée en base64 à la place, et `CODEAPI_JWT_PRIVATE_JWK_JSON` accepte une clé privée JWK. LibreChat prend en charge la signature Ed25519 (`EdDSA`, la valeur par défaut) et RSA (`RS256`). Consultez la [référence des variables d'environnement](/docs/configuration/dotenv#code-interpreter-jwt-authentication) pour tous les paramètres côté LibreChat.

Configurez le Code Interpreter avec le vérificateur correspondant :

```env
LOCAL_MODE=false
CODEAPI_AUTH_PROVIDER=librechat-jwt
CODEAPI_JWT_ISSUER=librechat
CODEAPI_JWT_AUDIENCE=codeapi
CODEAPI_JWT_ALLOWED_ALGS=EdDSA
CODEAPI_JWT_JWKS_JSON={"keys":[{"kty":"OKP","crv":"Ed25519","x":"...","kid":"lc-codeapi-2026-05","alg":"EdDSA"}]}
CODEAPI_JWT_SINGLE_TENANT_ID=legacy
```

L'émetteur, l'audience, l'ID de clé, l'algorithme et la clé publique doivent correspondre au signataire de LibreChat. Code Interpreter peut également charger des clés de vérification à partir de `CODEAPI_JWT_PUBLIC_KEY` et `CODEAPI_JWT_KID`, ou à partir de `CODEAPI_JWT_PUBLIC_KEYS_DIR` ; un JWKS en ligne est pratique pour la rotation. Maintenez le TTL du jeton à une valeur inférieure ou égale à `CODEAPI_JWT_MAX_TTL_SECONDS` du service Code Interpreter, qui est limité par défaut à 300 secondes.

Pour une installation locale, le dépôt Code Interpreter inclut un utilitaire qui génère les clés de signature Ed25519 et de manifeste d'exécution correspondantes, et met à jour les deux fichiers `.env` :

```bash
node scripts/setup-local-auth-env.js --librechat /path/to/LibreChat
```

Les déploiements à locataire unique peuvent laisser `CODEAPI_JWT_SINGLE_TENANT_ID=legacy`, mais la valeur doit correspondre sur les deux services. Les déploiements multi-locataires doivent fournir un contexte de locataire authentifié et activer `TENANT_ISOLATION_STRICT=true` dans LibreChat ainsi que `CODEAPI_TENANT_ISOLATION_STRICT=true` dans Code Interpreter. Le mode strict rejette les requêtes sans contexte de locataire au lieu d'utiliser le repli vers le locataire unique.

### Intégration directe de l'API [#direct-api-integration]

Le service auto-hébergé actuel attend un jeton bearer qui satisfait son contrat de revendication JWT LibreChat. Une intégration directe doit générer des jetons à courte durée de vie compatibles et les envoyer dans l'en-tête `Authorization: Bearer <token>`. Les déploiements compatibles avec les clés API acceptent plutôt leur clé configurée dans l'en-tête `x-api-key`. N'utilisez jamais le mode local sans authentification de Code Interpreter sur un endpoint public ou de production.

### URL de base auto-hébergée [#self-hosted-base-url]

Définissez `LIBRECHAT_CODE_BASEURL` pour pointer LibreChat vers votre instance [code-interpreter](https://github.com/ClickHouse/code-interpreter) auto-hébergée, puis configurez [l'authentification JWT](#self-hosted-jwt-authentication). Pour un service compatible avec les clés API, définissez plutôt `LIBRECHAT_CODE_API_KEY`. Les sessions d'agent avec état, hautement expérimentales, nécessitent une route de profil `stateful` distincte configurée via [`LIBRECHAT_CODE_BASEURL_STATEFUL`](/docs/configuration/dotenv#stateful-code-interpreter-endpoint) ou nommée [`statefulCodeSessions.environments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions).

## Fonctionnalités principales [#core-functionality]

### Exécution de code [#code-execution]

- Exécuter des extraits de code dans les langages pris en charge
- Recevoir la sortie stdout/stderr
- Obtenir les statistiques d'exécution (utilisation de la mémoire, temps CPU)
- Gérer les arguments du programme
- Accéder au statut d'exécution et aux résultats

### Opérations sur les fichiers [#file-operations]

- Télécharger des fichiers d'entrée
- Télécharger les sorties générées
- Prévisualisez les fichiers Office générés, y compris les présentations PowerPoint `.pptx` et les modèles `.potx`, ainsi que les artefacts CSV, texte et de type PDF en ligne lorsque LibreChat peut les extraire/rendre en toute sécurité.
- Afficher les images PNG, JPEG, GIF et WebP renvoyées par l'outil `read_file` d'un Agent en tant qu'artefacts visualisables
- Lister les fichiers disponibles
- Supprimer les fichiers inutiles
- Gérer les sessions de fichiers

Les aperçus d'artefacts générés sont intentionnellement limités en taille. Définissez [`FILE_PREVIEW_MAX_EXTRACT_BYTES`](/docs/configuration/dotenv#inline-file-previews) dans le fichier `.env` de LibreChat pour modifier la limite de taille des fichiers sources pour l'extraction des aperçus en ligne ; les fichiers plus volumineux restent disponibles au téléchargement.

Les images du Sandbox renvoyées par `read_file` ont une limite intégrée de 1 MiB. Les images plus volumineuses restent dans le Sandbox pour être traitées avec `bash_tool`. `LIBRECHAT_CODE_IMAGE_CHUNK_BYTES` contrôle uniquement la taille des segments de transport utilisés lors de la lecture des images éligibles ; cela n'augmente pas la limite intégrée.

<Callout type="warning" title="Vérification de mise à niveau pour les sorties de code héritées">
  Les déploiements ayant régénéré le même nom de fichier Code Interpreter avant l'ajout de l'index unique des fichiers de sortie peuvent comporter des enregistrements MongoDB en double qui empêchent la création de l'index. Prévisualisez la réparation avec `npm run migrate:code-file-duplicates:dry-run`, puis appliquez-la avec `npm run migrate:code-file-duplicates`. La migration conserve le nom de fichier canonique le plus récent, renomme les anciens enregistrements avec des suffixes numériques et crée l'index unique après une exécution réussie.
</Callout>

### Limitations [#limitations]
- Le code ne peut pas accéder au réseau
- Seuls 10 fichiers peuvent être générés par exécution
- Les limites de ressources (RAM par exécution, taille de téléchargement de fichiers et quotas de requêtes) dépendent de la manière dont vous provisionnez et configurez votre déploiement.

## Open Source & Self-Hosting [#open-source--self-hosting]

Le service Code Interpreter est open source sous licence Apache 2.0 sur [ClickHouse/code-interpreter](https://github.com/ClickHouse/code-interpreter). Maintenir l'exécution du code en tant que service séparé permet à l'application principale LibreChat de rester légère : vous ne déployez l'infrastructure sandbox que lorsque vous en avez besoin, et vous pouvez la mettre à l'échelle indépendamment de l'application de chat.

Le service s'exécute sous la forme d'un ensemble de composants évolutifs indépendamment (une passerelle API, des workers en bac à sable et un serveur de fichiers) et prend en charge des modes d'isolation robustes (NsJail ou une microVM via libkrun) afin que vous puissiez exécuter du code non fiable en toute sécurité. Consultez le README du dépôt pour les instructions de déploiement avec Docker Compose et Helm.

L'API Code Interpreter fournit un moyen sécurisé et pratique d'exécuter du code et de gérer des fichiers dans un bac à sable isolé. Pour des spécifications techniques détaillées, des guides de déploiement et la référence de l'API, consultez le [code-interpreter repository](https://github.com/ClickHouse/code-interpreter).
