## Introductie [#introduction]

De Code Interpreter API van LibreChat biedt een veilige en probleemloze manier om code uit te voeren en bestanden te beheren via een eenvoudige API-interface. Of je het nu gebruikt via de Agents van LibreChat of direct integreert in je eigen applicaties, de API biedt een krachtige sandbox-omgeving voor het uitvoeren van code in meerdere programmeertalen.

</Callout>

## Aan de slag [#getting-started]

1. Implementeer de [code-interpreter](https://github.com/ClickHouse/code-interpreter) service (Docker Compose of Helm, zie de README van de repository)
2. Wijs LibreChat ernaar met `LIBRECHAT_CODE_BASEURL`
3. Configureer [LibreChat JWT authentication](#self-hosted-jwt-authentication) voor de huidige open-source service, of stel `LIBRECHAT_CODE_API_KEY` in voor een API-key-compatibele implementatie
4. Om te experimenteren met stateful Agent-sessies, implementeer je een afzonderlijke `stateful`-profile Code Interpreter-route en configureer je `LIBRECHAT_CODE_BASEURL_STATEFUL` of de benoemde [`statefulCodeSessions.environments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions)
5. Begin met het veilig uitvoeren van code en het genereren van bestanden via LibreChat's Agents of de "Run Code" knop

## Belangrijkste functies [#key-features]

### Ondersteunde talen [#supported-languages]

Voer code uit in meerdere programmeertalen:

- Python, Node.js (JS/TS), Go, C/C++, Java, PHP, Rust, Fortran, Rscript

### Naadloze bestandsafhandeling [#seamless-file-handling]

- Bestanden uploaden voor verwerking
- Genereerde outputs downloaden
- Veilig bestandsbeheer
- Sessie-gebaseerde bestandsorganisatie

LibreChat herstelt gerefereerde gespreksbestanden naar beheerde Code Interpreter-omgevingen vóór een Agent-run. Als het herstel van elk vereist Code Interpreter-bestand mislukt, stopt de run vóór de model-aanroep en wordt de gebruiker gevraagd de bestanden opnieuw bij te voegen in plaats van door te gaan met verouderde referenties. In een geselecteerde bijgevoegde werkruimte worden chat-uploads **niet** gekopieerd naar de werkruimte van de gebruiker, en kunnen werkruimtebestanden en Bash-tools deze daar niet openen. Als de worker Programmatic Bash met file relay adverteert, ziet die tool in plaats daarvan de gefaseerde uploads onder `$LIBRECHAT_CODE_DATA_DIR` voor de duur van de run.

Code API-uploads herstellen van `429` rate limits door `Retry-After` te respecteren, de bronstream voor elke poging opnieuw te openen en een begrensd wachtbudget te delen. Beheerders kunnen het herstel per gebruiker en per route afstemmen met [`codeApiUploadConcurrency` en `codeApiMaxRetryWaitMs`](/docs/configuration/librechat_yaml/object_structure/agents#code-api-upload-recovery).

Wanneer gespreksinvoer op dezelfde sandbox-bestemming zou worden geplaatst, lost LibreChat het conflict op vóór de uitvoering. Gedeelde gespreksbestanden worden toegewezen vóór bestanden die privé zijn voor de Agent; binnen elk bereik behoudt de nieuwste inhoud de oorspronkelijke bestemming. Conflicterende paden worden indien nodig platgeslagen of krijgen een van de identiteit afgeleid achtervoegsel, en de opgeloste `/mnt/data/...` paden worden opgenomen in de bestandscontext van de Agent. Dit geldt ook voor een upload en een gegenereerde uitvoer die dezelfde bestandsnaam delen, zodat één conflict niet elke latere Code Interpreter-run in het gesprek afwijst. Dubbele seed-verwijzingen die nog steeds naar een reeds geclaimde bestemming verwijzen, worden overgeslagen in plaats van dat het volledige verzoek mislukt.

Sandbox-afbeeldingen worden overgedragen in begrensde vensters. Stel [`LIBRECHAT_CODE_SANDBOX_OUTPUT_MAX_SIZE`](/docs/configuration/dotenv#code-interpreter) in om overeen te komen met de `SANDBOX_OUTPUT_MAX_SIZE` van de worker; LibreChat leidt het grootste veilige afbeeldingsvenster af van dat budget en kan een kleinere limiet per service leren na één mislukte leesactie. Gebruik `LIBRECHAT_CODE_IMAGE_CHUNK_BYTES` alleen wanneer een exacte venster-override vereist is. Eerder gedownloade gegenereerde artefacten worden waar mogelijk hergebruikt binnen het verzoek, waardoor een nieuwe sandbox-leesactie wordt vermeden.

In een multi-Agent graaf, geef bestanden die privé zijn voor verschillende Agents afzonderlijke bestandsnamen. Elke Agent lost zijn privé-bestandspaden op voordat de graaf hun invoer combineert, dus oprecht verschillende privébestanden die onafhankelijk dezelfde bestemming claimen, kunnen op dit moment nog niet consistent worden hernoemd tijdens het samenvoegen; de eerst geplaatste bestemming wint.

### Programmatische Tool Calling [#programmatic-tool-calling]

Programmatic Tool Calling stelt LibreChat Agents in staat om geselecteerde MCP tools via de Code Interpreter sandbox te routeren. In plaats van het model te vragen om elke tool direct aan te roepen, biedt LibreChat een door Code Interpreter ondersteunde orchestratietool; gegenereerde sandbox-code kan geregistreerde tool-stubs aanroepen, lussen en voorwaardelijke logica gebruiken, tussenresultaten verwerken en een definitief antwoord retourneren.

De sandbox heeft nog steeds geen algemene netwerktoegang. Tool-aanroepen worden afgehandeld via de Code Interpreter Tool Call Server. LibreChat kruist de live caller-capability projectie met zijn vertrouwde register, zodat alleen actieve programmatische tools die al voor de Agent zijn geregistreerd, kunnen worden aangeroepen en een verzoek zijn eigen toegang niet kan uitbreiden.

Programmatische tools vereisen Code Interpreter op de Agent. Hun schakelaars blijven uitgeschakeld totdat Code Interpreter is geselecteerd, en het verwijderen van Code Interpreter wist bestaande programmatische selecties. LibreChat verwijdert ook verouderde programmatische aanroeper-opties bij het aanmaken, bijwerken, dupliceren en versie-herstel van Agents wanneer `execute_code` of de Code Interpreter tool niet beschikbaar is.

Tijdens een programmatische uitvoering kun je de Code Interpreter-kaart uitvouwen om een live terminal-stijl trace van interne tool-aanroepen te zien, inclusief begrensde argument-previews, statussen, looptijden en fouten. Deze trace helpt bij het inspecteren van het programma terwijl het wordt uitgevoerd, maar wordt niet bewaard na het verversen van de pagina.

### Background Code Execution [#background-code-execution]

Achtergronduitvoering stelt een Agent in staat om langlopende code of shell-taken te verzenden en het gesprek voort te zetten. Voor opgeslagen Agents worden ondersteunde content-only voltooiingen standaard automatisch geleverd in een vervolgactie. `check_background_task` blijft beschikbaar voor expliciete status, controle, live artefacten en herstel. In LibreChat-chats verschijnen stdout en gegenereerde bestanden, zodra het werk is voltooid, bij de oorspronkelijke code-aanroep en worden ze behouden voor volgende beurten. Achtergrondvoltooiingen en expliciete controles renderen taakkaarten met status, leveringsstatus en leesbare resultaten; het exacte oorspronkelijke resultaat blijft beschikbaar om te kopiëren. De chat-header groepeert lopende en recente taken en biedt individuele of stop-alles-bedieningselementen wanneer dit is toegestaan door het annuleringsbeleid van de deployment.

Deze functie is opt-in op implementatieniveau. Voeg `run_in_background` toe naast `execute_code` in de [Agents endpoint capabilities](/docs/configuration/librechat_yaml/object_structure/agents#capabilities) en schakel vervolgens Code Interpreter in op de agent. Code-executie en shell-aanroepen komen automatisch in aanmerking voor achtergrondverwerking; schakel **Background execution** uit in de instellingen van de Code Interpreter-tool wanneer een agent zich hiervoor moet afmelden. Het model beslist nog steeds per aanroep of in aanmerking komend werk op de achtergrond wordt uitgevoerd.

Gewone achtergronduitvoering blijft proces-lokaal en overleeft het verlies van zijn app-worker niet. Zodra een resultaat dat alleen uit inhoud bestaat is opgeslagen, is de automatische aflevering ervan duurzaam en kan deze doorgaan op een andere replica; taken met een live artifact vereisen nog steeds polling op de eigenaar-run. Stel [`endpoints.agents.backgroundTasks.completionWakeups: false`](/docs/configuration/librechat_yaml/object_structure/agents#backgroundtasks) in om polling voor elk resultaat te vereisen. Achtergrondverzending verlengt de uitvoeringslimiet van de Code Interpreter-service niet; de normale server-side time-out van de deployment blijft van toepassing.

Met [`ordinaryToolCancellation: true`](/docs/configuration/librechat_yaml/object_structure/agents#backgroundtasks) kunnen eigenaren coöperatieve annulering aanvragen van gewone achtergrond Code-tools, inclusief gekoppelde Bash. De taak blijft actief en verbruikt capaciteit totdat de aanroep is afgerond; een tool die annulering negeert, kan alsnog worden voltooid.

### Stateful Code Sessions [#stateful-code-sessions]

Stateful code sessions laten een LibreChat Agent één Code Interpreter sandbox-werkruimte hergebruiken over verschillende uitvoeringen heen. Bestanden, geïnstalleerde pakketten en de werkstatus blijven doorgaans behouden, wat iteratieve analyse en het genereren van bestanden in meerdere stappen efficiënter maakt. Elke agent selecteert één werkruimtebereik:

- **Gebruikerswerkruimte (aanbevolen):** één werkruimte voor de ingelogde gebruiker voor alle agents waarvoor stateful is ingeschakeld
- **Agent + user werkruimte:** één werkruimte voor elke combinatie van gebruiker en agent
- **Conversation workspace:** één werkruimte voor elke gebruiker en conversatie

Voor nieuw aangemaakte Agents komt het initiële bereik uit **Settings > Data Controls > Code execution > Default stateful workspace**. De persoonlijke instelling staat standaard op **User workspace**; het wijzigen hiervan heeft geen invloed op bestaande Agents en schakelt geen stateful sessies in. Deployment-beheerders kunnen de selecteerbare bereiken beperken met [`statefulCodeSessions.allowedEnvironments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions). Als een opgeslagen persoonlijke standaardinstelling niet langer beschikbaar is, gebruiken nieuwe Agents het eerste toegestane bereik; een bestaande ingeschakelde Agent met een nu niet-toegestaan bereik moet opnieuw worden geconfigureerd voordat deze kan worden uitgevoerd.

De workspace-scope staat los van de bijbehorende execution backend. Wanneer beheerders benoemde [`statefulCodeSessions.environments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions) configureren, voegt de Agent Builder een **Execution environment**-selector toe:

- **Managed:** een stateful Code API die wordt beheerd door de deployment
- **Bijgevoegd:** een compatibele Code API remote bridge die werk uitbesteedt aan een outbound `@librechat/code` worker, zoals een door een operator beheerde VM
- **Persoonlijk:** een aan de eigenaar gebonden `@librechat/code` worker die door een geautoriseerde gebruiker is gekoppeld via de LibreChat-instellingen
- **Deployment default:** de geconfigureerde omgeving die als standaard is gemarkeerd

<Callout type="warning" title="Zeer experimenteel">
  Stateful Code Sessions bevinden zich in een vroege experimentele fase. Hun gedrag, configuratie, persistentie-eigenschappen en onderliggende integratie kunnen aanzienlijk veranderen. Beschouw de huidige implementatie niet als een stabiel productiecontract.
</Callout>

Deze functie is opt-in. Schakel `execute_code` en `stateful_code_sessions` in bij de [Agents endpoint capabilities](/docs/configuration/librechat_yaml/object_structure/agents#capabilities), configureer een toegewezen stateful route met [`LIBRECHAT_CODE_BASEURL_STATEFUL`](/docs/configuration/dotenv#stateful-code-interpreter-endpoint) of benoemde omgevingen, schakel Code Interpreter in op de agent, en zet vervolgens **Stateful code sessions** aan en kies de execution backend en workspace scope onder Advanced settings.

Stateful verzoeken falen "closed" wanneer de geselecteerde omgeving ontbreekt, ontoegankelijk of incompatibel is; LibreChat verstuurt ze niet naar `LIBRECHAT_CODE_BASEURL` en kiest niet stilletjes een andere benoemde backend. Wanneer er geen benoemde omgevingen zijn geconfigureerd, blijft `LIBRECHAT_CODE_BASEURL_STATEFUL` de stateful route. Stateless agents blijven het normale endpoint gebruiken. LibreChat verstuurt ook `X-CodeAPI-Expected-Profile: stateful`, dus de toegewezen service moet het `stateful` profiel adverteren.

Stateful en stateless sessies delen geen live workspace. De stateful workspace kan op elk moment worden gereset, ongeacht het geselecteerde bereik. Sla in beheerde Code Interpreter-omgevingen belangrijke uitvoer op onder `/mnt/data` en vertrouw verder niet op de sessiestatus als duurzame opslag. Een gekoppelde workspace is een afzonderlijke, door de worker beheerde map; uploads worden daar standaard niet geplaatst.

Bestanden die zijn aangemaakt door stateful `create_file` en `edit_file` aanroepen verschijnen in het assistent-bericht onder een uitklapbare rij genaamd **Workspace changes**. Hierin wordt elk uniek gewijzigd pad voor dat antwoord vermeld en wordt een geauthenticeerde downloadactie aangeboden. Downloads maken gebruik van de persistente bestandsstroom van LibreChat wanneer deze beschikbaar is, en anders van een veilige Code Interpreter-fallback. De rij is een overzicht van gegenereerde outputs, geen duurzame snapshot van de workspace; stateless outputs blijven verschijnen als normale inline bijlagen.

#### Gekoppelde omgevingen en pairing [#attached-environments-and-pairing]

Gekoppelde omgevingen vereisen een bijbehorende experimentele Code Interpreter remote-bridge build. De bridge blijft het geauthenticeerde beleid, de wachtrij en de resultaatgrens van LibreChat, terwijl de `@librechat/code` worker uitgaand verbinding maakt vanaf de gekoppelde machine; de machine heeft geen inkomende publieke worker-poort nodig. LibreChat voert geen prewarming uit voor gekoppelde omgevingen.

Een operator kan een door de deployment beheerde gekoppelde omgeving vastzetten aan één worker met `workerId`, en kan `pairing.workerId` toevoegen wanneer LibreChat een administrator-koppelingscode voor diezelfde route moet uitgeven. `pairing.tokenEnv` benoemt de omgevingsvariabele die het bridge-administratortoken bevat; het geheim zelf hoort nooit in YAML thuis. Gekoppelde control planes vereisen HTTPS buiten loopback-ontwikkeling.

Voor self-service workers configureert u een door de deployment beheerd gekoppeld control plane met `pairing.allowPrincipalWorkers: true` en `pairing.tokenEnv`. Het kan beide worker-ID's weglaten en uitsluitend bestaan als een enrollment control plane; een dergelijk item is niet selecteerbaar voor uitvoering en kan niet de standaard voor de deployment zijn.

Gebruikers met de machtiging voor het beheer van Code Environment kunnen vervolgens **Settings > Code environments** openen, een omgeving een naam geven, een goedgekeurd control plane kiezen en **Connect VM** selecteren. LibreChat toont een kortstondig, eenmalig `librechat-code pair ...` commando. Voer dit uit op de VM van de gebruiker en start vervolgens `@librechat/code` met `LIBRECHAT_CODE_SANDBOX_ENDPOINT` wijzend naar de sandbox-service van die machine. De UI geeft de omgevingen van de gebruiker weer en kan deze later intrekken en verwijderen; sandbox-bestanden blijven op de VM staan.

Beheerders kunnen inschrijving beperken met [`statefulCodeSessions.principalWorkers`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions). Inschrijving is standaard ingeschakeld met maximaal vijf geregistreerde omgevingen per gebruiker wanneer dit blok wordt weggelaten. Het aantal omvat offline workers over elk control plane. De implementatieconfiguratie is het plafond: configuratie specifiek voor een principal kan dit verlagen of uitschakelen, maar niet verhogen. Het aanscherpen van het beleid trekt machines die al geregistreerd zijn niet in.

Persoonlijke omgevingen zijn gebonden aan de geauthenticeerde gebruiker en tenant, beveiligd door Code Environment ACL's, en krijgen alleen server-gevalideerde ID's en goedgekeurde basis-URL's toegewezen. LibreChat stelt het bridge-beheerdertoken of willekeurige operator-URL's niet bloot aan de client. Het verwijderen van een omgeving trekt de worker-referentie in voordat het registeritem wordt verwijderd, en het verwijderen van een gebruiker plant dezelfde intrekking en opschoning in, met achtergrondreconciliatie voor onderbroken pogingen. De geselecteerde worker-route is consistent van toepassing op Code Interpreter, shell, toegang tot gegenereerde bestanden en Programmatic Tool Calling.

Agents die een gekoppelde workspace gebruiken, kunnen de mappenstructuur weergeven, bestanden lezen, bestandsinhoud doorzoeken, bestanden aanmaken of bewerken en Bash uitvoeren op de geselecteerde worker. Bestandscitaties gebruiken paden die relatief zijn aan de workspace, aangemaakte bestanden verschijnen in de rij **Workspace changes** van het antwoord, en fouten in tools behouden de begrensde HTTP-diagnostiek van de worker. Een Agent kan ook een Git-naam en e-mailadres per Agent opslaan voor commits die in die workspace zijn gemaakt; deze waarden configureren alleen het auteurschap en bieden geen inloggegevens voor de repository.

In de chat toont een mislukt attached-workspace Bash-commando de exit-code, het terminating-signaal of de timeout, en de stderr wordt afzonderlijk van stdout gestyled. Zie [Activity Groups](/docs/features/agents#activity-groups) voor hoe Bash-output wordt weergegeven.

Een gekoppelde worker adverteert de workspace-roots die deze beschikbaar stelt. De composer laat de gebruiker één workspace selecteren voor elke gekoppelde omgeving die bereikbaar is via de Agent of zijn Subagents; voor een nieuw gesprek wordt automatisch één eenduidige workspace geselecteerd. LibreChat slaat deze selecties op bij het gesprek, valideert ze opnieuw tegen de live worker vóór uitvoering, en houdt ze vast tijdens pauzes voor goedkeuring en hervatte runs. Verzenden wordt geblokkeerd wanneer een vereiste selectie ontbreekt of niet beschikbaar is, en LibreChat vervangt nooit stilletjes een andere workspace. Bij de start van een run kan LibreChat repository-instructies laden vanuit de geselecteerde workspace, zodat de Agent de richtlijnen van die repository volgt; beheerders kunnen de detectie beperken met [`repositoryInstructions.timeoutMs`](/docs/configuration/librechat_yaml/object_structure/agents#repositoryinstructions). Native file- en Bash-workspace-tools kunnen een geadverteerde root gebruiken, zelfs wanneer de worker geen herbruikbare runtime-sessies ondersteunt. Workspace-aware Programmatic Bash is beschikbaar op compatibele Code API- en worker-builds wanneer de programmatic-tool-configuratie van de Agent dit toestaat, de geautoriseerde gekoppelde worker gereed is en `programmaticLanguages: ['bash']` adverteert, en zowel de geselecteerde workspace als de worker `execute_command` toestaan. LibreChat geeft de server-gevalideerde workspace-ID en de conversation workspace-instance-ID, indien aanwezig, door aan de programmatic tool; model-argumenten kunnen die selectie niet vervangen. Zonder deze mogelijkheden is Programmatic Bash uitgeschakeld; gebruik directe Bash voor workspace-aware commando's. Wanneer de worker file relay ondersteunt, worden chat-uploads afzonderlijk klaargezet onder `$LIBRECHAT_CODE_DATA_DIR` voor de programmatic run, en niet gekopieerd naar de geselecteerde workspace. **Stop** annuleert een signaal-bewust in-flight BYOM-commando zonder de workspace ongeldig te maken voor latere commando's; losgekoppeld werk behoudt zijn eigen afzonderlijke annuleringslevenscyclus.

Voor een gekoppelde uitvoeringsomgeving kan de Agent Builder een **Workspace default** instellen op een momenteel geadverteerde root. Deze wordt gevalideerd tegen die gekoppelde omgeving en gebruikt om nieuwe gesprekken voor die Agent te initialiseren. Kies **Last used** om de browser-lokale voorkeur van de ingelogde gebruiker voor die Agent en omgeving te gebruiken; dit is slechts een handige hint, nooit een autorisatietoewijzing of gespreksbinding. Het wijzigen van de uitvoeringsomgeving wist een expliciete standaardinstelling, en een opgeslagen root die niet langer wordt geadverteerd blijft zichtbaar, maar kan niet worden geselecteerd totdat deze opnieuw is geconfigureerd.

#### Wijzigingen in de Saved-chat werkruimte [#saved-chat-workspace-changes]

Standaard is de gekoppelde werkruimtebeslissing van een opgeslagen gesprek verzegeld. Met [`statefulCodeSessions.conversationMoves.enabled`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions) ingeschakeld, kan de eigenaar expliciet verplaatsen naar een andere geautoriseerde werkruimte of een ontbrekende werkruimte herstellen. Herstel behoudt de chatgeschiedenis, **niet** de bestanden van de verloren werkruimte. Het instellen van `allowAttachDetach: true` stelt de eigenaar bovendien in staat om een werkruimte te koppelen aan een opgeslagen niet-coderende chat of een gekoppelde werkruimte te verlaten om de normale chat voort te zetten; het enkel inschakelen van verplaatsingen schakelt koppelen/ontkoppelen niet in. Deze overgangen kunnen niet plaatsvinden terwijl een generatie wordt uitgevoerd en worden opnieuw gevalideerd op de server. Upgrade alle API-replica's en schakel `CODE_ENVIRONMENT_DECISION_VERSION=1` in voordat u zich aanmeldt. Zonder de schakelaars blijft het bestaande gedrag voor alleen verplaatsen en verzegelde gesprekken ongewijzigd.

Attached Bash gebruikt standaard een time-out van 30 seconden. Een omgeving kan een groter budget voor modelaanvragen beschikbaar stellen met [`configSchema.limits.maxCommandTimeoutMs`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions), tot aan het protocol-maximum van vijf minuten. De aangevraagde time-out overschrijdt nooit de limiet van de implementatie. Beheerders kunnen het aantal pogingen voor capaciteit afzonderlijk begrenzen met [`configSchema.limits.maxQueueWaitMs`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions); deze wachtrij-wachttijd annuleert geen toegelaten of lopend commando. Om langere **individuele** toelatingspogingen toe te staan, gebruik `configSchema.limits.maxRequestTimeoutMs` pas nadat de Code API de wachtrij-toelage per aanvraag respecteert en de kortste proxy-time-out op de live-route is geverifieerd. De optionele `configSchema.limits.minCommandAdmissionMs` reserveert standaard 10 seconden (geldig 1–300 seconden) voor toelating voorafgaand aan een commando. De geadverteerde Bash-time-out wordt aangepast aan het aanvraagbudget na deze reserve en nog eens 10 seconden voor afhandeling en bezorging. Dit budget vervangt `maxQueueWaitMs` niet.

#### Linked-worktree lanes [#linked-worktree-lanes]

Gekoppelde omgevingen kunnen kiezen voor [per-worktree request scheduling](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions) met `configSchema.workspaces.linkedWorktrees: true`. Upgrade eerst LibreChat, implementeer vervolgens een compatibele Code API-bridge en start de worker met `--linked-worktree-lanes`; schakel de YAML-instelling pas in nadat die worker `git_linked_worktree` adverteert. Verzoeken die structureel gericht zijn op `.worktrees/<name>/` gebruiken de lane van die worktree zonder de checkout-relatieve paden die aan de Agent worden getoond te wijzigen. Geef voor Bash de worktree-directory door in het `cwd`-argument van de tool; het uitvoeren van `cd .worktrees/<name>` binnen het commando blijft in de root-lane. Checkout-root operaties, omgevingsacties en conversation workspace-instanties blijven ook root-scoped. Zonder deze opt-in behouden alle verzoeken hun bestaande checkout-brede scheduling.

#### Workspace bewerkingsmatching en conflicten [#workspace-edit-matching-and-conflicts]

`edit_file` accepteert een `replace_all` op het hoogste niveau voor een enkele `old_text`/`new_text` vervanging, of een per-item vlag wanneer een `edits` batch wordt meegeleverd. Zonder deze vlag moet elke `old_text` naar één locatie verwijzen. Een meegeleverde batch moet niet-leeg en geldig zijn; LibreChat wijst een lege of onjuist gevormde `edits` waarde af in plaats van terug te vallen op vervangingsvelden op het hoogste niveau. Geldige JSON-geformatteerde batches en booleaanse vervangingsvlaggen worden genormaliseerd vóór de goedkeuring van de native tool, zodat het voorbeeld en de uitvoering dezelfde canonieke bewerkingen gebruiken, inclusief beoordeelde hook-herschrijvingen. Skill-file en managed-sandbox bewerkingen ondersteunen het vervangen van alle overeenkomsten binnen de limieten van LibreChat voor grootte en aantal overeenkomsten; gekoppelde workspaces vereisen een worker die `replace_all` ondersteunt en wijzen niet-ondersteunde verzoeken af vóór verzending.

Op gekoppelde workers die `tolerant_match` adverteren, proberen bewerkingen en beveiligde previews eerst een exacte overeenkomst, gevolgd door strategieën die tolerant zijn voor witruimte voor achterblijvende witruimte, CRLF, inspringingsverschuivingen of genormaliseerde witruimte. Beheerders kunnen exacte overeenkomsten vereisen met [`configSchema.edits.tolerantMatching: false`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions). Succesmeldingen identificeren niet-exacte overeenkomsten of meervoudige vervangingen. Mislukte batches zijn atomair: er wordt niets geschreven en LibreChat rapporteert begrensde redenen per bewerking, aantallen, kandidaat-regelnummers of een waarschuwing voor gewijzigde bestanden zonder willekeurige worker-tekst of bestandfragmenten door te sturen.

Deze attached-worker functies vereisen compatibele Code API- en worker-builds die [Code Interpreter #271](https://github.com/LibreChat-AI/code-interpreter/pull/271) implementeren. LibreChat verstuurt de nieuwe velden pas na capability negotiation. Bij oudere builds blijven het request-formaat en het matching-gedrag ongewijzigd; het enkel upgraden van LibreChat schakelt tolerant attached edits of `replace_all` niet in.

#### Rechten voor tools in de gekoppelde omgeving (Attached-environment) [#attached-environment-tool-permissions]

Gekoppelde en persoonlijke omgevingen gebruiken een 'vragen-bij-standaard' goedkeuringsbeleid voor het schrijven van bestanden en het uitvoeren van opdrachten of code. Lees- en zoekbewerkingen blijven vallen onder het reguliere toolbeleid van de implementatie. Als de beheerder een van beide categorieën openstelt via [`configSchema.permissions`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions), kunnen gebruikers met de machtiging voor Code Environment-beheer kiezen uit de toegestane waarden **Toestaan**, **Vragen** of **Weigeren** onder **Instellingen > Code-omgevingen**. Ontbrekende, verouderde of niet-toegestane instellingen vallen veilig terug op **Vragen**.

De composer toont een **Code approval mode** op gespreksniveau wanneer de geselecteerde gekoppelde omgeving dit ondersteunt:

- **Ask before changes** vraagt om bevestiging vóór bestandswijzigingen of opdrachten.
- **Accept edits** staat bestandswijzigingen toe, maar blijft om bevestiging vragen voordat opdrachten worden uitgevoerd.
- **Volledige toegang** staat beide categorieën toe zonder routinematige prompts.

De geselecteerde modus reist mee met dat gesprek en wordt gekruist met de toegestane waarden van de deployment en het omgevingsbeleid. **Full access** verschijnt alleen wanneer zowel `fileWrite` als `commandExecution` op `allow` staan; het omzeilt niet de sandbox-isolatie, roltoewijzingen, expliciete endpoint `ask` of `deny` regels, Skill-file bevestiging of goedkeuringshooks.

Bij een import van een conversatie kan geen Code approval mode worden geselecteerd voor de ontvanger. Nieuwe geïmporteerde of in bulk gekopieerde conversaties gebruiken de voorkeur/standaardinstelling van de ontvanger onder het huidige beleid; bulk-updates behouden elke lokaal opgeslagen keuze. Bestaande conversaties worden niet met terugwerkende kracht gereset, en het expliciet selecteren van een modus in LibreChat blijft deze behouden.

Deze besturingselementen hebben betrekking op tools voor het schrijven van bestanden, shell- en code-uitvoering, compilatiecontroles en Programmatic Tool Calling. Voor het schrijven naar persistente Skill-bestanden is nog steeds bevestiging vereist wanneer Skill-authoring beschikbaar is, zelfs wanneer gewone bestandsschrijfacties zijn toegestaan. De instellingen wijzigen geen VM-isolatie, netwerken, mounts, bevoorrechte uitvoering, inkomend verkeer, uitgaand verkeer of toegang tot geheimen.

De expliciete [`toolApproval.enabled: false`](/docs/configuration/librechat_yaml/object_structure/agents#toolapproval) instelling van de deployment is een nood-override die deze basislijn uitschakelt. Zonder die override zal een aanroeper die geen goedkeuringsverzoeken kan presenteren en hervatten, standaard falen in plaats van stilletjes een tool in een gekoppelde omgeving uit te voeren.

Pairing verifieert het transport van de externe worker; het is geen sandbox-grens. Houd het lokale uitvoering-endpoint van de worker op loopback of een privaat netwerk en gebruik een geschikte isolatiemodus voor niet-vertrouwde code.

Terwijl een uitvoering actief is, volgen de uitgebreide deelvensters voor code- en shell-details de gestreamde argumenten naar beneden. Omhoog scrollen pauzeert dit volg-gedrag, zodat u eerdere uitvoer kunt inspecteren zonder dat het deelvenster het weergavevenster wegtrekt.

## De API gebruiken [#using-the-api]

### In LibreChat [#in-librechat]

De API heeft eersteklas ondersteuning in LibreChat via deze hoofdmethoden:

1. **[AI Agents](/docs/features/agents#code-interpreter)**: Schakel Code Interpreter in de configuratie van je agent in om deze in staat te stellen automatisch code uit te voeren en bestanden te verwerken.

2. **Handmatige uitvoering**: Gebruik de "Run Code"-knop in codeblokken binnen de chatinterface, zoals hier getoond:

3. **[Programmatic Tool Calling](/docs/features/agents#programmatic-tool-calling)**: Schakel de `programmatic_tools` capability in en markeer geselecteerde MCP tools als Programmatic, zodat agents deze tools kunnen aansturen vanuit sandboxed code.

4. **[Background Tool Calls](/docs/features/agents#background-tool-calls)**: Laat een agent in aanmerking komende code op de achtergrond uitvoeren en doorgaan terwijl deze draait.

5. **[Stateful Code Sessions](/docs/features/agents#stateful-code-sessions)**: Hergebruik experimenteel een werkruimte die is gekoppeld aan een gebruiker, een agent-en-gebruiker, of een gesprek, voor de code-uitvoeringen van een agent.

### API-sleutel instellen [#set-up-api-key]

- **Per-user setup:** Voer uw API-sleutel in LibreChat in wanneer daarom wordt gevraagd.
- **Globale configuratie:** Stel `LIBRECHAT_CODE_API_KEY` in het `.env` bestand van LibreChat in om één sleutel voor alle gebruikers te verstrekken.

De huidige [ClickHouse/code-interpreter](https://github.com/ClickHouse/code-interpreter) service gebruikt LibreChat JWT-authenticatie buiten de lokale modus. API-sleutels blijven beschikbaar voor compatibele Code Interpreter-implementaties.

### Self-hosted JWT-authenticatie [#self-hosted-jwt-authentication]

Met JWT-authenticatie ondertekent LibreChat een kortstondig bearer-token voor de geauthenticeerde gebruiker bij elk Code Interpreter-verzoek. De Code Interpreter-service verifieert de bijbehorende publieke sleutel en gebruikt de ondertekende gebruikers- en tenantcontext om bestanden en sessies te isoleren. De private ondertekeningssleutel blijft in LibreChat; Code Interpreter ontvangt alleen de publieke verificateur.

Configureer LibreChat met:

```env
CODEAPI_AUTH_PROVIDER=librechat-jwt
CODEAPI_JWT_PRIVATE_KEY="-----BEGIN PRIVATE KEY-----\n...\n-----END PRIVATE KEY-----"
CODEAPI_JWT_ALGORITHM=EdDSA
CODEAPI_JWT_KID=lc-codeapi-2026-05
CODEAPI_JWT_ISSUER=librechat
CODEAPI_JWT_AUDIENCE=codeapi
CODEAPI_JWT_TTL_SECONDS=300
CODEAPI_JWT_MINT_CACHE_SECONDS=30
CODEAPI_JWT_SINGLE_TENANT_ID=legacy
```

`CODEAPI_JWT_PRIVATE_KEY_BASE64` kan in plaats daarvan een base64-gecodeerde PEM bevatten, en `CODEAPI_JWT_PRIVATE_JWK_JSON` accepteert een private JWK. LibreChat ondersteunt Ed25519 (`EdDSA`, de standaard) en RSA (`RS256`) ondertekening. Zie de [environment-variable reference](/docs/configuration/dotenv#code-interpreter-jwt-authentication) voor elke instelling aan de kant van LibreChat.

Configureer Code Interpreter met de bijbehorende verifier:

```env
LOCAL_MODE=false
CODEAPI_AUTH_PROVIDER=librechat-jwt
CODEAPI_JWT_ISSUER=librechat
CODEAPI_JWT_AUDIENCE=codeapi
CODEAPI_JWT_ALLOWED_ALGS=EdDSA
CODEAPI_JWT_JWKS_JSON={"keys":[{"kty":"OKP","crv":"Ed25519","x":"...","kid":"lc-codeapi-2026-05","alg":"EdDSA"}]}
CODEAPI_JWT_SINGLE_TENANT_ID=legacy
```

De issuer, audience, key ID, het algoritme en de publieke sleutel moeten overeenkomen met de signer van LibreChat. Code Interpreter kan ook verifier-sleutels laden vanuit `CODEAPI_JWT_PUBLIC_KEY` plus `CODEAPI_JWT_KID`, of vanuit `CODEAPI_JWT_PUBLIC_KEYS_DIR`; een inline JWKS is handig voor rotatie. Houd de token TTL op of onder de `CODEAPI_JWT_MAX_TTL_SECONDS` van de Code Interpreter-service, die standaard op 300 seconden staat en hierop is begrensd.

Voor een lokale checkout bevat de Code Interpreter-repository een helper die bijbehorende Ed25519 signing- en execution-manifest-sleutels genereert en beide `.env`-bestanden bijwerkt:

```bash
node scripts/setup-local-auth-env.js --librechat /path/to/LibreChat
```

Single-tenant deployments kunnen `CODEAPI_JWT_SINGLE_TENANT_ID=legacy` behouden, maar de waarde moet op beide services overeenkomen. Multi-tenant deployments moeten een geauthenticeerde tenant-context bieden en `TENANT_ISOLATION_STRICT=true` inschakelen in LibreChat, plus `CODEAPI_TENANT_ISOLATION_STRICT=true` in Code Interpreter. De strikte modus weigert verzoeken zonder tenant-context in plaats van de single-tenant fallback te gebruiken.

### Directe API-integratie [#direct-api-integration]

De huidige self-hosted service verwacht een bearer token dat voldoet aan het LibreChat JWT claim-contract. Een directe integratie moet compatibele kortstondige tokens aanmaken en deze verzenden in de `Authorization: Bearer <token>` header. API-key-compatibele implementaties accepteren in plaats daarvan hun geconfigureerde sleutel in de `x-api-key` header. Gebruik nooit de authenticatievrije lokale modus van Code Interpreter op een openbaar of productie-endpoint.

### Self-hosted base URL [#self-hosted-base-url]

Stel `LIBRECHAT_CODE_BASEURL` in om LibreChat te laten verwijzen naar je zelf-gehoste [code-interpreter](https://github.com/ClickHouse/code-interpreter) instantie en configureer vervolgens [JWT authentication](#self-hosted-jwt-authentication). Voor een service die compatibel is met API-sleutels, stel je in plaats daarvan `LIBRECHAT_CODE_API_KEY` in. Zeer experimentele stateful Agent-sessies vereisen een aparte `stateful`-profielroute die is geconfigureerd via [`LIBRECHAT_CODE_BASEURL_STATEFUL`](/docs/configuration/dotenv#stateful-code-interpreter-endpoint) of genaamd [`statefulCodeSessions.environments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions).

## Kernfunctionaliteit [#core-functionality]

### Code Execution [#code-execution]

- Voer codefragmenten uit in ondersteunde talen
- Ontvang stdout/stderr-uitvoer
- Verkrijg uitvoeringsstatistieken (geheugengebruik, CPU-tijd)
- Programma-argumenten afhandelen
- Toegang tot uitvoeringsstatus en resultaten

### Bestandsbewerkingen [#file-operations]

- Upload invoerbestanden
- Genereerde outputs downloaden
- Bekijk gegenereerde Office-bestanden, inclusief PowerPoint `.pptx` presentaties en `.potx` sjablonen, plus CSV-, tekst- en PDF-achtige artefacten inline wanneer LibreChat deze veilig kan extraheren/renderen
- Geef PNG-, JPEG-, GIF- en WebP-afbeeldingen die door de `read_file` tool van een Agent worden geretourneerd weer als bekijkbare artefacten
- Beschikbare bestanden weergeven
- Verwijder onnodige bestanden
- Bestandssessies beheren

Gegenereerde artifact-voorbeelden zijn opzettelijk beperkt in grootte. Stel [`FILE_PREVIEW_MAX_EXTRACT_BYTES`](/docs/configuration/dotenv#inline-file-previews) in het `.env` bestand van LibreChat in om de limiet voor de bronbestandsgrootte voor inline preview-extractie te wijzigen; grotere bestanden blijven beschikbaar om te downloaden.

Sandbox-afbeeldingen die via `read_file` worden geretourneerd, hebben een inline-limiet van 1 MiB. Grotere afbeeldingen blijven in de sandbox voor verwerking met `bash_tool`. `LIBRECHAT_CODE_IMAGE_CHUNK_BYTES` regelt alleen de transport-chunkgrootte die wordt gebruikt bij het lezen van in aanmerking komende afbeeldingen; het verhoogt de inline-limiet niet.

<Callout type="warning" title="Upgrade-controle voor legacy code-outputs">
  Implementaties die dezelfde Code Interpreter-bestandsnaam genereerden voordat de unieke output-file index werd toegevoegd, kunnen dubbele MongoDB-records bevatten die voorkomen dat de index wordt opgebouwd. Bekijk het herstelproces eerst met `npm run migrate:code-file-duplicates:dry-run` en pas het vervolgens toe met `npm run migrate:code-file-duplicates`. De migratie behoudt de nieuwste canonieke bestandsnaam, hernoemt oudere records met numerieke achtervoegsels en bouwt de unieke index na een succesvolle uitvoering.
</Callout>

### Beperkingen [#limitations]
- Code heeft geen toegang tot het netwerk
- Er kunnen slechts 10 bestanden per run worden gegenereerd
- Resourcelimieten (RAM per uitvoering, bestandsgrootte voor uploads en verzoekquota) zijn afhankelijk van hoe je jouw deployment provisioneert en configureert.

## Open Source & Self-Hosting [#open-source--self-hosting]

De Code Interpreter-service is open source onder de Apache 2.0-licentie op [ClickHouse/code-interpreter](https://github.com/ClickHouse/code-interpreter). Door code-uitvoering als een afzonderlijke service te behouden, blijft de kern van de LibreChat-applicatie lichtgewicht: je implementeert de sandbox-infrastructuur alleen wanneer je deze nodig hebt, en je kunt deze onafhankelijk van de chat-app schalen.

De service draait als een set onafhankelijk schaalbare componenten (een API gateway, sandboxed workers en een file server) en ondersteunt sterke isolatiemodi (NsJail of een microVM via libkrun), zodat je onbetrouwbare code veilig kunt uitvoeren. Zie de README van de repository voor Docker Compose en Helm deployment-instructies.

## Conclusie [#conclusion]

De Code Interpreter API biedt een veilige, handige manier om code uit te voeren en bestanden te beheren in een geïsoleerde sandbox. Of je het nu gebruikt via de Agents van LibreChat of direct integreert in je applicaties, het biedt een robuuste oplossing voor behoeften op het gebied van code-uitvoering.

Voor gedetailleerde technische specificaties, implementatiehandleidingen en de API-referentie, zie de [code-interpreter repository](https://github.com/ClickHouse/code-interpreter).
