title: Your First Chat

LibreChat is software you host yourself, and it ships with no API key of its own. Once your instance is running, these steps take you from the login page to a working conversation.

<Callout type="info" title="Nothing running yet?">

Install LibreChat first: [Quick Start](/docs/quick_start) for the 5-minute Docker path, [Local Installation](/docs/local) for Docker, npm, or Helm, or [Remote Hosting](/docs/remote) to deploy it on a server.

To try LibreChat before installing anything, the project runs a free public demo at [chat.librechat.ai](https://chat.librechat.ai). It is meant for evaluation, not for private data.

</Callout>

<Steps>
  <Step>

### Open LibreChat in your browser

A local Docker or npm install serves the app at [http://localhost:3080](http://localhost:3080). The port comes from `PORT`. If you changed it, or mapped a different host port in `docker-compose.override.yml`, use that one instead.

Anywhere else, the address is the one your deployment hands you: the domain Railway assigns, your `username-projectname.hf.space` URL on Hugging Face, the server IP or domain in front of your remote Docker or Kubernetes install. `DOMAIN_CLIENT` is a separate setting, the address LibreChat puts in the links it generates, so point it at that same public URL rather than reading your browsing address out of it.

If nothing loads, see [If nothing loads](#if-nothing-loads) below.

  </Step>
  <Step>

### Create your account

Email registration is enabled by default (`ALLOW_REGISTRATION=true`), and there are no default credentials: click **Sign up** and choose your own email and password.

Not every instance offers that form. If there is no **Sign up**, use a provider button if one is shown, or the login form if the instance authenticates against a directory: either may create your account on first sign-in. When none is offered, or when signing in is refused because your account does not exist, ask whoever runs the instance for one. Which controls appear is decided by the instance's [authentication settings](/docs/configuration/authentication).

<Callout type="info" title="First Account = Admin in Single-Tenant Deployments">

In an unscoped single-tenant deployment, the first account registered becomes the admin account, and every account after it gets the `USER` role by default. Tenant-scoped deployments do not auto-promote the first user in each tenant; provision tenant administrators through a trusted administrative flow ([Authentication](/docs/features/authentication)).

An OpenID deployment can override the default role either way: `OPENID_ADMIN_ROLE` elevates a matching account to admin, and generic role sync (`OPENID_ROLE_SYNC_ENABLED`) maps provider roles onto other non-admin roles. See [OpenID Connect](/docs/configuration/dotenv#openid-connect).

</Callout>

If you configured [OAuth2/OIDC](/docs/configuration/authentication/OAuth2-OIDC) or [SAML](/docs/configuration/authentication/SAML), use that provider's button instead of the form.

[LDAP/AD](/docs/configuration/authentication/ldap) adds no button. Sign in on the same email and password form, entering your directory username in place of the email when the server sets `LDAP_LOGIN_USES_USERNAME=true`.

  </Step>
  <Step>

### Give a model an API key

LibreChat talks to AI providers with your credentials, and `.env.example` ships the pre-configured providers as `user_provided`:

```bash filename=".env"
OPENAI_API_KEY=user_provided
ANTHROPIC_API_KEY=user_provided
GOOGLE_KEY=user_provided
```

With that value, every user supplies their own key from the web UI. Select the endpoint, open the gear icon next to it, and fill in the **Set API Key** dialog.

That value is a default only where the install starts from `.env.example`, which means Docker and npm. A Helm release, a Railway service or a Hugging Face Space carries only the variables you set, so an endpoint whose credential you never set does not load at all, and no key dialog appears for it. Set the variable to `user_provided` there before expecting users to bring their own keys, and roll the workload so running pods or containers pick it up. You can also set or replace a key through **Settings → Data & Privacy → API keys → Provider API keys → Manage**.

The settings path also works when discovery returns an empty model list and hides a provider. It works when [model specs](/docs/configuration/librechat_yaml/object_structure/model_specs) or `interface.modelSelect: false` hide the selector. It lists providers configured to take a personal key, within the configured provider scope and your permissions. See [Personal Settings](/docs/features/settings#data--privacy).

To configure a key once for everyone instead, set the real key in place of `user_provided` and restart LibreChat. On Docker, recreate the containers with `docker compose up -d`, adding `-f ./deploy-compose.yml` if that is the file your stack runs from: `docker compose restart` keeps the environment the container already has, so the old value survives. No user is prompted, and the key stays on the server. Where you set it depends on how you installed: `.env` for Docker and npm, a Kubernetes Secret for [Helm](/docs/local/helm_chart#configuration), the service's variables in the Railway dashboard, Space Secrets on [Hugging Face](/docs/remote/huggingface). Provider-by-provider steps live in [AI Setup](/docs/configuration/pre_configured_ai).

<Callout type="warn" title="A shared key on a public URL is anyone's to spend">

Registration is open by default, so on an instance reachable from the internet, whoever finds the URL can sign up and bill your key. Before you configure a server-side key on a public deployment, make sure nobody you did not intend can get an account. The email form, each provider button and any directory you authenticate against all create users on their own terms, so closing one is not closing them all; [Authentication](/docs/configuration/authentication) covers the setting behind each. Leaving the providers at `user_provided` avoids the problem entirely.

</Callout>

<Callout type="info" title="No paid API key?">

Run a model on your own hardware with [Ollama](/docs/configuration/librechat_yaml/ai_endpoints/ollama), or reach many providers through a gateway such as [OpenRouter](/docs/configuration/librechat_yaml/ai_endpoints/openrouter). Both are added as [custom endpoints](/docs/quick_start/custom_endpoints).

</Callout>

  </Step>
  <Step>

### Send your first message

Pick an endpoint and model from the selector at the top of the chat, type your prompt, and send it. Where the instance hides the selector, use its configured selection. If you see **Select a model to continue**, follow the [recovery steps](#if-no-model-answers) below. The reply streams in, and the conversation is saved so you can return to it from the sidebar.

  </Step>
</Steps>

## If nothing loads

A page that never appears is an install problem, and the check depends on how you installed:

- **Docker.** Confirm the containers are running with `docker compose ps`, then read the API logs with `docker compose logs api`. On a server set up with the [Docker on Linux](/docs/remote/docker_linux) guide, the stack runs from a non-default compose file, so use `sudo docker compose -f ./deploy-compose.yml ps` and `sudo docker compose -f ./deploy-compose.yml logs api`. More in [Docker troubleshooting](/docs/local/docker#troubleshooting).
- **npm.** LibreChat runs in the terminal where you started `npm run backend`, so read that terminal's output. If the process has exited, start it again and read the error it prints.
- **[Helm](/docs/local/helm_chart) or another Kubernetes install.** Check that the pods are running with `kubectl get pods -n <release-namespace>`, read the API pod with `kubectl logs -n <release-namespace> <pod>`, and confirm the service or ingress actually exposes the port you are browsing to. Both commands default to your current namespace, so an empty list usually means the wrong one.
- **Railway or another host.** Open the deployment logs in the provider's dashboard (in Railway, the **View logs** button on the service), and browse to the public URL the provider assigned rather than `localhost`.

## If no model answers

- **The endpoint itself is missing from the selector.** Check `ENDPOINTS` in `.env`: when it is set, only the endpoints named there load. [Model specs](/docs/configuration/librechat_yaml/object_structure/model_specs) can also limit the selector. Neither a spec nor `modelSpecs.addedEndpoints` overrides model availability. A provider with an empty final model list is hidden. A key-based endpoint with no credential configured does not load, so set its key or `user_provided` and restart. On Docker, recreate the containers with `docker compose up -d`. For personal keys, use the [Settings path above](#give-a-model-an-api-key), even if discovery hides the provider. Providers such as [Bedrock](/docs/configuration/pre_configured_ai/bedrock) can use credentials from their environment instead of a key.
- **The endpoint is there, but the model you want is not.** Check the provider's page in [AI Setup](/docs/configuration/pre_configured_ai). Built-in providers such as OpenAI use a configured or built-in list with `user_provided` keys; see [`OPENAI_MODELS`](/docs/configuration/pre_configured_ai/openai). Some built-in providers can discover models with a server-side key. Others, such as [Google](/docs/configuration/pre_configured_ai/google), use configured lists. A [custom endpoint](/docs/configuration/librechat_yaml/object_structure/custom_endpoint#models) uses `models.default` and `models.fetch`, not `_MODELS`. Custom endpoint discovery can use a stored personal key. Successful discovery replaces defaults, even with an empty list. Discovery failure uses configured defaults, or an empty list if there are none. Model specs can further limit which models appear.
- **The reply fails with an authentication or invalid-key error.** The key is wrong, expired, or has no access to the selected model. Re-enter it in the **Set API Key** dialog, or fix the value in your install's environment and restart.

### Continue a chat after model access changes

Your chat history remains available when a model becomes unavailable. When you chat directly with a provider, the loaded model list must include your selected model. Otherwise, sending is blocked and the chat shows **Select a model to continue**. Choose an available model, or restore access and reload the page. If the selector is hidden, ask your administrator to update the configured selection or restore access.

When a refreshed list includes the model again, it becomes selectable and usable. Choose it again if needed.

Before the browser has fetched a model list, an otherwise valid selection can still send. Server access checks still apply. If a later browser request for the list fails, the browser keeps its last fetched list. This differs from provider discovery failure: the server can return configured fallback models in a successful response to the browser.

### Model list cache

Where server caching is allowed, successful discovery results, including empty lists, use the existing two-minute cache. A failed refresh of token metadata can keep a cached model list without extending its lifetime. This metadata describes model token limits and costs. The cache does not make the browser poll every two minutes. After you restore access, reload the page to fetch the list again.
