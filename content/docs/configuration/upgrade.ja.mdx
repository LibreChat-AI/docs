## v0.8.9-rc1 の準備 [#preparing-for-v089-rc1]

ローカルでインストールする場合は、Node.js **24.22.1** を使用してください。バージョンを変更する前に、MongoDB、`librechat.yaml`、および暗号化の認証情報をバックアップしてください。`CREDS_KEY` と `CREDS_IV` は保持してください。これらを置き換えても移行にはなりません。設定バージョン `1.3.18` は、この候補版を説明しています。追加された設定については、[設定の変更履歴](/changelog/config_v1.3.18)を参照してください。

LibreChat のすべての API レプリカを、古いレプリカでは適用できない機能を有効にする前にアップグレードしてください。互換性のあるクライアント、Code API サービス、接続されたワーカーは、それぞれ個別に更新してください。LibreChat イメージは、独立してデプロイされた Code API やそのインストール済みの言語パッケージをアップグレードするものではありません。

### 異なるバージョン間の互換性 [#mixed-version-compatibility]

| 対象 | 非互換のレプリカまたはクライアントが残っている間 | ロールアウト後 |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| 保存されたユーザー資格情報 | 各レプリカのデプロイ用 YAML で `credentials.writeFormat: legacy` を設定します。 | 上書き設定を削除すると、値ごとにランダムな IV を用いる `v3` 形式で書き込まれます。両方の形式は、このリリースでも引き続き読み取れます。 |
| 2 要素認証のバックアップコード | 古いバックエンドやクライアントが強力なコードを読み取れない場合は、各レプリカで `TWO_FACTOR_BACKUP_CODE_FORMAT=legacy` を設定します。 | 削除すると、128 ビットのランダムかつ個別にソルトが付与されたコードが発行されます。既存のレガシーコードは再生成されるまで有効なままです。 |
| メールアドレスの変更 | `emailChange.enabled: false` または `ALLOW_EMAIL_CHANGE=false` を設定します。YAML のフラグが優先されます。 | すべてのノードがアドレスに紐づくパスワードリセットリンクに対応してから有効にしてください。対応していない古いノードが発行したリンクは、メールアドレス変更後も有効なままになる可能性があります。 |
| チャットごとのマシン選択 | `CODE_ENVIRONMENT_DECISION_VERSION=0` または `endpoints.agents.statefulCodeSessions.allowEnvironmentSelection: false` を設定します。 | 決定プロトコル v1 とマシン選択はデフォルトで有効ですが、マシンの明示的な許可リストを持つエージェントのみが選択肢を提示できます。 |
| 保存済みチャットのワークスペース変更 | `statefulCodeSessions.conversationMoves.enabled` はオフのままにします。`allowAttachDetach` は別途のオプトインです。 | すべての API レプリカおよび互換性のある Code API/ワーカーでプロトコル v1 を使用する場合にのみ有効にしてください。その後、クライアントを更新してください。 |
| 記憶されるツール承認 | `endpoints.agents.toolApproval.agentModes: false` のままにします。 | すべてのレプリカがこのモードに対応してから、明示的にオプトインしてください。管理者による確認/拒否のルールは引き続き優先されます。 |
| バッチ処理されるバックグラウンド完了通知 | 古いレプリカがトラフィックを処理している間は、`endpoints.agents.backgroundTasks.completionReceiptBatching: false` を設定します。 | 上書き設定を削除すると、完了した結果がまとめて配信されます。 |
| 実行中のチャットの名前変更 | 古いタイトル生成ジョブが完了するまで、`interface.runningChatRename: false` を設定します。 | 上書き設定を削除すると、実行中またはプレースホルダーのタイトルを持つチャットの名前変更が可能になります。 |

書き込み形式のスイッチを元に戻しても、すでに保存されているデータは変換されません。古いリリースでは、v3 形式で保存された認証情報や新たに発行された強力なバックアップコードを読み取ることができません。ロールバックの前に、暗号化キーをローテーションするのではなく、互換性のないデータを意図的に置き換えるか移行してください。

### 認証とセキュリティポリシー [#authentication-and-security-policy]

[パスキーでのサインイン](/docs/configuration/authentication)は、`ALLOW_PASSKEY_LOGIN=true` によってオプトインで有効化され, 本番環境では HTTPS が必要です。リライングパーティ ID は安定させてください。`PASSKEY_RP_ID` を変更すると、既存の登録が無効になる可能性があります。`passkeys.perUserMax` は `MAX_PASSKEYS_PER_USER` を上書きします。デフォルトは 20 です。

`ENFORCE_TWO_FACTOR_AUTHENTICATION` のデフォルト値は `false` です。有効にすると、メール/パスワードおよび LDAP アカウントは、完全なセッションを受け取る前に登録を完了する必要があります。フェデレーテッドプロバイダーは、それぞれ独自の多要素認証(MFA)に引き続き責任を持ちます。一時コードの試行回数上限(`TWO_FACTOR_TEMP_MAX`、`TWO_FACTOR_TEMP_WINDOW`)は、セットアップ手順の試行回数上限(`TWO_FACTOR_SETUP_MAX`、`TWO_FACTOR_SETUP_WINDOW`)とは別に管理されます。

システム権限の付与や、リソース共有範囲を広げる変更は、変更前の監査書き込みが失敗した場合、デフォルトで失敗側に倒れます(フェイルクローズ)。取り消し操作は監査の障害によってブロックされることはありません。`AUDIT_LOG_FAIL_CLOSED=false` を設定した場合にのみ、このデフォルトの保護が無効になります。その他の管理者による変更には、操作ごとに固有の監査順序があります。監査でエラーが発生したからといって、必ずしもロールバックが行われるわけではありません。

### 管理者設定とシークレット [#admin-configuration-and-secrets]

アクティブなデータベースのBaseプロファイルは、Baseの数値優先度に関係なく、ロール、グループ、ユーザーのプロファイルより前にデプロイ用YAMLの設定を上書きします。その他のアクティブなプロファイルは、優先度の昇順でマージされ、同順位の場合は決定的な順序で処理されます。上書きを削除すると継承が復元されます。トゥームストーン(削除マーカー)は、継承された値を抑制します。通常の配列は全体として抑制されます。サポートされているキー付きコレクションでは、名前付きの個別のエントリを非表示にすることもできます。そのトゥームストーンを削除すると、継承が復元されます。

管理者設定の `changes` エンドポイントは、バッチを1つのプロファイルに対してアトミックに適用します。`dryRun` を使用して検証を行い、`expectedRevision` を使用して楽観的同時実行制御を行います。古いリビジョンを指定すると `409` が返されます。保護された設定は、バッチ全体を拒否することなく未適用のまま残る場合があるため、無視された結果を確認してください。この保証により、ロール名の変更やその他の複数ドキュメントにまたがる管理者操作がアトミックになるわけではありません。

管理者が記述する `${ENV_VAR}` 参照は、デプロイ用 YAML で参照されている名前、組み込みエンドポイントの認証情報、および `CONFIG_OVERRIDE_ENV_ALLOWLIST`(カンマまたはスペース区切り)に含まれる名前に限定されます。許可されていない参照は書き込み時に拒否され、実行時には何にも解決されません。Vertex AI のオーバーライドはより厳しく制限されており、`endpoints.anthropic.vertex` では、デプロイ用 YAML の Vertex 設定自体で参照されている環境変数名のみを使用できます。一般的な許可リストに含まれるその他の名前は使用できません。`interface`、`modelSpecs`、エンドポイントのタイトル・アクティビティ・推論ラベルのプロンプト、要約プロンプト、メモリの指示、Firecrawl の変更追跡プロンプトで文字通りに使用されるテキストは、この制限の対象外です。

保存されたWeb検索、MCP、Azureの認証情報は、その送信先に紐付けられています。紐付けられた送信先を変更または削除する書き込みでは、同じ書き込みの中で保存済みのキーを再入力するか、キーを削除する必要があります。`secret_reentry_required` を処理する場合は、必要な秘密情報を再度収集してください。古いキーを新しいURLに対して黙って再試行しないでください。環境が管理する認証情報およびユーザーが管理する認証情報は、管理者プロファイルを通じて送信先を変更することはできません。

`CONFIG_REDERIVE_ENDPOINTS` は、このリリースではデフォルトでオフになっています。プロファイルによる Azure グループの上書き、`endpoints.anthropic.vertex`、および Azure Assistants のスイッチは、引き続き保存されますが、オペレーターが有効にするまで効果はありません。すべてのレプリカで有効にする前に、影響を受けるプロファイルおよび解決できないグループについて、起動時の診断情報を確認してください。プロファイルの Vertex 設定は、デプロイメントの YAML で Vertex が設定されている場合にのみ適用され、その際はデプロイメントが管理するキーファイルとリージョンが使用されます。

カスタムロールの名前を変更すると、そのテナント内でメンバー、設定プロファイル、権限付与、ACLエントリが移動されます。ロールを削除すると、メンバーは `USER` に再割り当てされ、依存する設定と権限付与は削除されます。これらの複数ドキュメントにわたる変更は、単一のアトミックなトランザクションとしては実行されません。失敗した後は、再試行する前に現在の状態を確認してください。すでに取り消されたアクセスは取り消されたままになる場合があります。

### 厳格なテナント認証 [#strict-tenant-authentication]

`TENANT_ISOLATION_STRICT=true` の場合、認証およびアカウント関連のルートは、ユーザーを検索する前に、実在する非システムのテナントを必要とします。テナントコンテキストが欠落している場合は `403` と `TENANT_CONTEXT_REQUIRED` で拒否されます。OAuth フローでは、失敗時のリダイレクトを使用します。サインインおよびリフレッシュのルートを含め、テナントのルーティングは、信頼できるプロキシまたは認証の境界で検証してください。厳格な分離を無効にしたり、任意の公開ヘッダーを信頼したりして、テナントの欠落を回避しないでください。

デプロイ全体にわたる起動時チェック、インデックスの同期、および権限の移行は、明示的なシステムスコープで実行されます。移行処理がリソースを書き込む際には、そのリソースのテナントパーティションが維持されます。これらのチェックが、通常の認証リクエストにシステムテナントへのフォールバックを許可することはありません。

### 共有パッケージの互換性 [#shared-package-compatibility]

更新された共有パッケージは Zod 4 を使用しています。LibreChat のスキーマをインポートして組み合わせるカスタム統合では、Zod の使用方法を更新し、対応するパッケージバージョンに対して再ビルドする必要があります。これらのパッケージを Zod 3 に戻すオーバーライドは行わないでください。今回のリリースでは、省略された任意の設定フィールドと検証診断情報が引き続き保持されます。ライブラリの移行に伴って、新しい YAML バージョンの増分や一括的な設定の書き換えは必要ありません。

カスタムフロントエンドで、削除されたレガシーの `@librechat/client` コントロールをインポートしている場合は、保守されているコントロールへ移行する必要があります。特に、`Select`、`SelectDropDown`、`Dialog`、`DialogTemplate`、および Radix の `DropdownMenu` エクスポートは提供されなくなりました。ダイアログには `OGDialog`/`OGDialogTemplate` を、単一値のセレクターには `Dropdown` を、アクションメニューには `DropdownPopup` または Ariakit のプリミティブを使用してください。LibreChat 自身の呼び出し元はすでに移行済みです。これは開発者向けの統合上の変更であり、セルフホスト環境の設定を書き換える必要はありません。

### ブラウザのテレメトリ [#browser-telemetry]

RUM、クライアントログ、セッションリプレイは、それぞれ独立したオプトインです。YAMLの`telemetry.rum.enabled`と`telemetry.rum.sessionReplay.enabled`は、環境変数によるフォールバックよりも優先されます。省略した場合は環境変数の設定が維持され、YAMLで空の`sessionReplay: {}`を指定するとリプレイが無効になります。

- `RUM_CLIENT_LOGS=true` は、認証付きプロキシモードでのみ、マスキング処理済みのクライアント診断ログを有効にします。
- `RUM_SESSION_REPLAY_ENABLED=true` は、RUM が有効な場合にリプレイを有効化します。これは非推奨となった反対の意味を持つ `RUM_DISABLE_REPLAY` フォールバックよりも優先されます。
- `RUM_PROXY_BODY_LIMIT` のデフォルトは `3mb` です。トレースとログは認証済みユーザーのバジェットを共有します: `RUM_PROXY_USER_WINDOW=1` 分あたり `RUM_PROXY_USER_MAX=240` 件です。上限を超えたリクエストは `429` を返します。
- Replay はテキストと入力値をマスクし、認証画面を除外しますが、**汎用の DLP（情報漏えい防止）機能ではありません**。実際のユーザーを記録する前に、合成データで検証してください。公開トークンによる直接的なデータ取り込みはサーバー側の Replay フィルタリングを回避するため、独自のコレクターポリシーが必要です。

`LOG_REDACTION_MAX_NODES=5000` は、サーバーログのレコード1件あたりに行われる編集（redaction）処理の作業量を制限します。オブジェクトや文字列は長さに応じた重みで予算を消費し、予算を超えたフィールドは未編集のままエクスポートされるのではなく、置き換えられます。この処理レベルの設定は、ロガーの初期化時に読み込まれます。

### 接続されたコーディングとMCP Apps [#connected-coding-and-mcp-apps]

Stateful Code セッションは依然として非常に実験的な機能です。ブラウザで承認されたエンロールメントだけでは、すべてのエージェントがマシンにアクセスできるようにはなりません。接続先の環境を設定し、principal-worker エンロールメントとその独立した `browserSetup.enabled` のオプトインを有効にし、正規の公開 `instance` を設定し、互換性のあるワーカーを起動し、エージェントの明示的なマシン許可リストを保存してください。新しいチャットでは、その許可リストからのみ選択できます。既存の会話は、記録されている決定を引き続き保持します。

`endpoints.agents.pullRequests` 統合（任意）には、git の状態を報告できる互換性のあるワーカー、Code API の `CODEAPI_BRIDGE_LANE_GIT=true`、リポジトリのスコープ、および適切な範囲に限定されたプロバイダートークンが必要です。GitHub では、Pull requests、Checks、Contents への読み取り専用アクセスが必要です。GitLab と Bitbucket は、それぞれのプロバイダー固有の認証情報を使用します。ユーザーごとの OAuth 接続は、別途オプトインする必要があります。

新しい MCP Apps には `mcpSettings.apps: true` が必要です。このキーを省略すると従来のインライン HTML の動作が維持され、`false` に設定すると両方とも無効になります。MCP App サンドボックスは専用のオリジンにデプロイし、`/api/mcp/sandbox` にルーティングしてください。デプロイ時のサンドボックスポリシーは、ロール・グループ・ユーザー単位の上書きには該当しません。サンドボックスオリジンとビルド時のセットアップについては、[MCP 設定ガイド](/docs/configuration/librechat_yaml/object_structure/mcp_settings)を参照して適用してください。

### ファイルクリーンアップの展開 [#file-cleanup-rollout]

`fileConfig.retainedFileCleanup` はデフォルトでオフのままです。すべてのレプリカとロールバック先が保持ファイルの保存先をサポートするまで、有効にしないでください。ベクトルのクリーンアップには、`fileConfig.vectorOwnershipTrackingStart` も必要です。これは、レガシーなベクトル書き込み処理とロールバック先がすべて廃止された後に選択する UTC のカットオフ時刻であり、さらにそのカットオフ時刻以降に作成されたファイルについて、完全な所有権の証明が記録されている必要があります。削除を進めるためだけにカットオフ時刻を過去に遡らせたり、過去のファイルの所有権を推測したりしないでください。

曖昧な記録、またはカットオフ以前の記録は、安全側に倒して失敗させます(フェイルクローズ)。セカンダリのクリーンアップが確認されるまで、プライマリファイルは読み取り可能な状態を保ちます。`fileConfig.vectorDeletionConcurrency` のデフォルト値は `4` で、ファイルごとに `1`〜`16` の名前空間の削除を指定できます。これらを有効にする前に、[ファイルのクリーンアップ制御](/docs/configuration/librechat_yaml/object_structure/file_config#retained-file-and-vector-cleanup)を参照してください。

### その他の変更されたデフォルト値 [#other-changed-defaults]

- デフォルトでは Enter キーでメッセージが送信されます。ユーザーは設定画面でこの設定を変更できます。
- ブラウザでの画像リサイズは、`fileConfig.clientImageResize.enabled` が省略されている場合、デフォルトで有効になります。明示的に `true` または `false` を指定すると、デプロイメント全体の設定が強制されます。
- `interface.retentionMode: ephemeral` は、すべてのチャットを一時的なものとして強制します。`temporary` に戻す前に、期限切れにしてはならないレコードから保持期限を削除してください。既存の期限は自動的には移行されません。
- 一時的なチャット（エフェメラルモードのチャットを含む）は、`langfuse.trace.temporaryChats` が有効になっていない限り、トレースもフィードバックのスコア付けも行われません。
- `interface.historyCacheTtlMs` のデフォルト値は `60000`、`historyCacheRecent` のデフォルト値は `1` です。さらに `historyCacheMaxBytes` として `8388608` バイトの上限が設けられており、最近離れた履歴がキャッシュされる期間を制限します。
- `toolCallPreviews` は、プレビューを要求するクライアントに対してデフォルトで制限付きのプレビューを返します。`outputChars` と `argsChars` のデフォルト値は `512` です。エクスポートやプレビューを要求しないクライアントでは、引き続き全内容が保持されます。

既存のオプションについては、[インターフェースのリファレンス](/docs/configuration/librechat_yaml/object_structure/interface)、[Agentsのリファレンス](/docs/configuration/librechat_yaml/object_structure/agents)、および[環境変数のリファレンス](/docs/configuration/dotenv)をご覧ください。
