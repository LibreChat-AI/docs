### Generale [#general]

LibreChat ha un sistema di logging centrale integrato nel suo backend (api).

- Con l'installazione **docker**, i file di log vengono salvati in `/logs`

<FileTree>
  <FileTree.Folder name="librechat" defaultOpen>
    <FileTree.Folder name="logs" defaultOpen>
      <FileTree.File name="debug-2024-01-01.log" active />
      <FileTree.File name="error-2024-01-01.log" active />
      <FileTree.File name="meiliSync-2024-01-01.log" active />
    </FileTree.Folder>
  </FileTree.Folder>
</FileTree>

- Con l'installazione **npm**, i file di log vengono salvati in `/api/logs`

<FileTree>
  <FileTree.Folder name="librechat" defaultOpen>
    <FileTree.Folder name="api" defaultOpen>
      <FileTree.Folder name="logs" defaultOpen>
        <FileTree.File name="debug-2024-01-01.log" active />
        <FileTree.File name="error-2024-01-01.log" active />
        <FileTree.File name="meiliSync-2024-01-01.log" active />
      </FileTree.Folder>
    </FileTree.Folder>
  </FileTree.Folder>
</FileTree>

I log degli errori vengono salvati per impostazione predefinita. I file di log di debug vengono scritti solo quando `DEBUG_LOGGING=true`; il file `.env.example` fornito lo imposta su `true`, ma se la variabile non è impostata non viene creato alcun file di debug.

Ciò ti consente di monitorare il tuo server tramite strumenti esterni che analizzano i file di log, come **[lo stack ELK](https://aws.amazon.com/what-is/elk-stack/)**.

I log di debug sono essenziali per il lavoro di sviluppo e per la risoluzione dei problemi. Se riscontri problemi nell'esecuzione di LibreChat, riproducili il più fedelmente possibile e **[segnala il problema](https://github.com/LibreChat-AI/LibreChat/issues)** includendo i log che trovi in `./api/logs/debug-%DATE%.log`.

I log degli errori vengono salvati nella stessa posizione: `./api/logs/error-%DATE%.log`. Se hai configurato meilisearch, esiste un file di log separato anche per questo.

<Callout type="note" title="Nota:">
  I file di log vengono ruotati ogni giorno: ogni giorno viene avviato un nuovo file, e un file viene inoltre suddiviso una volta raggiunti i 20 MB. I file ruotati vengono compressi con gzip e conservati per 14 giorni. Anche gli errori sono presenti nei file di log di debug, ma i file di log degli errori forniscono stack trace e maggiori dettagli.
</Callout>

### Configurazione [#setup]

- I file di log di debug vengono scritti solo quando questa variabile è impostata su `true`. Se non è impostata o è impostata su un valore diverso, non viene creato alcun file di debug.

<OptionTable
  options={[['DEBUG_LOGGING', 'boolean', 'Scrivi i log di debug su file. Necessario affinché vengano creati i file di log di debug.', 'DEBUG_LOGGING=true']]}
/>

> Nota: si consiglia di lasciare disattivati i log di debug in un ambiente di produzione.

- Per un output del server dettagliato nella console/terminale, è possibile impostare quanto segue su `TRUE`:

<OptionTable
  options={[
    [
      'DEBUG_CONSOLE',
      'boolean',
      'Abilita i log dettagliati della console/stdout nello stesso formato dei log di debug dei file.',
      'DEBUG_CONSOLE=false',
    ],
  ]}
/>

Tuttavia, questo non è consigliato, poiché gli output possono essere piuttosto prolissi. È disabilitato per impostazione predefinita e dovrebbe essere abilitato con parsimonia.

- Quando si gestiscono i log della console in distribuzioni cloud (come GCP o AWS), l'abilitazione di questa opzione scaricherà i log con un timestamp UTC e li formatterà come JSON.

<OptionTable
  options={[
    [
      'CONSOLE_JSON',
      'boolean',
      'Abilita log dettagliati in formato JSON su console/stdout adatti a distribuzioni cloud come GCP/AWS.',
      'CONSOLE_JSON=false',
    ],
  ]}
/>

Per impostazione predefinita, la lunghezza della stringa JSON viene troncata a 255 caratteri. È possibile configurarla con la seguente variabile d'ambiente:

<OptionTable
  options={[
    [
      'CONSOLE_JSON_STRING_LENGTH',
      'number',
      'Configura la dimensione di troncamento per i valori stringa nei log della console/stdout JSON. Predefinito: 255.',
      '# CONSOLE_JSON_STRING_LENGTH=255',
    ],
  ]}
/>

- La verbosità della console può essere impostata con `CONSOLE_LOG_LEVEL` (`error`, `warn`, `info`, `http`, `verbose`, `debug`, `activity`, `silly` o `silent`). `silent` disattiva l'output della console senza disabilitare la registrazione su file. I valori non validi ricorrono al valore predefinito con un avviso.

<OptionTable
  options={[
    [
      'CONSOLE_LOG_LEVEL',
      'string',
      'Verbosità della console. Il valore predefinito è info, oppure debug quando DEBUG_CONSOLE=true; un valore esplicito ha la precedenza.',
      '# CONSOLE_LOG_LEVEL=info',
    ],
  ]}
/>

- I messaggi di log di debug vengono troncati a 150 caratteri per impostazione predefinita, e la redazione dei log è limitata a 5000 valori per record. Puoi modificare questi valori con `DEBUG_MESSAGE_LENGTH` e `LOG_REDACTION_MAX_NODES`.

<OptionTable
  options={[
    [
      'DEBUG_MESSAGE_LENGTH',
      'number',
      'Lunghezza massima di un messaggio di log di debug prima che venga troncato. Predefinito: 150.',
      '# DEBUG_MESSAGE_LENGTH=150',
    ],
    [
      'LOG_REDACTION_MAX_NODES',
      'number',
      'Numero massimo di valori che un singolo record di log può oscurare prima che il resto venga sostituito. Predefinito: 5000.',
      '# LOG_REDACTION_MAX_NODES=5000',
    ],
  ]}
/>

- Per scrivere i file di log in una posizione diversa da quella predefinita, imposta `LIBRECHAT_LOG_DIR`. Vedi [Logging](/docs/configuration/dotenv#logging) nel riferimento del `.env`.

- I trasporti di log basati su file sono abilitati per impostazione predefinita. Imposta `LOG_TO_FILE=false` se la tua distribuzione deve emettere i log solo su stdout/stderr.

<OptionTable
  options={[
    [
      'LOG_TO_FILE',
      'boolean',
      'Impostare su false per disabilitare i transport Winston basati su file.',
      'LOG_TO_FILE=true',
    ],
  ]}
/>

### Tracciamento OpenTelemetry [#opentelemetry-tracing]

LibreChat può emettere tracce OpenTelemetry del backend per la visibilità di server, database, Redis e HTTP in uscita. Gli span a livello di comando di Redis sono facoltativi, in modo che le tracce predefinite rimangano ad alto livello. Questo è separato da Langfuse, che rimane l'opzione consigliata per l'osservabilità di prompt e modelli specifici per la GenAI.
