Ten przewodnik opisuje, jak skonfigurować Redis do buforowania i przechowywania sesji w LibreChat. Redis zapewnia znaczną poprawę wydajności i jest **wymagany do skalowania poziomego**. Jeśli uruchamiasz wiele instancji LibreChat za load balancerem, Redis zapewnia spójny stan we wszystkich instancjach.

## Podstawowa konfiguracja [#basic-setup]

### Włącz Redis [#enable-redis]

Aby włączyć Redis w LibreChat, ustaw następującą zmienną środowiskową w pliku `.env`:

```bash
USE_REDIS=true
```

**Ważne**: Gdy `USE_REDIS=true`, musisz również podać `REDIS_URI`. Aplikacja zgłosi błąd, jeśli Redis zostanie włączony bez podania URI połączenia.

## Typy połączeń [#connection-types]

### Pojedyncza instancja Redis [#single-redis-instance]

Dla standardowej konfiguracji z pojedynczym serwerem Redis:

```bash
# Local Redis instance
REDIS_URI=redis://127.0.0.1:6379

# Remote Redis instance
REDIS_URI=redis://your-redis-host:6379
```

### Klaster Redis [#redis-cluster]

W przypadku wdrożeń klastra Redis z wieloma węzłami:

```bash
# Multiple Redis cluster nodes
REDIS_URI=redis://127.0.0.1:7001,redis://127.0.0.1:7002,redis://127.0.0.1:7003
```

Aplikacja automatycznie wykrywa tryb klastra, gdy podano wiele adresów URI.

Jeśli twój klaster redis posiada tylko jeden URI, możesz użyć zmiennej środowiskowej `USE_REDIS_CLUSTER`, aby włączyć tryb klastra:

```bash
# Redis cluster with single URI
REDIS_URI=redis://127.0.0.1:7001
USE_REDIS_CLUSTER=true
```

### Zarządzane usługi Redis z pojedynczym punktem końcowym (Single-Endpoint) [#single-endpoint-managed-redis-services]

Niektóre zarządzane usługi Redis, w tym AWS ElastiCache Serverless oraz Redis Enterprise Cloud w AWS, udostępniają pojedynczy endpoint połączenia, wewnętrznie dzieląc klucze na partycje (sharding). W takiej konfiguracji należy pozostawić LibreChat w trybie połączenia jednowęzłowego (single-node), ale włączyć bezpieczne usuwanie w klastrze (cluster-safe deletes), jeśli czyszczenie pamięci podręcznej kończy się błędem `CROSSSLOT Keys in request don't hash to the same slot`.

```bash
USE_REDIS=true
REDIS_URI=rediss://your-managed-redis-endpoint:6379
USE_REDIS_CLUSTER=false
REDIS_CLUSTER_SAFE_DELETE=true
```

`REDIS_CLUSTER_SAFE_DELETE=true` sprawia, że LibreChat usuwa pasujące klucze pamięci podręcznej pojedynczo, zamiast wysyłać wielokluczowe polecenia `DEL`. Pozwala to uniknąć błędów `CROSSSLOT` bez zmiany sposobu, w jaki LibreChat łączy się z Redis.

Używaj `USE_REDIS_CLUSTER=true` tylko wtedy, gdy LibreChat ma utworzyć klienta Redis Cluster. W przypadku usług zarządzanych z pojedynczym punktem końcowym, bezpieczniejszą opcją jest `REDIS_CLUSTER_SAFE_DELETE=true`.

### Redis z TLS/SSL [#redis-with-tlsssl]

Dla bezpiecznych połączeń Redis:

```bash
# Redis with TLS encryption
REDIS_URI=rediss://127.0.0.1:6380

# Path to CA certificate for TLS verification
REDIS_CA=/path/to/ca-cert.pem
```

## Konfiguracja zabezpieczeń [#security-configuration]

### Uwierzytelnianie [#authentication]

Skonfiguruj dane uwierzytelniające Redis:

```bash
# Method 1: Include credentials in URI
# With both username and password
REDIS_URI=redis://myuser:mypassword@127.0.0.1:6379


# Method 2: Separate environment variables
REDIS_URI=redis://127.0.0.1:6379
REDIS_USERNAME=your_redis_username
REDIS_PASSWORD=your_redis_password
```

**Uwaga**: Dane uwierzytelniające zawarte w `REDIS_URI` mają pierwszeństwo. `REDIS_USERNAME` i `REDIS_PASSWORD` są używane wyłącznie jako rezerwa, gdy URI nie zawiera nazwy użytkownika lub hasła.

### Konfiguracja TLS [#tls-configuration]

Dla połączeń szyfrowanych:

```bash
# Enable TLS with rediss:// protocol
REDIS_URI=rediss://your-redis-host:6380

# Provide CA certificate for verification
REDIS_CA=/path/to/your/ca-certificate.pem
```

### TLS z Elasticache [#tls-with-elasticache]

Elasticache może wymagać użycia alternatywnego dnsLookup dla połączeń TLS. Zobacz "Special Note: Aws Elasticache Clusters with TLS" na tej stronie internetowej: https://www.npmjs.com/package/ioredis

```bash
# Enable redis alternate dnsLookup
REDIS_USE_ALTERNATIVE_DNS_LOOKUP=true
```

## Zaawansowane opcje [#advanced-options]

### Prefiksowanie kluczy [#key-prefixing]

Prefiksowanie kluczy Redis zapobiega zanieczyszczeniu między wdrożeniami poprzez izolację danych w pamięci podręcznej pomiędzy różnymi środowiskami, wersjami lub instancjami korzystającymi z tego samego serwera Redis. Jest to niezbędne dla:

- **Wdrożenia wielodostępne (Multi-tenant)**: Oddzielne środowiska testowe (staging), produkcyjne i programistyczne
- **Wdrożenia typu blue-green**: Izolacja pamięci podręcznej między różnymi wersjami aplikacji

```bash
# Option 1: Dynamic prefix from environment variable (recommended for cloud)

# Google Cloud Platform - Cloud Run
REDIS_KEY_PREFIX_VAR=K_REVISION

# AWS - ECS/Fargate
REDIS_KEY_PREFIX_VAR=AWS_EXECUTION_ENV

# Azure Container Instances
REDIS_KEY_PREFIX_VAR=CONTAINER_NAME

# Kubernetes - Pod name or deployment
REDIS_KEY_PREFIX_VAR=HOSTNAME
REDIS_KEY_PREFIX_VAR=POD_NAME

# Kubernetes - Custom deployment identifier
REDIS_KEY_PREFIX_VAR=DEPLOYMENT_ID

# Heroku
REDIS_KEY_PREFIX_VAR=DYNO

# Option 2: Static prefix (for manual control)
REDIS_KEY_PREFIX=librechat-prod-v2
REDIS_KEY_PREFIX=staging-branch-feature-x
REDIS_KEY_PREFIX=dev-john-local
```

**Ważne**: Nie można ustawić jednocześnie `REDIS_KEY_PREFIX_VAR` oraz `REDIS_KEY_PREFIX`.

**Przykłady zanieczyszczenia bez użycia prefiksów**:

- Pamięć podręczna środowiska produkcyjnego została nadpisana przez wdrożenie środowiska testowego (staging)
- Testy gałęzi funkcji powodujące uszkodzenie pamięci podręcznej gałęzi main
- Starsze wersje wdrożenia serwujące nieaktualne dane z pamięci podręcznej

**Format prefiksu klucza**:

- Klient IoRedis: `{prefix}::{key}`
- Klient Keyv: Obsługiwany przez warstwę magazynu

### Limity połączeń [#connection-limits]

Skonfiguruj limity połączeń Redis:

```bash
# Maximum number of event listeners (default: 40)
REDIS_MAX_LISTENERS=40
```

### Connection Keep-Alive [#connection-keep-alive]

Skonfiguruj sygnały kontrolne (heartbeats) Redis z ograniczeniem czasowym oraz mechanizm TCP keepalive:

```bash
# Redis ping interval in seconds (default: 0 = disabled)
# When set to a positive integer (in seconds), Redis clients will ping the server at this interval
# When unset or 0, no pinging is performed (recommended for most use cases)
# Example: 300 = ping every 5 minutes
REDIS_PING_INTERVAL=300

# Maximum time an enabled heartbeat PING may go unanswered (default: 5000 ms)
REDIS_PING_TIMEOUT=5000

# Dedicated pub/sub subscriber heartbeat (default: 15 seconds, 0 = disabled)
REDIS_SUBSCRIBER_PING_INTERVAL=15

# TCP keepalive idle delay for ioredis sockets (default: 10000 ms, 0 = kernel default)
REDIS_KEEP_ALIVE=10000
```

**Ważne**:

- Ustawienie `REDIS_PING_INTERVAL=0` lub pominięcie tej wartości całkowicie wyłącza pingowanie.
- Ustaw dodatnią wartość (w sekundach) tylko wtedy, gdy występują problemy z przekroczeniem limitu czasu połączenia
- `REDIS_PING_INTERVAL` jest określony w sekundach i kontroluje opcjonalny główny sygnał kontrolny (heartbeat) ioredis
- Dedykowani subskrybenci pub/sub używają własnego domyślnego interwału, ponieważ w przeciwnym razie nieaktywne, „martwe” gniazdo mogłoby pozostać niewykryte; ustaw `REDIS_SUBSCRIBER_PING_INTERVAL=0`, aby wyłączyć ten sygnał kontrolny (heartbeat).
- Każde włączone bicie serca (heartbeat) wykorzystuje `REDIS_PING_TIMEOUT` jako termin odpowiedzi i ponownie łączy gniazdo, gdy PING pozostaje bez odpowiedzi.
- `REDIS_KEEP_ALIVE` konfiguruje gniazdo TCP ioredis niezależnie od PING-ów na poziomie aplikacji
- Przykładowe wartości: `300` (5 minut), `600` (10 minut), `60` (1 minuta)

### Odzyskiwanie po awarii repliki (Replica Failover Recovery) [#replica-failover-recovery]

Podczas przełączania awaryjnego Sentinel, zdegradowana replika Redis może utrzymać otwarte istniejące gniazdo, odrzucając jednocześnie zapisy z komunikatem `READONLY`. LibreChat wykrywa tę odpowiedź na kliencie Keyv niebędącym w klastrze, zamyka nieaktualne połączenie i nawiązuje je ponownie, dzięki czemu bieżący węzeł główny (primary) może zostać rozpoznany bez konieczności restartowania aplikacji.

```bash
# Minimum interval between forced recovery attempts, in milliseconds
# Default: 5000
REDIS_READONLY_RECOVERY_INTERVAL=5000
```

Interwał ten ogranicza częstotliwość prób ponownego połączenia w przypadku serii nieudanych zapisów. Klienci Redis Cluster są wykluczeni, ponieważ korzystają z natywnej topologii klastra i obsługi przekierowań.

### Kontrole stanu (Health Checks) [#health-checks]

LibreChat udostępnia trzy endpointy sond. Tylko `/readyz` odzwierciedla stan Redis:

| Endpoint | Zwraca `200 OK` | Zwraca `503 NOT_READY` |
| --- | --- | --- |
| `/livez` | Zawsze, gdy proces obsługuje żądania | Nigdy |
| `/health` | Zawsze, gdy proces obsługuje żądania | Nigdy |
| `/readyz` | Po zakończeniu uruchamiania oraz, przy `USE_REDIS=true`, gdy połączenie z Redis jest aktywne | Przed zakończeniem uruchamiania lub gdy Redis jest włączony, ale rozłączony |

Gdy Redis zostaje uruchomiony ponownie, przełącza się awaryjnie lub staje się nieosiągalny dłużej niż okno ponowień klienta, żądania zależne od niego (logowanie, sesje, limity szybkości) kończą się niepowodzeniem, aż do przywrócenia połączenia. W tym czasie `/readyz` zwraca `503`, dzięki czemu load balancer lub sonda gotowości Kubernetes przestaje kierować ruch do danej instancji. Po ponownym nawiązaniu połączenia z Redis odpowiedź wraca do `200` bez konieczności restartowania aplikacji. Gdy Redis jest włączony, każdy klient Redis musi być połączony; w przypadku Redis Cluster dotyczy to każdego węzła głównego (primary).

Skieruj sprawdzenia gotowości (readiness) na `/readyz`, a sprawdzenia żywotności (liveness) na `/livez`. Nie uwzględniaj Redis w sprawdzeniu żywotności: sonda liveness, która kończy się niepowodzeniem podczas awarii Redis, spowoduje jednoczesny restart wszystkich podów i nie przywróci działania Redis.

```yaml
livenessProbe:
  httpGet:
    path: /livez
    port: 3080
readinessProbe:
  httpGet:
    path: /readyz
    port: 3080
  periodSeconds: 10
  failureThreshold: 3
```

`/readyz` sam nie czeka na krótkie ponowne połączenia, więc użyj `failureThreshold`, aby określić, jak długo może trwać awaria, zanim ruch zostanie wycofany.

### Selektywne buforowanie w pamięci (In-Memory Caching) [#selective-in-memory-caching]

Wymuś użycie pamięci operacyjnej (in-memory) dla określonych przestrzeni nazw pamięci podręcznej, nawet gdy Redis jest włączony:

```bash
# Comma-separated list of cache keys
FORCED_IN_MEMORY_CACHE_NAMESPACES=CONFIG_STORE,APP_CONFIG,ROLES
```

Gdy zmienna nie jest ustawiona, domyślną wartością jest `CONFIG_STORE,APP_CONFIG`, dzięki czemu konfiguracja pochodząca z `librechat.yaml` pozostaje lokalna dla każdego kontenera. Ustawienie tej zmiennej **zastępuje** wartość domyślną zamiast ją uzupełniać, dlatego uwzględnij `CONFIG_STORE,APP_CONFIG` na swojej liście, chyba że chcesz, aby te przestrzenie nazw były przechowywane w Redis. Ustawienie pustego ciągu znaków spowoduje przekierowanie wszystkich przestrzeni nazw do Redis.

## Optymalizacja wydajności [#performance-tuning]

### Connection Keep-Alive [#connection-keep-alive-1]

Aplikacja implementuje konfigurowalne podtrzymywanie połączenia (keep-alive):

- PINGi głównego klienta (main-client) są kontrolowane przez `REDIS_PING_INTERVAL` i domyślnie wyłączone
- Dedykowane PINGi subskrybenta są kontrolowane przez `REDIS_SUBSCRIBER_PING_INTERVAL` i domyślnie wynoszą 15 sekund
- Heartbeats używają `REDIS_PING_TIMEOUT` do wykrywania cicho zamkniętych gniazd i wymuszania ponownego połączenia
- TCP keepalive wykorzystuje `REDIS_KEEP_ALIVE`, niezależnie od sygnałów heartbeat na poziomie aplikacji
- Timery heartbeat są czyszczone przy zdarzeniach rozłączenia lub zamknięcia

### Strategia pamięci podręcznej [#cache-strategy]

Aplikacja wykorzystuje podejście dwuklienckie:

- **Klient IoRedis**: Podstawowe operacje Redis z automatycznym prefiksowaniem
- **Klient Keyv Redis**: Operacje warstwy przechowywania z obsługą prefiksów w `cacheFactory.js`

### Zaawansowane dostrajanie połączenia [#advanced-connection-tuning]

Te opcjonalne zmienne dostosowują zachowanie połączeń oraz operacje masowego cachowania. Wartości domyślne odpowiadają większości wdrożeń.

| Zmienna | Domyślnie | Opis |
| --- | --- | --- |
| `REDIS_CONNECT_TIMEOUT` | `10000` | Limit czasu połączenia w milisekundach. |
| `REDIS_RETRY_MAX_ATTEMPTS` | `10` | Maksymalna liczba prób ponownego połączenia przed rezygnacją. `0` oznacza nieskończoną liczbę prób. |
| `REDIS_RETRY_MAX_DELAY` | `3000` | Maksymalne opóźnienie między próbami ponownego połączenia, w milisekundach. |
| `REDIS_ENABLE_OFFLINE_QUEUE` | `true` | Kolejkuje polecenia w czasie braku połączenia. Ustaw `false`, aby natychmiast zwracać błąd dla tych poleceń. |
| `REDIS_SCAN_COUNT` | `1000` | Wskazówka `COUNT` dla operacji `SCAN` podczas wyszukiwania kluczy według wzorca. |
| `REDIS_DELETE_CHUNK_SIZE` | `1000` | Liczba kluczy usuwanych w jednej partii podczas masowego usuwania. |
| `MCP_REGISTRY_CACHE_TTL` | `5000` | Czas w milisekundach, przez jaki przechowywane są pamięci podręczne rejestru MCP. Nieaktualność danych między instancjami może sięgać dwukrotnej tej wartości. `0` wyłącza lokalną migawkę, dzięki czemu każdy odczyt trafia do Redis. |

### Optymalizacja pamięci [#memory-optimization]

Użyj `FORCED_IN_MEMORY_CACHE_NAMESPACES`, aby zoptymalizować wydajność poprzez przechowywanie często używanych, małych zbiorów danych w pamięci, podczas gdy Redis jest wykorzystywany do większych pamięci podręcznych.

## Wznawialne strumienie [#resumable-streams]

Redis umożliwia [Resumable Streams](/docs/features/resumable_streams) w przypadku wdrożeń skalowanych horyzontalnie. Po włączeniu tej funkcji odpowiedzi AI mogą płynnie wznawiać działanie i łączyć się ponownie pomiędzy instancjami serwera.

**Ważne:** Gdy `USE_REDIS=true`, wznawialne strumienie automatycznie używają Redis do koordynacji między instancjami. Jest to zalecana konfiguracja dla wdrożeń skalowanych horyzontalnie, w których użytkownicy mogą łączyć się z różnymi instancjami serwera.

**Uwaga:** Jeśli uruchamiasz pojedynczą instancję LibreChat, Redis do wznawialnych strumieni zazwyczaj jest zbędny; wbudowany tryb w pamięci działa poprawnie. Redis staje się niezbędny, gdy masz wiele instancji LibreChat za modułem równoważenia obciążenia, ponieważ ponowne połączenie użytkownika może trafić na inny serwer niż ten, na którym rozpoczął się strumień.

### Konfiguracja [#configuration]

```bash
# Redis enabled = resumable streams automatically use Redis
USE_REDIS=true
REDIS_URI=redis://127.0.0.1:6379

# Optional: explicitly control resumable streams behavior
# USE_REDIS_STREAMS=true  # Enabled by default when USE_REDIS=true
```

### Zgodność z protokołem generowania [#generation-protocol-compatibility]

Obecni klienci LibreChat automatycznie negocjują protokół generowania v2 z każdym wbudowanym magazynem generowania. Nie jest wymagane żadne ustawienie wdrożeniowe. Istniejące generacje z jawnym lub zapisanym znacznikiem protocol-v1 zachowują swoje niezmienne zachowanie v1 podczas sterowania, wstrzymywania/wznawiania, ponawiania i odzyskiwania aż do ich zakończenia.

W przypadku aktualizacji typu rolling upgrade, każdy uruchomiony obraz API oraz worker musi zawierać most kompatybilności v2:

- Każdy obraz API i worker uruchamia LibreChat `v0.8.8-rc1` lub nowszą wersję.
- Helm chart `2.0.8` lub nowszy wybiera kompatybilny domyślny obraz; nadpisanie niestandardowego obrazu musi nadal spełniać powyższe wymagania dotyczące obrazu.

Podczas aktualizacji ze starszej wersji należy przeprowadzić „zimne przekazanie” (cold handoff): zatrzymaj wszystkie stare repliki API i workerów przed uruchomieniem nowego obrazu. Zapobiega to współdzieleniu stanu generowania w Redis przez pliki binarne sprzed wersji v2 oraz automatyczne wersje v2.

<Callout type="warning" title="Bezpieczeństwo wdrożenia kroczącego">
  Nie uruchamiaj wersji starszej niż `v0.8.8-rc1` w odniesieniu do tego samego stanu generacji Redis, co obecne repliki. Przed wycofaniem wersji poniżej tego progu kompatybilności upewnij się najpierw, że obecne repliki oraz generacje protocol-v2 zostały opróżnione.
</Callout>

Strumienie generowania w pamięci (in-memory) również automatycznie negocjują protokół v2 i nie współdzielą stanu generowania między procesami.

### Łączenie delt strumienia (Stream Delta Coalescing) [#stream-delta-coalescing]

Strumienie oparte na Redis mogą grupować publikacje delta, aby ograniczyć liczbę skryptów Redis, komunikację sieciową (round trips) oraz zużycie procesora przy wysokich częstotliwościach generowania tokenów:

```bash filename=".env"
STREAM_DELTA_COALESCE_MS=25
```

Ustawienie domyślnie wynosi `25` milisekund, jeśli nie zostanie określone. Ustaw wartość `0`, aby wyłączyć łączenie (coalescing); wartości powyżej `1000` są ograniczane. Przetwarzanie wsadowe może dodać do jednego skonfigurowanego okna opóźnienia dostarczania i może spowodować utratę buforowanej końcówki, jeśli proces publikowania zakończy się przed jej opróżnieniem. Poszczególne ramki fragmentów są zachowywane ze względu na kompatybilność protokołu, więc to ustawienie zmniejsza obciążenie skryptów Redis i liczbę operacji typu round-trip bez zmiany formatu ramki subskrybenta. Strumienie generowania w pamięci pozostają bez zmian.

### Kluczowe korzyści (dla skalowania poziomego) [#key-benefits-for-horizontal-scaling]

- **Ciągłość między instancjami**: Użytkownicy mogą rozpocząć generowanie na jednym serwerze i wznowić je na innym
- **Wdrażanie kroczące (Rolling deployments)**: Aktywne strumienie przetrwają restarty serwera
- **Synchronizacja wielu kart**: Ta sama konwersja synchronizuje się między wieloma kartami przeglądarki w środowisku z równoważeniem obciążenia
- **Odporność połączenia**: Automatyczne ponowne łączenie niezależnie od tego, który serwer obsługuje żądanie

### Konfiguracja klastra [#cluster-configuration]

W przypadku wdrożeń Redis Cluster, LibreChat automatycznie używa kluczy z hasztagami, aby zapewnić, że operacje na strumieniach pozostają w tym samym slocie klastra:

```bash
USE_REDIS=true
USE_REDIS_STREAMS=true
USE_REDIS_CLUSTER=true
REDIS_URI=redis://node1:7001,redis://node2:7002,redis://node3:7003
```

Zobacz [Resumable Streams](/docs/features/resumable_streams), aby uzyskać więcej szczegółów na temat tej funkcji.

## Koordynacja katalogu MCP [#mcp-catalog-coordination]

Gdy Redis jest włączony, LibreChat koordynuje katalogi narzędzi MCP na poziomie aplikacji pomiędzy replikami. Publikacja przy starcie, synchronizacja po ponownym połączeniu oraz aktualizacje `notifications/tools/list_changed` wykorzystują znaczniki generacji i wersji, dzięki czemu nieaktualna replika nie może nadpisać nowszego katalogu.

Wdrożenia Redis Cluster wykorzystują klucze katalogu bezpieczne dla slotów (slot-safe) oraz operacje aktualizacji; nie jest wymagane żadne oddzielne ustawienie MCP Redis. Zobacz [Zarządzanie serwerem MCP](/docs/features/mcp#mcp-server-management), aby uzyskać informacje na temat dynamicznego katalogu i zachowania gotowości OAuth.
