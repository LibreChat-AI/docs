## Ogólne [#general]

![Aktywni użytkownicy w LibreChat](/images/metrics/librechat-metrics-active-users.png)

LibreChat udostępnia dwie powierzchnie metryk kompatybilne z Prometheus. Wbudowany w API endpoint `/metrics` raportuje zachowanie operacyjne, takie jak aktywność Redis oraz wyniki proxy telemetrii przeglądarki. Opcjonalny eksporter bazy danych raportuje dane o użyciu przechowywane w MongoDB, w tym sumy tokenów oraz liczbę aktywnych użytkowników.

## Wbudowane metryki API [#built-in-api-metrics]

LibreChat udostępnia metryki Prometheus z serwera API pod adresem `/metrics`. Ustaw `METRICS_SECRET` i pobieraj dane z endpointu za pomocą nagłówka `Authorization: Bearer <METRICS_SECRET>`. Endpoint zwraca `401`, gdy sekret nie jest ustawiony, brakuje nagłówka lub token się nie zgadza.

```yaml filename="prometheus.yml"
scrape_configs:
  - job_name: librechat-api
    scheme: https
    metrics_path: /metrics
    authorization:
      type: Bearer
      credentials: your-metrics-secret
    static_configs:
      - targets: ['librechat.example.com']
```

### Metryki procesów, HTTP i żądań [#process-http-and-request-metrics]

Punkt końcowy udostępnia również domyślne metryki Node.js i procesu z `prom-client` oraz następujące serie.

| Grupa | Metryka | Etykiety |
| --- | --- | --- |
| HTTP | `http_requests_total`, `http_request_duration_seconds` | `method`, `path`, `status` |
| HTTP | `http_requests_in_flight`, `http_request_body_bytes` (z `Content-Length`) | `method`, `path` |
| SSE | `sse_streams_total`, `sse_stream_duration_seconds` | `method`, `path`, `status` |
| SSE | `sse_streams_in_flight` | `method`, `path` |
| Przesyłanie plików | `upload_requests_total`, `upload_request_duration_seconds` | `method`, `path`, `status` |
| Przesyłanie plików | `upload_requests_in_flight`, `upload_bytes_total` (z `Content-Length`) | `method`, `path` |
| OpenID | `openid_user_lookup_total`, `openid_user_lookup_duration_seconds` | `result` |
| Mongoose | `mongoose_queries_total`, `mongoose_query_duration_seconds` | `model`, `operation`, `status` |
| Zadania generowania | `generation_jobs_total` | `store`, `result` |
| Zadania generowania | `generation_jobs_in_flight` | `store` |
| Strumienie generowania | `generation_stream_subscriptions_total` | `store`, `type`, `result` |
| Strumienie generowania | `generation_stream_resume_pending_events_total`, `generation_stream_early_buffer_overflows_total`, `generation_stream_first_attachment_delay_seconds` | `store` |
| Strumienie generowania | `generation_stream_attachment_outcomes_total` | `store`, `outcome` |
| Strumienie generowania | `generation_stream_recoveries_total`, `generation_stream_recovery_duration_seconds`, `generation_stream_recovery_events`, `generation_stream_recovery_content_parts` | `store`, `method`, `outcome` |
| Filtr treści | `content_filter_locator_traversal_failures_total` | `operation`, `reason` |
| Filtr treści | `content_filter_locator_traversal_size` | `operation`, `reason`, `dimension` |

Metryki odzyskiwania strumienia generowania opisują, w jaki sposób odtwarzany jest wcześniejszy bufor zdarzeń, który uległ przepełnieniu. Metryki filtra treści zliczają niekompletne przejścia przez rozwiązane lokalizatory plików.

### Metryki uruchamiania agenta [#agent-startup-metrics]

Początkowe żądania czatu agenta emitują dwie metryki startowe:

- `agent_startup_milestone_duration_seconds{milestone}` mierzy skumulowane opóźnienie od momentu wpłynięcia żądania do każdego etapu uruchomienia.
- `agent_startups_total{result}` zlicza próby uruchomienia według wyniku końcowego.

Kamienie milowe obejmują przyjęcie żądania, utworzenie i potwierdzenie zadania, ładowanie konwersacji i historii, inicjalizację klienta i uruchomienia, rozpoczęcie strumienia oraz pierwsze zdarzenie kolejki odpowiedzi lub zawartości. Wyniki rozróżniają zawartość w kolejce, zakończenie bez delty zawartości, deduplikację, odrzucenie, wstrzymanie, zastąpienie, przerwanie oraz błąd.

Gdy [śledzenie OpenTelemetry po stronie backendu](/docs/configuration/dotenv#opentelemetry-traces-and-logs) jest włączone, span `librechat.agent.startup` raportuje te same kamienie milowe jako zdarzenia. Zawiera on łączny czas uruchomienia, liczbę kamieni milowych, wynik końcowy oraz identyfikator strumienia generowania, gdy zostanie przypisany.

### Metryki Redis [#redis-metrics]

Usługi i pamięci podręczne oparte na Redis emitują dwie metryki operacji logicznych:

- `redis_operations_total{client,use_case,operation,status}` zlicza operacje.
- `redis_operation_duration_seconds{client,use_case,operation,status}` mierzy opóźnienie.

`client` to `keyv` lub `ioredis`, a `status` to `success` lub `error`. Ograniczone etykiety `use_case` identyfikują zadania takie jak pamięci podręczne, sesje, limity szybkości, współbieżność, podmioty ACL, wznawialne zadania strumieniowe i pub/sub, skany rejestru MCP oraz wybór lidera. Te metryki zliczają operacje logiczne LibreChat, a nie każdy wewnętrzny cykl komunikacji z Redis. Pingi cyklu życia połączenia i globalna konserwacja są wykluczone, a czyszczenie przestrzeni nazw jest liczone jako jedna operacja logiczna.

Gdy [śledzenie backendu OpenTelemetry](/docs/configuration/dotenv#opentelemetry-traces-and-logs) jest włączone, każdy span HTTP dodatkowo podsumowuje swoją pracę z Redis za pomocą:

- `librechat.redis.calls`
- `librechat.redis.duration_ms`
- `librechat.redis.errors`
- `librechat.redis.max_call_ms`
- `librechat.redis.operations`
- `librechat.redis.use_cases`

Dziesięć przypadków użycia o najwyższym łącznym czasie trwania otrzymuje również atrybuty `calls`, `duration_ms`, `errors` oraz `max_call_ms` w ramach `librechat.redis.<use_case>.*`. To podsumowanie na poziomie żądania nie wymaga zakresów (spans) Redis na poziomie poleceń; włącz `OTEL_IOREDIS_TRACING_ENABLED` tylko wtedy, gdy potrzebne są zakresy poszczególnych poleceń.

### Metryki proxy RUM przeglądarki [#browser-rum-proxy-metrics]

Wyniki proxy Browser RUM są raportowane jako `rum_proxy_requests_total{endpoint,result}`. `endpoint` to `traces`, `logs` lub `unknown`; `result` może przyjmować wartości `success`, `auth_drop`, `auth_error`, `bad_request`, `not_configured`, `collector_4xx`, `collector_5xx`, `collector_error` lub `collector_timeout`.

### Metryki aktora zdarzeń agenta [#agent-event-actor-metrics]

Trwałe zdarzenia agenta (Durable bound Agent Events) udostępniają metryki odbioru i odzyskiwania o niskiej kardynalności:

- `agent_event_actor_receipt_operations_total{operation,outcome,resolution}` zlicza odczyty potwierdzeń, rozliczenia oraz starsze uzupełnienia danych (backfill). `operation` przyjmuje wartości `read`, `settle` lub `backfill`; `outcome` przyjmuje wartości `hit`, `miss`, `success`, `replay` lub `conflict`.
- `agent_event_actor_receipts_retained{resolution}` raportuje potwierdzenia powtórzeń zachowane przez rozdzielczość `checkpoint_verified`, `action_compensated` lub `history_repaired`.
- `agent_event_actor_receipts_expiry_eligible` raportuje zachowane potwierdzenia, których 90-dniowy czas wygaśnięcia (TTL) w MongoDB upłynął, ale które nie zostały jeszcze usunięte.
- `agent_event_actor_reconciliations_pending` raportuje aktywne znaczniki uzgodnień oczekujące na potwierdzenie końcowe.
- `agent_event_actor_oldest_reconciliation_age_seconds` raportuje wiek najstarszej aktywnej rekoncyliacji.
- `agent_event_actor_deliveries{state}` raportuje wiersze dostaw znajdujące się obecnie w stanie `retry` lub `dead`.

Wskaźniki pamięci masowej są zbierane podczas uwierzytelnionych odczytów (scrapes) i buforowane przez maksymalnie 60 sekund. Należy ustawić alerty dla utrzymującego się wieku uzgadniania (reconciliation age), nieudanych dostaw lub potwierdzeń kwalifikujących się do wygaśnięcia, zamiast polegać na pojedynczym odczycie.

### Metryki udostępnionych linków [#shared-link-metrics]

`share_link_rejections_total{operation,code}` zlicza ograniczone niepowodzenia tworzenia lub aktualizacji. `operation` to `create` lub `update`; `code` to `TARGET_MESSAGE_NOT_FOUND`, gdy końcówka wybranej gałęzi nie jest utrwalona, lub `NO_MESSAGES`, gdy konwersacja nie posiada utrwalonych wiadomości. Metryka nie zawiera tekstu konwersacji ani tożsamości użytkownika.

## Eksporter metryk bazy danych [#database-metrics-exporter]

Eksporter metryk jest dostępny pod adresem [virtUOS/librechat_exporter](https://github.com/virtUOS/librechat_exporter).
Jest to oddzielne narzędzie, które wdrażasz obok LibreChat.

### Konfiguracja [#setup]

Aby wdrożyć eksporter, wystarczy dodać niezbędny kontener do swojej konfiguracji compose w następujący sposób:

```yaml
services:
  metrics:
    image: ghcr.io/virtuos/librechat_exporter:main
    depends_on:
      - mongodb
    ports:
      - '8000:8000'
    restart: unless-stopped
```

Opcjonalnie możesz również skonfigurować eksporter.
Zazwyczaj jednak ustawienia domyślne powinny być wystarczające.

```yaml
services:
  metrics:
    environment:
      - MONGODB_URI=mongodb://mongodb:27017/
      - LOGGING_LEVEL=info
```

### Użycie [#usage]

Możesz teraz dodać eksporter do swojej konfiguracji scrapowania Prometheus:

```yaml
- job_name: librechat
  static_configs:
    - targets:
        - 'librechat.example.com:8000'
```

Gdy zbieranie metryk się rozpocznie, wyszukaj metryki `librechat_*` (np. `librechat_registered_users`).
Exporter udostępnia kilka metryk.

Baw się dobrze podczas tworzenia swojego pulpitu nawigacyjnego Grafana!
