[Langfuse](https://langfuse.com)는 LLM 애플리케이션을 추적, 모니터링 및 디버깅하는 데 도움을 주는 오픈 소스 LLM 관측성 플랫폼입니다. Langfuse를 LibreChat과 통합하면 AI 대화에 대한 전체적인 가시성을 확보할 수 있습니다.

## 필수 조건 [#prerequisites]

시작하기 전에 다음 사항을 준비했는지 확인하세요:

1. 실행 중인 LibreChat 인스턴스 ( [빠른 시작](/docs/quick_start) 참조)
2. Langfuse 계정 ([무료 가입](https://cloud.langfuse.com))
3. 프로젝트 설정에서 가져온 Langfuse API 키

## 설정 [#setup]

단일 테넌트 배포를 위해 인앱 연결 또는 환경 관리형 자격 증명 중 하나를 선택하십시오. 환경 자격 증명을 모두 완료하면 해당 설정이 우선 적용됩니다.

### 앱 내 연결 [#in-app-connection]

권한이 있는 관리자는 **Settings → Langfuse**를 열고, 승인된 대상을 선택한 뒤, 프로젝트의 공개 키와 비밀 키를 입력하고 **Save & enable**을 선택할 수 있습니다. LibreChat은 저장하기 전에 두 키를 모두 확인하고, 확인된 프로젝트 ID를 기록하며, 비밀 키를 저장 시 암호화하고, 이후 읽기 작업 시에는 마스킹된 미리보기만 반환합니다. 저장된 연결은 비밀 키를 노출하지 않고도 활성화, 비활성화, 재테스트 또는 교체할 수 있습니다.

이 설정에는 `access:admin` 및 `manage:configs:langfuse` (또는 이에 상응하는 광범위한/관리자 권한)가 모두 필요합니다. 이 설정은 추적(tracing)이 활성화되어 있고 다음 조건이 충족될 때 사용할 수 있습니다:

- 단일 테넌트 배포에는 `LANGFUSE_PUBLIC_KEY`와 `LANGFUSE_SECRET_KEY`가 모두 포함되어 있지 않습니다.
- Fanout 배포는 수집기가 활성화되어 있고 비상 스위치에 의해 테넌트 내보내기가 비활성화되지 않은 상태입니다.

`librechat.yaml`에 일반 텍스트 형태의 `langfuse.secretKey`를 직접 입력하지 마십시오. 런타임은 승인된 설정 쓰기(config write)를 통해 생성된 암호화된 값을 허용합니다. 일반적인 연결 워크플로우를 위해서는 설정(Settings) 페이지를 사용하십시오.

저장된 연결은 기본 구성에 속합니다. 역할, 그룹 및 사용자 구성 재정의는 `langfuse` 섹션을 대체하거나 제거할 수 없습니다.

### 설정 예시 [#example-configuration]

```sh filename=".env"
# Langfuse Configuration
LANGFUSE_PUBLIC_KEY=pk-lf-***
LANGFUSE_SECRET_KEY=sk-lf-***
# LANGFUSE_PROJECT_ID=project-id
# LANGFUSE_SAMPLE_RATE=1

# 🇪🇺 EU Data Region
LANGFUSE_BASE_URL=https://cloud.langfuse.com

# 🇺🇸 US Data Region
# LANGFUSE_BASE_URL=https://us.cloud.langfuse.com
```

<Callout type="note" title="자체 호스팅 Langfuse">
  자체 호스팅된 Langfuse 인스턴스의 경우, `LANGFUSE_BASE_URL`을 사용자 지정 URL(예: 로컬 개발 환경의 경우 `http://localhost:3000`)로 설정하세요.
</Callout>

두 환경 키가 모두 존재할 때, LibreChat은 이를 중앙 프로젝트에 사용하며 **Settings → Langfuse**를 숨깁니다. `LANGFUSE_TRACING_ENABLED=false` 또는 `LANGFUSE_SAMPLE_RATE=0`으로 설정하면 추적(trace)과 피드백 점수 모두가 비활성화됩니다. 부분 샘플링은 추적당 하나의 결정론적 결정을 내리며, 샘플링에서 제외된 추적은 이후 피드백 점수를 받지 않습니다.

`LANGFUSE_BASE_URL`은 표준 기본 URL 설정입니다. 이전의 `LANGFUSE_HOST` 및 `LANGFUSE_BASEURL` 이름은 호환성을 위해 유지되며, 여러 설정이 지정된 경우 `LANGFUSE_BASE_URL`이 우선순위를 갖습니다.

### 인증된 프록시 및 게이트웨이 [#authenticated-proxies-and-gateways]

Cloudflare Access, oauth2-proxy 또는 기타 인증 게이트웨이 뒤에서 호스팅되는 자체 호스팅 Langfuse 인스턴스의 경우, `librechat.yaml`에서 배포 수준의 사용자 지정 요청 헤더를 정의하십시오:

```yaml filename="librechat.yaml"
langfuse:
  headers:
    CF-Access-Client-Id: '${CF_ACCESS_CLIENT_ID}'
    CF-Access-Client-Secret: '${CF_ACCESS_CLIENT_SECRET}'
```

LibreChat은 확인된 헤더를 모든 직접적인 Langfuse 인터페이스(추적 및 미디어 내보내기, 피드백 점수 생성 및 삭제, 프로젝트 ID 조회, 관리자 자격 증명 확인)에 적용합니다. Langfuse 자체의 `Authorization` 자격 증명은 REST 요청에서 권한을 유지합니다. 값은 `${ENV_VAR}` 보간을 지원하며, 확인되지 않은 변수, 보호된 인프라 비밀 참조, 빈 값 및 유효하지 않은 헤더 이름은 경고와 함께 삭제됩니다. 헤더 값은 시작 로그 및 관리자 구성 읽기 시 마스킹 처리되지만, 리터럴 자격 증명보다는 환경 변수 참조를 사용하는 것이 권장됩니다.

이 헤더들은 운영자 소유이며 YAML 전용입니다. 관리자 패널이나 구성 API를 통해 작성하거나, MongoDB에 저장하거나, 사용자별 `{{...}}` 플레이스홀더로 채울 수 없습니다. LibreChat은 구성이 정확히 하나의 Langfuse 출처로 확인될 때만 이 헤더들을 전송합니다. 여러 개의 중앙, 테넌트 또는 수집기 출처가 있는 경우, 맵이 수신자를 안전하게 선택할 수 없으므로 경고를 기록하고 사용자 지정 헤더를 전송하지 않습니다.

<Callout type="warning" title="Fanout 제한">
  fanout collector는 현재 `Authorization` 헤더만 테넌트 Langfuse 목적지로 전달합니다.
  사용자 지정 `langfuse.headers`는 단일 collector 또는 Langfuse 오리진에 대한 LibreChat의 직접적인 요청을 인증할 수 있지만, 다른 프록시 뒤에 있는 테넌트 목적지로 향하는 collector의 업스트림 요청은 인증하지 않습니다.
</Callout>

### 사용자 식별 및 메타데이터 추적 [#trace-user-identity-and-metadata]

기본적으로 Agent 추적은 LibreChat의 내부 사용자 ID를 Langfuse `userId`로 사용하며, 추가적인 사용자 또는 요청 메타데이터를 내보내지 않습니다. 배포 운영자는 다른 사용자 필드를 선택하고 `langfuse.trace` 아래에 메타데이터를 명시적으로 허용 목록(allowlist)에 추가할 수 있습니다.

```yaml filename="librechat.yaml"
langfuse:
  trace:
    userIdField: email
    userMetadataFields: [email, username, role, provider]
    conversationMetadataFields: [conversationId, endpoint, model, modelLabel, spec]
```

`userIdField`는 `id`, `email`, `username`, `name`, `openidId`, `samlId`, `ldapId`, `googleId`, `githubId`, `discordId`, `appleId` 또는 `facebookId`를 허용합니다. 선택한 필드가 사용자에게 없는 경우, 내부 ID는 추적 `userId`로 유지됩니다.

`userMetadataFields`는 해당 식별 필드와 더불어 `role` 및 `provider`를 허용합니다. 값은 `librechat.user.<field>`로 내보내집니다. `conversationMetadataFields`는 `conversationId`, `endpoint`, `endpointType`, `provider`, `model`, `modelLabel`, `spec`을 허용하며, 이는 각각 `librechat.conversation.id`, `librechat.endpoint`, `librechat.endpoint.type`, `librechat.provider`, `librechat.model`, `librechat.model.label`, `librechat.spec` 추적 속성으로 매핑됩니다.

이 세 가지 필드는 모두 선택 사항이며, 사용자나 요청에 존재한다는 이유만으로 메타데이터 필드가 내보내지는 것은 아닙니다. 이메일, 사용자 이름, 제공자 식별자, 대화 ID 및 모델 선택 항목은 잠재적으로 민감한 텔레메트리로 취급해야 합니다. Langfuse 보존 및 액세스 정책이 허용하는 필드만 허용 목록(allowlist)에 추가하십시오.

## 테넌트 팬아웃 (선택 사항) [#tenant-fanout-optional]

Langfuse fanout을 사용하면 다중 테넌트 LibreChat 배포에서 각 적격 추적(trace)과 해당 미디어를 중앙 Langfuse 프로젝트와 테넌트별 프로젝트 모두로 내보낼 수 있습니다. 이 기능은 선택 사항이며 게이트웨이와 내부 OpenTelemetry 수집기가 추가됩니다. fanout이 배포되지 않은 경우, 위에서 설명한 일반적인 단일 프로젝트 추적은 변경되지 않습니다.

Fanout은 두 가지 구성 계층을 사용합니다:

- 배포 환경 변수는 시작 시 중앙 프로젝트, 게이트웨이 및 허용된 테넌트 대상을 정의합니다.
- **Settings → Langfuse**는 테넌트의 활성화 상태, 공개 키, 암호화된 비밀 키, 검증된 프로젝트 ID 및 하나의 허용된 대상을 제공합니다. 키는 게이트웨이를 재시작하지 않고도 런타임에 변경할 수 있습니다.

포함된 Compose 오버라이드는 `eu`, `us`, 및 `jp` Langfuse Cloud 대상을 지원합니다:

```sh filename=".env"
LANGFUSE_BASE_URL=https://cloud.langfuse.com
LANGFUSE_FANOUT_CENTRAL_BASE_URL=https://cloud.langfuse.com
LANGFUSE_FANOUT_CENTRAL_AUTH_HEADER="Basic <base64-public-key-colon-secret-key>"
LANGFUSE_FANOUT_CENTRAL_MEDIA_UPLOAD_DISABLED=false
LANGFUSE_FANOUT_TENANT_DESTINATIONS="eu=https://cloud.langfuse.com,us=https://us.cloud.langfuse.com,jp=https://jp.cloud.langfuse.com"
LANGFUSE_FANOUT_TRACE_DESTINATION_KEYS=eu,us,jp
LANGFUSE_FANOUT_TENANT_EXPORT_DISABLED=false
```

fanout 오버라이드를 사용하여 일반 Compose 스택을 시작하세요:

```sh
docker compose -f docker-compose.yml -f docker-compose.langfuse-fanout.yml up -d
```

이 오버라이드는 `LANGFUSE_FANOUT_ENABLED`를 활성화하고, LibreChat이 게이트웨이를 가리키도록 설정하며, 수집기(collector) 및 비공개 Redis 서비스를 시작합니다. 배포된 스택의 경우, 대신 `deploy-compose.yml`과 `deploy-compose.langfuse-fanout.yml`을 결합하십시오.

게이트웨이는 기본적으로 `:4318`에서 수신 대기합니다. 사용자 지정 배포의 경우 `LANGFUSE_FANOUT_LISTEN_ADDR`을 사용하여 바인딩 주소를 재정의할 수 있으며, 포함된 Compose 및 Helm 구성은 이미 표준 게이트웨이 포트를 라우팅합니다.

### Helm 배포 [#helm-deployment]

Compose 오버라이드는 게이트웨이를 로컬에서 빌드하지만, Kubernetes는 레지스트리에서 사용할 수 있는 이미지가 필요합니다. LibreChat 저장소 루트에서 차트를 설치하기 전에 게이트웨이를 빌드하고 푸시하세요:

```sh
docker build \
  -f otel/langfuse-fanout/Dockerfile \
  -t registry.example.com/librechat-langfuse-fanout:<tag> .
docker push registry.example.com/librechat-langfuse-fanout:<tag>
```

전체 Langfuse Basic 인증 헤더를 포함하는 Kubernetes Secret을 생성합니다. 해당 값은 `Basic ` 뒤에 base64로 인코딩된 `<public-key>:<secret-key>` 자격 증명이 오는 형태입니다:

```sh
kubectl create secret generic langfuse-central \
  --from-literal=LANGFUSE_FANOUT_CENTRAL_AUTH_HEADER='Basic <base64-public-key-colon-secret-key>'
```

Helm values에서 fanout 배포를 활성화합니다. 이 예제는 번들로 제공되는 Redis 차트를 사용합니다. 외부 Redis 서비스를 사용하는 경우 대신 `langfuseFanout.redis.uri`를 설정하세요.

```yaml filename="values.yaml"
redis:
  enabled: true

langfuseFanout:
  enabled: true
  image:
    repository: registry.example.com/librechat-langfuse-fanout
    tag: '<tag>'
    pullPolicy: IfNotPresent
  central:
    baseUrl: https://cloud.langfuse.com
    authHeaderSecret:
      name: langfuse-central
      key: LANGFUSE_FANOUT_CENTRAL_AUTH_HEADER
  metrics:
    secret:
      name: librechat-metrics
      key: METRICS_SECRET
  tenant:
    destinations:
      eu:
        baseUrl: https://cloud.langfuse.com
      us:
        baseUrl: https://us.cloud.langfuse.com
      jp:
        baseUrl: https://jp.cloud.langfuse.com
  upstreamTimeout: 30s
  publicUrl: ''
  otelCollector:
    receiverEndpoint: 127.0.0.1:4319
  redis:
    uri: ''
    username: ''
    passwordSecret:
      name: ''
      key: REDIS_PASSWORD
    keyPrefix: langfuse-fanout
  memoryLimitMiB: 256
  memorySpikeLimitMiB: 64
  batchTimeout: 1s
  batchSendSize: 128
  metadataCardinalityLimit: 1000
```

metrics Secret은 선택 사항이지만, `langfuseFanout.metrics.secret`이 bearer 토큰을 제공하지 않으면 `/metrics`는 `401`을 반환합니다. 메트릭 스크래핑이 필요한 경우 별도로 생성하십시오:

```sh
kubectl create secret generic librechat-metrics \
  --from-literal=METRICS_SECRET='<metrics-bearer-token>'
```

이 차트는 포트 `4318`의 게이트웨이 컨테이너와 포트 `4319`의 내부 OpenTelemetry Collector 사이드카가 포함된 하나의 Deployment를 렌더링하며, 서비스에 의해 게이트웨이만 노출됩니다. 또한 `librechat.configEnv`에 해당 키가 이미 설정되어 있지 않은 경우, `LANGFUSE_FANOUT_ENABLED` 및 내부 `LANGFUSE_FANOUT_COLLECTOR_URL`을 LibreChat에 주입합니다.

Redis는 단기 일회성 미디어 업로드 계획을 저장하여 생성 및 업로드 요청이 서로 다른 게이트웨이 복제본에 도달할 수 있도록 합니다. 외부 인증된 Redis 서비스의 경우 `langfuseFanout.redis.uri`, 선택 사항인 `username` 및 `passwordSecret`을 설정하십시오. URI가 Deployment 환경에 직접 렌더링되므로 자격 증명을 URI에 포함하지 마십시오. 번들로 제공되는 Redis 차트와 인증이 활성화된 경우, 호환되는 비밀(Secret) 비밀번호를 제공하거나 명시적으로 인증된 외부 URI를 제공하십시오.

`langfuseFanout.replicaCount`를 사용하여 팬아웃(fanout)을 수동으로 확장하십시오. 차트는 팬아웃 HPA를 생성하지 않습니다. Liveness 및 readiness 프로브는 `/healthz`를 사용하며 `langfuseFanout.livenessProbe` 및 `langfuseFanout.readinessProbe`에서 사용자 지정할 수 있습니다.

추가적인 배포 재정의(override)에는 Service 유형, 포트 및 어노테이션을 위한 `langfuseFanout.service`, 게이트웨이 Pod를 위한 `resources`, `podAnnotations`, `podLabels`, 그리고 사이드카를 위한 `otelCollector.image` 및 `otelCollector.resources`가 포함됩니다. `langfuseFanout.traceCollectorUrl` 또는 `otelCollector.receiverEndpoint`를 변경하는 경우, 두 값 모두 동일한 내부 수집기 리스너를 가리키도록 유지하십시오.

저장된 최상위 `langfuse` 객체에는 `enabled`, `publicKey`, 암호화된 `secretKey`, 검증된 `projectId`, 서버에서 생성된 `secretKeyPreview` 및 `destination`이 포함되어 있습니다. 이를 API로 관리되는 구성으로 취급하십시오. 미리 보기 필드나 암호화된 페이로드를 비밀 값으로 다시 제출하지 마십시오. 이전의 `displaySecretKey` 및 중첩된 `fanout.enabled` 필드는 더 이상 사용되지 않습니다.

테넌트 내보내기(Tenant export)는 팬아웃(fanout)과 수집기(collector) URL이 활성화되어 있고, 저장된 연결이 유효한 키와 함께 활성화되어 있으며, `destination`이 허용된 시작 대상과 일치할 때만 발생합니다. 다른 추적(trace)은 여전히 중앙 프로젝트로 흐를 수 있습니다. `LANGFUSE_FANOUT_TENANT_EXPORT_DISABLED=true`를 비상 스위치로 설정하면 중앙 내보내기는 유지하면서 테넌트 추적 및 피드백 점수 내보내기를 중단할 수 있습니다. 또한 이 설정은 테넌트 내보내기가 복구될 때까지 앱 내 연결 설정을 숨깁니다.

`LANGFUSE_FANOUT_CENTRAL_MEDIA_UPLOAD_DISABLED=true`를 설정하여 LibreChat SDK가 중앙 또는 폴백 수집기 추적을 위한 미디어 업로드를 생성하지 않도록 방지하세요. 테넌트 라우팅 미디어 업로드는 변경되지 않습니다. 이 앱 측 스위치는 게이트웨이 측 `LANGFUSE_FANOUT_CENTRAL_MEDIA_EXPORT_DISABLED`와는 별개이며, 후자는 업로드가 게이트웨이에 도달한 후 중앙 미디어 전달을 차단합니다.

미디어 전달의 경우, fanout 게이트웨이는 구성된 Langfuse 권한이 반환한 절대 HTTPS 업로드 대상만 허용하며 업로드 `PUT` 요청 시 리다이렉트를 따르지 않습니다. 프라이빗 MinIO 호스트를 포함한 자체 호스팅 객체 스토리지는 반환된 업로드 URL이 HTTPS를 사용하는 경우 계속 지원됩니다. 일반 HTTP 또는 리다이렉트에 의존하는 미디어 업로드 대상은 이제 실패 처리되지만, 추적(trace) 내보내기는 독립적으로 계속 수행됩니다.

추적 및 미디어 트래픽은 fanout gateway를 통과합니다. 피드백 점수는 LibreChat에서 직접 전송됩니다. 중앙 점수는 `LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY` 및 `LANGFUSE_BASE_URL`을 사용하며, 테넌트 점수는 테넌트 앱 구성을 사용합니다.

모든 게이트웨이 변수, 사용자 지정 대상 설정, 메트릭, 스케일링 및 Redis 동작에 대해서는 [Langfuse fanout deployment reference](https://github.com/LibreChat-AI/LibreChat/blob/dev/otel/langfuse-fanout/README.md)를 참조하세요.

### 진단 정보 내보내기 [#export-diagnostics]

추적된 각 요청은 테넌트 내보내기 결정을 설명하는 저카디널리티(low-cardinality) OpenTelemetry 속성을 기록합니다:

- `librechat.tenant.id`는 테넌트 컨텍스트를 식별합니다.
- `librechat.langfuse.export_plan`은 `central_only`, `tenant_fanout` 또는 `disabled`입니다.
- `librechat.langfuse.export_reason`는 `configured`, `collector_unconfigured`, `destination_unconfigured`, `emergency_disabled`, `fanout_disabled`, `missing_credentials` 또는 `tenant_disabled`입니다.

게이트웨이는 `langfuse_fanout_trace_exports_total{destination,result,tenant_id}`도 노출합니다. 테넌트가 없는 배치는 `<unknown>`을 사용하고, 혼합 테넌트 배치는 `<multiple>`을 사용하며, 잘못된 형식의 테넌트 ID는 `<invalid>`를 사용합니다. 게이트웨이는 프로세스당 최대 1,000개의 고유한 유효 테넌트 레이블을 유지하며, 이후의 ID는 `<overflow>`로 통합하여 메트릭 카디널리티를 제한합니다. 인식되지 않는 대상은 별도의 레이블을 생성하는 대신 `central`로 기록됩니다.

성공적인 인앱 연결 변경 사항은 구조화된 이벤트 `librechat.langfuse.connection.changed`도 기록합니다. 여기에는 테넌트, 구성 및 활성화 상태, 대상, 검증 결과, 주요 변경 사항, 그리고 키를 기록하지 않는 전체 변경 필드 목록이 포함됩니다. 이러한 필드를 사용하여 의도적인 중앙 전용 또는 비활성화된 플랜과 수집기, 대상 또는 자격 증명 구성 누락을 구분하십시오.

## Langfuse에서 추적(Traces) 확인하기 [#see-traces-in-langfuse]

### 대화 추적 뷰어 (Conversation Trace Viewer) [#conversation-trace-viewer]

`librechat.yaml`에서 `interface.traceViewer.enabled: true`를 활성화하면 사용자가 자신의 대화에 대한 샘플링된 Langfuse 추적을 모델 및 도구 워터폴(waterfall) 형태로 검사할 수 있습니다. 이를 위해서는 v2 Observations API를 지원하는 Langfuse 릴리스가 필요합니다. 뷰어는 다른 사용자의 대화, 샘플링되지 않은 추적, 또는 사용자 식별자가 LibreChat의 내부 사용자 ID를 사용하지 않는 추적에는 나타나지 않습니다.

기본적으로 입력, 출력, 메타데이터 및 도구 이름은 숨겨져 있습니다. 사용자가 해당 필드에 나타날 수 있는 시스템 프롬프트, 에이전트 지침 및 도구 정의를 볼 수 있도록 허용하는 경우에만 `interface.traceViewer.showInputOutput: true`로 설정하십시오. 도구 입력이나 출력을 노출하지 않고 도구 이름만 표시하려면 `interface.traceViewer.showToolNames: true`로 설정하십시오. 이 설정은 추가적인 Langfuse 관찰 읽기를 필요로 하며, 응답을 위해 이름만 유지됩니다. `maxRecords`, `maxContentLength`, `requestsPerMinute` 및 `requestTimeoutMs`는 각 요청을 제한합니다. 기본값과 범위는 [Config v1.3.16](/changelog/config_v1.3.16)을 참조하십시오.

Langfuse가 구성된 상태로 LibreChat을 다시 시작하면, Langfuse UI에서 모든 채팅 메시지 응답에 대한 새로운 추적(trace)을 확인할 수 있습니다:

LibreChat v0.8.8-rc2는 에이전트 추적(Agent trace) 구성을 업데이트하여 `StandardGraph`, `MultiAgentGraph` 및 `AgentModelCall` 런타임 관찰 이름을 사용하며, 활동 및 추론 레이블 호출은 해당 작업 내에 중첩됩니다. 추적 수준의 입력 및 출력도 루트 관찰에 표시됩니다. 이전 관찰 이름이나 추적 수준의 입력/출력 필드에 의존하는 저장된 Langfuse 필터, 대시보드 및 평가를 검토하십시오.

![LibreChat 예시 추적](https://langfuse.com/images/cookbook/integration_librechat/librechat-example-trace.png)

[Langfuse UI에서 추적 링크 보기](https://cloud.langfuse.com/project/cloramnkj0002jz088vzn1ja4/traces/57b4aa20a258a2e9e2d1ce2e4eacb21c?observation=06f5341a68d723b1&timestamp=2026-02-04T13%3A02%3A54.248Z&traceId=57b4aa20a258a2e9e2d1ce2e4eacb21c)

`access:admin` 및 `manage:configs:langfuse` 권한을 가진 관리자는 대화의 **Context Usage** 분석을 열고 **View session in Langfuse**를 선택할 수 있습니다. 동일한 작업은 Langfuse 구성 권한을 가진 인증된 동일 테넌트 관리자를 위한 공유 대화에서도 나타날 수 있습니다. 공개 및 일반 공유 링크 뷰어에게는 이 기능이 표시되지 않습니다.

이 링크는 생성이 완료되고 대화에 활성 인앱 Langfuse 연결로 전송된 샘플링된 추적(trace)이 하나 이상 포함된 경우에만 나타납니다. 이 링크는 해당 연결의 검증된 대상 및 프로젝트를 가리킵니다. 환경 관리 자격 증명, 비활성화된 연결, 샘플링에서 제외된 대화, 테넌트 간 뷰어 또는 필요한 권한이 없는 사용자에게는 표시되지 않습니다.

## 메시지 피드백 점수 [#message-feedback-scores]

Langfuse 추적(tracing)이 구성되면, LibreChat은 메시지 피드백을 일치하는 추적에 대한 `user-feedback` BOOLEAN 점수로 Langfuse에 전송합니다. 좋아요(thumbs-up) 평가는 `1`로, 싫어요(thumbs-down) 평가는 `0`으로 전송되며, 선택된 피드백 태그나 댓글은 점수에 포함됩니다. 피드백을 삭제하면 해당 점수도 삭제됩니다.

피드백 점수에는 사용 가능한 경우 메시지 ID, 부모 메시지 ID, 대화/세션 ID, 사용자 ID, endpoint, 발신자, `isCreatedByUser`, 토큰 수, 평점 및 피드백 태그를 포함한 메시지 컨텍스트 메타데이터가 포함됩니다. 점수가 전송되기 전에 비어 있는 메타데이터 값은 생략됩니다.

피드백 점수는 피드백 버튼이 활성화되어 있을 때만 생성됩니다. [`interface.feedback`](/docs/configuration/librechat_yaml/object_structure/interface#feedback)를 `false`로 설정하면 버튼이 숨겨지고 피드백 작성이 거부되므로, Langfuse로 점수가 전송되지 않습니다.

피드백 점수는 추적(tracing)과 동일한 Langfuse 자격 증명 및 기본 URL을 사용합니다. 또한 `LANGFUSE_TRACING_ENABLED=false`, `LANGFUSE_SAMPLE_RATE=0`, `LANGFUSE_TRACING_ENVIRONMENT` 설정을 따릅니다. 점수 전송은 최선형(best-effort) 방식으로 이루어지므로, Langfuse를 일시적으로 사용할 수 없는 경우에도 피드백 UI가 차단되지 않습니다.
