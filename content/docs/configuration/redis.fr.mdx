Ce guide explique comment configurer Redis pour le cache et le stockage des sessions dans LibreChat. Redis apporte des gains de performance significatifs et est **requis pour la mise à l'échelle horizontale**. Si vous exécutez plusieurs instances de LibreChat derrière un répartiteur de charge, Redis garantit un état cohérent entre toutes les instances.

## Configuration de base [#basic-setup]

### Activer Redis [#enable-redis]

Pour activer Redis dans LibreChat, définissez la variable d'environnement suivante dans votre fichier `.env` :

```bash
USE_REDIS=true
```

**Important** : Lorsque `USE_REDIS=true`, vous devez également fournir une `REDIS_URI`. L'application générera une erreur si Redis est activé sans URI de connexion.

## Types de connexion [#connection-types]

### Instance Redis unique [#single-redis-instance]

Pour une configuration standard avec un seul serveur Redis :

```bash
# Local Redis instance
REDIS_URI=redis://127.0.0.1:6379

# Remote Redis instance
REDIS_URI=redis://your-redis-host:6379
```

### Cluster Redis [#redis-cluster]

Pour les déploiements de cluster Redis avec plusieurs nœuds :

```bash
# Multiple Redis cluster nodes
REDIS_URI=redis://127.0.0.1:7001,redis://127.0.0.1:7002,redis://127.0.0.1:7003
```

L'application détecte automatiquement le mode cluster lorsque plusieurs URI sont fournis.

Si votre cluster Redis ne possède qu'une seule URI, vous pouvez utiliser la variable d'environnement `USE_REDIS_CLUSTER` pour activer le mode cluster :

```bash
# Redis cluster with single URI
REDIS_URI=redis://127.0.0.1:7001
USE_REDIS_CLUSTER=true
```

### Services Redis gérés à point de terminaison unique [#single-endpoint-managed-redis-services]

Certains services Redis gérés, notamment AWS ElastiCache Serverless et Redis Enterprise Cloud sur AWS, exposent un seul endpoint de connexion tout en fragmentant les clés en interne. Dans cette configuration, maintenez LibreChat en mode de connexion à nœud unique, mais activez les suppressions sécurisées pour le cluster (cluster-safe deletes) si les effacements de cache échouent avec l'erreur `CROSSSLOT Keys in request don't hash to the same slot`.

```bash
USE_REDIS=true
REDIS_URI=rediss://your-managed-redis-endpoint:6379
USE_REDIS_CLUSTER=false
REDIS_CLUSTER_SAFE_DELETE=true
```

`REDIS_CLUSTER_SAFE_DELETE=true` permet à LibreChat de supprimer les clés de cache correspondantes une par une au lieu d'envoyer des commandes `DEL` multi-clés. Cela évite les erreurs `CROSSSLOT` sans modifier la manière dont LibreChat se connecte à Redis.

Utilisez `USE_REDIS_CLUSTER=true` uniquement lorsque LibreChat doit créer un client Redis Cluster. Pour les services gérés à point de terminaison unique, `REDIS_CLUSTER_SAFE_DELETE=true` est l'option la plus sûre.

### Redis avec TLS/SSL [#redis-with-tlsssl]

Pour des connexions Redis sécurisées :

```bash
# Redis with TLS encryption
REDIS_URI=rediss://127.0.0.1:6380

# Path to CA certificate for TLS verification
REDIS_CA=/path/to/ca-cert.pem
```

## Configuration de la sécurité [#security-configuration]

### Authentification [#authentication]

Configurez les identifiants d'authentification Redis :

```bash
# Method 1: Include credentials in URI
# With both username and password
REDIS_URI=redis://myuser:mypassword@127.0.0.1:6379


# Method 2: Separate environment variables
REDIS_URI=redis://127.0.0.1:6379
REDIS_USERNAME=your_redis_username
REDIS_PASSWORD=your_redis_password
```

**Remarque** : Les identifiants intégrés dans `REDIS_URI` sont prioritaires. `REDIS_USERNAME` et `REDIS_PASSWORD` ne sont utilisés qu'en solution de repli lorsque l'URI ne contient ni nom d'utilisateur ni mot de passe.

### Configuration TLS [#tls-configuration]

Pour les connexions chiffrées :

```bash
# Enable TLS with rediss:// protocol
REDIS_URI=rediss://your-redis-host:6380

# Provide CA certificate for verification
REDIS_CA=/path/to/your/ca-certificate.pem
```

### TLS avec Elasticache [#tls-with-elasticache]

Elasticache peut nécessiter l'utilisation d'un dnsLookup alternatif pour les connexions TLS. Voir « Special Note: Aws Elasticache Clusters with TLS » sur cette page web : https://www.npmjs.com/package/ioredis

```bash
# Enable redis alternate dnsLookup
REDIS_USE_ALTERNATIVE_DNS_LOOKUP=true
```

## Options avancées [#advanced-options]

### Préfixage de clé [#key-prefixing]

Le préfixage des clés Redis empêche la contamination entre les déploiements en isolant les données de cache entre différents environnements, versions ou instances partageant le même serveur Redis. Ceci est essentiel pour :

- **Déploiements multi-locataires** : environnements de staging, de production et de développement distincts
- **Blue-green deployments** : Isoler le cache entre différentes versions de l'application

```bash
# Option 1: Dynamic prefix from environment variable (recommended for cloud)

# Google Cloud Platform - Cloud Run
REDIS_KEY_PREFIX_VAR=K_REVISION

# AWS - ECS/Fargate
REDIS_KEY_PREFIX_VAR=AWS_EXECUTION_ENV

# Azure Container Instances
REDIS_KEY_PREFIX_VAR=CONTAINER_NAME

# Kubernetes - Pod name or deployment
REDIS_KEY_PREFIX_VAR=HOSTNAME
REDIS_KEY_PREFIX_VAR=POD_NAME

# Kubernetes - Custom deployment identifier
REDIS_KEY_PREFIX_VAR=DEPLOYMENT_ID

# Heroku
REDIS_KEY_PREFIX_VAR=DYNO

# Option 2: Static prefix (for manual control)
REDIS_KEY_PREFIX=librechat-prod-v2
REDIS_KEY_PREFIX=staging-branch-feature-x
REDIS_KEY_PREFIX=dev-john-local
```

**Important** : Vous ne pouvez pas définir `REDIS_KEY_PREFIX_VAR` et `REDIS_KEY_PREFIX` simultanément.

**Exemples de contamination sans préfixe :**

- Le cache de production a été écrasé par le déploiement de staging
- Les tests de branches de fonctionnalités corrompent le cache de la branche principale
- Anciennes versions de déploiement fournissant des données en cache obsolètes

**Format de préfixe de clé :**

- Client IoRedis : `{prefix}::{key}`
- Client Keyv : Géré par la couche de stockage

### Limites de connexion [#connection-limits]

Configurer les limites de connexion Redis :

```bash
# Maximum number of event listeners (default: 40)
REDIS_MAX_LISTENERS=40
```

### Connection Keep-Alive [#connection-keep-alive]

Configurez les heartbeats Redis à délai limité et le keepalive TCP :

```bash
# Redis ping interval in seconds (default: 0 = disabled)
# When set to a positive integer (in seconds), Redis clients will ping the server at this interval
# When unset or 0, no pinging is performed (recommended for most use cases)
# Example: 300 = ping every 5 minutes
REDIS_PING_INTERVAL=300

# Maximum time an enabled heartbeat PING may go unanswered (default: 5000 ms)
REDIS_PING_TIMEOUT=5000

# Dedicated pub/sub subscriber heartbeat (default: 15 seconds, 0 = disabled)
REDIS_SUBSCRIBER_PING_INTERVAL=15

# TCP keepalive idle delay for ioredis sockets (default: 10000 ms, 0 = kernel default)
REDIS_KEEP_ALIVE=10000
```

**Important** :

- Définir `REDIS_PING_INTERVAL=0` ou l'omettre désactive complètement le ping.
- Ne définissez une valeur positive (en secondes) que si vous rencontrez des problèmes de délai d'attente de connexion.
- `REDIS_PING_INTERVAL` est spécifié en secondes et contrôle le heartbeat optionnel principal d'ioredis
- Les abonnés pub/sub dédiés utilisent leur propre intervalle activé par défaut, car une socket morte inactive pourrait autrement rester indétectée ; définissez `REDIS_SUBSCRIBER_PING_INTERVAL=0` pour désactiver ce signal de pulsation (heartbeat).
- Chaque heartbeat activé utilise `REDIS_PING_TIMEOUT` comme délai de réponse et reconnecte le socket lorsqu'un PING reste sans réponse.
- `REDIS_KEEP_ALIVE` configure le socket TCP ioredis indépendamment des PING au niveau de l'application
- Valeurs d'exemple : `300` (5 minutes), `600` (10 minutes), `60` (1 minute)

### Récupération après basculement de réplica [#replica-failover-recovery]

Lors d'un basculement Sentinel, un réplica Redis rétrogradé peut maintenir une socket ouverte tout en rejetant les écritures avec `READONLY`. LibreChat détecte cette réponse sur le client Keyv hors cluster, ferme la connexion obsolète et se reconnecte afin que le primaire actuel puisse être résolu sans redémarrer l'application.

```bash
# Minimum interval between forced recovery attempts, in milliseconds
# Default: 5000
REDIS_READONLY_RECOVERY_INTERVAL=5000
```

L'intervalle permet de temporiser (debounce) les tentatives de reconnexion lors d'une série d'écritures échouées. Les clients Redis Cluster sont exclus car ils utilisent une topologie de cluster native et une gestion des redirections.

### Vérifications de l'état de santé [#health-checks]

LibreChat expose trois endpoints de sonde. Seul `/readyz` reflète l'état de Redis :

| Endpoint | Renvoie `200 OK` | Renvoie `503 NOT_READY` |
| --- | --- | --- |
| `/livez` | Chaque fois que le processus traite des requêtes | Jamais |
| `/health` | Chaque fois que le processus traite des requêtes | Jamais |
| `/readyz` | Après la fin du démarrage et, avec `USE_REDIS=true`, tant que Redis est connecté | Avant la fin du démarrage, ou tant que Redis est activé mais déconnecté |

Lorsque Redis redémarre, bascule (failover) ou devient injoignable pendant une durée supérieure à la fenêtre de nouvelle tentative du client, les requêtes qui en dépendent (connexion, sessions, limites de débit) échouent jusqu'au rétablissement de la connexion. Pendant cette période, `/readyz` répond `503`, de sorte qu'un load balancer ou une sonde de disponibilité Kubernetes cesse d'acheminer le trafic vers l'instance. Elle repasse à `200` dès que Redis se reconnecte, sans redémarrage. Lorsque Redis est activé, chaque client Redis doit être connecté ; dans le cas d'un Redis Cluster, cela inclut chaque nœud primaire.

Dirigez les vérifications de disponibilité (readiness) vers `/readyz` et les vérifications de vivacité (liveness) vers `/livez`. N'incluez pas Redis dans la vérification de vivacité : une sonde de vivacité qui échoue pendant une panne de Redis redémarre tous les pods en même temps, sans pouvoir rétablir Redis.

```yaml
livenessProbe:
  httpGet:
    path: /livez
    port: 3080
readinessProbe:
  httpGet:
    path: /readyz
    port: 3080
  periodSeconds: 10
  failureThreshold: 3
```

`/readyz` n'attend pas de lui-même les reconnexions courtes. Utilisez donc `failureThreshold` pour décider de la durée d'une panne avant que le trafic ne soit retiré.

### Mise en cache sélective en mémoire [#selective-in-memory-caching]

Forcer l'utilisation du stockage en mémoire pour des espaces de noms de cache spécifiques, même lorsque Redis est activé :

```bash
# Comma-separated list of cache keys
FORCED_IN_MEMORY_CACHE_NAMESPACES=CONFIG_STORE,APP_CONFIG,ROLES
```

Lorsqu'elle n'est pas définie, la valeur par défaut est `CONFIG_STORE,APP_CONFIG`, de sorte que la configuration issue de `librechat.yaml` reste propre à chaque conteneur. Définir cette variable **remplace** la valeur par défaut au lieu de s'y ajouter ; incluez donc `CONFIG_STORE,APP_CONFIG` dans votre liste, sauf si vous souhaitez que ces espaces de noms soient stockés dans Redis. Définissez-la sur une chaîne vide pour acheminer tous les espaces de noms via Redis.

Clés de cache valides (issues de l'énumération `CacheKeys` dans `librechat-data-provider`) :

| Clé | Description |
| --- | --- |
| `CONFIG_STORE` | Magasin de configuration |
| `TOOL_CACHE` | Cache des outils (plugins, outils MCP, définitions d'outils) |
| `ROLES` | Rôles des utilisateurs |
| `USER_PRINCIPALS` | Appartenances aux groupes utilisées pour résoudre les principaux ACL |
| `PROMPT_GROUPS_ACCESS` | Ensembles d'identifiants d'accès aux groupes de prompts |
| `AGENT_LINKED_INSTRUCTIONS` | Instructions résolues des groupes de prompts liés à un agent |
| `SANDBOX_PREWARM` | État de préchauffage du bac à sable de code par conversation |
| `GEN_TITLE` | Titres générés |
| `TOOLS` | Données des outils |
| `MODELS_CONFIG` | Configuration des modèles |
| `MODEL_QUERIES` | Requêtes de modèles |
| `STARTUP_CONFIG` | Configuration de démarrage |
| `ENDPOINT_CONFIG` | Configuration des endpoints |
| `TOKEN_CONFIG` | Configuration des jetons |
| `REASONING_CAPABILITIES` | Effort de raisonnement par modèle pour les endpoints OpenRouter |
| `PULL_REQUESTS` | Recherches de pull requests et délais de recharge de la limite de débit GitHub |
| `APP_CONFIG` | Configuration de l'application |
| `ABORT_KEYS` | Clés d'annulation |
| `BANS` | Données de bannissement |
| `ENCODED_DOMAINS` | Domaines encodés |
| `AUDIO_RUNS` | Exécutions de traitement audio |

| `OPENID_SESSION` | Sessions OpenID |

<Callout type="warn" title="Clés invalides">
  L'utilisation d'une clé invalide (par exemple, la clé obsolète `STATIC_CONFIG`) provoquera une erreur au démarrage. Utilisez uniquement les clés du tableau ci-dessus.
</Callout>

## Optimisation des performances [#performance-tuning]

### Connection Keep-Alive [#connection-keep-alive-1]

L'application implémente une connexion keep-alive configurable :

- Les PINGs du client principal sont contrôlés par `REDIS_PING_INTERVAL` et sont désactivés par défaut.
- Les PINGs dédiés aux abonnés sont contrôlés par `REDIS_SUBSCRIBER_PING_INTERVAL` et sont définis par défaut sur 15 secondes.
- Les Heartbeats utilisent `REDIS_PING_TIMEOUT` pour détecter les sockets silencieusement inactifs et forcer la reconnexion.
- Le keepalive TCP utilise `REDIS_KEEP_ALIVE`, indépendamment des pulsations (heartbeats) au niveau de l'application.
- Les minuteurs de pulsation (heartbeat timers) sont effacés lors des événements de déconnexion ou de fermeture.

### Stratégie de cache [#cache-strategy]

L'application utilise une approche à double client :

- **Client IoRedis** : Opérations Redis principales avec préfixage automatique
- **Client Keyv Redis** : Opérations de couche de stockage avec gestion des préfixes dans `cacheFactory.js`

### Réglage avancé de la connexion [#advanced-connection-tuning]

Ces variables optionnelles permettent d'ajuster le comportement des connexions et les opérations de cache en masse. Les valeurs par défaut conviennent à la plupart des déploiements.

| Variable | Default | Description |
| --- | --- | --- |
| `REDIS_CONNECT_TIMEOUT` | `10000` | Délai d'expiration de la connexion en millisecondes. |
| `REDIS_RETRY_MAX_ATTEMPTS` | `10` | Nombre maximum de tentatives de reconnexion avant d'abandonner. `0` réessaie indéfiniment. |
| `REDIS_RETRY_MAX_DELAY` | `3000` | Délai maximum entre les tentatives de reconnexion, en millisecondes. |
| `REDIS_ENABLE_OFFLINE_QUEUE` | `true` | Met les commandes en file d'attente pendant la déconnexion. Définissez `false` pour les faire échouer immédiatement. |
| `REDIS_SCAN_COUNT` | `1000` | Indication `COUNT` pour les opérations `SCAN` lors de la recherche de clés par motif. |
| `REDIS_DELETE_CHUNK_SIZE` | `1000` | Nombre de clés supprimées par lot lors des suppressions en masse. |
| `MCP_REGISTRY_CACHE_TTL` | `5000` | Durée en millisecondes pendant laquelle les caches du registre MCP sont conservés. Le décalage entre instances peut atteindre deux fois cette valeur. `0` désactive l'instantané local, de sorte que chaque lecture est envoyée à Redis. |

### Optimisation de la mémoire [#memory-optimization]

Utilisez `FORCED_IN_MEMORY_CACHE_NAMESPACES` pour optimiser les performances en conservant en mémoire les petits jeux de données fréquemment consultés, tout en utilisant Redis pour les caches plus volumineux.

## Exemples de configuration [#configuration-examples]

```bash
USE_REDIS=true

REDIS_KEY_PREFIX=librechat-dev
```


## Flux reprenables [#resumable-streams]

Redis active les [Resumable Streams](/docs/features/resumable_streams) pour les déploiements mis à l'échelle horizontalement. Lorsqu'ils sont activés, les réponses de l'IA peuvent se reconnecter et reprendre de manière transparente entre les instances de serveur.

**Important :** Lorsque `USE_REDIS=true`, les flux reprenables utilisent automatiquement Redis pour la coordination entre instances. Il s'agit de la configuration recommandée pour les déploiements mis à l'échelle horizontalement où les utilisateurs peuvent se connecter à différentes instances de serveur.

**Remarque :** Si vous exécutez une seule instance de LibreChat, Redis pour les flux reprenables est généralement superflu ; le mode en mémoire intégré fonctionne parfaitement. Redis devient indispensable lorsque vous avez plusieurs instances de LibreChat derrière un équilibreur de charge, car la reconnexion d'un utilisateur peut atteindre un serveur différent de celui où son flux a démarré.

### Configuration [#configuration]

```bash
# Redis enabled = resumable streams automatically use Redis
USE_REDIS=true
REDIS_URI=redis://127.0.0.1:6379

# Optional: explicitly control resumable streams behavior
# USE_REDIS_STREAMS=true  # Enabled by default when USE_REDIS=true
```

### Compatibilité du protocole de génération [#generation-protocol-compatibility]

Les clients LibreChat actuels négocient automatiquement le protocole de génération v2 avec chaque magasin de génération intégré. Aucun paramètre de déploiement n'est requis. Les générations existantes avec un marqueur de protocole v1 explicite ou stocké conservent leur comportement v1 immuable via le pilotage, la pause/reprise, la réessai et la récupération jusqu'à leur achèvement.

Pour une mise à jour continue, chaque image API et worker en cours d'exécution doit inclure le pont de compatibilité v2 :

- Chaque image d'API et de worker exécute LibreChat `v0.8.8-rc1` ou une version plus récente.
- Le Helm chart `2.0.8` ou plus récent sélectionne une image par défaut compatible ; une substitution d'image personnalisée doit toujours répondre aux exigences d'image ci-dessus.

Lors d'une mise à niveau depuis une ancienne version, effectuez un transfert à froid (cold handoff) : arrêtez chaque ancienne réplique d'API et de worker avant de démarrer la nouvelle image. Cela empêche les binaires pré-v2 et automatic-v2 de partager l'état de génération dans Redis.

<Callout type="warning" title="Sécurité du déploiement progressif">
  Ne faites pas fonctionner une version antérieure à `v0.8.8-rc1` avec le même état de génération Redis que les réplicas actuels. Avant de revenir à une version inférieure à ce seuil de compatibilité, assurez-vous d'abord que les réplicas actuels et les générations protocol-v2 ont été vidés.
</Callout>

Les flux de génération en mémoire négocient également automatiquement le protocole v2 et ne partagent pas l'état de génération entre les processus.

### Fusion des deltas de flux (Stream Delta Coalescing) [#stream-delta-coalescing]

Les flux basés sur Redis peuvent regrouper les publications delta pour réduire les scripts Redis, les allers-retours et l'utilisation du CPU lors de taux de jetons élevés :

```bash filename=".env"
STREAM_DELTA_COALESCE_MS=25
```

Le paramètre est défini par défaut sur `25` millisecondes lorsqu'il n'est pas configuré. Définissez-le explicitement sur `0` pour désactiver la coalescence ; les valeurs supérieures à `1000` sont plafonnées. Le traitement par lots peut ajouter jusqu'à une fenêtre configurée de latence de livraison et peut entraîner la perte de la fin de la mémoire tampon si le processus de publication se termine avant son vidage. Les trames de segments individuelles sont conservées pour la compatibilité du protocole, donc ce paramètre réduit le travail lié aux scripts Redis et aux allers-retours sans modifier le format de trame de l'abonné. Les flux de génération en mémoire restent inchangés.

### Avantages clés (pour la mise à l'échelle horizontale) [#key-benefits-for-horizontal-scaling]

- **Continuité inter-instance** : Les utilisateurs peuvent démarrer une génération sur un serveur et la reprendre sur un autre
- **Déploiements progressifs** : Les flux actifs survivent aux redémarrages du serveur
- **Synchronisation multi-onglets** : La même conversation est synchronisée sur plusieurs onglets de navigateur dans un environnement à charge équilibrée
- **Résilience de la connexion** : Reconnexion automatique, quel que soit le serveur qui traite la requête

### Configuration du cluster [#cluster-configuration]

Pour les déploiements Redis Cluster, LibreChat utilise automatiquement des clés avec hash-tag pour garantir que les opérations de flux restent dans le même slot de cluster :

```bash
USE_REDIS=true
USE_REDIS_STREAMS=true
USE_REDIS_CLUSTER=true
REDIS_URI=redis://node1:7001,redis://node2:7002,redis://node3:7003
```

Voir [Resumable Streams](/docs/features/resumable_streams) pour plus de détails sur cette fonctionnalité.

## Coordination du catalogue MCP [#mcp-catalog-coordination]

Lorsque Redis est activé, LibreChat coordonne les catalogues d'outils MCP au niveau de l'application entre les répliques. La publication au démarrage, la synchronisation lors de la reconnexion et les mises à jour `notifications/tools/list_changed` utilisent des marqueurs de génération et de révision afin qu'une réplique obsolète ne puisse pas écraser un catalogue plus récent.

Les déploiements de Redis Cluster utilisent des clés de catalogue compatibles avec les slots et des opérations de mise à jour ; aucun paramètre Redis MCP distinct n'est requis. Consultez [Gestion du serveur MCP](/docs/features/mcp#mcp-server-management) pour le comportement dynamique du catalogue et la préparation OAuth.
