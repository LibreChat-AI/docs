[Langfuse](https://langfuse.com) は、LLMアプリケーションのトレース、監視、デバッグを支援するオープンソースのLLM可観測性プラットフォームです。LangfuseをLibreChatと統合することで、AIとの会話を完全に可視化できます。

## 前提条件 [#prerequisites]

始める前に、以下が準備されていることを確認してください：

1. 実行中のLibreChatインスタンス（[クイックスタート](/docs/quick_start)を参照）
2. Langfuseアカウント（[無料で登録](https://cloud.langfuse.com)）
3. プロジェクト設定のLangfuse APIキー

## セットアップ [#setup]

シングルテナントデプロイメントでは、アプリ内接続または環境管理された認証情報のいずれかを選択してください。環境認証情報が設定されている場合、そちらが優先されます。

### アプリ内接続 [#in-app-connection]

権限を持つ管理者は、**Settings → Langfuse** を開き、承認済みの宛先を選択し、プロジェクトの公開鍵と秘密鍵を入力して、**Save & enable** を選択できます。LibreChat は保存前に両方のキーを検証し、検証済みのプロジェクトIDを記録し、秘密鍵を保存時に暗号化します。その後読み取る際には、マスクされたプレビューのみが返されます。保存された接続は、秘密鍵を公開することなく、有効化、無効化、再テスト、または置き換えが可能です。

この設定には `access:admin` と `manage:configs:langfuse` （またはそれに対応する広範な権限/管理者権限）の両方が必要です。これは、トレーシングが有効になっており、かつ以下の場合に利用可能です：

- シングルテナントのデプロイメントには、`LANGFUSE_PUBLIC_KEY` と `LANGFUSE_SECRET_KEY` の両方が含まれていません。
- ファンアウトデプロイメントでは、コレクターが有効になっており、かつ緊急スイッチによってテナントのエクスポートが無効化されていない状態です。

プレーンテキストの `langfuse.secretKey` を直接 `librechat.yaml` に記述しないでください。ランタイムは、承認された設定書き込みによって生成された暗号化された値を受け入れます。通常の接続ワークフローには、設定ページを使用してください。

保存された接続は基本設定に属します。ロール、グループ、およびユーザー設定のオーバーライドでは、`langfuse` セクションを置き換えたり削除したりすることはできません。

### 設定例 [#example-configuration]

```sh filename=".env"
# Langfuse Configuration
LANGFUSE_PUBLIC_KEY=pk-lf-***
LANGFUSE_SECRET_KEY=sk-lf-***
# LANGFUSE_PROJECT_ID=project-id
# LANGFUSE_SAMPLE_RATE=1

# 🇪🇺 EU Data Region
LANGFUSE_BASE_URL=https://cloud.langfuse.com

# 🇺🇸 US Data Region
# LANGFUSE_BASE_URL=https://us.cloud.langfuse.com
```

<Callout type="note" title="セルフホスト型 Langfuse">
  セルフホスト型の Langfuse インスタンスを使用する場合は、`LANGFUSE_BASE_URL` をカスタム URL に設定してください（例: ローカル開発環境の場合は `http://localhost:3000`）。
</Callout>

両方の環境変数が存在する場合、LibreChatはそれらを中央プロジェクトに使用し、**Settings → Langfuse** を非表示にします。`LANGFUSE_TRACING_ENABLED=false` または `LANGFUSE_SAMPLE_RATE=0` を設定すると、トレースとフィードバックスコアの両方が無効になります。サンプリングレートを小数で指定した場合、トレースごとに決定論的な判断が下されます。サンプリング対象外となったトレースには、その後のフィードバックスコアは付与されません。

`LANGFUSE_BASE_URL` は標準的なベースURL設定です。以前の `LANGFUSE_HOST` および `LANGFUSE_BASEURL` という名称は互換性のためのエイリアスとして残されており、複数が設定されている場合は `LANGFUSE_BASE_URL` が優先されます。

### 認証済みプロキシとゲートウェイ [#authenticated-proxies-and-gateways]

Cloudflare Access、oauth2-proxy、またはその他の認証ゲートウェイの背後にあるセルフホスト型のLangfuseインスタンスについては、`librechat.yaml`でデプロイメントレベルのカスタムリクエストヘッダーを定義してください：

```yaml filename="librechat.yaml"
langfuse:
  headers:
    CF-Access-Client-Id: '${CF_ACCESS_CLIENT_ID}'
    CF-Access-Client-Secret: '${CF_ACCESS_CLIENT_SECRET}'
```

LibreChatは、解決されたヘッダーをすべての直接的なLangfuseインターフェース（トレースおよびメディアのエクスポート、フィードバックスコアの作成と削除、プロジェクトIDの検索、および管理者資格情報の検証）に適用します。RESTリクエストにおいては、Langfuse自身の `Authorization` 資格情報が引き続き優先されます。値は `${ENV_VAR}` の補間をサポートしており、解決されない変数、保護されたインフラストラクチャシークレットの参照、空白の値、および無効なヘッダー名は警告とともに破棄されます。ヘッダー値は起動ログや管理設定の読み取り時にマスクされますが、リテラルな資格情報よりも環境変数の参照を使用することが推奨されます。

これらのヘッダーはオペレーターが所有するものであり、YAMLでのみ設定可能です。これらはAdmin Panelや設定APIを通じて書き込んだり、MongoDBに保存したり、ユーザーごとの `{{...}}` プレースホルダーで埋めたりすることはできません。LibreChatは、設定でLangfuseのオリジンが正確に1つに解決される場合にのみ、これらのヘッダーを送信します。複数のセントラル、テナント、またはコレクターのオリジンが存在する場合、マップが安全に送信先を選択できないため、警告をログに記録し、カスタムヘッダーは送信されません。

<Callout type="warning" title="ファンアウト制限">
  fanout collectorは現在、`Authorization`ヘッダーのみをテナントのLangfuse送信先に転送します。
カスタムの`langfuse.headers`は、LibreChatから単一のコレクターまたはLangfuseオリジンへの直接リクエストを認証することはできますが、別のプロキシの背後にあるテナント送信先へのコレクターの上流リクエストを認証することはできません。
</Callout>

### ユーザーIDとメタデータの追跡 [#trace-user-identity-and-metadata]

デフォルトでは、AgentのトレースはLibreChatの内部ユーザーIDをLangfuseの `userId` として使用し、追加のユーザーメタデータやリクエストメタデータはエクスポートしません。デプロイメントの運用者は、別のユーザーフィールドを選択し、`langfuse.trace` の下でメタデータを明示的に許可リストに追加することができます。

```yaml filename="librechat.yaml"
langfuse:
  trace:
    userIdField: email
    userMetadataFields: [email, username, role, provider]
    conversationMetadataFields: [conversationId, endpoint, model, modelLabel, spec]
```

`userIdField` は `id`、`email`、`username`、`name`、`openidId`、`samlId`、`ldapId`、`googleId`、`githubId`、`discordId`、`appleId`、または `facebookId` を受け入れます。選択されたフィールドがユーザーに存在しない場合、内部IDはトレース `userId` のままとなります。

`userMetadataFields` は、それらの識別フィールドに加えて `role` および `provider` を受け入れます。値は `librechat.user.<field>` の下でエクスポートされます。`conversationMetadataFields` は `conversationId`、`endpoint`、`endpointType`、`provider`、`model`、`modelLabel`、および `spec` を受け入れます。これらは `librechat.conversation.id`、`librechat.endpoint`、`librechat.endpoint.type`、`librechat.provider`、`librechat.model`、`librechat.model.label`、および `librechat.spec` トレース属性にマッピングされます。

これら3つのフィールドはすべてオプションであり、ユーザーやリクエストに存在するからといってメタデータフィールドが自動的にエクスポートされることはありません。メールアドレス、ユーザー名、プロバイダーID、会話ID、およびモデルの選択は、機密性の高いテレメトリとして扱う必要があります。Langfuseの保持ポリシーおよびアクセス権限ポリシーで許可されているフィールドのみを許可リスト（allowlist）に登録してください。

## テナントファンアウト (オプション) [#tenant-fanout-optional]

Langfuse fanoutを使用すると、マルチテナントのLibreChatデプロイメントにおいて、各対象のトレースとそのメディアを、中央のLangfuseプロジェクトとテナント固有のプロジェクトの両方にエクスポートできます。この機能はオプトイン形式であり、ゲートウェイと内部のOpenTelemetryコレクターを追加します。fanoutがデプロイされていない場合、上記の通常の単一プロジェクトトレースは変更されません。

Fanoutは2つの設定レイヤーを使用します：

- デプロイメント環境変数は、起動時に中央プロジェクト、ゲートウェイ、および許可されたテナントの宛先を定義します。
- **Settings → Langfuse** は、テナントの有効状態、公開鍵、暗号化された秘密鍵、検証済みプロジェクトID、および許可された宛先を1つ提供します。キーはゲートウェイを再起動することなく、実行時に変更可能です。

付属の Compose オーバーライドは、`eu`、`us`、および `jp` の Langfuse Cloud 宛先をサポートしています：

```sh filename=".env"
LANGFUSE_BASE_URL=https://cloud.langfuse.com
LANGFUSE_FANOUT_CENTRAL_BASE_URL=https://cloud.langfuse.com
LANGFUSE_FANOUT_CENTRAL_AUTH_HEADER="Basic <base64-public-key-colon-secret-key>"
LANGFUSE_FANOUT_CENTRAL_MEDIA_UPLOAD_DISABLED=false
LANGFUSE_FANOUT_TENANT_DESTINATIONS="eu=https://cloud.langfuse.com,us=https://us.cloud.langfuse.com,jp=https://jp.cloud.langfuse.com"
LANGFUSE_FANOUT_TRACE_DESTINATION_KEYS=eu,us,jp
LANGFUSE_FANOUT_TENANT_EXPORT_DISABLED=false
```

fanoutオーバーライドを使用して、通常のComposeスタックを開始します：

```sh
docker compose -f docker-compose.yml -f docker-compose.langfuse-fanout.yml up -d
```

このオーバーライドにより `LANGFUSE_FANOUT_ENABLED` が有効になり、LibreChatがゲートウェイを指すようになり、コレクターおよびプライベートなRedisサービスが起動します。デプロイ済みのスタックについては、代わりに `deploy-compose.yml` と `deploy-compose.langfuse-fanout.yml` を組み合わせてください。

ゲートウェイはデフォルトで `:4318` でリッスンします。カスタムデプロイメントでは `LANGFUSE_FANOUT_LISTEN_ADDR` を使用してバインドアドレスを上書きできます。同梱の Compose および Helm 設定では、標準のゲートウェイポートが既にルーティングされています。

### Helm デプロイメント [#helm-deployment]

Composeのオーバーライドはゲートウェイをローカルでビルドしますが、Kubernetesにはレジストリから利用可能なイメージが必要です。LibreChatリポジトリのルートから、チャートをインストールする前にゲートウェイをビルドしてプッシュしてください：

```sh
docker build \
  -f otel/langfuse-fanout/Dockerfile \
  -t registry.example.com/librechat-langfuse-fanout:<tag> .
docker push registry.example.com/librechat-langfuse-fanout:<tag>
```

完全な中央Langfuse Basic認証ヘッダーを含むKubernetes Secretを作成します。その値は `Basic ` に続けて、base64エンコードされた `<public-key>:<secret-key>` 認証情報を指定します：

```sh
kubectl create secret generic langfuse-central \
  --from-literal=LANGFUSE_FANOUT_CENTRAL_AUTH_HEADER='Basic <base64-public-key-colon-secret-key>'
```

Helm valuesでfanoutデプロイメントを有効にします。この例ではバンドルされているRedisチャートを使用しています。外部のRedisサービスを使用する場合は、代わりに `langfuseFanout.redis.uri` を設定してください。

```yaml filename="values.yaml"
redis:
  enabled: true

langfuseFanout:
  enabled: true
  image:
    repository: registry.example.com/librechat-langfuse-fanout
    tag: '<tag>'
    pullPolicy: IfNotPresent
  central:
    baseUrl: https://cloud.langfuse.com
    authHeaderSecret:
      name: langfuse-central
      key: LANGFUSE_FANOUT_CENTRAL_AUTH_HEADER
  metrics:
    secret:
      name: librechat-metrics
      key: METRICS_SECRET
  tenant:
    destinations:
      eu:
        baseUrl: https://cloud.langfuse.com
      us:
        baseUrl: https://us.cloud.langfuse.com
      jp:
        baseUrl: https://jp.cloud.langfuse.com
  upstreamTimeout: 30s
  publicUrl: ''
  otelCollector:
    receiverEndpoint: 127.0.0.1:4319
  redis:
    uri: ''
    username: ''
    passwordSecret:
      name: ''
      key: REDIS_PASSWORD
    keyPrefix: langfuse-fanout
  memoryLimitMiB: 256
  memorySpikeLimitMiB: 64
  batchTimeout: 1s
  batchSendSize: 128
  metadataCardinalityLimit: 1000
```

metrics Secret はオプションですが、`langfuseFanout.metrics.secret` でベアラートークンを指定しない限り、`/metrics` は `401` を返します。メトリクスのスクレイピングが必要な場合は、個別に作成してください：

```sh
kubectl create secret generic librechat-metrics \
  --from-literal=METRICS_SECRET='<metrics-bearer-token>'
```

このチャートは、ポート `4318` のゲートウェイコンテナと、ポート `4319` の内部 OpenTelemetry Collector サイドカーを持つ1つの Deployment をレンダリングします。Service によって公開されるのはゲートウェイのみです。また、`librechat.configEnv` にこれらのキーが既に設定されていない限り、`LANGFUSE_FANOUT_ENABLED` と内部の `LANGFUSE_FANOUT_COLLECTOR_URL` を LibreChat に注入します。

Redisは短命なワンタイムのメディアアップロードプランを保存するため、作成およびアップロードのリクエストが異なるゲートウェイのレプリカに到達できるようになります。外部の認証済みRedisサービスを使用する場合は、`langfuseFanout.redis.uri`、およびオプションの`username`と`passwordSecret`を設定してください。URIはDeployment環境に直接レンダリングされるため、認証情報はURIに含めないようにしてください。バンドルされているRedisチャートを使用し、認証を有効にする場合は、互換性のあるパスワードSecretを提供するか、明示的に認証された外部URIを指定してください。

`langfuseFanout.replicaCount` を使用して手動でファンアウトをスケールします。チャートはファンアウト用のHPAを作成しません。LivenessプローブおよびReadinessプローブは `/healthz` を使用しており、`langfuseFanout.livenessProbe` および `langfuseFanout.readinessProbe` でカスタマイズ可能です。

その他のデプロイメントのオーバーライドには、Serviceのタイプ、ポート、アノテーションを指定する `langfuseFanout.service`、ゲートウェイPod用の `resources`、`podAnnotations`、`podLabels`、そしてサイドカー用の `otelCollector.image` および `otelCollector.resources` が含まれます。`langfuseFanout.traceCollectorUrl` または `otelCollector.receiverEndpoint` を変更する場合は、両方の値が同じ内部コレクターリスナーを指すようにしてください。

保存されたトップレベルの `langfuse` オブジェクトには、`enabled`、`publicKey`、暗号化された `secretKey`、検証済みの `projectId`、サーバー生成された `secretKeyPreview`、および `destination` が含まれています。これらはAPI管理下の設定として扱い、プレビューフィールドや暗号化されたペイロードをシークレットとして再送信しないでください。以前の `displaySecretKey` およびネストされた `fanout.enabled` フィールドは使用されなくなりました。

テナントのエクスポートは、ファンアウトとコレクターURLが有効で、保存された接続が有効なキーで有効化されており、かつ `destination` が許可された起動先と一致する場合にのみ発生します。その他のトレースは、引き続き中央プロジェクトに送信可能です。`LANGFUSE_FANOUT_TENANT_EXPORT_DISABLED=true` を緊急スイッチとして設定することで、中央へのエクスポートを維持したまま、テナントのトレースおよびフィードバックスコアのエクスポートを停止できます。これを行うと、テナントのエクスポートが復元されるまで、アプリ内の接続設定も非表示になります。

`LANGFUSE_FANOUT_CENTRAL_MEDIA_UPLOAD_DISABLED=true` を設定すると、LibreChat SDK がセントラルまたはフォールバックコレクタートレース用のメディアアップロードを作成するのを防ぐことができます。テナントルーティングされたメディアアップロードには影響しません。このアプリ側のスイッチは、ゲートウェイ側でアップロードが到達した後のセントラルメディア転送をブロックする `LANGFUSE_FANOUT_CENTRAL_MEDIA_EXPORT_DISABLED` とは異なります。

メディア転送において、ファンアウトゲートウェイは設定されたLangfuseオーソリティによって返される絶対的なHTTPSアップロードターゲットのみを受け入れ、アップロードの `PUT` リクエストに対するリダイレクトには従いません。プライベートなMinIOホストを含むセルフホストのオブジェクトストレージは、返されるアップロードURLがHTTPSを使用している限り、引き続きサポートされます。プレーンなHTTPやリダイレクトに依存するメディアアップロードターゲットは、トレースのエクスポートが独立して継続される一方で、現在は失敗するように設定されています。

トレースおよびメディアトラフィックはファンアウトゲートウェイを経由します。フィードバックスコアはLibreChatから直接送信されます。セントラルスコアは `LANGFUSE_PUBLIC_KEY`、`LANGFUSE_SECRET_KEY`、および `LANGFUSE_BASE_URL` を使用し、テナントスコアはテナントアプリの設定を使用します。

すべてのゲートウェイ変数、カスタム送信先の設定、メトリクス、スケーリング、およびRedisの動作については、[Langfuse fanout deployment reference](https://github.com/LibreChat-AI/LibreChat/blob/dev/otel/langfuse-fanout/README.md)を参照してください。

### 診断情報をエクスポート [#export-diagnostics]

各トレースされたリクエストは、テナントのエクスポート決定を説明する低カーディナリティのOpenTelemetry属性を記録します。

- `librechat.tenant.id` はテナントコンテキストを識別します
- `librechat.langfuse.export_plan` は `central_only`、`tenant_fanout`、または `disabled` です。
- `librechat.langfuse.export_reason` は `configured`、`collector_unconfigured`、`destination_unconfigured`、`emergency_disabled`、`fanout_disabled`、`missing_credentials`、または `tenant_disabled` です。

ゲートウェイは `langfuse_fanout_trace_exports_total{destination,result,tenant_id}` も公開します。テナントのないバッチは `<unknown>` を使用し、混合テナントのバッチは `<multiple>` を使用し、不正な形式のテナントIDは `<invalid>` を使用します。ゲートウェイはプロセスごとに最大1,000個の異なる有効なテナントラベルを保持し、それ以降のIDは `<overflow>` に統合することでメトリクスのカーディナリティを制限します。認識されない送信先は、別のラベルを作成するのではなく `central` として記録されます。

アプリ内での接続変更が成功すると、構造化イベント `librechat.langfuse.connection.changed` も書き込まれます。これには、テナント、構成および有効状態、送信先、検証結果、主な変更点、およびキーをログに記録することなく変更されたフィールドの完全なリストが含まれます。これらのフィールドを使用して、意図的な中央のみ（central-only）または無効化されたプランと、コレクター、送信先、または資格情報の構成の欠落を区別してください。

## LibreChat を再起動する [#restart-librechat]

環境変数を追加した後、LibreChatインスタンスを再起動して変更を適用してください。


## Langfuseでトレースを確認する [#see-traces-in-langfuse]

### 会話トレースビューア [#conversation-trace-viewer]

`librechat.yaml` で `interface.traceViewer.enabled: true` を有効にすると、ユーザーは自身の会話のサンプリングされた Langfuse トレースを、モデルとツールのウォーターフォール形式で確認できるようになります。これには、v2 Observations API を備えた Langfuse リリースが必要です。このビューアは、他のユーザーの会話、サンプリングされていないトレース、または LibreChat の内部ユーザー ID を使用していないユーザー ID のトレースには表示されません。

デフォルトでは、入力、出力、メタデータ、およびツール名は非表示のままです。ユーザーがシステムプロンプト、エージェントの指示、およびそれらのフィールドに表示される可能性のあるツール定義を閲覧しても問題ない場合にのみ、`interface.traceViewer.showInputOutput: true` を設定してください。ツール名を表示しつつツールへの入力や出力を公開しないようにするには、`interface.traceViewer.showToolNames: true` を設定します。これには追加の Langfuse 観測読み取りが必要となり、レスポンスには名前のみが保持されます。`maxRecords`、`maxContentLength`、`requestsPerMinute`、および `requestTimeoutMs` は各リクエストを制限します。デフォルト値と範囲については、[Config v1.3.16](/changelog/config_v1.3.16) を参照してください。

Langfuseが設定された状態でLibreChatを再起動すると、Langfuse UI上のすべてのチャットメッセージ応答に対して新しいトレースが表示されるようになります。

LibreChat v0.8.8-rc2では、エージェントトレースのシェイピングが更新され、`StandardGraph`、`MultiAgentGraph`、および `AgentModelCall` のランタイム観測名が使用されるようになりました。アクティビティおよび推論ラベルの呼び出しは、それらが記述する作業の下にネストされます。トレースレベルの入力と出力もルート観測上に表現されます。以前の観測名やトレースレベルの入出力フィールドに依存している、保存済みのLangfuseフィルター、ダッシュボード、および評価を確認してください。

![LibreChat example trace](https://langfuse.com/images/cookbook/integration_librechat/librechat-example-trace.png)

[Langfuse UIのトレースへのリンク](https://cloud.langfuse.com/project/cloramnkj0002jz088vzn1ja4/traces/57b4aa20a258a2e9e2d1ce2e4eacb21c?observation=06f5341a68d723b1&timestamp=2026-02-04T13%3A02%3A54.248Z&traceId=57b4aa20a258a2e9e2d1ce2e4eacb21c)

`access:admin` および `manage:configs:langfuse` を持つ管理者は、会話の **Context Usage**（コンテキスト使用量）の内訳を開き、**View session in Langfuse**（Langfuseでセッションを表示）を選択できます。同じ操作は、Langfuse設定へのアクセス権を持つ、認証済みかつ同一テナントの管理者が共有会話を表示した際にも表示される場合があります。公開リンクや通常の共有リンクの閲覧者には表示されません。

このリンクは、生成が完了し、かつ会話にアクティブなアプリ内Langfuse接続へ送信されたサンプリングトレースが少なくとも1つ含まれている場合にのみ表示されます。このリンクは、その接続の検証済み送信先およびプロジェクトを指します。環境管理の認証情報、無効化された接続、サンプリング対象外の会話、テナント間ビューアー、または必要なアクセス権を持たないユーザーに対しては表示されません。

## メッセージフィードバックスコア [#message-feedback-scores]

Langfuseトレーシングが設定されている場合、LibreChatはメッセージのフィードバックも、対応するトレース上の `user-feedback` BOOLEANスコアとしてLangfuseに送信します。高評価（サムズアップ）は `1` として、低評価（サムズダウン）は `0` として送信され、選択されたフィードバックタグやコメントもスコアに含まれます。フィードバックをクリアすると、そのスコアは削除されます。

フィードバックスコアには、利用可能な場合にメッセージコンテキストのメタデータが含まれます。これには、メッセージID、親メッセージID、会話/セッションID、ユーザーID、endpoint、送信者、`isCreatedByUser`、トークン数、評価、およびフィードバックタグが含まれます。空のメタデータ値は、スコアが送信される前に省略されます。

フィードバックスコアは、フィードバックボタンが利用可能な場合にのみ生成されます。[`interface.feedback`](/docs/configuration/librechat_yaml/object_structure/interface#feedback) を `false` に設定するとボタンが非表示になり、フィードバックの書き込みが拒否されるため、Langfuseにスコアが送信されることはありません。

フィードバックスコアは、トレーシングと同じLangfuse認証情報およびベースURLを使用します。また、`LANGFUSE_TRACING_ENABLED=false`、`LANGFUSE_SAMPLE_RATE=0`、および`LANGFUSE_TRACING_ENVIRONMENT`の設定も尊重されます。スコアの送信はベストエフォート型であるため、Langfuseが一時的に利用できない場合でもフィードバックUIがブロックされることはありません。
