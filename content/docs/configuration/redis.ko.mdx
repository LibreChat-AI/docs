## 기본 설정 [#basic-setup]

### Redis 활성화 [#enable-redis]

LibreChat에서 Redis를 활성화하려면 `.env` 파일에 다음 환경 변수를 설정하세요:

```bash
USE_REDIS=true
```

**중요**: `USE_REDIS=true`로 설정할 경우, `REDIS_URI`도 반드시 제공해야 합니다. 연결 URI 없이 Redis를 활성화하면 애플리케이션에서 오류가 발생합니다.

## 연결 유형 [#connection-types]

### 단일 Redis 인스턴스 [#single-redis-instance]

표준 단일 Redis 서버 설정의 경우:

```bash
# Local Redis instance
REDIS_URI=redis://127.0.0.1:6379

# Remote Redis instance
REDIS_URI=redis://your-redis-host:6379
```

### Redis Cluster [#redis-cluster]

여러 노드를 사용하는 Redis 클러스터 배포의 경우:

```bash
# Multiple Redis cluster nodes
REDIS_URI=redis://127.0.0.1:7001,redis://127.0.0.1:7002,redis://127.0.0.1:7003
```

여러 개의 URI가 제공되면 애플리케이션이 자동으로 클러스터 모드를 감지합니다.

Redis 클러스터의 URI가 하나뿐인 경우, `USE_REDIS_CLUSTER` 환경 변수를 사용하여 클러스터 모드를 활성화할 수 있습니다:

```bash
# Redis cluster with single URI
REDIS_URI=redis://127.0.0.1:7001
USE_REDIS_CLUSTER=true
```

### 단일 엔드포인트 관리형 Redis 서비스 [#single-endpoint-managed-redis-services]

AWS ElastiCache Serverless 및 AWS의 Redis Enterprise Cloud를 포함한 일부 관리형 Redis 서비스는 내부적으로 키를 샤딩(sharding)하면서 단일 연결 endpoint를 노출합니다. 이러한 설정에서는 LibreChat을 단일 노드 연결 모드로 유지하되, 캐시 삭제 시 `CROSSSLOT Keys in request don't hash to the same slot` 오류가 발생하면 클러스터 안전 삭제(cluster-safe deletes) 기능을 활성화하십시오.

```bash
USE_REDIS=true
REDIS_URI=rediss://your-managed-redis-endpoint:6379
USE_REDIS_CLUSTER=false
REDIS_CLUSTER_SAFE_DELETE=true
```

`REDIS_CLUSTER_SAFE_DELETE=true`는 LibreChat이 다중 키 `DEL` 명령을 보내는 대신 일치하는 캐시 키를 하나씩 삭제하도록 합니다. 이는 LibreChat이 Redis에 연결하는 방식을 변경하지 않고도 `CROSSSLOT` 오류를 방지합니다.

LibreChat이 Redis Cluster 클라이언트를 생성해야 하는 경우에만 `USE_REDIS_CLUSTER=true`를 사용하세요. 단일 엔드포인트 관리형 서비스의 경우 `REDIS_CLUSTER_SAFE_DELETE=true`가 더 안전한 옵션입니다.

### TLS/SSL을 사용하는 Redis [#redis-with-tlsssl]

보안 Redis 연결의 경우:

```bash
# Redis with TLS encryption
REDIS_URI=rediss://127.0.0.1:6380

# Path to CA certificate for TLS verification
REDIS_CA=/path/to/ca-cert.pem
```

## 보안 구성 [#security-configuration]

### 인증 [#authentication]

Redis 인증 자격 증명 구성:

```bash
# Method 1: Include credentials in URI
# With both username and password
REDIS_URI=redis://myuser:mypassword@127.0.0.1:6379


# Method 2: Separate environment variables
REDIS_URI=redis://127.0.0.1:6379
REDIS_USERNAME=your_redis_username
REDIS_PASSWORD=your_redis_password
```

**참고**: `REDIS_URI`에 포함된 자격 증명이 우선합니다. `REDIS_USERNAME`과 `REDIS_PASSWORD`는 URI에 사용자 이름이나 비밀번호가 없는 경우에만 대체값으로 사용됩니다.

### TLS 구성 [#tls-configuration]

암호화된 연결의 경우:

```bash
# Enable TLS with rediss:// protocol
REDIS_URI=rediss://your-redis-host:6380

# Provide CA certificate for verification
REDIS_CA=/path/to/your/ca-certificate.pem
```

### Elasticache를 사용한 TLS [#tls-with-elasticache]

Elasticache는 TLS 연결을 위해 대체 dnsLookup을 사용해야 할 수도 있습니다. 이 웹페이지의 "Special Note: Aws Elasticache Clusters with TLS" 섹션을 참조하세요: https://www.npmjs.com/package/ioredis

```bash
# Enable redis alternate dnsLookup
REDIS_USE_ALTERNATIVE_DNS_LOOKUP=true
```

## 고급 옵션 [#advanced-options]

### Key Prefixing [#key-prefixing]

Redis key prefixing은 동일한 Redis 서버를 공유하는 서로 다른 환경, 버전 또는 인스턴스 간의 캐시 데이터를 격리하여 배포 간 오염을 방지합니다. 이는 다음 사항에 필수적입니다:

- **Multi-tenant deployments**: 스테이징, 프로덕션 및 개발 환경 분리
- **Blue-green deployments**: 서로 다른 애플리케이션 버전 간의 캐시를 격리합니다.

```bash
# Option 1: Dynamic prefix from environment variable (recommended for cloud)

# Google Cloud Platform - Cloud Run
REDIS_KEY_PREFIX_VAR=K_REVISION

# AWS - ECS/Fargate
REDIS_KEY_PREFIX_VAR=AWS_EXECUTION_ENV

# Azure Container Instances
REDIS_KEY_PREFIX_VAR=CONTAINER_NAME

# Kubernetes - Pod name or deployment
REDIS_KEY_PREFIX_VAR=HOSTNAME
REDIS_KEY_PREFIX_VAR=POD_NAME

# Kubernetes - Custom deployment identifier
REDIS_KEY_PREFIX_VAR=DEPLOYMENT_ID

# Heroku
REDIS_KEY_PREFIX_VAR=DYNO

# Option 2: Static prefix (for manual control)
REDIS_KEY_PREFIX=librechat-prod-v2
REDIS_KEY_PREFIX=staging-branch-feature-x
REDIS_KEY_PREFIX=dev-john-local
```

**중요**: `REDIS_KEY_PREFIX_VAR`와 `REDIS_KEY_PREFIX`를 동시에 설정할 수 없습니다.

**접두사 없이 오염된 예시**:

- 스테이징 배포에 의해 프로덕션 캐시가 덮어쓰여졌습니다
- 기능 브랜치 테스트가 메인 브랜치 캐시를 손상시킴
- 오래된 배포 버전이 캐시된 구식 데이터를 제공함

**키 접두사 형식**:

- IoRedis 클라이언트: `{prefix}::{key}`
- Keyv client: 스토어 계층에서 처리됨

### 연결 제한 [#connection-limits]

Redis 연결 제한 구성:

```bash
# Maximum number of event listeners (default: 40)
REDIS_MAX_LISTENERS=40
```

### Connection Keep-Alive [#connection-keep-alive]

기한이 제한된 Redis 하트비트 및 TCP keepalive 구성:

```bash
# Redis ping interval in seconds (default: 0 = disabled)
# When set to a positive integer (in seconds), Redis clients will ping the server at this interval
# When unset or 0, no pinging is performed (recommended for most use cases)
# Example: 300 = ping every 5 minutes
REDIS_PING_INTERVAL=300

# Maximum time an enabled heartbeat PING may go unanswered (default: 5000 ms)
REDIS_PING_TIMEOUT=5000

# Dedicated pub/sub subscriber heartbeat (default: 15 seconds, 0 = disabled)
REDIS_SUBSCRIBER_PING_INTERVAL=15

# TCP keepalive idle delay for ioredis sockets (default: 10000 ms, 0 = kernel default)
REDIS_KEEP_ALIVE=10000
```

**중요**:

- `REDIS_PING_INTERVAL=0`으로 설정하거나 생략하면 핑(ping) 기능이 완전히 비활성화됩니다.
- 연결 시간 초과 문제가 발생하는 경우에만 양수 값(초 단위)을 설정하세요.
- `REDIS_PING_INTERVAL`은 초 단위로 지정되며, 선택적인 메인 ioredis 하트비트를 제어합니다.
- 전용 pub/sub 구독자는 유휴 상태의 데드 소켓이 감지되지 않을 수 있으므로 자체적인 기본 활성화 간격을 사용합니다. 이 하트비트를 비활성화하려면 `REDIS_SUBSCRIBER_PING_INTERVAL=0`으로 설정하세요.
- 활성화된 모든 하트비트는 응답 기한으로 `REDIS_PING_TIMEOUT`을 사용하며, PING에 대한 응답이 없을 경우 소켓을 재연결합니다.
- `REDIS_KEEP_ALIVE`는 애플리케이션 수준의 PING과는 독립적으로 ioredis TCP 소켓을 구성합니다.
- 예시 값: `300` (5분), `600` (10분), `60` (1분)

### 복제본 장애 조치 복구 (Replica Failover Recovery) [#replica-failover-recovery]

Sentinel 장애 조치(failover) 중에 강등된 Redis 복제본은 기존 소켓을 열어둔 상태에서 `READONLY`로 쓰기 요청을 거부할 수 있습니다. LibreChat은 비클러스터 Keyv 클라이언트에서 이러한 응답을 감지하면, 오래된 연결을 끊고 재연결을 수행하여 애플리케이션을 재시작하지 않고도 현재 기본(primary) 노드를 확인할 수 있도록 합니다.

```bash
# Minimum interval between forced recovery attempts, in milliseconds
# Default: 5000
REDIS_READONLY_RECOVERY_INTERVAL=5000
```

이 간격은 쓰기 실패가 급증하는 동안 재연결 시도를 디바운스(debounce)합니다. Redis Cluster 클라이언트는 네이티브 클러스터 토폴로지 및 리다이렉트 처리를 사용하므로 제외됩니다.

### 헬스 체크 [#health-checks]

LibreChat는 세 개의 프로브 엔드포인트를 제공합니다. `/readyz`만 Redis 상태를 반영합니다:

| 엔드포인트 | `200 OK` 반환 조건 | `503 NOT_READY` 반환 조건 |
| --- | --- | --- |
| `/livez` | 프로세스가 요청을 처리하고 있는 경우 언제나 | 해당 없음 |
| `/health` | 프로세스가 요청을 처리하고 있는 경우 언제나 | 해당 없음 |
| `/readyz` | 시작 절차가 완료된 후, 그리고 `USE_REDIS=true`인 경우 Redis가 연결되어 있는 동안 | 시작 절차가 완료되기 전이거나, Redis가 활성화되어 있으나 연결이 끊어진 상태인 경우 |

Redis가 재시작되거나 장애 조치(failover)가 발생하거나, 클라이언트의 재시도 기간보다 오랫동안 연결할 수 없게 되면, Redis에 의존하는 요청(로그인, 세션, 속도 제한)은 연결이 복구될 때까지 실패합니다. 이 기간 동안 `/readyz`는 `503`을 응답하므로, 로드 밸런서나 Kubernetes readiness probe는 해당 인스턴스로 트래픽을 보내지 않습니다. Redis가 다시 연결되면 재시작 없이 `200`으로 돌아갑니다. Redis가 활성화된 경우 모든 Redis 클라이언트가 연결되어 있어야 하며, Redis Cluster의 경우 모든 primary 노드가 여기에 포함됩니다.

readiness 확인은 `/readyz`를, liveness 확인은 `/livez`를 가리키도록 설정하세요. liveness 확인에는 Redis를 포함하지 마세요. Redis 장애 중에 liveness 프로브가 실패하면 모든 파드가 동시에 재시작되며, 이 과정으로는 Redis를 복구할 수 없습니다.

```yaml
livenessProbe:
  httpGet:
    path: /livez
    port: 3080
readinessProbe:
  httpGet:
    path: /readyz
    port: 3080
  periodSeconds: 10
  failureThreshold: 3
```

`/readyz`는 짧은 재연결을 자체적으로 기다려주지 않으므로, 트래픽을 차단하기 전까지 장애가 얼마나 지속되어야 하는지는 `failureThreshold`를 사용해 결정하세요.

### 선택적 인메모리 캐싱 [#selective-in-memory-caching]

Redis가 활성화된 경우에도 특정 캐시 네임스페이스가 인메모리 스토리지를 사용하도록 강제합니다:

```bash
# Comma-separated list of cache keys
FORCED_IN_MEMORY_CACHE_NAMESPACES=CONFIG_STORE,APP_CONFIG,ROLES
```

기본값이 설정되지 않은 경우 `CONFIG_STORE,APP_CONFIG`이며, 이에 따라 `librechat.yaml`에서 파생된 구성은 컨테이너별로 유지됩니다. 이 변수를 설정하면 기본값에 추가되는 것이 아니라 기본값을 **대체**하므로, 해당 네임스페이스를 Redis에 저장하지 않으려면 목록에 `CONFIG_STORE,APP_CONFIG`을 포함하세요. 모든 네임스페이스를 Redis를 통해 라우팅하려면 빈 문자열로 설정하세요.

유효한 캐시 키 (`librechat-data-provider`의 `CacheKeys` enum에서 가져옴):

| Key | Description |
| --- | --- |
| `CONFIG_STORE` | 구성 저장소 |
| `TOOL_CACHE` | 도구 캐시 (플러그인, MCP 도구, 도구 정의) |
| `ROLES` | 사용자 역할 |
| `USER_PRINCIPALS` | ACL 주체를 확인하는 데 사용되는 그룹 멤버십 |
| `PROMPT_GROUPS_ACCESS` | 프롬프트 그룹 액세스 ID 집합 |
| `AGENT_LINKED_INSTRUCTIONS` | 에이전트에 연결된 프롬프트 그룹의 확인된 지침 |
| `SANDBOX_PREWARM` | 대화별 코드 샌드박스 사전 워밍 상태 |
| `GEN_TITLE` | 생성된 제목 |
| `TOOLS` | 도구 데이터 |
| `MODELS_CONFIG` | 모델 구성 |
| `MODEL_QUERIES` | 모델 쿼리 |
| `STARTUP_CONFIG` | 시작 구성 |
| `ENDPOINT_CONFIG` | 엔드포인트 구성 |
| `TOKEN_CONFIG` | 토큰 구성 |
| `REASONING_CAPABILITIES` | OpenRouter 엔드포인트의 모델별 추론 노력 수준 |
| `PULL_REQUESTS` | 풀 리퀘스트 조회 및 GitHub 속도 제한 쿨다운 |
| `APP_CONFIG` | 애플리케이션 구성 |
| `ABORT_KEYS` | 중단 키 |
| `BANS` | 차단 데이터 |
| `ENCODED_DOMAINS` | 인코딩된 도메인 |
| `AUDIO_RUNS` | 오디오 처리 실행 |
| `MESSAGES` | 진행 중인 메시지 |
| `FLOWS` | 진행 중인 플로우 상태 |
| `PENDING_REQ` | 대기 중인 요청 |

## 성능 튜닝 [#performance-tuning]

### Connection Keep-Alive [#connection-keep-alive-1]

이 애플리케이션은 구성 가능한 연결 유지(keep-alive) 기능을 구현합니다:

- Main-client PING은 `REDIS_PING_INTERVAL`에 의해 제어되며 기본적으로 비활성화되어 있습니다.
- 전용 구독자 PING은 `REDIS_SUBSCRIBER_PING_INTERVAL`에 의해 제어되며 기본값은 15초입니다.
- Heartbeats는 `REDIS_PING_TIMEOUT`을 사용하여 조용히 끊긴 소켓을 감지하고 강제로 재연결합니다.
- TCP keepalive는 애플리케이션 수준의 하트비트와 독립적으로 `REDIS_KEEP_ALIVE`를 사용합니다.
- 연결 해제 또는 닫기 이벤트 발생 시 Heartbeat 타이머가 초기화됩니다.

### 캐시 전략 [#cache-strategy]

이 애플리케이션은 이중 클라이언트 방식을 사용합니다:

- **IoRedis client**: 자동 접두사(prefixing)가 포함된 기본 Redis 작업
- **Keyv Redis client**: `cacheFactory.js` 내 접두사(prefix) 처리를 포함한 저장소 계층 작업

### 고급 연결 튜닝 [#advanced-connection-tuning]

이 선택 사항인 변수들은 연결 동작과 대량 캐시 작업을 조정합니다. 대부분의 배포 환경에서는 기본값이 적합합니다.

| 변수 | 기본값 | 설명 |
| --- | --- | --- |
| `REDIS_CONNECT_TIMEOUT` | `10000` | 연결 시간 초과(밀리초)입니다. |
| `REDIS_RETRY_MAX_ATTEMPTS` | `10` | 포기하기 전까지의 최대 재연결 시도 횟수입니다. `0`으로 설정하면 무기한 재시도합니다. |
| `REDIS_RETRY_MAX_DELAY` | `3000` | 재연결 시도 사이의 최대 지연 시간(밀리초)입니다. |
| `REDIS_ENABLE_OFFLINE_QUEUE` | `true` | 연결이 끊긴 동안 명령을 큐에 저장합니다. `false`로 설정하면 명령이 즉시 실패합니다. |
| `REDIS_SCAN_COUNT` | `1000` | 패턴으로 키를 찾을 때 `SCAN` 작업에 사용되는 `COUNT` 힌트입니다. |
| `REDIS_DELETE_CHUNK_SIZE` | `1000` | 대량 삭제 시 배치당 삭제되는 키의 개수입니다. |
| `MCP_REGISTRY_CACHE_TTL` | `5000` | MCP 레지스트리 캐시가 유지되는 시간(밀리초)입니다. 인스턴스 간 데이터 불일치는 이 값의 두 배까지 발생할 수 있습니다. `0`으로 설정하면 로컬 스냅샷이 비활성화되며, 모든 읽기 요청이 Redis로 전달됩니다. |

### 메모리 최적화 [#memory-optimization]

`FORCED_IN_MEMORY_CACHE_NAMESPACES`를 사용하여 자주 액세스하는 작은 데이터 세트는 메모리에 유지하고, 더 큰 캐시에는 Redis를 사용하여 성능을 최적화하세요.

## 재개 가능한 스트림 (Resumable Streams) [#resumable-streams]

Redis는 수평적으로 확장된 배포를 위해 [Resumable Streams](/docs/features/resumable_streams) 기능을 활성화합니다. 이 기능이 활성화되면, AI 응답이 서버 인스턴스 간에 원활하게 재연결되고 재개될 수 있습니다.

**중요:** `USE_REDIS=true`일 때, 재개 가능한 스트림은 인스턴스 간 조정을 위해 자동으로 Redis를 사용합니다. 이는 사용자가 서로 다른 서버 인스턴스에 연결될 수 있는 수평적 확장 배포 환경에서 권장되는 설정입니다.

**참고:** LibreChat 인스턴스를 하나만 실행하는 경우, 재개 가능한 스트림을 위한 Redis는 일반적으로 과도합니다. 내장된 인메모리 모드로도 충분히 잘 작동합니다. Redis는 여러 개의 LibreChat 인스턴스가 로드 밸런서 뒤에서 실행될 때 필수적이 되는데, 이 경우 사용자가 다시 연결할 때 스트림이 시작된 서버가 아닌 다른 서버에 연결될 수 있기 때문입니다.

### 구성 [#configuration]

```bash
# Redis enabled = resumable streams automatically use Redis
USE_REDIS=true
REDIS_URI=redis://127.0.0.1:6379

# Optional: explicitly control resumable streams behavior
# USE_REDIS_STREAMS=true  # Enabled by default when USE_REDIS=true
```

### Generation Protocol Compatibility [#generation-protocol-compatibility]

현재 LibreChat 클라이언트는 모든 내장 생성 저장소와 자동으로 생성 프로토콜 v2를 협상합니다. 별도의 배포 설정은 필요하지 않습니다. 명시적 또는 저장된 protocol-v1 마커가 있는 기존 생성물은 완료될 때까지 스티어링(steering), 일시 중지/재개, 재시도 및 복구 과정을 통해 변경 불가능한 v1 동작을 유지합니다.

롤링 업그레이드를 수행하려면, 실행 중인 모든 API 및 워커 이미지에 v2 호환성 브리지가 포함되어야 합니다:

- 모든 API 및 워커 이미지는 LibreChat `v0.8.8-rc1` 이상을 실행합니다.
- Helm chart `2.0.8` 이상 버전은 호환되는 기본 이미지를 선택합니다. 사용자 지정 이미지 재정의는 여전히 위의 이미지 요구 사항을 충족해야 합니다.

이전 릴리스에서 업그레이드할 때는 콜드 핸드오프(cold handoff)를 수행하십시오. 새 이미지를 시작하기 전에 모든 이전 API 및 워커 복제본을 중지해야 합니다. 이는 v2 이전 버전과 자동 v2 바이너리가 Redis에서 생성 상태를 공유하는 것을 방지합니다.

<Callout type="warning" title="롤링 배포 안전성">
  현재 복제본과 동일한 Redis 생성 상태에서 `v0.8.8-rc1`보다 이전 릴리스를 실행하지 마십시오. 해당 호환성 하한선 아래로 롤백하기 전에, 먼저 현재 복제본과 protocol-v2 세대가 모두 비워졌는지(drained) 확인하십시오.
</Callout>

In-memory generation streams는 프로토콜 v2를 자동으로 협상하며 프로세스 간에 생성 상태를 공유하지 않습니다.

### Stream Delta Coalescing [#stream-delta-coalescing]

Redis 기반 스트림은 델타 게시를 일괄 처리하여 높은 토큰 속도에서 Redis 스크립트, 왕복(round trip) 및 CPU 사용량을 줄일 수 있습니다:

```bash filename=".env"
STREAM_DELTA_COALESCE_MS=25
```

이 설정은 지정되지 않은 경우 기본값이 `25` 밀리초입니다. 병합(coalescing)을 비활성화하려면 명시적으로 `0`으로 설정하십시오. `1000`을 초과하는 값은 제한됩니다. 일괄 처리는 구성된 전달 지연 시간만큼의 윈도우를 추가할 수 있으며, 게시 프로세스가 플러시(flush)되기 전에 종료될 경우 버퍼링된 마지막 데이터가 손실될 수 있습니다. 개별 청크 프레임은 프로토콜 호환성을 위해 유지되므로, 이 설정은 구독자 프레임 형식을 변경하지 않고 Redis 스크립트 및 왕복(round-trip) 작업을 줄여줍니다. 메모리 내 생성 스트림은 변경되지 않습니다.

### 주요 이점 (수평적 확장을 위한) [#key-benefits-for-horizontal-scaling]

- **인스턴스 간 연속성**: 사용자가 한 서버에서 생성을 시작하고 다른 서버에서 이어서 진행할 수 있습니다.
- **롤링 배포**: 서버 재시작 시에도 활성 스트림이 유지됨
- **Multi-tab sync**: 로드 밸런싱 환경에서 동일한 대화가 여러 브라우저 탭 간에 동기화됩니다.
- **연결 복원력**: 요청을 처리하는 서버와 관계없이 자동 재연결

### 클러스터 구성 [#cluster-configuration]

Redis Cluster 배포의 경우, LibreChat은 스트림 작업이 동일한 클러스터 슬롯 내에서 유지되도록 자동으로 해시 태그가 지정된 키를 사용합니다:

```bash
USE_REDIS=true
USE_REDIS_STREAMS=true
USE_REDIS_CLUSTER=true
REDIS_URI=redis://node1:7001,redis://node2:7002,redis://node3:7003
```

이 기능에 대한 자세한 내용은 [Resumable Streams](/docs/features/resumable_streams)를 참조하세요.

## MCP Catalog Coordination [#mcp-catalog-coordination]

Redis가 활성화되면 LibreChat은 복제본 간에 애플리케이션 수준의 MCP 도구 카탈로그를 조정합니다. 시작 시 게시, 재연결 동기화 및 `notifications/tools/list_changed` 업데이트는 생성 및 수정 마커를 사용하여 오래된 복제본이 더 최신 카탈로그를 덮어쓰지 않도록 합니다.

Redis 클러스터 배포에서는 슬롯 안전 카탈로그 키와 업데이트 작업을 사용하며, 별도의 MCP Redis 설정은 필요하지 않습니다. 동적 카탈로그 및 OAuth 준비 상태 동작에 대해서는 [MCP 서버 관리](/docs/configuration/librechat_yaml/object_structure/mcp_servers#additional-information)를 참조하세요.
