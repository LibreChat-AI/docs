`.env` 파일을 사용하여 애플리케이션 환경을 구성하기 위한 종합 가이드에 오신 것을 환영합니다. 이 문서는 다양한 상황에서 애플리케이션의 동작을 결정하는 환경 변수를 이해하고 사용자 지정하기 위한 원스톱 리소스입니다.

기본 설정만으로도 표준 `docker` 설치를 위한 탄탄한 기반을 제공하지만, 이 가이드를 자세히 살펴보면 LibreChat의 잠재력을 완전히 끌어낼 수 있습니다. 이 가이드를 통해 귀하의 필요에 맞춰 LibreChat을 조정할 수 있습니다. 언어 모델 가용성을 조정하고, 소셜 로그인을 통합하며, 자동 조정 시스템을 관리하는 등 다양한 방법을 알아보세요. 이 모든 것은 최적의 사용자 경험을 위해 LibreChat을 세밀하게 조정할 수 있는 제어 권한을 제공하기 위함입니다.

> **알림: 구성 변경 사항을 적용하려면 LibreChat을 다시 시작해 주세요.**

또는, LibreChat의 메인 `docker-compose.yml` 파일과 동일한 디렉토리에 `docker-compose.override.yml`이라는 새 파일을 생성할 수 있습니다. 이 파일에서 `environment` 아래에 필요한 .env 변수를 설정하거나, 전체 파일을 직접 수정하거나 복제할 필요 없이 메인 `docker-compose.yml`에서 제공하는 기본 구성을 수정할 수 있습니다.

  - **[docker docs - merge-compose-files](https://docs.docker.com/compose/how-tos/multiple-compose-files/merge/)**

- LibreChat 폴더 및 GitHub에서 LibreChat을 위한 오버라이드 파일 예시를 확인할 수도 있습니다:

## 서버 구성 [#server-configuration]

### 포트 [#port]

- 서버는 특정 포트에서 수신 대기합니다.
- `PORT` 환경 변수는 서버가 수신 대기할 포트를 설정합니다. 기본값은 `3080`으로 설정되어 있습니다.

### HTTP 서버 타임아웃 [#http-server-timeouts]

이 선택적 값들은 Node.js HTTP 서버를 구성합니다. Node의 기본값을 유지하려면 설정하지 않은 상태로 두십시오. `0`으로 설정하면 해당 타임아웃이 비활성화됩니다.

값은 음수가 아닌 안전한 정수여야 하며, 유효하지 않은 값은 무시됩니다. 헤더 타임아웃과 요청 타임아웃이 모두 활성화된 경우, LibreChat은 헤더 타임아웃이 요청 타임아웃보다 높으면 이를 요청 타임아웃 값으로 제한합니다. Node는 30초마다 연결을 스윕(sweep)하여 헤더 및 요청 만료를 확인하므로, `30000` 미만의 값은 정확한 밀리초 단위로 강제되지 않습니다. Bun은 현재 이러한 설정을 허용하지만 강제하지는 않으며, API 서버가 Bun에서 실행될 때 LibreChat은 경고를 로그에 기록합니다.

### Trust proxy [#trust-proxy]

Express 애플리케이션으로부터 최대 n개의 홉(hop) 거리에 있는 주소를 사용합니다.
req.socket.remoteAddress는 첫 번째 홉이며, 나머지는 X-Forwarded-For 헤더에서 오른쪽에서 왼쪽으로 탐색합니다.
값이 0이면 첫 번째 신뢰할 수 없는 주소가 req.socket.remoteAddress가 됨을 의미하며, 즉 리버스 프록시가 없음을 뜻합니다.
`TRUST_PROXY` 환경 변수의 기본값은 `1`로 설정되어 있습니다.

이에 대한 자세한 내용은 [Express.js - trust proxy](https://expressjs.com/en/guide/behind-proxies.html)를 참조하세요.

### Trusted Tenant Header [#trusted-tenant-header]

`TRUST_TENANT_HEADER`는 LibreChat이 `/oauth`, `/api/auth` 및 `/api/share` 경로 트리에서 인증 전에 `X-Tenant-Id`를 허용할지 여부를 제어합니다. 기본적으로 비활성화되어 있으며, 비활성화된 상태에서는 해당 경로들이 헤더를 무시합니다.

  신뢰할 수 있는 리버스 프록시가 모든 수신 `X-Tenant-Id` 값을 제거하고 권한 있는 테넌트 ID를 직접 설정하는 경우에만 이 설정을 활성화하십시오. 그렇지 않으면, 인증 전에 신뢰할 수 없는 클라이언트가 사용될 테넌트 컨텍스트를 선택할 수 있습니다. 이 설정이 활성화되면 LibreChat은 보안 경고를 기록합니다.
</Callout>

`TENANT_ISOLATION_STRICT`가 활성화되어 있지만 `TRUST_TENANT_HEADER`가 비활성화된 경우, LibreChat은 시작 시 사전 인증 테넌트 헤더가 무시된다는 경고를 표시합니다.

### 자격 증명(Credentials) 구성 [#credentials-configuration]

LibreChat은 데이터베이스에 저장된 지원되는 자격 증명을 암호화하기 위해 `CREDS_KEY`와 `CREDS_IV`를 사용합니다. 프로덕션 환경을 위해 고정된 고유 값을 구성하고 모든 복제본에서 동일한 값을 공유하십시오.

      'CREDS_KEY=',

`CREDS_KEY`, `CREDS_IV`, `JWT_SECRET` 또는 `JWT_REFRESH_SECRET` 중 하나라도 비어 있으면, LibreChat은 먼저 임시 자격 증명 파일에서 유효한 값을 재사용합니다. 만약 존재하는 값이 없다면, 암호학적으로 무작위인 값을 생성하고 소유자 전용 권한으로 파일을 작성합니다. 명시적인 환경 변수 값이 항상 우선합니다. LibreChat은 `.env` 또는 `.env.example`을 생성된 파일 경로로 사용하는 것을 거부하며, 이는 두 설정 파일 중 하나가 실수로 교체되는 것을 방지합니다.

LibreChat은 `JWT_SECRET` 또는 `JWT_REFRESH_SECRET`이 여전히 폐기된 기본 공개 값을 사용하는 경우, 해당 값이 환경 변수에서 오든 임시 자격 증명 파일에서 오든 관계없이 시작을 거부합니다. 배포 시 오래된 샘플 시크릿을 그대로 사용하지 말고 고유한 값으로 교체하십시오.

번들로 제공되는 Docker Compose 파일은 `/app/data/.env.temp`를 `librechat-data` 볼륨에 유지하므로, 단일 Compose 배포는 이러한 생성된 값을 변경하지 않고 재시작할 수 있습니다. 파일이 유지되지 않으면 값은 프로세스 로컬로 처리되며, 재시작 후 세션이나 암호화된 레코드에 액세스할 수 없게 될 수 있습니다.

<Callout type="warning" title="프로덕션을 위한 영구 값 설정">
  임시 생성은 부트스트랩 편의를 위한 것이며, 자격 증명 교체 시스템이 아닙니다. 프로덕션 환경에서 사용하기 전에 [Credentials Generator](/toolkit/creds_generator)를 사용하여 영구적인 값을 생성하고, 이를 비밀 관리자(secret manager)에 저장한 다음, 모든 복제본에 동일한 값을 제공하십시오. 설정된 키를 변경해도 기존 레코드가 다시 암호화되지는 않습니다. LibreChat은 데이터베이스에 자격 증명 지문을 기록하며 활성 값이 변경될 때 경고를 표시합니다. 제어된 마이그레이션을 수행하는 대신 해당 마커를 덮어쓰지 마십시오.
</Callout>

### 보안 헤더 및 콘텐츠 보안 정책 (Content Security Policy) [#security-headers-and-content-security-policy]

LibreChat은 기본적으로 기준이 되는 HSTS, framing, content-type, opener, resource 및 referrer 헤더를 전송합니다. `SECURITY_HEADERS=false`는 이 모든 헤더를 비활성화하며, 전역 CSP 킬 스위치 역할도 합니다.

Nonce 기반 CSP는 `CSP_ENABLED=true`를 통해 별도로 선택할 수 있으며 기본적으로 보고 전용(report-only) 모드로 설정됩니다. `CSP_REPORT_ONLY=true`로 시작하여 위반 사항을 검사하고, 적용하기 전에 배포에 필요한 오리진만 추가하십시오. CSP가 활성화되면 SPA 셸은 항상 `Cache-Control: no-store`와 함께 전송되므로, 응답별 nonce가 캐시에서 재사용될 수 없습니다.

모든 기준 및 CSP 변수, 허용되는 값, 기본값, 소스 목록 재정의, 그리고 롤아웃 지침에 대해서는 [HTTP Security Headers](/docs/configuration/security_headers)를 참조하세요.

**동작:**

정적 파일에 대한 [Cache-Control](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Cache-Control) 헤더를 설정합니다. 이 구성은 `NODE_ENV`가 `production`으로 설정된 경우에만 트리거됩니다.

- `STATIC_CACHE_MAX_AGE`의 주석을 해제하여 정적 파일에 대한 로컬 `max-age`를 변경할 수 있습니다. 기본값은 2일(172800초)로 설정되어 있습니다.
- `STATIC_CACHE_S_MAX_AGE`의 주석을 해제하여 공유 캐시(CDN 및 프록시)에 대한 `s-maxage`를 설정하세요. 기본값은 1일(86400초)로 설정되어 있습니다.
- `DISABLE_COMPRESSION`의 주석을 해제하면 정적 파일에 대한 압축을 비활성화할 수 있습니다. 기본적으로 압축은 활성화되어 있습니다.
- `ENABLE_IMAGE_OUTPUT_GZIP_SCAN`의 주석을 해제하면 동일한 폴더 내에 동일한 이름과 .gz 확장자로 미리 압축된 이미지가 있을 경우, 해당 gzip 버전의 이미지를 스캔하고 제공할 수 있습니다. 기본적으로 업로드된 이미지에 대한 gzip 스캔은 비활성화되어 있습니다.
- `ENABLE_STATIC_ASSET_BROTLI`의 주석을 해제하면 존재하는 경우 사전 압축된 `.br` 버전의 정적 앱 에셋을 제공합니다. 활성화되면 API를 통해 제공되는 정적 파일에 대해 gzip보다 Brotli가 우선적으로 사용됩니다.

<Callout type="warning" title="경고">
  - 이는 API 서버에서 제공되는 정적 파일에만 영향을 미치며, _Firebase_, _NGINX_ 또는 기타 다른 구성에는 적용되지 않습니다.
</Callout>

### 공개 검색 엔진의 인덱싱 방지 [#prevent-public-search-engines-indexing]

기본적으로 귀하의 웹사이트는 공개 검색 엔진(예: Google, Bing 등)에 의해 색인되지 않습니다. 이는 사람들이 이러한 검색 엔진을 통해 귀하의 웹사이트를 찾을 수 없음을 의미합니다. 웹사이트의 가시성을 높이고 검색 가능하게 만들고 싶다면, 다음 설정을 `false`로 변경할 수 있습니다.

  ]}

❗**참고:** 이 방법이 모든 검색 엔진에서 작동한다고 보장할 수는 없으며, 일부 검색 엔진은 캐싱이나 아카이빙과 같은 다른 목적으로 귀하의 웹사이트나 웹 페이지를 여전히 색인화할 수 있습니다. 따라서 웹사이트나 웹 페이지의 민감하거나 기밀인 정보를 보호하기 위해 이 방법만 전적으로 의존해서는 안 됩니다.

### Uncaught Exception Handling [#uncaught-exception-handling]

기본적으로 LibreChat은 처리되지 않은 예외가 발생하면 프로세스를 종료하며, 이는 표준 Node.js 동작 방식입니다. 처리되지 않은 예외 발생 후에도 앱이 계속 실행되도록 이 설정을 재정의할 수 있습니다.

</Callout>

`FILE_UPLOAD_SSE_ENABLED=true`를 설정하면, `text/event-stream`을 요청하는 클라이언트는 업로드 처리가 진행되는 동안 1초 간격의 하트비트 이벤트를 수신하며, 이후 `data` 또는 `error` 이벤트와 최종 `close` 이벤트가 이어집니다. SSE를 요청하지 않는 클라이언트는 기존과 동일한 JSON 응답을 계속 수신합니다. 이는 OCR, 파싱 또는 RAG 작업이 길어질 때 리버스 프록시가 유휴 연결을 종료하는 상황을 방지하는 데 유용합니다.

원격 가져오기(remote fetch) 제어는 LibreChat이 HTTP 또는 HTTPS 파일 URL을 로컬, Firebase, Azure 또는 S3/CloudFront 스토리지로 수집할 때 적용됩니다. LibreChat은 선언된 `Content-Length`와 실제로 스트리밍된 바이트를 모두 확인하므로, 원격 서버가 길이를 생략하거나 잘못 기재하더라도 제한이 적용됩니다. 이러한 제어는 [`fileConfig`](/docs/configuration/librechat_yaml/object_structure/file_config)의 업로드당 제한과는 독립적입니다.

### Stateful Code Interpreter Endpoint [#stateful-code-interpreter-endpoint]

[`stateful_code_sessions`](/docs/configuration/librechat_yaml/object_structure/agents#capabilities)는 매우 실험적인 기능이며 별도의 Code Interpreter 경로가 필요합니다. `LIBRECHAT_CODE_BASEURL_STATEFUL`을 사용하여 기본 경로를 구성하거나, [`endpoints.agents.statefulCodeSessions.environments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions) 아래에 명명된 관리형 또는 연결된 백엔드를 정의하세요. 선택된 서비스는 `stateful` 프로필을 실행해야 합니다. LibreChat은 상태 저장 요청과 함께 `X-CodeAPI-Expected-Profile: stateful`을 전송합니다.

Stateful 요청은 절대 `LIBRECHAT_CODE_BASEURL`로 대체(fallback)되지 않습니다. 선택한 명명된 환경을 사용할 수 없거나, 명명된 기본값 또는 `LIBRECHAT_CODE_BASEURL_STATEFUL`이 구성되어 있지 않은 경우, LibreChat은 구성 오류와 함께 Agent 실행을 중단합니다. Stateless Agent는 계속해서 `LIBRECHAT_CODE_BASEURL`을 사용하며, 두 실행 프로필은 라이브 작업 공간을 공유하지 않습니다.

각 Agent는 상태 저장 작업 공간(stateful workspace)의 범위를 로그인한 사용자, 사용자 및 Agent, 또는 사용자 및 대화로 지정할 수 있습니다. 설정 및 지속성 제한 사항에 대해서는 [Stateful Code Sessions](/docs/features/code_interpreter#stateful-code-sessions)을 참조하세요.

이름이 지정된 연결된 환경(Named attached environments)은 `pairing.allowPrincipalWorkers: true`를 통해 셀프 서비스 페어링 제어 평면을 노출할 수도 있습니다. 권한이 있는 사용자는 **Settings > Code environments**에서 해당 소유자 바인딩 워커를 관리합니다. 페어링 전용 항목은 `LIBRECHAT_CODE_BASEURL_STATEFUL`을 대체하지 않으며 배포 기본값으로 사용될 수 없습니다.

모든 공유 링크 읽기는 인증 없이 접근할 수 있으므로 IP 버킷을 사용합니다. 로그인한 뷰어는 사용자 버킷도 사용합니다. 두 제한 중 하나를 초과하면 HTTP 429가 반환되며, 0이 아닌 `SHARE_VIOLATION_SCORE`가 기존 위반 시스템에 해당 이벤트를 기록합니다.

`librechat.yaml`에서 [`endpoints.agents.eventDriven.selfUrl`](/docs/configuration/librechat_yaml/object_structure/agents#eventdriven) 및 [`rateLimits.agentEvents`](/docs/configuration/librechat_yaml/object_structure/config#ratelimits) 설정을 사용하는 것을 권장합니다. `AGENT_TRIGGERS_SELF_URL` 및 속도 제한 변수는 호환성을 위한 대체 수단으로 유지되며, YAML에 명시적으로 설정된 값이 우선합니다.

바운드 자식 연속(Bound child continuations), 분리된 Subagent 부모 연속(detached Subagent parent continuations), 그리고 이벤트 액터 분리된 액션 완료(Event Actor detached Action completion)는 자동으로 처리됩니다. 더 이상 사용되지 않는 `ENABLE_AGENT_EVENT_CHILD_TURNS`, `ENABLE_SUBAGENT_COMPLETION_WAKEUPS`, 그리고 `AGENT_TRIGGERS_DETACHED_ACTIONS_PRODUCER_ENABLED` 변수는 더 이상 읽지 않습니다.

인메모리 생성 저장소(in-memory generation store)는 프로세스가 살아있는 동안 프로세스 로컬 Event Actor 분리 완료(detached completion)를 지원합니다. Redis 생성 스트림은 지속 가능한 재시작 복구 및 복제본 핸드오프를 추가합니다. 혼합 버전 배포 전 [Generation Protocol Compatibility](/docs/configuration/redis#generation-protocol-compatibility)를 참조하세요.

일반적인 바운드 리스너(bound-listener) 경로를 사용하려면 `AGENT_TRIGGERS_SELF_URL`을 설정하지 마십시오. 내부 이벤트 허용이 TLS 프런트 도어와 같은 다른 HTTP 오리진을 통과해야 하는 경우에만 설정하십시오. 값은 자격 증명이 포함되지 않은 HTTP 또는 HTTPS URL이어야 합니다.

LibreChat은 인증된 Agent Events API를 노출하며, 인증되지 않은 웹훅은 노출하지 않습니다. API 키 ID, Remote Agents 권한, 대상 액세스, 멱등성 및 전용 Agent Event 속도 제한이 인그레스를 보호합니다. MongoDB 기반의 순서 지정 레인, 액터 메일박스, 수신 확인, 임대, 재시도 및 데드 레터가 복제본 전반의 워커를 지원합니다. 동작 및 예시는 [Agent Event Delivery](/docs/features/agents#agent-event-delivery) 및 [Agents API - Agent Events](/docs/features/agents_api#agent-events)를 참조하세요.

### 잔액 [#balance]

다음 기능은 시스템의 endpoint 내에서 사용자 잔액을 관리할 수 있게 해줍니다. 잔액을 수동으로 추가하거나, 사용자를 위해 자동으로 잔액을 누적하는 시스템을 구현할 수 있습니다. 구성에서 특정 초기 잔액이 정의된 경우, 사용자가 등록할 때 토큰이 사용자 잔액으로 자동 적립됩니다.

#### 잔액 관리 [#managing-balances]

- `npm run add-balance`를 실행하여 잔액을 수동으로 추가하세요.
  - 또한 이메일과 추가할 토큰 크레딧 금액을 지정할 수도 있습니다. 예: `npm run add-balance example@example.com 1000`
- `npm run set-balance`를 실행하여 `add-balance`와 유사하게 잔액을 수동으로 설정합니다.
- `npm run list-balances`를 실행하여 모든 사용자의 잔액을 확인하세요.

> **참고:** 1000 크레딧 = $0.001 (0.1 센트 USD)

- Azure 앱 등록은 `OPENID_SCOPE`에 사용된 LibreChat API 범위를 노출해야 합니다.
- 4개의 SharePoint 환경 변수를 모두 설정해야 합니다.
- 운영 환경에서는 HTTPS가 필수입니다.

<Callout type="info" title="기능 역량">
  활성화되면 사용자는 다음을 수행할 수 있습니다:
- SharePoint 문서 라이브러리 및 OneDrive for Business에서 파일 액세스
- 한 번에 여러 파일 선택 (기본 최대값: 10개 파일)
- 실시간 다운로드 진행 상황 확인

- Redis Cluster 모드의 경우, 여러 개의 URI를 제공하십시오: `redis://node1:7001,redis://node2:7002,redis://node3:7003` (클러스터 모드는 자동으로 감지됩니다).
- 내부적으로 키를 샤딩하는 단일 엔드포인트 관리형 Redis 서비스의 경우, `USE_REDIS_CLUSTER=false`를 유지하고 캐시 삭제 시 `CROSSSLOT` 오류가 발생하면 `REDIS_CLUSTER_SAFE_DELETE=true`로 설정하십시오.
- `REDIS_READONLY_RECOVERY_INTERVAL`은 장애 조치(failover) 후 강등된 읽기 전용 복제본에 열린 소켓이 남아 있을 때 Keyv 재연결 시도를 디바운스(debounce)합니다. Redis Cluster 클라이언트는 대신 자체적인 토폴로지 처리를 사용합니다.
- `REDIS_PING_INTERVAL`은 메인 ioredis 클라이언트의 선택적 하트비트를 제어합니다. 전용 pub/sub 구독자는 `REDIS_SUBSCRIBER_PING_INTERVAL`을 사용하여 유휴 상태인 죽은 소켓을 감지합니다. 두 설정 모두 `REDIS_PING_TIMEOUT`을 응답 기한으로 사용하며, 기한이 만료되면 재연결을 시도합니다.
- TLS 연결에는 `rediss://` 프로토콜을 사용하고, CA가 공개적으로 신뢰되지 않는 경우 `REDIS_CA`를 설정하세요.
- `REDIS_KEY_PREFIX_VAR`와 `REDIS_KEY_PREFIX`는 상호 배타적입니다.
- **AWS Elasticache with TLS**: Elasticache는 TLS 연결을 위해 대체 dnsLookup을 사용해야 할 수 있습니다. TLS가 적용된 Elasticache를 사용하는 경우 `REDIS_USE_ALTERNATIVE_DNS_LOOKUP=true`로 설정하세요. 자세한 내용은 [ioredis documentation](https://www.npmjs.com/package/ioredis)을 참조하세요.

#### 리더 선출 (Leader Election) [#leader-election]

Redis를 사용하여 다중 인스턴스 배포를 위한 분산 리더 선출(distributed leader election)을 구성하세요. 리더 선출은 예약된 작업과 같은 특정 작업을 하나의 인스턴스만 수행하도록 보장합니다.

참고:

- 리더 선출(Leader election)을 사용하려면 Redis가 활성화(`USE_REDIS=true`)되어 있어야 합니다.
- 이 설정은 다중 인스턴스 배포에만 관련이 있습니다.
- 리더십을 유지하려면 만료되기 전에 리더 임대(leader lease)를 갱신해야 합니다.
- 최대 시도 횟수 이후에도 임대 갱신에 실패하면, 해당 인스턴스는 리더십을 포기합니다.
