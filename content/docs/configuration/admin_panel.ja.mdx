[Admin Panel](/docs/features/admin_panel) は、LibreChat の `/api/admin` エンドポイントと通信する独立したサービスです。利用するには、LibreChat v0.8.5 以降、パネルから LibreChat API へのネットワークアクセス、そして `ADMIN` ロールまたは `access:admin` 権限を持つアカウントが必要です。シングルテナント構成では、最初に登録されたアカウントが管理者になります(テナント単位の構成では、管理者は別途プロビジョニングされます)。他のユーザーを管理者に昇格させるには、[Access Control configuration](/docs/configuration/access_control#promote-another-admin) を参照してください。

## LibreChatに同梱 [#bundled-with-librechat]

公式の `docker-compose.yml` および `deploy-compose.yml` には、スタックの他のサービスとともに起動する `admin-panel` サービス(イメージ `registry.librechat.ai/librechat-ai/librechat-admin-panel:latest`)が含まれています。

| Compose ファイル | 管理パネルの URL | 提供方法 |
| ------------ | --------------- | ---------------- |
| `docker-compose.yml` | `http://localhost:3000` | ホストのポート `ADMIN_PANEL_PORT`(デフォルトは `3000`)で公開 |
| `deploy-compose.yml` | `http://admin.localhost` | 同梱の nginx を経由し、`admin.localhost` サブドメインでルーティング |

パネルは、セッションシークレットが設定されていないと起動を拒否します。LibreChat の `.env` でこれを設定してください。Compose ファイルがこれを `SESSION_SECRET` としてパネルに渡します。

```bash filename=".env"
# At least 32 characters. Generate one with: openssl rand -hex 32
ADMIN_PANEL_SESSION_SECRET=replace-with-a-32-char-random-string

# Optional: host port for the default docker-compose.yml
# ADMIN_PANEL_PORT=3000

# Optional: set to true when the panel is served over HTTPS
# ADMIN_PANEL_SESSION_COOKIE_SECURE=false
```

compose ファイルでは、残りの設定も行われます。`API_SERVER_URL` は `api` サービスを指し、`VITE_API_BASE_URL` はブラウザ向けのリダイレクトのために `DOMAIN_CLIENT` に従います。また `deploy-compose.yml` は API の `ADMIN_PANEL_URL` を `http://admin.localhost` に設定し、SSO の後に管理者がパネルへ戻されるようにしています。パネルを使用しない場合は、`admin-panel` サービスを削除するか、Compose の[プロファイル](https://docs.docker.com/compose/how-tos/profiles/)の中に配置してください。

ブラウザは `*.localhost` を `127.0.0.1` に解決するため、hosts ファイルを編集しなくても `admin.localhost` で接続できます。実際のドメインを使用する場合は、DNS レコードをホストに向け、`client/nginx.conf` の `admin.localhost` の `server_name` を変更し、`ADMIN_PANEL_URL` を一致するように設定してください。

## スタンドアロン [#standalone]

単独でパネルを実行し、別の場所にある LibreChat インスタンスを指定したい場合は、イメージを直接使用します:

```bash
docker run -p 3000:3000 \
  --add-host=host.docker.internal:host-gateway \
  -e SESSION_SECRET=replace-with-a-32-char-random-string \
  -e VITE_API_BASE_URL=http://localhost:3080 \
  -e API_SERVER_URL=http://host.docker.internal:3080 \
  -e SESSION_COOKIE_SECURE=false \
  registry.librechat.ai/librechat-ai/librechat-admin-panel:latest
```

パネルがLibreChatに接続するには2つのアドレスが必要です。`VITE_API_BASE_URL`は、ブラウザがLibreChatにアクセスするためのアドレスで、サインイン時のリダイレクトに使用されます。`API_SERVER_URL`は、パネル自身のサーバーがLibreChatにアクセスするためのアドレスです。コンテナ内では`localhost`はそのコンテナ自身を指すため、LibreChatが同じホスト上で動作している場合、`API_SERVER_URL`には`http://host.docker.internal:3080`を使用します(Linuxでは上記の`--add-host`フラグが必要です)。一方、ブラウザには`http://localhost:3080`をそのまま使用します。本番環境では、両方の値を、それぞれの側が名前解決できるDNS名に設定してください。

[admin-panel リポジトリ](https://github.com/LibreChat-AI/admin-panel)にも `docker-compose.yml` があり、Bun を使ってソースから実行する手順（`bun install` の後に `bun dev`）も記載されています。

## LibreChat 設定 [#librechat-settings]

### リダイレクト URL [#redirect-url]

パネルが LibreChat とは異なる URL でホストされている場合は、LibreChat の `.env` で `ADMIN_PANEL_URL` を、パネルの外部ベース URL に設定してください。パスプレフィックスを含め、末尾のスラッシュは付けないでください。LibreChat はこの値を使って、SSO の後に管理者をパネルへ戻します。この値を設定すると、管理者には **Settings > General** に **Admin Panel** リンクが表示されます。

```bash filename=".env"
ADMIN_PANEL_URL=https://admin.example.com/admin
```

Helm チャートを使用する場合は、values ファイルで `librechat.adminPanelUrl` を設定してください。チャートはこれを `ADMIN_PANEL_URL` としてレンダリングします。

```yaml filename="values.yaml"
librechat:
  adminPanelUrl: https://admin.example.com/admin
```

### シングルサインオン [#single-sign-on]

管理者は、LibreChat が使用しているのと同じ OpenID Connect プロバイダーを使って、管理パネルにサインインできます。`${DOMAIN_SERVER}/api/admin/oauth/openid/callback` を、ご利用の ID プロバイダーに追加のリダイレクト URI として登録してください。プロバイダーのその他の設定については、[OpenID Connect](/docs/configuration/authentication/OAuth2-OIDC) を参照してください。IdP のロールまたはグループから `ADMIN` ロールを付与するには、`OPENID_ADMIN_ROLE` を使用します([.env リファレンス](/docs/configuration/dotenv#openid-connect)に記載されています)。

Google サインインによるパネルへのログインには、`GOOGLE_CLIENT_ID` と `GOOGLE_CLIENT_SECRET` を使用します。Google に `${DOMAIN_SERVER}/api/admin/oauth/google/callback` を登録してください。パネルはオフラインアクセスを要求するため、期限切れの管理者トークンを新たにログインし直さなくても更新できます。トークンを更新するたびに、アカウントの ID、BAN 状態、許可されたメールドメイン、テナント、管理者アクセス権が再度確認されます。

## 設定の上書き [#configuration-overrides]

オーバーライドは、ロール、グループ、またはユーザーといったプリンシパルごとにプロファイルとして保存され、`librechat.yaml` の上に適用されます。さらに、全員に適用されるベースプロファイルも用意されています。

**マージ順序。** Base プロファイルは、その優先度に関係なく最初に適用され、その後は残りのプロファイルが優先度の昇順で適用されます。優先度が同じ場合は、ロール、グループ、ユーザー、作成順の順で決まります。優先度を指定せずに作成されたプロファイルには、そのプリンシパルタイプのデフォルト値が割り当てられます。ロールは 10、グループは 20、ユーザーは 100 です(Base は 0)。優先度を省略した後続の書き込みでは、保存されている優先度が維持されます。

**検証。** 書き込み(`PUT /api/admin/config/:principalType/:principalId` および `PATCH .../fields`)は、ベース設定に適用された `librechat.yaml` スキーマに対して検証されます。無効な結果の場合は HTTP 400 で拒否され、何も保存されません:

```json
{
  "error": "Invalid config override",
  "code": "CONFIG_OVERRIDE_INVALID",
  "issues": [{ "path": "interface.fileSearch", "code": "invalid_type" }]
}
```

各問題には、パス（path）とコードのみが含まれ、送信された値そのものは含まれません。コードには、スキーマのコード（`invalid_type` など）や、`missing_merge_key`、`duplicate_merge_key`、`indexed_merge_key_write`、`union_dropped_key`、`invalid_document` があります。フィールドのパッチは、それが影響する、または新たに導入した問題がある場合にのみ拒否されます。

後のアップグレードでスキーマが厳格になるなどの理由により、保存されたオーバーライドが無効になった場合でも、致命的なエラーにはなりません。設定の解決時に無効なフィールドは破棄され、その下にある値が適用されます。また、サーバーはフィールドごとに1行のログを出力します。

```text
[mergeConfigOverrides] Ignoring invalid override "<path>" for <principalType>/<principalId> (<code>)
```

テーマ上書きが[テーマのルール](/docs/configuration/librechat_yaml/object_structure/theme#validation)に違反した場合も、同様にベーステーマへフォールバックします。

**シークレット。** 管理者APIを通じて書き込まれた登録済みのシークレットフィールドは、保存時に暗号化され、マスクされたプレビューとしてのみ返されます。対象は、Langfuse、OCR、音声、Web検索、Assistants、Azure Assistants、MCPサーバーの認証情報、Azureグループキー、および各`endpoints.custom[].apiKey`です。後続の編集でシークレットを省略した場合は、保存済みの値が維持されます。ただし、保存済みのキーの送信先(サーバーURLやベースURLなど)を変更する書き込みでは、キーを改めて指定する必要があります。カスタムエンドポイントのキーについては、`${ENV_VAR}`および`user_provided`の値はそのまま保持されます。カスタムヘッダーなどの汎用マップ内の任意の値は暗号化されないため、そこでは環境変数の参照を使用してください。

**環境変数の参照。** オーバーライド内の `${ENV_VAR}` 参照は、`librechat.yaml` で既に参照されている名前、組み込みエンドポイントの認証情報、および `CONFIG_OVERRIDE_ENV_ALLOWLIST` に列挙された名前に限定されます。それ以外の参照は、書き込み時に拒否されます。

**YAML専用の設定。** `type: stdio` のMCPサーバー、またはプロセス関連フィールド（`command`、`args`、`env`、`cwd`、`stderr`）、および `langfuse.headers` は、`librechat.yaml` でのみ設定できます。管理者APIはこれらへの書き込みを拒否し、オーバーライドでこれらを置き換えたり削除したりすることはできません。詳細は [Langfuse: 認証付きプロキシとゲートウェイ](/docs/configuration/langfuse#authenticated-proxies-and-gateways) を参照してください。

**セクション単位のアクセス制御。** 設定機能は広範囲（`read:configs`、`manage:configs`）に付与することも、トップレベルの1つのセクションに限定（`read:configs:<section>`、`manage:configs:<section>`）することもできます。Base プロファイルの作成、変更、削除には常に広範囲の `manage:configs` が必要です。セクション単位の管理は、ロール、グループ、ユーザープロファイルに適用されます。詳しくは [管理者の機能](/docs/configuration/access_control#admin-capabilities) を参照してください。

## 管理者 API [#admin-api]

パネルは、以下のLibreChatエンドポイントと通信します。すべてのルートで管理者アクセスと関連する権限が確認されます。

| マウント | 目的 |
| ----- | ------- |
| `POST /api/admin/login`, `/api/admin/oauth/*` | 管理者サインイン(ローカルおよびSSO) |
| `GET /api/admin/verify` | 管理者セッションを検証 |
| `/api/admin/users` | ユーザーの一覧表示と検索 |
| `/api/admin/groups` | グループとそのメンバー |
| `/api/admin/roles` | カスタムロール、その権限、およびメンバー |
| `/api/admin/grants` | システム機能の付与 |
| `/api/admin/config` | ベースおよびプリンシパルごとの設定プロファイル |
| `/api/admin/skills` | GitHubスキル同期のステータス、実行履歴、および認証情報 |
| `/api/admin/code-environments` | コード環境ワーカーのペアリングおよび取り消し |
| `/api/admin/langfuse` | Langfuseの接続設定とテスト |
| `/api/admin/audit-log` | 付与の監査ログ: `GET /`(一覧)、`GET /export.csv`、`GET /verify`(整合性チェック)、`GET /:id`。`read:audit_log` が必要です。書き込み用のエンドポイントはありません |

設定の読み取り: `GET /api/admin/config/meta`(デプロイメントの機能)、`/catalog`(スコープとモデルのオプション)、`/env-status`(環境変数参照のステータス)、`/effective`(呼び出し元の有効な設定)、`/resolved/:principalType/:principalId`(プリンシパルの解決済み設定)。読み取りでも認可とシークレットのマスキングは維持されます。

`POST /api/admin/config/:principalType/:principalId/changes` は、1 つのプロファイルに対する複数の変更をアトミックに適用し、書き込みレポートを返します。レポートでは、適用された場所とスキップされた場所が別々に一覧表示されます。また、デプロイ専用のパスはバッチ全体を失敗させることなくスキップできます。

`POST /api/admin/config/reload` は、ローカルの設定を再読み込みし、他のインスタンスに無効化を通知します。ローカルでの再読み込みが成功した後に通知が失敗した場合は `503` を返すことがあります。これはロールバックではなく、他のレプリカが再読み込みを行っていない可能性があります。詳しくは[アップグレードガイド](/docs/configuration/upgrade#admin-configuration-and-secrets)を参照してください。

テナントを跨いだプレビューや実効ユーザーの読み取りは、対象のテナント(そのテナントのBaseプロファイルを含む)内で解決されます。テナントにスコープされた呼び出し元は、別のテナントに到達することはできません。また、ロール名は呼び出し元自身のパーティションを指します。
