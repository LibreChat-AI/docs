## Général [#general]

![Utilisateurs actifs dans LibreChat](/images/metrics/librechat-metrics-active-users.png)

LibreChat fournit deux surfaces de métriques compatibles avec Prometheus. Le endpoint `/metrics` intégré à l'API rapporte le comportement opérationnel tel que l'activité de Redis et les résultats du proxy de télémétrie du navigateur. L'exportateur de base de données optionnel rapporte les données d'utilisation stockées dans MongoDB, y compris les totaux de jetons et le nombre d'utilisateurs actifs.

## Métriques d'API intégrées [#built-in-api-metrics]

LibreChat expose les métriques Prometheus depuis le serveur API à l'adresse `/metrics`. Définissez `METRICS_SECRET` et récupérez le endpoint avec `Authorization: Bearer <METRICS_SECRET>`. Le endpoint renvoie `401` lorsque le secret n'est pas défini, que l'en-tête est manquant ou que le jeton ne correspond pas.

```yaml filename="prometheus.yml"
scrape_configs:
  - job_name: librechat-api
    scheme: https
    metrics_path: /metrics
    authorization:
      type: Bearer
      credentials: your-metrics-secret
    static_configs:
      - targets: ['librechat.example.com']
```

### Métriques de processus, HTTP et de requêtes [#process-http-and-request-metrics]

Le point de terminaison expose également les métriques Node.js et de processus par défaut de `prom-client`, ainsi que les séries suivantes.

| Groupe | Métrique | Labels |
| --- | --- | --- |
| HTTP | `http_requests_total`, `http_request_duration_seconds` | `method`, `path`, `status` |
| HTTP | `http_requests_in_flight`, `http_request_body_bytes` (à partir de `Content-Length`) | `method`, `path` |
| SSE | `sse_streams_total`, `sse_stream_duration_seconds` | `method`, `path`, `status` |
| SSE | `sse_streams_in_flight` | `method`, `path` |
| Téléversements | `upload_requests_total`, `upload_request_duration_seconds` | `method`, `path`, `status` |
| Téléversements | `upload_requests_in_flight`, `upload_bytes_total` (à partir de `Content-Length`) | `method`, `path` |
| OpenID | `openid_user_lookup_total`, `openid_user_lookup_duration_seconds` | `result` |
| Mongoose | `mongoose_queries_total`, `mongoose_query_duration_seconds` | `model`, `operation`, `status` |
| Tâches de génération | `generation_jobs_total` | `store`, `result` |
| Tâches de génération | `generation_jobs_in_flight` | `store` |
| Flux de génération | `generation_stream_subscriptions_total` | `store`, `type`, `result` |
| Flux de génération | `generation_stream_resume_pending_events_total`, `generation_stream_early_buffer_overflows_total`, `generation_stream_first_attachment_delay_seconds` | `store` |
| Flux de génération | `generation_stream_attachment_outcomes_total` | `store`, `outcome` |
| Flux de génération | `generation_stream_recoveries_total`, `generation_stream_recovery_duration_seconds`, `generation_stream_recovery_events`, `generation_stream_recovery_content_parts` | `store`, `method`, `outcome` |
| Filtre de contenu | `content_filter_locator_traversal_failures_total` | `operation`, `reason` |
| Filtre de contenu | `content_filter_locator_traversal_size` | `operation`, `reason`, `dimension` |

Les métriques de récupération du flux de génération décrivent comment un tampon d'événements précoce ayant débordé est reconstruit. Les métriques du filtre de contenu comptent les parcours incomplets du localisateur de fichiers résolu.

### Métriques de démarrage de l'agent [#agent-startup-metrics]

Les requêtes de chat initiales de l'Agent émettent deux métriques de démarrage :

- `agent_startup_milestone_duration_seconds{milestone}` mesure la latence cumulative depuis l'entrée de la requête jusqu'à chaque étape de démarrage.
- `agent_startups_total{result}` compte les tentatives de démarrage par résultat terminal.

Les jalons couvrent l'admission de la requête, la création et l'accusé de réception du travail, le chargement de la conversation et de l'historique, l'initialisation du client et de l'exécution, le démarrage du flux, ainsi que la première réponse mise en file d'attente ou l'événement de contenu. Les résultats distinguent le contenu mis en file d'attente, l'achèvement sans delta de contenu, la déduplication, le rejet, la pause, le remplacement, l'abandon et l'erreur.

Lorsque le [traçage backend OpenTelemetry](/docs/configuration/dotenv#opentelemetry-traces-and-logs) est activé, le span `librechat.agent.startup` signale les mêmes jalons sous forme d'événements. Il inclut la durée totale du démarrage, le nombre de jalons, le résultat final et l'identifiant du flux de génération lorsqu'un est attribué.

### Métriques Redis [#redis-metrics]

Les caches et services basés sur Redis émettent deux métriques d'opération logique :

- `redis_operations_total{client,use_case,operation,status}` compte les opérations.
- `redis_operation_duration_seconds{client,use_case,operation,status}` mesure la latence.

`client` est `keyv` ou `ioredis`, et `status` est `success` ou `error`. Les étiquettes `use_case` délimitées identifient des tâches telles que les caches, les sessions, les limites de débit, la concurrence, les principaux ACL, les tâches de flux reprenables et pub/sub, les analyses de registre MCP, et l'élection de leader. Ces métriques comptent les opérations logiques de LibreChat plutôt que chaque aller-retour interne Redis. Les pings du cycle de vie de la connexion et la maintenance globale sont exclus, et l'effacement d'un espace de noms est compté comme une seule opération logique.

Lorsque le [traçage OpenTelemetry côté serveur](/docs/configuration/dotenv#opentelemetry-traces-and-logs) est activé, chaque span HTTP résume également ses opérations Redis à l'aide de :

- `librechat.redis.calls`
- `librechat.redis.duration_ms`
- `librechat.redis.errors`
- `librechat.redis.max_call_ms`
- `librechat.redis.operations`
- `librechat.redis.use_cases`

Les dix cas d'utilisation ayant la durée totale la plus élevée reçoivent également les attributs `calls`, `duration_ms`, `errors` et `max_call_ms` sous `librechat.redis.<use_case>.*`. Ce résumé au niveau de la requête ne nécessite pas de spans Redis au niveau de la commande ; activez `OTEL_IOREDIS_TRACING_ENABLED` uniquement lorsque des spans de commande individuels sont nécessaires.

### Métriques du proxy RUM du navigateur [#browser-rum-proxy-metrics]

Les résultats du proxy RUM du navigateur sont rapportés sous la forme `rum_proxy_requests_total{endpoint,result}`. `endpoint` peut être `traces`, `logs` ou `unknown` ; `result` peut être `success`, `auth_drop`, `auth_error`, `bad_request`, `not_configured`, `collector_4xx`, `collector_5xx`, `collector_error` ou `collector_timeout`.

### Métriques de l'acteur d'événement d'agent [#agent-event-actor-metrics]

Les Agent Events liés de manière durable exposent des métriques de réception et de récupération à faible cardinalité :

- `agent_event_actor_receipt_operations_total{operation,outcome,resolution}` compte les lectures de réception, le règlement et le backfill hérité. `operation` est `read`, `settle` ou `backfill` ; `outcome` est `hit`, `miss`, `success`, `replay` ou `conflict`.
- `agent_event_actor_receipts_retained{resolution}` rapporte les reçus de relecture conservés par la résolution `checkpoint_verified`, `action_compensated` ou `history_repaired`.
- `agent_event_actor_receipts_expiry_eligible` signale les reçus conservés dont le TTL MongoDB de 90 jours est écoulé mais qui n'ont pas encore été supprimés.
- `agent_event_actor_reconciliations_pending` signale les marqueurs de réconciliation actifs en attente d'un reçu terminal.
- `agent_event_actor_oldest_reconciliation_age_seconds` rapporte l'âge de la plus ancienne réconciliation active.
- `agent_event_actor_deliveries{state}` rapporte les lignes de livraison actuellement dans l'état `retry` ou `dead`.

Les jauges de stockage sont collectées lors des scrapes authentifiés et mises en cache pendant une durée maximale de 60 secondes. Configurez des alertes sur l'âge de réconciliation soutenu, les livraisons mortes ou les reçus éligibles à l'expiration plutôt que sur un seul scrape.

### Métriques des liens partagés [#shared-link-metrics]

`share_link_rejections_total{operation,code}` comptabilise les échecs de création ou de mise à jour limités. `operation` est `create` ou `update` ; `code` est `TARGET_MESSAGE_NOT_FOUND` lorsque la fin de la branche sélectionnée n'est pas persistée, ou `NO_MESSAGES` lorsque la conversation ne contient aucun message persisté. La métrique ne contient aucun texte de conversation ni identité d'utilisateur.

## Exportateur de métriques de base de données [#database-metrics-exporter]

L'exportateur de métriques est disponible sur [virtUOS/librechat_exporter](https://github.com/virtUOS/librechat_exporter).
Il s'agit d'un outil distinct que vous déployez aux côtés de LibreChat.

### Configuration [#setup]

Pour déployer l'exporter, ajoutez simplement le conteneur nécessaire à votre configuration compose comme ceci :

```yaml
services:
  metrics:
    image: ghcr.io/virtuos/librechat_exporter:main
    depends_on:
      - mongodb
    ports:
      - '8000:8000'
    restart: unless-stopped
```

Vous pouvez également configurer l'exportateur en option.
Mais en général, les paramètres par défaut devraient très bien convenir.

```yaml
services:
  metrics:
    environment:
      - MONGODB_URI=mongodb://mongodb:27017/
      - LOGGING_LEVEL=info
```

### Utilisation [#usage]

Vous pouvez maintenant ajouter l'exportateur à votre configuration de scrape Prometheus :

```yaml
- job_name: librechat
  static_configs:
    - targets:
        - 'librechat.example.com:8000'
```

Une fois que la collecte des métriques a commencé, recherchez les métriques `librechat_*` (par exemple, `librechat_registered_users`).
L'exportateur fournit plusieurs métriques.

Amusez-vous bien à construire votre tableau de bord Grafana !
