A configuração `webSearch` permite que você personalize a funcionalidade de pesquisa na web dentro do LibreChat, incluindo provedores de pesquisa, scrapers de conteúdo e rerankers de resultados.

## Visão geral [#overview]

O recurso de pesquisa na web consiste em três componentes principais:

1. **Provedores de pesquisa**: Serviços que realizam a pesquisa inicial na web
2. **Scrapers**: Serviços que extraem conteúdo de páginas da web
3. **Rerankers**: Serviços que reordenam resultados de pesquisa para melhor relevância

## Exemplo [#example]

```yaml filename="webSearch"
webSearch:
  # Search Provider Configuration
  serperApiKey: "${SERPER_API_KEY}"
  searxngInstanceUrl: "${SEARXNG_INSTANCE_URL}"
  searxngApiKey: "${SEARXNG_API_KEY}"
  searchProvider: "serper" # Options: "serper", "searxng", "tavily", "keenable"

  # Optional: query options sent to a SearXNG instance
  searxngSearchOptions:
    engines: "google,bing,startpage" # Default: "google,bing,duckduckgo"
    language: "en" # Default: "all"

  # Tavily Configuration (search and/or scraper)
  tavilyApiKey: "${TAVILY_API_KEY}"
  # Optional: custom Tavily-compatible endpoints
  tavilySearchUrl: "${TAVILY_SEARCH_URL}"
  tavilyExtractUrl: "${TAVILY_EXTRACT_URL}"

  # Keenable Configuration (search and/or scraper; all credentials optional)
  keenableApiKey: "${KEENABLE_API_KEY}"
  keenableApiUrl: "${KEENABLE_API_URL}"
  keenableSearchOptions:
    maxResults: 8
    site: "example.com"
    attributionTitle: "LibreChat"
    timeout: 15000
  keenableScraperOptions:
    attributionTitle: "LibreChat"
    timeout: 15000

  # Scraper Configuration
  firecrawlApiKey: "${FIRECRAWL_API_KEY}"
  firecrawlApiUrl: "${FIRECRAWL_API_URL}"
  firecrawlVersion: "${FIRECRAWL_VERSION}"
  scraperProvider: "firecrawl" # Options: "firecrawl", "serper", "tavily", "keenable"

  # Reranker Configuration
  jinaApiKey: "${JINA_API_KEY}"
  jinaApiUrl: "${JINA_API_URL}"
  cohereApiKey: "${COHERE_API_KEY}"
  rerankerType: "jina" # Options: "jina", "cohere", "none"

  # General Settings
  scraperTimeout: 7500 # Timeout in milliseconds for scraper requests (default: 7500)
  safeSearch: 1 # Options: 0 (OFF), 1 (MODERATE - default), 2 (STRICT)
  # Required for deliberately private self-hosted provider endpoints
  allowedAddresses:
    - "searxng:8080"
```

## Proteção contra SSRF e Provedores Privados [#ssrf-protection-and-private-providers]

O LibreChat valida cada conexão que abre para pesquisa na web, scraping e reranking. Destinos privados, loopback, link-local e de metadados de nuvem são bloqueados por padrão, incluindo saltos de redirecionamento e nomes de host que resolvem para um endereço privado no momento da conexão.

Use `webSearch.allowedAddresses` quando um endpoint configurado de SearXNG, Firecrawl, Jina, compatível com Tavily, compatível com Keenable ou provedor relacionado for deliberadamente privado:

```yaml filename="webSearch / allowedAddresses"
webSearch:
  searxngInstanceUrl: "${SEARXNG_INSTANCE_URL}"
  allowedAddresses:
    - "searxng:8080"
    - "10.0.0.5:3002"
    - "[fd00::5]:8080"
```

Este campo é uma lista de exceção de SSRF, não uma lista de permissões estrita. Destinos públicos permanecem disponíveis. As entradas devem ser pares exatos de `host:port`, `private.ip:port` ou `[ipv6]:port`; URLs, caminhos, intervalos CIDR, hosts/IPs simples e literais de IP público são rejeitados. Um nome de host isento confia em qualquer IP privado para o qual ele seja resolvido naquela porta, portanto, prefira um literal de IP privado e liste apenas nomes cujo DNS você controla.

O LibreChat isenta automaticamente um endpoint de proxy de encaminhamento HTTP(S) configurado para que ele possa ser alcançado. Quando o proxy realiza uma solicitação, ele resolve o destino e deve aplicar a saída (egress) de destino por conta própria. `NO_PROXY` pode tornar uma solicitação direta, onde o guardião de conexão do LibreChat ainda se aplica. O guardião cobre conexões que o LibreChat abre para APIs de provedores; ele não pode restringir uma URL de página que um scraper de terceiros recebe como dados de solicitação e busca em sua própria infraestrutura.

## Propriedade de Credenciais [#credential-ownership]

Uma URL de Firecrawl, SearXNG ou Jina fornecida pelo usuário não deve receber uma chave de API de propriedade do servidor. A validação SSRF não torna um endpoint público selecionado pelo usuário seguro para receber as credenciais da implantação. Configure a URL e a chave juntas como configurações de propriedade do administrador, ou permita que o usuário forneça seu próprio par; o SearXNG também pode ser executado sem uma chave.

Se uma URL de usuário salva for, de outra forma, pareada com a chave do servidor, o LibreChat ignora a URL opcional do Firecrawl e usa seu endpoint padrão. A URL da instância do SearXNG é obrigatória, portanto, essa configuração de propriedade mista não é autenticada e a ferramenta de busca não é inicializada. Para uma implantação auto-hospedada usando a chave do servidor, configure `FIRECRAWL_API_URL` ou `SEARXNG_INSTANCE_URL` juntamente com essa chave, em vez de depender da URL salva de um usuário. Endpoints privados ainda precisam de [`allowedAddresses`](#ssrf-protection-and-private-providers).

#### Escolhendo engines [#choosing-engines]

Os nomes dos engines devem corresponder aos engines que estão habilitados na sua própria instância, e duas coisas decorrem disso:

- O SearXNG ignora um mecanismo que ele não reconhece em vez de relatar um erro. Um erro de digitação, ou um mecanismo que está desativado em sua instância, resulta em menos resultados em vez de uma falha.
- Os nomes válidos são específicos da instância. Verifique a lista habilitada em `https://your-instance/config`, que retorna um JSON incluindo cada engine habilitada, ou abra a aba **Engines** na página de preferências da sua instância.

O padrão é `google,bing,duckduckgo`. O SearXNG agrega o que quer que os mecanismos selecionados retornem, portanto, um mecanismo bloqueado custa apenas a sua parcela dos resultados em vez da resposta inteira, e uma pesquisa só retorna vazia quando todos os mecanismos selecionados falham ou não retornam nada.

DuckDuckGo é o mecanismo no conjunto padrão com maior probabilidade de ser bloqueado, uma vez que ele apresenta CAPTCHAs para a maioria das instâncias auto-hospedadas. Com apenas três mecanismos no conjunto, perdê-lo ao mesmo tempo que o Google ou o Bing, devido a limites de taxa, é uma forma comum de acabar sem nenhum resultado. Definir `engines` explicitamente, deixando o DuckDuckGo de fora e listando mais de três mecanismos, reduz esse risco.

Motores que respondem rapidamente e toleram tráfego auto-hospedado compõem o melhor conjunto inicial, por exemplo:

```yaml filename="webSearch"
webSearch:
  searchProvider: "searxng"
  searxngInstanceUrl: "${SEARXNG_INSTANCE_URL}"
  searxngSearchOptions:
    engines:
      - google
      - bing
      - brave
      - startpage
      - qwant
```

Adicionar mais mecanismos amplia a cobertura, mas também torna cada pesquisa mais lenta, já que o SearXNG aguarda o mecanismo mais lento do conjunto antes de responder. Tenha o `timeout` em mente ao aumentar a lista.

#### O que estas opções não controlam [#what-these-options-do-not-control]

- **Safe search** não faz parte deste bloco. Ele vem da chave de nível superior [`safeSearch`](#safesearch) e é encaminhado para o SearXNG como `safesearch`.
- **Result categories** são escolhidas por consulta pelo LibreChat, que mapeia o tipo de pesquisa para `general`, `images`, `videos` ou `news`. Elas não podem ser substituídas aqui.
- **O número da página e o formato do resultado** são fixos. O LibreChat sempre solicita a página 1 no formato JSON, e é por isso que sua instância deve ter `json` habilitado em `formats`.

## Notas [#notes]

- As chaves de API podem ser configuradas de duas maneiras:
  1. Defina as variáveis de ambiente especificadas na configuração YAML
  2. Se as variáveis de ambiente não estiverem definidas, os usuários serão solicitados a fornecer as chaves de API através da interface.
- A configuração suporta múltiplos serviços para cada componente (providers, scrapers, rerankers)
- Se um tipo de serviço específico não for especificado, o sistema tentará todos os serviços disponíveis nessa categoria
- O Safe search oferece três níveis de filtragem de conteúdo: OFF (0), MODERATE (1) e STRICT (2)
- O Tavily não herda a configuração global de pesquisa segura por padrão; defina `tavilySearchOptions.safeSearch` explicitamente apenas quando sua conta Tavily oferecer suporte a `safe_search`.
- O Keenable oferece suporte a busca sem chave e busca de página; sua chave opcional aumenta os limites de taxa públicos, e sua substituição de URL de busca é exclusiva do ambiente.
- O comportamento de consulta do SearXNG (engines, idioma, intervalo de tempo, tempo limite da solicitação) é configurado em `searxngSearchOptions`; veja [Escolhendo engines](#choosing-engines) caso as pesquisas retornem vazias
- Nunca coloque chaves de API reais na configuração YAML - use apenas nomes de variáveis de ambiente

## Configurando o SearXNG [#setting-up-searxng]

SearXNG é um meta mecanismo de busca focado em privacidade que você pode auto-hospedar. 
Para mais informações, consulte a [documentação oficial do SearXNG](https://docs.searxng.org/).

Aqui estão os passos para configurar sua própria instância do SearXNG para uso com o LibreChat:

### Usando o Docker Desktop [#using-docker-desktop]

1. **Procure pela imagem oficial do SearXNG**
   - Abra o Docker Desktop
   - Pesquise por `searxng/searxng` na aba **Images**
   - Clique em **Run** na imagem oficial para baixar automaticamente e executar um container da imagem

2. **Executando o container**
   - Expanda o menu suspenso **Optional Settings** no painel subsequente que aparece assim que o download for concluído
   - Defina os detalhes de configuração desejados (número da porta, nome do container, etc.)
   - Clique em **Run** para iniciar o container

3. **Configurar o SearXNG para o LibreChat**
   - Navegue até a aba `Files` no Docker Desktop
   - Vá para `/etc/searxng/settings.yaml`
   - Abra o editor de arquivos
   - Navegue até a seção `formats`
   - Adicione `json` como um formato aceitável para que o LibreChat possa se comunicar com sua instância
   - Salve o arquivo

4. **Reinicie o container**
   - Reinicie o container para que as alterações entrem em vigor

#### Configuração YAML [#yaml-configuration]

Para configurar o SearXNG para todos na instância em vez de por usuário, defina os mesmos valores no `librechat.yaml`:

```yaml filename="librechat.yaml"
webSearch:
  searchProvider: "searxng"
  searxngInstanceUrl: "${SEARXNG_INSTANCE_URL}"
  # searxngApiKey: "${SEARXNG_API_KEY}" # Only if your instance requires authentication
  # Required: a self-hosted instance is a private destination, so exempt it from the connection guard
  allowedAddresses:
    - "localhost:55011"
  searxngSearchOptions:
    engines:
      - google
      - bing
      - startpage
      - qwant
    language: "en"
    timeout: 10000
```

A URL e a chave ainda são lidas a partir do ambiente, portanto, combine a configuração acima com:

```bash filename=".env"
SEARXNG_INSTANCE_URL=http://localhost:55011
# SEARXNG_API_KEY=your_api_key
```

<Callout type="warning" title="Instâncias privadas precisam de uma entrada allowedAddresses">
`localhost:55011` é um endereço de loopback, o qual a [proteção SSRF](#ssrf-protection-and-private-providers) do LibreChat bloqueia no momento da conexão. Sem a entrada correspondente em `allowedAddresses`, a pesquisa falha mesmo quando o SearXNG está saudável. A entrada deve ser o par `host:port` exato da URL da sua instância.

Quando o LibreChat é executado no Docker, `localhost` refere-se ao contêiner do LibreChat, não ao do SearXNG. Use um nome de host que o contêiner consiga alcançar, como o nome do serviço no compose, e adicione-o à lista de exceções:

```yaml filename="librechat.yaml"
webSearch:
  searxngInstanceUrl: "${SEARXNG_INSTANCE_URL}" # SEARXNG_INSTANCE_URL=http://searxng:8080
  allowedAddresses:
    - "searxng:8080"
```
</Callout>

Veja [`searxngSearchOptions`](#searxngsearchoptions) para todas as subchaves que este bloco aceita.

#### Solução de problemas de resultados vazios [#troubleshooting-empty-results]

Uma pesquisa no SearXNG que não retorna nada quase sempre significa que a solicitação nunca chegou a uma instância funcional, em vez de o LibreChat descartar os resultados. Siga estes passos em ordem:

1. **A instância é um endereço privado sem nenhuma entrada em `allowedAddresses`.** O LibreChat bloqueia destinos de loopback e privados no momento da conexão, portanto, uma instância auto-hospedada precisa que seu `host:port` exato esteja listado em [`allowedAddresses`](#ssrf-protection-and-private-providers). Isso bloqueia a solicitação imediatamente em vez de retornar um conjunto de resultados vazio.
2. **`json` está faltando em `formats`.** O LibreChat solicita resultados como JSON. Se a seção `formats` do seu arquivo de configurações da instância não listar `json`, a instância responderá com uma página de erro e todas as pesquisas retornarão vazias. Este é o passo 3 da configuração do Docker acima.
3. **Every selected engine failed.** O SearXNG mescla os mecanismos que responderam, portanto, uma resposta vazia significa que nenhum deles retornou nada. O DuckDuckGo está no conjunto padrão (`google,bing,duckduckgo`) e apresenta CAPTCHAs para a maioria das instâncias auto-hospedadas, o que deixa apenas dois mecanismos para realizar a busca. Defina `searxngSearchOptions.engines` explicitamente, remova o DuckDuckGo e liste alguns outros mecanismos.
4. **Um nome de engine não existe na sua instância.** O SearXNG ignora silenciosamente engines que ele não reconhece, portanto, um erro de digitação significa apenas menos resultados. Compare sua lista com `https://your-instance/config`.
5. **A instância está mais lenta que o tempo limite.** Aumente `searxngSearchOptions.timeout` acima do padrão `10000` se sua instância consultar muitos mecanismos ou estiver atrás de um caminho de rede lento.

Você pode reproduzir o que o LibreChat envia chamando a instância diretamente:

```bash
curl -s "http://localhost:55011/search?q=librechat&format=json&engines=google,bing,startpage" | head -c 500
```

Isso é executado a partir da sua própria máquina, portanto, ignora completamente o guardião de conexão do LibreChat. Um array `results` vazio aqui confirma que o problema está no lado do SearXNG; resultados aqui enquanto o LibreChat ainda não encontra nada apontam de volta para `allowedAddresses`.
