## maxProviderErrorChars

Controla quanto texto de erro do provedor o LibreChat preserva quando uma falha de um Agent não pode ser classificada. O padrão é `2000` caracteres. Defina como `0` para omitir o texto do provedor; o máximo é `1000000`.

```yaml filename="endpoints / agents / maxProviderErrorChars"
maxProviderErrorChars: 2000
```

## repositoryInstructions

Controla a descoberta de instruções do repositório para ambientes de Código anexados. `timeoutMs` limita a solicitação de carregamento de instruções de `100` a `30000` milissegundos, com um padrão de `2000`.

```yaml filename="endpoints / agents / repositoryInstructions"
repositoryInstructions:
  timeoutMs: 2000
```

## Disjuntores de fluxo (Stream circuit breakers) [#stream-circuit-breakers]

Essas configurações interrompem a execução de um Agent quando o stream de um provedor parece estar produzindo argumentos de ferramenta descontrolados ou uma sequência ilimitada de eventos delta.

<OptionTable
  options={[
    [
      'maxToolCallArgBytes',
      'Number',
      'Máximo de bytes cumulativos para os argumentos de uma chamada de ferramenta via stream. Defina como 0 para desativar a proteção global.',
      '65536',
    ],
    [
      'maxDeltaEventsPerTurn',
      'Number',
      'Máximo de eventos transmitidos para um turno de geração de modelo. Defina como 0 ou omita para desativar esta proteção.',
      '0 (disabled)',
    ],
    [
      'maxToolCallArgBytesByTool',
      'Object',
      'Substituições de bytes de argumento por ferramenta, indexadas pelo nome da ferramenta voltado para o modelo. Um valor de 0 desativa a proteção para essa ferramenta.',
      'create_file: 131072',
    ],
  ]}
/>

O LibreChat usa um limite global de argumentos de 64 KiB e fornece uma substituição de 128 KiB para `create_file`, cujas cargas úteis legítimas são frequentemente maiores. As entradas em `maxToolCallArgBytesByTool` são mescladas sobre essa substituição integrada. Se qualquer uma das proteções for acionada, o LibreChat interrompe o fluxo do provedor em andamento e informa qual limite foi excedido.

```yaml filename="endpoints / agents / stream circuit breakers"
maxToolCallArgBytes: 65536
maxDeltaEventsPerTurn: 100000
maxToolCallArgBytesByTool:
  create_file: 262144
  large_import: 524288
```

Para desativar todos os limites de tamanho de argumento, defina tanto o limite global quanto a substituição `create_file` fornecida como `0`:

```yaml
maxToolCallArgBytes: 0
maxToolCallArgBytesByTool:
  create_file: 0
```

## titleTiming

<OptionTable
  options={[
    [

/>

**Padrão:** `"immediate"`

**Valores Disponíveis:**

- **`"immediate"`**: Gera o título assim que a solicitação é iniciada, em paralelo com a resposta do modelo, usando a primeira mensagem do usuário.

**Exemplo:**

```yaml filename="endpoints / agents / titleTiming"
titleTiming: immediate
```

## activityLabel

Defina `activityLabel: true` para agrupar cada bloco de raciocínio do Agente e chamadas de ferramenta sob um cabeçalho de uma linha gerado. Use `activityModel`, `activityEndpoint`, `activityPrompt`, `activityMaxPerRun` e `activityCharLimit` para controlar a chamada de modelo adicional e seu custo. Veja [Agent Activity Groups](/docs/configuration/librechat_yaml/object_structure/shared_endpoint_settings#agent-activity-groups) para a referência completa de campos e regras de precedência.

```yaml filename="endpoints / agents / activity groups"
activityLabel: true
activityEndpoint: openAI
activityModel: gpt-4.1-nano
activityMaxPerRun: 20
activityCharLimit: 600
activityPhaseLabel: true
activityPhaseMaxPerRun: 5
```

`activityPhaseLabel` pode adicionar independentemente um resumo pai recolhido em torno de cada fase de execução que contenha pelo menos duas atividades lógicas. Use `activityPhaseModel`, `activityPhaseEndpoint`, `activityPhasePrompt` e `activityPhaseMaxPerRun` para ajustar essas chamadas; `activityCharLimit` é compartilhado com os rótulos das atividades filhas.

## capabilities

<OptionTable
  options={[
    [
      'capabilities',
      'Array/List of Strings',
      'Especifica as capacidades de agente disponíveis para todos os usuários para o endpoint agents.',
      'Defines the agent capabilities that are available to all users for the agents endpoint. You can omit the capabilities you wish to exclude from the list.',
    ],
  ]}
/>

**Padrão:** `["deferred_tools", "execute_code", "file_search", "web_search", "artifacts", "subagents", "actions", "context", "skills", "memory", "ask_user_question", "tools", "chain", "ocr"]`

`programmatic_tools`, `stateful_code_sessions`, `run_in_background` e `tool_intents` são opcionais e devem ser adicionados explicitamente. Ferramentas programáticas e sessões com estado também exigem `execute_code` e uma implementação compatível de Code Interpreter. O Agent Builder desativa seleções de MCP programático sem o Code Interpreter, e o servidor remove opções de chamadores programáticos obsoletos quando a execução de código não está disponível. `run_in_background` torna as ferramentas do Code Interpreter elegíveis por padrão e permite a ativação por ferramenta para MCP, Plugins e Actions elegíveis; a execução de código em segundo plano também exige `execute_code` e Code Interpreter.

`stateful_code_sessions` é altamente experimental. Ele requer uma rota de Code Interpreter com perfil `stateful` separada, configurada com [`LIBRECHAT_CODE_BASEURL_STATEFUL`](/docs/configuration/dotenv#stateful-code-interpreter-endpoint) ou [`statefulCodeSessions.environments`](#statefulcodesessions). Requisições stateful falham de forma fechada em vez de recorrer ao serviço stateless normal. No Agent Builder, cada Agent habilitado escolhe um escopo de workspace de usuário, agente-e-usuário ou conversa e, quando backends nomeados estão configurados, um ambiente de execução. Novos Agents começam com o escopo pessoal padrão do usuário e o ambiente de execução padrão da implantação.

**Exemplo:**

```yaml filename="endpoints / agents / capabilities"
capabilities:
  - 'deferred_tools'
  # Optional: enables Programmatic Tool Calling for MCP tools marked Programmatic in the Agent Builder.
  # Requires execute_code and a Code Interpreter deployment with the Tool Call Server component.
  # - 'programmatic_tools'
  - 'execute_code'
  - 'file_search'
  - 'web_search'
  - 'artifacts'
  - 'subagents'
  - 'actions'
  - 'context'
  - 'skills'
  - 'memory'
  - 'ask_user_question'
  - 'tools'
  - 'chain'
  - 'ocr'
  # Optional and highly experimental: reuse a user-, agent-and-user-, or
  # conversation-scoped workspace. Requires LIBRECHAT_CODE_BASEURL_STATEFUL
  # or a named statefulCodeSessions environment.
  # - 'stateful_code_sessions'
  # Optional: allow eligible Code Interpreter, MCP, Plugin, and Action tools to run as background tasks.
  # - 'run_in_background'
  # Optional: show live model-written intent labels for native and selected MCP tools.
  # - 'tool_intents'
```

**Nota:** Este campo é opcional. Se omitido, o comportamento padrão é incluir todas as capacidades listadas no default.

## statefulCodeSessions

Configura os escopos de compartilhamento e backends de execução opcionais para workspaces de Code Interpreter com estado altamente experimentais.

<Callout type="warning" title="Altamente experimental">
  Stateful Code Sessions, ambientes de execução nomeados, workers conectados e pareamento estão em uma fase inicial de experimentação. Seu comportamento, configuração, características de persistência e protocolo de integração podem mudar substancialmente.
</Callout>

<OptionTable

/>

Ambientes anexados aceitam `environments[].configSchema.limits.maxQueueWaitMs`, que controla por quanto tempo uma solicitação pode tentar novamente aguardar pela capacidade do workspace. O padrão e o máximo são `300000` milissegundos (5 minutos). Defina como `0` para desativar as tentativas do cliente após a tentativa inicial de admissão; isso não cancela o trabalho que já foi admitido ou está em execução. Esses campos pertencem a `configSchema.limits`, **não** a `userConfig.bash`.

`environments[].configSchema.limits.maxRequestTimeoutMs` limita opcionalmente o **tempo HTTP total para uma chamada de ferramenta de workspace**, incluindo admissão, execução, liquidação e entrega. Ele aceita de `1` a `610000` ms, mas a configuração rejeita orçamentos pequenos demais que não deixem tempo de execução de comando após a admissão e a reserva de 10 segundos para liquidação/entrega. Sem ele, a admissão ainda possui um orçamento de 30 segundos por tentativa; `maxQueueWaitMs` permanece como um horizonte de nova tentativa separado. **Não habilite uma admissão mais longa** até que cada réplica da API do LibreChat entenda este campo, a rota da Code API respeite as permissões de fila por solicitação e o tempo limite mais curto em todo o caminho do proxy/ingress ativo tenha sido medido. Uma mutação expirada pode ter sido concluída no worker, portanto, o LibreChat não tenta novamente um tempo limite ambíguo.

Com um orçamento total de solicitação, `environments[].configSchema.limits.minCommandAdmissionMs` reserva tempo para que um comando entre no worker antes que a execução comece. O padrão é `10000` ms; defina entre `1000` e `300000` ms. O orçamento da solicitação deve **exceder** essa tolerância mais 10000 ms de carência para liquidação/entrega; sem um orçamento total, a configuração não tem efeito. O limite de execução Bash anunciado para um Agent é o menor valor entre o seu teto configurado ou upstream e o tempo restante após essas reservas. Por exemplo, um orçamento de solicitação de 90000 ms com um teto de comando de 80000 ms e a reserva padrão anuncia no máximo um comando de 70000 ms.

```yaml filename="endpoints / agents / statefulCodeSessions"
statefulCodeSessions:
  allowedEnvironments:
    - 'user'
    - 'agent-user'
    - 'conversation'
  principalWorkers:
    enabled: true
    maxPerUser: 5
  environments:
    - id: managed-default
      name: Managed Code API
      type: managed
      baseURL: https://code.example.com/v1
      default: true
    - id: engineering-vm
      name: Engineering VM
      type: attached
      baseURL: https://code-bridge.example.com/v1
      owner: deployment
      pairing:
        workerId: engineering-vm
        tokenEnv: CODE_BRIDGE_ADMIN_TOKEN
    - id: personal-workers
      name: Personal Code Workers
      type: attached
      baseURL: https://code-bridge.example.com/v1
      owner: deployment
      configSchema:
        limits:
          maxCommandTimeoutMs: 120000
          # Before enabling, verify Code API queue allowances and the live proxy deadline.
          # maxRequestTimeoutMs: 160000
          # minCommandAdmissionMs: 10000
          # maxQueueWaitMs: 300000
        # After upgrading Code API and opting in the worker with --linked-worktree-lanes:
        # workspaces:
        #   linkedWorktrees: true
        # Optional: require exact matching even on workers supporting tolerant edits.
        # edits:
        #   tolerantMatching: false
        permissions:
          fileWrite:
            allowed: [allow, ask, deny]
            default: ask
          commandExecution:
            allowed: [ask, deny]
            default: ask
      pairing:
        allowPrincipalWorkers: true
        tokenEnv: CODE_BRIDGE_ADMIN_TOKEN
```

`allowedEnvironments` é obrigatório sempre que o bloco estiver presente e deve incluir pelo menos um escopo de workspace. Omita o bloco inteiro para permitir todos os três escopos e continuar roteando o trabalho com estado através de [`LIBRECHAT_CODE_BASEURL_STATEFUL`](/docs/configuration/dotenv#stateful-code-interpreter-endpoint). O padrão pessoal e o Agent Builder permitem apenas valores permitidos. Se um administrador restringir a política, um padrão pessoal salvo permanece visível, mas desativado, e novos Agents usam o primeiro escopo permitido. Agents habilitados existentes mantêm seu escopo salvo, mas um escopo agora não permitido falha de forma segura (fails closed) em tempo de execução até que o Agent seja reconfigurado.

`conversationMoves.enabled: true` permite que o proprietário da conversa mova explicitamente um workspace anexado selado para um ambiente compatível e recupere um workspace ausente sem substituir o histórico do chat ou restaurar arquivos antigos do workspace. Para permitir adicionalmente que um chat salvo **anexe** um workspace ou **deixe** um para um chat normal, defina `conversationMoves.allowAttachDetach: true`. Ambos os interruptores estão desativados por padrão; habilitar apenas as movimentações mantém o comportamento exclusivo de movimentação. Atualize **todas** as réplicas da API e, em seguida, habilite [`CODE_ENVIRONMENT_DECISION_VERSION=1`](/docs/configuration/dotenv#code-interpreter) antes de optar por participar. A propriedade, o acesso ao destino, o trabalho ativo e a política atual são verificados novamente na transição; uma geração em execução não pode ser movida.

```yaml filename="endpoints / agents / statefulCodeSessions / conversationMoves"
statefulCodeSessions:
  allowedEnvironments: ['user', 'agent-user', 'conversation']
  conversationMoves:
    enabled: true
    allowAttachDetach: true
```

`principalWorkers` controla o autoatendimento de inscrição para workers pessoais vinculados. Valores omitidos são resolvidos como `enabled: true` e `maxPerUser: 5`; defina `enabled: false` ou `maxPerUser: 0` para interromper novas inscrições. O limite contabiliza cada ambiente pessoal registrado para aquele usuário em todos os planos de controle configurados, incluindo workers offline. Reduzir o limite ou desativar a inscrição não revoga ambientes existentes.

O Deployment YAML é o limite máximo absoluto. Uma substituição de configuração de função, grupo ou usuário pode desativar a inscrição ou reduzir o `maxPerUser`, mas não pode aumentar o valor do deployment. Um usuário vê planos de controle com pareamento ativado apenas quando o limite efetivo é maior que zero, [`pairing.allowPrincipalWorkers`](#statefulcodesessions) está ativado nesse plano de controle, a autenticação principal está disponível e o usuário possui permissão de gerenciamento de Code Environment.

Quando `environments` não está vazio, cada entrada requer um `id` único, um `name` de exibição, um `type` como `managed` ou `attached`, e uma `baseURL` HTTP(S) sem string de consulta ou fragmento. Se a lista contiver ambientes executáveis, exatamente uma dessas entradas deve definir `default: true`. O Agent Builder então adiciona um seletor de **Execution environment**; deixá-lo em **Deployment default** utiliza essa entrada padrão. Uma lista contendo apenas planos de controle de pareamento self-service não precisa de um padrão. Um Agent que nomeia um ambiente que é posteriormente removido ou que não está mais acessível falha de forma segura (fails closed) em vez de recorrer a outro backend.

- `managed` aponta diretamente para uma Code API stateful gerenciada por operador.
- `attached` aponta para um backend `remote-bridge` da Code API compatível que delega trabalho para um worker `@librechat/code` de saída. O worker não requer uma porta pública de entrada, mas seu endpoint de execução local ainda precisa de isolamento apropriado.
- `workerId` opcionalmente roteia um ambiente anexado para um worker de saída. Ele é exclusivo do servidor e não é exposto através da configuração de inicialização do cliente.
- `owner` assume o valor padrão `deployment`. Ambientes de propriedade do principal são criados através da API de Ambientes de Código autenticada do LibreChat, protegida por ACLs, e mesclados apenas para solicitações autorizadas; não coloque URLs fornecidas pelo cliente no YAML de deployment.
- `pairing` é opcional e válido apenas para entradas `attached` de propriedade da implantação. `pairing.workerId` identifica um worker gerenciado pelo operador a ser inscrito, enquanto `pairing.allowPrincipalWorkers: true` permite que usuários autorizados inscrevam workers vinculados ao proprietário no plano de controle. Pelo menos um desses campos é obrigatório quando `pairing` está presente.
- `pairing.tokenEnv` nomeia a variável de ambiente que contém o token do administrador da ponte; ela nunca contém o próprio token. O pareamento requer HTTPS, exceto para desenvolvimento em loopback.
- `configSchema.permissions` permite opcionalmente que proprietários autorizados escolham a política de `fileWrite` e `commandExecution` para ambientes pessoais em **Configurações > Ambientes de código**. Cada campo requer uma lista `allowed` não vazia contendo `allow`, `ask` e/ou `deny`; `default` é `ask` quando omitido e deve aparecer em `allowed`. O LibreChat rejeita valores armazenados fora da lista do administrador.
- `configSchema.limits.maxCommandTimeoutMs` define o maior tempo limite de Bash que o modelo pode solicitar para aquele ambiente. Ele aceita de `1` a `300000` ms; a omissão preserva o padrão de 30 segundos. Com um orçamento total de solicitação, o tempo limite de comando anunciado também se ajusta ao tempo restante após a admissão, liquidação e entrega do comando. Este é um limite de implantação e não é configurável pelo usuário.
- `configSchema.workspaces.linkedWorktrees: true` habilita o agendamento por worktree apenas para workspaces anexados que anunciam `git_linked_worktree`; a omissão mantém todas as solicitações na lane raiz do checkout. Atualize o LibreChat **antes** que um worker anuncie este escopo, implante uma Code API que suporte lanes de linked-worktree e, em seguida, inicie o worker com `--linked-worktree-lanes` antes de habilitar a configuração no YAML. Operações de arquivo que visam um caminho dentro de `.worktrees/<name>` e comandos Bash com um `cwd` lá usam essa lane e retornam caminhos relativos ao checkout. Comandos que executam `cd` dentro do texto do comando, operações na raiz do checkout, instâncias de workspace de conversação e ações de ambiente permanecem com escopo na raiz.
- `configSchema.edits.tolerantMatching` permite fallback com tolerância a espaços em branco por padrão em workers conectados que anunciam `tolerant_match`; defina como `false` para exigir correspondência exata, incluindo visualizações de edição protegidas. A correspondência deve permanecer única, a menos que a edição defina explicitamente `replace_all`. Workers mais antigos não recebem novos campos de correspondência; `replace_all` conectado é recusado antes do despacho, a menos que o worker o anuncie. Esses recursos exigem Code API compatível e builds de worker que implementem [Code Interpreter #271](https://github.com/LibreChat-AI/code-interpreter/pull/271).
- Não configure `settings` no YAML de implantação. O LibreChat fornece esse campo de escopo de solicitação a partir das preferências validadas pelo servidor do proprietário autenticado.
- Apenas a política de escrita de arquivos e execução de comandos é configurável pelo usuário. Isolamento, rede, montagens, execução privilegiada, entrada, saída e segredos permanecem sob controle do administrador.
- Se tanto o `workerId` de nível superior quanto o `pairing.workerId` estiverem presentes, eles devem coincidir. Uma entrada com `allowPrincipalWorkers: true` e nenhum dos IDs de worker sendo exclusivo de pareamento (pairing-only): ela é omitida dos seletores de execução e não pode definir `default: true`.

A execução anexada habilita automaticamente uma linha de base de aprovação segura: gravações de arquivos e execução de comandos ou códigos solicitam confirmação, enquanto operações de leitura e pesquisa continuam sob a política de ferramentas regular. A linha de base é delimitada ao Agent que utiliza o ambiente anexado. Se nenhuma configuração de usuário estiver disponível, o LibreChat usa `ask`; [`toolApproval.enabled: false`](#toolapproval) é a substituição de emergência do administrador que desativa essa linha de base de ambiente anexado. Chamadores sem suporte a aprovação e retomada falham de forma fechada, a menos que essa substituição explícita seja definida.

A execução anexada requer uma compilação experimental correspondente do remote-bridge do Code Interpreter. O pareamento autentica a conexão de saída do worker; ele não substitui o isolamento de sandbox ou VM. Usuários com permissão de gerenciamento de Code Environment realizam o pareamento, configuram a política de ferramentas permitidas e revogam workers pessoais em **Settings > Code environments**. Veja [Stateful Code Sessions](/docs/features/code_interpreter#stateful-code-sessions).

Padrões usam correspondência glob. Ferramentas MCP podem ser delimitadas com `mcp:<server>:<tool>`; por exemplo, `mcp:github:*` corresponde a todas as ferramentas do servidor `github`. toolApproval:

```yaml filename="endpoints / agents / toolApproval / hooks"
      options:
```

Aumente este valor quando uma implantação executar agentes com orquestração pesada que precisem delegar tarefas para mais de dez filhos. O valor é lido na inicialização e aplicado em três locais:

- Solicitações de criação, atualização e duplicação de agentes, para `subagents.agent_ids` e `subagents.graphs`
- As listas de permissões (allowlists) de `subagents.agent_ids` nas Model Specs, validadas na mesma passagem de configuração

<Callout type="warning">
  `maxSubagents` deve ser um número inteiro entre 1 e 50. Para voltar ao padrão deliberadamente, remova a chave: um `maxSubagents` omitido resulta em `10` sem erro.
</Callout>

<Callout type="note">
  O limite é aplicado a todo o processo e vem do `librechat.yaml`. Uma substituição no banco de dados por usuário ou por grupo de `endpoints.agents.maxSubagents` é refletida na configuração servida, mas não é aplicada pela validação da requisição.
</Callout>

Aumentar isso apenas altera quantos subagentes um agente pode referenciar. Os limites de profundidade, nó de grafo e configuração de execução não são afetados. Veja [Subagents](/docs/features/subagents#limits).

## fileSharing

`fileSharing` é um compartilhamento opcional e com escopo de execução para trabalho delegado de Agentes. Defina `enabled: true` aqui e habilite `subagents.shareFiles` em cada Agente delegador. As entradas são somente leitura para os destinatários; as saídas permanecem privadas, a menos que sejam explicitamente publicadas, e os arquivos publicados permanecem disponíveis para download após a execução.

```yaml filename="endpoints / agents / fileSharing"
endpoints:
  agents:
    fileSharing:
      enabled: true
      allowSiblingSharing: false
      maxFiles: 100
      maxPrivateBytes: 268435456
      ttlMs: 3600000
```

`allowSiblingSharing` permite destinatários irmãos ou descendentes explicitamente nomeados. `maxFiles` varia de `1` a `1000`; `maxPrivateBytes` limita os snapshots de saída privada retidos; e `ttlMs` é o tempo de vida ativo do manifesto, limitado a 24 horas. Omitir este bloco deixa o compartilhamento desativado.

```yaml filename="endpoints / agents / Code API upload recovery"
  agents:
    codeApiUploadConcurrency: 3

```

O LibreChat respeita o `Retry-After`, reabre fluxos persistentes para cada tentativa e remove os chamadores cancelados da fila. Definir `codeApiMaxRetryWaitMs: 0` desativa a espera, em vez de desativar os uploads.

## Capacidades dos Agentes [#agent-capabilities]

O campo `capabilities` permite que você habilite ou desabilite funcionalidades específicas para agentes. As capacidades disponíveis são:

- **deferred_tools**: Permite que agentes descubram ferramentas MCP adiadas em tempo de execução, em vez de carregar todas as ferramentas no contexto antecipadamente.
- **programmatic_tools**: Habilita a Chamada de Ferramentas Programáticas para ferramentas MCP marcadas como Programmatic no Agent Builder. Requer `execute_code` e uma implementação de Code Interpreter com o componente Tool Call Server. Esta funcionalidade é opcional e não está habilitada por padrão.
- **execute_code**: Permite que o agente execute código.
- **stateful_code_sessions**: Permite que agentes que optaram pelo uso reutilizem um workspace do Code Interpreter no escopo de usuário, agente-e-usuário ou conversa. Requer `execute_code`, uma implementação compatível do Code Interpreter e a configuração Avançada por agente. Novos agentes usam o escopo preferencial do usuário conectado. Esta funcionalidade é altamente experimental, não está habilitada por padrão e pode mudar substancialmente durante a experimentação; não trate seu comportamento ou configuração atual como um contrato de produção estável.
- **file_search**: Permite que o agente pesquise e interaja com arquivos. Quando ativado, o comportamento de citação é controlado pelas configurações `maxCitations`, `maxCitationsPerFile` e `minRelevanceScore`.
- **web_search**: Habilita a funcionalidade de pesquisa na web para agentes, permitindo que eles pesquisem e recuperem informações da internet.
- **artifacts**: Permite que o agente gere artefatos interativos (componentes React, HTML, diagramas Mermaid).
- **subagents**: Habilita execuções de agentes filhos em contexto isolado. Veja [Subagents](/docs/features/subagents).
- **actions**: Permite que o agente execute ações predefinidas.
- **context**: Habilita a funcionalidade "Upload as Text" no chat e "File Context" para agentes, permitindo que os usuários enviem arquivos e tenham seu conteúdo extraído e incluído diretamente na conversa.
- **skills**: Habilita Skills no painel lateral, invocação manual com `$`, skills invocadas pelo modelo e listas de permissão de skills de agentes. Veja [Skills](/docs/features/skills).
- **memory**: Permite que agentes usem `set_memory` e `delete_memory` quando a memória está configurada e o usuário tem acesso. Habilitado por padrão; removido em tempo de execução quando a memória está desabilitada.
- **ask_user_question**: Permite que os agentes façam uma pausa para realizar de uma a quatro perguntas relacionadas em um único formulário e retomem com as respostas. Habilitado por padrão.
- **tools**: Concede ao agente acesso a várias ferramentas.
- **chain**: Habilita o recurso Beta para encadeamento de agentes, também conhecido como fluxos de trabalho Mixture-of-Agents (MoA).
- **ocr**: Opcionalmente aprimora o "Upload as Text" no chat e o "File Context" para agentes, permitindo que arquivos sejam enviados e processados com OCR. **Requer que um serviço de OCR seja configurado.**
- **run_in_background**: Torna a execução do Code Interpreter e das ferramentas de shell elegíveis para execução em segundo plano por padrão e habilita a opção de execução em segundo plano por ferramenta para MCP, Plugins e Actions elegíveis. Um interruptor no nível da Action habilita todas as operações elegíveis; Actions OAuth e operações que já definem um parâmetro `run_in_background` são excluídas. Um agente pode optar explicitamente por desativar o Code Interpreter. A configuração permite a execução em segundo plano; o modelo decide por chamada se deve utilizá-la. Requer `execute_code` e uma implementação configurada do Code Interpreter para código. Esta funcionalidade não está habilitada por padrão.
- **tool_intents**: Adiciona rótulos de intenção escritos pelo modelo em tempo real a chamadas de ferramentas elegíveis. Ferramentas nativas, incluindo ferramentas de Code Interpreter, optam automaticamente; ferramentas MCP podem ser habilitadas individualmente ou em massa no Agent Builder. Model Specs usam `describeIntent`. Esta funcionalidade não é habilitada por padrão.

Ao especificar as capabilities, você pode controlar os recursos disponíveis para os usuários ao interagir com agentes.

## Exemplo de Configuração [#example-configuration]

Aqui está um exemplo de configuração do endpoint `agents` com capacidades personalizadas e configurações de citação de arquivos:

```yaml filename="Agents Endpoint"
endpoints:
  agents:
    disableBuilder: false
    # File citation configuration
    maxCitations: 20
    maxCitationsPerFile: 5
    minRelevanceScore: 0.6
    # Custom capabilities
    capabilities:
      # Optional: enables Programmatic Tool Calling for MCP tools marked Programmatic in the Agent Builder.
      # - 'programmatic_tools'
      - 'execute_code'
      # Optional: makes Code Interpreter background-eligible and enables selected MCP, Plugin, and Action tools.
      # - 'run_in_background'
      # Optional: enables live intent labels for native and selected MCP tools.
      # - 'tool_intents'
      - 'file_search'
      - 'skills'
      - 'subagents'
      - 'actions'
      - 'artifacts'
      - 'context'
      - 'ocr'
      - 'web_search'
```

Neste exemplo:

- A interface do construtor está habilitada
- As citações de arquivos são limitadas a um total de 20, com no máximo 5 por arquivo
- Apenas fontes com 60%+ de relevância são incluídas
- Os agentes do LibreChat têm acesso à execução de código, pesquisa de arquivos (com citações), Skills, Subagentes, ações, artefatos, contexto de arquivos, serviços de OCR (se configurados) e recursos de pesquisa na web.
- O Programmatic Tool Calling permanece desativado, a menos que você adicione a capacidade `programmatic_tools` junto com `execute_code`
- As chamadas de ferramentas em segundo plano permanecem desativadas, a menos que você adicione `run_in_background`; as ferramentas do Code Interpreter tornam-se elegíveis por padrão, enquanto ferramentas MCP, Plugins e Actions elegíveis ainda exigem seleção.
- Os rótulos de intenção de ferramentas permanecem desativados, a menos que você adicione `tool_intents`; as ferramentas nativas então optam automaticamente, enquanto as ferramentas MCP ainda exigem seleção por ferramenta.

## managementApi

A API de Gerenciamento de Agentes em beta permite que clientes de máquina confiáveis criem, listem, leiam, atualizem e excluam Agentes, gerenciem seus arquivos e descubram ou editem Skills acessíveis. Ela é separada da [`remoteApi`](#remoteapi): as rotas de gerenciamento aceitam apenas identidades de máquina OIDC vinculadas à implantação e não aceitam chaves de API de Agentes Remotos do LibreChat ou sessões de navegador.

```yaml filename="endpoints / agents / managementApi"
endpoints:
  agents:
    managementApi:
      auth:
        oidc:
          enabled: true
          issuer: https://identity.example.com/
          audience: https://librechat.example.com/agents
          # jwksUri: https://identity.example.com/.well-known/jwks.json
        clients:
          - clientId: machine-client-id
            # subject: provider-specific-service-principal-subject
            userId: 507f1f77bcf86cd799439011
            tenantId: tenant-id
            enabled: true
```

## Notas [#notes]

- Não é recomendado desativar a interface do construtor, a menos que você esteja usando [modelSpecs](/docs/configuration/librechat_yaml/object_structure/model_specs) para definir uma lista de agentes para escolha.
- A configuração de citação de arquivos (`maxCitations`, `maxCitationsPerFile`, `minRelevanceScore`) só se aplica quando a capacidade `file_search` está habilitada.
- A pontuação de relevância é calculada usando similaridade vetorial, onde 1.0 representa uma correspondência perfeita e 0.0 representa nenhuma similaridade.
- Os limites de citação ajudam a equilibrar a recuperação abrangente de informações com a qualidade e o desempenho da resposta.
- A capacidade `context` funciona sem configuração de OCR usando métodos de análise de texto. O OCR aprimora a qualidade da extração quando configurado.
- A funcionalidade `ocr` requer que um serviço de OCR seja configurado (veja [Configuração de OCR](/docs/configuration/librechat_yaml/object_structure/ocr)).
- `maxSubagents` limita quantos subagentes um único agente pode referenciar. Isso não altera os limites de profundidade ou de grafo documentados em [Subagents](/docs/features/subagents#limits).
