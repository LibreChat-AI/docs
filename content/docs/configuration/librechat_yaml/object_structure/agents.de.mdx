## Beispiel [#example]

```yaml filename="Agents Endpoint"

    modelResponseBodyTimeoutMs: 900000

      create_file: 131072

    # (optional) Agent Capabilities available to all users. Omit the ones you wish to exclude. Defaults to list below.
    # Opt-in capabilities: "programmatic_tools", "stateful_code_sessions", "run_in_background", and "tool_intents".
    # capabilities: ["deferred_tools", "execute_code", "file_search", "web_search", "artifacts", "subagents", "actions", "context", "skills", "memory", "ask_user_question", "tools", "chain", "ocr"]
    # (optional) File citation configuration for file_search capability

      maxCatalogSkills: 20

        enabled: true
        maxPerUser: 5
      environments:
        - id: managed-default
          name: Managed Code API
          type: managed

          default: true
        - id: engineering-vm
          name: Engineering VM

            allowPrincipalWorkers: true
            tokenEnv: CODE_BRIDGE_ADMIN_TOKEN
    # eventDriven:
    #   selfUrl: https://librechat.internal
    backgroundTasks:
      completionWakeups: true

            tenantId: tenant-id

        oidc:
          enabled: false
```

## maxProviderErrorChars

Steuert, wie viel des Anbieter-Fehlertextes LibreChat beibehält, wenn ein Agent-Fehler nicht klassifiziert werden kann. Der Standardwert beträgt `2000` Zeichen. Setzen Sie ihn auf `0`, um den Anbietertext wegzulassen; das Maximum liegt bei `1000000`.

```yaml filename="endpoints / agents / maxProviderErrorChars"
maxProviderErrorChars: 2000
```

## repositoryInstructions

Steuert die Erkennung von Repository-Anweisungen für angehängte Code-Umgebungen. `timeoutMs` begrenzt die Anfrage zum Laden von Anweisungen auf einen Bereich von `100` bis `30000` Millisekunden und ist standardmäßig auf `2000` eingestellt.

```yaml filename="endpoints / agents / repositoryInstructions"
repositoryInstructions:
  timeoutMs: 2000
```

## Stream circuit breakers [#stream-circuit-breakers]

Diese Einstellungen stoppen einen Agent-Lauf, wenn ein Provider-Stream anscheinend ausufernde Tool-Argumente oder eine unbegrenzte Sequenz von Delta-Events erzeugt.

<OptionTable
  options={[
    [
      'maxToolCallArgBytes',
      'Number',
      'Maximale kumulative Bytes für die Argumente eines gestreamten Tool-Aufrufs. Auf 0 setzen, um den globalen Schutz zu deaktivieren.',
      '65536',
    ],
    [
      'maxDeltaEventsPerTurn',
      'Number',
      'Maximale Anzahl an gestreamten Ereignissen für einen Modell-Generierungsdurchlauf. Auf 0 setzen oder weglassen, um diesen Schutz zu deaktivieren.',
      '0 (disabled)',
    ],
    [
      'maxToolCallArgBytesByTool',
      'Object',
      'Pro-Tool-Argument-Byte-Überschreibungen, indiziert nach dem modellseitigen Tool-Namen. Ein Wert von 0 deaktiviert den Schutz für dieses Tool.',
      'create_file: 131072',
    ],
  ]}
/>

LibreChat verwendet ein globales Argument-Limit von 64 KiB und liefert eine 128 KiB-Überschreibung für `create_file` mit, deren legitime Payloads oft größer sind. Einträge in `maxToolCallArgBytesByTool` werden über diese eingebaute Überschreibung zusammengeführt. Wenn eine der Schutzmaßnahmen greift, bricht LibreChat den laufenden Provider-Stream ab und meldet, welches Limit überschritten wurde.

```yaml filename="endpoints / agents / stream circuit breakers"
maxToolCallArgBytes: 65536
maxDeltaEventsPerTurn: 100000
maxToolCallArgBytesByTool:
  create_file: 262144
  large_import: 524288
```

Um jede Argumentgrößen-Beschränkung zu deaktivieren, setzen Sie sowohl das globale Limit als auch die mitgelieferte `create_file`-Überschreibung auf `0`:

```yaml
maxToolCallArgBytes: 0
maxToolCallArgBytesByTool:
  create_file: 0
```

## titleTiming

<OptionTable
  options={[

**Standard:** `"immediate"`


## activityLabel

Setzen Sie `activityLabel: true`, um jeden Block von Agent-Reasoning und Tool-Aufrufen unter einer generierten einzeiligen Überschrift zu gruppieren. Verwenden Sie `activityModel`, `activityEndpoint`, `activityPrompt`, `activityMaxPerRun` und `activityCharLimit`, um den zusätzlichen Modellaufruf und dessen Kosten zu steuern. Siehe [Agent Activity Groups](/docs/configuration/librechat_yaml/object_structure/shared_endpoint_settings#agent-activity-groups) für die vollständige Feldreferenz und die Rangfolgeregeln.

```yaml filename="endpoints / agents / activity groups"
activityLabel: true
activityEndpoint: openAI
activityModel: gpt-4.1-nano
activityMaxPerRun: 20
activityCharLimit: 600
activityPhaseLabel: true
activityPhaseMaxPerRun: 5
```

`activityPhaseLabel` kann unabhängig eine eingeklappte übergeordnete Zusammenfassung um jede Ausführungsphase hinzufügen, die mindestens zwei logische Aktivitäten enthält. Verwenden Sie `activityPhaseModel`, `activityPhaseEndpoint`, `activityPhasePrompt` und `activityPhaseMaxPerRun`, um diese Aufrufe anzupassen; `activityCharLimit` wird mit untergeordneten Aktivitätsbezeichnungen geteilt.

## capabilities

<OptionTable
  options={[
    [
      'capabilities',
      'Array/List of Strings',
      'Legt die Agent-Funktionen fest, die allen Benutzern für den agents endpoint zur Verfügung stehen.',
      'Defines the agent capabilities that are available to all users for the agents endpoint. You can omit the capabilities you wish to exclude from the list.',
    ],
  ]}
/>

**Standard:** `["deferred_tools", "execute_code", "file_search", "web_search", "artifacts", "subagents", "actions", "context", "skills", "memory", "ask_user_question", "tools", "chain", "ocr"]`

`programmatic_tools`, `stateful_code_sessions`, `run_in_background` und `tool_intents` sind Opt-in-Funktionen und müssen explizit hinzugefügt werden. Programmatic Tools und stateful sessions erfordern zudem `execute_code` sowie eine kompatible Code Interpreter-Bereitstellung. Der Agent Builder deaktiviert die Auswahl von Programmatic MCP ohne Code Interpreter, und der Server entfernt veraltete programmatic caller-Optionen, wenn die Codeausführung nicht verfügbar ist. `run_in_background` macht Code Interpreter-Tools standardmäßig berechtigt und ermöglicht ein pro-Tool-Opt-in für berechtigte MCP-, Plugin- und Action-Tools; die Codeausführung im Hintergrund erfordert ebenfalls `execute_code` und Code Interpreter.

`stateful_code_sessions` ist hochgradig experimentell. Es erfordert eine separate `stateful`-Profil Code Interpreter-Route, die mit [`LIBRECHAT_CODE_BASEURL_STATEFUL`](/docs/configuration/dotenv#stateful-code-interpreter-endpoint) oder [`statefulCodeSessions.environments`](#statefulcodesessions) konfiguriert ist. Stateful-Anfragen schlagen fehl (fail closed), anstatt auf den normalen zustandslosen Dienst zurückzugreifen. Im Agent Builder wählt jeder aktivierte Agent einen Arbeitsbereichsbereich für Benutzer, Agent-und-Benutzer oder Konversation aus und, sofern benannte Backends konfiguriert sind, eine Ausführungsumgebung. Neue Agents starten mit dem standardmäßigen persönlichen Bereich des Benutzers und der Standard-Ausführungsumgebung der Bereitstellung.

**Beispiel:**

```yaml filename="endpoints / agents / capabilities"
capabilities:
  - 'deferred_tools'
  # Optional: enables Programmatic Tool Calling for MCP tools marked Programmatic in the Agent Builder.
  # Requires execute_code and a Code Interpreter deployment with the Tool Call Server component.
  # - 'programmatic_tools'
  - 'execute_code'
  - 'file_search'
  - 'web_search'
  - 'artifacts'
  - 'subagents'
  - 'actions'
  - 'context'
  - 'skills'
  - 'memory'
  - 'ask_user_question'
  - 'tools'
  - 'chain'
  - 'ocr'
  # Optional and highly experimental: reuse a user-, agent-and-user-, or
  # conversation-scoped workspace. Requires LIBRECHAT_CODE_BASEURL_STATEFUL
  # or a named statefulCodeSessions environment.
  # - 'stateful_code_sessions'
  # Optional: allow eligible Code Interpreter, MCP, Plugin, and Action tools to run as background tasks.
  # - 'run_in_background'
  # Optional: show live model-written intent labels for native and selected MCP tools.
  # - 'tool_intents'
```

**Hinweis:** Dieses Feld ist optional. Wenn es weggelassen wird, besteht das Standardverhalten darin, alle Funktionen einzubeziehen, die in der Standardeinstellung aufgeführt sind.

## statefulCodeSessions

Konfiguriert die Freigabebereiche und optionalen Ausführungs-Backends für hochgradig experimentelle, zustandsbehaftete Code Interpreter-Arbeitsbereiche.

<Callout type="warning" title="Hochgradig experimentell">
  Stateful Code Sessions, benannte Ausführungsumgebungen, angehängte Worker und Pairing befinden sich in einer frühen experimentellen Phase. Ihr Verhalten, ihre Konfiguration, ihre Persistenzeigenschaften und ihr Integrationsprotokoll können sich grundlegend ändern.
</Callout>

<OptionTable
  options={[
    [
      'allowedEnvironments',
      'Array/List of Strings',
      'Zulässige zustandsbehaftete Workspace-Scopes: `user`, `agent-user` und/oder `conversation`.',
      '["user", "agent-user", "Konversation"]',
    ],
    [
      'environments',
      'Array of Objects',
      'Optionale benannte verwaltete oder angehängte Code-API-Umgebungen, die im Agent Builder angezeigt werden.',
      'Unset; LIBRECHAT_CODE_BASEURL_STATEFUL remains the stateful endpoint',
    ],
    [
      'principalWorkers',
      'Object',
      'Optionale Bereitstellungsobergrenze für die Registrierung persönlicher Worker. `enabled` ist standardmäßig true und `maxPerUser` ist standardmäßig 5.',
      '{ enabled: true, maxPerUser: 5 }',
    ],
    [
      'conversationMoves',
      'Object',
      'Opt-in für vom Besitzer autorisierte Workspace-Übergänge für gespeicherte Konversationen. `allowAttachDetach` erlaubt zusätzlich das Anhängen oder Verlassen eines angehängten Workspaces.',
      'Disabled',
    ],
  ]}
/>

Angehängte Umgebungen akzeptieren `environments[].configSchema.limits.maxQueueWaitMs`, was steuert, wie lange eine Anfrage warten darf, während sie auf Workspace-Kapazität wartet. Der Standardwert und das Maximum liegen bei `300000` Millisekunden (5 Minuten). Setzen Sie diesen Wert auf `0`, um Client-Wiederholungsversuche nach dem ersten Zulassungsversuch zu deaktivieren; dies bricht keine Arbeit ab, die bereits zugelassen wurde oder läuft. Diese Felder gehören unter `configSchema.limits`, **nicht** `userConfig.bash`.

`environments[].configSchema.limits.maxRequestTimeoutMs` begrenzt optional die **gesamte HTTP-Zeit für einen Workspace-Tool-Aufruf**, einschließlich Zulassung (Admission), Ausführung, Abwicklung (Settlement) und Zustellung. Es akzeptiert Werte von `1` bis `610000` ms, jedoch weist die Konfiguration Budgets zurück, die zu klein sind, um nach der Zulassung und der 10-sekündigen Reserve für Abwicklung/Zustellung noch Zeit für die Befehlsausführung zu lassen. Ohne diesen Wert hat die Zulassung weiterhin ein Budget von 30 Sekunden pro Versuch; `maxQueueWaitMs` bleibt ein separater Wiederholungshorizont. **Aktivieren Sie keine längere Zulassungszeit**, bis jede LibreChat API-Replika dieses Feld versteht, die Code API-Route die Warteschlangen-Kontingente pro Anfrage berücksichtigt und das kürzeste Timeout entlang des Live-Proxy-/Ingress-Pfads gemessen wurde. Eine abgelaufene Mutation könnte auf dem Worker abgeschlossen worden sein, daher führt LibreChat bei einem mehrdeutigen Timeout keine Wiederholung durch.

Bei einem gesamten Anfrage-Budget reserviert `environments[].configSchema.limits.minCommandAdmissionMs` Zeit für einen Befehl, um in den Worker einzutreten, bevor die Ausführung beginnt. Der Standardwert beträgt `10000` ms; setzen Sie einen Wert zwischen `1000` und `300000` ms. Das Anfrage-Budget muss diesen Spielraum zuzüglich 10000 ms für die Bereitstellungs-/Zustellungs-Karenzzeit **überschreiten**; ohne ein Gesamtbudget hat die Einstellung keine Auswirkung. Das Bash-Ausführungslimit, das einem Agenten mitgeteilt wird, ist der kleinere Wert aus seinem konfigurierten oder dem vorgelagerten Höchstwert sowie der nach diesen Reserven verbleibenden Zeit. Zum Beispiel kündigt ein Anfrage-Budget von 90000 ms mit einem Befehls-Höchstwert von 80000 ms und der Standardreserve maximal einen 70000 ms-Befehl an.

```yaml filename="endpoints / agents / statefulCodeSessions"
statefulCodeSessions:
  allowedEnvironments:
    - 'user'
    - 'agent-user'
    - 'conversation'
  principalWorkers:
    enabled: true
    maxPerUser: 5
  environments:
    - id: managed-default
      name: Managed Code API
      type: managed
      baseURL: https://code.example.com/v1
      default: true
    - id: engineering-vm
      name: Engineering VM
      type: attached
      baseURL: https://code-bridge.example.com/v1
      owner: deployment
      pairing:
        workerId: engineering-vm
        tokenEnv: CODE_BRIDGE_ADMIN_TOKEN
    - id: personal-workers
      name: Personal Code Workers
      type: attached
      baseURL: https://code-bridge.example.com/v1
      owner: deployment
      configSchema:
        limits:
          maxCommandTimeoutMs: 120000
          # Before enabling, verify Code API queue allowances and the live proxy deadline.
          # maxRequestTimeoutMs: 160000
          # minCommandAdmissionMs: 10000
          # maxQueueWaitMs: 300000
        # After upgrading Code API and opting in the worker with --linked-worktree-lanes:
        # workspaces:
        #   linkedWorktrees: true
        # Optional: require exact matching even on workers supporting tolerant edits.
        # edits:
        #   tolerantMatching: false
        permissions:
          fileWrite:
            allowed: [allow, ask, deny]
            default: ask
          commandExecution:
            allowed: [ask, deny]
            default: ask
      pairing:
        allowPrincipalWorkers: true
        tokenEnv: CODE_BRIDGE_ADMIN_TOKEN
```

`allowedEnvironments` ist erforderlich, sobald der Block vorhanden ist, und muss mindestens einen Workspace-Scope enthalten. Lassen Sie den gesamten Block weg, um alle drei Scopes zuzulassen und die Weiterleitung zustandsbehafteter Arbeit über [`LIBRECHAT_CODE_BASEURL_STATEFUL`](/docs/configuration/dotenv#stateful-code-interpreter-endpoint) fortzusetzen. Der persönliche Standardwert und der Agent Builder erlauben nur zulässige Werte. Wenn ein Administrator die Richtlinie verschärft, bleibt ein gespeicherter persönlicher Standardwert sichtbar, aber deaktiviert, und neue Agents verwenden den ersten zulässigen Scope. Bestehende aktivierte Agents behalten ihren gespeicherten Scope bei, aber ein nun unzulässiger Scope schlägt zur Laufzeit fehl, bis der Agent neu konfiguriert wird.

`conversationMoves.enabled: true` ermöglicht es dem Besitzer einer Konversation, einen versiegelten angehängten Workspace explizit in eine kompatible Umgebung zu verschieben und einen fehlenden Workspace wiederherzustellen, ohne den Chatverlauf zu ersetzen oder alte Workspace-Dateien wiederherzustellen. Um zusätzlich zu erlauben, dass ein gespeicherter Chat einen Workspace **anhängt** oder für einen normalen Chat **verlässt**, setzen Sie `conversationMoves.allowAttachDetach: true`. Beide Schalter sind standardmäßig deaktiviert; das alleinige Aktivieren von Verschiebungen behält das reine Verschiebeverhalten bei. Aktualisieren Sie **alle** API-Replikate und aktivieren Sie dann [`CODE_ENVIRONMENT_DECISION_VERSION=1`](/docs/configuration/dotenv#code-interpreter), bevor Sie sich dafür entscheiden. Eigentümerschaft, Zielzugriff, aktive Arbeit und die aktuelle Richtlinie werden beim Übergang erneut überprüft; eine laufende Generierung kann nicht verschoben werden.

```yaml filename="endpoints / agents / statefulCodeSessions / conversationMoves"
statefulCodeSessions:
  allowedEnvironments: ['user', 'agent-user', 'conversation']
  conversationMoves:
    enabled: true
    allowAttachDetach: true
```

`principalWorkers` steuert die Self-Service-Registrierung für persönlich zugewiesene Worker. Fehlende Werte werden standardmäßig als `enabled: true` und `maxPerUser: 5` aufgelöst; setzen Sie `enabled: false` oder `maxPerUser: 0`, um neue Registrierungen zu unterbinden. Das Limit zählt jede registrierte persönliche Umgebung für diesen Benutzer über alle konfigurierten Control Planes hinweg, einschließlich offline befindlicher Worker. Eine Senkung des Limits oder die Deaktivierung der Registrierung widerruft keine bestehenden Umgebungen.

Die Deployment YAML ist die absolute Obergrenze. Eine Rollen-, Gruppen- oder Benutzerkonfigurationsüberschreibung kann die Registrierung deaktivieren oder `maxPerUser` senken, aber den Deployment-Wert nicht erhöhen. Ein Benutzer sieht nur dann Pairing-fähige Control Planes, wenn das effektive Limit größer als null ist, [`pairing.allowPrincipalWorkers`](#statefulcodesessions) auf dieser Control Plane aktiviert ist, eine Principal-Authentifizierung verfügbar ist und der Benutzer über die Berechtigung zur Verwaltung von Code-Umgebungen verfügt.

Wenn `environments` nicht leer ist, erfordert jeder Eintrag eine eindeutige `id`, einen Anzeige-`name`, einen `type` von `managed` oder `attached` sowie eine HTTP(S)-`baseURL` ohne Query-String oder Fragment. Wenn die Liste ausführbare Umgebungen enthält, muss genau einer dieser Einträge `default: true` gesetzt haben. Der Agent Builder fügt dann eine Auswahlmöglichkeit für die **Execution environment** hinzu; die Einstellung **Deployment default** verwendet diesen Standardeintrag. Eine Liste, die nur Self-Service-Pairing-Control-Planes enthält, benötigt keinen Standardwert. Ein Agent, der eine Umgebung benennt, die später entfernt wird oder nicht mehr zugänglich ist, schlägt fehl (fails closed), anstatt auf ein anderes Backend auszuweichen.

- `managed` verweist direkt auf einen vom Operator verwalteten zustandsbehafteten Code API.
- `attached` verweist auf ein kompatibles Code API `remote-bridge`-Backend, das Aufgaben an einen ausgehenden `@librechat/code`-Worker delegiert. Der Worker benötigt keinen eingehenden öffentlichen Port, aber sein lokaler Ausführungs-endpoint erfordert dennoch eine angemessene Isolierung.
- `workerId` leitet optional eine angehängte Umgebung an einen ausgehenden Worker weiter. Dies ist nur serverseitig verfügbar und wird nicht über die Client-Startkonfiguration offengelegt.
- `owner` ist standardmäßig auf `deployment` gesetzt. Principal-owned Umgebungen werden über die authentifizierte Code Environments API von LibreChat erstellt, durch ACLs geschützt und nur für autorisierte Anfragen zusammengeführt; fügen Sie keine vom Client bereitgestellten URLs in die deployment YAML ein.
- `pairing` ist optional und nur für `attached`-Einträge gültig, die sich im Besitz der Bereitstellung befinden. `pairing.workerId` identifiziert einen von einem Operator verwalteten Worker für die Registrierung, während `pairing.allowPrincipalWorkers: true` es autorisierten Benutzern ermöglicht, besitzergebundene Worker bei dieser Control Plane zu registrieren. Mindestens eines dieser Felder ist erforderlich, wenn `pairing` vorhanden ist.
- `pairing.tokenEnv` benennt die Umgebungsvariable, die das Bridge-Administrator-Token enthält; sie enthält niemals das Token selbst. Pairing erfordert HTTPS, außer bei der Loopback-Entwicklung.
- `configSchema.permissions` ermöglicht es autorisierten Eigentümern optional, die Richtlinien für `fileWrite` und `commandExecution` für persönliche Umgebungen unter **Einstellungen > Code-Umgebungen** festzulegen. Jedes Feld erfordert eine nicht leere `allowed`-Liste, die `allow`, `ask` und/oder `deny` enthält; `default` ist `ask`, wenn es weggelassen wird, und muss in `allowed` enthalten sein. LibreChat lehnt gespeicherte Werte ab, die außerhalb der Liste des Administrators liegen.
- `configSchema.limits.maxCommandTimeoutMs` legt das maximale Bash-Timeout fest, das das Modell für diese Umgebung anfordern darf. Es akzeptiert Werte von `1` bis `300000` ms; bei Auslassung bleibt der Standardwert von 30 Sekunden erhalten. Bei einem gesamten Anfragebudget passt sich das angegebene Befehls-Timeout zudem an die verbleibende Zeit nach Befehlszulassung, -abwicklung und -zustellung an. Dies ist eine Obergrenze für die Bereitstellung und kann nicht vom Benutzer konfiguriert werden.
- `configSchema.workspaces.linkedWorktrees: true` aktiviert die pro-Worktree-Planung nur für angehängte Workspaces, die `git_linked_worktree` ankündigen; das Weglassen behält alle Anfragen in der Root-Lane des Checkouts bei. Aktualisieren Sie LibreChat, **bevor** ein Worker diesen Bereich ankündigt, stellen Sie eine Code-API bereit, die Linked-Worktree-Lanes unterstützt, und starten Sie dann den Worker mit `--linked-worktree-lanes`, bevor Sie die YAML-Einstellung aktivieren. Dateivorgänge, die auf einen Pfad innerhalb von `.worktrees/<name>` abzielen, sowie Bash-Befehle mit einem dortigen `cwd` verwenden diese Lane und geben Checkout-relative Pfade zurück. Befehle, die innerhalb ihres Befehlstextes `cd` verwenden, Checkout-Root-Vorgänge, Konversations-Workspace-Instanzen und Umgebungsaktionen bleiben auf die Root beschränkt.
- `configSchema.edits.tolerantMatching` erlaubt standardmäßig ein Whitespace-tolerantes Fallback bei verbundenen Workern, die `tolerant_match` unterstützen; setzen Sie es auf `false`, um eine exakte Übereinstimmung zu erzwingen, einschließlich geschützter Bearbeitungsvorschauen. Die Übereinstimmung muss eindeutig bleiben, es sei denn, die Bearbeitung setzt explizit `replace_all`. Ältere Worker erhalten keine neuen Matching-Felder; ein angehängtes `replace_all` wird vor dem Versand abgelehnt, sofern der Worker dies nicht unterstützt. Diese Funktionen erfordern eine kompatible Code API und Worker-Builds, die [Code Interpreter #271](https://github.com/LibreChat-AI/code-interpreter/pull/271) implementieren.
- Konfigurieren Sie `settings` nicht in der Deployment-YAML. LibreChat stellt dieses anfragebezogene Feld aus den vom Server validierten Einstellungen des authentifizierten Eigentümers bereit.
- Nur die Richtlinien für das Schreiben von Dateien und die Ausführung von Befehlen sind durch den Benutzer konfigurierbar. Isolierung, Netzwerk, Mounts, privilegierte Ausführung, Ingress, Egress und Secrets bleiben unter der Kontrolle des Administrators.
- Wenn sowohl die `workerId` auf oberster Ebene als auch `pairing.workerId` vorhanden sind, müssen sie übereinstimmen. Ein Eintrag mit `allowPrincipalWorkers: true`, bei dem keine der beiden Worker-IDs nur für das Pairing bestimmt ist, wird von den Ausführungsselektoren ausgeschlossen und kann nicht auf `default: true` gesetzt werden.

Die angehängte Ausführung aktiviert automatisch eine sichere Genehmigungs-Baseline: Dateischreibvorgänge sowie Befehls- oder Codeausführungen erfordern eine Bestätigung, während schreibgeschützte Vorgänge und Suchoperationen weiterhin unter der regulären Tool-Richtlinie laufen. Die Baseline ist auf den Agenten beschränkt, der die angehängte Umgebung verwendet. Wenn keine Benutzereinstellung verfügbar ist, verwendet LibreChat `ask`; [`toolApproval.enabled: false`](#toolapproval) ist die Notfall-Außerkraftsetzung durch den Administrator, die diese Baseline der angehängten Umgebung deaktiviert. Aufrufer ohne Unterstützung für Genehmigungen und Fortsetzungen schlagen fehl („fail closed“), sofern diese explizite Außerkraftsetzung nicht festgelegt ist.

Die angehängte Ausführung erfordert einen passenden experimentellen Code Interpreter remote-bridge Build. Das Pairing authentifiziert die ausgehende Worker-Verbindung; es ersetzt nicht die Sandbox- oder VM-Isolierung. Benutzer mit der Berechtigung zur Verwaltung von Code-Umgebungen können unter **Einstellungen > Code-Umgebungen** Pairings vornehmen, Richtlinien für zulässige Tools konfigurieren und persönliche Worker widerrufen. Siehe [Stateful Code Sessions](/docs/features/code_interpreter#stateful-code-sessions).

`eventDriven.idlePolling` begrenzt das Wiederherstellungs-Polling pro Replikat, wenn nichts bereit ist: `deliveryMaxIntervalMs` ist standardmäßig auf `15000` gesetzt (gültig `1000`–`300000`), `queuedTurnMaxIntervalMs` und `maintenanceMaxIntervalMs` sind jeweils standardmäßig auf `120000` gesetzt (gültig `30000`–`300000`) und `completionWaitMaxIntervalMs` ist standardmäßig auf `60000` gesetzt (gültig `5000`–`300000`). Letzteres begrenzt erneute Überprüfungen, während ein Hintergrund- oder Subagent-Ergebnis aussteht oder dessen übergeordneter Turn beschäftigt ist. Bereitschaftsereignisse beschleunigen die Zustellung; diese Grenzwerte dienen als Fallback für replikatübergreifende Wiederherstellungen und Absturzwiederherstellungen, anstatt die normale Abschlusslatenz zu definieren.

```yaml filename="endpoints / agents / eventDriven / idlePolling"
eventDriven:
  idlePolling:
    deliveryMaxIntervalMs: 15000
    queuedTurnMaxIntervalMs: 120000
    maintenanceMaxIntervalMs: 120000
    completionWaitMaxIntervalMs: 60000
```

Die Event Actor detached Action-Vervollständigung wird automatisch aus dem integrierten Generierungsspeicher ausgewählt. Die In-Memory-Ausführung ist prozesslokal; Redis-Generierungs-Streams fügen eine dauerhafte Neustart-Wiederherstellung und Replica-Übergabe hinzu. Es ist kein `librechat.yaml`-Schalter oder Feature-Flag in der .env erforderlich. Siehe [Agent Event Runtime](/docs/configuration/dotenv#agent-event-runtime).

## toolApproval

Steuert die manuelle Überprüfung für Agent-Tool-Aufrufe. Die bereitstellungsweite Richtlinie ist deaktiviert, wenn dieser Block weggelassen wird. Eine Ausnahme bildet ein Agent, der eine angehängte Code-Umgebung verwendet: LibreChat aktiviert seine bereichsbezogene „Ask-by-default“-Sicherheitsrichtlinie, es sei denn, der Administrator setzt explizit `enabled: false`. Wenn die Überprüfung angewendet wird, pausieren entsprechende Aufrufe, bis der Benutzer eine zulässige Entscheidung übermittelt, wie z. B. das Genehmigen, Ablehnen oder Bearbeiten der Argumente.

<OptionTable

    ['allow', 'Array of strings', 'Glob-Muster für Aufrufe, die ohne Aufforderung ausgeführt werden können.', ''],

    ['ask', 'Array of strings', 'Glob-Muster für Aufrufe, die immer eine Überprüfung erfordern.', ''],
    [
      'reason',
      'String',

      '',
    ],
  ]}
/>

Muster verwenden Glob-Matching. MCP-Tools können mit `mcp:<server>:<tool>` eingegrenzt werden; `mcp:github:*` entspricht beispielsweise jedem Tool des `github`-Servers. LibreChat wendet statische Regeln und Hook-Matcher auf MCP-Laufzeitnamen und modellseitige Aliase an, einschließlich Tools, die über verschachtelte Subagents erreichbar sind. Statische Regeln werden in der Reihenfolge `deny`, `ask` und dann `allow` ausgewertet, bevor der gewählte Modus den Fallback bereitstellt. Eine Deny-Regel hat daher immer Vorrang, auch im `bypass`-Modus.

```yaml filename="endpoints / agents / toolApproval"
toolApproval:
  enabled: true
  mode: default
  allow:
    - 'mcp:analytics:read_*'
  deny:
    - 'mcp:*:delete_*'
  ask:
    - 'mcp:*:*'
  reason: 'Review {tool} before it runs.'
```

Hooks werden einmal beim Serverstart geladen und im LibreChat-Prozess ausgeführt. Jeder Eintrag akzeptiert ein `module`, ein optionales Tool-Name `matcher` Regex und ein optionales `options`-Objekt, das an den Builder des Moduls übergeben wird. Laden Sie nur Code, dem Sie vertrauen. Rollen- oder mandantenspezifische Überschreibungen laden Hook-Module nicht neu; implementieren Sie kontextbezogenes Verhalten innerhalb des Hooks.

```yaml filename="endpoints / agents / toolApproval / hooks"
toolApproval:
  enabled: true
  hooks:
    - module: '@acme/librechat-approval-hook'
      matcher: '^mcp:production:'
      options:
        requireTicket: true
```

## fileSharing

`fileSharing` ist eine optionale, auf den Laufzeitbereich beschränkte Freigabe für delegierte Agenten-Arbeit. Setzen Sie hier `enabled: true` und aktivieren Sie `subagents.shareFiles` bei jedem delegierenden Agenten. Eingaben sind für Empfänger schreibgeschützt; Ausgaben bleiben privat, sofern sie nicht explizit veröffentlicht werden, und veröffentlichte Dateien bleiben nach dem Lauf herunterladbar.

```yaml filename="endpoints / agents / fileSharing"
endpoints:
  agents:
    fileSharing:
      enabled: true
      allowSiblingSharing: false
      maxFiles: 100
      maxPrivateBytes: 268435456
      ttlMs: 3600000
```

`allowSiblingSharing` erlaubt explizit benannte gleichrangige oder untergeordnete Empfänger. `maxFiles` reicht von `1` bis `1000`; `maxPrivateBytes` begrenzt die gespeicherten privaten Ausgabe-Snapshots; und `ttlMs` ist die aktive Manifest-Lebensdauer, die auf 24 Stunden begrenzt ist. Wenn dieser Block weggelassen wird, bleibt das Teilen deaktiviert.

```yaml filename="endpoints / agents / minRelevanceScore"
minRelevanceScore: 0.45
```

### Beispiele für die Konfiguration von Dateizitaten [#file-citation-configuration-examples]

**Standardkonfiguration (Ausgewogen)**

```yaml
endpoints:
  agents:
    maxCitations: 30
    maxCitationsPerFile: 7
    minRelevanceScore: 0.45
```

Bietet umfassende Zitate, verhindert gleichzeitig übermäßig lange Antworten und filtert minderwertige Übereinstimmungen heraus.

**Strenge Konfiguration (Hohe Qualität)**

```yaml
endpoints:
  agents:
    maxCitations: 10
    maxCitationsPerFile: 3
    minRelevanceScore: 0.7
```

Enthält nur hochrelevante Zitate mit strikten Begrenzungen für fokussierte Antworten.

**Umfassende Konfiguration (Recherche)**

```yaml
endpoints:
  agents:
    maxCitations: 50
    maxCitationsPerFile: 10
    minRelevanceScore: 0.0
```

Maximale Informationsgewinnung für umfassende Rechercheaufgaben, einschließlich aller Quellen, unabhängig von ihrer Relevanz.

## Agent-Funktionen [#agent-capabilities]

Das Feld `capabilities` ermöglicht es Ihnen, spezifische Funktionalitäten für Agents zu aktivieren oder zu deaktivieren. Die verfügbaren Funktionen sind:

- **deferred_tools**: Ermöglicht es Agenten, verzögerte MCP-Tools zur Laufzeit zu entdecken, anstatt jedes Tool vorab in den Kontext zu laden.
- **programmatic_tools**: Aktiviert den programmatischen Tool-Aufruf (Programmatic Tool Calling) für MCP-Tools, die im Agent Builder als Programmatic markiert sind. Erfordert `execute_code` und eine Code Interpreter-Bereitstellung mit der Tool Call Server-Komponente. Diese Funktion ist optional und standardmäßig nicht aktiviert.
- **execute_code**: Ermöglicht dem Agenten, Code auszuführen.
- **stateful_code_sessions**: Ermöglicht es Agenten, die sich dafür entscheiden, einen Code Interpreter-Arbeitsbereich auf Benutzer-, Agent-und-Benutzer- oder Konversationsebene wiederzuverwenden. Erfordert `execute_code`, eine kompatible Code Interpreter-Bereitstellung sowie die erweiterte Einstellung pro Agent. Neue Agenten verwenden den bevorzugten Bereich des angemeldeten Benutzers. Diese Funktion ist hochgradig experimentell, standardmäßig nicht aktiviert und kann sich während der Experimentierphase erheblich ändern; betrachten Sie das aktuelle Verhalten oder die Konfiguration nicht als stabilen Produktionsvertrag.
- **file_search**: Ermöglicht dem Agenten, Dateien zu durchsuchen und mit ihnen zu interagieren. Wenn diese Funktion aktiviert ist, wird das Zitierverhalten durch die Einstellungen `maxCitations`, `maxCitationsPerFile` und `minRelevanceScore` gesteuert.
- **web_search**: Aktiviert die Websuchfunktion für Agents, wodurch diese Informationen aus dem Internet suchen und abrufen können.
- **artifacts**: Ermöglicht es dem Agenten, interaktive Artefakte (React-Komponenten, HTML, Mermaid-Diagramme) zu generieren.
- **subagents**: Ermöglicht isolierte Child-Agent-Ausführungen mit eigenem Kontext. Siehe [Subagents](/docs/features/subagents).
- **actions**: Erlaubt dem Agenten, vordefinierte Aktionen auszuführen.
- **context**: Aktiviert die Funktion „Als Text hochladen“ im Chat sowie den „Dateikontext“ für Agents, wodurch Benutzer Dateien hochladen können, deren Inhalt extrahiert und direkt in die Konversation einbezogen wird.
- **skills**: Aktiviert Skills in der Seitenleiste, manuelle `$`-Aufrufe, von Modellen aufgerufene Skills und Agent-Skill-Allowlists. Siehe [Skills](/docs/features/skills).
- **memory**: Ermöglicht es Agenten, `set_memory` und `delete_memory` zu verwenden, wenn memory konfiguriert ist und der Benutzer Zugriff hat. Standardmäßig aktiviert; wird zur Laufzeit entfernt, wenn memory deaktiviert ist.
- **ask_user_question**: Ermöglicht es Agenten, zu pausieren, um ein bis vier zusammenhängende Fragen in einem einzigen Formular zu stellen und mit den Antworten fortzufahren. Standardmäßig aktiviert.
- **tools**: Gewährt dem Agenten Zugriff auf verschiedene Tools.
- **chain**: Aktiviert die Beta-Funktion für Agent-Chaining, auch bekannt als Mixture-of-Agents (MoA)-Workflows.
- **ocr**: Verbessert optional „Als Text hochladen“ im Chat sowie den „Dateikontext“ für Agents, wodurch Dateien hochgeladen und mittels OCR verarbeitet werden können. **Erfordert die Konfiguration eines OCR-Dienstes.**
- **run_in_background**: Macht die Ausführung von Code Interpreter und Shell-Tools standardmäßig hintergrundfähig und ermöglicht ein pro-Tool-Opt-in für den Hintergrund bei geeigneten MCP-, Plugin- und Action-Tools. Ein Schalter auf Action-Ebene aktiviert dies für alle geeigneten Operationen; OAuth-Actions und Operationen, die bereits einen `run_in_background`-Parameter definieren, sind ausgeschlossen. Ein Agent kann den Code Interpreter explizit vom Hintergrundbetrieb ausschließen. Die Einstellung erlaubt die Hintergrundausführung; das Modell entscheidet pro Aufruf, ob es diese nutzt. Erfordert `execute_code` und eine konfigurierte Code Interpreter-Bereitstellung für Code. Diese Funktion ist standardmäßig nicht aktiviert.
- **tool_intents**: Fügt berechtigten Tool-Aufrufen live vom Modell geschriebene Intent-Labels hinzu. Native Tools, einschließlich Code Interpreter-Tools, werden automatisch einbezogen; MCP-Tools können im Agent Builder einzeln oder gesammelt aktiviert werden. Model Specs verwenden `describeIntent`. Diese Funktion ist standardmäßig nicht aktiviert.

Durch die Angabe der capabilities können Sie die Funktionen steuern, die Benutzern bei der Interaktion mit Agents zur Verfügung stehen.

## Beispielkonfiguration [#example-configuration]

Hier ist ein Beispiel für die Konfiguration des `agents` endpoint mit benutzerdefinierten Fähigkeiten und Einstellungen für Dateizitate:

```yaml filename="Agents Endpoint"
endpoints:
  agents:
    disableBuilder: false
    # File citation configuration
    maxCitations: 20
    maxCitationsPerFile: 5
    minRelevanceScore: 0.6
    # Custom capabilities
    capabilities:
      # Optional: enables Programmatic Tool Calling for MCP tools marked Programmatic in the Agent Builder.
      # - 'programmatic_tools'
      - 'execute_code'
      # Optional: makes Code Interpreter background-eligible and enables selected MCP, Plugin, and Action tools.
      # - 'run_in_background'
      # Optional: enables live intent labels for native and selected MCP tools.
      # - 'tool_intents'
      - 'file_search'
      - 'skills'
      - 'subagents'
      - 'actions'
      - 'artifacts'
      - 'context'
      - 'ocr'
      - 'web_search'
```

In diesem Beispiel:

- Die Builder-Schnittstelle ist aktiviert
- Dateizitate sind auf insgesamt 20 begrenzt, mit maximal 5 pro Datei
- Nur Quellen mit einer Relevanz von 60%+ werden einbezogen
- LibreChat Agents haben Zugriff auf Code-Ausführung, Dateisuche (mit Zitaten), Skills, Subagents, Aktionen, Artefakte, Dateikontext, OCR-Dienste (sofern konfiguriert) sowie Web-Suchfunktionen.
- Programmatic Tool Calling bleibt deaktiviert, es sei denn, Sie fügen die `programmatic_tools` Capability zusammen mit `execute_code` hinzu.
- Hintergrund-Tool-Aufrufe bleiben deaktiviert, es sei denn, Sie fügen `run_in_background` hinzu; Code Interpreter-Tools werden dann standardmäßig berechtigt, während berechtigte MCP-, Plugin- und Action-Tools weiterhin eine Auswahl erfordern.
- Tool-Intent-Labels bleiben deaktiviert, es sei denn, Sie fügen `tool_intents` hinzu; native Tools werden dann automatisch aktiviert, während MCP-Tools weiterhin eine Auswahl pro Tool erfordern.

## managementApi

Die Beta-Agent-Management-API ermöglicht es vertrauenswürdigen Maschinen-Clients, Agents zu erstellen, aufzulisten, zu lesen, zu aktualisieren und zu löschen, deren Dateien zu verwalten sowie zugängliche Skills zu entdecken oder zu bearbeiten. Sie ist getrennt von [`remoteApi`](#remoteapi): Management-Routen akzeptieren nur an die Bereitstellung gebundene OIDC-Maschinenidentitäten und akzeptieren keine LibreChat Remote Agents API-Schlüssel oder Browser-Sitzungen.

```yaml filename="endpoints / agents / managementApi"
endpoints:
  agents:
    managementApi:
      auth:
        oidc:
          enabled: true
          issuer: https://identity.example.com/
          audience: https://librechat.example.com/agents
          # jwksUri: https://identity.example.com/.well-known/jwks.json
        clients:
          - clientId: machine-client-id
            # subject: provider-specific-service-principal-subject
            userId: 507f1f77bcf86cd799439011
            tenantId: tenant-id
            enabled: true
```

## Hinweise [#notes]

- Es wird nicht empfohlen, das Builder-Interface zu deaktivieren, es sei denn, Sie verwenden [modelSpecs](/docs/configuration/librechat_yaml/object_structure/model_specs), um eine Liste von Agents zu definieren, aus denen ausgewählt werden kann.
- Die Konfiguration für Dateizitate (`maxCitations`, `maxCitationsPerFile`, `minRelevanceScore`) gilt nur, wenn die `file_search`-Funktion aktiviert ist.
- Der Relevanz-Score wird mithilfe von Vektorähnlichkeit berechnet, wobei 1.0 eine perfekte Übereinstimmung und 0.0 keine Ähnlichkeit darstellt.
- Zitierlimits helfen dabei, ein Gleichgewicht zwischen umfassender Informationsbeschaffung sowie Antwortqualität und Leistung zu finden.
- Die `context`-Funktion funktioniert ohne OCR-Konfiguration mithilfe von Text-Parsing-Methoden. OCR verbessert die Extraktionsqualität, wenn es konfiguriert ist.
- Die `ocr` Funktion erfordert die Konfiguration eines OCR-Dienstes (siehe [OCR Configuration](/docs/configuration/librechat_yaml/object_structure/ocr)).
- `maxSubagents` begrenzt, wie viele Subagents ein einzelner Agent referenzieren darf. Dies ändert nichts an den unter [Subagents](/docs/features/subagents#limits) dokumentierten Tiefen- oder Graph-Beschränkungen.
