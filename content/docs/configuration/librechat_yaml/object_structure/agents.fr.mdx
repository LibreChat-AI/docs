## maxProviderErrorChars

Contrôle la quantité de texte d'erreur du fournisseur que LibreChat conserve lorsqu'une défaillance d'un Agent ne peut pas être classée. La valeur par défaut est `2000` caractères. Définissez-la sur `0` pour omettre le texte du fournisseur ; le maximum est `1000000`.

```yaml filename="endpoints / agents / maxProviderErrorChars"
maxProviderErrorChars: 2000
```

## Délais d'attente du transport des réponses des modèles [#model-response-transport-timeouts]

Ces paramètres limitent les appels de modèle d'Agent qui utilisent des transports compatibles avec OpenAI, y compris les endpoints personnalisés compatibles.

<OptionTable

```yaml filename="endpoints / agents / model response transport timeouts"
modelResponseBodyTimeoutMs: 900000
modelResponseHeadersTimeoutMs: 300000
```

## repositoryInstructions

Contrôle la découverte des instructions du dépôt pour les environnements de code joints. `timeoutMs` limite la requête de chargement des instructions entre `100` et `30000` millisecondes, avec une valeur par défaut de `2000`.

```yaml filename="endpoints / agents / repositoryInstructions"
repositoryInstructions:
  timeoutMs: 2000
```

## Disjoncteurs de flux (Stream circuit breakers) [#stream-circuit-breakers]

Ces paramètres arrêtent l'exécution d'un Agent lorsqu'un flux de fournisseur semble produire des arguments d'outil incontrôlés ou une séquence illimitée d'événements delta.

<OptionTable
  options={[
    [
      'maxToolCallArgBytes',
      'Number',
      'Nombre maximal d\'octets cumulés pour les arguments d\'un appel d\'outil en flux. Définissez sur 0 pour désactiver la protection globale.',
      '65536',
    ],
    [
      'maxDeltaEventsPerTurn',
      'Number',
      'Nombre maximal d\'événements diffusés pour un tour de génération de modèle. Définissez sur 0 ou omettez pour désactiver cette protection.',
      '0 (disabled)',
    ],
    [
      'maxToolCallArgBytesByTool',
      'Object',
      'Remplacements d\'octets d\'argument par outil, indexés par le nom de l\'outil exposé au modèle. Une valeur de 0 désactive la protection pour cet outil.',
      'create_file: 131072',
    ],
  ]}
/>

LibreChat utilise une limite globale d'arguments de 64 KiB et intègre une valeur de remplacement de 128 KiB pour `create_file`, dont les charges utiles légitimes sont souvent plus volumineuses. Les entrées dans `maxToolCallArgBytesByTool` fusionnent par-dessus cette valeur de remplacement intégrée. Si l'une ou l'autre de ces protections est déclenchée, LibreChat interrompt le flux du fournisseur en cours et signale quelle limite a été dépassée.

```yaml filename="endpoints / agents / stream circuit breakers"
maxToolCallArgBytes: 65536
maxDeltaEventsPerTurn: 100000
maxToolCallArgBytesByTool:
  create_file: 262144
  large_import: 524288
```

Pour désactiver toutes les protections de taille d'argument, définissez à la fois la limite globale et la substitution `create_file` fournie sur `0` :

```yaml
maxToolCallArgBytes: 0
maxToolCallArgBytesByTool:
  create_file: 0
```

## titleTiming

<OptionTable
  options={[
    [

**Par défaut :** `"immediate"`

**Valeurs disponibles :**

- **`"immediate"`** : Génère le titre dès que la requête commence, en parallèle avec la réponse du modèle, en utilisant le premier message de l'utilisateur.

```yaml filename="endpoints / agents / titleTiming"
titleTiming: immediate
```

## activityLabel

Définissez `activityLabel: true` pour regrouper chaque bloc de raisonnement de l'Agent et les appels d'outils sous un en-tête généré sur une ligne. Utilisez `activityModel`, `activityEndpoint`, `activityPrompt`, `activityMaxPerRun` et `activityCharLimit` pour contrôler l'appel de modèle supplémentaire et son coût. Consultez [Agent Activity Groups](/docs/configuration/librechat_yaml/object_structure/shared_endpoint_settings#agent-activity-groups) pour obtenir la référence complète des champs et les règles de priorité.

```yaml filename="endpoints / agents / activity groups"
activityLabel: true
activityEndpoint: openAI
activityModel: gpt-4.1-nano
activityMaxPerRun: 20
activityCharLimit: 600
activityPhaseLabel: true
activityPhaseMaxPerRun: 5
```

`activityPhaseLabel` peut ajouter indépendamment un résumé parent réduit autour de chaque phase d'exécution qui contient au moins deux activités logiques. Utilisez `activityPhaseModel`, `activityPhaseEndpoint`, `activityPhasePrompt` et `activityPhaseMaxPerRun` pour ajuster ces appels ; `activityCharLimit` est partagé avec les étiquettes d'activité enfants.

## capabilities

<OptionTable
  options={[
    [
      'capabilities',
      'Array/List of Strings',
      'Spécifie les capacités d\'agent disponibles pour tous les utilisateurs pour l\'endpoint agents.',
      'Defines the agent capabilities that are available to all users for the agents endpoint. You can omit the capabilities you wish to exclude from the list.',
    ],
  ]}
/>

**Par défaut :** `["deferred_tools", "execute_code", "file_search", "web_search", "artifacts", "subagents", "actions", "context", "skills", "memory", "ask_user_question", "tools", "chain", "ocr"]`

`programmatic_tools`, `stateful_code_sessions`, `run_in_background` et `tool_intents` sont des options à activer et doivent être ajoutées explicitement. Les outils programmatiques et les sessions avec état nécessitent également `execute_code` et un déploiement de Code Interpreter compatible. L'Agent Builder désactive les sélections MCP programmatiques sans Code Interpreter, et le serveur supprime les options d'appelant programmatique obsolètes lorsque l'exécution de code n'est pas disponible. `run_in_background` rend les outils Code Interpreter éligibles par défaut et permet une activation par outil pour les outils MCP, Plugin et Action éligibles ; l'exécution de code en arrière-plan nécessite également `execute_code` et Code Interpreter.

`stateful_code_sessions` est hautement expérimental. Il nécessite une route d'interpréteur de code avec profil `stateful` distincte, configurée avec [`LIBRECHAT_CODE_BASEURL_STATEFUL`](/docs/configuration/dotenv#stateful-code-interpreter-endpoint) ou [`statefulCodeSessions.environments`](#statefulcodesessions). Les requêtes avec état (stateful) échouent par défaut au lieu de basculer vers le service sans état (stateless) normal. Dans le générateur d'agents (Agent Builder), chaque agent activé choisit une portée d'espace de travail utilisateur, agent-et-utilisateur, ou conversation et, lorsque des backends nommés sont configurés, un environnement d'exécution. Les nouveaux agents commencent avec la portée personnelle par défaut de l'utilisateur et l'environnement d'exécution par défaut du déploiement.

**Exemple :**

```yaml filename="endpoints / agents / capabilities"
capabilities:
  - 'deferred_tools'
  # Optional: enables Programmatic Tool Calling for MCP tools marked Programmatic in the Agent Builder.
  # Requires execute_code and a Code Interpreter deployment with the Tool Call Server component.
  # - 'programmatic_tools'
  - 'execute_code'
  - 'file_search'
  - 'web_search'
  - 'artifacts'
  - 'subagents'
  - 'actions'
  - 'context'
  - 'skills'
  - 'memory'
  - 'ask_user_question'
  - 'tools'
  - 'chain'
  - 'ocr'
  # Optional and highly experimental: reuse a user-, agent-and-user-, or
  # conversation-scoped workspace. Requires LIBRECHAT_CODE_BASEURL_STATEFUL
  # or a named statefulCodeSessions environment.
  # - 'stateful_code_sessions'
  # Optional: allow eligible Code Interpreter, MCP, Plugin, and Action tools to run as background tasks.
  # - 'run_in_background'
  # Optional: show live model-written intent labels for native and selected MCP tools.
  # - 'tool_intents'
```

**Remarque :** Ce champ est facultatif. S'il est omis, le comportement par défaut consiste à inclure toutes les capacités listées dans le défaut.

## statefulCodeSessions

Configure les portées de partage et les backends d'exécution optionnels pour les espaces de travail hautement expérimentaux et avec état de l'interpréteur de code (Code Interpreter).

<Callout type="warning" title="Hautement expérimental">
  Les Stateful Code Sessions, les environnements d'exécution nommés, les workers attachés et le pair programming sont dans une phase d'expérimentation précoce. Leur comportement, leur configuration, leurs caractéristiques de persistance et leur protocole d'intégration peuvent changer de manière substantielle.
</Callout>

<OptionTable
  options={[
    [
      'allowedEnvironments',
      'Array/List of Strings',
      'Portées d\'espace de travail avec état autorisées : `user`, `agent-user` et/ou `conversation`.',
      '["user", "agent-user", "conversation"]',
    ],
    [
      'environments',
      'Array of Objects',
      'Environnements Code API gérés ou attachés nommés optionnels affichés dans l\'Agent Builder.',
      'Unset; LIBRECHAT_CODE_BASEURL_STATEFUL remains the stateful endpoint',
    ],
    [
      'principalWorkers',
      'Object',
      'Plafond de déploiement optionnel pour l\'inscription des workers personnels. `enabled` est défini par défaut sur true et `maxPerUser` est défini par défaut sur 5.',
      '{ enabled: true, maxPerUser: 5 }',
    ],
    [
      'conversationMoves',
      'Object',
      'Transitions d\'espace de travail autorisées par le propriétaire avec consentement pour les conversations enregistrées. `allowAttachDetach` permet en outre de joindre ou de quitter un espace de travail joint.',
      'Disabled',
    ],
  ]}
/>

Les environnements attachés acceptent `environments[].configSchema.limits.maxQueueWaitMs`, qui contrôle la durée pendant laquelle une requête peut réessayer d'attendre la capacité de l'espace de travail. La valeur par défaut et maximale est de `300000` millisecondes (5 minutes). Réglez-la sur `0` pour désactiver les tentatives du client après la tentative d'admission initiale ; cela n'annule pas le travail déjà admis ou en cours d'exécution. Ces champs appartiennent à `configSchema.limits`, **et non** à `userConfig.bash`.

`environments[].configSchema.limits.maxRequestTimeoutMs` limite optionnellement le **temps HTTP total pour un appel d'outil d'espace de travail**, incluant l'admission, l'exécution, le règlement et la livraison. Il accepte des valeurs de `1` à `610000` ms, mais la configuration rejette les budgets trop faibles pour laisser un temps d'exécution de commande après l'admission et la réserve de 10 secondes pour le règlement/la livraison. Sans cela, l'admission dispose toujours d'un budget de 30 secondes par tentative ; `maxQueueWaitMs` demeure un horizon de nouvelle tentative distinct. **N'activez pas une admission plus longue** tant que chaque réplique de l'API LibreChat ne reconnaît pas ce champ, que la route de l'API Code ne respecte pas les allocations de file d'attente par requête, et que le délai d'expiration le plus court sur le chemin du proxy/ingress actif n'a pas été mesuré. Une mutation expirée peut avoir été terminée sur le worker, donc LibreChat ne réessaie pas en cas de délai d'expiration ambigu.

Avec un budget de requête total, `environments[].configSchema.limits.minCommandAdmissionMs` réserve du temps pour qu'une commande entre dans le worker avant le début de l'exécution. La valeur par défaut est `10000` ms ; définissez une valeur entre `1000` et `300000` ms. Le budget de la requête doit **dépasser** cette allocation plus 10000 ms de délai de grâce pour l'établissement/la livraison ; sans budget total, ce paramètre n'a aucun effet. La limite d'exécution Bash annoncée à un Agent est la plus petite valeur entre son plafond configuré ou en amont et le temps restant après ces réserves. Par exemple, un budget de requête de 90000 ms avec un plafond de commande de 80000 ms et la réserve par défaut annonce au maximum une commande de 70000 ms.

```yaml filename="endpoints / agents / statefulCodeSessions"
statefulCodeSessions:
  allowedEnvironments:
    - 'user'
    - 'agent-user'
    - 'conversation'
  principalWorkers:
    enabled: true
    maxPerUser: 5
  environments:
    - id: managed-default
      name: Managed Code API
      type: managed
      baseURL: https://code.example.com/v1
      default: true
    - id: engineering-vm
      name: Engineering VM
      type: attached
      baseURL: https://code-bridge.example.com/v1
      owner: deployment
      pairing:
        workerId: engineering-vm
        tokenEnv: CODE_BRIDGE_ADMIN_TOKEN
    - id: personal-workers
      name: Personal Code Workers
      type: attached
      baseURL: https://code-bridge.example.com/v1
      owner: deployment
      configSchema:
        limits:
          maxCommandTimeoutMs: 120000
          # Before enabling, verify Code API queue allowances and the live proxy deadline.
          # maxRequestTimeoutMs: 160000
          # minCommandAdmissionMs: 10000
          # maxQueueWaitMs: 300000
        # After upgrading Code API and opting in the worker with --linked-worktree-lanes:
        # workspaces:
        #   linkedWorktrees: true
        # Optional: require exact matching even on workers supporting tolerant edits.
        # edits:
        #   tolerantMatching: false
        permissions:
          fileWrite:
            allowed: [allow, ask, deny]
            default: ask
          commandExecution:
            allowed: [ask, deny]
            default: ask
      pairing:
        allowPrincipalWorkers: true
        tokenEnv: CODE_BRIDGE_ADMIN_TOKEN
```

`allowedEnvironments` est requis dès que le bloc est présent et doit inclure au moins une portée d'espace de travail (workspace scope). Omettez le bloc entier pour autoriser les trois portées et continuer à acheminer le travail avec état via [`LIBRECHAT_CODE_BASEURL_STATEFUL`](/docs/configuration/dotenv#stateful-code-interpreter-endpoint). La valeur par défaut personnelle et le générateur d'Agents (Agent Builder) n'autorisent que les valeurs permises. Si un administrateur renforce la politique, une valeur par défaut personnelle enregistrée reste visible mais désactivée, et les nouveaux Agents utilisent la première portée autorisée. Les Agents activés existants conservent leur portée enregistrée, mais une portée désormais non autorisée échouera par défaut lors de l'exécution jusqu'à ce que l'Agent soit reconfiguré.

`conversationMoves.enabled: true` permet au propriétaire de la conversation de déplacer explicitement un espace de travail attaché et scellé vers un environnement compatible et de récupérer un espace de travail manquant sans remplacer l'historique du chat ni restaurer les anciens fichiers de l'espace de travail. Pour autoriser en plus un chat enregistré à **attacher** un espace de travail ou à en **quitter** un pour un chat normal, définissez `conversationMoves.allowAttachDetach: true`. Les deux commutateurs sont désactivés par défaut ; l'activation des déplacements seuls conserve le comportement de déplacement uniquement. Mettez à niveau **toutes** les répliques de l'API, puis activez [`CODE_ENVIRONMENT_DECISION_VERSION=1`](/docs/configuration/dotenv#code-interpreter) avant d'opter pour cette fonctionnalité. La propriété, l'accès à la cible, le travail actif et la politique actuelle sont revérifiés lors de la transition ; une génération en cours ne peut pas être déplacée.

```yaml filename="endpoints / agents / statefulCodeSessions / conversationMoves"
statefulCodeSessions:
  allowedEnvironments: ['user', 'agent-user', 'conversation']
  conversationMoves:
    enabled: true
    allowAttachDetach: true
```

`principalWorkers` contrôle l'inscription en libre-service pour les travailleurs personnels attachés. Les valeurs omises sont résolues par `enabled: true` et `maxPerUser: 5` ; définissez `enabled: false` ou `maxPerUser: 0` pour arrêter toute nouvelle inscription. La limite comptabilise chaque environnement personnel enregistré pour cet utilisateur sur l'ensemble des plans de contrôle configurés, y compris les travailleurs hors ligne. Réduire la limite ou désactiver l'inscription ne révoque pas les environnements existants.

Le YAML de déploiement constitue la limite absolue. Une configuration prioritaire de rôle, de groupe ou d'utilisateur peut désactiver l'inscription ou réduire `maxPerUser`, mais ne peut pas augmenter la valeur du déploiement. Un utilisateur ne voit les plans de contrôle avec appairage activé que lorsque la limite effective est supérieure à zéro, que [`pairing.allowPrincipalWorkers`](#statefulcodesessions) est activé sur ce plan de contrôle, que l'authentification principale est disponible et que l'utilisateur dispose de l'autorisation de gestion de l'environnement de code.

Lorsque `environments` n'est pas vide, chaque entrée nécessite un `id` unique, un `name` d'affichage, un `type` défini sur `managed` ou `attached`, et une `baseURL` HTTP(S) sans chaîne de requête ni fragment. Si la liste contient des environnements exécutables, exactement une de ces entrées doit définir `default: true`. Le constructeur d'agent (Agent Builder) ajoute alors un sélecteur **Execution environment** ; le laisser sur **Deployment default** utilise cette entrée par défaut. Une liste contenant uniquement des plans de contrôle de couplage en libre-service ne nécessite aucune valeur par défaut. Un agent qui nomme un environnement qui est ultérieurement supprimé ou n'est plus accessible échoue par sécurité au lieu de basculer vers un autre backend.

- `managed` pointe directement vers une API de code avec état gérée par l'opérateur.
- `attached` pointe vers un backend `remote-bridge` de l'API Code compatible qui délègue le travail à un worker `@librechat/code` sortant. Le worker ne nécessite pas de port public entrant, mais son endpoint d'exécution local a tout de même besoin d'une isolation appropriée.
- `workerId` achemine optionnellement un environnement attaché vers un worker sortant. Il est réservé au serveur et n'est pas exposé via la configuration de démarrage du client.
- `owner` a pour valeur par défaut `deployment`. Les environnements appartenant à un mandant (principal-owned) sont créés via l'API Code Environments authentifiée de LibreChat, protégés par des ACL, et fusionnés uniquement pour les requêtes autorisées ; ne placez pas d'URLs fournies par le client dans le YAML de déploiement.
- `pairing` est facultatif et n'est valide que pour les entrées `attached` appartenant au déploiement. `pairing.workerId` identifie un worker géré par l'opérateur à inscrire, tandis que `pairing.allowPrincipalWorkers: true` permet aux utilisateurs autorisés d'inscrire des workers liés au propriétaire sur ce plan de contrôle. Au moins l'un de ces champs est requis lorsque `pairing` est présent.
- `pairing.tokenEnv` nomme la variable d'environnement contenant le jeton d'administrateur du pont ; elle ne contient jamais le jeton lui-même. Le jumelage nécessite HTTPS, sauf pour le développement en boucle locale (loopback).
- `configSchema.permissions` permet facultativement aux propriétaires autorisés de choisir la politique `fileWrite` et `commandExecution` pour les environnements personnels sous **Settings > Code environments**. Chaque champ nécessite une liste `allowed` non vide contenant `allow`, `ask` et/ou `deny` ; `default` est `ask` lorsqu'il est omis et doit figurer dans `allowed`. LibreChat rejette les valeurs stockées en dehors de la liste de l'administrateur.
- `configSchema.limits.maxCommandTimeoutMs` définit le délai d'expiration Bash maximal que le modèle peut demander pour cet environnement. Il accepte une valeur comprise entre `1` et `300000` ms ; l'omission conserve la valeur par défaut de 30 secondes. Avec un budget de requête total, le délai d'expiration de commande annoncé s'ajuste également au temps restant après l'admission, le règlement et la livraison de la commande. Il s'agit d'un plafond de déploiement qui n'est pas configurable par l'utilisateur.
- `configSchema.workspaces.linkedWorktrees: true` active la planification par worktree uniquement pour les espaces de travail attachés annonçant `git_linked_worktree` ; son omission maintient toutes les requêtes dans la file racine du checkout. Mettez à jour LibreChat **avant** qu'un worker n'annonce cette portée, déployez une Code API prenant en charge les files de worktrees liés, puis démarrez le worker avec `--linked-worktree-lanes` avant d'activer le paramètre YAML. Les opérations sur les fichiers ciblant un chemin à l'intérieur de `.worktrees/<name>` et les commandes Bash avec un `cwd` à cet emplacement utilisent cette file et renvoient des chemins relatifs au checkout. Les commandes qui utilisent `cd` dans leur texte de commande, les opérations à la racine du checkout, les instances d'espace de travail de conversation et les actions d'environnement restent limitées à la racine.
- `configSchema.edits.tolerantMatching` autorise par défaut une tolérance aux espaces pour le repli sur les workers connectés annonçant `tolerant_match` ; définissez-le sur `false` pour exiger une correspondance exacte, y compris pour les aperçus de modifications protégées. La correspondance doit rester unique, sauf si la modification définit explicitement `replace_all`. Les anciens workers ne reçoivent aucun nouveau champ de correspondance ; les `replace_all` joints sont refusés avant la répartition à moins que le worker ne les annonce. Ces fonctionnalités nécessitent une API Code compatible et des builds de worker implémentant [Code Interpreter #271](https://github.com/LibreChat-AI/code-interpreter/pull/271).
- Ne configurez pas `settings` dans le YAML de déploiement. LibreChat fournit ce champ à portée de requête à partir des préférences de l'utilisateur authentifié, validées par le serveur.
- Seules les politiques d'écriture de fichiers et d'exécution de commandes sont configurables par l'utilisateur. L'isolation, la mise en réseau, les montages, l'exécution privilégiée, l'entrée, la sortie et les secrets restent sous le contrôle de l'administrateur.
- Si `workerId` au niveau supérieur et `pairing.workerId` sont tous deux présents, ils doivent correspondre. Une entrée avec `allowPrincipalWorkers: true` et sans aucun ID de worker n'est pas réservée au jumelage (pairing-only) : elle est omise des sélecteurs d'exécution et ne peut pas définir `default: true`.

L'exécution attachée active automatiquement une base de référence de sécurité pour l'approbation : les écritures de fichiers ainsi que l'exécution de commandes ou de code demandent une confirmation, tandis que les opérations de lecture seule et de recherche continuent de suivre la politique habituelle des outils. Cette base de référence est limitée à l'Agent utilisant l'environnement attaché. Si aucun paramètre utilisateur n'est disponible, LibreChat utilise `ask` ; [`toolApproval.enabled: false`](#toolapproval) est la commande de secours de l'administrateur qui désactive cette base de référence de l'environnement attaché. Les appelants sans support d'approbation et de reprise échouent par défaut, sauf si cette commande de secours explicite est définie.

L'exécution attachée nécessite une version expérimentale correspondante du pont distant (remote-bridge) de l'interpréteur de code. Le jumelage authentifie la connexion sortante du worker ; il ne remplace pas l'isolation par sandbox ou VM. Les utilisateurs disposant de l'autorisation de gestion de l'environnement de code peuvent effectuer le jumelage, configurer la politique des outils autorisés et révoquer des workers personnels sous **Paramètres > Environnements de code**. Voir [Sessions de code avec état](/docs/features/code_interpreter#stateful-code-sessions).

```yaml filename="endpoints / agents / eventDriven"
eventDriven:
```

```yaml filename="endpoints / agents / eventDriven / idlePolling"
    deliveryMaxIntervalMs: 15000
    queuedTurnMaxIntervalMs: 120000
    maintenanceMaxIntervalMs: 120000

```

L'exécution en mémoire est locale au processus ; les flux de génération Redis ajoutent une récupération durable après redémarrage et un transfert de réplica. Aucun commutateur `librechat.yaml` ni indicateur de fonctionnalité d'environnement n'est requis. Voir [Agent Event Runtime](/docs/configuration/dotenv#agent-event-runtime).

<OptionTable

- Requêtes de création, de mise à jour et de duplication d'agents, pour `subagents.agent_ids` et `subagents.graphs`
- Les listes d'autorisation `subagents.agent_ids` des Model Specs, validées lors de la même passe de configuration

  `maxSubagents` doit être un nombre entier compris entre 1 et 50. Une valeur en dehors de cette plage échoue à la validation de `librechat.yaml`, et LibreChat enregistre l'erreur et s'arrête au démarrage au lieu de revenir à la valeur par défaut. Démarrer avec `CONFIG_BYPASS_VALIDATION=true` permet d'éviter l'arrêt, mais la configuration personnalisée entière est ignorée dans ce cas, donc la limite revient à `10`. Pour revenir délibérément à la valeur par défaut, supprimez la clé : un `maxSubagents` omis est résolu à `10` sans erreur.
</Callout>

<Callout type="note">
  La limite s'applique à l'ensemble du processus et provient de `librechat.yaml`. Une substitution dans la base de données par utilisateur ou par groupe de `endpoints.agents.maxSubagents` est reflétée dans la configuration servie, mais n'est pas appliquée par la validation des requêtes.
</Callout>

Augmenter cette valeur modifie uniquement le nombre de sous-agents qu'un agent peut référencer. La profondeur, le nœud de graphe et les limites de configuration d'exécution ne sont pas affectés. Voir [Subagents](/docs/features/subagents#limits).

## fileSharing

`fileSharing` est un partage optionnel, limité à l'exécution, pour le travail délégué des Agents. Définissez `enabled: true` ici et activez `subagents.shareFiles` sur chaque Agent déléguant. Les entrées sont en lecture seule pour les destinataires ; les sorties restent privées à moins d'être explicitement publiées, et les fichiers publiés restent téléchargeables après l'exécution.

```yaml filename="endpoints / agents / fileSharing"
endpoints:
  agents:
    fileSharing:
      enabled: true
      allowSiblingSharing: false
      maxFiles: 100
      maxPrivateBytes: 268435456
      ttlMs: 3600000
```

`allowSiblingSharing` autorise les destinataires frères ou descendants explicitement nommés. `maxFiles` varie de `1` à `1000` ; `maxPrivateBytes` limite les instantanés de sortie privés conservés ; et `ttlMs` est la durée de vie active du manifeste, plafonnée à 24 heures. Omettre ce bloc désactive le partage.

## Capacités des agents [#agent-capabilities]

Le champ `capabilities` vous permet d'activer ou de désactiver des fonctionnalités spécifiques pour les agents. Les capacités disponibles sont :

- **deferred_tools** : Permet aux agents de découvrir les outils MCP différés au moment de l'exécution au lieu de charger chaque outil dans le contexte au préalable.
- **programmatic_tools** : Active l'appel de programme par outils (Programmatic Tool Calling) pour les outils MCP marqués comme Programmatic dans l'Agent Builder. Nécessite `execute_code` et un déploiement de Code Interpreter avec le composant Tool Call Server. Cette fonctionnalité est optionnelle et n'est pas activée par défaut.
- **execute_code** : Permet à l'agent d'exécuter du code.
- **stateful_code_sessions** : Permet aux agents ayant opté pour cette option de réutiliser un espace de travail Code Interpreter selon une portée définie par utilisateur, par agent et utilisateur, ou par conversation. Nécessite `execute_code`, un déploiement Code Interpreter compatible, et le paramètre avancé par agent. Les nouveaux agents utilisent la portée préférée de l'utilisateur connecté. Cette fonctionnalité est hautement expérimentale, n'est pas activée par défaut et peut changer considérablement au cours de l'expérimentation ; ne considérez pas son comportement ou sa configuration actuelle comme un contrat de production stable.
- **file_search** : Permet à l'agent de rechercher et d'interagir avec des fichiers. Lorsqu'il est activé, le comportement des citations est contrôlé par les paramètres `maxCitations`, `maxCitationsPerFile` et `minRelevanceScore`.
- **web_search** : Active la fonctionnalité de recherche web pour les agents, leur permettant de rechercher et de récupérer des informations sur Internet.
- **artifacts** : Permet à l'agent de générer des artefacts interactifs (composants React, HTML, diagrammes Mermaid).
- **subagents** : Permet l'exécution d'agents enfants dans un contexte isolé. Voir [Subagents](/docs/features/subagents).
- **actions**: Permet à l'agent d'effectuer des actions prédéfinies.
- **context** : Active la fonctionnalité « Télécharger en tant que texte » dans le chat, ainsi que le « Contexte de fichier » pour les agents, permettant aux utilisateurs de télécharger des fichiers et de faire extraire leur contenu pour l'inclure directement dans la conversation.
- **skills** : Active les Skills dans le panneau latéral, l'invocation manuelle via `$`, les skills invoqués par le modèle et les listes d'autorisation de skills pour les agents. Voir [Skills](/docs/features/skills).
- **memory** : Permet aux agents d'utiliser `set_memory` et `delete_memory` lorsque la mémoire est configurée et que l'utilisateur y a accès. Activé par défaut ; supprimé au moment de l'exécution lorsque la mémoire est désactivée.
- **ask_user_question** : Permet aux agents de faire une pause pour poser une à quatre questions connexes dans un seul formulaire et de reprendre avec les réponses. Activé par défaut.
- **tools** : Accorde à l'agent l'accès à divers outils.
- **chain** : Active la fonctionnalité bêta pour le chaînage d'agents, également connue sous le nom de flux de travail Mixture-of-Agents (MoA).
- **ocr** : Améliore optionnellement « Téléverser en tant que texte » dans le chat, ainsi que le « Contexte de fichier » pour les agents, permettant aux fichiers d'être téléversés et traités avec l'OCR. **Nécessite la configuration d'un service OCR.**
- **run_in_background** : Rend l'exécution de Code Interpreter et les outils shell éligibles à l'exécution en arrière-plan par défaut et permet une option d'arrière-plan par outil pour les outils MCP, Plugin et Action éligibles. Un commutateur au niveau de l'Action active cette option pour chaque opération éligible ; les Actions OAuth et les opérations qui définissent déjà un paramètre `run_in_background` sont exclues. Un agent peut explicitement désactiver Code Interpreter pour l'arrière-plan. Le paramètre autorise l'exécution en arrière-plan ; le modèle décide par appel s'il doit l'utiliser. Nécessite `execute_code` et un déploiement Code Interpreter configuré pour le code. Cette fonctionnalité n'est pas activée par défaut.
- **tool_intents** : Ajoute des étiquettes d'intention rédigées en direct par le modèle aux appels d'outils éligibles. Les outils natifs, y compris les outils d'interprétation de code (Code Interpreter), s'activent automatiquement ; les outils MCP peuvent être activés individuellement ou en masse dans le générateur d'agents (Agent Builder). Les Model Specs utilisent `describeIntent`. Cette fonctionnalité n'est pas activée par défaut.

En spécifiant les capacités, vous pouvez contrôler les fonctionnalités disponibles pour les utilisateurs lorsqu'ils interagissent avec des agents.

## Exemple de configuration [#example-configuration]

Voici un exemple de configuration de l'endpoint `agents` avec des capacités personnalisées et des paramètres de citation de fichiers :

```yaml filename="Agents Endpoint"
endpoints:
  agents:
    disableBuilder: false
    # File citation configuration
    maxCitations: 20
    maxCitationsPerFile: 5
    minRelevanceScore: 0.6
    # Custom capabilities
    capabilities:
      # Optional: enables Programmatic Tool Calling for MCP tools marked Programmatic in the Agent Builder.
      # - 'programmatic_tools'
      - 'execute_code'
      # Optional: makes Code Interpreter background-eligible and enables selected MCP, Plugin, and Action tools.
      # - 'run_in_background'
      # Optional: enables live intent labels for native and selected MCP tools.
      # - 'tool_intents'
      - 'file_search'
      - 'skills'
      - 'subagents'
      - 'actions'
      - 'artifacts'
      - 'context'
      - 'ocr'
      - 'web_search'
```

Dans cet exemple :

- L'interface du constructeur est activée
- Les citations de fichiers sont limitées à 20 au total, avec un maximum de 5 par fichier.
- Seules les sources ayant une pertinence de 60 % ou plus sont incluses
- Les agents LibreChat ont accès à l'exécution de code, à la recherche de fichiers (avec citations), aux Skills, aux Subagents, aux actions, aux artifacts, au contexte de fichier, aux services OCR s'ils sont configurés, ainsi qu'aux capacités de recherche web.
- L'appel d'outils programmatique reste désactivé à moins que vous n'ajoutiez la capacité `programmatic_tools` en plus de `execute_code`
- Les appels d'outils en arrière-plan restent désactivés à moins que vous n'ajoutiez `run_in_background` ; les outils Code Interpreter deviennent alors éligibles par défaut, tandis que les outils MCP, Plugin et Action éligibles nécessitent toujours une sélection.
- Les étiquettes d'intention des outils restent désactivées à moins que vous n'ajoutiez `tool_intents` ; les outils natifs s'activent alors automatiquement, tandis que les outils MCP nécessitent toujours une sélection par outil.

## managementApi

L'API de gestion des Agents en version bêta permet aux clients machines de confiance de créer, lister, lire, mettre à jour et supprimer des Agents, de gérer leurs fichiers, et de découvrir ou modifier les Skills accessibles. Elle est distincte de [`remoteApi`](#remoteapi) : les routes de gestion acceptent uniquement les identités machine OIDC liées au déploiement et n'acceptent pas les clés API des Remote Agents de LibreChat ni les sessions de navigateur.

```yaml filename="endpoints / agents / managementApi"
        clients:
          - clientId: machine-client-id
            # subject: provider-specific-service-principal-subject
            userId: 507f1f77bcf86cd799439011
            tenantId: tenant-id
            enabled: true
```

## Notes [#notes]

- Il n'est pas recommandé de désactiver l'interface du générateur à moins que vous n'utilisiez [modelSpecs](/docs/configuration/librechat_yaml/object_structure/model_specs) pour définir une liste d'agents parmi lesquels choisir.
- La configuration des citations de fichiers (`maxCitations`, `maxCitationsPerFile`, `minRelevanceScore`) s'applique uniquement lorsque la fonctionnalité `file_search` est activée.
- Le score de pertinence est calculé en utilisant la similarité vectorielle, où 1.0 représente une correspondance parfaite et 0.0 représente aucune similarité.
- Les limites de citation aident à équilibrer la récupération d'informations complètes avec la qualité et la performance des réponses.
- La fonctionnalité `context` fonctionne sans configuration OCR en utilisant des méthodes d'analyse de texte. L'OCR améliore la qualité de l'extraction lorsqu'il est configuré.
- La fonctionnalité `ocr` nécessite la configuration d'un service OCR (voir [Configuration OCR](/docs/configuration/librechat_yaml/object_structure/ocr)).
- `maxSubagents` limite le nombre de sous-agents auxquels un seul agent peut faire référence. Cela ne modifie pas la profondeur ou les limites du graphe documentées sous [Subagents](/docs/features/subagents#limits).
