이 페이지는 [`agents`](/docs/features/agents) endpoint에 적용됩니다.

## 예시 [#example]

```yaml filename="Agents Endpoint"
endpoints:
  agents:
    modelResponseBodyTimeoutMs: 900000
    modelResponseHeadersTimeoutMs: 300000
    recursionLimit: 50
    maxRecursionLimit: 100
    maxSubagents: 20
    codeApiUploadConcurrency: 3
    codeApiMaxRetryWaitMs: 20000
    maxToolCallArgBytes: 65536
    maxDeltaEventsPerTurn: 100000
    maxToolCallArgBytesByTool:
      create_file: 131072
    disableBuilder: false
    # (optional) Agent Capabilities available to all users. Omit the ones you wish to exclude. Defaults to list below.
    # Opt-in capabilities: "programmatic_tools", "stateful_code_sessions", "run_in_background", and "tool_intents".
    # capabilities: ["deferred_tools", "execute_code", "file_search", "web_search", "artifacts", "subagents", "actions", "context", "skills", "memory", "ask_user_question", "tools", "chain", "ocr"]
    # (optional) File citation configuration for file_search capability
    maxCitations: 30 # Maximum total citations in responses (1-50)
    maxCitationsPerFile: 7 # Maximum citations from each file (1-10)
    minRelevanceScore: 0.45 # Minimum relevance score threshold (0.0-1.0)
    titleTiming: immediate
    activityLabel: true
    activityModel: gpt-4.1-nano
    activityPhaseLabel: true
    activityPhaseMaxPerRun: 5
    skills:
      maxCatalogSkills: 20
    statefulCodeSessions:
      allowedEnvironments: ['user', 'agent-user', 'conversation']
      principalWorkers:
        enabled: true
        maxPerUser: 5
      environments:
        - id: managed-default
          name: Managed Code API
          type: managed
          baseURL: https://code.example.com/v1
          default: true
        - id: engineering-vm
          name: Engineering VM
          type: attached
          baseURL: https://code-bridge.example.com/v1
          pairing:
            workerId: engineering-vm
            tokenEnv: CODE_BRIDGE_ADMIN_TOKEN
        - id: personal-workers
          name: Personal Code Workers
          type: attached
          baseURL: https://code-bridge.example.com/v1
          pairing:
            allowPrincipalWorkers: true
            tokenEnv: CODE_BRIDGE_ADMIN_TOKEN
    # eventDriven:
    #   selfUrl: https://librechat.internal
    backgroundTasks:
      completionWakeups: true
      ordinaryToolCancellation: false
    toolApproval:
      enabled: true
      mode: default
      deny: ['mcp:*:delete_*']
      ask: ['mcp:*:*']
    checkpointer:
      type: mongo
      ttl: 86400
    managementApi:
      auth:
        oidc:
          enabled: true
          issuer: https://identity.example.com/
          audience: https://librechat.example.com/agents
          # tokenUse: access
          # requiredScopes:
          #   - agents-api/manage
        clients:
          - clientId: machine-client-id
            userId: 507f1f77bcf86cd799439011
            tenantId: tenant-id
    remoteApi:
      auth:
        oidc:
          enabled: false
```

> 이 구성은 에이전트를 위한 빌더 인터페이스를 활성화합니다.

## maxProviderErrorChars

에이전트 오류를 분류할 수 없을 때 LibreChat이 보존할 공급자 오류 텍스트의 양을 제어합니다. 기본값은 `2000` 문자입니다. 공급자 텍스트를 생략하려면 `0`으로 설정하십시오. 최대값은 `1000000`입니다.



## 스트림 서킷 브레이커(Stream circuit breakers) [#stream-circuit-breakers]

이 설정들은 공급자 스트림이 제어할 수 없는 도구 인수를 생성하거나 제한 없는 델타 이벤트 시퀀스를 생성하는 것으로 보일 때 Agent 실행을 중단합니다.

<OptionTable
  options={[
    [
      'maxToolCallArgBytes',
      'Number',
      '한 번의 스트리밍된 도구 호출 인수에 대한 최대 누적 바이트 수입니다. 전역 가드를 비활성화하려면 0으로 설정하세요.',
      '65536',
    ],
    [
      'maxDeltaEventsPerTurn',
      'Number',
      '한 번의 모델 생성 턴에 대한 최대 스트리밍 이벤트 수입니다. 이 가드를 비활성화하려면 0으로 설정하거나 생략하세요.',
      '0 (disabled)',
    ],
    [
      'maxToolCallArgBytesByTool',
      'Object',
      '모델이 인식하는 도구 이름을 키로 사용하는 도구별 인수 바이트(argument-byte) 재정의입니다. 0으로 설정하면 해당 도구에 대한 가드가 비활성화됩니다.',
      'create_file: 131072',
    ],
  ]}
/>

LibreChat은 64 KiB의 전역 인수 제한을 사용하며, 합법적인 페이로드가 더 큰 경우가 많은 `create_file`에 대해 128 KiB의 오버라이드를 기본으로 제공합니다. `maxToolCallArgBytesByTool`의 항목은 해당 내장 오버라이드에 병합됩니다. 두 제한 중 하나라도 초과되면 LibreChat은 진행 중인 공급자 스트림을 중단하고 어떤 제한이 초과되었는지 보고합니다.

```yaml filename="endpoints / agents / stream circuit breakers"
maxToolCallArgBytes: 65536
maxDeltaEventsPerTurn: 100000
maxToolCallArgBytesByTool:
  create_file: 262144
  large_import: 524288
```

모든 인수 크기 제한(argument-size guard)을 비활성화하려면, 전역 제한과 기본 제공 `create_file` 재정의를 모두 `0`으로 설정하세요:

```yaml
maxToolCallArgBytes: 0
maxToolCallArgBytesByTool:
  create_file: 0
```

## activityLabel

`activityLabel: true`를 설정하여 각 에이전트 추론 및 도구 호출 블록을 생성된 한 줄 헤더 아래로 그룹화합니다. `activityModel`, `activityEndpoint`, `activityPrompt`, `activityMaxPerRun` 및 `activityCharLimit`를 사용하여 추가 모델 호출과 그 비용을 제어하세요. 전체 필드 참조 및 우선순위 규칙은 [Agent Activity Groups](/docs/configuration/librechat_yaml/object_structure/shared_endpoint_settings#agent-activity-groups)를 참조하세요.

```yaml filename="endpoints / agents / activity groups"
activityLabel: true
activityEndpoint: openAI
activityModel: gpt-4.1-nano
activityMaxPerRun: 20
activityCharLimit: 600
activityPhaseLabel: true
activityPhaseMaxPerRun: 5
```

`activityPhaseLabel`은 최소 두 개의 논리적 활동을 포함하는 각 실행 단계 주위에 독립적으로 하나의 접힌 상위 요약을 추가할 수 있습니다. 해당 호출을 조정하려면 `activityPhaseModel`, `activityPhaseEndpoint`, `activityPhasePrompt` 및 `activityPhaseMaxPerRun`을 사용하세요. `activityCharLimit`은 하위 활동 레이블과 공유됩니다.

## capabilities

<OptionTable
  options={[
    [
      'capabilities',
      'Array/List of Strings',
      'agents 엔드포인트에 대해 모든 사용자에게 제공되는 에이전트 기능을 지정합니다.',
      'Defines the agent capabilities that are available to all users for the agents endpoint. You can omit the capabilities you wish to exclude from the list.',
    ],
  ]}
/>

**기본값:** `["deferred_tools", "execute_code", "file_search", "web_search", "artifacts", "subagents", "actions", "context", "skills", "memory", "ask_user_question", "tools", "chain", "ocr"]`

`programmatic_tools`, `stateful_code_sessions`, `run_in_background` 및 `tool_intents`는 옵트인(opt-in) 방식이며 명시적으로 추가해야 합니다. Programmatic 도구와 stateful 세션은 `execute_code` 및 호환되는 Code Interpreter 배포도 필요합니다. Agent Builder는 Code Interpreter 없이는 Programmatic MCP 선택을 비활성화하며, 서버는 코드 실행을 사용할 수 없을 때 오래된 programmatic 호출자 옵션을 제거합니다. `run_in_background`는 Code Interpreter 도구를 기본적으로 적격하게 만들며, 적격한 MCP, Plugin 및 Action 도구에 대해 도구별 옵트인을 허용합니다. 백그라운드 코드 실행 또한 `execute_code` 및 Code Interpreter가 필요합니다.

`stateful_code_sessions`는 매우 실험적인 기능입니다. 이 기능은 [`LIBRECHAT_CODE_BASEURL_STATEFUL`](/docs/configuration/dotenv#stateful-code-interpreter-endpoint) 또는 [`statefulCodeSessions.environments`](#statefulcodesessions)로 구성된 별도의 `stateful` 프로필 Code Interpreter 경로를 필요로 합니다. Stateful 요청은 일반적인 stateless 서비스로 대체되지 않고 실패 시 차단(fail closed)됩니다. Agent Builder에서 활성화된 각 에이전트는 사용자(user), 에이전트 및 사용자(agent-and-user), 또는 대화(conversation) 작업 공간 범위를 선택하며, 명명된 백엔드가 구성된 경우 실행 환경을 선택합니다. 새로운 에이전트는 사용자의 개인 범위 기본값과 배포의 기본 실행 환경으로 시작합니다.

**예시:**

```yaml filename="endpoints / agents / capabilities"
capabilities:
  - 'deferred_tools'
  # Optional: enables Programmatic Tool Calling for MCP tools marked Programmatic in the Agent Builder.
  # Requires execute_code and a Code Interpreter deployment with the Tool Call Server component.
  # - 'programmatic_tools'
  - 'execute_code'
  - 'file_search'
  - 'web_search'
  - 'artifacts'
  - 'subagents'
  - 'actions'
  - 'context'
  - 'skills'
  - 'memory'
  - 'ask_user_question'
  - 'tools'
  - 'chain'
  - 'ocr'
  # Optional and highly experimental: reuse a user-, agent-and-user-, or
  # conversation-scoped workspace. Requires LIBRECHAT_CODE_BASEURL_STATEFUL
  # or a named statefulCodeSessions environment.
  # - 'stateful_code_sessions'
  # Optional: allow eligible Code Interpreter, MCP, Plugin, and Action tools to run as background tasks.
  # - 'run_in_background'
  # Optional: show live model-written intent labels for native and selected MCP tools.
  # - 'tool_intents'
```

**참고:** 이 필드는 선택 사항입니다. 생략할 경우, 기본 동작은 기본값에 나열된 모든 기능을 포함하는 것입니다.

## statefulCodeSessions

매우 실험적인 상태 유지(stateful) Code Interpreter 작업 공간을 위한 공유 범위 및 선택적 실행 백엔드를 구성합니다.

<Callout type="warning" title="매우 실험적인 기능">
  Stateful Code Sessions, named execution environments, attached workers, 그리고 pairing은 초기 실험 단계에 있습니다. 이들의 동작, 구성, 지속성 특성 및 통합 프로토콜은 크게 변경될 수 있습니다.
</Callout>

연결된 환경(Attached environments)은 `environments[].configSchema.limits.maxQueueWaitMs`를 허용하며, 이는 요청이 작업 공간 용량을 기다리며 재시도할 수 있는 시간을 제어합니다. 기본값 및 최댓값은 `300000` 밀리초(5분)입니다. 초기 승인 시도 후 클라이언트 재시도를 비활성화하려면 `0`으로 설정하십시오. 이는 이미 승인되었거나 실행 중인 작업을 취소하지는 않습니다. 이 필드들은 `userConfig.bash`가 **아닌** `configSchema.limits` 아래에 속합니다.

`environments[].configSchema.limits.maxRequestTimeoutMs`는 **하나의 워크스페이스 도구 호출에 대한 총 HTTP 시간**(승인, 실행, 정산 및 전달 포함)을 선택적으로 제한합니다. 이 설정은 `1`에서 `610000` ms 사이의 값을 허용하지만, 승인 후 10초의 정산/전달 예비 시간을 제외하고 명령 실행 시간이 남지 않을 정도로 작은 예산은 구성에서 거부됩니다. 이 설정이 없으면 승인 단계는 시도당 30초의 예산을 유지하며, `maxQueueWaitMs`는 별도의 재시도 기간으로 유지됩니다. 모든 LibreChat API 복제본이 이 필드를 이해하고, Code API 경로가 요청별 대기열 허용량을 준수하며, 라이브 프록시/인그레스 경로 전체에서 가장 짧은 타임아웃이 측정되기 전까지는 **더 긴 승인 시간을 활성화하지 마십시오**. 만료된 변경 작업이 워커에서 완료되었을 수 있으므로, LibreChat은 모호한 타임아웃에 대해 재시도를 수행하지 않습니다.

총 요청 예산과 함께, `environments[].configSchema.limits.minCommandAdmissionMs`는 명령이 실행을 시작하기 전에 워커(worker)에 진입할 시간을 예약합니다. 기본값은 `10000` ms이며, `1000`–`300000` ms 사이로 설정할 수 있습니다. 요청 예산은 이 허용치에 10000 ms의 정산/전달 유예 시간을 더한 값보다 **커야** 합니다. 총 예산이 없으면 이 설정은 아무런 효과가 없습니다. 에이전트에게 알리는 Bash 실행 제한은 설정된 값 또는 업스트림 상한값 중 더 작은 값에서 해당 예약 시간을 뺀 나머지 시간입니다. 예를 들어, 90000 ms의 요청 예산, 80000 ms의 명령 상한값, 그리고 기본 예약 시간을 사용하는 경우, 최대 70000 ms의 명령 시간이 에이전트에게 전달됩니다.

```yaml filename="endpoints / agents / statefulCodeSessions"
statefulCodeSessions:
  allowedEnvironments:
    - 'user'
    - 'agent-user'
    - 'conversation'
  principalWorkers:
    enabled: true
    maxPerUser: 5
  environments:
    - id: managed-default
      name: Managed Code API
      type: managed
      baseURL: https://code.example.com/v1
      default: true
    - id: engineering-vm
      name: Engineering VM
      type: attached
      baseURL: https://code-bridge.example.com/v1
      owner: deployment
      pairing:
        workerId: engineering-vm
        tokenEnv: CODE_BRIDGE_ADMIN_TOKEN
    - id: personal-workers
      name: Personal Code Workers
      type: attached
      baseURL: https://code-bridge.example.com/v1
      owner: deployment
      configSchema:
        limits:
          maxCommandTimeoutMs: 120000
          # Before enabling, verify Code API queue allowances and the live proxy deadline.
          # maxRequestTimeoutMs: 160000
          # minCommandAdmissionMs: 10000
          # maxQueueWaitMs: 300000
        # After upgrading Code API and opting in the worker with --linked-worktree-lanes:
        # workspaces:
        #   linkedWorktrees: true
        # Optional: require exact matching even on workers supporting tolerant edits.
        # edits:
        #   tolerantMatching: false
        permissions:
          fileWrite:
            allowed: [allow, ask, deny]
            default: ask
          commandExecution:
            allowed: [ask, deny]
            default: ask
      pairing:
        allowPrincipalWorkers: true
        tokenEnv: CODE_BRIDGE_ADMIN_TOKEN
```

`allowedEnvironments`는 해당 블록이 존재할 때 필수이며, 최소 하나의 작업 공간(workspace) 범위를 포함해야 합니다. 전체 블록을 생략하면 세 가지 범위가 모두 허용되며, 상태 유지 작업은 계속해서 [`LIBRECHAT_CODE_BASEURL_STATEFUL`](/docs/configuration/dotenv#stateful-code-interpreter-endpoint)을 통해 라우팅됩니다. 개인 기본값 및 Agent Builder는 허용된 값만 사용할 수 있습니다. 관리자가 정책을 강화하면 저장된 개인 기본값은 계속 표시되지만 비활성화되며, 새로운 Agent는 첫 번째로 허용된 범위를 사용합니다. 기존에 활성화된 Agent는 저장된 범위를 유지하지만, 이제 허용되지 않는 범위는 Agent가 재구성될 때까지 런타임에 실패(fail closed) 처리됩니다.

`conversationMoves.enabled: true`는 대화 소유자가 봉인된 연결된 작업 공간(workspace)을 호환되는 환경으로 명시적으로 이동하고, 채팅 기록을 대체하거나 이전 작업 공간 파일을 복원하지 않고도 누락된 작업 공간을 복구할 수 있게 합니다. 저장된 채팅이 작업 공간을 **연결(attach)**하거나 일반 채팅을 위해 **떠나기(leave)**를 추가로 허용하려면 `conversationMoves.allowAttachDetach: true`로 설정하십시오. 두 스위치 모두 기본적으로 꺼져 있으며, 이동 기능만 활성화하면 이동 전용 동작이 유지됩니다. **모든** API 복제본을 업그레이드한 다음, 옵트인하기 전에 [`CODE_ENVIRONMENT_DECISION_VERSION=1`](/docs/configuration/dotenv#code-interpreter)을 활성화하십시오. 전환 시 소유권, 대상 액세스, 활성 작업 및 현재 정책이 재확인되며, 실행 중인 생성 작업은 이동할 수 없습니다.

```yaml filename="endpoints / agents / statefulCodeSessions / conversationMoves"
statefulCodeSessions:
  allowedEnvironments: ['user', 'agent-user', 'conversation']
  conversationMoves:
    enabled: true
    allowAttachDetach: true
```

`principalWorkers`는 개인 연결 워커에 대한 셀프 서비스 등록을 제어합니다. 값이 생략되면 `enabled: true` 및 `maxPerUser: 5`로 설정됩니다. 새로운 등록을 중단하려면 `enabled: false` 또는 `maxPerUser: 0`으로 설정하십시오. 제한은 오프라인 워커를 포함하여 구성된 제어 평면 전반에서 해당 사용자에 대해 등록된 모든 개인 환경을 계산합니다. 제한을 낮추거나 등록을 비활성화해도 기존 환경은 취소되지 않습니다.

Deployment YAML은 상한선 역할을 합니다. 역할, 그룹 또는 사용자 구성 재정의를 통해 등록을 비활성화하거나 `maxPerUser` 값을 낮출 수는 있지만, 배포 값을 높일 수는 없습니다. 사용자는 유효 제한이 0보다 크고, 해당 제어 평면에서 [`pairing.allowPrincipalWorkers`](#statefulcodesessions)가 활성화되어 있으며, 주체 인증(principal authentication)을 사용할 수 있고, 사용자에게 Code Environment 관리 권한이 있는 경우에만 페어링이 활성화된 제어 평면을 볼 수 있습니다.

`environments`가 비어 있지 않은 경우, 모든 항목에는 고유한 `id`, 표시용 `name`, `managed` 또는 `attached` 유형의 `type`, 그리고 쿼리 문자열이나 프래그먼트가 없는 HTTP(S) `baseURL`이 필요합니다. 목록에 실행 가능한 환경이 포함된 경우, 해당 항목 중 정확히 하나는 `default: true`로 설정되어야 합니다. 그러면 Agent Builder가 **Execution environment** 선택기를 추가하며, 이를 **Deployment default**로 두면 해당 기본 항목이 사용됩니다. 셀프 서비스 페어링 제어 평면만 포함된 목록에는 기본값이 필요하지 않습니다. 나중에 제거되거나 더 이상 액세스할 수 없는 환경을 지정한 에이전트는 다른 백엔드로 대체되지 않고 실패 상태로 종료됩니다.

- `managed`는 운영자가 관리하는 상태 저장 Code API를 직접 가리킵니다.
- `attached`는 작업물을 아웃바운드 `@librechat/code` 워커에 임대하는 호환 가능한 Code API `remote-bridge` 백엔드를 가리킵니다. 워커는 인바운드 공용 포트를 필요로 하지 않지만, 로컬 실행 endpoint는 여전히 적절한 격리가 필요합니다.
- `workerId`는 선택적으로 연결된 환경을 하나의 아웃바운드 워커로 라우팅합니다. 이는 서버 전용이며 클라이언트 시작 구성(startup configuration)을 통해 노출되지 않습니다.
- `owner`의 기본값은 `deployment`입니다. 주체(Principal)가 소유한 환경은 LibreChat의 인증된 Code Environments API를 통해 생성되며, ACL로 보호되고, 승인된 요청에 대해서만 병합됩니다. 클라이언트가 제공한 URL을 deployment YAML에 넣지 마십시오.
- `pairing`은 선택 사항이며 배포 소유의 `attached` 항목에 대해서만 유효합니다. `pairing.workerId`는 등록할 운영자 관리 워커를 식별하며, `pairing.allowPrincipalWorkers: true`는 승인된 사용자가 소유자 귀속 워커를 해당 제어 평면에 등록할 수 있도록 합니다. `pairing`이 존재할 경우, 이 필드 중 최소 하나는 필수입니다.
- `pairing.tokenEnv`는 브리지 관리자 토큰을 포함하는 환경 변수의 이름을 지정하며, 토큰 자체를 포함하지는 않습니다. 페어링에는 루프백 개발을 제외하고 HTTPS가 필요합니다.
- `configSchema.permissions`는 선택적으로 권한이 있는 소유자가 **Settings > Code environments**에서 개인 환경에 대한 `fileWrite` 및 `commandExecution` 정책을 선택할 수 있도록 합니다. 각 필드는 `allow`, `ask` 및/또는 `deny`를 포함하는 비어 있지 않은 `allowed` 목록을 요구합니다. `default`는 생략 시 `ask`이며 반드시 `allowed`에 포함되어야 합니다. LibreChat은 관리자가 설정한 목록 외의 저장된 값은 거부합니다.
- `configSchema.limits.maxCommandTimeoutMs`는 모델이 해당 환경에 대해 요청할 수 있는 최대 Bash 타임아웃을 설정합니다. `1`에서 `300000` ms 사이의 값을 허용하며, 생략 시 30초 기본값이 유지됩니다. 총 요청 예산 내에서, 공지된 명령 타임아웃은 명령 승인, 처리 및 전달 후 남은 시간에도 맞춰집니다. 이는 배포 상한선이며 사용자가 구성할 수 없습니다.
- `configSchema.workspaces.linkedWorktrees: true`는 `git_linked_worktree`를 알리는 연결된 워크스페이스에 대해서만 워크트리별 스케줄링을 활성화합니다. 이 설정을 생략하면 모든 요청이 체크아웃의 루트 레인(root lane)에 유지됩니다. 워커가 이 범위를 알리기 **전에** LibreChat을 업그레이드하고, 연결된 워크트리 레인을 지원하는 Code API를 배포한 다음, YAML 설정을 활성화하기 전에 `--linked-worktree-lanes` 옵션으로 워커를 시작하십시오. `.worktrees/<name>` 내부의 경로를 대상으로 하는 파일 작업과 해당 경로를 `cwd`로 사용하는 Bash 명령은 해당 레인을 사용하며 체크아웃 상대 경로를 반환합니다. 명령 텍스트 내에서 `cd`를 수행하는 명령, 체크아웃 루트 작업, 대화 워크스페이스 인스턴스 및 환경 작업은 루트 범위로 유지됩니다.
- `configSchema.edits.tolerantMatching`은 `tolerant_match`를 알리는 연결된 워커(worker)에서 기본적으로 공백을 허용하는 폴백(fallback)을 허용합니다. 이를 `false`로 설정하면 보호된 편집 미리보기를 포함하여 정확한 일치를 요구하게 됩니다. 편집에서 명시적으로 `replace_all`을 설정하지 않는 한 일치는 고유해야 합니다. 이전 버전의 워커는 새로운 일치 필드를 수신하지 않으며, 워커가 이를 알리지 않는 한 연결된 `replace_all`은 디스패치 전에 거부됩니다. 이러한 기능은 [Code Interpreter #271](https://github.com/LibreChat-AI/code-interpreter/pull/271)을 구현하는 호환 가능한 Code API 및 워커 빌드가 필요합니다.
- 배포 YAML에서 `settings`를 구성하지 마십시오. LibreChat은 인증된 소유자의 서버 검증된 기본 설정에서 해당 요청 범위(request-scoped) 필드를 제공합니다.
- 파일 쓰기 및 명령 실행 정책만 사용자가 구성할 수 있습니다. 격리, 네트워킹, 마운트, 권한 있는 실행, 인그레스, 이그레스 및 보안 비밀은 관리자가 제어합니다.
- 최상위 `workerId`와 `pairing.workerId`가 모두 존재할 경우, 두 값은 일치해야 합니다. `allowPrincipalWorkers: true`로 설정된 항목에 워커 ID가 모두 없는 경우, 해당 항목은 페어링 전용(pairing-only)으로 간주됩니다. 이 경우 실행 선택기(execution selectors)에서 제외되며 `default: true`를 설정할 수 없습니다.

Attached execution은 안전한 승인 기준을 자동으로 활성화합니다. 파일 쓰기 및 명령 또는 코드 실행은 확인을 요청하며, 읽기 전용 및 검색 작업은 일반 도구 정책에 따라 계속됩니다. 이 기준은 연결된 환경을 사용하는 Agent로 범위가 지정됩니다. 사용자 설정이 없는 경우, LibreChat은 `ask`를 사용합니다. [`toolApproval.enabled: false`](#toolapproval)는 이 연결된 환경 기준을 비활성화하는 관리자 긴급 재정의(override)입니다. 승인 및 재개 지원이 없는 호출자는 해당 명시적 재정의가 설정되지 않은 경우 실패(fail closed) 처리됩니다.

연결된 실행을 위해서는 일치하는 실험적 Code Interpreter remote-bridge 빌드가 필요합니다. 페어링은 아웃바운드 워커 연결을 인증하며, 샌드박스나 VM 격리를 대체하지 않습니다. Code Environment 관리 권한이 있는 사용자는 **설정 > 코드 환경(Settings > Code environments)**에서 페어링하고, 허용된 도구 정책을 구성하며, 개인 워커를 취소할 수 있습니다. [상태 저장 코드 세션(/docs/features/code_interpreter#stateful-code-sessions)](/docs/features/code_interpreter#stateful-code-sessions)을 참조하세요.

바인딩된 하위 연속(Bound child continuations)은 자동으로 처리됩니다. `eventDriven` 하위의 이전 `childTurns`, `completionWakeups`, `coalescing`, `actorMailbox`, `checkpointForks`, `durableReceipts` 필드는 더 이상 구성 스위치가 아니므로 제거해야 합니다. 런타임은 이제 해당 전달 보장을 직접 적용합니다. 별도의 [`backgroundTasks.completionWakeups`](#backgroundtasks) 필드는 완료된 백그라운드 도구 및 분리된 Subagent에 대한 대화형 전달을 제어합니다.

일반적인 바운드 리스너(bound-listener) 경로의 경우 `selfUrl`을 설정하지 않은 상태로 두십시오. 신뢰할 수 있는 내부 트리거 허용이 TLS 프런트 도어와 같은 다른 HTTP(S) 오리진을 통과해야 하는 경우에만 설정하십시오. 이 필드가 생략된 경우 `AGENT_TRIGGERS_SELF_URL`이 호환성을 위한 대체 수단으로 유지됩니다. [Agents API events](/docs/features/agents_api#agent-events) 및 [Automatic Parent Continuation](/docs/features/subagents#automatic-parent-continuation)을 참조하십시오.

`eventDriven.idlePolling`은 준비된 작업이 없을 때 레플리카별 복구 폴링의 상한을 제한합니다. `deliveryMaxIntervalMs`의 기본값은 `15000`(유효 범위 `1000`–`300000`)이며, `queuedTurnMaxIntervalMs`와 `maintenanceMaxIntervalMs`는 각각 기본값이 `120000`(유효 범위 `30000`–`300000`)입니다. 또한 `completionWaitMaxIntervalMs`의 기본값은 `60000`(유효 범위 `5000`–`300000`)입니다. 후자는 백그라운드 작업이나 Subagent 결과가 대기 중이거나 상위 턴이 바쁜 동안 재확인 주기를 제한합니다. 준비 상태 이벤트는 전달을 가속화하며, 이러한 상한값은 일반적인 완료 지연 시간을 정의하는 것이 아니라 레플리카 간 및 충돌 복구 폴백을 유지하기 위한 것입니다.

```yaml filename="endpoints / agents / eventDriven / idlePolling"
eventDriven:
  idlePolling:
    deliveryMaxIntervalMs: 15000
    queuedTurnMaxIntervalMs: 120000
    maintenanceMaxIntervalMs: 120000
    completionWaitMaxIntervalMs: 60000
```

Event Actor detached Action completion은 내장된 생성 저장소(generation store)에서 자동으로 선택됩니다. 인메모리 실행은 프로세스 로컬 방식이며, Redis 생성 스트림은 내구성이 있는 재시작 복구 및 복제본 핸드오프 기능을 추가합니다. 별도의 `librechat.yaml` 스위치나 환경 기능 플래그는 필요하지 않습니다. [Agent Event Runtime](/docs/configuration/dotenv#agent-event-runtime)을 참조하세요.

[Background Tool Calls](/docs/features/agents#background-tool-calls) 및 [Automatic Parent Continuation](/docs/features/subagents#automatic-parent-continuation)을 참조하세요.

패턴은 glob 매칭을 사용합니다. MCP 도구는 `mcp:<server>:<tool>`로 범위를 지정할 수 있습니다. 예를 들어, `mcp:github:*`는 `github` 서버의 모든 도구와 일치합니다.
```yaml filename="endpoints / agents / toolApproval"
toolApproval:

  mode: default
  allow:
    - 'mcp:analytics:read_*'
  deny:

  ask:
    - 'mcp:*:*'
  reason: 'Review {tool} before it runs.'
```

Hooks는 서버 시작 시 한 번 로드되며 LibreChat 프로세스 내에서 실행됩니다. 각 항목은 `module`, 선택 사항인 도구 이름 `matcher` 정덱스(regex), 그리고 모듈의 빌더로 전달되는 선택 사항인 `options` 객체를 허용합니다. 신뢰할 수 있는 코드만 로드하십시오. 역할별 또는 테넌트별 재정의는 hook 모듈을 다시 로드하지 않으므로, hook 내부에서 상황에 맞는 동작을 구현하십시오.

```yaml filename="endpoints / agents / toolApproval / hooks"
toolApproval:
  enabled: true
  hooks:
    - module: '@acme/librechat-approval-hook'
      matcher: '^mcp:production:'
      options:
        requireTicket: true
```

배포 환경에서 10개 이상의 하위 에이전트에게 작업을 위임해야 하는 오케스트레이션 중심의 에이전트를 실행할 때 이 값을 높이십시오. 이 값은 시작 시 읽히며 다음 세 곳에서 적용됩니다:

- `subagents.agent_ids` 및 `subagents.graphs`에 대한 에이전트 생성, 업데이트 및 복제 요청
- Model spec `subagents.agent_ids` 허용 목록은 동일한 구성 단계에서 유효성이 검사됩니다.
- 설정된 값에서 새로운 하위 에이전트(subagent) 항목 입력을 중단하는 Agent Builder 패널

Model specs는 `subagents` 하위에서 `enabled`, `allowSelf`, `agent_ids`만 허용합니다. Subagent `graphs`는 에이전트 수준의 기능입니다. 따라서 model spec의 `graphs` 키는 설정이 파싱될 때 오류 없이 삭제됩니다.

<Callout type="warning">
  `maxSubagents`는 1에서 50 사이의 정수여야 합니다. 해당 범위를 벗어난 값은 `librechat.yaml` 유효성 검사를 통과하지 못하며, LibreChat은 오류를 기록하고 기본값으로 대체하는 대신 시작 시 종료됩니다. `CONFIG_BYPASS_VALIDATION=true`로 시작하면 종료를 건너뛸 수 있지만, 이 경우 사용자 지정 설정 전체가 폐기되므로 제한은 `10`으로 돌아갑니다. 의도적으로 기본값으로 되돌리려면 해당 키를 제거하십시오. `maxSubagents`를 생략하면 오류 없이 `10`으로 설정됩니다.
</Callout>

<Callout type="note">
  이 제한은 프로세스 전체에 적용되며 `librechat.yaml`에서 설정됩니다. `endpoints.agents.maxSubagents`에 대한 사용자별 또는 그룹별 데이터베이스 재정의는 제공되는 구성에는 반영되지만, 요청 유효성 검사에는 적용되지 않습니다.
</Callout>

이 값을 높이는 것은 하나의 에이전트가 참조할 수 있는 하위 에이전트의 수만 변경합니다. 깊이, 그래프 노드 및 실행 구성 제한은 영향을 받지 않습니다. [Subagents](/docs/features/subagents#limits)를 참조하세요.

## fileSharing

`fileSharing`은 위임된 Agent 작업을 위한 옵트인(opt-in), 실행 범위(run-scoped) 공유 기능입니다. 여기서 `enabled: true`를 설정하고 각 위임 Agent에서 `subagents.shareFiles`를 활성화하세요. 입력값은 수신자에게 읽기 전용으로 제공되며, 출력값은 명시적으로 게시하지 않는 한 비공개로 유지됩니다. 게시된 파일은 실행이 종료된 후에도 다운로드할 수 있습니다.

```yaml filename="endpoints / agents / fileSharing"
      ttlMs: 3600000
```

`allowSiblingSharing`는 명시적으로 지정된 형제 또는 하위 수신자를 허용합니다. `maxFiles`는 `1`에서 `1000` 사이의 범위를 가지며, `maxPrivateBytes`는 보존되는 비공개 출력 스냅샷의 크기를 제한하고, `ttlMs`는 활성 매니페스트의 수명으로 최대 24시간으로 제한됩니다. 이 블록을 생략하면 공유 기능이 비활성화됩니다.

## 에이전트 기능 (Agent Capabilities) [#agent-capabilities]

`capabilities` 필드를 사용하면 에이전트에 대한 특정 기능을 활성화하거나 비활성화할 수 있습니다. 사용 가능한 기능은 다음과 같습니다:

- **deferred_tools**: 에이전트가 모든 도구를 사전에 컨텍스트로 로드하는 대신 런타임에 지연된 MCP 도구를 검색할 수 있도록 합니다.
- **programmatic_tools**: 에이전트 빌더(Agent Builder)에서 Programmatic으로 표시된 MCP 도구에 대해 프로그래밍 방식의 도구 호출(Programmatic Tool Calling)을 활성화합니다. `execute_code` 및 Tool Call Server 구성 요소가 포함된 코드 인터프리터(Code Interpreter) 배포가 필요합니다. 이 기능은 선택 사항이며 기본적으로 활성화되어 있지 않습니다.
- **execute_code**: 에이전트가 코드를 실행할 수 있도록 허용합니다.
- **stateful_code_sessions**: 옵트인(opted-in)된 에이전트가 사용자, 에이전트 및 사용자, 또는 대화 범위에서 하나의 Code Interpreter 워크스페이스를 재사용할 수 있도록 합니다. `execute_code`, 호환되는 Code Interpreter 배포, 그리고 에이전트별 고급(Advanced) 설정이 필요합니다. 새로운 에이전트는 로그인한 사용자가 선호하는 범위를 사용합니다. 이 기능은 매우 실험적인 단계이며 기본적으로 활성화되어 있지 않고, 실험 과정에서 크게 변경될 수 있습니다. 현재의 동작이나 구성을 안정적인 프로덕션 계약으로 간주하지 마십시오.
- **file_search**: 에이전트가 파일을 검색하고 상호작용할 수 있도록 합니다. 활성화되면 인용 동작은 `maxCitations`, `maxCitationsPerFile` 및 `minRelevanceScore` 설정에 의해 제어됩니다.
- **web_search**: 에이전트가 인터넷을 검색하고 정보를 가져올 수 있도록 웹 검색 기능을 활성화합니다.
- **artifacts**: 에이전트가 대화형 아티팩트(React 컴포넌트, HTML, Mermaid 다이어그램)를 생성할 수 있도록 합니다.
- **subagents**: 격리된 컨텍스트의 하위 에이전트 실행을 활성화합니다. [Subagents](/docs/features/subagents)를 참조하세요.
- **actions**: 에이전트가 미리 정의된 작업을 수행할 수 있도록 허용합니다.
- **context**: 채팅에서 "텍스트로 업로드(Upload as Text)" 기능과 에이전트를 위한 "파일 컨텍스트(File Context)"를 활성화하여, 사용자가 파일을 업로드하고 해당 내용을 추출하여 대화에 직접 포함할 수 있도록 합니다.
- **skills**: 사이드 패널에서 Skills를 활성화하고, 수동 `$` 호출, 모델 호출 Skills, 그리고 에이전트 skill 허용 목록을 지원합니다. [Skills](/docs/features/skills)를 참조하세요.
- **memory**: 메모리가 구성되어 있고 사용자에게 접근 권한이 있을 때 에이전트가 `set_memory` 및 `delete_memory`를 사용할 수 있도록 합니다. 기본적으로 활성화되어 있으며, 메모리가 비활성화되면 런타임에 제거됩니다.
- **ask_user_question**: 에이전트가 일시 중지하고 단일 양식으로 1~4개의 관련 질문을 한 뒤 답변을 받아 재개할 수 있도록 합니다. 기본적으로 활성화되어 있습니다.
- **tools**: 에이전트에게 다양한 도구에 대한 액세스 권한을 부여합니다.
- **chain**: 에이전트 체이닝(Mixture-of-Agents (MoA) 워크플로우라고도 함)을 위한 베타 기능을 활성화합니다.
- **ocr**: 채팅에서 "텍스트로 업로드(Upload as Text)" 기능과 에이전트를 위한 "파일 컨텍스트(File Context)"를 선택적으로 향상시켜, 파일을 업로드하고 OCR로 처리할 수 있게 합니다. **OCR 서비스를 구성해야 합니다.**
- **run_in_background**: Code Interpreter 실행 및 셸 도구를 기본적으로 백그라운드 실행이 가능하도록 설정하며, 적격한 MCP, Plugin 및 Action 도구에 대해 도구별 백그라운드 옵트인(opt-in)을 활성화합니다. Action 수준의 스위치는 모든 적격한 작업에 대해 옵트인을 적용합니다. 단, OAuth Action 및 이미 `run_in_background` 매개변수를 정의한 작업은 제외됩니다. 에이전트는 Code Interpreter를 명시적으로 옵트아웃(opt-out)할 수 있습니다. 이 설정은 백그라운드 실행을 허용하며, 모델이 호출 시마다 사용 여부를 결정합니다. 코드를 실행하려면 `execute_code`와 구성된 Code Interpreter 배포가 필요합니다. 이 기능은 기본적으로 활성화되어 있지 않습니다.
- **tool_intents**: 적격한 도구 호출에 모델이 직접 작성한 인텐트(intent) 레이블을 추가합니다. 코드 인터프리터 도구를 포함한 기본 도구는 자동으로 옵트인(opt-in)되며, MCP 도구는 Agent Builder에서 개별적으로 또는 일괄적으로 활성화할 수 있습니다. Model Specs는 `describeIntent`를 사용합니다. 이 기능은 기본적으로 활성화되어 있지 않습니다.

기능(capabilities)을 지정하여 사용자가 에이전트와 상호작용할 때 사용할 수 있는 기능을 제어할 수 있습니다.

## 예시 구성 [#example-configuration]

다음은 사용자 지정 기능 및 파일 인용 설정을 사용하여 `agents` endpoint를 구성하는 예시입니다:

```yaml filename="Agents Endpoint"
endpoints:
  agents:
    disableBuilder: false
    # File citation configuration
    maxCitations: 20
    maxCitationsPerFile: 5
    minRelevanceScore: 0.6
    # Custom capabilities
    capabilities:
      # Optional: enables Programmatic Tool Calling for MCP tools marked Programmatic in the Agent Builder.
      # - 'programmatic_tools'
      - 'execute_code'
      # Optional: makes Code Interpreter background-eligible and enables selected MCP, Plugin, and Action tools.
      # - 'run_in_background'
      # Optional: enables live intent labels for native and selected MCP tools.
      # - 'tool_intents'
      - 'file_search'
      - 'skills'
      - 'subagents'
      - 'actions'
      - 'artifacts'
      - 'context'
      - 'ocr'
      - 'web_search'
```

이 예시에서:

- 빌더 인터페이스가 활성화되었습니다
- 파일 인용은 총 20개로 제한되며, 파일당 최대 5개까지 가능합니다.
- 60% 이상의 관련성을 가진 소스만 포함됩니다
- LibreChat 에이전트는 코드 실행, 파일 검색(출처 포함), Skills, Subagents, actions, artifacts, 파일 컨텍스트, 구성된 경우 OCR 서비스, 그리고 웹 검색 기능에 액세스할 수 있습니다.
- `execute_code`와 함께 `programmatic_tools` 기능을 추가하지 않으면 Programmatic Tool Calling은 비활성화된 상태로 유지됩니다.
- 백그라운드 도구 호출은 `run_in_background`를 추가하지 않는 한 비활성화된 상태로 유지됩니다. Code Interpreter 도구는 기본적으로 사용 가능하게 되지만, 사용 가능한 MCP, Plugin 및 Action 도구는 여전히 선택이 필요합니다.
- `tool_intents`를 추가하지 않으면 도구 의도(tool intent) 레이블은 비활성화된 상태로 유지됩니다. 기본 도구(native tools)는 자동으로 옵트인(opt in)되지만, MCP 도구는 여전히 도구별로 선택해야 합니다.

## managementApi

베타 Agent Management API를 사용하면 신뢰할 수 있는 머신 클라이언트가 Agent를 생성, 나열, 읽기, 업데이트 및 삭제하고, 파일을 관리하며, 액세스 가능한 Skill을 검색하거나 편집할 수 있습니다. 이는 [`remoteApi`](#remoteapi)와는 별개입니다. 관리 경로는 배포에 바인딩된 OIDC 머신 ID만 허용하며, LibreChat Remote Agents API 키나 브라우저 세션은 허용하지 않습니다.

```yaml filename="endpoints / agents / managementApi"
endpoints:

    managementApi:
      auth:
        oidc:
          enabled: true
          issuer: https://identity.example.com/
          audience: https://librechat.example.com/agents
          # jwksUri: https://identity.example.com/.well-known/jwks.json
        clients:
          - clientId: machine-client-id
            # subject: provider-specific-service-principal-subject
            userId: 507f1f77bcf86cd799439011
            tenantId: tenant-id
            enabled: true
```

토큰은 만료되지 않아야 하며 단일하고 충돌하지 않는 클라이언트 식별자를 제공해야 합니다. 검증 후, LibreChat은 바인딩된 테넌트 내부에서만 구성된 사용자를 확인하며, 누락되었거나 비활성 상태이거나, 테넌트 간 교차, 비활성화 또는 주체 불일치가 있는 프린시펄은 거부합니다. 이후 모든 관리 작업은 해당 사용자의 현재 역할 기능과 Agent 또는 Skill ACL을 사용하며, 바인딩은 추가적인 리소스 액세스 권한을 부여하지 않습니다.

알 수 없는 management-auth 필드, 중복된 클라이언트 ID, 형식이 잘못된 사용자 또는 테넌트 ID, 그리고 클라이언트 바인딩 없이 활성화된 인증은 구성 유효성 검사에 실패합니다. 경로 및 예제는 [Agents API - Agent Management](/docs/features/agents_api#agent-management-api)를 참조하세요.

</Callout>

각 `graphs` 항목은 고유한 `type`, `name`, `description`, `agent_ids`, 직접적인 `edges`, `entry_agent_id` 및 `result_agent_id`를 필요로 합니다. 팀 정의는 연결된 비순환 방향 그래프(DAG)를 형성해야 하며, 모든 구성원은 사용자에게 보여야 합니다. 또한 전체 구성은 50개의 고유한 Agent 대상과 100개의 확장된 실행 구성으로 제한됩니다. [saved-team 예시 및 런타임 동작](/docs/features/subagents#configure-an-agent)을 참조하세요.

사용자 대상 동작 및 제한 사항은 [Subagents](/docs/features/subagents)를 참조하세요.

## 참고 사항 [#notes]

- [modelSpecs](/docs/configuration/librechat_yaml/object_structure/model_specs)를 사용하여 선택할 에이전트 목록을 정의하는 경우가 아니라면, 빌더 인터페이스를 비활성화하는 것은 권장되지 않습니다.
- 파일 인용 설정(`maxCitations`, `maxCitationsPerFile`, `minRelevanceScore`)은 `file_search` 기능이 활성화된 경우에만 적용됩니다.
- 관련성 점수는 벡터 유사도를 사용하여 계산되며, 1.0은 완벽한 일치를, 0.0은 유사성이 없음을 나타냅니다.
- 인용 제한은 포괄적인 정보 검색과 응답 품질 및 성능 사이의 균형을 맞추는 데 도움을 줍니다.
- `context` 기능은 OCR 설정 없이도 텍스트 파싱 방식을 사용하여 작동합니다. OCR을 설정하면 추출 품질이 향상됩니다.
- `ocr` 기능을 사용하려면 OCR 서비스를 구성해야 합니다 ([OCR 구성](/docs/configuration/librechat_yaml/object_structure/ocr) 참조).
- `maxSubagents`는 단일 에이전트가 참조할 수 있는 하위 에이전트의 수를 제한합니다. 이는 [Subagents](/docs/features/subagents#limits) 문서에 명시된 깊이 또는 그래프 제한을 변경하지 않습니다.
