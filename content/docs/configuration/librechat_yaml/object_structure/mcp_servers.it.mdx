## Esempio [#example]

```yaml filename="MCP Servers Object Structure"
# Example MCP Servers Object Structure
mcpServers:
  everything:
    # type: sse # type can optionally be omitted
    url: http://localhost:3001/sse
  googlesheets:
    type: sse
    url: https://mcp.composio.dev/googlesheets/some-endpoint
    requiresOAuth: true
    headers:
      X-User-ID: '{{LIBRECHAT_USER_ID}}'
      X-API-Key: '${SOME_API_KEY}'
    serverInstructions: true # Use server-provided instructions
  puppeteer:
    type: stdio
    command: npx
    args:
      - -y
      - '@modelcontextprotocol/server-puppeteer'
    serverInstructions: 'Do not access any local files or local/internal IP addresses'
  filesystem:
    # type: stdio
    command: npx
    args:
      - -y
      - '@modelcontextprotocol/server-filesystem'
      - /home/user/LibreChat/
    iconPath: /home/user/LibreChat/client/public/assets/logo.svg
    # The “wrench” icon shows up if no icon is provided as it is the default rendering.
  mcp-obsidian:
    command: npx
    args:
      - -y
      - 'mcp-obsidian'
      - /path/to/obsidian/vault
  streamable-http-server:
    type: streamable-http
    url: https://example.com/api/
    proxy: '${MCP_PROXY_URL}'
  per-user-credentials-example:
    type: streamable-http
    url: 'https://example.com/api/'
    headers:
      X-Auth-Token: '{{MY_SERVICE_API_KEY}}'
    customUserVars:
      MY_SERVICE_API_KEY:
        title: 'My Service API Key'
        description: "Enter your personal API key for the service. You can generate one at <a href='https://myservice.example.com/developer/keys' target='_blank'>Service Developer Portal</a>."
        sensitive: true
      MY_SERVICE_PROJECT:
        title: 'Project ID'
        description: 'Enter the project ID used by this service.'
        sensitive: false
  oauth-example:
    type: streamable-http
    url: https://api.example.com/mcp/
    oauth:
      authorization_url: https://example.com/oauth/authorize
      token_url: https://example.com/oauth/token
      client_id: your_client_id
      client_secret: your_client_secret
      redirect_uri: http://localhost:3080/api/mcp/oauth-example/oauth/callback
      scope: 'read execute'
  obo-example:
    type: streamable-http
    url: https://api.example.com/mcp/
    obo:
      scopes: 'api://mcp-server-id/Mcp.Tools.ReadWrite'
```

<Callout type="warning" title="I server basati su processi sono di proprietà dell'operatore">
  I server MCP che utilizzano `type: stdio` o campi di processo come `command`, `args`, `env`, `cwd` o `stderr` devono essere configurati in `librechat.yaml`. L'API di configurazione dell'amministratore rifiuta le voci basate su processi e i database o gli override per principal non possono sostituire o rimuovere un server basato su processi esistente. I server MCP remoti continuano a seguire la normale precedenza di override della configurazione.
</Callout>

  Le chiavi degli strumenti rivolte al modello preservano lettere, numeri, `_`, `.` e `-`; gli altri caratteri nel nome di un server vengono sostituiti con `_`. #### `title` [#title]

- **Tipo:** Stringa (Opzionale)
- **Descrizione:** Nome visualizzato personalizzato per il server MCP nell'interfaccia utente. Se non specificato, viene utilizzato il nome della chiave del server.
- **Validazione:** Deve iniziare con una lettera o un numero Unicode. I caratteri rimanenti possono includere lettere Unicode, numeri, segni diacritici, spazi, trattini e apostrofi dritti o curvi.
- **Esempio:**
  ```yaml
  my-server:
    title: 'File System Access'
    command: npx
    args: ['-y', '@modelcontextprotocol/server-filesystem']
  ```

#### `description` [#description]

- **Tipo:** Stringa (Opzionale)
- **Descrizione:** Descrizione del server MCP, visualizzata nell'interfaccia utente per aiutare gli utenti a comprenderne lo scopo e le funzionalità.
- **Esempio:**
  ```yaml
  my-server:
    title: 'File System Access'
    description: 'Provides read/write access to local files and directories'
    command: npx
    args: ['-y', '@modelcontextprotocol/server-filesystem']
  ```

#### `type` [#type]

- **Tipo:** String
- **Descrizione:** Specifica il tipo di connessione al server MCP. Le opzioni valide sono `"stdio"`, `"websocket"`, `"streamable-http"` o `"sse"`. `"http"` è accettato come alias di `"streamable-http"`.
- **Valore predefinito:** Determinato in base alla presenza e al formato di `url` o `command`.

#### `command` [#command]

- **Tipo:** String
- **Descrizione:** (Per il tipo `stdio`) Il comando o l'eseguibile da eseguire per avviare il server MCP.

#### `args` [#args]

- **Tipo:** Array di stringhe
- **Descrizione:** (Per il tipo `stdio`) Argomenti da riga di comando da passare a `command`. I segnaposto come `${ENV_VAR}`, `{{LIBRECHAT_USER_*}}` e `{{CUSTOM_VARIABLE_NAME}}` vengono risolti in ciascun argomento, allo stesso modo di `env`.

#### `url` [#url]

- **Tipo:** String
- **Descrizione:** (Per il tipo `websocket`, `streamable-http` o `sse`) L'URL a cui connettersi al server MCP. Supporta segnaposto dinamici per i campi utente (`{{LIBRECHAT_USER_*}}`) e la sostituzione delle variabili d'ambiente (`${ENV_VAR}`).
- **Note:**
  - Per il tipo `sse`, l'URL deve iniziare con `http://` o `https://`.
  - Per il tipo `streamable-http`, l'URL deve iniziare con `http://` o `https://`.
  - Per il tipo `websocket`, l'URL deve iniziare con `ws://` o `wss://`.

#### `proxy` [#proxy]

- **Tipo:** Stringa (Opzionale, per i tipi `sse` e `streamable-http`)
- **Descrizione:** URL del proxy in uscita per questo server MCP remoto. Il valore può fare riferimento a variabili d'ambiente con `${ENV_VAR}`.
- **Protocolli supportati:** `http://`, `https://`, `socks://` e `socks5://`
- **Nota sulla sicurezza:** `proxy` è controllato dall'amministratore. Risolve le variabili d'ambiente, ma non risolve i segnaposto controllati dall'utente come `{{LIBRECHAT_USER_ID}}` o `customUserVars`.
- **Esempio:**
  ```yaml
  mcpServers:
    remote-api:
      type: streamable-http
      url: https://api.example.com/mcp
      proxy: '${MCP_PROXY_URL}'
  ```

#### `headers` [#headers]

- **Tipo:** Oggetto (Opzionale, per i tipi `sse` e `streamable-http`)
- **Descrizione:** Header personalizzati da inviare con la richiesta. Supporta vari tipi di segnaposto per la sostituzione dinamica dei valori.
- **Supporto segnaposto:**
  - `{{LIBRECHAT_USER_ID}}`: Verrà sostituito con l'ID dell'utente corrente, abilitando il supporto multi-utente.
  - `{{LIBRECHAT_USER_*}}`: Segnaposto dinamici per i campi utente. Sostituisci `*` con la versione in MAIUSCOLO di qualsiasi campo consentito.
  - `{{LIBRECHAT_OPENID_*}}`: segnaposto per token/sessione OpenID per server definiti in YAML.
  - `{{LIBRECHAT_GRAPH_*}}`: segnaposto dei token di Microsoft Graph per i server definiti in YAML.
  - `{{LIBRECHAT_BODY_*}}`: Segnaposto del corpo della richiesta per server definiti in YAML, come i correnti `conversationId`, `parentMessageId` o `messageId`.
  - `{{CUSTOM_VARIABLE_NAME}}`: Sostituito con il valore fornito dall'utente per una variabile definita in `customUserVars` (ad esempio, `{{MY_API_KEY}}`).
  - `${ENV_VAR}`: Verrà sostituito con il valore della variabile d'ambiente `ENV_VAR`.

**Segnaposto dei campi utente disponibili:**

| Segnaposto | Campo Utente | Tipo | Descrizione |
| ------------------------------------- | ------------------ | ---------------- | ----------------------------------------------------------- |
| `{{LIBRECHAT_USER_NAME}}`             | `name`             | String | Nome visualizzato dell'utente |
| `{{LIBRECHAT_USER_USERNAME}}`         | `username`         | String | Nome utente |
| `{{LIBRECHAT_USER_EMAIL}}`            | `email`            | String | Indirizzo email dell'utente |
| `{{LIBRECHAT_USER_PROVIDER}}`         | `provider`         | String | Provider di autenticazione (es. "email", "google", "github") |
| `{{LIBRECHAT_USER_ROLE}}`             | `role`             | String | Ruolo dell'utente (es. "user", "admin") |
| `{{LIBRECHAT_USER_GOOGLEID}}`         | `googleId`         | String | ID account Google |
| `{{LIBRECHAT_USER_FACEBOOKID}}`       | `facebookId`       | String | ID account Facebook |
| `{{LIBRECHAT_USER_OPENIDID}}`         | `openidId`         | String | ID account OpenID |
| `{{LIBRECHAT_USER_SAMLID}}`           | `samlId`           | String | ID account SAML |
| `{{LIBRECHAT_USER_LDAPID}}`           | `ldapId`           | String | ID account LDAP |
| `{{LIBRECHAT_USER_GITHUBID}}`         | `githubId`         | String | ID account GitHub |
| `{{LIBRECHAT_USER_DISCORDID}}`        | `discordId`        | String | ID account Discord |
| `{{LIBRECHAT_USER_APPLEID}}`          | `appleId`          | String | ID account Apple |
| `{{LIBRECHAT_USER_EMAILVERIFIED}}`    | `emailVerified`    | Boolean → String | Stato verifica email ("true" o "false") |
| `{{LIBRECHAT_USER_TWOFACTORENABLED}}` | `twoFactorEnabled` | Boolean → String | Stato 2FA ("true" o "false") |
| `{{LIBRECHAT_USER_TERMSACCEPTED}}`    | `termsAccepted`    | Boolean → String | Stato accettazione termini ("true" o "false") |
| `{{LIBRECHAT_USER_TERMSACCEPTEDAT}}`  | `termsAcceptedAt`  | Date → String | Timestamp accettazione termini |

**Nota:** I campi mancanti verranno sostituiti con stringhe vuote.

I segnaposto `{{LIBRECHAT_BODY_*}}` sono limitati all'ambito della richiesta (request-scoped). LibreChat crea la connessione MCP per l'esecuzione attiva, la riutilizza tra le chiamate agli strumenti durante tale esecuzione e la chiude al termine della richiesta. I server limitati alla richiesta sono esclusi dalla cache persistente degli strumenti, in modo che le intestazioni e gli URL specifici della richiesta non vengano riutilizzati al di fuori dell'esecuzione attiva. L'Agent Builder collega il server completo tramite una selezione di runtime-tools e risolve i suoi strumenti dopo che un'esecuzione fornisce i valori del corpo. Il completamento di OAuth memorizza l'autorizzazione ma rimanda la connessione fino a quando non esiste quel contesto di richiesta. I segnaposto `{{LIBRECHAT_USER_*}}`, `{{LIBRECHAT_OPENID_*}}` e `{{LIBRECHAT_GRAPH_*}}` rendono ancora il server limitato all'utente (user-scoped), ma i trasporti HTTP aggiornano le intestazioni risolte prima di ogni chiamata allo strumento senza forzare autonomamente una riconnessione.

`{{LIBRECHAT_BODY_PARENTMESSAGEID}}` riceve il messaggio genitore del turno radice nelle chat Agent native, nelle richieste API degli Agent compatibili con OpenAI e nelle esecuzioni degli Assistants legacy. Le richieste Open Responses non hanno un modello di messaggio genitore compatibile, quindi un server che richiede questo segnaposto fallisce in modo chiuso su quell'interfaccia; `previous_response_id` non viene sostituito al suo posto.

I token di accesso e di ID OpenID scadono in modo indipendente. `{{LIBRECHAT_OPENID_ACCESS_TOKEN}}` e il legacy `{{LIBRECHAT_OPENID_TOKEN}}` utilizzano la scadenza del token di accesso memorizzato, mentre `{{LIBRECHAT_OPENID_ID_TOKEN}}` richiede un ID token corrente. Se un token di credenziale non è disponibile o è scaduto, LibreChat restituisce un errore di ri-autenticazione `401` azionabile invece di inviare un valore bearer vuoto o letterale; effettua nuovamente l'accesso prima di riprovare. Per una richiesta senza identità OpenID, un'intestazione contenente uno di quei segnaposto di credenziali non risolti viene omessa del tutto. I segnaposto dei metadati di identità mantengono il loro comportamento esistente con valore vuoto.

Gli operatori autorizzati possono trasmettere il token di accesso OpenID live dell'utente che ha effettuato l'accesso direttamente a un server MCP remoto definito in YAML:

```yaml
mcpServers:
  trusted-api:
    type: streamable-http
    url: https://mcp.example.com/mcp
    headers:
      Authorization: 'Bearer {{LIBRECHAT_OPENID_ACCESS_TOKEN}}'
```

Utilizzare il passthrough diretto solo quando il server MCP è considerato attendibile per ricevere il token di accesso upstream dell'utente. L'OAuth MCP esplicito, lo [scambio per conto terzi (on-behalf-of exchange)](#obo) e l'autenticazione tramite chiave API dell'amministratore hanno la precedenza su questa intestazione. LibreChat risolve il token di sessione live prima di connettersi e aggiorna la connessione una volta dopo un `401` o `403`. Non riesegue automaticamente la chiamata allo strumento rifiutata poiché il server potrebbe averla già eseguita; riprovare lo strumento deliberatamente dopo che il ripristino è avvenuto con successo. Se il token non può essere aggiornato, l'utente deve accedere nuovamente.

`{{LIBRECHAT_GRAPH_ACCESS_TOKEN}}` scambia il token di accesso OpenID riutilizzabile dell'utente con un token di Microsoft Graph tramite il flusso on-behalf-of. Gli ambiti richiesti provengono da [`GRAPH_API_SCOPES`](/docs/configuration/dotenv#microsoft-graph-api--entra-id-integration), che per impostazione predefinita è `https://graph.microsoft.com/.default` ed è separato da `OPENID_GRAPH_SCOPES` (ricerca di persone e gruppi).

- **Esempio:**
  ```yaml
  headers:
    X-User-ID: '{{LIBRECHAT_USER_ID}}'
    X-User-Email: '{{LIBRECHAT_USER_EMAIL}}'
    X-User-Role: '{{LIBRECHAT_USER_ROLE}}'
    X-API-Key: '${SOME_API_KEY}'
    Authorization: 'Bearer ${SOME_AUTH_TOKEN}'
  ```

#### `requestHeaders` [#requestheaders]

- **Tipo:** Oggetto (Opzionale, per i tipi `sse` e `streamable-http`)
- **Descrizione:** Gli header vengono risolti solo per una richiesta di chat attiva. Utilizzano gli stessi segnaposto di `headers`, vengono uniti sopra `headers` e hanno la priorità quando entrambi gli oggetti definiscono lo stesso nome.
- **Comportamento di scoperta:** La scoperta degli strumenti omette completamente `requestHeaders`, quindi i valori relativi alla sola richiesta come `{{LIBRECHAT_BODY_*}}` non nascondono il catalogo degli strumenti del server. L'esecuzione attiva li risolve e li invia al momento della connessione.

```yaml
requestHeaders:
  X-Conversation-ID: '{{LIBRECHAT_BODY_CONVERSATIONID}}'
  X-Schedule-ID: '{{LIBRECHAT_BODY_SCHEDULEID}}'
```

#### `apiKey` [#apikey]

- **Tipo:** Oggetto (Opzionale, per i tipi `sse` e `streamable-http`)
- **Descrizione:** Configurazione dell'autenticazione tramite chiave API per il server MCP. Fornisce un modo strutturato per configurare l'autenticazione basata su chiave API.
- **Sotto-chiavi:**
  - `source`: Stringa (obbligatorio) - Da dove proviene la chiave API. Opzioni:
    - `"admin"`: la chiave API viene configurata dall'amministratore con `key`
    - `"user"`: la chiave API viene fornita dall'utente tramite l'interfaccia utente
  - `key`: String - (Per `source: "admin"`) Il valore della chiave API, condiviso da tutti gli utenti. Supporta i riferimenti `${ENV_VAR}`. Con `source: "admin"`, se `key` viene omesso non viene inviato alcun header.
  - `authorization_type`: String (obbligatorio) - Come viene inviata la chiave API nelle richieste. Opzioni:
    - `"bearer"`: Inviato come `Authorization: Bearer <key>`
    - `"basic"`: Inviato come `Authorization: Basic <key>`
    - `"custom"`: Inviato in un header personalizzato (richiede `custom_header`)
  - `custom_header`: String - (Utilizzato quando `authorization_type` è `"custom"`) Il nome dell'header da utilizzare per la chiave API. Il valore predefinito è `X-Api-Key` se omesso.
- **Esempio:**

  ```yaml
  # Admin-provided API key with Bearer auth
  my-server:
    type: streamable-http
    url: https://api.example.com/mcp
    apiKey:
      source: 'admin'
      key: '${MY_SERVER_API_KEY}'
      authorization_type: 'bearer'

  # User-provided API key with custom header
  another-server:
    type: sse
    url: https://api.example.com/sse
    apiKey:
      source: 'user'
      authorization_type: 'custom'
      custom_header: 'X-API-Key'
  ```

Per i server condivisi creati dall'interfaccia utente che utilizzano `apiKey.source: user`, le chiavi salvate sono vincolate alla destinazione della richiesta normalizzata. La modifica del percorso o della query dell'URL, del proxy, del trasporto, del formato o dell'intestazione di autorizzazione, oppure del client OAuth o della destinazione configurati, richiede agli utenti di inserire nuove chiavi; le modifiche equivalenti o puramente estetiche preservano le chiavi esistenti. Le chiavi legacy già esistenti continuano a funzionare sul confine invariato. Solo le variabili di credenziale attualmente dichiarate possono essere sostituite, anche in `requestHeaders`; una variabile generata in precedenza e iniettata non può riutilizzare la propria chiave. Completare l'aggiornamento su **ogni replica dell'API**, inclusi i writer della configurazione. Vedi [Crea un server dall'interfaccia utente](/docs/features/mcp#create-a-server-from-the-ui) per ciò che vedono gli utenti.

#### `iconPath` [#iconpath]

- **Tipo:** Stringa (Opzionale)
- **Descrizione:** Definisce l'icona di visualizzazione dello strumento mostrata nella finestra di dialogo di selezione dello strumento.

#### `chatMenu` [#chatmenu]

- **Tipo:** Booleano (Opzionale)
- **Descrizione:** Se impostato su `false`, il server viene escluso dalla sezione **MCP Servers** del compositore di chat, e le richieste di chat che lo indicano vengono rifiutate. Gli agenti possono comunque utilizzare il server, così come una model spec che lo elenca.
- **Valore predefinito:** `true`
- **Esempio:**
  ```yaml
  mcpServers:
    internal-tools:
      command: npx
      args: ['-y', 'internal-mcp-server']
      chatMenu: false # only available in the Agent Builder
  ```

#### `serverInstructions` [#serverinstructions]

- **Tipo:** Booleano o Stringa (Opzionale)
- **Descrizione:** Controlla come le istruzioni del server MCP vengono iniettate nel contesto dell'agente. Le istruzioni del server forniscono una guida all'utilizzo di alto livello per l'intero server MCP, integrando le descrizioni dei singoli strumenti.
- **Opzioni:**
  - **`undefined`** (predefinito): Nessuna istruzione è inclusa
  - **`true`**: Utilizza le istruzioni fornite dal server (se disponibili) - ideale per server ben documentati con una guida completa
  - **`false`**: Disabilita esplicitamente le istruzioni - utile per risparmiare token di contesto o quando gli strumenti sono autoesplicativi
  - **`string`**: Utilizza istruzioni personalizzate (sovrascrivono quelle fornite dal server) - ideale per flussi di lavoro specifici dell'applicazione o quando le istruzioni del server non sono sufficienti
- **Valore predefinito:** `undefined` (nessuna istruzione inclusa)
- **Note:**
  - Le istruzioni vengono iniettate automaticamente quando `serverInstructions` è configurato e gli strumenti del server sono disponibili per l'agente.
  - Più server possono contribuire ciascuno con istruzioni al contesto dell'agente
  - LibreChat memorizza il testo pubblicizzato dal server separatamente dalla dichiarazione configurata. L'ispezione non sostituisce `true` o una stringa creata dall'operatore, e le voci del registro basate su Redis provenienti da build precedenti vengono aggiornate automaticamente durante l'inizializzazione.
- **Esempio:**

  ```yaml
  # Use server-provided instructions
  serverInstructions: true

  # Use custom instructions
  serverInstructions: |
    When using this filesystem server:
    1. Always use absolute paths for file operations
    2. Check file permissions before attempting write operations

  # Explicitly disable instructions
  serverInstructions: false
  ```

#### `env` [#env]

- **Tipo:** Oggetto (Opzionale, solo tipo `stdio`)
- **Descrizione:** Variabili d'ambiente da utilizzare durante la generazione del processo.
- **Supporto segnaposto:**
  - `{{LIBRECHAT_USER_ID}}`: Sostituito con l'ID dell'utente corrente.
  - `{{LIBRECHAT_USER_*}}`: Segnaposto dinamici per i campi utente (es. `{{LIBRECHAT_USER_EMAIL}}`).
  - `{{CUSTOM_VARIABLE_NAME}}`: Sostituito con il valore fornito dall'utente per una variabile definita in `customUserVars` (ad esempio, `{{MY_API_KEY}}`).
  - `${ENV_VAR}`: Sostituito con il valore della variabile d'ambiente lato server `ENV_VAR`.

#### `timeout` [#timeout]

- **Tipo:** Intero (Opzionale)
- **Descrizione:** Timeout in millisecondi per le richieste ai server MCP, incluse le chiamate agli strumenti. Deve essere un numero intero non negativo.
- **Valore predefinito:** `60000` (60 secondi)
- **Nota:** Se le chiamate agli strumenti lunghe continuano a essere interrotte, verifica i timeout di qualsiasi reverse proxy posto davanti a LibreChat o al server MCP (nginx, Traefik e simili).
- **Esempio:**
  ```yaml
  mcpServers:
    data-processor:
      type: streamable-http
      url: https://api.example.com/mcp
      initTimeout: 15000 # 15 seconds to connect
      timeout: 60000 # 60 seconds per tool call
  ```

#### `initTimeout` [#inittimeout]

- **Tipo:** Intero (Opzionale)
- **Descrizione:** Timeout in millisecondi per l'inizializzazione del server MCP. Deve essere un intero non negativo. Non limita il tempo a disposizione dell'utente per completare l'accesso OAuth; tale limite è definito da `MCP_OAUTH_HANDLING_TIMEOUT` (vedi [URL di callback OAuth](#oauth-callback-url)).
- **Valore predefinito:** `30000` (30 secondi)

#### `requiresOAuth` [#requiresoauth]

- **Tipo:** Booleano (Opzionale, solo per trasporti remoti: `sse`, `streamable-http`, `websocket`)
- **Descrizione:** Indica se questo server richiede l'autenticazione OAuth. Se non specificato, verrà rilevato automaticamente all'avvio del server. Sebbene sia facoltativo, è preferibile impostare questo valore esplicitamente se si sa se il server richiede o meno OAuth.
- **Valore predefinito:** Rilevato automaticamente se non specificato
- **Note:**
  - Applicabile ai trasporti remoti (basati su URL): `sse`, `streamable-http` e `websocket`. Non ha alcun effetto sui server `stdio`, che non hanno un URL su cui autenticarsi.
  - Il rilevamento automatico avviene durante l'avvio del server, il che potrebbe aumentare il tempo di inizializzazione.
  - La configurazione esplicita migliora le prestazioni all'avvio saltando il rilevamento
  - Imposta `requiresOAuth: false` per i server protetti solo da un'intestazione `Authorization` statica (ad esempio, una chiave API Bearer). Il rilevamento automatico esegue il probe del server _senza_ le intestazioni configurate, quindi un server che risponde con un errore `401` e una richiesta `WWW-Authenticate: Bearer` può essere erroneamente classificato come protetto da OAuth; questo flag ignora tale probe e consente alla tua intestazione statica di autenticare la connessione normalmente.
  - Funziona con le variabili d'ambiente MCP OAuth (`MCP_OAUTH_ON_AUTH_ERROR`, `MCP_OAUTH_DETECTION_TIMEOUT`, `MCP_OAUTH_HANDLING_TIMEOUT`, `MCP_OAUTH_FLOW_TTL`) per una gestione avanzata delle connessioni

#### Coordinamento del refresh OAuth [#oauth-refresh-coordination]

Per deployment con più repliche, `oauthRefreshCoordination: true` serializza il refresh dei token tramite l'istanza Redis condivisa. `oauthRefreshWaitTimeout` controlla per quanto tempo una replica attende il risultato del refresh, mentre `oauthPersistenceWaitTimeout` controlla per quanto tempo attende che le credenziali aggiornate diventino leggibili; entrambi hanno come valore predefinito `15000` millisecondi. `oauthRefreshWaitTimeout` è limitato a un massimo di `30000`, mentre `oauthPersistenceWaitTimeout` accetta al massimo `840000` (14 minuti).

Abilita il coordinamento solo dopo che ogni replica è stata aggiornata e connessa alla stessa distribuzione Redis. Utilizza valori identici su ogni replica, svuota le richieste attive prima di modificare l'impostazione ed evita di attivarla o disattivarla durante un deployment a rotazione (rolling deployment).

#### `stderr` [#stderr]

- **Tipo:** Stringa o Intero (Opzionale, solo tipo `stdio`)
- **Descrizione:** Come gestire `stderr` del processo figlio. Questo corrisponde alla semantica di [`child_process.spawn`](https://nodejs.org/api/child_process.html#child_processspawncommand-args-options) di Node. Valori stringa validi: `"pipe"`, `"ignore"`, `"inherit"`. In alternativa, è possibile utilizzare un numero intero non negativo come descrittore di file.
- **Valore predefinito:** `"inherit"` (i messaggi verso `stderr` verranno stampati sullo `stderr` del processo genitore).

#### `customUserVars` [#customuservars]

- **Tipo:** Oggetto (Opzionale)
- **Descrizione:** Definisce variabili personalizzate che gli utenti possono impostare per questo server MCP. Ciò consente agli amministratori di specificare variabili (ad esempio, chiavi API, URL) che ogni utente deve configurare individualmente. Questi valori forniti dall'utente possono quindi essere utilizzati nella configurazione di `headers` o `env`. I server con `customUserVars` vengono automaticamente esclusi dalle connessioni a livello di app, garantendo che le credenziali per utente vengano sempre risolte in fase di esecuzione.
- **Struttura:**
  - L'oggetto `customUserVars` contiene chiavi, dove ogni chiave rappresenta un nome di variabile (ad esempio, `MY_API_KEY`). Questo nome verrà utilizzato nei segnaposto come `{{MY_API_KEY}}`.
  - Ogni nome di variabile è un oggetto con le seguenti sottochiavi:
    - `title`: String (Obbligatorio) - Un titolo intuitivo per la variabile, visualizzato nell'interfaccia di configurazione.
    - `description`: String (Obbligatorio) - Una descrizione o istruzioni per la variabile, visualizzate anche nell'interfaccia utente per guidare l'utente. In questo campo è possibile utilizzare HTML (ad esempio, per creare un link: `<a href="https://example.com" target="_blank">More info</a>`).
    - `sensitive`: Booleano (Opzionale) - Controlla se il valore viene trattato come un segreto e mascherato nell'interfaccia utente. Per impostazione predefinita, se omesso, il comportamento è mascherato/segreto; impostare su `false` per campi non segreti come ID progetto o URL di base.
- **Utilizzo in `headers` e `env`:**
  - Una volta definite sotto `customUserVars`, queste variabili possono essere referenziate nelle sezioni `headers` (per i tipi `sse` e `streamable-http`) o `env` (per il tipo `stdio`) utilizzando la sintassi `{{VARIABLE_NAME}}`.
  - Gli utenti inseriscono questi valori quando si connettono per la prima volta al server, e possono modificarli in seguito con **Configura** nel compositore della chat o in **Impostazioni MCP**. Vedi [Credenziali e variabili](/docs/features/mcp#credentials-and-variables).
  - Questi valori forniti dall'utente sono memorizzati per ogni utente e per ogni server MCP, e vengono sostituiti a runtime.
  - Se le variabili non sono disponibili all'avvio di LibreChat (ad esempio un token di accesso personale di GitHub), puoi anche impostare [`startup: false`](#startup) in modo che LibreChat non tenti di connettersi finché non lo fa un utente.
- **Esempio:**
  ```yaml
  customUserVars:
    MY_SERVICE_API_KEY:
      title: 'My Service API Key'
      description: "Your personal API access key for My Service. Find it at <a href='https://myservice.example.com/settings/api' target='_blank'>My Service API Settings</a>."
      sensitive: true
    SOME_OTHER_VAR:
      title: 'Some Other Variable'
      description: 'The specific value for some other configuration (e.g., a specific path or identifier).'
      sensitive: false
  ```
  Utilizzo in `headers`:
  ```yaml
  headers:
    X-Auth-Token: '{{MY_SERVICE_API_KEY}}'
    X-Some-Other-Config: '{{SOME_OTHER_VAR}}'
  ```
  Usage in `env` (for `stdio` type):
  ```yaml
  env:
    API_KEY: '{{MY_SERVICE_API_KEY}}'
  ```

#### `obo` [#obo]

- **Tipo:** Oggetto (Opzionale, solo per i tipi `sse` e `streamable-http`)
- **Descrizione:** Configura lo scambio di token OAuth 2.0 On-Behalf-Of per un server MCP. LibreChat scambia il token di accesso OpenID dell'utente connesso con un token delegato downstream con gli scope configurati, quindi inoltra tale token al server MCP come header `Authorization: Bearer ...`.
- **Sottochiavi richieste:**
  - `scopes`: String - Scopes non vuoti richiesti per lo scambio di token a valle.
- **Validazione:**
  - `obo` è valido solo per i server MCP `sse` e `streamable-http`.
  - `obo` viene rifiutato per i server `stdio` e `websocket`.
  - Gli utenti necessitano dell'autorizzazione del ruolo `MCP_SERVERS.CONFIGURE_OBO` per configurare questo campo. Impostalo inizialmente con [`interface.mcpServers.configureObo`](/docs/configuration/librechat_yaml/object_structure/interface#mcpservers) o gestiscilo dal pannello di amministrazione.
- **Prerequisiti:**
  - L'autenticazione OpenID deve essere configurata con token di accesso riutilizzabili.
  - Il tuo identity provider e l'applicazione downstream devono consentire l'ambito delegato richiesto.
- **Esempio:**
  ```yaml
  mcpServers:
    enterprise-tools:
      type: streamable-http
      url: https://api.example.com/mcp/
      obo:
        scopes: 'api://mcp-server-id/Mcp.Tools.ReadWrite'
  ```

Vedi [OpenID Connect Token Reuse](/docs/configuration/authentication/OAuth2-OIDC/token-reuse) e [SharePoint Integration](/docs/configuration/sharepoint) per la configurazione correlata del riutilizzo dei token e dei token delegati.

#### `oauth` [#oauth]

- **Tipo:** Oggetto (Opzionale)
- **Descrizione:** Configurazione OAuth2 per l'autenticazione con il server MCP. Una volta configurato, agli utenti verrà richiesto di autenticarsi tramite il flusso OAuth prima che il server MCP possa essere utilizzato. Se non vengono forniti client id e client secret, verrà utilizzata la Dynamic Client Registration (DCR).
- **Sottochiavi:** Tutte le sottochiavi di `oauth` sono opzionali. Gli endpoint possono essere rilevati automaticamente e un client può essere ottenuto tramite Dynamic Client Registration.
  - `authorization_url`: String - L'URL dell'endpoint di autorizzazione OAuth
  - `token_url`: String - L'URL dell'endpoint del token OAuth
  - `client_id`: String - Identificativo client OAuth
  - `client_secret`: Stringa - Segreto del client OAuth
  - `redirect_uri`: String - [URI di reindirizzamento OAuth](#oauth-callback-url) (es. `http://localhost:3080/api/mcp/${serverName}/oauth/callback`)
  - `scope`: String - Scope OAuth (separati da spazi)
- **Sottochiavi aggiuntive:**
  - `grant_types_supported`: Array di Stringhe - Tipi di grant supportati (predefinito a `["authorization_code", "refresh_token"]`)
  - `token_endpoint_auth_methods_supported`: Array of Strings - Metodi di autenticazione dell'endpoint del token supportati (predefinito a `["client_secret_basic", "client_secret_post"]`)
  - `token_exchange_method`: String - Override opzionale per lo scambio di token. Utilizzare `default_post` per inviare le credenziali del client nel corpo POST form-encoded, oppure `basic_auth_header` per inviarle nell'intestazione di autorizzazione HTTP Basic. Se omesso, LibreChat rileva i metodi di autenticazione dell'endpoint del token pubblicizzati dal provider e utilizza l'autenticazione Basic come impostazione predefinita se non ne viene pubblicizzato nessuno.
  - `response_types_supported`: Array di Stringhe - Tipi di risposta supportati (predefinito a `["code"]`)
  - `code_challenge_methods_supported`: Array di Stringhe - Metodi di code challenge PKCE supportati (predefinito a `["S256", "plain"]`)
  - `skip_code_challenge_check`: Booleano - Salta il controllo per verificare se il provider OAuth pubblicizza il supporto PKCE. Utile per provider come AWS Cognito che supportano S256 ma non lo pubblicizzano nei propri metadati. (il valore predefinito è `false`)
  - `revocation_endpoint`: Stringa - URL dell'endpoint di revoca dei token. Viene rilevato automaticamente quando omesso.
  - `revocation_endpoint_auth_methods_supported`: Array di stringhe - Metodi di autenticazione supportati dall'endpoint di revoca. Rilevati automaticamente se omesso.
  - `audience`: String - Inviato come parametro `audience` nella richiesta di autorizzazione, per provider come Auth0 che emettono token con ambito API solo quando viene richiesto un audience. Solo per amministratori: rifiutato per i server creati dagli utenti nell'interfaccia utente.
  - `forward_audience_on_refresh`: Booleano - Indica se `audience` viene inviato anche nella richiesta di tipo `refresh_token` grant. Il valore predefinito è `true`, necessario per Auth0. Impostare a `false` per i provider con endpoint dei token rigorosi, come AWS Cognito, che rifiutano il parametro aggiuntivo. Viene ignorato quando `audience` non è impostato. Solo amministratori.
  - `send_resource_parameter`: Booleano - Indica se il parametro `resource` previsto dall'RFC 8707 viene inviato nella richiesta di autorizzazione, nello scambio del codice e nella richiesta di aggiornamento (refresh grant). Il valore predefinito è `true`. Impostare su `false` per i provider che lo rifiutano, come Microsoft Entra ID v2.0, che restituisce l'errore `AADSTS9010010` quando `resource` e `scope` vengono inviati entrambi. Per ottenere un token limitato a un'API, utilizzare invece `scope` o `audience`. Solo amministratori.
- **Variabili d'ambiente:** i campi URL OAuth definiti in YAML, inclusi `authorization_url`, `token_url`, `redirect_uri` e `revocation_endpoint`, possono utilizzare riferimenti `${ENV_VAR}`. LibreChat risolve il valore dell'ambiente prima della convalida dell'URL. Gli URL degli endpoint OAuth gestiti dall'utente e inviati tramite l'interfaccia utente devono essere URL letterali e rifiutare i segnaposto `${ENV_VAR}`.
- **Esempio:**

  ```yaml
  oauth-api-server:
    authorization_url: https://api.example.com/oauth/authorize
    token_url: https://api.example.com/oauth/token
    client_id: your_client_id
    client_secret: your_client_secret
    redirect_uri: http://localhost:3080/api/mcp/oauth-api-server/oauth/callback
    scope: 'read execute'
    grant_types_supported: ['authorization_code', 'refresh_token']
    token_endpoint_auth_methods_supported: ['client_secret_post']
    token_exchange_method: default_post
    response_types_supported: ['code']
    code_challenge_methods_supported: ['S256', 'plain']
  ```

  Esempio Auth0:

  ```yaml
  auth0-server:
    type: streamable-http
    url: https://api.example.com/mcp/
    oauth:
      audience: https://api.example.com
      scope: 'read:data offline_access'
  ```

Quando `token_exchange_method` e `token_endpoint_auth_methods_supported` vengono entrambi omessi per un client secret preconfigurato, LibreChat concede fino a cinque secondi per l'individuazione dei metadati della risorsa protetta e del server di autorizzazione. Utilizza le funzionalità pubblicizzate solo quando l'endpoint del token individuato corrisponde esattamente al `token_url` configurato; l'individuazione non può reindirizzare le credenziali client configurate verso un altro endpoint. Imposta `token_exchange_method` in modo esplicito quando un provider non pubblica metadati utilizzabili o richiede un metodo forzato.

Le richieste HTTP lato server per l'individuazione, la registrazione, il token e la revoca OAuth **non** seguono i redirect, anche se l'URL originale è consentito. Configura direttamente l'endpoint finale del provider quando questo effettua un redirect. Le destinazioni con indirizzi IP privati letterali sono bloccate a meno che non siano esplicitamente consentite dalla policy dell'amministratore relativa agli host attendibili o all'esatta combinazione di indirizzo e porta. Questa restrizione si applica alle richieste HTTP OAuth lato server; non impedisce al browser dell'utente di completare il normale redirect alla pagina di autorizzazione.

#### `oauth_headers` [#oauth_headers]

- **Tipo:** Oggetto (Opzionale)
- **Descrizione:** Intestazioni utilizzate specificamente per le richieste del flusso OAuth. Queste intestazioni vengono impiegate durante l'autenticazione OAuth, come la registrazione dinamica del client e lo scambio di token, e non vengono inviate durante la normale comunicazione con il server MCP.
- **Casi d'uso comuni:**
  - Aggiunta dell'autenticazione agli endpoint di registrazione client dinamica, come `Authorization: Bearer ${DCR_API_KEY}`
  - Inclusione di intestazioni personalizzate specifiche del provider richieste per i flussi OAuth
  - Impostazione degli header necessari per gli endpoint dei token OAuth
- **Supporto ai segnaposto:** I valori accettano i segnaposto `{{LIBRECHAT_USER_*}}` e i riferimenti `${ENV_VAR}`, così come i campi di tipo stringa presenti sotto `oauth`.
- **Differenze chiave rispetto a `headers`:**
  - **`headers`**: Inviati con le normali richieste al server MCP dopo il completamento dell'autenticazione
  - **`oauth_headers`**: Inviato solo durante i flussi di autenticazione OAuth
- **Esempio:**
  ```yaml
  oauth_headers:
    Authorization: "Bearer ${DCR_API_KEY}"
    X-Custom-Header: "custom_value"
  ```

#### `oauthPrompt` [#oauthprompt]

- **Tipo:** Stringa (Opzionale)
- **Descrizione:** Controlla quando un utente viene invitato ad accedere a un server protetto da OAuth.
  - `on_start`: il messaggio di accesso compare all'inizio del turno di conversazione, prima che l'agente venga eseguito.
  - `on_use`: il turno inizia senza un prompt e l'agente trova gli strumenti del server tramite la ricerca degli strumenti. Il prompt compare quando l'agente chiama per la prima volta uno degli strumenti del server, e l'esecuzione attende che l'utente effettui l'accesso.
- **Valore predefinito:** `on_start`
- **Note:**
  - `on_use` si applica solo quando tutti gli strumenti selezionati dall'agente dal server sono [differiti](/docs/features/agents#deferred-tools) (opzione "Defer" attiva). Se uno qualsiasi degli strumenti selezionati viene caricato in anticipo, oppure se l'agente seleziona l'intero server anziché singoli strumenti, il prompt rimane all'inizio del turno.
  - Il checkpoint `deferred_tools` della [funzionalità dell'agente](/docs/configuration/librechat_yaml/object_structure/agents#capabilities) deve essere abilitato. Quando la funzionalità `run_in_background` è abilitata, uno strumento selezionato che sceglie l'esecuzione in background mantiene la richiesta all'inizio del turno, poiché una chiamata separata non può attendere un accesso.
  - `on_use` richiede un [`oauthToolCatalog`](#oauthtoolcatalog) dichiarato. Senza di esso, il server mantiene il prompt all'avvio del turno, anche per un utente che si è già connesso in precedenza.
  - Gli strumenti offerti prima dell'accesso devono includere ogni strumento selezionato, altrimenti il prompt resta all'inizio del turno. Questo è il catalogo dichiarato oppure, quando una connessione precedente ne ha lasciato uno, l'elenco di strumenti dell'utente.
  - Solo i server configurati dall'operatore sono idonei: quelli definiti in `librechat.yaml` o aggiunti tramite [override della configurazione di amministrazione](/docs/configuration/admin_panel#configuration-overrides). I server creati dagli utenti nell'interfaccia mantengono il prompt all'inizio del turno. Il prompt rimane all'inizio del turno per un server che utilizza `obo`, `customUserVars`, `requestHeaders` o segnaposto per utente o per richiesta (`{{LIBRECHAT_USER_*}}`, `{{LIBRECHAT_OPENID_*}}`, `{{LIBRECHAT_GRAPH_*}}`, `{{LIBRECHAT_BODY_*}}`) nelle sue impostazioni di connessione.
  - Si applica sia quando OAuth è configurato in anticipo (`oauth`, `requiresOAuth: true`) sia quando viene rilevato nel momento in cui il server rifiuta la connessione.
  - Non disponibile sui server che gli utenti creano nell'interfaccia utente.
- **Esempio:**
  ```yaml
  mcpServers:
    google-sheets:
      type: streamable-http
      url: https://sheets.example.com/mcp
      requiresOAuth: true
      oauthPrompt: on_use
      oauthToolCatalog:
        - name: read_sheet
          description: Read the values in a spreadsheet range
  ```

#### `oauthToolCatalog` [#oauthtoolcatalog]

- **Tipo:** Array di oggetti (opzionale)
- **Descrizione:** Gli strumenti che un server con `oauthPrompt: on_use` offre alla ricerca di strumenti prima che un utente effettui l'accesso. LibreChat non può elencare gli strumenti di un server protetto per un utente che non ha effettuato l'accesso, quindi l'operatore li dichiara qui. Il catalogo è lo stesso per tutti gli utenti; la connessione di nessun utente determina ciò che vedono gli agenti degli altri utenti. Una volta che un utente ha effettuato l'accesso, vengono utilizzate le definizioni degli strumenti del server stesso, e il server convalida ogni chiamata.
- **Campi di inserimento:**
  - `name`: String (Obbligatorio) - Il nome dello strumento sul server, così come viene selezionato dall'agente.
  - `description`: Stringa (Facoltativo) - Descrizione di cosa fa lo strumento, mostrata alla ricerca degli strumenti e al modello.
  - `inputSchema`: Object (Facoltativo) - I parametri dello strumento:
    - `type`: deve essere `object`
    - `properties`: mappa dal nome del parametro a uno schema della proprietà
    - `required`: array di nomi dei parametri obbligatori
- **Schema delle proprietà:** un sottoinsieme limitato di JSON Schema con solo queste chiavi:
  - `type`: uno tra `string`, `number`, `integer`, `boolean`, `object`, `array`, `null`, oppure un elenco non vuoto di questi valori
  - `description`: String
  - `enum`: array non vuoto di stringhe, numeri, booleani o `null`
  - `default`: una stringa, un numero, un booleano o `null`
  - `items`: per gli array, un oggetto con `type`, `description` e `enum`
- **Note:**
  - La validazione è rigorosa. Una chiave di voce scritta in modo errato (ad esempio `input_schema`) oppure una parola chiave al di fuori dello schema delimitato (ad esempio `minLength`, `pattern` o `$ref`) causa il fallimento della validazione della configurazione, invece di essere ignorata.
  - Un utente la cui connessione precedente ha lasciato un elenco di strumenti riceve invece quell'elenco; in ogni caso deve includere tutti gli strumenti che l'agente ha selezionato dal server, altrimenti il prompt resta all'inizio del turno.
  - Non disponibile sui server che gli utenti creano nell'interfaccia utente.
- **Esempio:**
  ```yaml
  oauthToolCatalog:
    - name: read_sheet
      description: Read the values in a spreadsheet range
      inputSchema:
        type: object
        properties:
          range: { type: string }
        required: [range]
  ```

#### `startup` [#startup]

- **Tipo:** Booleano (Opzionale)
- **Descrizione:** Se impostato su `false`, questo server MCP non verrà connesso all'avvio dell'applicazione. Ciò è utile per i server che richiedono l'input o la configurazione dell'utente prima della connessione, o per i casi in cui si desidera controllare quando il server viene inizializzato.
- **Valore predefinito:** `true`
- **Esempio:**
  ```yaml
  mcpServers:
    my-mcp-server:
      type: streamable-http
      url: 'https://api.example.com/mcp/'
      startup: false
  ```

### Note [#notes]

- **Inferenza del tipo:**
  - Se `type` viene omesso:
    - Se `url` è specificato e inizia con `http://` o `https://`, `type` è impostato per impostazione predefinita su `sse`.
    - Se `url` è specificato e inizia con `ws://` o `wss://`, `type` è impostato come `websocket` per impostazione predefinita.
    - Se `command` è specificato, `type` è impostato come `stdio` per impostazione predefinita.
- **Tipi di connessione:**
  - **`stdio`**: Avvia un server MCP come processo figlio e comunica tramite input/output standard.
  - **`websocket`**: Si connette a un server MCP esterno tramite WebSocket.
  - **`sse`**: Si connette a un server MCP esterno tramite Server-Sent Events (SSE).
  - **`streamable-http`**: Si connette a un server MCP esterno tramite HTTP con supporto per lo streaming delle risposte.
  - `stdio` esegue un processo sull'host di LibreChat ed è adatto a configurazioni locali con un singolo utente. `sse` è il vecchio trasporto remoto. Per distribuzioni multi-utente o di produzione, usa `streamable-http`.
- **Indirizzi Interni/Locali:**
  - **Importante**: I server MCP che utilizzano indirizzi IP interni (ad esempio, `172.24.1.165`, `192.168.1.100`) o domini locali (ad esempio, `mcp-server`, `host.docker.internal`) **devono** essere esplicitamente autorizzati. Utilizza [`mcpSettings.allowedAddresses`](/docs/configuration/librechat_yaml/object_structure/mcp_settings#allowedaddresses) per servizi host:porta privati specifici quando desideri che le destinazioni pubbliche rimangano raggiungibili, oppure [`mcpSettings.allowedDomains`](/docs/configuration/librechat_yaml/object_structure/mcp_settings#alloweddomains) quando desideri una whitelist rigorosa.
  - Vedi [MCP Settings](/docs/configuration/librechat_yaml/object_structure/mcp_settings) per i dettagli sulla configurazione.

## URL di callback OAuth [#oauth-callback-url]

Quando un server utilizza OAuth, il provider reindirizza a LibreChat all'indirizzo:

```text
${DOMAIN_SERVER}/api/mcp/<server-name>/oauth/callback
```

`<server-name>` è la chiave sotto `mcpServers`. Ad esempio, un server denominato `salesforce` con `DOMAIN_SERVER=https://chat.example.com` utilizza `https://chat.example.com/api/mcp/salesforce/oauth/callback`. Un'installazione locale con Docker di solito utilizza `http://localhost:3080` come base. Per i server creati dall'interfaccia utente, l'identificatore generato del server sostituisce la chiave e LibreChat mostra l'**URI di reindirizzamento** completo dopo la creazione del server.

Registra questo URL esatto presso il provider OAuth. Gli altri percorsi di callback di LibreChat, come `/api/oauth/callback` o `/api/oauth/openid/callback`, non funzionano per MCP.

Se il provider supporta la registrazione dinamica del client, il server non richiede alcun blocco `oauth`; LibreChat si registra da sé come client la prima volta che un utente si connette:

```yaml
mcpServers:
  # No refresh tokens: users sign in again when the token expires
  paypal:
    type: sse
    url: https://mcp.paypal.com/sse
    initTimeout: 150000
  # Issues refresh tokens: LibreChat renews access automatically
  spotify:
    type: streamable-http
    url: https://mcp-spotify-oauth-example.account.workers.dev/mcp
    initTimeout: 150000
```

Gli utenti hanno 10 minuti per completare l'accesso, e LibreChat mantiene il flusso in sospeso per 15 minuti. Puoi modificare questi valori con `MCP_OAUTH_HANDLING_TIMEOUT` e `MCP_OAUTH_FLOW_TTL` nel file `.env` (vedi [variabili d'ambiente MCP](/docs/configuration/dotenv#mcp-model-context-protocol)). Il TTL del flusso viene sempre mantenuto almeno un minuto più lungo del timeout di gestione, così una callback che arriva vicino alla scadenza trova comunque il proprio flusso.

## Server creati nell'interfaccia utente [#servers-created-in-the-ui]

Gli utenti il cui ruolo dispone del permesso `CREATE` (vedi [`interface.mcpServers`](/docs/configuration/librechat_yaml/object_structure/interface#mcpservers)) possono aggiungere server da **Impostazioni MCP** senza modificare questo file. Questi server sono memorizzati nel database e differiscono dai server YAML in alcuni aspetti:

- Sono disponibili solo i trasporti remoti (`streamable-http` e `sse`). I server `stdio` devono essere definiti qui.
- `${ENV_VAR}`, `{{LIBRECHAT_USER_*}}`, `{{LIBRECHAT_OPENID_*}}`, `{{LIBRECHAT_GRAPH_*}}`, e `{{LIBRECHAT_BODY_*}}` i segnaposto vengono rimossi dalle intestazioni, perché il server potrebbe essere condiviso con altri utenti. Vengono mantenuti solo i segnaposto `customUserVars`.
- Gli URL degli endpoint OAuth devono essere URL letterali; i riferimenti `${ENV_VAR}` vengono rifiutati.
- Scegliere una chiave API che ogni utente fornisce crea una voce `customUserVars` denominata `MCP_API_KEY_<hash>` e l'intestazione corrispondente. I server salvati prima di questa modifica possono mantenere il nome legacy `MCP_API_KEY` finché non cambiano il loro URL o l'autenticazione. Consulta [`apiKey`](#apikey) per sapere quali modifiche richiedono agli utenti di inserire di nuovo la propria chiave.
- Un server con una chiave API (condivisa o per utente) viene trattato come autenticato tramite chiave API e salta il rilevamento automatico di OAuth, a meno che non disponga anche di una configurazione OAuth. Se un server con chiave API salvato da una versione precedente rimane in **Needs Auth**, modificalo e salvalo una volta per aggiornarne i metadati memorizzati.
- I client OAuth memorizzati e i token sono associati all'URL del server e alle impostazioni del client OAuth e dell'endpoint. Modificarli comporta che gli utenti debbano effettuare nuovamente l'accesso, e chi modifica la configurazione deve reinserire il client secret memorizzato quando cambia l'URL, il client ID, l'URL di autorizzazione, l'URL del token o il metodo di scambio del token.
- `oauthPrompt` e `oauthToolCatalog` non sono disponibili.
- [`mcpSettings`](/docs/configuration/librechat_yaml/object_structure/mcp_settings) si applicano restrizioni di dominio e indirizzo.
- I server nuovi e modificati entrano in vigore senza riavviare. Un server OAuth viene salvato come disconnesso finché un utente non effettua l'accesso.

Per il set completo di segnaposto, definisci il server in `librechat.yaml`.

## Trovare i server [#finding-servers]

[Smithery](https://smithery.ai) elenca server MCP pubblici. Nella pagina di un server, la sezione **Connect** può generare un comando di installazione per il client LibreChat che scrive la voce in `librechat.yaml`; successivamente, riavvia LibreChat. Le [guide sui server MCP](/docs/mcp_servers) illustrano la configurazione di server specifici.

## Esempi [#examples]

### Configurazione con indirizzi interni [#configuration-with-internal-addresses]

Quando si utilizzano server MCP interni/locali e non è necessaria una whitelist di domini rigorosa, configurare `mcpSettings.allowedAddresses` con l'host e la porta esatti:

```yaml filename="Complete MCP Configuration with Internal Servers"
# MCP Settings - Required for internal/local addresses
mcpSettings:
  allowedAddresses:
    - '172.24.1.165:8000' # Internal IP and port
    - 'mcp-prod:8001' # Docker container and port
    - 'host.docker.internal:8080' # Docker host and port

# MCP Servers - Individual configurations
mcpServers:
  prod-mcp:
    type: streamable-http
    url: http://172.24.1.165:8000/mcp
    timeout: 120000

  test-mcp:
    type: streamable-http
    url: http://mcp-prod:8001/mcp
    timeout: 120000
```

## Informazioni aggiuntive [#additional-information]

- **Comportamento predefinito:**
  - I server definiti in `librechat.yaml` vengono inizializzati all'avvio, quindi le modifiche a questo file richiedono un riavvio. I server creati nell'interfaccia utente no.
  - I server che inviano `notifications/tools/list_changed` possono aggiungere o rimuovere strumenti durante l'esecuzione; LibreChat recupera nuovamente l'elenco degli strumenti dalla connessione attiva senza bisogno di un riavvio.
  - Quando un utente preme **Stop** durante una chiamata a uno strumento, LibreChat annulla la richiesta MCP. I server Streamable HTTP ricevono `notifications/cancelled` e devono rispettarla per interrompere il proprio lavoro. Le chiamate agli strumenti in esecuzione in background non vengono annullate.
  - Se vengono specificati sia `url` che `command`, il `type` deve essere definito esplicitamente per evitare ambiguità.
- **Supporto Multi-Utente:**
  - MCPManager ora supporta connessioni distinte a livello utente e a livello app, consentendo una corretta gestione delle connessioni per ogni utente.
  - Le connessioni degli utenti vengono tracciate e gestite separatamente, con una corretta configurazione e pulizia.
  - Con Redis abilitato, lo stato del flusso OAuth e il catalogo degli strumenti MCP vengono condivisi tra le repliche, inclusi i deployment Redis Cluster. Consulta [Coordinamento del refresh OAuth](#oauth-refresh-coordination) per il refresh dei token tra le repliche.
  - Usa segnaposto dinamici per i campi utente in intestazioni, URL e variabili d'ambiente:
    - `{{LIBRECHAT_USER_ID}}` - Identificativo univoco dell'utente
    - `{{LIBRECHAT_USER_EMAIL}}` - Indirizzo email dell'utente
    - `{{LIBRECHAT_USER_USERNAME}}` - Nome utente dell'utente
    - `{{LIBRECHAT_USER_ROLE}}` - Ruolo dell'utente (es. "user", "admin")
    - E molti altri campi (vedi la sezione headers per l'elenco completo)
- **Gestione dell'inattività dell'utente:**
  - Le connessioni degli utenti vengono monitorate per rilevare l'attività e verranno disconnesse dopo 15 minuti di inattività. Puoi modificare questo valore con `MCP_USER_CONNECTION_IDLE_TIMEOUT` (in millisecondi).
- **Variabili d'ambiente:**
  - **In `env` (per il tipo `stdio`):** Utile per impostare specifici ambienti di runtime o configurazioni richieste dal processo del server MCP.
  - **In `headers` (per i tipi `sse` e `streamable-http`):** Utilizza la sintassi `${ENV_VAR}` per fare riferimento alle variabili d'ambiente nei valori delle intestazioni.
- **Campi utente dinamici:**
  - I segnaposto del campo utente vengono sostituiti in fase di esecuzione con le informazioni dell'utente autenticato.
  - Sono disponibili solo i campi non sensibili (password e altri dati sensibili sono esclusi)
  - I campi mancanti vengono impostati come stringhe vuote per impostazione predefinita
  - I campi booleani vengono convertiti in rappresentazioni stringa ("true" o "false")
- **Gestione degli errori (`stderr`):**
  - La configurazione di `stderr` ti consente di gestire il modo in cui vengono gestiti i messaggi di errore dal processo del server MCP. L'impostazione predefinita `"inherit"` significa che gli errori verranno stampati nello `stderr` del processo padre.
- **Istruzioni del Server:**
  - Le istruzioni vengono iniettate automaticamente nel messaggio di sistema dell'agente quando vengono utilizzati gli strumenti del server MCP.
  - Le Custom instructions (valori stringa) hanno la precedenza sulle istruzioni fornite dal server
  - Più server MCP possono contribuire ciascuno con le proprie istruzioni al contesto dell'agente
  - Le istruzioni sono incluse solo quando gli strumenti del server MCP corrispondente sono effettivamente disponibili per l'agente
- **Autenticazione OAuth:**
  - Il flusso OAuth2 è supportato per un'autenticazione sicura con i server MCP
  - Agli utenti verrà richiesto di autenticarsi tramite OAuth prima che il server MCP possa essere utilizzato
