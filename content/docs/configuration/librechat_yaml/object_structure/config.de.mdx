## langfuse

<OptionTable
  options={[
    [
      'langfuse',
      'Object',
      'Konfiguriert die verschlüsselte Langfuse-Verbindung und die vom Deployment besessenen Request-Header.',
      '',
    ],
  ]}
/>

**Untergeordnete Schlüssel:**

<OptionTable
  options={[
    ['enabled', 'Boolean', 'Aktiviert oder deaktiviert das Langfuse-Tracing für diesen Konfigurationsbereich.', ''],
    ['publicKey', 'String', 'Öffentlicher Schlüssel des Langfuse-Projekts.', ''],
    ['secretKey', 'String', 'Verschlüsselter geheimer Projektschlüssel für Langfuse.', ''],
    ['projectId', 'String', 'Verifizierte Langfuse-Projektidentität.', ''],
    ['secretKeyPreview', 'String', 'Vom Server generierte maskierte Vorschau des gespeicherten geheimen Schlüssels.', ''],
    [
      'destination',
      'String',
      'Wählt einen für die Bereitstellung genehmigten Langfuse-Zielschlüssel aus.',
      '',
    ],
    [
      'headers',
      'Object/Map of Strings',
      'Vom Deployment bereitgestellte Header, die zur Proxy- oder Gateway-Authentifizierung an einen konfigurierten Langfuse-Ursprung gesendet werden. Unterstützt `${ENV_VAR}`-Referenzen.',
      '',
    ],
  ]}
/>

Verwalten Sie Verbindungsfelder über **Einstellungen → Langfuse** oder einen autorisierten Administrator-Konfigurations-Client. Der Einstellungs-Ablauf überprüft die Verbindung und leitet die `projectId` ab; der autorisierte Administrator schreibt die verschlüsselte `secretKey`, generiert eine `secretKeyPreview` und schwärzt den geheimen Schlüssel bei Lesezugriffen. Im Klartext angegebene `secretKey`-Werte, die direkt in die `librechat.yaml` eingetragen werden, werden vom Laufzeit-Verbindungspfad nicht akzeptiert. Die veralteten Felder `displaySecretKey` und `fanout.enabled` sind nicht mehr Teil des Schemas.

`headers` ist anders: Es handelt sich um eine Bereitstellungsinfrastruktur, die nur in `librechat.yaml` festgelegt werden kann. Die Admin-Konfiguration lehnt sowohl die gesamte Map als auch einzelne Header-Pfade ab, sodass Gateway-Anmeldeinformationen nicht gespeichert oder über die Mongo-basierte Konfiguration zurückgegeben werden. Werte unterstützen `${ENV_VAR}`-Interpolation; verwenden Sie Umgebungsreferenzen anstelle von Literalen. LibreChat verwirft nicht aufgelöste Variablen, geschützte Infrastruktur-Geheimnis-Referenzen, leere Werte und ungültige HTTP-Header-Namen mit einer Warnung.

Benutzerdefinierte Header werden nur dann bei Trace- und Medienexporten, Feedback-Score-Anfragen, Projektsuchen und der Überprüfung von Admin-Anmeldeinformationen gesendet, wenn die Bereitstellung genau einen Langfuse-Ursprung auflösbar macht. Wenn die zentrale, Mandanten- oder Collector-Konfiguration mehrere Ursprünge erzeugt, sendet LibreChat keine benutzerdefinierten Header und protokolliert eine Warnung, da die Zuordnung einen Empfänger nicht sicher identifizieren kann. Sie können keine benutzerbezogenen `{{...}}`-Platzhalter verwenden, und der Fanout-Collector leitet nur den `Authorization`-Header weiter.

```yaml filename="langfuse / headers"
langfuse:
  headers:
    CF-Access-Client-Id: '${CF_ACCESS_CLIENT_ID}'
    CF-Access-Client-Secret: '${CF_ACCESS_CLIENT_SECRET}'
```

`langfuse` ist ein Abschnitt, der nur für die Basiskonfiguration vorgesehen ist. Rollen-, Gruppen- und Benutzerkonfigurations-Overrides können diesen weder ersetzen noch deaktivieren (tombstone).

Siehe [Langfuse Configuration](/docs/configuration/langfuse) für Verfügbarkeitsregeln, die Einrichtung eines authentifizierten Proxys, umgebungsverwaltete Anmeldeinformationen und optionales Fanout-Deployment.

## fileStrategy

- **Optionen**: "local" | "firebase" | "s3" | "azure_blob" | "cloudfront"

<OptionTable
  options={[
    [
      'fileStrategy',
      'String',
      'Bestimmt, wo hochgeladene/generierte Benutzerdateien gespeichert werden. Standardmäßig auf `"local"` gesetzt, falls weggelassen.',
      'fileStrategy: "firebase"',
    ],
  ]}
/>

- **Hinweise**:
  - `"cloudfront"` speichert Dateien in S3 und gibt CloudFront-URLs für eine stabile Medienbereitstellung, signierte Cookies und signierte Downloads zurück.
  - `"firebase"` stellt Dateien über Firebase Storage und Firebase Hosting Edge-Standorte bereit.
  - S3 stellt Dateien über **presigned URLs** (temporäre signierte Token) bereit, die ablaufen. Sobald sie abgelaufen sind, wird jedes Bild oder jeder Avatar, der auf diese URL verweist, in der UI als defekt angezeigt. Dies macht S3 als primäre Strategie für visuelle Assets ungeeignet. Siehe die [zugehörige Diskussion](https://github.com/LibreChat-AI/LibreChat/discussions/10280#discussioncomment-14803903) für Details.
  - Für die beste Leistung von Bildern und Avataren verwenden Sie `"cloudfront"` oder `"firebase"`, oder konfigurieren Sie `fileStrategies`, um `avatar` und `image` an eine CDN-gestützte Strategie weiterzuleiten.
  - Bitte lesen Sie die [File Storage & CDN documentation](/docs/configuration/cdn) für Details zur Einrichtung.

## fileStrategies

Ermöglicht eine granulare Kontrolle über Dateispeicherstrategien für verschiedene Dateitypen.

- **Verfügbare Strategien**: "local" | "firebase" | "s3" | "azure_blob" | "cloudfront"

<OptionTable
  options={[
    [
      'fileStrategies',
      'Object',
      'Konfiguriert verschiedene Speicherstrategien für unterschiedliche Dateitypen. Flexibler als die einzelne fileStrategy-Option.',
      '',
    ],
  ]}
/>

**Untergeordnete Schlüssel:**

<OptionTable
  options={[
    [
      'default',
      'String',
      'Fallback-Speicherstrategie, wenn kein spezifischer Typ definiert ist. Standardmäßig auf "local" gesetzt.',
      '',
    ],
    [
      'avatar',
      'String',
      'Speicherstrategie für Benutzer- und Agenten-Avatarbilder. Für eine optimale Leistung wird eine CDN-gestützte Strategie (`"cloudfront"` oder `"firebase"`) empfohlen.',
      '',
    ],
    [
      'image',
      'String',
      'Speicherstrategie für in Chats hochgeladene Bilder. Für eine optimale Leistung wird die Verwendung einer CDN-gestützten Strategie (`"cloudfront"` oder `"firebase"`) empfohlen.',
      '',
    ],
    ['document', 'String', 'Speicherstrategie für Dokumenten-Uploads (PDFs, Textdateien usw.).', ''],
    ['skills', 'String', 'Speicherstrategie für Dateien, die mit Skills gebündelt sind.', ''],
  ]}
/>

- **Hinweise**:
  - Diese Einstellung hat Vorrang vor der einzelnen `fileStrategy`-Option
  - Wenn ein bestimmter Dateityp nicht konfiguriert ist, wird auf `default` zurückgegriffen, dann auf `fileStrategy` und schließlich auf `"local"`.
  - Bilder und Avatare benötigen persistente, stabile URLs, um in der gesamten UI korrekt gerendert zu werden. S3-presigned URLs laufen ab (AWS-Limit: 7 Tage für IAM-Benutzer, Stunden für STS/rollenbasierte Anmeldeinformationen), was zu defekten Bildern in der Modellauswahl und der Chat-UI führt. Siehe die [zugehörige Diskussion](https://github.com/LibreChat-AI/LibreChat/discussions/10280#discussioncomment-14803903) für den vollständigen Kontext. Verwenden Sie `"cloudfront"` oder `"firebase"` für `avatar` und `image`, um dies zu vermeiden.
  - S3 und Azure Blob Storage eignen sich gut für die `document`-Speicherung, bei der kurzlebige, vorab signierte Download-URLs angemessen sind.
  - Bitte lesen Sie die [File Storage & CDN documentation](/docs/configuration/cdn) für Einrichtungsdetails zu den jeweiligen Speicheranbietern.

**Beispiele:**

```yaml filename="fileStrategies - All in one place"
# Use a single strategy for all file types
fileStrategies:
  default: 's3'
```

```yaml filename="fileStrategies - Mixed strategies"
# Route images and avatars to CDN, keep documents in object storage
fileStrategies:
  avatar: 'cloudfront' # CDN delivery for avatars
  image: 'cloudfront' # CDN delivery for generated/uploaded images
  document: 's3' # Object storage for documents
```

```yaml filename="fileStrategies - Partial configuration"
# Only configure specific types, others use default
fileStrategies:
  default: 'local'
  avatar: 'firebase' # Only avatars use Firebase CDN, everything else is local
```

## secureImageLinks

<OptionTable
  options={[
    [
      'secureImageLinks',
      'Boolean',
      'Erfordert eine Autorisierung für Bild-Links, die lokal von der App gehostet werden. Standard: true.',
      'secureImageLinks: true',
    ],
  ]}
/>

Lokale Bilder sind geschützt, wenn dieses Feld weggelassen wird. Bilder aus privaten Unterhaltungen erfordern eine aktive Sitzung und Besitzerzugriff. Gespeicherte Benutzer-Avatare erfordern einen authentifizierten Betrachter im selben Mandanten. Agenten-Avatare folgen der Ansichts-ACL des Agenten, einschließlich öffentlicher Sichtbarkeit, während Assistenten-Avatare denselben Mandanten sowie die effektive Endpunkt-Freigabe- oder Assistenten-Verwaltungsrichtlinie erfordern. Fehler bei der Autorisierung und Konfigurationssuche führen zu einer Sicherheitsblockade (fail closed).

Setzen Sie `secureImageLinks: false` nur als Kompatibilitätsoption für Bereitstellungen, die absichtlich lokale Bild-URLs ohne Authentifizierung freigeben. Rollen- und Benutzerkonfigurations-Overrides werden aus der effektiven Konfiguration des Bildbesitzers aufgelöst.

**Beschreibung:**

Die `clientImageResize`-Konfiguration steuert die clientseitige Verkleinerung vor dem Hochladen. Diese Funktion hilft bei:

- **Verhindern Sie Upload-Fehler**, die durch große Bilddateien entstehen, welche die Serverlimits überschreiten
- **Bandbreitennutzung reduzieren**, indem Bilder vor der Übertragung komprimiert werden
- **Verbessern Sie die Upload-Leistung** mit kleineren Dateigrößen
- **Bildqualität beibehalten** bei gleichzeitiger Optimierung der Dateigröße

Wenn die Größenänderung aktiviert ist, werden unterstützte Bilder, die `maxWidth` oder `maxHeight` überschreiten, vor dem Hochladen im Browser herunterskaliert. LibreChat behält das Seitenverhältnis bei, skaliert kleinere Bilder niemals hoch und behält die Originaldatei bei, wenn das kodierte Ergebnis nicht kleiner wäre.

Wenn `enabled` weggelassen wird, können Benutzer **Bilder vor dem Hochladen skalieren** unter **Einstellungen > Chat** ein- oder ausschalten. Die Einstellung wird im jeweiligen Browser gespeichert und ist standardmäßig deaktiviert. Das Setzen von `enabled: true` oder `enabled: false` in der `librechat.yaml` überschreibt die Benutzereinstellungen und deaktiviert den Schalter.

**Beispiel:**

```yaml filename="clientImageResize"
fileConfig:
  clientImageResize:
    # Omit enabled so each user can choose under Settings > Chat.
    maxWidth: 1900
    maxHeight: 1900
    quality: 0.92
```

Um ein Verhalten für die Bereitstellung zu erzwingen, fügen Sie entweder `enabled: true` oder `enabled: false` zum selben Block hinzu.

**Hinweise:**

- Die Größenänderungs-Pipeline unterstützt JPEG, PNG und WebP in Browsern mit den erforderlichen Canvas-APIs.
- Animierte PNG- und WebP-Dateien werden unverändert gesendet, sodass die Größenänderung die Animation nicht verwirft.
- Die Ausgabe behält das Quellformat bei. Es gibt keine `compressFormat`-Einstellung.
- Browser-Encoder ignorieren möglicherweise `quality` bei verlustfreien Formaten wie PNG.
- Ein Fehler bei der Größenänderung führt dazu, dass auf die ursprüngliche Datei zurückgegriffen wird; die normalen Upload-Limits des Servers gelten weiterhin.

  #   - "*.example.com"         # All subdomains
  #   - "http://mcp-server:3000" # Internal service, explicitly whitelisted

  # Default SSRF mode with private service exemptions:
  allowedAddresses:
    - 'host.docker.internal:8080' # Permit one private host on one port

## mcpServers

**Schlüssel:**

<OptionTable
  options={[
    [
      'mcpServers',
      'Object',
      'Definiert die Konfiguration für Model Context Protocol (MCP) Server und ermöglicht die dynamische Integration von MCP-Servern innerhalb der Anwendung.',
      '',
    ],
  ]}
/>

**Untergeordnete Schlüssel:**

<OptionTable
  options={[
    [
      '<serverName>',
      'Object',
      'Jeder Schlüssel unter `mcpServers` repräsentiert eine individuelle MCP server Konfiguration, identifiziert durch einen eindeutigen Namen.',
      '',
    ],
  ]}
/>

- **Hinweise**:
  - Die Initialisierung erfolgt beim Start, und die App muss neu gestartet werden, damit Änderungen wirksam werden.
  - Der `<serverName>` ist ein eindeutiger Bezeichner für jede MCP Server-Konfiguration.
  - Jeder MCP server kann über einen von vier Verbindungstypen konfiguriert werden:
    - `stdio`
    - `websocket`
    - `sse`
    - `streamable-http`
  - Das Feld `type` gibt den Verbindungstyp zum MCP Server an.
  - Wenn `type` weggelassen wird, erfolgt die Standardeinstellung basierend auf dem Vorhandensein und dem Format von `url` oder `command`:
    - Wenn `url` angegeben ist und mit `http` oder `https` beginnt, ist der Standardwert für `type` `sse`.
    - Wenn `url` angegeben ist und mit `ws` oder `wss` beginnt, wird `type` standardmäßig auf `websocket` gesetzt.
    - Wenn `command` angegeben ist, ist der Standardwert für `type` `stdio`.
  - Zusätzliche Konfigurationsoptionen umfassen:
    - `timeout`: Timeout in Millisekunden für MCP-Server-Anfragen. Bestimmt, wie lange auf eine Antwort für Tool-Anfragen gewartet werden soll.
    - `initTimeout`: Timeout in Millisekunden für die MCP-Server-Initialisierung. Bestimmt, wie lange auf die Initialisierung des Servers gewartet werden soll.
    - `serverInstructions`: Steuert, ob Server-Anweisungen in den Agenten-Kontext einbezogen werden. Kann `true` (vom Server bereitgestellt verwenden), `false` (deaktiviert) oder eine benutzerdefinierte Zeichenfolge (überschreibt die vom Server bereitgestellten) sein.
    - `customUserVars`: (Optional) Definiert benutzerdefinierte Variablen (z. B. API-Schlüssel, URLs), die einzelne Benutzer für einen MCP-Server festlegen können. Diese benutzerspezifischen Werte, die über die Benutzeroberfläche bereitgestellt werden, können dann in den `headers`- oder `env`-Konfigurationen des Servers unter Verwendung der `{{VARIABLE_NAME}}`-Syntax referenziert werden. Dies ermöglicht eine benutzerspezifische Authentifizierung oder Anpassung für MCP-Tools.
  - siehe: [MCP Servers Object Structure](/docs/configuration/librechat_yaml/object_structure/mcp_servers)

**Beispiel:**

```yaml filename="mcpServers"
mcpServers:
  everything:
    # type: sse # type can optionally be omitted
    url: http://localhost:3001/sse
    timeout: 30000
    initTimeout: 10000
    serverInstructions: true # Use server-provided instructions
  puppeteer:
    type: stdio
    command: npx
    args:
      - -y
      - '@modelcontextprotocol/server-puppeteer'
    timeout: 30000
    initTimeout: 10000
    serverInstructions: 'Do not access any local files or local/internal IP addresses'
  filesystem:
    # type: stdio
    command: npx
    args:
      - -y
      - '@modelcontextprotocol/server-filesystem'
      - /home/user/LibreChat/
    iconPath: /home/user/LibreChat/client/public/assets/logo.svg
  mcp-obsidian:
    command: npx
    args:
      - -y
      - 'mcp-obsidian'
      - /path/to/obsidian/vault
  streamable-http-example:
    type: streamable-http
    url: https://example.com/mcp
    headers:
      Authorization: 'Bearer ${API_TOKEN}'
    timeout: 30000
  per-user-crendentials-example:
    type: sse
    url: 'https//some.mcp/sse'
    headers:
      X-Custom-Auth-Token: '{{USER_API_KEY}}' # Placeholder for the user-provided API key, defined in `customUserVars` below.
    customUserVars:
      USER_API_KEY:
        title: 'Service API Key'
        description: "Your personal API key for this service. You can get it <a href='https://example.com/api-keys' target='_blank'>here</a>."
    serverInstructions: true
```
