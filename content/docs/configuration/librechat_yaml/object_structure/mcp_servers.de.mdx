## Beispiel [#example]

```yaml filename="MCP Servers Object Structure"
# Example MCP Servers Object Structure
mcpServers:
  everything:
    # type: sse # type can optionally be omitted
    url: http://localhost:3001/sse
  googlesheets:
    type: sse
    url: https://mcp.composio.dev/googlesheets/some-endpoint
    requiresOAuth: true
    headers:
      X-User-ID: '{{LIBRECHAT_USER_ID}}'
      X-API-Key: '${SOME_API_KEY}'
    serverInstructions: true # Use server-provided instructions
  puppeteer:
    type: stdio
    command: npx
    args:
      - -y
      - '@modelcontextprotocol/server-puppeteer'
    serverInstructions: 'Do not access any local files or local/internal IP addresses'
  filesystem:
    # type: stdio
    command: npx
    args:
      - -y
      - '@modelcontextprotocol/server-filesystem'
      - /home/user/LibreChat/
    iconPath: /home/user/LibreChat/client/public/assets/logo.svg
    # The “wrench” icon shows up if no icon is provided as it is the default rendering.
  mcp-obsidian:
    command: npx
    args:
      - -y
      - 'mcp-obsidian'
      - /path/to/obsidian/vault
  streamable-http-server:
    type: streamable-http
    url: https://example.com/api/
    proxy: '${MCP_PROXY_URL}'
  per-user-credentials-example:
    type: streamable-http
    url: 'https://example.com/api/'
    headers:
      X-Auth-Token: '{{MY_SERVICE_API_KEY}}'
    customUserVars:
      MY_SERVICE_API_KEY:
        title: 'My Service API Key'
        description: "Enter your personal API key for the service. You can generate one at <a href='https://myservice.example.com/developer/keys' target='_blank'>Service Developer Portal</a>."
        sensitive: true
      MY_SERVICE_PROJECT:
        title: 'Project ID'
        description: 'Enter the project ID used by this service.'
        sensitive: false
  oauth-example:
    type: streamable-http
    url: https://api.example.com/mcp/
    oauth:
      authorization_url: https://example.com/oauth/authorize
      token_url: https://example.com/oauth/token
      client_id: your_client_id
      client_secret: your_client_secret
      redirect_uri: http://localhost:3080/api/mcp/oauth-example/oauth/callback
      scope: 'read execute'
  obo-example:
    type: streamable-http
    url: https://api.example.com/mcp/
    obo:
      scopes: 'api://mcp-server-id/Mcp.Tools.ReadWrite'
```

<Callout type="warning" title="Prozessbasierte Server befinden sich im Besitz des Betreibers">
  MCP-Server, die `type: stdio` oder Prozessfelder wie `command`, `args`, `env`, `cwd` oder `stderr` verwenden, müssen in `librechat.yaml` konfiguriert werden. Die Admin-Konfigurations-API lehnt prozessbasierte Einträge ab, und datenbankbasierte oder prinzipal-spezifische Überschreibungen können keinen bestehenden prozessbasierten Server ersetzen oder entfernen. Remote-MCP-Server folgen weiterhin der normalen Rangfolge für Konfigurationsüberschreibungen.
</Callout>

#### `title` [#title]

- **Typ:** String (Optional)
- **Beschreibung:** Benutzerdefinierter Anzeigename für den MCP Server in der Benutzeroberfläche. Falls nicht angegeben, wird der Schlüsselname des Servers verwendet.
- **Validierung:** Muss mit einem Unicode-Buchstaben oder einer Zahl beginnen. Die restlichen Zeichen können Unicode-Buchstaben, Zahlen, kombinierende Zeichen, Leerzeichen, Bindestriche sowie gerade oder geschweifte Apostrophe enthalten.
- **Beispiel:**
  ```yaml
  my-server:
    title: 'File System Access'
    command: npx
    args: ['-y', '@modelcontextprotocol/server-filesystem']
  ```

#### `description` [#description]

- **Typ:** String (Optional)
- **Beschreibung:** Beschreibung des MCP-Servers, die in der Benutzeroberfläche angezeigt wird, um Benutzern zu helfen, dessen Zweck und Funktionen zu verstehen.
- **Beispiel:**
  ```yaml
  my-server:
    title: 'File System Access'
    description: 'Provides read/write access to local files and directories'
    command: npx
    args: ['-y', '@modelcontextprotocol/server-filesystem']
  ```

#### `type` [#type]

- **Typ:** String
- **Beschreibung:** Legt den Verbindungstyp zum MCP-Server fest. Gültige Optionen sind `"stdio"`, `"websocket"`, `"streamable-http"` oder `"sse"`. `"http"` wird als Alias für `"streamable-http"` akzeptiert.
- **Standardwert:** Wird basierend auf dem Vorhandensein und Format von `url` oder `command` bestimmt.

#### `command` [#command]

- **Typ:** String
- **Beschreibung:** (Für den Typ `stdio`) Der Befehl oder die ausführbare Datei, die ausgeführt werden soll, um den MCP Server zu starten.

#### `args` [#args]

- **Typ:** Array von Strings
- **Beschreibung:** (Für den Typ `stdio`) Kommandozeilenargumente, die an den `command` übergeben werden. Platzhalter wie `${ENV_VAR}`, `{{LIBRECHAT_USER_*}}` und `{{CUSTOM_VARIABLE_NAME}}` werden in jedem Argument aufgelöst, genauso wie in `env`.

#### `url` [#url]

- **Typ:** String
- **Beschreibung:** (Für den Typ `websocket`, `streamable-http` oder `sse`) Die URL, um eine Verbindung zum MCP Server herzustellen. Unterstützt dynamische Platzhalter für Benutzerfelder (`{{LIBRECHAT_USER_*}}`) und die Ersetzung von Umgebungsvariablen (`${ENV_VAR}`).
- **Hinweise:**
  - Für den Typ `sse` muss die URL mit `http://` oder `https://` beginnen.
  - Für den Typ `streamable-http` muss die URL mit `http://` oder `https://` beginnen.
  - Für den Typ `websocket` muss die URL mit `ws://` oder `wss://` beginnen.

#### `proxy` [#proxy]

- **Typ:** String (Optional, für `sse` und `streamable-http` Typen)
- **Beschreibung:** Ausgehende Proxy-URL für diesen entfernten MCP-Server. Der Wert kann Umgebungsvariablen mit `${ENV_VAR}` referenzieren.
- **Unterstützte Protokolle:** `http://`, `https://`, `socks://` und `socks5://`
- **Sicherheitshinweis:** `proxy` wird vom Administrator gesteuert. Es löst Umgebungsvariablen auf, löst jedoch keine benutzergesteuerten Platzhalter wie `{{LIBRECHAT_USER_ID}}` oder `customUserVars` auf.
- **Beispiel:**
  ```yaml
  mcpServers:
    remote-api:
      type: streamable-http
      url: https://api.example.com/mcp
      proxy: '${MCP_PROXY_URL}'
  ```

#### `headers` [#headers]

- **Typ:** Objekt (Optional, für `sse` und `streamable-http` Typen)
- **Beschreibung:** Benutzerdefinierte Header, die mit der Anfrage gesendet werden. Unterstützt verschiedene Platzhaltertypen für die dynamische Wertersetzung.
- **Platzhalter-Unterstützung:**
  - `{{LIBRECHAT_USER_ID}}`: Wird durch die ID des aktuellen Benutzers ersetzt, was die Unterstützung für mehrere Benutzer ermöglicht.
  - `{{LIBRECHAT_USER_*}}`: Dynamische Platzhalter für Benutzerfelder. Ersetzen Sie `*` durch die GROSSGESCHRIEBENE Version eines beliebigen zulässigen Feldes.
  - `{{LIBRECHAT_OPENID_*}}`: OpenID-Token-/Sitzungs-Platzhalter für in YAML definierte Server.
  - `{{LIBRECHAT_GRAPH_*}}`: Microsoft Graph-Token-Platzhalter für in YAML definierte Server.
  - `{{LIBRECHAT_BODY_*}}`: Platzhalter für den Request-Body bei YAML-definierten Servern, wie zum Beispiel die aktuelle `conversationId`, `parentMessageId` oder `messageId`.
  - `{{CUSTOM_VARIABLE_NAME}}`: Wird durch den vom Benutzer bereitgestellten Wert für eine in `customUserVars` definierte Variable ersetzt (z. B. `{{MY_API_KEY}}`).
  - `${ENV_VAR}`: Wird durch den Wert der Umgebungsvariable `ENV_VAR` ersetzt.

**Verfügbare Platzhalter für Benutzerfelder:**

| Platzhalter | Benutzerfeld | Typ | Beschreibung |
| :--- | :--- | :--- | :--- |
| `{{LIBRECHAT_USER_NAME}}` | `name` | String | Anzeigename des Benutzers |
| `{{LIBRECHAT_USER_USERNAME}}` | `username` | String | Benutzername des Benutzers |
| `{{LIBRECHAT_USER_EMAIL}}` | `email` | String | E-Mail-Adresse des Benutzers |
| `{{LIBRECHAT_USER_PROVIDER}}` | `provider` | String | Authentifizierungsanbieter (z. B. "email", "google", "github") |
| `{{LIBRECHAT_USER_ROLE}}` | `role` | String | Rolle des Benutzers (z. B. "user", "admin") |
| `{{LIBRECHAT_USER_GOOGLEID}}` | `googleId` | String | Google-Konto-ID |
| `{{LIBRECHAT_USER_FACEBOOKID}}` | `facebookId` | String | Facebook-Konto-ID |
| `{{LIBRECHAT_USER_OPENIDID}}` | `openidId` | String | OpenID-Konto-ID |
| `{{LIBRECHAT_USER_SAMLID}}` | `samlId` | String | SAML-Konto-ID |
| `{{LIBRECHAT_USER_LDAPID}}` | `ldapId` | String | LDAP-Konto-ID |
| `{{LIBRECHAT_USER_GITHUBID}}` | `githubId` | String | GitHub-Konto-ID |
| `{{LIBRECHAT_USER_DISCORDID}}` | `discordId` | String | Discord-Konto-ID |
| `{{LIBRECHAT_USER_APPLEID}}` | `appleId` | String | Apple-Konto-ID |
| `{{LIBRECHAT_USER_EMAILVERIFIED}}` | `emailVerified` | Boolean → String | E-Mail-Verifizierungsstatus ("true" oder "false") |
| `{{LIBRECHAT_USER_TWOFACTORENABLED}}` | `twoFactorEnabled` | Boolean → String | 2FA-Status ("true" oder "false") |
| `{{LIBRECHAT_USER_TERMSACCEPTED}}` | `termsAccepted` | Boolean → String | Status der Akzeptanz der Nutzungsbedingungen ("true" oder "false") |
| `{{LIBRECHAT_USER_TERMSACCEPTEDAT}}` | `termsAcceptedAt` | Date → String | Zeitstempel der Akzeptanz der Nutzungsbedingungen |

**Hinweis:** Fehlende Felder werden durch leere Zeichenfolgen ersetzt.

`{{LIBRECHAT_BODY_*}}` Platzhalter sind auf den Request begrenzt (request-scoped). LibreChat erstellt die MCP-Verbindung für den aktiven Lauf, verwendet sie für Tool-Aufrufe innerhalb dieses Laufs wieder und bereinigt sie, wenn der Request endet. Request-begrenzte Server sind vom persistenten Tool-Cache ausgeschlossen, sodass Request-spezifische Header und URLs nicht außerhalb des aktiven Laufs wiederverwendet werden. Der Agent Builder bindet den vollständigen Server über eine Auswahl an Runtime-Tools ein und löst dessen Tools auf, nachdem ein Lauf Body-Werte bereitgestellt hat. Der Abschluss von OAuth speichert die Autorisierung, stellt die Verbindung jedoch erst her, wenn dieser Request-Kontext existiert. `{{LIBRECHAT_USER_*}}`, `{{LIBRECHAT_OPENID_*}}` und `{{LIBRECHAT_GRAPH_*}}` Platzhalter machen den Server weiterhin benutzerbezogen (user-scoped), aber HTTP-Transporte aktualisieren die aufgelösten Header vor jedem Tool-Aufruf, ohne von sich aus eine erneute Verbindung zu erzwingen.

`{{LIBRECHAT_BODY_PARENTMESSAGEID}}` empfängt die Root-Turn-Elternnachricht in nativen Agent-Chats, OpenAI-kompatiblen Agents API-Anfragen und Legacy-Assistants-Runs. Open Responses-Anfragen haben kein kompatibles Elternnachrichten-Modell, daher schlägt ein Server, der diesen Platzhalter erfordert, bei dieser Schnittstelle fehl; `previous_response_id` wird nicht dafür eingesetzt.

OpenID-Zugriffs- und ID-Token laufen unabhängig voneinander ab. `{{LIBRECHAT_OPENID_ACCESS_TOKEN}}` und das veraltete `{{LIBRECHAT_OPENID_TOKEN}}` verwenden den gespeicherten Ablauf des Zugriffstokens, während `{{LIBRECHAT_OPENID_ID_TOKEN}}` ein aktuelles ID-Token erfordert. Wenn ein Berechtigungstoken nicht verfügbar oder abgelaufen ist, gibt LibreChat einen umsetzbaren `401`-Fehler zur erneuten Authentifizierung zurück, anstatt einen leeren oder wörtlichen Bearer-Wert zu senden; melden Sie sich erneut an, bevor Sie es erneut versuchen. Bei einer Anfrage ohne OpenID-Identität wird ein Header, der einen dieser nicht aufgelösten Berechtigungs-Platzhalter enthält, vollständig weggelassen. Platzhalter für Identitäts-Metadaten behalten ihr bestehendes Verhalten bei leeren Werten bei.

Vertrauenswürdige Betreiber können das Live-OpenID-Zugriffstoken des angemeldeten Benutzers direkt an einen in der YAML-Datei definierten Remote-MCP-Server weiterleiten:

```yaml
mcpServers:
  trusted-api:
    type: streamable-http
    url: https://mcp.example.com/mcp
    headers:
      Authorization: 'Bearer {{LIBRECHAT_OPENID_ACCESS_TOKEN}}'
```

Verwenden Sie die direkte Durchleitung (Direct Passthrough) nur dann, wenn dem MCP Server vertraut werden kann, das Upstream-Zugriffstoken des Benutzers zu empfangen. Explizites MCP OAuth, [on-behalf-of exchange](#obo) und die Authentifizierung über Administrator-API-Schlüssel haben Vorrang vor diesem Header. LibreChat löst das Live-Sitzungstoken vor dem Verbindungsaufbau auf und aktualisiert die Verbindung einmalig nach einem `401` oder `403` Fehler. Der abgelehnte Tool-Aufruf wird nicht automatisch wiederholt, da der Server ihn möglicherweise bereits ausgeführt hat; wiederholen Sie den Tool-Aufruf bewusst, nachdem die Wiederherstellung erfolgreich war. Wenn das Token nicht aktualisiert werden kann, muss sich der Benutzer erneut anmelden.

- **Beispiel:**
  ```yaml
  headers:
    X-User-ID: '{{LIBRECHAT_USER_ID}}'
    X-User-Email: '{{LIBRECHAT_USER_EMAIL}}'
    X-User-Role: '{{LIBRECHAT_USER_ROLE}}'
    X-API-Key: '${SOME_API_KEY}'
    Authorization: 'Bearer ${SOME_AUTH_TOKEN}'
  ```

#### `requestHeaders` [#requestheaders]

- **Typ:** Objekt (Optional, für `sse` und `streamable-http` Typen)
- **Beschreibung:** Header werden nur für eine aktive Chat-Anfrage aufgelöst. Sie verwenden dieselben Platzhalter wie `headers`, werden über `headers` zusammengeführt und haben Vorrang, wenn beide Objekte denselben Namen definieren.
- **Discovery-Verhalten:** Die Tool-Discovery lässt `requestHeaders` vollständig aus, sodass nur für Anfragen geltende Werte wie `{{LIBRECHAT_BODY_*}}` den Tool-Katalog des Servers nicht verbergen. Der aktive Lauf löst diese auf und sendet sie, sobald die Verbindung hergestellt ist.

```yaml
requestHeaders:
  X-Conversation-ID: '{{LIBRECHAT_BODY_CONVERSATIONID}}'
  X-Schedule-ID: '{{LIBRECHAT_BODY_SCHEDULEID}}'
```

#### `apiKey` [#apikey]

- **Typ:** Objekt (Optional, für `sse` und `streamable-http` Typen)
- **Beschreibung:** Konfiguration der API-Schlüssel-Authentifizierung für den MCP-Server. Bietet eine strukturierte Möglichkeit zur Konfiguration der API-Schlüssel-basierten Authentifizierung.
- **Untergeordnete Schlüssel:**
  - `source`: String (Erforderlich) - Gibt an, woher der API-Schlüssel stammt. Optionen:
    - `"admin"`: Der API-Schlüssel wird vom Administrator mit `key` konfiguriert
    - `"user"`: API-Schlüssel wird vom Benutzer über die UI bereitgestellt
  - `key`: String - (Für `source: "admin"`) Der API-Schlüssel-Wert, der von allen Benutzern geteilt wird. Unterstützt `${ENV_VAR}`-Referenzen. Bei `source: "admin"` wird kein Header gesendet, wenn `key` weggelassen wird.
  - `authorization_type`: String (erforderlich) - Legt fest, wie der API-Schlüssel in Anfragen übermittelt wird. Optionen:
    - `"bearer"`: Wird als `Authorization: Bearer <key>` gesendet
    - `"basic"`: Wird als `Authorization: Basic <key>` gesendet
    - `"custom"`: Wird in einem benutzerdefinierten Header gesendet (erfordert `custom_header`)
  - `custom_header`: String - (Wird verwendet, wenn `authorization_type` den Wert `"custom"` hat) Der Name des Headers, der für den API-Schlüssel verwendet wird. Standardmäßig wird `X-Api-Key` verwendet, wenn dieser Wert weggelassen wird.
- **Beispiel:**

  ```yaml
  # Admin-provided API key with Bearer auth
  my-server:
    type: streamable-http
    url: https://api.example.com/mcp
    apiKey:
      source: 'admin'
      key: '${MY_SERVER_API_KEY}'
      authorization_type: 'bearer'

  # User-provided API key with custom header
  another-server:
    type: sse
    url: https://api.example.com/sse
    apiKey:
      source: 'user'
      authorization_type: 'custom'
      custom_header: 'X-API-Key'
  ```

Für über die UI erstellte, geteilte Server, die `apiKey.source: user` verwenden, sind gespeicherte Schlüssel an das normalisierte Anforderungsziel gebunden. Das Ändern des URL-Pfads oder der Abfrage, des Proxys, des Transports, des Autorisierungsformats/-headers oder des konfigurierten OAuth-Clients/-Ziels erfordert, dass Benutzer neue Schlüssel eingeben; gleichwertige oder kosmetische Änderungen bleiben erhalten. Bestehende Legacy-Schlüssel funktionieren innerhalb ihrer unveränderten Begrenzung weiterhin. Nur aktuell deklarierte Anmeldeinformationsvariablen können ersetzt werden, einschließlich in `requestHeaders`; ein injizierter, alter generierter Name kann seinen Schlüssel nicht wiederverwenden. Schließen Sie das Upgrade auf **jeder API-Replik** ab, einschließlich der Konfigurations-Writer. Siehe [Credential Variables for UI-Created Servers](/docs/features/mcp#credential-variables-for-ui-created-servers) für den bestehenden Ablauf der Schlüsseleingabe.

#### `iconPath` [#iconpath]

- **Typ:** String (Optional)
- **Beschreibung:** Definiert das Anzeige-Icon des Tools, das im Tool-Auswahldialog angezeigt wird.

#### `chatMenu` [#chatmenu]

- **Typ:** Boolean (Optional)
- **Beschreibung:** Wenn auf `false` gesetzt, wird der MCP Server aus der regulären Chat-Auswahl und den vom Picker bereitgestellten Chat-Anfragen ausgeschlossen. Er bleibt für gespeicherte Agents und Model Specs verfügbar, die ihn explizit zuweisen.
- **Standardwert:** `true` (Der MCP Server kann im normalen Chat ausgewählt werden)

#### `serverInstructions` [#serverinstructions]

- **Typ:** Boolean oder String (Optional)
- **Beschreibung:** Steuert, wie MCP-Server-Anweisungen in den Agenten-Kontext eingefügt werden. Server-Anweisungen bieten eine allgemeine Nutzungsanleitung für den gesamten MCP-Server und ergänzen die Beschreibungen der einzelnen Tools.
- **Optionen:**
  - **`undefined`** (Standard): Es sind keine Anweisungen enthalten
  - **`true`**: Verwende die vom Server bereitgestellten Anweisungen (falls verfügbar) – ideal für gut dokumentierte Server mit umfassender Anleitung
  - **`false`**: Anweisungen explizit deaktivieren – nützlich, um Kontext-Token zu sparen oder wenn Tools selbsterklärend sind
  - **`string`**: Verwenden Sie benutzerdefinierte Anweisungen (überschreiben die vom Server bereitgestellten) – am besten geeignet für anwendungsspezifische Workflows oder wenn die Server-Anweisungen nicht ausreichen
- **Standardwert:** `undefined` (keine Anweisungen enthalten)
- **Hinweise:**
  - Anweisungen werden automatisch eingefügt, wenn `serverInstructions` konfiguriert ist und die Tools des Servers für den Agenten verfügbar sind.
  - Mehrere Server können jeweils Anweisungen zum Agent-Kontext beitragen
  - LibreChat speichert vom Server angekündigten Text separat von der konfigurierten Deklaration. Die Inspektion ersetzt weder `true` noch eine vom Operator verfasste Zeichenfolge, und Redis-gestützte Registrierungseinträge aus früheren Builds werden während der Initialisierung automatisch aktualisiert.
- **Beispiel:**

  ```yaml
  # Use server-provided instructions
  serverInstructions: true

  # Use custom instructions
  serverInstructions: |
    When using this filesystem server:
    1. Always use absolute paths for file operations
    2. Check file permissions before attempting write operations

  # Explicitly disable instructions
  serverInstructions: false
  ```

#### `env` [#env]

- **Typ:** Objekt (Optional, nur `stdio`-Typ)
- **Beschreibung:** Umgebungsvariablen, die beim Starten des Prozesses verwendet werden sollen.
- **Platzhalter-Unterstützung:**
  - `{{LIBRECHAT_USER_ID}}`: Wird durch die ID des aktuellen Benutzers ersetzt.
  - `{{LIBRECHAT_USER_*}}`: Dynamische Platzhalter für Benutzerfelder (z. B. `{{LIBRECHAT_USER_EMAIL}}`).
  - `{{CUSTOM_VARIABLE_NAME}}`: Wird durch den vom Benutzer bereitgestellten Wert für eine in `customUserVars` definierte Variable ersetzt (z. B. `{{MY_API_KEY}}`).
  - `${ENV_VAR}`: Wird durch den Wert der serverseitigen Umgebungsvariable `ENV_VAR` ersetzt.

#### `timeout` [#timeout]

- **Typ:** Ganzzahl (Optional)
- **Beschreibung:** Timeout in Millisekunden für Anfragen an MCP-Server. Muss eine nicht negative ganze Zahl sein. Bei `sse`-Verbindungen begrenzt derselbe Wert auch den initialen Verbindungsaufbau, der bis zu 120000 ms (2 Minuten) wartet, wenn `timeout` nicht gesetzt ist.
- **Standardwert:** `60000` (60 Sekunden)

#### `initTimeout` [#inittimeout]

- **Typ:** Ganzzahl (Optional)
- **Beschreibung:** Timeout in Millisekunden für die Initialisierung des MCP-Servers. Muss eine nicht-negative Ganzzahl sein.
- **Standardwert:** `30000` (30 Sekunden)

#### `sseReadTimeout` [#ssereadtimeout]

- **Typ:** Ganzzahl (optional, für die Typen `sse` und `streamable-http`)
- **Beschreibung:** Timeout in Millisekunden für den Body des langlebigen SSE-`GET`-Streams. Wenn innerhalb dieses Zeitfensters keine Daten eintreffen, wird der Stream abgebrochen. Muss eine positive ganze Zahl sein.
- **Standardwert:** `300000` (5 Minuten)

#### `requiresOAuth` [#requiresoauth]

- **Typ:** Boolean (Optional, nur für Remote-Transports: `sse`, `streamable-http`, `websocket`)
- **Beschreibung:** Ob dieser Server eine OAuth-Authentifizierung erfordert. Falls nicht angegeben, wird dies während des Serverstarts automatisch erkannt. Obwohl optional, ist es am besten, diesen Wert explizit festzulegen, wenn Sie wissen, ob der Server OAuth erfordert oder nicht.
- **Standardwert:** Automatisch erkannt, falls nicht angegeben
- **Hinweise:**
  - Gilt für Remote-Transports (URL-basiert): `sse`, `streamable-http` und `websocket`. Dies hat keine Auswirkungen auf `stdio`-Server, da diese keine URL zur Authentifizierung besitzen.
  - Die automatische Erkennung erfolgt während des Serverstarts, was die Initialisierungszeit verlängern kann.
  - Die explizite Konfiguration verbessert die Startleistung, da die Erkennung übersprungen wird.
  - Setzen Sie `requiresOAuth: false` für Server, die nur durch einen statischen `Authorization`-Header (z. B. einen Bearer-API-Schlüssel) geschützt sind. Die automatische Erkennung prüft den Server _ohne_ Ihre konfigurierten Header; daher kann ein Server, der mit `401` und einer `WWW-Authenticate: Bearer`-Challenge antwortet, fälschlicherweise als OAuth-geschützt eingestuft werden. Dieses Flag umgeht diese Prüfung und ermöglicht es Ihrem statischen Header, die Verbindung normal zu authentifizieren.
  - Funktioniert mit MCP OAuth Umgebungsvariablen (`MCP_OAUTH_ON_AUTH_ERROR`, `MCP_OAUTH_DETECTION_TIMEOUT`, `MCP_OAUTH_HANDLING_TIMEOUT`, `MCP_OAUTH_FLOW_TTL`) für ein verbessertes Verbindungsmanagement

#### OAuth-Aktualisierungskoordinierung [#oauth-refresh-coordination]

Für Deployments mit mehreren Replikas serialisiert `oauthRefreshCoordination: true` die Token-Aktualisierung über die gemeinsame Redis-Instanz. `oauthRefreshWaitTimeout` steuert, wie lange eine Replika auf das Ergebnis der Aktualisierung wartet, und `oauthPersistenceWaitTimeout` steuert, wie lange sie darauf wartet, dass aktualisierte Zugangsdaten lesbar werden; beide Werte sind standardmäßig auf `15000` Millisekunden gesetzt. `oauthRefreshWaitTimeout` ist auf maximal `30000` begrenzt, `oauthPersistenceWaitTimeout` akzeptiert höchstens `840000` (14 Minuten).

Aktivieren Sie die Koordination erst, nachdem jedes Replikat aktualisiert und mit derselben Redis-Bereitstellung verbunden wurde. Verwenden Sie identische Werte auf jedem Replikat, leeren Sie aktive Anfragen, bevor Sie die Einstellung ändern, und vermeiden Sie es, diese während eines Rolling Deployments umzuschalten.

#### `stderr` [#stderr]

- **Typ:** String oder Integer (Optional, nur `stdio`-Typ)
- **Beschreibung:** Wie mit `stderr` des Kindprozesses umgegangen werden soll. Dies entspricht der Semantik von Nodes [`child_process.spawn`](https://nodejs.org/api/child_process.html#child_processspawncommand-args-options). Gültige String-Werte: `"pipe"`, `"ignore"`, `"inherit"`. Alternativ kann eine nicht-negative Ganzzahl als Dateideskriptor verwendet werden.
- **Standardwert:** `"inherit"` (Nachrichten an `stderr` werden an das `stderr` des übergeordneten Prozesses ausgegeben).

#### `customUserVars` [#customuservars]

- **Typ:** Objekt (Optional)
- **Beschreibung:** Definiert benutzerdefinierte Variablen, die Benutzer für diesen MCP-Server festlegen können. Dies ermöglicht es Administratoren, Variablen (z. B. API-Schlüssel, URLs) anzugeben, die jeder Benutzer individuell konfigurieren muss. Diese vom Benutzer bereitgestellten Werte können dann in `headers` oder `env`-Konfigurationen verwendet werden. Server mit `customUserVars` werden automatisch von Verbindungen auf App-Ebene ausgeschlossen, wodurch sichergestellt wird, dass benutzerspezifische Anmeldeinformationen immer zur Laufzeit aufgelöst werden.
- **Struktur:**
  - Das `customUserVars`-Objekt enthält Schlüssel, wobei jeder Schlüssel einen Variablennamen darstellt (z. B. `MY_API_KEY`). Dieser Name wird in Platzhaltern wie `{{MY_API_KEY}}` verwendet.
  - Jeder Variablenname ist ein Objekt mit den folgenden Unterschlüsseln:
    - `title`: String (Erforderlich) - Ein benutzerfreundlicher Titel für die Variable, der in der Konfigurations-UI angezeigt wird.
    - `description`: String (Erforderlich) - Eine Beschreibung oder Anweisungen für die Variable, die auch in der Benutzeroberfläche angezeigt werden, um den Benutzer zu unterstützen. In diesem Feld kann HTML verwendet werden (z. B. um einen Link zu erstellen: `<a href="https://example.com" target="_blank">More info</a>`).
    - `sensitive`: Boolean (Optional) – Steuert, ob der Wert als Geheimnis behandelt und in der UI maskiert wird. Standardmäßig wird das maskierte/geheime Verhalten angewendet, wenn dies weggelassen wird; setzen Sie es auf `false` für nicht geheime Felder wie Projekt-IDs oder Basis-URLs.
- **Verwendung in `headers` und `env`:**
  - Sobald diese Variablen unter `customUserVars` definiert wurden, können sie in den Abschnitten `headers` (für die Typen `sse` und `streamable-http`) oder `env` (für den Typ `stdio`) unter Verwendung der Syntax `{{VARIABLE_NAME}}` referenziert werden.
  - Benutzer geben diese Werte über die UI ein. Auf diese Einstellungen kann auf zwei Arten zugegriffen werden:
    - **Von der Chat-Eingabe**: Im Abschnitt **MCP Servers** der [**+**-Palette des Composers](/docs/features/composer#turn-on-tools-skills-and-mcp-servers) verfügen konfigurierbare Server über ein **Configure**-Steuerelement in ihrer Zeile. Die Auswahl öffnet einen Dialog zur Verwaltung der Anmeldedaten für diesen Server. Die Auswahl eines Servers, für den noch Anmeldedaten benötigt werden, öffnet denselben Dialog.
      <img
        src="/images/mcp/mcp_per_user_vars_assistant_dialog.png"
        alt="Konfiguration der MCP-Variablen pro Benutzer – Dialog für Assistentenzugriff"
        width={800}
      />
    - **Über das Einstellungsmenü**: Ein dedizierter Bereich "MCP Settings" im rechten Bedienfeld listet alle MCP-Server mit definierbaren benutzerdefinierten Variablen auf. Benutzer können auf einen Server klicken, um den Konfigurationsdialog zu öffnen und ihre Anmeldedaten für diesen spezifischen MCP-Server festzulegen oder zu aktualisieren.
      <img
        src="/images/mcp/mcp_per_user_vars_side_panel.png"
        alt="Konfiguration von MCP-Variablen pro Benutzer – Zugriff über das Einstellungsmenü"
        width={300}
      />
  - Im UI erstellte Server lösen nur die Variablen auf, die sie in `customUserVars` deklarieren. `${ENV_VAR}`-Referenzen und `{{LIBRECHAT_USER_*}}`-Platzhalter werden nicht aufgelöst.
  - Diese vom Benutzer bereitgestellten Werte werden sicher gespeichert, dem jeweiligen Benutzer sowie dem spezifischen MCP Server zugeordnet und zur Laufzeit ersetzt.
- **Beispiel:**
  ```yaml
  customUserVars:
    MY_SERVICE_API_KEY:
      title: 'My Service API Key'
      description: "Your personal API access key for My Service. Find it at <a href='https://myservice.example.com/settings/api' target='_blank'>My Service API Settings</a>."
      sensitive: true
    SOME_OTHER_VAR:
      title: 'Some Other Variable'
      description: 'The specific value for some other configuration (e.g., a specific path or identifier).'
      sensitive: false
  ```
  Verwendung in `headers`:
  ```yaml
  headers:
    X-Auth-Token: '{{MY_SERVICE_API_KEY}}'
    X-Some-Other-Config: '{{SOME_OTHER_VAR}}'
  ```
  Verwendung in `env` (für den Typ `stdio`):
  ```yaml
  env:
    API_KEY: '{{MY_SERVICE_API_KEY}}'
  ```

#### `obo` [#obo]

- **Typ:** Objekt (Optional, nur für `sse` und `streamable-http` Typen)
- **Beschreibung:** Konfiguriert den OAuth 2.0 On-Behalf-Of-Token-Austausch für einen MCP Server. LibreChat tauscht das OpenID-Zugriffstoken des angemeldeten Benutzers gegen ein delegiertes Downstream-Token mit den konfigurierten Scopes aus und leitet dieses Token dann als `Authorization: Bearer ...`-Header an den MCP Server weiter.
- **Erforderliche Unter-Keys:**
  - `scopes`: String - Nicht leere Scopes, die für den nachgelagerten Token-Austausch angefordert werden.
- **Validierung:**
  - `obo` ist nur für `sse` und `streamable-http` MCP-Server gültig.
  - `obo` wird für `stdio`- und `websocket`-Server abgelehnt.
  - Benutzer benötigen die `MCP_SERVERS.CONFIGURE_OBO` Rollenberechtigung, um dieses Feld zu konfigurieren. Initialisieren Sie es mit [`interface.mcpServers.configureObo`](/docs/configuration/librechat_yaml/object_structure/interface#mcpservers) oder verwalten Sie es über das Admin-Panel.
- **Voraussetzungen:**
  - Die OpenID-Authentifizierung muss mit wiederverwendbaren Zugriffstokens konfiguriert werden.
  - Ihr Identitätsanbieter und die nachgelagerte Anwendung müssen den angeforderten delegierten Bereich (delegated scope) zulassen.
- **Beispiel:**
  ```yaml
  mcpServers:
    enterprise-tools:
      type: streamable-http
      url: https://api.example.com/mcp/
      obo:
        scopes: 'api://mcp-server-id/Mcp.Tools.ReadWrite'
  ```

Siehe [OpenID Connect Token Reuse](/docs/configuration/authentication/OAuth2-OIDC/token-reuse) und [SharePoint Integration](/docs/configuration/sharepoint) für Informationen zur Wiederverwendung von Token und zur Einrichtung delegierter Token.

#### `oauth` [#oauth]

- **Typ:** Objekt (Optional)
- **Beschreibung:** OAuth2-Konfiguration für die Authentifizierung mit dem MCP-Server. Wenn diese konfiguriert ist, werden Benutzer aufgefordert, sich über einen OAuth-Flow zu authentifizieren, bevor der MCP-Server verwendet werden kann. Wenn keine Client-ID und kein Client-Secret angegeben sind, wird die dynamische Client-Registrierung (DCR) verwendet.
- **Unterschlüssel:** Alle `oauth`-Unterschlüssel sind optional. Endpunkte können automatisch erkannt werden, und ein Client kann über die Dynamische Client-Registrierung bezogen werden.
  - `authorization_url`: String - Die OAuth-Autorisierungs-Endpoint-URL
  - `token_url`: String - Die URL des OAuth-Token-Endpunkts
  - `client_id`: String - OAuth-Client-Identifikator
  - `client_secret`: String - OAuth-Client-Secret. Erfordert `client_id`, und ein `client_id` mit einem `client_secret` erfordert außerdem sowohl `authorization_url` als auch `token_url`.
  - `redirect_uri`: String - [OAuth-Weiterleitungs-URI](/docs/features/mcp#oauth-callback-url). Standardmäßig `/api/mcp/{serverName}/oauth/callback`.
  - `scope`: String - OAuth-Scopes (durch Leerzeichen getrennt)
- **Zusätzliche Unterschlüssel:**
  - `grant_types_supported`: Array von Strings - Unterstützte Grant-Typen (Standardwert ist `["authorization_code", "refresh_token"]`)
  - `token_endpoint_auth_methods_supported`: Array of Strings – Unterstützte Authentifizierungsmethoden für den Token-Endpunkt (Standardwert ist `["client_secret_basic", "client_secret_post"]`)
  - `token_exchange_method`: String - Optionale Überschreibung für den Token-Austausch. Verwenden Sie `default_post`, um Client-Anmeldeinformationen im form-encoded POST-Body zu senden, oder `basic_auth_header`, um sie in einem HTTP Basic Authorization-Header zu senden. Wenn dieser Wert weggelassen wird, ermittelt LibreChat die vom Anbieter beworbenen Authentifizierungsmethoden für den Token-Endpunkt und verwendet standardmäßig Basic Auth, falls keine beworben werden.
  - `response_types_supported`: Array von Strings - Unterstützte Antworttypen (Standardwert ist `["code"]`)
  - `code_challenge_methods_supported`: Array of Strings - Unterstützte PKCE-Code-Challenge-Methoden (Standardwert ist `["S256", "plain"]`)
  - `skip_code_challenge_check`: Boolean - Überspringt die Überprüfung, ob der OAuth-Anbieter PKCE-Unterstützung ankündigt. Nützlich für Anbieter wie AWS Cognito, die S256 unterstützen, dies aber nicht in ihren Metadaten angeben. (Standardwert ist `false`)
  - `revocation_endpoint`: String - Token-Widerrufs-Endpunkt-URL. Wird automatisch ermittelt, wenn sie weggelassen wird.
  - `revocation_endpoint_auth_methods_supported`: Array von Strings - Authentifizierungsmethoden, die vom Widerrufsendpunkt unterstützt werden. Wird automatisch ermittelt, wenn dieser Wert weggelassen wird.
  - `audience`: String - Wird als `audience`-Parameter in der Autorisierungsanfrage gesendet, etwa für Anbieter wie Auth0, die API-bezogene Tokens nur ausstellen, wenn ein Audience angefordert wird. Nur für Administratoren: Wird für Server, die Benutzer in der Benutzeroberfläche erstellen, abgelehnt.
  - `forward_audience_on_refresh`: Boolean - Gibt an, ob `audience` auch beim `refresh_token`-Grant gesendet wird. Standardmäßig `true`, was Auth0 benötigt. Auf `false` setzen für Provider mit strengen Token-Endpunkten, wie AWS Cognito, die den zusätzlichen Parameter ablehnen. Wird ignoriert, wenn `audience` nicht gesetzt ist. Nur für Administratoren.
  - `send_resource_parameter`: Boolean - Gibt an, ob der RFC-8707-Parameter `resource` in der Autorisierungsanfrage, beim Austausch des Codes und beim Refresh-Grant gesendet wird. Standardmäßig `true`. Setzen Sie den Wert auf `false` für Anbieter, die diesen Parameter ablehnen, etwa Microsoft Entra ID v2.0, das mit `AADSTS9010010` fehlschlägt, wenn `resource` und `scope` gleichzeitig gesendet werden. Verwenden Sie stattdessen `scope` oder `audience`, um ein API-spezifisches Token zu erhalten. Nur für Administratoren.
- **Umgebungsvariablen:** In YAML definierten OAuth-URL-Felder, einschließlich `authorization_url`, `token_url`, `redirect_uri` und `revocation_endpoint`, können `${ENV_VAR}`-Referenzen verwenden. LibreChat löst den Umgebungswert vor der URL-Validierung auf. Vom Benutzer verwaltete OAuth-Endpunkt-URLs, die über die Benutzeroberfläche übermittelt werden, müssen literale URLs sein und lehnen `${ENV_VAR}`-Platzhalter ab.
- **Beispiel:**

  ```yaml
  oauth-api-server:
    authorization_url: https://api.example.com/oauth/authorize
    token_url: https://api.example.com/oauth/token
    client_id: your_client_id
    client_secret: your_client_secret
    redirect_uri: http://localhost:3080/api/mcp/oauth-api-server/oauth/callback
    scope: 'read execute'
    grant_types_supported: ['authorization_code', 'refresh_token']
    token_endpoint_auth_methods_supported: ['client_secret_post']
    token_exchange_method: default_post
    response_types_supported: ['code']
    code_challenge_methods_supported: ['S256', 'plain']
  ```

  Auth0-Beispiel:

  ```yaml
  auth0-server:
    type: streamable-http
    url: https://api.example.com/mcp/
    oauth:
      audience: https://api.example.com
      scope: 'read:data offline_access'
  ```

Wenn sowohl `token_exchange_method` als auch `token_endpoint_auth_methods_supported` für ein vorkonfiguriertes Client-Secret weggelassen werden, gewährt LibreChat bis zu fünf Sekunden für die Ermittlung der Metadaten des geschützten Ressourcen- und Autorisierungsservers. Es verwendet die angekündigten Funktionen nur dann, wenn der ermittelte Token-Endpunkt exakt mit der konfigurierten `token_url` übereinstimmt; die Ermittlung kann die konfigurierten Client-Anmeldeinformationen nicht an einen anderen Endpunkt umleiten. Setzen Sie `token_exchange_method` explizit, wenn ein Anbieter keine verwendbaren Metadaten veröffentlicht oder eine erzwungene Methode erforderlich ist.

HTTP-Anfragen für serverseitige OAuth-Discovery, Registrierung, Token und Widerruf folgen **keinen** Weiterleitungen, selbst wenn die ursprüngliche URL erlaubt ist. Konfigurieren Sie den endgültigen Endpunkt des Anbieters direkt, wenn dieser weiterleitet. Ziele mit privaten IP-Literalen sind blockiert, sofern sie nicht explizit durch die Richtlinie des Administrators für vertrauenswürdige Hosts oder exakte Adress-und-Port-Kombinationen zugelassen wurden. Diese Einschränkung gilt für serverseitige OAuth-HTTP-Anfragen; sie hindert den Browser des Benutzers nicht daran, die normale Weiterleitung zur Autorisierungsseite abzuschließen.

#### `oauth_headers` [#oauth_headers]

- **Typ:** Objekt (Optional)
- **Beschreibung:** Header, die speziell für OAuth-Flow-Anfragen verwendet werden. Diese Header werden während der OAuth-Authentifizierung, wie z. B. bei der dynamischen Client-Registrierung und dem Token-Austausch, verwendet und nicht während der regulären MCP-Server-Kommunikation gesendet.
- **Häufige Anwendungsfälle:**
  - Hinzufügen einer Authentifizierung zu dynamischen Client-Registrierungs-endpoints, wie z. B. `Authorization: Bearer ${DCR_API_KEY}`
  - Einschließlich benutzerdefinierter anbieterspezifischer Header, die für OAuth-Flows erforderlich sind
  - Festlegen der für OAuth-Token-Endpunkte erforderlichen Header
- **Platzhalterunterstützung:** Werte akzeptieren `{{LIBRECHAT_USER_*}}`-Platzhalter und `${ENV_VAR}`-Referenzen, ebenso wie die Zeichenkettenfelder unter `oauth`.
- **Hauptunterschiede zu `headers`:**
  - **`headers`**: Werden nach Abschluss der Authentifizierung mit regulären MCP-Serveranfragen gesendet
  - **`oauth_headers`**: Wird nur während OAuth-Authentifizierungsabläufen gesendet
- **Beispiel:**
  ```yaml
  oauth_headers:
    Authorization: "Bearer ${DCR_API_KEY}"
    X-Custom-Header: "custom_value"
  ```

#### `oauthPrompt` [#oauthprompt]

- **Typ:** String (Optional)
- **Beschreibung:** Steuert, wann ein Benutzer aufgefordert wird, sich bei einem OAuth-geschützten Server anzumelden.
  - `on_start`: Die Anmeldeaufforderung erscheint, wenn der Gesprächsschritt beginnt, bevor der Agent ausgeführt wird.
  - `on_use`: Der Durchlauf beginnt ohne Eingabeaufforderung, und der Agent findet die Tools des Servers über die Tool-Suche. Die Eingabeaufforderung erscheint, sobald der Agent zum ersten Mal eines der Tools des Servers aufruft, und der Durchlauf wartet, bis sich der Benutzer angemeldet hat.
- **Standardwert:** `on_start`
- **Hinweise:**
  - `on_use` gilt nur, wenn jedes Tool, das der Agent aus dem Server ausgewählt hat, [verzögert geladen](/docs/features/agents#deferred-tools) wird („Defer“ aktiviert). Wenn ein ausgewähltes Tool sofort geladen wird oder der Agent den gesamten Server statt einzelner Tools auswählt, bleibt die Eingabeaufforderung zu Beginn des Turns.
  - Die [Agent-Fähigkeit](/docs/configuration/librechat_yaml/object_structure/agents#capabilities) `deferred_tools` muss aktiviert sein. Wenn die Fähigkeit `run_in_background` aktiviert ist, bleibt bei einem ausgewählten Tool, das die Hintergrundausführung aktiviert, die Abfrage zu Beginn des Durchlaufs erhalten, da ein losgelöster Aufruf nicht auf eine Anmeldung warten kann.
  - `on_use` erfordert einen deklarierten [`oauthToolCatalog`](#oauthtoolcatalog). Ohne diesen behält der Server den Prompt zu Beginn des Durchlaufs bei, selbst für einen Benutzer, der sich bereits zuvor verbunden hat.
  - Die Tools, die vor der Anmeldung angeboten werden, müssen jedes ausgewählte Tool enthalten, andernfalls bleibt die Eingabeaufforderung am Beginn des Zugs stehen. Dies ist der deklarierte Katalog oder die eigene Tool-Liste des Benutzers, falls eine frühere Verbindung eine solche hinterlassen hat.
  - Nur vom Betreiber konfigurierte Server kommen dafür infrage: solche, die in `librechat.yaml` definiert oder über [Überschreibungen der Administrationskonfiguration](/docs/features/admin_panel#configuration-management) hinzugefügt wurden. Server, die Benutzer in der Benutzeroberfläche anlegen, behalten die Eingabeaufforderung zu Beginn eines Durchgangs bei. Die Eingabeaufforderung bleibt außerdem zu Beginn eines Durchgangs bestehen für einen Server, der in seinen Verbindungseinstellungen `obo`, `customUserVars`, `requestHeaders` oder benutzer- bzw. anfragebezogene Platzhalter (`{{LIBRECHAT_USER_*}}`, `{{LIBRECHAT_OPENID_*}}`, `{{LIBRECHAT_GRAPH_*}}`, `{{LIBRECHAT_BODY_*}}`) verwendet.
  - Gilt unabhängig davon, ob OAuth im Voraus konfiguriert ist (`oauth`, `requiresOAuth: true`) oder erst erkannt wird, wenn der Server die Verbindung ablehnt.
  - Auf Servern, die Benutzer in der Benutzeroberfläche erstellen, nicht verfügbar.
- **Beispiel:**
  ```yaml
  mcpServers:
    google-sheets:
      type: streamable-http
      url: https://sheets.example.com/mcp
      requiresOAuth: true
      oauthPrompt: on_use
      oauthToolCatalog:
        - name: read_sheet
          description: Read the values in a spreadsheet range
  ```

#### `oauthToolCatalog` [#oauthtoolcatalog]

- **Typ:** Array von Objekten (optional)
- **Beschreibung:** Die Tools, die ein `oauthPrompt: on_use`-Server der Tool-Suche anbietet, bevor sich ein Benutzer anmeldet. LibreChat kann die Tools eines geschützten Servers für einen Benutzer, der sich noch nicht angemeldet hat, nicht auflisten. Daher deklariert der Betreiber sie hier. Der Katalog ist für alle Benutzer gleich; die Verbindung eines Benutzers bestimmt nicht, welche Agenten anderer Benutzer sehen. Sobald sich ein Benutzer anmeldet, werden die eigenen Tool-Definitionen des Servers verwendet, und der Server validiert jeden Aufruf.
- **Eingabefelder:**
  - `name`: String (Erforderlich) - Der Name des Tools auf dem Server, so wie der Agent ihn auswählt.
  - `description`: String (optional) - Was das Tool macht, wird der Tool-Suche und dem Modell angezeigt.
  - `inputSchema`: Objekt (optional) – Die Parameter des Tools:
    - `type`: muss `object` sein
    - `properties`: Zuordnung von Parametername zu einem Eigenschaftsschema
    - `required`: Array der erforderlichen Parameternamen
- **Eigenschaftsschema:** eine begrenzte Teilmenge von JSON Schema mit ausschließlich diesen Schlüsseln:
  - `type`: einer von `string`, `number`, `integer`, `boolean`, `object`, `array`, `null` oder eine nicht leere Liste davon
  - `description`: String
  - `enum`: nicht leeres Array aus Strings, Zahlen, Booleans oder `null`
  - `default`: ein String, eine Zahl, ein Boolescher Wert oder `null`
  - `items`: bei Arrays ein Objekt mit `type`, `description` und `enum`
- **Hinweise:**
  - Die Validierung ist streng. Ein falsch geschriebener Eintragsschlüssel (etwa `input_schema`) oder ein Schlüsselwort außerhalb des begrenzten Schemas (etwa `minLength`, `pattern` oder `$ref`) führt zu einem Fehler bei der Konfigurationsvalidierung, anstatt ignoriert zu werden.
  - Ein Benutzer, dessen frühere Verbindung eine Werkzeugliste hinterlassen hat, erhält stattdessen diese Liste angeboten; in jedem Fall muss sie jedes Werkzeug enthalten, das der Agent vom Server ausgewählt hat, andernfalls bleibt die Eingabeaufforderung am Anfang des Durchlaufs stehen.
  - Auf Servern, die Benutzer in der Benutzeroberfläche erstellen, nicht verfügbar.
- **Beispiel:**
  ```yaml
  oauthToolCatalog:
    - name: read_sheet
      description: Read the values in a spreadsheet range
      inputSchema:
        type: object
        properties:
          range: { type: string }
        required: [range]
  ```

#### `startup` [#startup]

- **Typ:** Boolean (Optional)
- **Beschreibung:** Wenn dies auf `false` gesetzt ist, wird dieser MCP Server nicht beim Anwendungsstart verbunden. Dies ist nützlich für Server, die vor dem Verbinden eine Benutzereingabe oder Konfiguration erfordern, oder für Fälle, in denen Sie steuern möchten, wann der Server initialisiert wird.
- **Standardwert:** `true`
- **Beispiel:**
  ```yaml
  mcpServers:
    my-mcp-server:
      type: streamable-http
      url: 'https://api.example.com/mcp/'
      startup: false
  ```

### Hinweise [#notes]

- **Typinferenz:**
  - Wenn `type` weggelassen wird:
    - Wenn `url` angegeben ist und mit `http://` oder `https://` beginnt, ist der Standardwert für `type` `sse`.
    - Wenn `url` angegeben ist und mit `ws://` oder `wss://` beginnt, wird `type` standardmäßig auf `websocket` gesetzt.
    - Wenn `command` angegeben ist, ist der Standardwert für `type` `stdio`.
- **Verbindungstypen:**
  - **`stdio`**: Startet einen MCP-Server als untergeordneten Prozess und kommuniziert über die Standard-Ein-/Ausgabe.
  - **`websocket`**: Verbindet sich über WebSocket mit einem externen MCP Server.
  - **`sse`**: Verbindet sich über Server-Sent Events (SSE) mit einem externen MCP-Server.
  - **`streamable-http`**: Stellt eine Verbindung zu einem externen MCP-Server über HTTP her, mit Unterstützung für Streaming-Antworten.
- **Interne/Lokale Adressen:**
  - **Wichtig**: MCP-Server, die interne IP-Adressen (z. B. `172.24.1.165`, `192.168.1.100`) oder lokale Domains (z. B. `mcp-server`, `host.docker.internal`) verwenden, **müssen** explizit erlaubt werden. Verwenden Sie [`mcpSettings.allowedAddresses`](/docs/configuration/librechat_yaml/object_structure/mcp_settings#allowedaddresses) für spezifische private Host:Port-Dienste, wenn öffentliche Ziele weiterhin erreichbar bleiben sollen, oder [`mcpSettings.allowedDomains`](/docs/configuration/librechat_yaml/object_structure/mcp_settings#alloweddomains), wenn Sie eine strikte Whitelist wünschen.
  - Siehe [MCP Settings](/docs/configuration/librechat_yaml/object_structure/mcp_settings) für Konfigurationsdetails.

## Beispiele [#examples]

### Konfiguration mit internen Adressen [#configuration-with-internal-addresses]

Wenn Sie interne/lokale MCP-Server verwenden und keine strikte Domain-Whitelist erforderlich ist, konfigurieren Sie `mcpSettings.allowedAddresses` mit dem exakten Host und Port:

```yaml filename="Complete MCP Configuration with Internal Servers"
# MCP Settings - Required for internal/local addresses
mcpSettings:
  allowedAddresses:
    - '172.24.1.165:8000' # Internal IP and port
    - 'mcp-prod:8001' # Docker container and port
    - 'host.docker.internal:8080' # Docker host and port

# MCP Servers - Individual configurations
mcpServers:
  prod-mcp:
    type: streamable-http
    url: http://172.24.1.165:8000/mcp
    timeout: 120000

  test-mcp:
    type: streamable-http
    url: http://mcp-prod:8001/mcp
    timeout: 120000
```

**Importieren von MCP Server-Konfigurationen**

Die `mcpServers`-Konfigurationen ermöglichen es LibreChat, dynamisch mit verschiedenen MCP-Servern zu interagieren, die spezialisierte Aufgaben ausführen oder spezifische Funktionen innerhalb der Anwendung bereitstellen können. Dieser modulare Ansatz erleichtert die Erweiterung der Anwendungsfunktionen durch einfaches Hinzufügen oder Ändern von Serverkonfigurationen.

## Zusätzliche Informationen [#additional-information]

- **Standardverhalten:**
  - Die Initialisierung erfolgt beim Start, und die App muss neu gestartet werden, damit Änderungen wirksam werden.
  - Wenn sowohl `url` als auch `command` angegeben sind, muss der `type` explizit definiert werden, um Mehrdeutigkeiten zu vermeiden.
- **Multi-User-Unterstützung:**
  - Der MCPManager unterstützt jetzt separate Verbindungen auf Benutzer- und App-Ebene, was eine ordnungsgemäße Verbindungsverwaltung pro Benutzer ermöglicht.
  - Benutzerverbindungen werden separat nachverfolgt und verwaltet, mit ordnungsgemäßer Einrichtung und Bereinigung.
  - Verwenden Sie dynamische Platzhalter für Benutzerfelder in Headern, URLs und Umgebungsvariablen:
    - `{{LIBRECHAT_USER_ID}}` - Eindeutige Kennung des Benutzers
    - `{{LIBRECHAT_USER_EMAIL}}` - E-Mail-Adresse des Benutzers
    - `{{LIBRECHAT_USER_USERNAME}}` - Benutzername des Benutzers
    - `{{LIBRECHAT_USER_ROLE}}` - Rolle des Benutzers (z. B. "user", "admin")
    - Und viele weitere Felder (siehe Abschnitt „Headers“ für eine vollständige Liste)
- **Verwaltung der Benutzerinaktivität:**
  - Benutzerverbindungen werden auf Aktivität überwacht und nach 15 Minuten Inaktivität getrennt.
- **Umgebungsvariablen:**
  - **In `env` (für den Typ `stdio`):** Nützlich zum Einrichten spezifischer Laufzeitumgebungen oder Konfigurationen, die für den MCP Server-Prozess erforderlich sind.
  - **In `headers` (für `sse`- und `streamable-http`-Typen):** Verwenden Sie die `${ENV_VAR}`-Syntax, um auf Umgebungsvariablen in Header-Werten zu verweisen.
- **Dynamische Benutzerfelder:**
  - Benutzerfeld-Platzhalter werden zur Laufzeit durch die Informationen des authentifizierten Benutzers ersetzt.
  - Nur nicht sensible Felder sind verfügbar (Passwörter und andere sensible Daten sind ausgeschlossen)
  - Fehlende Felder werden standardmäßig als leere Strings behandelt
  - Boolesche Felder werden in String-Repräsentationen ("true" oder "false") konvertiert.
- **Fehlerbehandlung (`stderr`):**
  - Die Konfiguration von `stderr` ermöglicht es Ihnen zu verwalten, wie Fehlermeldungen des MCP Server-Prozesses behandelt werden. Die Standardeinstellung `"inherit"` bedeutet, dass die Fehler an den `stderr` des übergeordneten Prozesses ausgegeben werden.
- **Server-Anweisungen:**
  - Anweisungen werden automatisch in die Systemnachricht des Agenten eingefügt, wenn MCP Server-Tools verwendet werden.
  - Benutzerdefinierte Anweisungen (String-Werte) haben Vorrang vor den vom Server bereitgestellten Anweisungen
  - Mehrere MCP-Server können jeweils ihre eigenen Anweisungen zum Agent-Kontext beitragen
  - Anweisungen werden nur dann einbezogen, wenn die Tools des entsprechenden MCP-Servers tatsächlich für den Agenten verfügbar sind.
- **OAuth-Authentifizierung:**
  - Der OAuth2-Ablauf wird für die sichere Authentifizierung mit MCP-Servern unterstützt.
  - Benutzer werden aufgefordert, sich über OAuth zu authentifizieren, bevor der MCP Server verwendet werden kann.
