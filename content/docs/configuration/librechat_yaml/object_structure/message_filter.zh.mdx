## 概述 [#overview]

LibreChat 提供两种服务端过滤器配置：

- `filters` 将基于来源的策略应用于消息、提示词、智能体、文件、技能、记忆、工具以及其他可重用内容中的选定字段。
- `messageFilter` 是旧版消息文本过滤器。现有部署可以在迁移到 `filters.messages` 的同时继续使用它。

两者均为选择性加入。当两者均已配置时，两条策略同时适用。

<Callout type="warning" title="仅基础配置">
  `filters` 仅从基础 `librechat.yaml` 加载。数据库、角色、组和用户覆盖项无法添加、更改或删除它。在多副本部署中，请统一发布或重启所有副本，并在将策略视为生效之前，验证每个副本是否加载了相同的基础配置。
</Callout>

## 源感知过滤器 [#source-aware-filters]

每个源都有一个可选的 `pii` 策略。省略 `filters`、某个源或其 `pii` 块即可禁用该范围。

```yaml filename="librechat.yaml"
filters:
  messages:
    unattributedAssistantContent: model_output
    pii:
      action: audit
      fields: [text, summary, attachment_reference]
      starterPatterns: [sk_prefix, bearer_header, api_key_header]
      customPatterns:
        - id: organization_identifier
          label: Organization identifier
          regex: 'ORG-[A-Z0-9]{12}'
  files:
    pii:
      fields: [name, content, extracted_text, transcript]
      uninspectable: block
  skills:
    pii:
      fields: [name, description, instructions, imported_text, file_text]
```

### 模式配置 [#pattern-configuration]

对于每个已启用的源：

- 省略 `action` 或将其设置为 `block` 以拒绝匹配内容。设置 `action: audit` 可进行影子发布(shadow rollout),仅记录检测结果,而不拒绝、更改或编辑内容。设置 `action: redact` 可启用编辑功能(参见[编辑](#redaction))。
- 省略 `fields` 以检查该源支持的所有字段。显式列表必须包含 1 到 256 个受支持的字段名称。
- 省略 `starterPatterns` 以启用完整的入门目录。将其设置为 `[]` 可禁用入门模式，同时保留任何 `customPatterns`。
- 使用 `id`、面向用户的 `label` 和 `regex` 配置 `customPatterns`。可选地将 `category` 设置为 `email`、`phone`、`name`、`credential` 或 `custom` 之一。
- `maxCharacters`(1 到 262144,默认值 65536)用于限制每个转换会话中检查的文本总量,`maxMatches`(1 到 4096,默认值 256)用于限制每个会话中的匹配数量。两者均适用于 `redact`。

审计模式会评估所有已配置的片段和规则,使运维人员能够在强制执行之前衡量检测结果。每条 info 级别的审计记录都会标明动作、检测器、规则、标签、来源、字段和出处,但绝不包含匹配的文本或来源内容。在 `audit` 模式下,任何内容都不会被更改或脱敏。当配置加载时,`block`、`audit` 和 `redact` 之外的动作值都会被拒绝。

Actions 是针对每个源独立配置的，因此一个源可以执行审计（audit），而另一个源可以执行拦截（block）。即使某个源的模式动作为 `audit`，`filters.files.pii.uninspectable: block` 仍然作为针对不透明或超大所选文件内容的独立“故障关闭”（fail-closed）规则存在。

### 脱敏 [#redaction]

`action: redact` 会对新的、纯文本的交互式 Agent 聊天提交中的匹配内容进行转换,这类提交需携带 `clientRequestId`。编辑、续写、文件、引用、其他端点以及其他字段仍然使用阻断式检查。

脱敏需要有效的 `CREDS_KEY`。原始文本以加密且未建立索引的字段存储,该字段会随消息一同被删除或过期。因此请保留相同的 `CREDS_KEY`,以确保所有者能够恢复原始内容;更改该密钥将导致现有原始内容无法访问。消息文本仍为规范版本,并会在普通导出中被过滤。

```yaml filename="librechat.yaml"
filters:
  messages:
    pii:
      action: redact
      maxCharacters: 65536
      maxMatches: 256
      customPatterns:
        - id: organization_identifier
          label: Organization identifier
          regex: 'ORG-[A-Z0-9]{12}'
          category: custom
```

内置的 starter pattern ID 为：

- `sk_prefix`: `sk-` 风格的令牌前缀。
- `bearer_header`: 文本中的 bearer token。
- `api_key_header`: `api-key` 标头格式文本。

自定义模式使用 RE2JS 的有界线性时间正则表达式语法。不支持反向引用和环视（lookaround），且某些转义符与 JavaScript 正则表达式不同。LibreChat 在加载配置时会拒绝无效或不支持的模式。

### 消息来源 (Message Provenance) [#message-provenance]

`filters.messages.unattributedAssistantContent` 控制如何分类没有来源的旧版 assistant 内容：

- `model_output`（默认）：保留旧有行为，将未归属的助手内容视为模型输出。
- `inspect`：将原本未归属的助手内容（包括选定的附件投影）视为已提交内容。明确标记为模型输出的助手内容则保持豁免。

即使省略了 `filters.messages.pii`，此分类仍可能影响已启用的旧版 `messageFilter.pii` 策略。在依赖追溯性检查之前，请先盘点或迁移旧记录。

### 无法检查的文件 [#uninspectable-files]

`filters.files.pii.uninspectable` 控制 LibreChat 无法检查的所选文件内容，包括不透明或过大的内容：

- `allow`（默认）：保持兼容性并允许该内容。
- `block`：在提供商或存储端产生副作用之前拒绝它。

谨慎地推出 `block`。在存在可检查文本之前，它可能会导致旧文件无法重复使用。

### 存储与复用的内容 [#stored-and-reused-content]

启用或更改策略不会重写或删除已存储的记录。当受保护的内容被提交、复制、共享、重用或与模型绑定时，LibreChat 会应用当前策略。

安全的元数据编辑仍然可以成功，因此被拦截的记录仍然可以修复。在管理视图中，被拦截的 prompt 或预设字段可能为空，并显示 `contentFilterBlocked: true`；被拦截的 prompt 组在直接检索时会返回错误，并从集合和重用响应中被忽略。被拒绝的后台记忆更新可以被跳过，而主要的聊天响应则会继续进行。

阻止源感知文本匹配将返回 HTTP `400` 并附带 `content_filter_block`。无法检查的文件拒绝将使用 `content_filter_uninspectable`。

### 限制 [#limits]

- 每个源最多支持 256 个字段、起始模式或自定义模式。
- 在整个配置中最多支持 256 个自定义模式。
- Pattern ID 最长 256 个字符，标签最长 512 个字符，正则表达式最长 512 个字符。
- 最多 8,192 个正则表达式字符和 8,192 条已编译的过滤指令。

## 旧版 `messageFilter` [#legacy-messagefilter]

`messageFilter.pii` 会在进行内容审核、模型请求或持久化之前，根据 `message_filter_pii_block` 拒绝匹配的调用方提供的消息文本。它仅支持拦截功能，不接受 `action` 参数。它不会检查文件内容或 `filters` 所涵盖的其他可重用来源。

```yaml filename="librechat.yaml"
messageFilter:
  pii:
    starterPatterns:
      - sk_prefix
      - bearer_header
      - api_key_header
    customPatterns:
      - id: anthropic_api_key
        label: Anthropic API key
        regex: 'sk-ant-[A-Za-z0-9_-]{20,}'
```

旧版过滤器会检查 OpenAI 兼容的 Chat Completions 和 Responses 请求中所有角色的聊天路由用户文本及调用方提供的文本。它使用上述相同的内置 ID 和线性时间自定义正则表达式规则。
