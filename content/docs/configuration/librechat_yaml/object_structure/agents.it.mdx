## Esempio [#example]

```yaml filename="Agents Endpoint"

      create_file: 131072

    # (optional) Agent Capabilities available to all users. Omit the ones you wish to exclude. Defaults to list below.
    # Opt-in capabilities: "programmatic_tools", "stateful_code_sessions", "run_in_background", and "tool_intents".
    # capabilities: ["deferred_tools", "execute_code", "file_search", "web_search", "artifacts", "subagents", "actions", "context", "skills", "memory", "ask_user_question", "tools", "chain", "ocr"]
    # (optional) File citation configuration for file_search capability

      maxCatalogSkills: 20

        enabled: true
        maxPerUser: 5
      environments:
        - id: managed-default
          name: Managed Code API

          default: true
        - id: engineering-vm

          type: attached

          pairing:
            allowPrincipalWorkers: true
            tokenEnv: CODE_BRIDGE_ADMIN_TOKEN
    # eventDriven:
    #   selfUrl: https://librechat.internal
    backgroundTasks:
      completionWakeups: true
      ordinaryToolCancellation: false

      enabled: true

            tenantId: tenant-id
    remoteApi:
      auth:
        oidc:
          enabled: false
```

## maxProviderErrorChars

Controlla la quantità di testo di errore del provider che LibreChat conserva quando un errore dell'Agent non può essere classificato. Il valore predefinito è `2000` caratteri. Impostalo su `0` per omettere il testo del provider; il massimo è `1000000`.

```yaml filename="endpoints / agents / maxProviderErrorChars"
maxProviderErrorChars: 2000
```

## repositoryInstructions

Controlla l'individuazione delle istruzioni del repository per gli ambienti Code collegati. `timeoutMs` limita la richiesta di caricamento delle istruzioni da `100` a `30000` millisecondi e ha un valore predefinito di `2000`.

```yaml filename="endpoints / agents / repositoryInstructions"
repositoryInstructions:
  timeoutMs: 2000
```

## Interruttori di circuito per lo stream [#stream-circuit-breakers]

Queste impostazioni interrompono l'esecuzione di un Agent quando il flusso di un provider sembra produrre argomenti di strumenti fuori controllo o una sequenza illimitata di eventi delta.

<OptionTable
  options={[
    [
      'maxToolCallArgBytes',
      'Number',
      'Byte cumulativi massimi per gli argomenti di una chiamata a funzione in streaming. Impostare a 0 per disabilitare la protezione globale.',
      '65536',
    ],
    [
      'maxDeltaEventsPerTurn',
      'Number',
      'Numero massimo di eventi in streaming per un turno di generazione del modello. Impostare a 0 o omettere per disabilitare questa protezione.',
      '0 (disabled)',
    ],
    [
      'maxToolCallArgBytesByTool',
      'Object',
      'Override dei byte degli argomenti per strumento, indicizzati in base al nome dello strumento visualizzato dal modello. Un valore pari a 0 disabilita la protezione per quello strumento.',
      'create_file: 131072',
    ],
  ]}
/>

LibreChat utilizza un limite globale di argomenti di 64 KiB e fornisce un override di 128 KiB per `create_file`, i cui payload legittimi sono spesso più grandi. Le voci in `maxToolCallArgBytesByTool` si uniscono a tale override integrato. Se uno dei due controlli viene attivato, LibreChat interrompe lo stream del provider in corso e segnala quale limite è stato superato.

```yaml filename="endpoints / agents / stream circuit breakers"
maxToolCallArgBytes: 65536
maxDeltaEventsPerTurn: 100000
maxToolCallArgBytesByTool:
  create_file: 262144
  large_import: 524288
```

Per disabilitare ogni protezione sulla dimensione degli argomenti, imposta sia il limite globale che l'override `create_file` predefinito a `0`:

```yaml
maxToolCallArgBytes: 0
maxToolCallArgBytesByTool:
  create_file: 0
```

## titleTiming

<OptionTable
  options={[
    [

**Predefinito:** `"immediate"`

**Valori disponibili:**

- **`"immediate"`**: Genera il titolo non appena la richiesta ha inizio, in parallelo con la risposta del modello, utilizzando il primo messaggio dell'utente.

```yaml filename="endpoints / agents / titleTiming"
titleTiming: immediate
```

## activityLabel

Imposta `activityLabel: true` per raggruppare ogni blocco di ragionamento dell'Agent e le chiamate agli strumenti sotto un'intestazione generata su una riga. Utilizza `activityModel`, `activityEndpoint`, `activityPrompt`, `activityMaxPerRun` e `activityCharLimit` per controllare la chiamata al modello aggiuntiva e il relativo costo. Consulta [Agent Activity Groups](/docs/configuration/librechat_yaml/object_structure/shared_endpoint_settings#agent-activity-groups) per il riferimento completo dei campi e le regole di precedenza.

```yaml filename="endpoints / agents / activity groups"
activityLabel: true
activityEndpoint: openAI
activityModel: gpt-4.1-nano
activityMaxPerRun: 20
activityCharLimit: 600
activityPhaseLabel: true
activityPhaseMaxPerRun: 5
```

`activityPhaseLabel` può aggiungere in modo indipendente un riepilogo principale compresso attorno a ogni fase di esecuzione che contiene almeno due attività logiche. Utilizza `activityPhaseModel`, `activityPhaseEndpoint`, `activityPhasePrompt` e `activityPhaseMaxPerRun` per ottimizzare tali chiamate; `activityCharLimit` è condiviso con le etichette delle attività secondarie.

## capabilities

<OptionTable
  options={[
    [
      'capabilities',
      'Array/List of Strings',
      'Specifica le funzionalità dell\'agente disponibili per tutti gli utenti per l\'endpoint agents.',
      'Defines the agent capabilities that are available to all users for the agents endpoint. You can omit the capabilities you wish to exclude from the list.',
    ],
  ]}
/>

**Predefinito:** `["deferred_tools", "execute_code", "file_search", "web_search", "artifacts", "subagents", "actions", "context", "skills", "memory", "ask_user_question", "tools", "chain", "ocr"]`

`programmatic_tools`, `stateful_code_sessions`, `run_in_background` e `tool_intents` sono opzionali e devono essere aggiunti esplicitamente. I Programmatic tools e le sessioni stateful richiedono inoltre `execute_code` e un deployment di Code Interpreter compatibile. L'Agent Builder disabilita le selezioni MCP programmatiche in assenza di Code Interpreter e il server rimuove le opzioni del chiamante programmatico non aggiornate quando l'esecuzione del codice non è disponibile. `run_in_background` rende gli strumenti di Code Interpreter idonei per impostazione predefinita e consente l'attivazione per singolo strumento per gli strumenti MCP, Plugin e Action idonei; l'esecuzione del codice in background richiede anch'essa `execute_code` e Code Interpreter.

`stateful_code_sessions` è altamente sperimentale. Richiede una rotta separata per il Code Interpreter con profilo `stateful` configurata tramite [`LIBRECHAT_CODE_BASEURL_STATEFUL`](/docs/configuration/dotenv#stateful-code-interpreter-endpoint) o [`statefulCodeSessions.environments`](#statefulcodesessions). Le richieste stateful falliscono in modo chiuso (fail closed) invece di ripiegare sul normale servizio stateless. Nell'Agent Builder, ogni agente abilitato sceglie un ambito di workspace utente, agente-e-utente o conversazione e, quando sono configurati backend denominati, un ambiente di esecuzione. I nuovi agenti iniziano con l'ambito personale predefinito dell'utente e l'ambiente di esecuzione predefinito della distribuzione.

**Esempio:**

```yaml filename="endpoints / agents / capabilities"
capabilities:
  - 'deferred_tools'
  # Optional: enables Programmatic Tool Calling for MCP tools marked Programmatic in the Agent Builder.
  # Requires execute_code and a Code Interpreter deployment with the Tool Call Server component.
  # - 'programmatic_tools'
  - 'execute_code'
  - 'file_search'
  - 'web_search'
  - 'artifacts'
  - 'subagents'
  - 'actions'
  - 'context'
  - 'skills'
  - 'memory'
  - 'ask_user_question'
  - 'tools'
  - 'chain'
  - 'ocr'
  # Optional and highly experimental: reuse a user-, agent-and-user-, or
  # conversation-scoped workspace. Requires LIBRECHAT_CODE_BASEURL_STATEFUL
  # or a named statefulCodeSessions environment.
  # - 'stateful_code_sessions'
  # Optional: allow eligible Code Interpreter, MCP, Plugin, and Action tools to run as background tasks.
  # - 'run_in_background'
  # Optional: show live model-written intent labels for native and selected MCP tools.
  # - 'tool_intents'
```

**Nota:** Questo campo è facoltativo. Se omesso, il comportamento predefinito consiste nell'includere tutte le funzionalità elencate nel default.

## statefulCodeSessions

Configura gli ambiti di condivisione e i backend di esecuzione opzionali per workspace di Code Interpreter stateful altamente sperimentali.

<Callout type="warning" title="Altamente sperimentale">
  Stateful Code Sessions, named execution environments, attached workers e pairing sono in una fase di sperimentazione iniziale. Il loro comportamento, la configurazione, le caratteristiche di persistenza e il protocollo di integrazione potrebbero subire cambiamenti sostanziali.
</Callout>

<OptionTable

Gli ambienti collegati accettano `environments[].configSchema.limits.maxQueueWaitMs`, che controlla per quanto tempo una richiesta può riprovare ad attendere la capacità dell'area di lavoro. Il valore predefinito e massimo è `300000` millisecondi (5 minuti). Impostalo su `0` per disabilitare i tentativi del client dopo il tentativo iniziale di ammissione; ciò non annulla il lavoro già ammesso o in esecuzione. Questi campi appartengono a `configSchema.limits`, **non** a `userConfig.bash`.

`environments[].configSchema.limits.maxRequestTimeoutMs` limita facoltativamente il **tempo HTTP totale per una chiamata allo strumento dell'area di lavoro**, inclusi ammissione, esecuzione, regolamento e consegna. Accetta valori da `1` a `610000` ms, ma la configurazione rifiuta budget troppo piccoli per lasciare tempo di esecuzione dei comandi dopo l'ammissione e la riserva di 10 secondi per regolamento/consegna. Senza di esso, l'ammissione ha comunque un budget di 30 secondi per tentativo; `maxQueueWaitMs` rimane un orizzonte di riprova separato. **Non abilitare un'ammissione più lunga** finché ogni replica dell'API di LibreChat non riconosce questo campo, la rotta dell'API Code non rispetta le quote di coda per richiesta e non è stato misurato il timeout più breve lungo il percorso proxy/ingress attivo. Una mutazione scaduta potrebbe essere stata completata sul worker, quindi LibreChat non riprova un timeout ambiguo.

Con un budget totale di richiesta, `environments[].configSchema.limits.minCommandAdmissionMs` riserva del tempo affinché un comando entri nel worker prima che inizi l'esecuzione. Il valore predefinito è `10000` ms; impostare tra `1000` e `300000` ms. Il budget della richiesta deve **superare** questa tolleranza più 10000 ms di margine per l'assestamento/consegna; senza un budget totale, l'impostazione non ha alcun effetto. Il limite di esecuzione Bash pubblicizzato a un Agent è il minore tra il suo tetto configurato o quello a monte e il tempo rimanente dopo tali riserve. Ad esempio, un budget di richiesta di 90000 ms con un tetto di comando di 80000 ms e la riserva predefinita pubblicizza al massimo un comando di 70000 ms.

```yaml filename="endpoints / agents / statefulCodeSessions"
statefulCodeSessions:
  allowedEnvironments:
    - 'user'
    - 'agent-user'
    - 'conversation'
  principalWorkers:
    enabled: true
    maxPerUser: 5
  environments:
    - id: managed-default
      name: Managed Code API
      type: managed
      baseURL: https://code.example.com/v1
      default: true
    - id: engineering-vm
      name: Engineering VM
      type: attached
      baseURL: https://code-bridge.example.com/v1
      owner: deployment
      pairing:
        workerId: engineering-vm
        tokenEnv: CODE_BRIDGE_ADMIN_TOKEN
    - id: personal-workers
      name: Personal Code Workers
      type: attached
      baseURL: https://code-bridge.example.com/v1
      owner: deployment
      configSchema:
        limits:
          maxCommandTimeoutMs: 120000
          # Before enabling, verify Code API queue allowances and the live proxy deadline.
          # maxRequestTimeoutMs: 160000
          # minCommandAdmissionMs: 10000
          # maxQueueWaitMs: 300000
        # After upgrading Code API and opting in the worker with --linked-worktree-lanes:
        # workspaces:
        #   linkedWorktrees: true
        # Optional: require exact matching even on workers supporting tolerant edits.
        # edits:
        #   tolerantMatching: false
        permissions:
          fileWrite:
            allowed: [allow, ask, deny]
            default: ask
          commandExecution:
            allowed: [ask, deny]
            default: ask
      pairing:
        allowPrincipalWorkers: true
        tokenEnv: CODE_BRIDGE_ADMIN_TOKEN
```

`allowedEnvironments` è obbligatorio ogni volta che il blocco è presente e deve includere almeno uno scope di workspace. Ometti l'intero blocco per consentire tutti e tre gli scope e continuare a instradare il lavoro stateful tramite [`LIBRECHAT_CODE_BASEURL_STATEFUL`](/docs/configuration/dotenv#stateful-code-interpreter-endpoint). Il valore predefinito personale e l'Agent Builder consentono solo i valori permessi. Se un amministratore restringe la policy, un valore predefinito personale salvato rimane visibile ma disabilitato, e i nuovi Agent utilizzano il primo scope consentito. Gli Agent abilitati esistenti mantengono il loro scope salvato, ma uno scope ora non consentito fallisce in modo chiuso (fails closed) al runtime finché l'Agent non viene riconfigurato.

`conversationMoves.enabled: true` consente al proprietario della conversazione di spostare esplicitamente un workspace allegato sigillato in un ambiente compatibile e di recuperare un workspace mancante senza sostituire la cronologia della chat o ripristinare i vecchi file del workspace. Per consentire inoltre a una chat salvata di **allegare** un workspace o **lasciarne** uno per la chat normale, impostare `conversationMoves.allowAttachDetach: true`. Entrambi gli interruttori sono disattivati per impostazione predefinita; l'abilitazione dei soli spostamenti mantiene il comportamento di "solo spostamento". Aggiornare **tutte** le repliche API, quindi abilitare [`CODE_ENVIRONMENT_DECISION_VERSION=1`](/docs/configuration/dotenv#code-interpreter) prima di aderire. La proprietà, l'accesso alla destinazione, il lavoro attivo e la policy corrente vengono ricontrollati durante la transizione; una generazione in corso non può essere spostata.

```yaml filename="endpoints / agents / statefulCodeSessions / conversationMoves"
statefulCodeSessions:
  allowedEnvironments: ['user', 'agent-user', 'conversation']
  conversationMoves:
    enabled: true
    allowAttachDetach: true
```

`principalWorkers` controlla l'iscrizione self-service per i worker personali collegati. I valori omessi vengono risolti in `enabled: true` e `maxPerUser: 5`; impostare `enabled: false` o `maxPerUser: 0` per interrompere le nuove iscrizioni. Il limite conteggia ogni ambiente personale registrato per quell'utente attraverso i control plane configurati, inclusi i worker offline. L'abbassamento del limite o la disabilitazione dell'iscrizione non revocano gli ambienti esistenti.

Il file di configurazione Deployment YAML rappresenta il limite massimo invalicabile. Una sovrascrittura della configurazione a livello di ruolo, gruppo o utente può disabilitare l'iscrizione o ridurre il valore di `maxPerUser`, ma non può aumentare il valore definito nel deployment. Un utente visualizza i control plane con pairing abilitato solo quando il limite effettivo è maggiore di zero, [`pairing.allowPrincipalWorkers`](#statefulcodesessions) è abilitato su quel control plane, l'autenticazione principale è disponibile e l'utente dispone dell'autorizzazione di gestione dell'ambiente di codice (Code Environment).

Quando `environments` non è vuoto, ogni voce richiede un `id` univoco, un `name` visualizzato, un `type` di tipo `managed` o `attached` e un `baseURL` HTTP(S) senza stringa di query o frammento. Se l'elenco contiene ambienti eseguibili, esattamente una di queste voci deve impostare `default: true`. L'Agent Builder aggiunge quindi un selettore **Execution environment**; lasciandolo su **Deployment default** viene utilizzata quella voce predefinita. Un elenco contenente solo piani di controllo per il pairing self-service non necessita di un valore predefinito. Un agente che nomina un ambiente che viene successivamente rimosso o non è più accessibile fallisce in modo sicuro (fails closed) invece di ripiegare su un altro backend.

- `managed` punta direttamente a una Code API stateful gestita dall'operatore.
- `attached` punta a un backend `remote-bridge` dell'API Code compatibile che assegna il lavoro a un worker `@librechat/code` in uscita. Il worker non richiede una porta pubblica in entrata, ma il suo endpoint di esecuzione locale necessita comunque di un isolamento appropriato.
- `workerId` instrada facoltativamente un ambiente collegato a un worker in uscita. È solo lato server e non viene esposto tramite la configurazione di avvio del client.
- `owner` è impostato su `deployment` come valore predefinito. Gli ambienti di proprietà del principal vengono creati tramite l'API Code Environments autenticata di LibreChat, protetta da ACL, e uniti solo per le richieste autorizzate; non inserire URL forniti dal client nel file YAML di deployment.
- `pairing` è facoltativo e valido solo per le voci `attached` di proprietà del deployment. `pairing.workerId` identifica un worker gestito dall'operatore da registrare, mentre `pairing.allowPrincipalWorkers: true` consente agli utenti autorizzati di registrare worker vincolati al proprietario su quel control plane. Almeno uno di questi campi è richiesto quando `pairing` è presente.
- `pairing.tokenEnv` indica la variabile d'ambiente contenente il token dell'amministratore del bridge; non contiene mai il token stesso. Il pairing richiede HTTPS, eccetto per lo sviluppo in loopback.
- `configSchema.permissions` consente facoltativamente ai proprietari autorizzati di scegliere la policy `fileWrite` e `commandExecution` per gli ambienti personali in **Settings > Code environments**. Ogni campo richiede una lista `allowed` non vuota contenente `allow`, `ask` e/o `deny`; il valore `default` è `ask` quando omesso e deve essere presente in `allowed`. LibreChat rifiuta i valori memorizzati al di fuori della lista dell'amministratore.
- `configSchema.limits.maxCommandTimeoutMs` imposta il timeout Bash massimo che il modello può richiedere per quell'ambiente. Accetta valori da `1` a `300000` ms; l'omissione mantiene il valore predefinito di 30 secondi. Con un budget totale per la richiesta, il timeout del comando pubblicizzato si adatta anche al tempo rimanente dopo l'ammissione, la risoluzione e la consegna del comando. Si tratta di un limite massimo di distribuzione e non è configurabile dall'utente.
- `configSchema.workspaces.linkedWorktrees: true` abilita la pianificazione per-worktree solo per gli spazi di lavoro collegati che pubblicizzano `git_linked_worktree`; l'omissione mantiene tutte le richieste nella corsia principale (root lane) del checkout. Aggiorna LibreChat **prima** che un worker pubblicizzi questo ambito, distribuisci una Code API che supporti le corsie per i worktree collegati, quindi avvia il worker con `--linked-worktree-lanes` prima di abilitare l'impostazione YAML. Le operazioni sui file che puntano a un percorso all'interno di `.worktrees/<name>` e i comandi Bash con una `cwd` in quella posizione utilizzano quella corsia e restituiscono percorsi relativi al checkout. I comandi che eseguono `cd` all'interno del testo del comando, le operazioni sulla root del checkout, le istanze dello spazio di lavoro della conversazione e le azioni sull'ambiente rimangono limitati alla root.
- `configSchema.edits.tolerantMatching` consente il fallback con tolleranza agli spazi bianchi per impostazione predefinita sui worker collegati che pubblicizzano `tolerant_match`; impostalo su `false` per richiedere una corrispondenza esatta, incluse le anteprime di modifica protette. La corrispondenza deve rimanere univoca a meno che la modifica non imposti esplicitamente `replace_all`. I worker meno recenti non ricevono nuovi campi di corrispondenza; l'opzione `replace_all` collegata viene rifiutata prima dell'invio a meno che il worker non la pubblicizzi. Queste funzionalità richiedono Code API compatibili e build dei worker che implementino [Code Interpreter #271](https://github.com/LibreChat-AI/code-interpreter/pull/271).
- Non configurare `settings` nel file YAML di deployment. LibreChat fornisce quel campo, limitato alla richiesta, dalle preferenze dell'utente autenticato convalidate dal server.
- Solo la policy di scrittura dei file e di esecuzione dei comandi è configurabile dall'utente. L'isolamento, il networking, i mount, l'esecuzione privilegiata, l'ingresso, l'uscita e i segreti rimangono sotto il controllo dell'amministratore.
- Se sia `workerId` di primo livello che `pairing.workerId` sono presenti, devono corrispondere. Una voce con `allowPrincipalWorkers: true` e nessun ID worker è solo di accoppiamento (pairing-only): viene omessa dai selettori di esecuzione e non può impostare `default: true`.

L'esecuzione collegata abilita automaticamente una baseline di approvazione sicura: la scrittura di file e l'esecuzione di comandi o codice richiedono conferma, mentre le operazioni di sola lettura e ricerca continuano secondo la normale policy degli strumenti. La baseline è limitata all'Agente che utilizza l'ambiente collegato. Se non è disponibile alcuna impostazione utente, LibreChat utilizza `ask`; [`toolApproval.enabled: false`](#toolapproval) è l'override di emergenza dell'amministratore che disabilita questa baseline dell'ambiente collegato. I chiamanti senza supporto per l'approvazione e la ripresa falliscono in modalità chiusa (fail closed) a meno che non sia impostato tale override esplicito.

L'esecuzione allegata richiede una build sperimentale corrispondente di Code Interpreter remote-bridge. L'abbinamento autentica la connessione del worker in uscita; non sostituisce l'isolamento della sandbox o della VM. Gli utenti con autorizzazione di gestione dell'ambiente di codice effettuano l'abbinamento, configurano i criteri degli strumenti consentiti e revocano i worker personali in **Impostazioni > Ambienti di codice**. Vedi [Stateful Code Sessions](/docs/features/code_interpreter#stateful-code-sessions).

## eventDriven

Configura l'origine interna attendibile utilizzata per la consegna degli eventi di Agent. La maggior parte delle distribuzioni dovrebbe omettere questo blocco e utilizzare il listener associato al processo corrente.

<OptionTable

```yaml filename="endpoints / agents / eventDriven"
endpoints:
  agents:
    eventDriven:
      selfUrl: https://librechat.internal
```

Le continuazioni dei figli vincolate sono automatiche. I campi obsoleti `childTurns`, `completionWakeups`, `coalescing`, `actorMailbox`, `checkpointForks` e `durableReceipts` sotto `eventDriven` non sono più interruttori di configurazione e dovrebbero essere rimossi. Il runtime ora applica direttamente tali garanzie di consegna. Il campo separato [`backgroundTasks.completionWakeups`](#backgroundtasks) controlla la consegna conversazionale per gli strumenti in background completati e i Subagent scollegati.

Lasciare `selfUrl` non impostato per il normale percorso del bound-listener. Impostarlo solo quando l'ammissione di trigger interni attendibili deve attraversare un'altra origine HTTP(S), come un front door TLS. `AGENT_TRIGGERS_SELF_URL` rimane un fallback di compatibilità quando questo campo viene omesso. Consultare [Eventi API degli Agent](/docs/features/agents_api#agent-events) e [Continuazione automatica del genitore](/docs/features/subagents#automatic-parent-continuation).

`eventDriven.idlePolling` limita il polling di ripristino per replica quando nulla è pronto: `deliveryMaxIntervalMs` ha un valore predefinito di `15000` (valido `1000`–`300000`), `queuedTurnMaxIntervalMs` e `maintenanceMaxIntervalMs` hanno ciascuno un valore predefinito di `120000` (valido `30000`–`300000`), e `completionWaitMaxIntervalMs` ha un valore predefinito di `60000` (valido `5000`–`300000`). Quest'ultimo limita i riesami mentre un risultato in background o di un Subagent è in sospeso o il suo turno genitore è occupato. Gli eventi di prontezza accelerano la consegna; questi limiti mantengono i fallback tra repliche e di ripristino da crash piuttosto che definire la normale latenza di completamento.

```yaml filename="endpoints / agents / eventDriven / idlePolling"
eventDriven:
  idlePolling:
    deliveryMaxIntervalMs: 15000
    queuedTurnMaxIntervalMs: 120000
    maintenanceMaxIntervalMs: 120000
    completionWaitMaxIntervalMs: 60000
```

Il completamento dell'azione Event Actor detached viene selezionato automaticamente dall'archivio di generazione integrato. L'esecuzione in-memory è locale al processo; i flussi di generazione Redis aggiungono un ripristino durevole al riavvio e il passaggio tra repliche. Non è richiesto alcuno switch in `librechat.yaml` o flag di funzionalità nelle variabili d'ambiente. Vedi [Agent Event Runtime](/docs/configuration/dotenv#agent-event-runtime).

## toolApproval

Controlla la revisione umana per le chiamate agli strumenti dell'Agente. La policy a livello di distribuzione è disabilitata quando questo blocco viene omesso. Un Agente che utilizza un ambiente Code collegato costituisce un'eccezione: LibreChat abilita la sua policy di sicurezza "ask-by-default" con ambito limitato, a meno che l'amministratore non imposti esplicitamente `enabled: false`. Quando la revisione è applicata, le chiamate corrispondenti rimangono in pausa finché l'utente non invia una decisione consentita, come l'approvazione, il rifiuto o la modifica degli argomenti.

<OptionTable
  options={[
    [
      'enabled',
      'Boolean',

      'default',
    ],
    ['allow', 'Array of strings', 'Pattern glob per chiamate che possono essere eseguite senza richiesta.', ''],
    ['deny', 'Array of strings', 'Pattern glob per le chiamate che vengono sempre negate. Le regole di negazione hanno la priorità.', ''],
    ['ask', 'Array of strings', 'Pattern glob per le chiamate che richiedono sempre una revisione.', ''],
    [
      'reason',
      'String',
      'Spiegazione facoltativa mostrata nel prompt di approvazione. Usa `{tool}` per inserire il nome dello strumento.',

I pattern utilizzano il glob matching. Gli strumenti MCP possono essere limitati con `mcp:<server>:<tool>`; ad esempio, `mcp:github:*` corrisponde a ogni strumento del server `github`. LibreChat applica regole statiche e matcher di hook ai nomi di runtime MCP e agli alias rivolti al modello, inclusi gli strumenti raggiungibili tramite Subagent nidificati. Le regole statiche vengono valutate nell'ordine `deny`, `ask`, quindi `allow` prima che la modalità selezionata fornisca il fallback. Una regola di negazione (deny) ha quindi sempre la precedenza, inclusa la modalità `bypass`.

```yaml filename="endpoints / agents / toolApproval"
toolApproval:
  enabled: true
  mode: default
  allow:
    - 'mcp:analytics:read_*'
  deny:
    - 'mcp:*:delete_*'
  ask:
    - 'mcp:*:*'
  reason: 'Review {tool} before it runs.'
```

Gli Hooks vengono caricati una volta all'avvio del server ed eseguiti nel processo di LibreChat. Ogni voce accetta un `module`, un `matcher` regex opzionale per il nome dello strumento e un oggetto `options` opzionale passato al builder del modulo. Carica solo codice di cui ti fidi. Gli override per ruolo o tenant non ricaricano i moduli degli hook; implementa il comportamento contestuale all'interno dell'hook.

```yaml filename="endpoints / agents / toolApproval / hooks"
toolApproval:
  enabled: true
  hooks:
    - module: '@acme/librechat-approval-hook'
      matcher: '^mcp:production:'
      options:
        requireTicket: true
```

## fileSharing

`fileSharing` è una funzionalità di condivisione opt-in, limitata all'esecuzione, per il lavoro delegato degli Agent. Imposta `enabled: true` qui e abilita `subagents.shareFiles` su ogni Agent delegante. Gli input sono di sola lettura per i destinatari; gli output rimangono privati a meno che non vengano esplicitamente pubblicati, e i file pubblicati rimangono scaricabili dopo l'esecuzione.

```yaml filename="endpoints / agents / fileSharing"
endpoints:
  agents:
    fileSharing:
      enabled: true
      allowSiblingSharing: false
      maxFiles: 100
      maxPrivateBytes: 268435456
      ttlMs: 3600000
```

`allowSiblingSharing` consente destinatari sibling o discendenti esplicitamente nominati. `maxFiles` varia da `1` a `1000`; `maxPrivateBytes` limita gli snapshot di output privati conservati; e `ttlMs` è la durata attiva del manifest, limitata a 24 ore. Omettere questo blocco lascia la condivisione disabilitata.

## Funzionalità degli Agent [#agent-capabilities]

Il campo `capabilities` ti consente di abilitare o disabilitare funzionalità specifiche per gli agenti. Le funzionalità disponibili sono:

- **deferred_tools**: consente agli agenti di scoprire gli strumenti MCP differiti in fase di esecuzione invece di caricare ogni strumento nel contesto in anticipo.
- **programmatic_tools**: Abilita la chiamata a strumenti programmatici (Programmatic Tool Calling) per gli strumenti MCP contrassegnati come Programmatic nel generatore di agenti (Agent Builder). Richiede `execute_code` e un deployment di Code Interpreter con il componente Tool Call Server. Questa funzionalità è facoltativa e non è abilitata per impostazione predefinita.
- **execute_code**: Consente all'agente di eseguire codice.
- **stateful_code_sessions**: Consente agli agenti che hanno aderito di riutilizzare un workspace di Code Interpreter nell'ambito di un utente, di un agente e utente, o di una conversazione. Richiede `execute_code`, una distribuzione di Code Interpreter compatibile e l'impostazione avanzata specifica per l'agente. I nuovi agenti utilizzano l'ambito preferito dell'utente che ha effettuato l'accesso. Questa funzionalità è altamente sperimentale, non è abilitata per impostazione predefinita e potrebbe subire modifiche sostanziali durante la fase di sperimentazione; non considerare il suo comportamento o la sua configurazione attuale come un contratto di produzione stabile.
- **file_search**: Abilita l'agente a cercare e interagire con i file. Quando abilitato, il comportamento delle citazioni è controllato dalle impostazioni `maxCitations`, `maxCitationsPerFile` e `minRelevanceScore`.
- **web_search**: Abilita la funzionalità di ricerca web per gli agenti, consentendo loro di cercare e recuperare informazioni da internet.
- **artifacts**: Abilita l'agente a generare artefatti interattivi (componenti React, HTML, diagrammi Mermaid).
- **subagents**: Abilita l'esecuzione di agenti secondari in contesti isolati. Vedi [Subagents](/docs/features/subagents).
- **actions**: Consente all'agente di eseguire azioni predefinite.
- **context**: Abilita la funzionalità "Carica come testo" nella chat e il "Contesto file" per gli agenti, consentendo agli utenti di caricare file e far sì che il loro contenuto venga estratto e incluso direttamente nella conversazione.
- **skills**: Abilita le Skills nel pannello laterale, l'invocazione manuale tramite `$`, le skills invocate dal modello e le allowlist delle skills per gli agenti. Vedi [Skills](/docs/features/skills).
- **memory**: Consente agli agenti di utilizzare `set_memory` e `delete_memory` quando la memoria è configurata e l'utente ha l'accesso. Abilitato per impostazione predefinita; rimosso in fase di esecuzione quando la memoria è disabilitata.
- **ask_user_question**: Consente agli agenti di mettere in pausa per porre da una a quattro domande correlate in un unico modulo e riprendere con le risposte. Abilitato per impostazione predefinita.
- **tools**: Concede all'agente l'accesso a vari strumenti.
- **chain**: Abilita la funzionalità Beta per il concatenamento degli agenti, nota anche come flussi di lavoro Mixture-of-Agents (MoA).
- **ocr**: Migliora facoltativamente "Carica come testo" nella chat e il "Contesto file" per gli agenti, consentendo ai file di essere caricati ed elaborati tramite OCR. **Richiede la configurazione di un servizio OCR.**
- **run_in_background**: Rende l'esecuzione di Code Interpreter e gli strumenti shell idonei per l'esecuzione in background per impostazione predefinita e abilita l'opt-in in background per singolo strumento per MCP, Plugin e Action idonei. Un interruttore a livello di Action abilita ogni operazione idonea; le Action OAuth e le operazioni che definiscono già un parametro `run_in_background` sono escluse. Un agente può esplicitamente escludere Code Interpreter. L'impostazione consente l'esecuzione in background; il modello decide per ogni chiamata se utilizzarla. Richiede `execute_code` e una distribuzione di Code Interpreter configurata per il codice. Questa funzionalità non è abilitata per impostazione predefinita.
- **tool_intents**: Aggiunge etichette di intento scritte dal modello in tempo reale alle chiamate agli strumenti idonei. Gli strumenti nativi, inclusi gli strumenti Code Interpreter, si attivano automaticamente; gli strumenti MCP possono essere abilitati singolarmente o in blocco nell'Agent Builder. Le Model Specs utilizzano `describeIntent`. Questa funzionalità non è abilitata per impostazione predefinita.

Specificando le funzionalità, puoi controllare le caratteristiche disponibili agli utenti quando interagiscono con gli agenti.

## Esempio di configurazione [#example-configuration]

Ecco un esempio di configurazione dell'endpoint `agents` con funzionalità personalizzate e impostazioni di citazione dei file:

```yaml filename="Agents Endpoint"
endpoints:
  agents:
    disableBuilder: false
    # File citation configuration
    maxCitations: 20
    maxCitationsPerFile: 5
    minRelevanceScore: 0.6
    # Custom capabilities
    capabilities:
      # Optional: enables Programmatic Tool Calling for MCP tools marked Programmatic in the Agent Builder.
      # - 'programmatic_tools'
      - 'execute_code'
      # Optional: makes Code Interpreter background-eligible and enables selected MCP, Plugin, and Action tools.
      # - 'run_in_background'
      # Optional: enables live intent labels for native and selected MCP tools.
      # - 'tool_intents'
      - 'file_search'
      - 'skills'
      - 'subagents'
      - 'actions'
      - 'artifacts'
      - 'context'
      - 'ocr'
      - 'web_search'
```

In questo esempio:

- L'interfaccia del builder è abilitata
- Le citazioni dei file sono limitate a un totale di 20, con un massimo di 5 per file
- Vengono incluse solo le fonti con una rilevanza pari o superiore al 60%
- Gli agenti LibreChat hanno accesso all'esecuzione di codice, alla ricerca di file (con citazioni), a Skills, Subagents, azioni, artefatti, contesto dei file, servizi OCR se configurati e funzionalità di ricerca web.
- Il Programmatic Tool Calling rimane disabilitato a meno che non si aggiunga la capability `programmatic_tools` insieme a `execute_code`
- Le chiamate agli strumenti in background rimangono disabilitate a meno che non si aggiunga `run_in_background`; gli strumenti Code Interpreter diventano quindi idonei per impostazione predefinita, mentre gli strumenti MCP, Plugin e Action idonei richiedono ancora la selezione.
- Le etichette di intent degli strumenti rimangono disabilitate a meno che non si aggiunga `tool_intents`; gli strumenti nativi vengono quindi abilitati automaticamente, mentre gli strumenti MCP richiedono ancora una selezione per singolo strumento.

## managementApi

L'API di gestione degli Agent in beta consente ai client macchina attendibili di creare, elencare, leggere, aggiornare ed eliminare Agent, gestirne i file e scoprire o modificare le Skill accessibili. È separata da [`remoteApi`](#remoteapi): le rotte di gestione accettano solo identità macchina OIDC legate al deployment e non accettano chiavi API di LibreChat Remote Agents o sessioni del browser.

```yaml filename="endpoints / agents / managementApi"
endpoints:
  agents:
    managementApi:
      auth:
        oidc:
          enabled: true
          issuer: https://identity.example.com/
          audience: https://librechat.example.com/agents
          # jwksUri: https://identity.example.com/.well-known/jwks.json
        clients:
          - clientId: machine-client-id
            # subject: provider-specific-service-principal-subject
            userId: 507f1f77bcf86cd799439011
            tenantId: tenant-id
            enabled: true
```

## Note [#notes]

- Non è consigliato disabilitare l'interfaccia del builder a meno che non si stiano utilizzando i [modelSpecs](/docs/configuration/librechat_yaml/object_structure/model_specs) per definire un elenco di agenti tra cui scegliere.
- La configurazione delle citazioni dei file (`maxCitations`, `maxCitationsPerFile`, `minRelevanceScore`) si applica solo quando la funzionalità `file_search` è abilitata.
- Il punteggio di rilevanza viene calcolato utilizzando la similarità vettoriale, dove 1.0 rappresenta una corrispondenza perfetta e 0.0 rappresenta nessuna similarità.
- I limiti di citazione aiutano a bilanciare il recupero completo delle informazioni con la qualità e le prestazioni della risposta.
- La funzionalità `context` funziona senza configurazione OCR utilizzando metodi di analisi del testo. L'OCR migliora la qualità dell'estrazione quando configurato.
- La funzionalità `ocr` richiede che sia configurato un servizio OCR (vedi [Configurazione OCR](/docs/configuration/librechat_yaml/object_structure/ocr)).
- `maxSubagents` limita il numero di subagenti a cui un singolo agente può fare riferimento. Non modifica la profondità o i limiti del grafo documentati in [Subagents](/docs/features/subagents#limits).
