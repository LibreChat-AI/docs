이 페이지는 [대화 풀 리퀘스트](/docs/features/pull_requests)의 관리자 측면을 다룹니다. 모든 키는 `librechat.yaml`의 `endpoints.agents.pullRequests` 아래에 있습니다. [`pullRequests` 레퍼런스](/docs/configuration/librechat_yaml/object_structure/agents#pullrequests)에는 각 키의 범위와 기본값이 나열되어 있으며, 환경 변수는 [dotenv](/docs/configuration/dotenv#conversation-pull-requests)에 있습니다.

## 요구 사항 [#requirements]

채팅에 풀 리퀘스트가 표시되려면 다음 조건이 모두 충족되어야 합니다:

1. LibreChat에는 서버 토큰과 저장소 범위(`allowedRepositories` 또는 `allowAllRepositories`)가 있으며, 사용자는 `oauth`를 통해 자신의 계정을 연결할 수도 있습니다.
2. 채팅은 일반 채팅이 아니라, 첨부된 코드 워크스페이스에서 코드를 실행합니다.
3. 워크스페이스는 자신의 git 브랜치를 보고합니다. 이를 위해서는 `LibreChat-AI/code-interpreter` #311 이상으로 빌드된 워커가 필요하며, `CODEAPI_BRIDGE_LANE_GIT=true`는 LibreChat이 아닌 Code API에 설정해야 합니다. [Code Interpreter](/docs/features/code_interpreter)를 참고하세요.

별도로 켜는 스위치는 없습니다. 토큰과 스코프, 또는 동작하는 `oauth` 앱이 없으면 이 기능은 비활성 상태로 남아 있으며, 클라이언트에 아무것도 광고되지 않고 모든 채팅에 풀 리퀘스트가 표시되지 않지만 오류도 나지 않습니다. `enabled: false`를 설정하면 다른 설정과 관계없이 기능이 꺼집니다.

## 제공자 및 호스트 [#provider-and-host]

`provider`는 pull request가 저장되는 위치를 선택합니다. 하나의 배포(deployment)에서는 하나의 provider만 사용합니다.

| `provider` | 서비스 | 기본 `host` |
| ------------------ | ----------------------------------------------------------------------------------------------- | --------------- |
| `github` (기본값) | GitHub.com, GitHub Enterprise Server, 또는 GitHub Enterprise Cloud 데이터 상주 테넌트(`*.ghe.com`) | `github.com` |
| `gitlab` | gitlab.com 또는 자체 관리형 GitLab의 병합 요청 | `gitlab.com` |
| `bitbucket` | Bitbucket Cloud 전용 | `bitbucket.org` |

GitHub Enterprise Server, `*.ghe.com` 테넌트 또는 자체 관리형 GitLab의 경우에만 `host`를 설정하세요:

- 이것은 호스트 이름이며 URL이 아닙니다. 스킴이나 경로를 포함하지 않습니다(예: `github.example.com`).
- 1부터 65535까지의 포트를 사용할 수 있으며, 예를 들어 `git.example.com:8443`과 같이 지정할 수 있습니다. `:443`은 제외됩니다.
- GitHub에서 LibreChat은 `github.com`의 경우 `api.github.com`을, `*.ghe.com` 테넌트의 경우 `api.<host>`를, Enterprise Server의 경우 `https://<host>/api/v3`를 호출합니다. GitLab에서는 `https://<host>/api/v4` 및 `https://<host>/api/graphql`을 호출합니다.
- Bitbucket은 다른 호스트를 허용하지 않습니다. `bitbucket.org` 이외의 `host`가 설정되면 토큰을 다른 곳으로 전송하지 않도록 해당 기능이 비활성화됩니다.

```yaml filename="librechat.yaml"
endpoints:
  agents:
    pullRequests:
      provider: 'gitlab'
      host: 'gitlab.example.com'
      allowedRepositories:
        - 'platform/backend/api'
        - 'platform/frontend/*'
```

`provider`, `host`, `oauth` 및 `sharedCacheSlots`는 `librechat.yaml`에서만 읽습니다. 역할, 그룹, 사용자, 테넌트 단위의 이 키에 대한 재정의는 무시되므로, 재정의를 통해 토큰을 다른 서비스로 전송하거나 사용자에게 부여되는 앱 접근 권한을 바꿀 수 없습니다. `token`, `allowedRepositories` 같은 다른 키는 주체(principal)별로 다를 수 있습니다.

## 서버 토큰 [#the-server-token]

서버 토큰은 자체 계정을 연결하지 않은 모든 사용자에게 사용됩니다. 읽기 전용으로 설정하고, 공개해도 괜찮은 저장소로만 범위를 제한하세요.

- GitHub: 읽기 전용 Pull requests, Checks, Contents 권한이 있는 세분화된 토큰입니다. Checks 권한이 없으면 일치하는 모든 pull request를 불러올 수 없습니다. Contents 권한이 없으면, 마지막 명령 이후 브랜치가 변경된 채팅을 불러올 수 없습니다. LibreChat이 일치 여부를 확인하기 위해 커밋을 비교하기 때문입니다.
- GitLab: `read_api` 범위를 가진 개인, 그룹 또는 프로젝트 액세스 토큰.
- Bitbucket Cloud: 저장소, 프로젝트 또는 워크스페이스 액세스 토큰으로, 베어러 토큰(bearer token)으로 전송되며, 풀 리퀘스트와 저장소에 대한 읽기 권한을 가집니다.

LibreChat는 다음 순서로 토큰을 찾습니다:

1. `token: '${MY_VAR}'` in `librechat.yaml`은 환경 변수를 참조하는 방식입니다. 스키마는 리터럴 토큰 값을 허용하지 않습니다.
2. `token`이 설정되지 않은 경우, 제공자의 대체 변수 중 설정되어 있는 첫 번째 변수를 사용합니다:

| 제공자 | 대체 변수 (우선순위 순) |
| --------- | ------------------------------------------------------- |
| GitHub | `GITHUB_PULL_REQUEST_TOKEN`, `GITHUB_TOKEN`, `GH_TOKEN` |
| GitLab | `GITLAB_PULL_REQUEST_TOKEN`, `GITLAB_TOKEN` |
| Bitbucket | `BITBUCKET_PULL_REQUEST_TOKEN` |

`token`이 설정되어 있지만 비어 있거나 존재하지 않는 변수를 가리키는 경우에는 대체값으로 넘어가지 않으며, 조회는 `NOT_CONFIGURED`와 함께 실패합니다.

<Callout type="warning" title="GITHUB_TOKEN 및 GITLAB_TOKEN은 일반적인 이름입니다">
  만약 배포 환경에서 이미 다른 용도로 이 중 하나를 설정해 두었다면, 저장소 범위가 존재하는 순간 이 기능이 해당 값을 자동으로 가져갑니다. 이를 분리하려면 `token`을 명시적으로 설정하거나 `*_PULL_REQUEST_TOKEN` 변수를 사용하세요.
</Callout>

## 저장소 범위 [#repository-scope]

워크스페이스는 자체 리포지토리를 보고하므로, 서버는 자신의 토큰을 사용할 수 있는 리포지토리를 결정해야 합니다. 범위(scope)가 없으면 서버 토큰은 절대 사용되지 않습니다.

- `allowedRepositories`: `owner/name` 또는 `owner/*` 형식의 항목을 최대 256개까지 지정할 수 있으며, 대소문자를 구분하지 않고 매칭합니다. GitLab에서는 `group/sub/name` 또는 `group/sub/*`와 같은 중첩 그룹 경로를 사용할 수 있습니다. `*`는 정확히 하나의 세그먼트를 의미하므로, `group/*`는 `group/sub/name`과 매칭되지 않습니다. `*/*`, `*`, 단일 `owner`, 또는 `.` 또는 `..` 세그먼트가 포함된 경로와 같은 항목은 거부됩니다.
- `allowAllRepositories: true`: 토큰이 읽을 수 있는 모든 저장소를 조회합니다. 이 옵션은 기본적으로 꺼져 있습니다. 코드를 실행할 수 있는 사용자는 서버 토큰이 볼 수 있는 어떤 저장소든 지정하여, 풀 리퀘스트의 제목, 크기, 체크 상태를 읽을 수 있기 때문입니다.

A repository outside the scope looks exactly like one with no pull request. For a pull request from a fork, checks are read from the fork only when the fork is in scope; otherwise they are read from the base repository, so the token never reaches an unlisted fork.

## 예시 [#examples]

GitHub, 서버 환경에 `GITHUB_PULL_REQUEST_TOKEN`이 설정된 경우:

```yaml filename="librechat.yaml"
endpoints:
  agents:
    pullRequests:
      allowedRepositories:
        - 'LibreChat-AI/LibreChat'
        - 'my-org/*'
```

GitHub Enterprise Server, 명시적 토큰 참조 포함:

```yaml filename="librechat.yaml"
endpoints:
  agents:
    pullRequests:
      host: 'github.example.com'
      token: '${GHES_PULL_REQUEST_TOKEN}'
      allowedRepositories: ['platform/*']
```

Bitbucket Cloud, `BITBUCKET_PULL_REQUEST_TOKEN`이 설정된 경우:

```yaml filename="librechat.yaml"
endpoints:
  agents:
    pullRequests:
      provider: 'bitbucket'
      allowedRepositories: ['my-workspace/*']
```

## 사용자별 계정 [#per-user-accounts]

`oauth`를 설정하면 사용자는 **설정 > 계정 > Pull request 계정**에서 자신의 계정을 연결할 수 있으며, 이때 조회는 사용자 본인의 토큰, 속도 제한, 저장소 접근 권한으로 실행됩니다. 작동하는 `oauth` 앱이 있으면 서버 토큰이나 범위(scope)가 없더라도 해당 기능이 활성화됩니다.

```yaml filename="librechat.yaml"
endpoints:
  agents:
    pullRequests:
      oauth:
        clientId: '${GITHUB_PR_OAUTH_CLIENT_ID}'
        clientSecret: '${GITHUB_PR_OAUTH_CLIENT_SECRET}'
      # optional: the server token's scope, for users who have not connected
      allowedRepositories: ['my-org/*']
```

`clientId`와 `clientSecret`은 환경 변수 참조입니다. 둘 중 하나라도 해석되지 않으면 사용자는 연결할 수 없으며, 서버 토큰만 사용됩니다. 이 흐름은 `JWT_SECRET`으로 서명되며, 콜백 URL은 `DOMAIN_SERVER`를 기반으로 생성됩니다.

```
<DOMAIN_SERVER>/api/pull-requests/oauth/callback
```

How connected accounts behave:

- 연결된 사용자의 토큰은 해당 사용자가 이미 볼 수 있는 내용만 확인할 수 있으므로, `allowedRepositories`의 제한을 받지 않습니다.
- 아직 연결하지 않은 사용자는 서버 토큰을 해당 범위(scope)에서 계속 사용합니다. 서버 토큰이 없다면, 연결하기 전까지 아무것도 표시되지 않습니다.
- 제공자 또는 키 저장소가 중단되어 연결된 사용자의 토큰을 갱신할 수 없는 경우, 해당 사용자의 조회는 pull request를 사용할 수 없는 것으로 보고합니다. 서버 토큰으로 대체(fallback)되는 일은 없습니다.
- 제공자가 권한 부여(grant)가 취소되었기 때문에 갱신을 거부하면, 해당 연결은 제거되고 사용자는 연결되지 않은 상태로 간주됩니다.
- 자격 증명(grants)은 사용자와 제공자 호스트마다 하나씩 암호화되어 저장됩니다. `clientId`, `provider` 또는 `host`를 변경하면 기존 연결은 더 이상 유효하게 취급되지 않으므로, 사용자는 다시 연결해야 합니다. `scope`를 변경하면 새로 생성되는 연결에만 적용됩니다.
- `oauth`를 제거하면 저장된 권한 부여(grant)는 사용되지 않은 상태로 남게 되며, 사용자는 **사용 안 함**으로 표시되고 연결을 해제할 수 있습니다.

`scope`, `flowTimeoutMinutes`, `requestTimeoutSeconds`, `retentionDays`은 선택 사항입니다. 자세한 내용은 [`pullRequests.oauth` 참조](/docs/configuration/librechat_yaml/object_structure/agents#pullrequestsoauth)를 확인하세요.

## 요율 제한 및 캐싱 [#rate-limits-and-caching]

결과는 자격 증명, 저장소, 브랜치, 커밋 단위로 `cacheTtlSeconds`(기본값 30초) 동안 캐시됩니다. 실패한 결과는 최대 10초 동안 기억됩니다.

하나의 호스트에서 자격 증명에 적용된 속도 제한은 해당 토큰 아래의 모든 브랜치에 대한 조회를 일시 중지시키며, 사용자별 계정을 사용하는 경우 각 사용자는 각자의 제한을 갖습니다. 일시 중지 시간은 최소 10초이며, 제공자가 지정한 대기 시간(최대 1시간)을 따르고, 지정된 대기 시간이 없는 GitHub 보조 제한의 경우 60초입니다. 일시 중지 중에는 조회 요청에 `RATE_LIMITED`가 응답됩니다.

여러 개의 레플리카를 운영하는 경우 `sharedCache: true`를 설정하면, 각 레플리카가 같은 결과를 반복해서 조회하는 대신 찾은 풀 리퀘스트와 속도 제한(rate limit) 대기 상태를 Redis를 통해 공유합니다. 이 설정은 배포가 `USE_REDIS`와 함께 실행될 때에만 적용됩니다. 각 레플리카는 Redis 앞단에 자체 인메모리 캐시를 유지하며, `sharedCacheTimeoutMs`(기본값 250 ms)보다 오래 걸리는 Redis 호출은 건너뜁니다. `sharedCacheSlots`(64~1000000, 기본값 65536)는 공유 캐시가 사용하는 Redis 키의 최대 개수를 제한합니다. 이 값은 YAML에서만 읽습니다.

```yaml filename="librechat.yaml"
endpoints:
  agents:
    pullRequests:
      allowedRepositories: ['my-org/*']
      sharedCache: true
```

나머지 제한값(동시 실행 수, 타임아웃, 재사용된 브랜치 이름을 검색할 범위, 확인할 체크 페이지 수)에는 합리적인 기본값이 설정되어 있습니다. 이 값들은 [`pullRequests` 참조](/docs/configuration/librechat_yaml/object_structure/agents#pullrequests)에 나열되어 있습니다.

## 롤링 업그레이드 [#rolling-upgrades]

사이드바는 배치 경로를 사용하며, `/api/config`가 `pullRequestsBatchVersion`을 노출하는 경우에만 이를 요청합니다. 배치 경로가 없는 레플리카가 404로 응답하면 클라이언트는 대화마다 개별 조회를 하는 방식으로 대체합니다. `/api/config` 자체가 플래그가 없는 레플리카에서 제공되면 사이드바 표시가 비어 있게 되므로, 이에 의존하기 전에 모든 레플리카를 업그레이드하십시오.

## 보안 [#security]

- 토큰은 서버에만 보관됩니다. 브라우저로 전송되지 않으며, 오류 응답에는 공급자 응답 텍스트, 토큰 또는 스택 트레이스가 포함되지 않습니다.
- 서버 토큰은 범위에 포함된 저장소에만, 그리고 설정된 호스트에서만 사용됩니다.
- 조회 경로는 로그인한 사용자를 요구하며, 해당 사용자의 대화에 대해서만 응답합니다. 대화가 없거나, 만료되었거나, 다른 사용자의 것인 경우에는 풀 리퀘스트가 없는 대화와 동일하게 보입니다.

## 문제 해결 [#troubleshooting]

Pull request가 발견되기 전에는 조회 실패가 사이드바에 아무것도 표시하지 않습니다. 디버그 로그에는 provider와 reason code가 기록되며, 저장소 이름이나 provider 응답은 포함되지 않습니다. 이 기능이 활성화되어 있는지 확인하려면 로그인한 상태에서 `/api/config`를 열고 `pullRequestsEnabled: true`가 있는지 확인하세요.

| 증상 | 가능한 원인 | 해결 방법 |
| --- | --- | --- |
| 어디에도 칩이나 사이드바 표시가 없음 | 토큰이 없거나, 저장소 범위가 없거나, `enabled: false` 설정 | 토큰과 범위를 확인한 다음 `/api/config`를 확인하세요. |
| 특정 워크스페이스 채팅에만 칩이 없음 | 해당 저장소가 `allowedRepositories`에 없음 | 저장소를 추가하거나, 소유자를 `owner/*` 형식으로 추가하세요. |
| 일부 워크스페이스 채팅에만 칩이 표시됨 | 워크스페이스가 브랜치를 보고하지 않음 | Code API에서 `CODEAPI_BRIDGE_LANE_GIT=true`가 설정되어 있는지, 그리고 code-interpreter #311 이상 버전의 워커를 사용하고 있는지 확인하세요. |
| 헤더 칩은 작동하지만 사이드바에는 아무것도 표시되지 않음 | `/api/config`에 `pullRequestsBatchVersion`이 없음 (이전 빌드이거나 오래된 탭) | 모든 레플리카를 업그레이드하고, 재시작한 다음 강력 새로고침(hard reload)을 하세요. |
| `NOT_CONFIGURED` | `token`은 설정되어 있지만 해당 변수가 비어 있거나 없음 | 변수를 설정하거나, `token`을 제거하여 대체 변수를 사용하세요. |
| 모든 GitHub 풀 리퀘스트 로딩이 실패함 | 토큰에 Checks 권한이 없음 | Checks 읽기 전용 권한을 부여하세요. |
| 브랜치가 이동한 후에만 실패함 | 토큰에 Contents 권한이 없음 | Contents 읽기 전용 권한을 부여하세요. |
| `RATE_LIMITED`가 자주 발생함 | 여러 사용자가 하나의 토큰을 공유하거나, 레플리카마다 제공자에게 요청함 | `cacheTtlSeconds`를 늘리고, `maxConcurrentLookups`를 줄이고, `sharedCache`를 활성화하거나, `oauth`를 설정하세요. |
| 포크의 풀 리퀘스트에 체크가 표시되지 않음 | 해당 포크가 범위에 포함되지 않음 | 포크의 소유자를 추가하거나, `allowAllRepositories: true`를 설정하세요. |
| GitLab 또는 Bitbucket에서 아무것도 표시되지 않음 | `provider`가 설정되지 않았거나, `host`가 일치하지 않음 | `provider`를 설정하고, 자체 호스팅 GitLab의 경우 `host`를 설정하세요. Bitbucket은 `bitbucket.org`에서만 작동합니다. |
| `gh pr create` 링크가 무시됨 | 링크가 다른 호스트 또는 다른 저장소의 것임 | 설정된 호스트와 워크스페이스의 저장소에 있는 링크만 인식됩니다. |
| 연결된 사용자에게 풀 리퀘스트가 사용 불가로 표시됨 | 사용자의 토큰을 갱신할 수 없었음 | 나중에 다시 시도하세요. 연결된 사용자는 서버 토큰으로 대체되지 않습니다. |
| 자주 재사용되는 브랜치 이름에서 풀 리퀘스트가 없음 | 검색이 해당 항목에 도달하기 전에 중단됨 | `maxCandidatePullRequests`, `maxCandidatePages` 또는 `maxHeadComparisons`를 늘리세요. |
| 프록시 뒤에서 조회가 느리거나 시간 초과됨 | `requestTimeoutSeconds`가 너무 낮음 | 값을 늘리고, `HTTPS_PROXY`와 `NO_PROXY`를 확인하세요. |

## API [#api]

두 개의 대화 라우트는 로그인한 사용자를 필요로 하며, 해당 사용자의 대화에 대해서만 응답합니다.

- `GET /api/convos/:conversationId/pull-request`은 `{ "pullRequest": null }` 또는 다음 필드를 가진 풀 리퀘스트를 반환합니다: `number`, `title`, `url`, `additions`, `deletions`, `state`(`open`, `closed`, `merged`), `isDraft`, `mergeable`(`clean`, `conflicting`, `unknown`), `checks`(`passing`, `failing`, `running`, `none`). 실패 시에는 503 응답이 반환되며, `code`는 `NOT_CONFIGURED`, `RATE_LIMITED`, `UPSTREAM_ERROR` 중 하나로 설정됩니다.
- `POST /api/convos/pull-requests`는 `{ "conversationIds": [...] }`를 입력으로 받으며, 개수는 1개에서 50개 사이여야 합니다. 응답은 `{ "results": [...] }` 형태이며, 결과는 요청과 같은 순서로 반환되고 각 항목에는 `pullRequest` 또는 `error.code`가 포함됩니다. 하나의 조회가 실패하더라도 나머지 조회 결과는 가려지지 않습니다.

계정 라우트는 `JWT_SECRET`이 설정된 경우에만 존재합니다: `GET /api/pull-requests/oauth/connect`, `GET /api/pull-requests/oauth/callback`, `GET /api/pull-requests/oauth/status`, 그리고 `DELETE /api/pull-requests/oauth`.

`/api/config`에는 `pullRequestsEnabled`가 포함되며, 기능이 켜져 있으면 `pullRequestsBatchVersion`과 `pullRequestsMaxConcurrentLookups`도 함께 포함됩니다. 사용자가 계정을 연결할 수 있는 경우에는 `pullRequestsConnect`(제공자)도 포함됩니다. 이 값들은 서버가 설정하는 것이며, 사용자가 변경하는 설정이 아닙니다. 위에서 언급한 오류 코드만 안정적인 값입니다.
