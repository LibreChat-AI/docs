Questa guida descrive come configurare Redis per la cache e l'archiviazione delle sessioni in LibreChat. Redis offre miglioramenti significativi delle prestazioni ed è **obbligatorio per la scalabilità orizzontale**. Se esegui più istanze di LibreChat dietro un bilanciatore di carico, Redis garantisce uno stato coerente su tutte le istanze.

## Configurazione di base [#basic-setup]

### Abilitare Redis [#enable-redis]

Per abilitare Redis in LibreChat, imposta la seguente variabile d'ambiente nel tuo file `.env`:

```bash
USE_REDIS=true
```

**Importante**: Quando `USE_REDIS=true`, è necessario fornire anche un `REDIS_URI`. L'applicazione genererà un errore se Redis viene abilitato senza un URI di connessione.

## Tipi di connessione [#connection-types]

### Singola istanza Redis [#single-redis-instance]

Per una configurazione standard con un singolo server Redis:

```bash
# Local Redis instance
REDIS_URI=redis://127.0.0.1:6379

# Remote Redis instance
REDIS_URI=redis://your-redis-host:6379
```

### Redis Cluster [#redis-cluster]

Per distribuzioni di cluster Redis con più nodi:

```bash
# Multiple Redis cluster nodes
REDIS_URI=redis://127.0.0.1:7001,redis://127.0.0.1:7002,redis://127.0.0.1:7003
```

L'applicazione rileva automaticamente la modalità cluster quando vengono forniti più URI.

Se il tuo cluster Redis ha un solo URI, puoi utilizzare la variabile d'ambiente `USE_REDIS_CLUSTER` per abilitare la modalità cluster:

```bash
# Redis cluster with single URI
REDIS_URI=redis://127.0.0.1:7001
USE_REDIS_CLUSTER=true
```

### Servizi Redis gestiti a endpoint singolo [#single-endpoint-managed-redis-services]

Alcuni servizi Redis gestiti, inclusi AWS ElastiCache Serverless e Redis Enterprise Cloud su AWS, espongono un singolo endpoint di connessione mentre effettuano lo sharding delle chiavi internamente. In tale configurazione, mantieni LibreChat in modalità di connessione a nodo singolo, ma abilita le eliminazioni sicure per il cluster (cluster-safe deletes) se la pulizia della cache fallisce con l'errore `CROSSSLOT Keys in request don't hash to the same slot`.

```bash
USE_REDIS=true
REDIS_URI=rediss://your-managed-redis-endpoint:6379
USE_REDIS_CLUSTER=false
REDIS_CLUSTER_SAFE_DELETE=true
```

`REDIS_CLUSTER_SAFE_DELETE=true` fa sì che LibreChat elimini le chiavi della cache corrispondenti una alla volta invece di inviare comandi `DEL` multi-chiave. Ciò evita errori `CROSSSLOT` senza modificare il modo in cui LibreChat si connette a Redis.

Usa `USE_REDIS_CLUSTER=true` solo quando LibreChat deve creare un client Redis Cluster. Per i servizi gestiti a endpoint singolo, `REDIS_CLUSTER_SAFE_DELETE=true` è l'opzione più sicura.

### Redis con TLS/SSL [#redis-with-tlsssl]

Per connessioni Redis sicure:

```bash
# Redis with TLS encryption
REDIS_URI=rediss://127.0.0.1:6380

# Path to CA certificate for TLS verification
REDIS_CA=/path/to/ca-cert.pem
```

## Configurazione di sicurezza [#security-configuration]

### Autenticazione [#authentication]

Configura le credenziali di autenticazione Redis:

```bash
# Method 1: Include credentials in URI
# With both username and password
REDIS_URI=redis://myuser:mypassword@127.0.0.1:6379


# Method 2: Separate environment variables
REDIS_URI=redis://127.0.0.1:6379
REDIS_USERNAME=your_redis_username
REDIS_PASSWORD=your_redis_password
```

**Nota**: Le credenziali incluse in `REDIS_URI` hanno la precedenza. `REDIS_USERNAME` e `REDIS_PASSWORD` vengono utilizzate solo come alternativa quando l'URI non contiene un nome utente o una password.

### Configurazione TLS [#tls-configuration]

Per connessioni crittografate:

```bash
# Enable TLS with rediss:// protocol
REDIS_URI=rediss://your-redis-host:6380

# Provide CA certificate for verification
REDIS_CA=/path/to/your/ca-certificate.pem
```

### TLS con Elasticache [#tls-with-elasticache]

Elasticache potrebbe richiedere l'utilizzo di un dnsLookup alternativo per le connessioni TLS. Consulta "Special Note: Aws Elasticache Clusters with TLS" su questa pagina web: https://www.npmjs.com/package/ioredis

```bash
# Enable redis alternate dnsLookup
REDIS_USE_ALTERNATIVE_DNS_LOOKUP=true
```

## Opzioni avanzate [#advanced-options]

### Prefissi delle chiavi [#key-prefixing]

Il prefisso delle chiavi Redis previene la contaminazione tra diverse distribuzioni isolando i dati della cache tra ambienti, versioni o istanze differenti che condividono lo stesso server Redis. Questo è essenziale per:

- **Distribuzioni multi-tenant**: Ambienti separati di staging, produzione e sviluppo
- **Blue-green deployments**: Isolare la cache tra diverse versioni dell'applicazione

```bash
# Option 1: Dynamic prefix from environment variable (recommended for cloud)

# Google Cloud Platform - Cloud Run
REDIS_KEY_PREFIX_VAR=K_REVISION

# AWS - ECS/Fargate
REDIS_KEY_PREFIX_VAR=AWS_EXECUTION_ENV

# Azure Container Instances
REDIS_KEY_PREFIX_VAR=CONTAINER_NAME

# Kubernetes - Pod name or deployment
REDIS_KEY_PREFIX_VAR=HOSTNAME
REDIS_KEY_PREFIX_VAR=POD_NAME

# Kubernetes - Custom deployment identifier
REDIS_KEY_PREFIX_VAR=DEPLOYMENT_ID

# Heroku
REDIS_KEY_PREFIX_VAR=DYNO

# Option 2: Static prefix (for manual control)
REDIS_KEY_PREFIX=librechat-prod-v2
REDIS_KEY_PREFIX=staging-branch-feature-x
REDIS_KEY_PREFIX=dev-john-local
```

**Importante**: Non è possibile impostare contemporaneamente `REDIS_KEY_PREFIX_VAR` e `REDIS_KEY_PREFIX`.

**Esempi di contaminazione senza prefissi**:

- Cache di produzione sovrascritta dal deployment di staging
- I test dei branch di funzionalità corrompono la cache del branch principale
- Vecchie versioni di deployment che forniscono dati memorizzati nella cache non aggiornati

**Formato del prefisso della chiave**:

- Client IoRedis: `{prefix}::{key}`
- Client Keyv: Gestito dal livello di archiviazione

### Limiti di connessione [#connection-limits]

Configura i limiti di connessione di Redis:

```bash
# Maximum number of event listeners (default: 40)
REDIS_MAX_LISTENERS=40
```

### Connection Keep-Alive [#connection-keep-alive]

Configura gli heartbeat Redis con limite di tempo e il TCP keepalive:

```bash
# Redis ping interval in seconds (default: 0 = disabled)
# When set to a positive integer (in seconds), Redis clients will ping the server at this interval
# When unset or 0, no pinging is performed (recommended for most use cases)
# Example: 300 = ping every 5 minutes
REDIS_PING_INTERVAL=300

# Maximum time an enabled heartbeat PING may go unanswered (default: 5000 ms)
REDIS_PING_TIMEOUT=5000

# Dedicated pub/sub subscriber heartbeat (default: 15 seconds, 0 = disabled)
REDIS_SUBSCRIBER_PING_INTERVAL=15

# TCP keepalive idle delay for ioredis sockets (default: 10000 ms, 0 = kernel default)
REDIS_KEEP_ALIVE=10000
```

**Importante**:

- Impostare `REDIS_PING_INTERVAL=0` o ometterlo disabilita completamente il ping.
- Imposta un valore positivo (in secondi) solo se riscontri problemi di timeout della connessione
- `REDIS_PING_INTERVAL` è specificato in secondi e controlla l'heartbeat opzionale del client ioredis principale
- I subscriber pub/sub dedicati utilizzano il proprio intervallo predefinito, poiché un socket inattivo e non più funzionante potrebbe altrimenti rimanere non rilevato; imposta `REDIS_SUBSCRIBER_PING_INTERVAL=0` per disabilitare tale heartbeat.
- Ogni heartbeat abilitato utilizza `REDIS_PING_TIMEOUT` come scadenza per la risposta e riconnette il socket quando un PING rimane senza risposta
- `REDIS_KEEP_ALIVE` configura il socket TCP di ioredis indipendentemente dai PING a livello di applicazione
- Valori di esempio: `300` (5 minuti), `600` (10 minuti), `60` (1 minuto)

### Ripristino da Failover della Replica [#replica-failover-recovery]

Durante un failover di Sentinel, una replica Redis declassata può mantenere aperto un socket esistente rifiutando al contempo le scritture con `READONLY`. LibreChat rileva questa risposta sul client Keyv non-cluster, interrompe la connessione obsoleta e si riconnette in modo che il primary corrente possa essere risolto senza riavviare l'applicazione.

```bash
# Minimum interval between forced recovery attempts, in milliseconds
# Default: 5000
REDIS_READONLY_RECOVERY_INTERVAL=5000
```

L'intervallo esegue il debounce dei tentativi di riconnessione durante un picco di scritture fallite. I client Redis Cluster sono esclusi perché utilizzano la topologia cluster nativa e la gestione dei reindirizzamenti.

### Controlli di integrità [#health-checks]

LibreChat espone tre endpoint di probe. Solo `/readyz` riflette lo stato di Redis:

| Endpoint | Restituisce `200 OK` | Restituisce `503 NOT_READY` |
| --- | --- | --- |
| `/livez` | Ogni volta che il processo sta servendo le richieste | Mai |
| `/health` | Ogni volta che il processo sta servendo le richieste | Mai |
| `/readyz` | Dopo il completamento dell'avvio e, con `USE_REDIS=true`, mentre Redis è connesso | Prima del completamento dell'avvio, oppure mentre Redis è abilitato ma non connesso |

Quando Redis si riavvia, va in failover o diventa irraggiungibile per un periodo superiore alla finestra di nuovi tentativi del client, le richieste che ne dipendono (accesso, sessioni, limiti di frequenza) falliscono finché la connessione non viene ripristinata. Durante questo intervallo, `/readyz` risponde con `503`, quindi un load balancer o una sonda di readiness di Kubernetes interrompe l'instradamento del traffico verso l'istanza. Torna a `200` non appena Redis si riconnette, senza bisogno di un riavvio. Con Redis abilitato, ogni client Redis deve essere connesso; per un Redis Cluster, questo include ogni nodo primario.

Indirizza i controlli di readiness a `/readyz` e i controlli di liveness a `/livez`. Escludi Redis dal controllo di liveness: una probe di liveness che fallisce durante un'interruzione di Redis riavvia tutti i pod contemporaneamente e non può riportare Redis in funzione.

```yaml
livenessProbe:
  httpGet:
    path: /livez
    port: 3080
readinessProbe:
  httpGet:
    path: /readyz
    port: 3080
  periodSeconds: 10
  failureThreshold: 3
```

`/readyz` non attende da solo le riconnessioni brevi, quindi usa `failureThreshold` per decidere quanto deve durare un'interruzione prima che il traffico venga ritirato.

### Caching selettivo in memoria [#selective-in-memory-caching]

Forza specifici namespace di cache a utilizzare l'archiviazione in-memory anche quando Redis è abilitato:

```bash
# Comma-separated list of cache keys
FORCED_IN_MEMORY_CACHE_NAMESPACES=CONFIG_STORE,APP_CONFIG,ROLES
```

Quando non impostato, il valore predefinito è `CONFIG_STORE,APP_CONFIG`, in modo che la configurazione derivata da `librechat.yaml` rimanga per ogni container. Impostare questa variabile **sostituisce** il valore predefinito anziché aggiungervisi, quindi includi `CONFIG_STORE,APP_CONFIG` nell'elenco a meno che tu non voglia che questi namespace vengano salvati in Redis. Impostala su una stringa vuota per instradare tutti i namespace tramite Redis.

Chiavi di cache valide (dall'enum `CacheKeys` in `librechat-data-provider`):

| Chiave | Descrizione |
| --- | --- |
| `CONFIG_STORE` | Archivio di configurazione |
| `TOOL_CACHE` | Cache degli strumenti (plugin, strumenti MCP, definizioni degli strumenti) |
| `ROLES` | Ruoli utente |
| `USER_PRINCIPALS` | Appartenenze ai gruppi utilizzate per risolvere i principal ACL |
| `PROMPT_GROUPS_ACCESS` | Insiemi di ID per l'accesso ai gruppi di prompt |
| `AGENT_LINKED_INSTRUCTIONS` | Istruzioni risolte dei gruppi di prompt collegati a un agente |
| `SANDBOX_PREWARM` | Stato di preriscaldamento della sandbox di codice per conversazione |
| `GEN_TITLE` | Titoli generati |
| `TOOLS` | Dati degli strumenti |
| `MODELS_CONFIG` | Configurazione dei modelli |
| `MODEL_QUERIES` | Query dei modelli |
| `STARTUP_CONFIG` | Configurazione di avvio |
| `ENDPOINT_CONFIG` | Configurazione degli endpoint |
| `TOKEN_CONFIG` | Configurazione dei token |
| `REASONING_CAPABILITIES` | Sforzo di ragionamento per modello per gli endpoint OpenRouter |
| `PULL_REQUESTS` | Ricerche di pull request e periodi di raffreddamento per i limiti di frequenza di GitHub |
| `APP_CONFIG` | Configurazione dell'applicazione |
| `ABORT_KEYS` | Chiavi di interruzione |
| `BANS` | Dati dei ban |
| `ENCODED_DOMAINS` | Domini codificati |

  L'utilizzo di una chiave non valida (ad esempio, la deprecata `STATIC_CONFIG`) causerà un errore all'avvio. Utilizzare solo le chiavi presenti nella tabella sopra.
</Callout>

## Ottimizzazione delle prestazioni [#performance-tuning]

### Connection Keep-Alive [#connection-keep-alive-1]

L'applicazione implementa un keep-alive della connessione configurabile:

- I PING del main-client sono controllati da `REDIS_PING_INTERVAL` e sono disabilitati per impostazione predefinita
- I PING dei sottoscrittori dedicati sono controllati da `REDIS_SUBSCRIBER_PING_INTERVAL` e sono impostati per impostazione predefinita a 15 secondi
- I Heartbeat utilizzano `REDIS_PING_TIMEOUT` per rilevare socket silenziosamente interrotti e forzare la riconnessione
- Il TCP keepalive utilizza `REDIS_KEEP_ALIVE`, indipendentemente dagli heartbeat a livello di applicazione
- I timer heartbeat vengono cancellati in caso di eventi di disconnessione o chiusura

### Strategia di cache [#cache-strategy]

L'applicazione utilizza un approccio a doppio client:

- **Client IoRedis**: Operazioni Redis primarie con prefisso automatico
- **Client Keyv Redis**: Operazioni a livello di archivio con gestione dei prefissi in `cacheFactory.js`

### Ottimizzazione Avanzata della Connessione [#advanced-connection-tuning]

Queste variabili opzionali regolano il comportamento delle connessioni e le operazioni di cache in blocco. I valori predefiniti sono adatti alla maggior parte delle installazioni.

| Variabile | Predefinito | Descrizione |
| --- | --- | --- |
| `REDIS_CONNECT_TIMEOUT` | `10000` | Timeout di connessione in millisecondi. |
| `REDIS_RETRY_MAX_ATTEMPTS` | `10` | Numero massimo di tentativi di riconnessione prima di rinunciare. `0` riprova indefinitamente. |
| `REDIS_RETRY_MAX_DELAY` | `3000` | Ritardo massimo tra i tentativi di riconnessione, in millisecondi. |
| `REDIS_ENABLE_OFFLINE_QUEUE` | `true` | Accoda i comandi quando la connessione è assente. Impostare su `false` per farli fallire immediatamente. |
| `REDIS_SCAN_COUNT` | `1000` | Suggerimento `COUNT` per le operazioni `SCAN` quando si cercano chiavi per pattern. |
| `REDIS_DELETE_CHUNK_SIZE` | `1000` | Numero di chiavi eliminate per batch nelle eliminazioni in blocco. |
| `MCP_REGISTRY_CACHE_TTL` | `5000` | Millisecondi per cui vengono mantenute le cache del registro MCP. La obsolescenza tra istanze può arrivare fino al doppio di questo valore. `0` disabilita lo snapshot locale, quindi ogni lettura va a Redis. |

### Ottimizzazione della memoria [#memory-optimization]

Usa `FORCED_IN_MEMORY_CACHE_NAMESPACES` per ottimizzare le prestazioni mantenendo in memoria i set di dati piccoli e consultati frequentemente, utilizzando al contempo Redis per le cache più grandi.

## Stream riprendibili [#resumable-streams]

Redis abilita [Resumable Streams](/docs/features/resumable_streams) per distribuzioni scalate orizzontalmente. Quando abilitato, le risposte dell'AI possono riconnettersi e riprendere senza interruzioni tra le istanze del server.

**Importante:** Quando `USE_REDIS=true`, i flussi riprendibili utilizzano automaticamente Redis per il coordinamento tra le istanze. Questa è la configurazione consigliata per distribuzioni scalate orizzontalmente in cui gli utenti potrebbero connettersi a diverse istanze del server.

**Nota:** Se utilizzi una singola istanza di LibreChat, Redis per gli stream riprendibili è in genere eccessivo; la modalità integrata in memoria funziona perfettamente. Redis diventa indispensabile quando hai più istanze di LibreChat dietro un load balancer, dove la riconnessione di un utente potrebbe avvenire su un server diverso da quello in cui è iniziato lo stream.

### Configurazione [#configuration]

```bash
# Redis enabled = resumable streams automatically use Redis
USE_REDIS=true
REDIS_URI=redis://127.0.0.1:6379

# Optional: explicitly control resumable streams behavior
# USE_REDIS_STREAMS=true  # Enabled by default when USE_REDIS=true
```

### Compatibilità del Protocollo di Generazione [#generation-protocol-compatibility]

I client LibreChat attuali negoziano automaticamente il protocollo di generazione v2 con ogni archivio di generazione integrato. Non è richiesta alcuna impostazione di distribuzione. Le generazioni esistenti con un marcatore di protocollo v1 esplicito o memorizzato mantengono il loro comportamento v1 immutabile attraverso steering, pausa/ripresa, riprova e ripristino fino al completamento.

Per un aggiornamento progressivo (rolling upgrade), ogni immagine API e worker in esecuzione deve includere il bridge di compatibilità v2:

- Ogni immagine API e worker esegue LibreChat `v0.8.8-rc1` o versioni successive.
- Il Helm chart `2.0.8` o versioni successive seleziona un'immagine predefinita compatibile; un override dell'immagine personalizzata deve comunque soddisfare il requisito dell'immagine sopra indicato.

Quando si esegue l'aggiornamento da una versione precedente, eseguire un cold handoff: arrestare ogni vecchia replica dell'API e del worker prima di avviare la nuova immagine. Questo impedisce ai binari pre-v2 e automatic-v2 di condividere lo stato di generazione in Redis.

<Callout type="warning" title="Sicurezza del deployment progressivo">
  Non eseguire una release precedente alla `v0.8.8-rc1` con lo stesso stato di generazione Redis delle repliche attuali. Prima di eseguire il rollback a una versione inferiore a questo limite di compatibilità, assicurarsi innanzitutto che le repliche attuali e le generazioni protocol-v2 siano state svuotate.
</Callout>

I flussi di generazione in-memory negoziano automaticamente anche il protocollo v2 e non condividono lo stato di generazione tra i processi.

### Stream Delta Coalescing [#stream-delta-coalescing]

I flussi basati su Redis possono raggruppare le pubblicazioni delta per ridurre gli script Redis, i round trip e l'utilizzo della CPU a velocità di token elevate:

```bash filename=".env"
STREAM_DELTA_COALESCE_MS=25
```

L'impostazione è predefinita su `25` millisecondi quando non è configurata. Impostala esplicitamente su `0` per disabilitare il coalescing; i valori superiori a `1000` vengono limitati. Il batching può aggiungere fino a una finestra configurata di latenza di consegna e potrebbe perdere la coda bufferizzata se il processo di pubblicazione termina prima dello svuotamento. I singoli frame dei chunk vengono conservati per compatibilità di protocollo, quindi questa impostazione riduce il lavoro dello script Redis e i round-trip senza modificare il formato del frame del sottoscrittore. I flussi di generazione in memoria rimangono invariati.

### Vantaggi chiave (per lo scaling orizzontale) [#key-benefits-for-horizontal-scaling]

- **Continuità tra istanze**: Gli utenti possono avviare una generazione su un server e riprenderla su un altro
- **Rolling deployments**: I flussi attivi sopravvivono ai riavvii del server
- **Sincronizzazione multi-scheda**: la stessa conversazione si sincronizza tra più schede del browser in un ambiente con bilanciamento del carico
- **Resilienza della connessione**: Riconnessione automatica indipendentemente dal server che gestisce la richiesta

### Configurazione del Cluster [#cluster-configuration]

Per le distribuzioni Redis Cluster, LibreChat utilizza automaticamente chiavi con hash-tag per garantire che le operazioni di stream rimangano all'interno dello stesso slot del cluster:

```bash
USE_REDIS=true
USE_REDIS_STREAMS=true
USE_REDIS_CLUSTER=true
REDIS_URI=redis://node1:7001,redis://node2:7002,redis://node3:7003
```

Vedi [Resumable Streams](/docs/features/resumable_streams) per ulteriori dettagli su questa funzionalità.

## Coordinamento del catalogo MCP [#mcp-catalog-coordination]

Quando Redis è abilitato, LibreChat coordina i cataloghi degli strumenti MCP a livello di applicazione tra le repliche. La pubblicazione all'avvio, la sincronizzazione alla riconnessione e gli aggiornamenti `notifications/tools/list_changed` utilizzano marcatori di generazione e revisione, in modo che una replica obsoleta non possa sovrascrivere un catalogo più recente.

Le distribuzioni Redis Cluster utilizzano chiavi di catalogo e operazioni di aggiornamento compatibili con gli slot; non è richiesta alcuna impostazione Redis separata per MCP. Consulta [MCP Server Management](/docs/configuration/librechat_yaml/object_structure/mcp_servers#additional-information) per il comportamento del catalogo dinamico e la predisposizione di OAuth.
