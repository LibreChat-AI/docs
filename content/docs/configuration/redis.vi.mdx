Hướng dẫn này trình bày cách cấu hình Redis để lưu trữ bộ nhớ đệm (caching) và phiên làm việc (session storage) trong LibreChat. Redis mang lại cải thiện hiệu năng đáng kể và **bắt buộc đối với việc mở rộng theo chiều ngang (horizontal scaling)**. Nếu bạn đang chạy nhiều phiên bản LibreChat phía sau bộ cân bằng tải (load balancer), Redis đảm bảo trạng thái nhất quán giữa tất cả các phiên bản.

## Thiết lập cơ bản [#basic-setup]

### Bật Redis [#enable-redis]

Để kích hoạt Redis trong LibreChat, hãy thiết lập biến môi trường sau trong tệp `.env` của bạn:

```bash
USE_REDIS=true
```

**Quan trọng**: Khi `USE_REDIS=true`, bạn cũng phải cung cấp `REDIS_URI`. Ứng dụng sẽ báo lỗi nếu Redis được bật mà không có URI kết nối.

## Các loại kết nối [#connection-types]

### Một instance Redis duy nhất [#single-redis-instance]

Đối với thiết lập máy chủ Redis đơn lẻ tiêu chuẩn:

```bash
# Local Redis instance
REDIS_URI=redis://127.0.0.1:6379

# Remote Redis instance
REDIS_URI=redis://your-redis-host:6379
```

### Redis Cluster [#redis-cluster]

Đối với các triển khai cụm Redis với nhiều node:

```bash
# Multiple Redis cluster nodes
REDIS_URI=redis://127.0.0.1:7001,redis://127.0.0.1:7002,redis://127.0.0.1:7003
```

Ứng dụng sẽ tự động phát hiện chế độ cụm (cluster mode) khi có nhiều URI được cung cấp.

Nếu cụm redis của bạn chỉ có một URI duy nhất, bạn có thể sử dụng biến môi trường `USE_REDIS_CLUSTER` để kích hoạt chế độ cụm:

```bash
# Redis cluster with single URI
REDIS_URI=redis://127.0.0.1:7001
USE_REDIS_CLUSTER=true
```

### Các dịch vụ Redis được quản lý với một endpoint duy nhất [#single-endpoint-managed-redis-services]

Một số dịch vụ Redis được quản lý, bao gồm AWS ElastiCache Serverless và Redis Enterprise Cloud trên AWS, cung cấp một endpoint kết nối duy nhất trong khi vẫn thực hiện phân đoạn (sharding) các khóa ở bên trong. Trong thiết lập đó, hãy giữ LibreChat ở chế độ kết nối đơn nút (single-node), nhưng hãy bật tính năng xóa an toàn cho cụm (cluster-safe deletes) nếu việc xóa bộ nhớ đệm thất bại với thông báo lỗi `CROSSSLOT Keys in request don't hash to the same slot`.

```bash
USE_REDIS=true
REDIS_URI=rediss://your-managed-redis-endpoint:6379
USE_REDIS_CLUSTER=false
REDIS_CLUSTER_SAFE_DELETE=true
```

`REDIS_CLUSTER_SAFE_DELETE=true` khiến LibreChat xóa các khóa bộ nhớ đệm (cache keys) khớp từng cái một thay vì gửi các lệnh `DEL` đa khóa. Điều này giúp tránh các lỗi `CROSSSLOT` mà không làm thay đổi cách LibreChat kết nối với Redis.

Chỉ sử dụng `USE_REDIS_CLUSTER=true` khi LibreChat cần tạo một client Redis Cluster. Đối với các dịch vụ được quản lý có một endpoint duy nhất, `REDIS_CLUSTER_SAFE_DELETE=true` là tùy chọn an toàn hơn.

### Redis với TLS/SSL [#redis-with-tlsssl]

Đối với các kết nối Redis bảo mật:

```bash
# Redis with TLS encryption
REDIS_URI=rediss://127.0.0.1:6380

# Path to CA certificate for TLS verification
REDIS_CA=/path/to/ca-cert.pem
```

## Cấu hình bảo mật [#security-configuration]

### Xác thực [#authentication]

Cấu hình thông tin xác thực Redis:

```bash
# Method 1: Include credentials in URI
# With both username and password
REDIS_URI=redis://myuser:mypassword@127.0.0.1:6379


# Method 2: Separate environment variables
REDIS_URI=redis://127.0.0.1:6379
REDIS_USERNAME=your_redis_username
REDIS_PASSWORD=your_redis_password
```

**Lưu ý**: Thông tin xác thực (credentials) được nhúng trong `REDIS_URI` sẽ được ưu tiên sử dụng. `REDIS_USERNAME` và `REDIS_PASSWORD` chỉ được dùng như phương án dự phòng khi URI không có tên người dùng hoặc mật khẩu.

### Cấu hình TLS [#tls-configuration]

Đối với các kết nối được mã hóa:

```bash
# Enable TLS with rediss:// protocol
REDIS_URI=rediss://your-redis-host:6380

# Provide CA certificate for verification
REDIS_CA=/path/to/your/ca-certificate.pem
```

### TLS với Elasticache [#tls-with-elasticache]

Elasticache có thể cần sử dụng một dnsLookup thay thế cho các kết nối TLS. Xem "Special Note: Aws Elasticache Clusters with TLS" trên trang web này: https://www.npmjs.com/package/ioredis

```bash
# Enable redis alternate dnsLookup
REDIS_USE_ALTERNATIVE_DNS_LOOKUP=true
```

## Các tùy chọn nâng cao [#advanced-options]

### Tiền tố khóa (Key Prefixing) [#key-prefixing]

Tiền tố khóa Redis giúp ngăn chặn sự nhiễm chéo giữa các lần triển khai bằng cách cô lập dữ liệu bộ nhớ đệm giữa các môi trường, phiên bản hoặc thực thể khác nhau khi dùng chung một máy chủ Redis. Điều này rất cần thiết cho:

- **Triển khai đa người thuê (Multi-tenant deployments)**: Tách biệt các môi trường staging, production và development
- **Blue-green deployments**: Cô lập bộ nhớ đệm giữa các phiên bản ứng dụng khác nhau

```bash
# Option 1: Dynamic prefix from environment variable (recommended for cloud)

# Google Cloud Platform - Cloud Run
REDIS_KEY_PREFIX_VAR=K_REVISION

# AWS - ECS/Fargate
REDIS_KEY_PREFIX_VAR=AWS_EXECUTION_ENV

# Azure Container Instances
REDIS_KEY_PREFIX_VAR=CONTAINER_NAME

# Kubernetes - Pod name or deployment
REDIS_KEY_PREFIX_VAR=HOSTNAME
REDIS_KEY_PREFIX_VAR=POD_NAME

# Kubernetes - Custom deployment identifier
REDIS_KEY_PREFIX_VAR=DEPLOYMENT_ID

# Heroku
REDIS_KEY_PREFIX_VAR=DYNO

# Option 2: Static prefix (for manual control)
REDIS_KEY_PREFIX=librechat-prod-v2
REDIS_KEY_PREFIX=staging-branch-feature-x
REDIS_KEY_PREFIX=dev-john-local
```

**Quan trọng**: Bạn không thể thiết lập đồng thời cả `REDIS_KEY_PREFIX_VAR` và `REDIS_KEY_PREFIX`.

**Các ví dụ về nhiễm bẩn không có tiền tố**:

- Bộ nhớ đệm production bị ghi đè bởi quá trình triển khai staging
- Các bài kiểm tra trên nhánh tính năng làm hỏng bộ nhớ đệm của nhánh chính
- Các phiên bản triển khai cũ đang phục vụ dữ liệu lưu trữ đệm (cached) lỗi thời

**Định dạng tiền tố khóa**:

- Máy khách IoRedis: `{prefix}::{key}`
- Keyv client: Được xử lý bởi lớp lưu trữ

### Giới hạn kết nối [#connection-limits]

Cấu hình giới hạn kết nối Redis:

```bash
# Maximum number of event listeners (default: 40)
REDIS_MAX_LISTENERS=40
```

### Connection Keep-Alive [#connection-keep-alive]

Cấu hình heartbeat Redis giới hạn thời gian và TCP keepalive:

```bash
# Redis ping interval in seconds (default: 0 = disabled)
# When set to a positive integer (in seconds), Redis clients will ping the server at this interval
# When unset or 0, no pinging is performed (recommended for most use cases)
# Example: 300 = ping every 5 minutes
REDIS_PING_INTERVAL=300

# Maximum time an enabled heartbeat PING may go unanswered (default: 5000 ms)
REDIS_PING_TIMEOUT=5000

# Dedicated pub/sub subscriber heartbeat (default: 15 seconds, 0 = disabled)
REDIS_SUBSCRIBER_PING_INTERVAL=15

# TCP keepalive idle delay for ioredis sockets (default: 10000 ms, 0 = kernel default)
REDIS_KEEP_ALIVE=10000
```

**Quan trọng**:

- Việc đặt `REDIS_PING_INTERVAL=0` hoặc bỏ qua nó sẽ vô hiệu hóa hoàn toàn tính năng ping.
- Chỉ đặt giá trị dương (tính bằng giây) nếu bạn gặp sự cố hết thời gian chờ kết nối
- `REDIS_PING_INTERVAL` được chỉ định bằng giây và kiểm soát nhịp tim ioredis chính tùy chọn
- Các trình đăng ký pub/sub chuyên dụng sử dụng khoảng thời gian mặc định của riêng chúng vì một socket chết ở trạng thái nhàn rỗi có thể không bị phát hiện; hãy đặt `REDIS_SUBSCRIBER_PING_INTERVAL=0` để tắt nhịp tim (heartbeat) đó.
- Mỗi heartbeat được kích hoạt sẽ sử dụng `REDIS_PING_TIMEOUT` làm thời hạn phản hồi và thực hiện kết nối lại socket khi một PING không nhận được phản hồi.
- `REDIS_KEEP_ALIVE` cấu hình socket TCP của ioredis một cách độc lập với các PING ở cấp độ ứng dụng.
- Các giá trị ví dụ: `300` (5 phút), `600` (10 phút), `60` (1 phút)

### Khôi phục chuyển đổi dự phòng bản sao (Replica Failover Recovery) [#replica-failover-recovery]

Trong quá trình chuyển đổi dự phòng (failover) của Sentinel, một bản sao Redis bị hạ cấp có thể vẫn giữ kết nối socket hiện có trong khi từ chối các lệnh ghi với thông báo `READONLY`. LibreChat phát hiện phản hồi này trên client Keyv không thuộc cluster, ngắt kết nối cũ và kết nối lại để có thể phân giải primary hiện tại mà không cần khởi động lại ứng dụng.

```bash
# Minimum interval between forced recovery attempts, in milliseconds
# Default: 5000
REDIS_READONLY_RECOVERY_INTERVAL=5000
```

Khoảng thời gian này giúp debounce (chống rung) các nỗ lực kết nối lại trong một đợt ghi thất bại. Các client Redis Cluster được loại trừ vì chúng sử dụng cấu trúc liên kết cụm (cluster topology) và cơ chế xử lý chuyển hướng (redirect handling) gốc.

### Kiểm tra tình trạng hoạt động (Health Checks) [#health-checks]

LibreChat cung cấp ba endpoint probe. Chỉ `/readyz` phản ánh trạng thái của Redis:

| Endpoint | Trả về `200 OK` | Trả về `503 NOT_READY` |
| --- | --- | --- |
| `/livez` | Bất cứ khi nào tiến trình đang phục vụ các yêu cầu | Không bao giờ |
| `/health` | Bất cứ khi nào tiến trình đang phục vụ các yêu cầu | Không bao giờ |
| `/readyz` | Sau khi quá trình khởi động hoàn tất và, khi `USE_REDIS=true`, trong khi Redis đang được kết nối | Trước khi quá trình khởi động hoàn tất, hoặc khi Redis được bật nhưng chưa được kết nối |

Khi Redis khởi động lại, chuyển đổi dự phòng (failover) hoặc không thể truy cập trong khoảng thời gian dài hơn cửa sổ thử lại (retry window) của client, các yêu cầu phụ thuộc vào Redis (đăng nhập, phiên làm việc, giới hạn tần suất) sẽ thất bại cho đến khi kết nối được khôi phục. Trong thời gian đó, `/readyz` trả về `503`, do đó load balancer hoặc readiness probe của Kubernetes sẽ ngừng định tuyến lưu lượng đến instance. Endpoint này trả về `200` ngay khi Redis kết nối lại, mà không cần khởi động lại. Khi Redis được bật, mọi Redis client phải được kết nối; đối với Redis Cluster, điều này bao gồm tất cả các node primary.

Hướng dẫn kiểm tra tính sẵn sàng (readiness) tới `/readyz` và kiểm tra tính sống (liveness) tới `/livez`. Không đưa Redis vào kiểm tra liveness: nếu probe liveness thất bại khi Redis gặp sự cố, mọi pod sẽ bị khởi động lại cùng lúc và điều đó không thể khôi phục Redis.

```yaml
livenessProbe:
  httpGet:
    path: /livez
    port: 3080
readinessProbe:
  httpGet:
    path: /readyz
    port: 3080
  periodSeconds: 10
  failureThreshold: 3
```

`/readyz` không tự chờ qua các lần kết nối lại ngắn hạn, vì vậy hãy dùng `failureThreshold` để quyết định một sự cố kéo dài bao lâu trước khi lưu lượng bị rút khỏi.

### Bộ nhớ đệm trong bộ nhớ có chọn lọc (Selective In-Memory Caching) [#selective-in-memory-caching]

Buộc các namespace bộ nhớ đệm cụ thể sử dụng bộ nhớ trong (in-memory) ngay cả khi Redis đã được bật:

```bash
# Comma-separated list of cache keys
FORCED_IN_MEMORY_CACHE_NAMESPACES=CONFIG_STORE,APP_CONFIG,ROLES
```

Khi không được thiết lập, giá trị mặc định là `CONFIG_STORE,APP_CONFIG`, vì vậy cấu hình lấy từ `librechat.yaml` sẽ được lưu riêng cho từng container. Thiết lập biến này sẽ **thay thế** giá trị mặc định thay vì bổ sung thêm vào, vì vậy hãy đưa `CONFIG_STORE,APP_CONFIG` vào danh sách của bạn trừ khi bạn muốn các namespace đó được lưu trong Redis. Đặt giá trị thành chuỗi rỗng để định tuyến tất cả các namespace qua Redis.

| `AGENT_LINKED_INSTRUCTIONS` | Hướng dẫn đã được phân giải của các nhóm prompt được liên kết với một agent |
| `SANDBOX_PREWARM` | Trạng thái khởi động sẵn sandbox mã theo từng cuộc hội thoại |
| `GEN_TITLE` | Tiêu đề được tạo tự động |
| `TOOLS` | Dữ liệu công cụ |
| `MODELS_CONFIG` | Cấu hình mô hình |
| `MODEL_QUERIES` | Truy vấn mô hình |
| `STARTUP_CONFIG` | Cấu hình khởi động |

| `ABORT_KEYS` | Khóa hủy |
| `BANS` | Dữ liệu cấm truy cập |
| `ENCODED_DOMAINS` | Tên miền đã mã hóa |
| `AUDIO_RUNS` | Các lượt xử lý âm thanh |

| `FLOWS` | Trạng thái luồng đang xử lý |
| `PENDING_REQ` | Yêu cầu đang chờ xử lý |
| `S3_EXPIRY_INTERVAL` | Khoảng thời gian hết hạn S3 |
| `OPENID_EXCHANGED_TOKENS` | Token OpenID đã trao đổi |

</Callout>

## Tinh chỉnh hiệu năng [#performance-tuning]

### Connection Keep-Alive [#connection-keep-alive-1]

Ứng dụng triển khai tính năng duy trì kết nối (keep-alive) có thể cấu hình:

- Các PING của main-client được kiểm soát bởi `REDIS_PING_INTERVAL` và bị vô hiệu hóa theo mặc định
- Các PING của người đăng ký chuyên dụng được kiểm soát bởi `REDIS_SUBSCRIBER_PING_INTERVAL` và mặc định là 15 giây.
- Heartbeats sử dụng `REDIS_PING_TIMEOUT` để phát hiện các socket bị chết âm thầm và buộc phải kết nối lại
- TCP keepalive sử dụng `REDIS_KEEP_ALIVE`, độc lập với các heartbeat ở cấp độ ứng dụng
- Các bộ đếm thời gian heartbeat sẽ bị xóa khi xảy ra sự kiện ngắt kết nối hoặc đóng kết nối.

### Chiến lược bộ nhớ đệm (Cache Strategy) [#cache-strategy]

Ứng dụng sử dụng phương pháp tiếp cận hai máy khách (dual-client):

- **IoRedis client**: Các thao tác Redis chính với tiền tố tự động
- **Keyv Redis client**: Các thao tác lớp lưu trữ với xử lý tiền tố trong `cacheFactory.js`

### Điều chỉnh kết nối nâng cao [#advanced-connection-tuning]

Các biến tùy chọn này điều chỉnh hành vi kết nối và các thao tác cache hàng loạt. Giá trị mặc định phù hợp với hầu hết các triển khai.

| Biến | Mặc định | Mô tả |
| --- | --- | --- |
| `REDIS_CONNECT_TIMEOUT` | `10000` | Thời gian chờ kết nối, tính bằng mili giây. |
| `REDIS_RETRY_MAX_ATTEMPTS` | `10` | Số lần thử kết nối lại tối đa trước khi từ bỏ. `0` nghĩa là thử lại vô thời hạn. |
| `REDIS_RETRY_MAX_DELAY` | `3000` | Độ trễ tối đa giữa các lần thử kết nối lại, tính bằng mili giây. |
| `REDIS_ENABLE_OFFLINE_QUEUE` | `true` | Xếp hàng các lệnh khi mất kết nối. Đặt thành `false` để các lệnh thất bại ngay lập tức. |
| `REDIS_SCAN_COUNT` | `1000` | Gợi ý `COUNT` cho các thao tác `SCAN` khi tìm khóa theo mẫu. |
| `REDIS_DELETE_CHUNK_SIZE` | `1000` | Số khóa được xóa mỗi lô trong các thao tác xóa hàng loạt. |
| `MCP_REGISTRY_CACHE_TTL` | `5000` | Thời gian, tính bằng mili giây, mà bộ nhớ đệm registry MCP được giữ lại. Độ lỗi thời giữa các instance có thể lên tới gấp đôi giá trị này. `0` tắt bản snapshot cục bộ, do đó mọi lần đọc đều truy vấn Redis. |

### Tối ưu hóa bộ nhớ [#memory-optimization]

Sử dụng `FORCED_IN_MEMORY_CACHE_NAMESPACES` để tối ưu hóa hiệu suất bằng cách lưu trữ các tập dữ liệu nhỏ, thường xuyên truy cập trong bộ nhớ trong khi vẫn sử dụng Redis cho các bộ nhớ đệm lớn hơn.

## Luồng có thể tiếp tục (Resumable Streams) [#resumable-streams]

Redis cho phép [Resumable Streams](/docs/features/resumable_streams) đối với các triển khai mở rộng theo chiều ngang. Khi được bật, các phản hồi AI có thể kết nối lại và tiếp tục một cách liền mạch trên các instance máy chủ.

**Quan trọng:** Khi `USE_REDIS=true`, các luồng có thể tiếp tục (resumable streams) sẽ tự động sử dụng Redis để điều phối giữa các instance. Đây là thiết lập được khuyến nghị cho các triển khai mở rộng theo chiều ngang (horizontally scaled), nơi người dùng có thể kết nối với các instance máy chủ khác nhau.

**Lưu ý:** Nếu bạn chỉ chạy một phiên bản LibreChat duy nhất, Redis cho các luồng có thể tiếp tục (resumable streams) thường là không cần thiết; chế độ bộ nhớ trong (in-memory) tích hợp sẵn hoạt động tốt. Redis trở nên thiết yếu khi bạn có nhiều phiên bản LibreChat đứng sau một bộ cân bằng tải (load balancer), vì khi người dùng kết nối lại, yêu cầu có thể được chuyển đến một máy chủ khác với máy chủ nơi luồng đã bắt đầu.

### Cấu hình [#configuration]

```bash
# Redis enabled = resumable streams automatically use Redis
USE_REDIS=true
REDIS_URI=redis://127.0.0.1:6379

# Optional: explicitly control resumable streams behavior
# USE_REDIS_STREAMS=true  # Enabled by default when USE_REDIS=true
```

### Khả năng tương thích với Giao thức Tạo (Generation Protocol) [#generation-protocol-compatibility]

Các client LibreChat hiện tại tự động thương lượng giao thức tạo v2 với mọi kho lưu trữ tạo nội dung tích hợp sẵn. Không cần cài đặt triển khai nào. Các nội dung đã tạo trước đó có đánh dấu protocol-v1 rõ ràng hoặc được lưu trữ sẽ giữ nguyên hành vi v1 bất biến của chúng thông qua việc điều hướng, tạm dừng/tiếp tục, thử lại và khôi phục cho đến khi hoàn tất.

Để thực hiện nâng cấp luân phiên (rolling upgrade), mọi image API và worker đang chạy phải bao gồm v2 compatibility bridge:

- Mọi image API và worker đều chạy LibreChat `v0.8.8-rc1` hoặc mới hơn.
- Helm chart `2.0.8` hoặc mới hơn sẽ chọn một image mặc định tương thích; việc ghi đè image tùy chỉnh vẫn phải đáp ứng yêu cầu về image ở trên.

Khi nâng cấp từ một bản phát hành cũ hơn, hãy thực hiện chuyển giao nguội (cold handoff): dừng mọi bản sao API và worker cũ trước khi khởi chạy image mới. Điều này giúp ngăn chặn các tệp nhị phân tiền-v2 và tự động-v2 chia sẻ trạng thái thế hệ trong Redis.

<Callout type="warning" title="An toàn triển khai cuốn chiếu">
  Không chạy phiên bản cũ hơn `v0.8.8-rc1` với cùng trạng thái thế hệ Redis như các bản sao (replica) hiện tại. Trước khi quay lui (rollback) xuống dưới ngưỡng tương thích đó, hãy đảm bảo rằng các bản sao hiện tại và các thế hệ protocol-v2 đã được giải phóng (drain).
</Callout>

Các luồng tạo nội dung trong bộ nhớ (in-memory generation streams) cũng tự động thương lượng giao thức v2 và không chia sẻ trạng thái tạo nội dung giữa các tiến trình.

### Hợp nhất Stream Delta [#stream-delta-coalescing]

Các luồng được hỗ trợ bởi Redis có thể xử lý hàng loạt các bản tin delta để giảm bớt các tập lệnh Redis, số lượt truy vấn khứ hồi và mức sử dụng CPU ở tốc độ token cao:

```bash filename=".env"
STREAM_DELTA_COALESCE_MS=25
```

Cài đặt này mặc định là `25` mili giây khi không được thiết lập. Hãy đặt giá trị này thành `0` để tắt tính năng gộp (coalescing); các giá trị trên `1000` sẽ bị giới hạn. Việc xử lý theo lô (batching) có thể làm tăng thêm một khoảng thời gian trễ phân phối đã cấu hình và có thể làm mất phần đuôi được đệm nếu quá trình xuất bản thoát trước khi nó kịp đẩy dữ liệu đi. Các khung đoạn (chunk frames) riêng lẻ vẫn được giữ lại để đảm bảo tính tương thích của giao thức, vì vậy cài đặt này giúp giảm bớt công việc cho tập lệnh Redis và các lượt truy vấn khứ hồi mà không làm thay đổi định dạng khung của người đăng ký. Các luồng tạo trong bộ nhớ (in-memory generation streams) vẫn không thay đổi.

### Các lợi ích chính (cho việc mở rộng theo chiều ngang) [#key-benefits-for-horizontal-scaling]

- **Tính liên tục giữa các instance**: Người dùng có thể bắt đầu tạo phản hồi trên một máy chủ và tiếp tục trên một máy chủ khác
- **Rolling deployments**: Các luồng đang hoạt động vẫn tồn tại sau khi khởi động lại máy chủ
- **Đồng bộ hóa đa tab**: Cùng một cuộc trò chuyện được đồng bộ hóa trên nhiều tab trình duyệt trong môi trường cân bằng tải
- **Khả năng phục hồi kết nối**: Tự động kết nối lại bất kể máy chủ nào xử lý yêu cầu

### Cấu hình Cluster [#cluster-configuration]

Đối với các triển khai Redis Cluster, LibreChat tự động sử dụng các khóa có gắn thẻ băm (hash-tagged keys) để đảm bảo các thao tác luồng (stream operations) luôn nằm trong cùng một slot của cluster:

```bash
USE_REDIS=true
USE_REDIS_STREAMS=true
USE_REDIS_CLUSTER=true
REDIS_URI=redis://node1:7001,redis://node2:7002,redis://node3:7003
```

Xem [Resumable Streams](/docs/features/resumable_streams) để biết thêm chi tiết về tính năng này.

## Điều phối MCP Catalog [#mcp-catalog-coordination]

Khi Redis được bật, LibreChat điều phối các danh mục công cụ MCP ở cấp ứng dụng trên các bản sao (replicas). Việc công bố khi khởi động, đồng bộ hóa khi kết nối lại và các bản cập nhật `notifications/tools/list_changed` sử dụng các đánh dấu thế hệ và phiên bản để đảm bảo một bản sao cũ không thể ghi đè lên một danh mục mới hơn.

Các triển khai Redis Cluster sử dụng các khóa danh mục an toàn theo slot và các thao tác cập nhật; không cần cài đặt MCP Redis riêng biệt. Xem [Quản lý máy chủ MCP](/docs/features/mcp#mcp-server-management) để biết về hành vi của danh mục động và khả năng sẵn sàng OAuth.
