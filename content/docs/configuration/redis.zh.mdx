## 基本设置 [#basic-setup]

### 启用 Redis [#enable-redis]

要在 LibreChat 中启用 Redis，请在您的 `.env` 文件中设置以下环境变量：

```bash
USE_REDIS=true
```

**重要提示**：当 `USE_REDIS=true` 时，您还必须提供 `REDIS_URI`。如果启用了 Redis 但未提供连接 URI，应用程序将抛出错误。

## 连接类型 [#connection-types]

### 单个 Redis 实例 [#single-redis-instance]

对于标准的单 Redis 服务器设置：

```bash
# Local Redis instance
REDIS_URI=redis://127.0.0.1:6379

# Remote Redis instance
REDIS_URI=redis://your-redis-host:6379
```

### Redis 集群 [#redis-cluster]

对于具有多个节点的 Redis 集群部署：

```bash
# Multiple Redis cluster nodes
REDIS_URI=redis://127.0.0.1:7001,redis://127.0.0.1:7002,redis://127.0.0.1:7003
```

当提供多个 URI 时，应用程序会自动检测集群模式。

如果您的 redis 集群只有一个 URI，您可以使用 `USE_REDIS_CLUSTER` 环境变量来启用集群模式：

```bash
# Redis cluster with single URI
REDIS_URI=redis://127.0.0.1:7001
USE_REDIS_CLUSTER=true
```

### 单一端点托管 Redis 服务 [#single-endpoint-managed-redis-services]

一些托管的 Redis 服务（包括 AWS ElastiCache Serverless 和 AWS 上的 Redis Enterprise Cloud）在内部进行键分片的同时，仅暴露一个连接 endpoint。在这种设置下，请保持 LibreChat 处于单节点连接模式，但如果缓存清除失败并出现 `CROSSSLOT Keys in request don't hash to the same slot` 错误，请启用集群安全删除（cluster-safe deletes）。

```bash
USE_REDIS=true
REDIS_URI=rediss://your-managed-redis-endpoint:6379
USE_REDIS_CLUSTER=false
REDIS_CLUSTER_SAFE_DELETE=true
```

`REDIS_CLUSTER_SAFE_DELETE=true` 会使 LibreChat 逐个删除匹配的缓存键，而不是发送多键 `DEL` 命令。这可以避免 `CROSSSLOT` 错误，且无需更改 LibreChat 连接 Redis 的方式。

仅当 LibreChat 需要创建 Redis Cluster 客户端时，才使用 `USE_REDIS_CLUSTER=true`。对于单端点托管服务，`REDIS_CLUSTER_SAFE_DELETE=true` 是更安全的选择。

### 使用 TLS/SSL 的 Redis [#redis-with-tlsssl]

对于安全的 Redis 连接：

```bash
# Redis with TLS encryption
REDIS_URI=rediss://127.0.0.1:6380

# Path to CA certificate for TLS verification
REDIS_CA=/path/to/ca-cert.pem
```

## 安全配置 [#security-configuration]

### 身份验证 [#authentication]

配置 Redis 身份验证凭据：

```bash
# Method 1: Include credentials in URI
# With both username and password
REDIS_URI=redis://myuser:mypassword@127.0.0.1:6379


# Method 2: Separate environment variables
REDIS_URI=redis://127.0.0.1:6379
REDIS_USERNAME=your_redis_username
REDIS_PASSWORD=your_redis_password
```

**注意**:`REDIS_URI` 中嵌入的凭据优先生效。仅当 URI 中未包含用户名或密码时,才会回退使用 `REDIS_USERNAME` 和 `REDIS_PASSWORD`。

### TLS 配置 [#tls-configuration]

对于加密连接：

```bash
# Enable TLS with rediss:// protocol
REDIS_URI=rediss://your-redis-host:6380

# Provide CA certificate for verification
REDIS_CA=/path/to/your/ca-certificate.pem
```

### 使用 Elasticache 的 TLS [#tls-with-elasticache]

Elasticache 可能需要为 TLS 连接使用备用的 dnsLookup。请参阅此网页上的“Special Note: Aws Elasticache Clusters with TLS”：https://www.npmjs.com/package/ioredis

```bash
# Enable redis alternate dnsLookup
REDIS_USE_ALTERNATIVE_DNS_LOOKUP=true
```

## 高级选项 [#advanced-options]

### 键前缀 (Key Prefixing) [#key-prefixing]

Redis key prefixing 通过在共享同一 Redis 服务器的不同环境、版本或实例之间隔离缓存数据，防止跨部署污染。这对于以下方面至关重要：

- **多租户部署**：分离暂存、生产和开发环境
- **蓝绿部署 (Blue-green deployments)**：隔离不同应用程序版本之间的缓存

```bash
# Option 1: Dynamic prefix from environment variable (recommended for cloud)

# Google Cloud Platform - Cloud Run
REDIS_KEY_PREFIX_VAR=K_REVISION

# AWS - ECS/Fargate
REDIS_KEY_PREFIX_VAR=AWS_EXECUTION_ENV

# Azure Container Instances
REDIS_KEY_PREFIX_VAR=CONTAINER_NAME

# Kubernetes - Pod name or deployment
REDIS_KEY_PREFIX_VAR=HOSTNAME
REDIS_KEY_PREFIX_VAR=POD_NAME

# Kubernetes - Custom deployment identifier
REDIS_KEY_PREFIX_VAR=DEPLOYMENT_ID

# Heroku
REDIS_KEY_PREFIX_VAR=DYNO

# Option 2: Static prefix (for manual control)
REDIS_KEY_PREFIX=librechat-prod-v2
REDIS_KEY_PREFIX=staging-branch-feature-x
REDIS_KEY_PREFIX=dev-john-local
```

**重要提示**：你不能同时设置 `REDIS_KEY_PREFIX_VAR` 和 `REDIS_KEY_PREFIX`。

**未添加前缀的污染示例**：

- 生产缓存被暂存部署覆盖
- 功能分支测试破坏了 main 分支缓存
- 旧部署版本提供过期的缓存数据

**键前缀格式**：

- IoRedis 客户端：`{prefix}::{key}`
- Keyv client: 由存储层处理

### 连接限制 [#connection-limits]

配置 Redis 连接限制：

```bash
# Maximum number of event listeners (default: 40)
REDIS_MAX_LISTENERS=40
```

### 连接保持 (Connection Keep-Alive) [#connection-keep-alive]

配置截止时间限制的 Redis 心跳检测和 TCP keepalive：

```bash
# Redis ping interval in seconds (default: 0 = disabled)
# When set to a positive integer (in seconds), Redis clients will ping the server at this interval
# When unset or 0, no pinging is performed (recommended for most use cases)
# Example: 300 = ping every 5 minutes
REDIS_PING_INTERVAL=300

# Maximum time an enabled heartbeat PING may go unanswered (default: 5000 ms)
REDIS_PING_TIMEOUT=5000

# Dedicated pub/sub subscriber heartbeat (default: 15 seconds, 0 = disabled)
REDIS_SUBSCRIBER_PING_INTERVAL=15

# TCP keepalive idle delay for ioredis sockets (default: 10000 ms, 0 = kernel default)
REDIS_KEEP_ALIVE=10000
```

**重要提示**：

- 设置 `REDIS_PING_INTERVAL=0` 或省略该项将完全禁用 ping。
- 仅在遇到连接超时问题时，才设置正数值（以秒为单位）。
- `REDIS_PING_INTERVAL` 以秒为单位指定，用于控制可选的 main ioredis 心跳检测。
- 专用 pub/sub 订阅者使用其各自默认开启的间隔，因为空闲的死套接字（dead socket）否则可能无法被检测到；设置 `REDIS_SUBSCRIBER_PING_INTERVAL=0` 可禁用该心跳检测。
- 每个启用的心跳都会使用 `REDIS_PING_TIMEOUT` 作为其响应截止时间，并在 PING 未得到响应时重新连接套接字。
- `REDIS_KEEP_ALIVE` 在应用层 PING 之外独立配置 ioredis TCP 套接字。
- 示例值：`300`（5 分钟），`600`（10 分钟），`60`（1 分钟）

### 副本故障转移恢复 [#replica-failover-recovery]

在 Sentinel 故障转移期间，降级的 Redis 副本可能会保持现有的套接字连接，同时通过 `READONLY` 拒绝写入。LibreChat 会在非集群 Keyv 客户端上检测到此响应，断开陈旧连接并重新连接，从而在无需重启应用程序的情况下解析出当前的主节点。

```bash
# Minimum interval between forced recovery attempts, in milliseconds
# Default: 5000
REDIS_READONLY_RECOVERY_INTERVAL=5000
```

该间隔会对突发写入失败期间的重连尝试进行去抖动处理。Redis Cluster 客户端不在此列，因为它们使用原生的集群拓扑和重定向处理机制。

### 健康检查 [#health-checks]

LibreChat 提供三个探针端点。只有 `/readyz` 会反映 Redis 的状态:

| 端点 | 返回 `200 OK` | 返回 `503 NOT_READY` |
| --- | --- | --- |
| `/livez` | 只要进程正在处理请求 | 从不 |
| `/health` | 只要进程正在处理请求 | 从不 |
| `/readyz` | 启动完成后,且在 `USE_REDIS=true` 时 Redis 已连接期间 | 启动完成前,或 Redis 已启用但未连接期间 |

当 Redis 重启、发生故障切换或无法连接的时间超过客户端的重试窗口时,依赖它的请求(登录、会话、速率限制)将会失败,直到连接恢复。在此期间,`/readyz` 返回 `503`,因此负载均衡器或 Kubernetes 就绪探针会停止向该实例转发流量。一旦 Redis 重新连接,它会恢复为 `200`,无需重启。启用 Redis 时,每个 Redis 客户端都必须处于连接状态;对于 Redis Cluster,这包括每个主节点。

将就绪检查指向 `/readyz`,存活检查指向 `/livez`。请勿将 Redis 纳入存活检查:如果存活探针在 Redis 故障期间失败,会导致所有 Pod 同时重启,而这并不能让 Redis 恢复正常。

```yaml
livenessProbe:
  httpGet:
    path: /livez
    port: 3080
readinessProbe:
  httpGet:
    path: /readyz
    port: 3080
  periodSeconds: 10
  failureThreshold: 3
```

`/readyz` 本身不会等待短暂的重连过程，因此需要使用 `failureThreshold` 来决定在多长时间的故障之后才会撤回流量。

### 选择性内存缓存 [#selective-in-memory-caching]

强制特定的缓存命名空间使用内存存储，即使在启用了 Redis 的情况下：

```bash
# Comma-separated list of cache keys
FORCED_IN_MEMORY_CACHE_NAMESPACES=CONFIG_STORE,APP_CONFIG,ROLES
```

未设置时,默认值为 `CONFIG_STORE,APP_CONFIG`,因此从 `librechat.yaml` 派生的配置会保留在每个容器内。设置此变量会**替换**默认值而不是追加到默认值之后,因此除非您希望将这些命名空间存储在 Redis 中,否则请在列表中包含 `CONFIG_STORE,APP_CONFIG`。将其设置为空字符串可将所有命名空间都路由到 Redis。

| `TOOLS` | 工具数据 |
| `MODELS_CONFIG` | 模型配置 |
| `MODEL_QUERIES` | 模型查询 |
| `STARTUP_CONFIG` | 启动配置 |
| `ENDPOINT_CONFIG` | 端点配置 |

| `REASONING_CAPABILITIES` | OpenRouter 端点中每个模型的推理强度 |

## 性能调优 [#performance-tuning]

### 连接保持 (Connection Keep-Alive) [#connection-keep-alive-1]

该应用程序实现了可配置的连接保持活跃（keep-alive）功能：

- Main-client PING 由 `REDIS_PING_INTERVAL` 控制，默认情况下处于禁用状态。
- 专用订阅者 PING 由 `REDIS_SUBSCRIBER_PING_INTERVAL` 控制，默认值为 15 秒
- Heartbeats 使用 `REDIS_PING_TIMEOUT` 来检测静默死连接并强制重新连接
- TCP keepalive 使用 `REDIS_KEEP_ALIVE`，独立于应用层心跳机制。
- 当断开连接或关闭事件发生时，Heartbeat 定时器会被清除。

### 缓存策略 [#cache-strategy]

该应用程序采用双客户端方法：

- **IoRedis client**: 主要的 Redis 操作，支持自动添加前缀
- **Keyv Redis 客户端**：`cacheFactory.js` 中带有前缀处理的存储层操作

### 高级连接调优 [#advanced-connection-tuning]

这些可选变量用于调整连接行为和批量缓存操作。默认值适用于大多数部署场景。

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `REDIS_CONNECT_TIMEOUT` | `10000` | 连接超时时间,单位为毫秒。 |
| `REDIS_RETRY_MAX_ATTEMPTS` | `10` | 放弃前的最大重连次数。`0` 表示无限重试。 |
| `REDIS_RETRY_MAX_DELAY` | `3000` | 两次重连尝试之间的最大延迟,单位为毫秒。 |
| `REDIS_ENABLE_OFFLINE_QUEUE` | `true` | 断开连接时将命令加入队列。设置为 `false` 则立即使命令失败。 |
| `REDIS_SCAN_COUNT` | `1000` | 按模式查找键时,`SCAN` 操作使用的 `COUNT` 提示值。 |
| `REDIS_DELETE_CHUNK_SIZE` | `1000` | 批量删除时每批删除的键数量。 |
| `MCP_REGISTRY_CACHE_TTL` | `5000` | MCP 注册表缓存的保留时间,单位为毫秒。跨实例的数据陈旧时间最长可达该值的两倍。`0` 表示禁用本地快照,因此每次读取都会访问 Redis。 |

### 内存优化 [#memory-optimization]

使用 `FORCED_IN_MEMORY_CACHE_NAMESPACES` 可以通过将频繁访问的小型数据集保留在内存中，同时对较大的缓存使用 Redis，从而优化性能。

## 可恢复流 (Resumable Streams) [#resumable-streams]

[Resumable Streams](/docs/features/resumable_streams) 会将每个进行中的响应保存在任务存储中，使客户端能够重新连接并获取已错过的内容。单个 LibreChat 实例将该存储保存在内存中，无需任何配置。当多个实例部署在负载均衡器之后时，重新连接的请求可能会到达与生成响应的实例不同的实例，因此必须通过 Redis 共享该存储。

当 `USE_REDIS=true` 时,流会自动使用 Redis。`USE_REDIS_STREAMS` 可以覆盖此行为:将其设置为 `false` 可在 Redis 负责缓存的同时将流保留在内存中;设置为 `true` 则可显式声明使用 Redis。

```bash filename=".env"
USE_REDIS=true
REDIS_URI=redis://127.0.0.1:6379

# Optional: defaults to the value of USE_REDIS
# USE_REDIS_STREAMS=true
```

使用 Redis 时,流式输出的分块会写入 Redis Streams,任务元数据写入哈希(hashes),实时事件通过 Pub/Sub 传递,因此任意实例都可以处理重连请求。

需要 Redis 流(Redis streams)的定时智能体运行,如果需要暂停等待工具审批或向用户提问,若未启用 Redis 流,这些运行将失败,并提示你设置 `USE_REDIS_STREAMS=true`。

### 生成协议兼容性 [#generation-protocol-compatibility]

当前的 LibreChat 客户端会自动与每个内置生成存储协商生成协议 v2。无需任何部署设置。现有的带有显式或已存储协议 v1 标记的生成内容，在通过引导、暂停/恢复、重试和恢复直至完成的过程中，将保持其不可变的 v1 行为。

对于滚动升级，每个正在运行的 API 和 worker 镜像都必须包含 v2 兼容性桥接：

- 每个 API 和 worker 镜像均运行 LibreChat `v0.8.8-rc1` 或更高版本。
- Helm chart `2.0.8` 或更高版本会选择一个兼容的默认镜像；自定义镜像覆盖仍必须满足上述镜像要求。

从旧版本升级时，请执行冷切换：在启动新镜像之前，停止所有旧的 API 和 worker 副本。这可以防止 v2 之前版本和自动 v2 版本的二进制文件在 Redis 中共享生成状态。

<Callout type="warning" title="滚动部署安全性">
  不要在与当前副本相同的 Redis 生成状态下运行早于 `v0.8.8-rc1` 的版本。在回滚到该兼容性基准以下之前，请先确保当前副本和 protocol-v2 生成已排空。
</Callout>

内存中生成流也会自动协商 v2 协议，且不会在进程间共享生成状态。

### 流式增量合并 (Stream Delta Coalescing) [#stream-delta-coalescing]

`STREAM_DELTA_COALESCE_MS` 将流式增量按时间窗口合并为 Redis 写入，以便在高 token 速率下减少网络往返。默认值为 `25`（毫秒），设为 `0` 时每个增量都会单独发布，且取值上限为 `1000`。窗口越大，投递延迟最多会增加一个窗口的时长；如果实例在增量仍处于缓冲状态时崩溃，这些增量将会丢失。建议将其保持在流平滑节奏（`streamRate`，默认 25 毫秒）或以下。单个数据块帧仍会与批次一同发布，因此不支持批次的订阅者可以继续正常工作。内存流不受影响。

```bash filename=".env"
STREAM_DELTA_COALESCE_MS=25
```

### 集群配置 [#cluster-configuration]

对于 Redis 集群部署,LibreChat 使用哈希标签(hash-tagged)键,以确保同一个流的所有键位于同一个集群槽位(cluster slot)中:

```bash
USE_REDIS=true
USE_REDIS_STREAMS=true
USE_REDIS_CLUSTER=true
REDIS_URI=redis://node1:7001,redis://node2:7002,redis://node3:7003
```

### 故障排除 [#troubleshooting]

如果在多实例部署中,重新连接后响应没有恢复,请检查每个实例的 `USE_REDIS` 和 `USE_REDIS_STREAMS` 值是否一致,并确认它们都能访问 Redis,例如在 LibreChat 主机上执行 `redis-cli ping`。

## MCP Catalog Coordination [#mcp-catalog-coordination]

当启用 Redis 时，LibreChat 会在各个副本之间协调应用层级的 MCP 工具目录。启动发布、重连同步以及 `notifications/tools/list_changed` 更新均使用生成和修订标记，以确保过时的副本不会覆盖较新的目录。

Redis Cluster 部署使用槽位安全的目录键和更新操作，无需单独的 MCP Redis 设置。有关动态目录和 OAuth 就绪行为，请参阅 [MCP 服务器配置](/docs/configuration/librechat_yaml/object_structure/mcp_servers#additional-information)。
