## Geral [#general]

![Usuários ativos no LibreChat](/images/metrics/librechat-metrics-active-users.png)

O LibreChat fornece duas superfícies de métricas compatíveis com Prometheus. O endpoint `/metrics` integrado da API relata o comportamento operacional, como a atividade do Redis e os resultados do proxy de telemetria do navegador. O exportador de banco de dados opcional relata dados de uso armazenados no MongoDB, incluindo totais de tokens e contagens de usuários ativos.

## Métricas de API Integradas [#built-in-api-metrics]

O LibreChat expõe métricas do Prometheus a partir do servidor da API em `/metrics`. Defina `METRICS_SECRET` e colete o endpoint com `Authorization: Bearer <METRICS_SECRET>`. O endpoint retorna `401` quando o segredo não está definido, o cabeçalho está ausente ou o token não corresponde.

```yaml filename="prometheus.yml"
scrape_configs:
  - job_name: librechat-api
    scheme: https
    metrics_path: /metrics
    authorization:
      type: Bearer
      credentials: your-metrics-secret
    static_configs:
      - targets: ['librechat.example.com']
```

### Métricas de Processo, HTTP e Requisições [#process-http-and-request-metrics]

O endpoint também expõe as métricas padrão do Node.js e do processo do `prom-client`, além das seguintes séries.

| Grupo | Métrica | Rótulos |
| --- | --- | --- |
| HTTP | `http_requests_total`, `http_request_duration_seconds` | `method`, `path`, `status` |
| HTTP | `http_requests_in_flight`, `http_request_body_bytes` (a partir de `Content-Length`) | `method`, `path` |
| SSE | `sse_streams_total`, `sse_stream_duration_seconds` | `method`, `path`, `status` |
| SSE | `sse_streams_in_flight` | `method`, `path` |
| Uploads | `upload_requests_total`, `upload_request_duration_seconds` | `method`, `path`, `status` |
| Uploads | `upload_requests_in_flight`, `upload_bytes_total` (a partir de `Content-Length`) | `method`, `path` |
| OpenID | `openid_user_lookup_total`, `openid_user_lookup_duration_seconds` | `result` |
| Mongoose | `mongoose_queries_total`, `mongoose_query_duration_seconds` | `model`, `operation`, `status` |
| Jobs de geração | `generation_jobs_total` | `store`, `result` |
| Jobs de geração | `generation_jobs_in_flight` | `store` |
| Streams de geração | `generation_stream_subscriptions_total` | `store`, `type`, `result` |
| Streams de geração | `generation_stream_resume_pending_events_total`, `generation_stream_early_buffer_overflows_total`, `generation_stream_first_attachment_delay_seconds` | `store` |
| Streams de geração | `generation_stream_attachment_outcomes_total` | `store`, `outcome` |
| Streams de geração | `generation_stream_recoveries_total`, `generation_stream_recovery_duration_seconds`, `generation_stream_recovery_events`, `generation_stream_recovery_content_parts` | `store`, `method`, `outcome` |
| Filtro de conteúdo | `content_filter_locator_traversal_failures_total` | `operation`, `reason` |
| Filtro de conteúdo | `content_filter_locator_traversal_size` | `operation`, `reason`, `dimension` |

As métricas de recuperação do stream de geração descrevem como um buffer de eventos iniciais que transbordou é reconstruído. As métricas do filtro de conteúdo contam as travessias incompletas do localizador de arquivos resolvido.

### Métricas de Inicialização do Agente [#agent-startup-metrics]

As solicitações iniciais de chat do Agent emitem duas métricas de inicialização:

- `agent_startup_milestone_duration_seconds{milestone}` mede a latência acumulada desde a entrada da solicitação até cada marco de inicialização.
- `agent_startups_total{result}` conta as tentativas de inicialização por resultado do terminal.

Os Milestones cobrem a admissão de solicitações, criação e reconhecimento de tarefas, carregamento de conversas e histórico, inicialização de cliente e execução, início de stream e o primeiro evento de resposta ou conteúdo na fila. Os resultados distinguem conteúdo na fila, conclusão sem um delta de conteúdo, desduplicação, rejeição, pausa, substituição, aborto e erro.

Quando o [rastreamento OpenTelemetry do backend](/docs/configuration/dotenv#opentelemetry-traces-and-logs) está habilitado, o span `librechat.agent.startup` registra os mesmos marcos como eventos. Ele inclui a duração total da inicialização, a quantidade de marcos, o resultado final e o ID do stream de geração, quando um for atribuído.

### Métricas do Redis [#redis-metrics]

Os caches e serviços baseados em Redis emitem duas métricas de operação lógica:

- `redis_operations_total{client,use_case,operation,status}` conta as operações.
- `redis_operation_duration_seconds{client,use_case,operation,status}` mede a latência.

`client` é `keyv` ou `ioredis`, e `status` é `success` ou `error`. Rótulos delimitados de `use_case` identificam trabalhos como caches, sessões, limites de taxa (rate limits), concorrência, principais de ACL, trabalhos de fluxo (stream) retomáveis e pub/sub, varreduras de registro MCP e eleição de líder. Essas métricas contam as operações lógicas do LibreChat em vez de cada ida e volta (round trip) interna do Redis. Pings de ciclo de vida de conexão e manutenção global são excluídos, e a limpeza de um namespace é contada como uma operação lógica.

Quando o [rastreamento OpenTelemetry do backend](/docs/configuration/dotenv#opentelemetry-traces-and-logs) está habilitado, cada span HTTP também resume seu trabalho com o Redis por meio de:

- `librechat.redis.calls`
- `librechat.redis.duration_ms`
- `librechat.redis.errors`
- `librechat.redis.max_call_ms`
- `librechat.redis.operations`
- `librechat.redis.use_cases`

Os dez casos de uso com a maior duração total também recebem os atributos `calls`, `duration_ms`, `errors` e `max_call_ms` sob `librechat.redis.<use_case>.*`. Este resumo em nível de requisição não requer spans do Redis em nível de comando; habilite `OTEL_IOREDIS_TRACING_ENABLED` apenas quando spans de comandos individuais forem necessários.

### Métricas de Proxy RUM do Navegador [#browser-rum-proxy-metrics]

Os resultados do proxy RUM do navegador são relatados como `rum_proxy_requests_total{endpoint,result}`. `endpoint` pode ser `traces`, `logs` ou `unknown`; `result` pode ser `success`, `auth_drop`, `auth_error`, `bad_request`, `not_configured`, `collector_4xx`, `collector_5xx`, `collector_error` ou `collector_timeout`.

### Métricas do Ator de Eventos do Agente [#agent-event-actor-metrics]

Eventos de Agente vinculados duráveis (Durable bound Agent Events) expõem métricas de recebimento e recuperação de baixa cardinalidade:

- `agent_event_actor_receipt_operations_total{operation,outcome,resolution}` contabiliza leituras de recibo, liquidação e backfill legado. `operation` é `read`, `settle` ou `backfill`; `outcome` é `hit`, `miss`, `success`, `replay` ou `conflict`.
- `agent_event_actor_receipts_retained{resolution}` relata recibos de reprodução retidos pela resolução `checkpoint_verified`, `action_compensated` ou `history_repaired`.
- `agent_event_actor_receipts_expiry_eligible` relata recibos retidos cujo TTL de 90 dias do MongoDB expirou, mas que ainda não foram removidos.
- `agent_event_actor_reconciliations_pending` relata marcadores de reconciliação ativos aguardando um recibo de terminal.
- `agent_event_actor_oldest_reconciliation_age_seconds` relata a idade da reconciliação ativa mais antiga.
- `agent_event_actor_deliveries{state}` relata linhas de entrega atualmente no estado `retry` ou `dead`.

Os medidores de armazenamento são coletados em scrapes autenticados e armazenados em cache por até 60 segundos. Configure alertas para idade de reconciliação sustentada, entregas inativas ou recibos elegíveis para expiração, em vez de um único scrape.

### Métricas de Shared-Link [#shared-link-metrics]

`share_link_rejections_total{operation,code}` conta falhas limitadas de criação ou atualização. `operation` é `create` ou `update`; `code` é `TARGET_MESSAGE_NOT_FOUND` quando o final da ramificação selecionada não está persistido, ou `NO_MESSAGES` quando a conversa não possui mensagens persistidas. A métrica não contém texto da conversa ou identidade do usuário.

## Exportador de Métricas do Banco de Dados [#database-metrics-exporter]

O exportador de métricas está disponível em [virtUOS/librechat_exporter](https://github.com/virtUOS/librechat_exporter).
É uma ferramenta separada que você implanta junto ao LibreChat.

### Configuração [#setup]

Para implantar o exporter, basta adicionar o container necessário à sua configuração do compose desta forma:

```yaml
services:
  metrics:
    image: ghcr.io/virtuos/librechat_exporter:main
    depends_on:
      - mongodb
    ports:
      - '8000:8000'
    restart: unless-stopped
```

Opcionalmente, você também pode configurar o exporter.
Mas, geralmente, os padrões devem ser suficientes.

```yaml
services:
  metrics:
    environment:
      - MONGODB_URI=mongodb://mongodb:27017/
      - LOGGING_LEVEL=info
```

### Uso [#usage]

Agora você pode adicionar o exporter à sua configuração de scrape do Prometheus:

```yaml
- job_name: librechat
  static_configs:
    - targets:
        - 'librechat.example.com:8000'
```

Assim que a coleta de métricas for iniciada, procure por métricas `librechat_*` (por exemplo, `librechat_registered_users`).
O exportador fornece várias métricas.

Divirta-se criando seu dashboard no Grafana!
