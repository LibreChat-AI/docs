### Geral [#general]

O LibreChat possui um sistema de log centralizado integrado ao seu backend (api).

- Com a instalação **Docker**, os arquivos de log são salvos em `/logs`

<FileTree>
  <FileTree.Folder name="librechat" defaultOpen>
    <FileTree.Folder name="logs" defaultOpen>
      <FileTree.File name="debug-2024-01-01.log" active />
      <FileTree.File name="error-2024-01-01.log" active />
      <FileTree.File name="meiliSync-2024-01-01.log" active />
    </FileTree.Folder>
  </FileTree.Folder>
</FileTree>

- Com a instalação via **npm**, os arquivos de log são salvos em `/api/logs`

<FileTree>
  <FileTree.Folder name="librechat" defaultOpen>
    <FileTree.Folder name="api" defaultOpen>
      <FileTree.Folder name="logs" defaultOpen>
        <FileTree.File name="debug-2024-01-01.log" active />
        <FileTree.File name="error-2024-01-01.log" active />
        <FileTree.File name="meiliSync-2024-01-01.log" active />
      </FileTree.Folder>
    </FileTree.Folder>
  </FileTree.Folder>
</FileTree>

Os registros de erro são salvos por padrão. Os arquivos de log de depuração são gravados somente quando `DEBUG_LOGGING=true`; o `.env.example` fornecido define essa variável como `true`, mas, se a variável não estiver definida, nenhum arquivo de depuração é criado.

Isso permite que você monitore seu servidor por meio de ferramentas externas que inspecionam arquivos de log, como **[o ELK stack](https://aws.amazon.com/what-is/elk-stack/)**.

Logs de depuração são essenciais para o trabalho de desenvolvimento e para a correção de problemas. Se você encontrar qualquer problema ao executar o LibreChat, reproduza-o o mais próximo possível e **[relate o problema](https://github.com/LibreChat-AI/LibreChat/issues)** com seus logs encontrados em `./api/logs/debug-%DATE%.log`.

Os logs de erros também são salvos no mesmo local: `./api/logs/error-%DATE%.log`. Se você tiver o meilisearch configurado, há um arquivo de log separado para isso também.

<Callout type="note" title="Nota:">
  Os arquivos de log são rotacionados diariamente: um novo arquivo é iniciado a cada dia, e um arquivo também é dividido ao atingir 20 MB. Os arquivos rotacionados são compactados com gzip e mantidos por 14 dias. Os erros também estão presentes nos arquivos de log de depuração, mas os arquivos de log de erro fornecem stack traces e mais detalhes.
</Callout>

### Configuração [#setup]

- Os arquivos de log de depuração são gravados somente quando esta variável é definida como `true`. Se ela não estiver definida ou tiver qualquer outro valor, nenhum arquivo de depuração é criado.

<OptionTable
  options={[['DEBUG_LOGGING', 'boolean', 'Gravar logs de depuração em arquivo. Necessário para que os arquivos de log de depuração sejam criados.', 'DEBUG_LOGGING=true']]}
/>

> Nota: recomenda-se manter os logs de depuração desativados em um ambiente de produção.

- Para uma saída detalhada do servidor no console/terminal, você pode definir o seguinte como `TRUE`:

<OptionTable
  options={[
    [
      'DEBUG_CONSOLE',
      'boolean',
      'Habilitar logs detalhados no console/stdout no mesmo formato dos logs de depuração de arquivo.',
      'DEBUG_CONSOLE=false',
    ],
  ]}
/>

Isso não é recomendado, no entanto, pois as saídas podem ser bastante verbosas. Está desativado por padrão e deve ser habilitado com moderação.

- Ao lidar com logs de console em implantações na nuvem (como GCP ou AWS), habilitar isso fará o dump dos logs com um carimbo de data/hora UTC e os formatará como JSON.

<OptionTable
  options={[
    [
      'CONSOLE_JSON',
      'boolean',
      'Habilite logs de console/stdout JSON detalhados, adequados para implantações em nuvem como GCP/AWS.',
      'CONSOLE_JSON=false',
    ],
  ]}
/>

Por padrão, o comprimento da string JSON é truncado para 255 caracteres. Você pode configurar isso com a seguinte variável de ambiente:

<OptionTable
  options={[
    [
      'CONSOLE_JSON_STRING_LENGTH',
      'number',
      'Configure o tamanho de truncamento para valores de string nos logs do console/stdout em JSON. Padrão: 255.',
      '# CONSOLE_JSON_STRING_LENGTH=255',
    ],
  ]}
/>

- A verbosidade do console pode ser definida com `CONSOLE_LOG_LEVEL` (`error`, `warn`, `info`, `http`, `verbose`, `debug`, `activity`, `silly` ou `silent`). `silent` desativa a saída no console sem desativar o registro em arquivo. Valores inválidos recorrem ao padrão, com um aviso.

<OptionTable
  options={[
    [
      'CONSOLE_LOG_LEVEL',
      'string',
      'Verbosidade do console. O padrão é info, ou debug quando DEBUG_CONSOLE=true; um valor explícito tem precedência.',
      '# CONSOLE_LOG_LEVEL=info',
    ],
  ]}
/>

- As mensagens de log de depuração são truncadas em 150 caracteres por padrão, e a redação de logs é limitada a 5000 valores por registro. Ajuste esses valores com `DEBUG_MESSAGE_LENGTH` e `LOG_REDACTION_MAX_NODES`.

<OptionTable
  options={[
    [
      'DEBUG_MESSAGE_LENGTH',
      'number',
      'Comprimento máximo de uma mensagem de log de depuração antes de ser truncada. Padrão: 150.',
      '# DEBUG_MESSAGE_LENGTH=150',
    ],
    [
      'LOG_REDACTION_MAX_NODES',
      'number',
      'Número máximo de valores que um registro de log pode ocultar antes de o restante ser substituído. Padrão: 5000.',
      '# LOG_REDACTION_MAX_NODES=5000',
    ],
  ]}
/>

- Para gravar os arquivos de log em um local diferente do padrão, defina `LIBRECHAT_LOG_DIR`. Consulte [Logging](/docs/configuration/dotenv#logging) na referência do `.env`.

- Os transportes de log baseados em arquivo estão habilitados por padrão. Defina `LOG_TO_FILE=false` se a sua implantação deve emitir logs apenas para stdout/stderr.

<OptionTable
  options={[
    [
      'LOG_TO_FILE',
      'boolean',
      'Defina como false para desativar os transportes Winston baseados em arquivo.',
      'LOG_TO_FILE=true',
    ],
  ]}
/>

### Rastreamento OpenTelemetry [#opentelemetry-tracing]

O LibreChat pode emitir traces de OpenTelemetry do backend para visibilidade de servidor, banco de dados, Redis e HTTP de saída. Os spans em nível de comando do Redis são opcionais, para que os traces padrão permaneçam em alto nível. Isso é separado do Langfuse, que continua sendo a opção recomendada para observabilidade de prompts e modelos específicos de GenAI.
