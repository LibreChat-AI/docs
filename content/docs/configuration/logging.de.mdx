### Allgemein [#general]

LibreChat verfügt über eine zentrale Protokollierung, die in das Backend (api) integriert ist.

- Bei der **Docker**-Installation werden Protokolldateien in `/logs` gespeichert.

<FileTree>
  <FileTree.Folder name="librechat" defaultOpen>
    <FileTree.Folder name="logs" defaultOpen>
      <FileTree.File name="debug-2024-01-01.log" active />
      <FileTree.File name="error-2024-01-01.log" active />
      <FileTree.File name="meiliSync-2024-01-01.log" active />
    </FileTree.Folder>
  </FileTree.Folder>
</FileTree>

- Bei der **npm**-Installation werden Protokolldateien unter `/api/logs` gespeichert.

<FileTree>
  <FileTree.Folder name="librechat" defaultOpen>
    <FileTree.Folder name="api" defaultOpen>
      <FileTree.Folder name="logs" defaultOpen>
        <FileTree.File name="debug-2024-01-01.log" active />
        <FileTree.File name="error-2024-01-01.log" active />
        <FileTree.File name="meiliSync-2024-01-01.log" active />
      </FileTree.Folder>
    </FileTree.Folder>
  </FileTree.Folder>
</FileTree>

Fehlerprotokolle werden standardmäßig gespeichert. Debug-Protokolldateien werden nur geschrieben, wenn `DEBUG_LOGGING=true` gesetzt ist; die mitgelieferte `.env.example` setzt diesen Wert auf `true`. Ist die Variable nicht gesetzt, wird jedoch keine Debug-Datei erstellt.

Dies ermöglicht es Ihnen, Ihren Server über externe Tools zu überwachen, die Protokolldateien untersuchen, wie zum Beispiel **[den ELK stack](https://aws.amazon.com/what-is/elk-stack/)**.

Debug-Logs sind für die Entwicklungsarbeit und die Fehlerbehebung unerlässlich. Wenn Sie bei der Ausführung von LibreChat auf Probleme stoßen, reproduzieren Sie diese so genau wie möglich und **[melden Sie das Problem](https://github.com/LibreChat-AI/LibreChat/issues)** unter Angabe Ihrer Logs, die Sie unter `./api/logs/debug-%DATE%.log` finden.

Fehlerprotokolle werden ebenfalls am selben Ort gespeichert: `./api/logs/error-%DATE%.log`. Wenn Sie Meilisearch konfiguriert haben, gibt es auch dafür eine separate Protokolldatei.

<Callout type="note" title="Hinweis:">
  Log-Dateien werden täglich rotiert: Jeden Tag wird eine neue Datei begonnen, und eine Datei wird außerdem aufgeteilt, sobald sie 20 MB erreicht. Rotierte Dateien werden mit gzip komprimiert und 14 Tage lang aufbewahrt. Fehler sind auch in den Debug-Log-Dateien enthalten, die Fehler-Log-Dateien liefern jedoch Stack-Traces und mehr Details.
</Callout>

### Einrichtung [#setup]

- Debug-Protokolldateien werden nur geschrieben, wenn diese Variable auf `true` gesetzt ist. Ist sie nicht gesetzt oder auf einen anderen Wert eingestellt, wird keine Debug-Datei erstellt.

<OptionTable
  options={[['DEBUG_LOGGING', 'boolean', 'Debug-Logs in eine Datei schreiben. Dies ist erforderlich, damit Debug-Logdateien erstellt werden.', 'DEBUG_LOGGING=true']]}
/>

> Hinweis: Es wird empfohlen, Debug-Protokolle in einer Produktionsumgebung deaktiviert zu lassen.

- Für eine ausführliche Server-Ausgabe in der Konsole/im Terminal können Sie Folgendes auf `TRUE` setzen:

<OptionTable
  options={[
    [
      'DEBUG_CONSOLE',
      'boolean',
      'Aktiviere ausführliche Konsolen-/stdout-Protokolle im gleichen Format wie Datei-Debug-Protokolle.',
      'DEBUG_CONSOLE=false',
    ],
  ]}
/>

Dies wird jedoch nicht empfohlen, da die Ausgaben recht ausführlich sein können. Es ist standardmäßig deaktiviert und sollte nur sparsam aktiviert werden.

- Wenn Sie Konsolenprotokolle in Cloud-Bereitstellungen (wie GCP oder AWS) verarbeiten, werden diese durch Aktivierung dieser Option mit einem UTC-Zeitstempel versehen und als JSON formatiert ausgegeben.

<OptionTable
  options={[
    [
      'CONSOLE_JSON',
      'boolean',
      'Aktiviere ausführliche JSON-Konsolen-/stdout-Protokolle, die für Cloud-Bereitstellungen wie GCP/AWS geeignet sind.',
      'CONSOLE_JSON=false',
    ],
  ]}
/>

Standardmäßig ist die Länge der JSON-Zeichenfolge auf 255 Zeichen begrenzt. Sie können dies mit der folgenden Umgebungsvariable konfigurieren:

<OptionTable
  options={[
    [
      'CONSOLE_JSON_STRING_LENGTH',
      'number',
      'Konfiguriere die Kürzungslänge für String-Werte in JSON-Konsolen-/stdout-Logs. Standard: 255.',
      '# CONSOLE_JSON_STRING_LENGTH=255',
    ],
  ]}
/>

- Die Ausführlichkeit der Konsolenausgabe kann mit `CONSOLE_LOG_LEVEL` festgelegt werden (`error`, `warn`, `info`, `http`, `verbose`, `debug`, `activity`, `silly` oder `silent`). `silent` schaltet die Konsolenausgabe ab, ohne die Protokollierung in Dateien zu deaktivieren. Ungültige Werte greifen auf den Standardwert zurück und es wird eine Warnung ausgegeben.

<OptionTable
  options={[
    [
      'CONSOLE_LOG_LEVEL',
      'string',
      'Konsolen-Ausführlichkeit. Standardmäßig info, oder debug, wenn DEBUG_CONSOLE=true gesetzt ist; ein explizit angegebener Wert hat Vorrang.',
      '# CONSOLE_LOG_LEVEL=info',
    ],
  ]}
/>

- Debug-Logmeldungen werden standardmäßig auf 150 Zeichen gekürzt, und die Protokollschwärzung ist auf 5000 Werte pro Eintrag begrenzt. Diese Werte können Sie mit `DEBUG_MESSAGE_LENGTH` und `LOG_REDACTION_MAX_NODES` anpassen.

<OptionTable
  options={[
    [
      'DEBUG_MESSAGE_LENGTH',
      'number',
      'Maximale Länge einer Debug-Log-Nachricht, bevor sie gekürzt wird. Standard: 150.',
      '# DEBUG_MESSAGE_LENGTH=150',
    ],
    [
      'LOG_REDACTION_MAX_NODES',
      'number',
      'Maximale Anzahl von Werten, die ein Protokolleintrag maskieren darf, bevor der Rest ersetzt wird. Standard: 5000.',
      '# LOG_REDACTION_MAX_NODES=5000',
    ],
  ]}
/>

- Um Protokolldateien an einem anderen Ort als dem Standardpfad zu speichern, setze `LIBRECHAT_LOG_DIR`. Siehe [Logging](/docs/configuration/dotenv#logging) in der `.env`-Referenz.

- Datei-basierte Log-Transports sind standardmäßig aktiviert. Setzen Sie `LOG_TO_FILE=false`, wenn Ihre Bereitstellung Logs nur an stdout/stderr ausgeben soll.

<OptionTable
  options={[
    [
      'LOG_TO_FILE',
      'boolean',
      'Auf false setzen, um dateibasierte Winston-Transports zu deaktivieren.',
      'LOG_TO_FILE=true',
    ],
  ]}
/>

### OpenTelemetry Tracing [#opentelemetry-tracing]

LibreChat kann Backend-OpenTelemetry-Traces für Server, Datenbank, Redis und ausgehende HTTP-Sichtbarkeit ausgeben. Redis-Spans auf Befehlsebene sind optional, sodass die Standard-Traces auf einer hohen Ebene bleiben. Dies ist unabhängig von Langfuse, das weiterhin die empfohlene Option für die Beobachtbarkeit von GenAI-spezifischen Prompts und Modellen bleibt.
