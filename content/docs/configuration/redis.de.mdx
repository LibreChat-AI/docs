Dieser Leitfaden beschreibt, wie Redis für Caching und Sitzungsspeicherung in LibreChat konfiguriert wird. Redis bietet deutliche Leistungsverbesserungen und ist **für horizontale Skalierung erforderlich**. Wenn Sie mehrere LibreChat-Instanzen hinter einem Load Balancer betreiben, sorgt Redis für einen konsistenten Zustand über alle Instanzen hinweg.

## Grundlegende Einrichtung [#basic-setup]

### Redis aktivieren [#enable-redis]

Um Redis in LibreChat zu aktivieren, setzen Sie die folgende Umgebungsvariable in Ihrer `.env` Datei:

```bash
USE_REDIS=true
```

**Wichtig**: Wenn `USE_REDIS=true` gesetzt ist, müssen Sie auch eine `REDIS_URI` angeben. Die Anwendung wird einen Fehler ausgeben, wenn Redis ohne eine Verbindungs-URI aktiviert wird.

## Verbindungstypen [#connection-types]

### Einzelne Redis-Instanz [#single-redis-instance]

Für eine standardmäßige Einzel-Redis-Server-Einrichtung:

```bash
# Local Redis instance
REDIS_URI=redis://127.0.0.1:6379

# Remote Redis instance
REDIS_URI=redis://your-redis-host:6379
```

### Redis Cluster [#redis-cluster]

Für Redis-Cluster-Bereitstellungen mit mehreren Knoten:

```bash
# Multiple Redis cluster nodes
REDIS_URI=redis://127.0.0.1:7001,redis://127.0.0.1:7002,redis://127.0.0.1:7003
```

Die Anwendung erkennt den Cluster-Modus automatisch, wenn mehrere URIs bereitgestellt werden.

Wenn Ihr Redis-Cluster nur über einen einzigen URI verfügt, können Sie die Umgebungsvariable `USE_REDIS_CLUSTER` verwenden, um den Clustermodus zu aktivieren:

```bash
# Redis cluster with single URI
REDIS_URI=redis://127.0.0.1:7001
USE_REDIS_CLUSTER=true
```

### Managed Redis-Dienste mit einem einzelnen Endpoint [#single-endpoint-managed-redis-services]

Einige verwaltete Redis-Dienste, einschließlich AWS ElastiCache Serverless und Redis Enterprise Cloud auf AWS, stellen einen einzelnen Verbindungs-endpoint bereit, während sie Schlüssel intern sharden. Behalten Sie in dieser Konfiguration LibreChat im Single-Node-Verbindungsmodus bei, aktivieren Sie jedoch cluster-sichere Löschvorgänge (cluster-safe deletes), falls Cache-Bereinigungen mit `CROSSSLOT Keys in request don't hash to the same slot` fehlschlagen.

```bash
USE_REDIS=true
REDIS_URI=rediss://your-managed-redis-endpoint:6379
USE_REDIS_CLUSTER=false
REDIS_CLUSTER_SAFE_DELETE=true
```

`REDIS_CLUSTER_SAFE_DELETE=true` veranlasst LibreChat dazu, übereinstimmende Cache-Schlüssel einzeln zu löschen, anstatt Multi-Key-`DEL`-Befehle zu senden. Dies vermeidet `CROSSSLOT`-Fehler, ohne die Art und Weise zu ändern, wie LibreChat eine Verbindung zu Redis herstellt.

Verwenden Sie `USE_REDIS_CLUSTER=true` nur, wenn LibreChat einen Redis Cluster-Client erstellen soll. Für verwaltete Dienste mit einem einzelnen endpoint ist `REDIS_CLUSTER_SAFE_DELETE=true` die sicherere Option.

### Redis mit TLS/SSL [#redis-with-tlsssl]

Für sichere Redis-Verbindungen:

```bash
# Redis with TLS encryption
REDIS_URI=rediss://127.0.0.1:6380

# Path to CA certificate for TLS verification
REDIS_CA=/path/to/ca-cert.pem
```

## Sicherheitskonfiguration [#security-configuration]

### Authentifizierung [#authentication]

Konfigurieren Sie die Redis-Authentifizierungsdaten:

```bash
# Method 1: Include credentials in URI
# With both username and password
REDIS_URI=redis://myuser:mypassword@127.0.0.1:6379


# Method 2: Separate environment variables
REDIS_URI=redis://127.0.0.1:6379
REDIS_USERNAME=your_redis_username
REDIS_PASSWORD=your_redis_password
```

**Hinweis**: Zugangsdaten, die in `REDIS_URI` enthalten sind, haben Vorrang. `REDIS_USERNAME` und `REDIS_PASSWORD` werden nur als Ersatzwerte verwendet, wenn die URI keinen Benutzernamen oder kein Passwort enthält.

### TLS-Konfiguration [#tls-configuration]

Für verschlüsselte Verbindungen:

```bash
# Enable TLS with rediss:// protocol
REDIS_URI=rediss://your-redis-host:6380

# Provide CA certificate for verification
REDIS_CA=/path/to/your/ca-certificate.pem
```

### TLS mit Elasticache [#tls-with-elasticache]

Elasticache erfordert möglicherweise ein alternatives dnsLookup für TLS-Verbindungen. Siehe „Special Note: Aws Elasticache Clusters with TLS“ auf dieser Webseite: https://www.npmjs.com/package/ioredis

```bash
# Enable redis alternate dnsLookup
REDIS_USE_ALTERNATIVE_DNS_LOOKUP=true
```

## Erweiterte Optionen [#advanced-options]

### Key Prefixing [#key-prefixing]

Das Redis-Key-Prefixing verhindert eine Kontamination zwischen verschiedenen Deployments, indem Cache-Daten zwischen unterschiedlichen Umgebungen, Versionen oder Instanzen, die denselben Redis-Server nutzen, isoliert werden. Dies ist unerlässlich für:

- **Multi-tenant-Bereitstellungen**: Separate Staging-, Produktions- und Entwicklungsumgebungen
- **Blue-green deployments**: Isolierung des Caches zwischen verschiedenen Anwendungsversionen

```bash
# Option 1: Dynamic prefix from environment variable (recommended for cloud)

# Google Cloud Platform - Cloud Run
REDIS_KEY_PREFIX_VAR=K_REVISION

# AWS - ECS/Fargate
REDIS_KEY_PREFIX_VAR=AWS_EXECUTION_ENV

# Azure Container Instances
REDIS_KEY_PREFIX_VAR=CONTAINER_NAME

# Kubernetes - Pod name or deployment
REDIS_KEY_PREFIX_VAR=HOSTNAME
REDIS_KEY_PREFIX_VAR=POD_NAME

# Kubernetes - Custom deployment identifier
REDIS_KEY_PREFIX_VAR=DEPLOYMENT_ID

# Heroku
REDIS_KEY_PREFIX_VAR=DYNO

# Option 2: Static prefix (for manual control)
REDIS_KEY_PREFIX=librechat-prod-v2
REDIS_KEY_PREFIX=staging-branch-feature-x
REDIS_KEY_PREFIX=dev-john-local
```

**Wichtig**: Sie können nicht gleichzeitig `REDIS_KEY_PREFIX_VAR` und `REDIS_KEY_PREFIX` festlegen.

**Beispiele für Kontamination ohne Präfix**:

- Produktions-Cache durch Staging-Deployment überschrieben
- Tests von Feature-Branches beschädigen den Cache des Main-Branches
- Alte Deployment-Versionen, die veraltete zwischengespeicherte Daten bereitstellen

**Format für Schlüsselpräfixe**:

- IoRedis-Client: `{prefix}::{key}`
- Keyv-Client: Wird von der Store-Ebene verarbeitet

### Verbindungslimits [#connection-limits]

Konfigurieren der Redis-Verbindungslimits:

```bash
# Maximum number of event listeners (default: 40)
REDIS_MAX_LISTENERS=40
```

### Connection Keep-Alive [#connection-keep-alive]

Konfigurieren Sie deadline-gebundene Redis-Heartbeats und TCP-Keepalive:

```bash
# Redis ping interval in seconds (default: 0 = disabled)
# When set to a positive integer (in seconds), Redis clients will ping the server at this interval
# When unset or 0, no pinging is performed (recommended for most use cases)
# Example: 300 = ping every 5 minutes
REDIS_PING_INTERVAL=300

# Maximum time an enabled heartbeat PING may go unanswered (default: 5000 ms)
REDIS_PING_TIMEOUT=5000

# Dedicated pub/sub subscriber heartbeat (default: 15 seconds, 0 = disabled)
REDIS_SUBSCRIBER_PING_INTERVAL=15

# TCP keepalive idle delay for ioredis sockets (default: 10000 ms, 0 = kernel default)
REDIS_KEEP_ALIVE=10000
```

**Wichtig**:

- Das Setzen von `REDIS_PING_INTERVAL=0` oder das Weglassen dieser Einstellung deaktiviert das Pingen vollständig.
- Setzen Sie nur dann einen positiven Wert (in Sekunden), wenn bei Ihnen Probleme mit Verbindungszeitüberschreitungen auftreten.
- `REDIS_PING_INTERVAL` wird in Sekunden angegeben und steuert den optionalen ioredis-Haupt-Heartbeat
- Dedizierte Pub/Sub-Abonnenten verwenden ihr eigenes standardmäßig aktiviertes Intervall, da ein inaktiver, toter Socket andernfalls unentdeckt bleiben könnte; setzen Sie `REDIS_SUBSCRIBER_PING_INTERVAL=0`, um diesen Heartbeat zu deaktivieren.
- Jeder aktivierte Heartbeat verwendet `REDIS_PING_TIMEOUT` als Antwortfrist und stellt die Socket-Verbindung wieder her, wenn ein PING unbeantwortet bleibt.
- `REDIS_KEEP_ALIVE` konfiguriert den ioredis TCP-Socket unabhängig von PINGs auf Anwendungsebene
- Beispielwerte: `300` (5 Minuten), `600` (10 Minuten), `60` (1 Minute)

### Wiederherstellung bei Replica-Failover [#replica-failover-recovery]

Während eines Sentinel-Failovers kann ein herabgestuftes Redis-Replikat einen bestehenden Socket offen halten, während es Schreibvorgänge mit `READONLY` ablehnt. LibreChat erkennt diese Antwort auf dem Nicht-Cluster-Keyv-Client, bricht die veraltete Verbindung ab und stellt sie neu her, sodass der aktuelle Primary aufgelöst werden kann, ohne die Anwendung neu zu starten.

```bash
# Minimum interval between forced recovery attempts, in milliseconds
# Default: 5000
REDIS_READONLY_RECOVERY_INTERVAL=5000
```

Das Intervall entprellt (debounces) Wiederverbindungsversuche während einer Häufung fehlgeschlagener Schreibvorgänge. Redis Cluster-Clients sind davon ausgenommen, da sie native Cluster-Topologie und Redirect-Handling verwenden.

### Health Checks [#health-checks]

LibreChat stellt drei Probe-Endpoints bereit. Nur `/readyz` spiegelt Redis wider:

| Endpunkt | Gibt `200 OK` zurück | Gibt `503 NOT_READY` zurück |
| --- | --- | --- |
| `/livez` | Immer dann, wenn der Prozess Anfragen bedient | Niemals |
| `/health` | Immer dann, wenn der Prozess Anfragen bedient | Niemals |
| `/readyz` | Nach Abschluss des Starts und, bei `USE_REDIS=true`, solange Redis verbunden ist | Vor Abschluss des Starts oder solange Redis aktiviert, aber nicht verbunden ist |

Wenn Redis neu gestartet wird, ein Failover durchführt oder länger als das Retry-Fenster des Clients nicht erreichbar ist, schlagen Anfragen, die davon abhängen (Anmeldung, Sitzungen, Ratenbegrenzungen), so lange fehl, bis die Verbindung wiederhergestellt ist. Während dieser Zeit liefert `/readyz` den Statuscode `503`, sodass ein Load Balancer oder eine Kubernetes-Readiness-Probe keinen Traffic mehr an die Instanz weiterleitet. Sobald Redis wieder verbunden ist, kehrt der Status ohne Neustart auf `200` zurück. Ist Redis aktiviert, müssen alle Redis-Clients verbunden sein; bei einem Redis Cluster gilt das für jeden Primary-Knoten.

Richte Bereitschaftsprüfungen (readiness checks) auf `/readyz` und Lebendigkeitsprüfungen (liveness checks) auf `/livez`. Nimm Redis nicht in die Lebendigkeitsprüfung auf: Eine Lebendigkeitsprüfung, die bei einem Redis-Ausfall fehlschlägt, startet alle Pods gleichzeitig neu und kann Redis dadurch nicht wieder in Betrieb nehmen.

```yaml
livenessProbe:
  httpGet:
    path: /livez
    port: 3080
readinessProbe:
  httpGet:
    path: /readyz
    port: 3080
  periodSeconds: 10
  failureThreshold: 3
```

`/readyz` wartet kurze Wiederverbindungen nicht von selbst ab, daher verwenden Sie `failureThreshold`, um festzulegen, wie lange ein Ausfall andauern darf, bevor der Traffic entzogen wird.

### Selektives In-Memory-Caching [#selective-in-memory-caching]

Erzwingt die Verwendung von In-Memory-Speicher für bestimmte Cache-Namespaces, selbst wenn Redis aktiviert ist:

```bash
# Comma-separated list of cache keys
FORCED_IN_MEMORY_CACHE_NAMESPACES=CONFIG_STORE,APP_CONFIG,ROLES
```

Wenn nicht gesetzt, ist der Standardwert `CONFIG_STORE,APP_CONFIG`, sodass die aus `librechat.yaml` abgeleitete Konfiguration pro Container erhalten bleibt. Das Setzen dieser Variable **ersetzt** den Standardwert, anstatt ihn zu ergänzen. Nimm deshalb `CONFIG_STORE,APP_CONFIG` in deine Liste auf, es sei denn, du möchtest diese Namespaces in Redis speichern. Setze den Wert auf eine leere Zeichenfolge, um jeden Namespace über Redis zu leiten.

## Performance-Optimierung [#performance-tuning]

### Connection Keep-Alive [#connection-keep-alive-1]

Die Anwendung implementiert ein konfigurierbares Connection Keep-Alive:

- Main-client PINGs werden durch `REDIS_PING_INTERVAL` gesteuert und sind standardmäßig deaktiviert.
- Dedizierte Abonnenten-PINGs werden durch `REDIS_SUBSCRIBER_PING_INTERVAL` gesteuert und sind standardmäßig auf 15 Sekunden eingestellt.
- Heartbeats verwenden `REDIS_PING_TIMEOUT`, um stumm unterbrochene Sockets zu erkennen und eine erneute Verbindung zu erzwingen.
- TCP-Keepalive verwendet `REDIS_KEEP_ALIVE`, unabhängig von Heartbeats auf Anwendungsebene.
- Heartbeat-Timer werden bei Trennungs- oder Schließungsereignissen gelöscht

### Cache-Strategie [#cache-strategy]

Die Anwendung verwendet einen Dual-Client-Ansatz:

- **IoRedis-Client**: Primäre Redis-Operationen mit automatischem Präfix
- **Keyv Redis-Client**: Speicher-Layer-Operationen mit Präfix-Handhabung in `cacheFactory.js`

### Erweiterte Verbindungseinstellungen [#advanced-connection-tuning]

Diese optionalen Variablen steuern das Verbindungsverhalten und die Massenoperationen des Caches. Die Standardwerte eignen sich für die meisten Bereitstellungen.

| Variable | Default | Beschreibung |
| --- | --- | --- |
| `REDIS_CONNECT_TIMEOUT` | `10000` | Verbindungszeitüberschreitung in Millisekunden. |
| `REDIS_RETRY_MAX_ATTEMPTS` | `10` | Maximale Anzahl an Wiederverbindungsversuchen, bevor aufgegeben wird. `0` wiederholt unbegrenzt. |
| `REDIS_RETRY_MAX_DELAY` | `3000` | Maximale Verzögerung zwischen Wiederverbindungsversuchen in Millisekunden. |
| `REDIS_ENABLE_OFFLINE_QUEUE` | `true` | Befehle während einer getrennten Verbindung in die Warteschlange stellen. Mit `false` schlagen sie sofort fehl. |
| `REDIS_SCAN_COUNT` | `1000` | `COUNT`-Hinweis für `SCAN`-Operationen beim Suchen von Schlüsseln nach Muster. |
| `REDIS_DELETE_CHUNK_SIZE` | `1000` | Anzahl der Schlüssel, die pro Batch bei Massenlöschungen gelöscht werden. |
| `MCP_REGISTRY_CACHE_TTL` | `5000` | Millisekunden, für die MCP-Registry-Caches vorgehalten werden. Die Veralterung zwischen Instanzen kann bis zum Doppelten dieses Wertes betragen. `0` deaktiviert den lokalen Snapshot, sodass jeder Lesezugriff an Redis geht. |

### Speicheroptimierung [#memory-optimization]

Verwenden Sie `FORCED_IN_MEMORY_CACHE_NAMESPACES`, um die Leistung zu optimieren, indem häufig abgerufene, kleine Datensätze im Arbeitsspeicher gehalten werden, während Redis für größere Caches genutzt wird.

## Fortsetzbare Streams [#resumable-streams]

Redis ermöglicht [Resumable Streams](/docs/features/resumable_streams) für horizontal skalierte Deployments. Wenn diese Funktion aktiviert ist, können sich KI-Antworten nahtlos über Serverinstanzen hinweg neu verbinden und fortsetzen.

**Wichtig:** Wenn `USE_REDIS=true` gesetzt ist, verwenden fortsetzbare Streams automatisch Redis für die instanzübergreifende Koordination. Dies ist die empfohlene Einrichtung für horizontal skalierte Bereitstellungen, bei denen Benutzer möglicherweise eine Verbindung zu verschiedenen Serverinstanzen herstellen.

**Hinweis:** Wenn Sie eine einzelne LibreChat-Instanz betreiben, ist Redis für fortsetzbare Streams in der Regel überdimensioniert; der integrierte In-Memory-Modus funktioniert problemlos. Redis wird unverzichtbar, wenn Sie mehrere LibreChat-Instanzen hinter einem Load Balancer betreiben, da die Wiederverbindung eines Benutzers auf einem anderen Server landen kann als der, auf dem der Stream gestartet wurde.

### Konfiguration [#configuration]

```bash
# Redis enabled = resumable streams automatically use Redis
USE_REDIS=true
REDIS_URI=redis://127.0.0.1:6379

# Optional: explicitly control resumable streams behavior
# USE_REDIS_STREAMS=true  # Enabled by default when USE_REDIS=true
```

### Kompatibilität des Generierungsprotokolls [#generation-protocol-compatibility]

Aktuelle LibreChat-Clients verhandeln das Generierungsprotokoll v2 automatisch mit jedem integrierten Generierungsspeicher. Es ist keine Bereitstellungseinstellung erforderlich. Bestehende Generierungen mit einer expliziten oder gespeicherten protocol-v1-Markierung behalten ihr unveränderliches v1-Verhalten durch Steuerung, Pause/Fortsetzen, Wiederholung und Wiederherstellung bei, bis sie abgeschlossen sind.

Für ein Rolling-Upgrade muss jedes laufende API- und Worker-Image die v2-Kompatibilitätsbrücke enthalten:

- Jedes API- und Worker-Image führt LibreChat `v0.8.8-rc1` oder neuer aus.
- Das Helm chart `2.0.8` oder neuer wählt ein kompatibles Standard-Image aus; eine benutzerdefinierte Image-Überschreibung muss dennoch die oben genannten Image-Anforderungen erfüllen.

Beim Upgrade von einer älteren Version führen Sie einen „Cold Handoff“ durch: Stoppen Sie jede alte API- und Worker-Replik, bevor Sie das neue Image starten. Dies verhindert, dass pre-v2- und automatic-v2-Binärdateien den Generierungsstatus in Redis gemeinsam nutzen.

<Callout type="warning" title="Sicherheit bei Rolling Deployments">
  Führen Sie keine Version aus, die älter als `v0.8.8-rc1` ist, während der gleiche Redis-Generierungsstatus wie bei aktuellen Replikaten verwendet wird. Bevor Sie ein Rollback unter diese Kompatibilitätsgrenze durchführen, stellen Sie sicher, dass die aktuellen Replikate und protocol-v2-Generierungen vollständig geleert (drained) wurden.
</Callout>

In-Memory-Generierungs-Streams handeln ebenfalls automatisch das Protokoll v2 aus und teilen den Generierungsstatus nicht prozessübergreifend.

### Stream Delta Coalescing [#stream-delta-coalescing]

Redis-gestützte Streams können Delta-Publikationen bündeln, um Redis-Skripte, Roundtrips und die CPU-Auslastung bei hohen Token-Raten zu reduzieren:

```bash filename=".env"
STREAM_DELTA_COALESCE_MS=25
```

Die Einstellung ist standardmäßig auf `25` Millisekunden gesetzt, wenn sie nicht konfiguriert ist. Setzen Sie sie explizit auf `0`, um das Coalescing zu deaktivieren; Werte über `1000` werden begrenzt. Batching kann bis zu einem konfigurierten Fenster an Übermittlungslatenz hinzufügen und kann den gepufferten Rest verlieren, wenn der Veröffentlichungsprozess beendet wird, bevor er geleert wurde. Einzelne Chunk-Frames bleiben aus Gründen der Protokollkompatibilität erhalten, daher reduziert diese Einstellung die Redis-Skript- und Round-Trip-Arbeit, ohne das Subscriber-Frame-Format zu ändern. In-Memory-Generierungs-Streams bleiben unverändert.

### Hauptvorteile (für horizontale Skalierung) [#key-benefits-for-horizontal-scaling]

- **Kontinuität über Instanzen hinweg**: Benutzer können eine Generierung auf einem Server starten und auf einem anderen fortsetzen
- **Rolling deployments**: Aktive Streams überstehen Server-Neustarts
- **Multi-tab-Synchronisierung**: Dieselbe Konversation wird in einer Load-Balanced-Umgebung über mehrere Browser-Tabs hinweg synchronisiert
- **Verbindungsstabilität**: Automatische Wiederverbindung, unabhängig davon, welcher Server die Anfrage bearbeitet

### Cluster-Konfiguration [#cluster-configuration]

Für Redis Cluster-Bereitstellungen verwendet LibreChat automatisch Hash-Tag-Schlüssel, um sicherzustellen, dass Stream-Operationen innerhalb desselben Cluster-Slots bleiben:

```bash
USE_REDIS=true
USE_REDIS_STREAMS=true
USE_REDIS_CLUSTER=true
REDIS_URI=redis://node1:7001,redis://node2:7002,redis://node3:7003
```

Weitere Details zu dieser Funktion finden Sie unter [Resumable Streams](/docs/features/resumable_streams).

## MCP-Katalog-Koordination [#mcp-catalog-coordination]

Wenn Redis aktiviert ist, koordiniert LibreChat anwendungsebene MCP-Tool-Kataloge über Replikate hinweg. Die Veröffentlichung beim Start, die Synchronisierung bei der Wiederverbindung und `notifications/tools/list_changed`-Aktualisierungen verwenden Generations- und Revisionsmarkierungen, sodass ein veraltetes Replikat keinen neueren Katalog überschreiben kann.

Redis-Cluster-Deployments verwenden slot-sichere Katalogschlüssel und Aktualisierungsoperationen; eine separate MCP-Redis-Einstellung ist nicht erforderlich. Informationen zum dynamischen Katalog und zur OAuth-Bereitschaft finden Sie unter [MCP Server Management](/docs/configuration/librechat_yaml/object_structure/mcp_servers#additional-information).
