虽然默认设置已为标准的 `docker` 安装提供了坚实的基础，但深入阅读本指南将揭示 LibreChat 的全部潜力。本指南旨在帮助您根据具体需求定制 LibreChat。了解如何调整语言模型的可用性、集成社交登录、管理自动审核系统等等。这一切都是为了让您能够掌控并微调 LibreChat，以获得最佳的用户体验。

值必须是非负的安全整数；无效值将被忽略。当同时启用标头超时和请求超时时，如果标头超时设置高于请求超时，LibreChat 会将其限制为请求超时值。Node 会在 30 秒的连接扫描中检查标头和请求是否过期，因此低于 `30000` 的值不会以精确的毫秒精度执行。Bun 目前接受这些设置但不强制执行；当 API 服务器在 Bun 下运行时，LibreChat 会记录一条警告。

### Trust proxy [#trust-proxy]

使用距离 Express 应用程序最多 n 跳的地址。
req.socket.remoteAddress 是第一跳，其余地址从右到左在 X-Forwarded-For 标头中查找。
值为 0 表示第一个不受信任的地址将是 req.socket.remoteAddress，即没有反向代理。
`TRUST_PROXY` 环境变量的默认值设置为 `1`。

有关此内容的更多信息，请参阅 [Express.js - trust proxy](https://expressjs.com/en/guide/behind-proxies.html)。

<OptionTable
  options={[['TRUST_PROXY', 'number', '指定跳数。', 'TRUST_PROXY=1']]}

### 受信任的租户标头 (Trusted Tenant Header) [#trusted-tenant-header]

`TRUST_TENANT_HEADER` 控制 LibreChat 是否在 `/oauth`、`/api/auth` 和 `/api/share` 路由树上接受身份验证前的 `X-Tenant-Id`。默认情况下该选项处于禁用状态；在禁用时，这些路由将忽略该标头。

<OptionTable
  options={[
    [
      'TRUST_TENANT_HEADER',
      'boolean',
      '在预认证路由上信任 X-Tenant-Id。仅在替换了客户端提供值的受信任代理后启用。',
      'TRUST_TENANT_HEADER=false',
    ],
  ]}
/>

<Callout type="warning" title="不要信任客户端提供的租户标头">
  仅当受信任的反向代理剥离了所有传入的 `X-Tenant-Id` 值并自行设置权威的租户 ID 时，才启用此设置。否则，不受信任的客户端可能会在身份验证之前选择所使用的租户上下文。当启用此设置时，LibreChat 会记录一条安全警告。
</Callout>

当启用 `TENANT_ISOLATION_STRICT` 但禁用 `TRUST_TENANT_HEADER` 时，LibreChat 会在启动时发出警告，提示预认证租户标头将被忽略。

### 凭据配置 [#credentials-configuration]

LibreChat 使用 `CREDS_KEY` 和 `CREDS_IV` 来加密存储在数据库中的受支持凭据。请为生产环境配置固定且唯一的值，并在每个副本中共享相同的值。

<OptionTable
  options={[
    [
      'CREDS_KEY',
      'string',
      '用于安全存储凭据的 32 字节密钥（64 个十六进制字符）。',
      'CREDS_KEY=',
    ],
    [
      'CREDS_IV',
      'string',
      '用于安全存储凭据的 16 字节 IV（32 个十六进制字符）。',
      'CREDS_IV=',
    ],
    [
      'LIBRECHAT_TEMP_CREDENTIALS_PATH',
      'string',
      '用于持久化自动生成的临时凭据的路径。默认为当前进程工作目录下的 `.env.temp`。',
      '# LIBRECHAT_TEMP_CREDENTIALS_PATH=/app/data/.env.temp',
    ],
  ]}
/>

当 `CREDS_KEY`、`CREDS_IV`、`JWT_SECRET` 或 `JWT_REFRESH_SECRET` 中的任何一个为空时，LibreChat 会首先从临时凭据文件中复用有效值。如果不存在，它将生成一个加密随机值，并以仅限所有者拥有的权限写入该文件。显式的环境变量值始终具有最高优先级。LibreChat 拒绝使用 `.env` 或 `.env.example` 作为生成的文件路径，以防止意外替换任一配置文件。

当 `JWT_SECRET` 或 `JWT_REFRESH_SECRET` 仍在使用已弃用的公开默认值时，LibreChat 也会拒绝启动，无论该值是来自环境变量还是临时凭据文件。请生成唯一的替代值，而不是将旧的示例密钥带入部署中。

捆绑的 Docker Compose 文件将 `/app/data/.env.temp` 持久化在 `librechat-data` 卷中，因此单个 Compose 部署可以在不更改这些生成值的情况下重启。如果该文件无法持久化，这些值将仅存在于进程本地，重启后会话或加密记录可能会变得无法访问。

<Callout type="warning" title="为生产环境设置永久值">
  临时生成是一种引导便利措施，而非凭据轮换系统。在生产环境使用前，请使用 [Credentials Generator](/toolkit/creds_generator) 生成永久值，将其存储在您的密钥管理器中，并为每个副本提供相同的值。更改已建立的密钥不会重新加密现有记录。LibreChat 会在数据库中记录凭据指纹，并在活动值发生偏移时发出警告；请勿通过覆盖该标记来代替受控迁移。
</Callout>

### 安全标头与内容安全策略 (Content Security Policy) [#security-headers-and-content-security-policy]

LibreChat 默认会发送基准的 HSTS、framing、content-type、opener、resource 和 referrer 标头。`SECURITY_HEADERS=false` 将禁用所有这些标头，同时也是全局 CSP 的关闭开关。

基于 Nonce 的 CSP 需要通过 `CSP_ENABLED=true` 单独启用，且默认处于仅报告模式。请先使用 `CSP_REPORT_ONLY=true`，检查违规情况，并在强制执行前仅添加您的部署所必需的源。当 CSP 处于活动状态时，SPA shell 始终会随 `Cache-Control: no-store` 一起发送，因此其每个响应的 nonce 无法从缓存中重复使用。

请参阅 [HTTP Security Headers](/docs/configuration/security_headers) 以获取所有基准和 CSP 变量、可接受的值、默认值、源列表覆盖以及部署指南。

      '如果同一文件夹中存在已上传图片的 gzip 版本，则启用对其的服务。',
      'ENABLE_IMAGE_OUTPUT_GZIP_SCAN=true',
    ],
    [
      'ENABLE_STATIC_ASSET_BROTLI',
      'boolean',
      '在可用时启用静态应用资源的预压缩 Brotli 版本服务。',
      'ENABLE_STATIC_ASSET_BROTLI=true',
    ],
  ]}
/>

**行为：**

为静态文件设置 [Cache-Control](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Cache-Control) 响应头。这些配置仅在 `NODE_ENV` 设置为 `production` 时生效。

- 取消注释 `STATIC_CACHE_MAX_AGE` 以更改静态文件的本地 `max-age`。默认设置为 2 天（172800 秒）。
- 取消注释 `STATIC_CACHE_S_MAX_AGE` 以设置共享缓存（CDN 和代理）的 `s-maxage`。默认设置为 1 天（86400 秒）。
- 取消注释 `DISABLE_COMPRESSION` 以禁用静态文件的压缩。默认情况下，压缩是启用的。
- 取消注释 `ENABLE_IMAGE_OUTPUT_GZIP_SCAN` 以启用对已压缩图像的扫描和提供服务功能，前提是这些图像已在同一文件夹中预先压缩，且具有相同的文件名及 .gz 扩展名。默认情况下，上传图像的 gzip 扫描功能处于禁用状态。
- 取消注释 `ENABLE_STATIC_ASSET_BROTLI` 以在存在预压缩的 `.br` 版本时，提供静态应用资源的预压缩版本。启用后，对于 API 提供的静态文件，Brotli 的优先级高于 gzip。

<Callout type="warning" title="警告">
  - 这仅影响由 API 服务器提供的静态文件，不适用于 _Firebase_、_NGINX_ 或任何其他配置。
</Callout>

❗**注意：** 此方法不能保证对所有搜索引擎都有效，且某些搜索引擎仍可能出于其他目的（例如缓存或归档）索引您的网站或网页。因此，您不应仅依赖此方法来保护网站或网页上的敏感或机密信息。

### 有状态代码解释器 endpoint [#stateful-code-interpreter-endpoint]

[`stateful_code_sessions`](/docs/configuration/librechat_yaml/object_structure/agents#capabilities) 处于高度实验性阶段，需要单独的 Code Interpreter 路由。请使用 `LIBRECHAT_CODE_BASEURL_STATEFUL` 配置默认路由，或在 [`endpoints.agents.statefulCodeSessions.environments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions) 下定义已命名的托管或附加后端。所选服务必须运行 `stateful` 配置文件；LibreChat 在发送有状态请求时会携带 `X-CodeAPI-Expected-Profile: stateful` 头部。

有状态请求永远不会回退到 `LIBRECHAT_CODE_BASEURL`。如果所选的命名环境不可用，或者既未配置命名默认值也未配置 `LIBRECHAT_CODE_BASEURL_STATEFUL`，LibreChat 将会停止 Agent 运行并抛出配置错误。无状态 Agent 将继续使用 `LIBRECHAT_CODE_BASEURL`，且这两种执行配置文件不会共享同一个实时工作区。

每个 Agent 都可以将其有状态工作区的作用域限定为已登录用户、用户与 Agent 共同作用域，或用户与对话共同作用域。有关设置和持久化限制，请参阅 [Stateful Code Sessions](/docs/features/code_interpreter#stateful-code-sessions)。

命名附加环境也可以通过 `pairing.allowPrincipalWorkers: true` 公开自助配对控制平面。授权用户可以在 **Settings > Code environments** 下管理这些绑定到所有者的 worker；仅配对条目不会取代 `LIBRECHAT_CODE_BASEURL_STATEFUL`，也不能作为部署默认值。

LibreChat 公开了一个经过身份验证的 Agent Events API；它不会公开未经身份验证的 webhook。API-key 身份验证、Remote Agents 权限、目标访问控制、幂等性以及专用的 Agent Event 速率限制共同保护了入口安全。基于 MongoDB 的排序通道、参与者邮箱、回执、租约、重试机制和死信队列支持跨副本的 worker 运行。有关行为和示例，请参阅 [Agent Event Delivery](/docs/features/agents#agent-event-delivery) 和 [Agents API - Agent Events](/docs/features/agents_api#agent-events)。

- 仅在每个副本都支持批处理帧后，才启用 `STREAM_DELTA_COALESCE_MS`。旧版订阅者会丢弃合并后的帧。请参阅 [Stream Delta Coalescing](/docs/configuration/redis#stream-delta-coalescing)。
- 对于 Redis Cluster 模式，请提供多个 URI：`redis://node1:7001,redis://node2:7002,redis://node3:7003`（集群模式会自动检测）。
- For single-endpoint managed Redis services that shard keys internally, keep `USE_REDIS_CLUSTER=false` and set `REDIS_CLUSTER_SAFE_DELETE=true` if cache clears fail with `CROSSSLOT` errors.
- `REDIS_READONLY_RECOVERY_INTERVAL` 会在故障转移导致打开的套接字连接到降级的只读副本后，对 Keyv 的重连尝试进行去抖动（debounce）处理。Redis Cluster 客户端则会使用其原生的拓扑处理机制。
- `REDIS_PING_INTERVAL` 用于控制主 ioredis 客户端上的可选心跳；专用的发布/订阅（pub/sub）订阅者使用 `REDIS_SUBSCRIBER_PING_INTERVAL`，以便检测处于空闲状态的死连接。两者均使用 `REDIS_PING_TIMEOUT` 作为响应截止时间，并在超时后进行重连。
- 对于 TLS 连接，请使用 `rediss://` 协议；如果您的 CA 不受公共信任，请设置 `REDIS_CA`。
- `REDIS_KEY_PREFIX_VAR` 和 `REDIS_KEY_PREFIX` 是互斥的。
- **AWS Elasticache 与 TLS**：Elasticache 在使用 TLS 连接时可能需要使用替代的 dnsLookup。如果在使用带有 TLS 的 Elasticache，请设置 `REDIS_USE_ALTERNATIVE_DNS_LOOKUP=true`。更多详细信息，请参阅 [ioredis documentation](https://www.npmjs.com/package/ioredis)。
