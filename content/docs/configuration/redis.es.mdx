Esta guía explica cómo configurar Redis para el almacenamiento en caché y de sesiones en LibreChat. Redis ofrece mejoras de rendimiento significativas y es **obligatorio para el escalado horizontal**. Si ejecutas varias instancias de LibreChat detrás de un balanceador de carga, Redis garantiza un estado coherente en todas las instancias.

## Configuración básica [#basic-setup]

### Habilitar Redis [#enable-redis]

Para habilitar Redis en LibreChat, configure la siguiente variable de entorno en su archivo `.env`:

```bash
USE_REDIS=true
```

**Importante**: Cuando `USE_REDIS=true`, también debe proporcionar una `REDIS_URI`. La aplicación lanzará un error si Redis está habilitado sin una URI de conexión.

## Tipos de conexión [#connection-types]

### Instancia única de Redis [#single-redis-instance]

Para una configuración estándar de un solo servidor Redis:

```bash
# Local Redis instance
REDIS_URI=redis://127.0.0.1:6379

# Remote Redis instance
REDIS_URI=redis://your-redis-host:6379
```

### Redis Cluster [#redis-cluster]

Para implementaciones de clúster de Redis con múltiples nodos:

```bash
# Multiple Redis cluster nodes
REDIS_URI=redis://127.0.0.1:7001,redis://127.0.0.1:7002,redis://127.0.0.1:7003
```

La aplicación detecta automáticamente el modo clúster cuando se proporcionan múltiples URIs.

Si tu clúster de Redis solo tiene una única URI, puedes usar la variable de entorno `USE_REDIS_CLUSTER` para habilitar el modo clúster:

```bash
# Redis cluster with single URI
REDIS_URI=redis://127.0.0.1:7001
USE_REDIS_CLUSTER=true
```

### Servicios de Redis gestionados de punto de conexión único [#single-endpoint-managed-redis-services]

Algunos servicios gestionados de Redis, incluidos AWS ElastiCache Serverless y Redis Enterprise Cloud en AWS, exponen un único endpoint de conexión mientras realizan el sharding de claves internamente. En esa configuración, mantenga LibreChat en modo de conexión de nodo único, pero habilite las eliminaciones seguras para clúster (cluster-safe deletes) si los borrados de caché fallan con `CROSSSLOT Keys in request don't hash to the same slot`.

```bash
USE_REDIS=true
REDIS_URI=rediss://your-managed-redis-endpoint:6379
USE_REDIS_CLUSTER=false
REDIS_CLUSTER_SAFE_DELETE=true
```

`REDIS_CLUSTER_SAFE_DELETE=true` hace que LibreChat elimine las claves de caché coincidentes una por una en lugar de enviar comandos `DEL` de múltiples claves. Esto evita errores `CROSSSLOT` sin cambiar la forma en que LibreChat se conecta a Redis.

Utilice `USE_REDIS_CLUSTER=true` solo cuando LibreChat deba crear un cliente de Redis Cluster. Para servicios gestionados de punto de conexión único, `REDIS_CLUSTER_SAFE_DELETE=true` es la opción más segura.

### Redis con TLS/SSL [#redis-with-tlsssl]

Para conexiones seguras a Redis:

```bash
# Redis with TLS encryption
REDIS_URI=rediss://127.0.0.1:6380

# Path to CA certificate for TLS verification
REDIS_CA=/path/to/ca-cert.pem
```

## Configuración de seguridad [#security-configuration]

### Autenticación [#authentication]

Configure las credenciales de autenticación de Redis:

```bash
# Method 1: Include credentials in URI
# With both username and password
REDIS_URI=redis://myuser:mypassword@127.0.0.1:6379


# Method 2: Separate environment variables
REDIS_URI=redis://127.0.0.1:6379
REDIS_USERNAME=your_redis_username
REDIS_PASSWORD=your_redis_password
```

**Nota**: Las credenciales incluidas en `REDIS_URI` tienen prioridad. `REDIS_USERNAME` y `REDIS_PASSWORD` solo se utilizan como alternativa cuando el URI no tiene nombre de usuario ni contraseña.

### Configuración de TLS [#tls-configuration]

Para conexiones cifradas:

```bash
# Enable TLS with rediss:// protocol
REDIS_URI=rediss://your-redis-host:6380

# Provide CA certificate for verification
REDIS_CA=/path/to/your/ca-certificate.pem
```

### TLS con Elasticache [#tls-with-elasticache]

Elasticache puede necesitar usar un dnsLookup alternativo para conexiones TLS. Consulta "Special Note: Aws Elasticache Clusters with TLS" en esta página web: https://www.npmjs.com/package/ioredis

```bash
# Enable redis alternate dnsLookup
REDIS_USE_ALTERNATIVE_DNS_LOOKUP=true
```

## Opciones avanzadas [#advanced-options]

### Prefijado de claves [#key-prefixing]

El prefijo de clave de Redis evita la contaminación entre despliegues al aislar los datos de caché entre diferentes entornos, versiones o instancias que comparten el mismo servidor Redis. Esto es esencial para:

- **Despliegues multi-inquilino**: Entornos separados de staging, producción y desarrollo
- **Despliegues azul-verde**: Aislar la caché entre diferentes versiones de la aplicación

```bash
# Option 1: Dynamic prefix from environment variable (recommended for cloud)

# Google Cloud Platform - Cloud Run
REDIS_KEY_PREFIX_VAR=K_REVISION

# AWS - ECS/Fargate
REDIS_KEY_PREFIX_VAR=AWS_EXECUTION_ENV

# Azure Container Instances
REDIS_KEY_PREFIX_VAR=CONTAINER_NAME

# Kubernetes - Pod name or deployment
REDIS_KEY_PREFIX_VAR=HOSTNAME
REDIS_KEY_PREFIX_VAR=POD_NAME

# Kubernetes - Custom deployment identifier
REDIS_KEY_PREFIX_VAR=DEPLOYMENT_ID

# Heroku
REDIS_KEY_PREFIX_VAR=DYNO

# Option 2: Static prefix (for manual control)
REDIS_KEY_PREFIX=librechat-prod-v2
REDIS_KEY_PREFIX=staging-branch-feature-x
REDIS_KEY_PREFIX=dev-john-local
```

**Importante**: No puede configurar `REDIS_KEY_PREFIX_VAR` y `REDIS_KEY_PREFIX` simultáneamente.

**Ejemplos de contaminación sin prefijos**:

- Caché de producción sobrescrita por el despliegue de staging
- Las pruebas de la rama de características corrompen la caché de la rama principal
- Versiones de despliegue antiguas que sirven datos en caché obsoletos

**Formato de prefijo de clave**:

- Cliente IoRedis: `{prefix}::{key}`
- Cliente Keyv: Gestionado por la capa de almacenamiento

### Límites de conexión [#connection-limits]

Configurar los límites de conexión de Redis:

```bash
# Maximum number of event listeners (default: 40)
REDIS_MAX_LISTENERS=40
```

### Connection Keep-Alive [#connection-keep-alive]

Configure los latidos (heartbeats) de Redis con límite de tiempo y el TCP keepalive:

```bash
# Redis ping interval in seconds (default: 0 = disabled)
# When set to a positive integer (in seconds), Redis clients will ping the server at this interval
# When unset or 0, no pinging is performed (recommended for most use cases)
# Example: 300 = ping every 5 minutes
REDIS_PING_INTERVAL=300

# Maximum time an enabled heartbeat PING may go unanswered (default: 5000 ms)
REDIS_PING_TIMEOUT=5000

# Dedicated pub/sub subscriber heartbeat (default: 15 seconds, 0 = disabled)
REDIS_SUBSCRIBER_PING_INTERVAL=15

# TCP keepalive idle delay for ioredis sockets (default: 10000 ms, 0 = kernel default)
REDIS_KEEP_ALIVE=10000
```

**Importante**:

- Configurar `REDIS_PING_INTERVAL=0` u omitirlo deshabilita el ping por completo
- Solo establezca un valor positivo (en segundos) si experimenta problemas de tiempo de espera de conexión.
- `REDIS_PING_INTERVAL` se especifica en segundos y controla el heartbeat opcional de ioredis principal
- Los suscriptores dedicados de pub/sub utilizan su propio intervalo predeterminado de activación porque, de lo contrario, un socket inactivo podría permanecer sin ser detectado; establezca `REDIS_SUBSCRIBER_PING_INTERVAL=0` para desactivar ese latido (heartbeat).
- Cada heartbeat habilitado utiliza `REDIS_PING_TIMEOUT` como fecha límite de respuesta y reconecta el socket cuando un PING permanece sin respuesta.
- `REDIS_KEEP_ALIVE` configura el socket TCP de ioredis independientemente de los PING a nivel de aplicación
- Valores de ejemplo: `300` (5 minutos), `600` (10 minutos), `60` (1 minuto)

### Recuperación de conmutación por error de réplica [#replica-failover-recovery]

Durante una conmutación por error de Sentinel, una réplica de Redis degradada puede mantener abierto un socket existente mientras rechaza escrituras con `READONLY`. LibreChat detecta esta respuesta en el cliente Keyv que no es de clúster, cierra la conexión obsoleta y se reconecta para que el primario actual pueda ser resuelto sin reiniciar la aplicación.

```bash
# Minimum interval between forced recovery attempts, in milliseconds
# Default: 5000
REDIS_READONLY_RECOVERY_INTERVAL=5000
```

El intervalo aplica *debounce* a los intentos de reconexión durante una ráfaga de escrituras fallidas. Los clientes de Redis Cluster están excluidos porque utilizan topología de clúster nativa y manejo de redirecciones.

### Verificaciones de estado [#health-checks]

LibreChat expone tres endpoints de sondeo. Solo `/readyz` refleja el estado de Redis:

| Endpoint | Devuelve `200 OK` | Devuelve `503 NOT_READY` |
| --- | --- | --- |
| `/livez` | Siempre que el proceso esté atendiendo solicitudes | Nunca |
| `/health` | Siempre que el proceso esté atendiendo solicitudes | Nunca |
| `/readyz` | Después de completar el inicio y, con `USE_REDIS=true`, mientras Redis esté conectado | Antes de completar el inicio, o mientras Redis esté habilitado pero desconectado |

Cuando Redis se reinicia, sufre una conmutación por error o queda inaccesible durante más tiempo que la ventana de reintentos del cliente, las solicitudes que dependen de él (inicio de sesión, sesiones, límites de frecuencia) fallan hasta que se restablece la conexión. Durante ese tiempo, `/readyz` responde `503`, de modo que un balanceador de carga o una sonda de disponibilidad de Kubernetes deja de enviar tráfico a la instancia. Vuelve a `200` en cuanto Redis se reconecta, sin necesidad de reiniciar. Con Redis habilitado, todos los clientes de Redis deben estar conectados; en el caso de un Redis Cluster, esto incluye a todos los nodos primarios.

Apunte las comprobaciones de disponibilidad (readiness) a `/readyz` y las comprobaciones de vida (liveness) a `/livez`. No incluya Redis en la comprobación de vida: una sonda de liveness que falla durante una caída de Redis reinicia todos los pods a la vez y no puede restablecer Redis.

```yaml
livenessProbe:
  httpGet:
    path: /livez
    port: 3080
readinessProbe:
  httpGet:
    path: /readyz
    port: 3080
  periodSeconds: 10
  failureThreshold: 3
```

`/readyz` no espera por sí solo a que se restablezcan las desconexiones breves, por lo que debes usar `failureThreshold` para decidir cuánto tiempo puede durar una interrupción antes de que se retire el tráfico.

### Almacenamiento en caché selectivo en memoria [#selective-in-memory-caching]

Forzar el uso de almacenamiento en memoria para espacios de nombres de caché específicos, incluso cuando Redis está habilitado:

```bash
# Comma-separated list of cache keys
FORCED_IN_MEMORY_CACHE_NAMESPACES=CONFIG_STORE,APP_CONFIG,ROLES
```

Cuando no está definida, el valor predeterminado es `CONFIG_STORE,APP_CONFIG`, de modo que la configuración derivada de `librechat.yaml` se mantiene por contenedor. Definir esta variable **reemplaza** el valor predeterminado en lugar de añadirse a él, por lo que debe incluir `CONFIG_STORE,APP_CONFIG` en su lista, a menos que desee que esos espacios de nombres se almacenen en Redis. Asígnele una cadena vacía para enviar todos los espacios de nombres a través de Redis.

Claves de caché válidas (del enum `CacheKeys` en `librechat-data-provider`):

| Clave | Descripción |
| --- | --- |
| `CONFIG_STORE` | Almacén de configuración |
| `TOOL_CACHE` | Caché de herramientas (plugins, herramientas MCP, definiciones de herramientas) |
| `ROLES` | Roles de usuario |
| `USER_PRINCIPALS` | Membresías de grupos utilizadas para resolver los principales de ACL |
| `PROMPT_GROUPS_ACCESS` | Conjuntos de IDs de acceso a grupos de prompts |
| `AGENT_LINKED_INSTRUCTIONS` | Instrucciones resueltas de los grupos de prompts vinculados a un agente |
| `SANDBOX_PREWARM` | Estado de precalentamiento del entorno de ejecución de código por conversación |
| `GEN_TITLE` | Títulos generados |
| `TOOLS` | Datos de herramientas |
| `MODELS_CONFIG` | Configuración de modelos |
| `MODEL_QUERIES` | Consultas de modelos |
| `STARTUP_CONFIG` | Configuración de inicio |
| `ENDPOINT_CONFIG` | Configuración de endpoints |
| `TOKEN_CONFIG` | Configuración de tokens |
| `REASONING_CAPABILITIES` | Esfuerzo de razonamiento por modelo para endpoints de OpenRouter |
| `PULL_REQUESTS` | Búsquedas de pull requests y períodos de espera por límites de tasa de GitHub |
| `APP_CONFIG` | Configuración de la aplicación |
| `ABORT_KEYS` | Claves de cancelación |
| `BANS` | Datos de baneos |
| `ENCODED_DOMAINS` | Dominios codificados |
| `AUDIO_RUNS` | Ejecuciones de procesamiento de audio |
| `MESSAGES` | Mensajes en curso |
| `FLOWS` | Estados de flujos en curso |

| `OPENID_EXCHANGED_TOKENS` | Tokens de OpenID intercambiados |
| `AUTH_USER_DOC` | Documentos de usuario autenticado en caché |
| `OPENID_SESSION` | Sesiones de OpenID |

<Callout type="warn" title="Claves no válidas">
  El uso de una clave no válida (por ejemplo, la obsoleta `STATIC_CONFIG`) provocará un error de inicio. Utilice únicamente las claves de la tabla anterior.
</Callout>

## Ajuste de rendimiento [#performance-tuning]

### Connection Keep-Alive [#connection-keep-alive-1]

La aplicación implementa una conexión keep-alive configurable:

- Los PINGs del cliente principal son controlados por `REDIS_PING_INTERVAL` y están desactivados de forma predeterminada.
- Los PINGs de suscriptor dedicados se controlan mediante `REDIS_SUBSCRIBER_PING_INTERVAL` y tienen un valor predeterminado de 15 segundos.
- Los Heartbeats utilizan `REDIS_PING_TIMEOUT` para detectar sockets muertos silenciosamente y forzar la reconexión
- TCP keepalive utiliza `REDIS_KEEP_ALIVE`, independientemente de los latidos (heartbeats) a nivel de aplicación
- Los temporizadores de heartbeat se borran en eventos de desconexión o cierre.

### Estrategia de caché [#cache-strategy]

La aplicación utiliza un enfoque de cliente dual:

- **Cliente IoRedis**: Operaciones principales de Redis con prefijado automático
- **Cliente Keyv Redis**: Operaciones de capa de almacenamiento con manejo de prefijos en `cacheFactory.js`

### Ajuste avanzado de la conexión [#advanced-connection-tuning]

Estas variables opcionales ajustan el comportamiento de las conexiones y las operaciones de caché masivas. Los valores predeterminados son adecuados para la mayoría de las implementaciones.

| Variable | Default | Descripción |
| --- | --- | --- |
| `REDIS_CONNECT_TIMEOUT` | `10000` | Tiempo de espera de conexión en milisegundos. |
| `REDIS_RETRY_MAX_ATTEMPTS` | `10` | Número máximo de intentos de reconexión antes de rendirse. `0` reintenta indefinidamente. |
| `REDIS_RETRY_MAX_DELAY` | `3000` | Retraso máximo entre intentos de reconexión, en milisegundos. |
| `REDIS_ENABLE_OFFLINE_QUEUE` | `true` | Pone en cola los comandos mientras está desconectado. Establézcalo en `false` para que fallen inmediatamente. |
| `REDIS_SCAN_COUNT` | `1000` | Sugerencia `COUNT` para las operaciones `SCAN` al buscar claves por patrón. |
| `REDIS_DELETE_CHUNK_SIZE` | `1000` | Número de claves eliminadas por lote en las eliminaciones masivas. |
| `MCP_REGISTRY_CACHE_TTL` | `5000` | Milisegundos durante los que se mantienen las cachés del registro MCP. La desactualización entre instancias puede llegar al doble de este valor. `0` desactiva la instantánea local, por lo que cada lectura va a Redis. |

### Optimización de memoria [#memory-optimization]

Utilice `FORCED_IN_MEMORY_CACHE_NAMESPACES` para optimizar el rendimiento manteniendo en memoria los conjuntos de datos pequeños a los que se accede con frecuencia, mientras utiliza Redis para cachés más grandes.

## Flujos reanudables [#resumable-streams]

Redis habilita [Resumable Streams](/docs/features/resumable_streams) para despliegues escalados horizontalmente. Cuando está habilitado, las respuestas de la IA pueden reconectarse y reanudarse sin problemas a través de instancias de servidor.

**Importante:** Cuando `USE_REDIS=true`, los flujos reanudables utilizan automáticamente Redis para la coordinación entre instancias. Esta es la configuración recomendada para implementaciones escaladas horizontalmente donde los usuarios podrían conectarse a diferentes instancias del servidor.

**Nota:** Si ejecutas una única instancia de LibreChat, Redis para los streams reanudables suele ser excesivo; el modo integrado en memoria funciona bien. Redis se vuelve esencial cuando tienes varias instancias de LibreChat detrás de un balanceador de carga, donde la reconexión de un usuario puede llegar a un servidor distinto del que inició el stream.

### Configuración [#configuration]

```bash
# Redis enabled = resumable streams automatically use Redis
USE_REDIS=true
REDIS_URI=redis://127.0.0.1:6379

# Optional: explicitly control resumable streams behavior
# USE_REDIS_STREAMS=true  # Enabled by default when USE_REDIS=true
```

### Compatibilidad del Protocolo de Generación [#generation-protocol-compatibility]

Los clientes de LibreChat actuales negocian el protocolo de generación v2 automáticamente con cada almacén de generación integrado. No se requiere ninguna configuración de despliegue. Las generaciones existentes con un marcador de protocolo v1 explícito o almacenado mantienen su comportamiento v1 inmutable a través de la dirección, pausa/reanudación, reintento y recuperación hasta que finalizan.

Para una actualización progresiva (rolling upgrade), cada imagen de API y worker en ejecución debe incluir el puente de compatibilidad v2:

- Cada imagen de API y worker ejecuta LibreChat `v0.8.8-rc1` o una versión más reciente.
- El Helm chart `2.0.8` o posterior selecciona una imagen predeterminada compatible; una anulación de imagen personalizada aún debe cumplir con el requisito de imagen anterior.

Al actualizar desde una versión anterior, realice una transferencia en frío: detenga cada réplica antigua de la API y del worker antes de iniciar la nueva imagen. Esto evita que los binarios pre-v2 y automatic-v2 compartan el estado de generación en Redis.

<Callout type="warning" title="Seguridad de despliegue continuo">
  No ejecute una versión anterior a `v0.8.8-rc1` con el mismo estado de generación de Redis que las réplicas actuales. Antes de revertir a una versión inferior a ese límite de compatibilidad, asegúrese primero de que las réplicas actuales y las generaciones de protocol-v2 se hayan vaciado.
</Callout>

Los flujos de generación en memoria también negocian el protocolo v2 automáticamente y no comparten el estado de generación entre procesos.

### Fusión de Delta de Flujo [#stream-delta-coalescing]

Los streams respaldados por Redis pueden procesar por lotes las publicaciones delta para reducir los scripts de Redis, los viajes de ida y vuelta y el uso de CPU a altas tasas de tokens:

```bash filename=".env"
STREAM_DELTA_COALESCE_MS=25
```

El ajuste tiene un valor predeterminado de `25` milisegundos cuando no se establece. Asígnelo explícitamente a `0` para desactivar la coalescencia; los valores superiores a `1000` se limitan. El procesamiento por lotes puede añadir hasta una ventana configurada de latencia de entrega y puede perder la cola almacenada en búfer si el proceso de publicación finaliza antes de vaciarse. Los marcos de fragmentos individuales se conservan para la compatibilidad del protocolo, por lo que este ajuste reduce el trabajo de los scripts de Redis y los viajes de ida y vuelta sin cambiar el formato del marco del suscriptor. Las transmisiones de generación en memoria no sufren cambios.

### Beneficios clave (para escalado horizontal) [#key-benefits-for-horizontal-scaling]

- **Continuidad entre instancias**: Los usuarios pueden iniciar una generación en un servidor y reanudarla en otro
- **Despliegues continuos**: Los flujos activos sobreviven a los reinicios del servidor
- **Sincronización multi-pestaña**: La misma conversación se sincroniza a través de múltiples pestañas del navegador en un entorno con balanceo de carga
- **Resiliencia de conexión**: Reconexión automática independientemente de qué servidor gestione la solicitud

### Configuración de clúster [#cluster-configuration]

Para implementaciones de Redis Cluster, LibreChat utiliza automáticamente claves con hash-tag para asegurar que las operaciones de stream permanezcan dentro del mismo slot del cluster:

```bash
USE_REDIS=true
USE_REDIS_STREAMS=true
USE_REDIS_CLUSTER=true
REDIS_URI=redis://node1:7001,redis://node2:7002,redis://node3:7003
```

Consulta [Resumable Streams](/docs/features/resumable_streams) para obtener más detalles sobre esta funcionalidad.

## Coordinación del catálogo MCP [#mcp-catalog-coordination]

Cuando Redis está habilitado, LibreChat coordina los catálogos de herramientas MCP a nivel de aplicación entre réplicas. La publicación al inicio, la sincronización de reconexión y las actualizaciones de `notifications/tools/list_changed` utilizan marcadores de generación y revisión para que una réplica obsoleta no pueda sobrescribir un catálogo más reciente.

Las implementaciones de Redis Cluster utilizan claves de catálogo seguras para ranuras (slot-safe) y operaciones de actualización; no se requiere una configuración de MCP Redis por separado. Consulta [MCP Server Management](/docs/features/mcp#mcp-server-management) para conocer el comportamiento del catálogo dinámico y la preparación para OAuth.
