## General [#general]

![Usuarios activos en LibreChat](/images/metrics/librechat-metrics-active-users.png)

LibreChat proporciona dos superficies de métricas compatibles con Prometheus. El endpoint `/metrics` integrado en la API informa sobre el comportamiento operativo, como la actividad de Redis y los resultados del proxy de telemetría del navegador. El exportador de base de datos opcional informa sobre los datos de uso almacenados en MongoDB, incluidos los totales de tokens y los recuentos de usuarios activos.

## Métricas de API integradas [#built-in-api-metrics]

LibreChat expone métricas de Prometheus desde el servidor de la API en `/metrics`. Configure `METRICS_SECRET` y realice el scrape del endpoint con `Authorization: Bearer <METRICS_SECRET>`. El endpoint devuelve `401` cuando el secreto no está configurado, falta el encabezado o el token no coincide.

```yaml filename="prometheus.yml"
scrape_configs:
  - job_name: librechat-api
    scheme: https
    metrics_path: /metrics
    authorization:
      type: Bearer
      credentials: your-metrics-secret
    static_configs:
      - targets: ['librechat.example.com']
```

### Métricas de proceso, HTTP y de solicitudes [#process-http-and-request-metrics]

El endpoint también expone las métricas predeterminadas de Node.js y de proceso de `prom-client`, además de las siguientes series.

| Grupo | Métrica | Etiquetas |
| --- | --- | --- |
| HTTP | `http_requests_total`, `http_request_duration_seconds` | `method`, `path`, `status` |
| HTTP | `http_requests_in_flight`, `http_request_body_bytes` (desde `Content-Length`) | `method`, `path` |
| SSE | `sse_streams_total`, `sse_stream_duration_seconds` | `method`, `path`, `status` |
| SSE | `sse_streams_in_flight` | `method`, `path` |
| Cargas | `upload_requests_total`, `upload_request_duration_seconds` | `method`, `path`, `status` |
| Cargas | `upload_requests_in_flight`, `upload_bytes_total` (desde `Content-Length`) | `method`, `path` |
| OpenID | `openid_user_lookup_total`, `openid_user_lookup_duration_seconds` | `result` |
| Mongoose | `mongoose_queries_total`, `mongoose_query_duration_seconds` | `model`, `operation`, `status` |
| Trabajos de generación | `generation_jobs_total` | `store`, `result` |
| Trabajos de generación | `generation_jobs_in_flight` | `store` |
| Streams de generación | `generation_stream_subscriptions_total` | `store`, `type`, `result` |
| Streams de generación | `generation_stream_resume_pending_events_total`, `generation_stream_early_buffer_overflows_total`, `generation_stream_first_attachment_delay_seconds` | `store` |
| Streams de generación | `generation_stream_attachment_outcomes_total` | `store`, `outcome` |
| Streams de generación | `generation_stream_recoveries_total`, `generation_stream_recovery_duration_seconds`, `generation_stream_recovery_events`, `generation_stream_recovery_content_parts` | `store`, `method`, `outcome` |
| Filtro de contenido | `content_filter_locator_traversal_failures_total` | `operation`, `reason` |
| Filtro de contenido | `content_filter_locator_traversal_size` | `operation`, `reason`, `dimension` |

Las métricas de recuperación del flujo de generación describen cómo se reconstruye un búfer de eventos tempranos que se desbordó. Las métricas del filtro de contenido cuentan los recorridos incompletos de localizadores de archivos resueltos.

### Métricas de inicio del agente [#agent-startup-metrics]

Las solicitudes iniciales de chat del agente emiten dos métricas de inicio:

- `agent_startup_milestone_duration_seconds{milestone}` mide la latencia acumulada desde la entrada de la solicitud hasta cada hito de inicio.
- `agent_startups_total{result}` cuenta los intentos de inicio por resultado terminal.

Los hitos cubren la admisión de solicitudes, la creación y el reconocimiento de trabajos, la carga de conversaciones e historial, la inicialización del cliente y la ejecución, el inicio del flujo y el primer evento de respuesta o contenido en cola. Los resultados distinguen entre contenido en cola, finalización sin un delta de contenido, deduplicación, rechazo, pausa, reemplazo, interrupción y error.

Cuando el [rastreo de OpenTelemetry del backend](/docs/configuration/dotenv#opentelemetry-traces-and-logs) está habilitado, el span `librechat.agent.startup` informa los mismos hitos como eventos. Incluye la duración total del inicio, el número de hitos, el resultado final y el ID del stream de generación cuando se asigna uno.

### Métricas de Redis [#redis-metrics]

Las cachés y servicios respaldados por Redis emiten dos métricas de operación lógica:

- `redis_operations_total{client,use_case,operation,status}` cuenta las operaciones.
- `redis_operation_duration_seconds{client,use_case,operation,status}` mide la latencia.

`client` es `keyv` o `ioredis`, y `status` es `success` o `error`. Las etiquetas `use_case` delimitadas identifican trabajos como cachés, sesiones, límites de tasa, concurrencia, principales de ACL, trabajos de flujo reanudables y pub/sub, escaneos de registro de MCP y elección de líder. Estas métricas cuentan las operaciones lógicas de LibreChat en lugar de cada viaje de ida y vuelta interno de Redis. Los pings del ciclo de vida de la conexión y el mantenimiento global están excluidos, y borrar un espacio de nombres se cuenta como una operación lógica.

Cuando el [rastreo de OpenTelemetry del backend](/docs/configuration/dotenv#opentelemetry-traces-and-logs) está habilitado, cada span HTTP también resume su trabajo con Redis mediante:

- `librechat.redis.calls`
- `librechat.redis.duration_ms`
- `librechat.redis.errors`
- `librechat.redis.max_call_ms`
- `librechat.redis.operations`
- `librechat.redis.use_cases`

Los diez casos de uso con la mayor duración total también reciben los atributos `calls`, `duration_ms`, `errors` y `max_call_ms` bajo `librechat.redis.<use_case>.*`. Este resumen a nivel de solicitud no requiere spans de Redis a nivel de comando; habilite `OTEL_IOREDIS_TRACING_ENABLED` solo cuando se necesiten spans de comandos individuales.

### Métricas de Proxy RUM del Navegador [#browser-rum-proxy-metrics]

Los resultados del proxy RUM del navegador se reportan como `rum_proxy_requests_total{endpoint,result}`. `endpoint` es `traces`, `logs` o `unknown`; `result` puede ser `success`, `auth_drop`, `auth_error`, `bad_request`, `not_configured`, `collector_4xx`, `collector_5xx`, `collector_error` o `collector_timeout`.

### Métricas del Actor de Eventos del Agente [#agent-event-actor-metrics]

Los Agent Events de enlace duradero exponen métricas de recepción y recuperación de baja cardinalidad:

- `agent_event_actor_receipt_operations_total{operation,outcome,resolution}` cuenta las lecturas de recibos, liquidaciones y backfill heredado. `operation` es `read`, `settle` o `backfill`; `outcome` es `hit`, `miss`, `success`, `replay` o `conflict`.
- `agent_event_actor_receipts_retained{resolution}` informa sobre los recibos de reproducción retenidos por la resolución `checkpoint_verified`, `action_compensated` o `history_repaired`.
- `agent_event_actor_receipts_expiry_eligible` informa sobre los recibos retenidos cuyo TTL de 90 días en MongoDB ha expirado pero que aún no han sido eliminados.
- `agent_event_actor_reconciliations_pending` informa sobre marcadores de reconciliación activos que esperan un recibo terminal.
- `agent_event_actor_oldest_reconciliation_age_seconds` informa sobre la antigüedad de la reconciliación activa más antigua.
- `agent_event_actor_deliveries{state}` informa sobre las filas de entrega que se encuentran actualmente en estado `retry` o `dead`.

Los indicadores de almacenamiento se recopilan en extracciones autenticadas y se almacenan en caché durante un máximo de 60 segundos. Configure alertas sobre la antigüedad de reconciliación sostenida, entregas fallidas o recibos elegibles para caducidad en lugar de una sola extracción.

### Métricas de enlaces compartidos [#shared-link-metrics]

`share_link_rejections_total{operation,code}` cuenta los fallos limitados de creación o actualización. `operation` es `create` o `update`; `code` es `TARGET_MESSAGE_NOT_FOUND` cuando el final de la rama seleccionada no está persistido, o `NO_MESSAGES` cuando la conversación no tiene mensajes persistidos. La métrica no contiene texto de la conversación ni identidad del usuario.

## Exportador de métricas de base de datos [#database-metrics-exporter]

El exportador de métricas está disponible en [virtUOS/librechat_exporter](https://github.com/virtUOS/librechat_exporter).
Es una herramienta independiente que se despliega junto a LibreChat.

### Configuración [#setup]

Para desplegar el exporter, simplemente añade el contenedor necesario a tu configuración de compose de la siguiente manera:

```yaml
services:
  metrics:
    image: ghcr.io/virtuos/librechat_exporter:main
    depends_on:
      - mongodb
    ports:
      - '8000:8000'
    restart: unless-stopped
```

Opcionalmente, también puede configurar el exporter.
Pero, por lo general, los valores predeterminados deberían ser suficientes.

```yaml
services:
  metrics:
    environment:
      - MONGODB_URI=mongodb://mongodb:27017/
      - LOGGING_LEVEL=info
```

### Uso [#usage]

Ahora puede agregar el exportador a su configuración de scrape de Prometheus:

```yaml
- job_name: librechat
  static_configs:
    - targets:
        - 'librechat.example.com:8000'
```

Una vez que el scraping de las métricas haya comenzado, busque las métricas `librechat_*` (por ejemplo, `librechat_registered_users`).
El exportador proporciona varias métricas.
