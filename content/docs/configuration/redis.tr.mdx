## Temel Kurulum [#basic-setup]

### Redis'i Etkinleştir [#enable-redis]

LibreChat'te Redis'i etkinleştirmek için `.env` dosyanızda aşağıdaki ortam değişkenini ayarlayın:

```bash
USE_REDIS=true
```

**Önemli**: `USE_REDIS=true` olduğunda, bir `REDIS_URI` da sağlamanız gerekir. Uygulama, bir bağlantı URI'si olmadan Redis etkinleştirilirse hata verecektir.

## Bağlantı Türleri [#connection-types]

### Tek Redis Örneği [#single-redis-instance]

Standart bir tekli Redis sunucusu kurulumu için:

```bash
# Local Redis instance
REDIS_URI=redis://127.0.0.1:6379

# Remote Redis instance
REDIS_URI=redis://your-redis-host:6379
```

### Redis Cluster [#redis-cluster]

Birden fazla düğüme sahip Redis kümesi dağıtımları için:

```bash
# Multiple Redis cluster nodes
REDIS_URI=redis://127.0.0.1:7001,redis://127.0.0.1:7002,redis://127.0.0.1:7003
```

Uygulama, birden fazla URI sağlandığında küme modunu otomatik olarak algılar.

Redis kümenizin yalnızca tek bir URI'si varsa, küme modunu etkinleştirmek için `USE_REDIS_CLUSTER` ortam değişkenini kullanabilirsiniz:

```bash
# Redis cluster with single URI
REDIS_URI=redis://127.0.0.1:7001
USE_REDIS_CLUSTER=true
```

### Tek Uç Noktalı Yönetilen Redis Hizmetleri [#single-endpoint-managed-redis-services]

AWS ElastiCache Serverless ve AWS üzerindeki Redis Enterprise Cloud dahil olmak üzere bazı yönetilen Redis hizmetleri, anahtarları dahili olarak parçalarken (sharding) tek bir bağlantı endpoint'i sunar. Bu kurulumda, LibreChat'i tek düğümlü (single-node) bağlantı modunda tutun, ancak önbellek temizleme işlemleri `CROSSSLOT Keys in request don't hash to the same slot` hatasıyla başarısız olursa küme güvenli (cluster-safe) silme işlemlerini etkinleştirin.

```bash
USE_REDIS=true
REDIS_URI=rediss://your-managed-redis-endpoint:6379
USE_REDIS_CLUSTER=false
REDIS_CLUSTER_SAFE_DELETE=true
```

`REDIS_CLUSTER_SAFE_DELETE=true`, LibreChat'in çoklu anahtar `DEL` komutları göndermek yerine eşleşen önbellek anahtarlarını tek tek silmesini sağlar. Bu, LibreChat'in Redis'e bağlanma şeklini değiştirmeden `CROSSSLOT` hatalarını önler.

Yalnızca LibreChat'in bir Redis Cluster istemcisi oluşturması gerektiğinde `USE_REDIS_CLUSTER=true` kullanın. Tek uç noktalı yönetilen hizmetler için `REDIS_CLUSTER_SAFE_DELETE=true` daha güvenli bir seçenektir.

### TLS/SSL ile Redis [#redis-with-tlsssl]

Güvenli Redis bağlantıları için:

```bash
# Redis with TLS encryption
REDIS_URI=rediss://127.0.0.1:6380

# Path to CA certificate for TLS verification
REDIS_CA=/path/to/ca-cert.pem
```

## Güvenlik Yapılandırması [#security-configuration]

### Kimlik Doğrulama [#authentication]

Redis kimlik doğrulama bilgilerini yapılandırın:

```bash
# Method 1: Include credentials in URI
# With both username and password
REDIS_URI=redis://myuser:mypassword@127.0.0.1:6379


# Method 2: Separate environment variables
REDIS_URI=redis://127.0.0.1:6379
REDIS_USERNAME=your_redis_username
REDIS_PASSWORD=your_redis_password
```

**Not**: `REDIS_URI` içinde gömülü kimlik bilgileri öncelikli olur. `REDIS_USERNAME` ve `REDIS_PASSWORD` yalnızca URI'de kullanıcı adı veya parola bulunmadığında yedek olarak kullanılır.

### TLS Yapılandırması [#tls-configuration]

Şifreli bağlantılar için:

```bash
# Enable TLS with rediss:// protocol
REDIS_URI=rediss://your-redis-host:6380

# Provide CA certificate for verification
REDIS_CA=/path/to/your/ca-certificate.pem
```

### Elasticache ile TLS [#tls-with-elasticache]

Elasticache, TLS bağlantıları için alternatif bir dnsLookup kullanma ihtiyacı duyabilir. Bu web sayfasındaki "Special Note: Aws Elasticache Clusters with TLS" bölümüne bakın: https://www.npmjs.com/package/ioredis

```bash
# Enable redis alternate dnsLookup
REDIS_USE_ALTERNATIVE_DNS_LOOKUP=true
```

## Gelişmiş Seçenekler [#advanced-options]

### Anahtar Önekleme (Key Prefixing) [#key-prefixing]

Redis anahtar önekleme (key prefixing), aynı Redis sunucusunu paylaşan farklı ortamlar, sürümler veya örnekler arasındaki önbellek verilerini izole ederek dağıtımlar arası kirlenmeyi önler. Bu, aşağıdakiler için gereklidir:

- **Çok kiracılı dağıtımlar**: Ayrı hazırlık (staging), üretim (production) ve geliştirme (development) ortamları
- **Blue-green deployments**: Farklı uygulama sürümleri arasında önbelleği yalıtın

```bash
# Option 1: Dynamic prefix from environment variable (recommended for cloud)

# Google Cloud Platform - Cloud Run
REDIS_KEY_PREFIX_VAR=K_REVISION

# AWS - ECS/Fargate
REDIS_KEY_PREFIX_VAR=AWS_EXECUTION_ENV

# Azure Container Instances
REDIS_KEY_PREFIX_VAR=CONTAINER_NAME

# Kubernetes - Pod name or deployment
REDIS_KEY_PREFIX_VAR=HOSTNAME
REDIS_KEY_PREFIX_VAR=POD_NAME

# Kubernetes - Custom deployment identifier
REDIS_KEY_PREFIX_VAR=DEPLOYMENT_ID

# Heroku
REDIS_KEY_PREFIX_VAR=DYNO

# Option 2: Static prefix (for manual control)
REDIS_KEY_PREFIX=librechat-prod-v2
REDIS_KEY_PREFIX=staging-branch-feature-x
REDIS_KEY_PREFIX=dev-john-local
```

**Önemli**: Hem `REDIS_KEY_PREFIX_VAR` hem de `REDIS_KEY_PREFIX` değişkenlerini aynı anda ayarlayamazsınız.

**Ön ek kullanılmadan kirlenme örnekleri**:

- Üretim önbelleği, hazırlık (staging) dağıtımı tarafından üzerine yazıldı
- Özellik dalı testleri ana dal önbelleğini bozuyor
- Eski önbelleğe alınmış verileri sunan eski dağıtım sürümleri

**Anahtar öneki formatı**:

- IoRedis istemcisi: `{prefix}::{key}`
- Keyv istemcisi: Depolama katmanı tarafından yönetilir

### Bağlantı Sınırları [#connection-limits]

Redis bağlantı sınırlarını yapılandırın:

```bash
# Maximum number of event listeners (default: 40)
REDIS_MAX_LISTENERS=40
```

### Connection Keep-Alive [#connection-keep-alive]

Süre sınırı olan Redis sinyallerini (heartbeats) ve TCP keepalive ayarlarını yapılandırın:

```bash
# Redis ping interval in seconds (default: 0 = disabled)
# When set to a positive integer (in seconds), Redis clients will ping the server at this interval
# When unset or 0, no pinging is performed (recommended for most use cases)
# Example: 300 = ping every 5 minutes
REDIS_PING_INTERVAL=300

# Maximum time an enabled heartbeat PING may go unanswered (default: 5000 ms)
REDIS_PING_TIMEOUT=5000

# Dedicated pub/sub subscriber heartbeat (default: 15 seconds, 0 = disabled)
REDIS_SUBSCRIBER_PING_INTERVAL=15

# TCP keepalive idle delay for ioredis sockets (default: 10000 ms, 0 = kernel default)
REDIS_KEEP_ALIVE=10000
```

**Önemli**:

- `REDIS_PING_INTERVAL=0` değerini ayarlamak veya bu değişkeni atlamak, ping işlemini tamamen devre dışı bırakır.
- Yalnızca bağlantı zaman aşımı sorunları yaşıyorsanız pozitif bir değer (saniye cinsinden) ayarlayın
- `REDIS_PING_INTERVAL` saniye cinsinden belirtilir ve isteğe bağlı ana ioredis sinyalini (heartbeat) kontrol eder
- Özel pub/sub aboneleri, boşta kalan bir ölü soketin aksi takdirde tespit edilememesi nedeniyle kendi varsayılan açık aralıklarını kullanırlar; bu sinyali (heartbeat) devre dışı bırakmak için `REDIS_SUBSCRIBER_PING_INTERVAL=0` olarak ayarlayın.
- Etkinleştirilen her heartbeat, yanıt son tarihi olarak `REDIS_PING_TIMEOUT` değerini kullanır ve bir PING yanıtsız kaldığında soketi yeniden bağlar.
- `REDIS_KEEP_ALIVE`, ioredis TCP soketini uygulama düzeyindeki PING'lerden bağımsız olarak yapılandırır
- Örnek değerler: `300` (5 dakika), `600` (10 dakika), `60` (1 dakika)

### Replica Failover Kurtarma [#replica-failover-recovery]

Bir Sentinel yük devretme (failover) sırasında, indirgenmiş bir Redis replikası, `READONLY` ile yazma işlemlerini reddederken mevcut bir soketi açık tutabilir. LibreChat, küme dışı (non-cluster) Keyv istemcisinde bu yanıtı algılar, eski bağlantıyı sonlandırır ve uygulamayı yeniden başlatmaya gerek kalmadan mevcut birincil (primary) sunucunun çözümlenebilmesi için yeniden bağlanır.

```bash
# Minimum interval between forced recovery attempts, in milliseconds
# Default: 5000
REDIS_READONLY_RECOVERY_INTERVAL=5000
```

Aralık, başarısız yazma işlemlerinin yoğun olduğu durumlarda yeniden bağlanma denemelerini geciktirir (debounce). Redis Cluster istemcileri, yerel küme topolojisini ve yönlendirme yönetimini kullandıkları için bu kapsamın dışındadır.

### Sağlık Kontrolleri [#health-checks]

LibreChat üç adet probe endpoint'i sunar. Yalnızca `/readyz` Redis durumunu yansıtır:

| Endpoint | `200 OK` döndürür | `503 NOT_READY` döndürür |
| --- | --- | --- |
| `/livez` | Süreç istekleri sunduğu sürece | Hiçbir zaman |
| `/health` | Süreç istekleri sunduğu sürece | Hiçbir zaman |
| `/readyz` | Başlatma tamamlandıktan sonra ve `USE_REDIS=true` ise, Redis bağlı olduğu sürece | Başlatma tamamlanmadan önce veya Redis etkin olmasına rağmen bağlantısı kesilmişken |

Redis yeniden başlatıldığında, arıza yaşadığında veya istemcinin yeniden deneme süresinden daha uzun bir süre erişilemez olduğunda, buna bağlı istekler (oturum açma, oturumlar, hız sınırları) bağlantı geri gelene kadar başarısız olur. Bu süre boyunca `/readyz` `503` yanıtı verir, bu nedenle bir yük dengeleyici veya Kubernetes hazırlık probu trafiği o örneğe yönlendirmeyi durdurur. Redis yeniden bağlandığı anda, yeniden başlatma gerekmeden `200` yanıtına geri döner. Redis etkinleştirildiğinde, her Redis istemcisinin bağlı olması gerekir; bir Redis Cluster için bu, her primary düğümü kapsar.

Hazır olma kontrollerini `/readyz` adresine, canlılık kontrollerini `/livez` adresine yönlendirin. Redis'i canlılık kontrolünün dışında tutun: Redis kesintisi sırasında başarısız olan bir canlılık probu tüm pod'ları aynı anda yeniden başlatır ve Redis'in geri gelmesini sağlayamaz.

```yaml
livenessProbe:
  httpGet:
    path: /livez
    port: 3080
readinessProbe:
  httpGet:
    path: /readyz
    port: 3080
  periodSeconds: 10
  failureThreshold: 3
```

`/readyz` kısa süreli yeniden bağlanmaları kendi başına beklemez; bu nedenle bir kesintinin ne kadar sürdüğünde trafiğin geri çekileceğine karar vermek için `failureThreshold` değerini kullanın.

### Seçici Bellek İçi Önbelleğe Alma [#selective-in-memory-caching]

Redis etkinleştirildiğinde bile belirli önbellek ad alanlarını bellek içi (in-memory) depolamayı kullanmaya zorlayın:

```bash
# Comma-separated list of cache keys
FORCED_IN_MEMORY_CACHE_NAMESPACES=CONFIG_STORE,APP_CONFIG,ROLES
```

Ayarlanmadığında varsayılan değer `CONFIG_STORE,APP_CONFIG` olur; böylece `librechat.yaml` dosyasından türetilen yapılandırma her konteyner için ayrı kalır. Bu değişkeni ayarlamak varsayılanı **değiştirir**, ona ekleme yapmaz. Bu nedenle, bu ad alanlarının Redis'te tutulmasını istemiyorsanız listenize `CONFIG_STORE,APP_CONFIG` değerini eklemeyi unutmayın. Tüm ad alanlarını Redis üzerinden yönlendirmek için değeri boş bir dize olarak ayarlayın.

## Performans Ayarı [#performance-tuning]

### Connection Keep-Alive [#connection-keep-alive-1]

Uygulama, yapılandırılabilir bağlantı canlı tutma (keep-alive) özelliğini uygular:

- Ana istemci PING'leri `REDIS_PING_INTERVAL` tarafından kontrol edilir ve varsayılan olarak devre dışıdır
- Özel abone PING'leri `REDIS_SUBSCRIBER_PING_INTERVAL` tarafından kontrol edilir ve varsayılan olarak 15 saniyedir.
- Heartbeats, sessizce ölü soketleri tespit etmek ve yeniden bağlanmaya zorlamak için `REDIS_PING_TIMEOUT` kullanır.
- TCP keepalive, uygulama düzeyi sinyallerden (heartbeats) bağımsız olarak `REDIS_KEEP_ALIVE` kullanır.
- Bağlantı kesilmesi veya kapatma olaylarında Heartbeat zamanlayıcıları temizlenir

### Önbellek Stratejisi [#cache-strategy]

Uygulama, ikili bir istemci yaklaşımı kullanır:

- **IoRedis istemcisi**: Otomatik önekleme ile birincil Redis işlemleri
- **Keyv Redis istemcisi**: `cacheFactory.js` içinde önek işleme ile depolama katmanı işlemleri

### Gelişmiş Bağlantı Ayarları [#advanced-connection-tuning]

Bu isteğe bağlı değişkenler bağlantı davranışını ve toplu önbellek işlemlerini ayarlar. Varsayılan değerler çoğu dağıtım için uygundur.

| Değişken | Varsayılan | Açıklama |
| --- | --- | --- |
| `REDIS_CONNECT_TIMEOUT` | `10000` | Milisaniye cinsinden bağlantı zaman aşımı. |
| `REDIS_RETRY_MAX_ATTEMPTS` | `10` | Pes etmeden önce yapılacak maksimum yeniden bağlanma denemesi sayısı. `0` değeri sınırsız yeniden deneme yapar. |
| `REDIS_RETRY_MAX_DELAY` | `3000` | Yeniden bağlanma denemeleri arasındaki maksimum gecikme, milisaniye cinsinden. |
| `REDIS_ENABLE_OFFLINE_QUEUE` | `true` | Bağlantı kesikken komutları kuyruğa alır. Komutların hemen başarısız olmasını sağlamak için `false` olarak ayarlayın. |
| `REDIS_SCAN_COUNT` | `1000` | Anahtarları desene göre ararken `SCAN` işlemleri için `COUNT` ipucu. |
| `REDIS_DELETE_CHUNK_SIZE` | `1000` | Toplu silme işlemlerinde her partide silinen anahtar sayısı. |
| `MCP_REGISTRY_CACHE_TTL` | `5000` | MCP kayıt defteri önbelleklerinin tutulduğu milisaniye süresi. Örnekler arası eski veri süresi bu değerin iki katına kadar ulaşabilir. `0` değeri yerel anlık görüntüyü devre dışı bırakır, böylece her okuma Redis'e gider. |

### Bellek Optimizasyonu [#memory-optimization]

Performansı optimize etmek için sık erişilen küçük veri kümelerini bellekte tutarken, daha büyük önbellekler için Redis kullanarak `FORCED_IN_MEMORY_CACHE_NAMESPACES` ayarını kullanın.

## Devam Ettirilebilir Akışlar [#resumable-streams]

Redis, yatay ölçekli dağıtımlar için [Resumable Streams](/docs/features/resumable_streams) özelliğini etkinleştirir. Etkinleştirildiğinde, yapay zeka yanıtları sunucu örnekleri arasında sorunsuz bir şekilde yeniden bağlanabilir ve kaldığı yerden devam edebilir.

**Önemli:** `USE_REDIS=true` olduğunda, devam ettirilebilir akışlar (resumable streams) örnekler arası koordinasyon için otomatik olarak Redis kullanır. Bu, kullanıcıların farklı sunucu örneklerine bağlanabileceği yatay ölçeklendirilmiş dağıtımlar için önerilen kurulumdur.

**Not:** Tek bir LibreChat örneği çalıştırıyorsanız, devam ettirilebilir akışlar için Redis genellikle gereksizdir; yerleşik bellek içi mod sorunsuz çalışır. Redis, birden fazla LibreChat örneğinin bir yük dengeleyicinin arkasında çalıştığı durumlarda zorunlu hale gelir; çünkü bir kullanıcının yeniden bağlanması, akışının başladığı sunucudan farklı bir sunucuya ulaşabilir.

### Yapılandırma [#configuration]

```bash
# Redis enabled = resumable streams automatically use Redis
USE_REDIS=true
REDIS_URI=redis://127.0.0.1:6379

# Optional: explicitly control resumable streams behavior
# USE_REDIS_STREAMS=true  # Enabled by default when USE_REDIS=true
```

### Generation Protocol Uyumluluğu [#generation-protocol-compatibility]

Mevcut LibreChat istemcileri, her yerleşik üretim deposuyla otomatik olarak v2 üretim protokolünü müzakere eder. Herhangi bir dağıtım ayarı gerekmez. Açık veya kayıtlı bir v1 protokol işaretine sahip mevcut üretimler, tamamlanana kadar yönlendirme, duraklatma/devam ettirme, yeniden deneme ve kurtarma işlemleri boyunca değişmez v1 davranışlarını korurlar.

Kademeli bir yükseltme için, çalışan her API ve worker imajı v2 uyumluluk köprüsünü içermelidir:

- Her API ve worker imajı, LibreChat `v0.8.8-rc1` veya daha yeni bir sürümünü çalıştırır.
- Helm chart `2.0.8` veya daha yeni sürümleri uyumlu bir varsayılan image seçer; özel bir image geçersiz kılma işlemi yine de yukarıdaki image gereksinimini karşılamalıdır.

Daha eski bir sürümden yükseltme yaparken soğuk bir devir teslim gerçekleştirin: yeni imajı başlatmadan önce her bir eski API ve worker kopyasını durdurun. Bu, v2 öncesi ve otomatik-v2 ikili dosyalarının Redis'teki nesil durumunu paylaşmasını önler.

<Callout type="warning" title="Kademeli dağıtım güvenliği">
  `v0.8.8-rc1` sürümünden daha eski bir sürümü, mevcut replikalarla aynı Redis nesil durumu üzerinde çalıştırmayın. Bu uyumluluk sınırının altına geri dönmeden önce, mevcut replikaların ve protocol-v2 nesillerinin boşaltıldığından (drained) emin olun.
</Callout>

Bellek içi (in-memory) üretim akışları da protokol v2'yi otomatik olarak müzakere eder ve üretim durumunu süreçler arasında paylaşmaz.

### Akış Delta Birleştirme (Stream Delta Coalescing) [#stream-delta-coalescing]

Redis destekli akışlar, yüksek token hızlarında Redis betiklerini, gidiş-dönüş sürelerini ve CPU kullanımını azaltmak için delta yayınlarını gruplayabilir:

```bash filename=".env"
STREAM_DELTA_COALESCE_MS=25
```

Ayar belirtilmediğinde varsayılan olarak `25` milisaniyedir. Birleştirmeyi (coalescing) devre dışı bırakmak için açıkça `0` olarak ayarlayın; `1000` üzerindeki değerler sınırlandırılır. Gruplama (batching), yapılandırılmış bir teslim gecikmesi penceresi kadar ek süre getirebilir ve yayınlama süreci temizlemeden önce sonlanırsa arabellekteki son kısmı kaybedebilir. Bireysel yığın çerçeveleri protokol uyumluluğu için korunur, bu nedenle bu ayar abone çerçeve biçimini değiştirmeden Redis betiği ve gidiş-dönüş iş yükünü azaltır. Bellek içi üretim akışları değişmeden kalır.

### Temel Avantajlar (Yatay Ölçeklendirme için) [#key-benefits-for-horizontal-scaling]

- **Örnekler arası süreklilik**: Kullanıcılar bir sunucuda oluşturma işlemini başlatıp diğerinde devam ettirebilirler
- **Kademeli dağıtımlar**: Aktif akışlar sunucu yeniden başlatmalarından etkilenmez
- **Çoklu sekme senkronizasyonu**: Aynı konuşma, yük dengelemeli bir ortamda birden fazla tarayıcı sekmesi arasında senkronize edilir
- **Bağlantı dayanıklılığı**: İsteği hangi sunucunun işlediğine bakılmaksızın otomatik yeniden bağlanma

### Küme Yapılandırması [#cluster-configuration]

Redis Cluster dağıtımları için LibreChat, akış işlemlerinin aynı küme yuvası (cluster slot) içinde kalmasını sağlamak amacıyla otomatik olarak hash-tag'li anahtarlar kullanır:

```bash
USE_REDIS=true
USE_REDIS_STREAMS=true
USE_REDIS_CLUSTER=true
REDIS_URI=redis://node1:7001,redis://node2:7002,redis://node3:7003
```

Bu özellik hakkında daha fazla bilgi için [Resumable Streams](/docs/features/resumable_streams) bölümüne bakın.

## MCP Katalog Koordinasyonu [#mcp-catalog-coordination]

Redis etkinleştirildiğinde, LibreChat uygulama düzeyindeki MCP araç kataloglarını replikalar arasında koordine eder. Başlangıç yayını, yeniden bağlanma senkronizasyonu ve `notifications/tools/list_changed` güncellemeleri, eski bir replikanın daha yeni bir kataloğun üzerine yazmasını önlemek için nesil ve revizyon işaretleyicilerini kullanır.

Redis Cluster dağıtımları, slot-safe katalog anahtarlarını ve güncelleme işlemlerini kullanır; ayrı bir MCP Redis ayarı gerekmez. Dinamik katalog ve OAuth hazırlık davranışı için [MCP Server Management](/docs/features/mcp#mcp-server-management) bölümüne bakın.
