[Langfuse](https://langfuse.com) é uma plataforma de observabilidade de LLM de código aberto que ajuda você a rastrear, monitorar e depurar suas aplicações de LLM. Ao integrar o Langfuse ao LibreChat, você obtém visibilidade total de suas conversas com IA.

## Pré-requisitos [#prerequisites]

Antes de começar, certifique-se de que você tem:

1. Uma instância do LibreChat em execução (veja [Quick Start](/docs/quick_start))
2. Uma conta Langfuse ([inscreva-se gratuitamente](https://cloud.langfuse.com))
3. Chaves de API do Langfuse nas configurações do seu projeto

## Configuração [#setup]

Escolha uma conexão no aplicativo ou credenciais gerenciadas pelo ambiente para uma implantação de locatário único (single-tenant). Credenciais de ambiente completas têm precedência.

### Conexão no Aplicativo [#in-app-connection]

Um administrador autorizado pode abrir **Settings → Langfuse**, escolher um destino aprovado, inserir as chaves pública e secreta do projeto e selecionar **Save & enable**. O LibreChat verifica ambas as chaves antes de salvar, registra o ID do projeto verificado, criptografa a chave secreta em repouso e retorna apenas uma visualização mascarada em leituras posteriores. Uma conexão salva pode ser ativada, desativada, testada novamente ou substituída sem expor seu segredo.

A configuração requer tanto `access:admin` quanto `manage:configs:langfuse` (ou as permissões amplas/de administrador correspondentes). Ela está disponível quando o rastreamento (tracing) está ativado e:

- Uma implantação de locatário único (single-tenant) não possui `LANGFUSE_PUBLIC_KEY` e `LANGFUSE_SECRET_KEY` simultaneamente.
- Uma implantação fanout tem um coletor habilitado e a exportação de tenant não está desabilitada pelo interruptor de emergência.

Não coloque uma `langfuse.secretKey` em texto simples diretamente no `librechat.yaml`; o runtime aceita o valor criptografado produzido por uma gravação de configuração autorizada. Use a página de Configurações para o fluxo de conexão normal.

A conexão salva pertence à configuração base. As substituições de configuração de função, grupo e usuário não podem substituir ou remover a seção `langfuse`.

### Exemplo de Configuração [#example-configuration]

```sh filename=".env"
# Langfuse Configuration
LANGFUSE_PUBLIC_KEY=pk-lf-***
LANGFUSE_SECRET_KEY=sk-lf-***
# LANGFUSE_PROJECT_ID=project-id
# LANGFUSE_SAMPLE_RATE=1

# 🇪🇺 EU Data Region
LANGFUSE_BASE_URL=https://cloud.langfuse.com

# 🇺🇸 US Data Region
# LANGFUSE_BASE_URL=https://us.cloud.langfuse.com
```

<Callout type="note" title="Langfuse auto-hospedado">
  Para instâncias do Langfuse auto-hospedadas, defina `LANGFUSE_BASE_URL` para sua URL personalizada (por exemplo, `http://localhost:3000` para desenvolvimento local).
</Callout>

Quando ambas as chaves de ambiente estão presentes, o LibreChat as utiliza para o projeto central e oculta **Settings → Langfuse**. `LANGFUSE_TRACING_ENABLED=false` ou `LANGFUSE_SAMPLE_RATE=0` desativa tanto os rastreamentos quanto as pontuações de feedback. A amostragem fracionária toma uma decisão determinística por rastreamento; rastreamentos não amostrados não recebem pontuações de feedback posteriores.

`LANGFUSE_BASE_URL` é a configuração de URL base canônica. Os nomes mais antigos `LANGFUSE_HOST` e `LANGFUSE_BASEURL` permanecem como aliases de compatibilidade, com `LANGFUSE_BASE_URL` tendo precedência quando mais de um estiver definido.

### Proxies e Gateways Autenticados [#authenticated-proxies-and-gateways]

Para uma instância do Langfuse auto-hospedada atrás do Cloudflare Access, oauth2-proxy ou outro gateway de autenticação, defina cabeçalhos de solicitação personalizados no nível de implantação no `librechat.yaml`:

```yaml filename="librechat.yaml"
langfuse:
  headers:
    CF-Access-Client-Id: '${CF_ACCESS_CLIENT_ID}'
    CF-Access-Client-Secret: '${CF_ACCESS_CLIENT_SECRET}'
```

O LibreChat aplica os cabeçalhos resolvidos a cada superfície direta do Langfuse: rastreamento e exportação de mídia, criação e exclusão de pontuação de feedback, busca de identidade de projeto e verificação de credenciais de administrador. A credencial `Authorization` do próprio Langfuse permanece autoritativa em solicitações REST. Os valores suportam interpolação `${ENV_VAR}`; variáveis não resolvidas, referências a segredos de infraestrutura protegidos, valores em branco e nomes de cabeçalho inválidos são descartados com um aviso. Os valores dos cabeçalhos são mascarados nos logs de inicialização e nas leituras de configuração do administrador, mas referências de ambiente ainda são recomendadas em vez de credenciais literais.

Estes cabeçalhos são de propriedade do operador e exclusivos do YAML. Eles não podem ser escritos através do Painel de Administração ou da API de configuração, armazenados no MongoDB ou preenchidos com espaços reservados `{{...}}` por usuário. O LibreChat os envia apenas quando a configuração resolve exatamente uma origem Langfuse. Com múltiplas origens centrais, de locatário ou de coletor, ele registra um aviso e não envia cabeçalhos personalizados, pois o mapa não pode selecionar um destinatário com segurança.

<Callout type="warning" title="Limitação de fanout">
  O coletor fanout atualmente encaminha apenas `Authorization` para destinos Langfuse de locatários.
  Cabeçalhos `langfuse.headers` personalizados podem autenticar a solicitação direta do LibreChat para um único coletor ou origem Langfuse, mas eles não autenticam a solicitação upstream do coletor para um destino de locatário atrás de outro proxy.
</Callout>

### Rastrear Identidade e Metadados do Usuário [#trace-user-identity-and-metadata]

Por padrão, os rastreamentos (traces) de Agentes usam o ID de usuário interno do LibreChat como o `userId` do Langfuse e não exportam metadados adicionais de usuário ou de solicitação. Os operadores de implantação podem escolher outro campo de usuário e permitir explicitamente metadados em `langfuse.trace`:

```yaml filename="librechat.yaml"
langfuse:
  trace:
    userIdField: email
    userMetadataFields: [email, username, role, provider]
    conversationMetadataFields: [conversationId, endpoint, model, modelLabel, spec]
```

`userIdField` aceita `id`, `email`, `username`, `name`, `openidId`, `samlId`, `ldapId`, `googleId`, `githubId`, `discordId`, `appleId` ou `facebookId`. Se o campo selecionado estiver ausente para um usuário, o ID interno permanece como o `userId` de rastreamento.

`userMetadataFields` aceita esses campos de identidade, além de `role` e `provider`. Os valores são exportados sob `librechat.user.<field>`. `conversationMetadataFields` aceita `conversationId`, `endpoint`, `endpointType`, `provider`, `model`, `modelLabel` e `spec`, que são mapeados para os atributos de rastreamento `librechat.conversation.id`, `librechat.endpoint`, `librechat.endpoint.type`, `librechat.provider`, `librechat.model`, `librechat.model.label` e `librechat.spec`.

Todos os três campos são opcionais e nenhum campo de metadados é exportado apenas por existir em um usuário ou solicitação. Trate e-mails, nomes de usuário, identidades de provedores, IDs de conversas e seleções de modelos como telemetria potencialmente sensível; adicione à lista de permissões (allowlist) apenas os campos que suas políticas de retenção e acesso do Langfuse permitirem.

## Tenant Fanout (Opcional) [#tenant-fanout-optional]

O fanout do Langfuse permite que uma implantação multi-tenant do LibreChat exporte cada trace elegível e sua mídia tanto para um projeto central do Langfuse quanto para um projeto específico do tenant. O recurso é opcional e adiciona um gateway, além de um coletor OpenTelemetry interno; o rastreamento padrão de projeto único mencionado acima permanece inalterado quando o fanout não está implantado.

O Fanout utiliza duas camadas de configuração:

- As variáveis de ambiente de implantação definem o projeto central, o gateway e os destinos de tenant permitidos na inicialização.
- **Settings → Langfuse** fornece o estado ativado do tenant, chave pública, chave secreta criptografada, ID do projeto verificado e um destino permitido. As chaves podem ser alteradas em tempo de execução sem reiniciar o gateway.

O Compose override incluído suporta os destinos Langfuse Cloud `eu`, `us` e `jp`:

```sh filename=".env"
LANGFUSE_BASE_URL=https://cloud.langfuse.com
LANGFUSE_FANOUT_CENTRAL_BASE_URL=https://cloud.langfuse.com
LANGFUSE_FANOUT_CENTRAL_AUTH_HEADER="Basic <base64-public-key-colon-secret-key>"
LANGFUSE_FANOUT_CENTRAL_MEDIA_UPLOAD_DISABLED=false
LANGFUSE_FANOUT_TENANT_DESTINATIONS="eu=https://cloud.langfuse.com,us=https://us.cloud.langfuse.com,jp=https://jp.cloud.langfuse.com"
LANGFUSE_FANOUT_TRACE_DESTINATION_KEYS=eu,us,jp
LANGFUSE_FANOUT_TENANT_EXPORT_DISABLED=false
```

Inicie a stack regular do Compose com o override de fanout:

```sh
docker compose -f docker-compose.yml -f docker-compose.langfuse-fanout.yml up -d
```

A substituição habilita `LANGFUSE_FANOUT_ENABLED`, aponta o LibreChat para o gateway e inicia os serviços de coletor e Redis privado. Para a stack implantada, combine `deploy-compose.yml` com `deploy-compose.langfuse-fanout.yml` em vez disso.

O gateway escuta na porta `:4318` por padrão. Implantações personalizadas podem substituir seu endereço de vinculação com `LANGFUSE_FANOUT_LISTEN_ADDR`; as configurações de Compose e Helm incluídas já roteiam a porta padrão do gateway.

### Implantação com Helm [#helm-deployment]

As substituições do Compose constroem o gateway localmente, mas o Kubernetes precisa de uma imagem disponível em um registro. A partir da raiz do repositório do LibreChat, construa e envie (push) o gateway antes de instalar o chart:

```sh
docker build \
  -f otel/langfuse-fanout/Dockerfile \
  -t registry.example.com/librechat-langfuse-fanout:<tag> .
docker push registry.example.com/librechat-langfuse-fanout:<tag>
```

Crie um Kubernetes Secret contendo o cabeçalho de autenticação Basic completo do Langfuse central. Seu valor é `Basic ` seguido pelas credenciais `<public-key>:<secret-key>` codificadas em base64:

```sh
kubectl create secret generic langfuse-central \
  --from-literal=LANGFUSE_FANOUT_CENTRAL_AUTH_HEADER='Basic <base64-public-key-colon-secret-key>'
```

Habilite o deployment fanout nos valores do Helm. Este exemplo utiliza o chart do Redis incluído; defina `langfuseFanout.redis.uri` ao utilizar um serviço Redis externo.

```yaml filename="values.yaml"
redis:
  enabled: true

langfuseFanout:
  enabled: true
  image:
    repository: registry.example.com/librechat-langfuse-fanout
    tag: '<tag>'
    pullPolicy: IfNotPresent
  central:
    baseUrl: https://cloud.langfuse.com
    authHeaderSecret:
      name: langfuse-central
      key: LANGFUSE_FANOUT_CENTRAL_AUTH_HEADER
  metrics:
    secret:
      name: librechat-metrics
      key: METRICS_SECRET
  tenant:
    destinations:
      eu:
        baseUrl: https://cloud.langfuse.com
      us:
        baseUrl: https://us.cloud.langfuse.com
      jp:
        baseUrl: https://jp.cloud.langfuse.com
  upstreamTimeout: 30s
  publicUrl: ''
  otelCollector:
    receiverEndpoint: 127.0.0.1:4319
  redis:
    uri: ''
    username: ''
    passwordSecret:
      name: ''
      key: REDIS_PASSWORD
    keyPrefix: langfuse-fanout
  memoryLimitMiB: 256
  memorySpikeLimitMiB: 64
  batchTimeout: 1s
  batchSendSize: 128
  metadataCardinalityLimit: 1000
```

O Secret de métricas é opcional, mas `/metrics` retorna `401` a menos que `langfuseFanout.metrics.secret` forneça um bearer token. Crie-o separadamente quando a coleta de métricas for necessária:

```sh
kubectl create secret generic librechat-metrics \
  --from-literal=METRICS_SECRET='<metrics-bearer-token>'
```

O gráfico renderiza um Deployment com um container de gateway na porta `4318` e um sidecar interno do OpenTelemetry Collector na porta `4319`; apenas o gateway é exposto pelo Service. Ele também injeta `LANGFUSE_FANOUT_ENABLED` e a `LANGFUSE_FANOUT_COLLECTOR_URL` interna no LibreChat, a menos que essas chaves já estejam definidas em `librechat.configEnv`.

O Redis armazena planos de upload de mídia de curta duração e de uso único, para que as solicitações de criação e upload possam alcançar diferentes réplicas de gateway. Para um serviço Redis externo autenticado, defina `langfuseFanout.redis.uri`, e opcionalmente `username` e `passwordSecret`; mantenha as credenciais fora da URI, pois a URI é renderizada diretamente no ambiente de Deployment. Com o chart do Redis incluído e a autenticação habilitada, forneça um Secret de senha compatível ou uma URI externa explicitamente autenticada.

Escale o fanout manualmente com `langfuseFanout.replicaCount`; o chart não cria um HPA para o fanout. As sondas de liveness e readiness usam `/healthz` e podem ser personalizadas em `langfuseFanout.livenessProbe` e `langfuseFanout.readinessProbe`.

Substituições de implantação adicionais incluem `langfuseFanout.service` para o tipo de Service, porta e anotações; `resources`, `podAnnotations` e `podLabels` para o Pod do gateway; e `otelCollector.image` e `otelCollector.resources` para o sidecar. Se você alterar `langfuseFanout.traceCollectorUrl` ou `otelCollector.receiverEndpoint`, mantenha ambos os valores apontando para o mesmo listener de coletor interno.

O objeto `langfuse` de nível superior armazenado contém `enabled`, `publicKey`, `secretKey` criptografada, `projectId` verificado, `secretKeyPreview` gerada pelo servidor e `destination`. Trate-o como uma configuração gerenciada por API: não envie campos de visualização ou payloads criptografados de volta como segredos. Os campos anteriores `displaySecretKey` e o `fanout.enabled` aninhado não são mais utilizados.

A exportação de tenant ocorre apenas quando o fanout e a URL do coletor estão habilitados, a conexão salva está habilitada com chaves válidas e o `destination` corresponde a um destino de inicialização permitido. Outros rastreamentos ainda podem fluir para o projeto central. Defina `LANGFUSE_FANOUT_TENANT_EXPORT_DISABLED=true` como um interruptor de emergência para interromper a exportação de rastreamento de tenant e pontuação de feedback, mantendo a exportação central; isso também oculta a configuração de conexão no aplicativo até que a exportação de tenant seja restaurada.

Defina `LANGFUSE_FANOUT_CENTRAL_MEDIA_UPLOAD_DISABLED=true` para impedir que o SDK do LibreChat crie uploads de mídia para rastreamentos (traces) de coletores centrais ou de fallback; os uploads de mídia roteados por tenant permanecem inalterados. Esta chave no lado da aplicação é distinta da `LANGFUSE_FANOUT_CENTRAL_MEDIA_EXPORT_DISABLED` no lado do gateway, que bloqueia o encaminhamento de mídia central após um upload chegar ao gateway.

Para o encaminhamento de mídia, o gateway de fanout aceita apenas destinos de upload HTTPS absolutos retornados pela autoridade Langfuse configurada e não segue redirecionamentos em solicitações `PUT` de upload. O armazenamento de objetos auto-hospedado, incluindo hosts MinIO privados, permanece suportado quando a URL de upload retornada utiliza HTTPS. Destinos de upload de mídia que utilizam HTTP simples ou que dependem de redirecionamento agora falham de forma segura (fail closed), enquanto a exportação de rastreamento (trace) continua independentemente.

O tráfego de rastreamento e mídia passa pelo gateway de fanout. As pontuações de feedback são enviadas diretamente do LibreChat: as pontuações centrais usam `LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY` e `LANGFUSE_BASE_URL`, enquanto as pontuações de tenant usam a configuração do aplicativo do tenant.

Consulte a [referência de implantação fanout do Langfuse](https://github.com/LibreChat-AI/LibreChat/blob/dev/otel/langfuse-fanout/README.md) para todas as variáveis de gateway, configuração de destino personalizado, métricas, escalonamento e comportamento do Redis.

### Exportar Diagnósticos [#export-diagnostics]

Cada solicitação rastreada registra atributos OpenTelemetry de baixa cardinalidade que explicam sua decisão de exportação de tenant:

- `librechat.tenant.id` identifica o contexto do tenant
- `librechat.langfuse.export_plan` é `central_only`, `tenant_fanout` ou `disabled`
- `librechat.langfuse.export_reason` é `configured`, `collector_unconfigured`, `destination_unconfigured`, `emergency_disabled`, `fanout_disabled`, `missing_credentials` ou `tenant_disabled`

O gateway também expõe `langfuse_fanout_trace_exports_total{destination,result,tenant_id}`. Um lote sem tenant usa `<unknown>`, um lote com múltiplos tenants usa `<multiple>` e um ID de tenant malformado usa `<invalid>`. O gateway retém no máximo 1.000 rótulos de tenant válidos distintos por processo e combina IDs posteriores sob `<overflow>`, limitando a cardinalidade da métrica; destinos não reconhecidos são registrados como `central` em vez de criar outro rótulo.

Alterações de conexão bem-sucedidas no aplicativo também gravam o evento estruturado `librechat.langfuse.connection.changed`. Ele inclui o tenant, o estado configurado e habilitado, o destino, o resultado da verificação, a alteração principal e a lista completa de campos alterados, sem registrar nenhuma chave. Use esses campos para distinguir um plano intencional apenas central ou desabilitado de uma configuração ausente de coletor, destino ou credencial.

## Reiniciar o LibreChat [#restart-librechat]

Após adicionar as variáveis de ambiente, reinicie sua instância do LibreChat para aplicar as alterações:

```sh
docker compose down
docker compose up -d
```

## Ver rastreamentos no Langfuse [#see-traces-in-langfuse]

### Visualizador de Rastreamento de Conversa [#conversation-trace-viewer]

Ative `interface.traceViewer.enabled: true` no `librechat.yaml` para permitir que os usuários inspecionem um rastreamento (trace) do Langfuse amostrado para sua própria conversa como um modelo de cascata de modelo e ferramenta (model-and-tool waterfall). Isso requer uma versão do Langfuse com a API de Observações v2. O visualizador não aparece para a conversa de outro usuário, rastreamentos não amostrados ou rastreamentos cuja identidade do usuário não utilize o ID de usuário interno do LibreChat.

Por padrão, a entrada, saída, metadados e nomes de ferramentas registrados permanecem ocultos. Defina `interface.traceViewer.showInputOutput: true` apenas quando os usuários puderem visualizar prompts do sistema, instruções de Agent e definições de ferramentas que podem aparecer nesses campos. Defina `interface.traceViewer.showToolNames: true` para exibir os nomes das ferramentas sem expor a entrada ou saída da ferramenta; isso requer leituras de observação adicionais do Langfuse, e apenas os nomes são retidos para a resposta. `maxRecords`, `maxContentLength`, `requestsPerMinute` e `requestTimeoutMs` limitam cada solicitação; consulte [Config v1.3.16](/changelog/config_v1.3.16) para seus valores padrão e intervalos.

Assim que o LibreChat for reiniciado com o Langfuse configurado, você verá um novo rastreamento para cada resposta de mensagem de chat na interface do Langfuse:

O LibreChat v0.8.8-rc2 atualiza a formatação de rastreamento (trace shaping) de agentes para usar os nomes de observação de tempo de execução `StandardGraph`, `MultiAgentGraph` e `AgentModelCall`, com chamadas de atividade e rótulos de raciocínio (reasoning-label) aninhadas sob o trabalho que descrevem. A entrada e a saída em nível de rastreamento também são representadas nas observações raiz. Revise os filtros, painéis e avaliações do Langfuse salvos que dependem dos nomes de observação anteriores ou dos campos de entrada/saída em nível de rastreamento.

![Exemplo de rastreamento do LibreChat](https://langfuse.com/images/cookbook/integration_librechat/librechat-example-trace.png)

[Link para o rastreamento na interface do Langfuse](https://cloud.langfuse.com/project/cloramnkj0002jz088vzn1ja4/traces/57b4aa20a258a2e9e2d1ce2e4eacb21c?observation=06f5341a68d723b1&timestamp=2026-02-04T13%3A02%3A54.248Z&traceId=57b4aa20a258a2e9e2d1ce2e4eacb21c)

Administradores com `access:admin` e `manage:configs:langfuse` podem abrir o detalhamento de **Context Usage** da conversa e selecionar **View session in Langfuse**. A mesma ação pode aparecer em uma conversa compartilhada para um administrador autenticado do mesmo tenant com acesso à configuração do Langfuse. Visualizadores de links públicos e comuns nunca a verão.

O link aparece apenas após a conclusão da geração e quando a conversa contém pelo menos um rastreamento amostrado enviado para a conexão Langfuse ativa no aplicativo. Ele aponta para o destino e projeto verificados dessa conexão; ele não é exibido para credenciais gerenciadas pelo ambiente, conexões desativadas, conversas excluídas da amostragem, visualizadores entre locatários ou usuários sem o acesso necessário.

## Pontuações de Feedback de Mensagem [#message-feedback-scores]

Quando o rastreamento do Langfuse está configurado, o LibreChat também envia o feedback da mensagem para o Langfuse como uma pontuação BOOLEAN `user-feedback` no rastreamento correspondente. Uma avaliação de "joinha" (positivo) é enviada como `1`, uma avaliação de "joinha para baixo" (negativo) é enviada como `0`, e qualquer tag de feedback ou comentário selecionado é incluído na pontuação. Limpar o feedback exclui a pontuação.

As pontuações de feedback incluem metadados de contexto da mensagem quando disponíveis, incluindo o ID da mensagem, ID da mensagem pai, ID da conversa/sessão, ID do usuário, endpoint, remetente, `isCreatedByUser`, contagem de tokens, classificação e tag de feedback. Valores de metadados vazios são omitidos antes que a pontuação seja enviada.

As pontuações de feedback só são produzidas quando os botões de feedback estão disponíveis. Definir [`interface.feedback`](/docs/configuration/librechat_yaml/object_structure/interface#feedback) como `false` oculta os botões e rejeita gravações de feedback, portanto, nenhuma pontuação chega ao Langfuse.

As pontuações de feedback usam as mesmas credenciais e URL base do Langfuse que o rastreamento (tracing). Elas também respeitam `LANGFUSE_TRACING_ENABLED=false`, `LANGFUSE_SAMPLE_RATE=0` e `LANGFUSE_TRACING_ENVIRONMENT`. O envio da pontuação é feito com o melhor esforço possível (best-effort), portanto, a interface de usuário de feedback não bloqueia caso o Langfuse esteja temporariamente indisponível.
