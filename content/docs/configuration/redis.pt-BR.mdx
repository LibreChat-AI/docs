Este guia aborda como configurar o Redis para cache e armazenamento de sessões no LibreChat. O Redis oferece melhorias significativas de desempenho e é **obrigatório para escalonamento horizontal**. Se você estiver executando várias instâncias do LibreChat atrás de um balanceador de carga, o Redis garante um estado consistente entre todas as instâncias.

## Configuração Básica [#basic-setup]

### Habilitar o Redis [#enable-redis]

Para habilitar o Redis no LibreChat, defina a seguinte variável de ambiente no seu arquivo `.env`:

```bash
USE_REDIS=true
```

**Importante**: Quando `USE_REDIS=true`, você também deve fornecer uma `REDIS_URI`. A aplicação lançará um erro se o Redis estiver habilitado sem uma URI de conexão.

## Tipos de Conexão [#connection-types]

### Instância Única do Redis [#single-redis-instance]

Para uma configuração padrão de servidor Redis único:

```bash
# Local Redis instance
REDIS_URI=redis://127.0.0.1:6379

# Remote Redis instance
REDIS_URI=redis://your-redis-host:6379
```

### Cluster Redis [#redis-cluster]

Para implantações de cluster Redis com múltiplos nós:

```bash
# Multiple Redis cluster nodes
REDIS_URI=redis://127.0.0.1:7001,redis://127.0.0.1:7002,redis://127.0.0.1:7003
```

O aplicativo detecta automaticamente o modo de cluster quando múltiplas URIs são fornecidas.

Se o seu cluster redis possuir apenas uma única URI, você pode usar a variável de ambiente `USE_REDIS_CLUSTER` para habilitar o modo de cluster:

```bash
# Redis cluster with single URI
REDIS_URI=redis://127.0.0.1:7001
USE_REDIS_CLUSTER=true
```

### Serviços Gerenciados de Redis de Endpoint Único [#single-endpoint-managed-redis-services]

Alguns serviços gerenciados de Redis, incluindo AWS ElastiCache Serverless e Redis Enterprise Cloud na AWS, expõem um único endpoint de conexão enquanto realizam o sharding de chaves internamente. Nessa configuração, mantenha o LibreChat no modo de conexão de nó único, mas habilite exclusões seguras para cluster (cluster-safe deletes) se as limpezas de cache falharem com `CROSSSLOT Keys in request don't hash to the same slot`.

```bash
USE_REDIS=true
REDIS_URI=rediss://your-managed-redis-endpoint:6379
USE_REDIS_CLUSTER=false
REDIS_CLUSTER_SAFE_DELETE=true
```

`REDIS_CLUSTER_SAFE_DELETE=true` faz com que o LibreChat exclua chaves de cache correspondentes uma por uma, em vez de enviar comandos `DEL` de múltiplas chaves. Isso evita erros `CROSSSLOT` sem alterar a forma como o LibreChat se conecta ao Redis.

Use `USE_REDIS_CLUSTER=true` apenas quando o LibreChat precisar criar um cliente de Redis Cluster. Para serviços gerenciados de endpoint único, `REDIS_CLUSTER_SAFE_DELETE=true` é a opção mais segura.

### Redis com TLS/SSL [#redis-with-tlsssl]

Para conexões Redis seguras:

```bash
# Redis with TLS encryption
REDIS_URI=rediss://127.0.0.1:6380

# Path to CA certificate for TLS verification
REDIS_CA=/path/to/ca-cert.pem
```

## Configuração de Segurança [#security-configuration]

### Autenticação [#authentication]

Configure as credenciais de autenticação do Redis:

```bash
# Method 1: Include credentials in URI
# With both username and password
REDIS_URI=redis://myuser:mypassword@127.0.0.1:6379


# Method 2: Separate environment variables
REDIS_URI=redis://127.0.0.1:6379
REDIS_USERNAME=your_redis_username
REDIS_PASSWORD=your_redis_password
```

**Nota**: As credenciais incorporadas em `REDIS_URI` têm precedência. `REDIS_USERNAME` e `REDIS_PASSWORD` são usados apenas como alternativa quando a URI não possui nome de usuário ou senha.

### Configuração de TLS [#tls-configuration]

Para conexões criptografadas:

```bash
# Enable TLS with rediss:// protocol
REDIS_URI=rediss://your-redis-host:6380

# Provide CA certificate for verification
REDIS_CA=/path/to/your/ca-certificate.pem
```

### TLS com Elasticache [#tls-with-elasticache]

O Elasticache pode precisar usar um dnsLookup alternativo para conexões TLS. Veja "Special Note: Aws Elasticache Clusters with TLS" nesta página da web: https://www.npmjs.com/package/ioredis

```bash
# Enable redis alternate dnsLookup
REDIS_USE_ALTERNATIVE_DNS_LOOKUP=true
```

## Opções Avançadas [#advanced-options]

### Prefixo de Chave [#key-prefixing]

O prefixo de chaves do Redis evita a contaminação entre implantações, isolando os dados de cache entre diferentes ambientes, versões ou instâncias que compartilham o mesmo servidor Redis. Isso é essencial para:

- **Implantações multi-tenant**: Ambientes separados de staging, produção e desenvolvimento
- **Blue-green deployments**: Isole o cache entre diferentes versões da aplicação

```bash
# Option 1: Dynamic prefix from environment variable (recommended for cloud)

# Google Cloud Platform - Cloud Run
REDIS_KEY_PREFIX_VAR=K_REVISION

# AWS - ECS/Fargate
REDIS_KEY_PREFIX_VAR=AWS_EXECUTION_ENV

# Azure Container Instances
REDIS_KEY_PREFIX_VAR=CONTAINER_NAME

# Kubernetes - Pod name or deployment
REDIS_KEY_PREFIX_VAR=HOSTNAME
REDIS_KEY_PREFIX_VAR=POD_NAME

# Kubernetes - Custom deployment identifier
REDIS_KEY_PREFIX_VAR=DEPLOYMENT_ID

# Heroku
REDIS_KEY_PREFIX_VAR=DYNO

# Option 2: Static prefix (for manual control)
REDIS_KEY_PREFIX=librechat-prod-v2
REDIS_KEY_PREFIX=staging-branch-feature-x
REDIS_KEY_PREFIX=dev-john-local
```

**Importante**: Você não pode definir `REDIS_KEY_PREFIX_VAR` e `REDIS_KEY_PREFIX` simultaneamente.

**Exemplos de contaminação sem prefixação**:

- Cache de produção sobrescrito pelo deployment de staging
- Testes de branch de funcionalidade corrompendo o cache da branch principal
- Versões de implantação antigas servindo dados em cache obsoletos

**Formato de prefixo de chave**:

- Cliente IoRedis: `{prefix}::{key}`
- Cliente Keyv: Gerenciado pela camada de armazenamento

### Limites de Conexão [#connection-limits]

Configure os limites de conexão do Redis:

```bash
# Maximum number of event listeners (default: 40)
REDIS_MAX_LISTENERS=40
```

### Connection Keep-Alive [#connection-keep-alive]

Configure heartbeats do Redis com limite de tempo e TCP keepalive:

```bash
# Redis ping interval in seconds (default: 0 = disabled)
# When set to a positive integer (in seconds), Redis clients will ping the server at this interval
# When unset or 0, no pinging is performed (recommended for most use cases)
# Example: 300 = ping every 5 minutes
REDIS_PING_INTERVAL=300

# Maximum time an enabled heartbeat PING may go unanswered (default: 5000 ms)
REDIS_PING_TIMEOUT=5000

# Dedicated pub/sub subscriber heartbeat (default: 15 seconds, 0 = disabled)
REDIS_SUBSCRIBER_PING_INTERVAL=15

# TCP keepalive idle delay for ioredis sockets (default: 10000 ms, 0 = kernel default)
REDIS_KEEP_ALIVE=10000
```

**Importante**:

- Definir `REDIS_PING_INTERVAL=0` ou omiti-lo desativa o ping completamente.
- Defina apenas um valor positivo (em segundos) se você encontrar problemas de tempo limite de conexão (timeout)
- `REDIS_PING_INTERVAL` é especificado em segundos e controla o heartbeat opcional do ioredis principal
- Assinantes pub/sub dedicados usam seu próprio intervalo padrão ativado, pois um socket inativo morto pode, de outra forma, permanecer sem detecção; defina `REDIS_SUBSCRIBER_PING_INTERVAL=0` para desativar esse heartbeat
- Cada heartbeat ativado usa `REDIS_PING_TIMEOUT` como seu prazo de resposta e reconecta o socket quando um PING permanece sem resposta
- `REDIS_KEEP_ALIVE` configura o socket TCP do ioredis independentemente dos PINGs em nível de aplicação
- Valores de exemplo: `300` (5 minutos), `600` (10 minutos), `60` (1 minuto)

### Recuperação de Failover de Réplica [#replica-failover-recovery]

Durante um failover do Sentinel, uma réplica do Redis rebaixada pode manter um socket existente aberto enquanto rejeita gravações com `READONLY`. O LibreChat detecta essa resposta no cliente Keyv não clusterizado, encerra a conexão obsoleta e reconecta para que o primário atual possa ser resolvido sem reiniciar a aplicação.

```bash
# Minimum interval between forced recovery attempts, in milliseconds
# Default: 5000
REDIS_READONLY_RECOVERY_INTERVAL=5000
```

O intervalo faz o debounce das tentativas de reconexão durante uma sequência de gravações com falha. Clientes Redis Cluster são excluídos porque utilizam topologia de cluster nativa e tratamento de redirecionamento.

### Verificações de Integridade [#health-checks]

LibreChat expõe três endpoints de verificação (probe). Somente `/readyz` reflete o Redis:

| Endpoint | Retorna `200 OK` | Retorna `503 NOT_READY` |
| --- | --- | --- |
| `/livez` | Sempre que o processo estiver atendendo requisições | Nunca |
| `/health` | Sempre que o processo estiver atendendo requisições | Nunca |
| `/readyz` | Após a conclusão da inicialização e, com `USE_REDIS=true`, enquanto o Redis estiver conectado | Antes da conclusão da inicialização, ou enquanto o Redis estiver habilitado mas desconectado |

Quando o Redis reinicia, sofre um failover ou fica inacessível por mais tempo que a janela de novas tentativas do cliente, as requisições que dependem dele (login, sessões, limites de taxa) falham até que a conexão seja restabelecida. Durante esse período, `/readyz` responde `503`, de modo que um load balancer ou uma sonda de prontidão do Kubernetes deixa de encaminhar tráfego para a instância. Ele volta a responder `200` assim que o Redis reconecta, sem necessidade de reinicialização. Com o Redis habilitado, todo cliente Redis deve estar conectado; em um Redis Cluster, isso inclui todos os nós primários.

Aponte as verificações de prontidão para `/readyz` e as verificações de vivacidade para `/livez`. Mantenha o Redis fora da verificação de vivacidade: uma sonda de vivacidade que falha durante uma interrupção do Redis reinicia todos os pods de uma só vez e não consegue fazer o Redis voltar.

```yaml
livenessProbe:
  httpGet:
    path: /livez
    port: 3080
readinessProbe:
  httpGet:
    path: /readyz
    port: 3080
  periodSeconds: 10
  failureThreshold: 3
```

`/readyz` não aguarda reconexões curtas por conta própria, então use `failureThreshold` para decidir por quanto tempo uma indisponibilidade pode durar antes que o tráfego seja retirado.

### Cache Seletivo em Memória [#selective-in-memory-caching]

Forçar namespaces de cache específicos a usar armazenamento em memória mesmo quando o Redis estiver habilitado:

```bash
# Comma-separated list of cache keys
FORCED_IN_MEMORY_CACHE_NAMESPACES=CONFIG_STORE,APP_CONFIG,ROLES
```

Quando não definida, o padrão é `CONFIG_STORE,APP_CONFIG`, de modo que a configuração derivada do `librechat.yaml` permanece por contêiner. Definir esta variável **substitui** o padrão em vez de acrescentar a ele; por isso, inclua `CONFIG_STORE,APP_CONFIG` na sua lista, a menos que você queira esses namespaces no Redis. Defina-a como uma string vazia para direcionar todos os namespaces para o Redis.

Chaves de cache válidas (do enum `CacheKeys` em `librechat-data-provider`):

| Chave | Descrição |
| --- | --- |
| `CONFIG_STORE` | Armazenamento de configuração |
| `TOOL_CACHE` | Cache de ferramentas (plugins, ferramentas MCP, definições de ferramentas) |
| `ROLES` | Funções de usuário |
| `USER_PRINCIPALS` | Associações de grupo usadas para resolver principais de ACL |
| `PROMPT_GROUPS_ACCESS` | Conjuntos de IDs de acesso a grupos de prompts |
| `AGENT_LINKED_INSTRUCTIONS` | Instruções resolvidas dos grupos de prompts vinculados a um agente |
| `SANDBOX_PREWARM` | Estado de pré-aquecimento do sandbox de código por conversa |
| `GEN_TITLE` | Títulos gerados |
| `TOOLS` | Dados de ferramentas |
| `MODELS_CONFIG` | Configuração de modelos |
| `MODEL_QUERIES` | Consultas de modelos |
| `STARTUP_CONFIG` | Configuração de inicialização |
| `ENDPOINT_CONFIG` | Configuração de endpoints |
| `TOKEN_CONFIG` | Configuração de tokens |
| `REASONING_CAPABILITIES` | Esforço de raciocínio por modelo para endpoints OpenRouter |
| `PULL_REQUESTS` | Consultas de pull requests e períodos de espera por limite de taxa do GitHub |
| `APP_CONFIG` | Configuração da aplicação |
| `ABORT_KEYS` | Chaves de cancelamento |
| `BANS` | Dados de banimento |
| `ENCODED_DOMAINS` | Domínios codificados |
| `AUDIO_RUNS` | Execuções de processamento de áudio |

| `FLOWS` | Estados de fluxos em andamento |

  Usar uma chave inválida (por exemplo, a obsoleta `STATIC_CONFIG`) causará um erro na inicialização. Use apenas as chaves da tabela acima.
</Callout>

## Ajuste de Desempenho [#performance-tuning]

### Connection Keep-Alive [#connection-keep-alive-1]

A aplicação implementa um keep-alive de conexão configurável:

- Os PINGs do main-client são controlados por `REDIS_PING_INTERVAL` e desativados por padrão
- Os PINGs de assinante dedicados são controlados por `REDIS_SUBSCRIBER_PING_INTERVAL` e o padrão é 15 segundos
- Heartbeats usam `REDIS_PING_TIMEOUT` para detectar sockets silenciosamente inativos e forçar a reconexão
- O TCP keepalive usa `REDIS_KEEP_ALIVE`, independentemente dos heartbeats em nível de aplicação
- Os temporizadores de heartbeat são limpos em eventos de desconexão ou fechamento.

### Estratégia de Cache [#cache-strategy]

A aplicação utiliza uma abordagem de cliente duplo:

- **Cliente IoRedis**: Operações primárias de Redis com prefixação automática
- **Cliente Keyv Redis**: Operações da camada de armazenamento com manipulação de prefixo em `cacheFactory.js`

### Ajuste Avançado de Conexão [#advanced-connection-tuning]

Essas variáveis opcionais ajustam o comportamento das conexões e as operações de cache em massa. Os valores padrão atendem à maioria das implantações.

| Variável | Padrão | Descrição |
| --- | --- | --- |
| `REDIS_CONNECT_TIMEOUT` | `10000` | Tempo limite de conexão em milissegundos. |
| `REDIS_RETRY_MAX_ATTEMPTS` | `10` | Número máximo de tentativas de reconexão antes de desistir. `0` tenta indefinidamente. |
| `REDIS_RETRY_MAX_DELAY` | `3000` | Atraso máximo entre as tentativas de reconexão, em milissegundos. |
| `REDIS_ENABLE_OFFLINE_QUEUE` | `true` | Enfileira comandos enquanto desconectado. Defina como `false` para falhar imediatamente. |
| `REDIS_SCAN_COUNT` | `1000` | Dica `COUNT` para operações `SCAN` ao localizar chaves por padrão. |
| `REDIS_DELETE_CHUNK_SIZE` | `1000` | Número de chaves excluídas por lote em exclusões em massa. |
| `MCP_REGISTRY_CACHE_TTL` | `5000` | Milissegundos pelos quais os caches do registro MCP são mantidos. A desatualização entre instâncias pode chegar ao dobro desse valor. `0` desativa o snapshot local, de modo que cada leitura vai ao Redis. |

### Otimização de Memória [#memory-optimization]

Use `FORCED_IN_MEMORY_CACHE_NAMESPACES` para otimizar o desempenho mantendo conjuntos de dados pequenos e acessados com frequência na memória, enquanto utiliza o Redis para caches maiores.

## Streams Resumíveis [#resumable-streams]

O Redis habilita [Resumable Streams](/docs/features/resumable_streams) para implantações com escalonamento horizontal. Quando ativado, as respostas da IA podem ser reconectadas e retomadas perfeitamente entre instâncias de servidor.

**Importante:** Quando `USE_REDIS=true`, os streams retomáveis usam automaticamente o Redis para coordenação entre instâncias. Esta é a configuração recomendada para implantações com escalonamento horizontal, onde os usuários podem se conectar a diferentes instâncias de servidor.

**Nota:** Se você estiver executando uma única instância do LibreChat, o Redis para streams retomáveis normalmente é desnecessário; o modo padrão em memória funciona bem. O Redis se torna essencial quando você tem várias instâncias do LibreChat atrás de um balanceador de carga, onde a reconexão de um usuário pode cair em um servidor diferente daquele em que o stream foi iniciado.

### Configuração [#configuration]

```bash
# Redis enabled = resumable streams automatically use Redis
USE_REDIS=true
REDIS_URI=redis://127.0.0.1:6379

# Optional: explicitly control resumable streams behavior
# USE_REDIS_STREAMS=true  # Enabled by default when USE_REDIS=true
```

### Compatibilidade do Protocolo de Geração [#generation-protocol-compatibility]

Os clientes atuais do LibreChat negociam o protocolo de geração v2 automaticamente com cada armazenamento de geração integrado. Nenhuma configuração de implantação é necessária. Gerações existentes com um marcador de protocolo v1 explícito ou armazenado mantêm seu comportamento v1 imutável por meio de direcionamento, pausa/retomada, nova tentativa e recuperação até que sejam concluídas.

Para uma atualização contínua (rolling upgrade), cada imagem de API e worker em execução deve incluir a ponte de compatibilidade v2:

- Cada imagem de API e worker executa o LibreChat `v0.8.8-rc1` ou mais recente.
- O Helm chart `2.0.8` ou mais recente seleciona uma imagem padrão compatível; uma substituição de imagem personalizada ainda deve atender ao requisito de imagem acima.

Ao atualizar de uma versão mais antiga, execute uma transferência a frio (cold handoff): pare todas as réplicas antigas da API e do worker antes de iniciar a nova imagem. Isso evita que binários pré-v2 e automatic-v2 compartilhem o estado de geração no Redis.

<Callout type="warning" title="Segurança de implantação contínua">
  Não execute uma versão anterior à `v0.8.8-rc1` com o mesmo estado de geração do Redis que as réplicas atuais. Antes de reverter para uma versão abaixo desse limite de compatibilidade, certifique-se primeiro de que as réplicas atuais e as gerações do protocol-v2 tenham sido esvaziadas (drained).
</Callout>

Fluxos de geração em memória também negociam o protocolo v2 automaticamente e não compartilham o estado de geração entre processos.

### Coalescência de Delta de Stream [#stream-delta-coalescing]

Fluxos baseados em Redis podem processar publicações delta em lote para reduzir scripts do Redis, viagens de ida e volta (round trips) e uso de CPU em taxas elevadas de tokens:

```bash filename=".env"
STREAM_DELTA_COALESCE_MS=25
```

A configuração assume o valor padrão de `25` milissegundos quando não definida. Defina-a explicitamente como `0` para desativar a coalescência; valores acima de `1000` são limitados. O processamento em lote (batching) pode adicionar até uma janela configurada de latência de entrega e pode perder o final do buffer se o processo de publicação for encerrado antes de ser liberado. Quadros de fragmentos individuais são retidos para compatibilidade de protocolo, portanto, essa configuração reduz o trabalho de script Redis e de ida e volta (round-trip) sem alterar o formato do quadro do assinante. Fluxos de geração em memória permanecem inalterados.

### Principais Benefícios (para Escalonamento Horizontal) [#key-benefits-for-horizontal-scaling]

- **Continuidade entre instâncias**: Os usuários podem iniciar uma geração em um servidor e retomá-la em outro
- **Implantações contínuas (Rolling deployments)**: Streams ativos sobrevivem a reinicializações do servidor
- **Sincronização de múltiplas abas**: A mesma conversa é sincronizada entre várias abas do navegador em um ambiente com balanceamento de carga
- **Resiliência de conexão**: Reconexão automática, independentemente de qual servidor processe a solicitação

### Configuração de Cluster [#cluster-configuration]

Para implantações de Redis Cluster, o LibreChat usa automaticamente chaves com hash-tag para garantir que as operações de stream permaneçam dentro do mesmo slot do cluster:

```bash
USE_REDIS=true
USE_REDIS_STREAMS=true
USE_REDIS_CLUSTER=true
REDIS_URI=redis://node1:7001,redis://node2:7002,redis://node3:7003
```

Veja [Resumable Streams](/docs/features/resumable_streams) para mais detalhes sobre este recurso.

## Coordenação do Catálogo MCP [#mcp-catalog-coordination]

Quando o Redis está habilitado, o LibreChat coordena catálogos de ferramentas MCP em nível de aplicação entre réplicas. A publicação na inicialização, a sincronização de reconexão e as atualizações `notifications/tools/list_changed` utilizam marcadores de geração e revisão para que uma réplica obsoleta não possa sobrescrever um catálogo mais recente.

As implantações em Redis Cluster usam chaves de catálogo seguras para slots e operações de atualização; nenhuma configuração separada do MCP Redis é necessária. Consulte [Gerenciamento de Servidores MCP](/docs/configuration/librechat_yaml/object_structure/mcp_servers#additional-information) para o comportamento do catálogo dinâmico e a prontidão do OAuth.
