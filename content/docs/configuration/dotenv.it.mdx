Benvenuti nella guida completa per la configurazione dell'ambiente della vostra applicazione tramite il file `.env`. Questo documento è la vostra risorsa unica per comprendere e personalizzare le variabili d'ambiente che determineranno il comportamento della vostra applicazione in diversi contesti.

Mentre le impostazioni predefinite forniscono una solida base per un'installazione `docker` standard, approfondire questa guida svelerà il pieno potenziale di LibreChat. Questa guida ti permette di adattare LibreChat alle tue esigenze specifiche. Scopri come regolare la disponibilità dei modelli linguistici, integrare i social login, gestire il sistema di moderazione automatica e molto altro. Si tratta di darti il controllo per ottimizzare LibreChat per un'esperienza utente ideale.

> **Promemoria: Riavviare LibreChat affinché le modifiche alla configurazione abbiano effetto**

In alternativa, puoi creare un nuovo file chiamato `docker-compose.override.yml` nella stessa directory del tuo file `docker-compose.yml` principale per LibreChat, dove puoi impostare le tue variabili .env come necessario sotto `environment`, oppure modificare la configurazione predefinita fornita dal `docker-compose.yml` principale, senza la necessità di modificare direttamente o duplicare l'intero file.

## Configurazione del Server [#server-configuration]

### Porta [#port]

- Il server è in ascolto su una porta specifica.
- La variabile d'ambiente `PORT` imposta la porta su cui il server rimane in ascolto. Per impostazione predefinita, è impostata su `3080`.

### Timeout del server HTTP [#http-server-timeouts]

Questi valori opzionali configurano il server HTTP Node.js. Lasciali non impostati per mantenere i valori predefiniti di Node. Un valore pari a `0` disabilita tale timeout.

      '# HTTP_KEEP_ALIVE_TIMEOUT_MS=70000',

I valori devono essere interi sicuri non negativi; i valori non validi vengono ignorati. Quando sia il timeout dell'header che quello della richiesta sono abilitati, LibreChat limita il timeout dell'header a quello della richiesta se quest'ultimo è inferiore. Node verifica la scadenza dell'header e della richiesta durante una scansione delle connessioni ogni 30 secondi, pertanto i valori inferiori a `30000` non vengono applicati con una precisione al millisecondo esatto. Bun attualmente accetta queste impostazioni ma non le applica; LibreChat registra un avviso quando il server API viene eseguito con Bun.

### Trust proxy [#trust-proxy]

Utilizza l'indirizzo che si trova al massimo a n salti di distanza dall'applicazione Express.
req.socket.remoteAddress è il primo salto, mentre i restanti vengono cercati nell'intestazione X-Forwarded-For da destra a sinistra.
Un valore pari a 0 significa che il primo indirizzo non attendibile sarebbe req.socket.remoteAddress, ovvero non è presente alcun reverse proxy.
Il valore predefinito della variabile d'ambiente `TRUST_PROXY` è impostato su `1`.

Fare riferimento a [Express.js - trust proxy](https://expressjs.com/en/guide/behind-proxies.html) per ulteriori informazioni a riguardo.

<OptionTable
  options={[['TRUST_PROXY', 'number', 'Specifica il numero di hop.', 'TRUST_PROXY=1']]}
/>

### Intestazione Trusted Tenant [#trusted-tenant-header]

`TRUST_TENANT_HEADER` controlla se LibreChat accetta `X-Tenant-Id` prima dell'autenticazione sugli alberi di percorso `/oauth`, `/api/auth` e `/api/share`. È disabilitato per impostazione predefinita; quando è disabilitato, tali percorsi ignorano l'intestazione.

<OptionTable
  options={[
    [
      'TRUST_TENANT_HEADER',
      'boolean',
      'Considera attendibile X-Tenant-Id sulle rotte di pre-autenticazione. Abilita solo dietro un proxy attendibile che sostituisca i valori forniti dal client.',
      'TRUST_TENANT_HEADER=false',
    ],
  ]}
/>

<Callout type="warning" title="Non fidarti degli header tenant forniti dal client">
  Abilita questa impostazione solo quando un reverse proxy affidabile rimuove ogni valore `X-Tenant-Id` in entrata e imposta esso stesso l'ID tenant autorevole. In caso contrario, un client non attendibile potrebbe scegliere il contesto del tenant utilizzato prima dell'autenticazione. LibreChat registra un avviso di sicurezza quando l'impostazione è abilitata.
</Callout>

Quando `TENANT_ISOLATION_STRICT` è abilitato ma `TRUST_TENANT_HEADER` è disabilitato, LibreChat avvisa all'avvio che le intestazioni tenant di pre-autenticazione verranno ignorate.

### Configurazione delle credenziali [#credentials-configuration]

LibreChat utilizza `CREDS_KEY` e `CREDS_IV` per crittografare le credenziali supportate memorizzate nel database. Configura valori fissi e univoci per la produzione e condividi gli stessi valori tra ogni replica.

<OptionTable
  options={[
    [
      'CREDS_KEY',
      'string',
      'Chiave a 32 byte (64 caratteri esadecimali) per l\'archiviazione sicura delle credenziali.',
      'CREDS_KEY=',
    ],
    [
      'CREDS_IV',
      'string',
      'IV a 16 byte (32 caratteri esadecimali) per l\'archiviazione sicura delle credenziali.',
      'CREDS_IV=',
    ],
    [
      'LIBRECHAT_TEMP_CREDENTIALS_PATH',
      'string',
      'Percorso utilizzato per mantenere le credenziali temporanee generate automaticamente. L\'impostazione predefinita è `.env.temp` nella directory di lavoro del processo.',
      '# LIBRECHAT_TEMP_CREDENTIALS_PATH=/app/data/.env.temp',
    ],
  ]}
/>

Quando uno qualsiasi tra `CREDS_KEY`, `CREDS_IV`, `JWT_SECRET` o `JWT_REFRESH_SECRET` è vuoto, LibreChat riutilizza innanzitutto un valore valido dal file delle credenziali temporanee. Se non ne esiste nessuno, ne genera uno crittograficamente casuale e scrive il file con permessi di sola lettura per il proprietario. I valori espliciti delle variabili d'ambiente hanno sempre la precedenza. LibreChat rifiuta di utilizzare `.env` o `.env.example` come percorso del file generato, impedendo la sostituzione accidentale di entrambi i file di configurazione.

LibreChat si rifiuta inoltre di avviarsi quando `JWT_SECRET` o `JWT_REFRESH_SECRET` utilizzano ancora uno dei valori predefiniti pubblicati e ritirati, indipendentemente dal fatto che il valore provenga dall'ambiente o dal file delle credenziali temporanee. Genera sostituzioni univoche invece di mantenere vecchi esempi di segreti in una distribuzione.

I file Docker Compose in bundle rendono persistente `/app/data/.env.temp` nel volume `librechat-data`, in modo che una singola distribuzione Compose possa riavviarsi senza modificare questi valori generati. Se il file non può essere reso persistente, i valori rimangono locali al processo e le sessioni o i record crittografati potrebbero diventare inaccessibili dopo il riavvio.

<Callout type="warning" title="Imposta valori permanenti per la produzione">
  La generazione temporanea è una comodità di bootstrap, non un sistema di rotazione delle credenziali. Prima dell'uso in produzione, genera valori permanenti con il [Credentials Generator](/toolkit/creds_generator), archiviali nel tuo secret manager e fornisci gli stessi valori a ogni replica. La modifica di una chiave stabilita non ricifra i record esistenti. LibreChat registra le impronte digitali delle credenziali nel database e avvisa quando i valori attivi divergono; non sovrascrivere quel marcatore invece di eseguire una migrazione controllata.
</Callout>

### Intestazioni di sicurezza e Content Security Policy [#security-headers-and-content-security-policy]

LibreChat invia per impostazione predefinita intestazioni HSTS, framing, content-type, opener, resource e referrer di base. `SECURITY_HEADERS=false` le disabilita tutte ed è anche l'interruttore globale per la CSP.

Il CSP basato su nonce è un'opzione separata attivabile con `CSP_ENABLED=true` e, per impostazione predefinita, è in modalità solo report. Inizia con `CSP_REPORT_ONLY=true`, controlla le violazioni e aggiungi solo le origini richieste dalla tua distribuzione prima di applicarlo. Quando il CSP è attivo, la shell SPA viene sempre inviata con `Cache-Control: no-store`, in modo che il suo nonce per singola risposta non possa essere riutilizzato dalla cache.

Consulta [HTTP Security Headers](/docs/configuration/security_headers) per tutte le variabili di base e CSP, i valori accettati, i valori predefiniti, le sostituzioni della source-list e le linee guida per l'implementazione.

      'Abilita la distribuzione di versioni gzipped delle immagini caricate se presenti nella stessa cartella.',
      'ENABLE_IMAGE_OUTPUT_GZIP_SCAN=true',
    ],
    [
      'ENABLE_STATIC_ASSET_BROTLI',
      'boolean',
      'Abilita la distribuzione di versioni Brotli precompresse degli asset statici dell\'app quando disponibili.',
      'ENABLE_STATIC_ASSET_BROTLI=true',
    ],
  ]}
/>

**Comportamento:**

Imposta le intestazioni [Cache-Control](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Cache-Control) per i file statici. Queste configurazioni si attivano solo quando `NODE_ENV` è impostato su `production`.

- Decommenta `STATIC_CACHE_MAX_AGE` per modificare il `max-age` locale per i file statici. Per impostazione predefinita, questo è impostato su 2 giorni (172800 secondi).
- Decommenta `STATIC_CACHE_S_MAX_AGE` per impostare `s-maxage` per le cache condivise (CDN e proxy). Per impostazione predefinita, questo valore è impostato su 1 giorno (86400 secondi).
- Decommenta `DISABLE_COMPRESSION` per disabilitare la compressione per i file statici. Per impostazione predefinita, la compressione è abilitata.
- Decommenta `ENABLE_IMAGE_OUTPUT_GZIP_SCAN` per abilitare la scansione e la distribuzione della versione compressa in gzip delle immagini, se sono state pre-compresse nella stessa cartella, con lo stesso nome e un'estensione .gz. Per impostazione predefinita, la scansione gzip per le immagini caricate è disabilitata.
- Decommenta `ENABLE_STATIC_ASSET_BROTLI` per servire versioni `.br` pre-compresse degli asset statici dell'app quando presenti. Quando abilitato, Brotli è preferito rispetto a gzip per i file statici serviti dall'API.

<Callout type="warning" title="Attenzione">
  - Ciò riguarda solo i file statici serviti dal server API e non è applicabile a _Firebase_, _NGINX_ o qualsiasi altra configurazione.
</Callout>

  A differenza delle risorse statiche che vengono memorizzate nella cache per migliorare le prestazioni, le intestazioni della cache del file index.html sono configurate separatamente per garantire che gli utenti ricevano sempre la shell dell'applicazione più recente.
</Callout>

### Impedire ai motori di ricerca pubblici l'indicizzazione [#prevent-public-search-engines-indexing]

Per impostazione predefinita, il tuo sito web non verrà indicizzato dai motori di ricerca pubblici (ad esempio Google, Bing, …). Ciò significa che le persone non saranno in grado di trovare il tuo sito web tramite questi motori di ricerca. Se desideri rendere il tuo sito web più visibile e ricercabile, puoi modificare la seguente impostazione in `false`

<OptionTable
  options={[
    [
      'NO_INDEX',
      'boolean',
      'Impedisce ai motori di ricerca pubblici di indicizzare il tuo sito web.',
      'NO_INDEX=true',
    ],
  ]}
/>

❗**Nota:** Non è garantito che questo metodo funzioni per tutti i motori di ricerca e alcuni motori di ricerca potrebbero comunque indicizzare il tuo sito web o la tua pagina web per altri scopi, come la memorizzazione nella cache o l'archiviazione. Pertanto, non dovresti fare affidamento esclusivamente su questo metodo per proteggere informazioni sensibili o riservate sul tuo sito web o sulla tua pagina web.

### Logging [#logging]

LibreChat dispone di un sistema di logging centrale integrato; consulta [Logging System](/docs/configuration/logging) per maggiori informazioni.

- Il debug logging è abilitato per impostazione predefinita ed è fondamentale per lo sviluppo.

- I log di errore sono archiviati nella stessa posizione.

### Endpoint Stateful Code Interpreter [#stateful-code-interpreter-endpoint]

[`stateful_code_sessions`](/docs/configuration/librechat_yaml/object_structure/agents#capabilities) è altamente sperimentale e richiede un percorso separato per il Code Interpreter. Configura il percorso predefinito con `LIBRECHAT_CODE_BASEURL_STATEFUL`, oppure definisci backend gestiti o collegati denominati sotto [`endpoints.agents.statefulCodeSessions.environments`](/docs/configuration/librechat_yaml/object_structure/agents#statefulcodesessions). Il servizio selezionato deve eseguire il profilo `stateful`; LibreChat invia `X-CodeAPI-Expected-Profile: stateful` con le richieste stateful.

Le richieste stateful non ripiegano mai su `LIBRECHAT_CODE_BASEURL`. Se l'ambiente denominato selezionato non è disponibile, o se non è configurato né un valore predefinito denominato né `LIBRECHAT_CODE_BASEURL_STATEFUL`, LibreChat interrompe l'esecuzione dell'Agent con un errore di configurazione. Gli agenti stateless continuano a utilizzare `LIBRECHAT_CODE_BASEURL` e i due profili di esecuzione non condividono un workspace attivo.

Ogni Agent può limitare il proprio workspace stateful all'utente che ha effettuato l'accesso, all'utente e all'Agent insieme, oppure all'utente e alla conversazione. Consulta [Stateful Code Sessions](/docs/features/code_interpreter#stateful-code-sessions) per la configurazione e le limitazioni di persistenza.

Gli ambienti collegati denominati possono anche esporre un piano di controllo di pairing self-service con `pairing.allowPrincipalWorkers: true`. Gli utenti autorizzati gestiscono tali worker vincolati al proprietario in **Settings > Code environments**; le voci di solo pairing non sostituiscono `LIBRECHAT_CODE_BASEURL_STATEFUL` e non possono fungere da impostazione predefinita per il deployment.

Le continuazioni dei figli vincolati, le continuazioni dei genitori dei Subagent scollegati e il completamento delle Action scollegate dell'Event Actor sono automatici. Le variabili deprecate `ENABLE_AGENT_EVENT_CHILD_TURNS`, `ENABLE_SUBAGENT_COMPLETION_WAKEUPS` e `AGENT_TRIGGERS_DETACHED_ACTIONS_PRODUCER_ENABLED` non vengono più lette.

L'archivio di generazione in-memory supporta il completamento distaccato dell'Event Actor locale al processo finché il processo rimane attivo. I flussi di generazione Redis aggiungono il ripristino durevole dopo il riavvio e il passaggio di consegne tra repliche. Consulta [Generation Protocol Compatibility](/docs/configuration/redis#generation-protocol-compatibility) prima di un deployment con versioni miste.

Lascia `AGENT_TRIGGERS_SELF_URL` non impostato per il normale percorso del bound-listener. Impostalo solo quando l'ammissione di eventi interni deve attraversare un'altra origine HTTP, come un front door TLS. Il valore deve essere un URL HTTP o HTTPS senza credenziali incorporate.

LibreChat espone un'API Agent Events autenticata; non espone un webhook non autenticato. L'identità tramite API-key, le autorizzazioni dei Remote Agents, l'accesso alla destinazione, l'idempotenza e il limite di frequenza dedicato agli Agent Event proteggono l'ingresso. Corsie di ordinamento basate su MongoDB, mailbox degli attori, ricevute, lease, tentativi e dead letter supportano i worker attraverso le repliche. Consulta [Agent Event Delivery](/docs/features/agents#agent-event-delivery) e [Agents API - Agent Events](/docs/features/agents_api#agent-events) per il comportamento ed esempi.

### Moderazione [#moderation]

Il sistema di moderazione automatizzata utilizza un meccanismo di punteggio per tracciare le violazioni degli utenti. Man mano che gli utenti compiono azioni come accessi, registrazioni o invio di messaggi eccessivi, accumulano punteggi di violazione. Questo sistema garantisce la sicurezza della piattaforma monitorando e penalizzando le attività rapide o sospette.

Se nella configurazione viene definito uno specifico saldo iniziale, i token verranno accreditati automaticamente sul saldo dell'utente al momento della registrazione.

#### Gestione dei saldi [#managing-balances]

- Esegui `npm run add-balance` per aggiungere manualmente i saldi.
  - Puoi anche specificare l'email e l'importo dei crediti token da aggiungere, ad esempio: `npm run add-balance example@example.com 1000`
- Esegui `npm run set-balance` per impostare manualmente i saldi, in modo simile a `add-balance`.
- Esegui `npm run list-balances` per elencare il saldo di ogni utente.

> **Nota:** 1000 crediti = $0.001 (1 mill USD)

  - I file vengono scaricati e allegati alla conversazione come normali caricamenti

Entrambi utilizzano `REDIS_PING_TIMEOUT` come scadenza per la risposta ed effettuano la riconnessione quando questa scade.
- Usa il protocollo `rediss://` per le connessioni TLS e imposta `REDIS_CA` se la tua CA non è pubblicamente attendibile.
- `REDIS_KEY_PREFIX_VAR` e `REDIS_KEY_PREFIX` si escludono a vicenda.
- **AWS Elasticache con TLS**: Elasticache potrebbe richiedere l'utilizzo di un dnsLookup alternativo per le connessioni TLS. Imposta `REDIS_USE_ALTERNATIVE_DNS_LOOKUP=true` se utilizzi Elasticache con TLS. Consulta la [documentazione di ioredis](https://www.npmjs.com/package/ioredis) per ulteriori dettagli.
