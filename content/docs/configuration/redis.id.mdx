Panduan ini membahas cara mengonfigurasi Redis untuk caching dan penyimpanan sesi di LibreChat. Redis memberikan peningkatan performa yang signifikan dan **wajib digunakan untuk horizontal scaling**. Jika Anda menjalankan beberapa instance LibreChat di belakang load balancer, Redis memastikan status yang konsisten di seluruh instance.

## Pengaturan Dasar [#basic-setup]

### Aktifkan Redis [#enable-redis]

Untuk mengaktifkan Redis di LibreChat, atur variabel lingkungan berikut di dalam file `.env` Anda:

```bash
USE_REDIS=true
```

**Penting**: Saat `USE_REDIS=true`, Anda juga harus menyediakan `REDIS_URI`. Aplikasi akan menampilkan error jika Redis diaktifkan tanpa URI koneksi.

## Tipe Koneksi [#connection-types]

### Instans Redis Tunggal [#single-redis-instance]

Untuk pengaturan server Redis tunggal standar:

```bash
# Local Redis instance
REDIS_URI=redis://127.0.0.1:6379

# Remote Redis instance
REDIS_URI=redis://your-redis-host:6379
```

### Redis Cluster [#redis-cluster]

Untuk penyebaran cluster Redis dengan beberapa node:

```bash
# Multiple Redis cluster nodes
REDIS_URI=redis://127.0.0.1:7001,redis://127.0.0.1:7002,redis://127.0.0.1:7003
```

Aplikasi secara otomatis mendeteksi mode klaster ketika beberapa URI disediakan.

Jika klaster redis Anda hanya memiliki satu URI, Anda dapat menggunakan variabel lingkungan `USE_REDIS_CLUSTER` untuk mengaktifkan mode klaster:

```bash
# Redis cluster with single URI
REDIS_URI=redis://127.0.0.1:7001
USE_REDIS_CLUSTER=true
```

### Layanan Redis Terkelola Endpoint Tunggal [#single-endpoint-managed-redis-services]

Beberapa layanan Redis terkelola, termasuk AWS ElastiCache Serverless dan Redis Enterprise Cloud di AWS, mengekspos satu endpoint koneksi tunggal sambil melakukan sharding kunci secara internal. Dalam pengaturan tersebut, biarkan LibreChat dalam mode koneksi single-node, tetapi aktifkan penghapusan yang aman untuk cluster (cluster-safe deletes) jika pembersihan cache gagal dengan pesan `CROSSSLOT Keys in request don't hash to the same slot`.

```bash
USE_REDIS=true
REDIS_URI=rediss://your-managed-redis-endpoint:6379
USE_REDIS_CLUSTER=false
REDIS_CLUSTER_SAFE_DELETE=true
```

`REDIS_CLUSTER_SAFE_DELETE=true` membuat LibreChat menghapus kunci cache yang cocok satu per satu alih-alih mengirim perintah `DEL` multi-kunci. Hal ini menghindari kesalahan `CROSSSLOT` tanpa mengubah cara LibreChat terhubung ke Redis.

Gunakan `USE_REDIS_CLUSTER=true` hanya jika LibreChat perlu membuat klien Redis Cluster. Untuk layanan terkelola dengan satu endpoint, `REDIS_CLUSTER_SAFE_DELETE=true` adalah opsi yang lebih aman.

### Redis dengan TLS/SSL [#redis-with-tlsssl]

Untuk koneksi Redis yang aman:

```bash
# Redis with TLS encryption
REDIS_URI=rediss://127.0.0.1:6380

# Path to CA certificate for TLS verification
REDIS_CA=/path/to/ca-cert.pem
```

## Konfigurasi Keamanan [#security-configuration]

### Autentikasi [#authentication]

Konfigurasikan kredensial autentikasi Redis:

```bash
# Method 1: Include credentials in URI
# With both username and password
REDIS_URI=redis://myuser:mypassword@127.0.0.1:6379


# Method 2: Separate environment variables
REDIS_URI=redis://127.0.0.1:6379
REDIS_USERNAME=your_redis_username
REDIS_PASSWORD=your_redis_password
```

**Catatan**: Kredensial yang disematkan di `REDIS_URI` lebih diutamakan. `REDIS_USERNAME` dan `REDIS_PASSWORD` hanya digunakan sebagai cadangan ketika URI tidak memiliki username atau password.

### Konfigurasi TLS [#tls-configuration]

Untuk koneksi terenkripsi:

```bash
# Enable TLS with rediss:// protocol
REDIS_URI=rediss://your-redis-host:6380

# Provide CA certificate for verification
REDIS_CA=/path/to/your/ca-certificate.pem
```

### TLS dengan Elasticache [#tls-with-elasticache]

Elasticache mungkin perlu menggunakan dnsLookup alternatif untuk koneksi TLS. lihat "Special Note: Aws Elasticache Clusters with TLS" pada halaman web ini: https://www.npmjs.com/package/ioredis

```bash
# Enable redis alternate dnsLookup
REDIS_USE_ALTERNATIVE_DNS_LOOKUP=true
```

## Opsi Lanjutan [#advanced-options]

### Awalan Kunci (Key Prefixing) [#key-prefixing]

Awalan kunci Redis mencegah kontaminasi lintas penyebaran dengan mengisolasi data cache antar lingkungan, versi, atau instans yang berbeda yang menggunakan server Redis yang sama. Hal ini sangat penting untuk:

- **Multi-tenant deployments**: Memisahkan lingkungan staging, production, dan development
- **Blue-green deployments**: Mengisolasi cache di antara versi aplikasi yang berbeda

```bash
# Option 1: Dynamic prefix from environment variable (recommended for cloud)

# Google Cloud Platform - Cloud Run
REDIS_KEY_PREFIX_VAR=K_REVISION

# AWS - ECS/Fargate
REDIS_KEY_PREFIX_VAR=AWS_EXECUTION_ENV

# Azure Container Instances
REDIS_KEY_PREFIX_VAR=CONTAINER_NAME

# Kubernetes - Pod name or deployment
REDIS_KEY_PREFIX_VAR=HOSTNAME
REDIS_KEY_PREFIX_VAR=POD_NAME

# Kubernetes - Custom deployment identifier
REDIS_KEY_PREFIX_VAR=DEPLOYMENT_ID

# Heroku
REDIS_KEY_PREFIX_VAR=DYNO

# Option 2: Static prefix (for manual control)
REDIS_KEY_PREFIX=librechat-prod-v2
REDIS_KEY_PREFIX=staging-branch-feature-x
REDIS_KEY_PREFIX=dev-john-local
```

**Penting**: Anda tidak dapat mengatur `REDIS_KEY_PREFIX_VAR` dan `REDIS_KEY_PREFIX` secara bersamaan.

**Contoh kontaminasi tanpa awalan**:

- Cache produksi ditimpa oleh deployment staging
- Pengujian branch fitur merusak cache branch utama
- Versi deployment lama yang menyajikan data cache usang

**Format awalan kunci**:

- Klien IoRedis: `{prefix}::{key}`
- Klien Keyv: Ditangani oleh lapisan penyimpanan

### Batas Koneksi [#connection-limits]

Konfigurasi batas koneksi Redis:

```bash
# Maximum number of event listeners (default: 40)
REDIS_MAX_LISTENERS=40
```

### Connection Keep-Alive [#connection-keep-alive]

Konfigurasikan heartbeat Redis yang dibatasi tenggat waktu dan TCP keepalive:

```bash
# Redis ping interval in seconds (default: 0 = disabled)
# When set to a positive integer (in seconds), Redis clients will ping the server at this interval
# When unset or 0, no pinging is performed (recommended for most use cases)
# Example: 300 = ping every 5 minutes
REDIS_PING_INTERVAL=300

# Maximum time an enabled heartbeat PING may go unanswered (default: 5000 ms)
REDIS_PING_TIMEOUT=5000

# Dedicated pub/sub subscriber heartbeat (default: 15 seconds, 0 = disabled)
REDIS_SUBSCRIBER_PING_INTERVAL=15

# TCP keepalive idle delay for ioredis sockets (default: 10000 ms, 0 = kernel default)
REDIS_KEEP_ALIVE=10000
```

**Penting**:

- Mengatur `REDIS_PING_INTERVAL=0` atau menghilangkannya akan menonaktifkan ping sepenuhnya
- Hanya tetapkan nilai positif (dalam detik) jika Anda mengalami masalah waktu tunggu koneksi (connection timeout)
- `REDIS_PING_INTERVAL` ditentukan dalam detik dan mengontrol heartbeat ioredis utama opsional
- Pelanggan pub/sub khusus menggunakan interval default-on mereka sendiri karena soket mati yang tidak aktif mungkin tidak terdeteksi; atur `REDIS_SUBSCRIBER_PING_INTERVAL=0` untuk menonaktifkan heartbeat tersebut.
- Setiap heartbeat yang diaktifkan menggunakan `REDIS_PING_TIMEOUT` sebagai tenggat waktu responsnya dan akan menyambungkan kembali soket saat PING tidak mendapatkan jawaban.
- `REDIS_KEEP_ALIVE` mengonfigurasi soket TCP ioredis secara independen dari PING tingkat aplikasi
- Nilai contoh: `300` (5 menit), `600` (10 menit), `60` (1 menit)

### Pemulihan Failover Replikasi [#replica-failover-recovery]

Selama failover Sentinel, replika Redis yang diturunkan statusnya dapat tetap membuka soket yang ada sambil menolak penulisan dengan `READONLY`. LibreChat mendeteksi respons ini pada klien Keyv non-cluster, memutus koneksi yang sudah kedaluwarsa, dan melakukan koneksi ulang sehingga primary saat ini dapat diselesaikan tanpa perlu memulai ulang aplikasi.

```bash
# Minimum interval between forced recovery attempts, in milliseconds
# Default: 5000
REDIS_READONLY_RECOVERY_INTERVAL=5000
```

Interval ini melakukan debounce pada upaya penyambungan kembali selama lonjakan penulisan yang gagal. Klien Redis Cluster dikecualikan karena mereka menggunakan topologi klaster asli dan penanganan pengalihan.

### Pemeriksaan Kesehatan [#health-checks]

LibreChat menyediakan tiga endpoint probe. Hanya `/readyz` yang mencerminkan status Redis:

| Endpoint | Mengembalikan `200 OK` | Mengembalikan `503 NOT_READY` |
| --- | --- | --- |
| `/livez` | Kapan pun proses sedang melayani permintaan | Tidak pernah |
| `/health` | Kapan pun proses sedang melayani permintaan | Tidak pernah |
| `/readyz` | Setelah startup selesai dan, dengan `USE_REDIS=true`, selama Redis terhubung | Sebelum startup selesai, atau selama Redis diaktifkan tetapi tidak terhubung |

Ketika Redis dimulai ulang, mengalami failover, atau tidak dapat dijangkau lebih lama dari jendela retry klien, permintaan yang bergantung padanya (masuk, sesi, batas laju) akan gagal hingga koneksi kembali. Selama itu, `/readyz` merespons `503`, sehingga load balancer atau probe kesiapan Kubernetes berhenti merutekan lalu lintas ke instance tersebut. Respons kembali menjadi `200` segera setelah Redis terhubung kembali, tanpa perlu restart. Saat Redis diaktifkan, setiap klien Redis harus terhubung; untuk Redis Cluster, ini mencakup setiap node primary.

Arahkan pemeriksaan kesiapan (readiness) ke `/readyz` dan pemeriksaan keaktifan (liveness) ke `/livez`. Jangan sertakan Redis dalam pemeriksaan liveness: probe liveness yang gagal saat Redis mengalami gangguan akan me-restart setiap pod sekaligus dan tidak dapat memulihkan Redis.

```yaml
livenessProbe:
  httpGet:
    path: /livez
    port: 3080
readinessProbe:
  httpGet:
    path: /readyz
    port: 3080
  periodSeconds: 10
  failureThreshold: 3
```

`/readyz` tidak menunggu koneksi yang terputus sebentar secara otomatis, jadi gunakan `failureThreshold` untuk menentukan berapa lama gangguan harus berlangsung sebelum lalu lintas dihentikan.

### Selective In-Memory Caching [#selective-in-memory-caching]

Paksa namespace cache tertentu untuk menggunakan penyimpanan in-memory meskipun Redis diaktifkan:

```bash
# Comma-separated list of cache keys
FORCED_IN_MEMORY_CACHE_NAMESPACES=CONFIG_STORE,APP_CONFIG,ROLES
```

Ketika tidak diatur, nilai defaultnya adalah `CONFIG_STORE,APP_CONFIG`, sehingga konfigurasi yang berasal dari `librechat.yaml` tetap berada di setiap container. Mengatur variabel ini **menggantikan** nilai default, bukan menambahkannya, jadi sertakan `CONFIG_STORE,APP_CONFIG` dalam daftar Anda kecuali Anda ingin namespace tersebut disimpan di Redis. Atur variabel ini ke string kosong untuk mengarahkan semua namespace melalui Redis.

Kunci cache yang valid (dari enum `CacheKeys` di `librechat-data-provider`):

| Key | Description |
| --- | --- |
| `CONFIG_STORE` | Penyimpanan konfigurasi |
| `TOOL_CACHE` | Cache alat (plugin, alat MCP, definisi alat) |
| `ROLES` | Peran pengguna |
| `USER_PRINCIPALS` | Keanggotaan grup yang digunakan untuk menyelesaikan principal ACL |
| `PROMPT_GROUPS_ACCESS` | Kumpulan ID akses grup prompt |
| `AGENT_LINKED_INSTRUCTIONS` | Instruksi yang telah diselesaikan dari grup prompt yang ditautkan ke agen |
| `SANDBOX_PREWARM` | Status pemanasan awal sandbox kode per percakapan |
| `GEN_TITLE` | Judul yang dihasilkan |
| `TOOLS` | Data alat |
| `MODELS_CONFIG` | Konfigurasi model |
| `MODEL_QUERIES` | Kueri model |
| `STARTUP_CONFIG` | Konfigurasi startup |
| `ENDPOINT_CONFIG` | Konfigurasi endpoint |
| `TOKEN_CONFIG` | Konfigurasi token |
| `REASONING_CAPABILITIES` | Tingkat upaya penalaran per model untuk endpoint OpenRouter |
| `PULL_REQUESTS` | Pencarian pull request dan masa tunggu batas laju GitHub |
| `APP_CONFIG` | Konfigurasi aplikasi |
| `ABORT_KEYS` | Kunci pembatalan |
| `BANS` | Data pemblokiran |
| `ENCODED_DOMAINS` | Domain yang dienkode |
| `AUDIO_RUNS` | Proses pemrosesan audio |
| `MESSAGES` | Pesan yang sedang diproses |
| `FLOWS` | Status alur yang sedang berjalan |
| `PENDING_REQ` | Permintaan yang tertunda |
| `S3_EXPIRY_INTERVAL` | Interval kedaluwarsa S3 |
| `OPENID_EXCHANGED_TOKENS` | Token OpenID yang ditukar |
| `AUTH_USER_DOC` | Dokumen pengguna terautentikasi yang di-cache |
| `OPENID_SESSION` | Sesi OpenID |
| `SAML_SESSION` | Sesi SAML |
| `ADMIN_OAUTH_EXCHANGE` | Kode pertukaran OAuth panel admin |
| `PASSKEY_CHALLENGE` | Tantangan seremoni passkey yang tertunda |

<Callout type="warn" title="Kunci tidak valid">
  Menggunakan kunci yang tidak valid (contohnya, `STATIC_CONFIG` yang sudah tidak digunakan lagi) akan menyebabkan kesalahan saat memulai. Hanya gunakan kunci dari tabel di atas.
</Callout>

## Penyetelan Performa [#performance-tuning]

### Connection Keep-Alive [#connection-keep-alive-1]

Aplikasi ini mengimplementasikan keep-alive koneksi yang dapat dikonfigurasi:

- PING main-client dikendalikan oleh `REDIS_PING_INTERVAL` dan dinonaktifkan secara default
- PING pelanggan khusus dikontrol oleh `REDIS_SUBSCRIBER_PING_INTERVAL` dan secara default diatur ke 15 detik
- Heartbeats menggunakan `REDIS_PING_TIMEOUT` untuk mendeteksi soket yang mati secara diam-diam dan memaksa penyambungan kembali
- TCP keepalive menggunakan `REDIS_KEEP_ALIVE`, secara independen dari heartbeat tingkat aplikasi
- Timer heartbeat dibersihkan pada peristiwa disconnect atau close

### Strategi Cache [#cache-strategy]

Aplikasi ini menggunakan pendekatan klien ganda:

- **Klien IoRedis**: Operasi Redis utama dengan pemberian awalan otomatis
- **Klien Keyv Redis**: Operasi lapisan penyimpanan dengan penanganan awalan di `cacheFactory.js`

### Pengaturan Lanjutan Koneksi [#advanced-connection-tuning]

Variabel opsional ini mengatur perilaku koneksi dan operasi cache massal. Nilai default sudah sesuai untuk sebagian besar deployment.

| Variabel | Default | Deskripsi |
| --- | --- | --- |
| `REDIS_CONNECT_TIMEOUT` | `10000` | Batas waktu koneksi dalam milidetik. |
| `REDIS_RETRY_MAX_ATTEMPTS` | `10` | Jumlah maksimum percobaan koneksi ulang sebelum menyerah. `0` berarti mencoba ulang tanpa batas. |
| `REDIS_RETRY_MAX_DELAY` | `3000` | Jeda maksimum antara percobaan koneksi ulang, dalam milidetik. |
| `REDIS_ENABLE_OFFLINE_QUEUE` | `true` | Antrikan perintah saat tidak terhubung. Atur ke `false` untuk langsung menggagalkannya. |
| `REDIS_SCAN_COUNT` | `1000` | Petunjuk `COUNT` untuk operasi `SCAN` saat mencari kunci berdasarkan pola. |
| `REDIS_DELETE_CHUNK_SIZE` | `1000` | Jumlah kunci yang dihapus per batch dalam penghapusan massal. |
| `MCP_REGISTRY_CACHE_TTL` | `5000` | Lama waktu dalam milidetik cache registri MCP disimpan. Ketidaksinkronan antar-instans dapat mencapai dua kali nilai ini. `0` menonaktifkan snapshot lokal, sehingga setiap pembacaan dikirim ke Redis. |

### Optimalisasi Memori [#memory-optimization]

Gunakan `FORCED_IN_MEMORY_CACHE_NAMESPACES` untuk mengoptimalkan performa dengan menyimpan dataset kecil yang sering diakses di dalam memori, sementara tetap menggunakan Redis untuk cache yang lebih besar.

## Resumable Streams [#resumable-streams]

Redis mengaktifkan [Resumable Streams](/docs/features/resumable_streams) untuk deployment yang diskalakan secara horizontal. Saat diaktifkan, respons AI dapat terhubung kembali dan dilanjutkan dengan mulus di seluruh instance server.

**Penting:** Saat `USE_REDIS=true`, aliran yang dapat dilanjutkan (resumable streams) secara otomatis menggunakan Redis untuk koordinasi lintas instans. Ini adalah pengaturan yang direkomendasikan untuk penyebaran berskala horizontal di mana pengguna mungkin terhubung ke instans server yang berbeda.

**Catatan:** Jika Anda menjalankan satu instans LibreChat, Redis untuk resumable streams biasanya berlebihan; mode in-memory bawaan sudah berfungsi dengan baik. Redis menjadi penting ketika Anda memiliki beberapa instans LibreChat di belakang load balancer, di mana koneksi ulang pengguna dapat mengarah ke server yang berbeda dari tempat stream dimulai.

### Konfigurasi [#configuration]

```bash
# Redis enabled = resumable streams automatically use Redis
USE_REDIS=true
REDIS_URI=redis://127.0.0.1:6379

# Optional: explicitly control resumable streams behavior
# USE_REDIS_STREAMS=true  # Enabled by default when USE_REDIS=true
```

### Kompatibilitas Protokol Generasi [#generation-protocol-compatibility]

Klien LibreChat saat ini menegosiasikan protokol generasi v2 secara otomatis dengan setiap penyimpanan generasi bawaan. Tidak diperlukan pengaturan deployment. Generasi yang sudah ada dengan penanda protokol-v1 yang eksplisit atau tersimpan akan tetap mempertahankan perilaku v1 yang tidak dapat diubah melalui steering, pause/resume, retry, dan recovery hingga selesai.

Untuk pembaruan bergulir (rolling upgrade), setiap image API dan worker yang berjalan harus menyertakan jembatan kompatibilitas v2:

- Setiap image API dan worker menjalankan LibreChat `v0.8.8-rc1` atau yang lebih baru.
- Helm chart `2.0.8` atau yang lebih baru memilih image default yang kompatibel; penggantian image kustom tetap harus memenuhi persyaratan image di atas.

Saat melakukan peningkatan dari rilis yang lebih lama, lakukan *cold handoff*: hentikan setiap replika API dan worker yang lama sebelum memulai image yang baru. Hal ini mencegah biner pra-v2 dan v2 otomatis berbagi status generasi di Redis.

<Callout type="warning" title="Keamanan deployment bergulir">
  Jangan menjalankan rilis yang lebih lama dari `v0.8.8-rc1` terhadap status generasi Redis yang sama dengan replika saat ini. Sebelum melakukan rollback di bawah batas kompatibilitas tersebut, pastikan terlebih dahulu bahwa replika saat ini dan generasi protocol-v2 telah dikosongkan (drained).
</Callout>

Aliran pembuatan dalam memori (in-memory generation streams) juga menegosiasikan protokol v2 secara otomatis dan tidak membagikan status pembuatan di seluruh proses.

### Penggabungan Delta Stream [#stream-delta-coalescing]

Stream yang didukung Redis dapat melakukan batch pada publikasi delta untuk mengurangi skrip Redis, round trip, dan CPU pada tingkat token yang tinggi:

```bash filename=".env"
STREAM_DELTA_COALESCE_MS=25
```

Pengaturan ini secara default bernilai `25` milidetik jika tidak diatur. Atur secara eksplisit ke `0` untuk menonaktifkan penggabungan (*coalescing*); nilai di atas `1000` akan dibatasi. Pemrosesan batch dapat menambah latensi pengiriman hingga satu jendela yang dikonfigurasi dan dapat menyebabkan hilangnya data di akhir buffer jika proses penerbitan keluar sebelum melakukan *flush*. Bingkai *chunk* individu tetap dipertahankan untuk kompatibilitas protokol, sehingga pengaturan ini mengurangi beban skrip Redis dan *round-trip* tanpa mengubah format bingkai pelanggan. Aliran pembuatan dalam memori (*in-memory*) tidak berubah.

### Manfaat Utama (untuk Penskalaan Horizontal) [#key-benefits-for-horizontal-scaling]

- **Cross-instance continuity**: Pengguna dapat memulai pembuatan di satu server dan melanjutkannya di server lain
- **Rolling deployments**: Stream aktif tetap bertahan saat server dimulai ulang
- **Sinkronisasi multi-tab**: Percakapan yang sama tersinkronisasi di berbagai tab browser dalam lingkungan *load-balanced*
- **Ketahanan koneksi**: Penyambungan kembali otomatis terlepas dari server mana yang menangani permintaan tersebut

### Konfigurasi Klaster [#cluster-configuration]

Untuk penyebaran Redis Cluster, LibreChat secara otomatis menggunakan kunci dengan hash-tag untuk memastikan operasi stream tetap berada dalam slot cluster yang sama:

```bash
USE_REDIS=true
USE_REDIS_STREAMS=true
USE_REDIS_CLUSTER=true
REDIS_URI=redis://node1:7001,redis://node2:7002,redis://node3:7003
```

Lihat [Resumable Streams](/docs/features/resumable_streams) untuk detail lebih lanjut mengenai fitur ini.

## Koordinasi Katalog MCP [#mcp-catalog-coordination]

Saat Redis diaktifkan, LibreChat mengoordinasikan katalog alat MCP tingkat aplikasi di seluruh replika. Publikasi saat startup, sinkronisasi penyambungan kembali, dan pembaruan `notifications/tools/list_changed` menggunakan penanda generasi dan revisi sehingga replika yang kedaluwarsa tidak dapat menimpa katalog yang lebih baru.

Deployment Redis Cluster menggunakan kunci katalog yang aman untuk slot dan operasi pembaruan; tidak diperlukan pengaturan MCP Redis terpisah. Lihat [MCP Server Management](/docs/configuration/librechat_yaml/object_structure/mcp_servers#additional-information) untuk perilaku katalog dinamis dan kesiapan OAuth.
