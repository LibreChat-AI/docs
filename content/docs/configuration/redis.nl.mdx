Deze gids behandelt hoe je Redis configureert voor caching en sessieopslag in LibreChat. Redis zorgt voor aanzienlijke prestatieverbeteringen en is **vereist voor horizontale schaalvergroting**. Als je meerdere LibreChat-instanties draait achter een load balancer, zorgt Redis voor een consistente status over alle instanties heen.

## Basisconfiguratie [#basic-setup]

### Redis inschakelen [#enable-redis]

Om Redis in LibreChat in te schakelen, stelt u de volgende omgevingsvariabele in uw `.env` bestand in:

```bash
USE_REDIS=true
```

**Belangrijk**: Wanneer `USE_REDIS=true` is ingesteld, moet je ook een `REDIS_URI` opgeven. De applicatie zal een foutmelding geven als Redis is ingeschakeld zonder een verbindings-URI.

## Verbindingstypen [#connection-types]

### Enkele Redis-instantie [#single-redis-instance]

Voor een standaard opstelling met één enkele Redis-server:

```bash
# Local Redis instance
REDIS_URI=redis://127.0.0.1:6379

# Remote Redis instance
REDIS_URI=redis://your-redis-host:6379
```

### Redis Cluster [#redis-cluster]

Voor Redis cluster-implementaties met meerdere nodes:

```bash
# Multiple Redis cluster nodes
REDIS_URI=redis://127.0.0.1:7001,redis://127.0.0.1:7002,redis://127.0.0.1:7003
```

De applicatie detecteert automatisch de cluster-modus wanneer er meerdere URI's worden opgegeven.

Als je redis-cluster slechts één URI heeft, kun je de `USE_REDIS_CLUSTER` omgevingsvariabele gebruiken om de clustermodus in te schakelen:

```bash
# Redis cluster with single URI
REDIS_URI=redis://127.0.0.1:7001
USE_REDIS_CLUSTER=true
```

### Managed Redis-services met één endpoint [#single-endpoint-managed-redis-services]

Sommige beheerde Redis-services, waaronder AWS ElastiCache Serverless en Redis Enterprise Cloud op AWS, stellen één enkel connection endpoint bloot terwijl ze keys intern sharden. Houd LibreChat in die configuratie in single-node connection mode, maar schakel cluster-safe deletes in als het wissen van de cache mislukt met `CROSSSLOT Keys in request don't hash to the same slot`.

```bash
USE_REDIS=true
REDIS_URI=rediss://your-managed-redis-endpoint:6379
USE_REDIS_CLUSTER=false
REDIS_CLUSTER_SAFE_DELETE=true
```

`REDIS_CLUSTER_SAFE_DELETE=true` zorgt ervoor dat LibreChat overeenkomende cache-sleutels één voor één verwijdert in plaats van multi-key `DEL` commando's te sturen. Dit voorkomt `CROSSSLOT` fouten zonder de manier waarop LibreChat verbinding maakt met Redis te veranderen.

Gebruik `USE_REDIS_CLUSTER=true` alleen wanneer LibreChat een Redis Cluster-client moet aanmaken. Voor beheerde services met één endpoint is `REDIS_CLUSTER_SAFE_DELETE=true` de veiligere optie.

### Redis met TLS/SSL [#redis-with-tlsssl]

Voor beveiligde Redis-verbindingen:

```bash
# Redis with TLS encryption
REDIS_URI=rediss://127.0.0.1:6380

# Path to CA certificate for TLS verification
REDIS_CA=/path/to/ca-cert.pem
```

## Beveiligingsconfiguratie [#security-configuration]

### Authenticatie [#authentication]

Configureer Redis-authenticatiegegevens:

```bash
# Method 1: Include credentials in URI
# With both username and password
REDIS_URI=redis://myuser:mypassword@127.0.0.1:6379


# Method 2: Separate environment variables
REDIS_URI=redis://127.0.0.1:6379
REDIS_USERNAME=your_redis_username
REDIS_PASSWORD=your_redis_password
```

**Let op**: Inloggegevens die in `REDIS_URI` zijn opgenomen, hebben voorrang. `REDIS_USERNAME` en `REDIS_PASSWORD` worden alleen als terugvaloptie gebruikt wanneer de URI geen gebruikersnaam of wachtwoord bevat.

### TLS-configuratie [#tls-configuration]

Voor versleutelde verbindingen:

```bash
# Enable TLS with rediss:// protocol
REDIS_URI=rediss://your-redis-host:6380

# Provide CA certificate for verification
REDIS_CA=/path/to/your/ca-certificate.pem
```

### TLS met Elasticache [#tls-with-elasticache]

Elasticache moet mogelijk een alternatieve dnsLookup gebruiken voor TLS-verbindingen. Zie "Special Note: Aws Elasticache Clusters with TLS" op deze webpagina: https://www.npmjs.com/package/ioredis

```bash
# Enable redis alternate dnsLookup
REDIS_USE_ALTERNATIVE_DNS_LOOKUP=true
```

## Geavanceerde opties [#advanced-options]

### Key Prefixing [#key-prefixing]

Redis key prefixing voorkomt contaminatie tussen deployments door cachegegevens te isoleren tussen verschillende omgevingen, versies of instanties die dezelfde Redis-server delen. Dit is essentieel voor:

- **Multi-tenant deployments**: Aparte staging-, productie- en ontwikkelomgevingen
- **Blue-green deployments**: Isoleer de cache tussen verschillende applicatieversies

```bash
# Option 1: Dynamic prefix from environment variable (recommended for cloud)

# Google Cloud Platform - Cloud Run
REDIS_KEY_PREFIX_VAR=K_REVISION

# AWS - ECS/Fargate
REDIS_KEY_PREFIX_VAR=AWS_EXECUTION_ENV

# Azure Container Instances
REDIS_KEY_PREFIX_VAR=CONTAINER_NAME

# Kubernetes - Pod name or deployment
REDIS_KEY_PREFIX_VAR=HOSTNAME
REDIS_KEY_PREFIX_VAR=POD_NAME

# Kubernetes - Custom deployment identifier
REDIS_KEY_PREFIX_VAR=DEPLOYMENT_ID

# Heroku
REDIS_KEY_PREFIX_VAR=DYNO

# Option 2: Static prefix (for manual control)
REDIS_KEY_PREFIX=librechat-prod-v2
REDIS_KEY_PREFIX=staging-branch-feature-x
REDIS_KEY_PREFIX=dev-john-local
```

**Belangrijk**: Je kunt niet tegelijkertijd `REDIS_KEY_PREFIX_VAR` en `REDIS_KEY_PREFIX` instellen.

**Voorbeelden van contaminatie zonder prefix**:

- Productiecache overschreven door staging-deployment
- Feature branch tests corrumperen cache van main branch
- Oude deployment-versies die verouderde gecachte gegevens serveren

**Formaat voor sleutelprefixen**:

- IoRedis-client: `{prefix}::{key}`
- Keyv client: Wordt afgehandeld door de store-laag

### Verbindingslimieten [#connection-limits]

Configureer Redis-verbindingslimieten:

```bash
# Maximum number of event listeners (default: 40)
REDIS_MAX_LISTENERS=40
```

### Connection Keep-Alive [#connection-keep-alive]

Configureer deadline-gebonden Redis heartbeats en TCP keepalive:

```bash
# Redis ping interval in seconds (default: 0 = disabled)
# When set to a positive integer (in seconds), Redis clients will ping the server at this interval
# When unset or 0, no pinging is performed (recommended for most use cases)
# Example: 300 = ping every 5 minutes
REDIS_PING_INTERVAL=300

# Maximum time an enabled heartbeat PING may go unanswered (default: 5000 ms)
REDIS_PING_TIMEOUT=5000

# Dedicated pub/sub subscriber heartbeat (default: 15 seconds, 0 = disabled)
REDIS_SUBSCRIBER_PING_INTERVAL=15

# TCP keepalive idle delay for ioredis sockets (default: 10000 ms, 0 = kernel default)
REDIS_KEEP_ALIVE=10000
```

**Belangrijk**:

- Het instellen van `REDIS_PING_INTERVAL=0` of het weglaten ervan schakelt pingen volledig uit.
- Stel alleen een positieve waarde in (in seconden) als je problemen ervaart met time-outs van de verbinding
- `REDIS_PING_INTERVAL` wordt gespecificeerd in seconden en bestuurt de optionele ioredis-heartbeat van de hoofdverbinding
- Toegewezen pub/sub-abonnees gebruiken hun eigen standaard ingeschakelde interval omdat een inactieve dode socket anders onopgemerkt kan blijven; stel `REDIS_SUBSCRIBER_PING_INTERVAL=0` in om die heartbeat uit te schakelen.
- Elke ingeschakelde heartbeat gebruikt `REDIS_PING_TIMEOUT` als deadline voor de reactie en verbindt de socket opnieuw wanneer een PING onbeantwoord blijft.
- `REDIS_KEEP_ALIVE` configureert de ioredis TCP-socket onafhankelijk van PINGs op applicatieniveau
- Voorbeeldwaarden: `300` (5 minuten), `600` (10 minuten), `60` (1 minuut)

### Replica Failover Herstel [#replica-failover-recovery]

Tijdens een Sentinel-failover kan een gedegradeerde Redis-replica een bestaande socket openhouden terwijl deze schrijfacties weigert met `READONLY`. LibreChat detecteert dit antwoord op de niet-cluster Keyv-client, verbreekt de verouderde verbinding en maakt opnieuw verbinding, zodat de huidige primaire server kan worden opgelost zonder de applicatie opnieuw op te starten.

```bash
# Minimum interval between forced recovery attempts, in milliseconds
# Default: 5000
REDIS_READONLY_RECOVERY_INTERVAL=5000
```

Het interval debounced herverbindingspogingen tijdens een reeks mislukte schrijfacties. Redis Cluster-clients zijn uitgesloten omdat zij gebruikmaken van native cluster-topologie en redirect-afhandeling.

### Health Checks [#health-checks]

LibreChat biedt drie probe-endpoints. Alleen `/readyz` geeft de status van Redis weer:

| Endpoint | Geeft `200 OK` terug | Geeft `503 NOT_READY` terug |
| --- | --- | --- |
| `/livez` | Zolang het proces verzoeken beantwoordt | Nooit |
| `/health` | Zolang het proces verzoeken beantwoordt | Nooit |
| `/readyz` | Nadat het opstarten is voltooid en, met `USE_REDIS=true`, zolang Redis is verbonden | Voordat het opstarten is voltooid, of zolang Redis is ingeschakeld maar niet verbonden |

Wanneer Redis opnieuw wordt opgestart, uitvalt of langer dan het hervraagvenster van de client onbereikbaar is, falen verzoeken die ervan afhankelijk zijn (inloggen, sessies, snelheidsbeperkingen) totdat de verbinding terugkeert. Gedurende die tijd antwoordt `/readyz` met `503`, waardoor een load balancer of Kubernetes readiness probe stopt met het doorsturen van verkeer naar de instantie. Het keert terug naar `200` zodra Redis opnieuw verbinding maakt, zonder herstart. Wanneer Redis is ingeschakeld, moet elke Redis-client verbonden zijn; voor een Redis Cluster betekent dit dat elke primaire node verbonden moet zijn.

Richt readiness-controles op `/readyz` en liveness-controles op `/livez`. Houd Redis buiten de liveness-controle: een liveness-probe die faalt tijdens een Redis-storing herstart alle pods tegelijk en kan Redis niet weer herstellen.

```yaml
livenessProbe:
  httpGet:
    path: /livez
    port: 3080
readinessProbe:
  httpGet:
    path: /readyz
    port: 3080
  periodSeconds: 10
  failureThreshold: 3
```

`/readyz` wacht zelf niet tot korte herverbindingen voorbij zijn, dus gebruik `failureThreshold` om te bepalen hoe lang een storing mag duren voordat het verkeer wordt teruggetrokken.

### Selectieve In-Memory Caching [#selective-in-memory-caching]

Forceer specifieke cache-namespaces om in-memory opslag te gebruiken, zelfs wanneer Redis is ingeschakeld:

```bash
# Comma-separated list of cache keys
FORCED_IN_MEMORY_CACHE_NAMESPACES=CONFIG_STORE,APP_CONFIG,ROLES
```

Wanneer deze variabele niet is ingesteld, is de standaardwaarde `CONFIG_STORE,APP_CONFIG`, zodat configuratie afgeleid van `librechat.yaml` per container blijft. Het instellen van deze variabele **vervangt** de standaardwaarde in plaats van deze aan te vullen. Neem daarom `CONFIG_STORE,APP_CONFIG` op in je lijst, tenzij je die namespaces in Redis wilt hebben. Stel de variabele in op een lege string om elke namespace via Redis te laten lopen.

## Performance Tuning [#performance-tuning]

### Connection Keep-Alive [#connection-keep-alive-1]

De applicatie implementeert configureerbare connection keep-alive:

- Main-client PINGs worden beheerd door `REDIS_PING_INTERVAL` en zijn standaard uitgeschakeld
- Toegewezen abonnee-PINGs worden beheerd door `REDIS_SUBSCRIBER_PING_INTERVAL` en staan standaard op 15 seconden.
- Heartbeats gebruiken `REDIS_PING_TIMEOUT` om stilletjes verbroken sockets te detecteren en een herverbinding af te dwingen
- TCP keepalive gebruikt `REDIS_KEEP_ALIVE`, onafhankelijk van heartbeats op applicatieniveau
- Heartbeat-timers worden gewist bij disconnect- of close-events.

### Cache-strategie [#cache-strategy]

De applicatie maakt gebruik van een dual-client benadering:

- **IoRedis client**: Primaire Redis-bewerkingen met automatische prefixing
- **Keyv Redis client**: Store-layer operaties met prefix-afhandeling in `cacheFactory.js`

### Geavanceerde verbindingsinstellingen [#advanced-connection-tuning]

Deze optionele variabelen stellen het verbindingsgedrag en de bulk-cachebewerkingen bij. De standaardwaarden zijn geschikt voor de meeste implementaties.

| Variabele | Standaard | Beschrijving |
| --- | --- | --- |
| `REDIS_CONNECT_TIMEOUT` | `10000` | Verbindingstimeout in milliseconden. |
| `REDIS_RETRY_MAX_ATTEMPTS` | `10` | Maximaal aantal pogingen om opnieuw verbinding te maken voordat wordt opgegeven. `0` probeert oneindig opnieuw. |
| `REDIS_RETRY_MAX_DELAY` | `3000` | Maximale wachttijd tussen pogingen om opnieuw verbinding te maken, in milliseconden. |
| `REDIS_ENABLE_OFFLINE_QUEUE` | `true` | Zet commando's in de wachtrij terwijl er geen verbinding is. Stel in op `false` om ze direct te laten mislukken. |
| `REDIS_SCAN_COUNT` | `1000` | `COUNT`-hint voor `SCAN`-bewerkingen bij het zoeken naar sleutels op patroon. |
| `REDIS_DELETE_CHUNK_SIZE` | `1000` | Aantal sleutels dat per batch wordt verwijderd bij bulkverwijderingen. |
| `MCP_REGISTRY_CACHE_TTL` | `5000` | Aantal milliseconden dat MCP-registercaches worden bewaard. Verouderde gegevens tussen instanties kunnen maximaal twee keer deze waarde bereiken. `0` schakelt de lokale snapshot uit, waardoor elke lees­actie naar Redis gaat. |

### Geheugenoptimalisatie [#memory-optimization]

Gebruik `FORCED_IN_MEMORY_CACHE_NAMESPACES` om de prestaties te optimaliseren door veelgebruikte, kleine datasets in het geheugen te houden, terwijl Redis wordt gebruikt voor grotere caches.

## Hervatbare Streams [#resumable-streams]

Redis maakt [Resumable Streams](/docs/features/resumable_streams) mogelijk voor horizontaal geschaalde implementaties. Wanneer dit is ingeschakeld, kunnen AI-antwoorden naadloos opnieuw verbinding maken en worden hervat over serverinstanties heen.

**Belangrijk:** Wanneer `USE_REDIS=true` is ingesteld, gebruiken hervatbare streams automatisch Redis voor coördinatie tussen instanties. Dit is de aanbevolen configuratie voor horizontaal geschaalde implementaties waarbij gebruikers verbinding kunnen maken met verschillende serverinstanties.

**Opmerking:** Als je een enkele LibreChat-instantie draait, is Redis voor hervatbare streams doorgaans overbodig; de ingebouwde in-memory modus werkt prima. Redis wordt essentieel wanneer je meerdere LibreChat-instanties achter een load balancer hebt, waarbij de herverbinding van een gebruiker mogelijk op een andere server terechtkomt dan waar de stream is gestart.

### Configuratie [#configuration]

```bash
# Redis enabled = resumable streams automatically use Redis
USE_REDIS=true
REDIS_URI=redis://127.0.0.1:6379

# Optional: explicitly control resumable streams behavior
# USE_REDIS_STREAMS=true  # Enabled by default when USE_REDIS=true
```

### Compatibiliteit met het generatieprotocol [#generation-protocol-compatibility]

Huidige LibreChat-clients onderhandelen automatisch over generatieprotocol v2 met elke ingebouwde generatie-store. Er is geen implementatie-instelling vereist. Bestaande generaties met een expliciete of opgeslagen protocol-v1-markering behouden hun onveranderlijke v1-gedrag via sturing, pauzeren/hervatten, opnieuw proberen en herstel totdat ze zijn voltooid.

Voor een rolling upgrade moet elke draaiende API- en worker-image de v2 compatibility bridge bevatten:

- Elke API- en worker-image draait LibreChat `v0.8.8-rc1` of nieuwer.
- Helm chart `2.0.8` of nieuwer selecteert een compatibele standaard image; een aangepaste image-override moet nog steeds voldoen aan de bovenstaande image-vereiste.

Bij het upgraden vanaf een oudere release moet je een 'cold handoff' uitvoeren: stop elke oude API- en worker-replica voordat je de nieuwe image start. Dit voorkomt dat pre-v2 en automatic-v2 binaries de generatiestatus in Redis delen.

<Callout type="warning" title="Veiligheid bij rolling deployment">
  Draai geen release ouder dan `v0.8.8-rc1` tegen dezelfde Redis-generatiestatus als de huidige replica's. Voordat je terugrolt naar een versie onder deze compatibiliteitsgrens, moet je er eerst voor zorgen dat de huidige replica's en protocol-v2-generaties zijn leeggemaakt.
</Callout>

In-memory generatiestreams onderhandelen ook automatisch over protocol v2 en delen de generatiestatus niet tussen processen.

### Stream Delta Coalescing [#stream-delta-coalescing]

Redis-ondersteunde streams kunnen delta-publicaties batchen om Redis-scripts, round-trips en CPU-gebruik bij hoge token-snelheden te verminderen:

```bash filename=".env"
STREAM_DELTA_COALESCE_MS=25
```

De instelling staat standaard op `25` milliseconden wanneer deze niet is ingesteld. Stel deze expliciet in op `0` om coalescing uit te schakelen; waarden boven `1000` worden begrensd. Batching kan tot één geconfigureerd venster aan afleveringslatentie toevoegen en kan het gebufferde staartstuk verliezen als het publicatieproces wordt afgesloten voordat het is geflushed. Individuele chunk-frames worden behouden voor protocolcompatibiliteit, dus deze instelling vermindert Redis-script- en round-trip-werk zonder het subscriber-frameformaat te wijzigen. In-memory generatiestreams blijven ongewijzigd.

### Belangrijkste voordelen (voor horizontale schaling) [#key-benefits-for-horizontal-scaling]

- **Continuïteit tussen instanties**: Gebruikers kunnen een generatie op de ene server starten en op een andere hervatten
- **Rolling deployments**: Actieve streams overleven serverherstarts
- **Multi-tab sync**: Dezelfde conversatie synchroniseert over meerdere browsertabbladen in een load-balanced omgeving
- **Verbindingsveerkracht**: Automatische herverbinding, ongeacht welke server het verzoek afhandelt

### Clusterconfiguratie [#cluster-configuration]

Voor Redis Cluster-implementaties gebruikt LibreChat automatisch hash-tagged keys om ervoor te zorgen dat stream-bewerkingen binnen dezelfde cluster-slot blijven:

```bash
USE_REDIS=true
USE_REDIS_STREAMS=true
USE_REDIS_CLUSTER=true
REDIS_URI=redis://node1:7001,redis://node2:7002,redis://node3:7003
```

Zie [Resumable Streams](/docs/features/resumable_streams) voor meer details over deze functie.

## MCP Catalog Coördinatie [#mcp-catalog-coordination]

Wanneer Redis is ingeschakeld, coördineert LibreChat MCP-toolcatalogi op applicatieniveau over replica's heen. Publicatie bij het opstarten, synchronisatie bij opnieuw verbinden en `notifications/tools/list_changed` updates gebruiken generatie- en revisiemarkeringen, zodat een verouderde replica geen nieuwere catalogus kan overschrijven.

Redis Cluster-implementaties gebruiken slot-safe catalog keys en update-operaties; er is geen aparte MCP Redis-instelling vereist. Zie [MCP Server Management](/docs/features/mcp#mcp-server-management) voor dynamische catalogus- en OAuth-gereedheidsgedrag.
