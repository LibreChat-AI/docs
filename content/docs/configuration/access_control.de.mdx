Wie sich Rollen, Gruppen und Freigaben für Benutzer verhalten, wird auf der Funktionsseite [Zugriffskontrolle](/docs/features/access_control) beschrieben. Diese Seite behandelt, was ein Administrator einrichtet.

## Funktionsberechtigungen [#feature-permissions]

Jede Rolle verfügt über einen Satz von Schaltern pro Berechtigungstyp. Du kannst sie an drei Stellen ändern:

- In LibreChat, über die Schaltfläche **Admin Settings** in den Panels für Agenten, Prompts, MCP-Server, Memories und Skills (nur für Administratoren).
- In dem [Admin Panel](/docs/features/admin_panel), unter **Access**, für jede Rolle einschließlich benutzerdefinierter Rollen.
- Im [`interface`](/docs/configuration/librechat_yaml/object_structure/interface)-Block von `librechat.yaml`. Diese Schlüssel initialisieren die Berechtigungen der eingebauten `USER`-Rolle nur beim Start, weshalb sie keine unterschiedlichen Einstellungen für benutzerdefinierte Rollen abbilden können.

Die Tabelle listet jeden Berechtigungstyp, den `interface`-Schlüssel, der ihn initialisiert, seine Aktionen und welche Aktionen die `USER`-Rolle standardmäßig besitzt.

| Berechtigungstyp | `interface`-Schlüssel | Aktionen | Standardmäßig aktiviert für `USER` |
| --------------- | --------------- | ------- | ------------------------ |
| `AGENTS` | `agents` | `USE`, `CREATE`, `SHARE`, `SHARE_PUBLIC` | `USE`, `CREATE` |
| `PROMPTS` | `prompts` | `USE`, `CREATE`, `SHARE`, `SHARE_PUBLIC` | `USE`, `CREATE` |
| `MCP_SERVERS` | `mcpServers` | `USE`, `CREATE`, `SHARE`, `SHARE_PUBLIC`, `CONFIGURE_OBO` | `USE`, `CREATE` |
| `SKILLS` | `skills` | `USE`, `CREATE`, `SHARE`, `SHARE_PUBLIC` | `USE`, `CREATE` |
| `REMOTE_AGENTS` | `remoteAgents` | `USE`, `CREATE`, `SHARE`, `SHARE_PUBLIC` | keine |
| `SHARED_LINKS` | `sharedLinks` | `CREATE`, `SHARE`, `SHARE_PUBLIC` | `CREATE`, `SHARE` |
| `SCHEDULES` | `schedules` | `USE`, `CREATE` | `USE`, `CREATE` |
| `MEMORIES` | `memories` | `USE`, `CREATE`, `UPDATE`, `READ`, `OPT_OUT` | alle |
| `BOOKMARKS` | `bookmarks` | `USE` | `USE` |
| `MULTI_CONVO` | `multiConvo` | `USE` | `USE` |
| `TEMPORARY_CHAT` | `temporaryChat` | `USE` | `USE` |
| `RUN_CODE` | `runCode` | `USE` | `USE` |
| `WEB_SEARCH` | `webSearch` | `USE` | `USE` |
| `FILE_SEARCH` | `fileSearch` | `USE` | `USE` |
| `FILE_CITATIONS` | `fileCitations` | `USE` | `USE` |
| `MARKETPLACE` | `marketplace` | `USE` | keine |
| `PEOPLE_PICKER` | `peoplePicker` | `VIEW_USERS`, `VIEW_GROUPS`, `VIEW_ROLES` | alle |

`SHARE` ermöglicht es einer Rolle, Inhalte mit bestimmten Benutzern, Gruppen oder Rollen zu teilen; `SHARE_PUBLIC` ermöglicht es, sie mit allen auf der Instanz zu teilen. `CONFIGURE_OBO` erlaubt es, den On-Behalf-Of-Token-Austausch auf einem MCP-Server einzurichten, der die delegierten Token der Benutzer an diesen Server weiterleitet. Diese Berechtigung ist daher standardmäßig deaktiviert.

## Personenauswahl [#people-picker]

Die `PEOPLE_PICKER`-Aktionen steuern, welche Arten von Prinzipalen eine Rolle im Suchfeld des Teilen-Dialogs finden kann. Das Ausblenden von Rollen ist üblich, wenn das Teilen nach Rolle eine Aufgabe für Administratoren bleiben soll:

```yaml filename="librechat.yaml"
interface:
  peoplePicker:
    users: true
    groups: true
    roles: false
```

Dies ändert nur, was die Suche anzeigt. Bestehende Freigaben mit einem ausgeblendeten Principal-Typ funktionieren weiterhin. Siehe [`interface.peoplePicker`](/docs/configuration/librechat_yaml/object_structure/interface#peoplepicker).

## Entra-ID-Gruppensynchronisierung [#entra-id-group-sync]

Gruppen aus Microsoft Entra ID werden in LibreChat synchronisiert, wenn sich ein Benutzer über OpenID Connect mit Entra anmeldet und `OPENID_REUSE_TOKENS=true` gesetzt ist. LibreChat liest die Gruppenmitgliedschaften des Benutzers bei jeder Anmeldung aus Microsoft Graph und speichert jede Gruppe mit ihrer Entra-Objekt-ID. Dadurch bleibt eine Gruppe, mit der geteilt wird, dieselbe Gruppe, auch wenn sie umbenannt wird. Richten Sie den Anbieter mit [Azure / Entra ID](/docs/configuration/authentication/OAuth2-OIDC/azure) und die Token-Wiederverwendung mit [OpenID Connect Token Reuse](/docs/configuration/authentication/OAuth2-OIDC/token-reuse) ein.

## Weiteren Administrator befördern [#promote-another-admin]

Bei einer Single-Tenant-Bereitstellung erhält das zuerst registrierte Konto die Rolle `ADMIN`. Tenant-spezifische Bereitstellungen befördern niemals ihren ersten Benutzer; Tenant-Administratoren werden stattdessen über einen vertrauenswürdigen administrativen Ablauf bereitgestellt. Um einen anderen bestehenden Benutzer zum Administrator zu machen, verwenden Sie die Seite **Users** im Admin-Panel oder setzen Sie die Rolle direkt in MongoDB:

```js filename="mongosh"
db.users.updateOne({ email: 'USER_EMAIL_ADDRESS' }, { $set: { role: 'ADMIN' } })
```

Der Benutzer sollte sich anschließend ab- und wieder anmelden. Mit OpenID Connect können Sie außerdem über `OPENID_ADMIN_ROLE` die Rolle `ADMIN` aus einer Rolle oder Gruppe des IdP zuweisen; siehe die [.env-Referenz](/docs/configuration/dotenv#openid-connect).

## Administrator-Funktionen [#admin-capabilities]

Berechtigungen werden einem Benutzer, einer Gruppe oder einer Rolle auf der Seite **Grants** im Admin-Panel zugewiesen. Benutzer mit der Rolle `ADMIN` besitzen alle Berechtigungen implizit; alle anderen benötigen zusätzlich zu den Berechtigungen für die Bereiche, die sie verwalten, `access:admin`. Jede `manage:`-Berechtigung impliziert die entsprechende `read:`-Berechtigung, auch pro Abschnitt: `manage:configs:endpoints` gewährt also auch `read:configs:endpoints`. Wer nur abschnittsbezogenen Konfigurationszugriff hat, erhält Konfigurationsantworten, die auf die Abschnitte gefiltert sind, die er lesen darf; ohne jeglichen Konfigurations-Lesezugriff erhält er `403`.

| Fähigkeit | Ermöglicht |
| ---------- | ------ |
| `access:admin` | Anmeldung im Admin-Panel |
| `read:users`, `manage:users` | Anzeigen und Ändern von Benutzerkonten |
| `read:groups`, `manage:groups` | Anzeigen und Ändern von Gruppen und deren Mitgliedern |
| `read:roles`, `manage:roles` | Anzeigen und Ändern von Rollen und deren Berechtigungen |
| `read:configs`, `manage:configs` | Anzeigen und Ändern der Konfiguration; `read:configs:<section>` und `manage:configs:<section>` beschränken dies auf einen einzelnen Abschnitt der obersten Ebene in `librechat.yaml` |
| `assign:configs:user`, `assign:configs:group`, `assign:configs:role` | Zuweisen von Konfigurationsüberschreibungen an diese Art von Prinzipal |
| `read:agents`, `manage:agents` | Anzeigen und Moderieren aller Agenten |
| `read:prompts`, `manage:prompts` | Anzeigen und Moderieren aller Prompts |
| `read:skills`, `manage:skills` | Anzeigen und Moderieren aller Skills |
| `read:sharedlinks`, `manage:sharedlinks` | Anzeigen und Moderieren aller geteilten Links |
| `manage:mcpservers` | Verwalten von MCP-Servern instanzweit |
| `manage:code_environments` | Registrieren und Widerrufen von vom Deployment verwalteten Code-Ausführungs-Workern |
| `read:usage` | Anzeigen von Nutzungsdaten |
| `read:insights` | Anzeigen von [Insights](/docs/features/insights) für alle Agenten |
| `read:audit_log` | Anzeigen, Verifizieren und Exportieren des Audit-Logs für Berechtigungsvergaben. Das Log ist nur anhängbar, daher gibt es kein `manage:`-Gegenstück |

`read:assistants` und `manage:assistants` existieren ebenfalls, sind aber reserviert; derzeit werden sie von nichts durchgesetzt.

## Gruppenmitgliedschafts-Cache [#group-membership-cache]

Um Berechtigungen zu prüfen, sucht LibreChat die Gruppen, denen ein Benutzer angehört, und speichert das Ergebnis fünf Minuten lang im Cache. Änderungen an der Gruppenzugehörigkeit leeren die betroffenen Einträge sofort. Die Rolle des Benutzers wird nicht im Cache gespeichert. Fehler beim Cache oder bei Sperren weichen auf die Datenbank aus und blockieren niemals eine Berechtigungsprüfung.

## Admin-Einblicke [#admin-insights]

Das [Insights](/docs/features/insights)-Dashboard ist standardmäßig deaktiviert. Setzen Sie `ENABLE_INSIGHTS=true` in `.env` und starten Sie LibreChat neu; solange die Funktion deaktiviert ist, antworten die Insights-Routen mit `404` und der Eintrag in der Seitenleiste bleibt ausgeblendet.

Administratoren können es öffnen, sobald es aktiviert ist. Um anderen Zugriff zu gewähren, können Sie entweder `read:insights` (für jeden Agenten) im Admin-Panel vergeben oder für bestimmte Personen oder Gruppen im Freigabedialog eines Agenten **View insights** aktivieren. Nur Administratoren können **View insights** vergeben, die Person benötigt außerdem Zugriff auf den Agenten selbst, und es kann nicht allen gleichzeitig gewährt werden. Insights zeigt Namen, E-Mail-Adressen und die erste Nachricht aktueller Unterhaltungen an, daher sollte es entsprechend sorgfältig vergeben werden.

Jede Insights-Abfrage ist auf den Mandanten des Betrachters beschränkt, und benutzerdefinierte Datumsbereiche sind auf 30 Tage begrenzt.

## Migration von Versionen vor ACL [#migrating-from-pre-acl-versions]

Versionen vor v0.8.0-rc3 verwendeten ein einfacheres Besitzmodell für Agenten und Prompts. Führe nach dem Upgrade die Migrationen aus, damit bestehende Agenten und Prompts weiterhin zugänglich bleiben; LibreChat gibt beim Start eine Warnung aus, wenn es nicht migrierte Agenten findet. Freigegebene Links wurden später ebenfalls in dieses System überführt. Instanzen, die freigegebene Links aus der Zeit davor besitzen, sollten daher zusätzlich die Migration für freigegebene Links ausführen.

Starten Sie mit einem Probelauf, um zu sehen, welche Änderungen vorgenommen würden, und führen Sie danach die Migration aus. Die `:batch`-Varianten verarbeiten jeweils 50 Datensätze, was bei großen Datenbanken hilfreich ist.
