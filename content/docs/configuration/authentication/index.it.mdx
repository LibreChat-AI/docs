> **Nota:** OpenID e SAML non supportano la possibilità di disabilitare solo la registrazione.

L'impostazione `ALLOW_EMAIL_LOGIN=false` nasconde il modulo di accesso tramite email e rifiuta le richieste di credenziali locali o LDAP verso `/api/auth/login`; l'accesso tramite OAuth, OpenID Connect e SAML rimane invariato. `ALLOW_EMAIL_LOGIN_OVERRIDE=true` è destinato esclusivamente a un'integrazione API controllata che necessita ancora dell'accesso tramite credenziali mentre il modulo è nascosto. Ogni utilizzo dell'override registra l'IP della richiesta, pertanto proteggi e monitora attentamente tale percorso.

Suggerimenti rapidi:

- Anche con la registrazione disabilitata, puoi aggiungere utenti direttamente al database utilizzando [lo script create-user](#create-user-script) descritto di seguito.
- Per eliminare un utente, puoi utilizzare [lo script delete-user](#delete-user-script) descritto anche di seguito.

Opzioni di accesso correlate per gli account locali:

- [Passkeys](/docs/configuration/authentication/passkeys): accesso senza password tramite blocco schermo del dispositivo o chiave di sicurezza (`ALLOW_PASSKEY_LOGIN`).
- [Modifica indirizzo email](/docs/configuration/authentication/email#email-address-change): consente agli utenti di modificare la propria email registrata da **Impostazioni > Account** (`ALLOW_EMAIL_CHANGE`, attivo per impostazione predefinita).

## Autenticazione a due fattori obbligatoria [#required-two-factor-authentication]

Gli utenti possono sempre attivare l'autenticazione a due fattori (TOTP) autonomamente da **Settings > Account**. Per renderla obbligatoria, imposta:

```bash filename=".env"
ENFORCE_TWO_FACTOR_AUTHENTICATION=true
```

**A chi si applica:** account locali (email e password) e LDAP. Gli account che effettuano l'accesso tramite OAuth, OpenID Connect o SAML non sono interessati, poiché il loro provider di identità è responsabile dell'MFA. Un account federato che tenta di accedere con una password mentre l'imposizione è attiva viene invitato a utilizzare invece il proprio provider di identità.

**Cosa vedono gli utenti:** un utente senza 2FA che effettua l'accesso (con password, credenziali LDAP o passkey) non ottiene alcuna sessione finché la configurazione non è completa. Viene indirizzato a una schermata di **Autenticazione a due fattori richiesta** ("Il tuo amministratore richiede l'autenticazione a due fattori. Configurala prima di continuare."), scansiona un codice QR con un'app di autenticazione, inserisce un codice per verificare e salva i propri codici di backup. Gli utenti che hanno già effettuato l'accesso vengono spostati nella stessa configurazione la volta successiva in cui la loro sessione viene controllata o aggiornata, e i token di accesso emessi prima della registrazione smettono di funzionare. La sessione di configurazione dura 10 minuti; se scade, l'utente torna alla pagina di login e ricomincia da capo.

**Dopo l'iscrizione:** il controllo **Disabilita 2FA** in **Impostazioni > Account** mostra **Richiesto dall'amministratore** e il server rifiuta i tentativi di disabilitare la 2FA mentre la policy è attiva. Gli utenti possono comunque rigenerare i codici di backup.

## JWT Secret e Refresh Secret [#jwt-secret-and-refresh-secret]

Utilizza valori univoci di almeno 32 byte. Genera valori permanenti con il [Credentials Generator](/toolkit/creds_generator), conservali in modo sicuro e fornisci gli stessi valori a ogni replica di LibreChat.

<OptionTable
  options={[
    ['JWT_SECRET', 'string (hex)', 'Chiave segreta JWT.','JWT_SECRET='],
    ['JWT_REFRESH_SECRET', 'string (hex)', 'Chiave segreta per il refresh dei JWT.','JWT_REFRESH_SECRET='],
  ]}
/>

Quando uno dei due valori è vuoto, LibreChat può generare e riutilizzare un valore dal suo file di credenziali temporanee. Gli stack Docker Compose predefiniti mantengono quel file, ma questo è inteso solo come una comodità di bootstrap. Se il file viene perso o non può essere scritto, le sessioni potrebbero diventare non valide dopo il riavvio. Consulta [Credentials Configuration](/docs/configuration/dotenv#credentials-configuration) per la precedenza, la persistenza e le linee guida per la produzione.

## Sistema di moderazione automatizzato (opzionale) [#automated-moderation-system-optional]

Il sistema di moderazione automatizzato è abilitato per impostazione predefinita. Utilizza un meccanismo di punteggio per tracciare le violazioni degli utenti. Man mano che gli utenti compiono azioni come accessi eccessivi, registrazioni o invio di messaggi, accumulano punteggi di violazione. Al raggiungimento di una soglia prestabilita, l'utente e il suo indirizzo IP vengono temporaneamente bannati. Questo sistema garantisce la sicurezza della piattaforma monitorando e penalizzando le attività rapide o sospette.

Per configurare il sistema di moderazione, consulta [la guida alla configurazione](/docs/configuration/mod_system).

> *Nota: Se desideri che questo funzioni in modalità di sviluppo, dovrai creare un file chiamato `.env.development` nella directory principale e impostare `DOMAIN_CLIENT` su `http://localhost:3090` o su qualsiasi porta fornita da vite durante l'esecuzione di `npm run frontend-dev`*

## Script di gestione utenti [#user-management-scripts]

### Crea User Script [#create-user-script]

Lo script create-user ti consente di aggiungere utenti direttamente al database, anche quando la registrazione è disabilitata. Ecco come utilizzarlo:

1. Per il `docker-compose.yml` predefinito (se utilizzi `docker compose up` per avviare l'app):
   ```bash
   docker compose exec api npm run create-user
   ```

2. Per il `deploy-compose.yml` (se hai seguito la [Guida Docker per Ubuntu](/docs/remote/docker_linux)):
   ```bash
   docker exec -it LibreChat-API /bin/sh -c "cd .. && npm run create-user"
   ```

3. Per lo sviluppo locale (dalla root del progetto):
   ```bash
   npm run create-user
   ```

Segui le istruzioni per inserire l'email e la password del nuovo utente.

### Script di eliminazione utente [#delete-user-script]

Per eliminare un utente, è possibile utilizzare lo script delete-user:

1. Per il `docker-compose.yml` predefinito (se utilizzi `docker compose up` per avviare l'app):
   ```bash
   docker compose exec api npm run delete-user email@domain.com
   ```

2. Per il `deploy-compose.yml` (se hai seguito la [Guida Docker per Ubuntu](/docs/remote/docker_linux)):
   ```bash
   docker exec -it LibreChat-API /bin/sh -c "cd .. && npm run delete-user email@domain.com"
   ```

3. Per lo sviluppo locale (dalla root del progetto):
   ```bash
   npm run delete-user email@domain.com
   ```

Sostituisci `email@domain.com` con l'email dell'utente che desideri eliminare.
