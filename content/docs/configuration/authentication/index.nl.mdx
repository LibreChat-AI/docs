> **Let op:** OpenID en SAML ondersteunen niet de mogelijkheid om alleen registratie uit te schakelen.

Het instellen van `ALLOW_EMAIL_LOGIN=false` verbergt het e-mailinlogformulier en weigert lokale of LDAP-inloggegevens voor `/api/auth/login`; OAuth, OpenID Connect en SAML-aanmeldingen blijven onaangetast. `ALLOW_EMAIL_LOGIN_OVERRIDE=true` is uitsluitend bedoeld voor een gecontroleerde API-integratie die nog steeds inloggegevens vereist terwijl het formulier verborgen is. Elk gebruik van de override logt het IP-adres van het verzoek, dus bescherm en monitor die route zorgvuldig.

Snelle tips:

- Zelfs als registratie is uitgeschakeld, kun je gebruikers direct toevoegen aan de database met behulp van [het create-user script](#create-user-script) dat hieronder wordt beschreven.
- Om een gebruiker te verwijderen, kun je [het delete-user script](#delete-user-script) gebruiken, dat hieronder ook in detail wordt beschreven.

Gerelateerde aanmeldopties voor lokale accounts:

- [Passkeys](/docs/configuration/authentication/passkeys): wachtwoordloos inloggen met een schermvergrendeling van een apparaat of een beveiligingssleutel (`ALLOW_PASSKEY_LOGIN`).
- [Emailadres wijzigen](/docs/configuration/authentication/email#email-address-change): stelt gebruikers in staat om hun geregistreerde e-mailadres te wijzigen via **Instellingen > Account** (`ALLOW_EMAIL_CHANGE`, standaard ingeschakeld).

## Vereiste tweefactorauthenticatie [#required-two-factor-authentication]

Gebruikers kunnen tweefactorauthenticatie (TOTP) altijd zelf inschakelen via **Settings > Account**. Om dit verplicht te stellen, stel het volgende in:

```bash filename=".env"
ENFORCE_TWO_FACTOR_AUTHENTICATION=true
```

**Op wie dit van toepassing is:** lokale (e-mail en wachtwoord) en LDAP-accounts. Accounts die inloggen via OAuth, OpenID Connect of SAML worden niet beïnvloed, omdat hun identiteitsprovider verantwoordelijk is voor MFA. Een gefedereerd account dat probeert in te loggen met een wachtwoord terwijl handhaving is ingeschakeld, krijgt de melding om in plaats daarvan de identiteitsprovider te gebruiken.

**Wat gebruikers zien:** een gebruiker zonder 2FA die inlogt (met een wachtwoord, LDAP-inloggegevens of een passkey) krijgt geen sessie totdat de configuratie is voltooid. Ze komen terecht op een **Two-Factor Authentication Required**-scherm ("Your administrator requires two-factor authentication. Set it up before continuing."), scannen een QR-code met een authenticator-app, voeren een code in om te verifiëren en slaan hun back-upcodes op. Gebruikers die al zijn ingelogd, worden naar dezelfde configuratie geleid zodra hun sessie de volgende keer wordt gecontroleerd of vernieuwd, en toegangstokens die vóór de inschrijving zijn uitgegeven, werken niet meer. De configuratiesessie duurt 10 minuten; als deze verloopt, keert de gebruiker terug naar de inlogpagina en begint het proces opnieuw.

**Na inschrijving:** de **Disable 2FA**-besturing in **Settings > Account** toont **Required by administrator**, en de server weigert pogingen om 2FA uit te schakelen terwijl het beleid actief is. Gebruikers kunnen nog steeds back-upcodes opnieuw genereren.

- Standaardwaarden: sessieverloop: 15 minuten, verloop van refresh token: 7 dagen

    Server-->>Client: Requested data

## JWT Secret en Refresh Secret [#jwt-secret-and-refresh-secret]

Gebruik unieke waarden van ten minste 32 bytes. Genereer permanente waarden met de [Credentials Generator](/toolkit/creds_generator), sla deze veilig op en verstrek dezelfde waarden aan elke LibreChat replica.

<OptionTable
  options={[
    ['JWT_SECRET', 'string (hex)', 'JWT geheime sleutel.','JWT_SECRET='],
    ['JWT_REFRESH_SECRET', 'string (hex)', 'JWT refresh secret key.','JWT_REFRESH_SECRET='],
  ]}
/>

Wanneer een van beide waarden leeg is, kan LibreChat een waarde genereren en hergebruiken vanuit het tijdelijke inloggegevensbestand. De standaard Docker Compose stacks behouden dat bestand, maar dit is alleen bedoeld als een bootstrap-gemak. Als het bestand verloren gaat of niet kan worden geschreven, kunnen sessies na een herstart ongeldig worden. Zie [Credentials Configuration](/docs/configuration/dotenv#credentials-configuration) voor prioriteit, persistentie en richtlijnen voor productie.

## Geautomatiseerd moderatiesysteem (optioneel) [#automated-moderation-system-optional]

Het Automated Moderation System is standaard ingeschakeld. Het maakt gebruik van een scoresysteem om gebruikersovertredingen bij te houden. Wanneer gebruikers acties uitvoeren zoals overmatig inloggen, registreren of berichten sturen, verzamelen zij overtredingspunten. Bij het bereiken van een ingestelde drempelwaarde worden de gebruiker en hun IP-adres tijdelijk verbannen. Dit systeem waarborgt de platformbeveiliging door snelle of verdachte activiteiten te monitoren en te bestraffen.

Om het mod-systeem in te stellen, bekijk [de installatiehandleiding](/docs/configuration/mod_system).

> *Let op: Als je wilt dat dit werkt in de development-modus, moet je een bestand genaamd `.env.development` aanmaken in de hoofdmap en `DOMAIN_CLIENT` instellen op `http://localhost:3090` of de poort die door vite wordt verstrekt bij het uitvoeren van `npm run frontend-dev`*

## Gebruikersbeheerscripts [#user-management-scripts]

### Gebruikersscript aanmaken [#create-user-script]

Het create-user script stelt je in staat om gebruikers direct aan de database toe te voegen, zelfs wanneer registratie is uitgeschakeld. Zo gebruik je het:

1. Voor de standaard `docker-compose.yml` (als je `docker compose up` gebruikt om de app te starten):
   ```bash
   docker compose exec api npm run create-user
   ```

2. Voor de `deploy-compose.yml` (als je de [Ubuntu Docker Guide](/docs/remote/docker_linux) hebt gevolgd):
   ```bash
   docker exec -it LibreChat-API /bin/sh -c "cd .. && npm run create-user"
   ```

3. Voor lokale ontwikkeling (vanaf de project root):
   ```bash
   npm run create-user
   ```

Volg de aanwijzingen om het e-mailadres en wachtwoord van de nieuwe gebruiker in te voeren.

### Gebruikersscript verwijderen [#delete-user-script]

Om een gebruiker te verwijderen, kun je het delete-user script gebruiken:

1. Voor de standaard `docker-compose.yml` (als je `docker compose up` gebruikt om de app te starten):
   ```bash
   docker compose exec api npm run delete-user email@domain.com
   ```

2. Voor de `deploy-compose.yml` (als je de [Ubuntu Docker Guide](/docs/remote/docker_linux) hebt gevolgd):
   ```bash
   docker exec -it LibreChat-API /bin/sh -c "cd .. && npm run delete-user email@domain.com"
   ```

3. Voor lokale ontwikkeling (vanaf de project root):
   ```bash
   npm run delete-user email@domain.com
   ```

Vervang `email@domain.com` door het e-mailadres van de gebruiker die je wilt verwijderen.
