### OpenID JWT User Cache [#openid-jwt-user-cache]

Implementaties met een hoge aanvraagsnelheid kunnen `AUTH_USER_CACHE_MODE=on` instellen om het gebruikersdocument dat is opgelost voor OpenID JWT-authenticatie gedurende vijf seconden te cachen. Dit vermindert herhaalde databaseleesacties tijdens korte pieken in aanvragen zonder de levensduur van het authenticatietoken te verlengen.

De cache staat standaard uit en vereist `USE_REDIS=true` met de `AUTH_USER_DOC` namespace ondersteund door Redis. LibreChat schakelt de modus uit en logt een waarschuwing wanneer aan deze vereisten niet wordt voldaan. Gecachte documenten worden opgeschoond voordat ze worden opgeslagen en worden ongeldig gemaakt wanneer de gebruiker wordt bijgewerkt.

```bash filename=".env"
USE_REDIS=true
AUTH_USER_CACHE_MODE=on
```

## Problemen oplossen met OpenID Connect [#troubleshooting-openid-connect]

Als u problemen ondervindt met OpenID Connect-authenticatie:

1. **Header-debuglogboekregistratie inschakelen**: Stel `DEBUG_OPENID_REQUESTS=true` in uw omgevingsvariabelen in om naast URL's ook aanvraagheaders te loggen (waarbij gevoelige gegevens worden gemaskeerd). Let op: Aanvraag-URL's worden altijd op debug-niveau gelogd.
2. **Controleer Redirect URIs**: Zorg ervoor dat je callback-URL exact overeenkomt tussen je provider en de LibreChat configuratie
3. **Scopes verifiëren**: Zorg ervoor dat alle vereiste scopes correct zijn geconfigureerd
4. **Review Provider Logs**: Controleer de logs van uw identiteitsprovider op authenticatiefouten
5. **Tokens valideren**: Zorg ervoor dat uw provider geldige tokens uitgeeft met de verwachte claims
6. **Zorg ervoor dat _nonce_ wordt gegenereerd**: Sommige identiteitsaanbieders genereren een `nonce` url-parameter als deze ontbreekt in het verzoek. Stel `OPENID_GENERATE_NONCE=true` in om de openid-client te dwingen deze te genereren.

### Ontdekkingspogingen [#discovery-retries]

Als uw identity provider tijdens het opstarten van LibreChat niet bereikbaar is, kan de OpenID-discovery opnieuw worden geprobeerd. `OPENID_DISCOVERY_RETRY_ATTEMPTS` bepaalt het aantal pogingen voordat het opstarten doorgaat (0 tot 100, standaard 1; `0` probeert alleen opnieuw op de achtergrond), en `OPENID_DISCOVERY_RETRY_DELAY_MS` bepaalt de wachttijd tussen pogingen (standaard 5000). Waarden die zijn ingesteld onder `registration.openidDiscovery` in `librechat.yaml` hebben voorrang. Zie [registration](/docs/configuration/librechat_yaml/object_structure/registration) voor die sleutels en voor `oauthStateTtlMs`, dat bepaalt hoe lang een gestarte social login mag duren voordat deze de callback bereikt (standaard 10 minuten).

### Oorsprong van profielavatars [#profile-avatar-origins]

Bij het ophalen van de profielfoto (avatar) van de gebruiker stuurt LibreChat het toegangstoken alleen naar de issuer- en userinfo-origins van de provider. Als de avatar wordt geleverd vanaf een andere origin die het token vereist, voeg die dan toe aan `OPENID_AVATAR_AUTHORIZED_ORIGINS` als een lijst van URL's, gescheiden door komma's of spaties.

```bash filename=".env"
OPENID_AVATAR_AUTHORIZED_ORIGINS=https://graph.example.com,https://photos.example.com
```

### Omleidingen in het Admin Panel [#admin-panel-redirects]

If the Admin Panel is hosted on a separate URL from LibreChat, set [`ADMIN_PANEL_URL`](/docs/configuration/admin_panel#redirect-url) in the LibreChat API environment. This tells LibreChat where to send admins after the admin OAuth or SSO callback completes.
