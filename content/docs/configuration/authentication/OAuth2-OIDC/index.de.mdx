### OpenID JWT Benutzer-Cache [#openid-jwt-user-cache]

Bereitstellungen mit hoher Anfragerate können `AUTH_USER_CACHE_MODE=on` setzen, um das für die OpenID JWT-Authentifizierung aufgelöste Benutzerdokument für fünf Sekunden zwischenzuspeichern. Dies reduziert wiederholte Datenbanklesevorgänge bei kurzen Anfragespitzen, ohne die Lebensdauer des Authentifizierungs-Tokens zu verlängern.

Der Cache ist standardmäßig deaktiviert und erfordert `USE_REDIS=true` mit dem durch Redis unterstützten `AUTH_USER_DOC`-Namespace. LibreChat deaktiviert den Modus und protokolliert eine Warnung, wenn diese Anforderungen nicht erfüllt sind. Zwischengespeicherte Dokumente werden vor der Speicherung bereinigt und bei einer Aktualisierung des Benutzers ungültig gemacht.

```bash filename=".env"
USE_REDIS=true
AUTH_USER_CACHE_MODE=on
```

## Fehlerbehebung bei OpenID Connect [#troubleshooting-openid-connect]

Falls Probleme mit der OpenID Connect-Authentifizierung auftreten:

1. **Header-Debug-Logging aktivieren**: Setzen Sie `DEBUG_OPENID_REQUESTS=true` in Ihren Umgebungsvariablen, um zusätzlich zu den URLs auch Anfrage-Header zu protokollieren (wobei sensible Daten maskiert werden). Hinweis: Anfrage-URLs werden immer auf der Debug-Ebene protokolliert.
2. **Redirect-URIs überprüfen**: Stellen Sie sicher, dass Ihre Callback-URL exakt zwischen Ihrem Anbieter und der LibreChat-Konfiguration übereinstimmt.
3. **Scopes überprüfen**: Stellen Sie sicher, dass alle erforderlichen Scopes ordnungsgemäß konfiguriert sind
4. **Anbieter-Logs überprüfen**: Überprüfen Sie die Logs Ihres Identitätsanbieters auf Authentifizierungsfehler
5. **Token validieren**: Stellen Sie sicher, dass Ihr Provider gültige Token mit den erwarteten Claims ausstellt
6. **Stellen Sie sicher, dass _nonce_ generiert wird**: Einige Identitätsanbieter generieren den `nonce` URL-Parameter, falls er in der Anfrage fehlt. Setzen Sie `OPENID_GENERATE_NONCE=true`, um den openid-client dazu zu zwingen, diesen zu generieren.

### Discovery-Wiederholungen [#discovery-retries]

Falls Ihr Identity Provider beim Start von LibreChat nicht erreichbar ist, kann die OpenID-Discovery erneut versucht werden. `OPENID_DISCOVERY_RETRY_ATTEMPTS` legt die Anzahl der Versuche fest, die unternommen werden, bevor der Start fortgesetzt wird (0 bis 100, Standard 1; `0` wiederholt nur im Hintergrund), und `OPENID_DISCOVERY_RETRY_DELAY_MS` legt die Verzögerung zwischen den Versuchen fest (Standard 5000). Werte, die unter `registration.openidDiscovery` in `librechat.yaml` gesetzt werden, haben Vorrang. Informationen zu diesen Schlüsseln sowie zu `oauthStateTtlMs`, das steuert, wie lange ein gestarteter Social Login bis zu seinem Callback benötigen darf (Standard 10 Minuten), finden Sie unter [registration](/docs/configuration/librechat_yaml/object_structure/registration).

### Herkunft der Profilbilder [#profile-avatar-origins]

Beim Abrufen des Profilbilds (Avatars) des Benutzers sendet LibreChat das Zugriffstoken nur an die Ursprünge (Origins) des Ausstellers (Issuer) und des Userinfo-Endpunkts des Anbieters. Wird das Avatar von einem anderen Ursprung bereitgestellt, der das Token erfordert, fügen Sie diesen in `OPENID_AVATAR_AUTHORIZED_ORIGINS` als durch Kommas oder Leerzeichen getrennte Liste von URLs hinzu.

```bash filename=".env"
OPENID_AVATAR_AUTHORIZED_ORIGINS=https://graph.example.com,https://photos.example.com
```

### Admin-Panel-Weiterleitungen [#admin-panel-redirects]

If the Admin Panel is hosted on a separate URL from LibreChat, set [`ADMIN_PANEL_URL`](/docs/configuration/admin_panel#redirect-url) in the LibreChat API environment. This tells LibreChat where to send admins after the admin OAuth or SSO callback completes.
