### Cache utilisateur OpenID JWT [#openid-jwt-user-cache]

Les déploiements à haut débit de requêtes peuvent définir `AUTH_USER_CACHE_MODE=on` pour mettre en cache le document utilisateur résolu pour l'authentification OpenID JWT pendant cinq secondes. Cela réduit les lectures répétées dans la base de données lors de courtes rafales de requêtes sans prolonger la durée de vie du jeton d'authentification.

Le cache est désactivé par défaut et nécessite `USE_REDIS=true` avec l'espace de noms `AUTH_USER_DOC` pris en charge par Redis. LibreChat désactive le mode et enregistre un avertissement lorsque ces exigences ne sont pas remplies. Les documents mis en cache sont nettoyés avant d'être stockés et invalidés lorsque l'utilisateur est mis à jour.

```bash filename=".env"
USE_REDIS=true
AUTH_USER_CACHE_MODE=on
```

## Dépannage d'OpenID Connect [#troubleshooting-openid-connect]

Si vous rencontrez des problèmes avec l'authentification OpenID Connect :

1. **Activer la journalisation de débogage des en-têtes** : Définissez `DEBUG_OPENID_REQUESTS=true` dans vos variables d'environnement pour journaliser les en-têtes de requête en plus des URL (avec les données sensibles masquées). Notez que les URL de requête sont toujours journalisées au niveau de débogage.
2. **Vérifier les URI de redirection** : Assurez-vous que votre URL de rappel correspond exactement entre votre fournisseur et la configuration de LibreChat
3. **Vérifier les scopes** : Assurez-vous que tous les scopes requis sont correctement configurés
4. **Examiner les journaux du fournisseur** : Vérifiez les journaux de votre fournisseur d'identité pour détecter les erreurs d'authentification
5. **Valider les jetons** : Assurez-vous que votre fournisseur émet des jetons valides avec les revendications attendues
6. **Assurez-vous que le _nonce_ est généré** : Certains fournisseurs d'identité génèrent le paramètre d'URL `nonce` s'il est absent de la requête. Définissez `OPENID_GENERATE_NONCE=true` pour forcer le openid-client à le générer.

### Nouvelles tentatives de découverte [#discovery-retries]

Si votre fournisseur d'identité est injoignable au démarrage de LibreChat, la découverte OpenID peut être relancée. `OPENID_DISCOVERY_RETRY_ATTEMPTS` définit le nombre de tentatives effectuées avant que le démarrage ne se poursuive (de 0 à 100, valeur par défaut : 1 ; `0` ne relance qu'en arrière-plan), et `OPENID_DISCOVERY_RETRY_DELAY_MS` définit le délai entre les tentatives (par défaut : 5000). Les valeurs définies sous `registration.openidDiscovery` dans `librechat.yaml` sont prioritaires. Consultez [registration](/docs/configuration/librechat_yaml/object_structure/registration) pour ces clés, ainsi que pour `oauthStateTtlMs`, qui contrôle le délai maximal entre le lancement d'une connexion sociale et son retour de rappel (par défaut : 10 minutes).

### Origines des avatars de profil [#profile-avatar-origins]

Lors de la récupération de l'avatar du profil utilisateur, LibreChat n'envoie le jeton d'accès qu'aux origines de l'émetteur et du point de terminaison userinfo du fournisseur. Si l'avatar est servi depuis une autre origine qui exige le jeton, ajoutez-la à `OPENID_AVATAR_AUTHORIZED_ORIGINS` sous forme de liste d'URL séparées par des virgules ou des espaces.

```bash filename=".env"
OPENID_AVATAR_AUTHORIZED_ORIGINS=https://graph.example.com,https://photos.example.com
```

### Redirections du panneau d'administration [#admin-panel-redirects]

Si le Panneau d'administration est hébergé sur une URL distincte de LibreChat, définissez [`ADMIN_PANEL_URL`](/docs/configuration/admin_panel#redirect-url) dans l'environnement de l'API LibreChat. Cela indique à LibreChat où rediriger les administrateurs une fois le callback OAuth ou SSO d'administration terminé.
