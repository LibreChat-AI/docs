### Caché de usuario OpenID JWT [#openid-jwt-user-cache]

Las implementaciones con una alta tasa de solicitudes pueden configurar `AUTH_USER_CACHE_MODE=on` para almacenar en caché el documento de usuario resuelto para la autenticación OpenID JWT durante cinco segundos. Esto reduce las lecturas repetidas de la base de datos durante ráfagas cortas de solicitudes sin extender el tiempo de vida del token de autenticación.

La caché está desactivada de forma predeterminada y requiere `USE_REDIS=true` con el espacio de nombres `AUTH_USER_DOC` respaldado por Redis. LibreChat deshabilita el modo y registra una advertencia cuando no se cumplen esos requisitos. Los documentos en caché se desinfectan antes de su almacenamiento y se invalidan cuando el usuario es actualizado.

```bash filename=".env"
USE_REDIS=true
AUTH_USER_CACHE_MODE=on
```

## Solución de problemas de OpenID Connect [#troubleshooting-openid-connect]

Si encuentras problemas con la autenticación de OpenID Connect:

1. **Habilitar el registro de depuración de encabezados**: Establezca `DEBUG_OPENID_REQUESTS=true` en sus variables de entorno para registrar los encabezados de las solicitudes además de las URLs (con los datos confidenciales enmascarados). Tenga en cuenta que las URLs de las solicitudes siempre se registran en el nivel de depuración.
2. **Verificar URIs de redirección**: Asegúrese de que su URL de callback coincida exactamente entre su proveedor y la configuración de LibreChat
3. **Verificar Scopes**: Asegúrese de que todos los scopes requeridos estén configurados correctamente
4. **Revisar los registros del proveedor**: Compruebe los registros de su proveedor de identidad para detectar errores de autenticación
5. **Validar tokens**: Asegúrese de que su proveedor esté emitiendo tokens válidos con las declaraciones esperadas
6. **Asegúrese de que se genere el _nonce_**: Algunos proveedores de identidad generan el parámetro de URL `nonce` si falta en la solicitud. Establezca `OPENID_GENERATE_NONCE=true` para forzar a openid-client a generarlo.

### Reintentos de descubrimiento [#discovery-retries]

Si tu proveedor de identidad no está disponible cuando LibreChat se inicia, el descubrimiento de OpenID puede reintentarse. `OPENID_DISCOVERY_RETRY_ATTEMPTS` define el número de intentos realizados antes de que el inicio continúe (de 0 a 100, por defecto 1; `0` reintenta solo en segundo plano), y `OPENID_DISCOVERY_RETRY_DELAY_MS` define el tiempo de espera entre intentos (por defecto 5000). Los valores definidos en `registration.openidDiscovery` dentro de `librechat.yaml` tienen prioridad. Consulta [registration](/docs/configuration/librechat_yaml/object_structure/registration) para conocer esas claves y `oauthStateTtlMs`, que controla cuánto tiempo puede tardar un inicio de sesión social en llegar a su callback (por defecto 10 minutos).

### Orígenes del avatar de perfil [#profile-avatar-origins]

Al obtener el avatar del perfil del usuario, LibreChat envía el token de acceso únicamente a los orígenes del emisor (issuer) y de userinfo del proveedor. Si el avatar se sirve desde otro origen que requiere el token, añádalo a `OPENID_AVATAR_AUTHORIZED_ORIGINS` como una lista de URL separadas por comas o espacios.

```bash filename=".env"
OPENID_AVATAR_AUTHORIZED_ORIGINS=https://graph.example.com,https://photos.example.com
```

### Redirecciones del Panel de Administración [#admin-panel-redirects]

Si el Panel de Administración está alojado en una URL separada de LibreChat, configura [`ADMIN_PANEL_URL`](/docs/configuration/admin_panel#redirect-url) en el entorno de la API de LibreChat. Esto le indica a LibreChat a dónde enviar a los administradores una vez que se complete la devolución de llamada de OAuth o SSO del administrador.
