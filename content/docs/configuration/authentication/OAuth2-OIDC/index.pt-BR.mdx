### Cache de Usuário JWT OpenID [#openid-jwt-user-cache]

Implantações com alta taxa de solicitações podem definir `AUTH_USER_CACHE_MODE=on` para armazenar em cache o documento do usuário resolvido para autenticação OpenID JWT por cinco segundos. Isso reduz leituras repetidas no banco de dados durante picos curtos de solicitações, sem estender o tempo de vida do token de autenticação.

O cache está desativado por padrão e requer `USE_REDIS=true` com o namespace `AUTH_USER_DOC` suportado pelo Redis. O LibreChat desativa o modo e registra um aviso quando esses requisitos não são atendidos. Os documentos em cache são higienizados antes do armazenamento e invalidados quando o usuário é atualizado.

```bash filename=".env"
USE_REDIS=true
AUTH_USER_CACHE_MODE=on
```

## Solução de problemas do OpenID Connect [#troubleshooting-openid-connect]

Se você encontrar problemas com a autenticação OpenID Connect:

1. **Habilitar Log de Depuração de Cabeçalho**: Defina `DEBUG_OPENID_REQUESTS=true` em suas variáveis de ambiente para registrar os cabeçalhos das requisições além das URLs (com dados sensíveis mascarados). Observe que as URLs das requisições são sempre registradas no nível de depuração.
2. **Verificar URIs de Redirecionamento**: Certifique-se de que sua URL de retorno corresponda exatamente entre seu provedor e a configuração do LibreChat
3. **Verificar Escopos**: Certifique-se de que todos os escopos necessários estejam configurados corretamente
4. **Revisar Logs do Provedor**: Verifique os logs do seu provedor de identidade para erros de autenticação
5. **Validar Tokens**: Certifique-se de que seu provedor esteja emitindo tokens válidos com as declarações (claims) esperadas
6. **Garanta que o _nonce_ seja gerado**: Alguns provedores de identidade geram o parâmetro de URL `nonce` caso ele esteja ausente na requisição. Defina `OPENID_GENERATE_NONCE=true` para forçar o openid-client a gerá-lo.

### Tentativas de Descoberta [#discovery-retries]

Se o seu provedor de identidade estiver inacessível quando o LibreChat iniciar, a descoberta do OpenID pode ser tentada novamente. `OPENID_DISCOVERY_RETRY_ATTEMPTS` define o número de tentativas feitas antes que a inicialização continue (0 a 100, padrão 1; `0` tenta novamente apenas em segundo plano), e `OPENID_DISCOVERY_RETRY_DELAY_MS` define o intervalo entre as tentativas (padrão 5000). Os valores definidos em `registration.openidDiscovery` no `librechat.yaml` têm precedência. Consulte [registration](/docs/configuration/librechat_yaml/object_structure/registration) para essas chaves e para `oauthStateTtlMs`, que controla por quanto tempo um login social iniciado pode levar para chegar ao seu callback (padrão 10 minutos).

### Origens do Avatar de Perfil [#profile-avatar-origins]

Ao buscar o avatar do perfil do usuário, o LibreChat envia o token de acesso apenas para as origens do emissor (issuer) e do userinfo do provedor. Se o avatar for servido de outra origem que exija o token, adicione-a em `OPENID_AVATAR_AUTHORIZED_ORIGINS` como uma lista de URLs separadas por vírgula ou espaço.

```bash filename=".env"
OPENID_AVATAR_AUTHORIZED_ORIGINS=https://graph.example.com,https://photos.example.com
```

### Redirecionamentos do Painel de Administração [#admin-panel-redirects]

Se o Admin Panel estiver hospedado em uma URL separada do LibreChat, defina [`ADMIN_PANEL_URL`](/docs/features/admin_panel#librechat-redirect-url) no ambiente da API do LibreChat. Isso informa ao LibreChat para onde enviar os administradores após a conclusão do callback de OAuth ou SSO do administrador.
