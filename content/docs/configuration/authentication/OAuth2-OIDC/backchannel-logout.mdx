OpenID back-channel logout lets your identity provider tell LibreChat that a provider session has ended. LibreChat then denies the next restoration or renewal of credentials linked to that session. Other provider sessions for the same user remain active.

<Callout type="info" title="Required LibreChat version">
  This feature requires a LibreChat build that includes [PR #17856](https://github.com/LibreChat-AI/LibreChat/pull/17856). Check that your deployed version includes it before adding this configuration.
</Callout>

An access token already issued remains valid until its own expiry. LibreChat does not check provider-session records on every authenticated request. With LibreChat-issued tokens, the lifetime is set by `SESSION_EXPIRY`. With [OpenID token reuse](/docs/configuration/authentication/OAuth2-OIDC/token-reuse), token expiry comes from the provider.

## Provider setup

Complete your provider's normal OpenID login setup first. Configure its back-channel logout URL to reach your LibreChat server:

```text
https://chat.example.com/oauth/openid/backchannel-logout
```

The provider sends an HTTP `POST` with `Content-Type: application/x-www-form-urlencoded` and a signed `logout_token` field. Allow these server-to-server requests through your reverse proxy and firewall. The login callback at `/oauth/openid/callback` and the post-logout browser redirect are separate URLs.

LibreChat requires the same session ID (`sid`) in the verified login ID token and the logout token. It identifies the session by issuer, client ID, and `sid`. A logout applies to all LibreChat credentials linked to that key, including credentials in different LibreChat tenants. It does not end every session for the user.

The logout token must use an allowed asymmetric signing algorithm. It must also contain the expected issuer and client audience, `iat`, `jti`, `sid`, and the back-channel logout event. It must not contain `nonce`. Tokens with only a subject (`sub`) and no `sid` are rejected. If a subject is supplied, it must match the subject already stored for that session.

`OPENID_USE_END_SESSION_ENDPOINT` controls the browser redirect to the provider when a user signs out of LibreChat. It does not enable this receiver. Configure the receiver through `librechat.yaml` as described below.

### Keycloak

In the LibreChat client's logout settings, turn **Front channel logout** off. Set **Backchannel logout URL** to the URL above and turn **Backchannel logout session required** on. This makes Keycloak include the session ID in logout tokens. See the [Keycloak logout settings](https://www.keycloak.org/docs/latest/server_admin/index.html#_oidc_clients).

### Auth0

Check that your tenant supports back-channel logout. Auth0 documents this feature for Enterprise plans. In **Applications → your application → Settings → OpenID Connect Back-Channel Logout**, set **Back-Channel Logout URI** to the URL above. Auth0 requires a publicly reachable HTTPS endpoint. See [Auth0 setup and availability](https://auth0.com/docs/authenticate/login/logout/back-channel-logout/configure-back-channel-logout).

After configuring it, use a fresh login to LibreChat. Test the actual logout action you plan to use, including logout from another application that shares the provider session. Confirm that it delivers a token with the matching `sid`. Provider support alone does not prove that every logout action sends a notification.

## Configure LibreChat

Add this block to your existing `librechat.yaml`. Start with `off` while deploying the new code to all replicas.

```yaml filename="librechat.yaml"
registration:
  openidBackchannelLogout:
    mode: off
```

All settings and limits are listed in the [registration reference](/docs/configuration/librechat_yaml/object_structure/registration#openidbackchannellogout). Settings are loaded once per process. Restart every LibreChat replica after changing them.

### Choose a mode

| Mode | Logout receiver | Known revoked session | Missing binding or record | Provider-session authorization database error |
| --- | --- | --- | --- | --- |
| `off` (default) | Returns 404 | No check | No check | No provider-session database operations |
| `record` | Enabled | Denies renewal or restoration | Allows | Allows |
| `enforce` | Enabled | Denies renewal or restoration | Denies; sign in again | Temporary failure; retry |

**`record` can sign users out.** Both enabled modes deny a session already known to be revoked. They also reject a conflicting subject. `record` permits missing bindings and failures in provider-session creation or authorization. It does not tolerate every authentication failure: configuration errors, admin refresh coordination, and refresh-token recovery failures can still prevent renewal.

The receiver returns 503 if it cannot validate or save a logout, in either enabled mode. It never reports successful delivery when storage is unavailable.

A fresh OpenID login creates the session binding. Renewal keeps an existing binding but does not add one to an older unbound session. In `enforce`, a new OpenID login without `sid` fails with `OPENID_SESSION_ID_MISSING`.

## Rollout and verification

1. Deploy a build with this feature to every replica using `mode: off`. Keep that mode during the code rollout. Older replicas can lose bindings when they rotate credentials.
2. Configure the provider's logout URL. Change to `mode: record` and restart every replica. Use fresh OpenID logins to establish bindings.
3. Sign in to LibreChat in two separate provider sessions. Trigger a real provider logout for one session. Confirm that the receiver returns 200, renewal of that session is denied, and the other session still works. An already issued access token can work until it expires.
4. Confirm that a new login works after the denial. Test duplicate logout delivery and a temporary storage failure in a test environment. A duplicate valid notification should be harmless. A storage failure must return a server error.
5. Test the credential paths your deployment uses, including local LibreChat refresh tokens, OpenID token reuse, and admin-panel login and refresh. Confirm that a temporary check failure allows a retry without clearing browser credentials.
6. Once the checks pass, change to `mode: enforce` and restart every replica. Tell users with older unbound sessions that their next restoration or renewal will require a new login. Waiting in `record` mode does not bind those sessions through renewal alone.

These are deployment checks to run with your own provider. A successful receiver response alone does not prove that a user's credentials carry the matching binding.

## Rollback and retention

Changing from `enforce` to `record` allows sessions with missing bindings or records. It still denies known revoked sessions. Changing to `off` disables provider-session checks and the receiver. Restart every replica after either change.

Changing modes does not clear revocations. Records have a stored expiry time (`expiresAt`). Login, renewal, and logout can extend that time. Duplicate logout delivery preserves the earliest revocation time and does not shorten retention. A notification received before login completes also creates a revoked record to cover the pending callback.

Time spent in `off` does not extend retention. Expired records are removed by database expiry cleanup. When a revocation record is gone, `record` can no longer deny that session based on it; `enforce` requires a new login when its record is missing. Do not assume a fixed retention window from the time you switch modes.

Existing browser bindings are carried through renewal while `off`. Admin sessions created or rotated while `off` have no binding. They are allowed in `record` and must sign in again in `enforce`.

Rolling back to older LibreChat code removes back-channel logout enforcement. The older code ignores the optional binding fields.

## Troubleshooting and limits

| Result | Meaning and next step |
| --- | --- |
| Receiver returns 404 | The mode is `off`, or no OpenID client is available. Check the deployed version, provider setup, configuration, and restart. |
| Receiver returns 400 | The request or token is invalid. Check `sid`, issuer, client audience, signing algorithm, token age, and clock settings. |
| Receiver returns 413 or 429 | The request exceeds the body-size or request-rate limit. Check the configured limits and proxy IP handling. |
| Receiver returns 503 | Validation, storage, configuration, or processing is temporarily unavailable. Check server logs and the provider's delivery status. |
| Browser renewal returns `401 OPENID_SESSION_ENDED` | The session is revoked, conflicts with its stored identity, or lacks a binding or record under `enforce`. The client signs out. Start a fresh login. |
| `503 AUTH_SESSION_CHECK_UNAVAILABLE` | A check could not complete. The browser keeps its credentials and shows Retry during startup or a notification during an active session. Restore the dependency and retry. Admin APIs expose the code through `error_code`. |
| Login reports `OPENID_SESSION_ID_MISSING` | `enforce` requires `sid` in the login ID token. Check the provider configuration. |

Login callback failures redirect to the login page; they do not use the browser renewal response format.

A notification that never reaches LibreChat cannot be enforced. LibreChat does not poll the provider to recover missed notifications. Check which logout actions send notifications and how your provider handles failed delivery. Back-channel logout does not immediately invalidate access tokens already issued.
