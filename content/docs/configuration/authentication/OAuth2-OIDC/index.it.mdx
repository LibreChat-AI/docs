### Cache Utente OpenID JWT [#openid-jwt-user-cache]

Le distribuzioni con un elevato tasso di richieste possono impostare `AUTH_USER_CACHE_MODE=on` per memorizzare nella cache il documento utente risolto per l'autenticazione OpenID JWT per cinque secondi. Ciò riduce le letture ripetute dal database durante brevi picchi di richieste senza estendere la durata del token di autenticazione.

La cache è disattivata per impostazione predefinita e richiede `USE_REDIS=true` con il namespace `AUTH_USER_DOC` supportato da Redis. LibreChat disabilita la modalità e registra un avviso quando tali requisiti non sono soddisfatti. I documenti memorizzati nella cache vengono sanificati prima dell'archiviazione e invalidati quando l'utente viene aggiornato.

```bash filename=".env"
USE_REDIS=true
AUTH_USER_CACHE_MODE=on
```

## Risoluzione dei problemi di OpenID Connect [#troubleshooting-openid-connect]

Se riscontri problemi con l'autenticazione OpenID Connect:

1. **Abilita il debug logging delle intestazioni**: Imposta `DEBUG_OPENID_REQUESTS=true` nelle tue variabili d'ambiente per registrare le intestazioni delle richieste oltre agli URL (con i dati sensibili mascherati). Nota: gli URL delle richieste vengono sempre registrati al livello di debug.
2. **Controlla gli URI di reindirizzamento**: Assicurati che il tuo URL di callback corrisponda esattamente tra il tuo provider e la configurazione di LibreChat
3. **Verifica degli ambiti (Scopes)**: Assicurati che tutti gli ambiti richiesti siano configurati correttamente
4. **Esamina i log del provider**: Controlla i log del tuo identity provider per errori di autenticazione
5. **Convalida i token**: Assicurati che il tuo provider stia emettendo token validi con le attestazioni (claims) previste
6. **Assicurati che il _nonce_ sia generato**: Alcuni provider di identità generano il parametro url `nonce` se manca nella richiesta. Imposta `OPENID_GENERATE_NONCE=true` per forzare l'openid-client a generarlo.

### Tentativi di scoperta [#discovery-retries]

Se il tuo identity provider non è raggiungibile all'avvio di LibreChat, la discovery OpenID può essere ritentata. `OPENID_DISCOVERY_RETRY_ATTEMPTS` imposta il numero di tentativi effettuati prima che l'avvio prosegua (da 0 a 100, valore predefinito 1; `0` riprova solo in background), e `OPENID_DISCOVERY_RETRY_DELAY_MS` imposta il ritardo tra i tentativi (valore predefinito 5000). I valori impostati sotto `registration.openidDiscovery` in `librechat.yaml` hanno la precedenza. Consulta [registration](/docs/configuration/librechat_yaml/object_structure/registration) per queste chiavi e per `oauthStateTtlMs`, che controlla quanto tempo può intercorrere tra l'avvio di un login social e il suo callback (valore predefinito 10 minuti).

### Origini degli avatar del profilo [#profile-avatar-origins]

Quando recupera l'avatar del profilo dell'utente, LibreChat invia il token di accesso solo agli origin dell'issuer e dell'userinfo del provider. Se l'avatar viene servito da un altro origin che richiede il token, aggiungilo a `OPENID_AVATAR_AUTHORIZED_ORIGINS` come elenco di URL separati da virgole o spazi.

```bash filename=".env"
OPENID_AVATAR_AUTHORIZED_ORIGINS=https://graph.example.com,https://photos.example.com
```

### Reindirizzamenti del Pannello di Amministrazione [#admin-panel-redirects]

Se l'Admin Panel è ospitato su un URL separato da LibreChat, imposta [`ADMIN_PANEL_URL`](/docs/features/admin_panel#librechat-redirect-url) nell'ambiente dell'API di LibreChat. Questo indica a LibreChat dove reindirizzare gli amministratori una volta completato il callback OAuth o SSO dell'amministratore.
