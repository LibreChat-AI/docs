Silakan ikuti panduan ini untuk men-deploy LibreChat pada Kubernetes menggunakan Helm, dengan menyesuaikan kebutuhan sesuai kasus penggunaan spesifik Anda. Helm chart lain yang dikontribusikan oleh komunitas tercantum di bawah ini pada bagian [Community Helm Charts](#community-helm-charts).

## Prasyarat [#prerequisites]

* Klaster Kubernetes yang sedang berjalan
* Instalasi _lokal_ `kubectl` dan Helm

## Konfigurasi [#configuration]

1. Gunakan [Credentials Generator](/toolkit/creds_generator) untuk membuat nilai aman bagi `CREDS_KEY`, `CREDS_IV`, `JWT_SECRET`, `JWT_REFRESH_SECRET`, dan `MEILI_MASTER_KEY`.
Tempatkan nilai-nilai tersebut ke dalam Kubernetes Secret seperti ini (jika Anda mengubah nama secret, jangan lupa untuk memperbarui nilai Helm Anda):

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: librechat-credentials-env
  namespace: <librechat-chart-namespace>
type: Opaque
stringData:
  CREDS_KEY: <generated value>
  CREDS_IV: <generated value>
  JWT_SECRET: <generated value>
  JWT_REFRESH_SECRET: <generated value>
  MEILI_MASTER_KEY: <generated value>
```

Gunakan nilai permanen dan mount Secret yang sama ke setiap replika. Jangan mengandalkan kredensial sistem berkas lokal proses atau ephemeral di Kubernetes: mengubah nilai-nilai ini dapat membatalkan sesi dan membuat catatan terenkripsi yang ada menjadi tidak dapat dibaca.

Secret yang diberi nama oleh `global.librechat.existingSecretName` harus ada sebelum kontainer LibreChat dimulai. Secret yang hilang atau salah penulisan akan menghalangi startup pod alih-alih kembali ke kredensial lokal pod sementara. Chart ini tidak memvalidasi kunci di dalamnya, jadi pastikan Secret tersebut berisi `CREDS_KEY`, `CREDS_IV`, `JWT_SECRET`, dan `JWT_REFRESH_SECRET`.

Atur `global.librechat.existingSecretName: ""` hanya jika setiap kredensial LibreChat disediakan melalui cara lain. `librechat.configEnv` menerima nilai string untuk data ConfigMap, sementara `global.librechat.env` menerima entri lingkungan Kubernetes seperti `valueFrom.secretKeyRef`. Gunakan referensi Secret untuk produksi.

Meilisearch yang dibundel memiliki dependensi terpisah pada `meilisearch.auth.existingMasterKeySecret`, yang secara default adalah `librechat-credentials-env` dan harus berisi `MEILI_MASTER_KEY` yang sama dengan yang diberikan ke LibreChat. Menghapus referensi Secret LibreChat tidak menghapus referensi Meilisearch ini. Jika Meilisearch yang dibundel dinonaktifkan, konfigurasikan layanan pencarian eksternal dan kredensialnya secara terpisah.
2. Tambahkan ke secret yang sama ini semua kunci API yang diperlukan untuk penyedia LLM:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: librechat-credentials-env
  namespace: <librechat-chart-namespace>
type: Opaque
stringData:
  CREDS_KEY: <same generated value as above>
  CREDS_IV: <same generated value as above>
  JWT_SECRET: <same generated value as above>
  JWT_REFRESH_SECRET: <same generated value as above>
  MEILI_MASTER_KEY: <same generated value as above>
  OPENAI_API_KEY: <your secret value>
```
3. Terapkan Secret ke Cluster:

Simpan manifes Secret lengkap sebagai `librechat-credentials.yaml`, menggunakan namespace yang dituju, lalu terapkan:

```bash
kubectl apply -f librechat-credentials.yaml
```

4. Arahkan probe ke endpoint khusus. Probe default chart menggunakan `/health`, yang tetap mengembalikan `200` saat Redis mati, sehingga pod yang tidak dapat memproses login tetap menerima trafik. Timpa probe tersebut di file values Anda agar readiness mengikuti status Redis dan liveness tidak.

```yaml
livenessProbe:
  httpGet:
    path: /livez
    port: 3080
readinessProbe:
  httpGet:
    path: /readyz
    port: 3080
```

Lihat [Pemeriksaan kesehatan Redis](/docs/configuration/redis#health-checks) untuk mengetahui apa yang dilaporkan oleh setiap endpoint.

## Instal Helm Chart [#install-helm-chart]

Untuk menginstal helm chart, jalankan:

`helm install <deployment-name> oci://ghcr.io/librechat-ai/librechat-chart/librechat`

<details>
  <summary>Versi pengembangan</summary>

Di direktori root repo, jalankan:

`helm install <deployment-name> ./helm/librechat`
</details>

Mirip dengan Helm chart lainnya, terdapat [values file](https://github.com/LibreChat-AI/LibreChat/blob/main/helm/librechat/values.yaml) yang menguraikan pengaturan default dan menunjukkan opsi konfigurasi mana yang dapat diubah.

Buat file `values.yaml` yang diisi dengan nilai-nilai yang ingin Anda ubah dari nilai default.

Pasang Helm chart: `helm install librechat oci://ghcr.io/librechat-ai/librechat-chart/librechat --values <values-override-file>`

Setelah rilis berjalan dan layanan dapat diakses, ikuti [Obrolan Pertama Anda](/docs/quick_start/first_chat) untuk membuat akun, menambahkan kunci API model, dan mengirim pesan pertama Anda.

## Menghapus Helm Chart [#uninstall-the-helm-chart]

Untuk menghapus Helm Chart: `helm uninstall <deployment-name>`

Contoh: `helm uninstall librechat`

## Meningkatkan ke chart 3.x [#upgrading-to-chart-3x]

Chart 3.0.0 mengaktifkan autentikasi pada MongoDB dan Redis yang disertakan secara default. Kata sandi yang dihasilkan tetap berada di Secret subchart dan sampai ke LibreChat melalui `secretKeyRef` (`MONGODB_ROOT_PASSWORD`, `REDIS_PASSWORD`), sedangkan `MONGO_URI` dirakit di dalam Deployment. Untuk menggunakan basis data Anda sendiri, atur `librechat.configEnv.MONGO_URI` (atau `REDIS_URI`). Atur `mongodb.auth.enabled=false` atau `redis.auth.enabled=false` hanya untuk mengembalikan perilaku lama yang tanpa autentikasi. Kata sandi root kustom harus aman untuk URL karena akan ditempatkan di dalam `MONGO_URI`.

Jika `MONGO_URI`, `REDIS_URI` atau `REDIS_PASSWORD` berasal dari Secret yang dinamai oleh `global.librechat.existingSecretName`, atur `librechat.injectBundledCredentials.mongodb=false` (untuk `MONGO_URI`) atau `librechat.injectBundledCredentials.redis=false` (untuk `REDIS_URI` atau `REDIS_PASSWORD`). Chart tidak dapat melihat isi Secret tersebut, dan nilai yang dihasilkan secara otomatis akan menimpanya. Kedua pengaturan ini bersifat independen. Jika Anda tetap menggunakan MongoDB atau Redis bawaan, database tersebut harus menggunakan kata sandi yang sama dengan Secret Anda: arahkan `mongodb.auth.existingSecret` atau `redis.auth.existingSecret` ke Secret tersebut, atau atur kata sandi `auth` yang sesuai. Jika tidak, database akan tetap menggunakan kata sandi yang dihasilkan secara otomatis, dan LibreChat akan gagal melakukan autentikasi. Kredensial dibaca saat pod dimulai, jadi setelah mengganti kata sandi database, mulai ulang setiap Deployment yang membacanya dengan `kubectl rollout restart deployment/<release>-librechat`.

### Menyimpan kata sandi yang dihasilkan selama pembaruan [#keeping-the-generated-passwords-across-upgrades]

Dengan pengaturan default, subchart akan membuat password secara otomatis saat instalasi pertama, dan subchart MongoDB menolak upgrade berikutnya yang tidak menyertakan kembali password tersebut ("PASSWORDS ERROR"). Baca nilai yang sedang digunakan dan sertakan nilai tersebut pada setiap `helm upgrade`, atau arahkan `mongodb.auth.existingSecret` dan `redis.auth.existingSecret` ke Secret yang Anda kelola sendiri.

```bash
kubectl get secret <release>-mongodb -o jsonpath='{.data.mongodb-root-password}' | base64 -d
helm upgrade <release> ... --set-string mongodb.auth.rootPassword=<password>
```

Redis membutuhkan `--set-string redis.auth.password=<password>` dengan cara yang sama (`redis-password` di Secret `<release>-redis`). Dengan `mongodb.architecture=replicaset`, simpan juga replica set key: baca `mongodb-replica-set-key` dari Secret yang sama dan teruskan sebagai `--set-string mongodb.auth.replicaSetKey=<key>`.

### Meningkatkan dari MongoDB bawaan tanpa autentikasi [#upgrading-from-an-unauthenticated-bundled-mongodb]

Rilis yang dipasang sebelum autentikasi menjadi default memiliki data volume tanpa root user, dan data yang disimpan tidak diinisialisasi ulang saat upgrade, sehingga LibreChat tidak dapat melakukan autentikasi setelah `helm upgrade`. Pilih salah satu jalur berikut:

1. Pertahankan perilaku lama: `--set mongodb.auth.enabled=false`.
2. Buat pengguna root terlebih dahulu. Pada pod yang sedang berjalan sebelum peningkatan, jalankan `mongosh admin --eval 'db.createUser({user: "<rootUser>", pwd: "<password>", roles: ["root"]})'` (`<rootUser>` adalah `mongodb.auth.rootUser`, `root` secara default). Kemudian lakukan peningkatan dengan `--set-string mongodb.auth.rootPassword=<password>` (yang ramah URL) dan `mongodb.auth.rootUser` yang sama jika Anda mengubahnya. Gunakan kata sandi yang sama pada setiap peningkatan berikutnya. Peningkatan tanpa `mongodb.auth.rootPassword` akan ditolak oleh subchart MongoDB ("PASSWORDS ERROR") karena belum ada Secret.

Chart tidak dapat mendeteksi kasus ini pada saat render, sehingga `NOTES.txt` mencetak pemberitahuan pada setiap upgrade dengan autentikasi yang diaktifkan.

### Ingress TLS [#ingress-tls]

Ingress diaktifkan secara default. Atur `ingress.tls` (sebuah `secretName` dan `hosts`) untuk setiap instalasi non-lokal; `helm install` akan menampilkan peringatan untuk setiap host ingress yang tidak dicakup oleh entri `ingress.tls` mana pun.

### URL panel admin [#admin-panel-url]

Set `librechat.adminPanelUrl` ke URL dasar panel admin yang digunakan untuk redirect OAuth/SSO. URL ini boleh menyertakan path, tetapi tidak boleh diakhiri dengan `/`. Lihat [Admin Panel](/docs/features/admin_panel).

```yaml
librechat:
  adminPanelUrl: https://admin.example.com/admin
```

## Migrasi 1.x -> 2.x [#migrate-1x---2x]
Jika Anda menggunakan chart sebelum versi 2.x, Anda mungkin perlu memperbarui struktur `value`.

1. Pindahkan Konfigurasi ke librechat.configEnv:
```diff
- env:
-     ALLOW_EMAIL_LOGIN: "true"
-     ALLOW_REGISTRATION: "true"
+ librechat:
+   configEnv:
+     ALLOW_REGISTRATION: "true"
+     ALLOW_EMAIL_LOGIN: "true"
```

2. Gabungkan semua nilai Secret menjadi satu Secret sebagaimana dijelaskan dalam [Configuration Step 1](#configuration).
3. Untuk memanfaatkan instans MongoDB eksternal, silakan merujuk ke [values file](https://github.com/LibreChat-AI/LibreChat/blob/main/helm/librechat/values.yaml) dari Chart tersebut, nonaktifkan komponen yang sesuai, dan ubah FQDN dari instans MongoDB. Hal ini direkomendasikan jika data sudah ada di dalam instans MongoDB yang dikelola secara eksternal ini.
