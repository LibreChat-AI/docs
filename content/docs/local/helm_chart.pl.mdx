Proszę postępować zgodnie z tą instrukcją, aby wdrożyć LibreChat na Kubernetes przy użyciu Helm, dostosowując ją w razie potrzeby do własnego przypadku użycia. Inne wykresy Helm dostarczone przez społeczność zostały wymienione poniżej w sekcji [Community Helm Charts](#community-helm-charts).

## Wymagania wstępne [#prerequisites]

* Działający klaster Kubernetes
* _Lokalne_ instalacje `kubectl` oraz Helm

## Konfiguracja [#configuration]

1. Użyj [Generatora poświadczeń](/toolkit/creds_generator), aby wygenerować bezpieczne wartości dla `CREDS_KEY`, `CREDS_IV`, `JWT_SECRET`, `JWT_REFRESH_SECRET` oraz `MEILI_MASTER_KEY`.
Umieść je w obiekcie Kubernetes Secret w następujący sposób (jeśli zmienisz nazwę secretu, pamiętaj o aktualizacji swoich wartości Helm):

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: librechat-credentials-env
  namespace: <librechat-chart-namespace>
type: Opaque
stringData:
  CREDS_KEY: <generated value>
  CREDS_IV: <generated value>
  JWT_SECRET: <generated value>
  JWT_REFRESH_SECRET: <generated value>
  MEILI_MASTER_KEY: <generated value>
```

Używaj stałych wartości i montuj ten sam Secret w każdej replice. Nie polegaj na poświadczeniach lokalnych dla procesu lub ulotnych systemach plików w Kubernetes: zmiana tych wartości może unieważnić sesje i sprawić, że istniejące zaszyfrowane rekordy staną się niemożliwe do odczytania.

Secret o nazwie określonej przez `global.librechat.existingSecretName` musi istnieć przed uruchomieniem kontenera LibreChat. Brakujący lub błędnie wpisany Secret blokuje uruchomienie poda, zamiast powracać do tymczasowych poświadczeń lokalnych poda. Wykres (chart) nie weryfikuje zawartych w nim kluczy, więc upewnij się, że zawiera on `CREDS_KEY`, `CREDS_IV`, `JWT_SECRET` oraz `JWT_REFRESH_SECRET`.

Ustaw `global.librechat.existingSecretName: ""` tylko wtedy, gdy wszystkie poświadczenia LibreChat są dostarczane w inny sposób. `librechat.configEnv` akceptuje wartości typu string dla danych ConfigMap, podczas gdy `global.librechat.env` akceptuje wpisy środowiskowe Kubernetes, takie jak `valueFrom.secretKeyRef`. W środowiskach produkcyjnych preferuj odwołania do Secret.

Dołączony Meilisearch posiada oddzielną zależność od `meilisearch.auth.existingMasterKeySecret`, która domyślnie przyjmuje wartość `librechat-credentials-env` i musi zawierać ten sam klucz `MEILI_MASTER_KEY`, który został dostarczony do LibreChat. Usunięcie odniesienia do Secret w LibreChat nie usuwa tego odniesienia w Meilisearch. Jeśli dołączony Meilisearch jest wyłączony, skonfiguruj zewnętrzną usługę wyszukiwania oraz jej dane uwierzytelniające oddzielnie.
2. Dodaj do tego samego Secret wymagane klucze API dla dostawców LLM:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: librechat-credentials-env
  namespace: <librechat-chart-namespace>
type: Opaque
stringData:
  CREDS_KEY: <same generated value as above>
  CREDS_IV: <same generated value as above>
  JWT_SECRET: <same generated value as above>
  JWT_REFRESH_SECRET: <same generated value as above>
  MEILI_MASTER_KEY: <same generated value as above>
  OPENAI_API_KEY: <your secret value>
```
3. Zastosuj Secret do klastra:

Zapisz kompletny manifest Secret jako `librechat-credentials.yaml`, używając docelowej przestrzeni nazw (namespace), a następnie zastosuj go:

```bash
kubectl apply -f librechat-credentials.yaml
```

4. Skieruj sondy na dedykowane endpointy. Domyślne sondy wykresu korzystają z `/health`, który zwraca `200`, nawet gdy Redis jest niedostępny, więc pod, który nie może zalogować żadnego użytkownika, nadal otrzymuje ruch. Nadpisz je w swoim pliku values, tak aby gotowość (readiness) zależała od Redis, a żywotność (liveness) nie:

```yaml
livenessProbe:
  httpGet:
    path: /livez
    port: 3080
readinessProbe:
  httpGet:
    path: /readyz
    port: 3080
```

Zobacz [Sprawdzanie stanu Redis](/docs/configuration/redis#health-checks), aby poznać informacje raportowane przez każdy punkt końcowy.

## Instalacja Helm Chart [#install-helm-chart]

Aby zainstalować helm chart, uruchom:

`helm install <deployment-name> oci://ghcr.io/librechat-ai/librechat-chart/librechat`

<details>
  <summary>Wersja deweloperska</summary>

W katalogu głównym repozytorium uruchom:

`helm install <deployment-name> ./helm/librechat`
</details>

Podobnie jak w przypadku innych wykresów Helm, istnieje [plik values](https://github.com/LibreChat-AI/LibreChat/blob/main/helm/librechat/values.yaml), który określa ustawienia domyślne i wskazuje, które opcje konfiguracji można modyfikować.

Utwórz plik `values.yaml` wypełniony wartościami, które chcesz zmodyfikować względem wartości domyślnych.

Zainstaluj wykres Helm: `helm install librechat oci://ghcr.io/librechat-ai/librechat-chart/librechat --values <values-override-file>`

Gdy wydanie zostanie uruchomione i usługa będzie dostępna, postępuj zgodnie z [Pierwszy czat](/docs/quick_start/first_chat), aby utworzyć konto, dodać klucz API modelu i wysłać pierwszą wiadomość.

## Odinstaluj Helm Chart [#uninstall-the-helm-chart]

Aby odinstalować Helm Chart, użyj: `helm uninstall <deployment-name>`

Przykład: `helm uninstall librechat`

## Aktualizacja do chart 3.x [#upgrading-to-chart-3x]

Chart 3.0.0 włącza domyślnie uwierzytelnianie dla wbudowanych baz MongoDB i Redis. Wygenerowane hasła pozostają w sekretach podchartów i trafiają do LibreChat poprzez `secretKeyRef` (`MONGODB_ROOT_PASSWORD`, `REDIS_PASSWORD`), a `MONGO_URI` jest składany w Deployment. Aby użyć własnej bazy danych, ustaw `librechat.configEnv.MONGO_URI` (lub `REDIS_URI`). Ustaw `mongodb.auth.enabled=false` lub `redis.auth.enabled=false` wyłącznie wtedy, gdy chcesz przywrócić poprzednie działanie bez uwierzytelniania. Niestandardowe hasła root muszą być bezpieczne dla URL, ponieważ są umieszczane w `MONGO_URI`.

Jeśli `MONGO_URI`, `REDIS_URI` lub `REDIS_PASSWORD` pochodzi z Secret wskazanego przez `global.librechat.existingSecretName`, ustaw `librechat.injectBundledCredentials.mongodb=false` (dla `MONGO_URI`) lub `librechat.injectBundledCredentials.redis=false` (dla `REDIS_URI` lub `REDIS_PASSWORD`). Chart nie widzi zawartości tego Secret, a wygenerowane wartości nadpisałyby je w przeciwnym razie. Oba ustawienia są niezależne. Jeśli zachowujesz wbudowane MongoDB lub Redis, muszą one używać tego samego hasła co Twój Secret: wskaż w `mongodb.auth.existingSecret` lub `redis.auth.existingSecret` ten Secret albo ustaw odpowiednie hasło w `auth`. W przeciwnym razie baza danych zachowa wygenerowane hasło i LibreChat nie będzie mógł się uwierzytelnić. Dane uwierzytelniające są odczytywane podczas startu poda, dlatego po zmianie hasła do bazy danych uruchom ponownie każdy Deployment, który je odczytuje, poleceniem `kubectl rollout restart deployment/<release>-librechat`.

### Zachowywanie wygenerowanych haseł podczas aktualizacji [#keeping-the-generated-passwords-across-upgrades]

Domyślnie podcharty generują hasła przy pierwszej instalacji, a podchart MongoDB odrzuca późniejsze aktualizacje, które nie powtarzają tych haseł (komunikat „PASSWORDS ERROR”). Odczytaj bieżące wartości i przekazuj je przy każdym `helm upgrade` albo wskaż `mongodb.auth.existingSecret` i `redis.auth.existingSecret` na Secrety zarządzane przez Ciebie.

```bash
kubectl get secret <release>-mongodb -o jsonpath='{.data.mongodb-root-password}' | base64 -d
helm upgrade <release> ... --set-string mongodb.auth.rootPassword=<password>
```

Redis wymaga `--set-string redis.auth.password=<password>` w ten sam sposób (`redis-password` w Secret `<release>-redis`). Przy `mongodb.architecture=replicaset` należy również zachować klucz zestawu replik: odczytaj `mongodb-replica-set-key` z tego samego Secret i przekaż go jako `--set-string mongodb.auth.replicaSetKey=<key>`.

### Aktualizacja z niezabezpieczonej, dołączonej bazy MongoDB [#upgrading-from-an-unauthenticated-bundled-mongodb]

Wydania zainstalowane przed tym, jak uwierzytelnianie stało się domyślne, mają wolumin danych bez użytkownika root, a zapisane dane nie są ponownie inicjalizowane podczas aktualizacji, dlatego LibreChat nie może uwierzytelnić użytkownika po wykonaniu `helm upgrade`. Wybierz jedną ścieżkę:

1. Zachowaj dotychczasowe zachowanie: `--set mongodb.auth.enabled=false`.
2. Najpierw utwórz użytkownika root. Na działającym podzie sprzed aktualizacji uruchom `mongosh admin --eval 'db.createUser({user: "<rootUser>", pwd: "<password>", roles: ["root"]})'` (`<rootUser>` to `mongodb.auth.rootUser`, domyślnie `root`). Następnie wykonaj aktualizację z parametrem `--set-string mongodb.auth.rootPassword=<password>` (przyjazne dla adresów URL) oraz tym samym `mongodb.auth.rootUser`, jeśli został zmieniony. Przy każdej kolejnej aktualizacji używaj tego samego hasła. Aktualizacja bez `mongodb.auth.rootPassword` zostanie odrzucona przez podchart MongoDB z błędem "PASSWORDS ERROR", ponieważ Secret jeszcze nie istnieje.

Wykres nie może wykryć tego przypadku w czasie renderowania, dlatego `NOTES.txt` wyświetla powiadomienie przy każdej aktualizacji, gdy uwierzytelnianie jest włączone.

### Ingress TLS [#ingress-tls]

Ingress jest domyślnie włączony. Dla każdej instalacji innej niż lokalna ustaw `ingress.tls` (pola `secretName` i `hosts`); `helm install` wyświetli ostrzeżenie dla każdego hosta ingress, który nie jest objęty żadnym wpisem `ingress.tls`.

### Adres URL panelu administratora [#admin-panel-url]

Ustaw `librechat.adminPanelUrl` na podstawowy adres URL panelu administracyjnego, używany do przekierowań OAuth/SSO. Może zawierać ścieżkę, ale nie może kończyć się znakiem `/`. Zobacz [Panel administracyjny](/docs/features/admin_panel).

```yaml
librechat:
  adminPanelUrl: https://admin.example.com/admin
```

## Migracja 1.x -> 2.x [#migrate-1x---2x]
Jeśli korzystałeś z wykresu przed wersją 2.x, być może będziesz musiał zaktualizować strukturę `value`.

1. Przenieś konfigurację do librechat.configEnv:
```diff
- env:
-     ALLOW_EMAIL_LOGIN: "true"
-     ALLOW_REGISTRATION: "true"
+ librechat:
+   configEnv:
+     ALLOW_REGISTRATION: "true"
+     ALLOW_EMAIL_LOGIN: "true"
```

2. Skonsoliduj wszystkie wartości Secret w jeden Secret, zgodnie z opisem w [Kroku konfiguracji 1](#configuration).
3. Aby skorzystać z zewnętrznej instancji MongoDB, zapoznaj się z [plikiem values](https://github.com/LibreChat-AI/LibreChat/blob/main/helm/librechat/values.yaml) dla Chart, odpowiednio dezaktywuj komponenty i zmień FQDN instancji MongoDB. Jest to zalecane, jeśli dane już istnieją w tej zewnętrznie zarządzanej instancji MongoDB.
