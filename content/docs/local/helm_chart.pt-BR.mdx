Siga estas orientações para implantar o LibreChat no Kubernetes usando Helm, ajustando conforme necessário para o seu caso de uso específico. Outros Helm charts contribuídos pela comunidade estão listados abaixo na seção [Community Helm Charts](#community-helm-charts).

## Pré-requisitos [#prerequisites]

* Um cluster Kubernetes em execução
* Instalações _locais_ de `kubectl` e Helm

## Configuração [#configuration]

1. Use o [Credentials Generator](/toolkit/creds_generator) para gerar valores seguros para `CREDS_KEY`, `CREDS_IV`, `JWT_SECRET`, `JWT_REFRESH_SECRET` e `MEILI_MASTER_KEY`.
Coloque-os em um Kubernetes Secret como este (se você alterar o nome do secret, lembre-se de atualizar seus valores Helm):

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: librechat-credentials-env
  namespace: <librechat-chart-namespace>
type: Opaque
stringData:
  CREDS_KEY: <generated value>
  CREDS_IV: <generated value>
  JWT_SECRET: <generated value>
  JWT_REFRESH_SECRET: <generated value>
  MEILI_MASTER_KEY: <generated value>
```

Use valores permanentes e monte o mesmo Secret em cada réplica. Não dependa de credenciais locais de processo ou de sistema de arquivos efêmero no Kubernetes: alterar esses valores pode invalidar sessões e tornar registros criptografados existentes ilegíveis.

O Secret nomeado por `global.librechat.existingSecretName` deve existir antes que o container do LibreChat inicie. Um Secret ausente ou com nome incorreto bloqueia a inicialização do pod em vez de recorrer a credenciais temporárias locais do pod. O chart não valida as chaves dentro dele, portanto, certifique-se de que ele contenha `CREDS_KEY`, `CREDS_IV`, `JWT_SECRET` e `JWT_REFRESH_SECRET`.

Defina `global.librechat.existingSecretName: ""` apenas quando todas as credenciais do LibreChat forem fornecidas de outra forma. `librechat.configEnv` aceita valores de string para dados de ConfigMap, enquanto `global.librechat.env` aceita entradas de ambiente do Kubernetes, como `valueFrom.secretKeyRef`. Prefira referências de Secret para produção.

O Meilisearch integrado possui uma dependência separada em `meilisearch.auth.existingMasterKeySecret`, que tem como padrão `librechat-credentials-env` e deve conter a mesma `MEILI_MASTER_KEY` fornecida ao LibreChat. Limpar a referência do Secret do LibreChat não limpa esta referência do Meilisearch. Se o Meilisearch integrado estiver desativado, configure o serviço de busca externo e suas credenciais separadamente.
2. Adicione a este mesmo secret quaisquer chaves de API necessárias para provedores de LLM:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: librechat-credentials-env
  namespace: <librechat-chart-namespace>
type: Opaque
stringData:
  CREDS_KEY: <same generated value as above>
  CREDS_IV: <same generated value as above>
  JWT_SECRET: <same generated value as above>
  JWT_REFRESH_SECRET: <same generated value as above>
  MEILI_MASTER_KEY: <same generated value as above>
  OPENAI_API_KEY: <your secret value>
```
3. Aplique o Secret ao Cluster:

Salve o manifesto Secret completo como `librechat-credentials.yaml`, usando o namespace pretendido, e então aplique-o:

```bash
kubectl apply -f librechat-credentials.yaml
```

4. Aponte as sondagens para os endpoints dedicados. As sondagens padrão do chart usam `/health`, que permanece `200` enquanto o Redis está indisponível; assim, um pod que não consegue autenticar ninguém continua recebendo tráfego. Sobrescreva-as no seu arquivo de values para que a readiness siga o Redis e a liveness não:

```yaml
livenessProbe:
  httpGet:
    path: /livez
    port: 3080
readinessProbe:
  httpGet:
    path: /readyz
    port: 3080
```

Veja [Verificações de integridade do Redis](/docs/configuration/redis#health-checks) para saber o que cada endpoint informa.

## Instalar Helm Chart [#install-helm-chart]

Para instalar o helm chart, execute:

`helm install <deployment-name> oci://ghcr.io/librechat-ai/librechat-chart/librechat`

<details>
  <summary>Versão de desenvolvimento</summary>

No diretório raiz do repositório, execute:

`helm install <deployment-name> ./helm/librechat`
</details>

Assim como outros Helm charts, existe um [values file](https://github.com/LibreChat-AI/LibreChat/blob/main/helm/librechat/values.yaml) que descreve as configurações padrão e indica quais opções de configuração podem ser modificadas.

Crie um arquivo `values.yaml` preenchido com os valores que você deseja modificar a partir do padrão.

Instale o chart do Helm: `helm install librechat oci://ghcr.io/librechat-ai/librechat-chart/librechat --values <values-override-file>`

Quando a versão estiver no ar e o serviço estiver acessível, siga [Seu Primeiro Chat](/docs/quick_start/first_chat) para criar uma conta, adicionar uma chave de API de modelo e enviar sua primeira mensagem.

## Desinstalar o Helm Chart [#uninstall-the-helm-chart]

Para desinstalar o Helm Chart: `helm uninstall <deployment-name>`

Exemplo: `helm uninstall librechat`

## Atualizando para o chart 3.x [#upgrading-to-chart-3x]

O Chart 3.0.0 ativa a autenticação no MongoDB e no Redis incluídos por padrão. Suas senhas geradas permanecem nos Secrets dos subcharts e chegam ao LibreChat por meio de `secretKeyRef` (`MONGODB_ROOT_PASSWORD`, `REDIS_PASSWORD`), e o `MONGO_URI` é montado no Deployment. Para usar seu próprio banco de dados, defina `librechat.configEnv.MONGO_URI` (ou `REDIS_URI`). Defina `mongodb.auth.enabled=false` ou `redis.auth.enabled=false` somente para restaurar o comportamento antigo, sem autenticação. Senhas de root personalizadas devem ser seguras para URL, pois são inseridas no `MONGO_URI`.

Se `MONGO_URI`, `REDIS_URI` ou `REDIS_PASSWORD` vierem do Secret indicado por `global.librechat.existingSecretName`, defina `librechat.injectBundledCredentials.mongodb=false` (para `MONGO_URI`) ou `librechat.injectBundledCredentials.redis=false` (para `REDIS_URI` ou `REDIS_PASSWORD`). O chart não consegue ver o conteúdo desse Secret, e os valores gerados, caso contrário, sobrescreveriam o que ele contém. As duas configurações são independentes. Se você mantiver o MongoDB ou o Redis incluídos no chart, eles devem usar a mesma senha do seu Secret: aponte `mongodb.auth.existingSecret` ou `redis.auth.existingSecret` para ele, ou defina a senha correspondente em `auth`. Caso contrário, o banco manterá a senha gerada e o LibreChat falhará na autenticação. As credenciais são lidas quando um pod é iniciado; portanto, após rotacionar a senha de um banco de dados, reinicie todos os Deployments que a utilizam com `kubectl rollout restart deployment/<release>-librechat`.

### Mantendo as senhas geradas entre atualizações [#keeping-the-generated-passwords-across-upgrades]

Com os valores padrão, os subcharts geram as senhas na primeira instalação, e o subchart do MongoDB recusa atualizações posteriores que não repetirem essas senhas ("PASSWORDS ERROR"). Leia os valores atuais e passe-os em cada `helm upgrade`, ou aponte `mongodb.auth.existingSecret` e `redis.auth.existingSecret` para Secrets que você gerencia:

```bash
kubectl get secret <release>-mongodb -o jsonpath='{.data.mongodb-root-password}' | base64 -d
helm upgrade <release> ... --set-string mongodb.auth.rootPassword=<password>
```

O Redis precisa de `--set-string redis.auth.password=<password>` da mesma forma (`redis-password` no Secret `<release>-redis`). Com `mongodb.architecture=replicaset`, também mantenha a chave do replica set: leia `mongodb-replica-set-key` do mesmo Secret e passe-a como `--set-string mongodb.auth.replicaSetKey=<key>`.

### Atualizando a partir de um MongoDB incluído sem autenticação [#upgrading-from-an-unauthenticated-bundled-mongodb]

Versões instaladas antes de a autenticação se tornar o padrão possuem um volume de dados sem usuário root, e os dados persistidos não são reinicializados na atualização, portanto o LibreChat não consegue autenticar após `helm upgrade`. Escolha um dos caminhos:

1. Mantenha o comportamento antigo: `--set mongodb.auth.enabled=false`.
2. Crie primeiro o usuário root. No pod pré-upgrade em execução, execute `mongosh admin --eval 'db.createUser({user: "<rootUser>", pwd: "<password>", roles: ["root"]})'` (`<rootUser>` é `mongodb.auth.rootUser`, `root` por padrão). Em seguida, faça o upgrade com `--set-string mongodb.auth.rootPassword=<password>` (compatível com URL) e o mesmo `mongodb.auth.rootUser`, caso você o tenha alterado. Mantenha a mesma senha em todos os upgrades posteriores. Um upgrade sem `mongodb.auth.rootPassword` será recusado pelo subchart do MongoDB ("PASSWORDS ERROR"), porque ainda não existe nenhum Secret.

O gráfico não consegue detectar este caso no momento da renderização, então o `NOTES.txt` exibe um aviso a cada atualização com a autenticação habilitada.

### Ingress TLS [#ingress-tls]

A entrada (ingress) está habilitada por padrão. Defina `ingress.tls` (um `secretName` e `hosts`) para qualquer instalação não local; `helm install` exibe um aviso para cada host de entrada que não é coberto por nenhuma entrada de `ingress.tls`.

### URL do painel de administração [#admin-panel-url]

Defina `librechat.adminPanelUrl` como a URL base do painel de administração usada para redirecionamentos OAuth/SSO. Ela pode incluir um caminho, mas não deve terminar com `/`. Consulte [Painel de Administração](/docs/features/admin_panel).

```yaml
librechat:
  adminPanelUrl: https://admin.example.com/admin
```

## Migrar 1.x -> 2.x [#migrate-1x---2x]
Se você usou o chart antes da versão 2.x, talvez precise atualizar a estrutura de `value`.

1. Mover Config para librechat.configEnv:
```diff
- env:
-     ALLOW_EMAIL_LOGIN: "true"
-     ALLOW_REGISTRATION: "true"
+ librechat:
+   configEnv:
+     ALLOW_REGISTRATION: "true"
+     ALLOW_EMAIL_LOGIN: "true"
```

2. Consolide todos os valores de Secret em um único Secret, conforme descrito em [Configuration Step 1](#configuration).
3. Para utilizar uma instância externa do MongoDB, consulte o [values file](https://github.com/LibreChat-AI/LibreChat/blob/main/helm/librechat/values.yaml) do Chart, desative os componentes adequadamente e altere o FQDN da instância do Mongodb. Isso é recomendado caso já existam dados nesta instância do MongoDB gerenciada externamente.
