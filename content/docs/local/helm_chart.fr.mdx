Veuillez suivre ces instructions pour déployer LibreChat sur Kubernetes en utilisant Helm, en les adaptant selon vos besoins spécifiques. D'autres charts Helm fournis par la communauté sont listés ci-dessous dans la section [Community Helm Charts](#community-helm-charts).

## Prérequis [#prerequisites]

* Un cluster Kubernetes en cours d'exécution
* Installations _locales_ de `kubectl` et Helm

## Configuration [#configuration]

1. Utilisez le [Credentials Generator](/toolkit/creds_generator) pour générer des valeurs sécurisées pour `CREDS_KEY`, `CREDS_IV`, `JWT_SECRET`, `JWT_REFRESH_SECRET` et `MEILI_MASTER_KEY`.
Placez-les dans un Kubernetes Secret comme ceci (si vous modifiez le nom du secret, n'oubliez pas de mettre à jour vos valeurs Helm) :

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: librechat-credentials-env
  namespace: <librechat-chart-namespace>
type: Opaque
stringData:
  CREDS_KEY: <generated value>
  CREDS_IV: <generated value>
  JWT_SECRET: <generated value>
  JWT_REFRESH_SECRET: <generated value>
  MEILI_MASTER_KEY: <generated value>
```

Utilisez des valeurs permanentes et montez le même Secret dans chaque réplica. Ne vous fiez pas aux identifiants locaux au processus ou au système de fichiers éphémère dans Kubernetes : la modification de ces valeurs peut invalider les sessions et rendre illisibles les enregistrements chiffrés existants.

Le Secret nommé par `global.librechat.existingSecretName` doit exister avant que le conteneur LibreChat ne démarre. Un Secret manquant ou mal orthographié bloque le démarrage du pod au lieu de revenir à des identifiants temporaires locaux au pod. Le chart ne valide pas les clés qu'il contient, assurez-vous donc qu'il inclut `CREDS_KEY`, `CREDS_IV`, `JWT_SECRET` et `JWT_REFRESH_SECRET`.

Définissez `global.librechat.existingSecretName: ""` uniquement lorsque toutes les informations d'identification LibreChat sont fournies par un autre moyen. `librechat.configEnv` accepte des valeurs de chaîne pour les données ConfigMap, tandis que `global.librechat.env` accepte des entrées d'environnement Kubernetes telles que `valueFrom.secretKeyRef`. Privilégiez les références de Secret pour la production.

Le Meilisearch intégré possède une dépendance distincte sur `meilisearch.auth.existingMasterKeySecret`, qui utilise par défaut `librechat-credentials-env` et doit contenir la même `MEILI_MASTER_KEY` fournie à LibreChat. La suppression de la référence au Secret LibreChat ne supprime pas cette référence Meilisearch. Si le Meilisearch intégré est désactivé, configurez le service de recherche externe et ses identifiants séparément.
2. Ajoutez à ce même secret toutes les clés API requises pour les fournisseurs de LLM :

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: librechat-credentials-env
  namespace: <librechat-chart-namespace>
type: Opaque
stringData:
  CREDS_KEY: <same generated value as above>
  CREDS_IV: <same generated value as above>
  JWT_SECRET: <same generated value as above>
  JWT_REFRESH_SECRET: <same generated value as above>
  MEILI_MASTER_KEY: <same generated value as above>
  OPENAI_API_KEY: <your secret value>
```
3. Appliquer le Secret au Cluster :

Enregistrez le manifeste Secret complet sous le nom `librechat-credentials.yaml`, en utilisant l'espace de noms prévu, puis appliquez-le :

```bash
kubectl apply -f librechat-credentials.yaml
```

4. Pointez les sondes vers les endpoints dédiés. Les sondes par défaut du chart utilisent `/health`, qui reste à `200` même lorsque Redis est indisponible ; un pod incapable d'authentifier qui que ce soit continue donc de recevoir du trafic. Remplacez-les dans votre fichier de valeurs afin que la readiness suive l'état de Redis et que la liveness n'en dépende pas :

```yaml
livenessProbe:
  httpGet:
    path: /livez
    port: 3080
readinessProbe:
  httpGet:
    path: /readyz
    port: 3080
```

Consultez [Vérifications de l'état de Redis](/docs/configuration/redis#health-checks) pour savoir ce que signale chaque point de terminaison.

## Installer le Helm Chart [#install-helm-chart]

Pour installer le helm chart, exécutez :

`helm install <deployment-name> oci://ghcr.io/librechat-ai/librechat-chart/librechat`

<details>
  <summary>Version de développement</summary>

Dans le répertoire racine du dépôt, exécutez :

`helm install <deployment-name> ./helm/librechat`
</details>

Tout comme pour les autres charts Helm, il existe un [values file](https://github.com/LibreChat-AI/LibreChat/blob/main/helm/librechat/values.yaml) qui décrit les paramètres par défaut et indique quelles options de configuration peuvent être modifiées.

Créez un fichier `values.yaml` rempli avec les valeurs que vous souhaitez modifier par rapport à celles par défaut.

Installez le chart Helm : `helm install librechat oci://ghcr.io/librechat-ai/librechat-chart/librechat --values <values-override-file>`

Une fois la version publiée et le service accessible, suivez [Votre premier chat](/docs/quick_start/first_chat) pour créer un compte, ajouter une clé API de modèle et envoyer votre premier message.

## Désinstaller le Helm Chart [#uninstall-the-helm-chart]

Pour désinstaller le Helm Chart : `helm uninstall <deployment-name>`

Exemple : `helm uninstall librechat`

## Mise à niveau vers le chart 3.x [#upgrading-to-chart-3x]

Le chart 3.0.0 active l'authentification sur les instances MongoDB et Redis fournies par défaut. Leurs mots de passe générés restent dans les Secrets des sous-charts et atteignent LibreChat via `secretKeyRef` (`MONGODB_ROOT_PASSWORD`, `REDIS_PASSWORD`), tandis que `MONGO_URI` est assemblé dans le Deployment. Pour utiliser votre propre base de données, définissez `librechat.configEnv.MONGO_URI` (ou `REDIS_URI`). Ne définissez `mongodb.auth.enabled=false` ou `redis.auth.enabled=false` que pour restaurer l'ancien comportement sans authentification. Les mots de passe root personnalisés doivent être compatibles avec les URL, car ils sont insérés dans `MONGO_URI`.

Si `MONGO_URI`, `REDIS_URI` ou `REDIS_PASSWORD` provient du Secret nommé par `global.librechat.existingSecretName`, définissez `librechat.injectBundledCredentials.mongodb=false` (pour `MONGO_URI`) ou `librechat.injectBundledCredentials.redis=false` (pour `REDIS_URI` ou `REDIS_PASSWORD`). Le chart ne peut pas voir à l'intérieur de ce Secret, et les valeurs générées remplaceraient sinon celles qu'il contient. Les deux paramètres sont indépendants. Si vous conservez MongoDB ou Redis intégrés, ils doivent utiliser le même mot de passe que votre Secret : pointez `mongodb.auth.existingSecret` ou `redis.auth.existingSecret` vers celui-ci, ou définissez le mot de passe correspondant dans `auth`, faute de quoi la base de données conserve son mot de passe généré et LibreChat échoue à s'authentifier. Les identifiants sont lus au démarrage d'un pod ; après avoir changé le mot de passe d'une base de données, redémarrez donc chaque Deployment qui l'utilise avec `kubectl rollout restart deployment/<release>-librechat`.

### Conserver les mots de passe générés lors des mises à jour [#keeping-the-generated-passwords-across-upgrades]

Avec les valeurs par défaut, les sous-graphiques génèrent les mots de passe lors de la première installation, et le sous-graphique MongoDB refuse les mises à niveau ultérieures qui ne répètent pas ces mots de passe (« PASSWORDS ERROR »). Lisez les valeurs actuelles et transmettez-les à chaque `helm upgrade`, ou faites pointer `mongodb.auth.existingSecret` et `redis.auth.existingSecret` vers des Secrets que vous gérez vous-même :

```bash
kubectl get secret <release>-mongodb -o jsonpath='{.data.mongodb-root-password}' | base64 -d
helm upgrade <release> ... --set-string mongodb.auth.rootPassword=<password>
```

Redis nécessite `--set-string redis.auth.password=<password>` de la même manière (`redis-password` dans le Secret `<release>-redis`). Avec `mongodb.architecture=replicaset`, conservez également la clé du jeu de réplicas : lisez `mongodb-replica-set-key` depuis le même Secret et transmettez-la via `--set-string mongodb.auth.replicaSetKey=<key>`.

### Mise à niveau depuis une base MongoDB intégrée non authentifiée [#upgrading-from-an-unauthenticated-bundled-mongodb]

Les versions installées avant que l'authentification ne devienne la configuration par défaut disposent d'un volume de données sans utilisateur root, et les données persistantes ne sont pas réinitialisées lors de la mise à niveau. Par conséquent, LibreChat ne peut pas s'authentifier après un `helm upgrade`. Choisissez l'une des deux options :

1. Conservez l'ancien comportement : `--set mongodb.auth.enabled=false`.
2. Créez d'abord l'utilisateur root. Sur le pod en cours d'exécution, avant la mise à niveau, exécutez `mongosh admin --eval 'db.createUser({user: "<rootUser>", pwd: "<password>", roles: ["root"]})'` (`<rootUser>` correspond à `mongodb.auth.rootUser`, `root` par défaut). Effectuez ensuite la mise à niveau avec `--set-string mongodb.auth.rootPassword=<password>` (compatible avec les URL) et le même `mongodb.auth.rootUser` si vous l'avez modifié. Conservez le même mot de passe lors de toutes les mises à niveau suivantes. Une mise à niveau sans `mongodb.auth.rootPassword` est refusée par le sous-chart MongoDB (« PASSWORDS ERROR ») car aucun Secret n'existe encore.

Le graphique ne peut pas détecter ce cas au moment du rendu ; `NOTES.txt` affiche donc un avertissement à chaque mise à jour lorsque l'authentification est activée.

### Ingress TLS [#ingress-tls]

L'ingress est activé par défaut. Définissez `ingress.tls` (un `secretName` et des `hosts`) pour toute installation non locale ; `helm install` affiche un avertissement pour chaque hôte d'ingress qu'aucune entrée `ingress.tls` ne couvre.

### URL du panneau d'administration [#admin-panel-url]

Définissez `librechat.adminPanelUrl` sur l'URL de base du panneau d'administration utilisée pour les redirections OAuth/SSO. Elle peut inclure un chemin mais ne doit pas se terminer par un `/`. Voir [Panneau d'administration](/docs/features/admin_panel).

```yaml
librechat:
  adminPanelUrl: https://admin.example.com/admin
```

## Migrer de 1.x vers 2.x [#migrate-1x---2x]
Si vous avez utilisé le chart avant la version 2.x, vous devrez peut-être mettre à jour la structure `value`.

1. Déplacer la configuration vers librechat.configEnv :
```diff
- env:
-     ALLOW_EMAIL_LOGIN: "true"
-     ALLOW_REGISTRATION: "true"
+ librechat:
+   configEnv:
+     ALLOW_REGISTRATION: "true"
+     ALLOW_EMAIL_LOGIN: "true"
```

2. Consolidez toutes les valeurs de Secret en un seul Secret comme décrit dans [Configuration Step 1](#configuration).
3. Pour utiliser une instance MongoDB externe, référez-vous au [values file](https://github.com/LibreChat-AI/LibreChat/blob/main/helm/librechat/values.yaml) du Chart, désactivez les composants en conséquence et modifiez le FQDN de l'instance MongoDB. Ceci est recommandé si des données existent déjà dans cette instance MongoDB gérée de manière externe.
