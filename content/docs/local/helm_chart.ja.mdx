Helmを使用してKubernetes上にLibreChatをデプロイするには、以下のガイダンスに従ってください。必要に応じて、特定のユースケースに合わせて調整してください。コミュニティによって提供されたその他のHelmチャートは、以下の[Community Helm Charts](#community-helm-charts)セクションに記載されています。

## 前提条件 [#prerequisites]

* 実行中のKubernetesクラスター
* `kubectl` および Helm の _ローカル_ インストール

## 設定 [#configuration]

1. [Credentials Generator](/toolkit/creds_generator) を使用して、`CREDS_KEY`、`CREDS_IV`、`JWT_SECRET`、`JWT_REFRESH_SECRET`、および `MEILI_MASTER_KEY` の安全な値を生成します。
以下のように Kubernetes Secret に配置します（シークレット名を変更した場合は、Helm の値を更新することを忘れないでください）：

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: librechat-credentials-env
  namespace: <librechat-chart-namespace>
type: Opaque
stringData:
  CREDS_KEY: <generated value>
  CREDS_IV: <generated value>
  JWT_SECRET: <generated value>
  JWT_REFRESH_SECRET: <generated value>
  MEILI_MASTER_KEY: <generated value>
```

永続的な値を使用し、すべてのレプリカに同じSecretをマウントしてください。Kubernetesにおいてプロセスローカルやエフェメラルなファイルシステムの認証情報に依存しないでください。これらの値を変更すると、セッションが無効になり、既存の暗号化されたレコードが読み取れなくなる可能性があります。

`global.librechat.existingSecretName` で指定された Secret は、LibreChat コンテナが起動する前に存在している必要があります。指定された Secret が存在しない、または名前が間違っている場合、一時的なポッドローカルの認証情報にフォールバックすることなく、ポッドの起動がブロックされます。このチャートは内部のキーを検証しないため、`CREDS_KEY`、`CREDS_IV`、`JWT_SECRET`、および `JWT_REFRESH_SECRET` が含まれていることを確認してください。

すべてのLibreChatの認証情報が他の方法で提供されている場合にのみ、`global.librechat.existingSecretName: ""` を設定してください。`librechat.configEnv` はConfigMapデータ用の文字列値を受け入れますが、`global.librechat.env` は `valueFrom.secretKeyRef` のようなKubernetes環境エントリを受け入れます。本番環境ではSecret参照を使用することを推奨します。

バンドルされているMeilisearchは、`meilisearch.auth.existingMasterKeySecret` に個別の依存関係を持っており、デフォルトでは `librechat-credentials-env` が設定されています。これには、LibreChatに提供されるものと同じ `MEILI_MASTER_KEY` が含まれている必要があります。LibreChatのシークレット参照をクリアしても、このMeilisearchの参照はクリアされません。バンドルされているMeilisearchが無効になっている場合は、外部の検索サービスとその認証情報を個別に設定してください。

2. LLMプロバイダーに必要なAPIキーを、この同じシークレットに追加します：

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: librechat-credentials-env
  namespace: <librechat-chart-namespace>
type: Opaque
stringData:
  CREDS_KEY: <same generated value as above>
  CREDS_IV: <same generated value as above>
  JWT_SECRET: <same generated value as above>
  JWT_REFRESH_SECRET: <same generated value as above>
  MEILI_MASTER_KEY: <same generated value as above>
  OPENAI_API_KEY: <your secret value>
```
3. シークレットをクラスターに適用する:

完全なSecretマニフェストを `librechat-credentials.yaml` として保存し、対象のネームスペースを指定した上で適用します：

```bash
kubectl apply -f librechat-credentials.yaml
```

4. プローブを専用のエンドポイントに向けます。チャートのデフォルトのプローブは `/health` を使用しますが、このエンドポイントは Redis が停止していても `200` を返し続けます。そのため、ユーザーをサインインさせられない Pod にもトラフィックが送られ続けてしまいます。values ファイルでこれらを上書きし、readiness が Redis の状態に従い、liveness は従わないようにしてください。

```yaml
livenessProbe:
  httpGet:
    path: /livez
    port: 3080
readinessProbe:
  httpGet:
    path: /readyz
    port: 3080
```

次のエンドポイントが報告する内容については、[Redis のヘルスチェック](/docs/configuration/redis#health-checks)を参照してください。

## Helm Chartのインストール [#install-helm-chart]

helm chartをインストールするには、以下を実行してください：

`helm install <deployment-name> oci://ghcr.io/librechat-ai/librechat-chart/librechat`

<details>
  <summary>開発バージョン</summary>

リポジトリのルートディレクトリで、以下を実行してください：

`helm install <deployment-name> ./helm/librechat`
</details>

他のHelmチャートと同様に、デフォルト設定の概要と変更可能な設定オプションを示す[valuesファイル](https://github.com/LibreChat-AI/LibreChat/blob/main/helm/librechat/values.yaml)が存在します。

デフォルトから変更したい値を設定した `values.yaml` ファイルを作成します。

Helm チャートをインストールします: `helm install librechat oci://ghcr.io/librechat-ai/librechat-chart/librechat --values <values-override-file>`

リリースが公開され、サービスに接続できるようになったら、[最初のチャット](/docs/quick_start/first_chat)の手順に従って、アカウントを作成し、モデルのAPIキーを追加して、最初のメッセージを送信してください。

## Helm Chart をアンインストールする [#uninstall-the-helm-chart]

Helm Chartをアンインストールするには、`helm uninstall <deployment-name>` を実行します。

例: `helm uninstall librechat`

## Chart 3.x へのアップグレード [#upgrading-to-chart-3x]

Chart 3.0.0では、同梱のMongoDBとRedisでデフォルトで認証が有効になります。生成されたパスワードはサブチャートのSecretに保存され、`secretKeyRef`(`MONGODB_ROOT_PASSWORD`、`REDIS_PASSWORD`)を通じてLibreChatに渡されます。また、`MONGO_URI`はDeploymentの中で組み立てられます。独自のデータベースを使用するには、`librechat.configEnv.MONGO_URI`(または`REDIS_URI`)を設定してください。従来の認証なしの動作に戻す場合にのみ、`mongodb.auth.enabled=false`または`redis.auth.enabled=false`を設定してください。カスタムのルートパスワードは`MONGO_URI`に組み込まれるため、URLセーフな文字列である必要があります。

`MONGO_URI`、`REDIS_URI`、または`REDIS_PASSWORD`が`global.librechat.existingSecretName`で指定されたSecretから取得される場合は、`MONGO_URI`には`librechat.injectBundledCredentials.mongodb=false`を、`REDIS_URI`または`REDIS_PASSWORD`には`librechat.injectBundledCredentials.redis=false`を設定してください。チャートはそのSecretの内容を参照できず、生成された値がそれを上書きしてしまうためです。この2つの設定は互いに独立しています。バンドルされたMongoDBまたはRedisを引き続き使用する場合は、Secretと同じパスワードを使う必要があります。`mongodb.auth.existingSecret`または`redis.auth.existingSecret`をそのSecretに向けるか、対応する`auth`のパスワードを設定してください。そうしないと、データベースが生成されたパスワードのままとなり、LibreChatが認証に失敗します。認証情報はPodの起動時に読み込まれるため、データベースのパスワードをローテーションした後は、`kubectl rollout restart deployment/<release>-librechat`を実行して、それを読み込むすべてのDeploymentを再起動してください。

### アップグレード後も生成されたパスワードを保持する [#keeping-the-generated-passwords-across-upgrades]

デフォルトの設定では、サブチャートが初回インストール時にパスワードを生成します。その後のアップグレードでパスワードを再度指定しない場合、MongoDB サブチャートはアップグレードを拒否します(「PASSWORDS ERROR」)。現在の値を読み取り、`helm upgrade` を実行するたびにそれらを渡すか、`mongodb.auth.existingSecret` および `redis.auth.existingSecret` で、自分で管理する Secret を指定してください。

```bash
kubectl get secret <release>-mongodb -o jsonpath='{.data.mongodb-root-password}' | base64 -d
helm upgrade <release> ... --set-string mongodb.auth.rootPassword=<password>
```

Redis も同様に `--set-string redis.auth.password=<password>` を指定する必要があります(`<release>-redis` Secret の `redis-password`)。`mongodb.architecture=replicaset` の場合は、レプリカセットキーも保持してください。同じ Secret から `mongodb-replica-set-key` を読み取り、`--set-string mongodb.auth.replicaSetKey=<key>` として渡します。

### 認証なしのバンドル版 MongoDB からのアップグレード [#upgrading-from-an-unauthenticated-bundled-mongodb]

認証がデフォルトになる前にインストールされたリリースでは、root ユーザーのいないデータボリュームが存在し、永続化されたデータはアップグレード時に再初期化されないため、`helm upgrade` の後に LibreChat が認証できなくなります。いずれかの方法を選択してください:

1. 以前の動作を維持するには、`--set mongodb.auth.enabled=false` を指定します。
2. 最初にroot ユーザーを作成します。稼働中のアップグレード前 Pod 上で `mongosh admin --eval 'db.createUser({user: "<rootUser>", pwd: "<password>", roles: ["root"]})'` を実行します(`<rootUser>` は `mongodb.auth.rootUser` の値で、デフォルトは `root` です)。その後、`--set-string mongodb.auth.rootPassword=<password>`(URL セーフな文字列)と、`mongodb.auth.rootUser` を変更した場合は同じ値を指定してアップグレードします。以降のアップグレードでも同じパスワードを使い続けてください。`mongodb.auth.rootPassword` を指定せずにアップグレードすると、まだ Secret が存在しないため、MongoDB サブチャートによって拒否されます("PASSWORDS ERROR")。

チャートはレンダリング時にこのケースを検出できないため、認証が有効になっている場合、アップグレードのたびに `NOTES.txt` が通知を出力します。

### Ingress TLS [#ingress-tls]

Ingress はデフォルトで有効になっています。ローカル以外のインストールでは `ingress.tls`(`secretName` と `hosts`)を設定してください。`ingress.tls` のエントリでカバーされていない ingress のホストごとに、`helm install` が警告を出力します。

### 管理パネルのURL [#admin-panel-url]

`librechat.adminPanelUrl` を設定すると、OAuth/SSO のリダイレクトに使用される管理パネルのベース URL を指定できます。パスを含めることはできますが、末尾に `/` を付けてはいけません。詳細は [Admin Panel](/docs/features/admin_panel) を参照してください。

```yaml
librechat:
  adminPanelUrl: https://admin.example.com/admin
```

## 1.x から 2.x への移行 [#migrate-1x---2x]
バージョン 2.x より前のチャートを使用していた場合、`value` 構造を更新する必要があるかもしれません。

1. 設定を librechat.configEnv に移動する:
```diff
- env:
-     ALLOW_EMAIL_LOGIN: "true"
-     ALLOW_REGISTRATION: "true"
+ librechat:
+   configEnv:
+     ALLOW_REGISTRATION: "true"
+     ALLOW_EMAIL_LOGIN: "true"
```

2. [Configuration Step 1](#configuration) で説明されているように、すべての Secret 値を単一の Secret に統合します。
3. 外部のMongoDBインスタンスを活用するには、Chartの[values file](https://github.com/LibreChat-AI/LibreChat/blob/main/helm/librechat/values.yaml)を参照し、それに応じてコンポーネントを無効化し、MongodbインスタンスのFQDNを変更してください。この外部管理されているMongoDBインスタンスに既にデータが存在する場合は、この方法が推奨されます。
