Si prega di seguire questa guida per distribuire LibreChat su Kubernetes utilizzando Helm, apportando le modifiche necessarie per il proprio caso d'uso specifico. Altri Helm chart forniti dalla community sono elencati di seguito nella sezione [Community Helm Charts](#community-helm-charts).

## Prerequisiti [#prerequisites]

* Un cluster Kubernetes in esecuzione
* Installazioni _locali_ di `kubectl` e Helm

## Configurazione [#configuration]

1. Utilizza il [Credentials Generator](/toolkit/creds_generator) per generare valori sicuri per `CREDS_KEY`, `CREDS_IV`, `JWT_SECRET`, `JWT_REFRESH_SECRET` e `MEILI_MASTER_KEY`.
Inseriscili in un Kubernetes Secret come questo (se modifichi il nome del secret, ricordati di aggiornare i tuoi valori Helm):

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: librechat-credentials-env
  namespace: <librechat-chart-namespace>
type: Opaque
stringData:
  CREDS_KEY: <generated value>
  CREDS_IV: <generated value>
  JWT_SECRET: <generated value>
  JWT_REFRESH_SECRET: <generated value>
  MEILI_MASTER_KEY: <generated value>
```

Utilizza valori permanenti e monta lo stesso Secret in ogni replica. Non fare affidamento su credenziali locali al processo o su file system effimeri in Kubernetes: la modifica di questi valori può invalidare le sessioni e rendere illeggibili i record crittografati esistenti.

Il Secret denominato da `global.librechat.existingSecretName` deve esistere prima dell'avvio del container LibreChat. Un Secret mancante o con un nome errato blocca l'avvio del pod invece di ripiegare su credenziali temporanee locali al pod. Il chart non convalida le chiavi al suo interno, quindi assicurati che contenga `CREDS_KEY`, `CREDS_IV`, `JWT_SECRET` e `JWT_REFRESH_SECRET`.

Imposta `global.librechat.existingSecretName: ""` solo quando ogni credenziale di LibreChat viene fornita in un altro modo. `librechat.configEnv` accetta valori stringa per i dati della ConfigMap, mentre `global.librechat.env` accetta voci di ambiente Kubernetes come `valueFrom.secretKeyRef`. Per la produzione, preferisci i riferimenti ai Secret.

Il Meilisearch in bundle ha una dipendenza separata su `meilisearch.auth.existingMasterKeySecret`, che ha come valore predefinito `librechat-credentials-env` e deve contenere la stessa `MEILI_MASTER_KEY` fornita a LibreChat. La cancellazione del riferimento al Secret di LibreChat non cancella questo riferimento di Meilisearch. Se il Meilisearch in bundle è disabilitato, configura il servizio di ricerca esterno e le sue credenziali separatamente.
2. Aggiungi a questo stesso secret tutte le chiavi API richieste per i provider LLM:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: librechat-credentials-env
  namespace: <librechat-chart-namespace>
type: Opaque
stringData:
  CREDS_KEY: <same generated value as above>
  CREDS_IV: <same generated value as above>
  JWT_SECRET: <same generated value as above>
  JWT_REFRESH_SECRET: <same generated value as above>
  MEILI_MASTER_KEY: <same generated value as above>
  OPENAI_API_KEY: <your secret value>
```
3. Applica il Secret al Cluster:

Salva il manifest Secret completo come `librechat-credentials.yaml`, utilizzando il namespace previsto, quindi applicalo:

```bash
kubectl apply -f librechat-credentials.yaml
```

4. Indirizza le probe verso gli endpoint dedicati. Le probe predefinite del chart usano `/health`, che restituisce `200` anche quando Redis è inattivo, quindi un pod che non è in grado di autenticare nessuno continua a ricevere traffico. Sovrascrivile nel tuo file dei valori in modo che la readiness segua lo stato di Redis e la liveness no:

```yaml
livenessProbe:
  httpGet:
    path: /livez
    port: 3080
readinessProbe:
  httpGet:
    path: /readyz
    port: 3080
```

Vedi [Controlli di integrità di Redis](/docs/configuration/redis#health-checks) per sapere cosa riporta ciascun endpoint.

## Installa Helm Chart [#install-helm-chart]

Per installare l'helm chart esegui:

`helm install <deployment-name> oci://ghcr.io/librechat-ai/librechat-chart/librechat`

<details>
  <summary>Versione di sviluppo</summary>

Nella directory root del repository, esegui:

`helm install <deployment-name> ./helm/librechat`
</details>

Similmente ad altri Helm chart, esiste un [values file](https://github.com/LibreChat-AI/LibreChat/blob/main/helm/librechat/values.yaml) che delinea le impostazioni predefinite e indica quali opzioni di configurazione possono essere modificate.

Crea un file `values.yaml` popolato con i valori che desideri modificare rispetto a quelli predefiniti.

Installa il chart Helm: `helm install librechat oci://ghcr.io/librechat-ai/librechat-chart/librechat --values <values-override-file>`

Una volta che la release è attiva e il servizio è raggiungibile, segui [Your First Chat](/docs/quick_start/first_chat) per creare un account, aggiungere una chiave API del modello e inviare il tuo primo messaggio.

## Disinstallare l'Helm Chart [#uninstall-the-helm-chart]

Per disinstallare l'Helm Chart: `helm uninstall <deployment-name>`

Esempio: `helm uninstall librechat`

## Aggiornamento alla chart 3.x [#upgrading-to-chart-3x]

Il Chart 3.0.0 abilita per impostazione predefinita l'autenticazione su MongoDB e Redis inclusi. Le password generate restano nei Secret dei subchart e raggiungono LibreChat tramite `secretKeyRef` (`MONGODB_ROOT_PASSWORD`, `REDIS_PASSWORD`), mentre `MONGO_URI` viene composta nel Deployment. Per usare un database proprio, imposta `librechat.configEnv.MONGO_URI` (oppure `REDIS_URI`). Imposta `mongodb.auth.enabled=false` o `redis.auth.enabled=false` solo per ripristinare il comportamento precedente senza autenticazione. Le password root personalizzate devono essere sicure per gli URL, perché vengono inserite in `MONGO_URI`.

Se `MONGO_URI`, `REDIS_URI` o `REDIS_PASSWORD` provengono dal Secret indicato da `global.librechat.existingSecretName`, impostare `librechat.injectBundledCredentials.mongodb=false` (per `MONGO_URI`) oppure `librechat.injectBundledCredentials.redis=false` (per `REDIS_URI` o `REDIS_PASSWORD`). Il chart non può leggere il contenuto di quel Secret e, in caso contrario, i valori generati sovrascriverebbero quelli presenti nel Secret. Le due impostazioni sono indipendenti. Se si mantengono MongoDB o Redis inclusi nel deployment, questi devono usare la stessa password del Secret: indirizzare `mongodb.auth.existingSecret` o `redis.auth.existingSecret` verso di esso, oppure impostare la password corrispondente in `auth`; altrimenti il database conserva la password generata automaticamente e LibreChat non riesce ad autenticarsi. Le credenziali vengono lette all'avvio di ciascun pod, quindi dopo aver ruotato la password di un database occorre riavviare ogni Deployment che la utilizza con `kubectl rollout restart deployment/<release>-librechat`.

### Mantenere le password generate durante gli aggiornamenti [#keeping-the-generated-passwords-across-upgrades]

Con i valori predefiniti, i subchart generano le password al primo install, e il subchart di MongoDB rifiuta gli upgrade successivi che non le ripetono ("PASSWORDS ERROR"). Leggi i valori correnti e passali con ogni `helm upgrade`, oppure imposta `mongodb.auth.existingSecret` e `redis.auth.existingSecret` in modo che puntino a Secret che gestisci tu:

```bash
kubectl get secret <release>-mongodb -o jsonpath='{.data.mongodb-root-password}' | base64 -d
helm upgrade <release> ... --set-string mongodb.auth.rootPassword=<password>
```

Redis richiede `--set-string redis.auth.password=<password>` allo stesso modo (`redis-password` nel Secret `<release>-redis`). Con `mongodb.architecture=replicaset`, mantieni anche la chiave del replica set: leggi `mongodb-replica-set-key` dallo stesso Secret e passala come `--set-string mongodb.auth.replicaSetKey=<key>`.

### Aggiornamento da un MongoDB incluso senza autenticazione [#upgrading-from-an-unauthenticated-bundled-mongodb]

Le release installate prima che l'autenticazione diventasse l'impostazione predefinita dispongono di un volume dati senza utente root, e i dati persistenti non vengono reinizializzati durante l'aggiornamento; di conseguenza LibreChat non può autenticarsi dopo `helm upgrade`. Scegli uno dei due percorsi:

1. Mantieni il comportamento precedente: `--set mongodb.auth.enabled=false`.
2. Crea prima l'utente root. Sul pod in esecuzione prima dell'aggiornamento, esegui `mongosh admin --eval 'db.createUser({user: "<rootUser>", pwd: "<password>", roles: ["root"]})'` (`<rootUser>` è `mongodb.auth.rootUser`, `root` per impostazione predefinita). Quindi esegui l'aggiornamento con `--set-string mongodb.auth.rootPassword=<password>` (compatibile con URL) e lo stesso `mongodb.auth.rootUser` se lo hai modificato. Mantieni la stessa password in ogni aggiornamento successivo. Un aggiornamento senza `mongodb.auth.rootPassword` viene rifiutato dal sottochart di MongoDB ("PASSWORDS ERROR") perché non esiste ancora alcun Secret.

Il grafico non è in grado di rilevare questo caso in fase di rendering, quindi `NOTES.txt` visualizza un avviso a ogni aggiornamento con l'autenticazione abilitata.

### Ingress TLS [#ingress-tls]

L'ingress è abilitato per impostazione predefinita. Imposta `ingress.tls` (un `secretName` e `hosts`) per qualsiasi installazione non locale; `helm install` stampa un avviso per ogni host dell'ingress che non è coperto da alcuna voce di `ingress.tls`.

### URL del pannello di amministrazione [#admin-panel-url]

Imposta `librechat.adminPanelUrl` sull'URL base del pannello di amministrazione utilizzato per i reindirizzamenti OAuth/SSO. Può includere un percorso, ma non deve terminare con un `/`. Vedi [Pannello di amministrazione](/docs/features/admin_panel).

```yaml
librechat:
  adminPanelUrl: https://admin.example.com/admin
```

## Migrazione da 1.x a 2.x [#migrate-1x---2x]
Se hai utilizzato il chart prima della versione 2.x, potresti dover aggiornare la struttura `value`.

1. Sposta la configurazione in librechat.configEnv:
```diff
- env:
-     ALLOW_EMAIL_LOGIN: "true"
-     ALLOW_REGISTRATION: "true"
+ librechat:
+   configEnv:
+     ALLOW_REGISTRATION: "true"
+     ALLOW_EMAIL_LOGIN: "true"
```

2. Consolidare tutti i valori Secret in un unico Secret come descritto nel [Passaggio di configurazione 1](#configuration).
3. Per utilizzare un'istanza MongoDB esterna, fare riferimento al [values file](https://github.com/LibreChat-AI/LibreChat/blob/main/helm/librechat/values.yaml) del Chart, disattivare i componenti di conseguenza e modificare l'FQDN dell'istanza MongoDB. Questa operazione è consigliata se i dati esistono già in questa istanza MongoDB gestita esternamente.
