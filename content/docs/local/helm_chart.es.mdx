Por favor, siga esta guía para desplegar LibreChat en Kubernetes usando Helm, ajustándola según sea necesario para su caso de uso específico. Otros Helm charts aportados por la comunidad se enumeran a continuación en la sección [Community Helm Charts](#community-helm-charts).

## Requisitos previos [#prerequisites]

* Un clúster de Kubernetes en ejecución
* Instalaciones _locales_ de `kubectl` y Helm

## Configuración [#configuration]

1. Utilice el [Credentials Generator](/toolkit/creds_generator) para generar valores seguros para `CREDS_KEY`, `CREDS_IV`, `JWT_SECRET`, `JWT_REFRESH_SECRET` y `MEILI_MASTER_KEY`.
Colóquelos en un Kubernetes Secret como este (si cambia el nombre del secret, recuerde actualizar sus valores de Helm):

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: librechat-credentials-env
  namespace: <librechat-chart-namespace>
type: Opaque
stringData:
  CREDS_KEY: <generated value>
  CREDS_IV: <generated value>
  JWT_SECRET: <generated value>
  JWT_REFRESH_SECRET: <generated value>
  MEILI_MASTER_KEY: <generated value>
```

Utilice valores permanentes y monte el mismo Secret en cada réplica. No dependa de credenciales locales del proceso o del sistema de archivos efímero en Kubernetes: cambiar estos valores puede invalidar sesiones y hacer que los registros cifrados existentes sean ilegibles.

El Secret nombrado por `global.librechat.existingSecretName` debe existir antes de que el contenedor de LibreChat se inicie. Un Secret nombrado faltante o mal escrito bloquea el inicio del pod en lugar de recurrir a credenciales temporales locales del pod. El chart no valida las claves dentro de él, así que asegúrese de que contenga `CREDS_KEY`, `CREDS_IV`, `JWT_SECRET` y `JWT_REFRESH_SECRET`.

Establezca `global.librechat.existingSecretName: ""` solo cuando todas las credenciales de LibreChat se suministren de otra manera. `librechat.configEnv` acepta valores de cadena para datos de ConfigMap, mientras que `global.librechat.env` acepta entradas de entorno de Kubernetes como `valueFrom.secretKeyRef`. Prefiera las referencias a Secret para producción.

El Meilisearch incluido tiene una dependencia separada en `meilisearch.auth.existingMasterKeySecret`, que por defecto es `librechat-credentials-env` y debe contener la misma `MEILI_MASTER_KEY` proporcionada a LibreChat. Borrar la referencia del Secret de LibreChat no borra esta referencia de Meilisearch. Si el Meilisearch incluido está desactivado, configure el servicio de búsqueda externo y sus credenciales por separado.

2. Añada a este mismo secret cualquier clave de API necesaria para los proveedores de LLM:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: librechat-credentials-env
  namespace: <librechat-chart-namespace>
type: Opaque
stringData:
  CREDS_KEY: <same generated value as above>
  CREDS_IV: <same generated value as above>
  JWT_SECRET: <same generated value as above>
  JWT_REFRESH_SECRET: <same generated value as above>
  MEILI_MASTER_KEY: <same generated value as above>
  OPENAI_API_KEY: <your secret value>
```
3. Aplicar el Secret al Cluster:

Guarde el manifiesto Secret completo como `librechat-credentials.yaml`, utilizando el namespace previsto, y luego aplíquelo:

```bash
kubectl apply -f librechat-credentials.yaml
```

4. Apunta las sondas a los endpoints dedicados. Las sondas predeterminadas del chart usan `/health`, que sigue devolviendo `200` mientras Redis está caído, por lo que un pod que no puede autenticar a nadie seguirá recibiendo tráfico. Sobrescríbelas en tu archivo de valores para que la readiness dependa de Redis y la liveness no:

```yaml
livenessProbe:
  httpGet:
    path: /livez
    port: 3080
readinessProbe:
  httpGet:
    path: /readyz
    port: 3080
```

Consulta [Comprobaciones de estado de Redis](/docs/configuration/redis#health-checks) para ver lo que informa cada endpoint.

## Instalar Helm Chart [#install-helm-chart]

Para instalar el helm chart, ejecuta:

`helm install <deployment-name> oci://ghcr.io/librechat-ai/librechat-chart/librechat`

<details>
  <summary>Versión de desarrollo</summary>

En el directorio raíz del repositorio, ejecuta:

`helm install <deployment-name> ./helm/librechat`
</details>

Al igual que otros Helm charts, existe un [values file](https://github.com/LibreChat-AI/LibreChat/blob/main/helm/librechat/values.yaml) que describe la configuración predeterminada e indica qué opciones de configuración se pueden modificar.

Cree un archivo `values.yaml` completado con los valores que desea modificar a partir de los predeterminados.

Instala el chart de Helm: `helm install librechat oci://ghcr.io/librechat-ai/librechat-chart/librechat --values <values-override-file>`

Una vez que la versión esté activa y el servicio sea accesible, sigue [Tu primer chat](/docs/quick_start/first_chat) para crear una cuenta, añadir una clave de API de modelo y enviar tu primer mensaje.

## Desinstalar el Helm Chart [#uninstall-the-helm-chart]

Para desinstalar el Helm Chart: `helm uninstall <deployment-name>`

Ejemplo: `helm uninstall librechat`

## Actualización a chart 3.x [#upgrading-to-chart-3x]

Chart 3.0.0 habilita la autenticación en MongoDB y Redis incluidos por defecto. Sus contraseñas generadas permanecen en los Secrets del subchart y llegan a LibreChat mediante `secretKeyRef` (`MONGODB_ROOT_PASSWORD`, `REDIS_PASSWORD`), y `MONGO_URI` se ensambla en el Deployment. Para usar tu propia base de datos, establece `librechat.configEnv.MONGO_URI` (o `REDIS_URI`). Establece `mongodb.auth.enabled=false` o `redis.auth.enabled=false` solo para restaurar el comportamiento anterior sin autenticación. Las contraseñas de root personalizadas deben ser seguras para URL, porque se colocan en `MONGO_URI`.

Si `MONGO_URI`, `REDIS_URI` o `REDIS_PASSWORD` provienen del Secret indicado en `global.librechat.existingSecretName`, establezca `librechat.injectBundledCredentials.mongodb=false` (para `MONGO_URI`) o `librechat.injectBundledCredentials.redis=false` (para `REDIS_URI` o `REDIS_PASSWORD`). El chart no puede ver el contenido de ese Secret, y de lo contrario los valores generados sobrescribirían el suyo. Ambas configuraciones son independientes. Si mantiene MongoDB o Redis incluidos, deben usar la misma contraseña que su Secret: apunte `mongodb.auth.existingSecret` o `redis.auth.existingSecret` a él, o establezca la contraseña correspondiente en `auth`; de lo contrario, la base de datos conserva su contraseña generada y LibreChat no podrá autenticarse. Las credenciales se leen cuando se inicia un pod, así que después de rotar la contraseña de una base de datos, reinicie cada Deployment que la lea con `kubectl rollout restart deployment/<release>-librechat`.

### Manteniendo las contraseñas generadas durante las actualizaciones [#keeping-the-generated-passwords-across-upgrades]

Con los valores predeterminados, los subcharts generan las contraseñas en la primera instalación, y el subchart de MongoDB rechaza las actualizaciones posteriores que no las repitan ("PASSWORDS ERROR"). Lee los valores actuales y pásalos en cada `helm upgrade`, o apunta `mongodb.auth.existingSecret` y `redis.auth.existingSecret` a Secrets que tú gestiones:

```bash
kubectl get secret <release>-mongodb -o jsonpath='{.data.mongodb-root-password}' | base64 -d
helm upgrade <release> ... --set-string mongodb.auth.rootPassword=<password>
```

Redis necesita `--set-string redis.auth.password=<password>` de la misma manera (`redis-password` en el Secret `<release>-redis`). Con `mongodb.architecture=replicaset`, también debes conservar la clave del conjunto de réplicas: lee `mongodb-replica-set-key` del mismo Secret y pásala como `--set-string mongodb.auth.replicaSetKey=<key>`.

### Actualización desde un MongoDB incluido sin autenticación [#upgrading-from-an-unauthenticated-bundled-mongodb]

Las versiones instaladas antes de que la autenticación se convirtiera en la opción predeterminada tienen un volumen de datos sin usuario root, y los datos persistidos no se reinicializan durante la actualización, por lo que LibreChat no puede autenticarse después de `helm upgrade`. Elija una de las siguientes opciones:

1. Mantén el comportamiento anterior: `--set mongodb.auth.enabled=false`.
2. Crea primero el usuario root. En el pod en ejecución previo a la actualización, ejecuta `mongosh admin --eval 'db.createUser({user: "<rootUser>", pwd: "<password>", roles: ["root"]})'` (`<rootUser>` es `mongodb.auth.rootUser`, que por defecto es `root`). Después, actualiza con `--set-string mongodb.auth.rootPassword=<password>` (apta para URL) y el mismo `mongodb.auth.rootUser` si lo has cambiado. Mantén la misma contraseña en todas las actualizaciones posteriores. Una actualización sin `mongodb.auth.rootPassword` será rechazada por el subchart de MongoDB ("PASSWORDS ERROR") porque todavía no existe ningún Secret.

El gráfico no puede detectar este caso en el momento de la renderización, por lo que `NOTES.txt` muestra un aviso en cada actualización con la autenticación habilitada.

### Ingress TLS [#ingress-tls]

El ingress está habilitado de forma predeterminada. Configura `ingress.tls` (un `secretName` y `hosts`) para cualquier instalación que no sea local; `helm install` muestra una advertencia por cada host de ingress que no esté cubierto por ninguna entrada de `ingress.tls`.

### URL del panel de administración [#admin-panel-url]

Establezca `librechat.adminPanelUrl` en la URL base del panel de administración que se utiliza para las redirecciones de OAuth/SSO. Puede incluir una ruta, pero no debe terminar con una `/`. Consulte [Panel de administración](/docs/features/admin_panel).

```yaml
librechat:
  adminPanelUrl: https://admin.example.com/admin
```

## Migrar 1.x -> 2.x [#migrate-1x---2x]
Si utilizó el chart antes de la versión 2.x, es posible que deba actualizar la estructura de `value`.

1. Mover la configuración a librechat.configEnv:
```diff
- env:
-     ALLOW_EMAIL_LOGIN: "true"
-     ALLOW_REGISTRATION: "true"
+ librechat:
+   configEnv:
+     ALLOW_REGISTRATION: "true"
+     ALLOW_EMAIL_LOGIN: "true"
```

2. Consolide todos los valores de Secret en un único Secret como se describe en [Configuration Step 1](#configuration).
3. Para aprovechar una instancia de MongoDB externa, consulte el [values file](https://github.com/LibreChat-AI/LibreChat/blob/main/helm/librechat/values.yaml) del Chart, desactive los componentes correspondientes y cambie el FQDN de la instancia de MongoDB. Esto se recomienda si ya existen datos en esta instancia de MongoDB gestionada externamente.
