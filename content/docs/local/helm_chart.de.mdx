Bitte befolge diese Anleitung, um LibreChat mit Helm auf Kubernetes bereitzustellen, und passe sie bei Bedarf an deinen spezifischen Anwendungsfall an. Weitere von der Community bereitgestellte Helm Charts sind unten im Abschnitt [Community Helm Charts](#community-helm-charts) aufgeführt.

## Voraussetzungen [#prerequisites]

* Ein laufender Kubernetes-Cluster
* _Lokale_ Installationen von `kubectl` und Helm

## Konfiguration [#configuration]

1. Verwenden Sie den [Credentials Generator](/toolkit/creds_generator), um sichere Werte für `CREDS_KEY`, `CREDS_IV`, `JWT_SECRET`, `JWT_REFRESH_SECRET` und `MEILI_MASTER_KEY` zu generieren.
Platzieren Sie diese wie folgt in einem Kubernetes Secret (wenn Sie den Namen des Secrets ändern, denken Sie daran, Ihre Helm-Werte zu aktualisieren):

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: librechat-credentials-env
  namespace: <librechat-chart-namespace>
type: Opaque
stringData:
  CREDS_KEY: <generated value>
  CREDS_IV: <generated value>
  JWT_SECRET: <generated value>
  JWT_REFRESH_SECRET: <generated value>
  MEILI_MASTER_KEY: <generated value>
```

Verwenden Sie permanente Werte und mounten Sie dasselbe Secret in jedes Replikat. Verlassen Sie sich in Kubernetes nicht auf prozesslokale oder ephemere Dateisystem-Anmeldeinformationen: Das Ändern dieser Werte kann Sitzungen ungültig machen und bestehende verschlüsselte Datensätze unlesbar machen.

Das unter `global.librechat.existingSecretName` angegebene Secret muss existieren, bevor der LibreChat-Container startet. Ein fehlendes oder falsch geschriebenes Secret blockiert den Pod-Start, anstatt auf temporäre, Pod-lokale Anmeldedaten zurückzugreifen. Das Chart validiert die darin enthaltenen Schlüssel nicht; stellen Sie daher sicher, dass es `CREDS_KEY`, `CREDS_IV`, `JWT_SECRET` und `JWT_REFRESH_SECRET` enthält.

Setzen Sie `global.librechat.existingSecretName: ""` nur dann, wenn alle LibreChat-Anmeldedaten auf andere Weise bereitgestellt werden. `librechat.configEnv` akzeptiert String-Werte für ConfigMap-Daten, während `global.librechat.env` Kubernetes-Umgebungseinträge wie `valueFrom.secretKeyRef` akzeptiert. Bevorzugen Sie Secret-Referenzen für die Produktion.

Das gebündelte Meilisearch hat eine separate Abhängigkeit von `meilisearch.auth.existingMasterKeySecret`, die standardmäßig auf `librechat-credentials-env` eingestellt ist und denselben `MEILI_MASTER_KEY` enthalten muss, der auch für LibreChat bereitgestellt wurde. Das Löschen der LibreChat-Secret-Referenz löscht diese Meilisearch-Referenz nicht. Wenn das gebündelte Meilisearch deaktiviert ist, konfigurieren Sie den externen Suchdienst und dessen Anmeldedaten separat.
2. Fügen Sie demselben Secret alle erforderlichen API-Schlüssel für LLM-Anbieter hinzu:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: librechat-credentials-env
  namespace: <librechat-chart-namespace>
type: Opaque
stringData:
  CREDS_KEY: <same generated value as above>
  CREDS_IV: <same generated value as above>
  JWT_SECRET: <same generated value as above>
  JWT_REFRESH_SECRET: <same generated value as above>
  MEILI_MASTER_KEY: <same generated value as above>
  OPENAI_API_KEY: <your secret value>
```
3. Wende das Secret auf den Cluster an:

Speichern Sie das vollständige Secret-Manifest als `librechat-credentials.yaml` unter Verwendung des vorgesehenen Namespace und wenden Sie es dann an:

```bash
kubectl apply -f librechat-credentials.yaml
```

4. Richte die Probes auf die dedizierten Endpunkte aus. Die Standard-Probes des Charts verwenden `/health`, das auch bei ausgefallenem Redis weiterhin `200` liefert. Dadurch erhält ein Pod, der niemanden anmelden kann, weiterhin Traffic. Überschreibe sie in deiner Values-Datei, sodass die Readiness dem Redis-Status folgt und die Liveness nicht:

```yaml
livenessProbe:
  httpGet:
    path: /livez
    port: 3080
readinessProbe:
  httpGet:
    path: /readyz
    port: 3080
```

Siehe [Redis-Health-Checks](/docs/configuration/redis#health-checks) für Informationen darüber, was jeder Endpunkt meldet.

## Helm Chart installieren [#install-helm-chart]

Um das helm chart zu installieren, führen Sie Folgendes aus:

`helm install <deployment-name> oci://ghcr.io/librechat-ai/librechat-chart/librechat`

<details>
  <summary>Entwicklungsversion</summary>

Führen Sie im Stammverzeichnis des Repositories Folgendes aus:

`helm install <deployment-name> ./helm/librechat`
</details>

Ähnlich wie bei anderen Helm-Charts gibt es eine [values file](https://github.com/LibreChat-AI/LibreChat/blob/main/helm/librechat/values.yaml), die die Standardeinstellungen beschreibt und angibt, welche Konfigurationsoptionen geändert werden können.

Erstellen Sie eine `values.yaml`-Datei, die mit den Werten gefüllt ist, die Sie gegenüber den Standardwerten ändern möchten.

Installiere das Helm-Chart: `helm install librechat oci://ghcr.io/librechat-ai/librechat-chart/librechat --values <values-override-file>`

Sobald das Release läuft und der Dienst erreichbar ist, folge [Dein erster Chat](/docs/quick_start/first_chat), um ein Konto zu erstellen, einen Modell-API-Schlüssel hinzuzufügen und deine erste Nachricht zu senden.

## Deinstallieren des Helm Charts [#uninstall-the-helm-chart]

Um das Helm Chart zu deinstallieren: `helm uninstall <deployment-name>`

Beispiel: `helm uninstall librechat`

## Upgrade auf Chart 3.x [#upgrading-to-chart-3x]

Chart 3.0.0 aktiviert die Authentifizierung für das mitgelieferte MongoDB und Redis standardmäßig. Die generierten Passwörter verbleiben in den Secrets der Subchart und werden über `secretKeyRef` (`MONGODB_ROOT_PASSWORD`, `REDIS_PASSWORD`) an LibreChat übergeben, während `MONGO_URI` im Deployment zusammengesetzt wird. Um eine eigene Datenbank zu verwenden, setzen Sie `librechat.configEnv.MONGO_URI` (oder `REDIS_URI`). Setzen Sie `mongodb.auth.enabled=false` oder `redis.auth.enabled=false` nur, wenn Sie das alte, nicht authentifizierte Verhalten wiederherstellen möchten. Benutzerdefinierte Root-Passwörter müssen URL-sicher sein, da sie in `MONGO_URI` eingefügt werden.

Wenn `MONGO_URI`, `REDIS_URI` oder `REDIS_PASSWORD` aus dem Secret stammen, das durch `global.librechat.existingSecretName` benannt ist, setzen Sie `librechat.injectBundledCredentials.mongodb=false` (für `MONGO_URI`) bzw. `librechat.injectBundledCredentials.redis=false` (für `REDIS_URI` oder `REDIS_PASSWORD`). Der Chart kann den Inhalt dieses Secrets nicht einsehen, und die generierten Werte würden es andernfalls überschreiben. Die beiden Einstellungen sind voneinander unabhängig. Wenn Sie das gebündelte MongoDB oder Redis beibehalten, muss es dasselbe Passwort wie Ihr Secret verwenden: Verweisen Sie `mongodb.auth.existingSecret` oder `redis.auth.existingSecret` darauf oder setzen Sie das entsprechende `auth`-Passwort, andernfalls behält die Datenbank ihr generiertes Passwort bei und LibreChat kann sich nicht authentifizieren. Die Zugangsdaten werden beim Start eines Pods gelesen. Nach dem Rotieren eines Datenbankpassworts müssen Sie daher jedes Deployment neu starten, das es verwendet, mit `kubectl rollout restart deployment/<release>-librechat`.

### Beibehaltung der generierten Passwörter bei Upgrades [#keeping-the-generated-passwords-across-upgrades]

Mit den Standardwerten erzeugen die Subcharts beim ersten Install die Passwörter, und das MongoDB-Subchart verweigert spätere Upgrades, die diese nicht erneut angeben ("PASSWORDS ERROR"). Lies die aktuellen Werte aus und übergib sie bei jedem `helm upgrade`, oder verweise `mongodb.auth.existingSecret` und `redis.auth.existingSecret` auf Secrets, die du selbst verwaltest:

```bash
kubectl get secret <release>-mongodb -o jsonpath='{.data.mongodb-root-password}' | base64 -d
helm upgrade <release> ... --set-string mongodb.auth.rootPassword=<password>
```

Redis benötigt `--set-string redis.auth.password=<password>` auf die gleiche Weise (`redis-password` im `<release>-redis` Secret). Mit `mongodb.architecture=replicaset` muss zusätzlich der Replica-Set-Schlüssel erhalten bleiben: Lesen Sie `mongodb-replica-set-key` aus demselben Secret und übergeben Sie ihn als `--set-string mongodb.auth.replicaSetKey=<key>`.

### Aktualisierung von einer nicht authentifizierten, mitgelieferten MongoDB [#upgrading-from-an-unauthenticated-bundled-mongodb]

Versionen, die vor der Einführung der Authentifizierung als Standard installiert wurden, verfügen über ein Datenvolume ohne Root-Benutzer. Die gespeicherten Daten werden beim Upgrade nicht neu initialisiert, weshalb sich LibreChat nach `helm upgrade` nicht authentifizieren kann. Wählen Sie einen der folgenden Wege:

1. Das alte Verhalten beibehalten: `--set mongodb.auth.enabled=false`.
2. Erstellen Sie zuerst den Root-Benutzer. Führen Sie auf dem laufenden Pod vor dem Upgrade `mongosh admin --eval 'db.createUser({user: "<rootUser>", pwd: "<password>", roles: ["root"]})'` aus (`<rootUser>` ist `mongodb.auth.rootUser`, standardmäßig `root`). Führen Sie anschließend das Upgrade mit `--set-string mongodb.auth.rootPassword=<password>` (URL-sicher) und dem gleichen `mongodb.auth.rootUser` aus, falls Sie diesen geändert haben. Verwenden Sie bei allen späteren Upgrades dasselbe Passwort. Ein Upgrade ohne `mongodb.auth.rootPassword` wird vom MongoDB-Subchart abgelehnt („PASSWORDS ERROR“), da noch kein Secret existiert.

Das Diagramm kann diesen Fall zur Renderzeit nicht erkennen. Daher gibt `NOTES.txt` bei jedem Upgrade mit aktivierter Authentifizierung einen Hinweis aus.

### Ingress TLS [#ingress-tls]

Der Ingress ist standardmäßig aktiviert. Setze `ingress.tls` (einen `secretName` und `hosts`) für jede nicht-lokale Installation; `helm install` gibt für jeden Ingress-Host, den kein `ingress.tls`-Eintrag abdeckt, eine Warnung aus.

### Admin-Panel-URL [#admin-panel-url]

Setze `librechat.adminPanelUrl` auf die Basis-URL des Admin-Panels, die für OAuth/SSO-Weiterleitungen verwendet wird. Sie kann einen Pfad enthalten, darf aber nicht mit einem nachgestellten `/` enden. Siehe [Admin Panel](/docs/features/admin_panel).

```yaml
librechat:
  adminPanelUrl: https://admin.example.com/admin
```

## Migration von 1.x -> 2.x [#migrate-1x---2x]
Wenn Sie das Chart vor der Version 2.x verwendet haben, müssen Sie möglicherweise die `value`-Struktur aktualisieren.

1. Verschiebe die Konfiguration nach librechat.configEnv:
```diff
- env:
-     ALLOW_EMAIL_LOGIN: "true"
-     ALLOW_REGISTRATION: "true"
+ librechat:
+   configEnv:
+     ALLOW_REGISTRATION: "true"
+     ALLOW_EMAIL_LOGIN: "true"
```

2. Fassen Sie alle Secret-Werte zu einem einzigen Secret zusammen, wie in [Konfigurationsschritt 1](#configuration) beschrieben.
3. Um eine externe MongoDB-Instanz zu nutzen, beziehen Sie sich auf die [values file](https://github.com/LibreChat-AI/LibreChat/blob/main/helm/librechat/values.yaml) des Charts, deaktivieren Sie die entsprechenden Komponenten und ändern Sie den FQDN der Mongodb-Instanz. Dies wird empfohlen, wenn bereits Daten in dieser extern verwalteten MongoDB-Instanz vorhanden sind.
