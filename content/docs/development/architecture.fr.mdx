## Structure du Monorepo [#monorepo-structure]

LibreChat est organisé sous forme de monorepo avec des limites d'espace de travail clairement définies :

| Espace de travail | Langage | Côté | Dépendance | Objectif |
| ----------------- | ------- | ---- | ---------- | -------- |
| `/api` | JS (legacy) | Backend | `packages/api`, `packages/data-schemas`, `packages/data-provider`, `@librechat/agents` | Serveur Express — minimiser les modifications ici |
| `/packages/api` | **TypeScript** | Backend | `packages/data-schemas`, `packages/data-provider` | Le nouveau code backend se trouve ici (TS uniquement, consommé par `/api`) |
| `/packages/data-schemas` | TypeScript | Backend | `packages/data-provider` | Modèles et schémas de base de données, partageables entre les projets backend |
| `/packages/data-provider` | TypeScript | Partagé | — | Types d'API partagés, points de terminaison, service de données — utilisé à la fois par le frontend et le backend |
| `/client` | TypeScript/React | Frontend | `packages/data-provider`, `packages/client` | SPA frontend |
| `/packages/client` | TypeScript | Frontend | `packages/data-provider` | Utilitaires frontend partagés |
| `/packages/chat` | TypeScript | Frontend | `packages/data-provider`, `packages/client` | `@librechat/chat` : état du chat, transport et composants de messages en cours de transfert depuis `/client` ; n'importe jamais l'application |

### Principes clés [#key-principles]

- **Tout nouveau code backend doit être en TypeScript** dans `/packages/api`.
- Gardez les changements dans `/api` au strict minimum — de légers wrappers JS appelant `/packages/api`.
- La logique partagée spécifique à la base de données se trouve dans `/packages/data-schemas`.
- La logique API partagée entre le frontend et le backend (endpoints, types, data-service) se trouve dans `/packages/data-provider`.

### Construction et installation [#build-and-install]

| Commande | Objectif |
| ----------------------------- | ---------------------------------------------------------------------------------- |
| `npm run smart-reinstall` | Installe les dépendances (si le lockfile a changé) et compile via Turborepo |
| `npm run reinstall` | Installation propre après un changement de versions de Node/npm ou lorsque l'état des dépendances est suspect |
| `npm run build` | Compile tout le code compilé via Turborepo (en parallèle, avec cache) |
| `npm run frontend` | Compile tout le code compilé séquentiellement (solution de repli héritée) |
| `npm run build:data-provider` | Recompile `packages/data-provider` après des modifications |
| `npm run backend` | Démarre le serveur backend |
| `npm run backend:dev` | Démarre le backend avec surveillance des fichiers (développement) |
| `npm run frontend:dev` | Démarre le serveur de développement frontend avec HMR (port 3090, nécessite que le backend soit en cours d'exécution) |

- Node.js : `v24.22.1`
- npm : `v11.13.0`
- Base de données : MongoDB
- Le backend s'exécute sur `http://localhost:3080/` ; le serveur de développement frontend sur `http://localhost:3090/`

## Compatibilité du schéma partagé et des composants [#shared-schema-and-component-compatibility]

Les packages partagés `v0.8.9-rc1` utilisent Zod 4. Les consommateurs qui composent des schémas de `librechat-data-provider` doivent utiliser des API compatibles avec Zod 4 et déduire les types d'entrée et de sortie à partir du schéma exporté, plutôt que de s'appuyer sur les éléments internes de Zod 3. Reconstruisez les consommateurs de packages personnalisés ensemble ; forcer Zod 3 par le biais d'une surcharge n'est pas une voie de compatibilité.

Le package client n'exporte plus les contrôles hérités `Select`, `SelectDropDown`, `Dialog`, `DialogTemplate` ou `DropdownMenu` de Radix. Utilisez les sélecteurs basés sur Dropdown et les primitives de dialogue maintenus, utilisés par les appelants actuels de LibreChat. Consultez le [guide de mise à niveau](/docs/configuration/upgrade#shared-package-compatibility).
