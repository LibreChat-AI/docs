## Estrutura do Monorepo [#monorepo-structure]

O LibreChat é organizado como um monorepo com limites de workspace claramente definidos:

| Workspace | Linguagem | Lado | Dependência | Finalidade |
| --- | --- | --- | --- | --- |
| `/api` | JS (legado) | Backend | `packages/api`, `packages/data-schemas`, `packages/data-provider`, `@librechat/agents` | Servidor Express — minimizar alterações aqui |
| `/packages/api` | **TypeScript** | Backend | `packages/data-schemas`, `packages/data-provider` | O novo código backend fica aqui (somente TS, consumido por `/api`) |
| `/packages/data-schemas` | TypeScript | Backend | `packages/data-provider` | Modelos/schemas de banco de dados, compartilháveis entre projetos backend |
| `/packages/data-provider` | TypeScript | Compartilhado | — | Tipos de API compartilhados, endpoints, data-service — usado tanto pelo frontend quanto pelo backend |
| `/client` | TypeScript/React | Frontend | `packages/data-provider`, `packages/client` | SPA frontend |
| `/packages/client` | TypeScript | Frontend | `packages/data-provider` | Utilitários compartilhados do frontend |
| `/packages/chat` | TypeScript | Frontend | `packages/data-provider`, `packages/client` | `@librechat/chat`: estado de chat, transporte e componentes de mensagem que estão sendo movidos para fora de `/client`; nunca importa o aplicativo |

### Princípios Fundamentais [#key-principles]

- **Todo novo código de backend deve ser em TypeScript** em `/packages/api`.
- Mantenha as alterações em `/api` no mínimo absoluto — wrappers JS simples chamando `/packages/api`.
- A lógica compartilhada específica do banco de dados pertence a `/packages/data-schemas`.
- A lógica de API compartilhada entre frontend/backend (endpoints, types, data-service) pertence a `/packages/data-provider`.

### Build e Instalação [#build-and-install]

| Comando | Finalidade |
| ----------------------------- | ---------------------------------------------------------------------------------- |
| `npm run smart-reinstall` | Instala as dependências (se o lockfile tiver sido alterado) e compila via Turborepo |
| `npm run reinstall` | Instalação limpa após alterar as versões do Node/npm ou quando o estado das dependências for suspeito |
| `npm run build` | Compila todo o código compilado via Turborepo (em paralelo, com cache) |
| `npm run frontend` | Compila todo o código compilado sequencialmente (fallback legado) |
| `npm run build:data-provider` | Recompila `packages/data-provider` após alterações |
| `npm run backend` | Inicia o servidor backend |
| `npm run backend:dev` | Inicia o backend com monitoramento de arquivos (desenvolvimento) |
| `npm run frontend:dev` | Inicia o servidor de desenvolvimento do frontend com HMR (porta 3090, requer o backend em execução) |

- Node.js: `v24.22.1`
- npm: `v11.13.0`
- Banco de dados: MongoDB
- O backend roda em `http://localhost:3080/`; o servidor de desenvolvimento do frontend em `http://localhost:3090/`

## Compatibilidade de Schema e Componentes Compartilhados [#shared-schema-and-component-compatibility]

O pacote compartilhado `v0.8.9-rc1` usa o Zod 4. Os consumidores que compõem schemas do `librechat-data-provider` devem usar APIs compatíveis com o Zod 4 e inferir os tipos de entrada/saída a partir do schema exportado, em vez de depender de internals do Zod 3. Recompile os consumidores de pacotes personalizados em conjunto; forçar o Zod 3 por meio de um override não é um caminho de compatibilidade.

O pacote do cliente não exporta mais os controles legados `Select`, `SelectDropDown`, `Dialog`, `DialogTemplate` ou `DropdownMenu` do Radix. Use os seletores baseados em Dropdown mantidos e os primitivos de diálogo usados pelos chamadores atuais do LibreChat. Consulte o [guia de atualização](/docs/configuration/upgrade#shared-package-compatibility).
