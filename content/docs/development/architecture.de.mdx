## Monorepo-Struktur [#monorepo-structure]

LibreChat ist als Monorepo mit klar definierten Workspace-Grenzen organisiert:

| Arbeitsbereich | Sprache | Seite | Abhängigkeit | Zweck |
| -------------- | ------- | ----- | ------------ | ----- |
| `/api` | JS (Legacy) | Backend | `packages/api`, `packages/data-schemas`, `packages/data-provider`, `@librechat/agents` | Express-Server — Änderungen hier minimieren |
| `/packages/api` | **TypeScript** | Backend | `packages/data-schemas`, `packages/data-provider` | Neuer Backend-Code liegt hier (nur TS, wird von `/api` genutzt) |
| `/packages/data-schemas` | TypeScript | Backend | `packages/data-provider` | Datenbankmodelle/Schemas, über Backend-Projekte hinweg teilbar |
| `/packages/data-provider` | TypeScript | Geteilt | — | Gemeinsame API-Typen, Endpunkte, Data-Service — von Frontend und Backend genutzt |
| `/client` | TypeScript/React | Frontend | `packages/data-provider`, `packages/client` | Frontend-SPA |
| `/packages/client` | TypeScript | Frontend | `packages/data-provider` | Gemeinsame Frontend-Hilfsfunktionen |
| `/packages/chat` | TypeScript | Frontend | `packages/data-provider`, `packages/client` | `@librechat/chat`: Chat-Zustand, Transport und Nachrichtenkomponenten, die aus `/client` ausgelagert werden; importiert niemals die App |

### Grundprinzipien [#key-principles]

- **All new backend code must be TypeScript** in `/packages/api`.
- Halten Sie Änderungen an `/api` auf ein absolutes Minimum — schlanke JS-Wrapper, die `/packages/api` aufrufen.
- Datenbankspezifische gemeinsame Logik gehört in `/packages/data-schemas`.
- Frontend/Backend-geteilte API-Logik (endpoints, types, data-service) gehört in `/packages/data-provider`.

### Erstellen und Installieren [#build-and-install]

| Befehl | Zweck |
| ----------------------------- | ---------------------------------------------------------------------------------- |
| `npm run smart-reinstall` | Abhängigkeiten installieren (falls Lockfile geändert wurde) + Build über Turborepo |
| `npm run reinstall` | Saubere Neuinstallation nach einer Änderung der Node/npm-Versionen oder wenn der Abhängigkeitszustand fragwürdig ist |
| `npm run build` | Alle kompilierten Komponenten über Turborepo bauen (parallel, mit Cache) |
| `npm run frontend` | Alle kompilierten Komponenten nacheinander bauen (veraltete Alternative) |
| `npm run build:data-provider` | `packages/data-provider` nach Änderungen neu bauen |
| `npm run backend` | Backend-Server starten |
| `npm run backend:dev` | Backend mit Dateiüberwachung starten (Entwicklung) |
| `npm run frontend:dev` | Frontend-Entwicklungsserver mit HMR starten (Port 3090, Backend muss laufen) |

- Node.js: `v24.22.1`
- npm: `v11.13.0`
- Datenbank: MongoDB
- Das Backend läuft unter `http://localhost:3080/`; der Frontend-Entwicklungsserver unter `http://localhost:3090/`

## Kompatibilität von gemeinsamem Schema und Komponenten [#shared-schema-and-component-compatibility]

Die gemeinsam genutzten Pakete in `v0.8.9-rc1` verwenden Zod 4. Anwender, die Schemas aus `librechat-data-provider` kombinieren, sollten kompatible Zod-4-APIs verwenden und Eingabe- und Ausgabetypen aus dem exportierten Schema ableiten, anstatt sich auf interne Zod-3-Strukturen zu verlassen. Benutzerdefinierte Paketanwender sollten gemeinsam neu gebaut werden; das Erzwingen von Zod 3 über ein Override ist kein Kompatibilitätsweg.

Das Client-Paket exportiert die veralteten Steuerelemente `Select`, `SelectDropDown`, `Dialog`, `DialogTemplate` oder Radix-`DropdownMenu` nicht mehr. Verwenden Sie stattdessen die gepflegten, auf Dropdown basierenden Auswahlelemente und Dialog-Primitive, die aktuelle LibreChat-Aufrufer nutzen. Siehe den [Upgrade-Leitfaden](/docs/configuration/upgrade#shared-package-compatibility).
